k8s-048: Cluster DNS, search paths, caching and discovery#

Level and prerequisites#

Intermediate; about 120 minutes plus optional supervised host observations. Direct prerequisites: k8s-047. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

Learning objectives#

Draw resolution and connection as separate phases. Design robust service discovery for a client. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

Purpose, vocabulary and mental model#

DNS maps names to records such as IP addresses. Kubernetes cluster DNS creates service records according to namespace and cluster domain. A short name can resolve differently depending on the caller’s namespace and search configuration. A fully qualified service name makes the intended scope clearer.

For a typical cluster domain cluster.local, a Service named api in namespace study has a name like api.study.svc.cluster.local. The cluster domain is configurable, so do not hardcode it as a universal fact in a reusable client. A DNS answer establishes name resolution, not a listening process or healthy application.

Caching affects how quickly clients observe changes. Resolver libraries and applications can cache differently, and long-lived connections can continue using an existing destination without a new DNS lookup. Diagnose the actual client behavior before concluding that a DNS record update should have moved every request immediately.

Mechanism and field-by-field reasoning#

A Pod’s dnsPolicy and dnsConfig influence resolver behavior. Search suffixes and ndots can cause multiple queries for one short-looking name. NetworkPolicy that blocks DNS can break service discovery even when direct IP transport works.

The fixture’s names are synthetic. Optional host observations should inspect the relevant Pod’s resolver and issue a bounded lookup from the intended namespace. Do not use a successful lookup on the laptop as proof of what a Pod’s resolver sees.

Trace the request or control path#

client name -> resolver search rules/cache -> cluster DNS -> Service record
resolved address -> separate TCP connection -> separate HTTP behavior

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

Worked example / walkthrough#

Worked example 1: Expand a namespaced service name#

Assume cluster.local only for this synthetic example.

short from study namespace: api
qualified: api.study
fully qualified: api.study.svc.cluster.local.

Expected observation: The trailing dot makes the name absolute for DNS resolution; actual cluster domain must be known.

Worked example 2: Separate resolution from serving#

These observations can disagree without contradiction.

DNS: api ->10.96.0.20
TCP: connection refused
HTTP: no response available

Expected observation: Name resolution succeeded; the failure is later in the path.

Diagnosis, failure boundaries and common mistakes#

The controlled failure in this chapter is: Diagnose direct-IP success with name failure. Its distinguishing result is Investigate resolver configuration, DNS reachability and policy. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
