## Outcome and mechanism

Recover from expected input failures without concealing programming defects or dropping diagnostics.

An error and a warning are different observations. stop signals an error; warning can report a concern while allowing evaluation to continue. Replacing both with a generic success result would erase information the caller may need. A robust interface states which failures are expected and which should propagate for investigation.

tryCatch can turn an expected error into a structured result. A parser might return list(ok=FALSE, value=NULL, message=...) for an invalid record, while valid records return the same field names with ok=TRUE. The caller can then count and inspect rejected records. Returning zero for every failure is dangerous when zero is also a legitimate measured value.

withCallingHandlers observes a warning while the signaled computation is still active. It can retain the warning and invoke a documented restart to suppress repeated console noise. This is different from an exiting handler that abandons the expression. Only muffle a condition after recording or deliberately handling it; blanket suppression can hide new compatibility or data-quality problems.

Resource cleanup belongs to the function that acquires the resource. on.exit can close a connection or restore an option even when later code errors. In a fresh classroom process, an operating-system cleanup may eventually occur anyway, but reusable functions should not depend on process exit to release files or restore configuration. Keep recoverable input errors separate from silent catches around arbitrary application code.

## Vocabulary

| Term | Meaning |
| --- | --- |
| Error | A condition that interrupts normal evaluation unless handled. |
| Warning | A condition that reports a concern while evaluation may continue. |
| Exiting handler | A handler such as tryCatch that returns control outside the failed expression. |
| Cleanup | Work that must occur when leaving an operation. |

## Read the syntax

tryCatch(expr, error=function(e) ...) handles an error result. conditionMessage extracts its text. withCallingHandlers can record warnings; invokeRestart("muffleWarning") continues after suppressing that recorded warning. on.exit(..., add=TRUE) registers cleanup in the current function.

## Worked examples

### Example 1: A parser returns an explicit rejection

```r
parse_count <- function(text) {
  if (!is.character(text) || length(text) != 1L || is.na(text) || !grepl("^[0-9]+$", text)) stop("count must contain digits", call. = FALSE)
  as.integer(text)
}
safe_count <- function(text) tryCatch(list(ok = TRUE, value = parse_count(text), message = NULL), error = function(e) list(ok = FALSE, value = NULL, message = conditionMessage(e)))
valid <- safe_count("12")
invalid <- safe_count("twelve")
stopifnot(valid$ok, valid$value == 12L, !invalid$ok, is.null(invalid$value))
print(invalid)
```

**Expected observation:** okFALSE with the digit-only diagnostic.

The rejected input remains distinguishable from a valid count of zero. Its diagnostic is retained for the caller.

### Example 2: Record a warning without abandoning its value

```r
warnings_seen <- character()
value <- withCallingHandlers(
  {
    warning("synthetic review notice"); 4
  },
  warning = function(w) {
    warnings_seen <<- c(warnings_seen, conditionMessage(w))
    invokeRestart("muffleWarning")
  }
)
stopifnot(value == 4, identical(warnings_seen, "synthetic review notice"))
print(list(value = value, warnings = warnings_seen))
```

**Expected observation:** Value 4 and one recorded notice.

The calling handler records this known warning and permits the expression to finish. The retained warning remains evidence alongside the value.
