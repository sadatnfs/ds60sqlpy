## Purpose and mental model

A function pointer lets a component accept behavior as data. The function type must match the call interface; casting an incompatible function pointer does not make the call valid. A callback contract also describes when it is invoked, whether it may retain input pointers and how errors are reported. qsort accepts a comparator returning negative, zero or positive according to ordering. Subtracting integers to implement comparison can overflow, so compare relationally instead. Sorting correctness depends on a consistent comparator; a contradictory ordering can invalidate algorithm assumptions even when individual calls compile.

## Vocabulary and concepts

- **Function pointer:** A value designating a function with a particular call type.
- **Callback contract:** The rules for invoking and retaining data passed to a callback.
- **Comparator:** A function defining a consistent ordering relation.

## Syntax anatomy and execution trace

int (*compare)(const void *,const void *) declares a function pointer rather than a function returning a pointer. qsort passes pointers to elements, which the comparator converts to the correct element type. (a>b)-(a<b) yields the required sign without subtracting the values themselves. A separate callback context can carry state when an API provides one; avoid hidden global mutable state for reusable components.

## Worked example / walkthrough

### Worked example 1: Invoke through a function pointer

Assign a doubling function and call it with 4.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int double_value(int value) { return value * 2; }
int compare_ints(const void *left, const void *right) {
  int a = *(const int *)left, b = *(const int *)right;
  return (a > b) - (a < b);
}
bool is_even(int value) { return value % 2 == 0; }
size_t count_if(const int *values, size_t n, bool (*predicate)(int)) {
  size_t count = 0;
  for (size_t i = 0; i < n; i++)
    if (predicate(values[i]))
      count++;
  return count;
}

int main(void) {
  /* Invoke through a function pointer */
  {
    int (*transform)(int) = double_value;
    CHECK(transform(4) == 8);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The result is 8.

The pointer type agrees with the function declaration, so the compiler can check the call.

### Worked example 2: Sort integers safely

Sort 3, 1, 2 with a relational comparator.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int double_value(int value) { return value * 2; }
int compare_ints(const void *left, const void *right) {
  int a = *(const int *)left, b = *(const int *)right;
  return (a > b) - (a < b);
}
bool is_even(int value) { return value % 2 == 0; }
size_t count_if(const int *values, size_t n, bool (*predicate)(int)) {
  size_t count = 0;
  for (size_t i = 0; i < n; i++)
    if (predicate(values[i]))
      count++;
  return count;
}

int main(void) {
  /* Invoke through a function pointer */
  {
    int (*transform)(int) = double_value;
    CHECK(transform(4) == 8);
  }

  /* Sort integers safely */
  {
    int values[] = {3, 1, 2};
    qsort(values, 3, sizeof values[0], compare_ints);
    CHECK(values[0] == 1 && values[1] == 2 && values[2] == 3);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The order becomes 1, 2, 3.

The comparator reports ordering rather than a numeric distance between elements.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
