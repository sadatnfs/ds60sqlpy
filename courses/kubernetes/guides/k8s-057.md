# k8s-057: Headless Services and stateful peer discovery

## Level and prerequisites

Advanced; about 120 minutes plus optional supervised host observations. Direct prerequisites: `k8s-056`. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

## Learning objectives

Draw a stateful peer discovery sequence. Design a stateful replacement check. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

## Purpose, vocabulary and mental model

A headless Service has clusterIP None and does not provide the ordinary virtual-IP load-balancing abstraction. With a selector, DNS can return endpoint addresses so clients discover individual backends. This is useful when an application protocol needs peer identity rather than an anonymous interchangeable service endpoint.

A StatefulSet provides stable Pod identities and ordered-management semantics under its configuration. Stable names do not mean a Pod process never changes, and storage retention does not guarantee application replication or consistency. A replacement Pod can have a new UID while keeping a stable logical name.

Stateful systems often need bootstrap discovery before every peer is ready. publishNotReadyAddresses can alter which endpoints are published, but it also exposes clients to peers that are not ready for ordinary work. Use it only with a protocol that understands the distinction between discovery and serving.

## Mechanism and field-by-field reasoning

The headless Service fixture names the same selector but sets clusterIP to None. Its A/AAAA answers identify Pod addresses directly. There is no virtual-IP proxy translating Service port 80 into targetPort 8080: a client using those addresses must connect to the actual endpoint listener 8080. A client using SRV discovery must honor the returned endpoint port and target. A/AAAA records carry addresses only, so those clients need the listener port from their application configuration. For this fixture, request http://network-study-headless:8080/version; the successful body is ds60-fixture-v1 plus a newline. The named-port SRV query uses _http._tcp.network-study-headless with the actual namespace and cluster domain, and a capable client honors each returned target/port. Merely requesting headless-name:80 would not reach this fixture’s 8080 listener.

A StatefulSet’s serviceName ties its network identity to a governing Service. DNS names depend on Pod identity, service, namespace and cluster domain.

A client receiving several addresses must implement its own selection, retries and protocol semantics. DNS returning three peers does not guarantee a quorum, leader election or replicated data. Those are application properties that require separate evidence.

## Worked example / walkthrough

### Worked example 1: Read the headless setting

This is a manual fixture fragment.

```yaml
clusterIP: None
selector:
  app: network-study
ports:
  - name: http
    port: 80
    targetPort: http
```

**Expected observation:** The Service does not allocate an ordinary ClusterIP virtual destination.

### Worked example 2: Separate logical and process identity

A replacement changes a concrete instance.

```text
logical peer: store-0
before Pod UID:uid-old
after Pod UID:uid-new
retained claim:explicit persistent storage identity
```

**Expected observation:** Stable naming and retained storage are distinct from an unchanged process.

## Diagnosis, failure boundaries and common mistakes

The controlled failure in this chapter is: Diagnose treating headless DNS as automatic load balancing. Its distinguishing result is The client owns address selection and connection behavior. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
