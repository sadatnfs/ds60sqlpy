**Level:** Intermediate | **Prepared runtime:** `python-core`

A language-model request begins before any tensor reaches a device. A browser sends bytes; an HTTP server parses a method, path, headers and body; the application authenticates the caller, validates a schema, selects a model, measures the token budget and reserves capacity. Each boundary can reject work. Calling all of this “the model” hides the places where identity, latency and resource ownership are established.

This chapter assumes ordinary Python dictionaries, JSON and the difference between a function call and a persistent server. Its goal is to trace a request without confusing successful submission with successful inference. The pad runs a deterministic identity mechanism. The separate inference-service workshop provides the real HTTP implementation. Opening this chapter does not start that service.

## The contract before computation

An HTTP request is a proposed action. A successful admission response means the server has retained enough information to identify that action and has accepted responsibility for its bounded execution. It does not mean output already exists. A useful response carries a server request ID, status and a digest of the accepted source. Later events and results carry that same identity.

The workshop accepts a prompt, maximum new-token count, temperature, top-k, seed, stop strings and an idempotency key. Unknown fields are rejected. Booleans are not accepted where integers are required, even though Python treats `bool` as an integer subclass. Nonfinite JSON numbers, duplicate JSON keys, malformed UTF-8 and unsupported control characters are also rejected. These choices remove ambiguous representations before they can influence resource calculations.

Validation has several layers. A byte limit bounds request parsing. A character restriction defines supported text. Tokenization converts the accepted text into the actual model vocabulary. A context check uses that token count, not a guessed characters-per-token ratio. Capacity admission then reserves the prompt plus the requested output budget. Rejecting excessive work before reservation is different from cancelling work that already owns resources.

Let \(P\) be prompt tokens including the beginning-of-sequence marker, \(N\) the requested maximum new tokens, and \(C\) the prepared context limit. The conservative contract is

\[
P+N\leq C.
\]

This reserves space for the entire allowed continuation. The service may finish early because it samples EOS or encounters a stop string; the unused reservation is then released. Increasing `max_new_tokens` therefore affects admission even when a particular prompt usually produces a short response.

Authentication answers who may invoke the service. Authorization answers what that caller may do. Routing selects the reviewed handler and model. These are separate from prompt instructions. Text that says “ignore the queue limit” remains model input; it cannot alter server limits. Conversely, restricting prompt text does not replace authentication or capacity controls.

The local workshop exposes a loopback port, checks its exact Host and browser origin, and requires a private request header for API calls. The token comes from a dedicated local file and never appears in the URL. These controls suit a single-user educational service. They do not implement public multi-tenant identity, TLS termination, organization policy or a production abuse system. Moving the same process onto a public network changes the threat model and requires an explicit design.

## Identity, retry and an unknown outcome

Networks can fail after the server accepts a request but before the client receives the response. A blind retry with a new identity might run the model twice. An idempotency key binds a logical submission to one accepted payload. Repeating the key with the same canonical payload returns the existing request. Repeating it with changed source produces a conflict.

Canonical JSON here sorts object keys and uses consistent separators. Its SHA-256 digest identifies the exact accepted data. It is not a password, encryption scheme or proof that the data is scientifically valid. Include model identity and generation settings in the conceptual request identity: the same prompt under a different tokenizer, checkpoint or sampling policy is a different experiment.

Do not normalize Unicode or trim whitespace silently after calculating a digest. If normalization is part of the product, specify it before hashing and tokenization, preserve the original input separately where appropriate, and test the transformation. Two strings can look alike while having different code points and UTF-8 bytes. That distinction matters for reproducibility and debugging.

## Worked case 1: a lost creation response

The first program case models a request whose initial response could have been lost. The key `request-a` binds to the prompt `model`, a fixed synthetic model version and seed seven. The first admission increments a counter. The second identical submission returns `existing`; the counter remains one. A third submission changes the prompt while retaining the key and is rejected.

The important observation is the counter, not the returned wording. It establishes that reconciliation did not create another execution. In the HTTP project, inspect the actual request ID and `generation_calls` before and after reading completed events. A successful read should leave the latter unchanged. A server restart likewise must not interpret an unfinished saved request as permission to generate again.

This case applies to clients that lose connectivity, users who double-click, reverse proxies that retry selected operations and notebooks that repeat cells. Not every POST is inherently idempotent. The application must define and retain the key binding. A key forgotten immediately after completion cannot protect a later repeated submission.

## Worked case 2: apparently equivalent inputs

The second case compares composed `é` with `e` followed by a combining accent. They display similarly, but the former occupies two UTF-8 bytes and the latter three. Without a declared normalization step, their source digests differ. That is correct for this contract. The example also rejects `True`, a negative seed and an out-of-range integer.

A common failure is to use `isinstance(seed, int)` and accidentally accept `True`. Another is to calculate identity from a prettified prompt while feeding the original bytes to the tokenizer. Both create disagreement between what the receipt claims and what actually ran. The safe order is parse, validate, apply only declared transformations, form the accepted representation, calculate identity, tokenize and admit.

```python
"""Request identity is a contract before it is a model invocation."""

import hashlib
import json


def fingerprint(prompt, version, seed):
    if not isinstance(prompt, str) or not 1 <= len(prompt.encode("utf-8")) <= 100:
        raise ValueError("bounded UTF-8 prompt required")
    if type(seed) is not int or not 0 <= seed < 2**31:
        raise ValueError("bounded integer seed required")
    raw = json.dumps(
        {"prompt": prompt, "model": version, "seed": seed}, sort_keys=True, separators=(",", ":")
    )
    return hashlib.sha256(raw.encode()).hexdigest()


def example_one():
    accepted = {}
    calls = 0

    def create(key, prompt):
        nonlocal calls
        digest = fingerprint(prompt, "synthetic-v1", 7)
        if key in accepted:
            if accepted[key] != digest:
                raise ValueError("idempotency conflict")
            return "existing"
        accepted[key] = digest
        calls += 1
        return "created"

    assert create("request-a", "model") == "created"
    assert create("request-a", "model") == "existing"
    assert calls == 1
    try:
        create("request-a", "changed")
    except ValueError as error:
        print("Conflict:", error)
    else:
        raise AssertionError("Changed source reused a key")
    print("admitted", calls, "digest", accepted["request-a"][:12])


def example_two():
    decomposed = "e\u0301"
    composed = "é"
    assert fingerprint(composed, "synthetic-v1", 7) != fingerprint(decomposed, "synthetic-v1", 7)
    assert len(composed.encode()) == 2 and len(decomposed.encode()) == 3
    for invalid in (True, -1, 2**31):
        try:
            fingerprint("safe", "synthetic-v1", invalid)
        except ValueError:
            print("Rejected seed", repr(invalid))
        else:
            raise AssertionError("Invalid seed accepted")
    print("No implicit Unicode normalization; identities remain source-bound.")


def main():
    example_one()
    example_two()


if __name__ == "__main__":
    main()
```

## Following the real project

In the workshop, `POST /api/requests` creates or reconciles an explicit request. `GET /api/requests/{id}/events` reads its event stream. `POST /api/requests/{id}/cancel` requests cancellation. Reading the record or the retained event suffix does not run the model. These paths are fixed handlers; the client cannot submit a shell command, model filename or arbitrary download URL.

A `202` admission, `429` capacity rejection and terminal inference error answer different questions. Preserve those distinctions in logs and user-facing text. Report the safe error category without returning authentication headers or a full private stack trace. An accepted request that later fails still needs a terminal record and released reservations.

For diagnosis, follow one ID through the accepted source hash, queue event, start event, token events and terminal event. If the ID changes unexpectedly, investigate retry or routing behavior before blaming model nondeterminism. If the hash changes with the same ID, investigate an identity violation rather than averaging the outputs together.

## Interview discussion

**Why is successful HTTP admission insufficient evidence of inference success?** Admission proves that the application accepted bounded work. It may still wait, be cancelled, hit a computation error or fail to save a result. A terminal event and its model/source identity provide stronger evidence.

**What should a client do after an unknown creation outcome?** Reconcile through the original identity or explicitly resubmit the same canonical request with the same idempotency key. It should not automatically create a new key and assume the old request never arrived.

**Can hashing replace validation?** No. A digest faithfully identifies malformed or unsafe input too. Validation defines the accepted language of requests; hashing identifies one member of that language.
