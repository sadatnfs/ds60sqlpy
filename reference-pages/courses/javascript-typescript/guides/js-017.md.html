js-017: HTTP, URLs and JSON boundaries#

Level and prerequisites#

Intermediate, approximately 90 minutes. Direct prerequisites: js-016

Learning objectives#

Explain http status, representation, query encoding, application validation with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: GET /sum with a=2 and b=3 and inspect status, content type and JSON. The final task tests guard arithmetic overflow after parsing.

Purpose and mental model#

HTTP transfers representations between a client and a server using a method, target, headers, status and body. A successful TCP exchange is not the same as a successful application response. fetch resolves for HTTP error statuses such as 404; callers must inspect status or ok. Parsing JSON is another separate stage, and schema validation remains necessary after successful parsing.

A URL parser separates the path, query and origin using defined encoding rules. Constructing query strings by concatenating user text can change the meaning of characters such as ampersand or equals. URLSearchParams encodes values and supports repeated keys. Applications must decide whether repeated parameters are allowed, rejected or combined instead of silently choosing a surprising value.

This lesson runs a real local HTTP server on an ephemeral port bound only to 127.0.0.1. The server handles a tiny read-only sum endpoint. It validates the method, exact parameter multiplicity and safe integer domain before calculating. The client sends actual requests and reads actual responses. The fixture has no authentication, persistence, TLS, rate limiting or public deployment claim. Loopback-only binding and a tiny bounded response make it appropriate for learning the protocol boundary.

Vocabulary and concepts#

HTTP status: The server's protocol-level result code.

Representation: The bytes and media type describing a resource or result.

Query encoding: Escaping values so delimiters retain their structural meaning.

Application validation: Checking parsed values against the endpoint's domain contract.

Syntax anatomy and execution trace#

createServer receives request and response objects. Construct new URL(request.url, a known base) to parse the target. searchParams.getAll lets the handler check duplicate parameters. writeHead selects the status and content type; end finishes the body. server.listen(0, '127.0.0.1') asks the OS for an available local port. fetch uses AbortSignal.timeout as a waiting bound. In finally, closeAllConnections and close ensure the fixture releases its listener even if an assertion fails.

Worked example / walkthrough#

Example A: Request a valid local calculation#

The checks distinguish transport completion, protocol success and representation content. An endpoint can respond successfully at one layer while violating another layer's contract.

import { strict as assert } from 'node:assert';
import { createServer } from 'node:http';

function sendJson(response, status, body, extra = {}) {
  response.writeHead(status, { 'content-type': 'application/json; charset=utf-8', ...extra });
  response.end(JSON.stringify(body));
}
function integerParameter(parameters, name) {
  const values = parameters.getAll(name);
  if (values.length !== 1 || !/^-?(0|[1-9][0-9]*)$/u.test(values[0])) return undefined;
  const value = Number(values[0]);
  return Number.isSafeInteger(value) ? value : undefined;
}
function handle(request, response) {
  const url = new URL(request.url, 'http://127.0.0.1');
  if (url.pathname !== '/sum') { sendJson(response, 404, { error: 'not_found' }); return; }
  if (request.method !== 'GET') { sendJson(response, 405, { error: 'method_not_allowed' }, { allow: 'GET' }); return; }
  const a = integerParameter(url.searchParams, 'a');
  const b = integerParameter(url.searchParams, 'b');
  if (a === undefined || b === undefined || [...url.searchParams.keys()].some(key => !['a', 'b'].includes(key))) {
    sendJson(response, 400, { error: 'invalid_parameters' }); return;
  }
  const total = a + b;
  if (!Number.isSafeInteger(total)) { sendJson(response, 400, { error: 'unsafe_total' }); return; }
  sendJson(response, 200, { total });
}
async function withServer(use) {
  const server = createServer(handle);
  await new Promise((resolve, reject) => {
    server.once('error', reject);
    server.listen(0, '127.0.0.1', resolve);
  });
  try {
    const address = server.address();
    if (address === null || typeof address === 'string') throw new Error('expected TCP listener');
    return await use(`http://127.0.0.1:${address.port}`);
  } finally {
    server.closeAllConnections();
    await new Promise((resolve, reject) => server.close(error => error ? reject(error) : resolve()));
  }
}

export async function verify() {
  // Worked example
  {
    await withServer(async base => {
      const response = await fetch(new URL('/sum?a=2&b=3', base), { signal: AbortSignal.timeout(2000) });
      assert.equal(response.status, 200);
      assert.match(response.headers.get('content-type'), /application\/json/u);
      assert.deepEqual(await response.json(), { total: 5 });
    });
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: status 200; application/json; total 5.

Example B: Inspect an HTTP error without expecting fetch rejection#

fetch rejects for failures such as network errors or aborts, not simply because the server sent a 404. A client that only catches rejection may mistakenly treat a protocol error body as success data.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

Exercises#

  1. Request a valid local calculation. GET /sum with a=2 and b=3 and inspect status, content type and JSON. Expected: status 200; application/json; total 5. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Inspect an HTTP error without expecting fetch rejection. Request an unknown route and inspect the actual response. Expected: fetch resolves; status 404, ok false, error not_found. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Encode query values through the URL API. Round-trip a query containing spaces, ampersand and equals without contacting a server. Expected: the value round-trips as one parameter. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Reject repeated or invalid parameters. Request repeated a values and a non-integer b value. Expected: both responses are 400 with invalid_parameters. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Reject an unsupported method. POST to the read-only sum route without a body. Expected: status 405 and Allow: GET. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Guard arithmetic overflow after parsing. Add one to Number.MAX_SAFE_INTEGER through the endpoint. Expected: status 400 rather than a rounded success value. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
