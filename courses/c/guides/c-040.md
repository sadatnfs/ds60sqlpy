# c-040: C ABI boundaries and foreign-function ownership

## Level and prerequisites

## Purpose and mental model

An application binary interface describes how compiled components exchange calls, values and symbols. A C function name alone does not define the entire contract: integer widths, struct layout, calling convention, ownership, error reporting and callback lifetime also matter. C interfaces are often used from C++, Rust or managed languages, but each side must agree on representation and who releases returned storage. Prefer explicit lengths and fixed-width types for data crossing the boundary. Do not return pointers to automatic locals or require another language to guess which allocator should free an allocation.

## Vocabulary and concepts

- **ABI:** The binary-level contract between compiled components.
- **Calling convention:** The rules for passing arguments, returning results and managing call state.
- **Allocator boundary:** The component responsible for releasing storage created by a particular allocator.

## Syntax anatomy and execution trace

extern declares a function or object defined elsewhere; C++ callers use an extern "C" declaration wrapper to request C linkage. A stable buffer API can accept caller-owned output plus capacity and return a status and required length. Keep structs simple and versioned when they form a public ABI. A foreign pointer must satisfy the same C lifetime, alignment and bounds rules as a native pointer.

## Worked example / walkthrough

### Worked example 1: Use caller-owned output

Copy hello into sufficient caller storage through a status API.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

enum ApiStatus { API_OK, API_TOO_SMALL, API_INVALID };
enum ApiStatus copy_api(const char *source, char *out, size_t capacity,
                        size_t *required) {
  if (source == NULL || required == NULL)
    return API_INVALID;
  size_t n = strlen(source);
  *required = n;
  if (n == SIZE_MAX || out == NULL || capacity <= n)
    return API_TOO_SMALL;
  memcpy(out, source, n + 1);
  return API_OK;
}
uint32_t identity_u32(uint32_t value) { return value; }

int main(void) {
  /* Use caller-owned output */
  {
    char out[8];
    size_t required = 0;
    CHECK(copy_api("hello", out, sizeof out, &required) == API_OK);
    CHECK(required == 5 && strcmp(out, "hello") == 0);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** The output is complete and required length is 5.

Caller-owned storage avoids requiring the foreign runtime to guess a deallocator.

### Worked example 2: Report insufficient capacity

Request the same copy into four bytes.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

enum ApiStatus { API_OK, API_TOO_SMALL, API_INVALID };
enum ApiStatus copy_api(const char *source, char *out, size_t capacity,
                        size_t *required) {
  if (source == NULL || required == NULL)
    return API_INVALID;
  size_t n = strlen(source);
  *required = n;
  if (n == SIZE_MAX || out == NULL || capacity <= n)
    return API_TOO_SMALL;
  memcpy(out, source, n + 1);
  return API_OK;
}
uint32_t identity_u32(uint32_t value) { return value; }

int main(void) {
  /* Use caller-owned output */
  {
    char out[8];
    size_t required = 0;
    CHECK(copy_api("hello", out, sizeof out, &required) == API_OK);
    CHECK(required == 5 && strcmp(out, "hello") == 0);
  }

  /* Report insufficient capacity */
  {
    char out[4] = "old";
    size_t required = 0;
    CHECK(copy_api("hello", out, sizeof out, &required) == API_TOO_SMALL);
    CHECK(required == 5 && strcmp(out, "old") == 0);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** The status is too-small and required length is 5.

The API reports the required payload length and preserves output on failure. The caller must reserve one more byte for termination.

## Prediction before execution

Distinguish a compiler diagnostic from a valid runtime rejection and from undefined behavior. Never execute an out-of-bounds access, dangling-pointer read or data race simply to discover what value it happens to print.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
