js-025: Typed modules and NodeNext resolution#

Level and prerequisites#

Advanced, approximately 120 minutes. Direct prerequisites: js-024

Learning objectives#

Explain nodenext, type-only import, emitted extension, noemitonerror with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Compile a main module importing twice from ./math.mjs and run it. The final task tests retain value imports beside erased type imports.

Purpose and mental model#

TypeScript source participates in two related dependency graphs: the compiler resolves source and declarations while checking, and Node resolves emitted JavaScript while running. Under NodeNext, a .mts source emits an ES module with a .mjs extension. Source imports name the runtime .mjs dependency; the compiler can resolve that specifier to its corresponding .mts source. A bundler may have different rules, but this route deliberately targets Node ESM.

Type-only imports declare dependencies needed only by the checker and disappear from emitted code. Value imports remain runtime dependencies. Successful type checking does not prove every required runtime artifact was packaged. The examples inspect emitted files and deliberately remove one owned temporary dependency to observe that distinction.

This reference creates tiny two-file projects in temporary directories, invokes the actual prepared compiler with strict NodeNext and noEmitOnError, and runs the emitted entry as a fresh Node process. Negative projects produce real diagnostics and verify that no entry was emitted. A fresh output directory avoids accidentally running stale JavaScript from an earlier successful build. No package is installed. The single main.mts pad owns and cleans up its temporary project.

Vocabulary and concepts#

NodeNext: Resolution rules modeling Node module formats and loading.

Type-only import: A dependency used for checking and erased before execution.

Emitted extension: The filename extension the runtime resolver actually sees.

NoEmitOnError: The policy preventing JavaScript output when checking fails.

How to run this lesson#

Use the prepared TypeScript 5.9.3 profile. The classroom saves main.mts, checks strict NodeNext resolution with noEmitOnError and an ES2022 target, then runs compiled/main.mjs on Node 24.22.1. Node typings 24.10.0 are prepared. Compilation and execution are separate stages. Types are erased and do not validate external JSON. No npm installation belongs inside the lesson.

Save your own learner copy under ignored .learning/expansion/js-025/ or use a saved classroom pad. Record predictions before execution. Each worked program includes its helper definitions. The reference puts the six exercises in separate scopes, so a task cannot silently rely on a variable from a previous task. A successful assertion is silent; the final JSON receipt reports how many exercise blocks completed. A failing assertion must produce a failed process, not a generic success message.

Syntax anatomy and execution trace#

The prepared compiler path is /opt/typescript/node_modules/typescript/bin/tsc. DS60_TSC_JS optionally selects an already prepared development copy; it never downloads one. The adjacent @types directory supplies Node declarations. spawnSync uses fixed argument arrays, separate stdout/stderr, a timeout and output cap. Type diagnostics and runtime loader errors are checked separately. The type-only dependency test inspects emitted code instead of inferring erasure from a successful run.

Worked example / walkthrough#

Example A: Compile and run a two-module project#

The runtime specifier is .mjs even though the source file is .mts. Naming a source-only extension without a corresponding emit policy can produce a runtime failure.

import { strict as assert } from 'node:assert';
import { mkdtemp, writeFile, readFile, access, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join, dirname, resolve } from 'node:path';
import { spawnSync } from 'node:child_process';

type ProcessResult = { status: number | null; stdout: string; stderr: string };
async function withProject(files: Record<string, string>, use: (directory: string) => Promise<void>): Promise<void> {
  const directory = await mkdtemp(join(tmpdir(), 'course-ts-project-'));
  try {
    for (const [name, source] of Object.entries(files)) await writeFile(join(directory, name), source, 'utf8');
    await use(directory);
  } finally { await rm(directory, { recursive: true, force: true }); }
}
function child(args: string[]): ProcessResult {
  const result = spawnSync(process.execPath, args, { encoding: 'utf8', timeout: 20000, maxBuffer: 1024 * 1024 });
  if (result.error) throw result.error;
  if (result.signal) throw new Error(`child terminated by ${result.signal}`);
  return { status: result.status, stdout: result.stdout, stderr: result.stderr };
}
function compile(directory: string): ProcessResult {
  const compiler = process.env.DS60_TSC_JS ?? '/opt/typescript/node_modules/typescript/bin/tsc';
  const typeRoots = resolve(dirname(compiler), '../..', '@types');
  return child([compiler, '--target', 'ES2022', '--module', 'NodeNext', '--moduleResolution', 'NodeNext', '--strict', '--noEmitOnError', '--skipLibCheck', '--types', 'node', '--typeRoots', typeRoots, '--outDir', join(directory, 'compiled'), join(directory, 'main.mts')]);
}
function runModule(directory: string): ProcessResult { return child([join(directory, 'compiled', 'main.mjs')]); }
async function exists(path: string): Promise<boolean> {
  try { await access(path); return true; }
  catch (error: unknown) {
    if (error instanceof Error && 'code' in error && error.code === 'ENOENT') return false;
    throw error;
  }
}

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    await withProject({ 'math.mts': 'export const twice = (value: number): number => value * 2;', 'main.mts': 'import { twice } from \'./math.mjs\'; console.log(twice(4));' }, async directory => {
      const compiled = compile(directory);
      assert.equal(compiled.status, 0, compiled.stdout + compiled.stderr);
      const executed = runModule(directory);
      assert.equal(executed.status, 0, executed.stderr);
      assert.equal(executed.stdout.trim(), '8');
      assert.equal(await exists(join(directory, 'compiled', 'math.mjs')), true);
    });
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: both processes succeed; output 8; math.mjs is emitted.

Example B: Inspect type-only erasure#

The type relation constrains source checking without becoming a value dependency. Inspecting the emitted program demonstrates this directly.

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    await withProject({ 'model.mts': 'export type Item = { id: string };', 'main.mts': 'import type { Item } from \'./model.mjs\'; const item: Item = { id: \'A\' }; console.log(item.id);' }, async directory => {
      const compiled = compile(directory);
      assert.equal(compiled.status, 0, compiled.stdout + compiled.stderr);
      const emitted = await readFile(join(directory, 'compiled', 'main.mjs'), 'utf8');
      assert.equal(emitted.includes('./model.mjs'), false);
      assert.equal(runModule(directory).stdout.trim(), 'A');
    });
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: no model import in emitted entry; output A.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

Exercises#

  1. Compile and run a two-module project. Compile a main module importing twice from ./math.mjs and run it. Expected: both processes succeed; output 8; math.mjs is emitted. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Inspect type-only erasure. Compile a type import and inspect the emitted entry before running it. Expected: no model import in emitted entry; output A. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Reject a type mismatch without output. Assign text to a number in a fresh project. Expected: TS2322; nonzero compiler status; no compiled main.mjs. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Require runtime-valid relative extensions. Import ./math without an extension under NodeNext ESM. Expected: TS2835 and no emitted entry. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Observe a missing runtime artifact. Compile successfully, remove only the owned emitted dependency, then run the entry. Expected: Node fails with ERR_MODULE_NOT_FOUND. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Retain value imports beside erased type imports. Import both a type and a value from one module. Expected: value dependency remains; runtime prints ready:A. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
