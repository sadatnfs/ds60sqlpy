c-038: C11 atomics and release-acquire publication#

Level and prerequisites#

Advanced, approximately 120 minutes plus a later retrieval session. Direct prerequisites: c-037

Learning objectives#

Explain atomic object, memory order, publication. Implement the six investigations with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

Purpose and mental model#

Atomic types make individual accesses participate in a defined concurrency model. They are not interchangeable with volatile, and they do not automatically protect a multi-field invariant. The default sequentially consistent operations are a useful starting point. Weaker memory orders require a proof connecting the writer and reader. A release store can publish preceding writes to a reader whose acquire load observes that store. A relaxed counter can count independent events without publishing unrelated memory. Lock-free status is implementation-dependent; atomic does not mean every operation avoids a lock on every platform.

Vocabulary and concepts#

  • Atomic object: An object accessed through the C atomic operation contract.
  • Memory order: The ordering guarantees requested by an atomic operation.
  • Publication: Making initialized non-atomic state visible through synchronization.

Syntax anatomy and execution trace#

atomic_int declares an atomic integer and atomic_init initializes it before sharing. atomic_fetch_add returns the previous value. atomic_compare_exchange_strong updates only when the current value matches expected and writes the observed value back to expected on failure. memory_order_release and memory_order_acquire form a publication relationship when the acquire observes the release. Avoid hand-built lock-free containers until ownership, reclamation and ABA hazards are understood.

Worked example / walkthrough#

Worked example 1: Inspect fetch-add semantics#

Add 3 to an atomic integer initially 2.

#include <assert.h>
#include <limits.h>
#include <pthread.h>
#include <sched.h>
#include <stdatomic.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

struct Publication {
  atomic_bool ready;
  int value;
};
void *atomic_publisher(void *argument) {
  struct Publication *p = argument;
  p->value = 42;
  atomic_store_explicit(&p->ready, true, memory_order_release);
  return NULL;
}

int main(void) {
  /* Inspect fetch-add semantics */
  {
    atomic_int value;
    atomic_init(&value, 2);
    int old = atomic_fetch_add(&value, 3);
    CHECK(old == 2 && atomic_load(&value) == 5);
  }
  puts("Worked example checks passed.");
  return 0;
}

Observe: The returned old value is 2 and current value is 5.

The return value is the prior state. Confusing it with the new value can create off-by-one ticketing logic.

  p->value = 42;
  atomic_store_explicit(&p->ready, true, memory_order_release);
  return NULL;

int main(void) {
  /* Inspect fetch-add semantics */
  {
    atomic_int value;
    atomic_init(&value, 2);
    int old = atomic_fetch_add(&value, 3);
    CHECK(old == 2 && atomic_load(&value) == 5);
  }

  /* Compare and exchange successfully */
  {
    atomic_int value;
    atomic_init(&value, 2);
    int expected = 2;
    CHECK(atomic_compare_exchange_strong(&value, &expected, 7));
    CHECK(atomic_load(&value) == 7);
  }
  puts("Worked example checks passed.");
  return 0;
}

Observe: The operation succeeds and stores 7.

The update is conditional on the observed state, not an unconditional assignment.

Common pitfalls and diagnosis#

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
