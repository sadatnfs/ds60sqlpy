## Purpose and mental model

Text has several representations. A Python string contains Unicode code points, while UTF-8 encodes that text as a sequence of bytes. The number of code points and the number of bytes need not agree. Before learning a tokenizer, trace this boundary so a character count is not silently substituted for a byte or token count.

The words cat, café and the single code-point smile 🙂 have respectively 3, 4 and 1 code points in these literal fixtures, but 3, 5 and 4 UTF-8 bytes. A displayed character can also be composed from multiple code points. The text é and the sequence e followed by a combining accent can look alike while having different raw byte representations.

Normalization is an explicit data policy that can deliberately make canonically equivalent spellings share a representation. NFC normalization is useful for some pipelines, but it changes raw identity. Decide it before deduplication and splitting, retain original provenance when needed, and do not claim that a normalized round trip reproduces every original byte. This lesson uses only the Python standard library and authored strings.

## Vocabulary and concepts

**Code point:** one Unicode numeric element in a Python string; it is not necessarily a complete displayed grapheme.

**UTF-8 byte:** one eight-bit unit in a variable-length encoding of Unicode text.

**Round trip:** encoding and decoding under a stated strict policy and obtaining the original representation.

**NFC normalization:** a Unicode canonical-composition policy that can merge equivalent code-point sequences.

**Replacement decoding:** a lossy policy that substitutes a replacement character for malformed bytes instead of preserving them.

## Syntax or reasoning anatomy

text.encode("utf-8") turns a string into bytes. payload.decode("utf-8") performs strict decoding by default and raises when byte sequences are invalid. len(text) counts Python code points; len(payload) counts bytes. Neither expression universally counts displayed characters or language-model tokens.

unicodedata.normalize("NFC", text) creates a normalized string rather than changing the original object. A hash of raw bytes identifies raw content; a hash of normalized bytes identifies the chosen canonicalized representation. Keep the policies labeled. The optional hash is not encryption, permission or a privacy guarantee. An empty string has a valid empty encoding, even though a later token-loss mean would still need a nonempty target denominator.

## Worked example / walkthrough

### Example A: Inspect bytes and code points

Compare three fixed strings and round-trip their exact UTF-8 payloads.

```python
texts = ["cat", "café", "🙂"]
counts = [(len(text), len(text.encode("utf-8"))) for text in texts]
assert counts == [(3, 3), (4, 5), (1, 4)]
assert all(text.encode("utf-8").decode("utf-8") == text for text in texts)
print(counts)
```

**Expected:** The accented word and smile require more bytes than code points. These are exact counts for the literal examples, not a general grapheme-counting algorithm.

### Example B: A deliberate identity change

Compare composed and decomposed spellings before and after NFC.

```python
import unicodedata

composed = "é"
# Construct directly to avoid a platform-dependent source-file normalization step.
decomposed = "e" + chr(0x0301)
assert composed != decomposed
assert composed.encode("utf-8") != decomposed.encode("utf-8")
assert unicodedata.normalize("NFC", decomposed) == composed
print(len(composed), len(decomposed))
```

**Expected:** Raw identity differs, while the explicit normalization makes these two fixtures agree. Retaining the normalized string cannot reconstruct which original spelling was supplied.

## Progressive hints

- **Hint 1:** Inspect code points and hex bytes separately from the rendered glyph.
- **Hint 2:** Make normalization an explicit returned policy and keep raw versus normalized identities distinct.
- **Hint 3:** Use strict decode for a round-trip claim; replacement is a different, lossy contract.

## Common pitfalls

If a count changes after export, inspect whether the file was decoded with a different codec or normalized. If a displayed string looks unchanged, compare repr, code points or encoded hex rather than assuming byte identity. If invalid bytes seem to disappear, inspect whether a replacement or ignore error policy was used.

A normalization policy can help detect canonical duplicates, but it does not identify every near-duplicate document or semantic paraphrase. Hash equality depends on the chosen representation, not on natural-language meaning. Keep original provenance where the task requires it, avoid collecting private text, and never describe a plain content hash as anonymization or encryption.
