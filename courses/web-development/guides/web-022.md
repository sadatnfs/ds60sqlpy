# web-022: CSS architecture, layers and maintainable components

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-021`

## Learning objectives

Build a small layered stylesheet with base, component and utility rules. Explain why important declarations complicate layer reasoning. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A stylesheet is easier to change when responsibilities are visible. Base rules describe document defaults, component rules describe reusable structures, and narrowly named utilities make deliberate local adjustments. These categories are a design choice, not a browser feature by themselves. Cascade layers let authors establish an explicit ordering among groups of declarations without continually increasing selector specificity.

For normal author declarations, later layers take priority over earlier layers, and unlayered normal declarations have priority over layered normal declarations. Important declarations reverse layer priority, which is one reason indiscriminate important usage makes reasoning harder. A good architecture keeps selectors understandable and limits the area a change can affect.

## Syntax anatomy and mechanism

Declare the layer order once with `@layer base, components, utilities`. Put actual rules inside those layers. Keep component names tied to a useful responsibility such as lesson-card, not a visual accident such as left-blue-box. Test a component in more than one surrounding context to expose accidental ancestor dependencies.

## Classroom execution and offline inputs

The browser uses its native HTML parser, so classic-script ordering, shared lexical bindings, inline modules and real DOMContentLoaded/load events keep their browser semantics. External module imports remain blocked. Navigation metadata such as base and meta http-equiv is rejected explicitly. On any supported host, the browser renders the document while Docker serves the classroom. No host compiler is needed.

## Worked example / walkthrough

### Worked example 1: Explicit ordering

Layer order establishes a policy before selectors compete within it.

```css
@layer base, components, utilities;
@layer base {
  p {
    color: #172033;
  }
}
@layer components {
  .note {
    color: #0753a4;
  }
}
```

**Expected observation:** The component layer can override the earlier base rule.

### Worked example 2: A narrow utility

The utility's responsibility is explicit.

```css
@layer utilities {
  .text-muted {
    color: #475569;
  }
}
```

**Expected observation:** The utility overrides earlier normal layered color declarations.

## Six progressive exercises

### Exercise 1: Predict the layer winner for normal declarations.

**Expected evidence:** A later declared layer outranks an earlier one before specificity is compared.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Move a component's rules into one named layer.

**Expected evidence:** Its styling responsibility is grouped and discoverable.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a small layered stylesheet with base, component and utility rules.

**Expected evidence:** The intended overrides work without escalating ids or important flags.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose an unlayered rule unexpectedly beating layered normal rules.

**Expected evidence:** Unlayered normal author declarations have higher layer priority.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Place the component under a different parent.

**Expected evidence:** Its behavior does not rely on an accidental deep ancestor selector.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain why important declarations complicate layer reasoning.

**Expected evidence:** Important layer ordering is reversed, so the normal ordering intuition no longer applies.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

A named architecture cannot prevent global selectors from leaking. Do not put every exception in an unlayered file because that silently bypasses the policy. Keep examples small enough to trace.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain cascade layer, component boundary, utility without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
