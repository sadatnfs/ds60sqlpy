# k8s-043: Three address spaces: Pod IP, node IP and Service IP

## Level and prerequisites

Intermediate; about 120 minutes. Direct prerequisites: `k8s-008`, `k8s-020`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Draw the internal request path with both ports.
- Explain a successful request with a changed backend UID.

## Purpose, vocabulary and mental model

An IP address identifies a network destination within a routing context. Kubernetes commonly exposes three distinct address roles. A Pod IP reaches a particular Pod network endpoint. A node IP reaches a machine participating in the cluster. A Service ClusterIP is a virtual destination whose implementation selects eligible service endpoints. These addresses are not interchangeable names for the same object.

A Pod can be replaced and receive a different IP and UID. A Service can keep its identity and virtual address while its backend Pods change. A node can host many Pods, and its address is not automatically the public address of every application on it. The correct destination depends on the caller and the intended traffic path.

The synthetic topology uses Pod 10.244.1.7, node 192.0.2.10 and Service 10.96.0.20. The node address is from documentation space and is never a real target. These values illustrate roles; actual ranges are cluster configuration. A browser on your laptop generally cannot route directly to an arbitrary ClusterIP or Pod IP in a desktop cluster.

### Key terms

- **Pod IP:** The address assigned to one Pod's network namespace. It is shared by the Pod's containers and changes when the Pod is replaced.
- **Node IP:** The address of a node's own network interface, distinct from the Pod addresses hosted on that node.
- **ClusterIP:** A Service's virtual destination address. It is implemented by forwarding rules that pick an eligible backend, not by one interface.
- **Network namespace:** A Linux kernel view of interfaces, addresses and routes. Each Pod has one, so a test result depends on which namespace the caller used.
- **Documentation address range:** Address blocks such as 192.0.2.0/24 reserved for examples, so a sample address is never a real target.

## Mechanism and field-by-field reasoning

The Pod status can report podIP and podIPs, while its spec names the scheduled node. A Service spec can report clusterIP, clusterIPs, type and ports. Node status contains addresses with types such as InternalIP. Read each field in its own object and preserve the object’s UID so an old address is not confused with a replacement.

A Service routes transport traffic to endpoints. It is not a process that has an application socket bound to every virtual address in the ordinary way. The implementation might program kernel rules or eBPF paths. The application process still listens inside a Pod at its target port.

## Trace the request or control path

```text
caller Pod -> Service 10.96.0.20:80 -> eligible Pod 10.244.1.7:8080
node 192.0.2.10 hosts the Pod; it is a separate address role
```

Follow the arrows left to right and attach an owner to each address. The caller Pod dials 10.96.0.20:80 because DNS or configuration gave it the Service, and the data plane on the caller's node rewrites that destination to 10.244.1.7:8080. The second line is not a hop at all: 192.0.2.10 only tells you which machine hosts the listener.

## Worked example / walkthrough

### Worked example 1: Classify a topology record

These are synthetic observations with explicit roles.

```json
{
  "node_ip": "192.0.2.10",
  "pod_ip": "10.244.1.7",
  "service_ip": "10.96.0.20",
  "service_port": 80,
  "target_port": 8080
}
```

**Expected observation:** The client selects a Service endpoint while the final listener belongs to a Pod.

### Worked example 2: Predict Pod replacement

The Service can remain stable while one backend changes.

```text
before: Service 10.96.0.20 -> Pod UID-A at 10.244.1.7
after:  Service 10.96.0.20 -> Pod UID-B at 10.244.1.9
```

**Expected observation:** The stable service destination does not prove the same backend process handled both requests.

## Six progressive exercises

### Exercise 1: Label all three synthetic address roles.

**Expected evidence:** One node address, one Pod address and one virtual Service address.

**Progressive hint:** For each address, find the object that reports it: a Node status, a Pod status or a Service spec.

### Exercise 2: Predict what can change after Pod replacement.

**Expected evidence:** Pod UID and IP can change while the Service remains stable.

**Progressive hint:** Ask which object a Deployment recreates and which one nobody recreates. Only the recreated one gets new identity fields.

### Exercise 3: Draw the internal request path with both ports.

**Expected evidence:** Service port 80 maps to Pod listener 8080.

**Progressive hint:** The Service port entry holds two numbers. Decide which one the caller dials and which one the process binds.

### Exercise 4: Diagnose a host browser trying a ClusterIP directly.

**Expected evidence:** The host may have no route to that virtual cluster destination.

**Progressive hint:** A ClusterIP lives in node rules inside the cluster. Does your laptop's routing table have any entry for 10.96.0.0/16?

### Exercise 5: Distinguish a node address from a public load-balancer address.

**Expected evidence:** They may be different infrastructure endpoints with different policies.

**Progressive hint:** Ask who hands out each address and what sits in front of it: the machine's network or a provider's edge.

### Exercise 6: Explain a successful request with a changed backend UID.

**Expected evidence:** Service continuity and backend identity are separate observations.

**Progressive hint:** Two observations are involved: the request succeeded, and the UID differs. Which object does each belong to?

## Diagnosis, failure boundaries and common mistakes

The classic mistake in Exercise 4 is treating 10.96.0.20 as a machine. No interface owns a ClusterIP; it exists only as translation rules on cluster nodes, so a host browser outside the cluster usually times out rather than getting a refusal. A second mistake is writing a Pod IP into configuration as if it were stable: the next rollout hands out a new one and the old address may later belong to a different Pod. A third is copying the node address column as the Pod's address because `kubectl get pods -o wide` prints them next to each other. When a request fails, first write down which of the three address roles the caller actually used, then look only at the component that owns that role.
