# c-027: Testing, injected allocation failure and useful oracles

## Level and prerequisites

Intermediate, approximately 120 minutes plus a later retrieval session. Direct prerequisites: `c-026`

## Learning objectives

Explain fault injection, test oracle, failure-path coverage. Implement the six investigations with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

Reliable tests target plausible defects rather than mirror the implementation line for line. A normal result, an exact boundary, malformed input and resource failure often exercise different contracts. Allocation failure is difficult to reproduce by exhausting real machine memory and should not be forced on a shared system. Inject a controlled allocator interface instead. The fake can fail on a selected call while recording ownership counts, making cleanup behavior deterministic. Such a fake proves local error-path logic, not the operating system allocator or every interleaving. Keep sanitizer and real integration evidence separate.

## Vocabulary and concepts

- **Fault injection:** Deliberately supplying a particular failure under controlled conditions.
- **Test oracle:** An independent rule defining the correct outcome.
- **Failure-path coverage:** Evidence that cleanup and state preservation work when an operation fails.

## Syntax anatomy and execution trace

A function pointer supplies allocation behavior. The fixture allocator either delegates to malloc or returns NULL according to an explicit flag. The component validates and allocates before modifying the caller output pointer. Tests retain the previous output on failure. A useful oracle checks both the returned status and absence of unintended state changes; a nonzero exit alone cannot explain which invariant was violated.

## Worked example / walkthrough

### Worked example 1: Exercise successful allocation

Copy a tiny string using the working allocator.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

bool fail_allocation = false;
void *controlled_alloc(size_t size) {
  return fail_allocation ? NULL : malloc(size);
}
bool copy_with_allocator(const char *source, char **out,
                         void *(*allocate)(size_t)) {
  size_t n = strlen(source);
  if (n == SIZE_MAX)
    return false;
  char *copy = allocate(n + 1);
  if (copy == NULL)
    return false;
  memcpy(copy, source, n + 1);
  *out = copy;
  return true;
}

int main(void) {
  /* Exercise successful allocation */
  {
    char *out = NULL;
    fail_allocation = false;
    CHECK(copy_with_allocator("abc", &out, controlled_alloc));
    CHECK(strcmp(out, "abc") == 0);
    free(out);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The output owns an equal string.

The test checks content and then releases the owned result.

### Worked example 2: Inject allocation failure

Configure the allocator to return NULL.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

bool fail_allocation = false;
void *controlled_alloc(size_t size) {
  return fail_allocation ? NULL : malloc(size);
}
bool copy_with_allocator(const char *source, char **out,
                         void *(*allocate)(size_t)) {
  size_t n = strlen(source);
  if (n == SIZE_MAX)
    return false;
  char *copy = allocate(n + 1);
  if (copy == NULL)
    return false;
  memcpy(copy, source, n + 1);
  *out = copy;
  return true;
}

int main(void) {
  /* Exercise successful allocation */
  {
    char *out = NULL;
    fail_allocation = false;
    CHECK(copy_with_allocator("abc", &out, controlled_alloc));
    CHECK(strcmp(out, "abc") == 0);
    free(out);
  }

  /* Inject allocation failure */
  {
    char *out = NULL;
    fail_allocation = true;
    CHECK(!copy_with_allocator("abc", &out, controlled_alloc));
    CHECK(out == NULL);
    fail_allocation = false;
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The copy fails and output remains NULL.

No real memory pressure is required. The failure is reproducible and isolated to this operation.

## Prediction before execution

Trace each object from initialization through its last valid use. Write down the size of every array, the capacity of every output buffer and the ownership of any allocated storage. Distinguish a compiler diagnostic from a valid runtime rejection and from undefined behavior. Never execute an out-of-bounds access, dangling-pointer read or data race simply to discover what value it happens to print.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
