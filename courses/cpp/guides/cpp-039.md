# cpp-039: C interfaces and loading boundaries

## Level and prerequisites

Advanced; 120 minutes. Direct prerequisites: `cpp-017`, `cpp-023`, `cpp-027`.

Learner artifact: [cpp-039.cpp](../lessons/cpp-039.cpp). [Case ledger](../fixtures/cpp-039-cases.json). [Solutions](../solutions/cpp-039_solutions.md).

## Learning objectives

Define ownership and error transport across a language/binary boundary.

## Vocabulary and concepts

A C interface exposes stable-shaped calls to clients that may not share a C++ compiler. An opaque handle hides implementation details while preserving a documented owner. A loading boundary introduces version, symbol and cleanup responsibilities. Destroying an object in the wrong allocator or letting an exception cross the boundary can break the contract.

<!-- terms:start -->

- **C interface:** functions with C linkage and C-compatible types that clients built with another compiler can call.
- **opaque handle:** a pointer-shaped value that hides the implementation layout from consumers.
- **paired allocation and release:** the rule that the provider that created an object also destroys it, instead of the consumer using its own delete.
- **no-throw boundary:** an interface that catches exceptions internally and reports failure as null or a status code.
- **custom deleter:** a function given to `unique_ptr`, such as the provider's destroy function, so cleanup uses the correct release.

<!-- terms:end -->

## Syntax and mechanism

Create returns a handle or failure; destroy releases it exactly once; getters validate pointers and report status. extern C controls linkage but the host still needs compatible architecture and calling conventions. Dynamic loading requires a separate platform-specific host test, not the single-file browser example.

## Trace the mechanism

The opaque handle keeps C++ layout private, but its lifetime is still a public responsibility. A successful create must pair with the provider's destroy function, which can be wrapped by a unique_ptr custom deleter in a C++ client. A pointer that has already been destroyed is not made safe by a null check. The lesson checks null arguments and proper ownership; dynamic symbol loading, ABI version negotiation and foreign-language use require separate host receipts.

## Opaque handles and ownership across an ABI

An opaque handle hides a C++ implementation behind a pointer-shaped public interface. A consumer can pass the handle back to the provider without knowing the class layout. This reduces coupling to implementation details, but the handle still has a lifecycle: creation succeeds or fails, use requires a live valid handle, and destruction ends that lifetime.

The create function catches allocation failure and returns null under its no-throw boundary. The caller checks that result before use. The read function returns a status code and writes through an output pointer only on success. The destroy function belongs to the provider, which keeps allocation and release responsibilities paired. A foreign consumer should not guess that its own delete or allocator is interchangeable.

The C++ consumer wraps the raw handle in a unique_ptr with the provider destroy function as custom deleter. That makes cleanup follow scope while preserving the ABI's release rule. The wrapper is a convenience on the C++ side; it is not part of the C-compatible signature. Other languages need their own lifetime wrapper or explicit finally/dispose discipline.

The null-handle negative checks a defined rejection path. It cannot make an arbitrary dangling nonnull pointer safe. Calling read after destroy is a use-after-lifetime error even if the old address still looks plausible. If the interface needs protection against stale external identifiers, it requires a different validated handle table or generation design, not only a null test.

extern "C" linkage and opaque layout are only part of ABI compatibility. Calling conventions, type widths, compiler settings, library loading and version negotiation can still matter. The single-file program demonstrates ownership and error semantics within one executable. A real shared-library consumer on each supported platform needs a separate build/load/run receipt.

## Worked example / walkthrough

Example 1 creates an opaque `Analyzer` through the C interface and hands it to a `std::unique_ptr` with `analyzer_destroy` as the deleter, so cleanup runs on every exit path; the read returns 0. Example 2 passes a null handle and gets status 1 while `out` keeps its sentinel -1, proving the call wrote nothing. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-039-example-1.cpp)

```cpp
#include <cassert>
#include <iostream>
#include <memory>

struct Analyzer {
  int total = 0;
};

extern "C" Analyzer *analyzer_create() noexcept {
  try {
    return new Analyzer{};
  } catch (...) {
    return nullptr;
  }
}
extern "C" void analyzer_destroy(Analyzer *p) noexcept { delete p; }
extern "C" int analyzer_read(const Analyzer *p, int *out) noexcept {
  if (!p || !out)
    return 1;
  *out = p->total;
  return 0;
}
int main() {
  Analyzer *raw = analyzer_create();
  if (!raw)
    return 1;
  std::unique_ptr<Analyzer, void (*)(Analyzer *)> owner(raw, analyzer_destroy);
  int value = -1;
  assert(analyzer_read(owner.get(), &value) == 0 && value == 0);
  std::cout << "cpp-039 example 1 checks passed\n";
  return 0;
}
```

**Expected:** With assertions enabled, the program exits with status 0 and prints:

#include <iostream>

struct Analyzer {
  int total = 0;

  } catch (...) {

    return 1;

## Exercises

### Exercise 1: Document ownership

Name who destroys a successfully created handle.

**Expected result/shape:** Caller invokes analyzer_destroy exactly once.

**Verify:** Check your answer against Worked example 1: the `unique_ptr` owner calls `analyzer_destroy` once at scope exit, and no other line deletes `raw`.

**Progressive hints:** The provider controls allocation and deallocation pairing.

### Exercise 2: Wrap safely

Use unique_ptr with analyzer_destroy as deleter.

**Expected result/shape:** Scope exit calls the provider destructor once.

**Verify:** Use a scratch deleter that increments a counter and then calls `analyzer_destroy`, and assert the counter is 0 inside the scope and 1 after it ends.

**Progressive hints:** RAII can manage a C boundary through a custom deleter.

### Exercise 3: Reject null arguments

Test null handle and null output independently.

**Expected result/shape:** Status 1 for either, no pointer dereference.

**Verify:** Assert `analyzer_read(nullptr, &out) == 1` and `analyzer_read(handle, nullptr) == 1` as two separate assertions, and that `out` keeps its old value -1.

**Progressive hints:** Both borrowed pointers require validation.

### Exercise 4: Repair cross-boundary throw

Review a create function that throws bad_alloc across C.

**Expected result/shape:** Catch inside and return null or a documented status.

**Verify:** Confirm the repaired function wraps `new` in `try`/`catch` inside its `extern "C"` body, as `analyzer_create` does, and that callers check for `nullptr` before use.

**Progressive hints:** The foreign caller may not support C++ unwinding.

### Exercise 5: Version the interface

Add a provider ABI-version query returning 1.

**Expected result/shape:** Caller rejects unsupported version before using handles.

**Verify:** Assert the query returns 1, then make the caller accept only version 2 in a scratch copy and confirm it stops before calling `analyzer_create`.

**Progressive hints:** A version check supplements, rather than proves, actual binary compatibility.

### Exercise 6: Transfer real loading

Build and load a shared provider in a separate owned host project.

**Expected result/shape:** Record exported symbols, architecture, compiler and create/destroy test.

**Verify:** Run `nm -D` on the shared library and confirm `analyzer_create`, `analyzer_destroy` and `analyzer_read` appear unmangled, then keep that list with `uname -m`, the compiler version and the create/destroy test result.

**Progressive hints:** The browser source is not a dynamic-loader acceptance receipt.

## Self-check

Why does one successful create have exactly one matching destroy, and what does the deleter guarantee on an early return? For Example 2, explain why `out` must still hold -1 after a call with a null handle.

## Common pitfalls

If a handle leaks on an exception path, wrap it immediately after successful creation. If a consumer frees it with the wrong allocator, restore the provider-owned destroy rule. If a null rejection passes but a stale pointer crashes, do not expand the test into undefined behavior; fix lifetime management. If dynamic loading fails, inspect exported symbols, architecture and ABI version separately from the function's internal logic.
