# k8s-048: Cluster DNS, search paths, caching and discovery

## Level and prerequisites

Intermediate; about 120 minutes. Direct prerequisites: `k8s-047`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Draw resolution and connection as separate phases.
- Design robust service discovery for a client.

## Purpose, vocabulary and mental model

DNS maps names to records such as IP addresses. Kubernetes cluster DNS creates service records according to namespace and cluster domain. A short name can resolve differently depending on the caller’s namespace and search configuration. A fully qualified service name makes the intended scope clearer.

For a typical cluster domain cluster.local, a Service named api in namespace study has a name like api.study.svc.cluster.local. The cluster domain is configurable, so do not hardcode it as a universal fact in a reusable client. A DNS answer establishes name resolution, not a listening process or healthy application.

Caching affects how quickly clients observe changes, but what can go stale depends on the Service type. A ClusterIP Service name keeps resolving to the same virtual IP while its endpoints change, so DNS caching does not delay endpoint changes there; staleness comes from long-lived connections that stay on their original backend. A headless Service returns Pod addresses directly, so a cached answer can keep sending new connections to a removed Pod until the record's TTL expires and the client resolves again. Resolver libraries and applications cache differently. Diagnose the actual client behavior before concluding that a DNS record update should have moved every request immediately.

### Key terms

- **Fully qualified domain name:** A complete name such as api.study.svc.cluster.local that includes the namespace and cluster domain, so no search expansion is needed.
- **Search domain:** A suffix from the Pod's resolver settings that is appended to a short name, such as the Pod's own namespace domain.
- **Cluster domain:** The configurable DNS suffix for the cluster, typically cluster.local, under which Service names are published.
- **DNS cache:** Stored answers kept until their TTL expires, so a client can keep using an old address after a record changes.
- **Headless Service:** A Service with clusterIP None whose DNS name returns the individual Pod addresses instead of one virtual IP.

## Mechanism and field-by-field reasoning

A Pod’s dnsPolicy and dnsConfig influence resolver behavior. Search suffixes and ndots can cause multiple queries for one short-looking name. NetworkPolicy that blocks DNS can break service discovery even when direct IP transport works.

The fixture’s names are synthetic. Optional host observations should inspect the relevant Pod’s resolver and issue a bounded lookup from the intended namespace. Do not use a successful lookup on the laptop as proof of what a Pod’s resolver sees.

## Trace the request or control path

```text
client name -> resolver search rules/cache -> cluster DNS -> Service record
resolved address -> separate TCP connection -> separate HTTP behavior
```

The two lines are separate phases with separate evidence. Line one turns a short name into an address using the resolver's search list and any cached answer, so the namespace you ask from matters. Line two starts only after an address exists. A correct answer of 10.96.0.20 followed by a failed connection is a line-two problem, not a DNS problem.

## Worked example / walkthrough

### Worked example 1: Expand a namespaced service name

Assume cluster.local only for this synthetic example.

```text
short from study namespace: api
qualified: api.study
fully qualified: api.study.svc.cluster.local.
```

**Expected observation:** The trailing dot makes the name absolute for DNS resolution; actual cluster domain must be known.

### Worked example 2: Separate resolution from serving

These observations can disagree without contradiction.

```text
DNS: api -> 10.96.0.20
TCP: connection refused
HTTP: no response available
```

**Expected observation:** Name resolution succeeded; the failure is later in the path.

## Six progressive exercises

### Exercise 1: Predict a short-name lookup from another namespace.

**Expected evidence:** It may search that namespace rather than the intended study service.

**Progressive hint:** Write out the client Pod's search list. Its first suffix is built from the client's own namespace.

### Exercise 2: State the configurable part of the FQDN.

**Expected evidence:** The cluster domain is not universally cluster.local.

**Progressive hint:** Two parts of the long name come from cluster configuration rather than from the Service. Which one is asked about?

### Exercise 3: Draw resolution and connection as separate phases.

**Expected evidence:** DNS record, transport connection and application response have distinct evidence.

**Progressive hint:** Draw a line between having an address and having a connection. Each side needs its own observation.

### Exercise 4: Diagnose direct-IP success with name failure.

**Expected evidence:** Investigate resolver configuration, DNS reachability and policy.

**Progressive hint:** If the address works and the name does not, the listener is fine. Look at what turns the name into the address.

### Exercise 5: Explain stale behavior after endpoint changes.

**Expected evidence:** For a ClusterIP Service, existing connections keep their old backend because the name still resolves to the same virtual IP; for a headless Service, cached Pod address records can also send new connections to a removed Pod.

**Progressive hint:** Separate the two Service types: one name resolves to a virtual IP, the other to the Pod addresses themselves.

### Exercise 6: Design robust service discovery for a client.

**Expected evidence:** Known namespace/domain, bounded resolution/connection and safe reconnect behavior.

**Progressive hint:** Decide what the client knows in advance, how long it waits at each phase and when it resolves again.

## Diagnosis, failure boundaries and common mistakes

Short names cause most surprises. A client in namespace tools asking for network-study tries network-study.tools.svc.cluster.local first and either fails or, worse, reaches a same-named Service there. Use the namespaced name whenever the namespace is known. Another mistake is hard-coding cluster.local; some clusters use a different domain. When direct-IP requests work and named ones fail, read the client's /etc/resolv.conf and check whether an egress policy blocks UDP and TCP 53 to the DNS Service before suspecting the app. Finally, a negative answer cached by the client can outlive the fix, so wait out its TTL before declaring the repair failed.
