# web-040: Objects, constructors and immutable value boundaries

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-039`

## Learning objectives

Build a validated study-session value object. Explain shallow readonly versus deep immutability. Use class, object and constructor accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

A class defines a kind of object, and an object combines state with behavior. Use an object when it makes a domain boundary clearer, not merely because the program has grown. A constructor establishes the initial state. An invariant is a condition that should remain true throughout the object's useful lifetime, such as a nonempty topic and nonnegative duration.

Publicly mutable properties can let callers bypass a carefully checked constructor. A small immutable value object can preserve its contract by validating once and exposing readonly data. Readonly does not make every nested object deeply immutable, and it does not replace validation. Understand the specific language guarantee rather than treating the keyword as a complete architecture.

### Key terms

- **Class:** A definition of properties and methods; each object created from it with `new` is an instance.
- **Constructor:** The `__construct()` method that runs when an object is created and should leave it in a valid state.
- **Invariant:** A condition that must hold for every valid object, checked by the constructor and preserved by every method.
- **Readonly property:** A property that can be assigned only once, during initialization inside the class, and never modified afterward.

## Syntax anatomy and mechanism

Constructor property promotion can declare and initialize properties directly in the parameter list. Use explicit types and meaningful names. A method can derive a display label from the stored values without changing them. PHP 8.4 also offers asymmetric visibility, such as `public private(set) int $minutes`, for a property that anyone may read but only the class may change, and property hooks, which run code in a property's `get` or `set` operation. Use them when an object genuinely changes; a value object that never changes is still clearest with `readonly`. Prefer composition of small responsibilities over a deep inheritance hierarchy built before requirements are known.

## Worked example / walkthrough

### Worked example 1: A validated value

Construction is the point where the invariant is established.

```php
final class Duration {
  public function __construct(public readonly int $minutes) {
    if ($minutes < 0) throw new InvalidArgumentException('Negative duration');
  }
}
```

**Expected observation:** Every successfully created Duration has nonnegative minutes.

### Worked example 2: Derived behavior

The method computes from the object's state.

```php fragment
$duration = new Duration(45);
echo $duration->minutes . ' minutes';
```

**Expected observation:** The value is readable without exposing a mutation operation.

## Contrast case: readonly is shallow

The property cannot be reassigned, but it holds an object. Try both changes and note which one PHP refuses.

```php expect-error
final class Plan {
  public function __construct(public readonly ArrayObject $topics) {}
}

$plan = new Plan(new ArrayObject(['HTML']));
$plan->topics[] = 'SQL';
echo count($plan->topics), "\n";

$plan->topics = new ArrayObject();
```

Appending SQL succeeds, because `readonly` stops reassignment of the property, not changes inside the object it points to, so the count prints 2. The final line tries to replace the property and throws an `Error` saying the readonly property cannot be modified. A class that promises an unchangeable topic list therefore needs to copy the input into an array, or keep the collection private, instead of exposing a mutable object.

## Debugging and common mistakes

Do not build an inheritance tree for every noun. A readonly array cannot be changed through that property, but a readonly property referring to an object does not freeze that object's internals. Keep the claimed guarantee precise.

When an object reaches an invalid state, look for a setter or public property written after construction; validate only in the constructor and remove the mutation path. When a readonly property still changes, check whether it holds an object whose own state is being modified.
