# k8s-047: ClusterIP Services and Layer 4 routing

## Level and prerequisites

Intermediate; about 120 minutes. Direct prerequisites: `k8s-046`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Trace a fresh TCP request through the Service.
- Design a stable endpoint for replacing Pods.

## Purpose, vocabulary and mental model

A ClusterIP Service gives clients a stable virtual endpoint for a changing set of backends. The selector usually identifies Pods by labels. The Service port is what clients address; targetPort identifies the backend listener, either numerically or through a named container port. A Service does not select an image name or Deployment name directly.

Layer 4 routing concerns transport connections such as TCP. It does not normally choose a backend by HTTP path or rewrite an application URL. HTTP-aware routing belongs to a proxy or controller with that capability. A long-lived TCP connection can continue using one backend even if individual requests are numerous.

A Service can exist with no eligible endpoints. Its ClusterIP allocation is not a health certificate. Read the selector, matching Pod labels, readiness and EndpointSlices, then issue a fresh request from the intended caller. Each observation narrows a different possible failure.

### Key terms

- **Service selector:** The label query that decides which Pods a Service sends traffic to.
- **Service port:** The port that clients connect to on the Service address.
- **targetPort:** The Pod port that receives forwarded Service traffic. It can be a named port, so backends may use different numbers.
- **Layer 4 routing:** Forwarding by IP address and TCP or UDP port only, without reading HTTP content.
- **Long-lived connection:** A connection that stays open across many requests. Service balancing happens when it opens, so a new Pod may receive little traffic.

## Mechanism and field-by-field reasoning

The fixture uses Service port 80 and named targetPort http, resolving to containerPort 8080 on the selected Pod. Named ports help avoid duplicating a number but still need a matching declaration and real listener. Protocol defaults and transport type should be explicit when teaching non-TCP workloads.

A selectorless Service can be paired with manually managed EndpointSlices, but it has a different ownership model and extra restrictions. This introductory fixture uses selectors so the controller maintains endpoints. Do not manually edit controller-owned slices to hide a wrong selector.

## Trace the request or control path

```text
client -> ClusterIP:80 -> service data plane -> ready endpoint PodIP:8080
selector labels -> endpoint controller -> EndpointSlice addresses and ports
```

The two lines run on different clocks. The bottom line is control: the selector app=network-study is evaluated continuously and the result lands in an EndpointSlice. The top line is one connection: at connect time the data plane picks one ready address from that slice and rewrites 10.96.0.20:80 to it. Repair a broken top line by reading the bottom one.

## Worked example / walkthrough

### Worked example 1: Read the complete routing fields

This is a Service fragment from the maintained fixture.

```yaml
type: ClusterIP
selector:
  app: network-study
ports:
  - name: http
    port: 80
    targetPort: http
```

**Expected observation:** Clients use 80; the named backend port resolves to the app listener 8080.

### Worked example 2: Compare a selector mismatch

Only the labels changed.

```text
Service selector: app=network-study
Pod labels: app=wrong
result: no matching backend Pods
```

**Expected observation:** The Service can retain its virtual IP while traffic has no eligible destination.

## Six progressive exercises

### Exercise 1: Predict client and backend ports.

**Expected evidence:** Client 80 and backend 8080.

**Progressive hint:** Find the two numbers on the Service port entry and decide which side of the translation each belongs to.

### Exercise 2: Change only the Service selector in a synthetic record.

**Expected evidence:** The matching endpoint set becomes empty.

**Progressive hint:** The selector is a filter over Pod labels. Change it in the record and ask which Pods still pass.

### Exercise 3: Trace a fresh TCP request through the Service.

**Expected evidence:** Caller, virtual destination, chosen endpoint and listener are named.

**Progressive hint:** Name four things in order: who connects, to which virtual address, which endpoint was chosen, which process accepts.

### Exercise 4: Diagnose a ClusterIP with no ready endpoints.

**Expected evidence:** Inspect selector matches and readiness before external routing.

**Progressive hint:** Before looking past the Service, compare its selector with real Pod labels and check each Pod's Ready condition.

### Exercise 5: Explain why HTTP path routing is not provided by this Service.

**Expected evidence:** Layer 4 connection selection does not interpret URL paths.

**Progressive hint:** Ask what a TCP connection contains at the moment its endpoint is chosen. Is the URL path visible yet?

### Exercise 6: Design a stable endpoint for replacing Pods.

**Expected evidence:** Clients use Service discovery while backend identities can change.

**Progressive hint:** Clients need a name that survives Pod replacement. Which object in this lesson keeps its address while Pods change?

## Diagnosis, failure boundaries and common mistakes

The most common ClusterIP failure is a selector typo: the Service exists, has an address and resolves in DNS, yet its slice is empty, so connections fail in a way that depends on the data plane. Read the EndpointSlice before changing anything else. Another frequent slip is setting targetPort to the Service port, 80, when the container listens on 8080; referring to the named port http avoids that and survives a later port change. Finally, expecting one ClusterIP to split /api and /web traffic confuses Layer 4 with Layer 7. A Service chooses a connection's endpoint without reading HTTP, so path routing needs Ingress or Gateway API.

Before concluding, record:

- `spec.selector` beside the labels of each candidate Pod, so a one-character typo in app=network-study is visible.
- `port` 80, `targetPort` http and the container port named http, which must resolve to listener 8080.
- Each EndpointSlice address with its `conditions.ready` value; an address marked not ready gets no new connections.
- The caller, the virtual destination 10.96.0.20:80 and the chosen Pod address for one fresh TCP connection.

General evidence rules: [diagnosis rules](../STUDY-GUIDE.md#diagnosis-rules).
