# web-009: Form constraints, errors and helpful recovery

## Level and prerequisites

Beginner; allow about 90 minutes, with extra time for independent practice. Direct prerequisites: `web-008`

## Learning objectives

Build a bounded study-time form with linked help. Separate client feedback from server-side acceptance. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

Validation checks whether input satisfies a contract. Browser constraint validation gives immediate feedback through attributes such as required, type, min and maxlength. It improves the interaction but is not a security boundary because a client can bypass it or send a request without using the form at all. A server must repeat the relevant validation and authorization decisions.

An error message should identify the field, explain the problem and offer a useful correction without losing the user's work. Color alone is insufficient. Connect instructions and errors with aria-describedby, and use aria-invalid when an actual invalid state has been identified. Do not mark every untouched field invalid when the page first opens.

## Syntax anatomy and mechanism

`checkValidity()` reports whether a control meets its constraints. `reportValidity()` also requests the browser's feedback interface. An empty required field is invalid, while a non-required empty email field may be valid. Email type checks syntax, not whether the mailbox exists or belongs to the user. This lesson uses native constraints and explicit explanatory text; it does not send data.

## Classroom execution and offline inputs

Choose **HTML browser preview** in the classroom. The pad is one complete HTML document with embedded CSS and, where taught, embedded JavaScript. Its preview is isolated from the classroom and recreated on each run. It does not contact a server, submit real forms, read cookies, fetch assets or load a CDN. All fixtures are inline and synthetic. The browser uses its native HTML parser, so classic-script ordering, shared lexical bindings, inline modules and real DOMContentLoaded/load events keep their browser semantics. External module imports remain blocked. Navigation metadata such as base and meta http-equiv is rejected explicitly. On any supported host, the browser renders the document while Docker serves the classroom. No host compiler is needed.

Run your own source after implementing the task. A reference's checks inspect only the named initial conditions. Its success message is not a full accessibility audit, proof of responsive behavior at every size, or evidence that you implemented the solution yourself. Inspect actual output after keyboard input, resizing and changes. Save your source before comparing with a reference. For visual experiments, explicitly turn on Live preview: the page refreshes after a short pause in typing, while Pause updates keeps the last rendered version and Stop preview cancels pending refreshes. Desktop, tablet and phone presets resize the same preview without rerunning it. Automatic previews do not create saved runs; choose Save observation or Run when you want to retain an exact source-and-output record. Changing lessons, opening history or reloading turns live execution off. The document and its CSS share one saved pad; HTML and CSS remain different languages within that artifact.

## Worked example / walkthrough

### Worked example 1: A bounded value

The contract is visible in the label and attributes.

```html
<label for="minutes">Minutes, 5 to 120</label
><input id="minutes" name="minutes" type="number" min="5" max="120" required />
```

**Expected observation:** An empty value fails required; 4 fails the minimum.

### Worked example 2: Connected help

Help remains available while entering data.

```html
<input id="alias" aria-describedby="alias-help" minlength="3" /><p id="alias-help"
  >Use at least three characters.</p
>
```

**Expected observation:** The input references its visible instruction.

## Six progressive exercises

### Exercise 1: Predict required, minimum and maximum outcomes for empty, 4, 30 and 121.

**Expected evidence:** Empty, 4 and 121 fail; 30 satisfies the numeric bounds.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add a clear unit and range to a control's label.

**Expected evidence:** The rule is understandable before an error occurs.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a bounded study-time form with linked help.

**Expected evidence:** The user can identify the rule, enter a valid value and retain it after a failed attempt.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Explain why type=email does not prove mailbox ownership.

**Expected evidence:** It checks a syntactic format, not identity or delivery.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test validation with keyboard and an empty field.

**Expected evidence:** The error is discoverable and the entered values are preserved.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Separate client feedback from server-side acceptance.

**Expected evidence:** The backend repeats contract checks and authorization regardless of browser validation.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not erase all fields after one invalid input. Do not imply red borders alone are adequate. Programmatic assignment and real user editing can differ for some constraints, so test actual interaction as well as scripted values.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain constraint validation, required, minlength without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
