# go-016: Closures, callbacks and controlled iteration

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-015

## Learning objectives

Write closures with independent state and an iterator that stops early when its consumer breaks out of a range loop. Along the way, explain closure, callback, early termination, iterator function; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A function value can be stored, passed and called like other values. A closure also refers to variables from its surrounding scope. That makes callbacks concise, but it makes lifetime and mutation worth tracing explicitly. Two closures can intentionally share one variable; two independent constructor calls can create separate state. A callback contract should describe when it is called, whether it may stop iteration and whether it can retain supplied values. Iterator-style APIs can avoid allocating intermediate slices, but early termination and cleanup must still be well defined. Do not confuse deferred execution with concurrent execution: a closure is not a goroutine by itself.

## Vocabulary and concepts

- **Closure:** A function value that refers to surrounding variables.
- **Callback:** A function supplied for another operation to invoke.
- **Early termination:** Ending traversal once the caller has enough evidence.
- **Iterator function:** A function of type iter.Seq that a for range loop can traverse.

## Syntax anatomy and reasoning

func(int) int is a function type. An anonymous func literal creates a function value. Returning a closure from makeCounter retains access to its captured count. A visitor returning bool can stop a traversal when false. Passing a function as a parameter makes selection policy explicit without an interface type when only one operation is needed. The iter package names this visitor shape: iter.Seq[V] is func(yield func(V) bool), and for x := range seq runs the loop body as the yield callback, so break, continue and return keep their ordinary meaning.

## Worked example / walkthrough

### Worked example 1: Capture a changing variable

Create a closure referring to factor, change factor, then call it.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Capture a changing variable
	{
		factor := 2
		multiply := func(x int) int { return factor * x }
		factor = 3
		check(multiply(4) == 12, "capture variable")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The closure uses the new factor 3.

The closure refers to the variable rather than freezing its initial value. Explicitly copying a value into a new binding produces a different contract.

### Worked example 2: Create independent counters

Construct two counter closures and call the first twice.

```go
package main

import (
	"fmt"
	"iter"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func makeCounter() func() int { n := 0; return func() int { n++; return n } }
func mapInts(items []int, f func(int) int) []int {
	out := make([]int, len(items))
	for i, x := range items {
		out[i] = f(x)
	}
	return out
}
func visit(limit int, f func(int) bool) {
	for i := 1; i <= limit; i++ {
		if !f(i) {
			return
		}
	}
}
func countTo(limit int, produced *int) iter.Seq[int] {
	return func(yield func(int) bool) {
		for i := 1; i <= limit; i++ {
			*produced++
			if !yield(i) {
				return
			}
		}
	}
}

func main() {
	// Capture a changing variable
	{
		factor := 2
		multiply := func(x int) int { return factor * x }
		factor = 3
		check(multiply(4) == 12, "capture variable")
	}

	// Create independent counters
	{
		a, b := makeCounter(), makeCounter()
		check(a() == 1 && a() == 2 && b() == 1, "independent closures")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The first returns 1 then 2; the second starts at 1.

Each constructor invocation creates its own captured state. Sharing a single returned closure would share that state instead.

## Exercises

### Exercise 1: Capture a changing variable: change one input

Copy worked example 1, change `factor = 3` to `factor = 4` and predict the failure before running; then restore the line.

**Expected:** The edited run panics with `capture variable` because `multiply(4) == 12` no longer holds.

**Verify:** Restoring `factor = 3` makes the check pass again with the worked observation: the closure uses the new factor 3.

### Exercise 2: Create independent counters: diagnose an edited check

A careless edit rewrote the check in worked example 2 as `check(a() != 1 && a() == 2 && b() == 1, "independent closures")`. Explain the failure, then restore it.

**Expected:** The defective run panics with `independent closures`; after restoring `check(a() == 1 && a() == 2 && b() == 1, "independent closures")`, the first returns 1 then 2; the second starts at 1.

**Verify:** The edited check fails with message `independent closures` for a state that `a() == 1 && a() == 2 && b() == 1` accepts.

### Exercise 3: Inject a transformation

Map a doubling callback over 1, 2 and 3.

**Expected:** The result is 2, 4 and 6.

**Verify:** Your solution must keep `len(v) == 3 && v[0] == 2 && v[2] == 6` true. Control: changing `v := mapInts([]int{1, 2, 3}, func(x int) int { return 2 * x })` to `v := mapInts([]int{1, 2, 3}, func(x int) int { return 2 + x })` panics with message `callback`; revert it.

### Exercise 4: Stop a visitor early

Visit 1 through 5 and stop after observing 3.

**Expected:** Exactly three values are visited.

**Verify:** Your solution must keep `count == 3` true. Control: changing `visit(5, func(x int) bool { count++; return x < 3 })` to `visit(5, func(x int) bool { count++; return x <= 3 })` panics with message `early stop`; revert it.

### Exercise 5: Handle an empty traversal

Visit an empty range with a callback that would increment a count.

**Expected:** The callback is never invoked.

**Verify:** Your solution must keep `count == 0` true. Control: changing `count := 0` to `count := 1` panics with message `empty callback`; revert it.

### Exercise 6: Transfer the visitor to a range-over-func iterator

Range over an iter.Seq[int] that yields 1 through 5, append each value, and break after 2.

**Expected:** The loop collects 1 and 2, and the iterator produces exactly two values.

**Verify:** Your solution must keep `len(got) == 2 && got[0] == 1 && got[1] == 2 && produced == 2` true. Control: changing `if x == 2 {` to `if x != 2 {` panics with message `range over func`; revert it.

## Common pitfalls and diagnosis

Assuming a closure snapshots its variables is the usual surprise: it refers to them, so later assignments are visible. The reverse mistake is sharing one closure where independent state was intended. With iterators, the dangerous bug is calling yield again after it returned false, which panics in a range-over-func loop. Return immediately when the consumer stops, and keep side effects visible to tests.

## Progressive hints

### Hint for investigation 1: Capture a changing variable: change one input

1. Restate the expected observation: The closure uses the new factor 3.
2. The closure refers to factor itself. Which value does factor hold when multiply runs?
3. With factor set to 4 before the call, multiply(4) returns 16, so `multiply(4)==12` fails. The closure still reads the variable; only the last assignment changed.

### Hint for investigation 2: Create independent counters: diagnose an edited check

1. Restate the expected observation: The first returns 1 then 2; the second starts at 1.
2. Each makeCounter call creates a new n. Which counter do the first two calls advance?
3. The first call of a returns 1, so `a()!=1` is false and `&&` stops there. A fresh counter starts at 1, so restore `a()==1`.

### Hint for investigation 3: Inject a transformation

1. Restate the expected observation: The result is 2, 4 and 6.
2. mapInts allocates out with the input length. What does the callback do to each element?
3. The traversal owns iteration while the callback owns the element transformation.

### Hint for investigation 4: Stop a visitor early

1. Restate the expected observation: Exactly three values are visited.
2. The callback returns `x<3`. After which value does visit receive false?
3. The stop decision occurs after the third callback.

### Hint for investigation 5: Handle an empty traversal

1. Restate the expected observation: The callback is never invoked.
2. With limit 0 the loop condition is false at once. How many callbacks run?
3. A caller should not need a fabricated sentinel callback to learn that there were no values.

### Hint for investigation 6: Transfer the visitor to a range-over-func iterator

1. Restate the expected observation: The loop collects 1 and 2, and the iterator produces exactly two values.
2. break makes yield return false. How many values has the iterator produced by then?
3. Since Go 1.23 a for statement can range over a function with the iter.Seq shape func(yield func(int) bool).
