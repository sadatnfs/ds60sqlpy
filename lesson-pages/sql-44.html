Day 44: Monitoring and Diagnostics#

How to run this lesson#

In ./classroom, choose PostgreSQL, open sql-44 and run it with Whole SQL lesson (psql) against advanced_sql_training. Day 44 reads the server's own state rather than changing course tables: the script opens BEGIN, lists non-idle sessions from pg_stat_activity, prints an EXPLAIN ANALYZE plan for a category join and ends with ROLLBACK. Its pg_stat_statements query is commented out, so the starter never touches that optional extension. Your editable copy is .learning/sql/sql-44/lesson/workspace/sql/postgres-60day/day44_monitoring_diagnostics.sql in the Docker learning volume. In our private PostgreSQL 17 container the transcript was BEGIN, SET, a one-row session list, a plan of about 21 lines under QUERY PLAN, and ROLLBACK. The session list depends on who else is connected, so the classroom can show more rows; the one row you can count on is your own script, which is active while it runs. psql runs the file with ON_ERROR_STOP, so the first ERROR ends the run. Setup and resume live in the classroom launch steps; JupyterLab users can take the contributor notebook path instead.

Level and prerequisites#

  • Level: Advanced
  • Prerequisites: Day 43; logical backup and recovery Day 43 staged customer rows and checked them inside BEGIN/ROLLBACK; Day 44 writes no course rows at all and reads the server's activity views instead.
  • Artifacts: learner SQL · solution reasoning · executable solution

A beginner's mental model for this lesson#

Day 44 reads two kinds of evidence that look alike and mean different things. pg_stat_activity is a live view with one row per server process at this instant. pg_stat_statements, when installed and loaded, keeps running totals per statement shape since its statistics were last reset. The first answers "what is running now?"; the second answers "what has cost the most so far?".

A Backend PID is the process ID of one connection, and pid is the key of every session exercise because it is unique in pg_stat_activity. Your own monitoring query has one too, returned by pg_backend_pid(), which is why the solution adds pid <> pg_backend_pid() when it lists active work: without it, the query reports itself. At rest our container's view held six rows: the script's own client backend plus five background processes (checkpointer, background writer, WAL writer, autovacuum launcher and logical replication launcher), all with a NULL state.

A Wait event names what a backend is waiting for. A second session sleeping in pg_sleep(6) showed wait_event_type Timeout and wait_event PgSleep; a session left open after BEGIN; SELECT 1; showed Client and ClientRead, meaning the server is waiting for the client's next command. Both wait columns are NULL when an active backend is busy rather than waiting. A long runtime with a Lock wait is a different problem from a long runtime with no wait at all.

A Normalized statement is the unit pg_stat_statements counts: constants are replaced by placeholders, so WHERE order_id = 7 and WHERE order_id = 8 add to one entry with one queryid. Its calls, mean_exec_time and total_exec_time describe that shape over many runs, never one session.

Read every session query in logical clause order: FROM pg_stat_activity yields one row per process, WHERE keeps the states the exercise names, and only then does SELECT compute an age. Because WHERE runs first, any test on state silently drops the background processes too, since NULL <> 'idle' is not true.

Two worked SQL examples#

Both excerpts come from day44_monitoring_diagnostics.sql and run between its BEGIN and ROLLBACK. The first reads the system view pg_stat_activity, which lives in pg_catalog; PostgreSQL searches that schema before training and public even though the file's SET search_path line does not name it. The second sends the course tables order_items, products and orders through EXPLAIN ANALYZE.

Example 1#
SELECT
  pid,
  usename,
  datname,
  state,
  query_start,
  NOW() - query_start AS running_for,
  left (query,
    120) AS query
FROM
  pg_stat_activity
WHERE
  state <> 'idle'
ORDER BY
  running_for DESC
LIMIT 20;

How to read it: FROM pg_stat_activity produces one row per server process. WHERE state <> 'idle' keeps active and idle-in-transaction sessions and drops the background processes, whose state is NULL. SELECT computes running_for as NOW() - query_start and trims the SQL text with left(query, 120). ORDER BY running_for DESC puts the oldest statement first and LIMIT 20 keeps at most twenty. Compare it with the first exercise: there is no pid <> pg_backend_pid() filter and no wait columns yet.

Expected result/shape: In our quiet container it returned one row: the script itself, user postgres, database advanced_sql_training, state active, and a running_for of about -00:00:00.0002. The negative age is real. NOW() is frozen at the start of the transaction, the BEGIN line, while query_start is the start of this later SELECT, so the subtraction runs backwards; after a pg_sleep(0.2) inside the same transaction the gap grew to about minus 0.2 seconds. The solution uses clock_timestamp(), which reads the clock when the row is evaluated. The query column prints over several lines ending in + because the stored SQL text keeps its line breaks. Your pid will differ.

Example 2#
EXPLAIN ANALYZE
SELECT
  p.category,
  SUM(oi.quantity) AS qty
FROM
  order_items oi
  JOIN products p ON p.product_id = oi.product_id
  JOIN orders o ON o.order_id = oi.order_id
WHERE
  o.order_date >= now() - interval '180 days'
GROUP BY
  p.category
ORDER BY
  qty DESC;

How to read it: EXPLAIN ANALYZE runs the query for real and prints the plan with measured times instead of the result rows. Underneath, the query starts from order_items, joins each line to its product and its order, keeps orders placed in the last 180 days, sums quantity per p.category and sorts by that sum. Read the plan from the most indented nodes outward, because those produce rows first.

Expected result/shape: Our plan had 21 lines: a Sort on sum(oi.quantity) DESC above a HashAggregate keyed on p.category, above two hash joins. The inner join scans all 13,085 order_items rows and hashes orders after a Filter on order_date kept 1,538 orders and removed 2,824; the outer join hashes the 300 products. The planner estimated 4,608 joined lines and 4,665 arrived, 6 groups came out, every node ran once (loops=1), and execution took 2 to 6 ms across our runs. The same query without EXPLAIN ANALYZE returned Apparel 2,382, Beauty 2,382, Books 2,338, Sports 2,324, Electronics 2,305 and Home 2,287. Apparel and Beauty tie, and ORDER BY qty DESC has no second key, so their order is not guaranteed. Because the window is now() - interval '180 days', these counts move as the calendar passes the fixture's order dates; ours were taken two days after its newest order.

Learning objectives#

  • Distinguish active session state from aggregated statement history.
  • Collect wait, runtime, and plan evidence before proposing intervention.

Vocabulary and concepts#

  • Wait event: the resource or condition an active backend is waiting on.
  • Backend PID: the process identifier for one PostgreSQL session.
  • Normalized statement: structurally equivalent SQL grouped for aggregate statistics.

Worked example / walkthrough#

Query pg_stat_activity, exclude pg_backend_pid(), and calculate runtime only for active statements. For one row, read user, state, wait type/event, and query together; a long duration alone does not prove a fault or authorize termination.

Common mistakes and how to recover#

  • Lesson-specific semantic mistake: treating the monitoring query's own row as a finding. Example 1 has no pid <> pg_backend_pid() filter, so on a quiet server its only row is the script itself, active, with a negative running_for. Exclude your own pid before reading anything into the list.
  • A negative or shrunken age: NOW() returns the transaction start, so inside the file's BEGIN it is earlier than the current statement's query_start, and every other session's age is short by the time since BEGIN. Use clock_timestamp() for ages computed inside a transaction.
  • Background processes vanish or crowd in: any WHERE test on state drops every process whose state is NULL, while the unfiltered connection summary keeps them as NULL groups. In our container they were five of the six rows, so decide which view you want before counting.
  • Missing failed transactions: state = 'idle in transaction' does not match idle in transaction (aborted). That is correct for a lock hunt (our aborted session held no relation locks), but a connection count must still include those sessions, because each one occupies a slot until ROLLBACK.
  • relation "pg_stat_statements" does not exist: a plain query naming the view fails this way when the extension is absent, and an installed but unloaded extension raises pg_stat_statements must be loaded via "shared_preload_libraries" (SQLSTATE 55000). Keep the solution's to_regclass check and narrow handler instead of installing anything.
  • psql stopped partway: fix the first error and rerun the whole file from BEGIN; the failure recovery checklist covers container and path problems.

Deep dive and reference#

What you will learn#

  • Find active statements and calculate their current runtime.
  • Interpret wait events before deciding that a query is stuck.
  • Read optional aggregate statement statistics when the extension is available.

How the learner script works#

The starter queries pg_stat_activity, then runs EXPLAIN ANALYZE on recent category units. Its pg_stat_statements query is commented because the extension may require server configuration and elevated access.

There are three distinct states to reason about:

  1. Absent: to_regclass('public.pg_stat_statements') is NULL.
  2. Installed but not loaded: the view exists, but reading it raises object_not_in_prerequisite_state because shared_preload_libraries did not load the module at server startup.
  3. Installed and loaded: the view is readable and can be ranked.

The portable solution treats the first two states as an explained empty optional result. It catches only the known not-preloaded condition; unrelated SQL errors still stop the script and must be diagnosed.

The course server runs PostgreSQL 17, where the relevant extension columns include calls, total_exec_time and mean_exec_time. These _exec_time names date from PostgreSQL 13; older examples that read total_time or mean_time fail against this version.

Practice map#

The six numbered exercises above are the practice set, in two families. The first, third, fourth and sixth read pg_stat_activity, and on a quiet server three of them correctly return nothing. When you can open a second psql connection, leave it in pg_sleep or in an open BEGIN while you run your answers, then ROLLBACK it. The second and fifth read pg_stat_statements through the temporary top_statement_stats table that the second one builds, so write that one first; without the extension both print an empty result after a NOTICE. The data checks quote our container, where the number of open sessions changed between runs, so compare shapes, states and orderings rather than exact ages.

Interpretation and safety#

  • A long-running query can be legitimate; inspect owner, purpose, wait state, locks, and plan before intervening.
  • pg_stat_statements aggregates normalized statement history; it is not a list of currently active sessions.
  • Statistics reset, server restarts, and extension availability affect the observation window.
  • Never install extensions, change shared_preload_libraries, reset statistics, cancel queries, or terminate backends merely to complete this lesson.
  • The executable solution remains portable by checking for the extension view, using dynamic SQL only when it exists, and catching only the defined installed-but-not-preloaded SQLSTATE around that optional read.

Expanded practice lab#

Prompts 3-6 build read-only operational judgment. query_start measures the current statement while xact_start measures the enclosing transaction; show both because long idle transactions can retain locks and old snapshots.

Aggregate connection counts instead of exposing full SQL text in a shared report. For historical workload, examine both mean_exec_time and total_exec_time: one reveals expensive calls, the other cumulative load. Never cancel a session as part of this practice.

Day 44 Solutions: Monitoring and Diagnostics#

How to study and run this solution#

Open this explanation only after making an honest attempt. The executable companion runs solely against the disposable advanced_sql_training database:

# Linux, macOS, or Windows through WSL 2, from the repository root
psql -X -v ON_ERROR_STOP=1 -d advanced_sql_training \
  -f sql/postgres-60day/solutions/day44_solutions.sql

In our container psql printed BEGIN, SET, an empty active-session list, CREATE TABLE for top_statement_stats, the NOTICE that pg_stat_statements is not installed, DO, the empty ranking, an empty age list, a three-row connection summary, the empty ranking again, an empty idle-in-transaction list and ROLLBACK. Empty lists are the right answer on a quiet server; open a second session if you want rows to inspect. The NOTICE is expected, but an ERROR is not, because the handler catches only the not-preloaded case. The solution reading notes describe how to compare your attempt.

Clause-by-clause reading map#

The file has two halves. The session half is four plain queries over pg_stat_activity; read each in logical order: FROM yields one row per process, WHERE picks the states, SELECT computes ages with clock_timestamp(), and ORDER BY puts the oldest first. The statistics half has three parts:

  • CREATE TEMP TABLE top_statement_stats declares the ten output columns, so the result keeps one shape whether or not the extension exists.
  • A DO block asks to_regclass('public.pg_stat_statements') whether the view exists and only then runs two INSERT ... SELECT statements through EXECUTE: one ranked by total_exec_time, one by mean_exec_time, each numbered with row_number() and cut to ten rows.
  • An inner BEGIN ... EXCEPTION WHEN object_not_in_prerequisite_state block catches the SQLSTATE 55000 error an installed but unloaded extension raises, empties the table and prints its own NOTICE. Any other error still stops the run.

Two final SELECTs read the table in ranking, rank_position order, once as SELECT * and once with every column named.

The two deliverables inspect active work and, when available, pg_stat_statements. The solution remains runnable on a fresh PostgreSQL installation where that optional extension is absent or installed without its shared-memory module being loaded at server startup. See day44_solutions.sql.

Exercise 1: Longest-running active statements#

SET search_path TO training, public;

SELECT
  pid,
  usename,
  datname,
  state,
  clock_timestamp() - query_start AS runtime,
  wait_event_type,
  wait_event,
  left (query,
    160) AS query
FROM
  pg_stat_activity
WHERE
  state = 'active'
  AND pid <> pg_backend_pid()
ORDER BY
  runtime DESC NULLS LAST;

Expected shape: zero or more currently active sessions, excluding the monitoring query itself. A long runtime can be normal; inspect wait events, locks, and the operation's purpose before intervening.

Exercise 2: Optional top statement statistics#

BEGIN;
SET search_path TO training, public;

CREATE TEMP TABLE top_statement_stats (
  ranking text,
  rank_position integer,
  userid oid,
  dbid oid,
  toplevel boolean,
  queryid bigint,
  query text,
  calls bigint,
  mean_exec_time double precision,
  total_exec_time double precision
);

DO $optional_pg_stat_statements$
BEGIN
  IF to_regclass('public.pg_stat_statements') IS NOT NULL THEN
    BEGIN
      EXECUTE $by_total$
        INSERT INTO top_statement_stats
        SELECT 'total_exec_time',
               row_number() OVER (
                 ORDER BY total_exec_time DESC,
                          userid, dbid, toplevel, queryid
               )::integer,
               userid,
               dbid,
               toplevel,
               queryid,
               left(query, 200),
               calls,
               mean_exec_time,
               total_exec_time
        FROM public.pg_stat_statements
        ORDER BY total_exec_time DESC, userid, dbid, toplevel, queryid
        LIMIT 10
      $by_total$;
      EXECUTE $by_mean$
        INSERT INTO top_statement_stats
        SELECT 'mean_exec_time',
               row_number() OVER (
                 ORDER BY mean_exec_time DESC,
                          userid, dbid, toplevel, queryid
               )::integer,
               userid,
               dbid,
               toplevel,
               queryid,
               left(query, 200),
               calls,
               mean_exec_time,
               total_exec_time
        FROM public.pg_stat_statements
        ORDER BY mean_exec_time DESC, userid, dbid, toplevel, queryid
        LIMIT 10
      $by_mean$;
    EXCEPTION
      WHEN object_not_in_prerequisite_state THEN
        TRUNCATE top_statement_stats;
        RAISE NOTICE
          'pg_stat_statements exists but is not loaded via shared_preload_libraries; optional result is empty';
    END;
  ELSE
    RAISE NOTICE 'pg_stat_statements is not installed; optional result is empty';
  END IF;
END
$optional_pg_stat_statements$;

SELECT
  *
FROM
  top_statement_stats
ORDER BY
  ranking,
  rank_position;

ROLLBACK;

Expected shape: up to twenty rows when pg_stat_statements is installed and loaded, at most ten for each ranking label. Otherwise the block emits an explanatory notice and the final query returns an empty result.

An existence check is necessary but not sufficient. PostgreSQL can install the extension's view without loading its shared-memory module at server startup. The nested block catches only that documented object_not_in_prerequisite_state condition. PL/pgSQL rolls back either partial ranking inside the nested block, and TRUNCATE makes the empty-result contract explicit. Any unrelated error still propagates.

Reasoning and verification#
  • Inputs/evidence: For sql-44 Exercise 2, inspect to_regclass('public.pg_stat_statements'), then read the optional public.pg_stat_statements view into the course-owned temporary top_statement_stats table. Build ranking, rank_position, userid, dbid, toplevel, queryid, query, calls, mean_exec_time, and total_exec_time; do not install the extension or reset shared statistics.
  • Expected result/shape: For sql-44 Exercise 2, expected output: up to 20 rows when pg_stat_statements is installed and loaded, with at most 10 rows per ranking label (total_exec_time and mean_exec_time); otherwise emit an explanatory notice and return an empty result. Each row is one statement within a ranking, identified by (ranking, userid, dbid, toplevel, queryid). The final columns are ranking, rank_position, userid, dbid, toplevel, queryid, query, calls, mean_exec_time, and total_exec_time. The final order is ranking, rank_position.
  • Independent verification: For sql-44 Exercise 2, if the optional view is absent or raises object_not_in_prerequisite_state because the module was not preloaded, require an explanatory notice and an empty result. If it is readable, require only the total_exec_time and mean_exec_time labels, at most 10 rows per label, unique (ranking, userid, dbid, toplevel, queryid), consecutive rank_position values from 1 through N, nonincreasing total_exec_time order for its label, nonincreasing mean_exec_time order for its label, and values that match a fresh read of public.pg_stat_statements.
  • Intermediate relation check: Check the branch before the ranking: SELECT to_regclass('public.pg_stat_statements') returned NULL in our container, which sends the block straight to the not-installed NOTICE. When the view is readable, run each INSERT's SELECT by itself and confirm that rank_position runs 1, 2, 3 without gaps in each list before reading the combined table.

LIMIT 10 use the same five keys, so the ten rows kept are exactly positions 1 to 10. The four tie-breakers are the view's identity: one normalized statement per user, database and top-level flag. left(query, 200) shortens the stored text, and the mean branch repeats the pattern with mean_exec_time DESC first.

  • state = 'active' is more precise than state <> 'idle' for the requested active-query list.
  • clock_timestamp() advances during the statement and is appropriate for an observed runtime.
  • Checking to_regclass keeps a missing extension view from ever being read. Inside PL/pgSQL the IF alone is enough, because a table name is resolved only when its statement first runs (a static PERFORM on the view inside the skipped branch ran cleanly in our container); EXECUTE makes that deferral explicit. Outside a DO block, a plain query naming the view fails with relation "pg_stat_statements" does not exist.
  • These are diagnostic reads. Do not cancel or terminate sessions without confirming ownership and operational impact.

  • Expected result/shape: For sql-44 Exercise 6, expected output: one row per pid whose state is idle in transaction. The final columns are pid, usename, datname, transaction_age, wait_event_type, and wait_event. The final order is transaction_age DESC NULLS LAST.
  • Independent verification: For sql-44 Exercise 6, confirm 0 rows on a quiet server; then open a second psql session, run BEGIN; SELECT 1;, and leave it open: confirm exactly one row with a unique pid, wait_event_type Client, wait_event ClientRead, and a growing transaction_age, while an aborted session (BEGIN; SELECT 1/0;) does not appear; run ROLLBACK in the open session and confirm the row disappears. Do not cancel or terminate the session.
  • Intermediate relation check: Before filtering, list pid, state for every client backend. With our controlled sessions that showed idle in transaction, idle in transaction (aborted) and two active rows (one of them the check itself), and the filter keeps only the first.
  • Clause check: The equality state = 'idle in transaction' does not match the aborted variant. wait_event_type Client with wait_event ClientRead means the server is waiting for the client to send something, not for a lock; the risk is in what the idle session holds, which other sessions may be waiting on. clock_timestamp() - xact_start measures how long it has held it.
  • Alternative/trade-off: Joining pg_locks on pid shows what an idle transaction holds: in our test, AccessShareLock on training.customers for a session that had run LOCK TABLE, and a backend_xmin snapshot plus locks on orders for a REPEATABLE READ session that had counted orders. That join changes the grain to one row per lock, so keep it as a follow-up query rather than the answer.
  • Edge case: A correct result may be empty. Create the state only in a controlled second session, then cleanly roll it back.

-- Day 44 solutions: monitoring and diagnostics
-- SOLUTION READING MAP for sql-44: Monitoring and Diagnostics
-- Explanation: sql/postgres-60day/solutions/day44_solutions.md
-- Run from the repository root only against advanced_sql_training:
--   psql -X -v ON_ERROR_STOP=1 -d advanced_sql_training -f sql/postgres-60day/solutions/day44_solutions.sql
-- Read each answer from inputs to output: establish FROM/JOIN grain; apply
-- row filters; group/aggregate; filter groups; compute windows; project named
-- keys/measures; then order with a deterministic tie-breaker. Treat every CTE
-- as an intermediate relation whose keys, row count, and totals can be checked.
-- A command tag is not enough for DDL/DML: inspect catalogs or before/after
-- rows, test a boundary case, and reconcile with an independent control.
-- NULL, zero, empty input, missing rows, and ties need explicit policies.
-- The documented transaction/cleanup boundary must leave no unintended persistent object.
--
BEGIN;
SET search_path TO training, public;

-- Exercise 1: longest-running active statements, excluding this session.
SELECT
  pid,
  usename,
  datname,
  state,
  clock_timestamp() - query_start AS runtime,
  wait_event_type,
  wait_event,
  left (query,
    160) AS query
FROM
  pg_stat_activity
WHERE
  state = 'active'
  AND pid <> pg_backend_pid()
ORDER BY
  runtime DESC NULLS LAST;

-- Exercise 2: pg_stat_statements is optional. Dynamic SQL keeps this file
-- runnable when the extension is not installed.
CREATE TEMP TABLE top_statement_stats (
  ranking text,
  rank_position integer,
  userid oid,
  dbid oid,
  toplevel boolean,
  queryid bigint,
  query text,
  calls bigint,
  mean_exec_time double precision,
  total_exec_time double precision
);

DO $optional_pg_stat_statements$
BEGIN
  IF to_regclass('public.pg_stat_statements') IS NOT NULL THEN
    BEGIN
      EXECUTE $by_total$
        INSERT INTO top_statement_stats
        SELECT 'total_exec_time',
               row_number() OVER (
                 ORDER BY total_exec_time DESC,
                          userid, dbid, toplevel, queryid
               )::integer,
               userid,
               dbid,
               toplevel,
               queryid,
               left(query, 200),
               calls,
               mean_exec_time,
               total_exec_time
        FROM public.pg_stat_statements
        ORDER BY total_exec_time DESC, userid, dbid, toplevel, queryid
        LIMIT 10
      $by_total$;
      EXECUTE $by_mean$
        INSERT INTO top_statement_stats
        SELECT 'mean_exec_time',
               row_number() OVER (
                 ORDER BY mean_exec_time DESC,
                          userid, dbid, toplevel, queryid
               )::integer,
               userid,
               dbid,
               toplevel,
               queryid,
               left(query, 200),
               calls,
               mean_exec_time,
               total_exec_time
        FROM public.pg_stat_statements
        ORDER BY mean_exec_time DESC, userid, dbid, toplevel, queryid
        LIMIT 10
      $by_mean$;
    EXCEPTION
      WHEN object_not_in_prerequisite_state THEN
        -- The extension can be installed (so its view exists) without being
        -- loaded at server startup. Roll back either partial ranking and
        -- preserve the same empty optional-result contract as absence.
        TRUNCATE top_statement_stats;
        RAISE NOTICE
          'pg_stat_statements exists but is not loaded via shared_preload_libraries; optional result is empty';
    END;
  ELSE
    RAISE NOTICE 'pg_stat_statements is not installed; optional result is empty';
  END IF;
END
$optional_pg_stat_statements$;

SELECT
  *
FROM
  top_statement_stats
ORDER BY
  ranking,
  rank_position;

-- Exercise 3: transaction age can exceed statement age, especially for
-- idle-in-transaction sessions.
SELECT
  pid,
  usename,
  state,
  clock_timestamp() - xact_start AS transaction_age,
  clock_timestamp() - query_start AS statement_age
FROM
  pg_stat_activity
WHERE
  pid <> pg_backend_pid()
  AND state <> 'idle'
ORDER BY
  transaction_age DESC NULLS LAST;

-- Exercise 4: aggregate rather than exposing full statement text.
SELECT
  datname,
  usename,
  state,
  COUNT(*) AS connections
FROM
  pg_stat_activity
GROUP BY
  datname,
  usename,
  state
ORDER BY
  datname,
  usename,
  state;

-- Exercise 5: retain both rankings. Mean identifies costly calls; total time
-- captures cumulative workload impact.
SELECT
  ranking,
  rank_position,
  userid,
  dbid,
  toplevel,
  queryid,
  query,
  calls,
  mean_exec_time,
  total_exec_time
FROM
  top_statement_stats
ORDER BY
  ranking,
  rank_position;

-- Exercise 6: this is diagnostic only; do not cancel or terminate sessions.
SELECT
  pid,
  usename,
  datname,
  clock_timestamp() - xact_start AS transaction_age,
  wait_event_type,
  wait_event
FROM
  pg_stat_activity
WHERE
  state = 'idle in transaction'
ORDER BY
  transaction_age DESC NULLS LAST;
