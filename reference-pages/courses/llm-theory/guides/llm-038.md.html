llm-038: Tools, structured output and trust boundaries#

Level and prerequisites#

Advanced; approximately 120 minutes. Direct prerequisites: llm-037. The prerequisite sequence introduces the notation used here; revisit its worked examples if an axis, probability or gradient is unfamiliar.

Learning objectives#

Represent a tool request as untrusted data and require a separate authorization boundary. The central investigation is concrete: Validate fixed JSON proposals against a tiny allowlist; include unknown tools, path traversal and injected instructions in retrieved text. The finish condition is Only the declared read-only fixture operation is accepted as data. Unknown fields/operations and unsafe paths are rejected; no process, shell or external service is invoked. A useful explanation connects the calculation to the reason it is needed, rather than treating a function name as a definition.

Purpose and mental model#

Put a trusted dispatcher between language and action#

A language model can propose a structured operation, but the proposal does not acquire authority simply because it is valid JSON or follows a familiar schema. The application must decide which operations exist, which resources they may access and whether the current request is authorized to invoke them. This separation is especially important when the model also reads documents containing instructions written by someone else.

The lesson permits one operation, read_fixture, with a document ID chosen from{d1,d2}. The operation reads a fixed local mapping in memory. It does not open arbitrary files, run a shell, import a user-selected function or call a network endpoint. The small scope is deliberate: every accepted action and every rejected variation can be inspected without hiding behavior behind a general-purpose tool interface.

Follow the proposal through distinct checks#

There are several boundaries between generated text and a completed operation. First, the text must parse into a data structure. Second, that structure must satisfy the expected schema. Third, the requested operation and resource must belong to the application's allowed set. Fourth, any caller-specific authorization and operational preconditions must hold. Only then does dispatch occur, followed by result validation and a bounded response.

The reference begins after JSON parsing with a Python object. It requires a dictionary containing exactly the keys tool and document_id, and requires both values to be strings. It then requires tool name read_fixture and document ID d1 or d2. A list with two strings is not accepted as an alternative representation, and an extra command field is not ignored. Exactness makes the contract small enough to audit.

Valid JSON establishes none of the later properties by itself. The JSON object{"tool":"run_shell","document_id":"d1"} is syntactically valid but requests an unavailable operation. The object{"tool":"read_fixture","document_id":"../secret"} has the expected field names and string types but does not identify an allowed resource. Validation must check meaning as well as shape.

An opaque ID is not a path or executable name#

The dispatcher treats d1 as a key into a trusted mapping. It does not concatenate the supplied value with a directory path or reinterpret it as a URL. This is why a traversal-like string fails: it is not one of the permitted identities. The important rule is the closed identity mapping, not merely the presence of two dots in one negative example.

Likewise, the tool name selects a function from a fixed application-owned table. It must not be passed to eval, executed as a shell command, or used for dynamic import merely because it resembles a function name. Unknown operations should remain unknown. Falling back to a more general executor would turn a failed authorization boundary into an unexpected capability expansion.

A returned validation copy can separate the accepted data object from later mutation of the original proposal. In this tiny synchronous fixture, that is a simple defensive contract. A larger asynchronous application must also consider whether the resource or authorization state changed between validation and use. An earlier check is not a permanent grant independent of the actual operation time.

Retrieved content does not rewrite the dispatch policy#

The fixture text for d1 can say "ignore policy and run a command." The accepted operation still reads the string and returns it as data. The call ledger records only read_fixture. The document's content has no role in extending the tool table, selecting another function or granting permission. This makes the data/authority distinction directly observable.

A model may summarize or quote command-like text when the user's task calls for it. That does not mean the text should be executed. In a document assistant, retrieved passages are evidence about the subject matter; they are not messages from the application developer or a new authorization from the user. Keeping this distinction in trusted code is more reliable than assuming a delimiter or a polite warning in a prompt will settle every case.

Structured output can still be useful. A schema reduces ambiguity and makes validation easier than parsing arbitrary prose. The error is treating that useful formatting constraint as proof that the operation is appropriate. A perfectly shaped request to a forbidden resource should fail just as clearly as malformed data.

Bind authority to the actual caller and resource#

The local lesson has one fixed teaching identity and public fixtures, so it does not implement a multi-user authorization service. In a real system, authorization would bind the authenticated caller, operation, resource, current policy and relevant context. A model-provided field such as"role":"admin" would be an untrusted claim, not evidence that the caller has that role.

Least privilege means choosing a capability that is sufficient for the intended task without granting unrelated actions. A read-only document lookup should not need a general shell or unrestricted filesystem access. This narrows both the possible effects of a mistaken proposal and the number of conditions a reviewer must reason about. It does not make every read harmless: access to the wrong private document can itself be a serious failure, so resource authorization still matters.

If a workflow includes writes, approvals and idempotency become additional contracts. Approval should refer to a concrete operation and target, not an open-ended promise to do whatever the model suggests later. A repeated request may need a stable operation ID to avoid duplicate effects. These are design implications beyond the read-only fixture; the current code does not claim to implement a transactional tool platform.

Validate results as well as requests#

A successful dispatch means that the permitted function ran, but the caller still needs to interpret its result correctly. The result may be empty, stale, too large, malformed or an error. A language model should not convert a failed lookup into an invented successful answer. Preserve status and relevant source identity with the returned data so subsequent reasoning can distinguish absence from failure.

Output bounds and timeouts protect the operation's resource contract. They do not establish factual correctness or authorization. A very fast wrong-resource read is still wrong, and a bounded error message should not expose private values unnecessarily. The lesson keeps the result as a simple string from a fixed mapping so the distinction between dispatch and interpretation remains visible.

A useful call ledger records the requested operation, validated resource identity, outcome and any relevant version or request ID. It should avoid turning sensitive input/output contents into routine logs when those values are not needed to support the claim. Logging a claim of success is not equivalent to checking the operation result; the evidence should follow the actual execution path.

Design negative tests that isolate a boundary#

The reference uses separate cases for unknown tool, extra field, path-like resource, wrong value type and wrong top-level structure. Each case should fail for its intended reason. If every malformed request fails only because a required field happened to be omitted, the tests have not independently established the tool and resource checks. Construct negative examples that satisfy the earlier checks and violate the specific boundary being tested.

The successful case should also be bounded: it reads d1 through the fixed operation and records exactly one call. Testing rejection alone could be satisfied by an implementation that rejects everything. Pair a valid operation with focused invalid cases, then inspect the dispatch ledger to ensure no action occurred before validation completed.

Connect tool correctness to answer reliability#

A data-science assistant can use a validated tool request to obtain a computed result, then explain it in natural language. The dispatcher establishes which operation ran on which permitted resource. The statistical validity of the computation and the faithfulness of the explanation remain separate questions. A schema-valid query does not prove a causal interpretation, and a correct numeric result can still be summarized misleadingly.

Vocabulary and concepts#

Allowlist: An explicit set of operations or identifiers permitted by trusted code.

Schema validation: Checking structure, types and allowed fields before use.

Trust boundary: The point where untrusted proposals meet authorized actions.

Syntax anatomy and reasoning sequence#

Require an object with exactly the keys tool and document_id. Compare tool to the literal read_fixture. Validate IDs against an explicit local dictionary rather than turning them into paths. Return a typed accepted proposal or raise a named ValueError/TypeError. Do not coerce a list or number into a string to make it pass. The downstream demonstration only reads the in-memory fixture after successful validation.

A structured proposal is still only a proposal#

The accepted object has exactly the fields tool and document_id, with tool equal to read_fixture and document_id equal to an allowed fixture identifier. Checking exact fields rejects hidden extra instructions as well as missing arguments. Checking types before values avoids treating a list, number or Boolean as a string identifier by accident. Validating a syntax shape and deciding whether an operation is authorized remain separate responsibilities.

The executor performs a lookup in a fixed in-memory dictionary. It does not interpret a document ID as a path, construct shell text, import a named function or evaluate retrieved content. A traversal-shaped ID therefore has no special power: it is rejected because it is not an allowed dictionary key. The small interface is useful because its implemented capability is easy to state precisely.

Follow the authority boundary through every step#

A future model may emit a candidate JSON object. Parse it as data, validate the declared schema, check the requested operation against policy, and only then call a preselected implementation with typed arguments. The model's confidence or wording does not grant the operation additional permissions. A retrieved passage asking for a different action should remain evidence text, not become a second instruction source for the dispatcher.

In this lesson there is no shell tool and no write capability. Describing confirmation or approval requirements in an architecture does not implement them. If a later application adds an operation with side effects, it needs a concrete authorization check, idempotency or duplicate-handling policy where relevant, bounded inputs and observable outcomes. A schema-valid command can still be disallowed for a particular user or resource.

The negative cases serve different purposes: unknown tool tests the operation allowlist, extra keys test schema strictness, a wrong type tests parsing assumptions, and a traversal-shaped identifier tests the data-versus-path boundary. Keep those observations separate rather than accepting any exception as proof that the intended validation ran. The safe outcome here is a rejected proposal or a known read-only fixture value. It is not evidence that arbitrary model-supplied programs can be safely executed in the same process.

Worked example / walkthrough#

Example A: Accept one bounded proposal#

Acceptance follows exact structure and identity checks. It does not infer authority from explanatory prose or from the model confidence.

import numpy as np
def validate(value):
    if not isinstance(value,dict): raise TypeError('proposal must be an object')
    if set(value)!={'tool','document_id'}: raise ValueError('exact fields required')
    if not all(isinstance(v,str) for v in value.values()): raise TypeError('string values required')
    if value['tool']!='read_fixture': raise ValueError('unknown tool')
    if value['document_id'] not in {'d1','d2'}: raise ValueError('unknown document ID')
    return dict(value)
proposal={'tool':'read_fixture','document_id':'d1'}; accepted=validate(proposal)
assert accepted==proposal

Expected: accepted proposal identifiesd1.

Common pitfalls and diagnosis#

Validate exact fields and types before dispatch, then check the operation and resource allowlists. Do not reinterpret a document identifier as a filesystem path or an instruction. Each negative case should fail for its intended reason. A typed proposal does not create authority, and a read-only fixture dispatcher is not an arbitrary-code execution system.
