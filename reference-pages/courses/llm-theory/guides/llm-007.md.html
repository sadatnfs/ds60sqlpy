Purpose and mental model#

A tokenizer is part of a model's data pipeline. Byte-pair encoding learns repeated neighboring-symbol merges from training text, then applies those frozen rules to other text. It does not gain permission to refit itself when validation contains an unfamiliar sequence. The learned merge order and the tie policy are part of the experiment identity.

Our tiny version begins with UTF-8 bytes, so every ordinary byte has a fixed base symbol. A token is represented as a tuple of byte IDs. A separate end-of-word marker uses ID 256, outside the byte range. Merge only inside each word, scan left to right without overlapping replacements, and break equally frequent pair ties lexicographically by these integer tuples.

For training words ab and ac, four adjacent pairs each occur once. The declared tie rule chooses a followed by b. After one merge, ab becomes [(97,98),(256,)], while ac remains separate bytes plus its marker. An unseen d is still a valid base byte; applying a frozen tokenizer to ad must not add a new learned merge. This tiny mechanism provides inspectable tokenizer lineage before embedding IDs and training enter the picture.

Vocabulary and concepts#

Base symbol: a fixed original encoding unit; here one UTF-8 byte ID, plus the separately declared end marker.

Merge rule: an ordered neighboring-token pair replaced by its concatenated token.

Tie policy: a deterministic rule selecting one candidate when pair counts are equal.

Frozen tokenizer: a fixed representation policy and ordered merge list used without fitting on evaluation text.

Nonoverlapping replacement: left-to-right pair replacement that consumes each matched occurrence once rather than reusing one position twice.

Syntax or reasoning anatomy#

Represent byte a as (97,) and byte b as (98,). Merging the pair creates (97,98), preserving their underlying byte sequence. The marker (256,) records the word boundary and is removed by the matching decoder. A merge can include the end marker, but no training pair crosses from one word into the next because each word has its own symbol sequence.

Count every neighboring pair over the current training tokenization, choose the highest count with the declared lexical tie-break, replace its nonoverlapping occurrences, and repeat up to the small merge budget. Save the ordered rules, not just an unordered vocabulary set. Encoding new text applies each saved rule in order. The fixed byte base supplies unseen byte fallback without changing the learned rules or their hash.

Worked example / walkthrough#

Example A: Inspect and apply the tied first merge#

Count byte-token neighbors, choose the documented tie and replace without overlap.

from collections import Counter

corpus = [[(97,), (98,), (256,)], [(97,), (99,), (256,)]]
counts = Counter(pair for word in corpus for pair in zip(word, word[1:]))
maximum = max(counts.values())
pair = min(pair for pair, count in counts.items() if count == maximum)
assert pair == ((97,), (98,))


def merge_once(tokens, chosen):
    result, index = [], 0
    while index < len(tokens):
        if index + 1 < len(tokens) and (tokens[index], tokens[index + 1]) == chosen:
            result.append(tokens[index] + tokens[index + 1])
            index += 2
        else:
            result.append(tokens[index])
            index += 1
    return result


assert merge_once(corpus[0], pair) == [(97, 98), (256,)]
print(pair, merge_once(corpus[0], pair))

Expected: Each candidate count is one. Lexical integer-tuple ordering selects a+b, whose replacement preserves the underlying bytes. Training input order cannot decide a tie accidentally.

Example B: A frozen rule leaves a new byte unmerged#

Reuse the selected rule on validation word ad without calling a fitting function.

rules = [pair]
before = tuple(rules)
validation = [(97,), (100,), (256,)]
for chosen in rules:
    validation = merge_once(validation, chosen)
assert validation == [(97,), (100,), (256,)]
assert tuple(rules) == before
assert bytes(value for token in validation[:-1] for value in token).decode("utf-8") == "ad"
print(validation)

Expected: The d byte is supported by the fixed base. Encoding leaves the learned rule list unchanged; appearing in validation does not justify fitting an a+d merge.

Progressive hints#

  • Hint 1: Write each word as its own byte-token sequence with an end marker.
  • Hint 2: Resolve count ties before replacing tokens, and advance past both positions of a matched pair.
  • Hint 3: The encoding path applies saved rules; only the fitting path may create a new rule.

Common pitfalls#

If two fits disagree, compare candidate counts, the declared tie order and the sequence of already applied rules. Sorting only the final vocabulary cannot recover a different merge history. If a decoder loses characters, inspect whether replacement reused overlapping positions or whether the end marker was confused with a real byte.

If validation improves after refitting the tokenizer, it has influenced representation selection. Freeze rules and base policy first. A byte-level toy tokenizer is not automatically a production tokenizer: it lacks a complete text segmentation, special-token and vocabulary-ID policy. The next unit separates token IDs from embedding feature coordinates. Do not pass arbitrary byte-tuple tokens directly into a learned lookup table without a declared mapping.
