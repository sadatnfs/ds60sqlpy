## Why this mechanism matters

Performance work starts with a behavioral contract and representative input. Complexity predicts growth in work, while a benchmark measures a particular implementation and environment. A linear scan visits each item; binary search repeatedly narrows a sorted interval. Faster execution is useful only if it preserves the result and failure policy. Preallocating slice capacity can avoid growth allocations, but preallocating length creates real zero elements. Tiny timings are noisy. Separate setup from measurement, repeat a representative workload, record environment and check results outside the timing loop. A profile should answer a hypothesis about where time or allocations are spent.

## Vocabulary and concepts

- **Complexity:** How work grows with input size.
- **Monotone predicate:** A predicate changing from false to true at most once over ordered indices.
- **Preallocation:** Reserving storage before appending.

## Syntax anatomy and reasoning

sort.Search finds the first index where a monotone predicate becomes true, or n when none does. It does not sort or validate input. make([]int,0,n) reserves capacity with zero length; make([]int,n) creates n elements. Prepared project benchmarks use testing.B in _test.go files; pprof investigates CPU or allocation evidence rather than establishing a universal speed ranking.

## Worked example / walkthrough

### Worked example 1: Find a lower boundary

Find the first value at least 5 in 2, 4, 6, 8.

```go
package main

import (
	"fmt"
	"sort"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Find a lower boundary
	{
		items := []int{2, 4, 6, 8}
		i := sort.Search(len(items), func(i int) bool { return items[i] >= 5 })
		check(i == 2, "boundary")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** The index is 2.

Sorting makes the predicate monotone. The same expression over unsorted input violates the algorithm precondition.

### Worked example 2: Represent no match

Search for a value at least 9 in the same data.

```go
package main

import (
	"fmt"
	"sort"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Find a lower boundary
	{
		items := []int{2, 4, 6, 8}
		i := sort.Search(len(items), func(i int) bool { return items[i] >= 5 })
		check(i == 2, "boundary")
	}

	// Represent no match
	{
		items := []int{2, 4, 6, 8}
		i := sort.Search(len(items), func(i int) bool { return items[i] >= 9 })
		check(i == len(items), "not found")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** The index equals the collection length.

The sentinel is not a valid element index. Check it before indexing.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
