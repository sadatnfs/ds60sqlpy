mle-012: A real HTTP contract before a network deployment#

Level and prerequisites#

Intermediate. Direct prerequisites: mle-007, mle-008, mle-011

Outcome: Define and test a serving contract with positive and negative requests.

Question and mechanism#

A serving interface should define which inputs it accepts and what evidence it returns. Validation errors are part of that interface, not an incidental exception path. The model version and feature contract should be visible so a prediction can be interpreted and compared with its source artifact.

This lesson exercises an actual FastAPI application through an in-process ASGI client. It tests HTTP parsing, schema validation, route execution and response encoding without starting a network server. The first case compares the route's probability with the same model's direct prediction. The second rejects a negative usage value and an undeclared target field.

These checks do not establish DNS, sockets, container networking, load capacity or external authentication. The complete local-system project later starts a real loopback HTTP service and qualifies those declared lifecycle paths separately. Keeping the evidence layers distinct prevents a useful unit-level API test from being mislabeled as a deployed system.

Syntax and data contract#

The Pydantic request model declares bounded usage/tickets and an allowed region vocabulary, with extra fields forbidden. A POST route converts the validated object into the model's expected frame and returns a numeric probability plus version. TestClient sends real ASGI requests inside the process. The networked project uses the same contract principles with Docker-owned state and loopback publication.

Run the lesson#

Open this subject in /classroom, then show its code and notes. The prepared data-engineering worker runs main.py in a fresh temporary directory. The guide distinguishes this local execution from the deployment decisions that need an owned production environment.

Worked case 1: Compare HTTP-contract and direct inference#

The first case submits a valid JSON body through the application. It checks status 200, the version label and numeric agreement with direct model inference. That makes the route behavior observable.

Expected evidence: The accepted request returns a probability matching the fitted model and version fixture-v1.

import numpy as np
import pandas as pd


def dataset():
    rng = np.random.default_rng(17)
    n = 120
    usage = rng.uniform(1, 100, n)
    tickets = rng.poisson(2, n)
    region = np.where(np.arange(n) % 2 == 0, "north", "south")
    logit = 0.9 * tickets - 0.035 * usage + (region == "north") * 0.3
    probability = 1 / (1 + np.exp(-logit))
    label = (rng.random(n) < probability).astype(int)
    cutoff = np.arange(n) + 100
    return pd.DataFrame(
        {
            "id": np.arange(n),
            "customer_id": np.arange(n) % 12,
            "cutoff": cutoff,
            "available_at": cutoff - 2,
            "label_available_at": cutoff + 4,
            "usage": usage,
            "tickets": tickets,
            "region": region,
            "label": label,
        }
    )


def fit_pipeline(frame):
    from sklearn.compose import ColumnTransformer
    from sklearn.impute import SimpleImputer
    from sklearn.linear_model import LogisticRegression
    from sklearn.pipeline import Pipeline
    from sklearn.preprocessing import OneHotEncoder, StandardScaler

    numeric = Pipeline([("impute", SimpleImputer(strategy="median")), ("scale", StandardScaler())])
    transform = ColumnTransformer(
        [
            ("numeric", numeric, ["usage", "tickets"]),
            ("region", OneHotEncoder(handle_unknown="ignore", sparse_output=False), ["region"]),
        ]
    )
    model = Pipeline(
        [("features", transform), ("classifier", LogisticRegression(max_iter=200, random_state=17))]
    )
    model.fit(frame[["usage", "tickets", "region"]], frame["label"])
    return model


def serving_app(model):
    from typing import Literal

    from fastapi import FastAPI
    from pydantic import BaseModel, ConfigDict, Field

    class Request(BaseModel):
        model_config = ConfigDict(extra="forbid")
        usage: float = Field(ge=0, le=10000)
        tickets: int = Field(ge=0, le=100)
        region: Literal["north", "south"]

    app = FastAPI()

    @app.post("/predict")
    def predict(request: Request):
        frame = pd.DataFrame([request.model_dump()])
        return {
            "probability": float(model.predict_proba(frame)[0, 1]),
            "model_version": "fixture-v1",
        }

    return app


def example_one():
    from fastapi.testclient import TestClient

    frame = dataset()
    model = fit_pipeline(frame[frame.label_available_at <= 180])
    payload = {"usage": 20.0, "tickets": 2, "region": "north"}
    with TestClient(serving_app(model)) as client:
        response = client.post("/predict", json=payload)
        assert response.status_code == 200
        expected = float(model.predict_proba(pd.DataFrame([payload]))[0, 1])
        assert abs(response.json()["probability"] - expected) < 1e-12
        assert response.json()["model_version"] == "fixture-v1"
        return {
            "in_process_asgi_status": 200,
            "model_parity": True,
            "no_network_server_started": True,
        }


if __name__ == "__main__":
    print(example_one())

Worked case 2: Reject invalid and undeclared input#

The second case sends a negative value and a label field that is not part of the prediction interface. Both must be rejected before model execution under the declared schema.

Expected evidence: Both requests return 422 validation responses.

    with TestClient(serving_app(model)) as client:
        negative = client.post("/predict", json={"usage": -1, "tickets": 2, "region": "north"})
        extra = client.post(
            "/predict", json={"usage": 1, "tickets": 2, "region": "north", "label": 1}
        )
        assert negative.status_code == 422 and extra.status_code == 422
        return {"negative_value_rejected": 422, "undeclared_target_field_rejected": 422}


if __name__ == "__main__":
    print(example_two())

Practice#

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.

1. Test a boundary value#

Submit usage 0 and the declared maximum.

Check: The response follows the documented bounds.

Hint: Boundaries need explicit tests.

2. Reject a hidden target#

Add label to an otherwise valid request.

Check: The API rejects the undeclared field.

Hint: The serving contract is an allowlist.

3. Inspect the model version#

Keep the returned version with a prediction record.

Check: The observation identifies its model.

Hint: A score without version context is hard to reproduce.

4. Test categorical policy#

Submit an unknown region.

Check: It is rejected under this interface contract.

Hint: The API may be stricter than an internal encoder.

5. Separate test boundaries#

List what the in-process client has not tested.

Check: It has not tested real network/container lifecycle.

Hint: ASGI behavior is one evidence layer.

6. Preserve safe errors#

Describe a diagnostic that avoids exposing credentials or internals.

Check: It is actionable without unnecessary sensitive detail.

Hint: Error handling is part of the API.

Diagnose errors and misleading results#

An HTTP 422 can be correct input rejection rather than a model failure. A 200 response can still carry the wrong model or transformation. Compare the route with direct inference, inspect the version and keep the limits of in-process testing explicit.

Transfer to independent work#

Define and test a serving contract with positive and negative requests. Verify model parity and version identity, then use the separate real Docker service project to qualify network and persistence behavior.
