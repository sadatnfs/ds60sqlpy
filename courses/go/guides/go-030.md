# go-030: Algorithms, benchmarks and allocation-aware design

## Level and prerequisites

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-029

## Learning objectives

Implement a binary search with correct boundaries and compare work and allocation instead of guessing performance. Along the way, explain complexity, monotone predicate, preallocation; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Performance work starts with a behavioral contract and representative input. Complexity predicts growth in work, while a benchmark measures a particular implementation and environment. A linear scan visits each item; binary search repeatedly narrows a sorted interval. Faster execution is useful only if it preserves the result and failure policy. Preallocating slice capacity can avoid growth allocations, but preallocating length creates real zero elements. Tiny timings are noisy. Separate setup from measurement, repeat a representative workload, record environment and check results outside the timing loop. A profile should answer a hypothesis about where time or allocations are spent.

## Vocabulary and concepts

- **Complexity:** How work grows with input size.
- **Monotone predicate:** A predicate changing from false to true at most once over ordered indices.
- **Preallocation:** Reserving storage before appending.

## Syntax anatomy and reasoning

sort.Search finds the first index where a monotone predicate becomes true, or n when none does. It does not sort or validate input. make([]int,0,n) reserves capacity with zero length; make([]int,n) creates n elements. Prepared project benchmarks use testing.B in _test.go files; pprof investigates CPU or allocation evidence rather than establishing a universal speed ranking.

## Worked example / walkthrough

### Worked example 1: Find a lower boundary

Find the first value at least 5 in 2, 4, 6, 8.

```go
package main

import (
	"fmt"
	"sort"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Find a lower boundary
	{
		items := []int{2, 4, 6, 8}
		i := sort.Search(len(items), func(i int) bool { return items[i] >= 5 })
		check(i == 2, "boundary")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The index is 2.

Sorting makes the predicate monotone. The same expression over unsorted input violates the algorithm precondition.

### Worked example 2: Represent no match

Search for a value at least 9 in the same data.

```go
package main

import (
	"fmt"
	"sort"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Find a lower boundary
	{
		items := []int{2, 4, 6, 8}
		i := sort.Search(len(items), func(i int) bool { return items[i] >= 5 })
		check(i == 2, "boundary")
	}

	// Represent no match
	{
		items := []int{2, 4, 6, 8}
		i := sort.Search(len(items), func(i int) bool { return items[i] >= 9 })
		check(i == len(items), "not found")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The index equals the collection length.

The sentinel is not a valid element index. Check it before indexing.

## Exercises

### Exercise 1: Find a lower boundary: change one input

Copy worked example 1 into a scratch pad and change `items := []int{2, 4, 6, 8}` to `items := []int{2, 5, 6, 8}`. Before running, predict which check fails and which value it now sees; then run it and restore the original line.

**Expected:** The changed run panics with `boundary` because `i == 2` no longer holds. Restoring the original line brings back the worked observation: the index is 2.

**Verify:** Compare your written prediction with the panic message `boundary` and name the value that made `i == 2` false. After restoring the input, the program must print its success line again.

### Exercise 2: Represent no match: debug a regression

A regression changed one token in worked example 2, so one line now reads `items := []int{2, 4, 6, 9}`. Run worked example 2 with that line, use the failure to locate the defect and repair it without changing the check.

**Expected:** Before the repair the program panics with `not found`; after it the line reads `items := []int{2, 4, 6, 8}` again and the index equals the collection length.

**Verify:** Keep the failing and the repaired runs. Explain why the changed token alters the value tested by `i == len(items)` for this input.

### Exercise 3: Separate length and capacity

Reserve capacity four, then append one value.

**Expected:** Length is 1, capacity is 4.

**Verify:** Keep a check equivalent to `len(items) == 1 && cap(items) == 4 && items[0] == 7`. As a control, change `items := make([]int, 0, 4)` to `items := make([]int, 1, 4)`: the run must panic with `capacity`. Restore the line before continuing.

### Exercise 4: Count linear work

Sum five values and count visits.

**Expected:** There are five visits and the sum is 15.

**Verify:** Keep a check equivalent to `visits == 5 && sum == 15`. As a control, change `sum += v` to `sum -= v`: the run must panic with `work`. Restore the line before continuing.

### Exercise 5: Handle empty search

Search a zero-length interval.

**Expected:** Index is 0 and the predicate is never called.

**Verify:** Keep a check equivalent to `i == 0 && calls == 0`. As a control, change `calls := 0` to `calls := 1`: the run must panic with `empty`. Restore the line before continuing.

### Exercise 6: Transfer duplicate boundaries

Find the first value at least 3 in 1, 3, 3, 5.

**Expected:** The first duplicate has index 1.

**Verify:** Keep a check equivalent to `i == 1`. As a control, change `i := sort.Search(len(items), func(i int) bool { return items[i] >= 3 })` to `i := sort.Search(len(items), func(i int) bool { return items[i] > 3 })`: the run must panic with `duplicates`. Restore the line before continuing.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
