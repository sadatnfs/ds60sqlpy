go-029: The memory model, race diagnosis and publication#

Level and prerequisites#

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-028

Learning objectives#

By the end, explain data race, publication, immutable snapshot; implement the six investigations below; and defend the expected result of a changed input before running it. A passing reference is evidence about that program, not a certification of your independent understanding.

Why this mechanism matters#

A data race occurs when conflicting concurrent accesses include a write and lack synchronization. A program that prints the desired value once can still race. The memory model specifies ordering guarantees supplied by channels, mutexes and other primitives. Publish initialized state through such a boundary, then keep it immutable or protect future mutations. The race detector observes executed instrumented paths; a clean run is evidence rather than proof about every schedule. Do not intentionally execute racy examples in ordinary references. Prefer a design whose ownership and ordering can be explained before relying on a diagnostic tool.

Vocabulary and concepts#

  • Data race: Conflicting unsynchronized concurrent memory access.
  • Publication: Sharing initialized state through synchronization.
  • Immutable snapshot: A shared value that is no longer mutated.

Syntax anatomy and reasoning#

A channel send synchronizes with its corresponding receive. Closing a channel synchronizes with a receive observing closure. An unlock synchronizes with a later lock on that mutex. atomic.Value can publish immutable snapshots. The ordinary pad has CGO disabled and does not claim race instrumentation; a prepared Linux development project with a compatible C toolchain can run go test -race ./....

Worked example / walkthrough#

Worked example 1: Publish through a channel#

Send an initialized record from a goroutine.

package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Published struct {
	Count int
	Ready bool
}

func main() {
	// Publish through a channel
	{
		ch := make(chan Published)
		go func() { ch <- Published{Count: 3, Ready: true} }()
		v := <-ch
		check(v.Ready && v.Count == 3, "publication")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: The reader observes count 3 and ready true.

The send and receive establish ordering without a timing guess.

Worked example 2: Publish through closure#

Write 7 before closing done, then read after receiving done.

package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Published struct {
	Count int
	Ready bool
}

func main() {
	// Publish through a channel
	{
		ch := make(chan Published)
		go func() { ch <- Published{Count: 3, Ready: true} }()
		v := <-ch
		check(v.Ready && v.Count == 3, "publication")
	}

	// Publish through closure
	{
		done := make(chan struct{})
		n := 0
		go func() { n = 7; close(done) }()
		<-done
		check(n == 7, "close publication")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: The reader observes 7.

Removing this synchronization would make the ordinary shared variable unsafe. The proof uses ordering, not elapsed time.

Common pitfalls and diagnosis#

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from check identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned error is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
