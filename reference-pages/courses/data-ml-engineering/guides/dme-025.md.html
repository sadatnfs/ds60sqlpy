dme-025: Object storage, object identity and conditional updates#

Level: Intermediate | Prepared runtime: python-core

Direct prerequisites: dme-015, dme-021.

Outcome: Model versioned object publication and conditional pointer updates explicitly.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

A key is not necessarily a stable version#

Object storage exposes named byte objects through a service API. A bucket or container organizes keys; a key names an object. Unlike a local filesystem, the service should not be assumed to provide the same rename, directory or locking semantics as Path.replace. A path-looking key may simply be a string. The service's actual consistency, versioning, conditional-request and multipart-upload contracts determine how a publisher can coordinate with readers.

An object key such as accepted can be mutable: its contents may point to a different dataset tomorrow. A version identifies a particular stored state. A content digest identifies bytes under a hash algorithm. Those are related concepts, but they answer different questions. “Where is the current object?” is a naming question. “Which version did I read?” is a concurrency and provenance question. “Do these bytes match the declared content?” is an integrity question. Do not use one field as a substitute for all three without checking the service's guarantees.

This chapter uses a generation-based local object-store mechanism model. It has real Python mutual exclusion around updates, but no HTTP client or cloud service. The model assigns a new monotonically increasing generation to every successful write. It also computes a SHA-256 digest of the bytes. Its conditional update compares generations, not digests. This deliberate choice makes a stale-writer problem visible without claiming that all providers expose identical precondition APIs.

Why check-then-write is insufficient#

Suppose two publishers read accepted generation 1. Publisher A prepares version 2; publisher B prepares version 3. If each later writes the accepted pointer unconditionally, the last writer wins even if it planned from an obsolete state. A separate read followed by a write leaves time for another publisher to intervene. The comparison and update must belong to one atomic operation at the coordinating authority.

The model's put holds a lock while it checks the currently observed generation and installs the replacement. A supplied expected generation of None means the key must not already exist. For an update, the expected generation must equal the current one. In notation,

CAS means compare and swap. A failed precondition is useful information: the writer's assumptions are stale. The correct response is to reread the accepted state and reconsider the operation, not simply retry the same unconditional overwrite. Some changes can be safely rebased; others need renewed validation because the newer state overlaps their intended update.

Worked case 1: prepare immutable data before moving a pointer#

example_one() writes a product object containing six packages and creates an accepted pointer to that object's key. The consumer first resolves the pointer, then reads the named data object. The program checks both the object's generation and its bytes. It then prepares a second product containing nine packages while the accepted pointer still references the first.

Preparation alone does not expose the second product as current. Only a successful conditional pointer update changes what a current-version consumer resolves. The old product remains readable by its original version. This separation supports validation before activation and permits an explicitly pinned reader to continue using an earlier accepted dataset. It also makes failed preparation recoverable: unreferenced prepared data need not become visible merely because their upload succeeded.

The example's data keys are written once under the model's create-if-absent precondition. That is an application convention, not a claim that naming a key v1 makes it immutable automatically. Actual object-store policies or conditional writes must enforce the convention. A publisher that later overwrites the bytes behind an accepted immutable key breaks the reader's version contract even if the pointer itself has not changed.

Worked case 2: a stale writer and a return to identical bytes#

Both readers in example_two() observe the same accepted generation. The first changes the pointer from v1 to v2. The second attempts to publish v3 using the older generation and receives a conflict. The accepted state remains the first writer's version. This is a real atomic decision inside the local model, though it does not exercise a remote network or provider implementation.

The example then changes the pointer back to the bytes v1. Its content digest now equals the digest seen by the original readers, but its generation is different. The stale original generation still cannot authorize an update. This is the ABA problem: a value can change from A to B and back to A while a stale observer sees bytes that look unchanged. A content-only comparison cannot necessarily distinguish that history.

Actual services have their own version, generation and entity-tag semantics. An HTTP ETag is a validator, not a portable promise that its text equals a particular checksum algorithm. S3 conditional writes use its documented ETag preconditions; another service may expose explicit generation matches. If your application requires detecting every intervening publication, put a monotone revision or unique publication identity in the pointer content and use the provider's supported atomic precondition. Do not infer a stronger guarantee from the spelling of a metadata field.

Complete worked program#

Use Python Core. Objects and history live only in memory during each case. The lock protects model operations within one Python process; it is not a cross-machine lock and creates no durable remote service.

"""A generation-based object-store mechanism model, not an S3 client."""

import hashlib
from threading import Lock


class Conflict(ValueError):
    pass


class Store:
    def __init__(self):
        self.objects = {}
        self.history = {}
        self.generation = 0
        self.lock = Lock()

    def put(self, key, body, expected_generation):
        if not isinstance(key, str) or not key or not isinstance(body, bytes) or len(body) > 4096:
            raise ValueError("Use a named object with bounded bytes")
        with self.lock:
            current = self.objects.get(key)
            observed = None if current is None else current[0]
            if observed != expected_generation:
                raise Conflict("Conditional write observed a different generation")
            self.generation += 1
            version = (self.generation, body, hashlib.sha256(body).hexdigest())
            self.objects[key] = version
            self.history[(key, version[0])] = version
            return version[0]

    def get(self, key, generation=None):
        with self.lock:
            return self.objects[key] if generation is None else self.history[(key, generation)]


def example_one():
    store = Store()
    first = store.put("products/v1", b'{"packages":6}', None)
    pointer = store.put("accepted", b"products/v1", None)
    data_key = store.get("accepted")[1].decode()
    accepted = store.get(data_key)
    assert accepted[0] == first and accepted[1] == b'{"packages":6}'
    second = store.put("products/v2", b'{"packages":9}', None)
    assert store.get("accepted")[1] == b"products/v1"
    store.put("accepted", b"products/v2", pointer)
    assert store.get("products/v1", first)[1] == b'{"packages":6}'
    return {
        "first_data_generation": first,
        "second_data_generation": second,
        "accepted_key": store.get("accepted")[1].decode(),
        "prior_version_retained": True,
    }


def example_two():
    store = Store()
    generation = store.put("accepted", b"v1", None)
    first_reader, second_reader = store.get("accepted"), store.get("accepted")
    assert first_reader[0] == second_reader[0] == generation
    store.put("accepted", b"v2", first_reader[0])
    try:
        store.put("accepted", b"v3", second_reader[0])
    except Conflict:
        pass
    else:
        raise AssertionError("A stale writer overwrote the accepted version")
    latest = store.get("accepted")
    store.put("accepted", b"v1", latest[0])
    returned = store.get("accepted")
    assert returned[2] == first_reader[2] and returned[0] != first_reader[0]
    try:
        store.put("accepted", b"v3", first_reader[0])
    except Conflict:
        pass
    else:
        raise AssertionError("A stale generation survived a return to identical bytes")
    return {
        "stale_writer_rejected": True,
        "same_bytes_same_digest": True,
        "same_bytes_different_generation": [first_reader[0], returned[0]],
        "scope": "local generation-CAS model; no cloud API was called",
    }


def main():
    print("Separate preparation from conditional publication:", example_one())
    print("Conflicts and the ABA boundary:", example_two())


if __name__ == "__main__":
    main()

Multi-object publication and incomplete uploads#

A dataset often consists of many objects. Uploading them individually does not automatically create an atomic dataset transaction. A common design writes data objects, constructs a manifest listing their exact identities, validates that manifest, and then conditionally updates one accepted pointer. Readers pin the manifest and use its listed objects rather than enumerating every key under a prefix. This prevents a reader from combining half of one publication with half of another.

A failed upload or abandoned candidate can leave unreferenced objects. Garbage collection needs a retention policy and a complete reachability view of accepted snapshots, active readers and in-progress writers. Deleting every object absent from the latest pointer is unsafe if an older snapshot remains supported. The snapshot-table chapter demonstrates this with actual files, while the real storage workshop exercises its service's own lifecycle.

Multipart upload introduces another boundary: uploaded parts are not necessarily a completed visible object. A publisher must inspect the completion response and reconcile uncertain outcomes. Retrying a whole upload without knowing whether completion succeeded can waste resources or create conflicting versions. Record upload identifiers and intended content identities without treating an in-memory success flag as durable acceptance evidence.

Diagnosis, uses and interview discussion#

If a publication disappears, inspect whether a stale writer used an unconditional pointer update. If identical bytes unexpectedly pass a stale check, inspect whether the precondition identifies content or a write generation. If a manifest references missing data, inspect the ordering of preparation and activation and whether the reader pins the same manifest throughout its read. A provider's successful PUT response proves that operation's result, not the completeness of a whole multi-object dataset.

This design reasoning applies to training snapshots, analytical exports, model artifacts and static report publication. It is particularly valuable when many workers prepare outputs but only one reviewed version should become current. Separate the expensive computation from the small coordination step so conflicts can be handled without blindly repeating all work.

An interviewer may ask, “Why not check whether the file exists and then upload?” Explain the race between those operations and the need for a server-side atomic precondition. If asked whether a checksum is a version, explain that identical content can occur at multiple points in history. If asked how to roll back, distinguish moving the accepted pointer to a retained compatible snapshot from deleting the newer objects or reversing every external side effect.
