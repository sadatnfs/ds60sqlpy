## Quality rules must preserve an account of the input

A quality pass can identify invalid records, choose a current snapshot or reject an ambiguous candidate. It should not silently make troublesome rows disappear while preserving the appearance of a complete product. The input population and the reason for every exclusion remain part of the contract.

This chapter uses real Polars transformations. The input contains a unique audit row ID, delivery identity, source version, package count and route identity. A separately declared physical schema specifies string and integer column types. Package values can be physically nullable so that a missing measurement can be classified rather than disappearing during an unrelated conversion.

The function checks the typed column contract before evaluating row rules. It also requires each supplied row to have a unique, non-null audit identity. That audit identity is different from the business delivery identity: several valid historical versions of one delivery can appear in the same input, and each source row still needs to be accounted for.

The output is a current snapshot over the supplied records, not proof that the supplied frame contains every source event or the latest state in the world. Combine it with the manifest, version and timing contracts from the earlier chapters before claiming a complete business product.

## Read the Polars expressions

`pl.col("packages")` names a column expression. A `when(...).then(...)` chain describes conditional values across rows. `with_columns` adds the resulting reason column, and `filter` selects records according to that reason. These are actual columnar operations rather than a Python row loop disguised as a different engine.

The reason rules are ordered. They check missing delivery identity, invalid source version, missing package count, nonpositive package count and unknown route. The first matching rule supplies the diagnostic for a row. That is an explicit priority policy. A different quality product might retain several reasons per record, but it should not claim to do so when the implementation records only one.

Null handling is explicit. A missing value is checked with `is_null`, rather than being assumed to behave like a normal false comparison. Expressions combined with `|` or `&` describe elementwise logic; they are different from using Python's ordinary scalar `or` and `and` on an entire column expression.

The allowed route identities are a tiny reviewed fixture. A real system should resolve a governed reference relation under the appropriate validity and availability policy. Hardcoding two route IDs is useful for a self-contained example, not a complete reference-data architecture.

## Separate invalid rows from valid historical versions

The fixture contains an earlier and later version of delivery A plus one version of delivery B. Both A rows can be valid observations of change even though only one belongs in a current snapshot. A nonselected older version is therefore not automatically a quarantined invalid record.

The function first separates invalid rows from valid rows. Among valid rows, it checks whether the same delivery and source version names conflicting package or route values. If a conflict exists, the function rejects the candidate rather than relying on input position to pick a winner.

Only after that check does it sort by delivery identity, source version and audit row identity, choose the latest row per delivery, and retain the audit IDs of valid rows that are not current. The final sort makes the displayed output order explicit. The selected representative of an exact replay has the same declared payload; a different payload at the same version is not treated as a harmless duplicate.

These operations assume source versions belong to the declared authoritative ordering domain. They do not infer whether a higher number from another producer is trustworthy. The change-event chapter explains why that authority and replay contract matter.

## Worked case 1: Build a current snapshot without losing history accounting

The first case supplies three valid rows. Audit row one describes A at version one with two packages. Row two describes B at version one with three packages. Row three describes A at version two with four packages.

The current snapshot contains A at version two and B at version one. Its package total is seven. Audit row one is recorded as historical or replayed rather than being silently forgotten. There are no quarantined rows, and the local publication rule accepts the candidate.

The reconciliation is

\[
N_{\mathrm{input}}
=N_{\mathrm{current}}+N_{\mathrm{not\ current}}+N_{\mathrm{quarantine}}
=2+1+0=3.
\]

Each \(N\) counts supplied rows in one of the declared outcome groups. The package total answers the current-snapshot question, so it is \(4+3=7\), not the sum of every historical package state. This connects the quality pass to the state-versus-event distinction in the CDC chapter.

The classroom displays the actual selected snapshot as a table, including business identity, version, packages and route. The output remains small enough to compare with the input by hand. A larger implementation should retain equivalent lineage and invariants rather than replacing them with an unsupported statement that deduplication succeeded.

## Conflicts need authority, not convenient ordering

A common shortcut is to sort rows and keep the last one for each key. That can be correct when the ordering has a justified meaning. It is dangerous when the “latest” row is merely the last input position or a processing timestamp that does not represent the source's authoritative state.

In particular, two different payloads sharing the same declared source version cannot be resolved by the version alone. A later audit row ID only says where this consumer observed the record. It does not establish which business value is correct. The function therefore checks payload agreement before using its deterministic selection order.

A real repair might consult an authoritative source, apply a reviewed conflict rule or create a new corrected source version. It should retain enough diagnostic information to explain the decision. An arbitrary deduplication rule can hide the problem and propagate a plausible but unsupported value into analytics or features.

## Worked case 2: Quarantine invalid records and reject equal-version conflicts

The changed case adds two rows. Delivery C has a missing package count, and D has a negative package count. The real Polars quality expressions retain both audit identities with their specific reason codes. The candidate current snapshot for the valid subset is still inspectable, but `publishable=False` under this chapter's complete-product policy.

The accounting now includes two current rows, one historical row and two quarantined rows, totaling five supplied rows. No invalid record is silently removed from the population. A consumer that deliberately permits a partial product would need a different explicit contract and coverage interpretation.

The case then constructs a separate candidate with another A version-two row containing nine packages instead of four. The grouped payload check finds the conflict and raises an error before an arbitrary winner can become the current snapshot. The tutorial checks that expected rejection and records it in the structured report.

The report contains bounded synthetic identities and reasons rather than an indiscriminate dump of an external production payload. In a real system, quarantine storage and access need the same governance attention as accepted data. Invalid data can still contain sensitive information.

## Complete worked program

```python
"""Actual Polars quality classification and version-aware snapshot selection."""

import polars as pl

SCHEMA = {
    "row_id": pl.Int64,
    "delivery_id": pl.String,
    "source_version": pl.Int64,
    "packages": pl.Int64,
    "route_id": pl.Int64,
}


def fixture():
    return pl.DataFrame(
        {
            "row_id": [1, 2, 3],
            "delivery_id": ["A", "B", "A"],
            "source_version": [1, 1, 2],
            "packages": [2, 3, 4],
            "route_id": [10, 20, 10],
        },
        schema=SCHEMA,
    )


def inspect(frame):
    if dict(frame.schema) != SCHEMA:
        raise ValueError("Validate the declared typed column schema before this quality pass")
    if frame["row_id"].null_count() or frame["row_id"].n_unique() != frame.height:
        raise ValueError("Each supplied row needs its own audit identity")
    classified = frame.with_columns(
        pl.when(
            pl.col("delivery_id").is_null()
            | (pl.col("delivery_id").str.strip_chars().str.len_chars() == 0)
        )
        .then(pl.lit("missing_delivery_id"))
        .when(pl.col("source_version").is_null() | (pl.col("source_version") < 1))
        .then(pl.lit("invalid_source_version"))
        .when(pl.col("packages").is_null())
        .then(pl.lit("missing_packages"))
        .when(pl.col("packages") < 1)
        .then(pl.lit("nonpositive_packages"))
        .when(pl.col("route_id").is_null() | ~pl.col("route_id").is_in([10, 20]))
        .then(pl.lit("unknown_route"))
        .otherwise(pl.lit(None, dtype=pl.String))
        .alias("reason")
    )
    rejected = classified.filter(pl.col("reason").is_not_null())
    valid = classified.filter(pl.col("reason").is_null())
    conflicts = (
        valid.group_by("delivery_id", "source_version")
        .agg(
            pl.col("packages").n_unique().alias("different_package_values"),
            pl.col("route_id").n_unique().alias("different_routes"),
        )
        .filter((pl.col("different_package_values") > 1) | (pl.col("different_routes") > 1))
    )
    if conflicts.height:
        raise ValueError(
            "A delivery source version has conflicting payloads; do not choose an arbitrary row"
        )
    latest = (
        valid.sort(["delivery_id", "source_version", "row_id"])
        .unique(subset="delivery_id", keep="last", maintain_order=True)
        .sort("delivery_id")
    )
    not_current = valid.filter(~pl.col("row_id").is_in(latest["row_id"].to_list()))
    assert frame.height == latest.height + not_current.height + rejected.height
    return {
        "current": latest.select(
            "delivery_id", "source_version", "packages", "route_id"
        ).to_dicts(),
        "quarantine": rejected.select("row_id", "delivery_id", "reason").to_dicts(),
        "historical_or_replayed_row_ids": not_current["row_id"].to_list(),
        "input_rows": frame.height,
        "publishable": rejected.height == 0,
    }


def example_one():
    result = inspect(fixture())
    assert result["current"] == [
        {"delivery_id": "A", "source_version": 2, "packages": 4, "route_id": 10},
        {"delivery_id": "B", "source_version": 1, "packages": 3, "route_id": 20},
    ]
    assert result["historical_or_replayed_row_ids"] == [1] and result["quarantine"] == []
    assert result["publishable"] is True and sum(row["packages"] for row in result["current"]) == 7
    return result


def example_two():
    bad = pl.DataFrame(
        {
            "row_id": [4, 5],
            "delivery_id": ["C", "D"],
            "source_version": [1, 1],
            "packages": [None, -1],
            "route_id": [10, 20],
        },
        schema=SCHEMA,
    )
    result = inspect(pl.concat([fixture(), bad]))
    assert result["input_rows"] == 5 and result["publishable"] is False
    assert [(row["row_id"], row["reason"]) for row in result["quarantine"]] == [
        (4, "missing_packages"),
        (5, "nonpositive_packages"),
    ]
    conflict = pl.DataFrame(
        {
            "row_id": [6],
            "delivery_id": ["A"],
            "source_version": [2],
            "packages": [9],
            "route_id": [10],
        }
    )
    try:
        inspect(pl.concat([fixture(), conflict]))
    except ValueError:
        result["equal_version_conflict_rejected"] = True
    else:
        raise AssertionError("A later input position is not a valid conflict-resolution policy")
    return result


def main():
    from ds60sqlpy.plot_artifacts import publish_report, publish_table

    first, second = example_one(), example_two()
    columns = ["delivery_id", "source_version", "packages", "route_id"]
    publish_table(
        columns,
        [[row[name] for name in columns] for row in first["current"]],
        description=(
            "Accepted current snapshot selected by declared "
            "delivery version; the earlier A record remains "
            "accounted for."
        ),
    )
    publish_report(
        second,
        description=(
            "Quarantined input identities and a deliberately "
            "rejected equal-version conflict; no partial product is "
            "silently published."
        ),
    )
    print("Current package total:", sum(row["packages"] for row in first["current"]))
    print("Rejected rows:", second["quarantine"])


if __name__ == "__main__":
    main()
```

## Diagnose quality metrics carefully

A rejection rate can improve because the producer improved, because the rules changed or because problematic records stopped arriving. Preserve rule versions, input population and reason counts before interpreting the change. A smaller quarantine table is not automatically a healthier system.

Similarly, a stable current-row count can hide changed identities or different chosen versions. Inspect representative records and compare the declared semantic fields. A global sum may remain unchanged while values are assigned to the wrong entities, as the dimensional-modeling chapter demonstrated.

If a quality function rejects the whole physical schema, investigate the parsing or serialization boundary before forcing a cast. An inferred float or string column may indicate an upstream contract change. If audit row IDs are missing or duplicated, establish reliable source positions before claiming complete reconciliation.

The complete code does not choose an external repair for an equal-version conflict. That decision requires authority the fixture does not have. It reports and stops at the relevant boundary instead of manufacturing certainty.

## Where this is useful

Use these checks for ingestion staging, current-state projections, feature preparation, reporting products and migration comparisons. Preserve the distinctions between valid history, exact replay, invalid values, unresolved conflicts and missing coverage. They lead to different operational actions and should not all be collapsed into a generic “duplicate” count.

## Answered interview discussion

**What makes deduplication correct?** A declared identity, a clear grain and a justified selection or replay policy. Keeping an arbitrary last row can produce a deterministic but wrong answer.

**Why keep audit row IDs as well as business IDs?** Multiple source rows can concern one entity. Audit identities let the quality pass account for every supplied observation and locate a rejected or superseded record.

**Can a quarantined subset still support a useful product?** Sometimes, but the consumer must accept the declared partial population and its limitations. This example deliberately blocks complete publication when invalid rows remain.

**What does this quality pass not establish?** It does not prove source completeness, external authorization, real-world measurement accuracy or current availability beyond the supplied frame. Those claims need their corresponding pipeline contracts and observations.
