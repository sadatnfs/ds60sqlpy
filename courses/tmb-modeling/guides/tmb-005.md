# Compile, load and isolate an owned library

Start with: tmb-004, cpp-001.

Outcome: Explain exactly which source and native library a model evaluation uses.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter fingerprints two source-description files with `tools::md5sum`; it compiles nothing. In the separately prepared [owned project](../projects/tmb-local/README.md), `R/compile.R` runs `TMB::compile`, and `make_objective()` in `R/api.R` loads the library with `dyn.load` and refuses a different library already loaded under the same name; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

A C++ source file is portable text. Its compiled shared library is not. The binary depends on CPU architecture, operating system, compiler conventions, R's ABI, TMB headers and linked libraries such as Matrix. A Linux ARM64 `.so` is not a macOS library, and it is not an AMD64 library. Docker standardizes the Linux environment but does not make incompatible machine instructions portable.

The project prepares R 4.6.1, TMB 1.9.25 and a matching Matrix/RcppEigen stack. `R/compile.R` copies allowlisted original source files into an owned build directory and compiles serially with `-O1 -g0`, `framework="CppAD"`, bounds checking and safe unloading. Preparation is separate from evaluation. `R/api.R` only loads an already prepared model library.

## Key terms

- **Shared library:** The compiled native file R loads to evaluate a model; unlike the portable C++ source, it is tied to CPU architecture, operating system, R and the linked toolchain.
- **Application binary interface (ABI):** The binary calling conventions and data layouts a compiled library must share with the R, TMB and native libraries that load it.
- **Stale binary:** A previously compiled library that no longer matches its edited source; loading it silently evaluates the old model.
- **Process lifetime:** The span during which a loaded library and its native pointers stay valid in one R process; a fresh process gives a clean boundary for rebuilding and reloading.

### Worked case A: source to loaded code

```bash
Rscript --vanilla R/compile.R "$PWD" /tmp/tmb-owned-build
TMB_BUILD_DIR=/tmp/tmb-owned-build Rscript --vanilla tests/acceptance.R
```

These are commands inside the separately prepared project, not commands for an ordinary R pad. `--vanilla` suppresses user startup files that might change repositories or compiler settings. `TMB_BUILD_DIR` selects one trusted directory. The project checks the loaded library's resolved path, so a same-named DLL already loaded from somewhere else causes an explicit error.

A compiler's success proves only that source could be translated and linked. A fresh process must then load the library, construct an objective and evaluate its value and gradient. Our acceptance layer performs those steps with independent oracles. The base-R companion illustrates source fingerprint changes; it does not pretend to invoke a compiler.

### Worked case B: stale binary after an edit

Suppose the source changes from a normal to a Poisson likelihood but the old `.so` remains. An optimizer can still return a clean result from the old normal code. Compare source fingerprints, rebuild explicitly and use a fresh R process. Never overwrite a library while another process is actively using it. Keep model binaries and their build records together, and do not serialize TMB objects between machines.

For deliberate compiler-error acceptance, work in a disposable copied build directory, introduce a syntax error there, and require a nonzero compilation status. Preserve the good source and library. The test is useful because wrappers sometimes swallow compiler status and attempt to load a stale binary. The project compiler checks each return status before continuing.

### Diagnostics and answered discussion

**Why use a fresh process instead of repeated `dyn.unload`?** R objects can retain native pointers. A fresh process gives a clear lifetime boundary and avoids accidentally using freed objects. **Is a matching filename sufficient?** No. Match source, build metadata and native architecture. **Can `TMBad` replace `CppAD` without any qualification?** It is a supported framework choice, but changes derivative machinery and compile behavior. Rebuild and rerun numerical checks. Some `intern=TRUE` paths specifically require TMBad.

The [compile and FreeADFun documentation](https://cran.r-project.org/web/packages/TMB/TMB.pdf) explains these boundaries. Retain third-party license notices with prepared dependencies; do not infer redistribution terms from the license of this course's original model files.

### Worked case C: reading the build receipt and the load guard

After `R/compile.R` compiles all nine models, it writes `build-receipt.txt` into the build directory. The file has one line per fact, in this order:

```text
R 4.6.1
TMB 1.9.25
Matrix <installed Matrix version>
RcppEigen <installed RcppEigen version>
architecture <R.version$platform, for example x86_64-pc-linux-gnu>
framework CppAD
flags -O1 -g0
```

The first two lines are pinned: the script stops with `Prepared R4.6.1/TMB1.9.25 required` before compiling anything if either differs. The Matrix and RcppEigen versions are recorded rather than enforced, because they come from the prepared image; a reviewer comparing two receipts can see whether a numerical difference coincides with a dependency change. The architecture line is the one people forget. A receipt that says `aarch64` cannot describe a library that a reviewer then loads on an `x86_64` host, even if every other line matches.

The second guard lives in `make_objective()`:

```r
library_path <- normalizePath(file.path(build_dir, TMB::dynlib(model)), mustWork = TRUE)
if (!model %in% names(getLoadedDLLs())) dyn.load(library_path)
actual <- normalizePath(getLoadedDLLs()[[model]][["path"]], mustWork = TRUE)
if (!identical(actual, library_path)) stop("A different model library is already loaded; use a fresh R process")
```

Trace it with two build directories, `build-a` and `build-b`, both containing `normal_mean.so`. In a fresh process with `TMB_BUILD_DIR` set to `build-a`, the first call loads `build-a/normal_mean.so` and `actual` equals `library_path`. If the same process later calls `make_objective("normal_mean", ..., build_dir = "build-b")`, the model name is already in `getLoadedDLLs()`, so nothing new is loaded; `actual` still resolves to `build-a`, the comparison fails, and the call stops. Without that comparison the function would quietly evaluate the old library while the caller believed it was testing the new build. `normalizePath` matters too: a symlink or a relative path such as `./build-a/../build-a` would otherwise compare as a different string for the same file.

### What a passing acceptance run does and does not show

When `tests/acceptance.R` prints its final `PASS` line, it has compiled nothing; it has loaded the nine libraries named by `TMB_BUILD_DIR` and compared their values and gradients against independent formulas. That is evidence about those binaries on that machine. It says nothing about a different architecture, a rebuild with `framework = "TMBad"`, or a library built with different flags. Keep the receipt, the acceptance output and the source fingerprints together as one record, and rerun acceptance after any change to any of them.

### Base-R companion (runs in the classroom)

```r
text1 <- "normal likelihood version 1"
text2 <- "normal likelihood version 2"
paths <- c(tempfile(), tempfile())
writeLines(text1, paths[1]); writeLines(text2, paths[2])
fingerprints <- tools::md5sum(paths)
print(fingerprints)
stopifnot(unname(fingerprints[1]) != unname(fingerprints[2]))
print(list(
  R = as.character(getRversion()), platform = R.version$platform,
  note = "Source identity demonstration only; no DLL compiled"
))
unlink(paths)
```
