# go-022: HTTP handlers and in-process service tests

## Level and prerequisites

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-021

## Learning objectives

Write an HTTP handler and test its status codes, methods, routes and headers in process with httptest. Along the way, explain handler, status code, response recorder; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

HTTP separates method, target, headers, status and body. A handler implements a protocol boundary, not merely a function that returns text. Validate the method and path before applying domain behavior. WriteHeader chooses a response status before the first body write; once a response starts, changing status may be too late. An in-process recorder can test routing and output without opening a socket. This is excellent unit evidence but does not establish real TLS, proxy, timeout or network behavior. Production servers also need bounded request bodies, explicit timeouts, graceful shutdown and safe logging.

## Vocabulary and concepts

- **Handler:** Code implementing the response to one HTTP request.
- **Status code:** A protocol-level classification of the response.
- **Response recorder:** An in-process test object capturing handler output.

## Syntax anatomy and reasoning

http.HandlerFunc adapts a function with ResponseWriter and *Request parameters. httptest.NewRequest creates an inbound request, and httptest.NewRecorder captures status, headers and body. Header().Set changes response metadata before writing. http.Error writes an error response. A handler should return after rejecting a request so it does not accidentally continue into a success path.

## Worked example / walkthrough

### Worked example 1: Serve a health request

Send GET /health to the handler.

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func health(w http.ResponseWriter, r *http.Request) {
	if r.URL.Path != "/health" {
		http.NotFound(w, r)
		return
	}
	if r.Method != "GET" {
		w.Header().Set("Allow", "GET")
		http.Error(w, "method not allowed", http.StatusMethodNotAllowed)
		return
	}
	w.Header().Set("Content-Type", "text/plain; charset=utf-8")
	w.WriteHeader(http.StatusOK)
	fmt.Fprintln(w, "ok")
}

func main() {
	// Serve a health request
	{
		r := httptest.NewRecorder()
		health(r, httptest.NewRequest("GET", "/health", nil))
		check(r.Code == 200 && r.Body.String() == "ok\n", "health")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The status is 200 and the body is ok plus a newline.

The recorder runs the handler directly. This proves the handler contract without making any network availability claim.

### Worked example 2: Reject an unsupported method

Send POST /health.

```go
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func health(w http.ResponseWriter, r *http.Request) {
	if r.URL.Path != "/health" {
		http.NotFound(w, r)
		return
	}
	if r.Method != "GET" {
		w.Header().Set("Allow", "GET")
		http.Error(w, "method not allowed", http.StatusMethodNotAllowed)
		return
	}
	w.Header().Set("Content-Type", "text/plain; charset=utf-8")
	w.WriteHeader(http.StatusOK)
	fmt.Fprintln(w, "ok")
}

func main() {
	// Serve a health request
	{
		r := httptest.NewRecorder()
		health(r, httptest.NewRequest("GET", "/health", nil))
		check(r.Code == 200 && r.Body.String() == "ok\n", "health")
	}

	// Reject an unsupported method
	{
		r := httptest.NewRecorder()
		health(r, httptest.NewRequest("POST", "/health", nil))
		check(r.Code == 405 && r.Header().Get("Allow") == "GET", "method")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The status is 405 and Allow is GET.

The method boundary is explicit. Returning after the error prevents success text from being appended to an already rejected response.

## Common pitfalls and diagnosis

Testing only the success body is the usual gap: a handler that returns 200 with ok for every method and path passes such a test. Check status, headers and body for wrong methods and unknown paths too. Another mistake is writing the body before setting headers or status; after the first byte is written, the status is fixed at 200 and later header changes are ignored.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Serve a health request: change one input

1. Restate the expected observation: The status is 200 and the body is ok plus a newline.
2. The recorder captures status and body. What does a successful handler write?
3. GET! is a different method token, so the handler takes the method-not-allowed branch and returns 405; `r.Code==200` fails. Restore GET; the handler is correct.

### Hint for investigation 2: Reject an unsupported method: debug a regression

1. Restate the expected observation: The status is 405 and Allow is GET.
2. The handler sets Allow before calling http.Error. Which status and header should POST produce?
3. The path /health! does not match, so the handler returns 404 before checking the method and `r.Code==405` fails. Restore /health so the method branch runs.

### Hint for investigation 3: Reject an unknown route

1. Restate the expected observation: The status is 404.
2. The path check runs first. What does http.NotFound write?
3. A catch-all success handler can conceal path mistakes and break monitoring assumptions.

### Hint for investigation 4: Check content metadata

1. Restate the expected observation: The response declares text/plain with UTF-8.
2. Headers must be set before the body. Which exact content type string is declared?
3. Representation metadata belongs to the response contract.

### Hint for investigation 5: Repeat without shared mutation

1. Restate the expected observation: Both responses succeed identically.
2. Each iteration creates a new recorder. Is any state shared between the two calls?
3. The handler has no mutable request-global state.

### Hint for investigation 6: Transfer query independence

1. Restate the expected observation: The path still matches and returns 200.
2. A query string is not part of r.URL.Path. Does /health?probe=1 match the route?
3. URL.Path excludes the query string.
