# Phase 5: Walkthroughs & Track Qualification - Research

**Researched:** 2026-11-18
**Domain:** Classroom walkthrough adapters, runtime capability evidence, per-track quality qualification
**Confidence:** HIGH for current machinery (files read this session); MEDIUM for the proposed design; LOW for numeric thresholds (need user confirmation)

## Summary

The classroom has exactly two live walkthrough adapters, and both serve only the legacy Python, SQL and bridge catalog (201 lessons): a Python line tracer and a SQL clause-by-clause planner in `src/ds60sqlpy/step_through.py`, exposed through one `step-through` lab action and one step panel in `classroom-guide.js`. Module lessons (1637 rows in 37 module tracks) never reach that action. The only "authored steps" mechanism in the repository is the DAX hand-derived worked reference (`module_drafts.worked_examples`), which binds a per-lesson trace to source and model bytes by SHA-256, refuses any record that is not `"hand-derived"`, and returns `"executed": False`. That is the precedent to generalize: a per-track `walkthroughs.json` with hash-bound, line-anchored authored steps, served read-only by a new `module-walkthrough` action and rendered as a third `kind` in the existing step panel with an explicit "authored steps, not a live trace" label.

Runtime evidence already exists but is scattered: `scripts/check_module_references.py` runs every admitted ordinary-profile reference in a disposable classroom (CI, Docker only), lists every excluded profile with a plain reason (`EXTERNAL_REASONS`), and browser, Kubernetes and GPU routes are separate. The coverage matrix `verification` field is coarse (`module-check` for every runnable module row) and `docs/implementation/runtime-reference-evidence.json` (385 records, 10 tracks) has no consumer or test. No shared quality rubric exists anywhere in `docs/`, `curriculum/`, `scripts/` or `tests/`; the ingredients are the lesson contract and depth standard in `docs/content-authoring.md`, the matrix gap codes, and the result labels in `docs/validation.md`.

**Primary recommendation:** Add one curated `curriculum/track-qualification.json` (40 track records holding a runtime capability ledger and rubric results) gated by `tests/test_track_qualification.py` that recomputes measured criteria from `curriculum/coverage-matrix.json`, plus a hash-bound authored walkthrough format rendered in the existing step panel. Keep live tracing Python and SQL only.

## Authored Walkthrough Design (WALK-03)

**Anchor choice:** bind each walkthrough to the lesson's executable reference as chosen by `check_module_references.reference_case` (tutorial: `source_path`; practice: the single non-Markdown solution file) [VERIFIED: scripts/check_module_references.py:91-124]. That file is exactly what the CI reference corpus executes and hashes, so walkthrough claims ride on existing runtime evidence. This mirrors the legacy "Step through the solution" flow.

**Format (proposed):** one file per track, `courses/<track>/walkthroughs.json`, modeled on `courses/dax/reference-results.json`.

```json
{
  "schema_version": 1,
  "track_id": "go",
  "evidence": "authored",
  "walkthroughs": [
    {
      "lesson_id": "go-001",
      "anchor": "reference",
      "source_path": "courses/go/solutions/go-001_solution.go",
      "source_sha256": "<64 hex>",
      "title": "How the checked program builds its greeting",
      "steps": [
        {
          "lines": [12, 14],
          "excerpt": "\t\tgreeting := \"Hello, Go\"\n...",
          "title": "Bind a name to a string value",
          "explanation": "The short declaration := creates greeting and stores the text Hello, Go.",
          "observe": "Nothing prints yet; the value only exists in memory."
        }
      ],
      "expected_output": ["Worked example checks passed."]
    }
  ]
}
```
Values in this skeleton (paths, line numbers, output text) are illustrative [ASSUMED]; the go-001 reference path is taken from its matrix row.

**Validator rules** (new `src/ds60sqlpy/walkthroughs.py`, reused by server, check script and tests):
1. `schema_version` 1, `track_id` equals directory, `evidence` exactly `"authored"` (mirror DAX's refusal of runtime claims).
2. `lesson_id` exists in `ModuleCatalog` for that track, is canonical, is not a `reading`, `k8s-kind` or `dax-offline` row; no duplicates.
3. `source_path` passes `validate_content_path` (`curriculum_framework.py:127`) and equals the path `reference_case` selects; `source_sha256` matches current bytes.
4. 3 to 20 steps; `lines` are 1-based, in range, non-decreasing start; `excerpt` equals the file text at those lines exactly (pins meaning even after formatting moves lines).
5. Bounded strings (title 200, explanation 1200, observe 600 characters), no em or en dash characters, no HTML-significant parsing needed (rendered with `textContent`).
6. `expected_output`: 0 to 5 strings, each at most 200 characters; required unless the profile is a browser profile.
7. Rebind helper (`scripts/check_walkthroughs.py --rebind`) updates `source_sha256` only when every excerpt still matches; otherwise it fails and names the step.

**Server:** add `module-walkthrough` to `ModuleService.action`, returning `{"kind": "authored", "label": "Authored steps, not a live trace", "evidence": "authored", "executed": false, "source_path", "source", "title", "steps", "verified_by"}`. Practice-track anchors are solutions, so require `payload.get("reveal") is True` and reuse `REVEAL_MESSAGE` ("Explicitly reveal a solution after your own attempt.", `exercises.py:37`); tutorial anchors (lesson source) need no reveal. Return a clear error for lessons without a walkthrough.

**UI:** in `classroom-guide.js`, add an `authoredAvailable()` gate for `current.engine === "module"` when `current.walkthrough_available` is true (add that boolean to the `module-lesson` payload), a button label "Walk through the reference" (not "Step through"), title "Walk through the worked reference", source label "Authored steps written by the course, not a live trace of your code. Your code is not run or changed.", a `renderAuthored` that reuses `.step-listing`/`ol.step-code` with `.is-current` on every line in `lines`, and narration from `title` plus `explanation` plus `observe`. Add `else if (walk.kind === "authored")` before the Python fallback. Set `panel.dataset.kind = "authored"` for styling.

**Coverage floor (proposed):** one walkthrough per stage (beginner, intermediate, advanced) per authored track: 3 x 32 = 96 walkthroughs. Every runnable module track has exactly 3 stages today (measured). The floor and actual count are recorded per track; the test ratchets the floor, not the maximum.

### Anti-Patterns to Avoid
- **Reusing the Python tracer for module lessons:** runs code outside the registered worker.
- **Storing walkthroughs inside generated guides:** many guides are generator-owned (`scripts/format-policy.json` lists R, JAX and DAX outputs); edits would be overwritten.
- **Adding ledger fields to `build_coverage_matrix.py` now:** another agent owns it; keep the ledger curated and separate.
- **Labeling authored steps as "Step through your code":** the authored steps explain the reference, not the learner's draft.

## Common Pitfalls

### Pitfall 1: Stale bindings after formatting or Phase 4 rewrites
**What goes wrong:** `format-repo` or a track generator rewrites a reference; line numbers drift.
**How to avoid:** author walkthroughs only after Phase 4 closes; verify `excerpt` text per step; `--rebind` only when excerpts still match.
**Warning signs:** sha256 mismatch failures in `tests/test_walkthroughs.py`.

### Pitfall 2: Implying execution
**What goes wrong:** UI copy or JSON says "trace" or shows the live-run status line for authored steps.
**How to avoid:** `evidence: "authored"`, `executed: false`, fixed label; UI test asserts the label and that no `lab("step-through")` request is made for module lessons.

### Pitfall 3: Solution leakage
**What goes wrong:** practice-track walkthroughs anchored on solutions are served without the reveal gesture.
**How to avoid:** require `reveal is True` for solution anchors, matching `module-solutions` (`module_service.py:347-349`).

### Pitfall 4: Rubric that counts files
**What goes wrong:** "pass" recorded without recomputation.
**How to avoid:** the test recomputes every measured criterion from the matrix; recorded data holds only judgments, lists and justifications.

### Pitfall 5: Treating local checks as runtime evidence
**What goes wrong:** `--list-only` or host compiler skips reported as verified.
**How to avoid:** ledger labels use the narrowest result label; CURR-05 closure cites CI qualify receipts, not local runs.

### Pitfall 6: Concurrent edits
**What goes wrong:** Phase 3/4 agents change `courses/*` and the matrix while Phase 5 records results.
**How to avoid:** Phase 5 closure plan runs after Phases 3 and 4 verify; rebuild matrix with `--check` first.
