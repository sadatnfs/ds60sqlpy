A beginner's mental model for this lesson#

The learner file asks three questions of the same order data, each at its own grain. The first collapses the 4,362 orders into one revenue figure per order day and slides a 15-row frame along that series. The second keeps every order and groups them by month, so each percentile sees that month's individual totals. The third sums line revenue per category and divides each sum by the grand total from an empty OVER ().

A z-score answers "how unusual is this day?" as (revenue - avg15) / sd15, and it is only as good as its frame. ROWS BETWEEN 14 PRECEDING AND CURRENT ROW counts the 14 previous order days, not calendar days. Early in the series orders are sparse: on a late-2026 load the first 15 order days stretch across 99 calendar days, so a "15-day" window there really covers more than three months. STDDEV_SAMP and VAR_SAMP divide by n - 1, so var15 is sd15 squared up to rounding; STDDEV_POP and VAR_POP divide by n, and mixing the two families makes the columns disagree.

An ordered-set aggregate such as PERCENTILE_CONT(0.9) WITHIN GROUP (ORDER BY amt) sorts a group's values and reads a position from that order. The continuous version uses interpolation between neighbors, so a median can be a value no order has, while PERCENTILE_DISC always returns one that exists.

Two worked SQL examples#

Example 1#
WITH daily AS (
  SELECT
    date_trunc('day', o.order_date) AS d,
    SUM(o.total_amount) AS revenue
  FROM
    orders o
  GROUP BY
    1
)
SELECT
  d,
  revenue,
  ROUND(AVG(revenue) OVER (ORDER BY d ROWS BETWEEN 14 PRECEDING AND CURRENT ROW), 2) AS ma15,
  ROUND(STDDEV_SAMP(revenue) OVER (ORDER BY d ROWS BETWEEN 14 PRECEDING AND CURRENT ROW), 2) AS sd15,
  ROUND(VAR_SAMP(revenue) OVER (ORDER BY d ROWS BETWEEN 14 PRECEDING AND CURRENT ROW), 2) AS var15
FROM
  daily
ORDER BY
  d DESC
LIMIT 60;

How to read it: daily turns the orders into one row per calendar day that has orders. All three window calls share one frame, the current day plus the 14 order days before it, so the mean, deviation and variance always describe the same rows; a WINDOW w AS (...) clause could name that frame once. The windows are computed over the whole ascending series before the outer ORDER BY d DESC LIMIT 60 keeps the newest 60 rows, so even the oldest displayed day still has 14 predecessors in its frame.

Expected result/shape: 60 rows, newest first. On a late-2026 load the top row is 2026-11-23 with revenue 742.14, ma15 3245.49 and sd15 1724.57. d prints as 2026-11-23 00:00:00+00 because date_trunc on a timestamptz keeps that type. var15 reads 2974133.16, a little off 1724.57 squared (2974141.68), because the two columns are rounded separately from unrounded values. No statistic is NULL, since every displayed date has a full 15-row frame. The newest date is the load day itself, so its revenue may be partial.

Example 2#
WITH monthly AS (
  SELECT
    date_trunc('month', o.order_date) AS m,
    o.total_amount AS amt
  FROM
    orders o
)
SELECT
  m,
  PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY amt) AS p50,
  PERCENTILE_CONT(0.9) WITHIN GROUP (ORDER BY amt) AS p90,
  PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY amt) AS p99
FROM
  monthly
GROUP BY
  m
ORDER BY
  m DESC
LIMIT 12;

How to read it: monthly does no aggregation; it only labels each order with the first day of its month. GROUP BY m then hands each month's amt values to three ordered-set aggregates, each of which sorts them with WITHIN GROUP (ORDER BY amt) and reads the 50th, 90th and 99th percentile positions. There is no OVER here: unlike Example 1's windows, these aggregates collapse a month to a single row.

Expected result/shape: 12 rows, one per month, newest first, with columns m, p50, p90 and p99. On a late-2026 load they run from November 2026, a partial month of 151 orders, back to December 2025. Some values print with float noise, such as October's p90 of 944.6360000000001, because PERCENTILE_CONT returns double precision; the exercises cast to numeric before ROUND for that reason. Every row should satisfy p50 <= p90 <= p99.

Learning objectives#

  • Calculate rolling dispersion, ordered-set percentiles, shares, and z-scores at explicit grains.
  • State the limits of small or sparse statistical windows.

Vocabulary and concepts#

  • Ordered-set aggregate: an aggregate whose calculation uses WITHIN GROUP (ORDER BY ...).
  • Z-score: distance from a mean measured in standard deviations.
  • Interpolation: estimating a percentile between observed values.

Worked example / walkthrough#

Aggregate to one row per observed order date, calculate a 15-observation mean and standard deviation, then derive (revenue - avg15) / NULLIF(sd15, 0). Keep the observation count beside the score so early, undersized windows are visible.

Deep dive and reference#

What you will learn#

  • Compute rolling mean, standard deviation, and variance with explicit frames.
  • Use ordered-set aggregates for percentiles.
  • Calculate a ratio to a window total and a rolling z-score.

How the learner script uses the current schema#

The script aggregates orders.total_amount by order day, then applies a 15-observation window (14 PRECEDING plus the current row). It calculates monthly p50/p90/p99 order totals and category revenue share from order_items and products.

ROWS counts result rows, not elapsed calendar days. Because the daily series does not build a calendar spine, the “15-day” names in the script are more precisely 15 observed order dates.

Statistical concepts#

  • A rolling z-score is (revenue - avg15) / sd15; use NULLIF(sd15, 0).
  • PERCENTILE_CONT interpolates between ordered values and may return a value not present in the data.
  • A share is value / SUM(value) OVER (...); calculate at one stable grain.
  • Small windows make tail percentiles and standard deviation noisy.

Practice map#

The six prompts move between grains, so name the grain before writing each query. The first and fifth work on one row per order day, the second on one row per category and order, and the fourth on one row per month and category. The third and sixth use tiny inline fixtures, four values and three identical fives, so you can work out the answer with pencil and paper first and then check that PostgreSQL agrees.

Pitfalls and validation#

  • Do not repeat the whole orders.total_amount once per category in a multi-category order; use category-attributable line revenue.
  • Cast ordered-set results to numeric before PostgreSQL's two-argument ROUND.
  • Undefined zero-dispersion z-scores should remain NULL, not be asserted as normal.
  • Validate that category revenue shares sum to one, allowing for rounding.

Expanded practice lab#

Prompts 3-6 distinguish continuous interpolation, observed-value percentiles, partitioned shares, leakage-free windows, and undefined dispersion. For (10,20,100,200), percentile_disc(0.5) returns an observed middle choice, while percentile_cont(0.5) interpolates between the two central values.

Monthly category share partitions by month; ranking should add a stable category tie-break. A forecasting window ends at 1 PRECEDING, and a constant series uses NULLIF(sd, 0) so “undefined” is not mislabeled as a score of zero.

  daily

  d DESC

  SELECT
    date_trunc('month', o.order_date) AS m,
    o.total_amount AS amt

    orders o

  m,
  PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY amt) AS p50,
  PERCENTILE_CONT(0.9) WITHIN GROUP (ORDER BY amt) AS p90,
  PERCENTILE_CONT(0.99) WITHIN GROUP (ORDER BY amt) AS p99
FROM
  monthly
GROUP BY
  m
ORDER BY
  m DESC
LIMIT 12;

-- Ratio to total (ratio_to_report equivalent)
WITH cat AS (
  SELECT
    p.category,
    SUM(oi.unit_price * oi.quantity * (1 - oi.discount)) AS revenue
  FROM
    order_items oi
    JOIN products p ON p.product_id = oi.product_id
  GROUP BY
    p.category
)
SELECT
  category,
  ROUND(revenue, 2) AS revenue,
  ROUND(revenue / NULLIF (SUM(revenue) OVER (), 0), 4) AS share_of_total
FROM
  cat
ORDER BY
  revenue DESC;

Every statement is a read, so the file needs no BEGIN or ROLLBACK. How these answers fit together#

The learner script computed rolling statistics, monthly percentiles and lifetime category shares, each at a different grain. These answers keep that discipline. The rolling z-score and the forecast work on one row per order day, the percentiles on one row per category and order, and the shares on one row per month and category. The median comparison and the constant series use inline fixtures, where the right answer can be worked out by hand before trusting the database.

Two cautions run through all six. A ROWS frame counts order days, not calendar days, so a sparse stretch of the series quietly widens the window. And a statistic over a tiny or constant sample can be undefined, which SQL should show as NULL rather than as a convenient zero.

Exercise 1: Fifteen-row rolling z-score for daily revenue#

SET search_path TO training, public;

WITH daily AS (
  SELECT
    date_trunc('day', order_date)::date AS order_day,
    SUM(total_amount) AS revenue
  FROM
    orders
  GROUP BY
    date_trunc('day', order_date)
),
rolling AS (
  SELECT
    order_day,
    revenue,
    AVG(revenue) OVER (ORDER BY order_day ROWS BETWEEN 14 PRECEDING AND CURRENT ROW) AS avg15,
    STDDEV_SAMP(revenue) OVER (ORDER BY order_day ROWS BETWEEN 14 PRECEDING AND CURRENT ROW) AS sd15
  FROM
    daily
)
SELECT
  order_day,
  ROUND(revenue, 2) AS revenue,
  ROUND(avg15, 2) AS avg15,
  ROUND(sd15, 2) AS sd15,
  ROUND((revenue - avg15) / NULLIF (sd15, 0), 4) AS z_score
FROM
  rolling
ORDER BY
  order_day;

Expected shape: one row per day with orders. A positive z-score is above the rolling mean; a negative score is below it. The first row has no sample standard deviation, and any zero-standard-deviation frame yields NULL.

Assumption: “15-day” in the learner example means 15 observed daily rows. To model 15 consecutive calendar days, first join revenue to a dense date series and decide whether missing days mean zero or unknown.

Reasoning and verification#
  • Inputs/evidence: For sql-40 Exercise 1, read from orders, sum total_amount per UTC day in the CTE daily, then compute a trailing 15-row mean and sample standard deviation (ROWS BETWEEN 14 PRECEDING AND CURRENT ROW) in rolling and the z-score (revenue - avg15) / NULLIF(sd15, 0).
  • Expected result/shape: For sql-40 Exercise 1, expected output: 1,080 rows on this load, one per UTC day with orders from 2023-02-13 to 2026-11-23; the second row, 2023-03-07, has revenue 1,034.00 against avg15 1,118.63 and z_score -0.7071. A positive z-score is above the rolling mean; a negative score is below it. The final columns are order_day, revenue, avg15, sd15, and z_score. The final order is order_day.
  • Independent verification: For sql-40 Exercise 1, confirm one row per order_day, so the row count equals SELECT COUNT(DISTINCT date_trunc('day', order_date)) FROM orders; the first row has NULL sd15 and z_score because a one-row sample has no standard deviation, and for one later day recompute avg15 as the mean of that day's and the 14 previous days' revenue in daily.
  • Intermediate relation check: daily alone returns one row per order day, 1,081 on a late-2026 load, starting at 2023-02-13 with 1,203.26. Its order_day values are unique because the CTE groups by the date_trunc expression it then casts to date, and under the course's UTC TimeZone each day bucket maps to one date.
  • Clause check: Both window calls repeat the frame ORDER BY order_day ROWS BETWEEN 14 PRECEDING AND CURRENT ROW, so mean and deviation cover the same rows. Rounding happens only in the last SELECT, after the score is built from unrounded avg15 and sd15. On that load the newest row's avg15 of 3,245.49 matches a hand average of the last 15 daily revenues.
  • Alternative/trade-off: Adding COUNT(*) over the same frame exposes the 14 short frames at the start of the series, which the worked walkthrough asks you to keep visible. A CASE could then blank scores whose count is under 15; this answer keeps every row and leaves that judgment to the reader.
  • Edge case: The second row scores -0.7071 or 0.7071 whatever the two revenues are, because two values always sit 0.7071 sample deviations (one over the square root of two) from their mean. Early scores therefore say little. On that load the extremes are 2.9949 and -2.3790, and 34 days fall beyond 2 in either direction.

Exercise 2: Category P50 and P90 of order values#

An order can contain several categories. This answer defines an “order total within a category” as the sum of that category's net lines in that order; using the whole order total for every category would double-count mixed orders.

SET search_path TO training, public;

WITH category_order_values AS (
  SELECT
    p.category,
    oi.order_id,
    SUM(oi.unit_price * oi.quantity * (1 - oi.discount)) AS category_order_value
  FROM
    order_items oi
    JOIN products p ON p.product_id = oi.product_id
  GROUP BY
    p.category,
    oi.order_id
)
SELECT
  category,
  ROUND(PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY category_order_value)::numeric, 2) AS p50_order_value,
  ROUND(PERCENTILE_CONT(0.9) WITHIN GROUP (ORDER BY category_order_value)::numeric, 2) AS p90_order_value,
  COUNT(*) AS category_orders
FROM
  category_order_values
GROUP BY
  category
ORDER BY
  category;

Expected shape: one row per sold category. PERCENTILE_CONT can interpolate between observed values, so a percentile need not equal an actual order value.

Reasoning and verification#
  • Inputs/evidence: For sql-40 Exercise 2, read from order_items joined to products, sum each order's net lines per category in category_order_values, then compute PERCENTILE_CONT(0.5) and PERCENTILE_CONT(0.9) of those per-order category values and count them per category.
  • Expected result/shape: For sql-40 Exercise 2, expected output: 6 rows, one per category, whose category_orders run from 2,145 for Books to 2,192 for Apparel and sum to 13,085, more than the 4,362 orders because an order with lines in several categories counts once in each; p50_order_value runs from 146.54 for Home to 150.24 for Electronics on this load. PERCENTILE_CONT can interpolate between observed values, so a percentile need not equal an actual order value. The final columns are category, p50_order_value, p90_order_value, and category_orders. The final order is category.
  • Independent verification: For sql-40 Exercise 2, confirm 6 rows, one per category, and that category_orders equals SELECT COUNT(DISTINCT oi.order_id) FROM order_items oi JOIN products p USING (product_id) WHERE p.category = <that category> (for example 2192 for Apparel); p90_order_value must be at least p50_order_value in every row.
  • Intermediate relation check: category_order_values holds 13,085 rows, one per (category, order_id). That equals the number of order_items lines, because no order in this seed repeats a category: orders carry one to five lines, each from a different category, and 3,490 of the 4,362 orders span two or more categories.
  • Clause check: The per-category values are small, with medians from 146.54 (Home) to 150.24 (Electronics) and P90s from 373.01 (Sports) to 386.32 (Books), while the median whole order is 561.21. That gap is the point: each value counts only one category's part of an order. category_orders runs from 2,145 for Books to 2,192 for Apparel and sums to 13,085.
  • Alternative/trade-off: PERCENTILE_DISC would return an observed category order value instead of an interpolated one. For Apparel both functions give 149.50, which shows that its two middle values, positions 1,096 and 1,097 of 2,192, are equal; in general the two can differ.
  • Edge case: An order with lines in several categories contributes one value to each of those categories; using the whole order total instead would count each of the 3,490 mixed orders at full value in every category it touches.

Pitfalls#

  • STDDEV_SAMP is NULL for a one-row frame. NULLIF(sd15, 0) also protects constant frames from division by zero.
  • A ROWS frame counts rows, not elapsed time.
  • Ordered-set aggregates such as PERCENTILE_CONT use WITHIN GROUP; they are not written with OVER in this grouped query.
  • Define the analytical grain before calculating a percentile. Line-level and order-level percentiles answer different questions.

Exercise 6: Preserve undefined dispersion#

The constant fixture has standard deviation zero. NULLIF(sd, 0) returns NULL for every z-score, accurately distinguishing undefined from normal.
