## Outcome and mechanism

Perform a validated many-to-one lookup and detect duplicate or unmatched keys before they change totals.

Joining tables is a data-model operation, not merely a convenient way to append columns. Declare the grain on both sides and the expected match cardinality. A sales-line table can have many rows for one product, while a product dimension should have one row per product key. Duplicate dimension keys can multiply fact rows and inflate a later sum.

For a many-to-one lookup, match can return one index per left-hand key while preserving the left table's order. This is useful only after verifying that the right-hand key is unique. match returns the first match when duplicates exist, which can hide an inconsistent dimension rather than expose it. Check uniqueness before trusting that apparent convenience.

Unmatched records need an explicit policy. Rejecting them, retaining them with missing dimension values and routing them to a diagnostic set are different choices. A left join that preserves all facts can still create missing attributes. Distinguish an unknown product key from a known product whose optional label is itself missing.

Base merge supports relational joins, but its output order and row count should be treated explicitly. A many-to-many relationship can legitimately expand rows when the model calls for it; it is a defect only relative to the stated contract. Always reconcile counts and additive totals around the join. A plausible-looking output table is not sufficient evidence that each fact appeared exactly once.

## Vocabulary

| Term | Meaning |
| --- | --- |
| Join cardinality | The relationship between matches on the left and right sides. |
| Many-to-one lookup | Many fact records mapped to at most one dimension record per key. |
| Unmatched key | A key without a corresponding record on the other side. |
| Join multiplication | Extra result rows created by multiple matching records. |

## Read the syntax

Validate !anyDuplicated(dimension$key) and !anyNA for required keys. match(fact$key, dimension$key) returns positions or NA. Use merge(..., by=..., all.x=TRUE) only with understood cardinality, and explicitly reorder results when presentation order matters.

## Worked examples

### Example 1: A validated dimension lookup preserves fact order

```r
facts <- data.frame(line = c("L1", "L2", "L3"), product = c("B", "A", "B"), amount = c(10, 20, 30))
dimension <- data.frame(product = c("A", "B"), category = c("Paper", "Home"))
stopifnot(!anyDuplicated(dimension$product), !anyNA(dimension$product))
index <- match(facts$product, dimension$product)
stopifnot(!anyNA(index))
facts$category <- dimension$category[index]
stopifnot(identical(facts$category, c("Home", "Paper", "Home")), sum(facts$amount) == 60)
print(facts)
```

**Expected observation:** Three rows, total 60.

The lookup adds exactly one category per fact and retains the original line order. Key validation makes the first-match behavior safe for this contract.

### Example 2: Duplicate matches inflate a naive join

```r
facts <- data.frame(product = c("A", "B"), amount = c(10, 20))
bad_dimension <- data.frame(product = c("A", "A", "B"), category = c("X", "Y", "Z"))
joined <- merge(facts, bad_dimension, by = "product", all.x = TRUE)
stopifnot(nrow(joined) == 3L, sum(joined$amount) == 40)
stopifnot(anyDuplicated(bad_dimension$product) > 0L)
print(joined)
```

**Expected observation:** Three rows, total 40 instead of 30.

The A fact appears twice. A duplicate-key guard would reject the dimension before the incorrect total becomes a report.
