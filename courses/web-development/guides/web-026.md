# web-026: Disclosures, dialogs and focus management

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-025`

## Learning objectives

Build a disclosure and a deliberately opened local dialog. Explain why a modal is inappropriate for every small message. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A disclosure reveals content in the current document, while a dialog creates a focused interaction context. These are different patterns and should not be chosen only for visual style. Native details and summary elements provide a useful disclosure without JavaScript. A modal dialog changes which content can be interacted with and needs a clear way to close, an accessible name and sensible focus restoration.

Focus is part of the interaction's state. When a dialog opens, the user should land in a meaningful place. When it closes, focus usually returns to the control that opened it if that control still exists. Keyboard users must not become trapped in an accidental custom implementation. Native dialog behavior supplies important mechanics, but authors still own labeling, content order and testing.

## Syntax anatomy and mechanism

Use details with summary for optional explanation. Use a dialog element and showModal when a true modal task is justified. A form with method=dialog can close the dialog; this local behavior is distinct from a network form submission. The offline preview may restrict submission APIs, so this reference closes explicitly through the dialog API and keeps all state local.

## Worked example / walkthrough

### Worked example 1: A native disclosure

The summary is the interactive label.

```html
<details><summary>Why this rule?</summary><p>The explanation remains in the document.</p></details>
```

**Expected observation:** The explanation expands and collapses without custom script.

### Worked example 2: An explicit dialog action

Opening is an intentional event, not page-load interruption.

```javascript
openButton.addEventListener('click', () => dialog.showModal());
closeButton.addEventListener('click', () => dialog.close());
```

**Expected observation:** The user controls entry and exit from the dialog.

## Six progressive exercises

### Exercise 1: Choose a disclosure or dialog for an optional explanation.

**Expected evidence:** A disclosure usually fits because it preserves the surrounding reading context.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Give a dialog a visible heading and accessible name.

**Expected evidence:** aria-labelledby connects it to the heading's unique id.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a disclosure and a deliberately opened local dialog.

**Expected evidence:** Both are labeled, keyboard operable and can be closed without losing the task.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose focus returning to an unrelated control after closure.

**Expected evidence:** Track the opener and restore focus when appropriate.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test Escape, close-button activation and repeated opening.

**Expected evidence:** The interaction remains consistent across repeated cycles and does not trap focus.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain why a modal is inappropriate for every small message.

**Expected evidence:** It interrupts context and imposes focus management costs that a simple inline message avoids.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not build a dialog by merely positioning a div over the page. Avoid automatically opening modal explanations during reading. Browser behavior must be tested after interaction, not only from initial DOM structure.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain disclosure, dialog, focus management without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
