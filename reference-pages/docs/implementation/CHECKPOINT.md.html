This file describes the architecture and continuation boundaries of the current source. It is not a record of a particular developer's machine, test session or hosted CI run. Use validation and the workflow results for the exact revision being reviewed.

Delivered application structure#

/classroom provides one home and workspace for all registered subjects. /, /learn, /journeys and /journey-preview are compatibility aliases for that shell. The old independent Python/SQL and module pages are retired. Subject selection, search, themes, lesson navigation, code or reading workspace, notes and progress belong to this shared interface.

The directory combines the historical Python, PostgreSQL and engineering bridge catalog with authored module subjects and the statistics/ML tutorial. Identity and prerequisite metadata are derived from the loaders. Inspect the current inventory rather than copying a past count:

python scripts/course.py catalog
python scripts/check_modules.py --json

Historical day labels, canonical lesson IDs and language variants remain stable. The legacy catalog and module manifests are separate authoring contracts that share one learner experience. See ADDING_A_MODULE.md before choosing where an extension belongs.

Presentation and learning modes#

The CUDA subject adds 128 chapters with default reading workspaces, separately saved CPU-model variants, selected framework/Spark CPU variants and optional NVIDIA variants. GPU workers are explicitly selected and excluded from ordinary default/--all builds. They require a real allocation/kernel/readback probe. CPU checks and compiler acceptance never establish device or performance qualification. See CUDA preparation for supported preparation and limits.

The web-development subject combines 60 HTML/CSS/PHP lessons. html-browser uses the existing opaque, network-blocked preview and browser observations; php-cli checks syntax then runs main.php with a prepared SQLite driver. The optional HTTP project is separate from the ordinary single-file worker. The preview studio supports opt-in, debounced HTML/CSS and browser JavaScript/D3 updates, fit/desktop/tablet/phone viewports, pause and stop controls, console navigation and protected editor focus. Automatic updates do not create history receipts. Manual runs and explicit observation saves do, and navigation cancels queued or stale work. Reload restores the draft without enabling execution.

Image distribution supports local builds or explicit Docker Hub selection. Per-project images.env stores source, namespace and version; architecture tags match the engine. Resume never pulls or builds. Publication is an explicit separate script and optional manual workflow, not a side effect of startup.

The shared renderer provides build-compiled TeX, accessible MathML, bundled Latin Modern typography and syntax highlighting. Reviewed prose normalization runs before reader generation; copying a code block must preserve source characters. The generated static library remains available without the application server. The old design-preview renderer and native launchers are retired. The five original module plans remain active metadata under docs/expansion/plans/, loaded by module_plans.load_core_plans. Contributor ds60 serve exposes the same classroom shell using its actual prepared local capabilities.

Practice lessons have progressive exercises, hints and separate solutions. The statistics book is a theory-and-code tutorial with directly available worked examples and answered interview discussions. Reading markers and learner-confirmed completion do not certify understanding.

Additional scientific and offline workspaces#

JAX uses a dedicated CPU worker with fixed JAX/JAXLIB versions. R uses a pinned Rscript worker with reviewed CRAN package hashes. Bayesian tutorials use a separate PyMC/ArviZ environment, preserving the InferenceData API expected by those examples. Profiles and subjects remain separate; optional hardware work must state its own preparation and qualification limits.

DAX is an editable offline workspace. It saves source and notes, exposes named hand-derived references with bound model/source hashes, and rejects execution requests. Reference tables are never converted to run receipts.

The statistics book's original chapter manifest and topic outline remain stable. Additional worked tutorials use tutorials/index.json and validated direct prerequisites. The paired data-visualization subject reuses Python Core and the browser JavaScript profile. Python and R figure documents are bounded and validated before storage; Plotly data renders in an opaque offline iframe. History displays stored figures without rerunning the source. See plotting and textbook rendering.

Runtime and storage boundaries#

The shared ./classroom launcher resumes existing containers, builds only missing images, waits for readiness and opens the actual loopback address. Existing containers are reused. Docker can reassign automatic host ports when restarting the same PostgreSQL container. If the browser port changes, only the app is recreated from its existing image to preserve exact Host/Origin checks; there is no build or pull. PostgreSQL and worker IDs and all volumes are retained. Fixed browser/database ports preserve the URL and all existing container IDs on later unchanged resumes. Deliberately changing ports uses --rebuild. The launcher remembers selected profiles and registry mode in .classroom/<project>/selection.env before preparation, so an interrupted build retains intent. Requested ports are also saved before preparation; the ready URL is saved only after HTTP acceptance. Older projects without the selection file infer recognized profiles from their own worker containers. A new project defaults to all ordinary CPU and language workers. Explicit --starter, --profile and --all replace the saved selection; they do not stop unselected running workers. resume and --no-build prohibit builds and pulls. --rebuild installs source/configuration updates, and build builds without starting. Missing containers can use existing images and volumes; database recreation repairs the app's shared network reference and public address. Custom project names must be supplied explicitly on later commands; there is no global project guess. Windows uses WSL 2 with an integrated Linux-container engine. Host compilers and databases are unnecessary for the ordinary classroom route. Linux containers are the supported release target. Native Windows backend installers, executable bundles and editor-launch APIs are retired. Thin Docker wrappers and WSL 2 instructions remain. Linux contributor checks and container/browser receipts govern the release matrix, as described in validation.

The app preserves Python/SQL pads, coaching phases and immutable run receipts. Module lessons preserve source, notes, variants and job history through their own storage adapter. Viewing a saved result is read-only. Reconnection must not replay a job whose outcome is unknown, and a receipt-save failure must not hide a successful execution.

The C17, Go, C#, Rust and Swift workers use fixed single-file compilation and execution. Rust includes a prepared Arrow dependency; C# includes its fixed .NET console project. Larger Cargo, Go, .NET and Swift packages are explicitly separate project workflows. Swift language and Foundation examples run in Linux; SwiftUI, UIKit, simulators and signing require the documented macOS/Xcode route.

D3 examples use bundled D3 in an opaque-origin browser iframe, with no CDN or network access. The preview captures initial output and later interaction errors, supports stopping and fullscreen viewing, and is removed on navigation. Its observations are saved by browser_runs.py separately from worker receipts. They carry the source hash and verified: false; client output is not a trusted worker verification. Viewing an observation never reruns it or replaces a pad. The iframe is not a hard CPU sandbox for arbitrary untrusted programs.

Docker and the extended Kubernetes networking units include explicit prepared lab workflows. The ordinary classroom does not expose the engine socket or implicitly apply a cluster manifest. The owned Kubernetes adapter admits only its reviewed operation/verifier set; new networking examples do not expand that authority merely by appearing in the curriculum.

Named Compose volumes hold learning state and PostgreSQL data. Reuse the same project name to resume that workspace. Keep volumes when replacing containers or removing images, and follow the documented backup workflow before moving machines. Private runtime sessions and credentials are separate from portable learner exports.

Kubernetes operations require deliberately prepared, owned local resources. Pretrained models, GPU experiments, external APIs and longer-running services have separate preparation and capability requirements. A small offline example demonstrates its mechanism; it does not prove model quality, production capacity or safety on arbitrary infrastructure.

Operational constraints retained across refactors#

These constraints replace scattered historical status notes. Their live sources, subject guidance and tests determine exact limits; old acceptance counts do not.

  • Worker isolation: the Linux supervisor demotes learner processes and keeps private credentials outside their working directory. Protect both token files and their parent directories; apparent file modes on a shared mount are not a substitute for actual access-denial checks. Keep narrow declared capabilities, bounded process groups, combined compile/run deadlines, output and scratch limits, cancellation and descendant cleanup. No ordinary worker gets an engine socket. A configured limit is not proof it is enforced.
  • Kubernetes ownership: require a short-lived target-bound lease, exact namespace/resource identity and recorded UIDs. Never use ambient kubeconfig. Admission is a finite reviewed operation/verifier set. Cleanup must preserve preexisting or replaced resources after failure. Optional CNI policy, storage, ingress/Gateway/TLS, CRDs and Secret observation need their actual capabilities; synthetic local fixtures do not establish those services. Keep secret bodies and private credentials out of user-facing failure messages and exports. See the owned adapter.
  • Spark state: use fresh owned file/checkpoint/sink roots and stop only queries created by the job before cleanup. A recovery scenario must preserve compatible source, query and state-store identity. Source recovery, business-event deduplication and external sink idempotency are distinct. Inspect actual plans and metric definitions; pushed-down filtering can change observed input counts. Local Spark does not qualify distributed fault tolerance. GPU plans add a separate compatible-component and supported-operator contract.
  • Compiled and database examples: the one-file C++/Java pads do not imply arbitrary multi-file builds. Use separate prepared CMake/Java projects when needed, preserving compile/link/run diagnostics. Prepared H2 JDBC fixtures are not PostgreSQL. Preserve inherited JVM resource settings and distinguish runtime diagnostics on stderr from application stdout. SQL stateful projects must never depend on objects rolled back by earlier steps.
  • ML and language-model evidence: preserve train-only preprocessing, split boundaries, tensor shapes, reductions and finite-value checks. CPU framework comparisons teach equivalent objectives without asserting identical kernels. Tiny attention, embedding, quantization or adapter examples do not establish pretrained quality or production memory/performance. RAG evidence, factual support, tool authorization and held-out task utility need separate evaluation; code may execute successfully while quality fails. Optional models are pinned, deliberately acquired and independently evaluated.
  • Immutable source evidence: preserve runtime JSON receipts and their hashes. A prose-only or AST-equivalent formatting change may retain a documented source correspondence, but changed behavior requires fresh runtime acceptance. Statistics source-outline.md and coverage identities remain authoritative; that tutorial has no mandatory exams or hidden answers.

Portable source ZIPs and container workspaces share course_paths.COURSE_PATHS. Staging excludes Git history, credentials, learner state and temporary output. The source ZIP is built by scripts/build_starter.py; it contains the Docker launcher and source, not prebuilt images. Workspace preparation must preserve an existing .learning directory when refreshing bundled sources. Package tests must verify both exclusion and a complete startable source payload.
