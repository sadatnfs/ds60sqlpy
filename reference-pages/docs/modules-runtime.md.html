Optional module runtimes#

The module application sends source to explicitly prepared private workers. The original Python/SQL pads and the reading path continue to work without these profiles. Preparing one subject does not install every framework.

Prepare only the profiles you need#

Start the ordinary Docker lab first. From the extracted complete course folder, use the host launcher to build and start selected workers. The launcher owns engine access; the browser and worker receive no Docker socket.

macOS or Linux:

bash scripts/module_lab.sh build --profiles python-core,cpp20
bash scripts/module_lab.sh start --profiles python-core,cpp20 --no-browser

Windows PowerShell:

powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\module_lab.ps1 build -Profiles python-core,cpp20
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\module_lab.ps1 start -Profiles python-core,cpp20 -NoBrowser

Open http://127.0.0.1:8765/journeys after readiness succeeds. Use the same profile list and project for later status, start or stop actions. Profile preparation needs a connected bootstrap; practice uses the prepared local images. Nothing uploads an image or downloads a model when you press Run. Kubernetes uses its separate owned-cluster preparation and lease checks.

The NumPy attention foundation uses python-core; it does not require PyTorch. A successful fixed compiler operation does not establish a CMake/CTest project build. The current browser operation compiles a single source file directly. Multi-file CMake, interactive REPL state, package resolvers, arbitrary compiler flags, arbitrary command lines, GPU jobs, distributed Spark and external model endpoints are outside this operation.

What readiness and a result mean#

At worker startup, a fixed bounded probe checks identity isolation and executes an actual backend smoke: C++20 compilation and run, a Scala compilation and run, a tiny local Spark count, or a framework tensor/array sum. That probe has a 45-second total deadline. /health returns its cached result and an ephemeral instance_id; health polling does not repeatedly start a JVM or import a framework. A failed probe leaves the service not ready. Preparation must inspect that failure rather than claiming that an image definition proves readiness.

A submitted job moves through preparing, compiling when needed, running and verifying when requested. For ordinary CPU workers, compilation and execution share the selected total 15, 60 or 120 second deadline. A compiler invocation also has a maximum 60-second phase deadline. Failed compilation never runs an older binary. Cancellation kills the owned process group and, inside the dedicated worker PID namespace, remaining processes with the fixed job UID. A job that creates a new session does not gain an unlimited background lifetime.

Execution-only success means an actual zero exit status. It does not mark mastery or invent checks. Registered verifiers call typed APIs against fixed fixtures and return named boolean checks:

  • tf-gradient-v1: three float64 gradient-step fixtures and invalid-rate cases.
  • llm-causal-attention-v1: numeric attention values, forbidden weights, future-value perturbation and malformed-input cases.
  • cpp-ownership-v1: fourteen value/ownership checks through an immutable compiled harness that calls the submitted functions.
  • spark-rows-v1: paid identities, typed schema, NULL-aware golden groups, repartition invariance and a changed-input fixture.

A selected verifier must produce a valid bounded check report, every reported check must pass, and the process must exit zero. Printed words such as success or checks passed do not create verification evidence. These checks are teaching feedback for trusted personal learner code, not a tamper-resistant examination system. Progress and mastery still require the learner's reasoning.

Resource and credential boundaries#

compose.modules.yaml attaches workers only to an internal project network. Worker port 8081 is not published. The app shares the PostgreSQL network namespace and reaches only fixed worker service names supplied by the host launcher. Worker credentials live in a private runtime session outside .learning; portable progress backups must exclude that session.

The worker token is mounted inside the image-owned /run/ds60 directory, which is root-owned mode 0700. This also protects token files when Windows file sharing expands their POSIX mode bits; it is not a general permission exception for arbitrary paths. The mandatory child-read probe still applies. The HTTP supervisor reads its private token, then each learner process runs as UID/GID 65534 with supplementary groups cleared. Readiness proves that this identity cannot open the credential and that the supervisor can terminate a process with that identity. Images require a private container PID namespace and the narrow CHOWN, SETUID, SETGID, DAC_OVERRIDE and KILL capabilities for this supervisor. Learner processes do not retain those capabilities. There is no engine socket, repository mount, learner home mount or cloud credential. The ordinary personal app remains a trusted-code environment, not a hostile multi-user sandbox.

Requests require X-DS60-Worker-Token, including health. Cross-origin browser requests are refused. A worker accepts one active job, retains at most 32 terminal snapshots, rejects bodies above a fixed bound and source above 256 KiB, and keeps at most 128000 bytes of output with a head/tail truncation notice. Output draining preserves final errors and exit status. The browser may impose a smaller source limit.

Each job has a disposable scratch directory, a 32 MiB total file allowance, a 1024-file allowance and a per-file 32 MiB limit. Container tmpfs is 128 MiB and explicitly permits execution of compiled job files; it is private disposable memory, not a host filesystem mount. Ordinary workers have a 2 GiB memory cap and heavy framework/Spark profiles have 3 GiB. Two CPUs and 128 processes are the ordinary worker ceilings; Spark services allow 384 tasks because JVM and Python worker threads count toward that limit. JVMs receive ActiveProcessorCount=2 and fixed small GC thread budgets. Health, polling and cancellation use an existing HTTP control thread so child PID pressure cannot prevent creation of a request-control thread. These are initial small-lab budgets, not guarantees for long training or large data. Enable a small number of workers within the engine's available memory. No model, generated dataset or Spark output is exported by this initial worker protocol. Source, notes and bounded results are saved through the app's existing host-mounted learning workspace; disposable worker files are removed.

Reproducibility and qualification#

TensorFlow and CPU PyTorch use separate Linux amd64 and arm64 requirements locks in docker/workers/, with exact transitive versions and wheel hashes. Builds use --require-hashes --only-binary=:all:. Re-resolve these locks intentionally, then repeat import, numeric verifier and process-cleanup proofs. Do not install the isolated TensorFlow tuple into the base course environment. Base-image version tags select the reviewed toolchain family; capture actual image IDs/digests and architecture from a successful build when qualifying it. A tag or a resolved dependency graph alone is not a runtime proof.

As of 22 October 2026, the upstream TensorFlow 2.20.0 release has CPython 3.12 Linux x86_64 and ARM64 wheels. The tensorflow_cpu package has no corresponding ARM64 wheel in that release, so the common profile uses tensorflow without a CUDA extra and disables GPU visibility. Official CPU PyTorch 2.9.1+cpu wheels exist for both Linux architectures. These metadata checks establish an available build input, not a successful import on either architecture. TensorFlow installation, TensorFlow 2.20.0 release metadata, official PyTorch CPU wheels.

Spark 4.0.1 requires Java 17/21 and Scala 2.13 with the same Scala version used by the distribution. The worker copies the official Spark distribution into its own Python 3.12/JDK 17 image and compiles against that distribution's jars. No Maven, Scala CLI or pip resolver runs during a learner job. Spark 4.0.1 prerequisites, Apache Spark image source, official GCC image architectures.

Windows uses a Linux-container engine; macOS uses its engine's Linux VM. Native amd64 and native arm64 are separate qualification rows. A successful arm64 run does not prove Windows host mount behavior, amd64 execution or an emulated platform. Record exact runtime evidence in the implementation checkpoint rather than filling an untested row with a checkmark.

For an explicitly trusted registry mirror, build arguments DS60_CPP_IMAGE, DS60_PYTHON_IMAGE, DS60_SPARK_IMAGE and DS60_CORE_IMAGE can override the corresponding reviewed base. Keep the same toolchain family and record the resolved digest and platform. Never disable TLS to repair registry access. An override is a new image input and needs the same runtime qualification.

Prepare and run the owned Kubernetes lab#

This is an optional host preparation path. Read the lesson and complete its prediction before preparing a session: the scoped credential lasts 15 minutes. Build images first, then prepare the cluster immediately before practice. A paused browser does not extend the lease. The app's Run creates and proves only fixed owned hello resources; it does not select an existing cluster or install Kubernetes. Opening or saving a lesson never performs preparation.

Use the same local Linux-container engine for the entire session. The helper requires host Python 3.12, but it does not require a host Kubernetes package or an existing kubeconfig. The main Docker lab continues to need no host Python. If your interpreter has another name, pass --python /absolute/path/to/python to Bash or -Python C:\absolute\path\python.exe to PowerShell. Use that same interpreter for prepare_kubernetes.py below. Keep paths in the terminal's own OS: Linux paths in WSL, Windows paths in PowerShell.

  1. From the extracted full course folder, build the fixture and dedicated worker while connected. This can take time and does not create a cluster.
   bash scripts/module_lab.sh build --profiles k8s-kind
   python3 scripts/prepare_kubernetes.py tools --allow-download
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\module_lab.ps1 build -Profiles k8s-kind
   python .\scripts\prepare_kubernetes.py tools --allow-download

The tool helper downloads pinned kind v0.33.0 and kubectl v1.37.0 from their official release locations and verifies SHA256 before publishing the files. doctor is a read-only availability check. Neither action creates a cluster. Registry/tool downloads require a connected bootstrap. No image is pushed.

  1. Obtain the selected local engine endpoint. In Bash:
   if [ -n "${DOCKER_HOST:-}" ]; then
     ENGINE="$DOCKER_HOST"
   else
     ENGINE="$(docker context inspect --format '{{.Endpoints.docker.Host}}')"
   fi
   python3 scripts/prepare_kubernetes.py prepare --confirm-create --docker-host "$ENGINE" --allow-node-download

In PowerShell:

   $Engine = $env:DOCKER_HOST
   if (-not $Engine) {
       $Engine = docker context inspect --format '{{.Endpoints.docker.Host}}'
       if ($LASTEXITCODE -ne 0) { throw 'Select a ready local Docker context first.' }
   }
   python .\scripts\prepare_kubernetes.py prepare --confirm-create --docker-host $Engine --allow-node-download
   if ($LASTEXITCODE -ne 0) { throw 'Owned preparation failed. Review its private receipt.' }

The helper refuses remote endpoints. --allow-node-download explicitly allows the pinned node-image bootstrap if absent; omit it for a fully cached run. A reviewed TLS-preserving mirror can be selected with --node-image mirror.gcr.io/kindest/node:v1.37.0@sha256:a1ed56cfb0e7b93589bdf97c8cd566405a265939e3620fc4f5de89adff580ae5. The digest is unchanged. Do not disable TLS or substitute a floating tag.

  1. Copy only the returned session_dir path into a terminal variable. The helper prints no credential. The random private directory is outside the course and .learning; do not move it into a backup, pad or export. Replace the example placeholder with the actual absolute receipt path.
   SESSION="/absolute/private/path/from/session_dir"
   bash scripts/module_lab.sh start --profiles k8s-kind --k8s-session "$SESSION" --no-browser
   $Session = 'C:\absolute\private\path\from\session_dir'
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\module_lab.ps1 start -Profiles k8s-kind -K8sSession $Session -NoBrowser

Start checks the private lease, host receipt, matching local endpoint and remaining lifetime before creating a worker token or starting services. It uses compose.kubernetes.yaml and the selected k8s-kind profile only. Remove --no-browser or -NoBrowser to open the local journey page. Choose k8s-003 for Deployment-only practice or k8s-008 for the pilot. An expired session is refused. Stop/release it, then prepare a new one; there is no silent renewal or switch to an ambient admin context.

  1. Stop the selected app/worker before explicitly releasing the owned cluster. Status and stop remain available when a lease has expired. They do not create a cluster, refresh credentials or delete the cluster.
   bash scripts/module_lab.sh status --profiles k8s-kind --k8s-session "$SESSION"
   bash scripts/module_lab.sh stop --profiles k8s-kind --k8s-session "$SESSION"
   python3 scripts/prepare_kubernetes.py release --session "$SESSION" --confirm-release
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\module_lab.ps1 status -Profiles k8s-kind -K8sSession $Session
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\module_lab.ps1 stop -Profiles k8s-kind -K8sSession $Session
   python .\scripts\prepare_kubernetes.py release --session $Session --confirm-release
   if ($LASTEXITCODE -ne 0) { throw 'Release was not confirmed. Preserve the private receipt for recovery.' }

Release validates the recorded full Docker container ID, kind owner label and namespace UID. It removes only that immutable owned one-node container, preserves a same-name replacement and leaves shared engine networks and unrelated contexts alone. Successful exact-name and ID listings must prove absence before credentials are removed. Repeating a completed release is safe while its private host receipt remains. It does not delete learner work or PostgreSQL data. Ambiguous/failed cleanup preserves private evidence.

The worker receives only a short-lived scoped kubeconfig in root-private mounts. It gets no engine socket or host admin config. The kubectl child runs as UID 65533, which must be unable to read supervisor credentials. Workload Pods run as UID 65532 without bearer-token mounts, host paths or privilege. The worker joins its private app network and the explicitly prepared kind network; no worker port is published to the host.

The 15/60/120-second selection bounds work. Cleanup then has a fresh independent 15-second reserve, even after cancellation or timeout. Shutdown requests cancellation and waits up to 20 seconds; Compose gives the service 30 seconds. The fixed synthetic Pod templates use a 1-second termination grace, rather than the general Kubernetes default 30 seconds, because they have no durable state to flush. Pod termination explains this distinction. Only resource UIDs recorded or recovered with this Run's private nonce are eligible for cleanup. Failure to prove cleanup reports failed with the affected resource; it never reports an unproved clean cancel.

k8s-readiness-v1 verifies the owned Deployment and stable Ready Pod identities, Service EndpointSlice UID membership, an actual in-cluster /version client and exact owned cleanup. The foundation can omit the Service and receives no routing grade. The pilot's rolling update, Pod deletion, second-Service tasks and explanations remain manual scoped/teacher activities. This one-shot Run does not grade the complete six-task course. Native Windows ACLs/file sharing and other host/architecture rows require separate acceptance.

Recorded runtime boundary#

The private work/modules-acceptance receipts record actual Linux aarch64 Ready plus positive and negative runs for python-core, tensorflow-cpu, cpp20, scala-jvm, spark-local-scala and spark-local-python. llm-torch-cpu currently has metadata/hash-lock evidence and remains unqualified. The final owned Kubernetes worker passed seven live Linux aarch64 cases: healthy Service/client, Deployment-only, unready timeout, wrong-selector timeout, namespace-escape rejection, privileged-source rejection and cancellation. Every applicable case confirmed owned cleanup. An actual SIGTERM while verifying left zero of four previously observed owned resources and exited zero in 6.837 seconds. Exact refreshed image and resource IDs remain in the root's private receipts. Windows WSL2/file sharing, Intel Mac, Linux amd64, rootless engines and emulation remain separate untested rows. Source tests and image definitions do not fill those rows.
