Validation and release readiness#

Validate the exact revision being shipped. Configuration, structural checks, unit tests, real runtime execution and browser behavior answer different questions. A passing parser does not prove a lesson runs, and a configured workflow does not prove that its hosted jobs passed.

Run commands from the repository root. Keep learner projects and their Docker volumes separate from disposable validation projects. Use the current workflow run and its artifacts as evidence for that revision, rather than copying old machine timings or test counts into documentation.

Prepare a development environment#

The supported product is the Linux-container Docker classroom. Windows runs through WSL 2; macOS uses its engine's Linux environment. Native Windows backends and native executable bundles are outside the release support matrix.

Maintainers running contributor checks on Linux or WSL 2 also need Python 3.12, the locked development dependencies and Node.js. The workflow uses Node 24 for the framework-free UI checks. Python 3.11 remains a supported core validation target; inspect .github/workflows/ci.yml for the exact matrix.

With uv installed:

uv lock --check
uv sync --frozen --extra notebooks --extra data --extra bridge --extra quality --extra professional --extra sql-notebooks --extra mcp
uv run --no-sync python scripts/course.py doctor

Prefix the Python commands below with uv run --no-sync, or use the interpreter inside this checkout's .venv. On Windows, WSL 2 provides the same Bash, Linux Python environment and Docker workflow. Retired native installers and executable builders are no longer shipped; they are not alternate release requirements.

Core setup does not install every heavy learning dependency. A test that needs an optional compiler, framework, SQL service or model asset must either run in its prepared environment or report that boundary explicitly.

Repository formatting#

Run ./scripts/format-repo to apply maintained code style, or ./scripts/format-repo --check to report drift without editing tracked source. Make exposes the same commands as make format and make format-check. ./scripts/lint-repo (or make lint) adds read-only static source checks using the same toolchain. make check requires both formatting and lint checks. These commands use pinned Docker toolchains on Linux, macOS and Windows through WSL 2. R uses its compatible styler/lintr image and Julia uses its prepared JuliaFormatter/parse tool image. Other languages use the main image, including stanc for Stan and SQLfmt for dbt SQL/Jinja. A full pass runs the separate adapters before refreshing shared generated views after successful source formatting. Image fingerprints follow tool inputs rather than lesson edits. The first invocation prepares missing images; --build explicitly rebuilds them, and --list reports coverage without formatting source. Classroom containers and learner volumes are not part of this operation.

C++ grammar checks project the declared TMB SIMULATE block and four-argument TMB_ATOMIC_VECTOR_FUNCTION form with a literal output dimension. The projection preserves comments, quoted/raw strings, diagnostic lines, both atomic bodies and surrounding C++ for parsing. Unsupported forms fail visibly. It does not expand TMB headers, check types or model automatic-differentiation semantics; the actual native compiler and numerical probes remain separate required evidence.

The R adapter parses without evaluating lesson code and checks that formatting preserves parsed expressions. Its fixed lexical lint rules do not substitute for runtime assertions. Check and lint modes use read-only source mounts. A focused language pass omits shared regeneration, so finish with the unfiltered checks.

Use a repeated --language selection for focused iteration and the unfiltered check before submission. Follow the contributor formatting workflow for generated-source ownership and optional pre-commit installation. Formatting checks and execution checks are separate evidence: still compile/run changed examples and inspect lesson rendering when either may be affected.

Run tests in parallel#

Use four grouped workers by default:

python -m pytest -n 4 --dist loadgroup

The equivalent Make targets are:

make test
make test TEST_WORKERS=2
make test TEST_WORKERS=6
make test-serial

Keep --dist loadgroup. Tests that use the same disposable PostgreSQL fixtures belong to the shared-postgres group and run serially within that group. The suite rejects unsafe distribution when those shared fixtures are enabled. Changing the scheduler can cause destructive fixture races even if individual tests pass. Use -n 0 for focused serial diagnosis, and reduce worker count on machines with little memory. On a machine with spare CPU and memory, measure six workers before increasing further. Long individual reader tests and shared fixtures still set a floor. More workers do not guarantee shorter runtimes.

Record the passed, failed and skipped totals from the actual run. Explain skips by surface, such as an optional framework, a live database or historical optional services or platform-specific filesystem cases. Do not describe a skipped platform as validated.

What hosted workflows check#

The workflow files are the executable source of truth. Routine validation uses read-only repository permissions, pinned action revisions and local image builds. The separate full image publication workflow opts in only on a push to main with [publish-docker] in the HEAD message. The targeted workflow accepts a single [build-test-ALIAS] on a branch for native App/Core plus one complete group without Hub credentials, staging or publication. A single [publish-ALIAS] on main publishes App, Core and that complete group as a partial versioned release. Both publication modes use the two repository secrets, require the exact revision's source/starter checks, qualify native AMD64 and ARM64 groups, upload commit-specific staging images and small receipts, and promote combined version/latest tags only after their required checks. Neither needs an extra enable variable or protected environment. Staging uploads are not a completed release; conflicting source versions are refused rather than overwritten. After promotion, separate native AMD64 and ARM64 jobs inspect the promotion receipt and published indexes, pull a fresh Hub classroom and verify stop/resume retention. For a full release the fresh runtime exercise uses App and Python Core; for a partial release it includes the selected group. Promotion can write canonical tags before this later acceptance fails, so inspect its distinct result before calling the release usable. A changing dynamic browser host port permits only an app-container repair from the same image; PostgreSQL, workers, named volumes, learner content and the saved image pin must remain stable.

The dispatch-only verify-published-images.yml workflow is a read-only recovery check for the already-promoted partial 1.0.0 tags. It binds the old successful promotion receipt and source revision, accepts only verifier-file changes, and inspects/pulls the existing combined indexes on native AMD64 and ARM64. It cannot stage, promote or overwrite Hub tags. Its separate successful native run qualified that partial release after the old publisher's post-promotion test failed. The original run remains failed overall; a new full release needs its own complete qualification and automatic pull acceptance.

Linux core jobs use UTF-8 and create their test workspace before starting four grouped pytest workers. Native Windows ACLs, PowerShell backend diagnostics and native executable bundles are not release gates. Windows Docker wrappers remain supported entrypoints into WSL 2.

Each publisher waits for the exact revision's required source/starter success and rechecks it before promotion. Successful same-run/revision receipts can be reused across failed-job retries with exact seed-digest binding; cross-run reuse is rejected.

The Docker groups cover Python Core, C, C++, Go, C#, Rust, Swift, Java, JavaScript/TypeScript, PHP, Scala/Spark, TensorFlow, PyTorch, JAX CPU, Bayesian CPU, R, data engineering, Apache data-platform libraries, dbt/DuckDB, Stan and Julia. Optional documentation-only CI skip#

For a push containing only prose and its regenerated readers, the native [skip ci] commit-message token skips push and pull_request workflows. Use the space; [skip-ci] is not a supported native token. No YAML gate or custom alias is required. Follow the commit example and push boundary.

Before that commit, use the prepared contributor environment to regenerate and check the documentation locally:

make generate
python scripts/normalize_lesson_prose.py
python scripts/check_content_rendering.py
python scripts/check_published_links.py
git diff --check

Review the whole push: executable lesson examples, tests, runtime code, configuration, dependencies and workflows require normal CI. Never hide an unvalidated implementation commit behind a marked documentation commit. Scheduled/manual runs are unaffected; existing runs are not cancelled. Required PR checks may remain Pending and prevent merging. Trigger normal checks with an unmarked follow-up commit, or use a manual run only if the repository's required-check policy accepts it. A skipped run is not passing CI evidence. GitHub documents the event and required-check behavior.

Notebook, SQL and optional-runtime boundaries#

python scripts/validate_notebooks.py checks structure. Add --smoke for the selected dependency-light execution set. Never aim reset commands at a production or shared database. The optional MCP tests use the actual stdio protocol and read-only defaults. They verify discovery, bounded content reads, explicit solution reveal and opt-in progress behavior. They do not call a hosted model or measure teaching quality. See MCP tutoring.

Compiler/framework reference tests must identify the prepared profile, actual source and observed result. A Dockerfile, installed dependency, parse-only check or old image hash is not current execution evidence. Preserve truthful historical receipts, but attach fresh evidence when executable source changes.

A guide may have a separate binding in curriculum/presentation-parity.json. For a prose-only correction, first verify that the committed guide matches the previous presentation hash and that every protected code block still matches its recorded hash. Preserve the historical runtime hash and code hashes. Record the previous and updated presentation hashes, baseline commit and reason in the binding's presentation_history, then update its current presentation hash and run the existing parity tests. This records a documentation change, not another execution. Never use it to approve changed examples or rewrite runtime receipts.

Release decision#

Before shipping, record the exact revision, generation drift result, quality checks, test totals and skipped surfaces, runtime receipts, browser observations, archive contents and supported-platform evidence. Verify no learner state or private configuration entered the package. Explain unresolved failures before publishing; do not rename them as expected skips.

Useful result labels are structure validated, representative behavior executed, complete artifact executed, offline verified after setup, and not validated on this platform. Use the narrowest label supported by the evidence. No finite test suite establishes that software has no bugs.

Scientific and data-system release gates#
