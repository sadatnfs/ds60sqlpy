# dme-065: Batching, continuous scheduling and fairness

A serving scheduler chooses which requests execute together and when they get another decode step. This decision changes utilization, memory consumption, time to first token and the gaps between later tokens. Batching is therefore a user-experience policy as well as a tensor-shape optimization.

The live workshop intentionally uses one compute slot and whole-request FIFO execution. It does not implement continuous batching. This chapter compares scheduling mechanisms using explicit deterministic timelines and padding counts, then explains what an actual batching engine would need to add. The distinction lets a CPU learner understand advanced serving without treating a simulation as a measured accelerator system.

## Static and dynamic batches

A static batch groups requests before running them. If every sequence has the same length, the resulting tensor shapes are easy to manage. Variable lengths usually require padding, masking or a representation that avoids padded work. In a completion workload, output lengths are unknown in advance, so some batch members may finish while others continue.

Dynamic batching waits for arriving requests until a count, token budget or maximum waiting interval is reached. A larger batch can improve useful work per launch, but waiting to fill it increases latency. A low-traffic service may never reach a large target batch unless it has a timeout. A high-traffic service may reach it quickly but still run out of KV capacity.

Continuous batching can admit or retire requests between decode iterations instead of waiting for an entire initial batch to finish. This reduces idle slots after short sequences terminate. It requires careful mapping between request identities, tensor rows, cache ownership, output events and cancellation state. Reordering rows for efficiency must not send one request's token to another client's stream.

Prefill and decode have different shapes and costs. A long prefill can delay many short decode iterations if they share one scheduling resource without a policy. Chunked prefill divides prompt processing into pieces so a scheduler can interleave work. Correct chunking requires offset-aware causal masking and cache updates; it is more than splitting a string into equal character chunks.

## The scheduling unit matters

Whole-request FIFO schedules complete generations. Round-robin decode schedules one step from each active request in turn. A token-budget scheduler can combine several steps or prompt chunks subject to a resource estimate. These policies optimize different objectives.

Let \(f_i\) be request \(i\)'s first-token time and \(c_i\) its completion time, measured from a common arrival origin. Reducing the mean of \(f_i\) does not necessarily reduce the mean of \(c_i\). A long request may receive its first token promptly under round robin but complete later because it shares compute with short requests.

Fairness also needs a unit. Equal requests, equal tokens, equal compute time and equal user shares are different policies. A tenant sending many tiny requests can exploit a request-count interpretation. A request with a very long context may consume much more time per generated token. A defensible policy states the protected unit and measures actual service received.

The workshop's simple FIFO rule is transparent and bounded. Its limitations are part of the lesson. Introducing a more sophisticated scheduler requires new correctness tests and capacity evidence; it should not be advertised as a free performance improvement based on a toy timeline.

## Worked case 1: one long and one short request

The first case assumes both requests arrive at time zero and every token step costs one time unit. The long request needs eight steps; the short request needs two. Whole-request FIFO produces first-token times one and nine, with completion times eight and ten. Round robin produces first-token times one and two, with the short request completing at four and the long one at ten.

The total work remains ten steps. Round robin changes who experiences the wait. It improves the short request's first-token and completion latency while delaying the long request's completion. The exact dictionaries printed by the program make this tradeoff visible without claiming any real throughput gain.

The equal-step assumption is deliberately strong. Real decode steps vary with cache length, batch composition, memory traffic and hardware. Context switching and tensor assembly can add overhead. Before choosing a production policy, replace unit steps with measured costs and model arrival patterns, cancellations and memory constraints.

## Worked case 2: padding and bucketing

The second case has prompt lengths two, ten and eleven. Padding all three to length eleven creates 33 token positions for 23 actual tokens, leaving ten padded positions. Grouping the short request separately and the two long requests together creates 24 positions, leaving one padded position.

This arithmetic motivates length bucketing. It does not show that waiting for a matching length is worthwhile at a particular request rate. Bucketing can delay a rare long or short request and can fragment the queue. A real policy needs a maximum wait and a fairness rule, plus actual kernels that benefit from the resulting shapes.

## Cache and stream ownership under batching

Each request needs an independent sequence length, position offset, random generator, stop state and event counter. When a batch member finishes, its cache resources are released without disturbing others. When a member cancels, an in-flight batch kernel may still need to finish before its slots can be safely reused.

The output tensor's row index is not a durable request ID. A scheduler can compact or reorder rows between iterations. Maintain an explicit mapping from row to request identity at each operation boundary. Tests should deliberately finish or cancel a middle member, then verify the remaining members' source-bound token sequences and receipts.

Randomness needs similar isolation. Using one global random stream can make request A's output depend on whether request B joins the batch. Per-request generators reduce this coupling, although different batched kernels and floating-point reductions can still change borderline decisions. Define the reproducibility claim carefully rather than promising identical outputs under every schedule.

Backpressure adds another interaction. A slow client should not accumulate an unbounded output buffer or indefinitely stall unrelated requests. A bounded policy might stop producing for that request, cancel it or move output into a bounded durable buffer. The choice changes user semantics and must preserve exact terminal status and reservation release.

## Measuring a proposed batching policy

Use a workload with declared prompt lengths, output budgets, arrivals and cancellation behavior. Report throughput with its denominator, queue delay, first-token latency, inter-token gaps, rejection rates and memory peaks. Include both warm and cold conditions where relevant. A single saturated batch benchmark does not describe an interactive service under light traffic.

Compare the same model, tokenizer, precision and decoding settings. If one policy truncates more outputs or rejects more long requests, a throughput improvement may reflect less work rather than better scheduling. Retain the distribution of accepted and rejected requests so the comparison remains interpretable.

The existing LLM evaluation route explains paired comparisons and uncertainty. Here the systems point is that performance evidence must identify the actual scheduler and workload. A CPU trace of round robin cannot qualify a GPU continuous-batching engine that has not been implemented or run.

## Interview discussion

**Why can throughput improve while a user sees worse latency?** Waiting to fill batches or interleaving long jobs may increase a particular user's queue delay or completion time even if aggregate tokens per second rises.

**What state must remain per request in a batch?** Identity, accepted source, sequence length, position, KV ownership, random state, stopping/decoder state, event cursor and cancellation status. Shared weights do not imply shared request state.

**Why is chunked prefill a correctness change as well as a scheduling change?** Queries in each chunk occupy offset positions and must see exactly the permitted prefix. A naive rectangular mask can hide valid past keys or expose future ones.

Next, examine the tensor and kernel work underneath these schedules. Better scheduling cannot compensate for incorrect layouts or claims about kernels that never executed.
