## Learning objectives

Make thread lifetime and cancellation ownership explicit.

## Vocabulary and concepts

A thread executes a function concurrently with its caller. Joining waits for that function to finish before borrowed state is destroyed. Cancellation is a request that cooperative code checks, not a forced kill. C++20 jthread adds joining destruction and stop_token support, while std::thread requires explicit joining on every path.

<!-- terms:start -->

- **`std::thread`:** starts a function on a new thread of execution and must be joined or detached before it is destroyed.
- **join:** waits for a thread's function to finish, so the state it borrows can then be safely read or destroyed.
- **cooperative cancellation:** a stop request that the running code checks and honors, not a forced kill.
- **`std::jthread`:** a C++20 thread that requests a stop and joins automatically in its destructor.
- **`stop_token`:** the object a jthread's function checks to learn whether a stop was requested.

<!-- terms:end -->

## Syntax and mechanism

Capture a variable by reference only while the owner outlives the worker. Calling join creates the synchronization needed before reading the worker result. The portable demonstration uses thread and an atomic stop flag; the guide contrasts the equivalent jthread pattern because some host standard libraries lack jthread.

## Trace the mechanism

Thread startup, cancellation request and completion are separate events. The promise reports startup, the atomic flag requests cancellation and join confirms completion. A fixed delay cannot replace any of these events because scheduling may be slower or faster than expected. A reference capture borrows a local variable, so scope must not end first. jthread adds automatic joining and stop support, but cooperative code still has to inspect its token.

<!-- depth:start -->
## Thread lifetime and cooperative cancellation

Starting a thread creates another flow of execution; it does not wait for that work to finish. A reference capture borrows an object from the creating scope. The owner must keep that object alive until the worker's last access. In the first program, answer belongs to main, the thread writes 42, and join completes before main reads the result or ends the scope. The join is part of the correctness argument, not an optional delay.

A thread object that remains joinable at destruction is a serious lifecycle error for std::thread. Every path after successful creation needs an ownership decision: join the work or deliberately transfer its management. Detaching makes lifetime reasoning harder because the creating scope can disappear while the worker still uses borrowed state. The course examples retain and join every worker instead.

Cancellation is a request, not an asynchronous kill. The second example uses a promise/future to establish that the worker reached its startup point, then an atomic flag to request stop. The worker repeatedly observes the flag and exits its loop. join confirms actual completion. A fixed sleep would prove neither startup nor completion and can fail on a slower or more heavily loaded machine.

The memory used for the flag must support concurrent access. A plain bool read and written by different threads without synchronization would introduce a data race. Atomic access makes the flag communication defined. That does not imply every other shared object is safe; each shared value needs its own ownership or synchronization argument.

std::jthread can automate joining and provide a stop token, but cooperative work still has to check the request at useful points. A blocking operation that never returns may prevent timely cancellation. Production design therefore needs bounded I/O, a shutdown deadline and a policy for unresponsive work. The tiny fixture teaches the request/observation/join sequence without pretending to solve arbitrary thread interruption.

## Worked example / walkthrough

Example 1 starts a thread that writes 42 and calls `join()` before reading, so the read happens after the write. Example 2 adds cancellation: the worker signals readiness through a `std::promise`, spins until an atomic stop flag is set, and is still joined. Every started thread ends in a join. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-029-example-1.cpp)

```cpp
#include <cassert>
#include <iostream>
#include <thread>

int main() {
  int answer = 0;
  std::thread t([&] { answer = 42; });
  t.join();
  assert(answer == 42);
  std::cout << "cpp-029 example 1 checks passed\n";
  return 0;
}
```

**Expected:** With assertions enabled, the program exits with status 0 and prints:

```text

```

### Worked example 2

[Complete program 2](../examples/cpp-029-example-2.cpp)

```cpp
#include <atomic>
#include <cassert>
#include <future>
#include <iostream>
#include <thread>

int main() {
  std::atomic<bool> stop{false};
  std::promise<void> ready;
  auto started = ready.get_future();
  std::thread worker([&] {
    ready.set_value();
    while (!stop.load())
      std::this_thread::yield();
  });
  started.get();
  stop.store(true);
  worker.join();
  assert(stop.load());
  std::cout << "cpp-029 example 2 checks passed\n";
  return 0;
}
```

**Expected:** With assertions enabled, the program exits with status 0 and prints:

```text
cpp-029 example 2 checks passed
```

## Exercises

### Exercise 1: Trace lifetimes

Draw result, worker creation, write, join and scope exit.

**Expected result/shape:** The owner remains alive until after join.

**Verify:** Check the drawing against Worked example 1: `answer` is declared before the thread, the write of 42 happens before `t.join()`, and the read and scope exit come after it.

**Progressive hints:** The reference capture borrows local state.

### Exercise 2: Read after joining

Compute 42 on one worker and read afterward.

**Expected result/shape:** 42, with a documented join before access.

**Verify:** Assert `answer == 42` on the line after `t.join()`, as Worked example 1 does; moving the assertion above the join creates a data race.

**Progressive hints:** join establishes completion and synchronization.

### Exercise 3: Request cancellation

Run the supplied ready handshake then set stop and join.

**Expected result/shape:** Worker terminates without a sleep-based timing assumption.

**Verify:** Confirm Worked example 2 contains no sleep, that `started.get()` returns before `stop.store(true)`, and that `worker.join()` returns.

**Progressive hints:** The promise proves startup before cancellation.

### Exercise 4: Repair detach

Review detaching a worker that captures a local by reference.

**Expected result/shape:** Reject detached borrow; keep ownership until join.

**Verify:** Trace the captured local to the end of its scope and confirm a detached thread could still use it afterward; the repaired code joins before the scope ends.

**Progressive hints:** Detached lifetime can outlast the referenced variable.

### Exercise 5: Translate to jthread

On a qualified C++20 library use jthread and stop_token.

**Expected result/shape:** request_stop followed by scope exit joins; record compiler/library support.

**Verify:** Write a `std::jthread` loop that checks `stop_token::stop_requested()`, call `request_stop()`, let the jthread leave scope, and record the compiler and library version that built it.

**Progressive hints:** A stop request only works if the body checks the token.

### Exercise 6: Transfer failure cleanup

Add an owner-side early return and keep joining mandatory.

**Expected result/shape:** No joinable thread reaches destructor; no dangling capture.

**Verify:** Take the early-return path in a test and confirm the program does not call `std::terminate`, which happens when a joinable `std::thread` is destroyed.

**Progressive hints:** RAII joining or a scope guard must cover exceptional paths.

## Self-check

Why is the result 42 after `join()`, and why is the borrowed local still alive? For Example 2, explain what the promise proves before the stop flag is set, and why the worker is still joined.

## Common pitfalls

If a test occasionally reads 0 instead of 42, inspect whether it observes completion before reading shared state. If shutdown hangs, locate the next cancellation check or blocking call rather than adding a longer sleep. If a function exits while a thread borrows its locals, fix the ownership scope. If thread creation can throw after another worker starts, join the already created worker during the failure path before propagating the exception.

## Retrieval and transfer
