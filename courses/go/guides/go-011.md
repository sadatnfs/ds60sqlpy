# go-011: Errors as values and preserving causal context

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-010

## Learning objectives

Wrap errors with %w and recover causes with errors.Is, errors.As and errors.Join instead of comparing message text. Along the way, explain sentinel error, wrapping, recovery policy; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Errors describe unsuccessful operations without forcing every failure into panic recovery. A function returning a value and error makes the caller choose what to do next. The error chain should preserve both human context and a machine-inspectable cause. Wrapping with fmt.Errorf and %w adds context while errors.Is and errors.As can inspect underlying identity or type. Comparing formatted text is brittle because wording is presentation, not a stable contract. A nil error means the operation succeeded according to its API; it does not prove every downstream interpretation is valid. Handle failures where you can add useful context, recover deliberately or report them accurately.

## Vocabulary and concepts

- **Sentinel error:** A named error value used as an identity contract.
- **Wrapping:** Adding context while preserving an underlying cause.
- **Recovery policy:** A deliberate response to a particular failure class.

## Syntax anatomy and reasoning

errors.New constructs an error value. fmt.Errorf("read: %w", err) wraps an existing cause. errors.Is follows supported wrapping relationships to compare a sentinel; errors.As finds an error assignable to a target type. Return nil for a successful error result, not an interface containing a typed nil pointer. Avoid logging and returning the same error at every layer because repeated messages can obscure the causal chain.

## Worked example / walkthrough

### Worked example 1: Preserve a cause

Wrap ErrMissing with a record-reading context.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

var ErrMissing = errors.New("missing record")
var ErrDenied = errors.New("access denied")

type LimitError struct{ Max int }

func (e *LimitError) Error() string { return fmt.Sprintf("limit %d", e.Max) }

func main() {
	// Preserve a cause
	{
		err := fmt.Errorf("read record: %w", ErrMissing)
		check(errors.Is(err, ErrMissing), "wrapped cause")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** errors.Is still recognizes ErrMissing.

%w exposes the cause to the error-inspection protocol. Replacing it with %v would format the cause as text but lose that wrapping relationship.

### Worked example 2: Reject text equality

Construct two separate errors with the same wording.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

var ErrMissing = errors.New("missing record")
var ErrDenied = errors.New("access denied")

type LimitError struct{ Max int }

func (e *LimitError) Error() string { return fmt.Sprintf("limit %d", e.Max) }

func main() {
	// Preserve a cause
	{
		err := fmt.Errorf("read record: %w", ErrMissing)
		check(errors.Is(err, ErrMissing), "wrapped cause")
	}

	// Reject text equality
	{
		a := errors.New("missing")
		b := errors.New("missing")
		check(!errors.Is(a, b), "identity not text")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Their identities differ.

A matching message does not establish the same error contract. Use an exported sentinel or typed error only when callers should rely on that distinction.

## Common pitfalls and diagnosis

Comparing `err.Error()` with a string, or formatting a cause with `%v` instead of `%w`, are the habits this lesson replaces. Both tie the code to presentation text, and `%v` also breaks the chain so errors.Is and errors.As stop working. Another mistake is passing a non-pointer target to errors.As; it needs a pointer to the variable that should receive the match.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Preserve a cause: change one input

1. Restate the expected observation: errors.Is still recognizes ErrMissing.
2. `%w` records the wrapped error for inspection. What does errors.Is walk through to find ErrMissing?
3. `%v` formats ErrMissing as text but does not wrap it, so errors.Is finds no cause and the check panics. Only `%w` adds the cause to the chain.

### Hint for investigation 2: Reject text equality: diagnose an edited check

1. Restate the expected observation: Their identities differ.
2. errors.New returns a distinct value on each call. Does identical text make two errors the same?
3. a and b are distinct values with the same text, so `errors.Is(a,b)` is false and the edited check panics. The original negated it because identity, not wording, is the contract.

### Hint for investigation 3: Inspect a typed boundary

1. Restate the expected observation: The extracted limit is 3.
2. errors.As needs a pointer to a variable of the target type. What does that variable receive on a match?
3. The type carries structured information without parsing presentation text.

### Hint for investigation 4: Handle successful parsing

1. Restate the expected observation: The result is 42 and the error is nil.
2. Check the error before using the value. What does Atoi return for well-formed decimal text?
3. The success branch establishes that the returned value is usable.

### Hint for investigation 5: Classify invalid parsing

1. Restate the expected observation: The typed parse error is present.
2. Atoi reports malformed text with a typed error. Which strconv type is it?
3. Typed inspection supports a specific response to invalid input.

### Hint for investigation 6: Transfer joined failures

1. Restate the expected observation: Both sentinels remain discoverable.
2. errors.Join keeps every non-nil error. Can errors.Is still find each sentinel separately?
3. Multiple failures can matter during cleanup or validation.
