Repository guidance for coding agents#

Mission and first steps#

Maintain one local Docker classroom at /classroom for programming, data science, statistics, machine learning and systems. Derive subject and lesson IDs, variants and readiness from the catalog loaders, not a copied inventory. Historical day numbers are stable labels, not a deadline.

Read README.md, CONTRIBUTING.md, and the closest subject AGENTS.md. Inspect git status --short --branch and preserve unrelated work. Use the user's requested checkout and parallel agents with explicit file ownership. Respect existing task authorization; do not add a separate approval step for ordinary authorized edits. Git publication, image publication, history rewrites and destructive cleanup have distinct scopes. Do not use em dashes.

Choose the right role#

  • For explanation, placement, debugging or resuming study, use Guide learning.
  • For new or extended lessons, subjects or runtimes, use Add a learning path.
  • For application work, begin with the repository tour and current architecture.

A tutoring request is not automatically a request to implement curriculum, replace a learner's attempt, run code or mark completion. Inspect the actual lesson and learner-provided work, explain one mechanism, and offer progressive hints. Reveal practice references when requested or when the chosen review explicitly includes comparison. The statistics book exposes worked answers without exams or solution gates. A read marker or reference run is not mastery.

The optional MCP adapter reads checked-in curriculum by default and does not execute code. Its module tools do not read Docker-volume pads or results. Do not claim to have inspected unseen learner state. Use a learner-provided attempt or an authorized workspace/UI interface. Progress writes need the adapter's opt-in and the learner's instruction. Preserve authorization already given for the current task rather than asking repeatedly.

Authoring and extension#

Define the learner's starting point, direct prerequisites, observable outcome and evidence before selecting a lesson count. Teach vocabulary and syntax before using them. Include at least two explained worked cases, meaningful mistakes, bounded fixtures and concrete next steps. Practice should progress from tracing to modification, independent work, debugging and transfer. Avoid generic repeated paragraphs that merely satisfy a heading or exercise counter.

Keep stable lesson IDs, prerequisite relationships, variant aliases and saved state namespaces. The legacy practice baseline is immutable; additions use its separate expansion registry. Modern modules use their own admission contracts. The statistics book and additive tutorial tracks expose complete examples and answered discussion without mandatory problem sets or hidden answers. Additive track.json supports only learning_mode: practice|tutorial, defaulting to practice. Applied Science, Bayesian Computing and Data and ML Engineering demonstrate tutorial authoring. Use the scientist roadmap to place new work without describing existing subjects as missing.

Read the subject's authoring/README.md when present. Edit its durable source, run only the relevant generator, format generated executable code, then refresh shared readers. Directly authored subjects retain their documented artifact sources. make generate refreshes shared metadata and readers; it does not run every subject generator. Never hand-edit START_HERE.html, lesson-pages/ or reference-pages/.

Write mathematics with \(...\) or \[...\] and code in accurately tagged fences. Preserve literal program characters. Rendering and highlighting must work offline. Compile TeX after prose normalization and before shared readers; keep the generated input inventory and compiled output synchronized. Use professional factual copy rather than motivational slogans. Prose normalization and statistics-example fence synchronization have reviewed contracts; they cannot change executable meaning or create new runtime evidence. Use UTF-8 and LF for generated repository text.

A subject, language and runtime are different concepts. Prefer an existing reviewed profile when it fits. New profiles need fixed operations, dependencies, formatting/lint support, image/launcher registration, actual failure/success checks and saved-work acceptance. A lexer or manifest alone does not create an executor. See the extension playbook.

Runtime and learner-state invariants#

Use Linux containers on Linux/macOS and Windows through WSL 2. Ordinary learners need no host compilers or database installation. Keep the thin Docker launchers; do not add native Windows backends, ACL machinery or executable-build gates. Separately prepared contributor SQL/Jupyter tools and genuine external projects, such as Swift/Xcode, have their own documented boundaries.

./classroom is resume-first: reuse saved selection and existing images and containers, preparing only missing images. resume and --no-build never build or pull. build prepares local images without startup. Hub --rebuild pulls and applies updates without compiling; keep the same project and volumes.

New --from-hub selections use combined release tags: app VERSION, workers VERSION-<catalog suffix>. Omitting --tag resolves the app's latest alias to a concrete version after the project lock, requires a matching source checkout, and saves that version. A same-namespace saved project retains its pin; bare resume never follows latest or contacts the registry. Repeatable --image-tag PROFILE=VERSION|latest|default selects a particular ordinary image or clears a saved worker pin. Validate a worker latest alias through its OCI index and require the same qualified source revision as the app before mixing versions. Current CI binds one version to each revision, so releases from different revisions cannot be mixed. A partial publish has only its selected profiles; --all requires a completed full release. Manual publisher tags need --architecture-tags; old three-field saved Hub settings retain that legacy layout. Validate native Linux architecture, preserve progress outside images, and do not switch projects to hide a defect.

Launcher preferences under .classroom/<project>/ are separate from named learning, PostgreSQL and private-runtime volumes. Preserve all learner state. A normal resume reuses containers; an automatically changed browser port can require recreating only the app from its existing image for exact Host/Origin checks. That is not an image rebuild. Fixed port choices preserve a stable URL; applying changed port settings uses the explicit update route.

Save or retain recoverable drafts before changing context. Keep source, notes, results and history separate by lesson, language/variant and SQL mode. Reading a past result must not rerun code or replace the current pad. Unknown job outcomes must be reconciled without replay. A receipt-save failure must report the real execution result and a storage warning.

HTML/CSS and JavaScript/D3 previews are opaque, offline browser observations. Live preview requires an explicit current-page opt-in, debounces edits, preserves editor focus and does not automatically create immutable receipts. Manual Run or explicit Save observation captures submitted source. Navigation, Stop, history selection and reload must not silently resume execution. PHP CLI uses main.php and PDO SQLite; real HTTP/session work belongs to the separate owned web fixture. Do not label request models as actual browser/server exchanges.

CUDA reading and CPU models are useful without NVIDIA hardware. Optional GPU workers stay outside default/--all, require explicit device selection and a real allocation/kernel/readback probe. Compilation, GPU correctness, profiling and multi-GPU operation are separate evidence. A Mac container does not turn an Apple GPU into CUDA. GPU Spark needs compatible components and actual supported operator/plan evidence. Never reset a shared GPU automatically after a fault.

DAX is an editable offline workspace. Its ready capability does not authorize a Run operation. Preserve drafts when opening hash-bound hand-derived references; never call those tables execution output. JAX defaults to CPU. Bayesian tutorials use their pinned PyMC/ArviZ API, and R uses prepared Rscript packages. Keep their runtime dependencies separate from the core environment.

Python/R/Julia plotting and structured reports share a two-output budget: PNG, Plotly, table or JSON; 180,000 bytes each and 384,000 bytes combined. Tables allow 12 columns and 100 rows. Encode integers beyond JavaScript exact range as strings. publish_table and publish_report belong to plot_artifacts.py; declared figure-contracts.json expectations are checked by the reference corpus. Plotly metadata and tables are data, never trusted page HTML. Validate animation frames and image sources as well as the top-level figure, preserve the source-bound receipt, and keep capture/storage warnings separate from execution. Plain Python must not eagerly import plotting libraries. Browser charts remain opaque offline observations.

Saved Plotly receipts from earlier versions may require a display-only precision projection. Preserve original receipt bytes, source/output/status and valid sibling figures. Withhold unsafe-number figures with an explicit warning and offer exact raw JSON text downloads without browser parsing or numeric rounding. Keep all new-write validation strict and derived readback metadata out of stored receipts; malformed artifacts and receipt/path violations still fail normally.

Polars, real dbt and ML engineering use data-engineering; dbt SQL-model variants use the fixed dbt-duckdb project. Do not imply a multi-file browser editor. stan-cpu compiles native main.stan with tiny transformed-data fixtures and fixed two-chain sampling. Its standard-data CmdStanPy project has separate explicit data/output files. julia runs main.jl with a read-only prepared project/depot and two threads. Keep package preparation outside lesson execution. The ML service project has an explicit Docker lifecycle and separate persistent state, with a read-only predictor mount; it is not a cloud service or ordinary pad. The engineering book adds owned data-product and inference-service projects. Keep raw/publication/recovery state and model/request history outside the source payload, and read completed receipts without replay. Their HTTP failure, exact resume and retained-state replacement gates are distinct from ordinary examples.

data-platforms-python supplies separately locked Arrow, DataFusion and PyIceberg library operations. Ballista and persistent platform services have separately prepared environments, not implicit worker dependencies. Read the Apache qualification ledger and each project's guidance. Prepared Atlas/Delta Sharing clients are not accepted servers; native architecture and complete topology checks remain distinct. Ordinary workers never receive an engine socket.

The classroom runs trusted local learner code, not arbitrary hosted tenants. Preserve Host, origin, token, path, request/output-size, process and resource checks. Publish ports to loopback; use http_server.py to avoid reverse-DNS startup dependencies. Keep worker COPY lists aligned with imports. Manifests cannot supply shell commands, compiler flags, endpoints or host paths.

Kubernetes needs explicitly owned resources, reviewed operations, no ambient kubeconfig and bounded UID-aware cleanup. Ordinary workers never receive an engine socket. Optional packages, external services and model/data downloads require deliberate preparation; opening a lesson must not fetch them.

SQL automation targets only the explicitly disposable local advanced_sql_training database, validates routing, uses a private credential environment and invokes psql -X -v ON_ERROR_STOP=1. Resetting training is destructive. Preserve declared stateful lesson sequences and never redirect checks to shared or valuable data. Fakes prove policy, not PostgreSQL behavior.

Verification and handoff#

Use focused checks during implementation and the release gates for the actual change. The shared entrypoints are:

./scripts/format-repo --check
./scripts/lint-repo
uv run --no-sync python scripts/check_modules.py
uv run --no-sync python scripts/course.py validate
uv run --no-sync python scripts/compile_lesson_tex.py --check
uv run --no-sync python scripts/build_lesson_readers.py --check
uv run --no-sync python -m pytest -n 4 --dist loadgroup
git diff --check

These uv commands require the prepared contributor environment from CONTRIBUTING. Keep --dist loadgroup for shared database fixtures. A classroom controller admits one active module job across all profiles. Parallel runtime checks need separate disposable projects. Bound parallelism and keep large Docker builds sequential when disk or memory is constrained. Do not weaken assertions or rewrite expected behavior to conceal a failure. Do not rerun expensive successful checks without a new change or unresolved concern.

Report source checks, unit tests, actual runtime execution, browser delivery, container recreation and hosted CI separately. Record exact source/revision and platform; name skips and unavailable hardware. Historical receipts and source-format parity records remain immutable. They do not qualify new behavior. Do not place machine-specific image IDs, ports, temporary paths or test-session counts into maintained onboarding instructions.

For a prose-only authorized push, GitHub's [skip ci] spelling is available under the documented constraints. It must not hide implementation, examples, dependencies, workflows or other unvalidated commits. A skipped check is not a passed check.

Portable payloads exclude learner state, credentials, caches, local logs and Git history. Preserve source licenses and use neutral public/synthetic examples. Review the chosen repository-local public commit identity without exposing private identity values. Git-push authorization alone does not authorize adding a publication marker. The full CI publisher runs only for a push to main with [publish-docker] in the HEAD message. The targeted workflow accepts one [build-test-ALIAS] on a branch for native App/Core plus complete-group qualification without Hub writes, or one [publish-ALIAS] on main for partial versioned publication. A profile alias expands to its entire CI group; js includes both JavaScript and TypeScript. Publication uses repository secrets DOCKERHUB_USERNAME and DOCKERHUB_TOKEN. There is no extra enable variable or protected-environment requirement. Keep secret values out of source, logs, build arguments and reports.

Grouped Docker CI requires the owned data-product gate in data engineering, the inference/SSE/browser gate in PyTorch, Flight/Rust IPC in data platforms and Kafka semantics/lifecycle in Java. Keep scripts/ci_classroom.py required check sets and source-bound publication receipt validation aligned when changing them.

Native AMD64/ARM64 seed and worker publication jobs upload commit-specific staging images and small evidence receipts. Build-test jobs do not stage or publish. Promote only after every required selected check succeeds: worker version tags before the app version, then selected latest aliases with app latest last. The full publisher requires every ordinary profile; the partial publisher requires only App, Core and its complete selected group. Refuse conflicting existing source versions; a later full release after a partial release from another commit needs a consistent checked-in patch bump instead of registry-only renumbering or overwriting released tags. Successful earlier-attempt receipts may be reused only within the same run and revision, with exact app/Core seed bindings; cross-run or mismatched-seed reuse is rejected. Failed promotion retries retain original qualified digests. Staging uploads and completed release promotion are distinct evidence. A separate post-promotion native AMD64/ARM64 job checks the published index and exact promotion receipt, then pulls and starts an owned fresh Hub classroom, stops it and resumes its saved containers and volumes. Its acceptance receipt is separate. Canonical tags can already be published if this later check fails; inspect that failure rather than claiming a usable release or deleting learner state.

The manual ./classroom publish --to-hub USER --tag VERSION remains a preview-first publisher of existing images for one architecture. Only --push uploads; the operator authenticates separately. The default is app plus all ordinary catalog images. Its exact --profile selection has no implicit app/Core; --namespace/--version aliases remain supported. It cannot fabricate a second architecture or combined index. See Docker Hub for both layouts, version pinning, publication limits and learner setup. Cleanup only owned task resources, and retain learner volumes unless their deletion was explicitly requested. Do not prune unrelated resources or rewrite history as incidental cleanup.
