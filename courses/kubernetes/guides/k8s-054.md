# k8s-054: Gateway API, routes and role-separated configuration

## Level and prerequisites

Advanced; about 120 minutes plus optional supervised host observations. Direct prerequisites: `k8s-053`. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

## Learning objectives

Design a route attachment boundary. Plan Gateway acceptance evidence. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

## Purpose, vocabulary and mental model

Gateway API separates infrastructure selection, traffic listeners and application routes into distinct resources. A GatewayClass describes a controller-managed class. A Gateway asks for listeners and an entrypoint. An HTTPRoute attaches routing rules to an allowed parent Gateway. This can separate platform responsibilities from application routing ownership.

The resources still require installed APIs and a compatible controller. Status conditions such as Accepted, Programmed and ResolvedRefs describe different aspects of reconciliation. A route being accepted does not prove an actual client request reached the expected application.

Cross-namespace references require deliberate authorization under the API’s rules. ReferenceGrant is one mechanism for allowing supported cross-namespace object references. It should be narrow, naming the intended kinds and relationships. Broad grants or permissive listener attachment can turn an organizational boundary into an accidental shared routing surface.

## Mechanism and field-by-field reasoning

The fixture uses gateway.networking.k8s.io/v1 for Gateway and HTTPRoute. The exact supported route features depend on the installed controller and API version. Read parentRefs, listener names, hostnames and backendRefs field by field.

A platform team might own a shared Gateway while an application team owns an HTTPRoute in its namespace. The listener’s allowedRoutes policy controls which routes may attach. This is separate from whether the referenced backend exists and whether traffic succeeds.

## Trace the request or control path

```text
GatewayClass -> controller implementation
Gateway listener <- allowed HTTPRoute parentRef -> Service backend
status conditions -> actual listener/request qualification
```

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

## Worked example / walkthrough

### Worked example 1: Read a route backend

The route assumes an explicitly prepared parent named study-gateway.

```yaml
parentRefs:
  - name: study-gateway
hostnames: [study.example.test]
rules:
  - backendRefs:
      - name: network-study
        port: 80
```

**Expected observation:** The route identifies a parent and Service backend; neither resource is created by this fragment.

### Worked example 2: Classify condition failures

These are synthetic controller observations.

```text
Accepted=False: route attachment or policy issue
ResolvedRefs=False: a referenced object or permission is unresolved
Programmed=False: desired data-plane configuration is not ready
```

**Expected observation:** Conditions localize different control-plane failures and still need actual request acceptance afterward.

## Diagnosis, failure boundaries and common mistakes

The controlled failure in this chapter is: Diagnose ResolvedRefs=False. Its distinguishing result is Inspect backend identity and required reference authorization. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
