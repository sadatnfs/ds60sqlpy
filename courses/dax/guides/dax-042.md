## The question and the mechanism

Convert compatible transactions before aggregation and diagnose a misleading latest-rate shortcut.

Amounts in different currencies cannot be added into a meaningful monetary total without a conversion policy. The ordinary retail Sales table is already USD; this lesson instead uses the separate ForeignSales fixture. Its LocalAmount must be paired with Currency and SaleDate before selecting the rate expressed as USD per local currency unit.

A January 100 EUR transaction at 1.1 USD/EUR converts to 110 USD; a February 50 EUR transaction at 1.2 converts to 60 USD. Their correct combined USD amount is 170. Multiplying the local EUR sum 150 by the latest rate 1.2 gives 180, which applies the wrong temporal rate to the earlier transaction.

The rate table's uniqueness and completeness are prerequisites. LOOKUPVALUE over date and currency can retrieve the matching scalar in this tiny fixture, but missing or ambiguous matches require diagnosis. A BLANK rate must not silently make an unconverted transaction disappear from SUMX. In a larger project, validate rate coverage and the chosen accounting convention before publishing any converted total.

## Vocabulary and expression anatomy

SUMX supplies each ForeignSales row's amount, date and currency. LOOKUPVALUE matches both rate-key columns. The second case intentionally computes a wrong latest-rate comparison under an EUR-only selection and exposes the exact ten-USD discrepancy derived below. Keep that arithmetic explicit rather than relying on a reassuring formatted total.

Concepts to explain in your own words: **exchange rate**, **LOOKUPVALUE**, **currency unit**, **rate date**, **quality gate**.

## Worked cases

### Case A: Convert each transaction before adding

**Starting context:** Analytics model; three ForeignSales rows; each date/currency rate key exists exactly once.

```dax
EVALUATE ROW ( "ConvertedUSD", SUMX ( ForeignSales, ForeignSales[LocalAmount] * LOOKUPVALUE ( ExchangeRate[USDPerUnit], ExchangeRate[RateDate], ForeignSales[SaleDate], ExchangeRate[Currency], ForeignSales[Currency] ) ) )
```

**Context trace:**

1. F1 is 100 USD at rate 1, contributing 100 USD.
2. F2 is 100 EUR at 1.1, contributing 110 USD; F3 is 50 EUR at 1.2, contributing 60 USD.
3. The compatible converted amounts sum to 270 USD.

**Hand-derived worked-reference result:**

| ConvertedUSD |
| --- |
| 270 |

The raw local sum 250 mixes USD and EUR and is not itself a legitimate currency total.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: A latest-rate shortcut changes the policy

**Starting context:** EUR-only transactions; contrast transaction-date rates with one selected maximum rate in this tiny increasing-rate fixture.

```dax
EVALUATE CALCULATETABLE ( ROW ( "LocalEUR", SUM ( ForeignSales[LocalAmount] ), "CorrectUSD", SUMX ( ForeignSales, ForeignSales[LocalAmount] * LOOKUPVALUE ( ExchangeRate[USDPerUnit], ExchangeRate[RateDate], ForeignSales[SaleDate], ExchangeRate[Currency], ForeignSales[Currency] ) ), "NaiveLatestRateUSD", SUM ( ForeignSales[LocalAmount] ) * MAXX ( FILTER ( ExchangeRate, ExchangeRate[Currency] = "EUR" ), ExchangeRate[USDPerUnit] ) ), ForeignSales[Currency] = "EUR" )
```

**Context trace:**

1. The local EUR amounts sum to 150.
2. Transaction-date conversion gives 110 +60 =170 USD.
3. Multiplying 150 by 1.2 gives 180 USD, ten more than the stated policy.

**Hand-derived worked-reference result:**

| LocalEUR | CorrectUSD | NaiveLatestRateUSD |
| --- | --- | --- |
| 150 | 170 | 180 |

MAX rate happens to equal the latest rate in this fixture. A real latest-date policy must select by date, not assume rates increase monotonically.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Use its February date and EUR currency key.
2. The maximum rate would no longer be the latest rate.
3. Each transaction needs exactly one compatible rate under the chosen policy.
4. Zero conversion makes recorded value disappear.
5. Read the rate's unit, USD per EUR.
6. A rate can depend on jurisdiction, date and transaction type.
