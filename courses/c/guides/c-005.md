# c-005: Functions, prototypes and output parameters

## Level and prerequisites

Beginner, approximately 90 minutes plus a later retrieval session. Direct prerequisites: `c-004`

## Learning objectives

Implement the six investigations, from the "call a pure calculation" case to the "transfer overflow prevention" case, with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

A function contract names inputs, outputs, side effects and failure behavior. A prototype lets the compiler check calls before seeing the implementation. C passes arguments by value, so changing a scalar parameter does not change its caller. A pointer parameter can permit a function to modify a caller-owned object, but the function must state whether null is accepted and what object size is required. Returning a status plus writing through an output pointer is a common C API pattern. On failure, define whether the output remains unchanged rather than leaving callers to guess.

## Vocabulary and concepts

- **Prototype:** A declaration describing a function call interface.
- **Output parameter:** A pointer through which a function returns a value.
- **Failure atomicity:** A contract that failed operations leave specified state unchanged.

## Syntax anatomy and execution trace

static limits a file-scope function to its translation unit. A prototype such as int twice(int x) declares parameter and result types. void in an empty parameter list means no parameters in C17. bool try_area(int w,int h,int *out) can report success and provide an output separately. Validate preconditions before writing through out. Returning a pointer to an automatic local object creates a dangling pointer and must not be used.

## Worked example / walkthrough

### Worked example 1: Call a pure calculation

Evaluate twice for 7 and 0.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int twice(int x) { return 2 * x; }
void reassign(int value) {
  value = 99;
  (void)value;
}
bool try_area(int w, int h, int *out) {
  if (out == NULL || w <= 0 || h <= 0 || w > INT_MAX / h)
    return false;
  *out = w * h;
  return true;
}

int main(void) {
  /* Call a pure calculation */
  {
    CHECK(twice(7) == 14);
    CHECK(twice(0) == 0);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The results are 14 and 0.

The helper has no external state and its tiny input range avoids overflow. A general API would need a stated range.

### Worked example 2: Return an output on success

Calculate area for width 3 and height 4.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int twice(int x) { return 2 * x; }
void reassign(int value) {
  value = 99;
  (void)value;
}
bool try_area(int w, int h, int *out) {
  if (out == NULL || w <= 0 || h <= 0 || w > INT_MAX / h)
    return false;
  *out = w * h;
  return true;
}

int main(void) {
  /* Call a pure calculation */
  {
    CHECK(twice(7) == 14);
    CHECK(twice(0) == 0);
  }

  /* Return an output on success */
  {
    int out = -1;
    CHECK(try_area(3, 4, &out));
    CHECK(out == 12);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** Success is true and output becomes 12.

The status and result are distinct. The caller checks status before using the new output.

## Exercises

### Exercise 1: Call a pure calculation: predict an edited check

In worked example 1, change `CHECK(twice(0) == 0);` to `CHECK(twice(1) == 0);`. Predict whether the CHECK still holds and why, then run and restore.

**Expected:** `Check failed`: `CHECK(twice(1) == 0);` is false, although the results are 14 and 0.

**Verify:** Explain which claim `CHECK(twice(1) == 0);` makes that the state fails; restoring `CHECK(twice(0) == 0);` passes again.

**Progressive hints:** First work out what `twice` returns here. Then compute what the CHECK sees with `CHECK(twice(1) == 0);` in place.

### Exercise 2: Return an output on success: diagnose an edited check

Worked example 2's CHECK now reads `CHECK(try_area(4, 4, &out));`. Explain why it fails although success is true and output becomes 12, then restore it.

**Expected:** `Check failed` until the CHECK reads `CHECK(try_area(3, 4, &out));` again, though success is true and output becomes 12.

**Verify:** Explain why `CHECK(try_area(4, 4, &out));` rejects a state that `out == 12` accepts, using your failing and repaired runs.

**Progressive hints:** First trace `out` from initialization. Then compare `CHECK(try_area(4, 4, &out));` with worked example 2's original line.

### Exercise 3: Preserve output on rejection

Request area with width zero.

**Expected:** The call fails and output remains -1.

**Verify:** Keep a CHECK equivalent to `out == -1`. Control edit: changing `int out = -1;` to `int out = -2;` must fail it; then restore it.

**Progressive hints:** First trace `out` from initialization. Then recall: The helper validates before writing.

### Exercise 4: Trace copied scalar state

Pass 5 to a helper that reassigns its parameter.

**Expected:** The caller remains 5.

**Verify:** Keep a CHECK equivalent to `value == 5`. Control edit: changing `int value = 5;` to `int value = 6;` must fail it; then restore it.

**Progressive hints:** First trace `value` from initialization. Then recall: The function receives a scalar copy.

### Exercise 5: Reject a missing output target

Call try_area with a null output pointer.

**Expected:** The call fails without dereferencing it.

**Verify:** Keep a CHECK equivalent to `!try_area(3, 4, NULL)`. Control edit: `CHECK(try_area(3, 4, NULL));` must fail; then restore it.

**Progressive hints:** First work out what `try_area` returns here. Then recall: This API deliberately accepts null as a rejected input.

### Exercise 6: Transfer overflow prevention

Request INT_MAX times 2.

**Expected:** The operation rejects it and preserves output.

**Verify:** Keep a CHECK equivalent to `out == 9`. Control edit: changing `int out = 9;` to `int out = 10;` must fail it; then restore it.

**Progressive hints:** First trace `out` from initialization. Then recall: Checking w > INT_MAX/h before multiplication avoids executing signed overflow while deciding whether overflow would occur.

## Common pitfalls and diagnosis

Writing to the output parameter before validation finishes: if a later check fails, the caller sees a half-updated value. Compute into a local and assign through the pointer only on success. A call with no visible prototype is diagnosed under `-std=c17`.
