## The question and the mechanism

Predict when a variable freezes a value and when a measure is reevaluated in modified context.

A variable binds the result of its expression in the context where the variable is evaluated. Reusing the variable uses that value. It is not textual substitution that reevaluates its defining formula wherever its name appears. This makes variables useful for clarity and avoiding repeated work, but it also explains a frequent context bug.

Suppose Revenue is evaluated before a Blue product filter is introduced. The scalar stored in that variable is 187. Passing the variable to CALCULATE after adding Blue does not turn it back into a measure; its value remains 187. Passing the measure reference itself allows evaluation in the changed context and yields 163.

The location of a variable is therefore a semantic choice. A variable defined inside an iterator can be evaluated separately for each iteration; one outside can hold one shared scalar. Prefer names that describe the bound value, such as RevenueBeforeColorChange, rather than suggesting an automatic live link to every later context. Return intermediate values while debugging and trace where they were bound.

## Vocabulary and expression anatomy

VAR introduces a local name and RETURN supplies the expression using it. Case A binds the scalar before CALCULATE adds Blue. Case B establishes Blue outside, then compares a frozen scalar with a measure after removing that color filter. The changed order of binding and filtering produces different answers without changing the underlying data.

Concepts to explain in your own words: **VAR**, **RETURN**, **evaluation context**, **binding**, **readability**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: Binding before a new filter

**Starting context:** Start unfiltered; bind the variable before introducing Blue.

```dax
EVALUATE
VAR RevenueBeforeColorChange = [NetRevenue]
RETURN ROW ( "FrozenInBlue", CALCULATE ( RevenueBeforeColorChange, Product[Color] = "Blue" ), "RecomputedInBlue", CALCULATE ( [NetRevenue], Product[Color] = "Blue" ) )
```

**Context trace:**

1. The variable binds NetRevenue in the original all-row context: 187.
2. CALCULATE around that scalar cannot recreate its earlier measure expression.
3. The direct measure reference is evaluated with Blue and returns 163.

**Hand-derived worked-reference result:**

| FrozenInBlue | RecomputedInBlue |
| --- | --- |
| 187 | 163 |

The wrong result is not repaired by renaming the variable. Its defining location or the expression passed to CALCULATE must change.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Binding inside Blue before removing it

**Starting context:** The outer CALCULATETABLE supplies Blue before the variable is bound.

```dax
EVALUATE CALCULATETABLE (
    VAR RevenueBeforeRemoval = [NetRevenue]
    RETURN ROW ( "FrozenWithoutColor", CALCULATE ( RevenueBeforeRemoval, REMOVEFILTERS ( Product[Color] ) ), "RecomputedWithoutColor", CALCULATE ( [NetRevenue], REMOVEFILTERS ( Product[Color] ) ) ),
    Product[Color] = "Blue"
)
```

**Context trace:**

1. Blue makes NetRevenue 163 at variable binding time.
2. Removing the color filter around the scalar still returns 163.
3. Removing color before evaluating the measure restores the full revenue 187.

**Hand-derived worked-reference result:**

| FrozenWithoutColor | RecomputedWithoutColor |
| --- | --- |
| 163 | 187 |

Variables and filter modifiers are both predictable when the sequence is explicit. Do not infer that a variable called Total always means an unfiltered grand total.

## Progressive hints

1. The pre-filter variable is unchanged.
2. Establish context before evaluating its defining expression.
3. Bind each measure in the context it is meant to represent.
4. Check whether the denominator uses a precomputed scalar variable.
5. Ask where its expression is evaluated.
6. Record binding context and value before each modifier.
