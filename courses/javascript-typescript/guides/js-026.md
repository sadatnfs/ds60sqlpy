# js-026: Classes, composition and private state

## Purpose and mental model

Classes combine state with operations that preserve invariants. A typed number can still be negative, fractional, infinite or too large for exact integer arithmetic. A balance object therefore checks values before assigning new state. Constructor and method annotations document accepted checked calls, while runtime checks protect the actual numeric domain.

JavaScript #private fields enforce privacy at runtime. TypeScript private is primarily a checking restriction and should not be confused with a security boundary around ordinary emitted properties. Encapsulation is useful when callers should request an operation rather than directly assign arbitrary state. A getter returning a number supplies a value; a getter returning a mutable object would need a separate ownership policy.

Composition supplies a collaborator through a small interface, such as a clock. A test can provide a deterministic clock without changing global time or subclassing a large framework. The interface describes the capability required by the consumer. Inheritance is appropriate when substitutability is real, but reusing a few implementation lines does not prove that every subclass preserves its parent's contract.

## Vocabulary and concepts

**Encapsulation:** Restricting state changes to invariant-preserving operations.

**Private field:** A JavaScript # field with runtime-enforced access.

**Composition:** Building behavior from explicit collaborators.

**Interface:** A static capability contract for compatible values.

## Syntax anatomy and execution trace

A constructor establishes initial state. #balance names a runtime private field, while the cents getter exposes a primitive observation. implements would check an interface without generating methods. Constructor parameter properties create fields as part of TypeScript emission. A readonly dependency reference prevents reassignment through that class; it does not guarantee the collaborator itself is immutable. Validate derived results before committing a state transition.

## Worked example / walkthrough

### Example A: Maintain balance through methods

The public API exposes observations and controlled mutations. A caller cannot directly assign the private field by an ordinary property name.

```typescript
import { strict as assert } from 'node:assert';

function validCents(value: number): void {
  if (!Number.isSafeInteger(value) || value < 0) throw new RangeError('nonnegative safe integer cents required');
}
class Wallet {
  #balance: number;
  constructor(initial: number) { validCents(initial); this.#balance = initial; }
  get cents(): number { return this.#balance; }
  deposit(amount: number): void {
    validCents(amount);
    const next = this.#balance + amount;
    validCents(next);
    this.#balance = next;
  }
  withdraw(amount: number): void {
    validCents(amount);
    if (amount > this.#balance) throw new RangeError('insufficient balance');
    this.#balance -= amount;
  }
}
interface Clock { now(): Date }
class ReceiptService {
  constructor(private readonly clock: Clock) {}
  create(id: string): { id: string; createdAt: string } {
    if (id === '') throw new TypeError('id required');
    return { id, createdAt: this.clock.now().toISOString() };
  }
}

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const wallet = new Wallet(100);
    wallet.deposit(50);
    wallet.withdraw(30);
    assert.equal(wallet.cents, 120);
    assert.equal(Object.hasOwn(wallet, 'balance'), false);
    assert.deepEqual(Object.keys(wallet), []);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** balance 120; no enumerable balance field.
### Example B: Inject a deterministic clock

The time dependency is explicit and replaceable. The test does not mutate global time or rely on a fragile elapsed-time tolerance.

```typescript
import { strict as assert } from 'node:assert';

function validCents(value: number): void {
  if (!Number.isSafeInteger(value) || value < 0) throw new RangeError('nonnegative safe integer cents required');
}
class Wallet {
  #balance: number;
  constructor(initial: number) { validCents(initial); this.#balance = initial; }
  get cents(): number { return this.#balance; }
  deposit(amount: number): void {
    validCents(amount);
    const next = this.#balance + amount;
    validCents(next);
    this.#balance = next;
  }
  withdraw(amount: number): void {
    validCents(amount);
    if (amount > this.#balance) throw new RangeError('insufficient balance');
    this.#balance -= amount;
  }
}
interface Clock { now(): Date }
class ReceiptService {
  constructor(private readonly clock: Clock) {}
  create(id: string): { id: string; createdAt: string } {
    if (id === '') throw new TypeError('id required');
    return { id, createdAt: this.clock.now().toISOString() };
  }
}

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const service = new ReceiptService({ now: () => new Date('2026-01-01T00:00:00.000Z') });
    assert.deepEqual(service.create('A'), { id: 'A', createdAt: '2026-01-01T00:00:00.000Z' });
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** timestamp 2026-01-01T00:00:00.000Z.

## Prediction before your attempt

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

## Progressive hints

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
