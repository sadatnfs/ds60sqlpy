web-013: Color, contrast, focus and accessible states#

Level and prerequisites#

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: web-012

Learning objectives#

Build status cards whose meaning does not depend on color. Explain why one palette check does not qualify every interaction state. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

Purpose, vocabulary and mental model#

Color can group information, but it cannot be the only carrier of an essential distinction. A failed status should have words or an icon with an accessible name as well as a color. Contrast is the difference in luminance that makes foreground content distinguishable from its background. A pleasing palette does not automatically provide readable text or usable controls. Test the actual foreground-background pair in each state, including hover, focus, disabled and error.

Focus identifies the element receiving keyboard input. Removing the browser's outline without a replacement makes navigation difficult or impossible for many users. The focus-visible pseudo-class lets the browser apply its heuristics for when focus needs a visible indicator. A control can also require an adequately sized target and enough spacing from neighboring controls.

Syntax anatomy and mechanism#

Define a small set of tokens for text, background, accent and borders, then inspect their combinations. Use an outline with an offset so it is not hidden by the border. A status element can contain the word Ready or Needs attention; color reinforces that label. Prefer explicit text to a legend that a reader must memorize.

Classroom execution and offline inputs#

Choose HTML browser preview in the classroom. The pad is one complete HTML document with embedded CSS and, where taught, embedded JavaScript. Its preview is isolated from the classroom and recreated on each run. It does not contact a server, submit real forms, read cookies, fetch assets or load a CDN. All fixtures are inline and synthetic. The browser uses its native HTML parser, so classic-script ordering, shared lexical bindings, inline modules and real DOMContentLoaded/load events keep their browser semantics. External module imports remain blocked. Navigation metadata such as base and meta http-equiv is rejected explicitly. On any supported host, the browser renders the document while Docker serves the classroom. No host compiler is needed.

Worked example / walkthrough#

Worked example 1: Visible keyboard focus#

A clear outline remains distinct from the control border.

button:focus-visible { outline: 3px solid #9c3200; outline-offset: 3px; }

Expected observation: Keyboard focus has a visible indicator.

Worked example 2: A labeled status#

Words preserve the information without color.

<p class="status"><strong>Status:</strong> Needs attention</p>

Expected observation: The status is understandable in monochrome.

Six progressive exercises#

Exercise 1: Identify the missing information in a red-only error dot.#

Expected evidence: The user needs a textual error meaning and a useful recovery action.

Progressive hint: Trace the smallest example before editing. Name which values are source and which are observations.

Exercise 2: Add a focus-visible style without removing focus support.#

Expected evidence: Keyboard focus is visibly distinguishable from hover.

Progressive hint: Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

Exercise 3: Build status cards whose meaning does not depend on color.#

Expected evidence: Each card contains a clear label, readable text and visible interactive focus.

Progressive hint: Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

Exercise 4: Diagnose a focus ring clipped by overflow.#

Expected evidence: Inspect the ancestor clipping boundary and provide space or a different visible indicator.

Progressive hint: Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

Exercise 5: Inspect the page in a forced-colors or high-contrast setting.#

Expected evidence: Native boundaries and meaningful labels remain available; document actual browser behavior.

Progressive hint: Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

Exercise 6: Explain why one palette check does not qualify every interaction state.#

Expected evidence: Backgrounds and foregrounds can change per state, so each important combination needs review.

Progressive hint: Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

Debugging and common mistakes#

Do not calculate contrast against an assumed background when an overlay or image changes it. A custom focus ring that resembles hover may still confuse users. Automated checks complement real keyboard review.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

Retrieval, transfer and next steps#

Close the worked answers and explain contrast, focus-visible, state without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
