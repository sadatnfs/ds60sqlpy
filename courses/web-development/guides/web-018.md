# web-018: Custom properties, tokens and component themes

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-017`

## Learning objectives

Build two themed cards using one component rule. Explain a token name that survives a palette change. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A design token names a recurring design decision such as a spacing step, text color or border radius. CSS custom properties store values that participate in the cascade and can be scoped to a component. A variable name should communicate its purpose, such as --surface or --space-small, rather than merely its current value. That allows the value to change while the role remains stable.

Custom properties are resolved where they are used and usually inherit. A card can override a small set of tokens while retaining the same component rules. A fallback in var supplies a value when a variable is missing or invalid in the relevant way, but a custom property can still produce an invalid declaration at computed-value time. Test the final computed result instead of assuming any string is suitable for any property.

## Syntax anatomy and mechanism

Define shared defaults at :root and override them on a component class. `background:var(--surface,white)` uses the current scope's value. Keep semantic text labels independent of theme color. A theme change must preserve contrast and focus behavior, not merely update an accent swatch.

## Worked example / walkthrough

### Worked example 1: Named decisions

The variable names describe their roles.

```css
:root {
  --surface: #ffffff;
  --ink: #172033;
  --space: 1rem;
}
.card {
  background: var(--surface);
  color: var(--ink);
  padding: var(--space);
}
```

**Expected observation:** One component consumes three reusable tokens.

### Worked example 2: A scoped variation

Only descendants of this component inherit the override.

```css
.card.featured {
  --surface: #e0f2fe;
  --space: 1.5rem;
}
```

**Expected observation:** The featured card changes without copying its full rule set.

## Six progressive exercises

### Exercise 1: Predict which card inherits a scoped token override.

**Expected evidence:** Only the element with the override and its relevant descendants use that scope.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Replace repeated spacing literals with a semantic token.

**Expected evidence:** A deliberate single token change updates the related spacing.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build two themed cards using one component rule.

**Expected evidence:** The variants preserve content labels, contrast and focus while sharing structure.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a custom property used with an incompatible value.

**Expected evidence:** Inspect the final property and computed-value validity, not only the variable's existence.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Remove an optional variable and inspect its fallback.

**Expected evidence:** The component remains usable with its declared fallback.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain a token name that survives a palette change.

**Expected evidence:** A role such as --error-text is more durable than a name tied only to a particular red value.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not treat a token system as a substitute for a content design. Overly granular tokens can make simple changes harder. A dark theme needs a full state review, not a global invert filter.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain custom property, design token, fallback without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism.
