# js-004: Functions, scope and closures

## Level and prerequisites

Beginner, approximately 90 minutes. Direct prerequisites: `js-003`

Along the way, explain lexical scope, closure, default parameter, receiver with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. Exercises 1 and 2 start from the worked examples; the authored investigations begin with this task: Create three closures in a let loop and three in a var loop. The final task tests reject an invalid factory configuration.

## Purpose and mental model

Functions define reusable computations, and lexical scope determines which bindings a function can read. A closure retains access to bindings from the environment where it was created. Those bindings can hold state across calls, which is useful for a small counter or factory. Closures do not automatically copy every captured value. A shared var binding in a loop can make several functions observe the same final value, while let creates the intended per-iteration bindings.

Default parameters apply when an argument is undefined, not when it is null. Ordinary function this depends on the callsite; arrow functions capture this lexically. A clear function contract should distinguish arguments, returned values, mutable captured state and receiver dependence. Prefer explicit parameters when a closure would hide important dependencies.

## Vocabulary and concepts

**Lexical scope:** Binding lookup determined by where code is written.

**Closure:** A function retaining access to its surrounding bindings.

**Default parameter:** A fallback used when the supplied argument is undefined.

**Receiver:** The this value used by an ordinary method call.

## Syntax anatomy and execution trace

A function declaration introduces a named callable; an arrow expression creates a function value. Returning a nested function forms a closure over its surrounding bindings. let and const are block-scoped, while var is function-scoped. The default syntax name=value is evaluated when the argument is undefined. Use call or bind only when receiver behavior is part of the contract, not as a substitute for understanding the callsite.

## Worked example / walkthrough

### Example A: Call a pure function

The function depends only on its arguments and changes no external state. Boundary examples can be tested independently.

```javascript
import { strict as assert } from 'node:assert';

function counter(step = 1) {
  if (!Number.isInteger(step) || step <= 0) throw new TypeError('positive integer step required');
  let value = 0;
  return () => {
    value += step;
    return value;
  };
}

export async function verify() {
  // Worked example
  {
    function add(left, right) {
      return left + right;
    }
    assert.equal(add(2, 3), 5);
    assert.equal(add(-1, 1), 0);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));
```

**Expected:** 5 and 0.
### Example B: Build independent closures

Each factory call creates a separate captured binding. Equal initial values do not imply shared counter state.

```javascript
import { strict as assert } from 'node:assert';

function counter(step = 1) {
  if (!Number.isInteger(step) || step <= 0) throw new TypeError('positive integer step required');
  let value = 0;
  return () => {
    value += step;
    return value;
  };
}

export async function verify() {
  // Worked example
  {
    const first = counter();
    const second = counter();
    assert.equal(first(), 1);
    assert.equal(first(), 2);
    assert.equal(second(), 1);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));
```

**Expected:** first 1, 2; second 1.

## Prediction before your attempt

Trace the entry point and identify the values that exist before each operation. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. ## Exercises

1. **Call a pure function: predict an edited check.** Copy Example A into a scratch `main.mjs` and change `assert.equal(add(-1, 1), 0);` to `assert.equal(add(-2, 1), 0);` inside its check. Before running it, predict whether the check still passes and explain why; then restore it.
   **Expected:** The changed run fails with an `AssertionError` at the check `assert.equal(add(-1, 1), 0)`. Restoring the original line brings back the worked observation: 5 and 0.
   **Verify:** Compare your written prediction with the reported `AssertionError`, including its actual and expected values, and explain why the edited check rejects the values that `assert.equal(add(-1, 1), 0)` accepts. After restoring the line, the program prints its `{"checks":1,"status":"passed"}` receipt again.

2. **Build independent closures: diagnose an edited check.** A careless edit changed a check in Example B so that it reads `assert.equal(second(), 2);`. Run Example B with that line, explain why the edited check now fails for the same program state, and restore it.
   **Expected:** Before the repair the run fails with an `AssertionError` at the check `assert.equal(second(), 1)`; after it the line reads `assert.equal(second(), 1);` again and first 1, 2; second 1.
   **Verify:** Keep the failing and the repaired runs. Explain why the edited check rejects the same program state that `assert.equal(second(), 1)` accepts.

3. **Compare let and var loop capture.** Create three closures in a let loop and three in a var loop.
   **Expected:** let returns 0, 1, 2; var returns 3, 3, 3.
   **Verify:** Keep a check equivalent to `assert.deepEqual(shared.map((fn) => fn()), [3, 3, 3])`. As a control, change `for (var index = 0; index < 3; index += 1) shared.push(() => index);` to `for (var index = 0; index <= 3; index += 1) shared.push(() => index);`: the run must fail with an `AssertionError` at that check. Restore the line before continuing.

4. **Distinguish undefined from null defaults.** Call a greeting function with no argument, undefined and null.
   **Expected:** default used for the first two; null preserved.
   **Verify:** Keep a check equivalent to `assert.equal(label(), 'guest')`. As a control, change `function label(value = 'guest') {` to `function label(value = 'guest!') {`: the run must fail with an `AssertionError` at that check. Restore the line before continuing.

5. **Observe an ordinary receiver.** Call a method through its object and then with an explicit alternate receiver.
   **Expected:** 4 and 9.
   **Verify:** Keep a check equivalent to `assert.equal(item.read.call({ value: 9 }), 9)`. As a control, change `assert.equal(item.read.call({ value: 9 }), 9);` to `assert.equal(item.read.call({ value: 10 }), 9);` inside it: the run must fail with an `AssertionError`, which shows the check can fail. Restore it.

6. **Reject an invalid factory configuration.** Create a step counter with nonpositive or noninteger step.
   **Expected:** TypeError for 0 and 1.5; step 2 yields 2, 4.
   **Verify:** Keep a check equivalent to `assert.deepEqual([next(), next()], [2, 4])`. As a control, change `const next = counter(2);` to `const next = counter(3);`: the run must fail with an `AssertionError` at that check. Restore the line before continuing.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.
