# js-003: Control flow and loop boundaries

## Level and prerequisites

Beginner, approximately 90 minutes. Direct prerequisites: `js-002`

## Learning objectives

Explain truthiness, short circuit, loop invariant, nullish fallback with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Inspect Boolean conversions of 0, empty string, empty array and empty object. The final task tests make a wrong boundary observable.

## Purpose and mental model

Control flow decides which expressions execute and how many times. JavaScript conditions use truthiness, so false, 0, empty string, null, undefined and NaN act differently from empty arrays and objects, which are truthy. Short-circuit operators can return an operand rather than a Boolean. The nullish-coalescing operator provides a fallback only for null or undefined, which is often different from treating zero or empty text as missing.

Loops need an initial state, an invariant and a termination condition. A prefix sum invariant says the accumulator equals the sum of elements already visited. Half-open index bounds align with zero-based arrays. Boundary tests on empty and single-element inputs expose off-by-one errors more clearly than a large happy-path example. A loop that mutates its own collection also needs an explicit policy about which elements are visited.

## Vocabulary and concepts

**Truthiness:** The Boolean interpretation used by conditions.

**Short circuit:** Skipping an operand after the result can be determined.

**Loop invariant:** A property preserved as each iteration advances.

**Nullish fallback:** A fallback applied only to null or undefined.

## Syntax anatomy and execution trace

Use if for a branch, for...of for values, and indexed for when positions matter. The expression left&&right evaluates right only when left is truthy; left||right uses right only when left is falsy. Neither necessarily returns a Boolean. The expression value??fallback preserves 0, false and empty string. A loop condition i<array.length excludes the invalid index length.

## Worked example / walkthrough

### Example A: Compare false and truthy containers

An empty collection is still an object. Testing if(array) does not establish that it contains any elements.

```javascript
import { strict as assert } from 'node:assert';



export async function verify() {
  // Worked example
  {
    assert.deepEqual([Boolean(0), Boolean(''), Boolean([]), Boolean({})], [false, false, true, true]);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** false, false, true, true.
### Example B: Preserve a valid zero with nullish fallback

The operators encode different absence policies. A valid zero count should not silently become a default because it is falsy.

```javascript
import { strict as assert } from 'node:assert';



export async function verify() {
  // Worked example
  {
    assert.equal(0 || 10, 10);
    assert.equal(0 ?? 10, 0);
    assert.equal(null ?? 10, 10);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** 10, 0, 10.

## Prediction before your attempt

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

## Progressive hints

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
