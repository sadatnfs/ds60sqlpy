Learning objectives#

  • Express a single-row write precondition in an atomic UPDATE predicate.
  • Distinguish stale versions, insufficient capacity, and successful writes from returned evidence.
  • Record actual two-session visibility and serialize observations without mistaking a model for live concurrency.

Vocabulary and concepts#

A user reads stock 5 at version 1, then thinks for a moment. Another user can change that row before the first user sends an update. The old reading is evidence about an earlier view, not a lock on the future. A write should state its assumption where PostgreSQL can test it atomically. Optimistic concurrency includes the expected version in the UPDATE condition and interprets the returned row count as part of the result, instead of assuming a successful network round trip means the business action happened.

  • Optimistic version: An optimistic version is an application-managed number changed on every successful guarded update.
  • Compare-and-set: A compare-and-set operation updates only when the current state matches a supplied expectation.
  • Precondition: A precondition is the condition that must still hold when a write occurs.
  • Stale write: A stale write uses an expectation that no longer matches current state.
  • Schedule: A schedule is an ordered list of actions by named transactions.
  • Visibility trace: A visibility trace records what each session actually observed under its isolation level and action order.

The default lesson is a deterministic single-session model. It proves the behavior of version and capacity predicates, including negative controls. It cannot prove a race, blocking, deadlock, or snapshot anomaly. The optional lab supplies a separately owned committed schema so two real sessions can observe one row. Its exact preparation and cleanup are explicit below. Neither a modeled schedule nor a selected isolation setting counts as an observed concurrent execution. Preserve session labels, statements, returned rows, commit order, and errors when claiming that evidence.

Syntax anatomy and query reasoning#

UPDATE concurrency_stock SET available = available - 2, version = version + 1 WHERE sku = 'A' AND version = 1 AND available >= 2 RETURNING sku, available, version combines three checks. The key selects the intended item, the version tests the caller's earlier observation, and capacity prevents negative stock. RETURNING exposes the committed candidate state to the caller inside the current transaction. A zero-row result is a failed precondition, not a SQL exception. The caller must distinguish that outcome and decide whether to reread, reject, or retry under the product's rules.

Always increment the version in every write path, including administrative changes that invalidate an old observation. A version cannot protect against writers that bypass it. Keep the read and its associated expected version together. An unconditional assignment derived from an old value can overwrite someone else's work even when both statements execute successfully. For simple capacity changes an arithmetic guarded UPDATE can avoid a separate read, but multi-row invariants may require stronger coordination or serializable retries. A single-row version predicate does not prove a cross-row business invariant.

At READ COMMITTED a statement normally sees a new snapshot when it begins; at REPEATABLE READ a transaction retains its established view. Competing writes under stronger isolation can raise a serialization failure rather than simply returning zero rows. Retrying requires a new transaction and a fresh read, not replaying only the final statement in an aborted transaction. A successful UPDATE is also provisional until COMMIT. Losing the commit acknowledgement creates an unknown outcome that needs an idempotency contract, covered in the bridge and replication tracks, rather than an unconditional retry.

Worked example / walkthrough#

Run these in the complete learner file so the temporary fixture and transaction are present. The fixture values are fixed; the examples never depend on the current clock. Predict each result before running it.

Example 1: Guard an update and inspect its result#
SAVEPOINT worked_success;
UPDATE concurrency_stock
SET available=available-2,version=version+1
WHERE sku='A' AND version=1 AND available>=2
RETURNING sku,available,version;
ROLLBACK TO SAVEPOINT worked_success;
RELEASE SAVEPOINT worked_success;

The returned row is A with stock 3 and version 2. The savepoint is a local experiment boundary; rolling back to it restores A to stock 5 and version 1 for later examples. The output grain is one successfully updated SKU. No returned row means no row met all preconditions. This demonstration is deterministic and does not involve another connection.

Expected: One updated row, columns sku, available, version: (A,3,2). After rollback the fixture is (A,5,1).

Example 2: A stale expectation does not write#
UPDATE concurrency_stock
SET available=available-1,version=version+1
WHERE sku='A' AND version=99 AND available>=1
RETURNING sku,available,version;
SELECT sku,available,version FROM concurrency_stock WHERE sku='A';

No row matches version 99, so PostgreSQL reports UPDATE 0 and RETURNING contains no rows. The following SELECT proves the stock and version stayed unchanged. An application that reports success merely because the statement raised no exception would mislead the user. Do not immediately remove the version condition to make the update succeed; that deletes the protection instead of handling the conflict.

Expected: Zero updated rows, then one inspected row (A,5,1), columns sku, available, version.

Optional observed two-session lab#

The default file above is a model. To observe visibility, this optional lab commits exactly one table in the course-owned sql_concurrency_live schema. It uses two terminals connected to the same local disposable database, needs no extension or superuser role, and must finish with the explicit cleanup. The preparation refuses to replace an existing schema. Stop if another learner is already using that schema; do not erase their work.

Run from the repository root, in PowerShell or a macOS/Linux terminal:

psql -X -v ON_ERROR_STOP=1 -d advanced_sql_training -f sql/professional/fixtures/concurrency/prepare.sql

Open Terminal A and Terminal B, each with:

psql -X -v ON_ERROR_STOP=1 -d advanced_sql_training

In A, establish a view and leave the transaction open:

BEGIN ISOLATION LEVEL READ COMMITTED;
SET LOCAL statement_timeout = '10s';
SELECT sku,available,version FROM sql_concurrency_live.stock WHERE sku='A';

Expect (A,5,1). In B, make and commit one guarded write:

BEGIN;
SET LOCAL lock_timeout = '2s';
SET LOCAL statement_timeout = '10s';
UPDATE sql_concurrency_live.stock
SET available=available-1,version=version+1
WHERE sku='A' AND version=1 AND available>=1
RETURNING sku,available,version;
COMMIT;

B returns (A,4,2). In A, run the same SELECT again, then ROLLBACK. The second READ COMMITTED statement now shows (A,4,2). Record session, isolation, action order, both A results, and B's commit. This transcript is visibility evidence; the single-session default script is not.

For a contrasting run, reset only the fixture row in B using the following statement when both previous transactions have ended:

UPDATE sql_concurrency_live.stock SET available=5,version=1 WHERE sku='A';

This reset is fixture preparation only. It deliberately resets the version and must never be copied into an application write path. Repeat A's sequence with BEGIN ISOLATION LEVEL REPEATABLE READ;. Run A's first SELECT before B updates and commits. A's second SELECT remains (A,5,1) within that transaction; after A rolls back, a new SELECT shows (A,4,2). If A had not established its first snapshot before B's commit, it could instead establish the later view, which is why action order belongs in the evidence. This lab observes reads; it does not reproduce a serialization failure or deadlock. Do not add timing sleeps to substitute for the explicit checkpoints.

Finally issue ROLLBACK; in both terminals to release any forgotten transaction, quit both with \q, and run:

psql -X -v ON_ERROR_STOP=1 -d advanced_sql_training -f sql/professional/fixtures/concurrency/cleanup.sql

Cleanup drops the known table and then its empty course schema without CASCADE; unexpected extra objects cause a visible failure instead of silent deletion. verify_cleanup.sql can confirm the schema is absent. If a client disconnects mid-experiment, its uncommitted transaction is rolled back, but the explicitly committed fixture still needs this cleanup. Nothing here changes server configuration, roles, extensions, replication, or another database.

Exercise 2: Reject a stale expected version#

UPDATE concurrency_stock SET available=available-1,version=version+1
WHERE sku='A' AND version=99 AND available>=1 RETURNING sku,available,version;

Version 99 does not match the current row, so no mutation occurs. This is intentionally a successful SQL statement with an unsuccessful business precondition. Keep those two outcomes distinct in application code and learner evidence. The assertion checks both the empty RETURNING relation and the unchanged stored state. Removing the version condition would make the statement affect a row while destroying the protection the caller requested. A caller can reread to investigate, but must decide whether the original business intent remains valid before retrying. Under actual concurrent stronger-isolation execution an exception may be another possible outcome; this deterministic stale-version example makes no claim that all conflicts are reported as zero rows.

Exercise 3: Reject insufficient capacity independently#

UPDATE concurrency_stock SET available=available-2,version=version+1
WHERE sku='B' AND version=1 AND available>=2 RETURNING sku,available,version;

The version precondition is satisfied, but available >= 2 is false for B's one unit. Both predicates belong to the atomic update condition, so stock never becomes negative and the version does not advance. The CHECK constraint is an additional invariant guard; the ordinary business shortage should be handled without intentionally violating it. The assertion verifies an empty result and the unchanged B row. A zero-row outcome alone does not identify which precondition failed, so the caller may need an explicit follow-up read and a conflict policy. Keep that diagnostic read separate from a claim that the earlier attempt succeeded.

The first caller's successful write advances version 1 to 2. A distinct second statement with the old version then finds no matching row. The solution executes two statements and captures their RETURNING counts into a temporary trace table, avoiding ambiguous attempts to update the same row twice inside one SQL statement. The assertion expects One to affect one row and Two none. This models the conflict contract but does not reproduce simultaneous transactions or show how long a writer waits. Exercise 6: Transfer the guard to an atomic replenishment#

UPDATE concurrency_stock SET available=available+3,version=version+1
WHERE sku='B' AND version=1 RETURNING sku,available,version;

Replenishment changes the state just as reservation does, so it must advance the version. Otherwise an old reader could still act on the former version while using outdated capacity information. The first update returns B with four units and version 2. Repeating the old version precondition affects no rows. The solution captures that second RETURNING count as a negative control before rolling back the exercise. This does not make arbitrary retries idempotent after an unknown commit result: a retried caller needs a durable operation identity to know whether the first intent already committed. The version guard prevents a stale conditional write, while idempotency solves a related but different recovery question.

Verify: For sql-concurrency-01 Exercise 6, Inspect initial RETURNING (B,4,2), then require zero rows for repeating old version 1, and inspect restored (B,1,1) after rollback. This tests stale-write protection, not unknown-commit recovery.
