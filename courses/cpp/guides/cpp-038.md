## Learning objectives

State a numeric error/overflow contract instead of assuming one machine result.

## Vocabulary and concepts

Integer overflow and floating-point rounding are different correctness problems. Signed overflow is undefined; floating values approximate many decimal fractions. A tolerance defines acceptable numerical error for a specific scale. Stable algorithms reduce accumulated error, but exact money and identity arithmetic should use exact representations whenever possible.

<!-- terms:start -->

- **signed overflow:** an `int` result outside the representable range, which is undefined behavior rather than wraparound.
- **checked add:** an addition guarded by a test, such as `a > max - b`, that runs before the dangerous operation.
- **floating-point rounding:** the approximation of most decimal fractions, such as 0.1, by nearby binary values.
- **tolerance:** the acceptable numerical error chosen for a specific scale.
- **stable algorithm:** an algorithm that limits the rounding error accumulated across many operations.

<!-- terms:end -->

## Syntax and mechanism

Check a>max-b before nonnegative integer addition, after validating nonnegative operands. For approximate floating comparison use an absolute/relative tolerance justified by units. Do not compare all numbers using one arbitrary epsilon or replace exact integer assertions with fuzzy tests.

## Trace the mechanism

The integer guard is arranged to avoid evaluating the dangerous sum. Because inputs are nonnegative, max-b is safe and can be compared with a before adding. Floating addition follows a different model: rounding can make different parenthesizations of [1e16, 1, -1e16] produce different results. Use exact arithmetic for integer cents and justify approximate tolerances using scale and units. A loose tolerance must not conceal an incorrect algorithm.

<!-- depth:start -->
## Integer overflow and floating-point error are different

Integer arithmetic and floating-point arithmetic have different contracts. Signed integer overflow is not a defined wraparound policy in C++. A checked-add function must establish that the result is representable before evaluating the dangerous addition. Checking whether the sum became negative after overflow is too late because the invalid operation already occurred.

For nonnegative a and b, the guard a>max-b detects whether a+b would exceed the maximum. max-b is safe under the stated nonnegative supported range. Only after that guard passes should the addition be evaluated. If negative operands are allowed, the guard logic must cover underflow and other sign combinations separately. A formula valid for one restricted domain is not automatically a general checked-add implementation.

Floating-point values represent a finite set of numbers with rounding. Decimal 0.1 and 0.2 do not generally have exact finite binary representations, so their sum can differ slightly from the stored approximation of 0.3. The complete example uses a small tolerance for this specific comparison. That does not justify one universal tolerance for every scale or unit.

Addition order can matter because intermediate rounding occurs. Summing [1e16, 1, -1e16] in one order can lose the small contribution, while another grouping can preserve it. Parallel reduction can change grouping, so exact bitwise equality may require a stronger reproducibility design. For integer cents within a checked range, exact comparison remains appropriate; do not introduce approximate tolerances to hide a wrong integer result.

Choose numeric representation from the domain. Money may use checked integer minor units or a deliberate decimal representation. Measurements may need floating-point with error bounds, scale-aware comparison and stable algorithms. More precision can reduce some error but cannot substitute for an explicit contract or eliminate every conditioning problem.

## Worked example / walkthrough

Example 1 asks `safe_add` for the int maximum plus 1 and gets an empty optional, because the comparison against `std::numeric_limits<int>::max() - b` runs before any overflow can happen. Example 2 compares `0.1 + 0.2` with `0.3` using a `1e-12` tolerance: binary floating point holds none of them exactly, so equality is the wrong test. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-038-example-1.cpp)

```cpp
#include <cassert>
#include <iostream>
#include <limits>
#include <optional>

std::optional<int> safe_add(int a, int b) {
  if (a < 0 || b < 0 || a > std::numeric_limits<int>::max() - b)
    return {};
  return a + b;
}
int main() {
  assert(!safe_add(std::numeric_limits<int>::max(), 1));
  std::cout << "cpp-038 example 1 checks passed\n";
  return 0;
}
```

## Exercises

### Exercise 1: Keep exact units

Add 100 and 25 integer cents.

**Expected result/shape:** Exactly 125 cents.

**Verify:** Assert `safe_add(100, 25) == 125` with `int` values and no `double` anywhere in the calculation.

**Progressive hints:** No approximate representation is needed.

### Exercise 2: Reject overflow

Try INT_MAX plus 1.

**Expected result/shape:** Absent result without evaluating overflow.

**Verify:** Assert `!safe_add(std::numeric_limits<int>::max(), 1)`, as Worked example 1 does, and confirm the guard compares before adding.

**Progressive hints:** A check after overflow is too late.

### Exercise 3: Inspect rounding

Print 0.1+0.2 with sufficient precision.

**Expected result/shape:** Possible difference from 0.3 is recorded with a suitable tolerance.

**Verify:** Print with `std::setprecision(17)` and record `0.30000000000000004`, then assert `std::abs((0.1 + 0.2) - 0.3) < 1e-12`, as Worked example 2 does.

**Progressive hints:** Decimal fractions may lack finite binary representations.

### Exercise 4: Repair one-size tolerance

Explain why epsilon=0.1 is poor for both tiny and huge measurements.

**Expected result/shape:** A scale-aware absolute/relative policy stated.

**Verify:** Test your policy on 1e-9 versus 2e-9, which an absolute 0.1 calls equal, and on 1e20 versus 1e20 + 1e5, which it calls different although they differ by about 1e-15 relatively.

**Progressive hints:** Tolerance depends on units and error budget.

### Exercise 5: Check zero boundary

Run safe_add(0, 0) and safe_add(-1, 2).

**Expected result/shape:** Present 0 and rejected negative input.

**Verify:** Assert `safe_add(0, 0) == 0` and `!safe_add(-1, 2)`; the second call is rejected by the `a < 0` check even though the true sum, 1, fits.

**Progressive hints:** The subtraction-based guard assumes nonnegative inputs.

### Exercise 6: Transfer stability

Compare sums [1e16, 1, -1e16] under different groupings.

**Expected result/shape:** Floating sums can differ; exact expected mathematical total is 1.

**Verify:** Assert `(1e16 + -1e16) + 1 == 1`, and print `(1e16 + 1) + -1e16`, which gives 0 because `1e16 + 1` rounds back to 1e16.

**Progressive hints:** Associativity is not guaranteed by floating arithmetic.

## Self-check

Why must the check reject the input before evaluating an overflowing sum? For Example 2, explain why `0.1 + 0.2 == 0.3` is false in binary floating point, and why a tolerance is the right comparison.

## Common pitfalls

If a checked sum computes a+b before its guard, the protection is ineffective. If a nonnegative-only helper receives negative input, reject it or implement the broader signed contract. If a floating test fails at a different scale, review absolute versus relative tolerance and units. If a parallel total differs slightly, inspect grouping and rounding before assuming a race, while still checking synchronization independently.
