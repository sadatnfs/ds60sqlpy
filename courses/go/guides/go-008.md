# go-008: Structs and explicit domain models

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-007

## Learning objectives

Model a small domain with structs, predict copy behavior, and validate values before they enter the model. Along the way, explain struct, keyed literal, shallow copy; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A struct groups named fields into one value. Naming fields makes the domain visible: a coordinate with X and Y is more readable than an unexplained two-element slice. Struct assignment copies fields, but fields containing slices, maps or pointers can continue to share referenced storage. Exported fields begin with uppercase letters, which also affects reflection-based encoders. Zero values are predictable, yet not every zero struct is a valid domain object. A constructor-like function can validate inputs and return a value plus error, but Go does not require all construction to pass through such a function. Choose visibility and validation together.

## Vocabulary and concepts

- **Struct:** A value composed of named fields.
- **Keyed literal:** Construction naming the field for each supplied value.
- **Shallow copy:** A field-by-field copy that can retain referenced storage.

## Syntax anatomy and reasoning

type Point struct { X, Y int } creates a named type with fields. Point{X:2,Y:3} uses keyed construction, so field meaning survives reordering. p.X selects a field. Comparable structs can be compared with == only if every field is comparable. A struct with a slice cannot be a map key. An anonymous embedded field promotes selectors but does not create class inheritance.

## Worked example / walkthrough

### Worked example 1: Model a coordinate

Construct Point with X 2 and Y 3 and calculate Manhattan distance from the origin.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Point struct{ X, Y int }
type Batch struct{ Items []int }
type Item struct{ Name string }

func newItem(name string) (Item, error) {
	if name == "" {
		return Item{}, errors.New("name required")
	}
	return Item{Name: name}, nil
}

func main() {
	// Model a coordinate
	{
		p := Point{X: 2, Y: 3}
		check(p.X+p.Y == 5, "point")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The distance is 5.

Named fields document the coordinate meaning. This tiny case assumes nonnegative coordinates; a general distance function needs absolute values.

### Worked example 2: Observe scalar copy

Copy a Point and change the copied X field.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Point struct{ X, Y int }
type Batch struct{ Items []int }
type Item struct{ Name string }

func newItem(name string) (Item, error) {
	if name == "" {
		return Item{}, errors.New("name required")
	}
	return Item{Name: name}, nil
}

func main() {
	// Model a coordinate
	{
		p := Point{X: 2, Y: 3}
		check(p.X+p.Y == 5, "point")
	}

	// Observe scalar copy
	{
		a := Point{X: 2, Y: 3}
		b := a
		b.X = 9
		check(a.X == 2 && b.X == 9, "struct copy")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The original X remains 2.

Both fields contain scalar values, so assignment produces independent field storage.

## Common pitfalls and diagnosis

Assuming that copying a struct copies everything inside it is the common mistake: scalar fields are copied, but a slice, map or pointer field still refers to the same storage. The other trap is trusting a constructor to guard an invariant while its fields remain exported, so any caller can later assign an invalid value. Keep invariant-bearing fields unexported if the constructor must be the only gate.

## Progressive hints

### Hint for investigation 1: Model a coordinate: change one input

1. Restate the expected observation: The distance is 5.
2. Read the keyed literal: which value is X and which is Y? Their sum is the distance used here.
3. With X at 3 the sum is 6, so `p.X+p.Y==5` fails. The struct works; the new coordinate is simply farther from the origin.

### Hint for investigation 2: Observe scalar copy: debug a regression

1. Restate the expected observation: The original X remains 2.
2. Both fields are ints. Does `b := a` give b its own copies of X and Y?
3. `a.X` starts at 3, so `a.X==2` fails even though the copy stayed independent. Restore the literal; the independence of b is not the defect.

### Hint for investigation 3: Expose a shallow field

1. Restate the expected observation: The original batch observes the mutation.
2. Items is a slice descriptor. After the copy, which backing array does `b.Items` point to?
3. The copied slice descriptor still points to the same backing array.

### Hint for investigation 4: Inspect zero state

1. Restate the expected observation: Both coordinates are 0.
2. Each field takes its own zero value. What is the zero value of an int field?
3. Field zero values compose into a deterministic struct zero value.

### Hint for investigation 5: Use a comparable key

1. Restate the expected observation: The equal coordinate finds origin.
2. Struct equality compares fields. Is `Point{}` equal to the key stored for the origin?
3. Equality compares corresponding fields.

### Hint for investigation 6: Transfer validation

1. Restate the expected observation: The empty name is rejected; the valid name is retained.
2. newItem returns a value and an error. What should each be for an empty name, and for sample?
3. Validation at construction reduces invalid states, but exported fields still allow later assignment.
