# dbt-001: A real dbt project and its execution stages

## Level and prerequisites

Beginner. Direct prerequisites: `sql-start-03`

**Outcome:** Build and inspect a local dbt project through its real adapter.

## Question and mechanism

dbt transforms data by executing project-defined SQL through a database adapter. A project contains model files, configuration, tests and dependency declarations. A profile tells the adapter which owned database and execution settings to use. The classroom examples write ordinary project files into a temporary directory, invoke the installed dbt CLI through its Python interface and inspect a real DuckDB database. They do not simulate a dbt run.

Parsing, compilation and execution establish different facts. Parsing builds a graph and checks project structure. Compilation resolves template expressions into SQL. Running materializes model relations in the database. Building also includes selected tests and other dependency-aware resources. A compiled SQL file is therefore useful evidence of what would be submitted, but it does not prove that the relation exists or that its contents passed tests.

The Python wrapper is necessary because the classroom has one Python pad. Its file writes are explicit and local; you can inspect the normal dbt filenames in the source. An external multi-file project uses the same concepts, but persistence, credentials and orchestration require their own owned setup. Nothing in this lesson selects a cloud warehouse or installs packages while running.

## Syntax and data contract

dbt_project.yml declares the project name, version, profile name and resource directories. profiles.yml declares the local DuckDB path and bounded threading settings. Model SQL belongs under models/. dbtRunner.invoke receives a list of CLI arguments; calls run serially in this program. The result's success flag is checked before interpreting artifacts, and the database is queried independently after execution.

## Full-project Python workspace

Open this subject in `/classroom`, then show its code and notes. The prepared `data-engineering` worker runs `main.py` in a fresh temporary directory. The examples use installed packages and synthetic local fixtures; no account, cloud service, network request or package download is required. Save source and notes before switching lessons. Temporary databases, project files and tracking artifacts are recreated by each complete program and removed after the job. The classroom retains the submitted source and bounded output, not an indefinitely running external service. The guide distinguishes this local execution from the deployment decisions that need an owned production environment.

## Worked case 1: Parse and build an actual relation

The first case parses a one-model project, checks its manifest node, builds the model and queries the resulting relation. The answer 42 is verified in DuckDB rather than inferred from the source text. The run-results artifact is then checked for successful materialization.

**Expected evidence:** A manifest node exists, the database returns 42, and the run result reports success.

```python
import json
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def artifact(root, name):
    return json.loads((root / "target" / name).read_text())


def example_one():
    with tempfile.TemporaryDirectory() as d:
        p = project(d)
        invoke(p, "parse")
        manifest = artifact(p, "manifest.json")
        assert "model.classroom.answer" in manifest["nodes"]
        invoke(p, "build")
        assert rows(p, "select answer from answer") == [(42,)]
        assert artifact(p, "run_results.json")["results"][0]["status"] == "success"
        return {"parsed_model": "answer", "actual_database_value": 42}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Compilation does not substitute for execution

The second case inspects compiled SQL before running the model. It checks that no answer relation has yet been materialized, then runs the model and observes the result. The fixture deliberately computes the same answer through an expression.

## Diagnose errors and misleading results

A missing profile error usually means the project profile name and profiles.yml key disagree. A missing relation after compile is expected unless the model was run. A successful run with no tests is not a quality certificate. Inspect the command, selected resources, result status and actual database contents before deciding what was established.
