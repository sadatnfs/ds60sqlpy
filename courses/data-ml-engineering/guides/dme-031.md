## Explain where an answer came from

Lineage describes dependencies between data and transformations. Provenance includes additional information about how an artifact was produced, by which activity and under which identities or responsibilities. A useful investigation needs more than a diagram with arrows. It needs concrete input versions, transformation definitions, output identities and evidence that the recorded computation corresponds to the artifact being examined.

Consider a report that says six packages were delivered. If the source file later changes, the old report does not become correct for the new file simply because it still opens successfully. A reviewer needs to know which source bytes produced it and which descendants are now stale. If only a grouping recipe changes, the impact may start later in the graph, leaving earlier parsing work reusable. Lineage makes that distinction explicit.

The program creates actual local CSV, JSON and text artifacts, executes a small transformation graph and records their hashes. It also writes the transformation recipes that the implementation actually reads. The ledger includes parent artifact identities and the implementation's source hash. This is a bounded local provenance mechanism, not an Atlas server or a complete implementation of the W3C PROV model. The separate catalog and lineage workshops exercise richer systems; the mechanism here teaches what evidence they need to preserve.

## Read the dependency graph

The delivery branch is `raw -> clean -> totals -> report`. A separate calendar branch is `calendar -> calendar_report`. The clean step parses CSV package counts into integers. The totals recipe groups by route and sums packages. The report totals those route aggregates. The calendar report counts source lines. These branches are deliberately disjoint so an input change can demonstrate selective invalidation rather than rebuilding everything indiscriminately.

A node's identity depends on its artifact bytes and, for computed nodes, its recipe, implementation and parent identities. A simplified expression is

\[
I_v=H(\mathrm{code}_v,\mathrm{recipe}_v,\{I_u:u\in\operatorname{parents}(v)\},\mathrm{output}_v).
\]

The implementation stores the components explicitly rather than hiding them inside only one opaque digest. That makes diagnosis possible: a changed input, changed recipe and changed output are different observations. The source hash is deliberately coarse here: editing the program invalidates computed nodes even if the edit was nonsemantic. A production build system can use finer reviewed identities, but it must not omit real computation dependencies for the sake of cache reuse.

Invalidation propagates through the graph. A directly changed node is stale; every descendant depending on it is also affected. An unaffected branch remains valid under the recorded identities. This does not automatically execute a rebuild or approve a replacement. Detection, recomputation, validation and acceptance are separate operations.

## Worked case 1: trace a changed source through actual artifacts

`example_one()` writes deliveries A2 and B3 in north, plus C1 in south. The actual transformation produces route totals north: five and south: one, then a report total of six. The initial ledger validates without affected nodes. The program then changes A's source count from two to four while leaving the existing derived files untouched.

The invalidation result identifies `raw` as directly changed and marks `clean`, `totals` and `report` as affected descendants. The calendar source and calendar report remain unaffected. The old report still contains six, which is now stale for the changed source. A correct recomputation would produce eight. The example prints both facts instead of rewriting the old report and losing the evidence of the discrepancy.

This distinction is useful during incidents. A stored artifact can be historically correct for its original input and simultaneously unsuitable as the current answer. Calling it simply “wrong” loses context. Preserve the original lineage and label the new input version so a reviewer can reconstruct both the earlier decision and the proposed correction.

## Worked case 2: a recipe change starts later in the graph

The second case leaves the raw and cleaned data unchanged but changes the totals recipe's grouping key from route to delivery identity. The recipe is an actual JSON file consumed by the implementation, not an unrelated description. The invalidator detects `totals` as directly changed and propagates that change to `report`. The clean artifact and both calendar nodes remain unaffected.

The earliest rebuild node is therefore totals. Its parent clean data can be reused under the recorded contract. The final grand total might still be six after a correct rebuild, because regrouping does not change the sum of this fixture. That numerical coincidence does not make the old grouped artifact valid under the new recipe. Lineage preserves transformation meaning even when one downstream metric happens to match.

A cache keyed only by final total would miss this change. A cache keyed by source filename would also miss it. The recipe and implementation identities belong in the dependency boundary. This is one reason reproducible ML training must record preprocessing and feature definitions in addition to raw dataset paths.

## Complete worked program

Use Python Core. The program creates and inspects only its owned temporary artifacts. It does not send lineage events to an external service or read private source data.

```python
"""Real local artifact lineage with explicit recipe and content identities."""

import csv
import hashlib
import json
import tempfile
from graphlib import TopologicalSorter
from pathlib import Path

GRAPH = {
    "raw": set(),
    "calendar": set(),
    "clean": {"raw"},
    "totals": {"clean"},
    "report": {"totals"},
    "calendar_report": {"calendar"},
}


def sha(path):
    return hashlib.sha256(path.read_bytes()).hexdigest()


def save(path, value):
    path.write_text(json.dumps(value, sort_keys=True, separators=(",", ":")), "utf-8")


def build(root):
    (root / "raw.csv").write_text("id,route,packages\nA,north,2\nB,north,3\nC,south,1\n")
    (root / "calendar.txt").write_text("2024-01-01\n")
    paths = {"raw": root / "raw.csv", "calendar": root / "calendar.txt"}
    recipes = {
        "clean": {"kind": "typed-csv"},
        "totals": {"kind": "group-sum", "key": "route", "value": "packages"},
        "report": {"kind": "total"},
        "calendar_report": {"kind": "line-count"},
    }
    ledger = {}
    for node in TopologicalSorter(GRAPH).static_order():
        if node not in paths:
            recipe_path = root / (node + ".recipe.json")
            save(recipe_path, recipes[node])
            recipe = json.loads(recipe_path.read_text())
            if recipe["kind"] == "typed-csv":
                with paths["raw"].open(newline="") as handle:
                    value = [
                        {**row, "packages": int(row["packages"])} for row in csv.DictReader(handle)
                    ]
            elif recipe["kind"] == "group-sum":
                value = {}
                for row in json.loads(paths["clean"].read_text()):
                    key = row[recipe["key"]]
                    value[key] = value.get(key, 0) + row[recipe["value"]]
            elif recipe["kind"] == "total":
                value = {"packages": sum(json.loads(paths["totals"].read_text()).values())}
            else:
                value = {"days": len(paths["calendar"].read_text().splitlines())}
            paths[node] = root / (node + ".json")
            save(paths[node], value)
        ledger[node] = {
            "file": paths[node].name,
            "sha256": sha(paths[node]),
            "parents": {parent: ledger[parent]["sha256"] for parent in sorted(GRAPH[node])},
        }
        if node in recipes:
            ledger[node]["recipe"] = {
                "file": node + ".recipe.json",
                "sha256": sha(root / (node + ".recipe.json")),
                "implementation_sha256": sha(Path(__file__)),
            }
    save(root / "lineage.json", ledger)
    return ledger


def invalidated(root, ledger):
    direct = set()
    affected = set()
    for node in TopologicalSorter(GRAPH).static_order():
        item = ledger[node]
        if sha(root / item["file"]) != item["sha256"]:
            direct.add(node)
        if "recipe" in item and sha(root / item["recipe"]["file"]) != item["recipe"]["sha256"]:
            direct.add(node)
        if "recipe" in item and item["recipe"]["implementation_sha256"] != sha(Path(__file__)):
            direct.add(node)
        if any(item["parents"].get(parent) != ledger[parent]["sha256"] for parent in GRAPH[node]):
            direct.add(node)
        if node in direct or GRAPH[node] & affected:
            affected.add(node)
    return {
        "direct": sorted(direct),
        "affected": sorted(affected),
        "unaffected": sorted(set(GRAPH) - affected),
    }


def example_one():
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        ledger = build(root)
        assert invalidated(root, ledger)["affected"] == []
        assert json.loads((root / "report.json").read_text()) == {"packages": 6}
        (root / "raw.csv").write_text("id,route,packages\nA,north,4\nB,north,3\nC,south,1\n")
        result = invalidated(root, ledger)
        assert result == {
            "direct": ["raw"],
            "affected": ["clean", "raw", "report", "totals"],
            "unaffected": ["calendar", "calendar_report"],
        }
        return {
            "changed_input_invalidation": result,
            "stored_report_is_now_stale": 6,
            "expected_rebuild_total": 8,
        }


def example_two():
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        ledger = build(root)
        save(root / "totals.recipe.json", {"kind": "group-sum", "key": "id", "value": "packages"})
        result = invalidated(root, ledger)
        assert result["direct"] == ["totals"] and result["affected"] == ["report", "totals"]
        assert "clean" in result["unaffected"]
        return {
            "changed_recipe_invalidation": result,
            "earliest_rebuild_node": "totals",
            "hashes_establish_consistency_not_authorization": True,
        }


def main():
    print("Trace a changed source through actual artifacts:", example_one())
    print("A recipe change has a different impact boundary:", example_two())


if __name__ == "__main__":
    main()
```

## Provenance is not authorization

A hash can show whether bytes match a recorded identity. It does not establish who approved those bytes or whether the transformation answered the right question. Someone able to replace both an artifact and its ledger can construct another internally consistent pair. Trusted storage, review, signatures or controlled publication may be needed depending on the threat model. Do not describe a checksum ledger as tamper-proof by itself.

Likewise, a complete lineage graph does not prove a statistically valid model. It can reveal that evaluation data entered preprocessing, but someone must still recognize that as leakage. It can record which experiment metric was computed, but it cannot decide whether the metric represents the product objective. Provenance enables review; it does not replace scientific and engineering judgment.

Lineage metadata can itself contain sensitive information: dataset names, user identities, paths, SQL text and sample values. Record only what is needed, protect access appropriately and avoid copying credentials or private payloads into logs. This teaching repository uses synthetic names and bounded fixtures so its provenance examples can be shared safely.

## Completeness and granularity

Table-level lineage says which tables depend on which. Column-level lineage can explain how individual fields were derived. Row-level provenance can be much more expensive and may create additional privacy concerns. Choose granularity based on the investigation questions and operational budget. A full row history is not always necessary, but a single arrow between broad systems may be too coarse to diagnose a feature bug.

Hidden dependencies are especially dangerous. A transformation that reads the current date, an environment flag, a mutable lookup table or an unrecorded library version can change its output while its declared inputs appear stable. The earlier reproducibility chapter records environment identity. In this fixture, recipes, source implementation and parent artifacts are visible; a larger system must extend the model to every material dependency.

A graph also needs versioned relationships. If today's report uses yesterday's feature snapshot intentionally, that should be recorded rather than inferred from execution timestamps. Event time, publication time and job start time are different clocks. A chronological list of jobs is not a substitute for an explicit dependency graph.

## Diagnose stale or contradictory evidence

If a report changes without a changed source, inspect recipe, code, environment and undeclared dependencies. If a source changes but no descendant is invalidated, inspect missing graph edges. If a node is marked valid while its bytes differ, inspect the artifact hash readback. If unrelated branches are rebuilt unnecessarily, inspect whether identities are scoped too broadly or whether the dependency graph contains accidental edges.

If two manifests claim the same output identity but list different parent versions, preserve both records and investigate. Do not pick whichever file has the newest modification time. Filesystem timestamps can change during copying and do not establish semantic authority. The accepted publication protocol should identify which lineage record belongs to the consumer-visible artifact.

## Applications and answered interview discussion

Use provenance for incident investigation, reproducible training, audit trails, cache invalidation, dataset retirement and impact analysis. It is also valuable for a portfolio: a reviewer can reproduce a claimed result from declared inputs instead of trusting a screenshot.

An interviewer may ask, “What should be rebuilt after a feature definition changes?” Explain the earliest affected node and its transitive descendants, preserving valid ancestors and unrelated branches. If asked whether matching output proves unchanged meaning, show the regrouping case where the grand total stays six. If asked what lineage cannot prove, distinguish recorded derivation from authorization, completeness and correctness of the original assumptions.
