# mle-004: Validate structural and semantic feature contracts

## Level and prerequisites

Beginner. Direct prerequisites: `mle-003`

**Outcome:** Validate a feature interface structurally and semantically.

## Question and mechanism

A feature contract includes more than column names. It describes types, permitted values, units, identity and missingness policy. A table can satisfy a dtype schema while violating a domain rule or changing units. Validation should therefore retain both structural and semantic evidence.

The first case checks nonnegative usage and a declared region vocabulary. It preserves rejected identifiers and reasons rather than silently dropping rows or replacing every unfamiliar value. Different failures may require different actions: a malformed measurement, a new legitimate category and an unavailable observation should not automatically receive the same treatment.

The second case keeps the same field names but changes usage from hours to minutes. A contract identity changes even though a superficial column-set check would pass. Downstream models may react strongly to that difference. A semantic change needs reviewed versioning and revalidation, not merely a successful parser.

## Syntax and data contract

Use explicit conditions for each domain and collect named rejection reasons. Reconcile accepted and rejected records against the original count. A canonical serialized contract can be hashed to identify a version, but the hash only detects change; it cannot determine whether the new meaning is scientifically valid or authorized.

## Worked case 1: Keep rejected evidence

The fixture includes a negative usage and an unknown region. The program classifies both while retaining the valid row. Each input has exactly one reported outcome under the declared policy.

**Expected evidence:** Only id 1 is accepted; ids 2 and 3 carry distinct reasons.

```python
def example_one():
    rows = [
        {"id": 1, "usage": 10.0, "tickets": 2, "region": "north"},
        {"id": 2, "usage": -1.0, "tickets": 1, "region": "south"},
        {"id": 3, "usage": 4.0, "tickets": 0, "region": "unknown"},
    ]
    valid = []
    rejected = []
    for row in rows:
        reasons = []
        if row["usage"] < 0:
            reasons.append("negative_usage")
        if row["region"] not in {"north", "south"}:
            reasons.append("unknown_region")
        (rejected if reasons else valid).append({**row, "reasons": reasons})
    assert [r["id"] for r in valid] == [1]
    assert [r["reasons"] for r in rejected] == [["negative_usage"], ["unknown_region"]]
    assert len(valid) + len(rejected) == len(rows)
    return {
        "accepted_ids": [1],
        "rejections": [{k: r[k] for k in ("id", "reasons")} for r in rejected],
    }


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Detect a type-preserving meaning change

The second case changes a unit definition while keeping the same field names. The differing contract identity makes the change visible, but human/model review is still required to judge compatibility.

**Expected evidence:** The column sets agree while contract hashes differ.

```python
import hashlib
import json


def digest(data):
    return hashlib.sha256(
        json.dumps(data, sort_keys=True, separators=(",", ":"), allow_nan=False).encode()
    ).hexdigest()


def example_two():
    expected = {
        "usage": "nonnegative float",
        "tickets": "nonnegative integer",
        "region": ["north", "south"],
    }
    approved = digest(expected)
    changed = {**expected, "usage": "minutes instead of hours"}
    assert digest(changed) != approved
    assert set(expected) == set(changed)
    return {"same_column_names": True, "semantic_contract_changed": True, "version": approved}


if __name__ == "__main__":
    print(example_two())
```


## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Add a missing value

Define a separate outcome for unavailable usage.

**Check:** Missing is not mislabeled as a negative value.

**Hint:** Classification needs explicit categories.


### 2. Add a legitimate category

Introduce a new region under a revised contract.

**Check:** The change is versioned and tested.

**Hint:** Unknown does not always mean invalid forever.


### 3. Check a unit conversion

Convert minutes to hours before applying an hours-based model.

**Check:** The converted value matches the declared unit.

**Hint:** A dtype cannot express the unit.


### 4. Preserve rejection counts

Report each reason and the original denominator.

**Check:** Accepted plus rejected equals the input population.

**Hint:** Avoid overlapping categories without explanation.


### 5. Review a hash claim

Explain what the contract digest establishes.

**Check:** It establishes exact serialized identity.

**Hint:** Identity is not correctness or authenticity.


### 6. Bind the consumer

State how a serving bundle identifies its expected feature contract.

**Check:** The version or digest is retained with the model.

**Hint:** A model artifact alone is insufficient.


## Diagnose errors and misleading results

When a model suddenly behaves differently, inspect units, vocabularies and missingness even if schemas still parse. Do not fix all unknown values by mapping them to a convenient valid category. Preserve rejected evidence and version semantic changes.

## Transfer to independent work

Validate a feature interface structurally and semantically. Keep explicit rejection reasons and bind accepted feature meaning to the model artifact. This protects both reproducibility and useful diagnostics when inputs evolve.
