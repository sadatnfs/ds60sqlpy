dme-004: SQL, row grain, keys and relational reasoning#

Level: Beginner | Prepared runtime: data-engineering

Direct prerequisites: dme-001, dme-003.

Outcome: Execute real DuckDB joins and grouped metrics with an independent row oracle.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

Think about the rows before the query#

SQL describes operations on relations, commonly represented as tables. A table has named columns and rows, but the useful engineering question is what one row means. In this chapter, deliveries contains one identified delivery, while routes contains one identified route. The output contains one row per route with a package total. Those are three distinct grains.

The prepared data-engineering profile executes the examples with actual DuckDB. It creates an in-memory database, runs SQL, fetches the resulting rows and closes the connection. This is genuine database execution, not a Python list pretending to be a SQL result. It is also a local embedded database, not a deployed PostgreSQL server or a distributed warehouse. Authentication, concurrent remote clients and external operations have separate boundaries.

Our input is small enough to inspect completely:

Delivery ID Route ID Packages
1 10 2
2 10 3
3 20 1

The route table maps route 10 to north and route 20 to south. Names are display values; route IDs are identities. Keeping both in the output avoids assuming that a display name is globally unique or permanent. A renamed route should not automatically become a different physical entity, and two routes with the same display name should not silently merge.

Keys express cardinality assumptions#

A primary key identifies a row under a declared table contract. The example defines primary keys on delivery ID and route ID. In this local DuckDB table those constraints reject repeated primary-key values. Constraints and their enforcement differ between engines and storage formats, so read the actual engine's capabilities instead of assuming every warehouse checks every declared relationship.

The relationship here is many deliveries to one route. A join matches each delivery's route ID to the route table. If every delivery has exactly one matching route, the join preserves the number of delivery rows before aggregation. If a route identity appears twice in an unvalidated dimension, each matching delivery can appear twice in the joined result. If a route is absent and an inner join is used, the delivery can disappear.

These failures are about cardinality, not merely query syntax. A query can parse and run correctly while returning the wrong business quantity because its input violates an assumption. A useful reconciliation therefore checks identities, row counts and aggregate values at the relevant boundaries. It does not rely only on whether the SQL process returned zero.

Read the query as a sequence of concepts#

FROM deliveries d names an input and gives it a short alias. JOIN routes r USING(route_id) matches the shared key column. GROUP BY r.route_id, r.name defines the output groups. SUM(d.packages) combines package counts within each group. ORDER BY r.route_id makes the displayed order explicit for the fetched result.

This is a helpful reading order, not a promise that the database physically executes every step in that order. Query engines can choose equivalent physical plans. Later chapters inspect actual plans and discuss when transformations are valid. At this stage, focus on the declared relation and the expected result.

A relation does not provide a useful row-order guarantee merely because a result happened to appear sorted during one run. If order matters to the consumer, state it explicitly. If order does not matter, compare rows by their keys rather than writing a test that accidentally depends on one engine's current output arrangement.

The SQL strings here are fixed reviewed teaching queries. When values come from an external request, use the database's parameter-binding interface rather than concatenating unreviewed text into SQL. A constant query in an example is not permission to turn arbitrary request strings into executable statements.

Worked case 1: Aggregate an identified, valid relation#

The first case creates both tables, inserts the five small source rows and executes the join/aggregation. Route 10 receives deliveries 1 and 2, so its package total is 2+3=52+3=52+3=5. Route 20 receives delivery 3, so its total is one. The expected ordered rows are (10, "north", 5) and (20, "south", 1).

Worked case 2: Duplicate keys and missing values change the answer#

The second case deliberately constructs an unvalidated route table by copying the original rows and appending another row for route 10. The copy does not retain the original primary-key protection. It now has two distinct rows with the same route identity. Deliveries 1 and 2 each match twice, while delivery 3 matches once. The joined package total becomes

The program independently queries the violating route identities and expects route 10. It does not “repair” the total by dividing by two, because duplication is not uniform across all deliveries. It also does not assume DISTINCT across complete rows will resolve the conflict: the two route rows have different names and represent an unresolved identity problem.

The same changed-condition case examines missing values in a separate observations table containing delays of zero minutes, ten minutes and NULL. COUNT(*) counts all three rows. COUNT(delay_minutes) counts the two non-null values. AVG(delay_minutes) returns five minutes for the known-value population. Zero is a known value and belongs in that average.

This behavior should match a stated metric contract. It is not automatically the correct answer to every question about the three deliveries. Replacing NULL with zero would produce a different mean; filtering for positive delays would describe only delayed observations. The query must be evaluated against the intended population and denominator, just as in the previous chapter.

Complete worked program#

"""Execute actual SQL and reconcile each result with identified input rows."""

import duckdb


def database():
    connection = duckdb.connect(":memory:")
    connection.execute(
        "create table deliveries(id integer primary key, route_id integer, packages integer)"
    )
    connection.execute("insert into deliveries values (1,10,2),(2,10,3),(3,20,1)")
    connection.execute("create table routes(route_id integer primary key, name varchar)")
    connection.execute("insert into routes values (10,'north'),(20,'south')")
    return connection


def example_one():
    with database() as connection:
        result = connection.execute(
            "select r.route_id, r.name, sum(d.packages) as packages from deliveries d "
            "join routes r using(route_id) group by r.route_id, r.name order by r.route_id"
        ).fetchall()
        assert result == [(10, "north", 5), (20, "south", 1)]
        assert sum(packages for _, _, packages in result) == 2 + 3 + 1
        return {"packages_by_route": result, "input_delivery_rows": 3, "output_route_rows": 2}


def example_two():
    with database() as connection:
        connection.execute(
            "create table unvalidated_routes as select * from routes "
            "union all select 10,'duplicate'"
        )
        wrong = connection.execute(
            "select sum(d.packages) from deliveries d join unvalidated_routes r using(route_id)"
        ).fetchone()[0]
        duplicate_keys = connection.execute(
            "select route_id from unvalidated_routes group by route_id having count(*) <> 1"
        ).fetchall()
        assert wrong == 11 and duplicate_keys == [(10,)]
        connection.execute("create table observations(delay_minutes integer)")
        connection.execute("insert into observations values (0),(10),(NULL)")
        counts = connection.execute(
            "select count(*), count(delay_minutes), avg(delay_minutes) from observations"
        ).fetchone()
        assert counts == (3, 2, 5.0)
        return {
            "fanout_total": wrong,
            "correct_packages": 6,
            "violating_route_keys": duplicate_keys,
            "all_rows_known_values_mean": counts,
        }


def main():
    print("Identified relational aggregation:", example_one())
    print("Changed key and missing-value assumptions:", example_two())


if __name__ == "__main__":
    main()

Diagnose a wrong result systematically#

First verify that the input grain is what you think it is. Then check whether the key columns are unique or repeated where expected. Inspect unmatched identities and join multiplicities before changing an aggregation. A misplaced join can multiply a measure before SUM ever sees it.

Next inspect the filter and missing-value policy. A condition on the right-hand table after a left join can remove unmatched rows and change the effective population. A denominator based on all rows differs from one based on known measurements. A display label may be insufficient as a grouping key. These are questions about meaning, not just performance tuning.

Finally, define how the result should be compared. An explicitly ordered result can be checked as a sequence. An unordered relation should be checked by keys or as a multiset, depending on whether duplicates are meaningful. A set comparison can accidentally hide duplicate rows, so it is not a universal replacement for a correct cardinality contract.

If a production warehouse does not enforce a constraint, implement a real validation gate and retain its result. A comment saying “this key is unique” is not equivalent to a test that rejects a violating dataset. The dbt workshop develops actual data tests and accepted-publication boundaries in more depth.

Where this is useful#

Use these techniques for dimensional models, feature tables, reporting marts, experimental metrics and service lookups. Join mistakes often cross responsibility boundaries: a producer adds a new versioned dimension row, while a consumer still assumes one current row per identity. Discuss the row grain and time semantics explicitly rather than treating a table name as a complete interface.

Answered interview discussion#

Why can a join inflate revenue or counts? A supposed many-to-one relationship may actually be many-to-many or contain duplicate dimension keys. The measure is repeated before aggregation. Inspect multiplicity and the intended grain instead of applying a numerical correction afterward.

When should I use a left join? When the intended output retains the left-side population even if the relationship is missing. You still need to classify unmatched values and handle filters carefully. A left join alone does not establish data quality.

Is COUNT(column) interchangeable with COUNT(*)? No. The former excludes nulls in that expression; the latter counts rows. Choose according to the metric's denominator and expose missing-value coverage where it matters.

Can an index or a faster engine fix a wrong join? It can make the wrong result arrive faster. Establish semantic correctness and a reliable oracle before interpreting performance changes.

Why retain an ID beside a name? An ID represents the declared identity; a name is a description that may change or be reused. Grouping only by a display label can combine distinct entities unintentionally.
