## The question and the mechanism

Explain why a calendar reference can represent a different year definition than a classic date column.

Calendar-based time intelligence uses a named calendar's tagged metadata rather than assuming that every time function receives a classic Date column. The metadata tells the engine which columns represent day, year and other temporal categories. A calendar name is not an arbitrary alias for a Date column; its definition is part of the formula's input contract.

For this optional conceptual continuation, the model specification declares RetailCalendar over Date with RetailYear beginning February 1 and named by its ending year. At February 3,2025 its year-to-date set contains February 1..3 and revenue 56. Classic Gregorian YTD at the same date contains January 1..February 3 and revenue 123. The difference comes from year membership, not a faster or more accurate sum.

The classroom does not create that engine calendar object. The second source case is complete relative to the stated calendar contract, and its result is hand-derived from the tagged-year population. Actual use requires a compatible external engine and correctly configured calendar metadata. The stable beginner path remains available through the classic and explicit-date-set examples.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

### Case A: Classic Gregorian YTD

**Starting context:** Classic marked Date column; Gregorian year; anchor 2025-02-03.

```dax
EVALUATE CALCULATETABLE ( ROW ( "GregorianYTD", TOTALYTD ( [NetRevenue], 'Date'[Date] ) ), 'Date'[Date] = DATE ( 2025, 2, 3 ) )
```

**Context trace:**

1. The classic year begins January 1.
2. January revenue 67 and February-to-date 56 are included.
3. Gregorian YTD is 123.

**Hand-derived worked-reference result:**

| GregorianYTD |
| --- |
| 123 |

This case requires only the already described classic date-table contract. It provides a stable baseline for comparing another calendar definition.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: The declared February-start retail calendar

**Starting context:** Assume the optional RetailCalendar metadata has been configured exactly as specified; RetailYear starts February 1.

```dax
EVALUATE CALCULATETABLE ( ROW ( "RetailYTD", TOTALYTD ( [NetRevenue], RetailCalendar ) ), 'Date'[Date] = DATE ( 2025, 2, 3 ) )
```

**Context trace:**

1. The anchor belongs to RetailYear 2026 under the ending-year naming rule.
2. Its year-to-date date set begins February 1,2025.
3. S7 and S 8 contribute 20 +36 =56; January belongs to the prior retail year.

**Hand-derived worked-reference result:**

| RetailYTD |
| --- |
| 56 |

This is a reference derivation under a declared metadata assumption, not observed preview-engine output. An undefined calendar name would not be a usable external query.

Hand-derived under the explicitly specified optional calendar metadata. No preview engine, model authoring or execution was performed.

## Progressive hints

1. The February-start year has not rolled over yet.
2. The calendar metadata, not the function name alone, defines the year.
3. Check tags, relationships, compatibility and boundary fixtures.
4. A named calendar definition is additional metadata.
5. Calendar membership and available outcomes remain separate.
6. Publish the exact period membership before choosing a function.
