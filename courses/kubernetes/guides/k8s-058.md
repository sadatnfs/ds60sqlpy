## Purpose, vocabulary and mental model

NetworkPolicy describes allowed network relationships for selected Pods. It requires a network implementation that enforces the API. Creating the object on a cluster without enforcement does not prove isolation. The policy is primarily about supported network traffic, not HTTP user identity or arbitrary application authorization.

Policies are additive. Once a Pod is isolated for a direction, the union of applicable allow rules determines permitted traffic for that direction. There is no general ordered deny rule that overrides a later allow in the ordinary API. A policy can select all Pods in one namespace with an empty podSelector, while namespace scope remains important.

Selector composition is subtle. A single peer containing both namespaceSelector and podSelector requires both conditions. Separate peers represent alternatives. Confusing these forms can allow far more callers than intended. This lesson makes that Boolean logic explicit with a small synthetic matrix.

## Mechanism and field-by-field reasoning

A policy’s podSelector selects the destination Pods for ingress rules. Each from item describes an allowed source. Ports constrain the destination transport port. Namespace labels are selected on Namespace objects, not copied from Pod labels by assumption.

For a connection between two Pods, the source Pod’s egress policy and the destination Pod’s ingress policy must both permit it when those directions are isolated. A direction with no applicable isolation does not restrict that connection through NetworkPolicy. Reply traffic belonging to a permitted connection is implicitly allowed; that does not authorize an unrelated new reverse-direction connection.

The fixture provides an allow-client policy as a manual-only example. It does not claim that the ordinary local kind network enforces NetworkPolicy. The offline checker validates selector logic and fields; a live test requires both an allowed and a denied owned client under a known enforcing implementation.

## Trace the request or control path

```text
policy selects destination Pods -> ingress isolation applies
allowed source peer AND allowed destination port -> candidate permitted flow
all applicable allow rules combine by union; actual CNI must enforce
```

## Worked example / walkthrough

### Worked example 1: Read an AND peer

Both namespace and Pod labels must match this one peer.

```yaml
from:
  - namespaceSelector:
      matchLabels:
        study-role: client
    podSelector:
      matchLabels:
        role: tester
```

**Expected observation:** A tester in a nonmatching namespace is not allowed by this peer.

### Worked example 2: Contrast OR peers

Two list items are alternatives.

```yaml
from:
  - namespaceSelector:
      matchLabels:
        study-role: client
  - podSelector:
      matchLabels:
        role: tester
```

**Expected observation:** The namespaceSelector-only branch permits all Pods in matching namespaces. The podSelector-only branch permits role=tester Pods only in the NetworkPolicy’s own namespace. Their union is broader than the combined AND peer; it does not mean testers in every namespace.

## Diagnosis, failure boundaries and common mistakes

The controlled failure in this chapter is: Diagnose a policy object with unrestricted actual traffic. Its distinguishing result is The implementation may not enforce policy or another allow rule may apply. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
