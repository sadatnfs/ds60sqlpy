# c-031: Checked arithmetic and allocation-size contracts

## Level and prerequisites

Advanced, approximately 120 minutes plus a later retrieval session. Direct prerequisites: `c-030`

## Learning objectives

Check addition and multiplication for overflow before computing a value or an allocation size. Along the way, explain precondition check, checked arithmetic and conversion boundary. Implement the six investigations, from the "add ordinary values" case to the "transfer the zero product" case, with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

Integer overflow is often a memory-safety defect in disguise. A wrapped allocation size can reserve less storage than later code assumes, and signed overflow cannot safely be used as the condition that detects itself. Validate before the operation using inequalities whose own arithmetic is defined. Keep signed value arithmetic separate from size_t storage arithmetic, and validate conversions at their boundary. The chosen failure policy should preserve outputs and let callers distinguish overflow from a legitimate zero. Compiler overflow builtins can be useful, but portable C17 logic remains worth understanding before depending on a toolchain extension.

## Vocabulary and concepts

- **Precondition check:** A condition established before a potentially invalid operation.
- **Checked arithmetic:** Arithmetic that reports range failure explicitly.
- **Conversion boundary:** A point where values move between representations with different ranges.

## Syntax anatomy and execution trace

For a positive addend b, a+b fits int only when a<=INT_MAX-b. For a negative b, require a>=INT_MIN-b. For size_t multiplication, if b is nonzero require a<=SIZE_MAX/b. Check output pointers before writing. These preconditions avoid evaluating the dangerous expression until its validity is established. A zero multiplier is a valid mathematical case, even when an allocator wrapper later rejects zero-sized storage by policy.

## Worked example / walkthrough

### Worked example 1: Add ordinary values

Add 7 and 5 through the checked helper.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

bool add_checked(int a, int b, int *out) {
  if (out == NULL || (b > 0 && a > INT_MAX - b) || (b < 0 && a < INT_MIN - b))
    return false;
  *out = a + b;
  return true;
}
bool size_product(size_t a, size_t b, size_t *out) {
  if (out == NULL || (b != 0 && a > SIZE_MAX / b))
    return false;
  *out = a * b;
  return true;
}

int main(void) {
  /* Add ordinary values */
  {
    int out = 0;
    CHECK(add_checked(7, 5, &out) && out == 12);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The result is 12.

The normal case uses the same guarded path as boundary cases.

### Worked example 2: Reject positive overflow

Add one to INT_MAX.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

bool add_checked(int a, int b, int *out) {
  if (out == NULL || (b > 0 && a > INT_MAX - b) || (b < 0 && a < INT_MIN - b))
    return false;
  *out = a + b;
  return true;
}
bool size_product(size_t a, size_t b, size_t *out) {
  if (out == NULL || (b != 0 && a > SIZE_MAX / b))
    return false;
  *out = a * b;
  return true;
}

int main(void) {
  /* Add ordinary values */
  {
    int out = 0;
    CHECK(add_checked(7, 5, &out) && out == 12);
  }

  /* Reject positive overflow */
  {
    int out = 9;
    CHECK(!add_checked(INT_MAX, 1, &out) && out == 9);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The operation fails and preserves output.

The addition itself is never evaluated after the precondition fails.

### Exercise 1: Add ordinary values: predict an edited check

### Exercise 3: Reject negative overflow

Add negative one to INT_MIN.

**Expected:** The operation fails without evaluating the overflow.

**Verify:** Keep a CHECK equivalent to `!add_checked(INT_MIN, -1, &out) && out == 9`. Control edit: changing `int out = 9;` to `int out = 10;` must fail it; then restore it.

**Progressive hints:** First trace `out` from initialization. Then recall: Checking the negative boundary requires a separate inequality from the positive case.

### Exercise 4: Accept exact boundaries

Add zero to both int extremes.

**Expected:** Both exact boundary values are accepted.

**Verify:** Keep a CHECK equivalent to `add_checked(INT_MIN, 0, &out) && out == INT_MIN`. Control edit: `CHECK(add_checked(INT_MIN, 1, &out) && out == INT_MIN);` must fail; then restore it.

**Progressive hints:** First trace `out` from initialization. Then recall: An overconservative check that rejects every extreme would violate the valid-domain contract.

### Exercise 5: Reject a size product

Multiply SIZE_MAX by two through a size helper.

**Expected:** The helper rejects it and preserves output.

**Verify:** Keep a CHECK equivalent to `!size_product(SIZE_MAX, 2, &out) && out == 7`. Control edit: changing `size_t out = 7;` to `size_t out = 8;` must fail it; then restore it.

**Progressive hints:** First trace `out` from initialization. Then recall: The division comparison avoids wrapping before allocation-size validation.

### Exercise 6: Transfer the zero product

Multiply SIZE_MAX by zero.

**Expected:** The checked mathematical result is zero.

**Verify:** Keep a CHECK equivalent to `size_product(SIZE_MAX, 0, &out) && out == 0`. Control edit: `CHECK(size_product(SIZE_MAX, 1, &out) && out == 0);` must fail; then restore it.

**Progressive hints:** First trace `out` from initialization. Then recall: Arithmetic validity and whether a zero-sized allocation is useful are separate policies.

## Common pitfalls and diagnosis

Testing `a + b < a` after the addition: for signed types the overflow has already happened, which is undefined. Compare against `INT_MAX - b` first. Converting a negative `int` to `size_t` yields a huge size, not an error.
