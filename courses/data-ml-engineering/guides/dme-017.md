## Start with the answer's contract

A query engine is software that turns a request for data into a sequence of reads, transformations and computations. SQLite, DuckDB and Polars can all group a small table, but that overlap does not make them interchangeable. SQLite is an embedded transactional relational database. DuckDB is an embedded analytical database. Polars is a typed DataFrame library with expression and lazy-query APIs. An application chooses among them partly by workload and partly by the surrounding contract: concurrent writes, transaction boundaries, required SQL, memory limits, file formats, deployment constraints and maintainers' familiarity.

Start a comparison with an answer whose meaning you can calculate without any engine. Our daily table has one row per route and calendar day. The key is `(route_id, day)`. A missing package observation is unknown; a numeric zero means that the observed route carried no packages. The result has one row per route with four fields: route identity, sum of known observations, number of recorded days and number of known observations. Do not quietly redefine the denominator when a library changes.

Let \(D_r\) be the recorded days for route \(r\), and \(K_r\subseteq D_r\) the days with a known count. The contract is

\[
N_r=|D_r|,\qquad n_r=|K_r|,\qquad
S_r=\begin{cases}\sum_{d\in K_r}x_{rd},&n_r>0,\\\mathrm{unknown},&n_r=0.\end{cases}
\]

The final branch is a business rule. Another product might deliberately define an empty sum as zero, but it must keep observation coverage available. A route with no known measurements cannot support the claim that its observed traffic was zero. The distinction affects anomaly alerts, capacity decisions and downstream model features.

## Read the three implementations

`sql_result` receives a connection factory. A factory is a function that creates a new resource when called. Passing `lambda: sqlite3.connect(":memory:")` or `lambda: duckdb.connect(":memory:")` lets the same query run against two actual engines. The connection is closed in a `finally` block, including when insertion or querying fails. The declared primary key rejects a repeated route-day observation rather than letting accidental duplicate rows inflate the aggregate.

The query uses `SUM(packages)`, `COUNT(*)` and `COUNT(packages)`. The first computes a known-value total, the second counts rows, and the third counts non-null values. `GROUP BY route_id` defines the result grain. `ORDER BY route_id` establishes a presentation order for this comparison. Grouping alone does not promise ordering. In a larger comparison, align by keys first and compare values second, especially when multiple engines use parallel execution.

Polars receives an explicit schema, including an integer package column that can contain nulls. `orient="row"` tells it how to interpret the Python tuples. A struct expression combines route and day so `n_unique()` can check the compound key. `pl.len()` counts rows, while `pl.col("packages").count()` counts non-null observations. The expression API builds column operations rather than running a Python loop for each row. Sorting at the end makes the printed reference easy to inspect; it is not needed to define the grouped relation.

## Worked case 1: three real engines agree on a mixed population

The fixture gives route 10 two days: two packages and one unknown observation. Route 20 has three packages and one known zero. Before running, compute the two expected tuples: `(10, 2, 2, 1)` and `(20, 3, 2, 2)`. Route 10 has two recorded days but only one known day. Route 20 has two known days, because zero is a value.

`example_one()` creates independent in-memory databases and a typed DataFrame. It executes each implementation, then compares all three results with the hand-calculated tuples. This is stronger than comparing engines only with one another: three implementations can share the same conceptual error. The explicit expected answer is a small independent oracle. The printed column list explains the tuple positions so that `2, 2, 1` is not an unexplained sequence of numbers.

This case demonstrates local semantic agreement for the declared fixture. It does not establish throughput, persistence guarantees, SQL dialect equivalence or behavior for arbitrary types. The databases are temporary and contain four rows. A fair performance experiment would specify much larger representative data, warm versus cold reads, thread counts, memory limits, result materialization and repeated measurements. Installing three tools and timing their imports would answer a different question from timing an analytical query.

## Worked case 2: an all-null group reveals a policy mismatch

The second fixture changes the condition that the first never exercised. Route 30 has one unknown observation and no known values; route 40 has one known zero. SQLite and DuckDB return null for route 30's sum. The prepared Polars version returns zero for that sum by default. Every implementation still reports one recorded row and zero known rows for route 30.

The raw Polars result therefore combines two distinct states into the same numeric total. The program does not label this a broken engine. It adds an explicit expression: if the non-null count is positive, use the sum; otherwise return a typed null. The resulting table matches the chosen contract. Route 40 remains zero with one known observation. The condition checks coverage, not whether the computed sum happens to equal zero, because positive and negative values could also cancel in another domain.

The typed `pl.lit(None, dtype=pl.Int64)` makes the intended result type explicit. This is useful when all rows in a fixture are null and inference otherwise has insufficient evidence. Changing `None` to a string such as `"unknown"` would mix numeric and textual concepts in one analytical field. Keep machine-readable missingness separate from the presentation label displayed to a learner or report consumer.

## Complete worked program

Run this in the prepared data-engineering profile. It creates no network connections, uses no persistent classroom database and requires no separately running service.

```python
"""Compare real local engines under one explicit known-value aggregation policy."""

import sqlite3

import duckdb
import polars as pl


def sql_result(factory, records):
    connection = factory()
    try:
        connection.execute(
            "create table daily(route_id integer, day varchar, "
            "packages integer, primary "
            "key(route_id,day))"
        )
        connection.executemany("insert into daily values (?,?,?)", records)
        return connection.execute(
            "select route_id,sum(packages),count(*),count(packages) "
            "from daily group by route_id order by "
            "route_id"
        ).fetchall()
    finally:
        connection.close()


def polars_result(records, explicit_empty_policy=False):
    frame = pl.DataFrame(
        records,
        schema={"route_id": pl.Int64, "day": pl.String, "packages": pl.Int64},
        orient=("row"),
    )
    if frame.select(pl.struct("route_id", "day").n_unique()).item() != frame.height:
        raise ValueError("The declared daily observation grain must be unique")
    total = pl.col("packages").sum()
    if explicit_empty_policy:
        total = (
            pl.when(pl.col("packages").count() > 0)
            .then(total)
            .otherwise(pl.lit(None, dtype=pl.Int64))
        )
    return (
        frame.group_by("route_id")
        .agg(
            total.alias("known_total"),
            pl.len().alias("all_days"),
            pl.col("packages").count().alias("known_days"),
        )
        .sort("route_id")
        .rows()
    )


def example_one():
    records = [
        (10, "2024-01-01", 2),
        (10, "2024-01-02", None),
        (20, "2024-01-01", 3),
        (20, "2024-01-02", 0),
    ]
    sqlite = sql_result(lambda: sqlite3.connect(":memory:"), records)
    duck = sql_result(lambda: duckdb.connect(":memory:"), records)
    polars = polars_result(records)
    expected = [(10, 2, 2, 1), (20, 3, 2, 2)]
    assert sqlite == duck == polars == expected
    return {
        "columns": ["route_id", "known_total", "all_days", "known_days"],
        "actual_sqlite": sqlite,
        ("actual_duckdb"): duck,
        ("actual_polars"): polars,
    }


def example_two():
    records = [(30, "2024-01-01", None), (40, "2024-01-01", 0)]
    sqlite = sql_result(lambda: sqlite3.connect(":memory:"), records)
    duck = sql_result(lambda: duckdb.connect(":memory:"), records)
    raw_polars = polars_result(records)
    normalized = polars_result(records, explicit_empty_policy=True)
    assert sqlite == duck == [(30, None, 1, 0), (40, 0, 1, 1)]
    assert raw_polars == [(30, 0, 1, 0), (40, 0, 1, 1)]
    assert normalized == sqlite
    return {
        "sql_policy": sqlite,
        "default_polars": raw_polars,
        "explicit_policy_alignment": normalized,
        ("unknown_total_differs_from_known_zero"): True,
    }


def main():
    print("Actual engine comparison on declared daily grain:", example_one())
    print("Empty known populations need an explicit policy:", example_two())


if __name__ == "__main__":
    main()
```

## Diagnose differences systematically

A missing group, a duplicated group and a changed null policy are different failures. First compare the set of keys and the input grain. Next compare row counts and known-value counts. Then compare typed values. Only after those checks consider numeric tolerance. Floating-point aggregates can differ because summation order changes rounding, but integer counts in this tiny fixture should match exactly. Adding a broad tolerance to every field would conceal a missing row or changed identifier.

If the SQL path raises a primary-key violation while Polars returns an answer, check whether the DataFrame uniqueness guard was removed. A permissive load is not evidence of a better answer. If strings such as `"2"` appear in the source, decide whether strict rejection or explicit conversion belongs to ingestion; do not depend on an engine's incidental coercion. For timestamps, make timezone and unit decisions before comparing results. For text ordering, investigate collation and case rules instead of assuming every alphabetical sort has the same semantics.

## Use this in an engineering decision

Choose SQLite when a small embedded application needs understandable local transactions and indexed lookups. Consider DuckDB when the work centers on analytical SQL over local or prepared columnar data. Consider Polars when a Python transformation pipeline benefits from typed expressions and lazy plans. These are starting hypotheses, not universal rankings. A product may use more than one: SQLite for an ingestion ledger and DuckDB or Polars for analytical publication, with a reviewed data boundary between them.

An interview may ask, “How would you migrate a pandas or SQL job without changing its meaning?” A strong answer begins with grain, types, nulls, order sensitivity and known business cases, then proposes differential tests plus an independent oracle. “Both tools ran successfully” is insufficient. If asked whether null should become zero, explain what is unobserved and what is measured; the correct policy follows the product's interpretation, not personal formatting preference.

A useful optional investigation is to add an all-null group, a duplicate key and an empty input separately, predict each outcome, and inspect the earliest failing contract. Keep the baseline fixture intact while doing so. The next chapter moves from engine semantics to physical file layout without changing this discipline of preserving the answer.
