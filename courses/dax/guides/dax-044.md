## The question and the mechanism

Describe a reusable transformation while preventing it from changing incompatible measures.

A calculation group contains calculation items that transform a selected measure. SELECTEDMEASURE stands for that underlying measure expression within the calculation-item context. It is not an ordinary variable that can be pasted into any standalone scalar query. The group and item are model metadata in a real engine.

Reusing a transformation requires an applicability policy. A hypothetical ten-percent revenue fee can apply to NetRevenue, but multiplying QuantitySold by 0.9 would turn 17 recorded units into 15.3 without any corresponding change in transactions. ISSELECTEDMEASURE can guard the transformation so unrelated measures retain their definitions.

The worked references show the current values and the algebraically expanded guarded item. This is deliberate offline reasoning, not an execution of model calculation-group machinery. The item definition below states the reusable model expression; the query expansions make the expected arithmetic independently inspectable.

## Vocabulary and expression anatomy

The illustrative calculation item is IF(ISSELECTEDMEASURE([NetRevenue]),SELECTEDMEASURE()*0.9,SELECTEDMEASURE()). Its two branches define revenue and non-revenue behavior. The reference queries expand those branches for named measures, so their expected results do not depend on a hidden configured group.

Concepts to explain in your own words: **calculation group**, **SELECTEDMEASURE**, **ISSELECTEDMEASURE**, **applicability**, **reuse**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

### Feature and version boundary

Calculation groups require a supported semantic model and compatibility level 1500 or higher according to the reviewed Microsoft documentation. This lesson teaches definitions and explicitly expanded calculations offline; it does not create a calculation group in an engine.

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
    MEASURE Sales[QuantitySold] = SUM ( Sales[Quantity] )
```

### Case A: Current measures before an item

**Starting context:** No calculation item applied; baseline measure definitions.

```dax
EVALUATE ROW ( "Revenue", [NetRevenue], "Units", [QuantitySold] )
```

**Context trace:**

1. The eligible Sales rows total 187 USD.
2. Their quantities total 17 units.
3. These quantities have different units and transformation policies.

**Hand-derived worked-reference result:**

| Revenue | Units |
| --- | --- |
| 187 | 17 |

A shared visual can contain both measures without implying that every calculation item should transform them identically.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Expanded guarded fee item

**Starting context:** Algebraic expansion of the named revenue-only item; no live calculation-group execution.

```dax
EVALUATE ROW ( "RevenueAfterFee", [NetRevenue] * 0.9, "UnitsUnchanged", [QuantitySold] )
```

**Context trace:**

1. The revenue branch multiplies 187 by 0.9, giving 168.3.
2. The guard leaves the quantity measure at 17.
3. The transformation changes a defined revenue policy, not the observed transaction counts.

**Hand-derived worked-reference result:**

| RevenueAfterFee | UnitsUnchanged |
| --- | --- |
| 168.3 | 17 |

An expanded query is a useful semantic reference. It does not establish that a particular external model's group selection, precedence or formatting is configured correctly.

Hand-derived algebraic expansion of a specified calculation item. No calculation group was created or executed in this classroom.

## A deeper model or scope review

A calculation-item definition is a different artifact from a full query:

```dax
IF ( ISSELECTEDMEASURE ( [NetRevenue] ), SELECTEDMEASURE() * 0.9, SELECTEDMEASURE() )
```

This expression belongs in a named calculation item in a separately prepared model. The offline reference expands it for two known measures; it does not install metadata or imply an external account is required for study.

## Progressive hints

2. The transformation would also apply to quantities.
3. Use SELECTEDMEASURE only in the correct model scope.
4. The placeholder requires a calculation-item context.
5. Selection behavior is model- and feature-dependent.
6. Not every measure should necessarily receive a date shift.
