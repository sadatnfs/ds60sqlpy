Validation and release readiness#

Validate the exact revision being shipped. Configuration, structural checks, unit tests, real runtime execution and browser behavior answer different questions. A passing parser does not prove a lesson runs, and a configured workflow does not prove that its hosted jobs passed.

Run commands from the repository root. Keep learner projects and their Docker volumes separate from disposable validation projects. Use the current workflow run and its artifacts as evidence for that revision, rather than copying old machine timings or test counts into documentation.

Prepare a development environment#

The supported product is the Linux-container Docker classroom. Windows runs through WSL 2; macOS uses its engine's Linux environment. Native Windows backends and native executable bundles are outside the release support matrix.

Maintainers running contributor checks on Linux or WSL 2 also need Python 3.12, the locked development dependencies and Node.js. The workflow uses Node 24 for the framework-free UI checks. Python 3.11 remains a supported core validation target; inspect .github/workflows/ci.yml for the exact matrix.

With uv installed:

uv lock --check
uv sync --frozen --extra notebooks --extra data --extra bridge --extra quality --extra professional --extra sql-notebooks --extra mcp
uv run --no-sync python scripts/course.py doctor

Prefix the Python commands below with uv run --no-sync, or use the interpreter inside this checkout's .venv. On Windows, WSL 2 provides the same Bash, Linux Python environment and Docker workflow. Historical native setup recipes are unsupported compatibility references, not alternate release requirements.

Core setup does not install every heavy learning dependency. A test that needs an optional compiler, framework, SQL service or model asset must either run in its prepared environment or report that boundary explicitly.

Repository formatting#

Run ./scripts/format-repo to apply maintained code style, or ./scripts/format-repo --check to report drift without editing tracked source. Make exposes the same commands as make format and make format-check. ./scripts/lint-repo (or make lint) adds read-only static source checks using the same toolchain. make check requires both formatting and lint checks. These commands use a dedicated Docker toolchain on Linux, macOS and Windows through WSL 2. The first invocation builds that tool image; later invocations reuse it. --build explicitly rebuilds it, and --list reports covered files. Classroom containers and learner volumes are not part of this operation.

Use a repeated --language selection for focused iteration and the unfiltered check before submission. Follow the contributor formatting workflow for generated-source ownership and optional pre-commit installation. Formatting checks and execution checks are separate evidence: still compile/run changed examples and inspect lesson rendering when either may be affected.

Fast checks during development#

Run the narrow tests for the changed area first, then verify the maintained source and generated views:

python scripts/build_catalog.py
python scripts/course.py validate
python scripts/audit_practice.py
python scripts/audit_lesson_depth.py

node scripts/check_classroom_ui.mjs
python -m ruff check src scripts tests bridge python/professional docker/init_module_runtime.py
./scripts/format-repo --check

normalize_lesson_prose.py is a dry check by default. When deliberately refreshing reviewed prose, run it with --write after authoring generators and before HTML generation. check_content_rendering.py renders the actual published Markdown and notebooks, checking mathematics and code blocks through the production reader. A generic Markdown parser is not a substitute.

After an intentional content change, regenerate the catalog, reports and readers with make generate, or run that target's listed Python commands when Make is unavailable. Review the generated diff. Never hand-edit maintained HTML to hide source drift. The journey preview is a developer design archive; the live /classroom, /learn and /journeys URLs use one shared interface.

The secret scanner reports categories and locations without copying suspected credentials into logs. It checks the current tree and reachable Git history. Keep private progress, work directories, caches and environment files out of source control and release archives. Source cleanup does not remove material already published in Git history; historical findings require a separate reviewed response.

Run tests in parallel#

Use four grouped workers by default:

python -m pytest -n 4 --dist loadgroup

The equivalent Make targets are:

make test
make test TEST_WORKERS=2
make test-serial

Keep --dist loadgroup. Tests that use the same disposable PostgreSQL fixtures belong to the shared-postgres group and run serially within that group. The suite rejects unsafe distribution when those shared fixtures are enabled. Changing the scheduler can cause destructive fixture races even if individual tests pass. Use -n 0 for focused serial diagnosis, and reduce worker count on machines with little memory. More workers do not guarantee shorter runtimes.

Record the passed, failed and skipped totals from the actual run. Explain skips by surface, such as an optional framework, a live database or historical native-platform compatibility tests outside the supported matrix. Do not describe a skipped platform as validated.

What hosted workflows check#

The workflow files are the executable source of truth. Routine validation uses read-only repository permissions, pinned action revisions and local image builds. The separate, opt-in image publication workflow requires manual dispatch, successful CI for the exact revision, deliberate repository enablement and protected credentials before it can publish. Linux core jobs use UTF-8 and create their test workspace before starting four grouped pytest workers. Native Windows ACLs, PowerShell backend diagnostics and native executable bundles are not release gates. Windows Docker wrappers remain supported entrypoints into WSL 2.

The Docker groups cover Python Core, C, C++, Go, C#, Rust, Swift, Java, JavaScript/TypeScript, PHP, Scala/Spark, TensorFlow and PyTorch. The Core group runs the statistics book, NLP and compatible LLM examples once; the framework groups execute their own TensorFlow, PyTorch and LLM references. PySpark and tutorial example variants are discovered from the same catalog used by the classroom. There is no second hand-maintained lesson list. Reading/manual lessons and owned-cluster operations appear as explicit exclusions from the ordinary corpus, never successful runs. CUDA CPU models and the selected CPU framework/Spark variants run in those ordinary groups. Optional NVIDIA profiles remain explicitly excluded: CPU execution, compiler-only acceptance and GPU device execution require separate receipts.

Each group owns a disposable project. At most four Docker groups run together, and each worker executes one reference at a time. The corpus records failures, source hashes, actual exit status and typed checks where registered. An overall time budget leaves unexecuted cases visibly pending and fails the job. Artifact JSON distinguishes reference execution from independent typed verification. Negative probes restore the previous source and notes, and container replacement checks read the original successful receipts without replay.

Chromium runs only in a separate CI browser environment with hash-locked packages. It is absent from the production image. Browser reports contain check results and screenshots, without session credentials or network traces. The separate Kubernetes workflow prepares checksum-verified host tools and a short-lived owned cluster, checks all supported reference manifests and cleanup behavior, then releases only its recorded resources. Optional pretrained-model downloads and external services remain outside these offline qualification paths.

A Linux hosted Docker result does not establish Windows WSL installation, macOS engine setup, another CPU architecture, GPU support or every rootless engine configuration. Check the actual matrix architecture and receipt before making a release claim. Historical native-platform results do not add supported product targets or create release requirements.

To run the workflows manually, open the repository's Actions tab, select Course validation, Application builds or Owned Kubernetes runtime, choose Run workflow, and select the revision to validate. With an authenticated GitHub CLI:

gh workflow run ci.yml --ref BRANCH_NAME
gh workflow run app-build.yml --ref BRANCH_NAME
gh workflow run kubernetes.yml --ref BRANCH_NAME

The manual Course validation run includes the Linux advanced-imports job. Keep its evidence attached to the same revision as the Docker and source-ZIP checks. Repository settings can disable workflows for private fork pull requests; a pull_request trigger does not override that access policy.

Read failed job logs and uploaded test results. A workflow syntax check is useful before pushing, but only a hosted run can establish hosted acceptance.

Optional documentation-only CI skip#

For a push containing only prose and its regenerated readers, the native [skip ci] commit-message token skips push and pull_request workflows. Use the space; [skip-ci] is not a supported native token. No YAML gate or custom alias is required. Follow the commit example and push boundary.

Before that commit, use the prepared contributor environment to regenerate and check the documentation locally:

make generate
python scripts/normalize_lesson_prose.py
python scripts/check_content_rendering.py
python scripts/check_published_links.py
git diff --check

Review the whole push: executable lesson examples, tests, runtime code, configuration, dependencies and workflows require normal CI. Never hide an unvalidated implementation commit behind a marked documentation commit. Scheduled/manual runs are unaffected; existing runs are not cancelled. Required PR checks may remain Pending and prevent merging. Trigger normal checks with an unmarked follow-up commit, or use a manual run only if the repository's required-check policy accepts it. A skipped run is not passing CI evidence. GitHub documents the event and required-check behavior.

Exercise the Docker product on disposable data#

Create a new project name that has never held learner work. For example, on macOS, Linux or Windows through WSL 2:

./classroom --rebuild --all --project ds60-release-check --no-browser

The explicit --rebuild qualifies current source rather than silently resuming an older image with the same tag. --all selects the full ordinary worker set even if this disposable project previously saved a smaller selection. For a focused check, replace --all with the required --profile options. Source updates do not take effect merely because a default resume succeeds.

Use the exact URL printed by that launcher, or read .classroom/ds60-release-check/classroom.url. The following commands write test pads and reset the course SQL fixture, so replace CLASSROOM_URL only with that disposable project's loopback URL:

python scripts/check_lab_http.py --url CLASSROOM_URL --confirm-disposable --reset-sql
python scripts/check_classroom_profiles.py --url CLASSROOM_URL --confirm-disposable --profiles "python-core cpp20 java21 javascript-node typescript-node tensorflow-cpu llm-torch-cpu scala-jvm spark-local-scala spark-local-python c17 go csharp-dotnet rust-stable swift-linux php-cli" --report work/release-runtime-receipts.json

To run the complete admitted module corpus for selected prepared profiles:

python scripts/check_module_references.py --url CLASSROOM_URL --confirm-disposable --profiles "python-core cpp20" --report work/module-reference-results.json
python scripts/check_classroom_failures.py --url CLASSROOM_URL --confirm-disposable --profiles "python-core cpp20" --check-timeout --report work/runtime-failures.json

The first command executes every selected module reference, including applicable book examples and variants. The second deliberately submits invalid code and a real 15-second Python timeout, checks diagnostics and recovery, and restores the prior source. These commands still need disposable state. --list-only on the corpus checker produces the inventory report without HTTP or execution; omit --url and --confirm-disposable in that mode.

The profile checker runs cataloged reference source through the authenticated classroom and records source-bound results. It does not declare every lesson execution-verified from one representative program. For changed runtime or lesson code, also run the relevant full reference corpus and its boundary/failure cases. Compile errors, runtime errors, timeouts and successful execution must remain distinct results.

Replace the disposable project's containers while retaining its volumes, then run both checks in persistence mode against the newly printed URL:

python scripts/check_lab_http.py --url CLASSROOM_URL --confirm-disposable --check-persistence
python scripts/check_classroom_profiles.py --url CLASSROOM_URL --confirm-disposable --profiles "python-core cpp20 java21 javascript-node typescript-node tensorflow-cpu llm-torch-cpu scala-jvm spark-local-scala spark-local-python c17 go csharp-dotnet rust-stable swift-linux php-cli" --report work/release-runtime-receipts.json --check-persistence

Persistence verification must read the original receipt rather than rerun code to recreate the expected result. A saved result belongs to its source, lesson, language and SQL mode. Receipt-storage failure after successful execution must not trigger an automatic replay.

After validation, stop only the test project with:

./classroom stop --project ds60-release-check

Removing named volumes is a separate destructive action. Never use a global volume prune as part of a learner-facing cleanup procedure.

Browser acceptance#

The Python Core Docker job runs scripts/check_classroom_browser.py against its actual classroom after persistence checks. For a prepared Linux x86_64 Python 3.12 browser environment, install requirements/ci-browser.lock, install Chromium with python -m playwright install --with-deps chromium, then run:

python scripts/check_classroom_browser.py --url CLASSROOM_URL --confirm-disposable --report work/browser-receipts.json

Use --fixtures-only --report work/browser-fixtures.json to execute just the isolated JavaScript browser references. A unit test of the probe's helpers is not a substitute for this real Chromium run. The browser probe writes its own disposable pads and progress; do not point it at a learner workspace.

Use a separate browser profile and disposable classroom state for checks that edit code or notes. Inspect the actual running page at desktop and narrow widths, in light and dark modes, using keyboard navigation as well as a mouse.

The web-development checks exercise all 30 HTML reference pages, real script lifecycle and module behavior, opaque-origin isolation, HTML/CSS and browser JavaScript/D3 live updates, viewport controls, focus, pause/stop and explicit observation saving:

python courses/web-development/authoring/check_browser.py --url CLASSROOM_URL --confirm-disposable --report work/web-browser-receipts.json
python courses/web-development/authoring/check_live_preview.py --url CLASSROOM_URL --confirm-disposable --report work/live-preview-receipts.json

Run them before the full D3 checker because both use some D3 lesson workspaces. Automatic preview updates must create no saved-run receipts. A manual run or explicit observation save records the exact submitted source. These client observations are not independent server verification. The separate PHP HTTP fixture qualifies cookies, sessions, CSRF handling and persistence through real requests; PHP CLI success alone does not establish those behaviors.

Check these user journeys:

  • Open the common home, search for a subject, choose a lesson and switch subjects.
  • Follow guide/reference links, render equations and code, and avoid raw source pages or broken anchors.
  • Edit a Python pad, run it, see readable stdout and a plot, then return after a page reload and verify the source, notes and saved result.
  • Run both SQL snippet and whole-lesson modes against the disposable database; preserve their separate drafts and result histories.
  • Compile and run a C++ or Java example and a TypeScript example. Deliberately introduce a small compiler error and verify that the diagnostic is truthful.
  • Open an older result without replacing the current pad. Switch lessons while a result loads and verify that late responses stay in their original context.
  • Confirm a reading-only lesson explains its capability and does not advertise execution. Tutorial read markers must not imply tested mastery.
  • Confirm focus, contrast, navigation labels, mobile layout and local asset loading. No runtime CDN should be needed for math or highlighting.

Also inspect START_HERE.html as a separate static reading mode. Static browser progress and server-backed classroom progress have different storage boundaries. Unit and DOM tests supplement this review; they do not replace it.

Notebook, SQL and optional-runtime boundaries#

python scripts/validate_notebooks.py checks structure. Add --smoke for the selected dependency-light execution set. Heavy training, external assets and SQL magic cells require their own declared environments. Keep executed copies under ignored artifacts/, and keep source notebooks free of incidental output.

Live SQL tests require the exact local disposable advanced_sql_training database. The environment opt-ins are documented in the fixtures and hosted PostgreSQL job. Never aim reset commands at a production or shared database. Use psql -X -v ON_ERROR_STOP=1; the Day 52 to 54 warehouse sequence is the explicit stateful exception to otherwise independent rollback-safe lessons.

The optional MCP tests use the actual stdio protocol and read-only defaults. They verify discovery, bounded content reads, explicit solution reveal and opt-in progress behavior. They do not call a hosted model or measure teaching quality. See MCP tutoring.

Compiler/framework reference tests must identify the prepared profile, actual source and observed result. A Dockerfile, installed dependency, parse-only check or old image hash is not current execution evidence. Preserve truthful historical receipts, but attach fresh evidence when executable source changes.

Release decision#

Before shipping, record the exact revision, generation drift result, quality checks, test totals and skipped surfaces, runtime receipts, browser observations, archive contents and supported-platform evidence. Verify no learner state or private configuration entered the package. Explain unresolved failures before publishing; do not rename them as expected skips.

Useful result labels are structure validated, representative behavior executed, complete artifact executed, offline verified after setup, and not validated on this platform. Use the narrowest label supported by the evidence. No finite test suite establishes that software has no bugs.

D3 and new systems-language qualification#

The ordinary reference corpus discovers C17, Go, C#, Rust and Swift programs from their manifests and runs them in their packaged Linux workers. The profile smoke gate uses an actual catalog reference and its observed completion marker; the failure gate requires the real staged filename and compiler diagnostic. Rust Arrow dependencies are prepared in the image. Ad hoc Cargo, NuGet or Go module downloads are not part of a lesson Run. Swift Apple UI projects remain explicitly outside the Linux compiler contract.

D3 uses a separate browser runtime and is excluded from ordinary worker corpus execution. In the prepared browser environment, run:

python scripts/check_d3_browser.py --url CLASSROOM_URL --confirm-disposable --report work/d3-browser-receipts.json

The checker submits all 24 references through the real classroom pad and Run button. It verifies chart output, source-bound saved client observations, keyboard controls, actual pointer brushing and wheel zoom, filtering, fresh browser-session persistence, history without rerun, failure/recovery, opaque origin/CSP isolation and stale-frame navigation. These results remain browser observations with verified: false, no process return code and no worker checks. The checker does not relabel browser output as independent server verification. The Python Core Docker CI group executes it after container replacement.

The Docker study subject is reading/manual practice. Its optional fixture uses an explicitly owned host project; it never mounts the engine socket into the classroom. Deep Kubernetes networking fixtures are also reading/manual unless the exact advanced capability was separately prepared and qualified. Run python courses/kubernetes/fixtures/networking/check_fixtures.py for offline consistency only. An offline pass does not prove NetworkPolicy enforcement, load-balancer provisioning, Gateway routing or dual-stack traffic.

After the D3 execution report is complete, replace the same disposable Core project's containers while retaining volumes, then use the newly printed URL:

python scripts/check_d3_browser.py --url CLASSROOM_URL --confirm-disposable --report work/d3-browser-receipts.json --check-persistence

This phase reads the original observation IDs and compares complete-record, source and output hashes, plus the final saved source/note hashes for every D3 lesson. It does not launch a browser, rerun code or write learner state. The report retains the original execution evidence and appends the readback result. The invoker must actually perform container replacement; a second read against the same process alone does not prove replacement durability. The Python Core CI job supplies that explicit down/up boundary after its D3 run.
