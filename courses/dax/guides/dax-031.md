## The question and the mechanism

Distinguish calendar coverage, observed facts and data-availability boundaries.

A Date dimension contains calendar members, including days with no sales. A list of distinct OrderDate values contains only days on which facts were recorded. Using the latter as a calendar confuses the absence of an event with the absence of a date, and can change time-window denominators or break classic time-intelligence assumptions.

The course Date fixture has one unique, nonblank date for every day of 2024 and 2025. The model contract marks that Date column for classic time intelligence. January 2025 therefore has 31 calendar rows even though sales occur on only January 2,3 and 5. A zero-sales day remains a date that can belong in an average or rolling interval.

Calendar extent is not the same as observation completeness. This fixture declares sales observation through 2025-02-28; dates later in the calendar do not imply those periods were observed. A future blank cell should not automatically become zero demand. Track the available-data boundary separately from the maximum date in the dimension.

## Vocabulary and expression anatomy

Case A compares calendar dates with distinct fact dates under the same month selection. Case B looks at a known observed date with no sale. The date row exists and the fact result is empty. A complete Date table is a model requirement, not a claim that every day has an event.

Concepts to explain in your own words: **date table**, **calendar grain**, **missing dates**, **mark as date table**, **coverage**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: January calendar versus event dates

**Starting context:** January 2025, active OrderDate relationship; observed coverage includes the full month.

```dax
EVALUATE CALCULATETABLE ( ROW ( "CalendarDates", COUNTROWS ( 'Date' ), "OrderDatesWithSales", DISTINCTCOUNT ( Sales[OrderDate] ) ), 'Date'[Year] = 2025, 'Date'[MonthNumber] = 1 )
```

**Context trace:**

1. The complete Date table contains January 1 through 31.
2. Sales occur on January 2,3 and 5.
3. The calendar count is 31 while observed event-date count is 3.

**Hand-derived worked-reference result:**

| CalendarDates | OrderDatesWithSales |
| --- | --- |
| 31 | 3 |

A sales-day average and a calendar-day average use different denominators. Neither should be called a generic daily average without that qualification.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: A date exists without a sale

**Starting context:** 2025-01-04 is inside declared observation coverage but has no OrderDate fact.

```dax
EVALUATE CALCULATETABLE ( ROW ( "CalendarDates", COUNTROWS ( 'Date' ), "SalesRows", COUNTROWS ( Sales ), "Revenue", [NetRevenue] ), 'Date'[Date] = DATE ( 2025, 1, 4 ) )
```

**Context trace:**

1. The Date selection contains one valid date.
2. No Sales row has OrderDate 2025-01-04.
3. The fact count and revenue are BLANK; the calendar row is not missing.

**Hand-derived worked-reference result:**

| CalendarDates | SalesRows | Revenue |
| --- | --- | --- |
| 1 | BLANK | BLANK |

If this were beyond observation coverage, the same blank visual appearance would need a different interpretation. Availability metadata prevents that ambiguity.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. The fixture includes a leap year.
2. One sale was ordered that day.
3. Separate uniqueness, completeness, type and extent.
4. The dimension extends through December 2025.
5. Future dates can be present without observed outcomes.
6. A business calendar is a declared population, not simply observed event days.
