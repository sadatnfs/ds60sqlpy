# go-033: Repository interfaces and transaction failure policy

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-032

## Learning objectives

Model a repository transaction that commits valid changes, rolls back failures and keeps retries idempotent. Along the way, explain transaction, repository boundary, unknown outcome; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A repository boundary separates business operations from database mechanics. The application should describe the transaction it needs, while an adapter manages SQL parameters, context cancellation, row scanning and commit or rollback. In database/sql, a DB is a connection pool rather than one connection. A Tx reserves a transaction context whose operations must all use that Tx. Calling the outer DB halfway through a transaction can escape its atomicity. This lesson uses a small copy-on-write transactional model to test policy offline. It is explicitly not evidence about PostgreSQL isolation, driver behavior or network failure. Those require a prepared database integration test.

## Vocabulary and concepts

- **Transaction:** A group of changes committed or rejected as one unit.
- **Repository boundary:** An application-facing data access contract.
- **Unknown outcome:** A state where failure to observe success does not prove work failed.

## Syntax anatomy and reasoning

A callback receiving a transaction-local value can stage changes before committing them to the outer state. An error aborts the staged changes. In a real database/sql adapter, begin with BeginTx(ctx, options), defer Rollback, execute parameterized statements through tx, and inspect Commit errors. SQL syntax and placeholder conventions depend on the selected driver. Never construct SQL by interpolating untrusted values. A transaction whose commit outcome is unknown cannot safely be replayed without an idempotency contract.

## Worked example / walkthrough

### Worked example 1: Commit a valid change

Transfer 3 between balances 5 and 5 in a staged transaction.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Balances struct{ A, B int }

func transact(s *Balances, f func(*Balances) error) error {
	copy := *s
	if err := f(&copy); err != nil {
		return err
	}
	*s = copy
	return nil
}

func main() {
	// Commit a valid change
	{
		s := Balances{A: 5, B: 5}
		err := transact(&s, func(t *Balances) error { t.A -= 3; t.B += 3; return nil })
		check(err == nil && s.A == 2 && s.B == 8, "commit")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The committed balances are 2 and 8.

The outer state changes only after the callback succeeds. This proves the local model policy, not database atomicity.

### Worked example 2: Rollback an explicit failure

Change staged state and return an error.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Balances struct{ A, B int }

func transact(s *Balances, f func(*Balances) error) error {
	copy := *s
	if err := f(&copy); err != nil {
		return err
	}
	*s = copy
	return nil
}

func main() {
	// Commit a valid change
	{
		s := Balances{A: 5, B: 5}
		err := transact(&s, func(t *Balances) error { t.A -= 3; t.B += 3; return nil })
		check(err == nil && s.A == 2 && s.B == 8, "commit")
	}

	// Rollback an explicit failure
	{
		s := Balances{A: 5, B: 5}
		err := transact(&s, func(t *Balances) error { t.A = 0; return errors.New("reject") })
		check(err != nil && s.A == 5, "rollback")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The outer balances remain unchanged.

A staged mutation is not a committed mutation. The distinction is visible because the model uses a separate value copy.

## Exercises

### Exercise 1: Commit a valid change: change one input

Copy worked example 1, change `s := Balances{A: 5, B: 5}` to `s := Balances{A: 6, B: 5}` and predict the failure before running; then restore the line.

**Expected:** The edited run panics with `commit` because `err == nil && s.A == 2 && s.B == 8` no longer holds.

**Verify:** Restoring `s := Balances{A: 5, B: 5}` makes the check pass again with the worked observation: the committed balances are 2 and 8.

### Exercise 2: Rollback an explicit failure: debug a regression

A one-token regression in worked example 2 makes a line read `s := Balances{A: 6, B: 5}`. Repair it without changing the check.

**Expected:** The defective run panics with `rollback`; after restoring `s := Balances{A: 5, B: 5}`, the outer balances remain unchanged.

**Verify:** The failing run shows message `rollback`; after the repair `err != nil && s.A == 5` holds again.

### Exercise 3: Reject invalid funds

Attempt a transfer larger than available balance.

**Expected:** The state remains 5 and 5.

**Verify:** Your solution must keep `err != nil && s.A == 5 && s.B == 5` true. Control: changing `s := Balances{A: 5, B: 5}` to `s := Balances{A: 6, B: 5}` panics with message `funds`; revert it.

### Exercise 4: Preserve total value

Apply two successful transfers and inspect the combined balance.

**Expected:** The total remains 10.

**Verify:** Your solution must keep `s.A+s.B == 10` true. Control: changing `check(s.A+s.B == 10, "total")` to `check(s.A-s.B == 10, "total")` panics with message `total`; revert it.

### Exercise 5: Keep a failed retry distinct

Fail one transaction, then explicitly start a new valid transaction.

**Expected:** Only the second change commits.

**Verify:** Your solution must keep `transact(&s, func(t *Balances) error { t.A--; t.B++; return nil }) == nil && s.A == 4` true. Control: changing `s := Balances{A: 5, B: 5}` to `s := Balances{A: 6, B: 5}` panics with message `retry`; revert it.

### Exercise 6: Transfer no-op semantics

Run a transaction that changes nothing.

**Expected:** The state is preserved and the operation succeeds.

**Verify:** Your solution must keep `err == nil && s.A == 5 && s.B == 5` true. Control: changing `s := Balances{A: 5, B: 5}` to `s := Balances{A: 6, B: 5}` panics with message `no-op`; revert it.

## Common pitfalls and diagnosis

The classic transaction bug is mixing handles: starting a Tx and then calling the outer DB for one statement, which runs outside the transaction and survives a rollback. Another is ignoring the Commit error. If Commit fails or the connection drops during it, the outcome may be unknown, so a blind retry can apply a change twice. Use idempotency keys or a read-back check there.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Commit a valid change: change one input

1. Restate the expected observation: The committed balances are 2 and 8.
2. transact copies the state and assigns it back on success. What are A and B afterward?
3. Starting A at 6 commits A=3, so `s.A==2` fails while B is still 8. The transaction works; the initial balance changed.

### Hint for investigation 2: Rollback an explicit failure: debug a regression

1. Restate the expected observation: The outer balances remain unchanged.
2. The function edits the copy and returns an error. Is the outer value replaced?
3. Starting A at 6 means the rollback correctly keeps 6, so `s.A==5` fails. Restore the initial 5; the failing function still leaves the state untouched.

### Hint for investigation 3: Reject invalid funds

1. Restate the expected observation: The state remains 5 and 5.
2. The guard fails before any change. What do both balances remain?
3. Validate the invariant in the same transaction that applies the change.

### Hint for investigation 4: Preserve total value

1. Restate the expected observation: The total remains 10.
2. Each transfer moves one unit between fields. Does the sum change?
3. The invariant relates both fields.

### Hint for investigation 5: Keep a failed retry distinct

1. Restate the expected observation: Only the second change commits.
2. The failed attempt never assigns back. From which A does the second start?
3. This retry is safe because the first local model outcome is known.

### Hint for investigation 6: Transfer no-op semantics

1. Restate the expected observation: The state is preserved and the operation succeeds.
2. A function returning nil with no edits still commits. What is the state?
3. Idempotent no-op behavior is useful, but it does not automatically make arbitrary external side effects replay-safe.
