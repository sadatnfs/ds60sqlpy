c-013: Preprocessing, macros and compile-time contracts#

Level and prerequisites#

Beginner, approximately 90 minutes plus a later retrieval session. Direct prerequisites: c-012

Learning objectives#

Explain macro expansion, repeated evaluation, compile-time assertion. Implement the six investigations with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

Purpose and mental model#

The preprocessor transforms tokens before the compiler performs ordinary type checking. Header inclusion, conditional compilation and macros can be useful, but a macro is not a normal function. Its arguments may be substituted more than once, and missing parentheses can change expression grouping. Side-effecting arguments such as increments are therefore hazardous in many function-like macros. Prefer typed functions or static inline functions for behavior when possible. Use macros for configuration and declarations that need preprocessing, and keep conditional platform code small and documented. The same source should not silently change semantic contracts because a build flag was forgotten.

Vocabulary and concepts#

  • Macro expansion: Token replacement before ordinary compilation.
  • Repeated evaluation: An argument expression being executed multiple times after substitution.
  • Compile-time assertion: A condition required for successful translation.

Syntax anatomy and execution trace#

#define creates a macro replacement. Parenthesize each expression argument and the full result, but understand that this does not prevent repeated evaluation. #if and #ifdef select tokens before compilation. Include guards prevent repeated header definitions. _Static_assert checks a constant expression during compilation. _Generic can select an expression by type in C11 and later without becoming a runtime type system.

Worked example / walkthrough#

Worked example 1: Use a parenthesized macro safely#

Square the side-effect-free expression 2+3.

#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

#define SQUARE(x) ((x) * (x))
#define LESSON_CAPACITY 8
#define TYPE_LABEL(x)                                                          \
  _Generic((x), int: "integer", double: "floating", default: "other")
int square_int(int value) { return value * value; }

int main(void) {
  /* Use a parenthesized macro safely */
  {
    CHECK(SQUARE(2 + 3) == 25);
  }
  puts("Worked example checks passed.");
  return 0;
}

Observe: The result is 25.

Parentheses preserve grouping. This macro still evaluates its argument twice, so side effects remain inappropriate.

Worked example 2: Prefer a typed helper for mutation#

Pass value++ to a normal square function.

#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

#define SQUARE(x) ((x) * (x))
#define LESSON_CAPACITY 8
#define TYPE_LABEL(x)                                                          \
  _Generic((x), int: "integer", double: "floating", default: "other")
int square_int(int value) { return value * value; }

int main(void) {
  /* Use a parenthesized macro safely */
  {
    CHECK(SQUARE(2 + 3) == 25);
  }

  /* Prefer a typed helper for mutation */
  {
    int value = 3;
    int result = square_int(value++);
    CHECK(result == 9 && value == 4);
  }
  puts("Worked example checks passed.");
  return 0;
}

Observe: The result is 9 and value increments once to 4.

A function argument expression is evaluated once for this call. SQUARE(value++) would create an unsequenced modification hazard.

Common pitfalls and diagnosis#

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
