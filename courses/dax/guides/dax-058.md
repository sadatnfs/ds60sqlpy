## The question and the mechanism

Produce a reviewable commercial metric specification with explicit populations and adjustment policies.

An integrated commercial model needs more than a large final revenue formula. Define the grain, currency, date role and adjustment policy for each input. Our core Sales are USD amounts after line discounts. Returns records monetary refunds linked to SaleID; this fixture attributes those refunds to the original sale's date, not an unprovided return-event date. ForeignSales is a separate population requiring explicit conversion.

Core sales total 187 and refunds total 13, giving adjusted core revenue 174. The foreign transaction fixture converts to 270 USD under its transaction-date rate policy. These are distinct named populations. Do not combine them with a budget unless the budget's scope includes both and source identities establish that no transaction is duplicated.

The supplied Budget covers the core Paper/Home categories in January and February 2025. Core actuals in that scope are 123 before refunds and 114 after the nine-dollar refund attributed to S4. The compatible budget is 165, giving an adjusted-revenue variance of-51. This does not establish accounting profit, inventory restatement or tax treatment, which require additional data and policy.

## Vocabulary and expression anatomy

The reference composes named measures for refund attribution, adjusted core revenue and converted foreign amounts. The relationship Sales->Returns propagates the original sale's dimension/date context. Budget remains disconnected and is matched explicitly by month and category. The two cases expose component totals before reporting a variance.

Concepts to explain in your own words: **commercial model**, **refund attribution**, **currency conversion**, **budget grain**, **reconciliation**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
    MEASURE Sales[QuantitySold] = SUM ( Sales[Quantity] )
    MEASURE Sales[GrossRevenue] = SUMX ( Sales, Sales[Quantity] * Sales[UnitPrice] )
    MEASURE Sales[OrderCount] = DISTINCTCOUNT ( Sales[OrderID] )
    MEASURE Sales[RefundsAttributedToSale] = COALESCE ( SUM ( Returns[Refund] ), 0 )
    MEASURE Sales[AdjustedCoreRevenue] = [NetRevenue] - [RefundsAttributedToSale]
    MEASURE ForeignSales[ConvertedUSD] = SUMX ( ForeignSales,
        ForeignSales[LocalAmount] * LOOKUPVALUE ( ExchangeRate[USDPerUnit],
            ExchangeRate[RateDate], ForeignSales[SaleDate],
            ExchangeRate[Currency], ForeignSales[Currency] ) )
```

### Case A: Reconcile named monetary populations

**Starting context:** Analytics model; complete supplied refund and rate fixtures; core and foreign populations are reported separately.

```dax
EVALUATE ROW ( "CoreNetSales", [NetRevenue], "RefundsAttributedToSales", [RefundsAttributedToSale], "AdjustedCoreRevenue", [AdjustedCoreRevenue], "SeparateForeignUSD", [ConvertedUSD] )
```

**Context trace:**

1. Core line discounts are already included in NetAmount, whose total is 187.
2. Refunds 4 and 9 total 13; adjusted core revenue is 174.
3. Foreign amounts convert to 100 +110 +60 =270 USD under their separate policy.

**Hand-derived worked-reference result:**

| CoreNetSales | RefundsAttributedToSales | AdjustedCoreRevenue | SeparateForeignUSD |
| --- | --- | --- | --- |
| 187 | 13 | 174 | 270 |

Showing components makes double subtraction and population mixing visible. The foreign number is not silently added to a core-only budget comparison.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Compare an aligned two-month core population

**Starting context:** FullJanuary/February 2025, Paper/Home core sales, refunds attributed to original sale dates; Budget covers exactly that month/category scope.

```dax
EVALUATE CALCULATETABLE ( VAR Target = CALCULATE ( SUM ( Budget[Amount] ), TREATAS ( VALUES ( 'Date'[MonthKey] ), Budget[MonthKey] ), TREATAS ( VALUES ( Product[Category] ), Budget[Category] ) ) RETURN ROW ( "CoreBeforeRefund", [NetRevenue], "Refunds", [RefundsAttributedToSale], "AdjustedCore", [AdjustedCoreRevenue], "Budget", Target, "Variance", [AdjustedCoreRevenue] - Target ), 'Date'[Year] = 2025, 'Date'[MonthNumber] IN { 1, 2 }, Product[Category] IN { "Paper", "Home" } )
```

**Context trace:**

1. Core 2025 sales in these months total 123.
2. Only the refund linked to S 4 belongs to that sale-date population, subtracting 9.
3. The four compatible budget rows total 165;114 -165 =-51.

**Hand-derived worked-reference result:**

| CoreBeforeRefund | Refunds | AdjustedCore | Budget | Variance |
| --- | --- | --- | --- | --- |
| 123 | 9 | 114 | 165 | -51 |

A return-date report could differ, but this fixture does not contain ReturnDate. The correct conclusion is to state the limitation, not invent another temporal attribution.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.
