js-018: A reliable command-line data tool#

Level and prerequisites#

Intermediate, approximately 90 minutes. Direct prerequisites: js-017

Learning objectives#

Explain cli contract, ndjson, failure atomicity, process boundary with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Send two rows worth 250 and 300 cents to the CLI. The final task tests enforce an input budget before retaining all data.

Purpose and mental model#

A reliable command-line program has an input contract, an output contract and a failure contract. Arguments select behavior, standard input supplies data, standard output carries machine-readable results, and standard error carries diagnostics. Exit status lets another process distinguish successful completion from invalid input or operational failure without parsing prose. Mixing a friendly banner into JSON stdout can break a downstream consumer even though a human finds the output readable.

The capstone is a small offline order aggregation tool. It accepts only --sum, reads bounded newline-delimited JSON from stdin, validates each row and rejects duplicate ids, then prints one JSON result. Blank lines are ignored under an explicit policy. Quantities and prices use safe integer units. It emits no partial aggregate on an invalid row, so a consumer cannot accidentally use an incomplete result as if it covered all input.

The reference launches the actual CLI as a fresh Node process with fixed arguments, bounded input, a timeout and separate stdout/stderr. All source files live in an owned temporary directory. Tests exercise successful totals, invalid arguments, malformed input, duplicates, empty input and the byte cap. This is a small single-process tool, not a general CSV parser, database transaction or production ingestion service. Later typed and streaming chapters extend the same separation of pure transformation and process I/O.

Vocabulary and concepts#

CLI contract: The documented arguments, input format, outputs and exit behavior.

NDJSON: One independent JSON value per nonblank line under this fixture policy.

Failure atomicity: No partial successful result is exposed when an input fails validation.

Process boundary: The interface between a program and its caller through arguments, streams and exit status.

How to run this lesson#

Use the prepared Node 24.22.1 profile. The classroom saves an ES module as main.mjs and executes it with Node. Only built-in Node or ECMAScript APIs are used. For a prepared native environment, node main.mjs is the same command on PowerShell and POSIX. Browser APIs have separate host requirements.

Save your own learner copy under ignored .learning/expansion/js-018/ or use a saved classroom pad. Record predictions before execution. Each worked program includes its helper definitions. The reference puts the six exercises in separate scopes, so a task cannot silently rely on a variable from a previous task. A successful assertion is silent; the final JSON receipt reports how many exercise blocks completed. A failing assertion must produce a failed process, not a generic success message.

Syntax anatomy and execution trace#

process.argv.slice(2) exposes user arguments after the executable and script paths. for await over process.stdin receives byte chunks. A byte budget is checked before retaining another chunk. Buffer.concat followed by UTF-8 decoding is appropriate only because this fixture enforces a small total input bound. Parsing attaches a one-based line number to validation errors. The program writes its JSON result only after every row passes, and sets process.exitCode on failure so pending diagnostic writes can finish.

Worked example / walkthrough#

Example A: Aggregate valid rows through a real child process#

The check uses the actual process contract, not a direct call to an internal aggregate function. Exact separation of result data and diagnostics makes the tool composable with another program.

import { strict as assert } from 'node:assert';
import { mkdtemp, writeFile, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
import { spawnSync } from 'node:child_process';

const CLI_SOURCE = String.raw`
async function main() {
  if (process.argv.slice(2).join(' ') !== '--sum') throw new Error('usage: main.mjs --sum');
  const chunks = [];
  let bytes = 0;
  for await (const chunk of process.stdin) {
    bytes += chunk.length;
    if (bytes > 4096) throw new Error('input limit: 4096 bytes');
    chunks.push(chunk);
  }
  const text = Buffer.concat(chunks).toString('utf8');
  const ids = new Set();
  let rows = 0;
  let totalCents = 0;
  for (const [index, line] of text.split(/\r?\n/u).entries()) {
    if (line.trim() === '') continue;
    try {
      const row = JSON.parse(line);
      if (row === null || typeof row !== 'object' || Array.isArray(row)) throw new Error('object required');
      if (Object.keys(row).sort().join(',') !== 'id,priceCents,quantity') throw new Error('exact schema required');
      if (typeof row.id !== 'string' || row.id === '') throw new Error('id required');
      if (!Number.isSafeInteger(row.quantity) || row.quantity <= 0 || !Number.isSafeInteger(row.priceCents) || row.priceCents < 0) throw new Error('invalid integer units');
      if (ids.has(row.id)) throw new Error('duplicate id');
      const contribution = row.quantity * row.priceCents;
      if (!Number.isSafeInteger(contribution) || !Number.isSafeInteger(totalCents + contribution)) throw new Error('unsafe total');
      ids.add(row.id);
      totalCents += contribution;
      rows += 1;
    } catch (error) {
      throw new Error('line ' + (index + 1) + ': ' + error.message, { cause: error });
    }
  }
  process.stdout.write(JSON.stringify({ rows, totalCents }) + '\n');
}
main().catch(error => { process.stderr.write(error.message + '\n'); process.exitCode = 2; });
`;
async function runCli(args, input) {
  const directory = await mkdtemp(join(tmpdir(), 'course-cli-'));
  try {
    const path = join(directory, 'main.mjs');
    await writeFile(path, CLI_SOURCE, 'utf8');
    const result = spawnSync(process.execPath, [path, ...args], { input, encoding: 'utf8', timeout: 10000, maxBuffer: 1024 * 1024 });
    if (result.error) throw result.error;
    if (result.signal) throw new Error(`CLI terminated by ${result.signal}`);
    return result;
  } finally {
    await rm(directory, { recursive: true, force: true });
  }
}

export async function verify() {
  // Worked example
  {
    const input = [{ id: 'A', quantity: 2, priceCents: 125 }, { id: 'B', quantity: 3, priceCents: 100 }].map(JSON.stringify).join('\n');
    const result = await runCli(['--sum'], input);
    assert.equal(result.status, 0, result.stderr);
    assert.deepEqual(JSON.parse(result.stdout), { rows: 2, totalCents: 550 });
    assert.equal(result.stderr, '');
    assert.equal(result.stdout.trim().split('\n').length, 1);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: exit 0; stdout is exactly one JSON result with 2 rows and 550 cents; stderr empty.

Example B: Reject unknown arguments before consuming data#

A strict argument contract catches misspellings. Silently ignoring an unknown option can make a caller believe an important behavior was enabled when it was not.

export async function verify() {
  // Worked example
  {

  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: exit 2; stdout empty; stderr includes usage.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
