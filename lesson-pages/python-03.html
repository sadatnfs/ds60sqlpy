Day 3: Control Flow, Truthiness, and Exceptions#

Level: Beginner

Control flow chooses which statements run. Exceptions separate an expected failure path from the successful path. Each example in this lesson runs its decision once: change the input value and rerun to test another case. Day 4 adds loops, which repeat a decision automatically.

Learning objectives#

By the end of this lesson, you can:

  • write mutually exclusive if/elif/else branches;
  • predict how truthiness and comparisons behave inside conditions;
  • catch only the exceptions you can handle with try/except/else/finally; and
  • raise a built-in exception such as ValueError with a message that explains the failure.

Beginner deep dive: build the idea before the syntax#

Start with one mental picture#

Control flow is the route execution takes through a program. An if/elif/else chain chooses exactly one branch: Python tests from top to bottom and stops at the first true condition. Put narrow or more specific rules before broader ones, and validate impossible inputs before classifying valid ones.

Exceptions separate a normal return path from a failure path. A try block should contain only the operation expected to fail, while except names the failure the current layer can interpret. Catching every exception hides programming bugs. else runs after a successful try; finally runs whether success or failure occurred.

Vocabulary in plain language#
  • condition: an expression evaluated for truthiness.
  • branch: one possible block selected by a condition.
  • guard clause: an early check that rejects or handles an invalid case.
  • exception: an object representing a failure that interrupts normal flow.
  • raise: to deliberately signal an exception.
  • handler: an except block for a named exception type.
Syntax anatomy#

In if score >= 90:, the colon ends the condition and starts an indented suite. Only code indented under that branch belongs to it. In except ValueError as exc:, ValueError is the narrow failure type and exc is the actual exception object. An exception handler is not a substitute for an ordinary condition that can be checked directly.

Worked example 2: Protect only the fallible conversion#

text = " 12 "

try:
    count = int(text.strip())
except ValueError:

    outcome = "not an integer"

Expected observation: (12, 'parsed'). Only int(...) sits inside try, so only a failed conversion can reach the handler, and the else block runs only after the conversion succeeded. A debugging routine for this topic#

When the output differs from your prediction, use this order:

  1. Trace conditions from top to bottom and mark the first one that becomes true.
  2. Move validation before classification when impossible values enter normal branches.
  3. Shrink a large try block until it contains only the operation with the expected failure.
  4. Replace bare except: or except Exception: with the narrow type you can recover from.

Vocabulary and mental model#

  • Branch: one possible route through a program.
  • Condition: an expression interpreted as true or false.
  • Traceback: the report Python prints for an unhandled exception; its last line names the exception type and message.
  • Exception: an object that interrupts normal execution when an operation cannot satisfy its contract.
  • Raise: signal a failure; catch: handle a specific failure.
  • else/finally: exception else runs only after success; finally runs whether the operation succeeds or fails.

Treat exceptions as structured failure information, not as a substitute for all branching.

Worked example#

raw = "42"

try:
    value = int(raw)
except ValueError as exc:
    raise ValueError(f"expected an integer, received {raw!r}") from exc

if value < 0:
    raise ValueError(f"value must be non-negative, received {value}")

value

With raw = "42" the cell displays 42. With raw = "forty", the conversion fails and the new message expected an integer, received 'forty' is raised; from exc keeps the original invalid literal for int() error in the traceback. With raw = "-4", the conversion succeeds and the domain rule raises value must be non-negative, received -4. The two failures have different causes, and the messages make both diagnosable.

Self-check#

  • Why does branch order matter in FizzBuzz?
  • Which boundary values (59, 60, 89, 90, 100, 101) prove that the score branches neither overlap nor leave gaps?
  • Why is except Exception: usually too broad?
  • What information is preserved by raise NewError(...) from exc?

Expected behavior: each FizzBuzz test value gets exactly one label, invalid numeric text is reported without hiding unrelated bugs, and a negative measurement raises ValueError with its exact message.

Common pitfalls and diagnosis#

  • FizzBuzz never prints the combined case: inspect branch order.
  • IndentationError, or a line running in the wrong branch: every line of a branch must be indented by the same amount under its if, elif, else, try, or except line. Find where the indentation ends.
  • Errors disappear silently: never use a bare except: pass; log, return a documented fallback, or re-raise.
  • NameError after try: a name was assigned only on the success path, so the failure path left it undefined. Assign it in the handler too (worked example 2 sets count = None) or initialize it before try.
  • The wrong exception is caught: reproduce the smallest failing expression and inspect the traceback's final line.

Day 3 Solutions: Control Flow, Truthiness, and Exceptions#

Concept review before comparing answers#

These worked answers demonstrate branch selection, truthiness in conditions, and narrow exception boundaries. Predict each named result before comparing your attempt with its matching assertions.

Control flow is the route execution takes through a program. An if/elif/else chain chooses exactly one branch: Python tests from top to bottom and stops at the first true condition. Put narrow or more specific rules before broader ones, and validate impossible inputs before classifying valid ones.

Exceptions separate a normal return path from a failure path. A try block should contain only the operation expected to fail, while except names the failure the current layer can interpret. Catching every exception hides programming bugs. else runs after a successful try; finally runs whether success or failure occurred.

Vocabulary used in the worked answers#
  • condition: an expression evaluated for truthiness.
  • branch: one possible block selected by a condition.
  • guard clause: an early check that rejects or handles an invalid case.
  • exception: an object representing a failure that interrupts normal flow.
  • raise: to deliberately signal an exception.
  • handler: an except block for a named exception type.
How to compare an answer#

For each answer, follow the input value through every condition or try clause to the printed output or assertion that proves the behavior. Then change the input to a boundary value, such as 59.49 or "seven", predict the new path, and rerun before accepting the answer.

Exercise 1: worked answer#

Learner contract: Given number = 15, write one ordered if/elif/else chain that sets label to "FizzBuzz" for multiples of both 3 and 5, "Fizz" for multiples of 3 only, "Buzz" for multiples of 5 only, and str(number) otherwise. Constraints: test divisibility with % and keep all four outcomes in one chain. Verify: rerun with number set to 3, 5, 15, 16, and 30 and assert the labels "Fizz", "Buzz", "FizzBuzz", "16", and "FizzBuzz". Day 4 repeats this decision for 1 through 30 with a for loop.

Reasoning: The combined rule must come first. Fifteen is also a multiple of 3, so if number % 3 == 0 were tested first, 15 would stop at "Fizz" and never reach "FizzBuzz". Testing number % 15 == 0 is the same as "divisible by 3 and by 5" because 3 and 5 share no factor; number % 3 == 0 and number % 5 == 0 says it more literally. str(number) keeps every label a string, so "16" and "Fizz" have the same type. Writing four separate if statements is the usual mistake: 15 then satisfies three of them, and the label is whichever assignment happened to run last.

number = 15

if number % 15 == 0:
    label = "FizzBuzz"
elif number % 3 == 0:
    label = "Fizz"
elif number % 5 == 0:
    label = "Buzz"
else:
    label = str(number)

print(number, label)
assert label == "FizzBuzz"
