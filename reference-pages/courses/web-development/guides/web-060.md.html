web-060: Integrated capstone: accessible, tested and recoverable web learning#

Level and prerequisites#

Advanced; allow about 150 minutes, with extra time for independent practice. Direct prerequisites: web-059

Learning objectives#

Build and review a learner-owned extension of the supplied local lab. Present a release-readiness review with explicit limits and next actions. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

Purpose, vocabulary and mental model#

The final project joins HTML structure, CSS presentation, browser interaction, PHP application logic and relational storage around one useful learner journey. Start with a small task: create and review a study plan, receive actionable validation feedback and return later without losing the plan. Expand only after the core behavior is explainable and tested. A framework may help organize a larger application, but it does not remove these contracts.

Use a threat model that names assets, actors, trust boundaries and likely failures. For this learning project, synthetic notes are the data asset; anonymous session ownership is an explicit limitation; request fields are untrusted; output, SQL and filesystem access are separate interpretation boundaries. If adding real accounts, the identity and recovery design must be upgraded deliberately rather than quietly inheriting the anonymous demo's assumptions.

Syntax anatomy and mechanism#

Create an acceptance matrix with normal, invalid, cross-session, restart and accessibility cases. Keep unit checks for pure functions, integration checks for HTTP and storage, and actual browser observations for focus and layout. Connect to the JavaScript and D3 path when adding data visualization, to SQL when expanding relational modeling, and to Docker and Kubernetes when studying delivery. Each extension needs evidence for its new boundary.

Classroom execution and offline inputs#

This is a reading and design worksheet with an optional external project lab. The classroom saves the worksheet but does not start an HTTP server, install packages or control Docker from its pad. Work from the supplied synthetic examples first. A command is a proposal until you deliberately execute it against your own disposable local project. The maintained optional fixture is courses/web-development/fixtures/php-http-lab/; read its README before preparing it. Do not expose that learning server to the internet or reuse real account data.

Worked example / walkthrough#

Worked example 1: A journey acceptance case#

The case spans multiple layers without confusing them.

Open page -> keyboard-enter plan -> submit -> observe 303 -> read saved plan
Reload -> same session sees plan
New browser session -> original plan is not listed

Expected observation: The observed journey qualifies local session ownership and persistence, not verified account identity.

Worked example 2: A deliberate project review#

The report states both completed and unqualified surfaces.

Verified: local request validation, prepared storage, CSRF rejection, keyboard form
Not yet qualified: production TLS, account recovery, multiple replicas, public abuse resistance

Expected observation: The report supports a concrete next step without claiming universal correctness.

Six progressive exercises#

Exercise 1: Define one small learner journey and its finish condition.#

Expected evidence: The journey ends with an observable saved plan and a clear way to recover from invalid input.

Progressive hint: Trace the smallest example before editing. Name which values are source and which are observations.

Exercise 2: Map every input and output to its validation or encoding boundary.#

Expected evidence: HTML text, SQL values, URLs, session identity and filesystem paths have distinct policies.

Progressive hint: Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

Exercise 3: Build and review a learner-owned extension of the supplied local lab.#

Expected evidence: The extension has coherent HTML/CSS, tested PHP behavior and a bounded reproducible setup.

Progressive hint: Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

Exercise 4: Introduce a controlled invalid request and preserve its evidence.#

Expected evidence: The application rejects it without a partial write or loss of existing user input.

Progressive hint: Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

Exercise 5: Perform a stop/resume and a separate restore rehearsal.#

Expected evidence: The report distinguishes retained volumes from an independently verified recovery copy.

Progressive hint: Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

Exercise 6: Present a release-readiness review with explicit limits and next actions.#

Expected evidence: The review connects claims to real evidence and identifies untested platforms or production controls without calling the system bug free.

Progressive hint: Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

Debugging and common mistakes#

Do not let a polished interface hide an unfinished trust boundary. Avoid copying a reference without explaining its limitations. Expert practice means selecting evidence and handling tradeoffs, not merely finishing every chapter or using a popular framework.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

Retrieval, transfer and next steps#

Close the worked answers and explain capstone, threat model, acceptance matrix without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
