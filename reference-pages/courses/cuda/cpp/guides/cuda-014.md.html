Purpose, vocabulary and mental model#

A one-dimensional launch gives a thread the starting index blockIdx.xblockDim.x+threadIdx.x. A grid-stride loop advances that index by blockDim.xgridDim.x until it reaches n. Every nonnegative index has one remainder modulo the positive stride, so exactly one starting thread owns it. Cast to a sufficiently wide integer before multiplying dimensions; widening after an overflow is too late. Ceiling division supplies enough threads for one-element mapping, but a grid-stride loop also allows a bounded grid to cover a much larger input. A bounds test is required even when most demonstration sizes divide evenly.

Mathematical contract#

i=t+kG,0≤t<G,k≥0i=t+kG,\qquad 0\leq t<G,\quad k\geq0

G is the positive grid stride and t is a unique starting thread index. Each valid i has a unique quotient and remainder, establishing coverage without duplicate ownership.

Worked example 1: trace the mechanism#

Use two blocks of four threads for n=19\mathrm{n}=19. Thread 0 owns indices 0,8,16; thread 1 owns 1,9,17; thread 2 owns 2,10,18; thread 3 owns 3,11. Every element has exactly one owner. This ownership trace is CPU reasoning, not a simulator of warp scheduling or GPU timing.

The complete CPU model below intentionally models only the named arithmetic, layout, dependency or capability decision. It does not model GPU scheduling, caches, instruction timing or device memory visibility.

n, stride = 19, 8
owners = [list(range(t, n, stride)) for t in range(stride)]
flat = [i for group in owners for i in group]
assert sorted(flat) == list(range(n)) and len(set(flat)) == n
assert owners[0] == [0, 8, 16]
print({"thread_0": owners[0], "all_elements_written_once": True})

Expected observation: Every assertion succeeds. A representative CPU output is:

{'thread_0': [0, 8, 16], 'all_elements_written_once': True}

Tiny floating-point display differences across platforms are acceptable only where the explicit assertions use a tolerance; integers, shapes and ordering must still satisfy their exact contracts. A printed hypothetical duration is a model output, not a measured GPU benchmark.

Common mistakes and diagnosis#

A tempting but incorrect claim in this chapter is: removing the bounds condition is harmless because a chosen demo length is divisible by the block size.

For the concrete failure exercise, a kernel tests i <= n instead of i < n. Diagnose it. Preserve the original input and the stage where behavior diverged. Compare with the CPU model or dependency diagram before changing hardware configuration. A compiler result, synthetic timing model, profiler counter and returned numeric answer support different claims. Record unavailable hardware honestly.
