# dbt-009: Keyed updates, lookback windows and idempotency

## Level and prerequisites

Intermediate. Direct prerequisites: `dbt-004`, `dbt-008`

**Outcome:** Implement a keyed incremental contract with tested boundary and repeat-run behavior.

## Question and mechanism

A keyed incremental strategy can replace records whose identity is already present. A lookback window can revisit recent source records so corrections and bounded late arrivals are considered. Together, these mechanisms address some weaknesses of a pure append watermark. They still require a valid key, deterministic source selection and a bound on lateness.

The example uses DuckDB's delete+insert strategy with id as the matching key. The source predicate includes a ten-unit lookback behind the current maximum. An update to id 1 and a late insertion of id 3 are therefore included, while unchanged id 2 can be revisited without creating another copy. The result is checked again after a repeat run.

The counterexample arrives outside that lookback. It remains missing until a full refresh. A ten-unit window is a data-contract choice, not proof that older corrections cannot occur. Also, unique_key configures incremental matching; it does not by itself replace a data test proving that the selected source has one record per key.

dbt 1.9 added a built-in strategy for this kind of time-series source: `incremental_strategy='microbatch'`. The model SQL selects ordinary rows with no `is_incremental()` filter. dbt splits the work into batches of `batch_size` (hour, day, month or year) beginning at `begin`, filters every parent that declares an `event_time` to the batch window, and replaces each batch as a unit; dbt-duckdb issues a delete and an insert scoped to the window. On a normal run dbt processes the batches up to the current time plus `lookback` earlier batches (default 1), which is the built-in form of this lesson's ten-unit window. The same limits remain. A correction older than the reprocessed batches stays missing until a declared backfill, and because batches are replaced by time window rather than matched by key, a record whose `event_time` moves to a later window keeps its old version in the earlier batch unless that batch is rebuilt too.

## Key terms

- **unique_key:** The incremental setting that names the columns identifying a row, so a new version replaces the old row instead of duplicating it.
- **delete+insert:** An incremental strategy that deletes target rows whose unique_key appears in the new batch and then inserts the batch.
- **Lookback window:** A deliberate overlap that reprocesses recent rows before the watermark so late corrections are picked up.
- **Idempotency:** The property that rerunning the same build on the same input leaves identical target rows, with no duplicates.
- **Microbatch:** The incremental strategy added in dbt 1.9 that processes time batches defined by event_time, batch_size and begin, replacing each batch whole.

## Syntax and data contract

unique_key names the matching identity. incremental_strategy='delete+insert' is an adapter-specific implementation choice that must be supported by the prepared database. The lookback predicate uses >= so the lower boundary is included. Keep an independent uniqueness test and a reviewed policy for multiple source versions of the same key.

The following microbatch version is a reading example; this lesson's program does not run it. Microbatch needs a date or timestamp `event_time` interpreted as UTC, so it assumes an `events` seed whose `updated_at` column holds timestamps rather than the integers used above. This configuration was run against the pinned dbt-core 1.11.16 and dbt-duckdb 1.11.1 on DuckDB 2.0.0 with a small timestamp seed.

```sql
{{ config(
    materialized='incremental',
    incremental_strategy='microbatch',
    event_time='updated_at',
    begin='2024-01-01',
    batch_size='day',
    lookback=1
) }}
select id, updated_at, amount
from {{ ref('events') }}
```

The parent must declare its own `event_time`, or dbt reads all of it for every batch:

```yaml
version: 2
seeds:
  - name: events
    config:
      event_time: updated_at
```

A declared backfill names a start and an end, both in UTC, and the end is exclusive. This command rebuilds the 2024-01-01 and 2024-01-02 batches, not 2024-01-03, each as an independent batch, and `dbt retry` reruns only batches that failed:

```bash
dbt run --select current_events --event-time-start "2024-01-01" --event-time-end "2024-01-03"
```

## Worked case 1: Revisit rows without duplicating them

The first case updates an existing amount and adds a late record within the allowed window. It then reruns the model to verify the same three identified values. This checks the combination of selection and write semantics.

**Project files.** The case writes these files before its first dbt command. YAML is shown in conventional key order; dbt reads the same mappings.

`models/current_events.sql`

```sql
{{ config(materialized='incremental', unique_key='id', incremental_strategy='delete+insert') }}
select *
from {{ ref('events') }}
{% if is_incremental() %}
    where updated_at >= (select max(updated_at) - 10 from {{ this }})
{% endif %}
```

`seeds/events.csv`

```text
id,updated_at,amount
1,10,5
2,20,7
```

**Commands and changes, in order.** Each `dbt` line is one `invoke(...)` call; the harness adds `--project-dir` and `--profiles-dir` for the temporary project.

```bash
dbt build
```

The case then writes `seeds/events.csv`:

```text
id,updated_at,amount
1,11,6
2,20,7
3,15,9
```

```bash
dbt build
dbt run
```

**Expected evidence:** Final amounts are id 1=6, id 2=7 and id 3=9, with three rows after rerun.

The program below shows only this case's own functions. They call the shared helpers `project`, `invoke` and `rows`, which write the files above, run dbt through `dbtRunner` and read the results; the helpers are explained in [dbt-001](dbt-001.md) and appear in full at the top of this lesson's [starter](../lessons/dbt-009.py).

```python
import tempfile


def example_one():
    with tempfile.TemporaryDirectory() as d:
        sql = (
            "{{ config(materialized='incremental', unique_key='id', "
            "incremental_strategy='delete+insert') }}\n"
            "select *\n"
            "from {{ ref('events') }}\n"
            "{% if is_incremental() %}\n"
            "    where updated_at >= (select max(updated_at) - 10 from {{ this }})\n"
            "{% endif %}"
        )
        p = project(
            d,
            models={"current_events": sql},
            seeds={"events": "id,updated_at,amount\n1,10,5\n2,20,7\n"},
        )
        invoke(p, "build")
        (p / "seeds/events.csv").write_text("id,updated_at,amount\n1,11,6\n2,20,7\n3,15,9\n")
        invoke(p, "build")
        invoke(p, "run")
        assert rows(p, "select id,amount from current_events order by id") == [
            (1, 6),
            (2, 7),
            (3, 9),
        ]
        return {"keyed_update_and_late_insert": True, "rows_after_rerun": 3}
```

The program below shows only this case's own functions. They call the shared helpers `project`, `invoke` and `rows`, which write the files above, run dbt through `dbtRunner` and read the results; the helpers are explained in [dbt-001](dbt-001.md) and appear in full at the top of this lesson's [starter](../lessons/dbt-009.py).

```python
import tempfile


def example_two():
    with tempfile.TemporaryDirectory() as d:
        sql = (
            "{{ config(materialized='incremental', unique_key='id', "
            "incremental_strategy='delete+insert') }}\n"
            "select *\n"
            "from {{ ref('events') }}\n"
            "{% if is_incremental() %}\n"
            "    where updated_at >= (select max(updated_at) - 10 from {{ this }})\n"
            "{% endif %}"
        )
        p = project(
            d, models={"current_events": sql}, seeds={"events": "id,updated_at,amount\n1,20,5\n"}
        )
        invoke(p, "build")
        (p / "seeds/events.csv").write_text("id,updated_at,amount\n1,20,5\n2,7,9\n")
        invoke(p, "build")
        assert rows(p, "select count(*) from current_events") == [(1,)]
        invoke(p, "run", "--full-refresh")
        assert rows(p, "select count(*) from current_events") == [(2,)]
        return {"outside_lookback_missed": True, "repair_requires_declared_backfill": True}
```

## Practice

The starter contains both worked cases, so a task can change either one. Make each change in a saved copy, run it, and compare the printed result with the task's check before opening the separate explained answers.

### 1. Test the exact boundary

Add a record at max(updated_at)-10.

**Check:** The inclusive predicate considers it.

**Hint:** The operator is >=.

### 2. Repeat a correction

Apply the same corrected source twice.

**Check:** The identified result remains unchanged.

**Hint:** Check both values and row count.

### 3. Duplicate a source key

Add two selected records with one id.

**Check:** A separate key test detects the ambiguity.

**Hint:** unique_key is not an automatic source uniqueness guarantee.

### 4. Widen the lookback

Include a previously missed old record by changing the window.

**Check:** The record is selected under the revised policy.

**Hint:** Measure added work as well as correctness.

### 5. Compare with full recomputation

Rebuild the small fixture and compare keyed rows.

**Check:** The accepted incremental case matches.

**Hint:** Use stable ordering and schema.

### 6. Specify a correction ledger

List what should be recorded for a backfill.

**Check:** It includes identity, time scope, source version and reconciliation.

**Hint:** A repair needs reproducible evidence.

## Diagnose errors and misleading results

If a keyed update creates duplicates, inspect selected-source uniqueness rather than assuming unique_key enforced it. If old corrections are missed, inspect the lookback bound. If a rerun changes results without source changes, inspect ordering, nondeterministic expressions and external state.
