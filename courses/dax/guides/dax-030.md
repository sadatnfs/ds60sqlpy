## The question and the mechanism

Model overlapping customer groups and reconcile unique reach without enabling ambiguous filter paths.

A customer can belong to several audiences, so storing one audience label on Customer would lose information. A membership bridge has one row per group/customer pair. Audience and Customer each have one-to-many relationships into that bridge in the supplied analytical model. With those single-direction paths, an Audience filter reaches membership rows but does not automatically flow backward into Customer and onward to Sales.

An explicit virtual mapping can carry the selected membership keys to Customer for one measure. This keeps the measure's intention visible without globally changing relationship direction. It is not automatically preferable in every real model; a deliberate physical many-to-many design can be appropriate after considering ambiguity, security and performance.

Newsletter contains Ada and Bo; Prospects contains Bo and Cy. Bo's 80 belongs to both audience reports. Adding the two audience revenues yields 267, larger than the unique-customer total 187. A combined audience should first form a unique customer set, then aggregate its facts. The model should distinguish audience memberships from distinct customer reach.

## Vocabulary and expression anatomy

Audience filters GroupMembership through GroupKey. VALUES extracts the selected bridge's CustomerKey values. TREATAS explicitly targets Customer[CustomerKey], whose ordinary relationship then filters Sales. The raw measure is included to show that the model's single-direction bridge alone does not perform that backward propagation.

Concepts to explain in your own words: **bridge table**, **many-to-many**, **TREATAS**, **filter direction**, **overlap**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: Newsletter's two customers

**Starting context:** Analytics model; Audience=Newsletter; single-direction relationships into GroupMembership.

```dax
EVALUATE CALCULATETABLE ( ROW ( "RawRevenue", [NetRevenue], "AudienceRevenue", CALCULATE ( [NetRevenue], TREATAS ( VALUES ( GroupMembership[CustomerKey] ), Customer[CustomerKey] ) ) ), Audience[Audience] = "Newsletter" )
```

**Context trace:**

1. Newsletter leaves membership keys 10 and 20.
2. Without explicit mapping the bridge does not filter Customer, so RawRevenue stays 187.
3. TREATAS selects Ada 51 and Bo 80, totaling 131.

**Hand-derived worked-reference result:**

| RawRevenue | AudienceRevenue |
| --- | --- |
| 187 | 131 |

The explicit result follows a documented mapping. Enabling broad bidirectional filtering would affect other queries as well, so it is a model decision rather than a cosmetic fix.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Prospects overlaps the first audience

**Starting context:** Analytics model; Audience=Prospects; selected membership keys 20 and 30.

```dax
EVALUATE CALCULATETABLE ( ROW ( "RawRevenue", [NetRevenue], "AudienceRevenue", CALCULATE ( [NetRevenue], TREATAS ( VALUES ( GroupMembership[CustomerKey] ), Customer[CustomerKey] ) ) ), Audience[Audience] = "Prospects" )
```

**Context trace:**

1. Prospects selects Bo and Cy through the explicit mapping.
2. Their revenues are 80 and 56, totaling 136.
3. Bo is shared with Newsletter, so summing the two audience totals would count 80 twice.

**Hand-derived worked-reference result:**

| RawRevenue | AudienceRevenue |
| --- | --- |
| 187 | 136 |

Overlap is legitimate membership information. The error is treating overlapping audience results as disjoint partitions.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. VALUES over the bridge deduplicates customer keys.
2. The membership count and sales amount can respond differently.
3. Subtract the overlapping population once.
4. Its declared grain is one pair, not one loading event.
5. A query-level filter can be edited or removed.
6. Programs overlap and patient identity remains distinct.
