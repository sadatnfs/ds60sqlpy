dme-054: Operational drill: detection, rollback and learning#

Level: Advanced | Prepared runtime: data-engineering

Direct prerequisites: dme-043, dme-047, dme-048, dme-049, dme-050, dme-052.

Outcome: Diagnose a bounded fault using actual recorded workflow/service evidence.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

Exercise the dangerous boundary with a real process#

A useful operational drill creates a controlled failure, records what happened and verifies a recovery decision against actual state. It should not merely print “crash simulated” while every operation completes normally. This capstone launches a real child Python process, commits a SQLite operation and then exits that process with a nonzero status before returning a normal acknowledgement to its parent.

The parent observes the failed process result, then reads the database to determine whether the effect committed. That is the unknown-outcome boundary seen throughout the book: a caller's failure observation does not prove that the business operation failed. Replaying automatically can duplicate effects or overwrite newer state. Recovery begins with source-bound readback.

All work occurs in owned temporary directories. The child uses only the reviewed chapter source and synthetic proposal file. The drill does not stop any unrelated process or damage a real service. It tests a process exit after a completed database transaction, not power loss, filesystem corruption or a multi-host outage. The persistent data-product project adds actual HTTP and Docker lifecycle drills under its own ownership and cleanup contract.

Keep operation receipts with accepted state#

The database contains versioned products, an accepted-version pointer, operation receipts and recovery records. The initial product is version 1 with six packages. The child receives a proposal containing counts two, three and four and a claimed total of nine. It validates that claim, then commits product version 2, a receipt binding the exact proposal bytes, and the accepted pointer in one transaction.

After closing its connection, the child writes a phase message to stdout and invokes os._exit(17). The parent therefore receives exit code 17 even though version 2 committed. The receipt and accepted product establish the database outcome independently of the child's final log message. Logs describe execution; durable state determines what is currently accepted.

The relevant reconciliation is

together with a readback of the expected product content. A receipt for another input or another version would not resolve this request. The outer classroom execution evidence separately binds the chapter program to its source identity; the operation receipt inside the example binds the submitted proposal.

Worked case 1: confirm a committed result without replay#

example_one() initializes version 1, launches the child once and captures its exit code, stdout and stderr. The child exits 17. The parent reads accepted version 2 with nine packages and finds the matching operation receipt. Two product versions exist, preserving the prior accepted state and the new candidate.

The recovery decision is to accept the confirmed committed result without invoking the worker again. The reported worker invocation count is one. This is a concrete alternative to treating every nonzero exit as permission to rerun the mutation. A supervising system can report the actual operation outcome and separately record that acknowledgement delivery failed.

The phase message is helpful for diagnosis, but the parent does not rely on it alone. A process can emit a log before a later write fails, or lose buffered logs after a successful commit. The database readback and source identity are the decisive evidence in this local transaction model. In a remote service, the equivalent might be a durable operation-status endpoint or an idempotency receipt.

Worked case 2: execution committed, but a separate consumer gate rejects it#

The second case repeats the real after-commit process failure and confirms the same nine-package version. It then applies an illustrative downstream consumer limit of eight. The candidate is structurally valid and its execution completed, but it fails this separate acceptance rule. The drill intentionally discovers that rule after activation to exercise recovery; a production workflow should normally include known consumer gates before activation.

The parent performs an explicit rollback from expected current version 2 to retained version 1. The rollback transaction checks that version 2 is still current and that the target exists, updates the pointer and appends a recovery record with a reason. Readback shows accepted version 1 with six packages. Version 2 remains stored for investigation, and there is one recovery record.

Rollback does not replay ingestion, delete the candidate or erase the operation receipt. Those records explain what happened. If another publisher had already changed the accepted version, the expected-current check would reject the stale rollback rather than overwriting that newer decision. Recovery actions need concurrency preconditions just as forward publication does.

Complete worked program#

Use data-engineering. The child process and SQLite transactions are real. Every process is bounded by a timeout, every database belongs to the temporary fixture, and the program creates no network listener.

"""Actual child-process failure after a committed operation, followed by readback and rollback."""

import hashlib
import json
import os
import sqlite3
import subprocess
import sys
import tempfile
from pathlib import Path


def database(root):
    return sqlite3.connect(root / "state.db")


def initialize(root):
    connection = database(root)
    try:
        with connection:
            connection.execute(
                "create table products(version integer primary key,packages integer not null)"
            )
            connection.execute(
                "create table accepted(id integer primary key,version integer not null)"
            )
            connection.execute(
                "create table operations(id text primary key,source_sha text not null,"
                "version integer not null)"
            )
            connection.execute(
                "create table recovery(old_version integer,new_version integer,reason text)"
            )
            connection.execute("insert into products values(1,6)")
            connection.execute("insert into accepted values(1,1)")
    finally:
        connection.close()


def worker(root):
    source = root / "proposal.json"
    proposal = json.loads(source.read_text())
    values = proposal["values"]
    if (
        not isinstance(values, list)
        or not values
        or len(values) > 100
        or any(type(value) is not int or value < 1 for value in values)
        or sum(values) != proposal["claimed_total"]
    ):
        os.write(1, b"validation_rejected\n")
        os._exit(23)
    source_sha = hashlib.sha256(source.read_bytes()).hexdigest()
    connection = database(root)
    try:
        with connection:
            connection.execute("insert into products values(2,?)", (sum(values),))
            connection.execute("insert into operations values('candidate-a',?,2)", (source_sha,))
            connection.execute("update accepted set version=2 where id=1")
    finally:
        connection.close()
    os.write(1, b"database_commit_completed_before_response\n")
    os._exit(17)


def run_worker(root, claimed_total=9):
    (root / "proposal.json").write_text(
        json.dumps({"values": [2, 3, 4], "claimed_total": claimed_total}, sort_keys=True)
    )
    result = subprocess.run(
        [sys.executable, str(Path(__file__).resolve()), "--commit-worker", str(root)],
        capture_output=True,
        text=True,
        timeout=10,
        stdin=subprocess.DEVNULL,
    )
    return {
        "returncode": result.returncode,
        "stdout": result.stdout,
        "stderr": result.stderr,
        "source_sha256": hashlib.sha256((root / "proposal.json").read_bytes()).hexdigest(),
    }


def inspect(root):
    connection = database(root)
    try:
        selected = connection.execute(
            "select p.version,p.packages from accepted a join products p on a.version=p.version"
        ).fetchone()
        receipt = connection.execute(
            "select source_sha,version from operations where id='candidate-a'"
        ).fetchone()
        return {
            "accepted": selected,
            "receipt": receipt,
            "products": connection.execute(
                "select version,packages from products order by version"
            ).fetchall(),
        }
    finally:
        connection.close()


def rollback(root, expected, target, reason):
    connection = database(root)
    try:
        with connection:
            connection.execute("begin immediate")
            current = connection.execute("select version from accepted").fetchone()[0]
            if current != expected or connection.execute(
                "select count(*) from products where version=?", (target,)
            ).fetchone() != (1,):
                raise ValueError("Rollback precondition or retained target failed")
            connection.execute("update accepted set version=? where id=1", (target,))
            connection.execute("insert into recovery values(?,?,?)", (expected, target, reason))
    finally:
        connection.close()


def example_one():
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        initialize(root)
        attempt = run_worker(root)
        observed = inspect(root)
        assert attempt["returncode"] == 17 and observed["accepted"] == (2, 9)
        assert observed["receipt"] == (attempt["source_sha256"], 2)
        assert len(observed["products"]) == 2
        return {
            "child_exit": 17,
            "accepted_after_readback": list(observed["accepted"]),
            "receipt_matches_exact_source": True,
            "worker_invocations": 1,
            "recovery_decision": "accept the committed result without replay",
        }


def example_two():
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        initialize(root)
        attempt = run_worker(root)
        observed = inspect(root)
        assert attempt["returncode"] == 17 and observed["receipt"] == (attempt["source_sha256"], 2)
        consumer_limit = 8
        assert observed["accepted"][1] > consumer_limit
        rollback(root, expected=2, target=1, reason="synthetic downstream package-limit gate")
        recovered = inspect(root)
        assert recovered["accepted"] == (1, 6) and recovered["products"] == [(1, 6), (2, 9)]
        connection = database(root)
        try:
            assert connection.execute("select count(*) from recovery").fetchone() == (1,)
        finally:
            connection.close()
        return {
            "committed_candidate_failed_separate_consumer_gate": True,
            "accepted_after_explicit_rollback": list(recovered["accepted"]),
            "candidate_retained_for_investigation": True,
            "worker_invocations": 1,
            "power_loss_and_multi_host_recovery_not_tested": True,
        }


def main():
    print("Reconcile an actual process failure after commit:", example_one())
    print("Separate execution success from consumer acceptance and rollback:", example_two())


if __name__ == "__main__":
    if len(sys.argv) == 3 and sys.argv[1] == "--commit-worker":
        worker(Path(sys.argv[2]))
    else:
        main()

Build a useful incident timeline#

A timeline should distinguish observations from hypotheses and actions. In this drill, the observations include the child exit, phase output, proposal hash, operation receipt, accepted product and recovery record. “The worker failed” is too vague because it combines process status with business outcome. “The process exited after a matching committed operation; acknowledgement was not returned normally” is more informative.

Record the evidence available at each decision. An operator should be able to explain why replay was avoided, why rollback was chosen and which accepted state was verified afterward. Avoid rewriting earlier evidence to make the final story look cleaner. The rejected or uncertain candidate is often the most useful artifact for understanding the failure mechanism.

In a real incident, also record source and image revisions, configuration changes, relevant metrics, affected populations and the time boundaries of uncertainty. Do not include credentials or sensitive payloads simply to make a report detailed. The provenance and governance chapters explain how to retain useful evidence without treating every log field as safe to share.

Separate recovery from root-cause analysis#

Restoring an accepted state can reduce impact before the full cause is known. Root-cause analysis then investigates why the failure occurred and how to prevent or detect recurrence. A successful rollback is evidence that changing the active version affected the outcome, but it may not by itself prove a single cause if other conditions changed concurrently.

This drill's failure cause is known because the source deliberately exits at a precise point. That makes it suitable for validating the recovery procedure. A production incident usually requires additional investigation. Preserve competing hypotheses until evidence distinguishes them, and avoid treating a plausible narrative as a verified mechanism.

A corrective action should address a concrete failure mode. Adding the missing consumer gate before activation is one action for the second case. Adding operation readback before retry is another. “Be more careful” is not an executable control. A regression should recreate the dangerous condition and assert the preserved state or rejection behavior.

What remains outside this drill#

The child closes its database after commit, so this is not a test of storage behavior during power interruption. It does not test a remote acknowledgement channel, multiple concurrent publishers or recovery after the entire Docker engine loses its disk. The full service project exercises additional process and container transitions, but each evidence layer still has a defined boundary.

A real disaster-recovery plan may require restoring backups, replaying source logs, rotating credentials or rebuilding infrastructure. Those actions need their own tested procedures. Do not generalize from a successful local rollback to a promise that every failure can be recovered with the same command.

Failure diagnosis and answered interview discussion#

If a supervisor duplicates an operation after a nonzero exit, inspect whether it reconciles durable receipts before retrying. If rollback overwrites newer work, inspect expected-version checks. If recovery removes diagnostic history, inspect whether cleanup is coupled unnecessarily to activation. If a drill passes only when logs are present, inspect whether it depends on buffered messages instead of durable state.

An interviewer may ask, “What would you do when a job failed after writing?” Explain the source-bound readback and accepted-state check before deciding to retry. If asked whether execution success means release acceptance, distinguish computation from consumer gates. If asked what makes an operational drill meaningful, identify a real failure boundary, explicit ownership, independent readback and a verified recovery outcome.
