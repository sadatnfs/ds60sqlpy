# js-004: Functions, scope and closures

## Level and prerequisites

Beginner, approximately 90 minutes. Direct prerequisites: `js-003`

## Learning objectives

Write pure functions and independent closures, explain let versus var capture and validate a factory's configuration.

By the end you can call a pure function, build independent closures, compare let and var loop capture, distinguish undefined from null defaults, observe an ordinary receiver, and reject an invalid factory configuration.

## Purpose and mental model

Functions define reusable computations, and lexical scope determines which bindings a function can read. A closure retains access to bindings from the environment where it was created. Those bindings can hold state across calls, which is useful for a small counter or factory. Closures do not automatically copy every captured value. A shared var binding in a loop can make several functions observe the same final value, while let creates the intended per-iteration bindings.

Default parameters apply when an argument is undefined, not when it is null. Ordinary function this depends on the callsite; arrow functions capture this lexically. A clear function contract should distinguish arguments, returned values, mutable captured state and receiver dependence. Prefer explicit parameters when a closure would hide important dependencies.

## Vocabulary and concepts

**Lexical scope:** Binding lookup determined by where code is written.

**Closure:** A function retaining access to its surrounding bindings.

**Default parameter:** A fallback used when the supplied argument is undefined.

**Receiver:** The this value used by an ordinary method call.

## Syntax anatomy and execution trace

A function declaration introduces a named callable; an arrow expression creates a function value. Returning a nested function forms a closure over its surrounding bindings. let and const are block-scoped, while var is function-scoped. The default syntax name=value is evaluated when the argument is undefined. Use call or bind only when receiver behavior is part of the contract, not as a substitute for understanding the callsite.

## Worked example / walkthrough

### Example A: Call a pure function

The function depends only on its arguments and changes no external state. Boundary examples can be tested independently.

```javascript
import { strict as assert } from 'node:assert';

function counter(step = 1) {
  if (!Number.isInteger(step) || step <= 0) throw new TypeError('positive integer step required');
  let value = 0;
  return () => {
    value += step;
    return value;
  };
}

export async function verify() {
  // Worked example
  {
    function add(left, right) {
      return left + right;
    }
    assert.equal(add(2, 3), 5);
    assert.equal(add(-1, 1), 0);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));
```

**Expected:** 5 and 0.
### Example B: Build independent closures

Each factory call creates a separate captured binding. Equal initial values do not imply shared counter state.

```javascript
import { strict as assert } from 'node:assert';

function counter(step = 1) {
  if (!Number.isInteger(step) || step <= 0) throw new TypeError('positive integer step required');
  let value = 0;
  return () => {
    value += step;
    return value;
  };
}

export async function verify() {
  // Worked example
  {
    const first = counter();
    const second = counter();
    assert.equal(first(), 1);
    assert.equal(first(), 2);
    assert.equal(second(), 1);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));
```

**Expected:** first 1, 2; second 1.

## Prediction before your attempt

A `var` loop shares one binding that finishes at 3, while `let` creates a fresh binding per iteration, so the answers are 3, 3, 3 versus 0, 1, 2. ## Exercises

1. **Call a pure function: predict an edited check.** In a scratch copy of Example A, change `assert.equal(add(-1, 1), 0);` to `assert.equal(add(-2, 1), 0);` inside its check. Does the check still pass?
   **Expected:** The edited run fails with an `AssertionError` at `assert.equal(add(-2, 1), 0);`. Restoring `assert.equal(add(-1, 1), 0);` brings back: 5 and 0.
   **Verify:** The function depends only on its arguments and changes no external state. Use that rule to account for the actual and expected values in the `AssertionError`.

2. **Build independent closures: diagnose an edited check.** Example B's check was edited to read `assert.equal(second(), 2);`. Run it, explain the failure and restore the original.
   **Expected:** Before the repair the run fails with an `AssertionError` at `assert.equal(second(), 2);`. Restoring `assert.equal(second(), 1);` brings back: first 1, 2; second 1.
   **Verify:** Each factory call creates a separate captured binding. Keep the failing and repaired runs and compare the values each one reports.

3. **Compare let and var loop capture.** Create three closures in a let loop and three in a var loop.
   **Expected:** let returns 0, 1, 2; var returns 3, 3, 3.
   **Verify:** Keep `assert.deepEqual(shared.map((fn) => fn()), [3, 3, 3])`. Control: changing `for (var index = 0; index < 3; index += 1) shared.push(() => index);` to `for (var index = 0; index <= 3; index += 1) shared.push(() => index);` must make that check fail; then restore it.

4. **Distinguish undefined from null defaults.** Call a greeting function with no argument, undefined and null.
   **Expected:** default used for the first two; null preserved.
   **Verify:** Keep `assert.equal(label(), 'guest')`. Control: changing `function label(value = 'guest') {` to `function label(value = 'guest!') {` must make that check fail; then restore it.

5. **Observe an ordinary receiver.** Call a method through its object and then with an explicit alternate receiver.
   **Expected:** 4 and 9.
   **Verify:** Keep `assert.equal(item.read.call({ value: 9 }), 9)`. Control: editing it to `assert.equal(item.read.call({ value: 10 }), 9);` must make the check fail; then restore it.

6. **Reject an invalid factory configuration.** Create a step counter with nonpositive or noninteger step.
   **Expected:** TypeError for 0 and 1.5; step 2 yields 2, 4.
   **Verify:** Keep `assert.deepEqual([next(), next()], [2, 4])`. Control: changing `const next = counter(2);` to `const next = counter(3);` must make that check fail; then restore it.

## Common pitfalls and diagnosis

Detaching a method, as in `const f = shape.area`, loses its receiver: in a module the call `f()` sees `this` as `undefined` and throws when it reads a property. When a method fails only after being passed as a callback, inspect how it is called, not how it is defined. ([Diagnosing a failure](../STUDY-GUIDE.md#diagnosing-a-failure).)

## Progressive hints

Reveal one hint at a time ([using the hints](../STUDY-GUIDE.md#using-the-hints)).

- **Exercise 1:** Compute the checked value with `assert.equal(add(-2, 1), 0);` in place before running it.
- **Exercise 2:** Compare `assert.equal(second(), 2);` with the original line and state the claim each version makes.
- **Exercise 3:** The difference is binding lifetime, not the time the function body was parsed. Trace each value that `assert.deepEqual(shared.map((fn) => fn()), [3, 3, 3])` reads.
- **Exercise 4:** A default parameter does not define a general missing-value policy. Trace each value that `assert.equal(label(), 'guest')` reads.
- **Exercise 5:** The same function can operate on different receivers. Trace each value that `assert.equal(item.read.call({ value: 9 }), 9)` reads.
- **Exercise 6:** Validate the configuration when the closure is created so every later call can rely on its invariant. Trace each value that `assert.deepEqual([next(), next()], [2, 4])` reads.
