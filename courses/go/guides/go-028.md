# go-028: Bounded worker pools and result ordering

## Level and prerequisites

## Why this mechanism matters

A worker pool limits active execution but does not create infinite capacity. Queues, in-flight tasks and result buffers all consume resources. Give each task an identity so completion order can differ from presentation order. A collector can place results by index to produce a deterministic final sequence. The producer owns input closure, workers process tasks, and a joiner closes results after all senders exit. Cancellation and partial failure need an explicit policy rather than silently losing tasks. This example performs bounded integer work and joins every goroutine. It illustrates coordination without claiming that more workers always make a program faster.

## Vocabulary and concepts

- **Concurrency bound:** The maximum number of active workers.
- **Task identity:** A stable key linking result and input.
- **Fan-in:** Combining results from multiple producers.

## Syntax anatomy and reasoning

A jobs channel carries indexed tasks. Start a bounded number of workers, feed jobs and close input. A WaitGroup tracks workers; close results only after Wait completes. Assign each result to its input index. Reject zero workers before starting the pipeline, otherwise a producer may block forever with no consumer.

## Worked example / walkthrough

### Worked example 1: Preserve input order

Square 3, 1 and 2 with two workers.

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type squareTask struct{ Index, Value int }

func parallelSquares(items []int, workers int) ([]int, error) {
	if workers < 1 || workers > 8 {
		return nil, errors.New("workers must be 1 through 8")
	}
	jobs := make(chan squareTask)
	results := make(chan squareTask)
	var wg sync.WaitGroup
	for i := 0; i < workers; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for task := range jobs {
				task.Value *= task.Value
				results <- task
			}
		}()
	}
	go func() {
		for i, v := range items {
			jobs <- squareTask{i, v}
		}
		close(jobs)
	}()
	go func() { wg.Wait(); close(results) }()
	out := make([]int, len(items))
	for result := range results {
		out[result.Index] = result.Value
	}
	return out, nil
}

func main() {
	// Preserve input order
	{
		v, err := parallelSquares([]int{3, 1, 2}, 2)
		check(err == nil && len(v) == 3 && v[0] == 9 && v[1] == 1 && v[2] == 4, "order")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** The result is 9, 1, 4.

Indices restore presentation order. Channel arrival order is not the input-order contract.

### Worked example 2: Handle empty input

Run the pool on an empty slice.

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type squareTask struct{ Index, Value int }

func parallelSquares(items []int, workers int) ([]int, error) {
	if workers < 1 || workers > 8 {
		return nil, errors.New("workers must be 1 through 8")
	}
	jobs := make(chan squareTask)
	results := make(chan squareTask)
	var wg sync.WaitGroup
	for i := 0; i < workers; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for task := range jobs {
				task.Value *= task.Value
				results <- task
			}
		}()
	}
	go func() {
		for i, v := range items {
			jobs <- squareTask{i, v}
		}
		close(jobs)
	}()
	go func() { wg.Wait(); close(results) }()
	out := make([]int, len(items))
	for result := range results {
		out[result.Index] = result.Value
	}
	return out, nil
}

func main() {
	// Preserve input order
	{
		v, err := parallelSquares([]int{3, 1, 2}, 2)
		check(err == nil && len(v) == 3 && v[0] == 9 && v[1] == 1 && v[2] == 4, "order")
	}

	// Handle empty input
	{
		v, err := parallelSquares(nil, 2)
		check(err == nil && len(v) == 0, "empty")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** It returns an empty result and terminates.

Every channel reaches its owned closure point even when no jobs exist.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.
