## The question and the mechanism

Reconcile order-date and ship-date totals without changing the fact amounts.

A fact can have several date roles. Our Sales rows have OrderDate and ShipDate, but the shared Date dimension's ordinary active relationship uses OrderDate. A month selection therefore means order month unless a measure deliberately activates the shipment relationship. A report title does not change that model behavior.

USERELATIONSHIP selects an existing relationship for the calculation. It does not create a relationship between arbitrary expressions, and it does not mutate the model's permanent active setting. For this pair of date roles, activating the shipment relationship displaces the ordinary order-date path for that calculation.

S6 is ordered on January 5 and shipped on February 1. It contributes 20 to January order revenue but February shipment revenue. The total amount remains unchanged; attribution across periods changes. This is the exact kind of case that should appear in a date-role regression matrix rather than relying only on orders shipped within the same month.

## Vocabulary and expression anatomy

The reference supplies the two existing relationship endpoint columns to USERELATIONSHIP. The outer Year and MonthNumber filters come from Date, then travel along the selected relationship. Both roles use the same NetRevenue expression and USD amounts.

Concepts to explain in your own words: **active relationship**, **inactive relationship**, **USERELATIONSHIP**, **role-playing date**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: January order versus shipment attribution

**Starting context:** Date year 2025/month 1; compare active OrderDate with the explicitly selected ShipDate relationship.

```dax
EVALUATE CALCULATETABLE ( ROW ( "OrderRevenue", [NetRevenue], "ShipRevenue", CALCULATE ( [NetRevenue], USERELATIONSHIP ( Sales[ShipDate], 'Date'[Date] ) ) ), 'Date'[Year] = 2025, 'Date'[MonthNumber] = 1 )
```

**Context trace:**

1. Orders S4,S5,S6 belong to January and total 67.
2. Shipments S4 and S 5 occur in January and total 47.
3. S6's 20 moves to shipment month February.

**Hand-derived worked-reference result:**

| OrderRevenue | ShipRevenue |
| --- | --- |
| 67 | 47 |

The 20 difference is explained by a timing boundary, not a lost transaction or a changed revenue formula.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: February absorbs the delayed shipment

**Starting context:** Date year 2025/month 2 with the same role comparison.

```dax
EVALUATE CALCULATETABLE ( ROW ( "OrderRevenue", [NetRevenue], "ShipRevenue", CALCULATE ( [NetRevenue], USERELATIONSHIP ( Sales[ShipDate], 'Date'[Date] ) ) ), 'Date'[Year] = 2025, 'Date'[MonthNumber] = 2 )
```

**Context trace:**

1. Orders S7,S8 total 56 in February.
2. Shipments include S6,S7,S8, totaling 76.
3. Across January and February, both date-role totals reconcile to 123.

**Hand-derived worked-reference result:**

| OrderRevenue | ShipRevenue |
| --- | --- |
| 56 | 76 |

Monthly attribution changes while the combined-period amount reconciles. A wider window is useful for checking that a role change has not duplicated facts.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.
