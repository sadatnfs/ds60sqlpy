# web-050: Password hashing and authentication boundaries

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-049`

## Learning objectives

Build a password-verification demonstration without printing the hash or secret. List the additional controls required around a real login. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

Passwords should not be stored as plaintext or encrypted with a reversible key merely so the application can compare them. A password hash is designed to make verification possible without retaining the original password and to impose a computational cost on guessing. Use a maintained password-hashing API rather than inventing a hash-plus-salt scheme. The encoded result records the algorithm and parameters needed for verification.

Authentication establishes an identity claim; it does not decide which objects that identity may access. A complete login flow also needs transport security, rate limiting, useful but nonrevealing errors, session rotation and account-recovery design. One successful hash comparison is only a primitive test, not a complete authentication system.

## Syntax anatomy and mechanism

Use password_hash and password_verify. Allow storage large enough for future encoded formats, and use password_needs_rehash during a deliberate migration policy. Algorithm support and cost depend on the prepared runtime; the example uses bcrypt with an explicit bounded teaching cost. Production parameters require current guidance and measurement. Bcrypt has a byte-length limit that must not be ignored when designing input policy.

## Worked example / walkthrough

### Worked example 1: Hash and verify

The library manages the encoded salt and parameters.

```php
$hash = password_hash('synthetic-demo-passphrase', PASSWORD_BCRYPT, ['cost' => 10]);
$valid = password_verify('synthetic-demo-passphrase', $hash);
```

**Expected observation:** The correct synthetic phrase verifies without storing plaintext.

### Worked example 2: A wrong candidate

Verification does not reveal the original phrase.

```php
$wrong = password_verify('different-phrase', $hash);
```

**Expected observation:** The wrong candidate returns false.

## Debugging and common mistakes

Never copy the teaching passphrase into a real account or print password hashes as routine diagnostics. Do not invent a manual salt. A stronger hashing parameter cannot compensate for an unbounded public login endpoint.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.
