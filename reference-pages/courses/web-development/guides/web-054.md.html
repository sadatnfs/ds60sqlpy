web-054: JSON APIs, schemas and consistent error responses#

Level and prerequisites#

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: web-053

Learning objectives#

Build a response model that maps success and validation failure consistently. Explain a backward-compatible versus breaking API change. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

Purpose, vocabulary and mental model#

An API contract describes inputs, outputs, error behavior and relevant operational limits. JSON is only the serialization format. A client needs to know whether minutes is an integer, whether a field can be null, which errors are recoverable and whether an operation changes state. Adding a field can be compatible for some clients while changing its meaning or type can break them.

Error responses should be structured and consistent without exposing internal exceptions. A validation error can identify fields; an unexpected internal error should provide a safe message and a correlation mechanism in a real deployment. Status codes, headers and body must agree. Returning a JSON error object with an unconditional 200 status makes clients and monitoring misinterpret failures.

Syntax anatomy and mechanism#

Keep a response builder separate from the domain function. Encode with JSON_THROW_ON_ERROR and declare application/json in the real HTTP adapter. Decode test output and inspect types rather than comparing arbitrary whitespace. This CLI lesson models the response; the external HTTP fixture later checks actual status and headers. It does not enable cross-origin access automatically.

Classroom execution and offline inputs#

Choose the PHP CLI worker in the classroom. The pad is staged as main.php and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write <?php at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

Worked example / walkthrough#

Worked example 1: A successful representation#

The type contract is visible in the record.

$body = ['topic' => 'CSS', 'minutes' => 30, 'complete' => false];

Expected observation: Minutes is numeric and complete is boolean, not display strings.

Worked example 2: A validation error#

A field map supports useful client feedback.

{"error":{"code":"invalid_plan","fields":{"minutes":"Use 5 to 120 minutes."}}}

Expected observation: The error shape is predictable and contains no stack trace.

Six progressive exercises#

Exercise 1: Distinguish a JSON number from a numeric-looking string.#

Expected evidence: 30 and "30" have different JSON types and can affect client validation.

Progressive hint: Trace the smallest example before editing. Name which values are source and which are observations.

Exercise 2: Add a consistent error code to invalid-input responses.#

Expected evidence: Clients can inspect a stable code without parsing human prose.

Progressive hint: Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

Exercise 3: Build a response model that maps success and validation failure consistently.#

Expected evidence: Status, content type and JSON body agree with the declared contract.

Progressive hint: Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

Exercise 4: Diagnose an internal exception serialized directly to a public response.#

Expected evidence: Translate it at the boundary and keep sensitive details in controlled diagnostics.

Progressive hint: Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

Exercise 5: Round-trip a Unicode label and a boolean through JSON.#

Expected evidence: The decoded values retain their intended types and text.

Progressive hint: Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

Exercise 6: Explain a backward-compatible versus breaking API change.#

Expected evidence: Compatibility depends on the documented client contract, especially type and semantic changes.

Progressive hint: Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

Debugging and common mistakes#

Do not append debugging output before or after a JSON body. Avoid exposing raw exception messages. A local encode/decode test does not prove actual Content-Type or status headers on a server.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

Retrieval, transfer and next steps#

Close the worked answers and explain API contract, JSON response, schema without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
