web-032: Values, types, strict comparisons and null#

Level and prerequisites#

Beginner; allow about 90 minutes, with extra time for independent practice. Direct prerequisites: web-031

Learning objectives#

Model an optional note without confusing missing, empty and null. Explain the limited scope of strict_types. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

Purpose, vocabulary and mental model#

A value has a type that influences allowed operations and comparison behavior. PHP provides integers, floating-point numbers, strings, booleans, arrays, objects and null among its types. Null commonly represents absence, but its meaning belongs to the application's contract. Zero, an empty string and false are different values and should not be casually treated as interchangeable missing data.

Loose comparison can coerce values before comparison; strict comparison checks both type and value. The string '0' and integer 0 may look similar when printed but are different under strict equality. A form normally supplies strings, so validation and explicit conversion are necessary before treating them as trusted numeric data. Strict typing at function boundaries does not validate arbitrary request arrays.

Syntax anatomy and mechanism#

Use === and !== when type distinctions are part of the contract. get_debug_type helps inspect the type. The null-coalescing operator ?? supplies a default for an absent or null value, while array_key_exists can distinguish a present null entry from a missing key. Floating-point values approximate many decimal fractions, so financial examples later use integer minor units.

Classroom execution and offline inputs#

Choose the PHP CLI worker in the classroom. The pad is staged as main.php and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write <?php at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

Worked example / walkthrough#

Worked example 1: Type matters#

The printed characters do not determine the comparison semantics.

$text = '0';
$number = 0;
var_export($text === $number);

Expected observation: The strict comparison is false.

Worked example 2: Missing versus null#

The application decides whether null is meaningful.

$record = ['note' => null];
var_export(array_key_exists('note', $record));
var_export($record['note'] ?? 'No note');

Expected observation: The key exists, but the coalescing expression uses the fallback.

Six progressive exercises#

Exercise 1: Predict strict equality for '0', 0 and false.#

Expected evidence: Each has a different type, so cross-type strict comparisons are false.

Progressive hint: Trace the smallest example before editing. Name which values are source and which are observations.

Exercise 2: Add a typed diagnostic to a value before converting it.#

Expected evidence: The output identifies the actual type rather than relying on its printed appearance.

Progressive hint: Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

Exercise 3: Model an optional note without confusing missing, empty and null.#

Expected evidence: The program documents and checks the chosen interpretation of each state.

Progressive hint: Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

Exercise 4: Repair a loose comparison that accepts an unintended type.#

Expected evidence: Use strict comparison after deliberate validation and conversion.

Progressive hint: Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

Exercise 5: Test zero as a valid numeric boundary.#

Expected evidence: Zero is retained when the contract permits it, rather than discarded as generic falsy data.

Progressive hint: Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

Exercise 6: Explain the limited scope of strict_types.#

Expected evidence: It affects relevant scalar call coercions; it does not replace runtime validation or static analysis.

Progressive hint: Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

Debugging and common mistakes#

Do not use empty() as a universal validation rule because it treats several distinct values as empty. Compare floating-point results with an appropriate tolerance when approximation is expected. A type declaration is not an input sanitizer.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

Retrieval, transfer and next steps#

Close the worked answers and explain integer, float, string without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
