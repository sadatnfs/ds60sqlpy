# k8s-029: Custom resources and structural schemas

## Level and prerequisites

Advanced; about 120 minutes plus review. Direct prerequisites: `k8s-028`.

## Learning objectives

Distinguish a custom resource instance from cluster-scoped API registration.

## Vocabulary and concepts

An API resource is a typed collection of objects, not necessarily a running process. A CustomResourceDefinition, abbreviated CRD, registers a new resource type with the API server. A custom resource is one instance of that type. Here the cluster-scoped registration is `lessonreports.learning.ds60sqlpy`, while hello-report is a namespaced LessonReport instance. Registering a schema does not install an operator or create a Deployment automatically.

The synthetic API describes a report application with message and replicas. A structural schema gives the server a typed shape it can validate and use for other API machinery. Our spec.message is one of two strings and spec.replicas is an integer from 1 through 2. These are deliberate course limits, not a generic configuration format. A desired instance can be valid yet remain unimplemented when no qualified controller observes it.

The normal module credential cannot register CRDs or create arbitrary custom resources. The live extension requires a separately provisioned advanced lease. Start by inspecting the complete registration in the linked fixture and the namespaced instance in the solution. Keep API registration, instance acceptance and application convergence as three separate evidence rows.

### Key terms

- **CustomResourceDefinition:** A cluster-scoped registration that adds a new resource type to the API, with its group, names, versions and schema.
- **Custom resource:** One instance of a type defined by a CustomResourceDefinition, stored and served by the API server like built-in objects.
- **Structural schema:** An openAPIV3Schema that declares a type for every field, which the API server uses to validate and prune custom resources.
- **Resource scope:** Whether a resource type is Namespaced or Cluster, which decides where its instances live.
- **Unknown-field pruning:** The API server dropping fields that the structural schema does not declare, unless the schema says to preserve them.

## Read the registration from outside inward

[The CRD fixture](../fixtures/k8s-029-crd.json) declares group learning.ds60sqlpy, plural `lessonreports` and kind LessonReport. The fully qualified API version in the instance combines group/version: learning.ds60sqlpy/v1. scope Namespaced means instances belong to a namespace; it does not make the CRD registration itself namespaced.

versions contains one entry with served true and storage true. Served means clients may use that version. Storage selects the representation persisted by the API server. Adding another served version later raises conversion and compatibility questions; changing a string without a migration plan is not an upgrade strategy. This chapter intentionally uses one version.

Under openAPIV3Schema, type object is followed by properties and required fields. Properties describe allowed shapes; required says which values must be present. A field being listed in properties does not by itself make it mandatory. Type validation also distinguishes an integer 1 from the string "1". YAML convenience must not erase the API contract.

## Separate desired state, status and unknown fields

spec records user intent. The status subresource is a separate write boundary for controller observations. Its observedGeneration should identify the spec generation actually reconciled. A learner-written ready: true is not a controller receipt, and a stale status describing an earlier generation cannot establish convergence for the current request.

Unknown-field handling needs an explicit test. Structural schemas can prune fields that are not preserved, and strict server-side field validation can reject unknown fields. Therefore the guaranteed negative controls here use a wrong type or out-of-range value. Do not claim every unknown field is rejected in every client mode. Read back the accepted object and record server behavior for the chosen request mode.

The offline checker only validates this tiny spec subset. It does not implement Kubernetes OpenAPI, admission, defaulting, authorization or conversion. Its purpose is to make the teaching values and boundary cases inspectable before a host-provisioned API test.

## Worked example / walkthrough

### Worked example 1: Read a valid instance

```yaml
apiVersion: learning.ds60sqlpy/v1
kind: LessonReport
metadata:
  name: hello-report
spec:
  message: hello
  replicas: 1
```

**Expected:** A namespaced LessonReport requests message hello and one replica; no Deployment follows from schema registration alone.

### Worked example 2: Trace two rejected variants

Keep the same object identity, but first change replicas to the string "2", then to integer 3. The first violates type; the second violates maximum. Compare those precise reasons with an unknown field named replcias, whose treatment also depends on field validation and pruning.

**Expected:** The two guaranteed invalid values fail different schema constraints. An unknown-field experiment must retain its actual rejection or readback behavior.

### Exercise 1: Map the two scopes

Identify the registration object and instance scope from the fixtures.

**Expected result/shape:** CRD is cluster-scoped; hello-report is namespaced.

**Verify:** Read `spec.scope` in the CRD and `metadata.namespace` in the instance.

**Progressive hints:** scope applies to custom resource instances.

### Exercise 2: Trace names and version

Connect group, version, kind, plural and metadata.name.

**Expected result/shape:** learning.ds60sqlpy/v1, LessonReport, `lessonreports` and hello-report are distinct fields.

**Verify:** Locate each value in its own field: `spec.group`, `spec.versions[].name`, `spec.names.kind`, `spec.names.plural` and the instance's `metadata.name`.

**Progressive hints:** Plural is a collection name; metadata.name identifies one object.

### Exercise 3: Predict schema negatives

Compare replicas 1, string 2, integer 3 and a missing message.

**Expected result/shape:** Only integer 1 with a present allowed message passes the stated complete spec.

**Verify:** Check each candidate against the schema's required list, type and range separately; one failed rule is enough to reject it.

**Progressive hints:** Check required, type and range separately.

### Exercise 4: Inspect unknown-field handling

Use the supplied replcias typo in a qualified server request and readback.

**Expected result/shape:** Record validation mode and actual rejection or pruning; do not assume silently stored intent.

**Verify:** Read the object back from the server and compare it with what you sent; record the field validation mode the request used.

**Progressive hints:** Look at the returned object, not only the input file.

### Exercise 5: Separate status from intent

Compare spec generation 7 with status observedGeneration 6 and ready true.

**Expected result/shape:** Current generation 7 is not yet proven reconciled by that status.

**Verify:** Compare `metadata.generation` with `status.observedGeneration` before reading any status condition.

**Progressive hints:** Ask which request the condition describes.

### Exercise 6: Plan scoped teardown

List which operations belong to learner instance cleanup and host API-registration cleanup.

**Expected result/shape:** Instance UID cleanup is separate from CRD removal; no learner privilege widening.

**Verify:** Separate the commands by scope: instance deletion uses the instance name and UID, while CRD removal is a cluster-scoped host operation.

**Progressive hints:** Deleting a type is broader than deleting one instance.

## Self-check

An instance with an unknown field was accepted, and reading it back shows the field missing. What happened under structural schema pruning, and how does that differ from a strict validation rejection?

## Common pitfalls

A no-matches-for-kind error suggests registration or discovery/version trouble. Forbidden suggests credentials lack authorization. A schema validation error should name a field and constraint. An accepted instance with no child workload suggests missing or failing reconciliation. Those errors require different repairs.

Do not grant the learner cluster-admin to make the example work. The host owns registration and the lease must provide only the intended namespaced instance operations. Removing a CRD can remove its stored custom resources, so registration cleanup is a separate host responsibility after instance/controller cleanup.
