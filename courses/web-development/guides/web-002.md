# web-002: Elements, attributes, nesting and text escaping

## Level and prerequisites

Beginner; allow about 90 minutes, with extra time for independent practice. Direct prerequisites: `web-001`

## Learning objectives

Build a notes paragraph with nested importance and literal angle brackets. Explain escaping versus validation with a text and URL example. Use element, attribute and nesting accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

An attribute adds information to an opening tag. In `<html lang="en">`, the attribute name is lang and its value identifies the document language. Attribute values should be quoted consistently. Nesting means one element's content contains another element; the resulting parent-child relationship matters to styling, accessibility and scripts. A paragraph can contain emphasized text, but a list does not belong inside that paragraph.

HTML has special syntax characters. A less-than sign begins markup, so literal comparison text may need `&lt;`. An ampersand begins a character reference and is commonly represented as `&amp;`. Escaping means representing text so a parser treats it as data. It is different from deleting characters and different from making an unsafe URL safe.

## Syntax anatomy and mechanism

Close nested elements in reverse order: open paragraph, open strong, close strong, close paragraph. Void elements such as `br` and `img` have no closing tag. A `data-*` attribute stores page-specific metadata; it does not create a visible label. `id` must uniquely identify an element in the document. Class names may repeat because they group related elements.

## Worked example / walkthrough

### Worked example 1: Nested emphasis

The strong element identifies importance within the paragraph.

```html
<p>Save <strong>before</strong> closing.</p>
```

**Expected observation:** The word before has semantic importance and typically bold styling.

### Worked example 2: Literal comparison

Character references preserve the intended data.

```html
<p>2 &lt; 3 &amp; 3 &gt; 2</p>
```

**Expected observation:** The reader sees 2 < 3 & 3 > 2.

## Six progressive exercises

Exercises that ask you to predict, explain, compare or diagnose keep their answers in the solutions file. The others show the evidence to look for.

### Exercise 1: Predict the text content after character references are parsed.

**Progressive hint:** Read &lt; and &amp; as instructions to the parser rather than as visible text.

### Exercise 2: Add a language attribute and explain its role.

**Expected evidence:** The root lang attribute identifies the language for pronunciation and processing.

**Progressive hint:** Look at the html start tag and think about how a screen reader chooses a pronunciation.

### Exercise 3: Build a notes paragraph with nested importance and literal angle brackets.

**Expected evidence:** The structure remains a paragraph and the comparison is text rather than an element.

**Progressive hint:** Use strong or em inside the paragraph and write the comparison with &lt; and &gt;.

### Exercise 4: Repair overlapping emphasis tags by drawing their tree.

**Expected evidence:** Each opened element is closed before its parent closes.

**Progressive hint:** Draw each start and end tag as a box; boxes may nest but never cross.

### Exercise 5: Add two related notes without duplicating an id.

**Expected evidence:** Shared class names group them while each id remains unique.

**Progressive hint:** Decide what must identify exactly one element and what only groups elements for styling.

### Exercise 6: Explain escaping versus validation with a text and URL example.

**Progressive hint:** Ask what each step protects: displaying a value exactly as text, or deciding whether the value is allowed at all.

## Debugging and common mistakes

A page that looks correct can still contain an unintended parser repair. Inspect the Elements tree rather than relying only on View Source. Never teach `innerHTML` as a general way to insert untrusted text.

Keep the failing source, the viewport width and what you observed, then repair one cause at a time. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order, so inspect the element and its computed styles in the browser's developer tools instead of trusting the rendering alone.
