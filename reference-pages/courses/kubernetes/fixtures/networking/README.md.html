Deep networking fixtures and owned host-lab boundary#

These are original synthetic teaching inputs for k8s-043 through k8s-066. They are not a saved cluster observation. No file contains a real kubeconfig, credential, cloud endpoint or public certificate. Addresses in topology.json are examples only. Do not contact them.

What is maintained here#

  • topology.json: distinct node, Pod and Service ranges; two endpoint identities; explicit readiness; three policy cases.
  • deployment.yaml and service.yaml: a non-root bounded app and ClusterIP mapping from 80 to named port 8080, using the separately preloaded course fixture image.
  • headless.yaml: direct Pod discovery without an ordinary ClusterIP. A/AAAA clients connect to the actual endpoint port 8080; there is no Service port 80 to 8080 proxy translation.
  • network-policy.yaml: an AND relationship between namespace and Pod selectors for ingress to 8080.
  • ingress.yaml: a manual HTTP route requiring an explicitly prepared IngressClass called study-controller.
  • gateway.yaml: Gateway and HTTPRoute requiring the APIs and a compatible GatewayClass called study-controller.
  • dual-stack-service.yaml: API intent requiring a dual-stack-capable cluster. The supplied app server binds IPv4 only, so IPv6 traffic additionally requires a separately reviewed IPv6/dual-stack listener and client.
  • lesson-inventory.json: reading-only lesson coverage and capability boundaries, not runtime receipts.

Names alone are insufficient because an object may have been replaced. Do not delete a namespace or run a broad label deletion from this README. Policy and endpoint interpretation#

A podSelector-only policy peer selects Pods in the policy’s own namespace. A namespaceSelector-only peer selects all Pods in matching namespaces. Both selectors in one peer combine as AND; separate peers combine as alternatives. A Pod-to-Pod connection must satisfy source egress and destination ingress when each is isolated. Reply traffic for an allowed connection is implicitly allowed; that does not allow an unrelated new reverse connection. The synthetic cases include an egress-blocked caller even though its destination ingress labels match.

Headless discovery returns individual Pod destinations and does not provide an ordinary Service port translation. Inspect EndpointSlice ports or actual SRV answers, and connect to the target listener. Do not assume the manifest’s Service port 80 is a proxy endpoint for this headless 8080 server.

Exact successful application requests#

The original IPv4 fixture serves GET /version with HTTP 200 and exact text ds60-fixture-v1 plus a newline; GET /ready returns ready plus a newline. GET / returns 404 by design. An Ingress/Gateway Prefix rule for / forwards /version as /version unless a separately documented rewrite is configured. Use /version for the positive application acceptance request. A correctly routed root404 is not evidence that the network failed.

For the ordinary ClusterIP fixture, an in-cluster client requests http://network-study:80/version. For the headless fixture, A/AAAA resolution returns Pod addresses and the client connects to the actual listener 8080, for example http://network-study-headless:8080/version with an appropriate client selection policy. SRV-aware clients inspect _http._tcp.network-study-headless within the actual namespace/domain and honor each returned target and port; A/AAAA-only clients do not receive a port from DNS. There is no headless Service port 80 to 8080 proxy translation.

The separate dual-stack application supplies an actual IPv6-capable listener and family-specific bounded client, alongside explicit cluster prerequisites and its own image identity. It remains manual-only and does not change the original admitted IPv4 verifier contract.
