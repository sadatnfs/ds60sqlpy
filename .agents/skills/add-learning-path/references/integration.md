# Registration and verification boundaries

Read only the section needed for the selected change. The maintained
[module contract](../../../../docs/implementation/ADDING_A_MODULE.md) owns exact
field descriptions; inspect loader code when extending the schema.

## Legacy Python, SQL and bridge

`curriculum/catalog.json` is generated by `catalog_builder.py` and
`scripts/build_catalog.py`. Preserve the historical IDs and day labels.
Existing named lessons use their established specifications and artifacts.
`curriculum/extensions/` supports additive legacy tracks and goals, with schema
examples outside the active directory. It is not the default registration path
for a modern module subject.

New legacy IDs use `curriculum/practice_expansion.json`; the baseline file is
immutable. Run `audit_practice.py` and `audit_lesson_depth.py` as well as the
subject's behavioral tests. SQL checks need PostgreSQL semantics, exact row
grain and ordering, explicit transaction/persistence behavior, and only the
local disposable database. Python notebooks need clean-kernel evidence in
addition to JSON validation. Bridge fakes prove policy, not server behavior.

Engine-specific query files keep their native identity. The owned Hive project
uses `.hql` sources, generic SQL highlighting and a native Hive lifecycle gate;
they are not PostgreSQL pad artifacts. Its two explicit layout-preservation
entries explain that boundary. Do not bypass PostgreSQL syntax/control proofs
to accommodate another dialect, or mark a new dialect executable merely because
the reader can display it. Define and actually qualify its reviewed runtime.

## Authored modules

Existing first-generation subjects use their plan under
`docs/expansion/plans/`. Additive subjects use `courses/<subject>/track.json`.
`ModuleCatalog` combines both route sources and admits authored records through
`courses/<subject>/lessons.json`. Read `modules.py` and `module_extensions.py`
under `src/ds60sqlpy/`. They reject duplicate IDs, graph cycles, unsafe paths,
unsupported profiles and malformed records.

Use Java's plan and manifest as a schema reference, without modifying Java
when adding another subject. Additive plans currently require all three stages;
keep a partial proposal outside active registration until it has a meaningful
full plan. A plan is not an authored lesson. Add only complete real bundles to
the authored manifest and keep incomplete work visibly planned.

`variants` is a curated alternate implementation of one canonical objective.
Its alias, such as `spark-013@pyspark`, has separate saved source and jobs.
Copy the exact existing schema, not a guessed field list. A new objective
requires a new canonical lesson.

The statistics book retains its dedicated loader and coverage contract. New
additive tutorial subjects use normal track/lesson manifests with validated
track-level `learning_mode: "tutorial"`; omitted mode is `practice`. Complete
worked `source_path` remains required, while tutorial solution paths may be
empty. Arbitrary books are not auto-discovered from a `manifest.json` filename.

## Runtime and UI

The supported runtime target is Linux Docker containers. Windows uses WSL 2;
macOS uses its Docker engine's Linux environment. New subjects must join those
workers and the Linux CI matrix. Retain Windows Docker wrappers, but do not add
native Windows backend, ACL or executable-build qualification gates. Native backend installers, desktop executables and editor-launch APIs are retired.
Contributor `ds60 serve` uses the same classroom shell with actual local capabilities. A Linux
runtime pass does not validate a host's WSL installer or engine configuration.

Inspect current definitions before declaring support:

- `modules.py`: language/profile and verifier allowlists.
- `module_jobs.py`: fixed services and validated worker endpoints.
- `worker_operations.py`: source filename, fixed compile/run argv and deadlines.
- `docker/workers/` and Compose: prepared dependencies, images and isolation.
- `scripts/classroom.sh` and `scripts/classroom_images.sh`: profile and image selection.
- `docker/classroom-images.tsv`: ordinary image inventory and explicit distribution tags.
- `.github/workflows/publish-images.yml` and `scripts/docker_release.py`: native builds for marked main commits, staging and gated promotion.
- `./classroom publish` and `scripts/publish-images`: separate single-architecture preview/`--push` route.
- `course_paths.py`, `scripts/course_payload.py`, `scripts/build_starter.py`: portable source staging.
- `scripts/format_repo.py`, `scripts/lint_repo.py`, `docker/formatting/`: prepared style and static validation.
- `classroom.py` and `assets/classroom.js`: derived directory and accessible themes.

Python filenames are under `src/ds60sqlpy/`. A new subject reusing an existing
profile needs no new worker. Check profile-specific package locks, not the
host's installed modules. C++ stages `main.cpp`; Java stages `Main.java` with
public `Main` and no package; Node runs `main.mjs`; TypeScript uses `main.mts`
with strict NodeNext compilation; Scala uses `Main.scala` and `object Main`.
Spark runs in bounded local mode. Browser DOM code cannot run in Node.

The additional Linux profiles stage `main.c` for C17, `main.go` for Go,
`Program.cs` for the fixed C# project, `main.rs` for Rust with prepared Arrow,
and `main.swift` for Swift 6 Linux. Their commands and dependencies are owned by
the backend; source cannot install packages or replace project files. SwiftUI,
UIKit and signing remain a separate macOS/Xcode project route.

The `javascript-browser` profile is a real opaque-origin classroom iframe with
bundled D3 7.9.0, `#chart`, `#output` and asynchronous source execution. It uses
`.js` files, inline synthetic inputs and no imports or fetches. Browser records
are source-bound client observations with `verified: false`, no return code and
no typed worker checks. Qualify them with `scripts/check_d3_browser.py` through
the actual UI, including isolation, interactions, history and stale navigation.
Do not add browser-only code to ordinary Node or worker qualification. A completion
marker establishes only the initial run boundary. Browser references must remain
error-free after representative keyboard/pointer interactions, resizing and
navigation. Inspect the settled painted result and current error/status output;
a sandbox-handled interaction error may not appear as an uncaught parent-page
exception. Preserve the earlier receipt, and save a new observation explicitly
when testing a later interaction result. Resize observers should schedule DOM
writes outside their notification callback and clean up observers/animation
work when the preview ends.

The `html-browser` profile accepts a complete HTML document, embedded CSS and
bounded inline JavaScript. Preserve native document parsing and lifecycle events;
external scripts/imports and navigation metadata are rejected. Source in a reader
stays escaped. Live preview is opt-in, debounced and cancelled on navigation,
Stop or history selection, without automatically creating result receipts.
Manual Run and explicit Save observation must preserve exact submitted source.
Use the web subject's browser and live-preview checkers against disposable state.

`php-cli` stages `main.php`, checks syntax then executes with PDO SQLite. It is
not an HTTP server and has no Composer channel. The web subject's separate
loopback HTTP fixture has its own ownership/session and lifecycle checks.

CUDA uses reading and CPU variants alongside explicitly prepared `cuda-cpp`,
`cuda-python`, `pytorch-cuda` and `tensorflow-cuda` profiles. GPU profiles remain
outside ordinary defaults/`--all`, require explicit compatible NVIDIA devices
and real allocation/kernel/readback probes. Preserve CPU framework routes and
separate device correctness from compilation or profiling. The external GPU
Spark route needs compatible versions and executed supported operators/plans;
no ordinary worker acquires cluster credentials or downloads a plugin.

Before designing an interactive CLI or a larger project, inspect the actual
arguments, standard-input, file and multi-file channels. Existing pads submit
source to fixed operations; arbitrary argv, interactive input, package installs
or project archives are not implied. A Cargo, Maven or other multi-file build
needs a bounded implemented channel or a clearly labeled, separately prepared
external workflow. Do not promise the single coding pad handles a project shape
that its adapter does not support.

Persistent learner state belongs to its storage adapter, never a source file
or container writable layer. Private worker credentials must stay out of
portable exports. A new external adapter needs explicit resource identity and
cleanup; manifests cannot supply arbitrary commands or host contexts.

An ordinary runtime joins both native architecture groups in the CI Hub set.
The opt-in trigger is a push to `main` with `[publish-docker]` in HEAD, using
repository secrets `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN`. Staging images and
small receipts must bind the source/profile/platform before promotion. Combined
tags use app `VERSION` and workers `VERSION-<catalog suffix>`; promote workers
before the app and move app latest last. Conflicting released versions require
a consistent source patch bump.

The manual `./classroom publish --to-hub USER --tag VERSION` route checks
existing images for one Linux architecture. Its `--profile` selects exact images
without implicit app/Core. Manual consumers use `--architecture-tags`; new Hub
selections otherwise use combined tags. Explicit latest resolves and saves a
matching concrete source version, and ordinary resume never pulls. Keep learner
volumes independent of image distribution and preserve older saved tag layouts.

A new ordinary runtime also needs a deterministic cataloged reference in
`CASES` of `scripts/check_classroom_profiles.py` and inclusion in the grouped
Docker workflow matrix. That checker uses an explicitly disposable classroom,
requires real source-bound reference execution with its expected output and
assertions plus declared typed checks where registered, and re-reads the saved
receipts after container replacement without running them again. Read its
`--help` and the workflow for invocation and prepared-project details. Do not
point its write mode at a learner's workspace. A subject reusing a profile does
not need another image or runtime matrix row.

`check_module_references.py` discovers all ordinary runnable references and book
examples from `ModuleCatalog`, including variants. A new lesson must execute in
its declared packaged worker and produce a matching source receipt; reading or
external workflows stay explicit. Use `--list-only` to review admission before
running the corpus on disposable state. New runtime profiles also need a real
syntax-failure case and diagnostic contract in `check_classroom_failures.py`.

Update expected subject sets in `check_classroom_browser.py`,
`check_classroom_ui.mjs` and their tests when adding a subject, then prove it
appears in Chromium with an accessible individual theme and separate saved work.
Browser-only language fixtures need real browser interaction checks. Kubernetes
references belong in the separate owned-cluster workflow and its reviewed
observation mapping. No model downloads or ambient cluster selection belong in
the ordinary qualification path. Read [validation](../../../../docs/validation.md)
for commands, artifacts and platform boundaries.

## Authoring and shared checks

There is no generic scaffold command. Read a subject's `authoring/README.md`
where present; some subjects are directly authored. Do not run another
subject's generator as a template over existing content.

Verified examples of subject-specific generation are:

```sh
python courses/javascript-typescript/authoring/build.py
python courses/deep-learning-pytorch/authoring/build.py
```

Run only the relevant generator. The shared sequence from a prepared environment
is:

```sh
./scripts/format-repo
python scripts/check_modules.py --json
python scripts/normalize_lesson_prose.py --write
make generate
./scripts/format-repo --check
./scripts/lint-repo
python scripts/normalize_lesson_prose.py
python scripts/check_content_rendering.py
python scripts/course.py validate
python scripts/audit_practice.py
python scripts/audit_lesson_depth.py
python scripts/build_course_guide.py --check
python scripts/build_lesson_readers.py --check
node scripts/check_classroom_ui.mjs
python -m pytest -n 4 --dist loadgroup
```

`make generate` covers the shared catalog, reports and readers,
not every subject's authoring pipeline. If Make is unavailable, inspect its
`generate` target and run those same Python commands in order. Do not edit
HTML output by hand. Rendering checks must preserve copied code and detect
unsupported equations. Run `python scripts/check_public_release.py` for public-source hygiene.
Additional lint/type checks are documented
in [validation](../../../../docs/validation.md).

Keep `--dist loadgroup` for shared database tests. Use focused selections first
and report optional runtime skips explicitly. Exercise compile failures,
incorrect results, timeout/cancellation, saved-source isolation and recovery in
the prepared worker and real UI when those contracts change. One platform's
success is not cross-platform acceptance. Do not alter a human's current pads
to test persistence; use an explicitly disposable test project and keep volumes
unless deleting them was authorized.


## Scientific runtimes, drafts and figures

R uses main.R and the r-statistics worker; its formatting runs in a separate
compatible R tools image. JAX and Bayesian Python have separate pinned CPU
profiles. Register source suffixes as well as language/profile names in modules.py.

DAX is a draft capability with no worker service. Its references are validated
against exact source and model bytes and contain typed hand-derived tables.
Never route its ready editing capability into ModuleJobs.start or infer execution
from a matching draft hash. Additive statistics tutorials use tutorials/index.json,
not another arbitrary manifest format.

Use plot_artifacts.py for bounded figures, tables and JSON reports, and the existing opaque Plotly renderer
for chart data. Never store an arbitrary HTML page as a trusted worker result.
Test metadata escaping, frame/image restrictions, plot storage failures, lazy
Python imports and saved-result readback. Compile TeX before shared reader
publication and preserve source/code byte contracts.

## Data, Stan and Julia adapters

- `data-engineering`: `main.py` with prepared Polars/Arrow/DuckDB, dbt Core/adapter
  and ML engineering packages. Root Python extras are a different environment.
- `data-platforms-python`: `main.py` with separately locked Arrow, DataFusion and
  PyIceberg library operations. Temporary files/catalogs do not persist between
  Runs. Ballista and actual platform services have separate prepared projects.
- `dbt-duckdb`: one `model.sql` in a fixed real project; compiled SQL, materialized
  result and run metadata are observed. Full project configuration and persistent
  state belong to the canonical Python examples or owned retail CLI fixture.
- `stan-cpu`: native `main.stan`, CmdStan 2.40.0, self-contained transformed-data
  fixtures, two seeded chains of 100 warmup plus 100 retained draws. Real data
  blocks use the separate CmdStanPy 1.3.0 project with explicit JSON and output.
- `julia`: `main.jl`, Julia 1.13.3, two threads and read-only prepared project/depot.
  The `DS60Plots` helper is classroom-specific, not a promise of Plots.jl.

The ML service fixture has owned training/control operations and a predictor
with a read-only state mount. Its loopback HTTP and persisted project state are
separate from ordinary pad execution and classroom learning volumes.
The Data and ML Engineering book adds the owned data-product and inference
projects: immutable data/pointer recovery and model/request/SSE history have
their own private state and explicit lifecycle gates. Follow their closest
guidance before changing schemas, receipt identities or failure behavior.

The Apache/open-data projects use engine access only from their host launcher,
never an ordinary worker. Consult the current environment ledger and each
project's qualification contract. A portable Atlas/Delta Sharing payload plan
is not server contact, and a checked component is not a complete topology.
The common workshop qualifier checks selected real services and exact retained
state. Its `--prepare` routes are explicit downloads, separate from lesson Run.

The native CI required-check contract lives in `scripts/ci_classroom.py`: Flight
and compiled Rust IPC join the data-platforms group, Kafka joins Java, inference
with Chromium joins PyTorch, and the data product joins data engineering. Keep
required checks, source/digest-bound receipts and publication validators aligned;
source registration or mocked tests cannot substitute for those native gates.

Formatting uses the pinned stanc adapter for Stan, JuliaFormatter/parse checks
for Julia, and SQLfmt for dbt SQL/Jinja. Preserve durable authoring programs and
refresh their exact guide fences. Package source/project/lock files deliberately;
exclude dbt target/log directories, databases, compiled models and trained state.

All captured kinds share the two-output/180,000-byte-per-payload/384,000-byte-total
budget. Tables have at most 12 columns and 100 rows; encode large integer IDs as
strings. Validate declarations through `scripts/declared_outputs.py` during the
reference corpus, then inspect actual browser/history output and retained
receipts after replacement. A capture warning cannot replace the real execution
status. Preserve scientific numerical oracles separately from shape/count checks.
