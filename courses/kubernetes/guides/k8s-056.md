## Purpose, vocabulary and mental model

Network address translation changes address or port fields as traffic crosses a boundary. Destination NAT changes where a packet is delivered; source NAT changes the apparent sender. Connection tracking can maintain state so replies follow the corresponding translated path. These mechanisms can make an application’s observed client address differ from the original caller.

Kubernetes traffic policies influence endpoint selection and source-address behavior, but exact paths depend on the Service type and implementation. externalTrafficPolicy Local can preserve source IP in common node-backed paths and restrict external traffic to local endpoints, with availability and load-distribution tradeoffs. It is not a universal declaration that every proxy will forward the original client address unchanged.

An HTTP proxy can also add forwarding headers. Those are application-layer claims, separate from the transport peer address. Trust them only from a configured proxy chain. A user-supplied header must not become an authoritative client identity merely because its name contains forwarded.

### Key terms

- **SNAT:** Source network address translation, which changes a packet's apparent sender, so a backend may see a node address instead of the client.
- **Connection tracking:** Kernel state that remembers each translated flow, so replies are translated back correctly.
- **externalTrafficPolicy Local:** A Service setting that sends external traffic only to backends on the receiving node, which can preserve the client source address because no second node hop applies SNAT.
- **Forwarding header:** An HTTP header that a proxy adds to carry the original client address. It is trustworthy only when a trusted proxy sets it.

## Mechanism and field-by-field reasoning

Track the source and destination tuple at each hop. A request arriving at nodeA may be forwarded to a Pod on nodeB, adding another route and potentially translation. A local-only policy can avoid that hop but requires an eligible local endpoint for the intended traffic.

The synthetic examples explain the tradeoff without asserting a particular provider behavior. A real source-IP test needs a known caller, a controlled server that reports its transport peer, and a documented proxy path. Do not infer it from a header alone.

## Trace the request or control path

```text
original clientIP:port -> node/LB translation -> backend peer address
reply -> connection state / routing -> original client
HTTP forwarding headers form a separate trust channel
```

The first line rewrites addresses: a node or load balancer changes the destination to a Pod and, under the Cluster policy, may also replace the source with its own address. The second line is why replies still find the client: connection tracking remembers the rewrite. The third line is a separate channel, since forwarding headers are only claims until a trusted proxy sets them.

## Six progressive exercises

### Exercise 1: Distinguish DNAT and SNAT.

**Expected evidence:** Destination rewrite versus source rewrite.

**Progressive hint:** Ask which field each rewrite changes: where the packet is going, or where it came from.

### Exercise 2: Predict backend peer identity after SNAT.

**Expected evidence:** It can be a node or proxy address rather than the original client.

**Progressive hint:** If a node rewrote the source, whose address does the Pod's socket report as the peer?

### Exercise 3: Draw a five-tuple path through one translation.

**Expected evidence:** Source/destination addresses and ports are named before and after.

**Progressive hint:** Write source IP, source port, destination IP, destination port and protocol on both sides of the translation.

### Exercise 4: Diagnose missing traffic on a node with Local policy and no endpoint.

**Expected evidence:** Endpoint locality and upstream health selection matter.

**Progressive hint:** Under Local policy a node forwards only to Pods on itself. Which fixture node has none ready?

### Exercise 5: Explain why arbitrary forwarded headers are untrusted.

**Expected evidence:** Clients can supply them unless the trusted proxy boundary sanitizes them.

**Progressive hint:** Who wrote the header? What stops a client from sending its own X-Forwarded-For value?

### Exercise 6: Design a source-IP acceptance test.

**Expected evidence:** Known caller, documented path, transport peer and trusted-header evidence.

**Progressive hint:** Name the caller, its path, the peer address the Pod reports and the header the trusted proxy set.

## Diagnosis, failure boundaries and common mistakes

Logging the socket peer and calling it the client address is the usual mistake; behind SNAT it is a node or proxy address. Switching to externalTrafficPolicy Local preserves the client address but drops traffic that arrives at nodes without a local ready endpoint, exactly what would happen on node-b in the fixture unless the load balancer's health check removes that node. The other trap is trusting X-Forwarded-For from anyone: a client can send any value unless the edge proxy overwrites it. Do not allowlist by header unless you know which proxy set it and that nothing else can reach the backend directly.
