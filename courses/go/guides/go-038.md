# go-038: Resource versions and optimistic concurrency

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-037

## Learning objectives

Implement optimistic concurrency that rejects stale resource versions and rereads current state before a retry. Along the way, explain optimistic concurrency, conflict, field ownership; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Optimistic concurrency protects a write from silently overwriting a newer observation. A client reads an object with resourceVersion, prepares a change and submits the version it observed. If another writer changed the object, the API can reject the stale write with a conflict. The correct response is usually to reread current state, recompute the intended change and retry within a budget. Retrying the identical stale object cannot resolve the conflict. Resource versions are opaque tokens, not counters for client arithmetic. Server-side apply and patch operations have additional field-management contracts that should not be confused with unrestricted last-writer-wins replacement.

## Vocabulary and concepts

- **Optimistic concurrency:** Rejecting a write when its observed version is stale.
- **Conflict:** Evidence that another state change invalidated a write assumption.
- **Field ownership:** Responsibility for a particular part of a shared object.

## Syntax anatomy and reasoning

This fixture represents an object as value plus opaque version. update requires equality with the observed token and returns a new server-selected token. A conflict is a typed outcome distinct from invalid input or access denial. Recompute from the new read rather than blindly replacing fields owned by another controller. Keep retries bounded and preserve context cancellation.

## Worked example / walkthrough

### Worked example 1: Accept a current version

Update value 2 using its current token a.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

var ErrConflict = errors.New("conflict")

type Versioned struct {
	Value   int
	Version string
	Labels  map[string]string
}

func versionUpdate(s *Versioned, observed string, value int, next string) error {
	if s.Version != observed {
		return ErrConflict
	}
	s.Value = value
	s.Version = next
	return nil
}

func main() {
	// Accept a current version
	{
		s := Versioned{Value: 2, Version: "a"}
		err := versionUpdate(&s, "a", 3, "b")
		check(err == nil && s.Value == 3 && s.Version == "b", "current update")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The value changes and token becomes b.

The new token is selected by the simulated server. A real client must not construct the next resourceVersion itself.

### Worked example 2: Reject a stale version

Attempt a write with old token a against current token b.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

var ErrConflict = errors.New("conflict")

type Versioned struct {
	Value   int
	Version string
	Labels  map[string]string
}

func versionUpdate(s *Versioned, observed string, value int, next string) error {
	if s.Version != observed {
		return ErrConflict
	}
	s.Value = value
	s.Version = next
	return nil
}

func main() {
	// Accept a current version
	{
		s := Versioned{Value: 2, Version: "a"}
		err := versionUpdate(&s, "a", 3, "b")
		check(err == nil && s.Value == 3 && s.Version == "b", "current update")
	}

	// Reject a stale version
	{
		s := Versioned{Value: 3, Version: "b"}
		err := versionUpdate(&s, "a", 9, "c")
		check(errors.Is(err, ErrConflict) && s.Value == 3, "conflict")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Conflict is returned and value stays unchanged.

The failed write does not overwrite newer state. The error is useful evidence about the caller assumption.

### Exercise 2: Reject a stale version: debug a regression

**Expected:** The defective run panics with `conflict`; after restoring `s := Versioned{Value: 3, Version: "b"}`, conflict is returned and value stays unchanged.

**Verify:** The failing run shows message `conflict`; after the repair `errors.Is(err, ErrConflict) && s.Value == 3` holds again.

### Exercise 3: Reread before retry

Read the current token after conflict and recompute an increment.

**Expected:** The new value is based on current state.

**Verify:** Your solution must keep `versionUpdate(&s, observed.Version, observed.Value+1, "c") == nil && s.Value == 5` true. Control: changing `check(versionUpdate(&s, observed.Version, observed.Value+1, "c") == nil && s.Value == 5, "reread")` to `check(versionUpdate(&s, observed.Version, observed.Value-1, "c") == nil && s.Value == 5, "reread")` panics with message `reread`; revert it.

### Exercise 4: Keep opaque tokens opaque

Use token rv:opaque rather than an integer.

**Expected:** Equality-based update succeeds.

**Verify:** Your solution must keep `versionUpdate(&s, "rv:opaque", 2, "next:opaque") == nil` true. Control: changing `s := Versioned{Value: 1, Version: "rv:opaque"}` to `s := Versioned{Value: 1, Version: "rv:opaque!"}` panics with message `opaque`; revert it.

### Exercise 5: Retain another field

## Common pitfalls and diagnosis

Retrying a conflicted write with the same object is the common error: the stale token conflicts forever, or, if the token is dropped, the write clobbers a newer change. On conflict, reread, recompute from current state and retry within a bound. Do not parse resourceVersion as a number, and do not send whole objects when you own only some of their fields.

## Progressive hints

### Hint for investigation 1: Accept a current version: change one input

1. Restate the expected observation: The value changes and token becomes b.
2. The supplied token equals the current one. What do Value and Version become?
3. The update now writes 4, so `s.Value==3` fails while the token still becomes b. The version check passed; the written value changed.

### Hint for investigation 2: Reject a stale version: debug a regression

1. Restate the expected observation: Conflict is returned and value stays unchanged.
2. The token a is stale against b. Does the update change anything?
3. Starting at Value 4, the conflict correctly leaves 4, so `s.Value==3` fails. Restore the initial 3; the stale write still changes nothing.

### Hint for investigation 3: Reread before retry

1. Restate the expected observation: The new value is based on current state.
2. The write uses the freshly read token and value. What is the result?
3. Recomputation preserves the intervening change.

### Hint for investigation 4: Keep opaque tokens opaque

1. Restate the expected observation: Equality-based update succeeds.
2. versionUpdate compares tokens only for equality. Does their format matter?
3. No parsing or arithmetic is needed.

### Hint for investigation 5: Retain another field

1. Restate the expected observation: The value and token change while the owner label is unchanged.
2. The update touches Value and Version only. What happens to Labels?
3. Real patches and apply operations should be scoped to fields the controller owns.

### Hint for investigation 6: Transfer bounded conflict handling

1. Restate the expected observation: Both attempts conflict and neither changes state.
2. Each attempt carries the same stale token. How many conflicts, and what value?
3. The counterexample explains why automatic retry must reread.
