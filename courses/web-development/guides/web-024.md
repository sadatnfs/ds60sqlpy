# web-024: HTML and CSS milestone: an accessible learning portal

## Level and prerequisites

Intermediate; allow about 180 minutes, with extra time for independent practice. Direct prerequisites: `web-023`

## Learning objectives

Build a complete offline portal with three paths and local destinations. Explain the portal's remaining backend requirements. Use information architecture, component system and responsive audit accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

A portal combines structure, navigation and repeated components around a user goal. Begin with the tasks: finding a topic, understanding prerequisites, choosing an action and reading progress. The information architecture groups content so those tasks are discoverable. A beautiful collection of cards is not enough if every label is vague or the reading order hides the main choice.

This milestone integrates the earlier mechanisms without requiring a framework. Semantic headings establish the outline, native links provide navigation, Grid or Flexbox distributes cards, and tokens maintain consistent spacing and color. Progress labels remain textual. The project uses synthetic data and does not claim persistent accounts or a working backend.

### Key terms

- **Information architecture:** The organization, labeling and navigation of content, so readers can find and understand what they need.
- **Component system:** A set of reusable patterns, such as a card or button, built from shared tokens with documented states.
- **Responsive audit:** A check of a page at several widths and zoom levels that records any overflow, reading order or focus problem.
- **Acceptance criteria:** Concrete, testable conditions that a page or feature must meet before it counts as done.

## Syntax anatomy and mechanism

Write acceptance criteria before styling: one main region, descriptive page title, reachable navigation, distinct card headings, no color-only status, a narrow-width layout and a usable zoomed view. Implement the smallest coherent page, then audit the settled state at multiple widths. Keep appearance checks separate from structural checks because each can pass while the other fails.

## Worked example / walkthrough

### Worked example 1: A meaningful card

The heading and link describe the same destination.

```html
<article>
  <h2>HTML foundations</h2>
  <p>Beginner. No prerequisites.</p>
  <a href="#html">Read HTML foundations</a>
</article>
```

**Expected observation:** A reader knows the topic, entry requirement and next action.

### Worked example 2: Adaptive collection

The layout supports a changing number of topics.

```css
.topics {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(min(100%, 15rem), 1fr));
  gap: 1rem;
}
```

**Expected observation:** Cards adapt without per-card coordinates.

## Contrast case: three cards that all say Read more

Both versions look the same apart from the link text. Open the accessibility tree or a screen reader links list for each.

```html
<!-- vague -->
<article><h2>HTML foundations</h2><a href="#html">Read more</a></article>
<article><h2>CSS layout</h2><a href="#css">Read more</a></article>

<!-- specific -->
<article><h2>HTML foundations</h2><a href="#html">Read HTML foundations</a></article>
<article><h2>CSS layout</h2><a href="#css">Read CSS layout</a></article>
```

Screen reader users often navigate by a list of links pulled out of context. In the vague version that list contains Read more twice with nothing to tell the items apart, and voice control users cannot say which one to activate. In the specific version each accessible name names its destination. Sighted readers still see the heading next to each link, so this problem is invisible in a screenshot, which is one reason the guide keeps structural checks separate from visual ones.

## Six progressive exercises

Exercises that ask you to predict, explain, compare or diagnose keep their answers in the solutions file. The others show the evidence to look for.

### Exercise 1: Write three learner tasks before drawing the interface.

**Expected evidence:** Find a topic, assess its prerequisites and choose a clear next action.

**Progressive hint:** Describe what a learner needs to do before choosing any layout.

### Exercise 2: Define a small token set for the page.

**Expected evidence:** Spacing, text and surface choices are consistent and named by role.

**Progressive hint:** Limit the tokens to surface, text, accent and spacing, named by role.

### Exercise 3: Build a complete offline portal with three paths and local destinations.

**Expected evidence:** All cards, navigation and headings are meaningful, keyboard reachable and responsive.

**Progressive hint:** Build the HTML structure first, then layer the CSS on top of it.

### Exercise 4: Audit one deliberately vague link and one broken fragment.

**Expected evidence:** Replace the vague label and repair the target relationship.

**Progressive hint:** Read each link out of context and click every fragment link.

### Exercise 5: Review narrow width, zoom, keyboard and print behavior.

**Expected evidence:** Retain observations for each surface instead of claiming a universal pass from one screenshot.

**Progressive hint:** Record one observation for each surface instead of a single screenshot.

### Exercise 6: Explain the portal's remaining backend requirements.

**Progressive hint:** List the information that must persist after the browser closes.

## Debugging and common mistakes

Do not invent working progress persistence in static HTML. Avoid screenshots as the sole accessibility evidence. A capstone should explain choices and limitations, not just imitate a reference's colors.

Keep the failing source, the viewport width and what you observed, then repair one cause at a time. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order, so inspect the element and its computed styles in the browser's developer tools instead of trusting the rendering alone.
