# c-029: Undefined behavior, aliasing and object representation

## Level and prerequisites

## Purpose and mental model

Undefined behavior is not a special runtime result such as a crash. It removes the language guarantee for the operation and can affect compiler reasoning about surrounding code. Common causes include out-of-bounds access, signed overflow, expired lifetimes and incompatible typed access. The effective-type and aliasing rules allow optimizers to assume certain pointer types do not refer to the same object. Use character access or memcpy for object representation rather than casting arbitrary byte storage to a typed pointer. Alignment and representation validity remain separate requirements. A plausible output from one build does not establish that an invalid operation is safe.

## Vocabulary and concepts

- **Effective type:** The type rules governing how stored values may be accessed.
- **Object representation:** The bytes used to represent an object.
- **Strict aliasing:** Rules restricting access through incompatible typed pointers.

## Syntax anatomy and execution trace

unsigned char can inspect object representation bytes. memcpy copies a specified number of bytes between valid nonoverlapping regions. memmove supports overlapping ranges. _Alignof describes a type alignment requirement. A pointer conversion alone does not create an object lifetime, correct alignment or valid value representation. This lesson deliberately demonstrates defined alternatives and never executes the invalid counterpart.

## Worked example / walkthrough

### Worked example 1: Copy a representation safely

Copy a float into bytes and back into a float object.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int main(void) {
  /* Copy a representation safely */
  {
    float original = 1.5f, restored = 0.0f;
    unsigned char bytes[sizeof original];
    memcpy(bytes, &original, sizeof original);
    memcpy(&restored, bytes, sizeof restored);
    CHECK(restored == original);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The restored value is 1.5.

The copied bytes originated from a valid object of the same type. This does not claim arbitrary external bytes are a valid float representation.

### Worked example 2: Inspect bytes without type punning

Read an integer representation through unsigned char.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int main(void) {
  /* Copy a representation safely */
  {
    float original = 1.5f, restored = 0.0f;
    unsigned char bytes[sizeof original];
    memcpy(bytes, &original, sizeof original);
    memcpy(&restored, bytes, sizeof restored);
    CHECK(restored == original);
  }

  /* Inspect bytes without type punning */
  {
    int value = 7;
    const unsigned char *bytes = (const unsigned char *)&value;
    unsigned int sum = 0;
    for (size_t i = 0; i < sizeof value; i++)
      sum += bytes[i];
    CHECK(sizeof value >= 1);
    (void)sum;
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The byte view has exactly sizeof(int) bytes.

Character access is the appropriate representation-view mechanism. The test deliberately avoids assuming a particular byte order.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
