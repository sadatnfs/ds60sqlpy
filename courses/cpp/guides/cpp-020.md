## Learning objectives

Express a useful generic contract and read a constraint diagnostic.

## Vocabulary and concepts

A template describes a family of functions parameterized by types. Deduction selects a type from arguments. A concept is a compile-time requirement that determines which template candidates are valid. A constraint improves the interface boundary, but it does not automatically prove arithmetic safety.

<!-- terms:start -->

- **function template:** describes a family of functions parameterized by types or values.
- **template argument deduction:** the compiler choosing template arguments from the types of the call arguments.
- **instantiation:** the compiler generating a concrete specialization for the chosen template arguments.
- **concept:** a named compile-time requirement such as `std::integral` that decides which types a template accepts.
- **`static_assert`:** a check evaluated during compilation that stops the build when its condition is false.

<!-- terms:end -->

## Syntax and mechanism

`template<std::integral T>` admits integral types and excludes std::string and floating types. The requires mechanism checks validity during compilation. Adding signed values can still overflow, so a concept is separate from a runtime range contract.

## Trace the mechanism

Template deduction happens before any generated function runs. Equal int arguments select one specialization; int and long long arguments can produce conflicting deductions because this signature asks for one T. A concept rejects categories that lack the intended operations, often near the call site. It cannot make every admitted value safe. The overflow check in later lessons is still needed even though integral<int> is true.

## Templates and constraints as interface documentation

A function template describes a family of functions parameterized by types or values. The compiler instantiates the needed specialization from a call. Generic syntax alone does not explain what operations are valid for a type, so constraints can make the intended domain visible before a deeply nested implementation error appears.

The integral constraint says that the type belongs to the language/library concept for integral types. The complete program instantiates identity_sum for integers and checks 2 + 3 = 5. The second program uses static_assert to establish that double is not integral. That assertion is checked during compilation and produces no runtime branch. The actual negative exercise attempts a constrained call with double and retains the compiler diagnostic.

A syntactic constraint is not the whole semantic contract. Integral addition can still overflow for signed types, and mixing signed and unsigned arguments can affect deduction or conversions. A template constrained to integral types must still state supported value ranges and any overflow policy. Concepts should not be advertised as automatic arithmetic safety or proof of all algorithm assumptions.

Template argument deduction also requires compatible inputs. A function taking two values of the same template parameter may reject an int and long combination even when a programmer considers both numbers. An explicit conversion can resolve the call, but it should be deliberate because narrowing or sign changes can lose meaning. Inspect the inferred types when a call does not match expectations.

Good constraints describe the weakest capabilities the implementation actually needs. Requiring a random-access container for a one-pass accumulation unnecessarily excludes useful inputs. Conversely, accepting any type while relying on an undocumented operation shifts the error into the implementation. The aim is a readable contract and useful diagnostics, followed by ordinary value-boundary tests.

## Worked example / walkthrough

Example 1 calls `identity_sum` with 2 and 3, which satisfy `std::integral` and add to 5. Example 2 uses `static_assert(!std::integral<double>)` to record that a double never reaches the template body: the concept rejects it at the call site with a constraint diagnostic, before any arithmetic is instantiated. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-020-example-1.cpp)

```cpp
#include <cassert>
#include <concepts>
#include <iostream>

#include <concepts>
template <std::integral T> T identity_sum(T a, T b) { return a + b; }
int main() {
  assert(identity_sum(2, 3) == 5);
  std::cout << "cpp-020 example 1 checks passed\n";
  return 0;
}
```

**Expected:** With assertions enabled, the program exits with status 0 and prints:

## Exercises

### Exercise 1: Read deduction

Call identity_sum with int values and long long values.

**Expected result/shape:** Result types int and long long respectively.

**Verify:** Add `static_assert(std::is_same_v<decltype(identity_sum(2, 3)), int>)` and the same check with `2LL` and `3LL` against `long long`.

**Progressive hints:** The argument types choose template instantiations.

### Exercise 2: Reject a category

Try identity_sum with two strings in a scratch file.

**Expected result/shape:** Constraint-related compile failure.

**Verify:** Compile the call with two `std::string` arguments and confirm the error names the unsatisfied `std::integral` constraint rather than a failure inside the function body.

**Progressive hints:** Strings do not satisfy integral.

### Exercise 3: Add a concept

Constrain a function to signed_integral.

**Expected result/shape:** int accepted; unsigned rejected.

**Verify:** Add `static_assert(std::signed_integral<int>)` and `static_assert(!std::signed_integral<unsigned>)`, then confirm a call with `3u` fails to compile.

**Progressive hints:** A narrower category documents intent.

### Exercise 4: Repair mixed deduction

Call identity_sum(2, 3LL), then choose a deliberate common type.

**Expected result/shape:** Mixed call fails deduction; explicit long long arguments succeed.

**Verify:** Keep the deduction error for `identity_sum(2, 3LL)`, where `T` would be both `int` and `long long`, then assert `identity_sum(2LL, 3LL) == 5LL`.

**Progressive hints:** Conflicting deductions need a policy, not an accidental conversion.

### Exercise 5: Inspect numeric boundary

Explain why INT_MAX+1 is still unsafe for integral T=int.

**Expected result/shape:** Concept accepts int but cannot make overflow valid.

**Verify:** Show that `identity_sum(std::numeric_limits<int>::max(), 1)` compiles because `int` satisfies `std::integral`; with `-fsanitize=undefined`, running it reports the signed overflow.

**Progressive hints:** Type eligibility is distinct from value validity.

### Exercise 6: Transfer a generic test

Run zero-identity tests for int and long long.

**Expected result/shape:** sum(x, 0)==x for bounded x=7 in both types.

**Verify:** Assert `identity_sum(7, 0) == 7` and `identity_sum(7LL, 0LL) == 7LL`; both arguments must have the same type for deduction to succeed.

**Progressive hints:** A reusable law should be checked across admitted types.

## Self-check

Why does deduction select int for `identity_sum(2, 3)` and return 5? For Example 2, explain where a call with a double is rejected, and why that diagnostic is better than an error deep inside the template body.

## Common pitfalls

If template errors are long, find the first failed constraint or mismatched deduced type rather than the final cascade. If a valid type produces a wrong numeric result, inspect values and conversions: type constraints do not prevent overflow. If an interface rejects an input range unnecessarily, compare the declared capability with the operations actually used. Do not weaken every constraint to make one call compile without reviewing the algorithm assumptions.

## Retrieval and transfer

Close the source and redo Exercise 6: check the zero identity `identity_sum(7, 0) == 7` for both int and long long. Explain why one constrained template covers both types. Then decide which further types the concept should admit or refuse, such as unsigned values, `char` or a type with a narrower range.
