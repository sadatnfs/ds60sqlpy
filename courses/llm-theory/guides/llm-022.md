# llm-022: Reproducibility, evaluation mode and restart

## Level and prerequisites

Intermediate; approximately 120 minutes. Direct prerequisites: `llm-021`. The prerequisite sequence introduces the notation used here; revisit its worked examples if an axis, probability or gradient is unfamiliar.

## Learning objectives

Distinguish repeatable inference from repeatable training and preserve optimizer state. The central investigation is concrete: Record seed/profile/dtype, disable dropout with model.eval(), and use Adam state plus model weights to compare an uninterrupted next update with a fresh-process restore on the same fixed batch. The finish condition is Eval-mode prefix tests pass with dropout disabled. Restored next-step tensors agree within 1e-6; cross-platform bitwise equality is not promised. A useful explanation connects the calculation to the reason it is needed, rather than treating a function name as a definition.

## Purpose and mental model

<!-- textbook-foundations-start -->

### A restart must preserve the state that determines the next step

Saving model weights is enough for some inference tasks: given the same architecture and input, those weights can reproduce a prediction under the required modes and numerical conditions. Continuing training asks more. The next update may depend on optimizer history, a schedule, random-number state and where the data iterator stopped. A checkpoint is sufficient only relative to the continuation claim being made.

The scalar experiment isolates optimizer history. It trains the parameter w on \({\left(w-2\right)}^{2}\) using Adam with learning rate 0.1. Adam maintains a running first moment of gradients, a running second moment of squared gradients and a step count used by bias correction. These values are part of its state. Reconstructing a new Adam object at the same w does not reconstruct those histories automatically.

For intuition, use Adam's default moment coefficients beta1=0.9 and beta2=0.999. At \(w=0\) the gradient is -4. Starting from zero moments gives \(m_{1}=-0.4\) and \(v_{1}=0.016\). Correcting their initial bias gives \(\widehat{m}=-4\) and \(\widehat{v}=16\). The update is approximately \(\frac{-0.1\cdot (-4)}{4+\epsilon}\), moving w to about 0.1. The next gradient is about -3.8, but the moments now combine it with the previous gradient rather than treating it as the first observation. The [Adam API](https://docs.pytorch.org/docs/2.9/generated/torch.optim.Adam.html) defines the stateful update convention used by the fixture.

After two updates, the reference saves both the parameter and optimizer state. It then takes the third step uninterrupted and records the resulting weight. A fresh Python interpreter loads the saved state, reconstructs the parameter and optimizer, and takes the same next step. Comparing those two results tests continuation, not merely the ability to deserialize a file. The separate weights-only branch deliberately starts a new optimizer and produces a different next weight, exposing the missing history.

The new interpreter is important evidence because it cannot accidentally reuse the original in-memory optimizer. The test still has a narrow scope: it uses one deterministic scalar objective and a trusted local checkpoint in a temporary directory. A stochastic training job would additionally need the relevant RNG state, data ordering and scheduler state to make an equivalent next-update claim. A seed written at the top of a script is not a replacement for the exact random state at the interruption point.

Evaluation mode and gradient recording are independent settings. The Dropout example calls eval so that the layer returns the supplied ones unchanged. no_grad would disable construction of a backward graph, but would not by itself change Dropout's training behavior. Conversely, eval does not generally prohibit gradients. A reproducibility report should name the forward mode and the gradient-recording mode separately instead of treating both as one "inference switch."

Finally, checkpoint compatibility includes architecture, parameter names, shapes, optimizer parameter grouping, dtypes and software assumptions. This lesson does not claim arbitrary files are safe to load or every version can resume another version's state. It establishes one owned, bounded restart and demonstrates why saving too little state changes the algorithm.

## Vocabulary and concepts

**Evaluation mode:** Module behavior chosen by eval, separate from gradient recording.

**Optimizer checkpoint:** State needed to reproduce a subsequent optimization update.

**Next-step parity:** Agreement after one identical update from saved state.

## Syntax anatomy and reasoning sequence

Use torch.save on a dictionary containing model state and optimizer state. Load only the locally created trusted checkpoint with weights_only=True. Reconstruct fresh objects before load_state_dict. A subprocess takes the same next step and returns its weight as JSON. A seed controls initial random draws but is not a substitute for restoring the exact optimizer state.

## Why weights alone do not specify the next Adam step

Adam's update depends on a first-moment estimate, a second-moment estimate and a step count as well as the current parameter. At the first gradient \(g=-4\), default beta values 0.9 and 0.999 give moments -0.4 and 0.016. Bias correction divides them by 0.1 and 0.001, recovering -4 and 16 for that first step. With learning rate 0.1 and the small epsilon term, the parameter moves from zero to approximately 0.1.

After more steps, the stored moments summarize earlier gradients. Starting a fresh optimizer at the same current weight instead initializes those moments to zero and starts the bias-correction counter again. The next update can therefore differ even with the same loss function, batch, learning rate and weight value. The reference compares that weights-only continuation against a restored optimizer rather than treating successful weight loading as a restart proof.

## What the fresh-process test actually preserves

The parent saves one scalar weight and the optimizer state after two updates, then computes the uninterrupted third update. A child interpreter constructs new objects, restores both components and computes the same next update. Matching those values within the stated tolerance tests reconstruction rather than another reference to the parent's live objects. Optimizer parameter-group structure and parameter ordering must match the state being restored.

This scalar task has a fixed objective and no stochastic data order, so the checkpoint does not need an RNG or sampler position to reproduce its declared next step. A realistic training continuation may also need Python/NumPy/framework RNG state, data position, scheduler state, mixed-precision scaler state and relevant preprocessing versions. The small success does not prove those unimplemented surfaces. Similarly, seeding after random model or adapter construction cannot reproduce the initialization that already happened.

The saved artifact is an owned local checkpoint, and loading uses the explicit CPU and weights-only options shown in the code. These choices do not authorize arbitrary untrusted files or prove general cross-version portability. Evaluation mode is another independent setting: Dropout.eval disables its random masking, while no_grad controls graph recording. A reproducibility claim should name all relevant state, mode, version and input contracts.


## Worked example / walkthrough

### Example A: Create Adam history

The checkpoint must contain nontrivial history. Saving before the first update would not distinguish a full optimizer restore from a fresh optimizer.

```python
import numpy as np
import torch
from torch import nn
from torch.nn import functional as F
import tempfile,json,subprocess,sys,textwrap
from pathlib import Path

w=nn.Parameter(torch.tensor(0.)); opt=torch.optim.Adam([w],lr=.1)
for _ in range(2): opt.zero_grad(set_to_none=True); (w-2).square().backward(); opt.step()
assert w.item()>0 and opt.state[w]['step'].item()==2
```

**Expected:** positive weight and optimizer step2.

### Example B: Save a trusted local checkpoint

The file is created by this lesson and loaded only for this local test. Loading arbitrary untrusted serialized objects is outside the fixture.

```python
import numpy as np
import torch
from torch import nn
from torch.nn import functional as F
import tempfile,json,subprocess,sys,textwrap
from pathlib import Path

w=nn.Parameter(torch.tensor(0.)); opt=torch.optim.Adam([w],lr=.1)
for _ in range(2): opt.zero_grad(set_to_none=True); (w-2).square().backward(); opt.step()
assert w.item()>0 and opt.state[w]['step'].item()==2
temporary=tempfile.TemporaryDirectory(); path=Path(temporary.name)/'state.pt'
torch.save({'weight':w.detach().clone(),'optimizer':opt.state_dict()},path)
assert path.is_file(); saved=w.item()
```

**Expected:** checkpoint file exists.

## Common pitfalls and diagnosis

Compare the uninterrupted and reconstructed next update, not only loaded weights. Check optimizer state, step count and parameter-group mapping. State explicitly whether RNG, data position and scheduler state matter to the declared experiment. A seed applied after random initialization cannot reproduce an earlier draw, and evaluation mode is separate from gradient recording.
