# C++ model families and end-to-end acceptance

Start with: tmb-047, tmb-024.

Outcome: Plan a qualified custom template using the appropriate authoring families.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter prints an acceptance plan and a coverage table. The separately prepared [C++ API probes](../projects/tmb-cpp-api/README.md) compile all five family models under CppAD in `check.R`, separately from the nine-model [owned project](../projects/tmb-local/README.md); a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

A custom TMB model is built from interface declarations, typed arithmetic, normalized density terms, derivative rules, sparse or dense structure, report/simulation definitions and a native process boundary. The [C++ API-family map](../CPP-API-FAMILIES.md) links these families to the chapters, existing original models and appropriate validation. It deliberately excludes a promise to teach every private Eigen or AD-engine symbol.

This course now combines a complete pinned R API inventory with a model-authoring map. The two are complementary: knowing `MakeADFun` is not enough to write a correct C++ objective, and writing a density is not enough to manage optimization, uncertainty and library lifetime.

## Key terms

- **C++ API family map:** The course map that links template macros, typed containers, densities, derivative rules and reporting families to chapters and validation.
- **Numerical acceptance:** A set of checks against independent references for array order, covariance meaning, normalizers, gradients and selected uncertainty.
- **Runtime boundary:** The native process limit where a compiled library is loaded and evaluated, separate from algebraic oracles that run without a compiler.
- **Transparent typed reference:** A plain typed version of a costly operation, used to validate a custom atomic's forward and reverse rules before comparing speed and memory.

### Worked case A: a correlated multi-sensor likelihood

Start with a typed response matrix and explicit row/column meaning. Decide whether covariance is dense, sparse precision or separable across axes. Write the normalized density, choose scientifically justified scales and transforms, and compare a tiny evaluation against a dense independent formula. Then test parameter derivatives, data-shape rejection, optimizer behavior and selected uncertainty reports.

The companion constructs a small acceptance plan with distinct checks for array order, covariance/precision meaning, normalizers and gradients. Each check addresses a concrete failure mode. A successful compiler invocation cannot replace them.

### Worked case B: an optimized custom primitive

Suppose the same model needs a costly special operation. First implement a transparent typed reference. Derive a candidate atomic's forward and reverse rules, compare them across the domain, and verify the higher derivative orders required by the actual latent integration. Only then compare tape size, runtime and memory under a fixed workload.

The companion shows that an API family may be explained, have an algebraic oracle and still lack a compiled runtime record. That state is acceptable when labeled; it must not be promoted to “all paths pass” because another original model happened to use the same library.

### Answered discussion

**What is covered comprehensively?** The public R function surface and the model-authoring families needed for original scalar, vector, multivariate, sparse, separable, latent and custom-derivative workflows. **What remains open-ended?** Every possible probability model, private dependency symbol, specialized build and hardware configuration. **How does a future contributor extend this safely?** Add original source and a distinct mathematical oracle, preserve old lesson IDs, update the family/API maps, and qualify the exact native and learner-facing surfaces before changing capability claims.

The original nine-model project, public API probe, Python bridge and advanced Spark integration provide separate evidence layers. Their shared scientific principle is explicit ownership of data, parameters, latent variables, native objects and results.

### Worked case C: turning the plan into numeric oracles

The companion's plan names five checks. Earlier chapters already supply a concrete oracle for four of them, each with a value that a broken implementation would miss (closed-form values from the cited chapters):

```text
check                        oracle                                   chapter
array order                  b[2, 3, 1] == 6 in array(1:12, c(2,3,2))  41
covariance versus precision  correct NLL 2.269114, swapped 1.668069     43
normalizer                   omitted Jacobian shifts NLL by log 2       44
gradient                     quartic reverse 17.576 at x = 1.3, adj 2   47
native execution             PASS line from tests/acceptance.R          separate run
```

Assembled into a single R acceptance script, the first four run anywhere base R runs:

```r
b <- array(1:12, dim = c(2, 3, 2))
Sigma <- matrix(c(2, .5, .5, 1), 2, 2); u <- c(.3, -.4)
nll <- function(x, S) length(x) * log(2 * pi) / 2 +
  as.numeric(determinant(S, logarithm = TRUE)$modulus) / 2 + sum(x * solve(S, x)) / 2
R <- matrix(c(1, .4, .4, 1), 2, 2); s <- c(2, 1); D <- diag(s)
stopifnot(
  b[2, 3, 1] == 6,
  abs(nll(u, Sigma) - 2.269114) < 1e-6,
  abs(nll(u, D %*% R %*% D) - nll(u / s, R) - log(2)) < 1e-12,
  abs(4 * 1.3^3 * 2 - 17.576) < 1e-12
)
```

Each line encodes the failure in the companion's `failure` column: a transposed array would read a different cell, a precision passed as a covariance would land near 1.668, a missing Jacobian would leave a gap of 0.693, and an unscaled reverse rule would return 8.788. The fifth row has no base-R oracle. It needs the compiled template, so its status stays "separate run" until a build receipt and the acceptance log exist.

### Worked case D: reading the coverage table

The companion's second table has two rows. Both have `math = TRUE`, and only the Gaussian model has `compiled = TRUE`, so `all(coverage$compiled)` is `FALSE` and the `stopifnot(!all(...))` line passes. That assertion is deliberately inverted: it fails if someone edits the table to claim the new primitive compiled without adding evidence. A reviewer reading the table should see that the new row has an algebraic oracle and nothing else, and should not infer a native result from the Gaussian row's success.

### Ordering the work for a new model

Run the checks cheapest first. The four base-R oracles take milliseconds and catch the errors that produce plausible but wrong fits. Compilation comes next, because a template that fails to compile gives a clear diagnostic. Only then are optimizer behavior, `sdreport` output and thread parity worth measuring, since each costs real time and each assumes the earlier layers are right. A failure at any layer stops the sequence; a later pass cannot certify an earlier failure.

### Base-R companion (runs in the classroom)

```r
plan <- data.frame(check = c("array order", "covariance versus precision", "normalizer", "gradient", "native execution"), failure = c("transposed meaning", "wrong quadratic form", "wrong estimator", "wrong optimizer direction", "incompatible binary"))

```
