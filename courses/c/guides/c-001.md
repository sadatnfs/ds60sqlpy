# c-001: Source, compilation, linking and checked execution

## Level and prerequisites

Beginner, approximately 90 minutes plus a later retrieval session. Direct prerequisites: None. Begin with the difference between source text, a compiler and a running process.

## Learning objectives

Compile, link and run a one-file C17 program whose checks fail loudly instead of printing an unchecked result. Along the way, explain translation unit, linker, assertion. Implement the six investigations with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

C source is text describing declarations and operations. The preprocessor handles directives, the compiler translates a translation unit, and the linker combines machine-code objects with required libraries. The executable is a separate artifact from main.c. A syntax error prevents compilation; an unresolved symbol prevents linking; an assertion can fail only after execution begins. These stages require different diagnoses. C does not automatically validate every runtime memory operation, so successful compilation is a starting point rather than a safety proof. Begin with independently checked scalar results before learning pointers and resource ownership.

## Vocabulary and concepts

- **Translation unit:** The source after preprocessing, compiled as one unit.
- **Linker:** The tool resolving references among compiled objects and libraries.
- **Assertion:** An explicit runtime check of a claimed property.

## Syntax anatomy and execution trace

#include makes header declarations available. int main(void) is an entrypoint with no parameters; returning zero signals successful termination. Braces form a block and semicolons finish most statements. printf formats values, while puts writes a string plus a newline. assert from assert.h checks a condition when NDEBUG is not defined. %d expects an int, and a mismatched format argument can be undefined behavior.

## Worked example / walkthrough

### Worked example 1: Check a first value

Store 2 plus 3 in an int.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int seven(void) { return 7; }

int main(void) {
  /* Check a first value */
  {
    int total = 2 + 3;
    CHECK(total == 5);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The stored value is 5.

The expectation is known independently of the program. A print statement alone would not reject a wrong calculation.

### Worked example 2: Format a checked result

Format total=5 into a bounded character buffer.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int seven(void) { return 7; }

int main(void) {
  /* Check a first value */
  {
    int total = 2 + 3;
    CHECK(total == 5);
  }

  /* Format a checked result */
  {
    char out[16];
    int n = snprintf(out, sizeof out, "total=%d", 5);
    CHECK(n == 7);
    CHECK(strcmp(out, "total=5") == 0);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The result length is 7 and text is total=5.

snprintf returns the length that would be required, excluding the terminating null byte. A caller must compare it with capacity before treating output as complete.

## Prediction before execution

Trace each object from initialization through its last valid use. Write down the size of every array, the capacity of every output buffer and the ownership of any allocated storage. Distinguish a compiler diagnostic from a valid runtime rejection and from undefined behavior. Never execute an out-of-bounds access, dangling-pointer read or data race simply to discover what value it happens to print.

## Exercises

### Exercise 1: Check a first value: change one input

Copy worked example 1 into a scratch pad and change `int total = 2 + 3;` to `int total = 3 + 3;`. Before running, predict which CHECK fails and which value it now sees; then run it and restore the original line.

**Expected:** The changed run stops with `Check failed` at the CHECK on `total == 5`. Restoring the original line brings back the worked observation: the stored value is 5.

**Verify:** Compare your written prediction with the failing CHECK and name the value that made `total == 5` false. The edit is defined behavior: it was run under AddressSanitizer and UndefinedBehaviorSanitizer without a report. After restoring the input, the program prints its success line again.

**Progressive hints:** First restate the expected observation: the stored value is 5. Then list the values read by `total == 5` and trace each one from its initialization. Finally, compute the checked value with `int total = 3 + 3;` in place before running.

### Exercise 2: Format a checked result: debug a regression

A regression changed one token in worked example 2, so one line now reads `int n = snprintf(out, sizeof out, "total=%d", 6);`. Run worked example 2 with that line, use the failing CHECK to locate the defect and repair it without changing the CHECK.

**Expected:** Before the repair the run stops with `Check failed` at the CHECK on `strcmp(out, "total=5") == 0`; after it the line reads `int n = snprintf(out, sizeof out, "total=%d", 5);` again and the result length is 7 and text is total=5.

**Verify:** Keep the failing and the repaired runs. Explain why the changed token alters the value tested by `strcmp(out, "total=5") == 0` for this input.

**Progressive hints:** First restate the expected observation: the result length is 7 and text is total=5. Then list the values read by `strcmp(out, "total=5") == 0` and trace each one from its initialization, including the bounds of every array it touches. Finally, compare `int n = snprintf(out, sizeof out, "total=%d", 6);` with the same line in worked example 2 and state the claim each version makes.

### Exercise 3: Trace statement order

Start at 1, increment, then multiply by 3.

**Expected:** The result is 6.

**Verify:** Keep a CHECK equivalent to `count == 6`. As a control, change `count += 1;` to `count -= 1;`: the run must stop with `Check failed` at that CHECK, with no sanitizer report. Restore the line before continuing.

**Progressive hints:** First restate the expected observation: the result is 6. Then list the values read by `count == 6` and trace each one from its initialization. Finally, predict the effect of changing `count += 1;` to `count -= 1;` before running anything.

### Exercise 4: Inspect a boolean condition

Compare 4 with 4 and 4 with 5.

**Expected:** Equality is true and inequality is true.

**Verify:** Keep a CHECK equivalent to `same &&different`. As a control, change `bool same = (4 == 4);` to `bool same = (4 != 4);`: the run must stop with `Check failed` at that CHECK, with no sanitizer report. Restore the line before continuing.

**Progressive hints:** First restate the expected observation: equality is true and inequality is true. Then list the values read by `same &&different` and trace each one from its initialization. Finally, predict the effect of changing `bool same = (4 == 4);` to `bool same = (4 != 4);` before running anything.

### Exercise 5: Use an explicit return contract

Call a helper returning the value 7.

**Expected:** The caller receives 7.

**Verify:** Keep a CHECK equivalent to `seven() == 7`. As a control, change `CHECK(seven() == 7);` to `CHECK(seven() != 7);` inside it: the run must stop with `Check failed`, which shows the CHECK can fail. Restore it.

**Progressive hints:** First restate the expected observation: the caller receives 7. Then list the values read by `seven() == 7` and trace each one from its initialization. Finally, name one defined input that would make `seven() == 7` false.

### Exercise 6: Transfer a receipt calculation

Multiply 4 items by a unit amount of 6.

**Expected:** The checked amount is 24.

**Verify:** Keep a CHECK equivalent to `amount == 24`. As a control, change `int amount = items * unit;` to `int amount = items + unit;`: the run must stop with `Check failed` at that CHECK, with no sanitizer report. Restore the line before continuing.

**Progressive hints:** First restate the expected observation: the checked amount is 24. Then list the values read by `amount == 24` and trace each one from its initialization. Finally, predict the effect of changing `int amount = items * unit;` to `int amount = items + unit;` before running anything.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
