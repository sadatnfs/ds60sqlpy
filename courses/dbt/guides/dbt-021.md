# dbt-021: Slim CI with actual builds and data tests

## Level and prerequisites

Advanced. Direct prerequisites: `dbt-004`, `dbt-006`, `dbt-013`, `dbt-020`

**Outcome:** Implement a reproducible reduced CI workflow with explicit selection, baseline and ownership.

## Question and mechanism

A slim CI workflow combines a selection plan with actual execution against an isolated target and an explicit upstream baseline. Its goal is to validate the relevant change efficiently while retaining meaningful tests. Selecting changed nodes without running them is not CI acceptance, and a successful model build without the required tests is incomplete evidence.

The example first builds an accepted baseline in a synthetic prod schema. It then changes a child and runs state:modified+ in dev with deferral. One change preserves the key contract; another duplicates rows and must fail uniqueness. The accepted baseline is queried afterward to verify that the CI exercise did not alter it.

A reduced CI scope is justified only under stated assumptions. Shared macros, environment changes, source contracts, schema migrations or operational behavior may require a broader gate. Keep the baseline, selected graph, executed statuses and target ownership with the result. An efficient test that reads the wrong data or omits the relevant condition is not a useful release check.

## Syntax and data contract

The workflow saves a baseline manifest separately, edits the current source, and invokes build with --select state:modified+, --defer, --state and an explicit target. It inspects run_results and the preserved baseline relation. The negative fixture is expected to fail; that failure proves the selected data test actually ran.

## Run the lesson

Open this subject in `/classroom`, then show its code and notes. The prepared `data-engineering` worker runs `main.py` in a fresh temporary directory. The examples use installed packages and synthetic local fixtures; no account, cloud service, network request or package download is required. Save source and notes before switching lessons. Temporary databases, project files and tracking artifacts are recreated by each complete program and removed after the job. The classroom retains the submitted source and bounded output, not an indefinitely running external service. The guide distinguishes this local execution from the deployment decisions that need an owned production environment.



## Worked case 1: Accept a compatible change

The first child change adds a filter that preserves the identified row. The selected build and its tests pass in dev, while the baseline still has one row. The result binds the selection to actual evidence.

**Expected evidence:** The changed candidate passes and the accepted baseline is unchanged.

```python
import json
import os
import shutil
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def artifact(root, name):
    return json.loads((root / "target" / name).read_text())


def targets(p):
    config = yaml.safe_load((p / "profiles.yml").read_text())
    original = config["classroom"]["outputs"]["dev"]
    config["classroom"]["outputs"] = {
        name: {**original, "schema": name} for name in ("dev", "prod")
    }
    (p / "profiles.yml").write_text(yaml.safe_dump(config))


def ci_case(bad):
    with tempfile.TemporaryDirectory() as d:
        schema = {
            "models": [
                {"name": "child", "columns": [{"name": "id", "data_tests": ["unique", "not_null"]}]}
            ]
        }
        p = project(
            d,
            models={"base": "select 1 as id", "child": "select id from {{ ref('base') }}"},
            schema=schema,
        )
        targets(p)
        invoke(p, "build", "--target", "prod")
        state = p / "state"
        state.mkdir()
        shutil.copyfile(p / "target/manifest.json", state / "manifest.json")
        sql = "select id from {{ ref('base') }}" + (
            " union all select id from {{ ref('base') }}" if bad else " where id > 0"
        )
        (p / "models/child.sql").write_text(sql)
        invoke(
            p,
            "build",
            "--target",
            "dev",
            "--select",
            "state:modified+",
            "--defer",
            "--state",
            str(state),
            succeeds=not bad,
        )
        assert rows(p, "select count(*) from prod.child") == [(1,)]
        statuses = [r["status"] for r in artifact(p, "run_results.json")["results"]]
        assert ("fail" in statuses) is bad
        return {"bad_change": bad, "protected_baseline_rows": 1, "statuses": statuses}


def example_one():
    return ci_case(False)


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Reject a duplicated output

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Inspect selected resources

List the nodes and tests included by the state expression.

**Check:** The changed child and required tests are visible.

**Hint:** Selection is inspectable before execution.


### 2. Introduce a semantic failure

Change the child quantity while keeping its schema.

**Check:** An independent semantic test is needed to detect it.

**Hint:** Key checks do not cover every contract.


### 3. Verify isolation

Query the accepted baseline after a failed candidate.

**Check:** Its content remains unchanged.

**Hint:** Targets should have explicit ownership.


### 4. Review a shared macro change

Decide whether the normal slim scope is sufficient.

**Check:** The decision includes downstream effects.

**Hint:** A small source edit can affect many nodes.


### 5. Retain invocation evidence

Record the source and baseline identities with statuses.

**Check:** The result can be traced to exact inputs.

**Hint:** A green badge alone loses context.


### 6. Define failure handling

State what a failed CI candidate is allowed to publish.

**Check:** It cannot replace the accepted product.

**Hint:** Testing and publication are separate stages.


## Diagnose errors and misleading results

A fast CI run can be empty or incomplete. Check resource counts, test selection and the baseline before interpreting its result. A failed test is useful evidence, not a reason to remove the assertion. Keep cleanup scoped to the owned CI target and preserve the accepted baseline.
