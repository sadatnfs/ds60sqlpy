# go-040: Work queues, retry budgets and error classification

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-039

## Learning objectives

Classify failures as retryable or invalid and bound retries with capped delays and a total budget. Along the way, explain coalescing, backoff, retry budget; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A controller queue decouples event ingestion from reconciliation. Repeated events for one key can be coalesced because reconciliation reads the latest state. A failing key should not spin in a tight loop or prevent unrelated keys from progressing. Rate-limited retry combines an increasing delay with a cap and often jitter; cancellation and a maximum work policy prevent unlimited resource use. Permanent invalid input differs from a transient API failure. Success should clear retry history so an old failure does not penalize a repaired object forever. This lesson models scheduling decisions without sleeping or claiming a full implementation of client-go workqueue semantics.

## Vocabulary and concepts

- **Coalescing:** Combining repeated notifications for the same work key.
- **Backoff:** Increasing delay after repeated transient failures.
- **Retry budget:** A bound on attempts or elapsed work.

## Syntax anatomy and reasoning

A queue key usually names a namespace and object name, not a pointer to a stale object. The worker gets a key, defers Done, reconciles and either Forget on success or schedules a rate-limited retry. The fixture uses integer delay units to test a capped exponential policy deterministically. Production jitter should be tested with an injected source rather than a fixed assumption about wall-clock timing.

## Worked example / walkthrough

### Worked example 1: Calculate increasing delay

Inspect attempts 0, 1 and 2.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func delay(attempt int) int {
	if attempt < 0 {
		return 1
	}
	if attempt >= 3 {
		return 8
	}
	return 1 << attempt
}
func retryable(class string) bool { return class == "transient" }

func main() {
	// Calculate increasing delay
	{
		check(delay(0) == 1 && delay(1) == 2 && delay(2) == 4, "growth")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The delays are 1, 2 and 4 units.

The first attempt and retry numbering must be documented. Ambiguous numbering creates off-by-one operational behavior.

### Worked example 2: Cap the delay

Inspect attempts beyond the configured cap.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func delay(attempt int) int {
	if attempt < 0 {
		return 1
	}
	if attempt >= 3 {
		return 8
	}
	return 1 << attempt
}
func retryable(class string) bool { return class == "transient" }

func main() {
	// Calculate increasing delay
	{
		check(delay(0) == 1 && delay(1) == 2 && delay(2) == 4, "growth")
	}

	// Cap the delay
	{
		check(delay(3) == 8 && delay(10) == 8, "cap")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The delay never exceeds 8 units.

A cap prevents exponential growth from becoming impractical or overflowing. It does not replace a total retry budget.

## Common pitfalls and diagnosis

Retrying every error is the classic queue bug: a validation failure retried forever burns API quota and fills logs with no chance of success. Classify errors, retry only transient ones and surface the rest. Uncapped exponential delay grows without bound, and forgetting to reset a key after success makes its next unrelated failure start at the maximum delay.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Calculate increasing delay: predict an edited check

1. Restate the expected observation: The delays are 1, 2 and 4 units.
2. delay shifts 1 left by the attempt. What are the first three values?
3. delay(1) is 2, so `delay(1)==1` is false and the growth check fails. The function is right; the edited check reads the wrong attempt.

### Hint for investigation 2: Cap the delay: diagnose an edited check

1. Restate the expected observation: The delay never exceeds 8 units.
2. Attempts at or beyond 3 return the cap. What are delay(3) and delay(10)?
3. delay(3) returns the cap of 8, so `delay(3)!=8` is false and the cap check fails. Restore `==`.

### Hint for investigation 3: Coalesce duplicate keys

1. Restate the expected observation: There are two pending identities.
2. A set keeps one entry per key. How many keys remain?
3. This model demonstrates identity coalescing only.

### Hint for investigation 4: Separate invalid from transient

1. Restate the expected observation: Only the transient class is retried.
2. Only the transient class returns true. Which class is retried?
3. Blindly retrying invalid desired state wastes resources and delays useful feedback to the user.

### Hint for investigation 5: Reset successful history

1. Restate the expected observation: Its next failure starts at the first delay.
2. A missing key reads as attempt 0. What delay does that give?
3. Success ends the current failure sequence.

### Hint for investigation 6: Transfer a total budget

1. Restate the expected observation: Three retries fit (1+2+4=7 units); the fourth delay of 8 would exceed the budget.
2. The loop stops when the next delay would pass 10. Which delays fit?
3. A delay cap bounds waiting per retry, while an attempt or elapsed-time budget bounds total work.
