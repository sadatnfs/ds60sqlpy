# dbt-011: Enforced model schemas and constraint boundaries

## Level and prerequisites

Intermediate. Direct prerequisites: `dbt-003`, `dbt-004`

**Outcome:** Define a model schema contract and verify both accepted and rejected changes.

## Question and mechanism

A model contract declares the output columns and types expected by consumers. Enforcing that contract can reject an incompatible model before a replacement relation is published. It complements data tests, which inspect conditions on resulting records. Schema compatibility and data quality remain different dimensions of a reliable product.

The first model declares an integer identifier and a bigint amount. Explicit SQL casts make the intended types predictable. The second case first builds a valid table, then changes amount into incompatible text. The command must fail, and the program checks that the previously valid relation remains available for this specific failure path.

That observation is deliberately narrow. It does not establish that an entire multi-model build is atomic or that every failure rolls back every prior change. Another model may have materialized earlier, and data tests can fail after materialization. Publication needs its own project-level decision and recovery contract.

## Syntax and data contract

The model config contains contract.enforced=true and a complete column/type declaration. Column constraints such as not_null depend on database support. An explicit cast documents the intended SQL type; it should not be used to hide a value-domain error. Query actual database contents after failure to establish what state survived.

## Worked case 1: Create a compatible relation

The valid model declares two fields and produces a matching row. The program checks actual values after build. The schema is a promise to a consumer, while the row assertion is evidence about this particular fixture.

**Expected evidence:** The model returns id 1 and amount 42 under the declared types.

```python
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def example_one():
    with tempfile.TemporaryDirectory() as d:
        schema = {
            "models": [
                {
                    "name": "contracted",
                    "config": {"materialized": "table", "contract": {"enforced": True}},
                    "columns": [
                        {
                            "name": "id",
                            "data_type": "integer",
                            "constraints": [{"type": "not_null"}],
                        },
                        {"name": "amount", "data_type": "bigint"},
                    ],
                }
            ]
        }
        p = project(
            d, models={"contracted": "select 1::integer as id, 42::bigint as amount"}, schema=schema
        )
        invoke(p, "build")
        assert rows(p, "select id,amount from contracted") == [(1, 42)]
        return {"declared_columns": ["id:integer", "amount:bigint"], "row": [1, 42]}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Reject incompatible output

The second case changes the amount expression to varchar. Contract validation rejects the altered output, and the previous amount 42 remains in the relation. The guide treats that result as a tested failure path rather than a universal transaction guarantee.

**Expected evidence:** The incompatible run fails and the previous valid amount remains 42.

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Remove a declared column

Delete amount from the model output.

**Check:** The enforced contract rejects the mismatch.

**Hint:** The declared schema is complete.


### 2. Add a new output field

Add an undeclared field and inspect enforcement.

**Check:** The schema change is explicit.

**Hint:** More columns can still change a contract.


### 3. Test a null identifier

Return null for the constrained identifier.

**Check:** The database/contract path reports the violation when supported.

**Hint:** Schema type and value presence differ.


### 4. Distinguish failure stages

Compare the incompatible-schema case with the earlier uniqueness-test failure.

**Check:** The two cases leave different observed state.

**Hint:** Where validation occurs matters.


### 5. Check consumer assumptions

List properties beyond column types.

**Check:** They include grain, units, time and missingness.

**Hint:** An integer field can still mean the wrong thing.


### 6. Plan an incompatible change

Describe a safe way to replace gross amount with net amount.

**Check:** It uses an explicit version and consumer migration.

**Hint:** A type-preserving semantic change can still break users.


## Diagnose errors and misleading results

A contract error may be the correct protection against an incompatible model. Inspect declared and actual column names/types instead of disabling enforcement. After failure, inspect the database and invocation artifacts; do not assume every relation reverted to a prior state.
