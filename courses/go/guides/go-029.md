# go-029: The memory model, race diagnosis and publication

## Level and prerequisites

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-028

## Learning objectives

Publish data between goroutines through a channel, a closed channel or an atomic value, and explain why an unsynchronized read is a data race. Along the way, explain data race, publication, immutable snapshot; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A data race occurs when conflicting concurrent accesses include a write and lack synchronization. A program that prints the desired value once can still race. The memory model specifies ordering guarantees supplied by channels, mutexes and other primitives. Publish initialized state through such a boundary, then keep it immutable or protect future mutations. The race detector observes executed instrumented paths; a clean run is evidence rather than proof about every schedule. Do not intentionally execute racy examples in ordinary references. Prefer a design whose ownership and ordering can be explained before relying on a diagnostic tool.

## Vocabulary and concepts

- **Data race:** Conflicting unsynchronized concurrent memory access.
- **Publication:** Sharing initialized state through synchronization.
- **Immutable snapshot:** A shared value that is no longer mutated.

## Syntax anatomy and reasoning

A channel send synchronizes with its corresponding receive. Closing a channel synchronizes with a receive observing closure. An unlock synchronizes with a later lock on that mutex. atomic.Value can publish immutable snapshots. The ordinary pad has CGO disabled and does not claim race instrumentation; a prepared Linux development project with a compatible C toolchain can run go test -race ./....

## Worked example / walkthrough

### Worked example 1: Publish through a channel

Send an initialized record from a goroutine.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Published struct {
	Count int
	Ready bool
}

func main() {
	// Publish through a channel
	{
		ch := make(chan Published)
		go func() { ch <- Published{Count: 3, Ready: true} }()
		v := <-ch
		check(v.Ready && v.Count == 3, "publication")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The reader observes count 3 and ready true.

The send and receive establish ordering without a timing guess.

### Worked example 2: Publish through closure

Write 7 before closing done, then read after receiving done.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Published struct {
	Count int
	Ready bool
}

func main() {
	// Publish through a channel
	{
		ch := make(chan Published)
		go func() { ch <- Published{Count: 3, Ready: true} }()
		v := <-ch
		check(v.Ready && v.Count == 3, "publication")
	}

	// Publish through closure
	{
		done := make(chan struct{})
		n := 0
		go func() { n = 7; close(done) }()
		<-done
		check(n == 7, "close publication")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The reader observes 7.

Removing this synchronization would make the ordinary shared variable unsafe. The proof uses ordering, not elapsed time.

## Exercises

### Exercise 1: Publish through a channel: change one input

Copy worked example 1, change `go func() { ch <- Published{Count: 3, Ready: true} }()` to `go func() { ch <- Published{Count: 4, Ready: true} }()` and predict the failure before running; then restore the line.

**Expected:** The edited run panics with `publication` because `v.Ready && v.Count == 3` no longer holds.

**Verify:** Restoring `go func() { ch <- Published{Count: 3, Ready: true} }()` makes the check pass again with the worked observation: the reader observes count 3 and ready true.

### Exercise 2: Publish through closure: debug a regression

A one-token regression in worked example 2 makes a line read `go func() { n = 8; close(done) }()`. Repair it without changing the check.

**Expected:** The defective run panics with `close publication`; after restoring `go func() { n = 7; close(done) }()`, the reader observes 7.

**Verify:** The failing run shows message `close publication`; after the repair `n == 7` holds again.

### Exercise 3: Publish an atomic value

Store a complete record in atomic.Value.

**Expected:** The loaded record has count 4.

**Verify:** Your solution must keep `v.Count == 4 && v.Ready` true. Control: changing `current.Store(Published{Count: 4, Ready: true})` to `current.Store(Published{Count: 5, Ready: true})` panics with message `atomic value`; revert it.

### Exercise 4: Retain a previous snapshot

Load a value, then replace the stored value.

**Expected:** The old copy remains 4 and the current value is 5.

**Verify:** Your solution must keep `old.Count == 4 && current.Load().(Published).Count == 5` true. Control: changing `current.Store(Published{Count: 4})` to `current.Store(Published{Count: 5})` panics with message `replacement`; revert it.

### Exercise 5: Copy reference-containing data

Copy a slice before mutating the original.

**Expected:** The snapshot retains its original first element.

**Verify:** Your solution must keep `snapshot[0] == 1` true. Control: changing `original := []int{1, 2}` to `original := []int{2, 2}` panics with message `independent data`; revert it.

### Exercise 6: Transfer local construction

Build a result string inside a worker and send the completed value.

**Expected:** The reader receives `ready:3`.

**Verify:** Your solution must keep `<-ch == "ready:3"` true. Control: changing `go func() { ch <- fmt.Sprintf("ready:%d", 3) }()` to `go func() { ch <- fmt.Sprintf("ready:%d", 4) }()` panics with message `result`; revert it.

## Common pitfalls and diagnosis

The most dangerous race is one that passes: a goroutine writes a value and then a flag, and a reader polls the flag without synchronization, sometimes seeing the flag first. Run tests with -race to collect evidence. Another mistake is publishing a struct that holds a slice or map and then mutating it; the receiver shares that storage, so copy it or never change it after publication.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Publish through a channel: change one input

1. Restate the expected observation: The reader observes count 3 and ready true.
2. The record is fully built before the send. What does the receiver observe?
3. The goroutine now publishes Count 4, so the reader sees 4 and `v.Count==3` fails. Publication through the channel still works; the published value changed.

### Hint for investigation 2: Publish through closure: debug a regression

1. Restate the expected observation: The reader observes 7.
2. Closing done happens after the write. Which value does the reader see after receiving?
3. The goroutine writes 8 before closing done, so the reader correctly sees 8 and `n==7` fails. Restore the write of 7; the close still orders it before the read.

### Hint for investigation 3: Publish an atomic value

1. Restate the expected observation: The loaded record has count 4.
2. atomic.Value stores the whole record. Which count does Load return?
3. Publishing a pointer does not make subsequent unsynchronized target mutation safe.

### Hint for investigation 4: Retain a previous snapshot

1. Restate the expected observation: The old copy remains 4 and the current value is 5.
2. Store replaces the shared value but not copies already loaded. What do old and current hold?
3. Value snapshots avoid shared mutable fields only when their contained values also have the intended ownership semantics.

### Hint for investigation 5: Copy reference-containing data

1. Restate the expected observation: The snapshot retains its original first element.
2. The snapshot gets its own backing array. Does writing original[0] reach it?
3. Copying can eliminate shared mutable storage.

### Hint for investigation 6: Transfer local construction

1. Restate the expected observation: The reader receives `ready:3`.
2. The worker builds the string locally and sends it finished. What does the reader receive?
3. Keeping construction state local simplifies the argument compared with exposing several partially updated shared fields.
