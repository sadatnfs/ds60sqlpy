# go-048: Capstone: a reliable, resumable controller design

## Why this mechanism matters

The capstone combines desired-state validation, exact identity, idempotent planning, cancellation and durable observations. A controller is successful when repeated observations converge without duplicating effects or damaging resources it does not own. Begin with an explicit state diagram and classify each operation as pure, read-only, idempotent mutation or potentially uncertain external side effect. Record what an operation observed and what it requested, not an invented certainty that the whole system is ready. Production readiness also includes minimal RBAC, bounded queues, useful status, metrics, graceful shutdown and a recovery runbook. This offline capstone proves a small orchestration model; the prepared client-go project and owned Kubernetes module supply the separate real-system learning routes.

## Vocabulary and concepts

- **Control-loop invariant:** A property preserved across every reconcile attempt.
- **Resumability:** Recovering useful work from durable state after interruption.
- **Operational contract:** The documented behavior under startup, failure, recovery and shutdown.

## Syntax anatomy and reasoning

The model stores UID, desired count, current count and a write counter. reconcileCap first checks cancellation, then ownership, then input validity, and finally changes state only when needed. The ordering prevents invalid or unauthorized work from reaching mutation. A real adapter adds optimistic concurrency, API errors, status subresources and cleanup. Preserve these boundaries when replacing the in-memory store rather than moving all logic into one untestable function.

## Worked example / walkthrough

### Worked example 1: Converge from a different state

Reconcile owned UID u1 from count 1 to desired 3.

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type CapState struct {
	UID             string
	Current, Writes int
}

func reconcileCap(ctx context.Context, s *CapState, expectedUID string, wanted int) error {
	if err := ctx.Err(); err != nil {
		return err
	}
	if s.UID != expectedUID {
		return errors.New("ownership mismatch")
	}
	if wanted < 0 {
		return errors.New("invalid count")
	}
	if s.Current != wanted {
		s.Current = wanted
		s.Writes++
	}
	return nil
}

func main() {
	// Converge from a different state
	{
		s := CapState{UID: "u1", Current: 1}
		err := reconcileCap(context.Background(), &s, "u1", 3)
		check(err == nil && s.Current == 3 && s.Writes == 1, "converge")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** The count becomes 3 with one write.

The mutation is justified by a current difference under a verified identity.

### Worked example 2: Repeat without duplicate writes

Run the same desired state twice.

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type CapState struct {
	UID             string
	Current, Writes int
}

func reconcileCap(ctx context.Context, s *CapState, expectedUID string, wanted int) error {
	if err := ctx.Err(); err != nil {
		return err
	}
	if s.UID != expectedUID {
		return errors.New("ownership mismatch")
	}
	if wanted < 0 {
		return errors.New("invalid count")
	}
	if s.Current != wanted {
		s.Current = wanted
		s.Writes++
	}
	return nil
}

func main() {
	// Converge from a different state
	{
		s := CapState{UID: "u1", Current: 1}
		err := reconcileCap(context.Background(), &s, "u1", 3)
		check(err == nil && s.Current == 3 && s.Writes == 1, "converge")
	}

	// Repeat without duplicate writes
	{
		s := CapState{UID: "u1", Current: 1}
		check(reconcileCap(context.Background(), &s, "u1", 3) == nil, "first")
		check(reconcileCap(context.Background(), &s, "u1", 3) == nil && s.Writes == 1, "idempotent")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** Only the first call writes.

Repeated notification is normal. Converged state should remain a no-op.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
