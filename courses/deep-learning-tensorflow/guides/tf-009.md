## Purpose and mental model

Training is a sequence of state changes. An example is one input paired with its target. A batch is the set whose losses are reduced before a single update. An epoch is one pass through the chosen examples, whereas an optimizer step is one update. These units differ even on six records. A smaller batch means more updates per epoch, and later batches see weights already changed by earlier batches. Averaging the endpoint weights of separate runs cannot reconstruct this trajectory. Keep record IDs beside values, since a plausible loss cannot reveal that one record was omitted. A short final batch is a real batch unless a deliberate dropping policy removes it. Its mean loss has its own denominator.

## Vocabulary and concepts

**Epoch:** One complete traversal of the selected records.

**Batch:** Observations contributing to one reduced gradient.

**Step:** One optimizer update with the current state.

## Syntax anatomy and reasoning sequence

The slice x[start:start+size] selects consecutive observations without copying the entire dataset. GradientTape records operations in its block; assign_sub applies the measured gradient only after the block. The update counter increments once per slice. The loss is recomputed at each new weight, so changing batch size changes both the number of updates and the values used to calculate later gradients. Use a small learning rate because the largest input here is six.

## Trace the optimizer's clock

An epoch counts exposure to a chosen dataset; a step counts an optimizer
update. Those clocks need not advance together. Six observations in batches
of two produce three updates, while batches of one produce six. Keeping the
epoch count fixed while changing batch size therefore changes the number of
updates, the noise in each gradient and the weights at which later gradients
are evaluated. A fair comparison must say which budget it holds fixed.

For this lesson's y=2x model, a batch gradient is
\(2(w-2)\) times the batch mean of x squared. Starting at \(w=0\) with learning
rate 0.01, the first batch \(x=[1,2]\) has mean square 2.5, gradient -10 and new
weight 0.1. The next batch \(x=[3,4]\) has mean square 12.5 and sees that new weight:
its gradient is -47.5 and the next weight is 0.575. The last batch sees 0.575,
not zero, and produces 1.44425. This is a state trajectory, not three
independent estimates whose final weights can simply be averaged.

The reporting clock is another choice. If two examples have losses 1 and 3
and a final short batch contains loss 8, their overall mean is 4. Averaging
the two batch means 2 and 8 gives 5, which weights batches equally instead of
examples. Accumulate loss sums and contributing counts when reporting an
example-weighted epoch mean. The same rule applies to validation loops.

Shuffling should permute complete example records, including IDs and targets.
The identity ledger is a useful check even when the loss falls: a training
curve cannot reveal that features and labels were shuffled independently.
Dropping the tail is a sampling decision that belongs in that ledger.

## Worked example / walkthrough

### Example A: Count updates

The counter measures updates, not observations. Concatenating the three batches recovers the six original identities exactly once. This check detects both an omitted final slice and a loop that increments once per record.

```python
import numpy as np
import tensorflow as tf

ids=list(range(1,7)); batches=[ids[i:i+2] for i in range(0,6,2)]
assert batches==[[1,2],[3,4],[5,6]]
```

**Expected:** batches [[1,2],[3,4],[5,6]] and 3 updates.

### Example B: Retain a remainder

An epoch with drop_remainder may not expose every record. Naming that choice avoids quietly changing the training population. The tail has one example and its mean gradient must divide by one.

```python
import numpy as np
import tensorflow as tf

ids=list(range(1,7)); batches=[ids[i:i+2] for i in range(0,6,2)]
assert batches==[[1,2],[3,4],[5,6]]
ids=list(range(1,6)); batches=[ids[i:i+2] for i in range(0,5,2)]
assert list(map(len,batches))==[2,2,1]
assert sum((b for b in batches if len(b)==2),[])==[1,2,3,4]
```

**Expected:** sizes [2,2,1]; dropping retains only IDs1..4.

## Common pitfalls and diagnosis

Check the number of optimizer updates before interpreting a changed
training curve. Then inspect the first two before/after weights against the
explicit recurrence. If per-batch metrics look plausible but the epoch metric
disagrees, compare its numerator and denominator with the retained record IDs.
Do not repair a dropped remainder by silently pretending it was observed.
