# k8s-020: DNS and layered network diagnosis

## Level and prerequisites

Intermediate; about 105 minutes plus review. Direct prerequisites: `k8s-007`, `k8s-012`. The chapter separates desired configuration, API acceptance, controller observation and application evidence.

## Learning objectives

Separate DNS resolution, Service backend selection and application response.

## Vocabulary and concepts

Network diagnosis should proceed through distinct layers: the client's namespace/DNS context, name resolution, Service selection and port mapping, transport connection, and application response. A failure at one layer can produce a similar user-visible symptom to another, but the evidence needed to distinguish them differs.

The browser's positive fixture uses an in-cluster client to reach hello on port 8080 and request /version. It does not publish a host port or depend on an external network service. Wrong-port, DNS and arbitrary-route experiments are separate scoped host fixtures because the browser client command and Service port are fixed.

A successful HTTP 404 already shows that some HTTP server answered; it is not a DNS failure. A timeout after name resolution leaves several transport/backend possibilities and should not be labeled NetworkPolicy denial without enforcement evidence. Use the most specific observation available and retain uncertainty where the evidence does not identify a unique cause.

### Key terms

- **Name resolution:** Translating a Service name into an address through cluster DNS. An NXDOMAIN answer fails before any connection is attempted.
- **DNS search configuration:** The Pod's resolver settings that expand a short name such as hello within the Pod's own namespace, so the same short name elsewhere can mean a different object.
- **Service port mapping:** The link from the Service port that clients call to the targetPort on the container. A wrong mapping resolves but reaches no listener.
- **HTTP status code:** The server's numeric answer to a request. A 404 proves that some HTTP server answered, so name resolution and the connection already worked.
- **Layered diagnosis:** Testing name resolution, connection, routing and HTTP response in order, so each result narrows where the request failed.

## Follow the Service name and backend path

A short Service name is interpreted in the client's namespace context. A fully qualified cluster name includes Service, namespace and cluster domain, whose actual value belongs to the environment configuration. Do not assume a name from another namespace resolves to the intended object.

After resolution, the Service's selector and EndpointSlices identify eligible backends. Its client-facing port maps to a target port on those Pods. DNS can succeed while the backend set is empty or the port is wrong. The owned verifier therefore compares identities and uses a fresh application request.

The fixture client has a bounded timeout and a small response-size limit. It accepts only the local synthetic hostname/path contract, so it cannot be repurposed to probe arbitrary external hosts. A source refusal for an unsupported URL is different from an observed network timeout.

## Classify a layered evidence table

Synthetic case A returns NXDOMAIN before a connection attempt. Case B resolves an address but cannot establish a connection within its budget. Case C returns HTTP 404. Case D returns HTTP 200 with the wrong version body. These correspond to name-resolution failure, an unresolved transport/backend problem, route mismatch and application-contract mismatch respectively.

For case B, inspect Service ports, ready endpoint identities and the declared network-policy capability before choosing a cause. A refused connection and a timeout can have different immediate meanings, but neither alone proves a specific CNI policy. For case C, compare the requested path with the application's documented routes.

A response from an unrelated endpoint is not success. Keep the source/Service/Pod identities and exact expected body in the packet so a stale or wrong service cannot satisfy a generic HTTP 200 check.

## Common pitfalls

Do not scan unrelated addresses or use an external endpoint to test a local lesson. A host port-forward is another host capability with its own scope and lifecycle; it is not implied by a ClusterIP Service. The current browser path uses the in-cluster client instead.

A positive one-shot request establishes only its observed path and payload. Production availability, network isolation and DNS reliability require broader evidence. A negative case should remain within a finite timeout and cleanup scope.

## Networking depth supplement

DNS resolution, transport connection and application behavior are separate phases. A name such as `hello` is interpreted through the caller's namespace and resolver search configuration. A qualified service name makes cross-namespace intent clearer, but the cluster domain is configurable and must not be assumed universally. `k8s-048` explains the search and caching behavior.

Loopback is relative to the caller network namespace. A sidecar shares its Pod's network namespace and can use localhost to reach its app. A different Pod using localhost reaches itself. A laptop browser has another namespace and generally needs a deliberately published or forwarded path instead of a raw ClusterIP. `k8s-043` through `k8s-046` make those address and route boundaries explicit.

When name-based traffic fails but a permitted direct endpoint request works, investigate DNS policy and resolver behavior. When both fail, compare the earliest shared failing layer. Do not change a Service selector, open public ports or select another cluster merely because a DNS lookup timed out.
