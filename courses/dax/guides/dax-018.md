## The question and the mechanism

Build a measure-dependent selection by evaluating the measure for each candidate member.

A simple Boolean filter argument to CALCULATE cannot directly refer to a measure. The expression 'keep products whose revenue exceeds 50' needs a candidate set and a measure evaluation for each candidate. FILTER can express that work: iterate a table of product keys, evaluate the measure in each row's transitioned context, and retain the keys meeting the condition.

The candidate table is part of the question. VALUES(Product[ProductKey]) uses visible product keys. ALL(Product[ProductKey]) would deliberately consider a different domain if a key selection is active. Neither version means 'all possible products in the business' unless the model and filter policy establish that population.

The retained key table can filter a later CALCULATE because it preserves its model-column identity. At threshold 50, Notebook and Mug qualify, so their revenues sum to 163. At threshold 90, only Mug qualifies, giving 96. This is not the same as testing whether the overall model revenue exceeds the threshold once and then keeping every product.

## Vocabulary and expression anatomy

FILTER supplies row context over VALUES(Product[ProductKey]). The measure [NetRevenue] performs context transition for that candidate key. The variable Qualifying holds the resulting table; using it as a CALCULATE filter applies those product keys to the measure evaluation. The source uses a table filter rather than an invalid direct measure predicate.

Concepts to explain in your own words: **FILTER**, **measure predicate**, **candidate set**, **table filter**, **lineage**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: Products above fifty

**Starting context:** No incoming filters; consider each visible ProductKey independently.

```dax
EVALUATE
VAR Qualifying = FILTER ( VALUES ( Product[ProductKey] ), [NetRevenue] > 50 )
RETURN ROW ( "Products", COUNTROWS ( Qualifying ), "Revenue", CALCULATE ( [NetRevenue], Qualifying ) )
```

**Context trace:**

1. Candidate revenues are Notebook 67, Pen 24, Mug 96 and Bag BLANK.
2. Keys 1 and 3 exceed 50.
3. Applying those retained keys yields 67 + 96 = 163.

**Hand-derived worked-reference result:**

| Products | Revenue |
| --- | --- |
| 2 | 163 |

The threshold is applied to each product's measure result. A single comparison of the grand total would not perform this segmentation.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: A stricter threshold

**Starting context:** Same candidate population, threshold changed from 50 to 90.

```dax
EVALUATE
VAR Qualifying = FILTER ( VALUES ( Product[ProductKey] ), [NetRevenue] > 90 )
RETURN ROW ( "Products", COUNTROWS ( Qualifying ), "Revenue", CALCULATE ( [NetRevenue], Qualifying ) )
```

**Context trace:**

1. Notebook no longer qualifies because 67 is not greater than 90.
2. Mug's 96 still qualifies.
3. The retained one-key table filters the final measure to 96.

**Hand-derived worked-reference result:**

| Products | Revenue |
| --- | --- |
| 1 | 96 |

Changing the threshold changes membership, not the source's definition of revenue. Keep both decisions visible in a segmentation specification.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Equality at the boundary is excluded.
2. Check the boundary product explicitly.
3. Iterate CustomerKey and invoke the revenue measure.
4. A measure is not allowed in that simple Boolean filter slot.
5. An empty qualifying table stays distinct from a one-row blank table.
6. Define the time window and candidate population before the threshold.
