## The question and the mechanism

Explain why broad filter removal and same-table combinations need model-aware reasoning.

A regular fact table participates in an expanded-table model that includes related one-side attributes. Removing filters with a broad fact-table modifier can therefore clear filters from related dimensions, not merely a visible fact column. In this clean regular star, ALL(Sales) can remove the Customer and Date restrictions that shaped the measure.

Another subtlety is existing combinations of values on one table. Paper and Home are valid categories, and Red is a valid color, but Home/Red is not a stored Product combination. Query optimization and value-filter behavior can combine same-table selections through existing combinations. The label auto-exist describes this family of behavior; it is not a universal instruction that every query or model version uses the same coalescing policy.

The second worked case enumerates requested versus existing combinations without claiming to reproduce a particular engine's hidden filtering plan. When a denominator involving ALL behaves unexpectedly, record the exact query shape, model value-filter setting and retained combinations, then qualify it on the intended engine. Do not replace that analysis with the slogan that ALL always ignores every filter.

## Vocabulary and expression anatomy

Case A compares an expanded fact-table modifier with a narrow amount-column removal. Case B counts an explicitly requested Cartesian pair set and the existing Product pairs satisfying those requests. The latter is a logical domain inspection, not a captured auto-exist execution trace.

Concepts to explain in your own words: **expanded table**, **ALL**, **auto-exist**, **value-filter behavior**, **model scope**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

### Case A: Fact-table removal reaches related dimensions

**Starting context:** Regular Import-style star; starting filters are North and order year 2025; no bidirectional or limited relationships.

```dax
EVALUATE CALCULATETABLE ( ROW ( "Original", [NetRevenue], "ClearExpandedSales", CALCULATE ( [NetRevenue], ALL ( Sales ) ), "ClearAmountOnly", CALCULATE ( [NetRevenue], REMOVEFILTERS ( Sales[NetAmount] ) ) ), Customer[Region] = "North", 'Date'[Year] = 2025 )
```

**Context trace:**

1. The starting context totals 83.
2. ALL(Sales) as a modifier clears filters over its expanded table, restoring the whole-model 187.
3. Removing only Sales.NetAmount does not remove Customer.Region or Date.Year, so the result stays 83.

**Hand-derived worked-reference result:**

| Original | ClearExpandedSales | ClearAmountOnly |
| --- | --- | --- |
| 83 | 187 | 83 |

The scope of a table modifier matters. A relationship or storage-mode redesign can change assumptions and requires fresh semantic checks.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Requested values are not all existing pairs

**Starting context:** Explicit domain comparison: requested Paper/Red and Home/Red versus stored Product combinations.

```dax
EVALUATE
VAR RequestedCategories = DATATABLE ( "WantedCategory", STRING, { { "Paper" }, { "Home" } } )
VAR RequestedColors = DATATABLE ( "WantedColor", STRING, { { "Red" } } )
RETURN ROW ( "RequestedPairs", COUNTROWS ( CROSSJOIN ( RequestedCategories, RequestedColors ) ), "ExistingPairs", COUNTROWS ( SUMMARIZE ( FILTER ( Product, Product[Category] IN { "Paper", "Home" } && Product[Color] = "Red" ), Product[Category], Product[Color] ) ) )
```

**Context trace:**

1. Two requested categories times one requested color gives two candidate pairs.
2. Only Paper/Red exists in Product, represented by Pen.
3. Home/Red is not a stored combination; the existing pair count is one.

**Hand-derived worked-reference result:**

| RequestedPairs | ExistingPairs |
| --- | --- |
| 2 | 1 |

This explains information that can matter when filters are coalesced. It does not by itself determine every ALL or ALLSELECTED result under every value-filter configuration.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.
