dme-042: HTTP serving, concurrency and cancellation boundaries#

Level: Advanced | Prepared runtime: data-engineering

Direct prerequisites: dme-021, dme-041.

Outcome: Exercise a bounded real ASGI contract and resource cleanup.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

A request has a lifecycle#

An online service must control what happens before, during and after computation. A request may wait for admission, acquire a resource, perform work, create an effect and send a response. The caller can disconnect or cancel at any point. If these phases are treated as one indivisible action, the system can leak capacity, duplicate effects or report misleading success and failure states.

Concurrency means multiple operations are in progress at once. In an asynchronous Python application, coroutines cooperate by suspending at await points. That is different from running CPU-heavy work on multiple cores. A blocking numerical function inside an async handler can still occupy the event loop unless the design moves it to an appropriate execution boundary. Threads, processes and accelerators introduce their own cancellation and resource constraints.

This chapter uses a real FastAPI application with HTTPX's ASGI transport. It creates actual asynchronous request tasks, controls their progress with events and cancels them deliberately. No TCP listener, proxy or remote network runs in the pad. That distinction lets us make precise claims: application admission and cleanup are executed, while propagation of a browser disconnect through a real server remains a separate service test.

Bound capacity instead of assuming it is infinite#

The /bounded endpoint permits at most two active requests. An async lock protects the check and increment of the active count. The lock is held only while changing shared state, not throughout the simulated wait. A third request receives HTTP 429 when both slots are occupied. The fixture rejects immediately rather than maintaining an unbounded queue.

Worked case 1: cancel an admitted request and recover capacity#

capacity_case() starts two actual request tasks. It waits until both have entered the endpoint, then sends a third request. The third returns 429 and the active count remains two. The test cancels the first task and awaits its cancellation result. The handler's finally block releases that slot, leaving one active request.

The test then releases the remaining request, verifies its successful response and checks that active count returns to zero. A later request succeeds. The observed maximum active count never exceeds two. These checks cover both the negative admission path and the cleanup path; a test that only saw two successful requests would not detect a leaked counter after cancellation.

Cleanup code also handles the test itself failing. In a final block, it releases waiting handlers, cancels unfinished tasks and awaits them with explicit exception collection. This prevents a failed assertion from leaving background tasks alive in the test loop. Structured cleanup matters in examples because learners often modify assertions and failure points while exploring behavior.

Worked case 2: cancellation after an effect does not undo the effect#

The /effect endpoint records an identified positive-unit operation in application state, then waits before returning its response. The test submits effect-a with three units and waits until the effect has been recorded. It cancels the caller's request task before the response is released. The accepted effect remains in the application state.

A retry using the same operation identity and content returns replayed with total three. A retry using the same identity but 100 units returns 409. The model does not increment the total again merely because the caller failed to observe a response. This is the same unknown-outcome problem encountered in the outbox chapter, now visible at an asynchronous request boundary.

The state here is in memory and does not survive process restart. It demonstrates request reconciliation within one application lifetime, not durable idempotency for a deployed service. A real service would need a durable operation ledger and an atomic connection between the recorded identity and the effect. The SQLite outbox/inbox chapter and complete ML service project supply those separate persistence mechanisms.

Complete worked program#

Run in data-engineering. The async client invokes the real application through an in-process transport. The base URL is an ASGI request label and does not cause an external network connection.

"""Actual asynchronous ASGI admission, cancellation cleanup and uncertain-effect reconciliation."""

import asyncio
from contextlib import suppress

import httpx
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, ConfigDict, Field


class Effect(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)
    operation_id: str = Field(min_length=1, max_length=30)
    units: int = Field(ge=1, le=100)


def application():
    app = FastAPI(docs_url=None, redoc_url=None, openapi_url=None)
    app.state.active = 0
    app.state.maximum = 0
    app.state.lock = asyncio.Lock()
    app.state.two_entered = asyncio.Event()
    app.state.release = asyncio.Event()
    app.state.effect_written = asyncio.Event()
    app.state.response_release = asyncio.Event()
    app.state.effects = {}

    @app.get("/bounded")
    async def bounded():
        async with app.state.lock:
            if app.state.active >= 2:
                raise HTTPException(429, "The bounded local capacity is full")
            app.state.active += 1
            app.state.maximum = max(app.state.maximum, app.state.active)
            if app.state.active == 2:
                app.state.two_entered.set()
        try:
            await app.state.release.wait()
            return {"accepted": True}
        finally:
            async with app.state.lock:
                app.state.active -= 1

    @app.post("/effect")
    async def effect(request: Effect):
        async with app.state.lock:
            prior = app.state.effects.get(request.operation_id)
            if prior is not None and prior != request.units:
                raise HTTPException(409, "Operation identity has conflicting content")
            outcome = "replayed" if prior is not None else "applied"
            app.state.effects[request.operation_id] = request.units
            app.state.effect_written.set()
        await app.state.response_release.wait()
        return {"outcome": outcome, "accepted_total": sum(app.state.effects.values())}

    return app


async def capacity_case():
    app = application()
    async with httpx.AsyncClient(
        transport=httpx.ASGITransport(app=app), base_url="http://fixture"
    ) as client:
        first = asyncio.create_task(client.get("/bounded"))
        second = asyncio.create_task(client.get("/bounded"))
        try:
            await asyncio.wait_for(app.state.two_entered.wait(), 2)
            rejected = await client.get("/bounded")
            assert rejected.status_code == 429 and app.state.active == 2
            first.cancel()
            with suppress(asyncio.CancelledError):
                await first
            assert app.state.active == 1
            app.state.release.set()
            response = await asyncio.wait_for(second, 2)
            assert response.status_code == 200 and app.state.active == 0
            final = await client.get("/bounded")
            assert final.status_code == 200 and app.state.maximum == 2
            return {
                "third_request_status": 429,
                "maximum_active": 2,
                "active_after_cleanup": 0,
                "scope": "actual in-process ASGI task cancellation, not a proxy or TCP timeout",
            }
        finally:
            app.state.release.set()
            for task in (first, second):
                if not task.done():
                    task.cancel()
            await asyncio.gather(first, second, return_exceptions=True)


async def effect_case():
    app = application()
    payload = {"operation_id": "effect-a", "units": 3}
    async with httpx.AsyncClient(
        transport=httpx.ASGITransport(app=app), base_url="http://fixture"
    ) as client:
        task = asyncio.create_task(client.post("/effect", json=payload))
        try:
            await asyncio.wait_for(app.state.effect_written.wait(), 2)
            task.cancel()
            with suppress(asyncio.CancelledError):
                await task
            assert app.state.effects == {"effect-a": 3}
            app.state.response_release.set()
            retry = await client.post("/effect", json=payload)
            conflict = await client.post("/effect", json={**payload, "units": 100})
            assert (
                retry.json() == {"outcome": "replayed", "accepted_total": 3}
                and conflict.status_code == 409
            )
            return {
                "caller_cancelled_after_effect": True,
                "retry": retry.json(),
                "conflicting_retry_status": 409,
                "state_is_in_memory_and_does_not_survive_process_restart": True,
            }
        finally:
            app.state.response_release.set()
            if not task.done():
                task.cancel()
            await asyncio.gather(task, return_exceptions=True)


def example_one():
    return asyncio.run(capacity_case())


def example_two():
    return asyncio.run(effect_case())


def main():
    print("Bounded admission and cleanup:", example_one())
    print("Cancellation does not reverse an accepted effect:", example_two())


if __name__ == "__main__":
    main()

Cancellation is a signal with boundaries#

Cancelling an asyncio task requests cancellation at a suspension point. It does not reverse a database commit, unsend an email or necessarily stop a running thread, subprocess or GPU kernel. A timeout observed by one layer may leave work continuing in another. The system needs a clear policy for work that remains in flight and for the effects it may produce.

For pure inference, cancellation may allow the service to discard an eventual result while releasing request bookkeeping, even if computation cannot be interrupted immediately. For a state-changing operation, the caller needs a stable identity and a way to query or reconcile the outcome. Returning a generic “failed” message when the effect actually committed can encourage an unsafe retry. Preserve the difference between computation failed, response not observed and accepted effect recorded.

Shielding a task from cancellation can be appropriate for a short critical cleanup or durable bookkeeping step, but indiscriminate shielding can let abandoned work consume resources indefinitely. Cleanup must itself be bounded and designed for failure. The simple fixture releases a local counter under a lock; a production cleanup that waits on a remote dependency needs a more careful recovery plan.

Queueing, overload and response codes#

Immediate rejection is one overload policy. A bounded queue is another. An unbounded queue can turn a transient burst into long latency, memory growth and a wave of client timeouts. If clients retry those timeouts, the system can amplify its own load. Capacity limits, queue limits, deadlines and retry budgets should be designed together.

A 429 response in this fixture means the service's declared capacity is full. Production semantics may distinguish rate limiting from unavailable capacity and may provide a retry hint. Whatever status is chosen, it should be observable and consistent with the client's policy. Do not remove overload responses from reliability metrics simply because they use a 4xx code; eligibility follows the service promise, not only the numeric status family.

The next capacity chapter uses a deterministic queue model to show why the same average request rate can produce different tail latency under bursts. This chapter establishes the implementation boundary that such a model describes: admission, active work, completion and release.

Diagnose lifecycle defects#

If capacity never recovers after cancellations, inspect cleanup paths and whether the active counter is decremented exactly once for every admitted request. If the counter becomes negative, inspect double cleanup or rejection paths that decrement without acquiring. If concurrency exceeds the limit, inspect whether checking and incrementing occur atomically.

If retries create duplicates, inspect operation identity and the effect's commit boundary. If an application test passes but real clients still hang, inspect server, proxy and transport timeouts separately. If CPU-heavy inference blocks unrelated lightweight requests, inspect event-loop blocking rather than adding more async keywords. Async syntax changes scheduling only when the awaited operations actually yield appropriately.

Applications and answered interview discussion#

These ideas apply to prediction APIs, data imports, report generation and interactive tools. Long-running inference introduces additional resource lifetimes, especially when streaming partial results. The later LLM-serving chapters extend the same reasoning to token queues, cancellation, caches and SSE output.

An interviewer may ask, “Does cancelling a request guarantee no work happened?” Explain the phase at which cancellation occurred and which effects were already accepted. If asked how to enforce a limit, describe atomic admission and cleanup on every exit path. If asked how to test concurrency reliably, explain controlled events and explicit state assertions rather than timing guesses.
