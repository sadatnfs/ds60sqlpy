Extend the curriculum#

A subject is a learning sequence. A runtime is the tool that executes its code. A lesson can reuse a runtime, be reading-only, or use the explicit offline DAX editing contract. All subjects join the same /classroom home, workspace, navigation and saved-work experience.

Start with the learner's goal and a real gap, then choose the existing content contract. Do not register empty lessons just to reach a desired count. The add-learning-path skill turns this playbook into a reusable contributor-agent workflow.

Choose the correct registration route#

Change Durable registration Validation
Extend existing Python, SQL or bridge material Existing artifacts and catalog_builder.py; additive legacy manifests when appropriate Legacy catalog, practice and depth gates
Add a tutorial subject Normal track.json with learning_mode: "tutorial", plus lessons.json and complete worked source Tutorial semantics, prerequisites, numerical examples, output contracts and rendering
Add a new subject to the classroom courses/<subject>/track.json and lessons.json ModuleCatalog, subject tests and browser/runtime checks
Extend one of the original five module subjects Existing plan under docs/expansion/plans/ and its courses/<subject>/lessons.json Same module gates and core-plan validation
Extend the statistics tutorial courses/statistics-ml/manifest.json or additive tutorials/index.json, chapters, examples and coverage Tutorial coverage, numerical examples and rendering
Add a new execution language or external operation Reviewed backend adapter, profile and image in addition to content Actual runtime success, failure, cleanup and persistence evidence

The original five module subjects are Kubernetes, TensorFlow, LLM theory, C++ and Scala/Spark. Their plans supply live route metadata; authored admission still comes from lessons.json. module_plans.load_core_plans owns these five plan inputs. Additive subjects use track.json. Do not migrate an existing subject between these contracts as an incidental edit.

The original statistics loader remains specific to its chapter/outline contract. New tutorial subjects use the validated additive track learning_mode: "tutorial" contract, as in Applied Science and Bayesian Computing. The default is practice. Tutorials expose complete worked source and may have empty solution_paths; ordinary practice keeps its separate learner/reference artifacts. Do not assume any arbitrary manifest.json is automatically discovered.

Design a useful progression#

Define the starting knowledge, observable independent project and prerequisites. Build the shortest sequence that teaches the mechanisms needed for that project:

  1. Orient the learner: where code lives, what Run does, where output appears, and how to read an ordinary error.
  2. Teach values, representations, control flow or query composition with small traces and exact observations.
  3. Introduce abstraction, data structures, contracts, state and error handling.
  4. Connect multiple pieces through tests, debugging, files or bounded data.
  5. Explain performance, concurrency, ownership or distributed semantics where they matter to the subject.
  6. Finish with an independently designed project and explicit tradeoffs, limitations and recovery behavior.

A beginner does not need every advanced topic immediately. Cross-subject prerequisites should name stable IDs, not hide a whole language inside a single introductory lesson. See the skill's progression reference for the language, web, GPU/ML, data and systems routes. Preserve distinctions such as browser versus Node, PHP CLI versus HTTP, CPU models versus NVIDIA execution, and Spark CPU operators versus supported accelerated plans.

Author and integrate a module#

Follow ADDING_A_MODULE.md for exact route, manifest, variant and runtime boundaries. Inspect an existing subject and the loader instead of guessing fields. There is no universal scaffold command in this repository. Create only the files needed for the chosen subject and use an existing subject's documented authoring command only for that subject.

Write the self-contained guide, learner artifact, reference and explanatory solution under courses/<subject>/. Define vocabulary, show worked examples, include expected observations and misconceptions, and provide progressive practice. Reading-only practice uses reasoning and a separate explanation. Tutorial-mode subjects have no exercise quota or hidden answer gate. Read the scientist roadmap before duplicating an already implemented scientific or data-engineering sequence.

Preserve IDs, variant aliases and state ownership. Add accessible subject colors and a text label to the existing UI; do not add another public page. Review the declared runtime before promising a Run action. A syntax lexer or file extension does not install a compiler. New ordinary workers also need the image catalog and launcher, formatting/lint adapters, source packaging and CI profile checks. Optional GPU/cluster routes require explicit capabilities and separate qualification rather than entry into ordinary defaults.

HTML/CSS and browser JavaScript use the shared opaque preview. Live updates are opt-in, cancel on navigation and do not automatically create result receipts. PHP HTTP/session examples use a separately owned project rather than pretending that the CLI worker is a web server. GPU lessons should retain meaningful reading/CPU routes without claiming those routes execute CUDA on another GPU.

Legacy catalog extensions#

Use curriculum/extensions/<subject>.json only when deliberately extending the legacy catalog contract. The inactive example shows its schema. It is not a template for modern track.json/lessons.json module registration and does not assert that its referenced files exist.

Legacy manifests use schema_version: 1, tracks, complete lessons, and optional learning_paths. Their runner and allowed suffixes come from src/ds60sqlpy/curriculum_framework.py. Preserve historical track/day pairs, IDs and the acyclic prerequisite graph. Add new legacy IDs to curriculum/practice_expansion.json with baseline zero and target six; do not change the historical baseline. Do not add module or tutorial IDs to that registry simply because they are new lessons.

The legacy capability descriptors can differ from module workers. Existing C++ and Scala module execution does not imply that a legacy extension entry using the same language has its own adapter. Report the capability of the actual route, not the availability of a different route's compiler.

Verify and publish#

From a prepared development environment at the repository root:

python scripts/check_modules.py
python scripts/normalize_lesson_prose.py --write
make generate
python scripts/normalize_lesson_prose.py
python scripts/check_content_rendering.py
python scripts/course.py validate
python scripts/audit_practice.py
python scripts/audit_lesson_depth.py
python scripts/build_course_guide.py --check
python scripts/build_lesson_readers.py --check
node scripts/check_classroom_ui.mjs

Use the documented subject authoring command before this sequence where one exists. Review all generated changes. Test changed reference programs and misconceptions in the intended worker; use a disposable classroom project for writes. Verify guide rendering, source loading, explicit solution reveal, subject/variant switching, saved drafts, result history and fresh-container restoration. Check read-only tutor discovery when registration changes.

Keep first-download preparation, offline execution and optional external resources distinct. Record exact checks and unresolved platform limits. Validation describes the grouped parallel suite and CI gates. A count check, build or reference execution alone does not establish a complete learning experience or independent learner competence.

Additional language and artifact contracts#

New language admission must include LANGUAGES and SOURCE_SUFFIXES in modules.py, a readable language label, the reader lexer/extension mapping, formatter/linter coverage and real source loading tests. A new runtime also needs the fixed worker operations, startup probe, private service mapping, Docker image/locks, launcher and image catalog, success/failure qualification cases and CI coverage. Merely adding the language name is insufficient.

For DAX-style offline editing, use an explicit draft capability and reject Run on both service and job boundaries. Validate reference/model bytes and typed worked tables; never imply that a learner edit produced those tables. For plotted outputs, follow the existing bounded artifact contract and test saved-result readback separately from chart rendering. Add only the prepared libraries a lesson actually uses.

After prose changes, compile TeX before generating readers. Maintain professional factual copy, preserve literal code, and review mathematical meaning independently of successful rendering. Keep current source hashes distinct from historical runtime evidence.

For current scientific and data examples, inspect the authored Applied Science, Bayesian Computing, Julia, Polars, dbt, ML engineering and LLM evaluation routes. A dbt SQL-model variant and its complete Python/CLI project serve different learning needs. A Stan pad and its separate JSON-data project are similarly distinct. A local ML HTTP service needs its own owned lifecycle and durable state, not an unbounded worker process. Reuse those contracts only when the new subject has the same requirements.
