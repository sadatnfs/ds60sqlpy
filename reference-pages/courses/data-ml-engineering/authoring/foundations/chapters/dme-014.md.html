dme-014: Event time, availability time and late-known facts#

A correct timestamp can still be the wrong clock#

A record may describe an event that happened earlier, become available later and be processed at another time. A model prediction or historical report has its own decision cutoff. Conflating these clocks can make a result look temporally reasonable while using information that was not actually available for the intended decision.

This chapter uses explicit integer hours relative to a fixed illustrative origin. It does not read a live clock or claim to operate a broker. The code is a bounded historical-selection mechanism over supplied observations. Its purpose is to define the information rule precisely before implementing it in SQL, a feature store or a streaming system.

An event time describes when the measured occurrence happened under the business contract. A known time describes when that information became available to the relevant consumer. A processing time describes when a computation handled it. A decision cutoff describes which information is eligible for a particular decision. These can all differ without any timestamp being malformed.

The earlier timezone chapter established how an instant is represented. Here the question is what the instant means. Converting every timestamp to UTC does not make event time and availability time interchangeable.

Define the historical feature you want#

The example asks for the latest historical observation that was known at the decision cutoff. For this particular observational feature, a row is eligible only when both its event hour and known hour are no later than the cutoff. Among eligible rows, the function chooses the greatest event hour and then the greatest known hour for a revised observation at that event time.

This definition applies to the declared historical-observation feature. A forecast about a future date can legitimately be known today; its issuance and target-time semantics need a different explicit contract. Do not turn one convenient predicate into a universal rule for every kind of time-indexed data.

The selector also rejects conflicting values that share the same selected event and known clocks. Choosing whichever row happened to appear first would make the result depend on incidental input order. A real producer may supply a separate version or sequence identity, which should then become part of the reviewed tie-resolution rule.

Late arrival and revision are different from a new event#

An observation can arrive late without becoming the latest business event. Suppose an event at hour four becomes known at hour eight, while an event at hour six was already known at hour six. At hour nine, the latest event is still the hour-six observation. Sorting only by arrival time would answer a different question: which information arrived most recently.

The late fact may nevertheless matter to another calculation. It could change a historical aggregate, trigger a backfill or reveal a source-quality problem. The latest-value selector does not declare the fact useless or authorize deleting it. Its output is limited to the particular feature definition in this chapter.

Corrections introduce another dimension. A new version of an older observation may alter its value while retaining its business event time. The consumer needs to know when that correction became available. A table containing the latest corrected history is not automatically safe for reconstructing what a past decision-maker knew.

Worked case 1: Event-only and arrival-only ordering both mislead#

The fixture contains three observations. One happened at hour two and was known at hour three, with value ten. Another happened at hour four but was not known until hour eight, with value 999. The last happened and became known at hour six, with value twenty.

At decision hour five, the eligible value is ten. The hour-four observation looks historical by event time, but it was not yet known. An event-only query would leak the value 999 into that earlier decision. The event at hour six is also ineligible because it had not happened under this historical-observation contract.

At decision hours seven and nine, the selector returns twenty. By hour nine the late hour-four observation is known, but it is still older in event time than the hour-six observation. Sorting only by known time would incorrectly replace twenty with 999 for the latest-event question.

The actual expected sequence is therefore [10, 20, 20] for cutoffs five, seven and nine. The program independently checks the misleading alternatives and records their value of 999. The Plotly figure places event hour on one axis and known hour on the other, with the hour-five cutoff shown on both axes. Only the point satisfying both boundaries is eligible at that cutoff.

The figure is a representation of these supplied records, not a measurement of a production pipeline's latency distribution. Its accessible table retains the exact event, known and value fields so the conclusion does not depend on interpreting the picture alone.

Coverage belongs to the request population#

Historical retrieval must also account for requests that have no eligible feature. Dropping those requests can silently change a training or evaluation population. A returned value of zero is different from no returned observation, so truthiness is not a safe test for feature availability.

Worked case 2: Keep unknown and measured zero distinct#

The changed case uses one known observation with value zero and a later observation with value twenty. It requests features at cutoffs one, five and seven. The expected values are None, zero and twenty. All three request identities remain in the result.

The known subset contains the requests named zero and later, so coverage is two out of three. Filtering with value is not None preserves the valid zero. A truthiness check would treat that zero like missing information and produce the wrong coverage.

The case then adds a conflicting value at the same selected event/known clock pair and confirms that the selector rejects the ambiguity. This is another reason to preserve identity and version meaning: a deterministic-looking sort is not a valid substitute for a declared conflict policy.

The classroom retains a compact report containing the requests, their selected values, coverage and the negative-case result. It does not automatically impute the unknown request or claim that excluding it is harmless for model training. A later workflow must choose and evaluate that policy explicitly.

Complete worked program#

Diagnose temporal leakage and false freshness#

First name the clock that each field represents. Check how it was produced and whether corrections preserve the original availability information. A field called timestamp is not enough to establish its role.

Then inspect the population and tie rules. Are requests missing from the result? Can two source records match the same key and clock? Does a join select a current corrected value rather than the version known at the cutoff? Does a late-arriving old event overwrite a newer business observation because the consumer orders by processing time?

Also separate historical eligibility from current serving freshness. A value can be valid for a past cutoff yet stale for a request today. A successful online-store read is not proof of a recent observation. Define an acceptable age or other freshness policy using the appropriate source metadata and test the actual rejection behavior.

Where this is useful#

These distinctions matter in feature generation, forecasting, experimentation, causal analysis, reporting corrections, stream windows and backfills. They are particularly useful when an offline model appears unusually accurate: inspect whether its inputs include information unavailable at the intended prediction time before interpreting the score as genuine performance.

Answered interview discussion#

Why can an event-time filter still leak information? The event may have happened before the cutoff while its value or correction became known afterward. Eligibility needs the appropriate knowledge boundary as well as business time.

Is the last arrival always the current feature? Only if that is the declared feature definition. The latest business event and most recently received information can be different records.

Should requests without features be removed? Not silently. Retain the authoritative request population, expose coverage and evaluate any exclusion or imputation policy against the intended deployment population.

Can a future-dated field ever be a valid input? Yes, when its meaning is information genuinely known at the cutoff, such as a declared forecast or schedule. The issuance, target and availability contracts must be explicit; a generic timestamp rule cannot decide that alone.
