dme-067: KV memory planning, paging and shared-prefix ownership#

Level: Advanced | Prepared runtime: python-core

Direct prerequisites: dme-066.

Outcome: Calculate page fragmentation and preserve shared prefix state through copy-on-write.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

A model can fit in device memory while its serving workload does not. Every active sequence accumulates keys and values across layers, and long contexts or many simultaneous requests can make that cache a major allocation. Memory planning must consider the dynamic request set, not only the checkpoint size.

This chapter uses a CPU allocation model and exact byte arithmetic. It does not execute a paged-attention GPU kernel. The live workshop uses a small contiguous cache per request; paging and shared prefixes are advanced mechanisms taught separately so their behavior is not confused with the implemented scheduler.

Grouped-query or multi-query attention changes the number of KV heads relative to query heads. Cache precision can differ from weight precision and needs its own correctness evaluation.

The formula excludes allocator metadata, page tables, alignment, temporary operations and retained unused capacity. It also excludes the weights themselves. A service that fills the entire nominal device capacity with weights and idealized cache estimates has left no room for the remaining runtime.

A maximum-length contiguous reservation is easy to index but may waste space for short or early-terminating sequences. Repeatedly reallocating a growing contiguous cache avoids some unused capacity but introduces copying and fragmentation. The workshop chooses the latter simple approach because its context is tiny; the limitation is explicit.

Pages separate logical sequence order from physical storage#

A paged cache divides storage into fixed-size blocks. A request has a logical sequence of blocks, while a page table maps those logical positions to physical allocations. Adding tokens may require one new page instead of moving the entire existing cache. Attention kernels must understand the mapping to read the correct keys and values.

Unused slots inside final pages are internal fragmentation. Smaller pages reduce that waste but increase metadata and mapping work. Larger pages may improve locality or simplify access while wasting more capacity. The best choice depends on kernels and workload; a neat page-count equation alone cannot choose it.

Paging does not eliminate the need for admission. A finite pool can still exhaust. The scheduler must know whether it can allocate the next page or has conservatively reserved sufficient growth. Allocation failure during decode needs a declared terminal behavior, not an unbounded retry loop that leaves other requests waiting indefinitely.

Shared prefixes and copy-on-write#

If two requests have exactly compatible prefixes, their computed cache blocks may be shareable. Compatibility includes model/checkpoint identity, tokenizer/template policy, positions, relevant attention configuration and the exact token prefix. Similar-looking text is insufficient. Access-control and isolation policy also matter in a multi-user deployment.

A shared block needs a reference count or another ownership mechanism. A fully computed shared prefix must remain immutable while other requests use it. If one branch appends to a partially filled shared page, it must allocate a private copy before writing. This is copy-on-write: the shared content remains unchanged for the other branch.

Incorrect reference counts can free a page still in use or leak pages forever. Incorrect copy-on-write can make one request's continuation alter another's prefix. These are serving correctness and isolation failures, even if the model arithmetic itself is perfect. Tests should branch, extend, cancel and release requests in varied orders.

The workshop does not share caches across requests. That simpler ownership rule makes its exact cancellation behavior easy to inspect. A future prefix-cache extension would need the compatibility keys and lifetime tests described here before it could be called implemented.

Worked case 1: page rounding and a real byte formula#

The first case considers sequence lengths five, nine and fifteen with page size four. The 29 used token positions occupy 36 page slots. A hypothetical fixed reservation of 32 positions per request would occupy 96 slots. Paging reduces this specific reserved capacity while still leaving seven unused final-page slots.

Then the program calculates a 32-layer, eight-KV-head, width-128 cache for 4,096 tokens at two bytes per element. The result is exactly 0.5 GiB. That value is a raw tensor calculation under the stated architecture, not a measured device allocation. It can serve as a useful cross-check against actual memory observations.

If the observation differs substantially, inspect active sequence counts, cache dtype, additional buffers, block rounding and allocator reservation before assuming the formula is wrong. The formula answers a narrower question than a process's total resident memory.

Worked case 2: a branch writes a shared tail#

The second case starts with two requests sharing pages zero and one. Page zero is full; page one contains two tokens. Both pages have reference count two. Request b wants to append token 99. The program copies page one to a new page, decrements the old reference count and updates only b's mapping.

The expected mappings are a: [0,1] and b: [0,2]. The old tail remains [14,15]; the private tail becomes [14,15,99]. Reference counts become two for the shared full page and one for each tail. These exact assertions expose an in-place mutation bug that would otherwise contaminate request a.

"""Paged-cache accounting and copy-on-write ownership as an explicit CPU model."""

import math


def cache_bytes(layers, kv_heads, width, tokens, element_bytes=2):
    return 2 * layers * kv_heads * width * tokens * element_bytes


def example_one():
    lengths = [5, 9, 15]
    page = 4
    allocated = sum(math.ceil(length / page) * page for length in lengths)
    assert allocated == 36 and sum(lengths) == 29
    reserved = len(lengths) * 32
    assert reserved == 96
    print("Used tokens", sum(lengths), "page slots", allocated, "fixed maximum slots", reserved)
    assert cache_bytes(32, 8, 128, 4096) == 2**29
    print("32-layer grouped-query KV GiB:", cache_bytes(32, 8, 128, 4096) / 2**30)


def example_two():
    pages = {0: [10, 11, 12, 13], 1: [14, 15]}
    mappings = {"a": [0, 1], "b": [0, 1]}
    refs = {0: 2, 1: 2}
    old = mappings["b"][-1]
    new = max(pages) + 1
    pages[new] = pages[old].copy()
    refs[old] -= 1
    refs[new] = 1
    mappings["b"][-1] = new
    pages[new].append(99)
    assert pages[1] == [14, 15] and pages[2] == [14, 15, 99]
    assert mappings == {"a": [0, 1], "b": [0, 2]}
    assert refs == {0: 2, 1: 1, 2: 1}
    print("Prefix-sharing maps", mappings, "reference counts", refs)
    print("A page table alone does not execute paged attention on a GPU.")


def main():
    example_one()
    example_two()


if __name__ == "__main__":
    main()

Eviction, preemption and accounting#

A prefix cache retained after requests finish is different from an active request's live KV allocation. Retained reusable pages may need eviction when memory is scarce. Eviction policy should not free pages still referenced by active computations. A page selected for eviction may also have in-flight operations that require synchronization before reuse.

Preempting an active request may involve swapping cache state, recomputing a prefix later or cancelling the request. These choices trade memory, compute and latency differently. Recomputing must not be confused with replaying an entire completed user action. The system needs explicit request state and a bounded policy for how work resumes.

Memory utilization is not the same as useful throughput. A very high occupancy can leave too little room for temporary operations, causing failures or reducing scheduling flexibility. Report rejected requests, allocator failures and tail latency alongside any utilization metric. A service that rejects all long contexts can appear efficient while failing the intended workload.

Interview discussion#

What does a page table provide? A mapping from a sequence's logical cache positions to physical blocks. The attention kernel and scheduler must honor it; the table itself performs no attention computation.

When is copy-on-write necessary? When a request wants to modify a shared allocation that another request must continue to observe unchanged, such as appending to a shared partial tail page.

Why can a prefix cache be unsafe even when tokens match? Model version, positions, tokenizer/template policy, attention settings and authorization can differ. Cache reuse must validate the complete compatibility and access contract.
