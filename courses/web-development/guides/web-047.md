# web-047: Server form validation and redisplay without data loss

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-046`

## Learning objectives

Build a validator returning cleaned values and field-specific errors. Explain the limits of POST redirect GET. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A server receives untrusted input even when the page supplied a constrained control. A caller can omit fields, send an array where a string was expected, alter a hidden value or bypass the browser entirely. Validate shape, type, length and domain rules before using values. An allowlist defines accepted choices; rejecting only known bad strings is usually harder to reason about.

Separate raw input, validated domain values and rendered output. Keep useful user input for redisplay after a validation error, but escape it in the HTML context. After a successful state-changing POST, a redirect to a GET page can reduce accidental resubmission on refresh. That pattern does not by itself provide idempotency, CSRF protection or authorization.

## Syntax anatomy and mechanism

A pure validator returns a value and an error map. Check is_string before trim or numeric parsing because request fields can be arrays. For an integer text field, define an accepted syntax and range explicitly. The example uses a bounded decimal digit pattern, then converts only after it passes. The CLI inputs model POST data; no form is submitted.

## Classroom execution and offline inputs

Choose the **PHP CLI** worker in the classroom. The pad is staged as `main.php` and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write `<?php` at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

## Worked example / walkthrough

### Worked example 1: Reject the wrong shape

The value must be a string before string operations.

```php
$raw = $input['topic'] ?? null;
if (!is_string($raw)) { $errors['topic'] = 'Choose a topic.'; }
```

**Expected observation:** An array-shaped field is rejected without a type error.

### Worked example 2: Validate a bounded decimal field

The accepted syntax is deliberate.

```php
if (!is_string($rawMinutes) || !preg_match('/^[0-9]{1,3}$/D', $rawMinutes)) { $errors['minutes'] = 'Use whole minutes.'; }
```

**Expected observation:** Unexpected syntax fails before numeric conversion.

## Six progressive exercises

### Exercise 1: Predict what happens when a caller sends topic[]=HTML.

**Expected evidence:** The server can receive an array, so a string-shape check is required.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add an allowlist for supported topics.

**Expected evidence:** Only explicitly declared topic values are accepted.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a validator returning cleaned values and field-specific errors.

**Expected evidence:** Valid data has a complete domain value; invalid data has actionable errors and no partial write.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose trimming an array-shaped request value.

**Expected evidence:** Validate its type before calling a string function.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test missing fields, arrays, out-of-range minutes and valid data.

**Expected evidence:** Each case returns a deliberate validation result without an uncaught type error.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain the limits of POST redirect GET.

**Expected evidence:** It helps refresh behavior but does not replace authorization, CSRF checks or duplicate-operation design.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not use hidden inputs as trusted prices or identities. Browser constraints are a convenience, not server enforcement. Avoid silently accepting partially validated records because one field looked correct.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain server validation, allowlist, field error without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
