# Atomic functions and custom derivative contracts

Start with: tmb-046, tmb-006.

Outcome: Design and test a custom derivative boundary without silently truncating derivatives.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter checks a reverse-mode derivative rule for \(x^4\) against finite differences. The separately prepared [C++ API probes](../projects/tmb-cpp-api/README.md) compile `models/atomic_quartic.cpp`, and `check.R` checks its atomic value, gradient and Hessian; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

An atomic function packages an operation behind a derivative-aware boundary. It can reduce tape size or expose an efficient algorithm whose derivatives are known. It also moves responsibility to the author: a wrong reverse rule makes the entire model's gradient wrong even when forward values look perfect.

TMB provides `TMB_ATOMIC_VECTOR_FUNCTION` and framework-specific implementation support. The pinned macro takes a name, output dimension, forward calculation and reverse calculation. It is a low-level extension mechanism, not a routine requirement for ordinary likelihood code. Prefer ordinary typed operations or reviewed built-in atomics when they already meet the need.

## Key terms

- **Atomic function:** An operation packaged behind a derivative-aware boundary whose author supplies the forward and reverse rules.
- **Reverse rule:** The code that maps an output adjoint to input adjoints, computing \(J^T\bar y\) rather than forming the full Jacobian \(J\).
- **Adjoint:** The derivative of the final objective with respect to an intermediate value; for \(y=x^4\), \(\bar x=4x^3\bar y\).
- **TMB_ATOMIC_VECTOR_FUNCTION:** The macro that defines a custom atomic from a name, output dimension, forward calculation and reverse calculation.
- **Higher-order check:** Testing derivatives beyond the first order at many points, needed because Laplace gradients and Hessians differentiate atomics again.

### Worked case A: derive the reverse rule

For \(y=x^4\), an incoming output adjoint \(\bar y\) produces input adjoint \(\bar x=4x^3\bar y\). For a vector function, the reverse rule computes \(J^T\bar y\), not the full Jacobian unless that is explicitly needed. The companion checks this rule with two different incoming adjoints and finite differences of the scalar composition.

A custom macro implementation must account for every input and output component, including zeros and unused coordinates. Its forward code may run on ordinary doubles while reverse code runs in a typed AD context. Casting reverse intermediates to double can make first derivatives appear plausible while breaking higher-order derivatives.

### Worked case B: a derivative that passes one point and fails elsewhere

A deliberately wrong derivative \(4x^3+0.1(x-1)\) agrees with the true derivative at x=1. The companion checks additional points and exposes the error. A derivative test only at the fitted optimum can likewise miss a broken implementation. Use a grid, random but seeded points, domain edges and incoming-adjoint variations.

Laplace gradients and Hessians can require derivatives beyond the first level. A custom atomic accepted for a fixed-effect first derivative is not automatically accepted for a latent model's higher-order requirements. Test the exact required derivative order under the chosen CppAD/TMBad build and report unsupported orders explicitly.

### Answered discussion

**Are atomics always faster?** No. They can reduce recording overhead but introduce their own call, memory and derivative costs. Benchmark only after numerical qualification. **Can a finite-difference reverse rule be used?** It changes accuracy and performance guarantees and needs a carefully stated approximation policy; it is not exact AD. **Should learners edit the library's internal atomic implementation?** Keep experiments in owned source with a clear boundary instead of modifying installed dependency internals.

Read the [TMB atomic macro interface](https://github.com/kaskr/adcomp/blob/master/TMB/inst/include/atomic_macro.hpp) and its [TMBad counterpart](https://github.com/kaskr/adcomp/blob/master/TMB/inst/include/tmbad_atomic_macro.hpp). This chapter's companion validates the derivative contract mathematically. The separate original quartic atomic in `projects/tmb-cpp-api` also compiled and passed value, gradient and Hessian oracles at three points on native Linux ARM64 with CppAD. This narrow test record does not qualify every custom atomic or TMBad variant.

### Worked case C: the reverse rule at the companion's points

The loop checks six combinations of point and incoming adjoint. Three of them, worked by hand (closed-form values):

```text
   x     adjoint   4 x^3       reverse = 4 x^3 * adjoint
-0.7     0.3      -1.372       -0.4116
 0.4     2.0       0.256        0.512
 1.3     2.0       8.788       17.576
```

The finite difference multiplies the function by the adjoint before differencing, so it checks the full product \(\bar y \, f'(x)\) and not merely \(f'(x)\). Using two different adjoints matters: a reverse routine that forgot to multiply by the incoming adjoint would still pass at \(\bar y = 1\), and neither of the companion's adjoints is 1.

The wrong-derivative table reads:

```text
 x    true   wrong    error
-1     -4    -4.2     -0.2
 0      0    -0.1     -0.1
 1      4     4.0      0.0
 2     32    32.1      0.1
```

The error is \(0.1(x - 1)\), so it vanishes only at \(x = 1\). A test at an optimum that happens to sit at 1 would pass the broken rule; three of four grid points expose it.

### Worked case D: the vector reverse rule

For a two-output atomic \(y = (x_1 x_2, \; x_1^2)\) the Jacobian is \(J = \begin{pmatrix} x_2 & x_1 \\ 2x_1 & 0 \end{pmatrix}\), and the reverse rule returns \(J^T \bar y = (x_2 \bar y_1 + 2x_1 \bar y_2, \; x_1 \bar y_1)\). At \(x = (0.5, -2)\) and \(\bar y = (1, 3)\) that is \((-2 + 3, \; 0.5) = (1, 0.5)\) (hand-derived). A check in R that mirrors the companion:

```r
g <- function(x) c(x[1] * x[2], x[1]^2)
x <- c(.5, -2); ybar <- c(1, 3); h <- 1e-6
reverse <- c(x[2] * ybar[1] + 2 * x[1] * ybar[2], x[1] * ybar[1])
numeric <- sapply(1:2, function(j) {
  e <- replace(numeric(2), j, h)
  sum(ybar * (g(x + e) - g(x - e))) / (2 * h)
})
stopifnot(max(abs(reverse - numeric)) < 1e-7, all.equal(reverse, c(1, .5)))
```

A common error is returning \(J \bar y\) instead of \(J^T \bar y\). With this \(J\), \(J \bar y = (-2 + 1.5, \; 1) = (-0.5, 1)\), which the check rejects.

### Why the Laplace path needs more than the first rule

In a latent model the inner Hessian of the joint NLL with respect to the random effects enters \(\tfrac12 \log|H|\), and the outer gradient differentiates that term again. For the quartic, the second derivative is \(12x^2\), so at \(x = 1.3\) it is \(20.28\). If the reverse code cast \(4x^3\) to `double` before multiplying, the first derivative would still read 8.788 at that point, while the tape would see a constant and return a second derivative of 0. The fit would then use a wrong log determinant without any error message.

### Base-R companion (runs in the classroom)

```r
f <- function(x) x^4;h <- 1e-6
for (adjoint in c(.3, 2)) for (x in c(-.7, .4, 1.3)) {
  reverse <- 4 * x^3 * adjoint;numeric <- (adjoint * f(x + h) - adjoint * f(x - h)) / (2 * h)
  stopifnot(abs(reverse - numeric) < 1e-7)
}
x <- c(-1, 0, 1, 2);wrong <- 4 * x^3 + .1 * (x - 1)
print(data.frame(x = x, true = 4 * x^3, wrong = wrong, error = wrong - 4 * x^3));stopifnot(wrong[3] == 4, any(abs(wrong - 4 * x^3) > .05))
```
