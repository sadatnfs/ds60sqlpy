# web-023: Print styles, progressive enhancement and resilient delivery

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-022`

## Learning objectives

Build printable study notes with a useful baseline layout. Explain what a feature query proves and what it does not. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

Progressive enhancement starts from useful content and adds capabilities when the environment supports them. A document should communicate its core information before advanced styling or scripts run. This does not mean every application must offer identical features in every environment; it means essential requirements and fallbacks are deliberate rather than accidental.

Print is a different presentation context. Navigation controls that are useful on screen can waste space on paper, while a visible URL or document title may become more valuable. A print stylesheet can remove decoration, preserve contrast and avoid splitting small related blocks. It cannot guarantee the printer, paper size or user settings, so inspect the browser's print preview before making claims.

## Syntax anatomy and mechanism

Use `@media print` for print-specific rules and `@supports` for a feature-dependent enhancement. Keep the base rule valid independently. Avoid hiding the actual article while removing navigation. `break-inside:avoid` is a request to the fragmentation system, not a promise that an arbitrarily large element fits on one page.

## Classroom execution and offline inputs

Choose **HTML browser preview** in the classroom. The pad is one complete HTML document with embedded CSS and, where taught, embedded JavaScript. Its preview is isolated from the classroom and recreated on each run. It does not contact a server, submit real forms, read cookies, fetch assets or load a CDN. All fixtures are inline and synthetic. The browser uses its native HTML parser, so classic-script ordering, shared lexical bindings, inline modules and real DOMContentLoaded/load events keep their browser semantics. External module imports remain blocked. Navigation metadata such as base and meta http-equiv is rejected explicitly. On any supported host, the browser renders the document while Docker serves the classroom. No host compiler is needed.

Run your own source after implementing the task. A reference's checks inspect only the named initial conditions. Its success message is not a full accessibility audit, proof of responsive behavior at every size, or evidence that you implemented the solution yourself. Inspect actual output after keyboard input, resizing and changes. Save your source before comparing with a reference. The document and its CSS share one saved pad; HTML and CSS remain different languages within that artifact.

## Worked example / walkthrough

### Worked example 1: A useful print view

Hide actions while retaining the document.

```css
@media print { nav, button { display: none; } body { color: black; background: white; } }
```

**Expected observation:** The article remains while interactive controls are removed.

### Worked example 2: Optional layout enhancement

The fallback remains a readable block layout.

```css
.cards { display: block; }
@supports (display: grid) { .cards { display: grid; gap: 1rem; } }
```

**Expected observation:** Supported environments use Grid; others keep the content.

## Six progressive exercises

### Exercise 1: Identify content that must survive when scripts fail.

**Expected evidence:** The page's primary information and basic navigation remain available.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add a print rule that removes only irrelevant controls.

**Expected evidence:** The article and its headings remain in print preview.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build printable study notes with a useful baseline layout.

**Expected evidence:** Screen and print views preserve meaning with appropriate presentation.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a print rule that hides the main region.

**Expected evidence:** Narrow the selector to navigation or actions instead of the content container.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Inspect multiple pages of print preview.

**Expected evidence:** Headings, tables and long blocks remain legible across page breaks.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain what a feature query proves and what it does not.

**Expected evidence:** It detects supported syntax, not performance, usability or correctness of the whole component.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not confuse feature detection with browser sniffing. Avoid claiming print quality from a screen screenshot. A large table may need its own print strategy rather than an indiscriminate no-break rule.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain print stylesheet, progressive enhancement, feature query without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
