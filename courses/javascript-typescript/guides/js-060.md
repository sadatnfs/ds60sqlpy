# js-060: Treemaps and area-based composition

## Learning objectives

## Purpose, vocabulary and mental model

A treemap divides a rectangular area into nested regions whose areas represent nonnegative values. It is useful for part-to-whole structure when many categories must fit in a compact view. Exact comparisons are harder than aligned position or length, so a table or labels should support precise reading.

Hierarchy sums need a clear grain. If a parent value already includes its children and you also sum the children, the total can be double-counted. A common input supplies values only at leaves and uses hierarchy.sum to aggregate upward. Missing or negative values require an explicit policy.

Padding and rounding change visible rectangle area, so pixel area may not exactly preserve ratios in tiny charts. This is a rendering tradeoff, not a reason to claim numerical precision from a treemap. The reference checks the hierarchy’s numeric total and nonnegative geometry separately.

## Syntax anatomy and mechanism

Create the hierarchy, call `.sum(d => d.value || 0)` only under a validated nonnegative-value contract, then apply a treemap layout. Each leaf receives x0,y0,x1,y1 bounds. Width is x1-x0 and height is y1-y0.

Sort deliberately if stable ordering matters. Updating values can substantially rearrange a treemap, making entity tracking difficult. Use stable keys and consider whether a bar chart would better serve the comparison task.

## Worked example / walkthrough

### Worked example 1: Aggregate leaf values

Parents have no independent duplicated amount.

```javascript
const root=d3.hierarchy({children:[{name:"A",value:2},{name:"B",value:3}]}).sum(d=>d.value||0);
console.log(root.value);
```

**Expected observation:** 5.

### Worked example 2: Read rectangle geometry

Bounds are positions, not direct widths.

```javascript
const leaf={x0:10,x1:110,y0:20,y1:70};
console.log(leaf.x1-leaf.x0,leaf.y1-leaf.y0);
```

**Expected observation:** Width 100 and height 50.

## Debugging and common mistakes

Keep three checkpoints separate: the records after parsing, the domain and geometry after transformation, and the visible marks after rendering. A chart can look plausible while silently dropping records or assigning the wrong scale. Inspect counts, IDs, finite coordinates and meaningful expected values before adjusting colors. A missing mark may come from invalid input, a missing selection, an undefined scale result or clipping outside the viewBox.

The controlled failure for this lesson is: Diagnose parent-plus-child double counting. Its distinguishing evidence is The input mixes aggregate and leaf grain. Preserve that failing case when repairing your program. Do not remove an assertion or broaden a scale merely to hide a wrong input. Explain whether a changed value should affect the data, an encoding, a layout or only presentation.

## Accessibility and interpretation

Give the visualization a descriptive title and a short textual summary of the main result. Keep a table or list when exact values matter. Do not encode a critical category only through color; use labels, shapes or position as appropriate. Interactive controls need keyboard operation and clear focus, and motion should respect the user's reduced-motion preference. Automated DOM checks support, but do not replace, a real keyboard and assistive-technology review.

A data scientist must also defend the statistical meaning. State the population, units, aggregation, missing-value policy and uncertainty where relevant. Synthetic points illustrate a mechanism and do not establish a real-world finding. A beautiful visualization should make a valid claim easier to inspect, not make a weak claim appear certain.
