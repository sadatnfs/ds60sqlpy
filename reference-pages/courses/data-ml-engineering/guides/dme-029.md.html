Outcome: Derive query-shaped partition keys and quantify a hot-partition case.

Design the access path before the table#

Cassandra is a distributed database designed around partitioned, replicated data and predictable access paths. Its CQL syntax resembles SQL, but a relational design with arbitrary joins and scans does not automatically become a good Cassandra design. Start by listing the queries, their keys, result sizes, ordering and latency requirements. Then choose tables and keys that make those queries bounded. The separate Apache Cassandra workshop runs the actual service and CQL; this chapter supplies explicit design and consistency models that execute on any prepared CPU environment.

A partition key determines which rows belong together for distribution. Clustering columns organize rows within that partition and help define row uniqueness and supported order. If the query is “deliveries for one tenant on one day, ordered by event time,” a compound partition key such as tenant plus day can bound the accessed population. The clustering key can include event time and an identity to distinguish events sharing the same timestamp. A query for all days then needs to address multiple partitions deliberately.

Denormalization is often a conscious choice: separate query-shaped tables can represent different access paths. That creates write and consistency responsibilities. Updating several denormalized views is not automatically one general-purpose cross-table transaction. The design should say how discrepancies are detected and repaired. Do not justify duplication merely by saying that distributed databases require it; explain which query it serves and what invariant connects the copies.

Partition size and query fanout#

A tenant-only partition can grow without a time bound and become hot if one tenant dominates traffic. Time buckets limit growth per partition, but they increase the number of partitions needed for longer-range queries. Adding a shard within a time bucket can spread a very busy tenant further, while requiring a query to read and combine all shards for that bucket. The correct balance depends on observed volume and access patterns.

If a tenant produces rrr rows per day and a query covers ddd days, a simple daily design has approximately rrr rows per tenant-day partition and query fanout ddd. With sss explicit shards per day, the target average becomes r/sr/sr/s rows per shard and fanout can become dsdsds. These are workload models, not promises of uniform hash distribution or latency. Skew, row width and concurrency still matter.

The example uses a small fixture so the tradeoff can be counted exactly. It does not benchmark Cassandra, allocate tokens or implement its storage engine. The result table is labelled as a synthetic query-shape model. Use it to reason about what the real schema should accomplish before observing the actual service workshop's behavior.

Worked case 1: a bounded day query versus all-history fanout#

example_one() creates 12 events for tenant busy, spread evenly across three days, plus two events for tenant small. Under a tenant-only grouping, the largest partition has 12 rows. Under tenant-day grouping, the largest has four. The requested busy-tenant day-2 query returns four events and four packages.

The same tenant's all-history query must now address three day partitions. That is the cost of the bounded layout. The program reports both the reduced per-partition row population and the increased long-range query fanout. It does not present only the favorable metric. A system serving mostly one-day queries may prefer the bounded design, while an all-history analytical query may belong in a different engine or precomputed product.

The fixture's counts are tiny and do not establish a recommended partition-size limit. Production sizing must include row bytes, tombstones, query concurrency and repair or compaction behavior. A partition with four extremely large values can be more expensive than one with many compact observations. Use this mechanism to define what to measure, then test the actual workload on the intended deployment.

Worked case 2: replica overlap and unsafe deletion cleanup#

The second case models three replicas. A completed deletion has reached two replicas with a newer timestamp, while the third still holds an older live value. Reading one arbitrary replica can return either the deletion or the stale live value. Reading any pair and selecting the newest comparable timestamp sees the deletion in this controlled scenario, because every pair intersects the two replicas that accepted it.

This demonstrates set intersection under stated assumptions: the write completed, clocks are comparable, the replicas belong to the same relevant set, and reconciliation selects the newer value.

It does not prove linearizability for arbitrary concurrent writes, failures or clock behavior. The model even rejects equal-timestamp conflicting values rather than implementing Cassandra's complete tie rules. Cassandra uses its actual timestamp and reconciliation semantics; a source business revision is not automatically the same thing as a database write timestamp.

The case then removes the two tombstones too early. The remaining old live value becomes the newest surviving value in the simplified merge, so it reappears. This illustrates why deletion markers and repair horizons must be coordinated. Actual tombstone purging depends on compaction and safety conditions; the model deliberately shows an unsafe action, not a recommended cleanup procedure.

Complete worked program#

Run in Python Core. No Cassandra driver, CQL statement or cluster is executed. The table and JSON report preserve the model's assumptions alongside its outcomes.

"""Query-shape and replica-intersection models, not a Cassandra server or client."""

from collections import Counter
from itertools import combinations


def fixture():
    return [("busy", day, event, 1) for day in (1, 2, 3) for event in range(4)] + [
        ("small", 1, 0, 2),
        ("small", 2, 0, 3),
    ]


def latest(versions):
    present = [version for version in versions if version is not None]
    if not present:
        return None
    timestamp = max(version[0] for version in present)
    candidates = {version for version in present if version[0] == timestamp}
    if len(candidates) != 1:
        raise ValueError("This teaching model rejects ambiguous equal-clock writes")
    return candidates.pop()


def example_one():
    rows = fixture()
    unbounded = Counter(tenant for tenant, _, _, _ in rows)
    bucketed = Counter((tenant, day) for tenant, day, _, _ in rows)
    query = [row for row in rows if row[0] == "busy" and row[1] == 2]
    assert unbounded["busy"] == 12 and max(bucketed.values()) == 4
    assert sum(row[3] for row in query) == 4
    tenant_partitions = sorted(key for key in bucketed if key[0] == "busy")
    assert len(tenant_partitions) == 3
    return {
        "tenant_only_largest_partition_rows": 12,
        "tenant_day_largest_rows": 4,
        "one_day_result": query,
        "all_days_query_partition_fanout": len(tenant_partitions),
        "scope": "query-model arithmetic; no CQL or replica network executed",
    }


def example_two():
    live = (1, "live", 2)
    deleted = (2, "deleted", None)
    replicas = [deleted, deleted, live]
    one_replica = [latest([replicas[index]])[1] for index in range(3)]
    quorum_reads = [
        latest([replicas[index] for index in pair])[1] for pair in combinations(range(3), 2)
    ]
    assert one_replica == ["deleted", "deleted", "live"] and quorum_reads == ["deleted"] * 3
    premature_purge = [None, None, live]
    resurrected = latest(premature_purge)
    assert resurrected == live
    return {
        "read_one_outcomes": one_replica,
        "read_two_outcomes": quorum_reads,
        "intersection_inequality": "2 + 2 > 3",
        "after_unsafe_tombstone_purge": list(resurrected),
        "assumptions": (
            "same replica set, completed writes, comparable clocks; not a proof of linearizability"
        ),
    }


def main():
    from ds60sqlpy.plot_artifacts import publish_report, publish_table

    first, second = example_one(), example_two()
    print("Partition design follows the required query:", first)
    print("Replica intersection and deletion retention:", second)
    counts = Counter((tenant, day) for tenant, day, _, _ in fixture())
    publish_table(
        ["tenant", "day", "rows"],
        [[tenant, day, count] for (tenant, day), count in sorted(counts.items())],
        description=(
            "Synthetic query-shape model: each busy tenant-day has four rows; "
            "no Cassandra server was run."
        ),
    )
    publish_report(
        second,
        description=(
            "Explicit three-replica model assumptions and deletion outcomes, "
            "not cluster qualification."
        ),
    )


if __name__ == "__main__":
    main()

Replication is not a substitute for recovery design#

Replication places copies on multiple nodes or failure domains. It can improve availability, but a replicated incorrect write is still incorrect. A deleted value can also require coordination with replicas that were temporarily unavailable. Repair, compaction, backup and restore have different purposes and operational costs. A backup retained outside the active replica set can help recover from mistakes that every replica already accepted.

Consistency-level choices trade off acknowledgement requirements, latency and availability under particular failures. A quorum write may be unavailable when too few relevant replicas respond. Lowering the requirement can restore availability while changing what reads may observe. State the product's allowed stale-read behavior and failure policy rather than treating one setting as universally correct. Lightweight transactions provide a different conditional-update mechanism and should be learned through their actual service behavior, not inferred from the simple quorum arithmetic here.

Time-to-live also needs interpretation. Expiration is not the same as immediately removing every physical byte, and expiring a deduplication record can permit old replay if the source still retains it. If timestamps are supplied by clients, clock skew can affect which value wins. Prefer a reviewed timestamp and mutation policy and test conflict scenarios explicitly.

Diagnose a poor access path#

If a query requires scanning many partitions, inspect whether its predicates supply the designed partition key. If one tenant dominates latency, inspect its partition sizes and traffic distribution. If adding nodes does not help one hot partition sufficiently, investigate key design rather than assuming aggregate cluster capacity is the only limit. If tombstones dominate reads, inspect deletion and TTL patterns together with compaction and repair, not just the current live-row count.

If a deleted value reappears, reconstruct replica availability, repair history and deletion retention before changing settings. If a read is stale, record the consistency level and timing relative to the write. A screenshot of one read cannot establish a system-wide consistency guarantee.

Applications and answered interview discussion#

Cassandra can suit large, predictable key-based workloads with explicit distribution and availability requirements. It is not the default answer for every dashboard or ad hoc scientific query. A data platform may ingest from Cassandra into an analytical lake or serving system while retaining source identities and update semantics.

An interviewer may ask, “Why bucket by day?” Explain bounded growth and query fanout together. If asked whether quorum means strong consistency, state the overlap assumptions and distinguish them from a blanket guarantee about concurrent operations. If asked why a delete needs a marker, explain how an unavailable replica can later present an older value and why the system needs evidence that the value was intentionally removed.
