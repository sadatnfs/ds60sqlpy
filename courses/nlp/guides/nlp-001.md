## What you will be able to do

Turn an informal request such as “understand our support tickets” into a concrete input, output and evaluation contract. Build a small inspectable corpus, distinguish documents from their correlated parts, and recognize why a good score can answer the wrong question. These decisions apply to a simple keyword rule, a classifier and a large language model alike.

## A text is an observation, but an observation of what?

Imagine a support team receives a ticket containing an email thread, a quoted earlier reply and a pasted error log. A request to classify “this text” is underspecified. Should the system assign one queue to the whole ticket, identify every product mentioned, classify the sentiment of each speaker, or extract the timestamp of a failure? Each task changes the meaning of a row in the dataset. It also changes the kind of error that matters.

A **document** is the text object you decide to store and process as one item. It may be a ticket, a paragraph, a research abstract or a chat turn. Its boundary is a modeling decision, not a universal linguistic fact. A **corpus** is a collection of such objects together with enough metadata to interpret them. A **label** is a target assigned under a stated annotation rule. “Billing” is meaningful only if annotators know whether a refund request belongs there, whether multiple labels are allowed, and what to do with an empty ticket.

An **example** is one input and, when relevant, its target. A **prediction unit** is the object for which the system produces an answer. An **evaluation unit** is the object over which a result is scored or averaged. A **sampling unit** is the object drawn into the dataset. These can differ, but the relationship must be explicit. For example, customers may be sampled, tickets classified and customer-level outcomes evaluated. Ten thousand sentences from three customers do not give the same information about new customers as ten thousand independent customers would.

Start with a sentence that contains all the boundaries: “Given the initial text of a new English support ticket, predict one of the account or billing queues, using the queue definition in policy version 1, and measure correct assignments on tickets from customers not used to design the system.” This is still a small teaching contract. A real team would also specify escalation, supported languages, confidence handling and cost. It is already much better than “use an LLM to understand tickets.”

## The principal NLP task families

**Classification** chooses a label for an input, such as a queue or a sentiment category. **Sequence labeling** assigns labels to tokens or spans, such as the start and continuation of a person's name. **Information extraction** converts text into records, for example an invoice number and amount. **Retrieval** ranks existing documents against a question. **Generation** creates an output sequence, such as a summary or answer. **Clustering** groups similar texts without using a fixed target label for each training example.

These are different contracts, even when one modern model can perform several of them. An extraction result may need exact span offsets so a reviewer can inspect the original evidence. A retrieval result may need document identifiers and version metadata. A generated answer may need citations and an explicit “insufficient evidence” outcome. Fluent language is not a substitute for the required structure.

For a subject-matter assistant, decompose the task before choosing training. The system may need retrieval to find a current policy, extraction to identify a date, a deterministic calculation to compute a duration, and generation to explain the result. A single final answer conceals those components unless the evaluation measures them separately. The applied LLM journey builds this architecture later. Here, learn to name the intermediate evidence that would make a claim inspectable.

## A minimal corpus with provenance

Use four authored tickets so every row is visible. The `id` identifies a stored example. The `family` groups paraphrases or related versions that should not be treated as independent. `text` is the model input. `label` is the target under this chapter's queue policy. A real corpus would also store source, collection time, annotation version, language and permitted uses. A family ID is not automatically the same as a class label: two unrelated billing problems can have the same class and different families.

```python
from collections import Counter

documents = [
    {"id": "a", "family": "account-reset", "text": "Reset password", "label": "account"},
    {"id": "b", "family": "billing-charge", "text": "Double charge", "label": "billing"},
    {"id": "c", "family": "account-reset", "text": "Password reset please", "label": "account"},
    {"id": "d", "family": "billing-refund", "text": "Refund request", "label": "billing"},
]
print(len(documents))
print(dict(Counter(row["label"] for row in documents)))
print([len(row["text"].split()) for row in documents])
```

Expected: 4 documents, `{'account': 2, 'billing': 2}`, and whitespace-piece counts `[2, 2, 3, 2]`. The total is 9 pieces. We deliberately call them whitespace pieces. `str.split()` is a convenient counting rule, not a language-independent tokenizer. It leaves punctuation attached and does not correctly segment every writing system. Chapter 4 will make tokenization a first-class choice.

The generator expression passed to `Counter` yields one label per document. It therefore counts documents, not words. The list comprehension for lengths yields one integer per document and preserves row order. Keeping these two computations separate makes it harder to confuse corpus size with text length. Neither result says that the corpus represents a population: these four records were authored to expose a mechanism, not sampled to estimate real support traffic.

## Why changing the denominator changes the question

Suppose a model gets one long document right and one short document wrong. Let `c_i` be 1 for a correct document prediction and 0 otherwise. Unweighted document accuracy is `sum(c_i) / n`. A length-weighted score is `sum(w_i * c_i) / sum(w_i)`, where `w_i` is document length. They estimate different summaries. Weights do not become appropriate merely because the arithmetic is easy.

```python
correct = [1, 0]
lengths = [1000, 10]
document_accuracy = sum(correct) / len(correct)
length_weighted_accuracy = sum(c * n for c, n in zip(correct, lengths)) / sum(lengths)
print(document_accuracy)
print(round(length_weighted_accuracy, 4))
```

Expected: `0.5` and `0.9901`. The second number is a **length-weighted document accuracy**, not token accuracy. There were no token-level predictions in this example. It gives the long document one hundred times as much weight as the short one. If each ticket consumes one routing decision, that weighting may hide an operationally important failure. If a different business question genuinely weights outcomes by text volume, document that estimand explicitly.

This is an early example of a recurring failure in machine learning: the model can improve a reported metric while the useful outcome gets worse. Before celebrating a number, name its numerator, denominator, weights and target population. Also report counts. An accuracy of 1.0 on two examples is not compelling evidence of reliability.

## Related text and leakage

If record `a` is used for training and `c` for evaluation, the model sees two versions of the password-reset problem. Depending on the intended deployment, that may be legitimate repeated traffic or an optimistic test of generalization to new problem families. The split should represent the question you intend to answer. Do not invent family labels after observing which split gives the highest score.

```python
train = [documents[0], documents[1]]
holdout = [documents[2], documents[3]]
overlap = {row["family"] for row in train} & {row["family"] for row in holdout}
print(sorted(overlap))
```

Expected: `['account-reset']`. The code detects a known overlap; it cannot discover every semantic paraphrase on its own. In real corpora, combine source IDs, customer or document lineage, content hashes and reviewed near-duplicate detection. An exact hash misses paraphrases, while aggressive semantic deduplication can erase useful variation. Later chapters explain those tradeoffs. The first responsibility is to preserve provenance so the split can be audited.

## Progressive hints and common mistakes

For identity, compare the number of rows with the size of the ID set before attempting a repair. For text validity, distinguish `isinstance(value, str)` from `bool(value.strip())`; the first checks representation and the second checks whether usable content remains. For the split, write the family sets on paper before calculating their intersection. Never use a class label as the family identifier just because both are strings.

Do not drop invalid rows without reporting the decision. Doing so can change the class distribution and make an evaluation incomparable with an earlier run. Do not deduplicate by keeping an arbitrary row when labels conflict. Preserve the disagreement for review. Do not report nine “samples” merely because the text has nine whitespace pieces. The prediction contract in this example concerns four documents.

## Interview reasoning

**Why can a random row split overestimate NLP performance?** Related documents, copied templates, shared customers or future information may appear on both sides. The model is then tested on a task easier than the intended deployment. Specify the deployment unit first, choose a grouping or temporal split that reflects it, and inspect remaining overlap.

**Can an LLM remove the need for labels?** It can produce proposed labels or explanations, but those outputs still need a definition and independent validation. Treating the model's own answers as unquestionable ground truth can make an evaluation circular. Human review also needs an annotation policy and a way to record disagreement.

**When is a simple baseline useful?** A majority-class or keyword baseline gives a concrete comparison, exposes label imbalance and may satisfy a low-complexity task. A more complex model needs evidence of a meaningful improvement under the same evaluation contract. A baseline is not automatically a lower bound for every subgroup or deployment condition.
