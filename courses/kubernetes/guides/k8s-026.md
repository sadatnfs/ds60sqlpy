# k8s-026: Placement and node-local DaemonSets

## Level and prerequisites

Intermediate; about 120 minutes plus review. Direct prerequisites: `k8s-010`, `k8s-012`.

## Learning objectives

Compare a replica-count workload with one Pod per eligible node and explain affinity/taint constraints.

## Vocabulary and concepts

A Deployment asks for a replica count; a DaemonSet asks for a Pod on each eligible node under its controller and placement rules. Eligibility depends on selectors, affinity, taints/tolerations and other constraints. A desired DaemonSet count therefore cannot be predicted from cluster node count alone.

The host fixture uses a restricted nonroot server with no host network, privileged mode or host mounts. It selects nodes labeled lesson.ds60sqlpy/zone=a. The normal worker does not create DaemonSets, read arbitrary Node details or patch node labels/taints. The host supplies sanitized node facts and an exclusive qualified placement scope.

The offline calculation models only the explicitly listed label and custom-taint conditions. It is not a full scheduler simulator. Resource capacity, automatic controller tolerations and runtime behavior still require actual cluster evidence.

### Key terms

- **DaemonSet:** A workload controller that runs one copy of a Pod on each eligible node, such as a log or network agent.
- **nodeSelector:** A Pod field listing node labels that a node must carry for the Pod to be scheduled there.
- **Node affinity:** Scheduling rules that require or prefer nodes by label expressions, more expressive than nodeSelector.
- **Taint:** A node property that repels Pods that do not tolerate it, for example to reserve a node for special workloads.
- **Toleration:** A Pod field that allows, but does not require, scheduling onto a node with a matching taint.

## Read selectors, affinity and tolerations

nodeSelector requires matching label key/value pairs. Required node affinity expresses a richer eligibility condition, while preferred affinity influences scoring without guaranteeing a placement. Scheduling rules named IgnoredDuringExecution do not generally imply that an ordinary running Pod is evicted immediately when a node label later changes.

A NoSchedule taint repels new Pods unless a matching toleration permits them. A toleration allows placement; it does not force the Pod onto that node. DaemonSet controllers add some standard tolerations for their operational role, but an arbitrary custom dedicated-node taint is not automatically an invitation to run there.

Do not patch Nodes to make the example pass. That changes a shared cluster-level scheduling input. A dedicated host capability must own such changes and provide a restoration plan if the lesson explicitly requires them.

## Compare expected and observed DaemonSet counts

Synthetic nodes: node-a has zone=a with no custom taint; node-b has zone=b; node-c has zone=a and a dedicated NoSchedule taint not tolerated by the fixture. Under this limited predicate, only node-a is eligible. Adding the matching toleration in a separately reviewed host variant makes node-c eligible as well.

Compare the host-provided eligible-node facts with desiredNumberScheduled, numberReady and actual Pod nodeName/UID observations. A count can lag during reconciliation, and a ready count smaller than desired needs conditions/events for diagnosis. Zero desired can be correct if no nodes satisfy the selector.

A one-node kind cluster does not establish multinode placement or DaemonSet behavior across failures. Keep the actual topology in the qualification receipt and avoid a generic claim of one Pod per every possible node.

## Exercises

### Exercise 1: Compare controller intent

Explain replicas 2 Deployment versus a DaemonSet over eligible nodes.

**Expected result/shape:** Fixed replica count versus topology-derived desired placement.

**Verify:** State the Pod count each controller would produce on a three-node cluster with two eligible nodes.

**Progressive hints:** The controllers answer different questions.

### Exercise 2: Evaluate node labels

Apply the zone=a selector to the three supplied node facts.

**Expected result/shape:** node-a and node-c pass the label condition; node-b does not.

**Verify:** Apply the selector to each node's labels one node at a time and record a yes or no for each.

**Progressive hints:** Separate label eligibility from taint/resource checks.

### Exercise 3: Evaluate the custom taint

Add the untolerated dedicated NoSchedule condition.

**Expected result/shape:** Only node-a remains eligible in the simplified model.

**Verify:** For each node that passed the label check, compare its taints with the Pod's tolerations; a node without a matching toleration drops out.

**Progressive hints:** A toleration permits but does not force placement.

### Exercise 4: Observe actual placement

In the qualified host topology, compare desired/ready counts and Pod nodeName/UIDs.

**Expected result/shape:** Observed eligible-node and controller evidence agree or a specific condition explains the gap.

**Verify:** Compare `status.desiredNumberScheduled`, `status.numberReady` and each Pod's `spec.nodeName` with your predicted eligible nodes.

**Progressive hints:** Record the actual node count and labels from the host receipt.

### Exercise 5: Reject automatic node edits

Review a proposal to remove a taint from a shared Node to make the lab pass.

**Expected result/shape:** No learner Node mutation; request the correct owned capability or report unavailable placement.

**Verify:** Check that the proposal changes no Node object and names the capability request or unavailable report that replaces the edit.

**Progressive hints:** Node labels and taints are cluster-level inputs.

### Exercise 6: Clean up the right resources

Describe DaemonSet UID-aware cleanup and retained host configuration.

**Expected result/shape:** Only the owned DaemonSet/controller children are removed; unrelated agents and node settings preserved.

**Verify:** List the DaemonSet UID and its child Pod UIDs, and confirm that node labels and taints are identical before and after cleanup.

**Progressive hints:** Controller ownership differs from node ownership.

## Self-check

Adding a toleration for the custom taint changed the eligible count from one to two. Why, and why is the fix for zero eligible nodes never to relabel or untaint nodes yourself?

## Common pitfalls

Pending can result from selector mismatch, untolerated taint or insufficient requested resources. A toleration does not grant host access, and a DaemonSet is not inherently privileged. The restricted fixture demonstrates the controller shape without exposing node files or network namespaces.

The static predicate explains supplied facts only. Actual desired/ready counts and node placement must be read from the exclusive host lab. Cleanup targets the recorded DaemonSet UID and its controlled Pods, not node labels or unrelated node-local agents.
