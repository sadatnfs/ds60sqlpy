js-038: Typed API design and contract testing#

Level and prerequisites#

Advanced, approximately 120 minutes. Direct prerequisites: js-037

Learning objectives#

Explain envelope, contract test, versioned schema, transport/domain agreement with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Send 2 and 3 through the handler, JSON round-trip its reply, then decode it. The final task tests keep invalid payload details out of response errors.

Purpose and mental model#

A typed API contract connects request validation, domain behavior, transport status and response decoding. TypeScript interfaces document what checked callers expect, but bytes crossing a process boundary are unknown again. JSON round-tripping is therefore part of the test: a server-side typed value must serialize into a representation that the client actually validates and understands.

This lesson defines a versioned sum endpoint with a discriminated success/error envelope and an explicit request identifier. HTTP-like status and body meaning must agree: a success body belongs to status 200, while a failure body carries a documented category for invalid input, absent route or unsupported method. An envelope that says success inside a 400 response creates an ambiguous client policy, even when both pieces are individually well-formed JSON.

The handler here is a pure in-memory function, not an HTTP server. It makes domain and representation contracts easy to test independently. Lesson 040 adds actual local transport. This separation allows malformed requests, version mismatches and information exposure to be tested without conflating them with socket behavior. The error message is a stable generic diagnostic; it does not echo arbitrary request bodies or secret-looking input.

A version field identifies this schema generation. It does not automatically migrate old clients or guarantee compatibility. Adding a required field or changing the meaning of a status can break consumers despite leaving function names unchanged. Contract tests should exercise the client's decoding behavior as well as the server's typed construction.

Vocabulary and concepts#

Envelope: A response structure distinguishing success data from failure information.

Contract test: A test checking that producer and consumer agree at an actual representation boundary.

Versioned schema: A declared generation of a payload shape and meaning.

Transport/domain agreement: Consistency between status code and response-body interpretation.

Syntax anatomy and execution trace#

The Reply type connects a status union with an Envelope union, while decodeReply independently checks unknown runtime values. A record guard establishes property access, then explicit comparisons check version, ok, fields and status agreement. Narrow ok before reading data or error. The handler validates exact input keys and safe integer results before constructing a success. Its return object is a fresh value suitable for serialization.

Worked example / walkthrough#

Example A: Handle and decode a successful request#

The JSON boundary removes any purely static guarantee. The client decoder re-establishes the runtime schema before using the success payload.

import { strict as assert } from 'node:assert';

type ErrorCode = 'bad_request' | 'not_found' | 'method_not_allowed';
type Envelope = { version: 1; requestId: string; ok: true; data: { total: number } } | { version: 1; requestId: string; ok: false; error: { code: ErrorCode; message: string } };
type Reply = { status: 200 | 400 | 404 | 405; body: Envelope };
type Request = { method: string; path: string; requestId: string; body: unknown };
function record(value: unknown): value is Record<string, unknown> { return typeof value === 'object' && value !== null && !Array.isArray(value); }
function failure(status: 400 | 404 | 405, code: ErrorCode, requestId: string): Reply {
  return { status, body: { version: 1, requestId, ok: false, error: { code, message: 'Request could not be accepted' } } };
}
function handle(request: Request): Reply {
  if (request.path !== '/sum') return failure(404, 'not_found', request.requestId);
  if (request.method !== 'POST') return failure(405, 'method_not_allowed', request.requestId);
  const body = request.body;
  if (!record(body) || Object.keys(body).sort().join(',') !== 'a,b' || typeof body.a !== 'number' || typeof body.b !== 'number' || !Number.isSafeInteger(body.a) || !Number.isSafeInteger(body.b) || !Number.isSafeInteger(body.a + body.b)) return failure(400, 'bad_request', request.requestId);
  return { status: 200, body: { version: 1, requestId: request.requestId, ok: true, data: { total: body.a + body.b } } };
}
function decodeReply(value: unknown): Reply {
  if (!record(value) || !record(value.body)) throw new TypeError('reply object required');
  const body = value.body;
  if (body.version !== 1 || typeof body.requestId !== 'string' || body.requestId.length === 0) throw new TypeError('unsupported envelope');
  if (body.ok === true && value.status === 200 && record(body.data) && typeof body.data.total === 'number' && Number.isSafeInteger(body.data.total)) {
    return { status: 200, body: { version: 1, requestId: body.requestId, ok: true, data: { total: body.data.total } } };
  }
  if (body.ok === false && record(body.error) && typeof body.error.message === 'string') {
    const code = body.error.code;
    if ((value.status === 400 && code === 'bad_request') || (value.status === 404 && code === 'not_found') || (value.status === 405 && code === 'method_not_allowed')) {
      return { status: value.status, body: { version: 1, requestId: body.requestId, ok: false, error: { code, message: body.error.message } } };
    }
  }
  throw new TypeError('status and body contract mismatch');
}

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const reply = handle({ method: 'POST', path: '/sum', requestId: 'R1', body: { a: 2, b: 3 } });
    const decoded = decodeReply(JSON.parse(JSON.stringify(reply)));
    assert.equal(decoded.status, 200);
    if (!decoded.body.ok) throw new Error(decoded.body.error.message);
    assert.equal(decoded.body.data.total, 5);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: status 200 and decoded total 5.

Example B: Return a stable invalid-input envelope#

The failure is represented deliberately rather than relying on JavaScript coercion. A stable category is easier for clients to branch on than free-form error prose.

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const reply = handle({ method: 'POST', path: '/sum', requestId: 'R2', body: { a: '2', b: 3 } });
    assert.equal(reply.status, 400);
    if (reply.body.ok) throw new Error('expected failure');
    assert.equal(reply.body.error.code, 'bad_request');
    assert.equal(reply.body.requestId, 'R2');
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: status 400 with bad_request and matching request id.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

Exercises#

  1. Handle and decode a successful request. Send 2 and 3 through the handler, JSON round-trip its reply, then decode it. Expected: status 200 and decoded total 5. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Return a stable invalid-input envelope. Submit a string operand instead of a number. Expected: status 400 with bad_request and matching request id. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Distinguish route and method failures. Use an unknown path and an unsupported method. Expected: 404 not_found versus 405 method_not_allowed. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Reject version or status/body disagreement. Decode an unsupported version and a success envelope paired with status 400. Expected: TypeError for both malformed replies. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Require success narrowing in checked client code. Attempt data access before checking ok in an uncalled function. Expected: expected compiler error; correctly narrowed success remains usable. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Keep invalid payload details out of response errors. Include a secret-looking extra field in an invalid request. Expected: bad_request response does not echo the supplied value. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
