# go-004: Functions and value-passing contracts

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-003

## Learning objectives

Design functions that return results and errors explicitly and show which arguments a call can or cannot change. Along the way, explain parameter, pure function, precondition; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A function separates a computation from its callers. Its contract names accepted inputs, returned values, mutation and failure. Go passes arguments by value. For an integer this copies the integer; for a slice it copies a descriptor whose backing storage may still be shared. Multiple return values make a result plus error a normal language pattern. Named return variables are real local variables, not a replacement for clear control flow. A pure function depends only on its inputs and does not mutate shared state, which usually makes boundary tests simpler. Design the contract before deciding whether a pointer or a collection is convenient.

## Vocabulary and concepts

- **Parameter:** A local variable initialized from an argument value.
- **Pure function:** A function whose result depends only on its inputs without external mutation.
- **Precondition:** An input requirement checked before calculation.

## Syntax anatomy and reasoning

func twice(x int) int declares a parameter and a return type. return ends the invocation. (int, error) declares two returned values, which callers normally bind together and check before using the result. A variadic parameter ...int accepts zero or more values; within the function it is a slice. A return from a helper returns only from that helper, not the caller.

## Worked example / walkthrough

### Worked example 1: Implement a pure helper

Implement twice and check inputs 7 and 0.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func twice(x int) int { return 2 * x }
func positiveArea(w, h int) (int, error) {
	if w <= 0 || h <= 0 {
		return 0, errors.New("positive dimensions required")
	}
	return w * h, nil
}
func reassign(x int) { x = 99 }
func bounds(a, b int) (int, int) {
	if a < b {
		return a, b
	}
	return b, a
}
func total(values ...int) int {
	n := 0
	for _, v := range values {
		n += v
	}
	return n
}

func main() {
	// Implement a pure helper
	{
		check(twice(7) == 14 && twice(0) == 0, "twice")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The results are 14 and 0.

The zero case confirms the helper calculates from its input rather than returning a memorized positive result.

### Worked example 2: Return an explicit failure

Implement positiveArea that rejects a nonpositive dimension.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func twice(x int) int { return 2 * x }
func positiveArea(w, h int) (int, error) {
	if w <= 0 || h <= 0 {
		return 0, errors.New("positive dimensions required")
	}
	return w * h, nil
}
func reassign(x int) { x = 99 }
func bounds(a, b int) (int, int) {
	if a < b {
		return a, b
	}
	return b, a
}
func total(values ...int) int {
	n := 0
	for _, v := range values {
		n += v
	}
	return n
}

func main() {
	// Implement a pure helper
	{
		check(twice(7) == 14 && twice(0) == 0, "twice")
	}

	// Return an explicit failure
	{
		area, err := positiveArea(3, 4)
		check(err == nil && area == 12, "area")
		_, err = positiveArea(0, 4)
		check(err != nil, "invalid area")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** 3 by 4 returns 12; zero width returns an error.

The error describes a domain policy. Another geometry API might allow zero area, but its contract must say so.

## Exercises

### Exercise 1: Implement a pure helper: predict an edited check

Copy worked example 1, change `check(twice(7) == 14 && twice(0) == 0, "twice")` to `check(twice(8) == 14 && twice(0) == 0, "twice")` inside its check and predict whether it still passes; then restore it.

## Common pitfalls and diagnosis

Discarding the error from a two-value function is the typical mistake: `area, _ := positiveArea(0, 4)` compiles and yields 0, which looks like a legitimate empty area. Another is expecting a function to change a caller's scalar because it assigns to its parameter; Go copies the argument, so only a pointer or a returned value can communicate a change. Test both the success path and the failure path of every contract.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Implement a pure helper: predict an edited check

1. Restate the expected observation: The results are 14 and 0.
2. A pure helper computes only from its input. Which input would expose a function that always returns 14?
3. `twice(8)` returns 16, so the first comparison in the check is false. The helper is still correct; the edit changed the claim, so restore 7.

### Hint for investigation 2: Return an explicit failure: debug a regression

1. Restate the expected observation: 3 by 4 returns 12; zero width returns an error.
2. positiveArea returns two values. Which do you inspect first, and what should the other contain on failure?
3. With width 1 the dimensions are valid, so err is nil and `err != nil` fails. The failure path needs a nonpositive width to be exercised.

### Hint for investigation 3: Trace copied scalar state

1. Restate the expected observation: The caller still holds 5.
2. Arguments are passed by value. Which variable does the assignment inside the helper actually change?
3. Reassigning the copied parameter does not reassign the caller variable.

### Hint for investigation 4: Return both ordered values

1. Restate the expected observation: Inputs 9 and 2 return 2 then 9.
2. bounds returns two results in a fixed order. Which comparison decides which input comes first?
3. Multiple returns can make a small contract clearer than mutating two caller-owned outputs.

### Hint for investigation 5: Test a variadic identity

1. Restate the expected observation: The results are 0 and 6.
2. A variadic parameter is a slice inside the function. What does the loop add when that slice is empty?
3. An empty variadic argument list is a normal case.

### Hint for investigation 6: Transfer the contract

1. Restate the expected observation: The invalid domain is rejected before returning a usable area.
2. A negative height violates the same precondition as a zero width. What should the error and the area be?
3. Using only value while discarding err would erase the distinction between a valid zero and a rejected request.
