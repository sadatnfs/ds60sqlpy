# dbt-024: Groups, model access and governance boundaries

## Level and prerequisites

Advanced. Direct prerequisites: `dbt-012`, `dbt-014`, `dbt-019`

**Outcome:** Use groups and model access to define supported project interfaces, while keeping database authorization claims separate.

## Question and mechanism

Project governance defines responsibilities and permitted dependency relationships. dbt groups can associate models with owners, while model access levels control which project models may reference another model. This helps manage interfaces inside a growing codebase. It is not the same mechanism as a database permission system.

The first case gives an internal model private access and uses it from a consumer in the same group. The build succeeds, and a direct DuckDB query can still read the internal relation in this owned database. That observation is important: a private model declaration does not automatically revoke SQL privileges from a database user.

The second case moves the consumer to another group and expects the dbt reference policy to reject it. This is a real compiler/project-governance check. A deployed environment still needs appropriate database grants, identities, credentials, network boundaries and audit practices. The local project makes no claim that those external controls have been installed.

## Syntax and data contract

Group definitions include an owner label. Model config declares group and access, and ref creates the dependency evaluated by that policy. The example compares a same-group reference with a cross-group reference to a private model. It then distinguishes the dbt dependency rule from direct database querying.

## Worked case 1: Use a private model within its group

The internal model returns 41 and its same-group consumer returns 42. Both are real relations in the local fixture. A direct query of the internal relation still works under the owned database connection.

**Expected evidence:** The build succeeds, while direct SQL visibility remains a separate fact.

```python
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def governance_case(cross_group):
    with tempfile.TemporaryDirectory() as d:
        groups = [
            {"name": "commerce", "owner": {"name": "Classroom team"}},
            {"name": "analysis", "owner": {"name": "Learning review"}},
        ]
        schema = {
            "groups": groups,
            "models": [
                {"name": "internal", "config": {"group": "commerce", "access": "private"}},
                {
                    "name": "consumer",
                    "config": {
                        "group": "analysis" if cross_group else "commerce",
                        "access": "public",
                    },
                },
            ],
        }
        p = project(
            d,
            models={
                "internal": "{{ config(materialized='table') }} select 41 as value",
                "consumer": "select value+1 as value from {{ ref('internal') }}",
            },
            schema=schema,
        )
        invoke(p, "build", succeeds=not cross_group)
        if not cross_group:
            assert rows(p, "select value from consumer") == [(42,)]
            assert rows(p, "select value from internal") == [(41,)]
        return {
            "cross_group_reference": cross_group,
            "dbt_build_accepted": not cross_group,
            "not_a_database_permission_system": True,
        }


def example_one():
    return governance_case(False)


if __name__ == "__main__":
    print(example_one())
```

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Identify the owner

Locate the group and owner metadata for a model.

**Check:** Responsibility is explicitly declared.

**Hint:** A label must correspond to a real maintained process outside the fixture.


### 2. Change access deliberately

Make the producer public and review the cross-group dependency.

**Check:** The reference policy changes explicitly.

**Hint:** This is an interface decision.


### 3. Test database visibility

Query the internal relation directly in the owned fixture.

**Check:** It remains readable here.

**Hint:** The database connection has its own privileges.


### 4. Define a sensitive field boundary

Explain how a restricted column should be controlled outside this fixture.

**Check:** The answer includes a real authorization mechanism.

**Hint:** Documentation alone cannot prevent a read.


### 5. Plan a dependency change

Describe how consumers should migrate from an internal model to a supported interface.

**Check:** The plan identifies versions and acceptance checks.

**Hint:** A dependency graph is a compatibility surface.


### 6. Audit the claim

Write exactly what these two cases establish.

**Check:** They establish local dbt reference-policy behavior.

**Hint:** Keep compiler and security evidence separate.


## Diagnose errors and misleading results

A private-reference error can be correct governance behavior. Do not bypass it by hardcoding a relation name and claiming the policy passed. Conversely, a private model that is readable through direct SQL is not surprising: inspect database permissions as a different layer.

## Transfer to independent work

Use groups and model access to define supported project interfaces, while keeping database authorization claims separate. Test both allowed and rejected dependencies and record who owns semantic compatibility and external access controls.
