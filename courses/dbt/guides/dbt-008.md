# dbt-008: Incremental watermarks and late-arriving records

## Level and prerequisites

Intermediate. Direct prerequisites: `dbt-002`, `dbt-003`, `dbt-004`

**Outcome:** State the assumptions under which an incremental result equals a full recomputation.

## Question and mechanism

An incremental model reuses an existing relation and processes selected new or changed records. This can reduce work, but it introduces state into the transformation. The result now depends on the previous materialization, the new source and the selection rule. A full recomputation and an incremental update should agree under the assumptions of that rule.

A strict maximum watermark is appropriate only when relevant records arrive with a monotonically increasing key and previously processed records do not change. The first case uses that narrow assumption and demonstrates a repeatable append. The second adds a record whose update key falls behind the current maximum. It is new to the pipeline but not newer under the chosen predicate, so it is missed.

The defect is not fixed by repeatedly running the same query. The program explicitly compares the incremental result with a full refresh to expose the missing record. A production strategy needs a late-arrival policy, a backfill process or a different source/change-tracking contract. Performance savings must be evaluated alongside those correctness assumptions.

## Syntax and data contract

config(materialized='incremental') declares the representation. is_incremental() identifies runs with an existing incremental relation, and this refers to that relation. The example selects source rows with updated_at greater than the target maximum. --full-refresh deliberately rebuilds the model; it is not the same operation as a normal rerun.

## Worked case 1: A monotone append satisfies its assumptions

The first case begins with one record, then adds a later key. A further run has no newer records and should not duplicate output. The database is checked after each complete sequence rather than assuming idempotency from the code shape.

**Expected evidence:** Two records remain after the append and repeat run.

```python
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def example_one():
    with tempfile.TemporaryDirectory() as d:
        sql = (
            "{{ config(materialized='incremental') }} select * from {{ "
            "ref('events') }} {% if is_incremental() %} where "
            "updated_at > (select max(updated_at) from {{ this }}) {% "
            "endif %}"
        )
        p = project(d, models={"history": sql}, seeds={"events": "id,updated_at,amount\n1,10,5\n"})
        invoke(p, "build")
        (p / "seeds/events.csv").write_text("id,updated_at,amount\n1,10,5\n2,20,7\n")
        invoke(p, "build")
        invoke(p, "run")
        assert rows(p, "select id,amount from history order by id") == [(1, 5), (2, 7)]
        return {"monotone_append_rows": 2, "rerun_did_not_duplicate": True}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: A late record violates the watermark assumption

The second case adds a record with key 15 after the target maximum reaches 20. The incremental predicate excludes it. A full refresh sees all three records, providing an independent comparison of the two execution paths.

**Expected evidence:** The incremental relation has 2 rows; full refresh has 3.

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Add a later event

Insert a record whose update key exceeds the watermark.

**Check:** The incremental relation gains that record.

**Hint:** Compare against the actual target maximum.


### 2. Repeat without changes

Run the incremental model again with the same source.

**Check:** No duplicate record appears under this fixture.

**Hint:** The strict predicate selects no new rows.


### 3. Add a late event

Insert a new id behind the current maximum.

**Check:** The normal incremental result misses it.

**Hint:** New to the pipeline differs from newer timestamp.


### 4. Modify an old record

Change a previously loaded amount without changing its update key.

**Check:** The simple append strategy does not reliably apply that correction.

**Hint:** The predicate and write strategy both matter.


### 5. Define a backfill

Specify a controlled way to recover missed history.

**Check:** The scope and expected reconciliation are explicit.

**Hint:** A full refresh is one possible bounded mechanism.


### 6. Compare costs fairly

Describe what an incremental performance claim must include.

**Check:** It includes state maintenance and repair obligations.

**Hint:** A cheap normal run is not the entire lifecycle.


## Diagnose errors and misleading results

If an incremental run succeeds but records are missing, inspect the target watermark and arrival pattern. If duplicates appear, inspect both the source predicate and write strategy. Keep an independently recomputed small fixture to detect divergence instead of relying only on the incremental table's own counts.
