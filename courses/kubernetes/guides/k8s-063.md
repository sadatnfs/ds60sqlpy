# k8s-063: Observability: events, logs, metrics and traces

## Level and prerequisites

Advanced; about 120 minutes. Direct prerequisites: `k8s-062`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Build a correlated synthetic request packet.
- Plan privacy-aware observability for a teaching service.

## Purpose, vocabulary and mental model

Observability uses system outputs to reason about internal behavior. Events describe notable Kubernetes lifecycle observations. Logs record application or component messages. Metrics summarize numeric measurements over time. Traces connect spans of a request across components. Each signal has different retention, sampling and interpretation limits.

A metric’s labels define its dimensions. High-cardinality labels such as every raw user ID or request token can create operational cost and privacy risk. Aggregation can hide a failing subgroup, while excessive detail can overwhelm the system. Choose dimensions that support the diagnostic question.

A trace ID can connect a browser request to proxy and application work when propagation is implemented. It is not a secret or authorization token, and it should not be confused with a Kubernetes resource UID. Time synchronization and sampling affect how confidently signals can be correlated.

### Key terms

- **Log:** A timestamped record of one discrete event from a process.
- **Trace:** The record of one request as it crosses services, made of linked spans.
- **Span:** One timed operation within a trace, with a link to its parent and descriptive attributes.
- **Trace ID:** The identifier shared by every span of one request, which lets logs and spans be joined.
- **High-cardinality label:** A metric label with many distinct values, such as a request ID, that multiplies time series and cost.

## Mechanism and field-by-field reasoning

Begin with a named symptom and time window. Read only relevant namespace objects, bounded logs and the minimal metric dimensions needed. A Pod event about scheduling does not prove a later HTTP request’s outcome. A request latency spike can involve DNS, connection setup, queueing or handler work.

The fixture supplies synthetic event and request records to practice correlation. Actual metrics stacks and distributed tracing require separately prepared components. The lesson does not install observability operators or collect all-cluster data automatically.

## Trace the request or control path

```text
one request identity -> proxy observation -> app observation -> data operation
resource UID/generation -> controller events
time window + bounded metrics -> compare symptoms and hypotheses
```

The first line follows one request through three components and needs a shared request ID to connect them. The second line ties events to a resource UID and generation, so lifecycle changes match the right object. The third line is the discipline: choose a time window first, then compare signals inside it instead of reading everything.

## Worked example / walkthrough

### Worked example 1: Classify evidence types

These are distinct synthetic signals.

```text
event: FailedScheduling for Pod UID-A
log: request idR returned 503
metric: request duration histogram for serviceapi
trace: spans for requestR across proxy and app
```

**Expected observation:** Each signal answers a different question and can have a different retention period.

### Worked example 2: Avoid a high-cardinality metric label

Use request IDs in bounded logs/traces instead.

```text
poor metric label: request_id=unique-for-every-request
better aggregate: route=/reports, status_class=5xx
```

**Expected observation:** The aggregate remains bounded while exact request investigation uses another signal.

## Run boundary and the owned host lab

The fixture app's only outputs are its /version and /ready responses described in the [fixture README](../fixtures/networking/README.md), and topology.json carries no time series, so this lesson's signals are the synthetic packets in the worked examples. The checker has nothing to evaluate about logs or metrics. Events and logs for network-study are readable in an owned lab; metrics and traces need a separately installed pipeline.

The [fixture checker](../fixtures/networking/README.md) makes no API calls; on Windows use WSL 2.

```sh

kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" --namespace "$LAB_NAMESPACE" get events --field-selector involvedObject.kind=Pod --sort-by=.lastTimestamp
```

Events expire after about an hour by default, so read them early and keep each involved object's UID. The log read is bounded by time and line count. Neither shows request latency; that needs metrics or traces captured in the same window. Read rules: [owned live reads](../STUDY-GUIDE.md#owned-live-reads).

## Six progressive exercises

### Exercise 1: Match each signal to a diagnostic question.

**Expected evidence:** Events for lifecycle, logs for messages, metrics for trends, traces for request paths.

**Progressive hint:** Ask what each signal is for: a lifecycle change, a message from code, a number over time or one request's path.

### Exercise 2: Define a bounded incident time window.

**Expected evidence:** Relevant timestamps and retained identities are explicit.

**Progressive hint:** Find the first and last timestamps that matter, then add margin for clock skew and delayed events.

### Exercise 3: Build a correlated synthetic request packet.

**Expected evidence:** Request ID, service, status, duration and resource revision are related carefully.

**Progressive hint:** Carry one request ID through every record and add the resource revision so you know which code answered.

### Exercise 4: Diagnose a latency metric without assuming app CPU is the cause.

**Expected evidence:** Break down DNS, connection, queueing and handler phases.

**Progressive hint:** Latency is a sum. Split it into lookup, connect, queue and handler time before naming a suspect.

### Exercise 5: Explain high-cardinality label risk.

**Expected evidence:** Unbounded unique label values expand metric state and cost.

**Progressive hint:** Every distinct label value creates a new series. What happens if the value is a user ID?

### Exercise 6: Plan privacy-aware observability for a teaching service.

**Expected evidence:** No credentials or private payloads, bounded retention and useful correlation fields.

**Progressive hint:** Keep what helps correlation, drop what identifies people or carries secrets, and decide how long records live.

## Diagnosis, failure boundaries and common mistakes

Reading events too late is common; default retention is short, and the event explaining a crash loop may already be gone. Another mistake is correlating by Pod name alone, which silently joins a replacement Pod with a different UID. When latency rises, people jump to CPU; break the request into DNS, connect, queue and handler time first. Do not put request IDs or user IDs into metric labels, and never log tokens or private payloads to make debugging easier, since logs are retained and copied far more widely than the request itself.

Before concluding, record:

- The incident window as start and end timestamps, chosen before you open any signal.
- The Pod UID and `metadata.generation` tied to each event, not the Pod name alone.
- One request ID followed through the proxy, the app and the data operation, with each hop's duration.
- Every proposed metric label with its bounded set of values; request IDs belong in logs or traces.

General evidence rules: [diagnosis rules](../STUDY-GUIDE.md#diagnosis-rules).
