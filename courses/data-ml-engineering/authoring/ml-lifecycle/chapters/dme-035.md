# dme-035: Feature quality and fitted transformations

## A transformation can learn from data

Replacing a missing value, standardizing a measurement and encoding a category can look like mechanical preparation. Many such operations learn parameters from the supplied rows. An imputer can learn a median, a scaler can learn a mean and variance, and an encoder can learn a vocabulary. Those learned values become part of the model's computational state.

Separate `fit` from `transform`. Fitting estimates the transformation's state from an allowed population. Transformation applies that state to another population. Under the future-prediction contract used here, fitting uses training rows. Validation, test and later serving inputs are transformed without changing the learned state. A single pipeline object can preserve that relationship through its named steps.

This chapter uses actual scikit-learn 1.9.1 transformers and a real logistic classifier in the prepared data-engineering worker. Its tiny dataset is designed to expose learned state directly. The objective is not a credible estimate of business performance from eight rows. It is to establish what the fitted pipeline remembers and what happens when later inputs differ.

## Describe numerical and categorical meaning separately

The training frame has two columns. `hours` is numerical and contains one missing value. `region` is categorical and contains the labels north and south. The target array is supplied separately; it is never included among transformation inputs.

For the numerical column, a `SimpleImputer` learns the median from observed training values. A `StandardScaler` then learns its statistics from the imputed training column. Write the imputed value as \(\tilde x\), the fitted mean as \(\mu\), and the fitted scale as \(\sigma\). A later value is transformed as

\[
z=\frac{\tilde x-\mu}{\sigma}.
\]

All quantities must use compatible units. Standardization does not convert minutes to hours or repair a mislabeled measurement. The numerical model receives a standardized coordinate only after the source measurement has a valid interpretation.

For the categorical column, another imputer learns a most-frequent category and a `OneHotEncoder` learns the training vocabulary. Each known label becomes a position in a numerical indicator vector. With both training categories retained, north and south occupy separate columns. The example explicitly selects `handle_unknown="ignore"`; a later unseen category therefore becomes an all-zero categorical vector.

That is a policy choice, not a discovery that all unknown regions have identical outcomes. It gives the classifier a defined numerical input for an unfamiliar category. Another deployment could reject such requests, use a declared unknown bucket or require a fallback policy. Chapter 036 demonstrates an explicit closed-category serving contract.

## Keep the fitted stages together

A `ColumnTransformer` directs `hours` through the numerical pipeline and `region` through the categorical pipeline. The outer `Pipeline` feeds the combined matrix to logistic regression. Calling `fit` on this outer object trains the transformations and classifier in their required order. Calling `predict_proba` on a future frame applies the existing transformations before scoring.

The example requests dense indicator output because its learned matrix has only three columns. This is not a recommendation to materialize a huge dense matrix for a high-cardinality identifier. Sparse representations, category limits and alternative encodings need their own memory and meaning contracts. Scaling is also not universally required by every estimator; the transformation should match the algorithm and objective.

Named output columns make the transformation inspectable. `get_feature_names_out()` reports `numeric__hours`, `category__region_north` and `category__region_south`. These names describe actual fitted positions. Writing down the original input columns alone would omit important information about the model's numerical interface.

## Worked case 1: Apply frozen state to three different future rows

`example_one()` fits the complete pipeline on eight training rows. The observed numerical values are one, two, four, five, six, seven and eight. Their median is five, so the imputed training column is `[1, 2, 5, 4, 5, 6, 7, 8]`. The scaler then sees mean 4.75 and variance 4.9375. Its mean is computed after imputation, not from only the seven observed values.

Three later rows change different conditions. The first has a missing numerical value and unseen region west. The learned median supplies five, whose standardized coordinate is approximately 0.11251. The region becomes `[0, 0]`. The second row has hours equal to one thousand and known region north; its standardized numerical coordinate is approximately 447.89749. The third has hours equal to four and a missing category; its numerical coordinate is approximately -0.33753 and the category imputer supplies north.

North and south have tied training frequencies in this fixture. The prepared transformer resolves that tie to north. This is an implementation rule that the program verifies, not evidence that a missing future region really is north. When missingness has substantive meaning, a different representation may be needed.

All three transformed rows are finite and retain the same three-column schema. The fitted median and mean stay unchanged. The classifier returns a two-class probability matrix with one row per future case. The captured table exposes the actual transformed coordinates so the reader can inspect rather than assume these properties.

A finite result does not establish that the second row belongs to the model's reliable operating range. One thousand may be a valid but unfamiliar measurement, a unit error or an invalid value. Statistical transformation, source validation and drift investigation answer separate questions. The pipeline does not settle them merely by returning a probability.

## Worked case 2: Future rows change both statistics and vocabulary

`example_two()` fits one preprocessor on training rows only. It deliberately fits another on the combination of those rows and two future rows with hours one thousand and two thousand and category west. No future target labels are supplied. The contamination still changes learned state.

The correct fitted numerical mean remains 4.75. In the combined population, the median used for imputation becomes six and the subsequent fitted mean becomes 303.9. The category vocabulary also gains west. The original preprocessor emits three columns, while the combined preprocessor emits four. The same original input column names no longer imply the same computation.

The program independently checks the numerical values and the resulting feature names. It then transforms future rows through the correct preprocessor and verifies that doing so does not alter its fitted mean. Reading new data and learning new parameters are distinct operations.

This example demonstrates contamination of the intended procedure. It does not claim that every leaked statistic necessarily improves a reported score. Leakage can change an evaluation in either direction. The problem is that the evaluated procedure no longer matches the declared future-prediction process. A deliberately transductive method or an externally fixed vocabulary would need a different, explicit evaluation contract.

## Diagnose fitted state rather than only final predictions

If two pipelines disagree, compare training populations, imputation statistics, category vocabulary, feature order and estimator parameters. A shared class name does not imply shared fitted state. If a later batch changes the number of encoded columns, investigate whether the encoder was refitted or its vocabulary changed.

If an unseen category becomes indistinguishable from a known reference category, inspect whether the encoding also drops a category. If a missing measurement is replaced with zero, establish whether zero is a legitimate measurement or an imputation policy. If scaling produces an enormous coordinate, inspect units and operating range before clipping it without an explanation.

Cross-validation adds another fitting boundary. A pipeline should be fitted inside each training fold, with that fold's held-out rows transformed using its own fitted state. Fitting preprocessing once on the entire cross-validation population can leak information across folds even if the final test set remains untouched.

## Answered interview discussion

**Why can preprocessing leak information without labels?** Means, medians and vocabularies describe a population. Using later evaluation rows to learn them changes the information available to the training procedure. Whether that is permitted depends on the declared inference setting.

**Does one-hot encoding solve unknown-category handling?** It supplies a numerical representation under a chosen policy. An all-zero representation still requires interpretation and monitoring; it does not validate an unfamiliar source value.

**Why use a pipeline instead of saving each step separately?** A pipeline keeps fitting and application order explicit and reduces accidental refitting or omitted transformations. Its complete fitted state still needs versioning, input validation and artifact checks.

**Should every model be standardized?** No. Consider the estimator, optimization, regularization, sparsity and units. Use transformations for a stated purpose and verify their actual effects.
