# c-030: Sanitizers, debugger evidence and safe regressions

## Level and prerequisites

Advanced, approximately 120 minutes plus a later retrieval session. Direct prerequisites: `c-029`

## Learning objectives

Explain instrumentation, regression fixture, diagnostic evidence. Implement the six investigations with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

Compiler warnings, static analysis, sanitizers and debugger traces reveal different classes of evidence. AddressSanitizer instruments many invalid memory accesses; UndefinedBehaviorSanitizer checks selected undefined operations. Neither establishes that every possible path is correct, and neither replaces ownership reasoning. A sanitizer failure should become a small regression case after the defect is repaired. Do not ship a reference that intentionally executes undefined behavior merely to print a diagnostic. This lesson runs safe regression cases and gives the separate instrumented build workflow. A debugger is most useful when you can name the first invariant that became false rather than merely stop at the final crash.

## Vocabulary and concepts

- **Instrumentation:** Additional checks inserted into a compiled program.
- **Regression fixture:** A small retained input exposing a prior defect.
- **Diagnostic evidence:** A trace or report tied to an actual source and execution.

## Worked example / walkthrough

### Worked example 1: Guard a formerly unsafe index

Use a checked accessor on the final valid index.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

bool at_index(const int *values, size_t n, size_t i, int *out) {
  if (values == NULL || out == NULL || i >= n)
    return false;
  *out = values[i];
  return true;
}

int main(void) {
  /* Guard a formerly unsafe index */
  {
    int values[] = {2, 4, 6}, out = 0;
    CHECK(at_index(values, 3, 2, &out) && out == 6);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** The value 6 is returned.

The accessor proves the index is below length before reading.

### Worked example 2: Reject the one-past index

Request index 3 from length 3.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

bool at_index(const int *values, size_t n, size_t i, int *out) {
  if (values == NULL || out == NULL || i >= n)
    return false;
  *out = values[i];
  return true;
}

int main(void) {
  /* Guard a formerly unsafe index */
  {
    int values[] = {2, 4, 6}, out = 0;
    CHECK(at_index(values, 3, 2, &out) && out == 6);
  }

  /* Reject the one-past index */
  {
    int values[] = {2, 4, 6}, out = 9;
    CHECK(!at_index(values, 3, 3, &out) && out == 9);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** The operation fails and output remains 9.

The regression preserves the boundary that an unchecked implementation would access illegally.

## Prediction before execution

Trace each object from initialization through its last valid use. Write down the size of every array, the capacity of every output buffer and the ownership of any allocated storage. Distinguish a compiler diagnostic from a valid runtime rejection and from undefined behavior. Never execute an out-of-bounds access, dangling-pointer read or data race simply to discover what value it happens to print.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
