# mle-003: Build features without losing the request population

## Level and prerequisites

Beginner. Direct prerequisites: `mle-002`, `polars-006`

**Outcome:** Build features at the decision grain while preserving all requests and missingness categories.

## Question and mechanism

Feature construction transforms raw events into one record for a decision. It must preserve the decision population, not merely return rows with convenient history. A request with no eligible feature is still a request and may need a default, an abstention or a failure response. Dropping it can change both model evaluation and service coverage.

The first case constructs event aggregates using Polars with explicit entity, event-time and known-time conditions. The event window excludes the current cutoff while known-time eligibility includes it. These boundary choices are stated so the aggregate can be checked directly. The result has one row per request after aggregation.

The second case distinguishes a real zero feature from an absent feature. It left-joins selected values back onto the complete request table and validates one-to-one matching. This pattern protects coverage even when an upstream tool omits unmatched rows. Later Feast lessons test that behavior against the actual prepared backend.

## Syntax and data contract

Join events to requests by entity, filter by the complete temporal rule, then group by the stable request identifier. The small candidate join is an inspectable mechanism, not an arbitrary-scale implementation. Reattach selected features to the authoritative request table with a validated left join so absent history does not erase requests.

## Worked case 1: Calculate eligible historical totals

The first fixture includes a late-known event that is excluded for an earlier request but included for a later one. The program checks each request's sum and count independently of input display order.

**Expected evidence:** Request totals/counts are 10:2/1,11:15/3 and 12:3/1.

```python
def example_one():
    import polars as pl

    events = pl.DataFrame(
        {
            "customer": [1, 1, 1, 2],
            "time": [1, 3, 8, 2],
            "known": [1, 5, 8, 2],
            "amount": [2, 4, 9, 3],
        }
    )
    requests = pl.DataFrame({"request": [10, 11, 12], "customer": [1, 1, 2], "cutoff": [4, 9, 4]})
    eligible = requests.join(events, on="customer").filter(
        (pl.col("time") < pl.col("cutoff")) & (pl.col("known") <= pl.col("cutoff"))
    )
    totals = (
        eligible.group_by("request")
        .agg(pl.col("amount").sum().alias("sum"), pl.len().alias("count"))
        .sort("request")
    )
    assert totals.to_dicts() == [
        {"request": 10, "sum": 2, "count": 1},
        {"request": 11, "sum": 15, "count": 3},
        {"request": 12, "sum": 3, "count": 1},
    ]
    return {"features": totals.to_dicts(), "event_end_is_exclusive": True}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Keep zero separate from unavailable

The second fixture supplies a valid zero, a nonzero value and no selected value for a third request. The joined result preserves all three request identities.

**Expected evidence:** Values are [0,4,null] and coverage is 2/3.

```python
def example_two():
    import polars as pl

    requests = pl.DataFrame({"request": [1, 2, 3]})
    selected = pl.DataFrame({"request": [1, 2], "value": [0.0, 4.0]})
    joined = requests.join(selected, on="request", how="left", validate="1:1")
    assert joined["value"].to_list() == [0.0, 4.0, None]
    assert joined.height == 3
    return {"zero_and_missing_are_distinct": True, "coverage": 2 / 3}


if __name__ == "__main__":
    print(example_two())
```

## Diagnose errors and misleading results

Unexpectedly high model quality may follow from dropping difficult unmatched requests. Unexpectedly large totals may follow from feature fanout. Inspect request coverage, key multiplicity and temporal eligibility before changing the model.
