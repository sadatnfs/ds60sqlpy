# web-055: Pagination, caching and bounded application workloads

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-054`

## Learning objectives

Implement a cursor-based slice over synthetic records. Explain what must be measured before claiming a faster database endpoint. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

An endpoint should not assume its dataset will remain small. Bound the amount of work and the response size. Pagination returns a portion of a collection under a documented order. Offset pagination is simple but can shift as records are inserted or removed. Cursor pagination identifies a position in a stable ordering and needs a tie-breaker when the primary sort value is not unique.

Caching reuses a previous result, but the cache key and invalidation policy are part of correctness. A key that omits user identity or authorization scope can expose another user's data. A stale result may be acceptable for one display and harmful for another. Define freshness, ownership and failure behavior before using a cache to hide an expensive query.

## Syntax anatomy and mechanism

The reference demonstrates a bounded in-memory cursor over unique increasing ids. It validates the page size, selects ids greater than the cursor and takes only the requested count. This is an algorithm model, not a database query plan or distributed cache. A production query needs a matching index and engine-specific measurement.

## Worked example / walkthrough

### Worked example 1: A stable cursor predicate

The id is both unique and ordered in this small model.

```sql
SELECT id, title FROM notes WHERE owner_id = :actor AND id > :after_id ORDER BY id ASC LIMIT :page_size;
```

**Expected observation:** A scoped ordered page can continue after the last seen id.

### Worked example 2: A scoped cache key

The key includes the context that changes the result.

```php
$key = 'notes:user:' . $actorId . ':version:' . $version;
```

**Expected observation:** Different actors and data versions do not accidentally share one entry.

## Six progressive exercises

### Exercise 1: Explain why pagination needs an explicit stable order.

**Expected evidence:** Without it, page boundaries can duplicate or omit records unpredictably.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add a maximum page-size rule.

**Expected evidence:** A caller cannot request an unbounded result.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Implement a cursor-based slice over synthetic records.

**Expected evidence:** The second page continues after the last id and the final page can be shorter.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a cache key shared by all authenticated users.

**Expected evidence:** The key omits an authorization-dependent dimension and risks data leakage.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test an empty page and an invalid page size.

**Expected evidence:** Empty results are represented normally while invalid budgets are rejected.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain what must be measured before claiming a faster database endpoint.

**Expected evidence:** Inspect the actual query plan, index, workload, latency distribution and correctness under the target engine.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not claim a cursor guarantees a snapshot while records change unless the storage contract provides that guarantee. A cache hit can still be wrong. Bound work even for authenticated clients.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.
