# cpp-005: Functions and parameter contracts

## Level and prerequisites

Beginner; 90 minutes. Direct prerequisites: `cpp-004`.

Learner artifact: [cpp-005.cpp](../lessons/cpp-005.cpp). [Case ledger](../fixtures/cpp-005-cases.json). [Solutions](../solutions/cpp-005_solutions.md).

## Learning objectives

Separate input, output, precondition and postcondition in a function.

## Vocabulary and concepts

A function names a computation with parameters as inputs and a return value as its output. A precondition is a promise the caller must satisfy. A postcondition describes the result. Pure functions avoid hidden state, so the same inputs produce the same value and small boundary tests are meaningful.

<!-- terms:start -->

- **pass by value:** each parameter receives its own copy, so changing it inside the function leaves the caller's variable unchanged.
- **precondition:** a promise the caller must satisfy before the call, such as low being at most high.
- **postcondition:** the guarantee the function makes about its result when the precondition holds.
- **pure function:** a function without hidden state, so the same inputs always produce the same value.

<!-- terms:end -->

## Syntax and mechanism

`int clamp(int value, int low, int high)` declares three copied integers. `return` ends that call. Checking low>high before applying min/max prevents a nonsensical interval from looking like success.

## Trace the mechanism

A caller has three distinct questions: are the bounds valid, is the value below/inside/above them, and may the call alter its input? The supplied function rejects reversed bounds first. Only then does it compute min(value, high), followed by max(low, ...). The three ordinary cases cover each position relative to the interval, while equal bounds test a degenerate but valid interval. A return value can differ from the argument without mutating the caller because parameters are copies.

<!-- depth:start -->
## Function contracts and call boundaries

A function call creates a local computation with a clear interface. The caller supplies x, low and high; the function returns one integer or rejects an invalid interval. Pass by value gives each parameter its own integer value. If the caller stores x=12, calling clamp_reading(x, 0, 10) can return 10 while the caller variable remains 12. Returning a value and modifying a caller object are different interface choices.

The contract has an ordering dependency. First establish low<=high. Only then does the phrase clamp into the interval have a meaningful interpretation. The expression max(low, min(x, high)) implements the valid interval behavior, but it is not an interval validator. With reversed bounds, those library calls still produce an integer, which can hide a nonsensical request. Explicit rejection preserves the distinction between a valid answer and invalid input.

Trace the three ordinary paths separately. Below the interval, min(x, high) leaves x and max raises it to low. Inside, both operations leave x unchanged. Above, min lowers x to high and max leaves it there. Equal bounds are valid: every input maps to the single permitted point. That fourth case checks that the validation uses > rather than >=.

The exception type communicates why no result is returned. In the second worked program, the catch block sets a flag, and the program asserts that the flag became true. Merely writing an empty catch block would not prove the exception occurred. Uncaught exceptions terminate the program through a different path from an explicit status return, so the caller must choose where to translate failures into a user-facing diagnostic.

For a larger API, document units and ranges as part of the contract. Integer cents and integer degrees use the same C++ type but represent different quantities. A pure clamp function is easy to test because it depends only on its arguments. A hidden global limit or filesystem read would add state that each test and caller must understand. Prefer that extra dependency to be explicit when it is actually needed.

## Worked example / walkthrough

Example 1 clamps 12 into the range 0 to 10 and gets the upper bound 10, which shows that `clamp_reading` replaces an out-of-range reading with a bound instead of rejecting it. Example 2 swaps the bounds to `(10, 0)`. That is a broken caller contract rather than a reading to clamp, so the function throws `std::invalid_argument` before comparing anything. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-005-example-1.cpp)

```cpp
#include <algorithm>
#include <cassert>
#include <iostream>
#include <stdexcept>

int clamp_reading(int x, int low, int high) {
  if (low > high)
    throw std::invalid_argument("reversed bounds");
  return std::max(low, std::min(x, high));
}
int main() {
  assert(clamp_reading(12, 0, 10) == 10);
  std::cout << "cpp-005 example 1 checks passed\n";
  return 0;
}
```

**Expected:** With assertions enabled, the program exits with status 0 and prints:

### Worked example 2

[Complete program 2](../examples/cpp-005-example-2.cpp)

```cpp
#include <algorithm>
#include <cassert>
#include <iostream>
#include <stdexcept>

int clamp_reading(int x, int low, int high) {
  if (low > high)
    throw std::invalid_argument("reversed bounds");
  return std::max(low, std::min(x, high));
}
int main() {
  bool rejected = false;
  try {
    (void)clamp_reading(5, 10, 0);
  } catch (const std::invalid_argument &) {
    rejected = true;
  }
  assert(rejected);
  std::cout << "cpp-005 example 2 checks passed\n";
  return 0;
}
```

## Exercises

### Exercise 1: Predict the contract

Evaluate -3, 5, 12 for bounds [0, 10].

**Expected result/shape:** Results [0, 5, 10].

**Verify:** Assert `clamp_reading(-3, 0, 10) == 0`, `clamp_reading(5, 0, 10) == 5` and `clamp_reading(12, 0, 10) == 10`: one call below, inside and above the interval.

**Progressive hints:** Below, inside and above are separate paths.

### Exercise 2: Check parameter isolation

Call with variable x=12 and inspect x afterward.

**Expected result/shape:** Result 10; caller x still 12.

**Verify:** Store the result in a second variable and assert `result == 10 && x == 12`; the by-value parameter cannot change the caller's `x`.

**Progressive hints:** Pass by value creates the parameter copy.

### Exercise 3: Build a predicate

Write inside(x, low, high) with inclusive bounds.

**Expected result/shape:** inside(0, 0, 10) true; inside(11, 0, 10) false.

**Verify:** Assert `inside(0, 0, 10)`, `inside(10, 0, 10)` and `!inside(11, 0, 10)` so both inclusive edges and one outside value are covered.

**Progressive hints:** Return a Boolean comparison conjunction.

### Exercise 4: Repair an invalid contract

Remove the reversed-bounds check and explain the lost guarantee.

**Expected result/shape:** clamp(5, 10, 0) must be rejected after repair.

**Verify:** Without the check, `clamp_reading(5, 10, 0)` silently returns 10; after restoring it, Worked example 2 must catch `std::invalid_argument` again.

**Progressive hints:** min/max alone do not validate the meaning of the bounds.

### Exercise 5: Check a one-point interval

Evaluate x=2, 3, 4 with bounds [3, 3].

**Expected result/shape:** All return 3.

**Verify:** Assert that `clamp_reading(2, 3, 3)`, `clamp_reading(3, 3, 3)` and `clamp_reading(4, 3, 3)` all equal 3; equal bounds form a one-value interval, not a reversed one.

**Progressive hints:** Equal bounds form a valid single-value interval.

### Exercise 6: Transfer to money

Clamp a cents amount of 1250 to [0, 1000].

**Expected result/shape:** 1000 integer cents, without floating conversion.

**Verify:** Assert `clamp_reading(1250, 0, 1000) == 1000` with `int` arguments only, and compile with `-Wconversion` to confirm no floating conversion appears.

**Progressive hints:** The contract applies to a different integer domain.

## Self-check

Why does 12 come back as 10 rather than as an error? For Example 2, explain why `(10, 0)` must throw before any comparison with the reading, and what a silent clamp against those reversed bounds would return for 5.

## Common pitfalls

A function-name typo or incompatible argument type is usually a compile problem. A declared but undefined function can compile at the call site and fail during linking. A reversed interval here is a runtime contract failure. Preserve the phase and diagnostic instead of treating all three as a generic failed function. If a caller value unexpectedly changes, inspect whether the real signature uses a nonconst reference or pointer rather than the copied parameters shown here.

## Retrieval and transfer

Close the source and redo Exercise 6: clamp 1250 cents into [0, 1000] and get 1000 without any floating-point step. Explain why integer cents keep the bound exact. Then name what would break if amounts arrived as doubles from another system, or if a total could exceed the range of int.
