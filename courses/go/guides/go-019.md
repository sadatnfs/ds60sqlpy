# go-019: JSON schemas, strict decoding and unknown input

## Level and prerequisites

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-018

## Learning objectives

Decode JSON strictly by rejecting unknown fields and trailing documents and preserving large integers as json.Number. Along the way, explain wire schema, unknown field, trailing value; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

JSON is a serialization format, not a complete application schema. A syntactically valid object can still contain unknown fields, missing required values, invalid ranges or extra documents after the first value. Go struct tags define field names and omission rules. The decoder normally tolerates unknown fields, so strict APIs must request a stricter policy. Numeric JSON values decoded into any become floating values unless the decoder uses json.Number; large integers can lose precision. Decode transport syntax, validate domain meaning and reject trailing data as separate steps. Do not use the same structure blindly for external input, internal state and public output.

## Vocabulary and concepts

- **Wire schema:** The fields and types accepted at a serialized boundary.
- **Unknown field:** A supplied property absent from the target structure.
- **Trailing value:** Additional serialized data after an expected document.

## Syntax anatomy and reasoning

json:"name" maps a field to its wire name. json.Marshal returns bytes and an error. Decoder.DisallowUnknownFields rejects fields missing from a target struct. A second Decode should return io.EOF when exactly one JSON value is required. omitempty omits zero-like fields during encoding; it does not validate mandatory fields. Use pointers or explicit presence types when absent and zero differ.

## Worked example / walkthrough

### Worked example 1: Decode a typed object

Decode a name and count into Config.

```go
package main

import (
	"encoding/json"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Config struct {
	Name  string `json:"name"`
	Count int    `json:"count"`
}

func main() {
	// Decode a typed object
	{
		var c Config
		err := json.Unmarshal([]byte(`{"name":"sample","count":3}`), &c)
		check(err == nil && c.Name == "sample" && c.Count == 3, "typed JSON")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The fields become sample and 3.

Field names follow tags rather than an accidental presentation format. Parsing success still leaves count-range and name rules to domain validation.

### Worked example 2: Reject an unknown property

Use a strict decoder on an object with an unexpected extra field.

```go
package main

import (
	"encoding/json"
	"fmt"
	"strings"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Config struct {
	Name  string `json:"name"`
	Count int    `json:"count"`
}

func main() {
	// Decode a typed object
	{
		var c Config
		err := json.Unmarshal([]byte(`{"name":"sample","count":3}`), &c)
		check(err == nil && c.Name == "sample" && c.Count == 3, "typed JSON")
	}

	// Reject an unknown property
	{
		var c Config
		d := json.NewDecoder(strings.NewReader(`{"name":"x","extra":1}`))
		d.DisallowUnknownFields()
		check(d.Decode(&c) != nil, "unknown field")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Decoding returns an error.

Strict rejection catches misspelled configuration keys instead of silently ignoring a learner or operator mistake.

## Common pitfalls and diagnosis

Accepting any syntactically valid JSON is the main mistake: unknown fields are ignored by default, a misspelled key silently leaves its field at the zero value and trailing documents go unnoticed after one Decode call. Strict decoding addresses only the wire shape; a negative count is still valid JSON. Validate domain rules after decoding, and keep large integers as json.Number when exactness matters.

## Progressive hints

### Hint for investigation 1: Decode a typed object: change one input

1. Restate the expected observation: The fields become sample and 3.
2. Struct tags map JSON keys to fields. Which key fills Count?
3. The edited document sets count to 4, so `c.Count==3` fails while the name still decodes. Decoding is correct; the input changed.

### Hint for investigation 2: Reject an unknown property: diagnose an edited check

1. Restate the expected observation: Decoding returns an error.
2. DisallowUnknownFields turns an extra key into an error. Which key is unexpected?
3. The strict decoder rejects the extra field, so Decode returns an error and `==nil` is false. The original check asserted that rejection with `!=nil`.

### Hint for investigation 3: Detect a second document

1. Restate the expected observation: A second value is observable, so the single-document contract fails.
2. A Decoder reads one value per call. What remains after the first object?
3. One successful Decode consumes one value.

### Hint for investigation 4: Confirm exact completion

1. Restate the expected observation: The second decode returns io.EOF.
2. After the only value, Decode reports the end of input. Which sentinel is that?
3. The second read establishes the single-document boundary.

### Hint for investigation 5: Preserve a large integer token

1. Restate the expected observation: The exact decimal token is retained.
2. UseNumber keeps the original token. Why can float64 not hold this integer exactly?
3. Keeping the token avoids an early float64 conversion.

### Hint for investigation 6: Transfer domain validation

1. Restate the expected observation: JSON syntax is valid but count validation fails.
2. Syntax and domain are separate checks. Which rule does -1 violate?
