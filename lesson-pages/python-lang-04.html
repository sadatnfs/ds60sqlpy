Learning objectives#

Use a structured task lifetime to return ordered results and propagate sibling failure. Distinguish a bound on active calls from a bound on all scheduled tasks. Place a deadline around cooperative local work, await cancellation cleanup, inspect individual leaves of grouped failures, and restore task-local request context under all exit paths. Produce event and context evidence without starting servers or relying on remote timing.

Vocabulary and concepts#

  • Coroutine: An asynchronous computation produced by calling an async def function. Creating it does not run its body. Await it or schedule it exactly under a deliberate owner; abandoning it can produce a warning.
  • Task: An event-loop-managed execution of a coroutine. Tasks overlap when they reach await points; they do not make ordinary Python CPU calculations parallel. Blocking synchronous work can prevent all tasks from progressing.
  • Structured concurrency: A lifetime rule in which a lexical scope owns its children and waits for them before leaving. asyncio.TaskGroup provides that scope and cancels siblings when an ordinary child failure occurs.
  • Cancellation: A request to interrupt a task at a cooperative point. task.cancel() requests it; awaiting the task observes the completed exit. CancelledError is a control signal derived from BaseException, so an ordinary except Exception does not catch it.
  • Deadline: A limit on how long an operation may remain in its scope. asyncio.timeout uses cancellation internally and translates its own timeout into TimeoutError outside the scope. It cannot forcibly interrupt a blocked event loop or terminate an external side effect.
  • Exception group: An exception containing multiple exceptions, possibly nested in further groups. Its summary text is not a list of leaf failures. except* can handle matching subgroups; this lesson also traces leaves to make the classification and original message order explicit.
  • Context variable: A value associated with the current execution context. A new task inherits a copy of its creator's current context. A token returned by ContextVar.set identifies the earlier binding for exact restoration.

The async with asyncio.TaskGroup() as group statement creates an owning scope. group.create_task(operation(value)) schedules a child in that scope. The list of task objects preserves input positions even if their results complete in another order. Read task.result() after successful group exit; reading it too early can raise InvalidStateError. If a child fails, there is no complete result tuple, and group exit raises after sibling cleanup.

A semaphore controls entry into a protected region. Put the actual operation inside async with gate, and place its finish observation in finally inside that region. Waiting for a semaphore is not active operation work. Creating one task per item still stores all those tasks; this lesson deliberately uses small finite tuples. For unknown or very large inputs, revisit the bounded queue design in the concurrency prerequisite rather than assuming a semaphore alone provides producer backpressure.

Worked example / walkthrough#

Task completion does not choose presentation order#

The following program uses yielding local operations. sleep(0) offers a cooperative scheduling opportunity without simulating a service or asserting an exact elapsed time. The enclosing synchronous entrypoint calls asyncio.run once to own a fresh loop. The final tuple follows the stored task list.

import asyncio


async def ordered_demo():
    async def calculate(value):
        await asyncio.sleep(0)
        return value * 10

    async with asyncio.TaskGroup() as group:
        tasks = [group.create_task(calculate(value)) for value in (3, 1)]
    result = tuple(task.result() for task in tasks)
    assert result == (30, 10)
    return result


print("Input-order results:", asyncio.run(ordered_demo()))

Expected: The tuple is (30, 10). It is tied to input order (3, 1), not numerical sort order or a claim about which task finished first. An empty task list would produce an empty tuple. A real failure needs separate evidence; this successful demonstration alone says nothing about sibling cancellation.

A cancellation request is followed by an awaited exit#

The worker signals readiness after its acquisition event, before waiting on an Event that this example never releases. The controller waits for that signal, asks the task to cancel, then awaits the task. This order proves the worker had entered its cleanup region. Guessing with a short sleep could race with startup on a busy machine and make a missing cleanup look intermittent.

import asyncio


async def cancellation_demo():
    ready = asyncio.Event()
    never = asyncio.Event()
    events = []

    async def worker():
        events.append("open")
        try:
            ready.set()
            await never.wait()
        finally:
            events.append("close")

    task = asyncio.create_task(worker())
    await ready.wait()
    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        pass
    else:
        raise AssertionError("Cancellation was swallowed")
    assert task.cancelled()
    assert events == ["open", "close"]
    return events


print("Awaited cancellation:", asyncio.run(cancellation_demo()))

Expected: The task is cancelled and the log is ['open', 'close'] before the controller returns. The controller catches the expected control signal only at the ownership boundary. The worker's finally records cleanup and allows cancellation to continue. Replacing the worker's cancellation with a success value would change what the controller can observe.

If a timeout expires, inspect TimeoutError outside the timeout context. Inside the operation, cleanup still runs through cancellation. If the caller cancels before the deadline, preserve CancelledError instead of relabeling it as a timeout. These are distinct causes, even though both can traverse a finally block. Keep ordinary operation failures such as ValueError distinct as well; a deadline wrapper should not hide malformed local data.

Common pitfalls#

If a task result is unavailable, inspect whether group exit has completed. If tasks keep running after a failure, look for an unowned create_task outside the TaskGroup. If cancellation closes nothing, check that readiness was signalled inside the acquired region and that the controller actually awaited the cancelled task. A log immediately after cancel() can be too early.

If active work exceeds the limit, inspect whether the awaited operation is inside the semaphore context. If a failure leaves the active count positive, move the finish event into finally. If a deadline never triggers, look for blocking code with no cooperative await point. This lesson cannot make such code interruptible by merely changing its annotation to async.

If grouped failures appear as only outer (3 sub-exceptions), the program is printing a summary rather than visiting leaves. Preserve duplicate messages because two failures can have the same text. If concurrent request labels leak, inspect for a shared module string instead of a ContextVar. If the label leaks only after an exception, token reset is probably outside finally. Resetting to a hardcoded default also breaks nested scopes that had a nondefault previous label.

Exercise 1: Return ordered structured results#

Inputs: A small finite tuple of integer values and an asynchronous operation for each value.

Expected: Create one child per value inside asyncio.TaskGroup, await group exit, and return results in input order regardless of completion order. Empty input returns (). Verify: Operations deliberately released in reverse order for (1, 2, 3) still return (10, 20, 30). An injected child failure cancels a waiting sibling and its finally block runs before the group exits.

ordered_group retains task objects in the same order as values while the TaskGroup owns their execution. Successful exit establishes that every child has completed, so reading result at that point is valid. Completion order does not affect presentation order. The failure fixture makes one child wait after signalling readiness and another raise only after that readiness signal. This proves the first child entered its finally-protected region before cancellation. Group exit raises an ExceptionGroup, and both finally observations must be present before the caller handles it. Returning whatever results happen to be available would silently change the promised all-success tuple. Empty input creates no children and returns an empty tuple. These semantics apply to cooperative tasks in a single loop; they do not imply CPU parallelism or automatically cancel effects already performed by external systems.

Exercise 2: Limit active work with cleanup#

Inputs: A small finite tuple, an async operation, an exact positive integer limit, and an event list.

Expected: Use a TaskGroup plus a Semaphore so at most limit operation calls are active. Record ("start", value) after acquisition and ("finish", value) in finally before releasing the slot. Verify: Six yielding operations with limit 2 return their six squares. Walk the event transcript to prove active work never exceeds 2 and ends at zero. Under failure every recorded start has a matching finish.

The semaphore belongs to one invocation, so separate runs do not accidentally share a capacity budget. Each child acquires a slot before its start event and before calling the operation. Its finish event is in a finally block inside the semaphore context, ensuring it is recorded before the slot becomes available again. A transcript walk increments on start and decrements on finish, checking every intermediate count rather than only a final total. This independently demonstrates a ceiling of two and a final count of zero. TaskGroup supplies sibling cancellation and awaited cleanup after failure. The input is deliberately small and finite: a semaphore limits active operations, while this implementation still schedules one child for every input. For a large or unbounded stream the prerequisite's bounded queue is the appropriate ownership and backpressure extension.

Exercise 3: Put a deadline around owned work#

The deadline is checked before the factory is invoked, so invalid configuration cannot create an abandoned coroutine. The timeout context owns cancellation associated with its deadline and exposes TimeoutError outside that context after unwinding. The blocked fixture waits on a local Event and records closed in finally; the caller checks that marker when it observes timeout. No assertion depends on exactly twenty milliseconds having elapsed. A fast operation returns seven unchanged. Ordinary ValueError from the operation and caller-requested CancelledError must keep their original categories. Catching all failures and returning zero would conflate success, malformed data, and cancellation. A cooperative timeout cannot stop an event loop blocked in synchronous work, and this example does not claim to interrupt threads or remote operations. The timeout belongs around awaited work under an explicit local owner.

Exercise 4: Make cancellation cleanup observable#

Inputs: Two Events in the running loop and an observation list. The ready signal lets a controller know acquisition has happened.

Expected: Append acquired, set ready, then await release and return released. Append closed in finally on success or cancellation; allow CancelledError to propagate. The controller owns the created task and must await it after cancelling. Do not use sleeps to guess whether acquisition occurred.

Verify: Wait for ready, cancel the task, await it, and require CancelledError with events ["acquired", "closed"]. With release already set, the result is released and the same balanced event list appears.

cancellable_wait puts acquisition, readiness, waiting, and cleanup in a visible sequence. The ready Event is set only after acquired has been recorded, so a controller that awaits ready knows cancellation will target a task that entered the resource region. The controller then requests cancellation and awaits the task; only after that await can it assert closed. The implementation uses finally without catching the control signal, allowing TaskGroup or another owner to observe the cancellation accurately. A second fixture begins with release already set, exercising successful completion through the same cleanup region. Both routes produce acquired and closed, but one returns released while the other raises CancelledError. Observing only the event list would miss that difference. Sleeps are unnecessary for coordination and would make the test sensitive to machine scheduling.

Exercise 5: Inspect every grouped failure#

Inputs: An ExceptionGroup, possibly containing nested ExceptionGroups and ValueError subclasses alongside other ordinary Exceptions.

The failure inspector walks nested ExceptionGroup objects recursively and classifies only leaves. It preserves traversal order within each output category and retains duplicate messages because equal text can come from distinct failures. isinstance recognizes ValueError subclasses as intended. Stringifying the outer group would only produce a summary and lose the individual evidence. The nested fixture contains bad, disk, and another bad, so the result must have two bad entries and one disk entry. A group of only TypeError produces an empty first category. The accepted type is an ordinary ExceptionGroup, which cannot contain BaseException control signals such as CancelledError. A broader BaseExceptionGroup API would need an explicit cancellation policy and is outside this task. An except-star handler can be useful for acting on matched subgroups, but this function reports them without claiming to recover.

Resetting to a hardcoded outside string would fail when nested inside a context whose previous label was already meaningful. Concurrent tasks inherit separate contexts, so north and south can yield and each still observe its own label. A child task sees the context copied at creation; later changes in its parent do not become a shared mutable global binding. The reference checks context before and after an await and inside a child, then verifies outside in the caller. Failure and cancellation are tested separately, with restoration inspected in the same task that entered the scope. Looking only at the controller's context after cancelling another task would be insufficient because those contexts were already separate. Invalid labels fail before the operation factory runs.

"""Executable references for python-lang-04 using only local awaitables."""

from __future__ import annotations

import asyncio
import math
from collections.abc import Awaitable, Callable
from contextvars import ContextVar

REQUEST_ID: ContextVar[str] = ContextVar("request_id", default="outside")


# Exercise 1: Return ordered structured results.
async def ordered_group(
    values: tuple[int, ...], operation: Callable[[int], Awaitable[int]]
) -> tuple[int, ...]:
    async def run(value: int) -> int:
        return await operation(value)

    async with asyncio.TaskGroup() as group:
        tasks = [group.create_task(run(value)) for value in values]
    return tuple(task.result() for task in tasks)


# Exercise 2: Limit active work with cleanup.
async def limited_group(
    values: tuple[int, ...],
    operation: Callable[[int], Awaitable[int]],
    limit: int,
    events: list[tuple[str, int]],
) -> tuple[int, ...]:
    if type(limit) is not int or limit <= 0:
        raise ValueError("Expected a positive integer limit")
    gate = asyncio.Semaphore(limit)

    async def run(value: int) -> int:
        async with gate:
            events.append(("start", value))
            try:
                return await operation(value)
            finally:
                events.append(("finish", value))

    async with asyncio.TaskGroup() as group:
        tasks = [group.create_task(run(value)) for value in values]
    return tuple(task.result() for task in tasks)


# Exercise 3: Put a deadline around owned work.
async def with_deadline(operation: Callable[[], Awaitable[int]], seconds: float) -> int:
    if type(seconds) not in (int, float) or not math.isfinite(seconds) or seconds <= 0:
        raise ValueError("Expected a finite positive deadline")
    async with asyncio.timeout(seconds):
        return await operation()


# Exercise 4: Make cancellation cleanup observable.
async def cancellable_wait(ready: asyncio.Event, release: asyncio.Event, events: list[str]) -> str:
    events.append("acquired")
    try:
        ready.set()
        await release.wait()
        return "released"
    finally:
        events.append("closed")


# Exercise 5: Inspect every grouped failure.
def describe_failures(group: ExceptionGroup) -> tuple[tuple[str, ...], tuple[str, ...]]:
    values: list[str] = []
    others: list[str] = []

    def visit(error: Exception) -> None:
        if isinstance(error, ExceptionGroup):
            for child in error.exceptions:
                visit(child)
        elif isinstance(error, ValueError):
            values.append(str(error))
        else:
            others.append(str(error))

    visit(group)
    return tuple(values), tuple(others)


# Exercise 6: Restore task-local request context.
async def scoped_request(value: str, operation: Callable[[], Awaitable[str]]) -> str:
    if not isinstance(value, str) or not value:
        raise ValueError("Expected a nonempty request label")
    token = REQUEST_ID.set(value)
    try:
        return await operation()
    finally:
        REQUEST_ID.reset(token)


async def _verify_async() -> None:
    async def calculate(value: int) -> int:
        await asyncio.sleep(0)
        return value * 10

    assert await ordered_group((3, 1, 2), calculate) == (30, 10, 20)
    assert await ordered_group((), calculate) == ()
    ready = asyncio.Event()
    closed: list[int] = []

    async def failing(value: int) -> int:
        try:
            if value == 0:
                ready.set()
                await asyncio.Event().wait()
            await ready.wait()
            raise ValueError("bad child")
        finally:
            closed.append(value)

    try:
        await ordered_group((0, 1), failing)
    except ExceptionGroup as errors:
        assert describe_failures(errors) == (("bad child",), ())
    else:
        raise AssertionError("A task failure was hidden")
    assert sorted(closed) == [0, 1]
    events: list[tuple[str, int]] = []

    async def square(value: int) -> int:
        await asyncio.sleep(0)
        return value * value

    assert await limited_group(tuple(range(6)), square, 2, events) == (0, 1, 4, 9, 16, 25)
    active = peak = 0
    for event, _ in events:
        active += 1 if event == "start" else -1
        assert 0 <= active <= 2
        peak = max(peak, active)
    assert active == 0 and peak == 2
    for invalid in (0, -1, True):
        try:
            await limited_group((), square, invalid, [])
        except ValueError:
            pass
        else:
            raise AssertionError("Invalid limit accepted")

    async def immediate() -> int:
        return 7

    assert await with_deadline(immediate, 1) == 7
    timeout_events: list[str] = []

    async def blocked() -> int:
        try:
            await asyncio.Event().wait()
            return 0
        finally:
            timeout_events.append("closed")

    try:
        await with_deadline(blocked, 0.02)
    except TimeoutError:
        assert timeout_events == ["closed"]
    else:
        raise AssertionError("Deadline did not expire")
    for invalid_deadline in (0, -1, True, math.inf, math.nan):
        try:
            await with_deadline(immediate, invalid_deadline)
        except ValueError:
            pass
        else:
            raise AssertionError("Invalid deadline accepted")
    started, release = asyncio.Event(), asyncio.Event()
    cancel_events: list[str] = []
    task = asyncio.create_task(cancellable_wait(started, release, cancel_events))
    await started.wait()
    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        pass
    else:
        raise AssertionError("Cancellation was hidden")
    assert task.cancelled() and cancel_events == ["acquired", "closed"]
    release.set()
    success_events: list[str] = []
    assert await cancellable_wait(asyncio.Event(), release, success_events) == "released"
    assert success_events == ["acquired", "closed"]

    async def read_label() -> str:
        before = REQUEST_ID.get()
        await asyncio.sleep(0)

        async def read_child() -> str:
            await asyncio.sleep(0)
            return REQUEST_ID.get()

        child = await asyncio.create_task(read_child())
        assert before == REQUEST_ID.get() == child
        return before

    assert tuple(
        await asyncio.gather(
            scoped_request("north", read_label), scoped_request("south", read_label)
        )
    ) == ("north", "south")
    assert REQUEST_ID.get() == "outside"

    async def bad_label() -> str:
        assert REQUEST_ID.get() == "broken"
        raise ValueError("broken operation")

    try:
        await scoped_request("broken", bad_label)
    except ValueError as error:
        assert str(error) == "broken operation"
    else:
        raise AssertionError("Request failure was hidden")
    assert REQUEST_ID.get() == "outside"
    cancellation_ready = asyncio.Event()
    restored: list[str] = []

    async def waiting_label() -> str:
        assert REQUEST_ID.get() == "cancelled"
        cancellation_ready.set()
        await asyncio.Event().wait()
        return "unreachable"

    async def owned_request() -> None:
        try:
            await scoped_request("cancelled", waiting_label)
        finally:
            restored.append(REQUEST_ID.get())

    request = asyncio.create_task(owned_request())
    await cancellation_ready.wait()
    request.cancel()
    try:
        await request
    except asyncio.CancelledError:
        pass
    else:
        raise AssertionError("Request cancellation was hidden")
    assert restored == ["outside"] and REQUEST_ID.get() == "outside"
    assert len(asyncio.all_tasks()) == 1
