# js-013: Async functions and cancellation

## Level and prerequisites

Intermediate, approximately 90 minutes. Direct prerequisites: `js-012`

## Learning objectives

Explain cooperative cancellation, abort signal, deadline, cleanup ownership with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Start a timer with a signal, abort it, and inspect the rejection. The final task tests combine caller and deadline signals.

## Purpose and mental model

Cancellation is a request communicated to cooperating code. It is not the same as a rejected Promise, a timeout observation, or forcibly rolling back work that already happened. AbortController owns the request; its signal can be passed to operations supporting cancellation. A signal records whether it was aborted and the reason. Repeating abort does not replace the first reason.

Check a signal before starting work, then arrange to observe it while waiting. A listener installed without a pre-check can miss an abort that already happened. Remove listeners after either success or failure to avoid keeping closures and resources alive. A timer-backed operation must clear its timer when cancelled; merely rejecting a wrapper Promise leaves the underlying timer running.

Timeouts express a waiting policy. A timeout does not establish that an external side effect failed to occur. Retrying a payment or write after a timeout requires an idempotency policy, introduced later. These examples own only small timers and trace arrays, making cancellation effects deterministic and reversible. No wall-clock speed claim is inferred from a one-millisecond delay.

## Vocabulary and concepts

**Cooperative cancellation:** An operation checks and acts on a cancellation request.

**Abort signal:** A read-only notification channel carrying abort state and reason.

**Deadline:** A policy limiting how long a caller is willing to wait.

**Cleanup ownership:** Responsibility for cancelling timers and removing listeners.

## Syntax anatomy and execution trace

controller.abort(reason) changes signal.aborted and signal.reason. signal.throwIfAborted throws the stored reason immediately. AbortSignal.any combines signals with a first-abort policy. Node's timers/promises delay accepts a signal and rejects with AbortError, retaining the caller's reason as cause. That wrapper error and the original reason are distinct objects. A custom API should document which cancellation shape it returns.

## Worked example / walkthrough

### Example A: Cancel a pending timer

The timer API cooperates with the signal and cancels its pending timer. The rejection shape is the API contract, not an arbitrary string comparison.

```javascript
import { strict as assert } from 'node:assert';
import { setTimeout as delay } from 'node:timers/promises';

function cancellableValue(value, signal, trace) {
  return new Promise((resolve, reject) => {
    if (signal.aborted) { reject(signal.reason); return; }
    trace.push('started');
    let timer;
    function cleanup() {
      clearTimeout(timer);
      signal.removeEventListener('abort', onAbort);
      trace.push('cleaned');
    }
    function onAbort() {
      trace.push('aborted');
      cleanup();
      reject(signal.reason);
    }
    signal.addEventListener('abort', onAbort, { once: true });
    timer = setTimeout(() => {
      trace.push('completed');
      cleanup();
      resolve(value);
    }, 1);
  });
}

export async function verify() {
  // Worked example
  {
    const controller = new AbortController();
    const reason = new Error('learner cancelled');
    const pending = delay(1000, 'unused', { signal: controller.signal });
    controller.abort(reason);
    await assert.rejects(pending, error => error.name === 'AbortError' && error.cause === reason);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** AbortError with the original reason as cause.
### Example B: Reject an already aborted request before work

The pre-check prevents side effects from beginning after cancellation was already known. It also handles an abort event that occurred before any listener was installed.

```javascript
import { strict as assert } from 'node:assert';
import { setTimeout as delay } from 'node:timers/promises';

function cancellableValue(value, signal, trace) {
  return new Promise((resolve, reject) => {
    if (signal.aborted) { reject(signal.reason); return; }
    trace.push('started');
    let timer;
    function cleanup() {
      clearTimeout(timer);
      signal.removeEventListener('abort', onAbort);
      trace.push('cleaned');
    }
    function onAbort() {
      trace.push('aborted');
      cleanup();
      reject(signal.reason);
    }
    signal.addEventListener('abort', onAbort, { once: true });
    timer = setTimeout(() => {
      trace.push('completed');
      cleanup();
      resolve(value);
    }, 1);
  });
}

export async function verify() {
  // Worked example
  {
    const controller = new AbortController();
    const reason = new Error('already stopped');
    controller.abort(reason);
    const trace = [];
    await assert.rejects(cancellableValue(7, controller.signal, trace), error => error === reason);
    assert.deepEqual(trace, []);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** the exact reason is rejected; no timer starts.

## Prediction before your attempt

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

## Exercises

1. **Cancel a pending timer.** Start a timer with a signal, abort it, and inspect the rejection.
   **Expected:** AbortError with the original reason as cause.
   **Verify:** Record the observed value, exception or browser state and compare it with that expectation.

2. **Reject an already aborted request before work.** Abort before calling the custom operation.
   **Expected:** the exact reason is rejected; no timer starts.
   **Verify:** Record the observed value, exception or browser state and compare it with that expectation.

3. **Complete normally and clean up once.** Run the custom operation without aborting, then abort its signal after completion.
   **Expected:** value 7; started,completed,cleaned exactly once.
   **Verify:** Record the observed value, exception or browser state and compare it with that expectation.

4. **Cancel custom work and release its timer.** Start the custom operation and immediately abort.
   **Expected:** rejected reason; started,aborted,cleaned.
   **Verify:** Record the observed value, exception or browser state and compare it with that expectation.

5. **Keep the first abort reason.** Abort a controller twice and call throwIfAborted.
   **Expected:** the first reason remains authoritative.
   **Verify:** Record the observed value, exception or browser state and compare it with that expectation.

6. **Combine caller and deadline signals.** Combine two controllers and abort the deadline controller.
   **Expected:** combined signal is aborted with deadline reason.
   **Verify:** Record the observed value, exception or browser state and compare it with that expectation.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.
