# js-048: Data cleaning: CSV parsing, missing values and aggregation

## Purpose, vocabulary and mental model

CSV is a text format whose cells do not automatically have the domain types your analysis needs. Parsing a file into rows and interpreting strings as numbers or dates are separate steps. Empty strings, malformed values and duplicate IDs require explicit policies before visual encoding.

A missing measurement is not necessarily zero. Replacing absence with zero can distort averages, totals and visual trends. Reject invalid rows with a reason, retain a count of excluded rows, and make the policy visible to the chart reader. Trimming text and checking finite numeric values are small but important boundary operations.

Aggregation changes the row grain. A transaction table has one row per event; a category summary may have one row per group. The correct denominator and missing-value policy depend on that grain. A data scientist should be able to reconstruct the aggregate from the small source rows before rendering it.

## Syntax anatomy and mechanism

`d3.csvParse` parses inline CSV without a network request. A row accessor can return a cleaned object or null to omit a row, but an omission should be counted and explained. `Number('')` is zero, which is why a blank-string check must precede numeric conversion.

`d3.rollup(rows, group => d3.sum(group, d => d.value), d => d.category)` returns a Map keyed by category. The grouping key should be normalized intentionally. Case-sensitive category names may be genuinely distinct or accidental inconsistencies; do not merge them without a domain decision.

## Worked example / walkthrough

### Worked example 1: Reject blank and malformed numbers

This function separates missingness from numeric conversion.

```javascript
function numberOrNull(text){
  if(text.trim()==="") return null;
  const n=Number(text); return Number.isFinite(n)?n:null;
}
console.log(numberOrNull(""),numberOrNull("3"),numberOrNull("oops"));
```

**Expected observation:** null, 3, null.

### Worked example 2: Aggregate a known grain

Each input row is one event.

```javascript
const totals=d3.rollup([{g:"A",v:2},{g:"A",v:3},{g:"B",v:4}], rows=>d3.sum(rows,d=>d.v), d=>d.g);
console.log(totals.get("A"));
```

**Expected observation:** 5, from exactly two A events.

## Debugging and common mistakes

Keep three checkpoints separate: the records after parsing, the domain and geometry after transformation, and the visible marks after rendering. A chart can look plausible while silently dropping records or assigning the wrong scale. Inspect counts, IDs, finite coordinates and meaningful expected values before adjusting colors. A missing mark may come from invalid input, a missing selection, an undefined scale result or clipping outside the viewBox.

The controlled failure for this lesson is: Diagnose treating a blank value as zero. Its distinguishing evidence is The chart includes an invented measurement. Preserve that failing case when repairing your program. Do not remove an assertion or broaden a scale merely to hide a wrong input. Explain whether a changed value should affect the data, an encoding, a layout or only presentation.

## Accessibility and interpretation

Give the visualization a descriptive title and a short textual summary of the main result. Keep a table or list when exact values matter. Do not encode a critical category only through color; use labels, shapes or position as appropriate. Interactive controls need keyboard operation and clear focus, and motion should respect the user's reduced-motion preference. Automated DOM checks support, but do not replace, a real keyboard and assistive-technology review.

A data scientist must also defend the statistical meaning. State the population, units, aggregation, missing-value policy and uncertainty where relevant. Synthetic points illustrate a mechanism and do not establish a real-world finding. A beautiful visualization should make a valid claim easier to inspect, not make a weak claim appear certain.
