# asm-018: Arrow batches and pandas partition functions

Tutorial mode. Stage: intermediate. Direct prerequisites: `asm-005`, `spark-026`.

## Starting point and result

Arrow is a columnar interchange format. pandas provides in-process tabular operations in Python. `mapInPandas` connects a Spark partition to a Python iterator of pandas batches. This chapter explains that boundary and uses the separately prepared Spark/Torch project case `arrow-batches`. The ordinary Spark profile alone does not promise installed pandas and PyArrow. This is a project guide with an editable investigation record, not an ordinary Run lesson.

## Mechanism: partition, batch and group are different objects

A physical partition is a unit of Spark scheduling. An Arrow record batch is a bounded transport unit within a partition. A statistical group is a set defined by the model, such as all observations from one patient. These three boundaries need not coincide. `mapInPandas` receives an iterator of batches, and the function must consume that iterator and yield DataFrames conforming to the declared output schema.

Suppose each batch returns count \(n_b\), loss sum \(s_b\) and gradient sum \(g_b\). Summing all batch summaries yields the partition summary. Averaging batch means equally is wrong when batch sizes differ. The same normalization theorem from asm-008 applies at this additional boundary. A maximum-record setting limits rows per transport batch, not necessarily the bytes of a single very wide row or the size of a whole grouped operation.

Conversion has semantics as well as cost. Check nullable integers, timestamps and timezone, strings, categorical values, binary fields and floating precision. A schema is not merely a display hint. Returning a different column order or incompatible dtype may fail conversion or change values before the model sees them.

## Worked case: change batch size without changing the objective

Prepare the owned combined project and run its fixed `arrow-batches` case. The case must retain stable observation IDs and compare results under at least two batch bounds. A correct summary consumes every batch, records row coverage and agrees with a serial reference. Expected evidence is identical accepted IDs/counts and loss/gradient agreement within the declared tolerance, not identical batch counts.

A common bug is `next(iterator)`, which processes only the first batch. Another is returning a single DataFrame directly when the API expects an iterator of DataFrames. A tiny dataset fitting in one batch can conceal both mistakes, so include enough rows to force multiple batches in the smallest configuration.

## Worked case: a model group crosses batches

Imagine one group of five observations delivered as batches of sizes two, two and one. An independent Gaussian mean can be recovered from total count and sum without retaining every row. Fitting three means and averaging them gives the wrong answer when the final batch differs in size. A coupled state-space model may require ordered boundary state rather than these two statistics.

If the model requires the complete group in memory, moving to a grouped pandas operation changes the contract and memory risk. It does not make a large group safe merely because Arrow is used. Preflight group sizes and design a valid summary or streaming state where possible.

## Failure diagnosis

A failure importing pandas or PyArrow is an environment-preparation failure. A schema mismatch is a transport contract failure. Correct execution with missing IDs is a coverage failure. Keep these distinct from a numerical optimizer failure. Save batch sizes, counts and conversion versions in the receipt before changing settings.

## Interview discussion

**Does Arrow eliminate all copies?** No universal zero-copy claim follows across JVM, Python, pandas and tensor representations. Data types, contiguity and conversion choices determine actual copies.

**Can a pandas batch run Torch autograd?** Yes when the combined runtime is prepared, but the graph lives in that process and batch. Returning numeric gradients does not export an autograd graph through Spark.

# Worked reference: Arrow batches and coverage

This is an editable reading/project reference. It has no ordinary pad Run action.

For values `[1, 3, 3, 3, 5]`, batch sizes `[2, 2, 1]` produce `(count, sum)` summaries `(2,4)`, `(2,6)`, `(1,5)`. The global mean is 15/5=3. Averaging batch means gives `(2+3+5)/3`, which is 10/3 and wrong for equal observation weights.

A complete audit retains all five unique IDs under several batch bounds. The batch count may change; the objective must not. Processing only the first iterator element loses three observations in this layout. This worked arithmetic is a reference, not an assertion that Arrow transport ran.
