# js-009: Errors and explicit validation

## Level and prerequisites

Beginner, approximately 90 minutes. Direct prerequisites: `js-008`

## Learning objectives

Explain validation boundary, error cause, domain invariant, failure category with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Validate id A, quantity 2, price 125 and calculate integer cents. The final task tests prove rejected input caused no mutation.

## Purpose and mental model

Errors should distinguish an invalid request from an expected missing result and an operational failure. JavaScript can throw any value, but throwing Error objects preserves a useful message, stack and cause chain. Validation belongs at an external boundary before state changes or resource work. A catch that returns a plausible default for every failure can turn corrupted input into misleading success.

This lesson parses a bounded order record with an identifier, positive quantity and integer-cent price. JSON syntax validity is only the first gate; the parsed value can still be null, an array, missing fields or semantically invalid. The validator returns a fresh accepted record and leaves the input untouched. A domain calculation checks integer overflow with Number.isSafeInteger. Error translation adds context while preserving the original cause.

## Vocabulary and concepts

**Validation boundary:** The point where untrusted values are checked before use.

**Error cause:** The original failure retained when adding higher-level context.

**Domain invariant:** A rule every accepted record must satisfy.

**Failure category:** A named distinction guiding diagnosis or recovery.

## Syntax anatomy and execution trace

Use try/catch around the operation whose failure you intend to handle. Check object shape, own keys, primitive types and value bounds explicitly. Number.isInteger and Number.isSafeInteger express different numeric contracts. Throw TypeError for a schema/type violation and RangeError for an out-of-range numeric value under this fixture. Error options can retain cause when translating an operational failure.

## Worked example / walkthrough

### Example A: Accept a valid order

The accepted record is a copy with a known schema. It does not expose a reference that an external caller can later edit to invalidate the already checked value.

```javascript
import { strict as assert } from 'node:assert';

function validateOrder(value) {
  if (value === null || typeof value !== 'object' || Array.isArray(value)) throw new TypeError('order object required');
  const keys = Object.keys(value).sort();
  if (keys.join(',') !== 'id,priceCents,quantity' || typeof value.id !== 'string' || value.id === '') throw new TypeError('exact order schema required');
  if (!Number.isSafeInteger(value.quantity) || value.quantity <= 0 || !Number.isSafeInteger(value.priceCents) || value.priceCents < 0) throw new RangeError('valid integer quantity and cents required');
  return { id: value.id, quantity: value.quantity, priceCents: value.priceCents };
}
function total(order) {
  const result = order.quantity * order.priceCents;
  if (!Number.isSafeInteger(result)) throw new RangeError('total exceeds safe integer range');
  return result;
}

export async function verify() {
  // Worked example
  {
    const raw = { id: 'A', quantity: 2, priceCents: 125 };
    const order = validateOrder(raw);
    assert.equal(total(order), 250);
    assert.notEqual(order, raw);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** total 250; fresh accepted object.
### Example B: Reject syntactically valid but wrong-shaped JSON

JSON.parse proves only syntax. It does not know the domain fields or reject a valid JSON value of the wrong kind.

```javascript
import { strict as assert } from 'node:assert';

function validateOrder(value) {
  if (value === null || typeof value !== 'object' || Array.isArray(value)) throw new TypeError('order object required');
  const keys = Object.keys(value).sort();
  if (keys.join(',') !== 'id,priceCents,quantity' || typeof value.id !== 'string' || value.id === '') throw new TypeError('exact order schema required');
  if (!Number.isSafeInteger(value.quantity) || value.quantity <= 0 || !Number.isSafeInteger(value.priceCents) || value.priceCents < 0) throw new RangeError('valid integer quantity and cents required');
  return { id: value.id, quantity: value.quantity, priceCents: value.priceCents };
}
function total(order) {
  const result = order.quantity * order.priceCents;
  if (!Number.isSafeInteger(result)) throw new RangeError('total exceeds safe integer range');
  return result;
}

export async function verify() {
  // Worked example
  {
    for (const text of ['null', '[]', '{"id":"A","quantity":1,"priceCents":2,"extra":true}']) {
      assert.throws(() => validateOrder(JSON.parse(text)), TypeError);
    }
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** TypeError for each shape violation.

## Prediction before your attempt

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

## Progressive hints

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
