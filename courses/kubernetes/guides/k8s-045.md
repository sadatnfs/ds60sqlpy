# k8s-045: Pod network namespaces, sidecars and localhost

## Level and prerequisites

Intermediate; about 120 minutes. Direct prerequisites: `k8s-044`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Draw a sidecar and app port allocation.
- Defend whether a helper belongs in a sidecar or separate Deployment.

## Purpose, vocabulary and mental model

Containers in the same Pod share a network namespace. They can communicate through localhost and share the Pod’s port space. Containers in different Pods normally have different network namespaces and Pod addresses. This makes a Pod a unit of co-location and shared networking rather than merely a label grouping unrelated containers.

Loopback always refers to the caller’s network namespace. A sidecar in the same Pod can reach an application bound to 127.0.0.1:8080. A different Pod cannot reach that listener through the first Pod’s loopback address. To accept traffic on the Pod interface, the application generally listens on an appropriate non-loopback address, often 0.0.0.0 for IPv4.

A sidecar is a supporting container associated with an application Pod. It may proxy traffic, collect logs or perform another bounded role. Co-location introduces shared fate, startup and shutdown ordering, resource competition and port conflicts. A sidecar is not automatically a separate security or availability boundary.

### Key terms

- **Shared network namespace:** All containers in a Pod share one network namespace, so they share an IP address and one port space.
- **Loopback address:** 127.0.0.1 or ::1, which reaches only processes in the same network namespace, such as another container in the same Pod.
- **Sidecar container:** A helper container, such as a proxy, that runs in the same Pod as the application and shares its network namespace.
- **Port conflict:** Two containers in one Pod trying to bind the same address and port, so the second bind fails.
- **Non-loopback listener:** A process listening on an address other than loopback, often 0.0.0.0 for IPv4, so traffic from outside the Pod can reach it.

## Mechanism and field-by-field reasoning

The containerPort field documents a container’s intended port and can supply a name used elsewhere. It does not start a listener. Two containers in one Pod cannot both bind the same address/port combination independently. Their filesystem namespaces can still differ even though networking is shared.

An emptyDir volume is one way to share files within a Pod, but it is not implied by shared networking and does not survive Pod replacement. Keep the network and storage contracts distinct when explaining a sidecar design.

Since Kubernetes 1.33, native sidecar containers are stable. Declare the helper under `initContainers` with `restartPolicy: Always`. The kubelet starts it in init-container order before the application containers and moves on once it has started, or once its startupProbe succeeds when one is defined. It keeps running for the life of the Pod, is restarted if it exits, is stopped only after the application containers during Pod termination, and does not keep a Job's Pod from completing. A helper listed under `containers` has none of these ordering guarantees, which is why older sidecar designs needed startup polling and shutdown workarounds.

## Trace the request or control path

```text
app container 127.0.0.1:8080 <-> sidecar in same Pod namespace
other Pod -> Pod IP:8080 -> requires listener on reachable interface
```

The first line stays inside one network namespace: the app and its sidecar share a loopback interface, so 127.0.0.1:8080 reaches whichever container bound that port. The second line crosses namespaces, and there loopback means the caller's own Pod. A caller in another Pod needs the Pod IP and a listener bound to a reachable interface such as 0.0.0.0.

## Worked example / walkthrough

### Worked example 1: Compare two localhost callers

The same string names different destinations in different Pods.

```text
sidecar in PodA -> 127.0.0.1:8080 -> app in PodA
client in PodB -> 127.0.0.1:8080 -> PodB itself
```

**Expected observation:** Only the same-Pod sidecar reaches PodA through loopback.

### Worked example 2: Declare a native sidecar beside the application

This Pod spec excerpt declares a log-forwarding sidecar and an application in one network namespace. The image names are placeholders.

```yaml
initContainers:
  - name: log-forwarder
    image: registry.example.test/log-forwarder:1.0
    restartPolicy: Always
    ports:
      - name: metrics
        containerPort: 9090
containers:
  - name: app
    image: registry.example.test/app:1.0
    ports:
      - name: http
        containerPort: 8080
```

**Expected observation:** The sidecar starts before app and keeps running beside it. Neither containerPort field starts a listener; the two ports must differ because both processes share one Pod port space.

## Six progressive exercises

### Exercise 1: Predict same-Pod localhost access.

**Expected evidence:** The sidecar shares the app network namespace.

**Progressive hint:** Two containers in one Pod: how many network namespaces, and so how many loopback interfaces, exist?

### Exercise 2: Predict different-Pod localhost access.

**Expected evidence:** The client reaches its own Pod namespace.

**Progressive hint:** The client's 127.0.0.1 is evaluated inside the client's own namespace. Whose loopback is that?

### Exercise 3: Draw a sidecar and app port allocation.

**Expected evidence:** Distinct listeners share one Pod port space.

**Progressive hint:** One Pod means one port table. Give each process its own number and mark which one other Pods may reach.

### Exercise 4: Diagnose two containers binding 0.0.0.0:8080.

**Expected evidence:** They compete for the same socket within one Pod namespace.

**Progressive hint:** The second bind call fails. Find which container's log reports the address already in use.

### Exercise 5: Explain containerPort versus a real listener.

**Expected evidence:** One is declared metadata; the other is process behavior.

**Progressive hint:** Delete the containerPort line in your head. Would the process still accept connections?

### Exercise 6: Defend whether a helper belongs in a sidecar or separate Deployment.

**Expected evidence:** Consider shared lifecycle, scaling, networking and failure requirements.

**Progressive hint:** List what the helper shares with the app: start and stop timing, replica count, loopback access and failure impact.

## Diagnosis, failure boundaries and common mistakes

When the second container in Exercise 4 crashes with an address-in-use error, people blame the image or the probe. Read that container's own log first; the failed bind is reported there. A related mistake is assuming `containerPort` opens or reserves a port: removing it changes nothing about the socket, and adding it does not make a loopback-only listener reachable from other Pods. The reverse trap is an app bound to 127.0.0.1 that passes every check run inside its own Pod yet refuses connections on the Pod IP. Check the bind address before you touch the Service or any policy, because neither can fix a listener that only accepts local callers.
