# cpp-021: Strong types and generic value APIs

## Level and prerequisites

Intermediate; 105 minutes. Direct prerequisites: `cpp-010`, `cpp-020`.

Learner artifact: [cpp-021.cpp](../lessons/cpp-021.cpp). [Case ledger](../fixtures/cpp-021-cases.json). [Solutions](../solutions/cpp-021_solutions.md).

## Learning objectives

Prevent mixing semantically different values with the same representation.

## Vocabulary and concepts

A strong type wraps a representation in a domain name so unrelated values cannot be mixed accidentally. An explicit constructor blocks implicit conversions. A value API should obey simple laws, such as addition identity and equality symmetry. Domain restrictions must be enforced at construction or operation boundaries.

<!-- terms:start -->

- **strong type:** a wrapper such as `Cents` that gives a representation a domain name so unrelated values cannot be mixed.
- **explicit constructor:** a constructor marked `explicit`, which blocks implicit conversion from the underlying representation.
- **operator overloading:** defining operators such as `+` and `==` for a type, which should keep their familiar meaning.
- **identity element:** a value, such as zero cents for addition, that leaves any other value unchanged.

<!-- terms:end -->

## Syntax and mechanism

`struct Cents { long long value; };` distinguishes money from a raw count. Define only meaningful operations. Cents+Cents can yield Cents, while adding a count should require a deliberate conversion. Avoid exposing unchecked arithmetic as a blanket promise for all long long values.

## Trace the mechanism

The wrapper's job is to stop accidental unit mixing before runtime. A count and an amount may both use long long storage, but only the domain-approved operations should exist. Equality and addition laws give clients predictable behavior. Those laws apply only within the declared numeric domain: overflowing signed arithmetic is not an exotic counterexample to the law, it is an operation outside the program contract. A checked addition API should preserve that distinction.

<!-- depth:start -->
## Strong domain types and operator meaning

Two integers can have incompatible meanings even when their machine representation is identical. A Cents type makes a monetary unit visible at function boundaries. It can prevent a caller from accidentally passing a raw row count where a price is expected, provided its constructors and conversions preserve that separation. This is a domain-model benefit rather than a different arithmetic engine.

An overloaded operator should preserve a familiar, documented meaning. Adding two Cents values produces a Cents result; comparing two values compares their amounts. The complete examples check 125 = 25 + 100 and the zero identity. They do not establish currency conversion, rounding policy or overflow handling. Those requirements would need distinct types or explicit functions and tests.

The zero value is useful because it supplies an identity for accumulation. If price+zero changes price, either the operator or the type invariant is wrong. Equality should compare the semantic value represented by the type, not an incidental address. In a richer money type, currency would also matter: equal numeric amounts in different currencies should not be casually added.

Operator syntax can hide cost and failure. A small Cents addition is simple, while an overloaded plus that performs network I/O or mutates unrelated state would violate ordinary reader expectations. Prefer explicit named operations when behavior is surprising or requires a policy argument. The goal is clearer code, not making every business action look like arithmetic.

Construction is the boundary where invalid states should be considered. If negative cents are forbidden in one domain but valid for a signed balance in another, one universal wrapper may be misleading. State the type's invariant and choose names accordingly. The lesson uses a tiny representation so the learner can separate unit correctness from the later checked-arithmetic policy.

## Worked example / walkthrough

Example 1 adds `Cents{25}` and `Cents{100}` and compares the sum with a price of 125. The strong type refuses a bare int, so units cannot mix silently. Example 2 adds `Cents{0}` to 125 and gets 125, the identity check that any generic sum must pass. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-021-example-1.cpp)

```cpp
#include <cassert>
#include <iostream>

struct Cents {
  long long value;
  bool operator==(const Cents &) const = default;
};

Cents operator+(Cents a, Cents b) { return Cents{a.value + b.value}; }
int main() {
  Cents price{125};
  Cents discount{25};
  assert((discount + Cents{100}) == price);
  std::cout << "cpp-021 example 1 checks passed\n";
  return 0;
}
```

## Exercises

### Exercise 1: Name the units

Compare Cents{125} with item count 125.

**Expected result/shape:** Equal representation, different domain meaning.

**Verify:** Confirm `Cents{125}.value == 125` compiles while `Cents{125} == 125` does not; equal numbers do not make the two domains comparable.

**Progressive hints:** Names prevent treating every integer as interchangeable.

### Exercise 2: Test identity

Add zero to Cents{125}.

**Expected result/shape:** Cents{125}.

**Verify:** Assert `(Cents{125} + Cents{0}) == Cents{125}`, as Worked example 2 does, with the zero written as `Cents{0}` rather than a raw integer.

**Progressive hints:** The operation should preserve the value at the identity.

### Exercise 3: Construct a separate type

Add struct ItemCount and avoid mixed addition.

**Expected result/shape:** Cents+ItemCount has no valid overload.

**Verify:** Write `Cents{1} + ItemCount{1}` in a scratch file and confirm the compiler finds no matching `operator+`, while `Cents + Cents` still compiles.

**Progressive hints:** Omitting meaningless operations is an interface feature.

### Exercise 4: Repair implicit conversion

Review a non-explicit raw integer constructor.

**Expected result/shape:** Use explicit construction at the domain boundary.

**Verify:** In a scratch copy, add a non-explicit `Cents(long long)` constructor and show that `Cents total = 125;` compiles; marking it `explicit` must make that line fail.

**Progressive hints:** Implicit conversion can silently cross units.

### Exercise 5: Check equality laws

Compare a=125, b=125, c=125.

**Expected result/shape:** Reflexive, symmetric and transitive equality for these values.

**Verify:** Assert `a == a`, `a == b`, `b == a`, `b == c` and `a == c` for the three `Cents{125}` values, all through the defaulted `operator==`.

**Progressive hints:** Default member equality implements the value contract.

### Exercise 6: Transfer safety

Specify checked addition when values approach LLONG_MAX.

**Expected result/shape:** Reject overflow before calculating a+b.

**Verify:** Test your guard with `LLONG_MAX` plus 1 and confirm it rejects before computing the sum, while `LLONG_MAX - 1` plus 1 is accepted.

**Progressive hints:** Strong naming does not prevent representation overflow.

## Self-check

Why does `Cents{25} + Cents{100}` compare equal to a price of 125 cents, and why can a bare int not join the sum? For Example 2, explain why adding `Cents{0}` is a useful check for any generic sum.

## Common pitfalls

If raw integers slip into a Cents API unexpectedly, inspect implicit constructors and conversion operators. If an operator mutates its left input when it is expected to return a new value, compare the intended value semantics with the implementation. If a large amount wraps or overflows, strong typing alone is not enough: add the numeric range policy. Keep unit tests distinct from arithmetic-boundary tests.
