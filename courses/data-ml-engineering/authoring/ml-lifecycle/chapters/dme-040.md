# dme-040: Artifacts, integrity and the software supply chain

## A model artifact has several independent contracts

A model artifact can contain numerical parameters, preprocessing state, a signature, dependency information and executable implementation code. The consumer needs to know which of those components it expects, where they came from and which operations loading them can perform. A filename ending in `model` does not answer those questions.

Separate byte integrity, structural compatibility, numerical behavior and origin trust. A hash can detect a change relative to an expected digest. A schema can reject an unsupported representation. A numerical oracle can compare known computations. An authenticated publication process can establish which producer is authorized to supply the artifact. None of these observations automatically proves the others.

This chapter implements a deliberately narrow numerical format. It trains an actual tiny linear model, writes a JSON bundle and loads only its fixed data representation. It does not offer a general deserializer for arbitrary Python objects or claim that this small format can express every machine-learning model.

## Make the numerical operation explicit

The predictor uses two inputs: hours and ticket count. Its numerical form is

\[
f_{\beta}(x_1,x_2)=\beta_0+\beta_1x_1+\beta_2x_2.
\]

The fixture supplies eight original observations with target rule \(3+2x_1-1.5x_2\). The program builds a design matrix with an intercept column and calls actual least squares. It checks that the matrix has rank three before using the fitted coefficients.

The stored representation includes a format version, ordered feature names, feature units, an intercept and exactly two coefficients. The consumer implements the known arithmetic. No payload field can name a Python constructor, import a module or provide a program to evaluate.

This restricted design is useful because its loading behavior is easy to inspect. More complex estimators need suitable reviewed formats and loaders. Their dependency and execution behavior should be part of the artifact contract rather than hidden behind a reassuring file extension.

## Identify bytes before interpreting their meaning

The manifest records a fixed model filename, model byte count, model SHA-256 digest and interface digest. For model bytes \(B\), its content identity is

\[
h=\operatorname{SHA256}(B).
\]

The interface digest separately identifies the declared feature order, units and scorer kind. It prevents a consumer from treating a different interface as though it were the expected one merely because both artifacts contain two numerical coefficients.

The loader checks exact manifest fields and versions. It accepts only `model.json` as the model filename, checks bounded integer sizes and validates the digest representation. It then reads and checks the actual model bytes before decoding their parameter fields.

Both files must be regular files within the 32,768-byte read limit. The Linux file operation refuses symbolic links and uses a nonblocking open before checking the file type. A request to read a pipe or an unexpectedly large file cannot be treated as an ordinary bounded model read. These are concrete operations in the supported Linux-container runtime.

JSON decoding also has a contract. Duplicate fields and nonfinite constants are rejected. Numerical parameters must have exact supported types, finite values and the declared bound. A boolean cannot become a coefficient through Python's integer inheritance. A valid content hash does not exempt an artifact from these structural checks.

## Publish under a declared local ownership model

`publish_bundle()` creates a fresh version directory for one trusted writer. It writes temporary files, flushes their data, requests file synchronization and replaces the final filenames. The manifest is committed after the model, and the function then requests directory synchronization.

This demonstrates an ordering pattern: readers require the manifest and complete validated model together. It is not a distributed compare-and-swap protocol, a multi-writer artifact service or a qualification of power-loss behavior on every filesystem. The ordinary pad uses temporary scratch storage and discards it after execution. Synchronization calls in that scratch directory do not turn a finite lesson into persistent storage.

For durable publication, the storage system, concurrency rules, selected pointer and recovery procedure need their own tested contract. The persistent project workflows preserve their state separately and verify readback after container replacement. The manifest-last pattern is one component of that wider design.

## Worked case 1: Restore a known numerical computation

`example_one()` fits the actual least-squares coefficients and publishes a fresh bundle. The loader validates its manifest, bytes, feature ordering and coefficient shape. It then reconstructs the fixed numerical scorer.

Three probe rows represent two hours and zero tickets, four hours and one ticket, and eight hours and two tickets. Their independent rule-based targets are seven, 9.5 and sixteen. Restored predictions agree with that oracle within the declared absolute tolerance of \(10^{-10}\), with zero relative tolerance.

The captured table exposes both restored predictions and oracle values. The report preserves the actual model digest, byte count and observed maximum numerical error. It also records that executable object code was not deserialized by this numerical JSON loader.

The conclusion is deliberately specific. This artifact round trip preserves the demonstrated linear computation. It does not establish that the target rule is scientifically appropriate, that a new input has valid units, or that an unrecognized model family should be accepted. The serving interface from chapter 036 remains a separate boundary.

## Worked case 2: Reject invalid artifacts and expose the limit of integrity checks

`example_two()` changes one numerical character in the stored intercept while preserving file length and valid JSON syntax. The original manifest still names the original digest. The loader rejects the changed bytes. This isolates the content-hash check from a trivial file-size difference.

Other bundles have internally consistent hashes but incompatible meaning. One contains only one coefficient; another reverses the feature names. Both are rejected after their byte checks because their structural or semantic contracts disagree with the scorer. A matching digest identifies the supplied representation; it does not make that representation compatible.

A manifest that names an escaping path is rejected. A model-file symbolic link is also rejected even though its target contains otherwise-valid model bytes. Using a valid target matters: the case establishes the link-path rule rather than relying on a separate hash failure to produce an error.

The case then publishes a different, internally consistent model with supported shape and units. The loader accepts it. This is intentional evidence of the loader's boundary: it validates the representation but has no independent authority that identifies the approved producer or approved coefficients. A different valid model can satisfy the same format.

If a consumer obtains both artifact and expected digest from an untrusted location, an unauthorized replacement can update both. Origin authentication and authorization must come from a trusted publication channel, signed provenance or another suitable system contract. Even an authenticated model still needs scientific and operational acceptance. A signature is not an accuracy metric.

## Connect artifacts to the wider supply chain

A complete inference computation includes more than a coefficient file. The preprocessing implementation, numerical libraries, runtime image, interface and selected model version can all affect results. Retain exact identities for the components relevant to the reproduction and trust claim.

Package requirements describe constraints; a reviewed lock adds exact resolved versions and distribution hashes. An image digest identifies a built image. A source revision identifies code history. These records should be connected to the artifact and its execution evidence, with explicit trust in the process that produced them. A collection of unrelated hashes does not automatically establish that connection.

Keep old accepted versions and their evidence when preparing an update. A failed candidate should not destroy the last usable model. The MLflow chapter demonstrated selection metadata, while the owned service projects test actual activation, readiness and rollback. Following an alias and verifying a loaded artifact are distinct operations.

## Answered interview discussion

**Does a SHA-256 digest make a model safe?** It can establish agreement with expected bytes. It does not establish origin, supported structure, permissible loading behavior or fitness for the intended decision. The example separates those checks.

**Why reject a symbolic link to valid bytes?** This loader has a fixed regular-file contract. Accepting an indirect filesystem reference would introduce another identity and path behavior that the format does not authorize.

**Why not load any serialized estimator that has the correct hash?** Some formats can restore executable object behavior. The consumer must trust the producer and understand the loader, dependencies and permitted types. This example instead demonstrates a fixed numerical format with a known computation.

**What would make rollback reviewable?** Retain the approved artifact and interface identities, its evaluation evidence, the runtime environment and the actual selection/readiness observations. Retraining a vaguely remembered configuration is not the same rollback operation.
