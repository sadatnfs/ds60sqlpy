## The question and the mechanism

Predict which rows survive a projection, an extension and a grouped summary.

A virtual table is an intermediate table value, not automatically a persisted model table. Its rows and columns matter independently of the scalar values calculated over it. SELECTCOLUMNS starts a projection with the named expressions; ADDCOLUMNS retains the input columns and extends each input row. Neither should be confused with an operation that groups and removes all-blank result rows.

SUMMARIZECOLUMNS creates groups and evaluates expressions for them. In the ordinary form used here, a group whose supplied expressions are all BLANK is omitted. Therefore a product with no sales can remain in an ADDCOLUMNS result yet disappear from a summary of revenue. That is a table-shape difference, not proof that the source product was deleted.

When debugging a larger expression, expose the intermediate table before aggregating it. Record its grain, candidate keys, row count, column names and whether blanks are preserved. A final scalar can conceal that the formula changed its candidate population several steps earlier.

## Vocabulary and expression anatomy

The first case projects the extended product-key table into explicit output names. [NetRevenue] transitions each candidate product row. The second groups directly by ProductKey with a revenue expression. Both use the clean model and explicit sorting; the only intended difference is all-blank group retention.

Concepts to explain in your own words: **ADDCOLUMNS**, **SELECTCOLUMNS**, **SUMMARIZECOLUMNS**, **virtual table**, **nonempty**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: Extend every candidate key

**Starting context:** All four clean-model Product keys; retain every input row while adding revenue.

```dax
EVALUATE SELECTCOLUMNS ( ADDCOLUMNS ( VALUES ( Product[ProductKey] ), "RevenueForKey", [NetRevenue] ), "ProductKey", Product[ProductKey], "Revenue", [RevenueForKey] )
ORDER BY [ProductKey]
```

**Context trace:**

1. VALUES supplies keys 1,2,3,4.
2. ADDCOLUMNS computes one revenue result per input key.
3. Bag's blank measure does not remove key 4 from this projected table.

**Hand-derived worked-reference result:**

| ProductKey | Revenue |
| --- | --- |
| 1 | 67 |
| 2 | 24 |
| 3 | 96 |
| 4 | BLANK |

An extension column is addressed by its name in the virtual table expression. It is not automatically installed as a persistent Product column.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: A grouped summary omits an all-blank group

**Starting context:** Same clean model; grouped summary with one measure expression.

```dax
EVALUATE SUMMARIZECOLUMNS ( Product[ProductKey], "Revenue", [NetRevenue] )
ORDER BY Product[ProductKey]
```

**Context trace:**

1. The four candidate keys form groups.
2. Key 4 has BLANK for every supplied expression.
3. That all-blank group is omitted; keys 1,2,3 remain.

**Hand-derived worked-reference result:**

| ProductKey | Revenue |
| --- | --- |
| 1 | 67 |
| 2 | 24 |
| 3 | 96 |

Adding a nonblank expression or deliberately coalescing revenue can alter which groups appear. Do not assume that all table-producing functions have the same row-retention policy.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. The fourth expression becomes nonblank.
2. A projection can change columns without grouping rows.
3. Separate candidates, extended values and retained rows.
4. Its scope is the current expression.
5. At least one expression would be nonblank even for Bag.
6. A complete eligibility list may need rows with no outcome.
