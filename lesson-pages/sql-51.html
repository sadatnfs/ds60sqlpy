Day 51: Finance/Operations Project, Part 3: Cash Flow#

How to run this lesson#

Open sql-51 from ./classroom (PostgreSQL), choose Whole SQL lesson (psql) and edit .learning/sql/sql-51/lesson/workspace/sql/postgres-60day/day51_project2_finance_part3.sql. The script reads payments, expenses and budgets in advanced_sql_training between BEGIN and ROLLBACK. A clean psql run prints up to 36 months of net and cumulative cash, newest first, then up to 120 category-month rows comparing actual spend with budget, then your exercises. Payment and expense dates are generated relative to the load date, so month labels move over time while totals stay the same. See the study guide for the launcher and recovery steps, and its notebook section for the optional notebook.

Level and prerequisites#

  • Level: Advanced
  • Prerequisites: Day 50; budget variance Day 50 compared expenses with budgets by category; today expenses meet the cash that customers actually paid.
  • Artifacts: learner SQL · solution reasoning · executable solution

A beginner's mental model for this lesson#

Cash flow is two monthly series that come from different tables. Cash in is payments.amount, 3,836 payments totaling about 1.83 million spread over roughly four years. Cash out is expenses.amount, 10,000 expense rows in five categories (COGS, G&A, Infrastructure, Marketing and Payroll, about 10.1 million each) that only cover the last two years. The two series therefore do not have the same months, and the gap is the whole lesson: summarize each table to one row per month on its own, then combine the summaries with a FULL OUTER JOIN so a month that appears on only one side is kept with a zero on the other.

Cash is not revenue. orders.total_amount sums to about 2.36 million, but roughly a fifth of orders are still placed without a payment, and 149 payments land in a later month than their order. A running total such as cumulative cash is a window over the monthly rows, so it must be computed after the monthly grain is fixed. Read each CTE in logical clause order.

Two worked SQL examples#

Both excerpts come from the learner script and run inside its transaction.

Example 1#
WITH pay_m AS (
  SELECT
    date_trunc('month', payment_date)::date AS month,
    SUM(amount) AS cash_in
  FROM
    payments
  GROUP BY
    1
),
exp_m AS (
  SELECT
    date_trunc('month', expense_date)::date AS month,
    SUM(amount) AS cash_out
  FROM
    expenses
  GROUP BY
    1
),
joined AS (
  SELECT
    COALESCE(p.month, e.month) AS month,
    COALESCE(p.cash_in, 0) AS cash_in,
    COALESCE(e.cash_out, 0) AS cash_out
  FROM
    pay_m p
    FULL OUTER JOIN exp_m e ON e.month = p.month
)
SELECT
  month,
  ROUND(cash_in - cash_out, 2) AS net_cash_flow,
  SUM(ROUND(cash_in - cash_out, 2)) OVER (ORDER BY month) AS cumulative_cash
FROM
  joined
ORDER BY
  month DESC
LIMIT 36;

How to read it: pay_m and exp_m each reduce one table to one row per month. joined combines them with FULL OUTER JOIN, taking the month from whichever side has it and turning a missing side into 0. The final SELECT computes net cash and a running SUM(...) OVER (ORDER BY month).

Expected result/shape: 36 rows, newest month first. The cumulative column is computed over every month before LIMIT trims the list, so the newest row carries a balance of about -48.65 million: expenses close to 2 million in a full month swamp cash in of 30,000 to 126,000. Older rows before expenses begin show small positive net cash.

Example 2#
WITH exp AS (
  SELECT
    date_trunc('month', expense_date)::date AS month,
    category,
    SUM(amount) AS actual
  FROM
    expenses
  GROUP BY
    1,
    2
),
bud AS (
  SELECT
    period AS month,
    category,
    SUM(amount) AS budget
  FROM
    budgets
  GROUP BY
    1,
    2
),
j AS (
  SELECT
    COALESCE(b.category, e.category) AS category,
    COALESCE(b.month, e.month) AS month,
    COALESCE(b.budget, 0) AS budget,
    COALESCE(e.actual, 0) AS actual
  FROM
    bud b
    FULL JOIN exp e ON e.month = b.month
      AND e.category = b.category
)
  SELECT
    category,
    month,
    actual,
    budget,
    ROUND(actual - budget, 2) AS variance,
    SUM(actual) OVER (PARTITION BY category ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS actual_ma3,
    SUM(budget) OVER (PARTITION BY category ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS budget_ma3
  FROM
    j
  ORDER BY
    month DESC,
    category
  LIMIT 120;

How to read it: exp and bud reduce expenses and budgets to (month, category). j full-joins them on both keys. The two window columns are three-row rolling sums per category, ordered by month.

Expected result/shape: 120 rows, newest month first and alphabetical by category within a month, so 24 months of five categories. Despite the _ma3 names, actual_ma3 and budget_ma3 are three-month sums, not averages; divide by 3 if you need a moving average, and remember the first two months of each category sum fewer than three rows.

Learning objectives#

  • Separate cash movement from booked order revenue.
  • Project three future months under a precisely stated seasonal-average rule.

Vocabulary and concepts#

  • Cash-in: received payment amount by payment date.
  • Cash-out: expense amount by expense date.
  • Seasonal average: an average of prior observations matching the target calendar period, distinct from a single seasonal-naive lag.

Worked example / walkthrough#

Aggregate payments and expenses independently by month, full-join the two series, and calculate net and cumulative cash. For a future target month, join historical net cash on calendar month, average the matches, and return the supporting observation count beside the projection.

Common mistakes and how to recover#

  • Lesson-specific semantic mistake: Use a full outer join so payment-only and expense-only months remain visible. With an inner join every month before expenses begin disappears, and the cumulative balance starts in the wrong place.
  • Totals that are too large: payments and expenses were joined row to row before summing, multiplying each payment by every expense in the month. Aggregate each table to months first.
  • Margin of 1.0000 or a division error: a month with no cost or no cash. Keep NULLIF(cash_in, 0) and show a status rather than hiding the case.
  • Cash and booked revenue mixed: orders.total_amount is not cash. Label which one a column measures.
  • More recovery steps are in the study guide.

Deep dive and reference#

Project focus#

  • Calculate monthly cash-in, cash-out, net cash flow, and cumulative cash.
  • Define an operating-margin metric from selected expense categories.
  • Project net cash for the next three months.

How the learner script uses the current schema#

Cash-in comes from payments.payment_date and payments.amount; cash-out comes from expenses.expense_date and expenses.amount. This is cash movement, not booked orders.total_amount. The starter also aligns monthly budgets and actuals at category grain.

Practice map#

Exercises 1 and 6 define and protect an operating margin, Exercise 2 builds a seasonal projection that shows its own evidence, Exercise 3 sets booked revenue beside cash, and Exercises 4 and 5 produce a balance sheet style roll-forward and a gap-free month list. The learner SQL repeats the same numbered prompts.

Ambiguous forecast wording#

The learner says “average of last 12 matching months (seasonal naive).” Seasonal naive usually means the single value from 12 months earlier, while “average” implies several observations. The reference answer interprets matching months as the same calendar month across prior years and averages the available values. State this assumption and return the supporting history count.

Validation and limits#

  • Use a full outer join so payment-only and expense-only months remain visible.
  • Guard margin when cash-in is zero.
  • Treat expense-category classification as course policy, not accounting advice.
  • A one-observation seasonal average is only a naive estimate.
  • Reconcile monthly net cash to total payments minus total expenses over the same represented period.

-- Cash flow projections; budget vs actual with rolling periods
BEGIN;
SET search_path TO training, public;

-- Net cash flow per month = customer payments - expenses
WITH pay_m AS (
  SELECT
    date_trunc('month', payment_date)::date AS month,
    SUM(amount) AS cash_in
  FROM
    payments
  GROUP BY
    1
),
exp_m AS (
  SELECT
    date_trunc('month', expense_date)::date AS month,
    SUM(amount) AS cash_out
  FROM
    expenses
  GROUP BY
    1
),
joined AS (
  SELECT
    COALESCE(p.month, e.month) AS month,
    COALESCE(p.cash_in, 0) AS cash_in,
    COALESCE(e.cash_out, 0) AS cash_out
  FROM
    pay_m p
    FULL OUTER JOIN exp_m e ON e.month = p.month
)
SELECT
  month,
  ROUND(cash_in - cash_out, 2) AS net_cash_flow,
  SUM(ROUND(cash_in - cash_out, 2)) OVER (ORDER BY month) AS cumulative_cash
FROM
  joined
ORDER BY
  month DESC
LIMIT 36;

Exercise 1: Monthly operating margin#

The prompt defines operating cost as COGS + Payroll + Infrastructure + G&A; Marketing is deliberately excluded.

SET search_path TO training, public;

WITH cash AS (
  SELECT
    date_trunc('month', payment_date)::date AS month,
    SUM(amount) AS cash_in
  FROM
    payments
  GROUP BY
    date_trunc('month', payment_date)
),
operating_expense AS (
  SELECT
    date_trunc('month', expense_date)::date AS month,
    SUM(amount) FILTER (WHERE category IN ('COGS', 'Payroll', 'Infrastructure', 'G&A')) AS operating_cost
  FROM
    expenses
  GROUP BY
    date_trunc('month', expense_date))
SELECT
  COALESCE(c.month, e.month) AS month,
  ROUND(COALESCE(c.cash_in, 0), 2) AS cash_in,
  ROUND(COALESCE(e.operating_cost, 0), 2) AS operating_cost,
  ROUND((COALESCE(c.cash_in, 0) - COALESCE(e.operating_cost, 0)) / NULLIF (c.cash_in, 0), 4) AS operating_margin
FROM
  cash c
  FULL OUTER JOIN operating_expense e USING (month)
ORDER BY
  month DESC;

Expected grain: one row per month appearing in either payments or operating expenses. Margin is NULL when there is no cash-in denominator.

Reasoning and verification#
  • Inputs/evidence: For sql-51 Exercise 1, sum payments.amount by payment month in cash, sum expenses.amount by expense month for the four operating categories (COGS, Payroll, Infrastructure, G&A, not Marketing) in operating_expense, and FULL OUTER JOIN the two USING (month).
  • Expected result/shape: For sql-51 Exercise 1, expected output: 46 rows, one per month appearing in either payments or operating expenses (2023-02-01 to 2026-11-01). The final columns are month, cash_in, operating_cost, and operating_margin. The final order is month DESC.
  • Independent verification: For sql-51 Exercise 1, confirm 46 distinct months, and that the 21 months before expenses begin (2023-02 to 2024-10) show operating_cost 0.00 and a margin of exactly 1.0000. Recompute the top row: 2026-11 has 76,045.60 cash in and 1,362,737.02 operating cost (that month's 1,712,274.61 of expenses minus 349,537.59 of Marketing), so the margin is -16.9200. Then, in a transaction, delete the 77 payments from 2025-03: that month stays with cash_in 0.00, cost 1,747,681.27, and a NULL margin instead of a division error; ROLLBACK.
  • Intermediate relation check: cash is one row per payment month and operating_expense one row per expense month; the second covers only the last two years. Count both, then count the full join: it should equal the number of distinct months across the two tables, here the payment months, since expenses never appear alone.
  • Clause check: SUM(amount) FILTER (WHERE category IN (...)) defines operating cost as four categories and leaves Marketing out. That choice is policy, so it is written into the query. NULLIF(c.cash_in, 0) makes the margin NULL instead of an error when a month has costs and no cash.
  • Alternative/trade-off: A WHERE category IN (...) inside operating_expense would give the same sums; the FILTER form keeps room for other cost columns from the same scan, such as a separate marketing total.
  • Edge case: A month with expenses but no payments would get cash_in 0 and a NULL margin through NULLIF. Months with cash but no expenses get a margin of 1.0000, which is arithmetically right and analytically misleading; Exercise 6 adds the status column that explains it.

Exercise 2: Next three months by matching calendar month#

The phrase “matching months” is interpreted as the same calendar month in earlier years.

SET search_path TO training, public;

WITH cash AS (
  SELECT
    date_trunc('month', payment_date)::date AS month,
    SUM(amount) AS cash_in
  FROM
    payments
  GROUP BY
    date_trunc('month', payment_date)
),
expense AS (
  SELECT
    date_trunc('month', expense_date)::date AS month,
    SUM(amount) AS cash_out
  FROM
    expenses
  GROUP BY
    date_trunc('month', expense_date)
),
historical AS (
  SELECT
    COALESCE(c.month, e.month) AS month,
    COALESCE(c.cash_in, 0) - COALESCE(e.cash_out, 0) AS net_cash
  FROM
    cash c
    FULL OUTER JOIN expense e USING (month)
),
future AS (
  SELECT
    (date_trunc('month', CURRENT_DATE) + n * interval '1 month')::date AS forecast_month
  FROM
    generate_series(1, 3) AS g (n))
SELECT
  f.forecast_month,
  ROUND(AVG(h.net_cash), 2) AS projected_net_cash,
  COUNT(h.month) AS matching_historical_months
FROM
  future f
  LEFT JOIN historical h ON EXTRACT(month FROM h.month) = EXTRACT(month FROM f.forecast_month)
    AND h.month < f.forecast_month
GROUP BY
  f.forecast_month
ORDER BY
  f.forecast_month;

Expected shape: exactly three future month rows. The count column shows how much history supports each estimate; a NULL projection means there was none.

Reasoning and verification#
  • Inputs/evidence: For sql-51 Exercise 2, build monthly net cash in historical from a FULL OUTER JOIN of payment and expense totals, generate the next three calendar months after CURRENT_DATE in future, and LEFT JOIN each one to the earlier months with the same calendar month number.
  • Expected result/shape: For sql-51 Exercise 2, expected output: exactly three rows, one per future forecast_month (2026-12-01, 2027-01-01, and 2027-02-01 when run in November 2026). The count column shows how much history supports each estimate; a NULL projection means there was none. The final columns are forecast_month, projected_net_cash, and matching_historical_months. The final order is forecast_month.
  • Independent verification: For sql-51 Exercise 2, run in November 2026, confirm the counts 3, 3, and 4, then recompute the first row by hand: the Decembers 2023, 2024, and 2025 have net cash 11,201.99, -2,102,060.09, and -2,062,784.20, whose mean is -1,384,547.43. February averages four months (2023 to 2026), so it is -941,106.45. Then, in a transaction, insert a 100.00 payment dated 2026-12-02 and rerun: the December projection does not change, because h.month < f.forecast_month keeps a month out of its own forecast; ROLLBACK.
  • Intermediate relation check: historical is one row per month with net cash. future is three rows from generate_series(1, 3). The LEFT JOIN then pairs each future month with the past months that share its calendar month, so each future row matches 3 or 4 history rows before GROUP BY collapses it again.
  • Clause check: The join condition compares EXTRACT(month ...) on both sides and adds h.month < f.forecast_month. COUNT(h.month) counts only matched history, so a future month with no history would show 0 and a NULL projection instead of being dropped.
  • Alternative/trade-off: A weighted average that favors recent years, or a trailing 12-month average, would react faster to the large expenses that started two years ago; the seasonal-naive average is simpler and shows its evidence count.
  • Edge case: Because expenses only exist in recent years, each average blends small positive years with large negative ones. Restricting historical to months with expense data would give a different and arguably fairer projection.

Reasoning, safety, and pitfalls#

  • Cash flow uses payments, not booked order revenue.
  • The operating-margin definition is course policy; real financial statements may classify categories differently.
  • A seasonal average needs multiple years to be convincing. Treat a one-point average as a naive forecast and disclose the sample count.
  • Both answers are read-only.

Exercise 3: Separate cash and booked revenue#

Orders are grouped by order month and payments by payment month. Displaying both reveals timing differences; combining them under one unlabeled “revenue” metric would be misleading.

Reasoning and verification#
  • Inputs/evidence: For sql-51 Exercise 3, read from orders and payments; sum total_amount by order month as booked_order_revenue and left join the payments summed by payment month as cash_received, using COALESCE(..., 0) for months without payments.
  • Expected result/shape: For sql-51 Exercise 3, expected output: one row per order month, ordered by month; cash_received is lower than booked_order_revenue in most months because unpaid orders bring no cash. The final columns are month, booked_order_revenue, and cash_received. The final order is month.
  • Independent verification: For sql-51 Exercise 3, confirm 46 unique months, that SUM(booked_order_revenue) is 2,355,646.89 and SUM(cash_received) is 1,831,900.81 (the same as SELECT SUM(amount) FROM payments), and that cash is lower than bookings in 45 months and equal only in 2023-02 (1,203.26). Then, in a transaction, insert a 100.00 payment dated 2026-12-02: the result keeps 46 rows and the same cash total, now 100.00 short of payments, because the query starts from order months and drops a payment-only month; ROLLBACK.
  • Intermediate relation check: The derived table p is one row per payment month. The outer query starts from orders, one row per order, and left joins p on the order month, so each payment-month total repeats on every order of that month until GROUP BY collapses them.
  • Clause check: p.cash_received is in the GROUP BY so it can be selected without an aggregate. Summing it instead would multiply it by the number of orders in the month. COALESCE turns a month with orders but no payments into 0.
  • Alternative/trade-off: Aggregating orders to months in their own CTE and full-joining to payment months, as in Exercise 1, would also keep payment-only months; here the order months drive the result, which matches the question about booked revenue.
  • Edge case: A payment made in the month after its order raises the next month's cash, so booked revenue and cash received measure different timing and should not be combined into one unlabeled margin. About 150 payments on the course data (148 on our load) cross a month boundary this way.

SELECT
  date_trunc('month', o.order_date)::date AS month,
  SUM(o.total_amount) AS booked_order_revenue,
  COALESCE(p.cash_received, 0) AS cash_received
FROM
  orders o
  LEFT JOIN (
    SELECT
      date_trunc('month', payment_date)::date AS month,

-- Exercise 4: monthly flows establish the grain; the running SUM turns net
-- movement into an ending balance from the declared zero opening balance.
WITH flow AS (
  SELECT
    month,
    SUM(cash_in) AS cash_in,
    SUM(cash_out) AS cash_out
  FROM (
    SELECT
      date_trunc('month', payment_date)::date AS month,
      amount AS cash_in,
      0::numeric AS cash_out
    FROM
      payments
    UNION ALL
    SELECT
      date_trunc('month', expense_date)::date,
      0::numeric,
      amount
    FROM
      expenses) entries
  GROUP BY
    month
),
balances AS (
  SELECT
    month,
    cash_in,
    cash_out,
    cash_in - cash_out AS net_cash,
    SUM(cash_in - cash_out) OVER (ORDER BY month) AS ending_cash
  FROM
    flow
)
SELECT
  month,
  LAG(ending_cash, 1, 0::numeric) OVER (ORDER BY month) AS beginning_cash,
  cash_in,
  cash_out,
  net_cash,
  ending_cash
FROM
  balances
ORDER BY
  month;

-- Exercise 5: the calendar spine retains months appearing on only one side.
WITH bounds AS (
  SELECT
    LEAST ((
      SELECT
        MIN(payment_date)::date
      FROM payments), (
      SELECT
        MIN(expense_date)
      FROM expenses)) AS first_day,
    GREATEST ((
      SELECT
        MAX(payment_date)::date
      FROM payments), (
      SELECT
        MAX(expense_date)
      FROM expenses)) AS last_day
),
months AS (
  SELECT
    generate_series(date_trunc('month', first_day), date_trunc('month', last_day), interval '1 month')::date AS month
  FROM
    bounds
),
cash AS (
  SELECT
    date_trunc('month', payment_date)::date AS month,
    SUM(amount) AS cash_in
  FROM
    payments
  GROUP BY
    1
),
costs AS (
  SELECT
    date_trunc('month', expense_date)::date AS month,
    SUM(amount) AS cash_out
  FROM
    expenses
  GROUP BY
    1
)
SELECT
  m.month,
  COALESCE(c.cash_in, 0) AS cash_in,
  COALESCE(x.cash_out, 0) AS cash_out
FROM
  months m
  LEFT JOIN cash c USING (month)
  LEFT JOIN costs x USING (month)
ORDER BY
  m.month;

-- Exercise 6: NULLIF preserves an undefined margin and the status explains it.
WITH toy (
  month,
  cash_in,
  operating_cost
) AS (
  VALUES (date '2026-01-01', 0::numeric, 100::numeric),
    (date '2026-02-01', 500, 300))
SELECT
  month,
  (cash_in - operating_cost) / NULLIF (cash_in, 0) AS operating_margin,
  CASE WHEN cash_in = 0 THEN
    'undefined: zero cash in'
  ELSE
    'defined'
  END AS margin_status
FROM
  toy;
