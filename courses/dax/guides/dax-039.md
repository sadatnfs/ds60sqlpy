## The question and the mechanism

Choose a time aggregation that matches a balance rather than summing repeated states.

Inventory snapshots record a state at a date. Summing different products at the same snapshot can be meaningful; summing the same stock across several dates usually counts repeated states. This is semi-additive behavior: additivity depends on the dimension over which aggregation occurs.

The analytical fixture totals 35 units at January 31 and 30 at February 28. Adding all six snapshot rows gives 65, which is not the ending inventory. A closing balance at the last selected snapshot is 30. If the question asks for average stock instead, it needs a stated time-weighting rule; the sum 65 divided by an arbitrary row count does not automatically provide that rule.

A last-known-value policy is another choice, not a new observation. At February 15 the latest available snapshots are January 31. Carrying Notebook 10 and Mug 5 forward gives 15 for those two products under an explicit hold-between-observations assumption. That is not proof their physical stock stayed unchanged. State a staleness limit and report missing or too-old values rather than silently carrying them indefinitely.

## Vocabulary and expression anatomy

Case A compares a sum over two snapshot dates with the balance at the last selected Date. Case B finds a last eligible Inventory date for each selected product before an as-of cutoff, then retrieves that product's balance. Product context must remain while Date filters are changed.

Concepts to explain in your own words: **snapshot**, **semi-additive**, **closing balance**, **last known**, **staleness**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

### Case A: Two states are not one closing balance

**Starting context:** Analytics model; January and February 2025; all products; complete snapshots on January 31 and February 28.

```dax
EVALUATE CALCULATETABLE ( ROW ( "SummedSnapshots", SUM ( Inventory[Units] ), "ClosingUnits", CALCULATE ( SUM ( Inventory[Units] ), LASTDATE ( 'Date'[Date] ) ) ), 'Date'[Year] = 2025, 'Date'[MonthNumber] IN { 1, 2 } )
```

**Context trace:**

1. January 31 has 10 +20 +5 =35 units.
2. February 28 has 8 +15 +7 =30 units.
3. All snapshot rows sum to 65; the closing selected-date balance is 30.

**Hand-derived worked-reference result:**

| SummedSnapshots | ClosingUnits |
| --- | --- |
| 65 | 30 |

The incorrect sum can still be useful as an intermediate check, but it must not be labeled inventory on hand at period end.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: An explicitly carried-forward subset

**Starting context:** Notebook and Mug only; as-of February 15; carry the last eligible snapshot under an explicit policy.

```dax
EVALUATE CALCULATETABLE ( ROW ( "CarriedUnits", SUMX ( VALUES ( Product[ProductKey] ), VAR Cutoff = DATE ( 2025, 2, 15 ) VAR LastKnown = CALCULATE ( MAX ( Inventory[SnapshotDate] ), REMOVEFILTERS ( 'Date' ), Inventory[SnapshotDate] <= Cutoff ) RETURN CALCULATE ( SUM ( Inventory[Units] ), REMOVEFILTERS ( 'Date' ), Inventory[SnapshotDate] = LastKnown ) ) ), Product[ProductKey] IN { 1, 3 } )
```

**Context trace:**

1. For each selected product, the last snapshot not after February 15 is January 31.
2. Notebook has 10 and Mug has 5 at that snapshot.
3. The policy-derived carried total is 15, with 15 days of staleness.

**Hand-derived worked-reference result:**

| CarriedUnits |
| --- |
| 15 |

This is a model-based as-of estimate, not a measured February 15 snapshot. Real systems may require stricter freshness or complete change-event accounting.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Use their latest observed snapshot values.
2. Compare a shared last-date policy with per-product last-known selection.
3. Include cutoff minus the chosen snapshot date.
4. Rows count product snapshots, not elapsed time.
5. No observed state can be selected under this policy.
6. A balance is a state, while transactions are flows.
