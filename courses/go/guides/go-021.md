## Why this mechanism matters

A command-line interface translates external strings into validated application configuration. Defaults, flags, environment and configuration files need an explicit precedence order; silently mixing them creates surprising deployments. Parse configuration once at the boundary and pass a typed value to the program. The browser pad has no arbitrary argument channel, so this lesson uses an isolated flag.FlagSet with synthetic argument slices. This exercises the real parser without changing the process global flags. A production CLI also needs clear help, stable exit codes, redacted diagnostics and a documented distinction between malformed input and runtime failure.

## Vocabulary and concepts

- **Precedence:** The declared order in which configuration sources override one another.
- **Flag set:** An isolated collection of command-line options.
- **Validation boundary:** The point where external input becomes trusted typed configuration.

## Syntax anatomy and reasoning

flag.NewFlagSet with ContinueOnError returns parse failures instead of exiting the process. IntVar binds a flag to storage, Parse accepts a []string and Args returns positional leftovers. SetOutput can redirect diagnostics to a buffer for tests. Do not call os.Exit from a library helper, because it prevents its caller from controlling cleanup and testing. Validate ranges after parsing: the parser can accept a negative integer even if the domain forbids it.

## Worked example / walkthrough

### Worked example 1: Apply an explicit flag

Parse -count=3 with a default of 1.

```go
package main

import (
	"errors"
	"flag"
	"fmt"
	"io"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func parseArgs(args []string) (int, []string, error) {
	f := flag.NewFlagSet("lesson", flag.ContinueOnError)
	f.SetOutput(io.Discard)
	n := 1
	f.IntVar(&n, "count", 1, "positive count")
	if err := f.Parse(args); err != nil {
		return 0, nil, err
	}
	if n < 1 {
		return 0, nil, errors.New("positive count required")
	}
	return n, f.Args(), nil
}

func main() {
	// Apply an explicit flag
	{
		n, args, err := parseArgs([]string{"-count=3"})
		check(err == nil && n == 3 && len(args) == 0, "flag")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** The resulting count is 3.

The synthetic argument slice tests the actual parser while remaining independent of the classroom process arguments.

### Worked example 2: Retain a default

Parse no arguments.

```go
package main

import (
	"errors"
	"flag"
	"fmt"
	"io"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func parseArgs(args []string) (int, []string, error) {
	f := flag.NewFlagSet("lesson", flag.ContinueOnError)
	f.SetOutput(io.Discard)
	n := 1
	f.IntVar(&n, "count", 1, "positive count")
	if err := f.Parse(args); err != nil {
		return 0, nil, err
	}
	if n < 1 {
		return 0, nil, errors.New("positive count required")
	}
	return n, f.Args(), nil
}

func main() {
	// Apply an explicit flag
	{
		n, args, err := parseArgs([]string{"-count=3"})
		check(err == nil && n == 3 && len(args) == 0, "flag")
	}

	// Retain a default
	{
		n, _, err := parseArgs(nil)
		check(err == nil && n == 1, "default")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** The count remains 1.

A default is an intentional contract, not an accidental zero value. Changing it can alter existing workflows even when parsing code is unchanged.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
