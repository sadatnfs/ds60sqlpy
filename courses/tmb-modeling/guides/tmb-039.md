# Benchmarking explicit and automatic parallelism

Start with: tmb-038, tmb-020.

Outcome: Plan a benchmark of a named operation that keeps thread policy and numerical correctness visible.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter tabulates illustrative timings and an Amdahl bound; its timings are hypothetical, not measurements. In the separately prepared [owned project](../projects/tmb-local/README.md), `tests/public_api.R` runs `TMB::benchmark(profile_obj, n = 10000, cores = 1)` with a fixed evaluation budget; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

`benchmark(obj, n=10, expr=NULL, cores=NULL)` measures selected model operations across thread counts. Its `plot.parallelBenchmark` method can display speedup or elapsed time. A timing object is evidence about a particular environment, input and operation, not a universal claim that C++ or more threads are faster.

The default benchmark distinguishes objective, gradient and sparse-Hessian/factorization work where applicable. A custom expression can time another operation. Record whether compilation, tape construction, data conversion and cold-start loading are included or excluded. Comparing a warm gradient to a cold end-to-end script exaggerates speedup.

## Key terms

- **benchmark:** The TMB function `benchmark(obj, n, expr, cores)` that times selected model operations across thread counts.
- **Speedup and efficiency:** Speedup is \(T_1/T_p\), the one-thread time over the \(p\)-thread time; efficiency is \(T_1/(pT_p)\).
- **Amdahl's law:** The limit on ideal speedup set by the serial fraction of a workload, before scheduling and memory effects.
- **autopar:** Experimental automatic parallelization via `openmp(autopar=TRUE)` that requires a TMBad and OpenMP build and needs its own parity evidence.

### Worked case A: speedup and efficiency

The companion uses an explicitly hypothetical timing table and computes speedup \(T_1/T_p\) and efficiency \(T_1/(pT_p)\). It labels the table as an arithmetic illustration, not a machine benchmark. A real run should retain repeated measurements, input sizes and the exact expression.

`openmp(n, DLL=...)` controls a model library's OpenMP threads. It does not control every BLAS/LAPACK thread pool. `max=TRUE` depends on the configured environment and platform. For a reproducible benchmark, use explicit small counts and record native and BLAS settings separately.

### Worked case B: automatic parallelization is a different mode

`openmp(autopar=TRUE)` is experimental, requires TMBad and an OpenMP-enabled compile, and can supersede explicit parallel constructs according to the manual. Compare its value and gradient to a serial reference before measuring speed. The existing CppAD `parallel_accumulator` test record does not qualify this automatic mode.

The companion uses Amdahl's law to show how a serial fraction limits ideal speedup. Real workloads add scheduling, memory-bandwidth and cache effects. For a small objective, overhead can dominate useful arithmetic, so a slower two-thread run may be the expected result rather than a bug.

Timer resolution also matters. A two-evaluation probe of the four-row Gaussian model produced zero elapsed times, making relative-speedup plotting undefined. The bounded API probe therefore uses 10,000 tiny evaluations per timed operation so its plotting input is measurable. This is a timing-resolution fix, not a claim that the workload became more representative or that one thread is faster than another.

### Answered discussion

**Can I benchmark with all available threads inside every Spark task?** That can oversubscribe the executor. Allocate concurrency across layers first. **Should I report the fastest single run?** Prefer a defined statistic across repeats and explain variability. **Can a plot establish numerical correctness?** No. Keep parity tests and timing records separate, and never disable failure checks solely to improve the chart.

See [benchmark and openmp](https://cran.r-project.org/web/packages/TMB/TMB.pdf). The project qualifies actual one/two-thread explicit-accumulator parity; measured speed and automatic parallelization require their own evidence.

### Worked case C: reading the hypothetical table

The companion's times are invented for arithmetic, and its `kind` column says so. With \(T_1=1\), \(T_2=0.62\) and \(T_4=0.48\):

```text
threads  seconds  speedup  efficiency  amdahl_ideal (serial fraction 0.25)
1        1.00     1.000    1.000       1.000
2        0.62     1.613    0.806       1.600
4        0.48     2.083    0.521       2.286
(arithmetic from the companion's illustrative values, rounded)
```

At two threads, the illustrative speedup 1.613 slightly exceeds the Amdahl ideal of 1.6 for a 25% serial fraction. A real measurement showing that would imply either a smaller serial fraction than assumed or a cache effect, since two threads each touch half the data. At four threads, 2.083 falls short of the 2.286 ideal, and efficiency halves to 0.52. The limit \(1/0.25=4\), which the `stopifnot` asserts, is the speedup with infinitely many threads; with four threads, the formula already sits at 57% of that ceiling.

### A measurement that respects these lessons

The project's API probe runs `TMB::benchmark(profile_obj, n = 10000, cores = 1)` to obtain measurable times for a tiny model. A parallel comparison on `parallel_gaussian` extends that call while keeping the parity check first:

```r
TMB::openmp(1, DLL = "parallel_gaussian"); one <- obj$fn(obj$par)
TMB::openmp(2, DLL = "parallel_gaussian"); two <- obj$fn(obj$par)
stopifnot(abs(one - two) <= 1e-10 * max(1, abs(one)))
bench <- TMB::benchmark(obj, n = 10000, cores = 1:2)
```

The tolerance acknowledges that a parallel sum adds terms in a different order, so the last few bits can differ. With four observations per evaluation, thread start-up costs more than the arithmetic, so a two-core result slower than one core is plausible and should be recorded, not hidden. A representative benchmark needs a data size where each thread's share of the sum takes far longer than scheduling, and the record should state that size beside the times.

### What to record beside each timing

For every benchmark row, keep the operation timed (objective, gradient or Hessian), the evaluation count, the number of observations, the OpenMP thread count set through `openmp`, the BLAS thread setting read from the environment, the build receipt from `R/compile.R`, and whether the first, cold evaluation was discarded. Without the observation count, the table above could not be compared with a later run on a larger dataset. Without the BLAS setting, a four-thread result might actually be using sixteen threads, four model threads each starting four BLAS threads, which would make the efficiency column meaningless.

### Base-R companion (runs in the classroom)

```r
threads <- c(1, 2, 4);illustrative_seconds <- c(1, .62, .48)
print(data.frame(kind = "hypothetical arithmetic", threads = threads, seconds = illustrative_seconds, speedup = illustrative_seconds[1] / illustrative_seconds, efficiency = illustrative_seconds[1] / (threads * illustrative_seconds)))
serial_fraction <- .25
print(data.frame(threads = threads, ideal_amdahl_speedup = 1 / (serial_fraction + (1 - serial_fraction) / threads)))
stopifnot(1 / serial_fraction == 4)
```
