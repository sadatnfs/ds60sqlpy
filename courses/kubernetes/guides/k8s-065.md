# k8s-065: Service meshes, multi-cluster traffic and architectural limits

## Level and prerequisites

Advanced; about 120 minutes plus optional supervised host observations. Direct prerequisites: `k8s-064`. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

## Learning objectives

Draw a two-cluster request path. Defend whether a mesh is justified for a workload. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

## Purpose, vocabulary and mental model

A service mesh adds traffic-management, identity or observability capabilities around application communication through a particular implementation. It may use sidecar proxies, node-level components or other designs. It does not remove the underlying need for Pod networking, Service discovery, healthy endpoints and application correctness.

Mutual TLS authenticates both ends of a connection under an identity system. It is not the same as application authorization for a business action. A mesh can establish workload identities while the application still needs to decide whether a caller may read a specific record.

Multi-cluster communication introduces additional discovery, routing, identity and failure-domain boundaries. Overlapping Pod CIDRs, different trust roots, regional latency and partial outages complicate the design. A working single-cluster demo does not qualify a cross-region platform.

## Mechanism and field-by-field reasoning

Draw the actual data and control planes. A mesh control plane distributes configuration and identity material; proxies or equivalent components handle traffic. Failure of one plane can have different effects from failure of the other. Policies and retries must account for idempotency and retry amplification.

This chapter is design and reading practice. The course does not install a mesh, connect clusters or create cloud networks. Use synthetic diagrams to compare when a mesh capability is justified and when application-level libraries or simpler routing are sufficient.

## Trace the request or control path

```text
appA -> local traffic component -> authenticated transport -> remote traffic component -> appB
control plane distributes policy/identity; underlying network still carries packets
second cluster adds discovery, routing and trust boundaries
```

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

## Worked example / walkthrough

### Worked example 1: Separate identity and authorization

A valid workload identity is only one input to policy.

```text
mTLS peer identity: serviceA
application action: read account123
authorization decision: separate policy for that action
```

**Expected observation:** An authenticated service is not automatically allowed every business operation.

### Worked example 2: Trace retry amplification

The numbers are synthetic.

```text
client makes at most 3 total attempts
proxy makes at most 3 upstream attempts per client attempt
upstream may receive up to 9 attempts without coordinated budgets
```

**Expected observation:** Retries at multiple layers can multiply load and duplicate unsafe operations.

## Diagnosis, failure boundaries and common mistakes

The controlled failure in this chapter is: Diagnose retry amplification. Its distinguishing result is Uncoordinated retry budgets multiply attempts and load. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
