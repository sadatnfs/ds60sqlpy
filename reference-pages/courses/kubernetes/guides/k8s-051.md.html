k8s-051: NodePort and the path through a node#

Level and prerequisites#

Intermediate; about 120 minutes plus optional supervised host observations. Direct prerequisites: k8s-050. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

Learning objectives#

Draw the local-engine NodePort path. Compare NodePort with a deliberate loopback port-forward. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

Purpose, vocabulary and mental model#

A NodePort Service allocates a port from the cluster’s configured NodePort range and makes the Service available through relevant node addresses according to the data-plane configuration. It usually also has a ClusterIP. A client addresses nodeIP:nodePort, and traffic is directed to an eligible backend.

A node address must actually be reachable from the client. Desktop cluster nodes may be containers or VMs behind additional network boundaries. A valid NodePort allocation does not automatically open a host firewall, publish a VM port or create an internet route. Local and cloud setups therefore have different external paths.

The commonly seen range 30000 through 32767 is a default, not a universal constant. Explicit allocations must fit the configured range and avoid collisions. Do not expose a teaching service publicly just to make a diagram seem more realistic.

Mechanism and field-by-field reasoning#

Read port as the ClusterIP-facing Service port, targetPort as the Pod listener and nodePort as the node-facing port. The application still listens at its target endpoint. externalTrafficPolicy can affect endpoint selection and source address behavior, covered in a later chapter.

The example uses nodePort 30080 only in a manual fixture. The ordinary classroom adapter does not admit this wider networking operation. A local kind setup needs deliberately prepared port mappings or another supported access route before host-browser acceptance is possible.

Trace the request or control path#

external client -> reachable nodeIP:30080 -> Service data plane -> PodIP:8080
internal client -> ClusterIP:80 -> same logical Service -> eligible Pod

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

Worked example / walkthrough#

Worked example 1: Read all three ports#

This is a manual-only Service fragment.

type: NodePort
ports:
  - port: 80
    targetPort: 8080
    nodePort: 30080

Expected observation: Three different roles; none changes the app listener automatically.

Worked example 2: Find the missing desktop hop#

The node may not be the laptop network namespace.

laptop -> desktop VM -> kind node container -> NodePort -> Pod
missing VM/container port mapping can block the first hops

Expected observation: The Kubernetes object can be valid while the laptop has no route to it.

Diagnosis, failure boundaries and common mistakes#

The controlled failure in this chapter is: Diagnose timeout before traffic reaches the node. Its distinguishing result is Inspect host/VM route and mapping rather than Pod selectors first. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
