# web-047: Server form validation and redisplay without data loss

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-046`

## Learning objectives

Build a validator returning cleaned values and field-specific errors. Explain the limits of POST redirect GET. Use server validation, allowlist and field error accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

A server receives untrusted input even when the page supplied a constrained control. A caller can omit fields, send an array where a string was expected, alter a hidden value or bypass the browser entirely. Validate shape, type, length and domain rules before using values. An allowlist defines accepted choices; rejecting only known bad strings is usually harder to reason about.

Separate raw input, validated domain values and rendered output. Keep useful user input for redisplay after a validation error, but escape it in the HTML context. After a successful state-changing POST, a redirect to a GET page can reduce accidental resubmission on refresh. That pattern does not by itself provide idempotency, CSRF protection or authorization.

### Key terms

- **Server validation:** Checking every submitted value on the server, because a client can skip or alter any browser check.
- **Allowlist:** A fixed set of accepted values, where anything not listed is rejected.
- **Backed enum:** An enum whose cases carry string or integer values; `tryFrom()` returns the matching case or null for an unknown value.
- **Redisplay:** Showing the form again with the submitted values, safely escaped, and an error beside each invalid field.
- **POST redirect GET:** Answering a successful POST with a redirect to a GET page, so refreshing the browser does not submit the form again.

## Syntax anatomy and mechanism

A pure validator returns a value and an error map. Check is_string before trim or numeric parsing because request fields can be arrays. For a fixed set of choices, a backed enum such as `enum Topic: string { case Html = 'HTML'; ... }` names the allowed values once, and `Topic::tryFrom($raw)` returns the matching case or null, so an unknown topic becomes a validation error instead of a free-form string. For an integer text field, define an accepted syntax and range explicitly. The example uses a bounded decimal digit pattern, then converts only after it passes. The CLI inputs model POST data; no form is submitted.

## Worked example / walkthrough

### Worked example 1: Reject the wrong shape

The value must be a string before string operations.

```php
$raw = $input['topic'] ?? null;
if (!is_string($raw)) { $errors['topic'] = 'Choose a topic.'; }
```

**Expected observation:** An array-shaped field is rejected without a type error.

### Worked example 2: Validate a bounded decimal field

The accepted syntax is deliberate.

```php
if (!is_string($rawMinutes) || !preg_match('/^[0-9]{1,3}$/D', $rawMinutes)) { $errors['minutes'] = 'Use whole minutes.'; }
```

**Expected observation:** Unexpected syntax fails before numeric conversion.

## Contrast case: trimming before checking the shape

This validator is shorter than worked examples 1 and 2. Send it a normal request and one with `topic[]=HTML` and `minutes=12abc`.

```php expect-error
function validateLoose(array $input): array {
  $topic = trim($input['topic'] ?? '');
  $minutes = (int) ($input['minutes'] ?? 0);
  return ['topic' => $topic, 'minutes' => $minutes];
}

validateLoose(['topic' => ['HTML'], 'minutes' => '12abc']);
```

When `topic[]=HTML` arrives, `$input['topic']` is an array, and `trim` throws a `TypeError` because internal string functions do not accept arrays in PHP 8. The caller sees an uncaught error instead of a Choose a topic message. If the topic were a string, the `(int)` cast would turn '12abc' into 12 and accept it, and a missing value would become 0. The reference checks `is_string` first and matches the minutes text against a digits pattern before converting, so each case returns a field error.

## Debugging and common mistakes

Do not use hidden inputs as trusted prices or identities. Browser constraints are a convenience, not server enforcement. Avoid silently accepting partially validated records because one field looked correct.

When validation throws a TypeError, a field arrived as an array, as in topic[]=HTML, and reached trim or a string function; check is_string first. When the form loses the learner's input after an error, return the raw submitted strings alongside the errors so the template can redisplay them.
