Day 55: Complex BI Project, Part 1: Drill-downs#

How to run this lesson#

Open sql-55 from ./classroom (PostgreSQL), choose Whole SQL lesson (psql) and edit your saved copy at .learning/sql/sql-55/lesson/workspace/sql/postgres-60day/day55_project4_bi_part1.sql. It needs only the course tables in advanced_sql_training (orders, customers, order_items, products and payments); the file wraps every query in BEGIN ... ROLLBACK, so it leaves nothing behind. A clean psql transcript prints the four-level ROLLUP report, the 210-row top-five product list and then one result per finished exercise. Month buckets follow the current date, so the first report's row count drifts slightly between runs while the country and category totals do not. Launcher steps and recovery are in the SQL study guide; the notebook alternative is in its notebook section.

Level and prerequisites#

  • Level: Advanced
  • Prerequisites: Day 54; warehouse aggregates From Day 54 you need the habit of computing revenue at line grain before any rollup, so subtotals add up to the same grand total.
  • Artifacts: learner SQL · solution reasoning · executable solution

A beginner's mental model for this lesson#

A BI report usually wants totals at several levels at once: each country and category, each country, and everything. GROUP BY ROLLUP (country, category) asks PostgreSQL for exactly those three grouping sets in one pass, and it fills the column that a level leaves out with NULL. That NULL is generated, not stored, so the lesson pairs every rolled-up column with GROUPING(column), which is 1 when the column was left out and 0 when it is a real value. CUBE (country, category) adds the fourth set, category without country.

The second idea is dimension hygiene. Example 1 adds payment method as a dimension, but 347 orders were paid with two different methods, so joining payments straight onto order lines would count those lines twice. The primary_payment_method CTE first reduces payments to one method per order (largest amount wins, method name breaks ties) and labels the 873 placed orders as unpaid. Only then is it safe to roll up. Read every query with the logical clause order and ask what one row of each CTE represents before the GROUP BY collapses it.

Two worked SQL examples#

Both excerpts come from the learner script and run in order.

Example 1#
WITH payment_by_method AS (
  SELECT
    order_id,
    method,
    SUM(amount) AS method_amount
  FROM
    payments
  GROUP BY
    order_id,
    method
),
primary_payment_method AS (
  SELECT
    order_id,
    method
  FROM (
    SELECT
      order_id,
      method,
      ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY method_amount DESC,
        method) AS method_rank
  FROM
    payment_by_method) ranked_methods
  WHERE
    method_rank = 1
),
line AS (
  SELECT
    c.country,
    p.category,
    COALESCE(pm.method, 'unpaid') AS payment_method,
    date_trunc('month', o.order_date)::date AS month,
    (oi.unit_price * oi.quantity * (1 - oi.discount)) AS revenue,
    oi.quantity AS qty
  FROM
    orders o
    JOIN customers c ON c.customer_id = o.customer_id
    JOIN order_items oi ON oi.order_id = o.order_id
    JOIN products p ON p.product_id = oi.product_id
    LEFT JOIN primary_payment_method pm ON pm.order_id = o.order_id
)
SELECT
  country,
  category,
  payment_method,
  month,
  ROUND(SUM(revenue), 2) AS revenue,
  SUM(qty) AS units,
  GROUPING (country) AS g_country,
  GROUPING (category) AS g_category,
  GROUPING (payment_method) AS g_method,
  GROUPING (month) AS g_month
FROM
  line
GROUP BY
  ROLLUP (country, category, payment_method, month)
ORDER BY
  country NULLS FIRST,
  category NULLS FIRST,
  payment_method NULLS FIRST,
  month NULLS FIRST;

How to read it: payment_by_method sums payments per (order, method), the inner ROW_NUMBER keeps the method with the largest amount, and line attaches that single method (or unpaid) to every order line together with country, category, month and line revenue. ROLLUP (country, category, payment_method, month) then produces five levels, from full detail down to the grand total, and the four GROUPING columns tell you which level each row is.

Expected result/shape: About six thousand rows (the exact count depends on how many months the data spans today). Because the sort uses NULLS FIRST, the first row is the grand total, 2,355,647.12 revenue and 39,257 units with all four flags at 1, then AU's country subtotal of 330,947.70 with g_country = 0 and the other flags at 1. A row with g_month = 1 is a subtotal over all months, never "unknown month".

Example 2#
WITH prod_rev AS (
  SELECT
    c.country,
    p.category,
    p.product_id,
    p.name,
    SUM(oi.unit_price * oi.quantity * (1 - oi.discount)) AS revenue
  FROM
    orders o
    JOIN customers c ON c.customer_id = o.customer_id
    JOIN order_items oi ON oi.order_id = o.order_id
    JOIN products p ON p.product_id = oi.product_id
  GROUP BY
    c.country,
    p.category,
    p.product_id,
    p.name
),
ranked AS (
  SELECT
    *,
    RANK() OVER (PARTITION BY country,
      category ORDER BY revenue DESC) AS rnk
  FROM
    prod_rev
)
SELECT
  *
FROM
  ranked
WHERE
  rnk <= 5
ORDER BY
  country,
  category,
  rnk;

How to read it: prod_rev collapses lines to one row per (country, category, product), and RANK() numbers products inside each (country, category) pair by revenue. Filtering rnk <= 5 happens in the outer query because a window result cannot be used in the WHERE of the same SELECT.

Expected result/shape: 210 rows on the course data: 7 countries with orders times 6 categories times 5 products. AU Apparel starts with Product 271 at 2,646.48. RANK gives tied products the same rank, so a tie at fifth place would add a sixth row to that group; Exercise 5 shows the deterministic fix.

Learning objectives#

  • Generate hierarchical subtotal levels with ROLLUP and distinguish them from all-combination CUBE output.
  • Rank deterministic top products within several dimensions.

Vocabulary and concepts#

  • ROLLUP: hierarchical grouping sets from detail through grand total.
  • CUBE: every grouping-key subset for the supplied dimensions.
  • GROUPING flag: an indicator separating generated subtotal NULLs from data NULLs.

Worked example / walkthrough#

Compare ROLLUP(country, category) with CUBE(country, category). Both include detail, country subtotal, and grand total; CUBE also adds category-only subtotals. Use GROUPING(country) and GROUPING(category) to label each level, then reconcile the grand total with source line revenue.

Common mistakes and how to recover#

  • Lesson-specific semantic mistake: A raw payment join fans out split-payment orders. Keep the declared primary method policy, or document a different allocation, before using that dimension.
  • Grand total larger than the line revenue: you joined payments before reducing it to one method per order. Compare SUM(revenue) from line with a plain line-revenue sum; they must both be 2,355,647.12 (rounded).
  • Subtotal rows treated as missing data: a blank country with g_country = 1 is the generated total; test GROUPING(...), never country IS NULL, before labeling it.
  • Six rows in a top-five group: RANK repeats a rank on ties. Use ROW_NUMBER() with product_id as the last sort key when the report promises exactly five.
  • General recovery steps (fanout, unexpected NULL, psql stopping) are in the study guide.

Self-check#

  • Is payment method reduced to one declared row per order before joining lines?
  • Does top-five ranking partition by every requested dimension and break ties deterministically?

Deep dive and reference#

Project focus#

  • Generate hierarchical subtotals with ROLLUP.
  • Compare hierarchical subtotal rows with all-combination CUBE.
  • Rank top products within country, category, and order status.

How the learner script uses the current schema#

The starter builds line revenue from orders, customers, order_items, and products, chooses one primary payment method per order by greatest paid amount (method name breaks ties), and rolls up country, category, payment method, and month. Unpaid orders receive the unpaid label. GROUPING(column) distinguishes subtotal nulls from detail values.

It separately ranks product revenue within (country, category).

Practice map#

Exercises 1, 3 and 4 explore which grouping sets ROLLUP and CUBE emit and how to name them, Exercises 2 and 5 make the top-five drill-down exact, and Exercise 6 keeps a stored unknown apart from the generated ALL row. The numbered list above is the contract, repeated unchanged in the learner SQL.

BI reasoning#

  • ROLLUP(a, b) returns (a,b), (a), and grand total.
  • CUBE(a, b) also returns the (b) subtotal.
  • Use GROUPING flags when real dimension nulls are possible.
  • Aggregate revenue before ranking; use ROW_NUMBER plus product_id for exactly five deterministic results.

Validation and limits#

  • A raw payment join fans out split-payment orders. Keep the declared primary method policy, or document a different allocation, before using that dimension.
  • Cube row counts grow rapidly with dimensions and distinct values.
  • Reconcile grand-total cube revenue to source line revenue.

Clause-by-clause reading map#

Read each query in the logical clause order. In this lesson the decisive clause is almost always GROUP BY: plain columns give one grain, ROLLUP gives a hierarchy of grains, CUBE gives every combination and GROUPING SETS lists them by hand. Whenever several grains share one result, look for the GROUPING(...) expression in the SELECT list that labels them, and check that the ORDER BY uses it.

The two worked exercises compare ROLLUP and CUBE, then add order status to a country/category/product top-five drill-down; Exercises 3 to 6 label levels, cap the drill-down at exactly five rows and protect real unknown members. See day55_solutions.sql.

Exercise 1: Compare row counts#

WITH line AS (
  SELECT
    c.country,
    p.category,
    oi.unit_price * oi.quantity * (1 - oi.discount) AS revenue
  FROM
    orders o
    JOIN customers c USING (customer_id)
    JOIN order_items oi USING (order_id)
    JOIN products p USING (product_id)
),
rollup_rows AS (
  SELECT
    country,
    category,
    SUM(revenue) AS revenue
  FROM
    line
  GROUP BY
    ROLLUP (country,
    category)
),
cube_rows AS (
SELECT
  country,
  category,
  SUM(revenue) AS revenue
  FROM
    line
  GROUP BY
    CUBE (country,
    category))
  SELECT
    (
      SELECT
        COUNT(*)
      FROM
        rollup_rows) AS rollup_row_count,
  (
    SELECT
      COUNT(*)
    FROM
      cube_rows) AS cube_row_count;

Expected shape: one comparison row. CUBE(country, category) adds category-only subtotals that the hierarchical ROLLUP(country, category) omits, so its count is greater on this seed.

Reasoning and verification#
  • Inputs/evidence: For sql-55 Exercise 1, join orders, customers, order_items, and products into one revenue line per order item (13,085 lines carrying country and category), group those lines once with ROLLUP (country, category) and once with CUBE (country, category), and count the rows each grouping produces.
  • Expected result/shape: For sql-55 Exercise 1, expected output: one row with rollup_row_count 50 and cube_row_count 56. Both share the 42 country and category detail rows, the 7 country subtotals, and the grand total; the 6 extra CUBE rows are the category-only subtotals. BR has no orders, so it appears in neither grouping.
  • Independent verification: For sql-55 Exercise 1, rebuild both counts from distinct values: 42 distinct (country, category) pairs plus 7 countries plus 1 total gives 50, and adding the 6 categories gives 56. In a rolled-back transaction, give BR customer 8 one order with a single Apparel line: both counts rise by 2 (52 and 58), one BR detail row and one BR subtotal, while the category-only subtotal count stays 6.
  • Intermediate relation check: Run line alone and confirm it has one row per order line, then run rollup_rows and cube_rows separately. On the course data they return 50 and 56 rows: 42 detail pairs, 7 country subtotals and 1 grand total in both, plus 6 category-only subtotals in the cube.
  • Clause check: The only difference between the two CTEs is ROLLUP versus CUBE in GROUP BY. The outer SELECT has no FROM of its own; two scalar subqueries each count one CTE, which is why the result is a single row with two columns.
  • Alternative/trade-off: SELECT 'rollup', count(*) FROM rollup_rows UNION ALL SELECT 'cube', count(*) FROM cube_rows gives the same numbers as two labeled rows. It is easier to extend to more variants, but it no longer matches the one-row, two-column contract.
  • Edge case: If a new country appeared with orders in only one category, the rollup would gain two rows (detail and country subtotal) and the cube would gain the same two, because its category subtotal already exists.

Exercise 2: Status-aware top five#

SET search_path TO training, public;

WITH line AS (
  SELECT
    c.country,
    p.category,
    o.status,
    p.product_id,
    p.name,
    oi.unit_price * oi.quantity * (1 - oi.discount) AS revenue
  FROM
    orders o
    JOIN customers c USING (customer_id)
    JOIN order_items oi USING (order_id)
    JOIN products p USING (product_id)
),
product_revenue AS (
  SELECT
    country,
    category,
    status,
    product_id,
    name,
    SUM(revenue) AS revenue
  FROM
    line
  GROUP BY
    country,
    category,
    status,
    product_id,
    name
),
ranked AS (
  SELECT
    *,
    ROW_NUMBER() OVER (PARTITION BY country,
      category,
      status ORDER BY revenue DESC,
      product_id) AS product_rank
  FROM
    product_revenue
)
SELECT
  country,
  category,
  status,
  product_id,
  name,
  ROUND(revenue, 2) AS revenue,
  product_rank
FROM
  ranked
WHERE
  product_rank <= 5
ORDER BY
  country,
  category,
  status,
  product_rank;

Expected grain: up to five rows per (country, category, status).

Reasoning and verification#
  • Inputs/evidence: For sql-55 Exercise 2, sum line revenue (unit_price * quantity * (1 - discount)) per country, category, status, product_id, and name (7,566 product rows), then number the products inside each (country, category, status) group with ROW_NUMBER() ordered by revenue DESC, product_id and keep numbers 1 to 5.
  • Expected result/shape: For sql-55 Exercise 2, expected output: 1,050 rows, exactly five for each of the 210 (country, category, status) groups (7 countries, 6 categories, 5 statuses, each group holding 30 to 42 products), with columns country, category, status, product_id, name, revenue (rounded to 2 places), and product_rank. The final order is country, category, status, product_rank; the first group is AU, Apparel, delivered, led by product 241 at 793.36.
  • Independent verification: For sql-55 Exercise 2, check that AU, Apparel, delivered lists products 241, 223, 163, 121, and 97 (793.36 down to 727.36), with product 109 sixth at 651.77, and that no (country, category, status, product_id) repeats. In a rolled-back transaction, add a 150.00 line for product 109 to AU order 47 (delivered): product 109 moves to rank 1 at 801.77, product 97 drops out, and the group still returns five rows.
  • Intermediate relation check: line is at order-line grain; product_revenue must be unique on (country, category, status, product_id), which you can prove by comparing its count(*) with a count(DISTINCT (country, category, status, product_id)). ranked keeps that row count and only adds product_rank.
  • Clause check: PARTITION BY country, category, status restarts the numbering for each of the 210 groups, and ORDER BY revenue DESC, product_id breaks revenue ties by id. The outer WHERE product_rank <= 5 then keeps at most five rows per group.
  • Alternative/trade-off: A LATERAL subquery with ORDER BY revenue DESC, product_id LIMIT 5 per (country, category, status) gives the same rows. It reads naturally as "top five for each group" but needs a separate list of groups to drive it.
  • Edge case: A status group with fewer than five sold products would return fewer rows rather than padding; on this data all 210 groups are full, so the result has exactly 1,050 rows.

Reasoning, safety, and pitfalls#

  • CUBE grows quickly: three dimensions produce up to eight grouping sets, before considering the number of distinct dimension values.
  • NULL can mean a subtotal or a real null dimension value. Include GROUPING(...) flags in user-facing subtotal reports when ambiguity exists.
  • Aggregate product revenue before ranking.
  • ROW_NUMBER plus product_id yields exactly five deterministic rows when at least five products exist; RANK can return more because of ties.

Exercise 3: Enumerate ROLLUP levels#

PostgreSQL's GROUPING(country, category) returns a bit mask: detail, country subtotal, and grand total have stable numeric identities.

Reasoning and verification#
  • Inputs/evidence: For sql-55 Exercise 3, first write down the grouping sets of ROLLUP (country, category, month) (4 sets, from full detail to the grand total) and of CUBE on the same columns (8 sets), then run ROLLUP (country, category) over the order-item revenue lines and expose GROUPING (country, category) as grouping_mask.
  • Expected result/shape: For sql-55 Exercise 3, expected output: 50 rows with columns country, category, revenue, and grouping_mask, ordered by grouping_mask, country, category: 42 detail rows with mask 0 (AU Apparel 54,277.4215), 7 country subtotals with mask 1 (AU 330,947.6960), and 1 grand total with mask 3 (2,355,647.1235). No row has mask 2, because ROLLUP never totals a category across countries.
  • Independent verification: For sql-55 Exercise 3, count the rows per mask (42, 7, 1) and confirm that the 7 mask 1 rows add up to the mask 3 total of 2,355,647.1235. In a rolled-back transaction, give BR customer 8 one order with a 20.00 Apparel line: the result grows to 52 rows (43 with mask 0, 8 with mask 1), and BR shows 20.0000 at both the detail and subtotal level.
  • Intermediate relation check: line has no GROUP BY; it is one row per order line with country, category and unrounded line revenue. Count it, then run the final query without ORDER BY and group its output by grouping_mask: you should see 42 rows with mask 0, 7 with mask 1 and 1 with mask 3, and the mask 0 rows for AU should add up to AU's mask 1 row of 330,947.70.
  • Clause check: GROUPING(country, category) reads the two arguments as bits, country first, so 1 means only category was rolled away and 3 means both were. ROLLUP (country, category) never drops country while keeping category, which is why mask 2 cannot appear.
  • Alternative/trade-off: Writing GROUPING SETS ((country, category), (country), ()) produces the same 50 rows and makes the hierarchy explicit; ROLLUP is the shorter spelling of exactly that list.
  • Edge case: The grand total row (mask 3, revenue 2355647.1235) must equal the sum of the 42 detail rows; if it does not, the line revenue was computed differently in the two places. Because ORDER BY grouping_mask comes first, the total is the last row, the reverse of Example 1, where NULLS FIRST put it on top.

Exercise 4: Label levels from the bit mask#

The display label is derived from that mask, not from column IS NULL. This keeps machine-readable level identity beside human-readable text.

Reasoning and verification#
  • Inputs/evidence: For sql-55 Exercise 4, group the same order-item revenue lines with ROLLUP (country, category) and return GROUPING (country, category) as level_id, plus a CASE on that same mask that maps 0, 1, and 3 to level_name values 'country/category detail', 'country subtotal', and 'grand total'.
  • Expected result/shape: For sql-55 Exercise 4, expected output: the same 50 rows as Exercise 3 with columns level_id, level_name, country, category, and revenue, ordered by level_id, country, category: 42 rows at level 0, 7 at level 1, and 1 at level 3, and no NULL level_name.
  • Independent verification: For sql-55 Exercise 4, count rows per level_id and level_name (42, 7, 1) and confirm each level_id maps to exactly one name. In a rolled-back transaction, run ALTER TABLE products ALTER COLUMN category DROP NOT NULL and set product 241's category to NULL: level 0 grows to 49 rows, 7 of them with a stored NULL category, and all 7 still say 'country/category detail' because the label reads the mask, not the column.
  • Intermediate relation check: Use the same line CTE as Exercise 3 (no payments, so no fan-out) and confirm the 50-row output carries only level_id values 0, 1 and 3. Then compare it row by row with Exercise 3: the country, category and revenue columns are identical, and only the two label columns at the front are new.
  • Clause check: The CASE GROUPING (country, category) expression maps each mask to a readable level_name, while level_id keeps the raw mask for code that filters or joins on it. Both come from GROUPING, not from testing country IS NULL, so a future customer with a stored NULL country could never be mislabeled as a subtotal.
  • Alternative/trade-off: A small VALUES lookup of (mask, name) joined on level_id would work too and keeps names in one place if several reports share them; the inline CASE is simpler for three levels.
  • Edge case: Switching the GROUP BY to CUBE would emit six mask 2 rows (category totals across all countries), and this CASE has no branch for them, so their level_name would be NULL and they would sort between the country subtotals and the grand total. Add a WHEN 2 branch before changing the grouping.

Exercise 5: Return exactly five products#

Revenue aggregates before ranking. ROW_NUMBER with product_id as final key limits every partition deterministically even when revenue ties.

Reasoning and verification#
  • Inputs/evidence: For sql-55 Exercise 5, sum order-item revenue per country, product_id, and name (1,925 rows, 275 products in each of 7 countries), then number the products inside each country with ROW_NUMBER() ordered by revenue DESC, product_id as position and keep positions 1 to 5.
  • Expected result/shape: For sql-55 Exercise 5, expected output: 35 rows, one per country and position 1 to 5, with columns country, product_id, name, revenue, and position. The final order is country, position; AU starts with product 238 at 3,319.3310, followed by products 207, 251, 261, and 243 (2,692.5745).
  • Independent verification: For sql-55 Exercise 5, confirm that no (country, product_id) repeats and that AU product 233 sits sixth at 2,684.2590.   • Intermediate relation check: revenue holds one row per (country, product) and ranked adds position without changing that count. The final result has 35 rows, five for each of the seven countries with orders. The rows are products, not orders: the columns are country, product_id, name, revenue and position, and the check for duplicates is on (country, product_id).
  • Clause check: ROW_NUMBER() OVER (PARTITION BY country ORDER BY revenue DESC, product_id) gives every product a distinct position, so WHERE position <= 5 can never return six rows even when two products tie on revenue.
  • Alternative/trade-off: RANK() with the same window would keep tied products together but may return more than five rows; choose it only if the report promises "all products at the top five revenue levels".
  • Edge case: If products 238 and 207 in AU had equal revenue, ROW_NUMBER would place 207 first because of the product_id tie-breaker, and the order would stay the same on every run.

Exercise 6: Preserve unknown versus ALL#

  GROUPING (country, category) AS level_id,
  CASE GROUPING (country, category)
  WHEN 0 THEN
    'country/category detail'
  WHEN 1 THEN
    'country subtotal'
  WHEN 3 THEN
    'grand total'
  END AS level_name,
  country,
  category,
  SUM(revenue) AS revenue
FROM
  line
GROUP BY
  ROLLUP (country, category)
ORDER BY
  level_id,
  country,
  category;

-- Exercise 5: ROW_NUMBER and product_id as the final sort key guarantee no more
-- than five deterministic products per group even when revenue ties.
WITH revenue AS (
  SELECT
    c.country,
    p.product_id,
    p.name,
    SUM(oi.quantity * oi.unit_price * (1 - oi.discount)) AS revenue
  FROM
    orders o
    JOIN customers c USING (customer_id)
    JOIN order_items oi USING (order_id)
    JOIN products p USING (product_id)
  GROUP BY
    c.country, p.product_id, p.name
),
ranked AS (
  SELECT
    *,
    ROW_NUMBER() OVER (PARTITION BY country ORDER BY revenue DESC,
      product_id) AS position
  FROM
    revenue
)
SELECT
  *
FROM
  ranked
WHERE
  position <= 5
ORDER BY
  country,
  position;

-- Exercise 6: grouping flag and stored-member label are separate columns, so
-- a real unknown value can never masquerade as the ALL subtotal.
SELECT
  CASE WHEN GROUPING (country) = 1 THEN
    'ALL'
  ELSE
    COALESCE(country, '(unknown member)')
  END AS display_country,
  GROUPING (country) AS is_generated_total,
  COUNT(*) AS customers
FROM
  customers
GROUP BY
  GROUPING SETS ((country),
    ())
ORDER BY
  is_generated_total,
  display_country;
