# go-001: From source text to a checked Go program

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: No previous Go knowledge. Read source as plain text and distinguish editing from executing.

## Learning objectives

By the end, explain package, entrypoint, assertion; implement the six investigations below; and defend the expected result of a changed input before running it. A passing reference is evidence about that program, not a certification of your independent understanding.

## Why this mechanism matters

A Go program is source text organized into packages. A runnable executable needs package main and a function named main with no arguments or return values. The compiler checks names and types before any statement executes. A successful build creates machine code for a particular operating system and processor architecture; the source file itself is not the executable. Inside a single goroutine, statements follow the program's control flow. Printing a reassuring message proves only that a print statement ran. A useful reference instead computes a result and checks an independently known expectation. This distinction becomes important when later lessons contain cancellation, partial failure and distributed state.

## Vocabulary and concepts

- **Package:** A collection of source files compiled together.
- **Entrypoint:** The function invoked when this executable starts.
- **Assertion:** An explicit check of a claimed program property.

## Syntax anatomy and reasoning

package declares the compilation unit's package. import makes another package available under a name such as fmt. func main() declares the entrypoint; braces delimit its body. A short declaration with := creates a variable and infers its type. fmt.Sprintf constructs text while fmt.Println writes it. Go inserts many semicolons automatically, so keep an opening brace on the declaration line. The helper check(condition, message) panics on false; its message should identify the broken claim.

## Worked example / walkthrough

### Worked example 1: Predict a first value

Bind greeting to Hello, Go and check its exact text.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Predict a first value
	{
		greeting := "Hello, Go"
		check(greeting == "Hello, Go", "greeting")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** greeting equals Hello, Go.

The quotes delimit a string literal; they are not part of the stored value. Matching the exact text catches a changed greeting even if printing would still look reasonable.

### Worked example 2: Compute before formatting

Add 2 and 3, then format total=5.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Predict a first value
	{
		greeting := "Hello, Go"
		check(greeting == "Hello, Go", "greeting")
	}

	// Compute before formatting
	{
		total := 2 + 3
		line := fmt.Sprintf("total=%d", total)
		check(total == 5 && line == "total=5", "format")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The integer is 5 and the text is total=5.

The arithmetic result and its presentation are separate values. %d formats a decimal integer, and a wrong formatting verb can produce diagnostic text rather than the intended representation.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
