# k8s-052: LoadBalancer Services: cloud controllers and local limitations

## Level and prerequisites

Intermediate; about 120 minutes. Direct prerequisites: `k8s-051`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Draw both node-backed and direct-Pod conceptual paths.
- Plan a local versus cloud qualification.

## Purpose, vocabulary and mental model

A load balancer distributes traffic among eligible destinations. A Kubernetes Service of type LoadBalancer asks an integrated implementation to provision or configure an external entrypoint. The API object is a request; a controller and supporting infrastructure must exist to fulfill it.

In a cloud, the controller may create provider resources, addresses, listeners and health checks. A local cluster may have no such integration and leave the external address pending. Local load-balancer implementations have their own routing and address-allocation requirements. The course does not install one or incur cloud resources automatically.

Load balancing is not a database replication mechanism, a certificate authority or application authorization. A reachable address can still route to unready nodes, wrong ports or an app that returns errors. Diagnose controller status, infrastructure health and actual request behavior separately.

### Key terms

- **LoadBalancer Service:** A Service type that asks a cloud integration for an external load balancer in front of the Service.
- **Cloud controller:** The component that talks to the provider to create load balancers and writes their address to status.loadBalancer.
- **Load balancer health check:** The provider's probe of nodes or backends that decides where external traffic is sent.
- **Pending external address:** A LoadBalancer Service with no address in status.loadBalancer yet, often because no controller can provision one.

## Mechanism and field-by-field reasoning

Inspect Service spec.type, loadBalancerClass when used, traffic policy, ports and status.loadBalancer.ingress. An ingress entry can contain an IP or hostname. Do not assume status arrives immediately or that a returned hostname resolves from every network.

Many implementations use NodePorts, while others can route directly to Pods or use alternate mechanisms. The allocation and routing design is implementation-specific. Changing allocateLoadBalancerNodePorts without knowing the implementation can remove a required path.

## Trace the request or control path

```text
Service intent -> load-balancer controller -> provider/local infrastructure
client -> external listener -> node or Pod backend path -> application
```

The top line is a request for infrastructure: a controller outside the core reads the Service and asks a cloud provider, or a local implementation, for an address. The bottom line is what a client then traverses. An address in Service status covers only the top line; the listener, health checks, backend path and application each need their own evidence.

## Worked example / walkthrough

### Worked example 1: Interpret pending external status

This is a synthetic local-cluster observation.

```text
spec.type=LoadBalancer
status.loadBalancer.ingress=[]
no load-balancer controller is prepared
```

**Expected observation:** Pending status is an unavailable capability, not proof that the app container is broken.

### Worked example 2: Separate listener and application acceptance

A sequence of increasingly strong observations.

```text
external address assigned -> listener reachable -> healthy backend selected
-> expected HTTP route -> expected application body
```

**Expected observation:** Address allocation alone does not establish the final result.

## Six progressive exercises

### Exercise 1: Predict a LoadBalancer Service on an unsupported local cluster.

**Expected evidence:** The requested external entrypoint may remain unprovisioned.

**Progressive hint:** Ask which component would fulfil the request on this cluster. Is one installed at all?

### Exercise 2: Name the controller and infrastructure responsibilities.

**Expected evidence:** Reconcile the request and provision actual routing resources.

**Progressive hint:** Split the work into deciding and doing: one part watches the Service, the other owns the real network resources.

### Exercise 3: Draw both node-backed and direct-Pod conceptual paths.

**Expected evidence:** The implementation choice is explicit rather than assumed.

**Progressive hint:** After the external listener, draw two variants: one stops at a node, the other goes straight to a Pod address.

### Exercise 4: Diagnose assigned address with no successful requests.

**Expected evidence:** Inspect listener, health checks, backend route and app behavior.

**Progressive hint:** Walk the bottom line of the diagram one arrow at a time. The address proves only that the first arrow exists.

### Exercise 5: Explain load-balancer health versus Pod readiness.

**Expected evidence:** Infrastructure health and Kubernetes endpoint eligibility can test different things.

**Progressive hint:** List what the provider's health check requests and what the kubelet's readiness probe requests. Are they the same?

### Exercise 6: Plan a local versus cloud qualification.

**Expected evidence:** Named implementation, owned resources, cost/cleanup boundary and real request evidence.

**Progressive hint:** For each environment, name the implementation, who pays and cleans up, and the request that proves success.

## Diagnosis, failure boundaries and common mistakes

A pending external address on a local cluster sends people into application logs, but the app is irrelevant until a controller exists. Report the capability as unavailable instead of installing one on a shared machine. The opposite trap is celebrating once an address appears: the provider's health check may target nodes that have no local ready endpoint, or a firewall may block the listener. Cloud load balancers also cost money and can outlive the lesson when cleanup is skipped, so record the provider resource's identity at creation and remove it through the owning Service, not by hand in a console.

Before concluding, record:

- The Service `status.loadBalancer.ingress` field, empty or filled, and the time you read it.
- The name of the load-balancer controller that should act, or a plain statement that none is installed.
- For an assigned address: the listener port, the provider health check target and its reported backend state.
- One real request result against the external address, kept separate from any Pod readiness reading.

General evidence rules: [diagnosis rules](../STUDY-GUIDE.md#diagnosis-rules).
