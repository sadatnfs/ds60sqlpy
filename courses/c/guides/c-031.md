# c-031: Checked arithmetic and allocation-size contracts

## Level and prerequisites

Advanced, approximately 120 minutes plus a later retrieval session. Direct prerequisites: `c-030`

## Learning objectives

## Purpose and mental model

Integer overflow is often a memory-safety defect in disguise. A wrapped allocation size can reserve less storage than later code assumes, and signed overflow cannot safely be used as the condition that detects itself. Validate before the operation using inequalities whose own arithmetic is defined. Keep signed value arithmetic separate from size_t storage arithmetic, and validate conversions at their boundary. The chosen failure policy should preserve outputs and let callers distinguish overflow from a legitimate zero. Compiler overflow builtins can be useful, but portable C17 logic remains worth understanding before depending on a toolchain extension.

## Vocabulary and concepts

- **Precondition check:** A condition established before a potentially invalid operation.
- **Checked arithmetic:** Arithmetic that reports range failure explicitly.
- **Conversion boundary:** A point where values move between representations with different ranges.

## Syntax anatomy and execution trace

For a positive addend b, a+b fits int only when a<=INT_MAX-b. For a negative b, require a>=INT_MIN-b. For size_t multiplication, if b is nonzero require a<=SIZE_MAX/b. Check output pointers before writing. These preconditions avoid evaluating the dangerous expression until its validity is established. A zero multiplier is a valid mathematical case, even when an allocator wrapper later rejects zero-sized storage by policy.

## Worked example / walkthrough

### Worked example 1: Add ordinary values

Add 7 and 5 through the checked helper.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

bool add_checked(int a, int b, int *out) {
  if (out == NULL || (b > 0 && a > INT_MAX - b) || (b < 0 && a < INT_MIN - b))
    return false;
  *out = a + b;
  return true;
}
bool size_product(size_t a, size_t b, size_t *out) {
  if (out == NULL || (b != 0 && a > SIZE_MAX / b))
    return false;
  *out = a * b;
  return true;
}

int main(void) {
  /* Add ordinary values */
  {
    int out = 0;
    CHECK(add_checked(7, 5, &out) && out == 12);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** The result is 12.

The normal case uses the same guarded path as boundary cases.

### Worked example 2: Reject positive overflow

Add one to INT_MAX.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

bool add_checked(int a, int b, int *out) {
  if (out == NULL || (b > 0 && a > INT_MAX - b) || (b < 0 && a < INT_MIN - b))
    return false;
  *out = a + b;
  return true;
}
bool size_product(size_t a, size_t b, size_t *out) {
  if (out == NULL || (b != 0 && a > SIZE_MAX / b))
    return false;
  *out = a * b;
  return true;
}

int main(void) {
  /* Add ordinary values */
  {
    int out = 0;
    CHECK(add_checked(7, 5, &out) && out == 12);
  }

  /* Reject positive overflow */
  {
    int out = 9;
    CHECK(!add_checked(INT_MAX, 1, &out) && out == 9);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** The operation fails and preserves output.

The addition itself is never evaluated after the precondition fails.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
