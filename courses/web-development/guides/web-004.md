# web-004: Links, paths, navigation and usable destinations

## Level and prerequisites

Beginner; allow about 90 minutes, with extra time for independent practice. Direct prerequisites: `web-003`

## Learning objectives

Build a contents list that navigates to three local sections. Explain the difference between absolute, root-relative and document-relative paths. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A URL identifies a resource and can contain a scheme, host, path, query and fragment. A relative path is resolved against a base URL; it is not resolved against the author's mental picture of a folder. A fragment such as #methods identifies a location within the current document and does not require another document to exist. An anchor with href provides navigation semantics and keyboard behavior automatically.

Good link text tells a reader the destination or action. A page full of links named click here loses meaning when links are read as a list. A link navigates; a button changes application state or submits an action. Styling a paragraph blue does not create link behavior, and adding a click listener does not automatically provide keyboard support.

## Syntax anatomy and mechanism

Use `href="#details"` with a unique `id="details"` for this offline lesson. A leading slash means a path from the origin root, while `../` moves one directory upward relative to the base path. Production external links may need a new-window notice and suitable rel values; do not open new tabs by default merely to keep a user on your site.

## Classroom execution and offline inputs

Choose **HTML browser preview** in the classroom. The pad is one complete HTML document with embedded CSS and, where taught, embedded JavaScript. Its preview is isolated from the classroom and recreated on each run. It does not contact a server, submit real forms, read cookies, fetch assets or load a CDN. All fixtures are inline and synthetic. The browser uses its native HTML parser, so classic-script ordering, shared lexical bindings, inline modules and real DOMContentLoaded/load events keep their browser semantics. External module imports remain blocked. Navigation metadata such as base and meta http-equiv is rejected explicitly. On any supported host, the browser renders the document while Docker serves the classroom. No host compiler is needed.

Run your own source after implementing the task. A reference's checks inspect only the named initial conditions. Its success message is not a full accessibility audit, proof of responsive behavior at every size, or evidence that you implemented the solution yourself. Inspect actual output after keyboard input, resizing and changes. Save your source before comparing with a reference. For visual experiments, explicitly turn on Live preview: the page refreshes after a short pause in typing, while Pause updates keeps the last rendered version and Stop preview cancels pending refreshes. Desktop, tablet and phone presets resize the same preview without rerunning it. Automatic previews do not create saved runs; choose Save observation or Run when you want to retain an exact source-and-output record. Changing lessons, opening history or reloading turns live execution off. The document and its CSS share one saved pad; HTML and CSS remain different languages within that artifact.

## Worked example / walkthrough

### Worked example 1: Within-page navigation

A fragment is enough for a self-contained document.

```html
<a href="#methods">Read the methods</a>
<section id="methods"><h2>Methods</h2></section>
```

**Expected observation:** The navigation target is the methods section.

### Worked example 2: Link versus button

Choose the element before its styling.

```html
<a href="#results">View results</a>
<button type="button">Toggle details</button>
```

**Expected observation:** The link navigates; the button requires an implemented action.

## Six progressive exercises

### Exercise 1: Resolve ../images/plot.svg from /notes/week1/page.html.

**Expected evidence:** The resolved path is /notes/images/plot.svg on the same origin.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Replace vague link text with destination-specific wording.

**Expected evidence:** The link makes sense outside its surrounding sentence.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a contents list that navigates to three local sections.

**Expected evidence:** Every fragment matches one unique section id and works with keyboard activation.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a link whose fragment has no matching id.

**Expected evidence:** The link has no intended target even if its visual style looks correct.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Distinguish a disabled action from an unavailable destination.

**Expected evidence:** A button can be disabled; a meaningful alternative explanation should replace a dead link.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain the difference between absolute, root-relative and document-relative paths.

**Expected evidence:** Each has a distinct base and can resolve differently when the document moves.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not test relative paths only from an editor preview with a special base. Avoid `href="#"` as a fake action. The classroom sandbox blocks external network behavior deliberately; use local fragments here.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain URL, relative path, fragment without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
