c-034: POSIX descriptors, pipes and explicit endpoint closure#

Level and prerequisites#

Advanced, approximately 120 minutes plus a later retrieval session. Direct prerequisites: c-033

Learning objectives#

Explain file descriptor, pipe endpoint, descriptor ownership. Implement the six investigations with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

Purpose and mental model#

POSIX file descriptors are small integer handles to open resources. They are not FILE pointers, and their read/write operations do not use the same buffering contract. A pipe provides a byte stream from one endpoint to another. Reads can be short, and EOF occurs only after all write endpoints are closed and buffered bytes are consumed. Forgetting an inherited or duplicated write endpoint can make a reader wait forever. Every descriptor needs a known owner and close point. These examples create only local anonymous pipes and close them within each case; they never open host paths or contact a network.

Vocabulary and concepts#

  • File descriptor: A process-local integer handle to an open POSIX resource.
  • Pipe endpoint: One read or write side of a byte stream.
  • Descriptor ownership: Responsibility for closing each acquired handle.

Syntax anatomy and execution trace#

pipe fills two descriptors: index zero reads and index one writes. read and write return ssize_t, with negative values indicating errors. A robust general loop handles EINTR and partial transfers under a total byte budget. close releases one descriptor reference. dup creates another reference to the same underlying open description, so closing one reference does not necessarily end the stream. POSIX APIs are platform extensions, not ISO C17 itself.

Worked example / walkthrough#

Worked example 1: Transfer a small pipe payload#

Write abc, close the writer and read the bytes.

#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/types.h>
#include <unistd.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int main(void) {
  /* Transfer a small pipe payload */
  {
    int fds[2];
    CHECK(pipe(fds) == 0);
    CHECK(write(fds[1], "abc", 3) == 3);
    CHECK(close(fds[1]) == 0);
    char out[4] = {0};
    CHECK(read(fds[0], out, 3) == 3 && strcmp(out, "abc") == 0);
    CHECK(close(fds[0]) == 0);
  }
  puts("Worked example checks passed.");
  return 0;
}

Observe: Three bytes arrive unchanged.

The tiny write is within the pipe atomic-write bound. General streams still require loops for partial operations.

Worked example 2: Observe EOF after closure#

Close an unused writer and read from its empty pipe.

#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/types.h>
#include <unistd.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int main(void) {
  /* Transfer a small pipe payload */
  {
    int fds[2];
    CHECK(pipe(fds) == 0);
    CHECK(write(fds[1], "abc", 3) == 3);
    CHECK(close(fds[1]) == 0);
    char out[4] = {0};
    CHECK(read(fds[0], out, 3) == 3 && strcmp(out, "abc") == 0);
    CHECK(close(fds[0]) == 0);
  }

  /* Observe EOF after closure */
  {
    int fds[2];
    CHECK(pipe(fds) == 0);
    CHECK(close(fds[1]) == 0);
    char byte = 0;
    CHECK(read(fds[0], &byte, 1) == 0);
    CHECK(close(fds[0]) == 0);
  }
  puts("Worked example checks passed.");
  return 0;
}

Observe: read returns zero.

Zero is EOF for this positive-sized read, not an error. All writers are closed before waiting.

Common pitfalls and diagnosis#

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path.
