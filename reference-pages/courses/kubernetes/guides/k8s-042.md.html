k8s-042: Capstone 3: platform release and incident review#

Level and prerequisites#

Advanced; about 300 minutes plus review. Direct prerequisites: k8s-030, k8s-031, k8s-033, k8s-034, k8s-038, k8s-039, k8s-041. The chapter separates desired configuration, API acceptance, controller observation and application evidence.

Learning objectives#

Defend an end-to-end Kubernetes change and recovery story within a bounded owned environment.

Vocabulary and concepts#

The final capstone is a reviewable release and recovery story. A policy-compliant custom resource expresses intent; a qualified controller creates owned child resources; the application responds correctly; the data contract holds; a bounded incident is diagnosed and repaired; and the owned environment is cleaned without disturbing unrelated resources. No single green status represents that entire chain.

Use the LessonReport API from k8s-029 and the reconciliation contract from k8s-030. The host must supply the exact CRD/controller, admission, metrics, traffic and storage/recovery capabilities used by the selected scenario. The normal browser adapter does not provide them. Begin with the complete offline evidence packet and explicitly mark live gates unavailable until their corresponding capability receipts exist.

The learner acts as both implementer and reviewer: first predict the expected observations, then compare actual evidence, then challenge the weakest conclusion. The capstone is not a license to install arbitrary operators, change cluster policy or choose another context. Privileged actions remain fixed host operations in an exclusive owned lease, with separate receipts and stop conditions.

Design the release packet before execution#

The packet starts with desired manifests, rendered artifact hashes, qualified image identity, prerequisite capability receipts and exact cluster/namespace ownership. It states which source fields are learner-controlled and which host identities are fixed. A manifest accepted by a schema is only the first gate.

Next define controller convergence: expected parent UID/generation, owned child graph, observed generation and application marker. Define admission and authorization controls separately, including one policy-specific denial and one permitted request. Define finite release samples and the rollback selector or desired-state restoration point. Do not turn a read-only signature check into an assumed cluster enforcement guarantee.

For autoscaling or storage, include only the scenario's qualified capabilities. An HPA source without metrics is not a completed scaling activity. A PVC object without a verified marker is not durable-data acceptance. If a capability is missing, the packet should make that gap visible instead of silently substituting a toy model for live execution.

Connect incident response to recovery objectives#

Choose one teacher-selected, host-allowlisted fault with a known restoration procedure. Capture the pre-fault baseline and preserve a timestamped investigation. The learner must explain why the selected observation distinguishes hypotheses and why the repair is scoped to the observed cause.

If the scenario requires restoration, measure recovery using the definitions from k8s-041. Keep service acceptance, data hash and durability points distinct. A repaired route with wrong data fails; correct data behind a broken Service also fails. The negative control should omit one required gate and prove the final acceptance function rejects the incomplete packet.

After recovery, review authorization and ownership again. Operational pressure is a common reason to widen permissions or bypass policy. This capstone succeeds only if the recovery story preserves the declared boundary or explicitly records a controlled host action with its own authorization and receipt.

Worked example / walkthrough#

Worked example 1: Trace one intended release#

LessonReport hello-report requests reviewer and2 replicas. The packet records parent UID p1, generation 3, child owner p1, observedGeneration 3, two ready replicas and four reviewer responses. These are synthetic teaching values until read from the qualified runtime.

Expected: The joined fields form a coherent convergence hypothesis. Copying them into a worksheet does not create a runtime receipt.

Worked example 2: Reject an attractive incomplete packet#

API pass, controller pass, application pass, authorization pass, recovery service pass, but data hash wrong and cleanup unknown. Even with every Pod Ready, the final gate fails. After independent data verification and owned cleanup receipts pass, the complete synthetic packet can be accepted.

Expected: All required gates must have evidence. Missing or failed data/cleanup rows cannot be replaced by a successful application request.

Inspect the specific owned object#

Only after the chapter's host capability is provisioned and its resources remain present, use the explicit receipt fields described in host-labs.md. A completed one-shot browser Run has already cleaned its objects. The following read does not provision the missing capability and does not justify changing credentials after a Forbidden result.

POSIX:

: "${LAB_KUBECONFIG:?Use the owned receipt path}"
: "${LAB_CONTEXT:?Use the owned receipt context}"
: "${LAB_NAMESPACE:?Use the owned receipt namespace}"
kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" --namespace "$LAB_NAMESPACE" get lessonreports hello-report -o json

PowerShell:

if (-not $env:LAB_KUBECONFIG -or -not $env:LAB_CONTEXT -or -not $env:LAB_NAMESPACE) { throw 'Owned receipt fields are required.' }
& kubectl --kubeconfig $env:LAB_KUBECONFIG --context $env:LAB_CONTEXT --namespace $env:LAB_NAMESPACE get lessonreports hello-report -o json
if ($LASTEXITCODE -ne 0) { throw 'The scoped observation failed.' }

Retain only the fields needed by this chapter's prediction. A NotFound result may be expected after one-shot cleanup; a Forbidden result may identify a deliberately absent advanced capability. Neither result authorizes an ambient-context fallback.

Run and bounded evidence#

The app artifact is a reading worksheet, courses/kubernetes/lessons/k8s-042.md. The current browser adapter does not provide the full exclusive integrated platform/controller/policy/metrics/traffic/storage/recovery lease operation. Use the synthetic fixture and offline check first. Live work follows the scoped host-lab guide only when the named capability and owned target have been provisioned. A worksheet or static check is never a cluster execution receipt.

The manifest example is separate from the learner artifact. The offline reference check evaluates explicitly synthetic facts and makes no API calls. Run it locally with python courses/kubernetes/solutions/k8s-042_checks.py after comparing your attempt. The case ledger is immutable teaching input.

Exercises#

Exercise 1: Prepare the capability and ownership packet#

List exact runtime capabilities, versions, source hashes and owned identities for the selected scenario.

Expected result/shape: Every requested live action has a qualified capability or an explicit unavailable row.

Verify: Retain the named field values, identities, counts, diagnostic or written comparison: Every requested live action has a qualified capability or an explicit unavailable row.

Progressive hints: Do not infer capabilities from manifests.

Exercise 2: Defend desired state and admission#

Review the custom resource and capture permitted and policy-denied controls.

Expected result/shape: Schema, authorization and admission conclusions remain separate.

Verify: Retain the named field values, identities, counts, diagnostic or written comparison: Schema, authorization and admission conclusions remain separate.

Progressive hints: Keep the negative request valid except for the intended policy violation.

Exercise 3: Prove owned convergence and release behavior#

Join parent generation, child ownership, readiness and finite application samples.

Expected result/shape: Current-generation owned resources serve the expected marker through the intended route.

Verify: Retain the named field values, identities, counts, diagnostic or written comparison: Current-generation owned resources serve the expected marker through the intended route.

Progressive hints: A status boolean without identity/generation is incomplete.

Exercise 4: Investigate one bounded incident#

Record baseline, fault, symptom, hypotheses, minimal repair and post-repair response.

Expected result/shape: Timestamped causal explanation with exact target and cancellation/restore behavior.

Verify: Retain the named field values, identities, counts, diagnostic or written comparison: Timestamped causal explanation with exact target and cancellation/restore behavior.

Progressive hints: Use one controlled fault and preserve alternatives.

Exercise 5: Measure service and data recovery#

Apply the stated RTO/RPO definitions and missing-data negative control.

Expected result/shape: Independent service/data gates and recomputable source timestamps/hashes.

Verify: Retain the named field values, identities, counts, diagnostic or written comparison: Independent service/data gates and recomputable source timestamps/hashes.

Progressive hints: Ready alone is insufficient.

Exercise 6: Complete cleanup and review limits#

Collect UID-aware cleanup/release receipts and defend each remaining claim.

Expected result/shape: No unrelated resources removed; missing or failed gates remain visible.

Verify: Retain the named field values, identities, counts, diagnostic or written comparison: No unrelated resources removed; missing or failed gates remain visible.

Progressive hints: An unknown cleanup row is not success.

Self-check#

Explain the mechanism behind the first example, then distinguish it from this boundary case: All required gates must have evidence. Missing or failed data/cleanup rows cannot be replaced by a successful application request. State which observations are synthetic and which, if any, were read from your owned runtime.

Common pitfalls#

Cleanup removes only resources owned by the lease and recorded operation, using UID-aware checks. Retained claims or backups need an explicit policy and protected location. The host releases its exclusive cluster only after finalizers, finite Jobs and data-retention decisions are resolved. A cleanup failure is an outcome to report, not a line to omit.

The final review distinguishes source correctness, offline examples, API acceptance, controller convergence, application/data behavior and lifecycle cleanup. It states the exact versions, architecture and finite observations. A small synthetic capstone does not prove production HA, arbitrary-code isolation, exactly-once external side effects or reliable recurring operation.

A reviewer should be able to point to the evidence for every claimed gate and identify every unavailable capability. That is the practical meaning of a defensible platform change: the conclusion is as specific as the measurements that support it.

Retrieval and transfer#
