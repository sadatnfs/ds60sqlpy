# dbt-009: Keyed updates, lookback windows and idempotency

## Level and prerequisites

Intermediate. Direct prerequisites: `dbt-004`, `dbt-008`

**Outcome:** Implement a keyed incremental contract with tested boundary and repeat-run behavior.

## Question and mechanism

A keyed incremental strategy can replace records whose identity is already present. A lookback window can revisit recent source records so corrections and bounded late arrivals are considered. Together, these mechanisms address some weaknesses of a pure append watermark. They still require a valid key, deterministic source selection and a bound on lateness.

The example uses DuckDB's delete+insert strategy with id as the matching key. The source predicate includes a ten-unit lookback behind the current maximum. An update to id 1 and a late insertion of id 3 are therefore included, while unchanged id 2 can be revisited without creating another copy. The result is checked again after a repeat run.

The counterexample arrives outside that lookback. It remains missing until a full refresh. A ten-unit window is a data-contract choice, not proof that older corrections cannot occur. Also, unique_key configures incremental matching; it does not by itself replace a data test proving that the selected source has one record per key.

## Syntax and data contract

unique_key names the matching identity. incremental_strategy='delete+insert' is an adapter-specific implementation choice that must be supported by the prepared database. The lookback predicate uses >= so the lower boundary is included. Keep an independent uniqueness test and a reviewed policy for multiple source versions of the same key.

## Worked case 1: Revisit rows without duplicating them

The first case updates an existing amount and adds a late record within the allowed window. It then reruns the model to verify the same three identified values. This checks the combination of selection and write semantics.

**Expected evidence:** Final amounts are id 1=6, id 2=7 and id 3=9, with three rows after rerun.

```python
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def example_one():
    with tempfile.TemporaryDirectory() as d:
        sql = (
            "{{ config(materialized='incremental', unique_key='id', "
            "incremental_strategy='delete+insert') }} select * from {{ "
            "ref('events') }} {% if is_incremental() %} where "
            "updated_at >= (select max(updated_at)-10 from {{ this }}) "
            "{% endif %}"
        )
        p = project(
            d,
            models={"current_events": sql},
            seeds={"events": "id,updated_at,amount\n1,10,5\n2,20,7\n"},
        )
        invoke(p, "build")
        (p / "seeds/events.csv").write_text("id,updated_at,amount\n1,11,6\n2,20,7\n3,15,9\n")
        invoke(p, "build")
        invoke(p, "run")
        assert rows(p, "select id,amount from current_events order by id") == [
            (1, 6),
            (2, 7),
            (3, 9),
        ]
        return {"keyed_update_and_late_insert": True, "rows_after_rerun": 3}


if __name__ == "__main__":
    print(example_one())
```

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Test the exact boundary

Add a record at max(updated_at)-10.

**Check:** The inclusive predicate considers it.

**Hint:** The operator is >=.


### 2. Repeat a correction

Apply the same corrected source twice.

**Check:** The identified result remains unchanged.

**Hint:** Check both values and row count.


### 3. Duplicate a source key

Add two selected records with one id.

**Check:** A separate key test detects the ambiguity.

**Hint:** unique_key is not an automatic source uniqueness guarantee.


### 4. Widen the lookback

Include a previously missed old record by changing the window.

**Check:** The record is selected under the revised policy.

**Hint:** Measure added work as well as correctness.


### 5. Compare with full recomputation

Rebuild the small fixture and compare keyed rows.

**Check:** The accepted incremental case matches.

**Hint:** Use stable ordering and schema.


### 6. Specify a correction ledger

List what should be recorded for a backfill.

**Check:** It includes identity, time scope, source version and reconciliation.

**Hint:** A repair needs reproducible evidence.


## Diagnose errors and misleading results

If a keyed update creates duplicates, inspect selected-source uniqueness rather than assuming unique_key enforced it. If old corrections are missed, inspect the lookback bound. If a rerun changes results without source changes, inspect ordering, nondeterministic expressions and external state.
