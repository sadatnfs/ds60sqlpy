# cpp-013: Warnings and CTest as feedback

## Level and prerequisites

Beginner; 90 minutes. Direct prerequisites: `cpp-009`, `cpp-012`.

Learner artifact: [cpp-013.cpp](../lessons/cpp-013.cpp). [Case ledger](../fixtures/cpp-013-cases.json). [Solutions](../solutions/cpp-013_solutions.md).

## Learning objectives

Turn behavioral contracts into tests that still run in Release builds.

## Vocabulary and concepts

A warning is compiler feedback about suspicious code even when compilation succeeds. A test is an executable check against a contract. CTest runs registered processes and reports their statuses. The NDEBUG macro disables standard assert expressions, so a Release test that only uses assert can accidentally check nothing.

<!-- terms:start -->

- **compiler warning:** a diagnostic about suspicious code that does not by itself stop compilation.
- **CTest:** the CMake test driver, which runs registered test processes and reports their statuses.
- **`NDEBUG`:** a macro that, when defined, removes standard `assert` expressions together with any side effects inside them.
- **always-active check:** an ordinary condition with an explicit failure result that runs in every build configuration.
- **build configuration:** a named set of compiler options such as Debug or Release whose actual flags should be inspected.

<!-- terms:end -->

## Syntax and mechanism

`if (actual != expected) return 1;` is an always-active test. `-Wall -Wextra -Wpedantic` requests common warning groups; it is not a proof of correctness. A successful CMake configure does not execute tests; run ctest and inspect the executed count.

## Trace the mechanism

A test has two jobs: perform a check and make failure observable. With NDEBUG, assert(expression) can remove expression entirely, including side effects accidentally placed inside it. An ordinary if condition and nonzero return stay active in Release. CTest adds process orchestration but cannot invent checks inside a program. Inspect the executed test count as well as the pass label, because a project with zero registered tests has not validated the intended behavior.

<!-- depth:start -->
## Build configuration and always-active checks

A build configuration selects compiler options and dependency relationships. CMake describes targets and their requirements; it does not replace the compiler or infer a correct source contract. A clean configure/build sequence should identify the source directory, build directory, selected generator, compiler and target. Keeping generated build files outside the source tree makes it easier to distinguish authored inputs from tool output.

Debug and Release commonly differ in optimization and assertion configuration, but those names alone are not a universal specification. Inspect the actual flags. The standard assert macro can be removed when NDEBUG is defined. Any expression inside assert can then disappear, including side effects. A validation step that must happen in every build should use an ordinary condition and explicit failure result rather than relying on assert.

The first complete example uses if to return failure when twice(3) is wrong. It remains active under NDEBUG. The second deliberately increments a counter inside assert to expose the macro behavior: without NDEBUG the counter reaches 1; with NDEBUG it stays 0. This is a teaching negative pattern, not a recommendation. It explains why tests should not initialize data or perform required work solely inside assert.

CMake target properties express requirements for one executable or library. A language standard requirement belongs to the target, and include/link dependencies should be scoped according to whether consumers need them. Global flags copied into every directory can accidentally couple unrelated targets and hide missing public dependencies. The real multifile fixture is the appropriate place to inspect this behavior.

A successful configuration only generates a build system. A successful build produces an artifact. Running the artifact and checking its output is another step. If the generator supports multiple configurations, the build/run path must select the intended configuration explicitly. The course host instructions distinguish those operations; the browser profile invokes its own fixed compiler pipeline and does not run arbitrary CMake projects.
<!-- depth:end -->

## Run and inspect

The pad checks `twice(3) == 6` and `twice(0) == 0` with a plain `if` that returns 1, then prints `2 always-active checks`. Because these checks are not `assert`, they still test the function when a build defines `NDEBUG`. Deliberately breaking `twice` should make Run exit 1 before that line prints. Pad routine: [study guide](../STUDY-GUIDE.md#run-a-lesson-pad). Commands and flags: [compile and run tutorial](../compile-and-run.md).

## Worked example / walkthrough

Example 1 checks `twice(3) != 6` with an ordinary `if` and `return 1`, so the check survives a Release build that defines `NDEBUG`. Example 2 hides a side effect inside `assert(++evaluations == 1)`. With assertions active it prints `evaluations=1`; with `NDEBUG` the whole expression disappears and the count stays 0. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-013-example-1.cpp)

```cpp
#include <iostream>

int twice(int x) { return x * 2; }
int main() {
  if (twice(3) != 6)
    return 1;
  std::cout << "always-active check passed\n";
  std::cout << "cpp-013 example 1 checks passed\n";
  return 0;
}
```

**Expected:** With assertions enabled, the program exits with status 0 and prints:

```text
always-active check passed
cpp-013 example 1 checks passed
```

### Worked example 2

[Complete program 2](../examples/cpp-013-example-2.cpp)

```cpp
#include <cassert>
#include <iostream>

int main() {
  int evaluations = 0;
  assert(++evaluations == 1);
#ifdef NDEBUG
  if (evaluations != 0)
    return 1;
  std::cout << "assert removed: evaluations=0\n";
#else
  if (evaluations != 1)
    return 1;
  std::cout << "assert active: evaluations=1\n";
#endif
  std::cout << "cpp-013 example 2 checks passed\n";
  return 0;
}
```

**Expected:** With assertions enabled, the program exits with status 0 and prints:

```text
assert active: evaluations=1
cpp-013 example 2 checks passed
```

## Exercises

### Exercise 1: Read flags

Explain -std=c++20, -Wall, -Wextra and -Wpedantic.

**Expected result/shape:** Language selection and three diagnostic groups distinguished.

**Verify:** Check that your explanation assigns `-std=c++20` to choosing the language standard and gives `-Wall`, `-Wextra` and `-Wpedantic` three different roles; `-Wall` does not enable every warning.

**Progressive hints:** Warnings are feedback rather than successful tests.

### Exercise 2: Run named tests

Use the supplied CMake project and ctest --output-on-failure.

**Expected result/shape:** One or more registered tests actually execute; record count and status.

**Verify:** Read the ctest summary line and record the number of tests run and passed; a summary of zero tests means nothing was registered, not that the code is correct.

**Progressive hints:** Configure/build/test are three phases.

### Exercise 3: Create a failing check

Change the expected twice(3) result to 7 in a scratch copy.

**Expected result/shape:** Executable exit 1 and failing test.

**Verify:** Build the scratch copy, run it, and confirm `echo $?` prints 1 and the `always-active check passed` line is missing; ctest must also mark the test as failed.

**Progressive hints:** A failed assertion needs to be observable outside the process.

### Exercise 4: Repair a disabled test

Build a scratch assert-only test with -DNDEBUG.

**Expected result/shape:** The wrong assert disappears; an if-based test still fails.

**Verify:** Build the scratch file with `-DNDEBUG` and confirm the wrong `assert` no longer stops the program while the `if`-based check still returns 1; without `-DNDEBUG` the `assert` aborts first.

**Progressive hints:** Do not use disabled assertions as the only release oracle.

### Exercise 5: Test zero

Keep the always-active twice(0)==0 check.

**Expected result/shape:** Exit 0 for the correct function.

**Verify:** Add `if (twice(0) != 0) return 1;` next to the existing check, build with `-DNDEBUG`, and confirm the exit status is still 0.

**Progressive hints:** Boundary behavior is a separate test input.

### Exercise 6: Transfer a regression

Break twice to x+x+1, run both tests, then restore.

**Expected result/shape:** Both normal and zero contracts reject the broken function.

**Verify:** With `x + x + 1`, confirm `twice(3)` gives 7 and `twice(0)` gives 1 so both checks return 1; after restoring `x * 2`, both must pass again.

**Progressive hints:** A test suite earns confidence by detecting a plausible defect.

## Self-check

Why does the plain `if` check still fail the process in a Release build? For Example 2, explain why `evaluations` reads 0 under `NDEBUG`, and why a side effect inside `assert` is a bug even when every test passes.

## Common pitfalls

If Release passes instantly while Debug catches a failure, inspect NDEBUG and any side effects inside assert. If CMake configures but linking fails, read the target's actual source/link inputs rather than assuming configuration validated them. If the wrong executable runs, inspect the selected build directory and configuration path. Record an always-active checksum before interpreting an optimized timing result, because a faster program that skipped required work is not an improvement.

## Retrieval and transfer

Close the source and redo Exercise 6: break `twice` to return `x + x + 1`, confirm that both always-active checks reject it, then restore it. Explain why an `assert`-only test could pass this broken version in a Release build. Then say which checks in a real codebase must survive `NDEBUG`.
