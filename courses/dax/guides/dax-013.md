## The question and the mechanism

Explain why iterating Product does not by itself filter a raw Sales aggregation.

Row context provides access to the current row's column values. A calculated column or iterator can create it. Filter context specifies which model rows are eligible for aggregations. They are different mechanisms: being positioned on a Product row does not automatically filter a raw SUM over Sales.

SELECTCOLUMNS iterates its input table to construct output rows. Product[Product] can read the current row's name. SUM(Sales[NetAmount]) still sees the outer filter context unless an operation transitions the current row into filters. This is why a raw aggregation can repeat the whole-model total beside every product, even with a perfectly valid relationship.

CALCULATE can perform context transition. Once the current Product row becomes filter context, its key travels through the active relationship to Sales. A model measure invoked in row context performs this transition implicitly. Understanding that implicit behavior explains why changing a raw SUM to a measure reference can change results even when the measure definition contains the same SUM.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

### Case A: A row label beside an unfiltered sum

**Starting context:** No outer filters; SELECTCOLUMNS supplies a Product row context only.

```dax
EVALUATE SELECTCOLUMNS ( Product, "Product", Product[Product], "RawSum", SUM ( Sales[NetAmount] ) )
ORDER BY [Product]
```

**Context trace:**

1. The Product label changes on each iteration.
2. The raw SUM has no transitioned Product filter.
3. Every iteration therefore adds the same eight sales lines and returns 187.

**Hand-derived worked-reference result:**

| Product | RawSum |
| --- | --- |
| Bag | 187 |
| Mug | 187 |
| Notebook | 187 |
| Pen | 187 |

The repeated total is not evidence of a broken relationship. It is evidence that the formula never supplied that relationship with a Product filter.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Transition the current product into a filter

**Starting context:** The same Product rows, now with explicit context transition for the raw SUM.

```dax
EVALUATE SELECTCOLUMNS ( Product, "Product", Product[Product], "Revenue", CALCULATE ( SUM ( Sales[NetAmount] ) ) )
ORDER BY [Product]
```

**Context trace:**

1. CALCULATE turns each current Product row into filters.
2. The active key relationship restricts Sales for that product.
3. Bag has no matching fact rows; the other products contribute 96, 67 and 24.

**Hand-derived worked-reference result:**

| Product | Revenue |
| --- | --- |
| Bag | BLANK |
| Mug | 96 |
| Notebook | 67 |
| Pen | 24 |

The sum of the three nonblank product results reconciles to 187 because these product populations partition the fact rows in the clean model.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. A model measure invoked in row context has an implicit transition.
2. Row context still does not become a Product filter.
3. Keep separate output labels in the same SELECTCOLUMNS call.
4. Inspect evaluation context before changing model structure.
5. SELECTCOLUMNS projects its input rows, including blank expressions.
6. A current customer row is initially row context.
