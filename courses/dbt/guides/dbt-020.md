# dbt-020: Deferral and the choice of upstream state

## Level and prerequisites

Advanced. Direct prerequisites: `dbt-013`, `dbt-019`

**Outcome:** Use deferral with an explicit upstream-state contract.

## Question and mechanism

Deferral lets a selected model resolve unselected dependencies using a prior manifest's relation information. It can support a small development or CI build that reuses accepted upstream relations. The manifest is therefore more than a source checksum: it identifies concrete relations that must exist and be appropriate for the intended test.

The first case builds a baseline in the synthetic prod schema, saves its manifest, and builds only a child in dev. No dev parent is created, so the child resolves the accepted prod parent. The second case gives dev its own parent with a different value. Normal deferral and favor-state then produce different observed results.

This difference matters when developers assume defer always means use production data. Existing target relations can influence resolution unless the selection policy explicitly favors the saved state. A reliable CI recipe should state which data is being read, how that baseline is qualified and whether target relations may already exist. The local schemas are owned fixtures, not access to a real production warehouse.

## Syntax and data contract

--defer and --state point compilation to a saved manifest for eligible unselected dependencies. --favor-state changes the preference when an existing target relation could otherwise be used. The example saves its baseline outside target/ and checks compiled SQL as well as actual result values. Qualified names in compiled SQL identify the chosen parent.

## Worked case 1: Resolve an absent dev dependency from accepted state

The first project builds prod.base and saves its manifest, then runs only dev.child. The result 11 comes from the baseline parent 1 plus 10. The program verifies that dev.base does not exist and that compiled SQL names prod.base.

**Expected evidence:** The child returns 11 and its parent is resolved from prod.

```python
import os
import shutil
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def targets(p):
    config = yaml.safe_load((p / "profiles.yml").read_text())
    original = config["classroom"]["outputs"]["dev"]
    config["classroom"]["outputs"] = {
        name: {**original, "schema": name} for name in ("dev", "prod")
    }
    (p / "profiles.yml").write_text(yaml.safe_dump(config))


def example_one():
    with tempfile.TemporaryDirectory() as d:
        p = project(
            d, models={"base": "select 1 as x", "child": "select x+10 as x from {{ ref('base') }}"}
        )
        targets(p)
        invoke(p, "build", "--target", "prod")
        state = p / "prod_state"
        state.mkdir()
        shutil.copyfile(p / "target/manifest.json", state / "manifest.json")
        invoke(p, "run", "--target", "dev", "--select", "child", "--defer", "--state", str(state))
        assert rows(p, "select x from dev.child") == [(11,)]
        assert rows(
            p,
            (
                "select count(*) from information_schema.tables where "
                "table_schema='dev' and table_name='base'"
            ),
        ) == [(0,)]
        compiled = (p / "target/compiled/classroom/models/child.sql").read_text()
        assert '"prod"."base"' in compiled
        return {"deferred_parent": "prod.base", "child": 11, "dev_parent_not_built": True}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Observe an existing target relation and favor-state

The second case creates dev.base with 100 after the baseline parent 1 exists. Default deferral uses the existing dev relation, while favor-state forces the saved baseline relation for the selected child.

**Expected evidence:** The default result is 101; favor-state produces 2.

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Inspect the chosen parent

Read the child's compiled relation name.

**Check:** It matches the intended source environment.

**Hint:** Do not infer resolution from flags alone.


### 2. Create a stale dev parent

Leave an old target relation before a deferred build.

**Check:** Its effect is explicitly observed.

**Hint:** Existing state changes the test environment.


### 3. Remove the baseline relation

Describe what happens if the manifest points to a missing table.

**Check:** Execution cannot rely on the manifest alone.

**Hint:** Metadata is not the relation itself.


### 4. Change a selected parent

Include the parent in the current selection.

**Check:** The current selected resource is built under the chosen target.

**Hint:** Selection and deferral interact.


### 5. Protect sensitive data

Explain why a deferred CI job still needs reviewed access.

**Check:** It may read baseline relations.

**Hint:** Small compute scope is not a privacy boundary.


### 6. Record baseline identity

Specify the metadata needed for a reproducible deferred run.

**Check:** It includes source revision, manifest hash and relation/data context.

**Hint:** The same path can point to different content later.


## Diagnose errors and misleading results

Unexpected values can come from an existing target relation rather than a wrong SQL formula. Inspect selected resources, state identity, favor-state behavior and compiled relation names. If the baseline is unavailable or unqualified, stop instead of silently selecting another environment.
