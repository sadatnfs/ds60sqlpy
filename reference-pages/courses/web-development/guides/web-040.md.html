web-040: Objects, constructors and immutable value boundaries#

Level and prerequisites#

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: web-039

Learning objectives#

Build a validated study-session value object. Explain shallow readonly versus deep immutability. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

Purpose, vocabulary and mental model#

A class defines a kind of object, and an object combines state with behavior. Use an object when it makes a domain boundary clearer, not merely because the program has grown. A constructor establishes the initial state. An invariant is a condition that should remain true throughout the object's useful lifetime, such as a nonempty topic and nonnegative duration.

Publicly mutable properties can let callers bypass a carefully checked constructor. A small immutable value object can preserve its contract by validating once and exposing readonly data. Readonly does not make every nested object deeply immutable, and it does not replace validation. Understand the specific language guarantee rather than treating the keyword as a complete architecture.

Syntax anatomy and mechanism#

Constructor property promotion can declare and initialize properties directly in the parameter list. Use explicit types and meaningful names. A method can derive a display label from the stored values without changing them. Prefer composition of small responsibilities over a deep inheritance hierarchy built before requirements are known.

Classroom execution and offline inputs#

Choose the PHP CLI worker in the classroom. The pad is staged as main.php and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write <?php at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

Worked example / walkthrough#

Worked example 1: A validated value#

Construction is the point where the invariant is established.

final class Duration {
  public function __construct(public readonly int $minutes) {
    if ($minutes < 0) throw new InvalidArgumentException('Negative duration');
  }
}

Expected observation: Every successfully created Duration has nonnegative minutes.

Worked example 2: Derived behavior#

The method computes from the object's state.

$duration = new Duration(45);
echo $duration->minutes . ' minutes';

Expected observation: The value is readable without exposing a mutation operation.

Six progressive exercises#

Exercise 1: Name the invariant enforced by the constructor.#

Expected evidence: A successfully constructed duration cannot begin with negative minutes.

Progressive hint: Trace the smallest example before editing. Name which values are source and which are observations.

Exercise 2: Add a method that formats the duration.#

Expected evidence: Formatting derives from state without changing it.

Progressive hint: Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

Exercise 3: Build a validated study-session value object.#

Expected evidence: Its topic and duration satisfy explicit constructor checks and remain readonly.

Progressive hint: Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

Exercise 4: Diagnose a setter that allows invalid state after construction.#

Expected evidence: Every mutation boundary must preserve the invariant, or mutation should be removed.

Progressive hint: Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

Exercise 5: Test an empty topic and zero duration.#

Expected evidence: The topic is rejected while zero follows the declared nonnegative policy.

Progressive hint: Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

Exercise 6: Explain shallow readonly versus deep immutability.#

Expected evidence: A readonly property cannot be reassigned, but referenced mutable objects can have their own changing state.

Progressive hint: Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

Debugging and common mistakes#

Do not build an inheritance tree for every noun. A readonly array cannot be changed through that property, but a readonly property referring to an object does not freeze that object's internals. Keep the claimed guarantee precise.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

Retrieval, transfer and next steps#

Close the worked answers and explain class, object, constructor without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
