## Starting point and result

Lightning organizes model steps, optimizers, callbacks and training loops. Spark can launch the environment in which that training runs. Combining them requires one clear owner for process creation and a verified interpretation of ranks and devices. The fixed `lightning-ddp` project case is the controlled integration surface; this reading chapter does not enable arbitrary nested launch commands in a classroom pad.

## Mechanism: preserve one process topology

A LightningModule defines forward computation, `training_step` and optimizer configuration. The Trainer controls loop details, device placement, precision and strategy. TorchDistributor can establish process-related environment for the launched function. If that function then asks Lightning to spawn an unrelated full set of processes on every rank, the result can be oversubscription, conflicting rendezvous or duplicate training.

The project must choose a supported handoff: either a launcher establishes ranks and Lightning uses the compatible external environment, or one launched process delegates process creation to Lightning under a deliberately qualified configuration. Do not infer that any combination of `devices`, `num_nodes`, `strategy` and environment variables is valid. Read the pinned project's actual configuration and retain rank/world-size evidence.

The loss returned by `training_step` still defines the objective. Automatic optimization does not correct an incorrect mean/sum convention or a detached loss. Metric logging also has a separate reduction contract: averaging rank means is not necessarily a global observation-weighted metric.

## Worked case: a custom likelihood in a Lightning step

The project uses a small original custom objective and records at least one actual optimization step through Lightning. Compare the step's loss and parameter change with the serial reference. Disable unnecessary external logging and checkpoint downloads for the offline fixture. Use explicit seeds and thread limits so reproducibility and resource consumption are inspectable.

A successful `Trainer` import is not this evidence. The required result includes the actual process topology, data IDs, step count and numerical agreement. GPU acceleration and multi-host behavior remain separate qualifications even if the CPU case passes.

## Worked case: duplicated topology is a design failure

Suppose Spark launches two ranks and each creates a Trainer that spawns two more processes without coordinating a shared world. Four processes may train duplicated data or contend for the same rendezvous. The error is architectural, not a reason to increase the timeout or suppress warnings. Draw the intended process tree before running it.

A correct two-rank fixture assigns each rank its intended data and verifies the resulting total coverage. If Lightning replaces or wraps the sampler, inspect the resulting loader rather than assuming the original sampler settings survived. The `sharding-audit` case provides a separate record of duplicates and omissions.

## Failure diagnosis

Unexpected rank counts indicate launch configuration problems. Repeated initialization messages may reveal nested spawning. A metric that differs from a serial result can be a logging reduction issue even when gradients are correct. A saved model missing optimizer state is a weights-only export, not necessarily an exact training-resume checkpoint.

## Interview discussion

**Does Lightning make a custom likelihood less customizable?** The model still defines its computation and can use custom optimization patterns within the framework's contract. Convenience does not remove the need to understand loss scaling and state.

**What should a Spark/Lightning adapter promise?** A narrow supported launch/data/version contract with actual tests. It should not claim arbitrary cluster, accelerator and strategy combinations merely because they share Python interfaces.

## Next step

Design the dataset and restart contract. A training job is reproducible only when the exact observations, shuffling, optimizer state and checkpoint boundaries can be reconstructed.
