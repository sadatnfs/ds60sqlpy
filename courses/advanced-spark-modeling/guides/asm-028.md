# asm-028: Two CPU ranks, exact shards and gradient scaling

Tutorial mode. Stage: advanced. Direct prerequisites: `asm-027`, `clp-019`.

## Starting point and result

DistributedDataParallel synchronizes gradients across processes, but the loss presented on each rank determines the global target. Unequal local batch sizes and sampler padding can quietly change that target. This chapter derives the correct scaling and ties it to the project's `sharding-audit` and `torch-distributor` cases.

## Mechanism: rank averaging is not observation averaging

Let rank r have local summed gradient \(g_r\), local count \(n_r\), world size R and global count \(N=\sum_r n_r\). Under ordinary DDP averaging, synchronizing local mean losses produces

\[g_{\mathrm{DDP}}=\frac1R\sum_r\frac{g_r}{n_r}.\]

The desired global mean is \(g=\sum_r g_r/N\). They agree when the local counts are equal, but not generally. One valid strategy is to backpropagate local summed loss multiplied by \(R/N\), so rank averaging yields the global mean. The normalization must reflect the actual synchronized step and any accumulation schedule. Weighted observations replace counts with total weights.

This derivation assumes the default relevant averaging behavior and participating ranks. Custom communication hooks, uneven-input join policies and gradient accumulation can alter the effective reduction. Record those settings instead of applying a memorized world-size multiplier blindly.

## Worked case: unequal local counts

Imagine rank zero has one gradient contribution equal to one. Rank one has three contributions, each three. Averaging local means yields two, while the global observation mean is 2.5. The same counterexample from partition aggregation now appears at a collective-training boundary. The sharding case should compute the serial target and verify the distributed update or gradient against it.

A practical simple fixture can choose equal local batch counts to establish basic DDP correctness, then separately demonstrate the unequal-count failure and a corrected scaling. Do not deliberately create mismatched collective schedules without a controlled timeout and a documented join design.

## Worked case: sampler padding changes coverage

With five observations and two ranks, a sampler may pad to six assignments so every rank receives the same number. At least one observation is repeated. With dropping enabled, one may instead be omitted. Both can be intentional training policies, but neither is an exact once-per-epoch pass over five distinct observations.

Record IDs seen per rank, the union, duplicates and omissions. Calling `set_epoch` when using a distributed sampler changes epoch-dependent shuffling; it does not itself prove exact coverage. A correct objective audit uses actual assignments rather than assuming the loader length equals the number of unique observations.

## Failure diagnosis

A factor-of-two gradient error suggests world-size or local-reduction mismatch. A hang may come from one rank exhausting data before another reaches a collective. A converged model can still be biased by repeated or missing observations. Compare counts and IDs before tuning learning rates to compensate for an unknown scaling error.

## Interview discussion

**Does DDP shard input automatically?** DDP synchronizes model gradients. The user or data-loading framework must partition inputs appropriately.

**Is padding always unacceptable?** It can be a reasonable training choice. For an exact likelihood or evaluation metric, account for duplicates explicitly or choose a delivery scheme that preserves the declared target.
