# CppAD, TMBad and derivative order

Start with: tmb-026, tmb-006.

Outcome: Choose an AD framework for a specific tested derivative target.

The classroom companion runs in the prepared R statistics runtime. It uses base R to expose the mathematics or data contract. Compiling and executing TMB uses the separate [owned project](../projects/tmb-local/README.md); a companion run is not a TMB compiler or rpy2 receipt.

Automatic differentiation is implemented by a concrete library, data representation and set of supported operations. TMB can compile a template using CppAD or TMBad. The statistical objective should remain the same when both support the chosen operations, but memory use, special-function support and higher-order derivative paths can differ.

The framework is selected at compilation. A library built with CppAD is not transformed into TMBad by changing an R option after loading it. Use a fresh native build and compare values, gradients and required curvature against the same independent oracle.

### Worked case A: first and second derivatives agree

The companion differentiates a simple nonlinear scalar function analytically and checks first and second central differences at two points. It demonstrates the target of a framework comparison without pretending to execute either AD backend. In a prepared experimental build directory, compile a copied original model with `framework="TMBad"` and repeat the existing acceptance checks before claiming support.

### Worked case B: why Laplace derivatives require more machinery

The Laplace objective contains a log determinant of a second derivative with respect to latent states. Differentiating that correction requires third-order joint derivatives; taking another derivative can require fourth-order quantities. The companion shows first through fourth derivatives of a small polynomial so the levels are explicit.

TMB's `compile(max.order=...)` controls generated derivative order for certain special functions, not a universal degree of mathematical accuracy. The current manual notes that `intern=TRUE` requires TMBad and that a Hessian of the internal Laplace approximation can need fourth-order special-function support. Increasing `max.order` increases compile time and binary size, so start from a specific required operation.

Automatic parallelization via `openmp(autopar=TRUE)` is experimental and requires a TMBad/OpenMP build. It differs from the explicit `parallel_accumulator` already qualified in the CppAD project. Treat it as a separate capability with separate numerical and resource evidence.

### Answered discussion

**Is TMBad statistically more accurate than CppAD?** Framework choice is not a replacement for model adequacy or approximation analysis. **Do fourth derivatives make Laplace exact?** No. They can differentiate the approximation more completely; the approximation can still be biased. **Can compiler flags such as fast math be enabled casually?** They can change floating-point assumptions and exceptional-value behavior. Requalify exact arithmetic and domain failures before considering them.

See [the pinned compile and MakeADFun documentation](https://cran.r-project.org/web/packages/TMB/TMB.pdf). This course's current native receipt covers CppAD. TMBad, internal Laplace and automatic parallelization remain explicitly separate until their own runs are recorded.

### Complete R companion

```r
f <- function(x) exp(x) + x^4
for (x in c(-.4, .7)) {
  h <- 1e-4
  numeric_first <- (f(x + h) - f(x - h)) / (2 * h)
  numeric_second <- (f(x + h) - 2 * f(x) + f(x - h)) / h^2
  print(c(x = x, first_error = numeric_first - (exp(x) + 4 * x^3), second_error = numeric_second - (exp(x) + 12 * x^2)))
  stopifnot(abs(numeric_first - (exp(x) + 4 * x^3)) < 1e-6)
}
x <- .5
print(c(first = 4 * x^3, second = 12 * x^2, third = 24 * x, fourth = 24))
```
