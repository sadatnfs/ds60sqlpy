# web-053: Authorization, ownership and object-level access

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-052`

## Learning objectives

Build an object-access function with separate trusted actor and requested id inputs. Explain why hiding an edit button is only a user-interface convenience. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

Authentication answers who the application believes is making a request. Authorization answers whether that identity may perform this action on this object. A record id in a URL is a locator, not proof of permission. A hidden owner field, disabled button or filtered interface cannot enforce access because the client can alter all of them.

Apply authorization on every relevant server operation, including reads, updates, deletion and exports. Scope queries by trusted identity or enforce an explicit policy before returning data. Deny by default when a required identity or permission is missing. Error behavior should avoid disclosing another user's sensitive record while still providing useful recovery for legitimate users.

## Syntax anatomy and mechanism

The reference receives a trusted synthetic actor id as a separate parameter from the requested record id. A query includes both record id and owner id as bound values. The fake actor is a test fixture, not a login implementation. A real adapter must obtain it from a verified session or credential and must not copy it from a form field.

## Classroom execution and offline inputs

Choose the **PHP CLI** worker in the classroom. The pad is staged as `main.php` and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write `<?php` at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

## Worked example / walkthrough

### Worked example 1: Scope a read

The owner comes from trusted server identity context.

```sql
SELECT
  title
FROM
  notes
WHERE
  id = :id
  AND owner_id = :actor_id;
```

**Expected observation:** A record belonging to another actor is not returned.

### Worked example 2: Separate input roles

A requested object is untrusted input; actor identity has a different origin.

```php
$title = loadOwnedNote($db, $trustedActorId, $requestedNoteId);
```

**Expected observation:** The API makes the trust distinction visible.

## Six progressive exercises

### Exercise 1: Explain why knowing a record id is not sufficient permission.

**Expected evidence:** Ids identify objects; a policy must authorize access for the current actor.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add owner scoping to a prepared read query.

**Expected evidence:** The query can return only the requested actor's matching record.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build an object-access function with separate trusted actor and requested id inputs.

**Expected evidence:** The owner can read the record and a different actor receives no record.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose trusting owner_id from a submitted form.

**Expected evidence:** A caller can forge it; derive ownership from the verified server-side identity.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test own, other and missing records.

**Expected evidence:** Each follows a deliberate policy without leaking another actor's title.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain why hiding an edit button is only a user-interface convenience.

**Expected evidence:** The server endpoint must enforce the same permission even when called directly.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not confuse an unpredictable id with an authorization check. Avoid logging sensitive returned data during denied requests. Ensure update and delete paths have the same ownership discipline as reads.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain authorization, ownership, least privilege without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
