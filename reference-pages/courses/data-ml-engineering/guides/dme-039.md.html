dme-039: Experiments, MLflow registry and acceptance decisions#

Level: Advanced | Prepared runtime: data-engineering

Direct prerequisites: dme-038.

Outcome: Create and read back real local MLflow runs and model versions.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

Track what happened before deciding what to deploy#

A training function returns an estimator. An engineering workflow also needs to retain what data and configuration produced it, which observations support it and which artifact a consumer should use. These are related records with different identities. Combining them into one filename called latest-model makes later investigations unnecessarily ambiguous.

This chapter uses real MLflow tracking and registry APIs against an owned local SQLite database. It logs actual scikit-learn models, registers versions, reads their lineage back and updates an alias only through an explicit acceptance decision. It does not start a model server or claim that a registry pointer automatically changes a running predictor.

The synthetic decision is deliberately small. Its purpose is to make every tracking and selection operation observable. The example's accuracy threshold demonstrates an acceptance mechanism; it is not a recommended universal standard for deploying machine learning.

Distinguish the identities#

An MLflow experiment organizes runs. A run records an execution's parameters, metrics, tags and associated artifacts. A logged model identifies a stored model artifact with its model information. A registered model provides a named collection of versions. A registered version links a particular artifact and its lineage into that collection. An alias is a named, changeable reference to a version.

These identifiers do not replace one another. The recipe fingerprint from chapter 037 relates declared computation inputs. A run ID distinguishes executions. A model ID identifies a logged model. A registry version identifies an entry under a registered model name. An alias such as champion expresses a current selection that may change later.

Preserve the resolved version or artifact identity when comparing results. If one batch resolves an alias before an update and another resolves it afterward, the shared alias string does not prove that both batches used the same model. A deployment process should resolve and record its selected artifact under an explicit update policy.

Make evidence populations comparable#

The program creates twenty training points and forty separate validation points for a simple threshold-shaped outcome. The candidate is a fitted scaler-plus-logistic pipeline. The challenger uses a most-frequent-class estimator. Both follow the same feature schema and are evaluated on the same declared validation population.

The validation input and labels are encoded into a content fingerprint that is logged with the run. In the second worked case, the program checks that candidate and challenger have the same evaluation fingerprint. This establishes a useful identity relationship for the fixture. It does not establish that the population is representative or the evaluation design is scientifically sufficient.

Log an actual model artifact#

train_and_register() fits the estimator, measures its validation accuracy and creates a real tracking run. It logs the candidate kind, feature unit and validation row count, plus the measured metric and evaluation fingerprint. It then calls mlflow.sklearn.log_model with a model name, an input example, an inferred signature and explicit requirement versions.

The signature describes the demonstrated model interface. It does not replace the semantic unit and validation rules from chapter 036. Likewise, the model's requirement list describes dependencies needed for that artifact's use; it is not an exhaustive reproduction claim about the complete runtime. The worker's reviewed image and hash-locked dependency closure provide the separate prepared environment.

The pinned MLflow release uses its current default scikit-learn serialization workflow, with the required skops serializer supplied in the prepared image. The program registers the returned model URI, rather than inventing a model version from a status message. It reads the stored run and registered version back and verifies that the parameter, measured metric and source run relationship agree.

The high-level registration function's waiting argument is await_registration_for. The lower-level client model-version operation has a different argument name. The complete program uses the actual API verified in the prepared release. Transplanting keyword arguments between similarly named APIs can fail even when their overall purposes appear related.

Worked case 1: Accept a measured candidate and update the alias explicitly#

example_one() creates a fresh local tracking and registry store. The fitted candidate achieves validation accuracy 0.975, corresponding to 39 correct decisions among forty. The declared demonstration gate accepts it.

The code then explicitly assigns champion to the candidate's registered version. Reading that alias through the registry returns the same version and source run ID. This confirms that actual metadata was written and read back, rather than merely assigning a Python variable that resembles a registry record.

The output records that no serving process was started. Selecting a registry alias does not, by itself, prove that an HTTP service loaded those weights, that a worker is ready, or that requests are being served by the selected version. The owned ML service project tests deployment and rollback through its own explicit lifecycle.

Worked case 2: Registration succeeds while acceptance fails#

example_two() starts with another fresh local store, registers an accepted linear candidate as version one and assigns the champion alias. It then logs and registers the majority-class challenger as version two. The challenger has validation accuracy 0.6 and fails the predeclared acceptance gate.

Version two still exists in the registry and retains its source run relationship. Registration succeeded. The code withholds the alias update, then reads champion again and verifies that it still resolves to version one. A rejected candidate can remain available for investigation without becoming the selected deployment artifact.

The captured table compares the two actual registered versions, their metrics and acceptance results. The structured report preserves run IDs, model IDs, version relationships and the shared evaluation fingerprint. The program also verifies that a failed acceptance decision did not erase the challenger's tracking record.

Each worked case owns its temporary local database and artifact directory. Those files are intentionally discarded when the finite case ends. The classroom retains submitted source and captured results; it does not promise to preserve every arbitrary temporary tracking store between Run operations. Use the separately documented persistent project for a durable service and training workspace.

Complete worked program#

"""Real local MLflow runs, flavored models, registry aliases and acceptance gates."""

import hashlib
import importlib.metadata
import json
import os
import tempfile
from pathlib import Path

import mlflow
import mlflow.sklearn
import numpy as np
import pandas as pd
from mlflow import MlflowClient
from mlflow.models import infer_signature
from sklearn.dummy import DummyClassifier
from sklearn.linear_model import LogisticRegression
from sklearn.metrics import accuracy_score
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

from ds60sqlpy.plot_artifacts import publish_report, publish_table

MODEL_NAME = "classroom-decision"


def setup(root):
    # This pad has no repository checkout; source provenance is recorded by the classroom receipt.
    os.environ["GIT_PYTHON_REFRESH"] = "quiet"
    uri = "sqlite:///" + str(root / "tracking.db")
    mlflow.set_tracking_uri(uri)
    mlflow.set_registry_uri(uri)
    client = MlflowClient(tracking_uri=uri, registry_uri=uri)
    experiment = client.create_experiment(
        "explicit-acceptance", artifact_location=(root / "artifacts").as_uri()
    )
    return client, experiment


def train_and_register(client, experiment, kind):
    train = pd.DataFrame({"signal": np.arange(20, dtype=float)})
    train_labels = (train.signal >= 12).astype(int)
    validation = pd.DataFrame({"signal": np.arange(0.25, 20, 0.5)})
    validation_labels = (validation.signal >= 12).astype(int)
    estimator = (
        LogisticRegression(C=1000, random_state=39)
        if kind == "linear"
        else DummyClassifier(strategy="most_frequent")
    )
    model = make_pipeline(StandardScaler(), estimator).fit(train, train_labels)
    predictions = model.predict(validation)
    accuracy = float(accuracy_score(validation_labels, predictions))
    evaluation = {"signal": validation.signal.tolist(), "labels": validation_labels.tolist()}
    evaluation_sha = hashlib.sha256(json.dumps(evaluation, sort_keys=True).encode()).hexdigest()
    requirements = [
        f"{name}=={importlib.metadata.version(name)}"
        for name in ("scikit-learn", "numpy", "pandas", "cloudpickle")
    ]
    created_run = client.create_run(experiment)
    with mlflow.start_run(run_id=created_run.info.run_id) as run:
        mlflow.log_params(
            {
                "candidate_kind": kind,
                "feature_unit": "dimensionless",
                "validation_rows": len(validation),
            }
        )
        mlflow.log_metric("validation_accuracy", accuracy)
        mlflow.set_tag("evaluation_sha256", evaluation_sha)
        info = mlflow.sklearn.log_model(
            sk_model=model,
            name="candidate",
            input_example=train.iloc[:2],
            signature=infer_signature(train, model.predict(train)),
            pip_requirements=requirements,
        )
        version = mlflow.register_model(info.model_uri, MODEL_NAME, await_registration_for=10)
        run_id = run.info.run_id
    stored_run = client.get_run(run_id)
    stored_version = client.get_model_version(MODEL_NAME, str(version.version))
    assert stored_run.data.params["candidate_kind"] == kind
    assert stored_run.data.metrics["validation_accuracy"] == accuracy
    assert stored_version.run_id == run_id
    return {
        "kind": kind,
        "run_id": run_id,
        "model_id": info.model_id,
        "version": str(version.version),
        "validation_accuracy": accuracy,
        "validation_rows": len(validation),
        "evaluation_sha256": evaluation_sha,
        "accepted": accuracy >= 0.9,
        "model_has_real_sklearn_flavor": True,
    }


def example_one():
    with tempfile.TemporaryDirectory() as directory:
        client, experiment = setup(Path(directory))
        candidate = train_and_register(client, experiment, "linear")
        assert candidate["accepted"]
        client.set_registered_model_alias(MODEL_NAME, "champion", candidate["version"])
        selected = client.get_model_version_by_alias(MODEL_NAME, "champion")
        assert (
            str(selected.version) == candidate["version"] and selected.run_id == candidate["run_id"]
        )
        return {
            "candidate": candidate,
            "alias_version": str(selected.version),
            "alias_change_was_explicit": True,
            "serving_process_started": False,
        }


def example_two():
    with tempfile.TemporaryDirectory() as directory:
        client, experiment = setup(Path(directory))
        original = train_and_register(client, experiment, "linear")
        client.set_registered_model_alias(MODEL_NAME, "champion", original["version"])
        challenger = train_and_register(client, experiment, "majority")
        assert not challenger["accepted"] and challenger["version"] != original["version"]
        if challenger["accepted"]:
            client.set_registered_model_alias(MODEL_NAME, "champion", challenger["version"])
        selected = client.get_model_version_by_alias(MODEL_NAME, "champion")
        assert str(selected.version) == original["version"]
        assert challenger["evaluation_sha256"] == original["evaluation_sha256"]
        assert (
            client.get_model_version(MODEL_NAME, challenger["version"]).run_id
            == challenger["run_id"]
        )
        return {
            "original": original,
            "registered_challenger": challenger,
            "retained_champion_version": str(selected.version),
            "registration_succeeded_while_acceptance_failed": True,
        }


def main():
    first, second = example_one(), example_two()
    candidates = [second["original"], second["registered_challenger"]]
    publish_table(
        ["candidate", "registry version", "validation accuracy", "accepted"],
        [
            [row["kind"], row["version"], row["validation_accuracy"], row["accepted"]]
            for row in candidates
        ],
        description="Registered model versions evaluated on the same population",
    )
    publish_report(
        {"case_one": first, "case_two": second},
        description="MLflow run-to-version lineage and explicit alias acceptance",
    )
    print(json.dumps({"case_one": first, "case_two": second}, allow_nan=False))
    print("dme-039: two MLflow registry cases passed")


if __name__ == "__main__":
    main()

Keep selection, activation and observation separate#

An artifact can be logged while scientifically unsuitable. A model can be registered while rejected by policy. An alias can change while a running process still holds an earlier model. A process can load the selected artifact while failing readiness or returning incorrect outputs. Each claim needs evidence from the relevant operation.

For a real rollout, retain the resolved version, artifact identity, interface contract and observed service behavior. A rollback should select a known retained artifact and verify its actual readiness and outputs. Recreating a model by retraining from memory is a different operation with a different reproduction risk.

A recorded metric also needs its population and evaluator definition. Two runs can use the same metric name on different data, label cutoffs or preprocessing. The evaluation fingerprint in this tutorial makes one part of that comparison explicit. The broader scientific design remains the team's responsibility.

Answered interview discussion#

What is the difference between a run and a model version? A run records an execution and its evidence. A registered version links a particular model artifact into a named registry collection. A single tracking workflow can create and compare several artifacts and versions.

Does a registry prove that a model is approved? No. Registration is a metadata operation. Acceptance and deployment selection require explicit criteria and actions. The second case registers a real challenger while retaining the original champion.

Why not identify every request only by an alias? Aliases are mutable. Preserve the resolved version or artifact identity for the execution being investigated so a later alias update cannot change the interpretation of historical results.

How do you know a selected model is actually serving? Inspect the running service's loaded identity, readiness and source-bound request results. A successful registry call alone does not establish those runtime observations.
