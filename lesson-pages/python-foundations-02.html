Debug from Evidence Instead of Guessing#

Stable ID: python-foundations-02

Estimated time: 150 minutes, split across sessions as needed.

Level and prerequisites#

Foundation. Direct catalog prerequisites: python-03.

You can assign values, inspect types, choose a branch, and recognize an exception from Days 1 to 3. This lab slows down the debugging process before loops and larger programs arrive. You do not need a debugger extension or any new package.

Learning objectives#

  • Classify syntax, runtime, and incorrect-result failures.
  • Read an exception from its final line back to the failing statement.
  • Reduce a failure to a small, repeatable input.
  • Change one hypothesis at a time and preserve a regression case.

Vocabulary and concepts#

Debugging is an investigation into a disagreement between intended and observed behavior. Treat the program as evidence, not as a puzzle solved by random edits. A small program with one input and one clear failure is easier to reason about than a full application whose state you cannot reconstruct. First write what should happen and what actually happened. Then locate the earliest difference. Only then propose and test a change.

  • Symptom: the observable failure, such as a wrong total or an exception.
  • Hypothesis: a specific explanation that could be disproved by a check.
  • Reproduction: a repeatable input and command that produces the symptom.
  • Traceback: the execution history printed when an exception escapes.
  • Regression case: a saved example that catches a previously fixed defect.
  • Boundary case: an input exactly at a rule's change point, such as zero.

Syntax errors prevent Python from interpreting a statement. Runtime errors happen while a syntactically valid program executes, such as division by zero. Logic errors can produce the wrong answer while the process still exits normally. An exit code of zero is useful process evidence, but it cannot prove that your intended calculation was implemented. A comment claiming success is even weaker: it does not inspect any actual behavior.

Worked example / walkthrough#

Example A: preserve the exact boundary#
quantity = 0
if quantity > 0:
    status = "ready"
else:
    status = "empty"
print(status)
assert status == "empty"

The contract says an order is ready only when quantity is strictly positive. > excludes zero. The colon begins a branch, and indentation marks its body. else covers every case that did not satisfy the first condition. Expected output is empty; the assertion checks that value. Replacing > with >= is a one-character change with a real policy effect. Testing only quantity three would miss it. Try quantities zero and one before calling the rule fixed.

Example B: inspect before converting#
raw_quantity = " 12 "
print(repr(raw_quantity), type(raw_quantity).__name__)
quantity = int(raw_quantity)
print(quantity + 1)
assert quantity == 12

Expected output first exposes surrounding spaces and type str, then 13. repr produces an inspectable representation; it can reveal whitespace that ordinary display hides. int accepts surrounding whitespace for this input. If the input becomes "twelve", conversion raises ValueError. That symptom does not prove that integer conversion is broken. It shows that the supplied text does not match the accepted numeric representation. Decide whether to reject it, prompt again, or support another representation. Do not silently replace every invalid quantity with zero.

Read a traceback deliberately#

Start with the final exception class and message. Find the named source line in your saved file. Inspect the values and types entering that line using a temporary, bounded print. In a longer traceback, move upward until you reach the call site that supplies those values. Do not copy a whole traceback into a bug report when it contains private paths or user data. Preserve the class, the smallest reproducing code, and harmless input that illustrates the failure.

When trying a repair, keep the input fixed. If you change code and data at the same time, a successful run cannot tell you which change mattered. Test the original reproduction, then a normal case and a boundary case. Removing a failing statement, catching every exception, or editing an assertion to match the wrong answer can make a process appear healthy while preserving the bug.

Keep an investigation log#

For each numbered task, write five short fields: expected behavior, observed behavior, hypothesis, smallest experiment, and result. If the result contradicts the hypothesis, keep it and choose a better explanation. A failed hypothesis is progress when it removes a possibility. Save the repaired example alongside its checks so a later refactor cannot quietly reintroduce the same defect.

  1. Disprove a hypothesis. Investigate "2" + "3" yielding "23". Test the hypothesis that Python added the numbers incorrectly by inspecting types and repeating the operation on integers.

Hint: Change one variable in your experiment: the value types.

  1. Write a regression note. Choose the shipping or receipt defect. Save a four-part note containing contract, smallest failing input, repaired observation, and one nearby boundary case. Add executable checks.

Verify: The note names concrete input 20 for shipping or (7, 3, 2) for the receipt, and assertions fail if you reintroduce the original operator.

Hint: Temporarily reverse the repair to see whether the check detects it, then restore it.

Self-check#

Explain the difference between a symptom and an explanation without looking at the vocabulary list. Describe a defect that never raises an exception. Show why a boundary test can find something a normal test misses. Reproduce one fixed example in a new file without copying its final implementation.

Common pitfalls#

If an edit appears to do nothing, verify saved file and executed path. If an except block produces a plausible number after invalid input, remove the fallback and inspect the conversion failure. If your test passes before the repair, ask whether its input reaches the failing branch. If every attempt changes many lines, return to the minimal reproduction and test one claim. Use a package installer only when the evidence identifies an import problem.

Next step#

Continue into loops and functions. Keep the investigation log for Day 10 tests and Day 11 debugging tools. Those tools make observations easier to collect; they do not replace a clear contract or a falsifiable hypothesis.

Debug from Evidence Instead of Guessing: solution reasoning#

Stable ID: python-foundations-02.

Read the guide and attempt the learner artifact first. The executable solution is a comparison implementation. It does not certify your changed program merely because its own demonstration succeeds. Copy the acceptance cases into your attempt, then change one input without changing the intended policy.

The reference keeps deliberate errors inside narrow demonstrations or describes them without crashing the entire module. Your original reproduction should still preserve the real failure. The central test is whether a check would detect the old defect. When a test passes both the broken and repaired program, it may document useful behavior but cannot prove that repair.

amount = 20
qualifies = amount >= 20
assert qualifies is True

This assertion checks the exact change point. An amount of 21 would pass both the original and repaired comparison and therefore provides weaker evidence.

Exercise 1. Classify three failures#

A missing closing parenthesis is a syntax failure: Python cannot finish parsing the statement. Dividing one by zero is a runtime failure, because the expression is grammatical but the operation has no defined numeric result here. Adding three and four is valid and returns seven; it becomes a logic failure only when the independent requirement says to multiply. Preserve the requirement alongside the input so another reader can judge the result. The interpreter cannot infer the business rule from a syntactically valid formula.

Exercise 2. Inspect the raw input#

Inspecting repr(raw) reveals the spaces and quotes; inspecting its type reveals str. Integer conversion returns 8, after which adding one gives 9. Leading zero and whitespace do not make this particular representation invalid. Replacing the word eight with zero would erase the distinction between an invalid record and a real quantity of zero. The reference catches ValueError only to demonstrate the rejected case, with a visible failure marker. It does not claim to support words as numeric input or silently expand the accepted language.

Exercise 3. Repair the boundary#

The phrase at least includes equality, so the repaired predicate is amount greater than or equal to twenty. Testing 19, 20, and 21 distinguishes the nonqualifying side, the exact boundary, and the qualifying side. The original operator produces false at twenty and true only above it. The changed observation at exactly twenty is evidence for this repair. Retain that case even if a later application uses much larger typical order amounts. A threshold is a policy, so document the units and meaning of the number.

Exercise 4. Read an exception precisely#

int("4.5") raises ValueError because the text is not an integer literal accepted by that conversion. Nothing about the symptom suggests a missing package. Converting first to float and then int would truncate, which is a new policy with possible data loss. Rejecting the value is a valid policy when quantities must be exact integers. Record the exception class and the expression without unnecessary machine-specific path details. That gives another learner enough information to reproduce the failure in a fresh process.

Exercise 5. Reduce a wrong result#

The wrong expression subtracts the order discount from the item count. With three items, a discount of two leaves one item, multiplied by seven for a result of seven. The intended calculation multiplies quantity and unit price first, then subtracts two once, producing nineteen. Both formulas yield twenty-one when the discount is zero. This is a useful example of an apparently sensible test that cannot expose the defect. Keep a nonzero-discount regression case and explain why that condition reaches the policy difference.

Exercise 6. Keep the failure visible#

Use a narrow try around conversion and catch ValueError. Assign or print a clear invalid-quantity status on failure. On successful conversion, use the accepted status and keep the parsed numeric quantity. This separates failure reporting from numeric output. An empty except block leaves the caller unable to distinguish a failure from no work. Catching Exception would also hide unrelated programming mistakes, such as a misspelled name. The reference demonstrates only this conversion boundary and does not pretend to implement a complete interactive input workflow.

Exercise 7. Disprove a hypothesis#

The control experiment compares the same visible digits as strings and as integers. The string operation joins characters and produces "23", while integer addition gives five. The observations reject the hypothesis that Python's integer addition is faulty. A better explanation is that the input values belong to a different type than expected. This style of experiment matters in larger programs too: inspect the boundary where data enters, then test a minimal operation with a controlled value before modifying downstream arithmetic or installing unrelated tools.

Exercise 8. Write a regression note#

The regression note supplies the rule, input, incorrect observation, and corrected observation. For shipping, amount twenty is the essential sentinel. For the receipt, seven times three with discount two is the essential sentinel. Add a nearby normal case to avoid fixing the special input with a constant. Temporarily restoring the old operator should make the sentinel assertion fail. Restore the real repair afterward. That deliberate failure is evidence that the test is sensitive to the original defect, not just evidence that the repaired file can run.

Compare and transfer#

Apply the same method to a temperature alarm that triggers below zero and to one that triggers at or below zero. Both may be legitimate contracts, but they need different expected results at zero. Explain which written requirement you implemented and show the case that would distinguish them. Debugging ends with evidence for a policy, not with the disappearance of red text.
