# go-009: Pointers, mutation and allocation lifetimes

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-008

## Learning objectives

Use pointers to share or update state on purpose, guard nil, and separate copying a value from mutating a target. Along the way, explain pointer, dereference, reachability; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A pointer contains the address of a value. Passing a pointer still copies the pointer value, but both copies identify the same target. This is useful when mutation is the intended contract and dangerous when callers expect isolation. Go's garbage collector keeps reachable objects alive, so returning a pointer to a local variable is valid; the compiler decides where storage must live. That does not make every pointer safe to use: nil has no target and dereferencing it panics. Ordinary Go pointers do not support arithmetic. Use a value receiver or an independent copy when shared mutation is unnecessary, and make optional pointer semantics explicit.

## Vocabulary and concepts

- **Pointer:** A value identifying another value in memory.
- **Dereference:** Reading or writing the target of a pointer.
- **Reachability:** Whether live program state still refers to an allocated object.

## Syntax anatomy and reasoning

&value obtains an address and *pointer dereferences it. In a type, *Point means a pointer to Point. new(T) returns a pointer to a zero T; it does not initialize maps or channels stored inside T. Selectors automatically follow a pointer to a struct, so p.X is convenient syntax for field access through p. A nil check guards dereference only when no unsynchronized writer can change the state between those operations.

## Worked example / walkthrough

### Worked example 1: Mutate through a pointer

Create an integer 4 and increment it through a helper receiving its address.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func increment(p *int) { *p = *p + 1 }
func seven() *int      { n := 7; return &n }
func setIfPresent(p *int, v int) bool {
	if p == nil {
		return false
	}
	*p = v
	return true
}

func main() {
	// Mutate through a pointer
	{
		n := 4
		increment(&n)
		check(n == 5, "pointer mutation")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The caller value becomes 5.

The helper changes the shared target, not the caller variable that stores the pointer. The mutation contract must be visible at the call site.

### Worked example 2: Return a live value

Return a pointer to a local integer initialized to 7.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func increment(p *int) { *p = *p + 1 }
func seven() *int      { n := 7; return &n }
func setIfPresent(p *int, v int) bool {
	if p == nil {
		return false
	}
	*p = v
	return true
}

func main() {
	// Mutate through a pointer
	{
		n := 4
		increment(&n)
		check(n == 5, "pointer mutation")
	}

	// Return a live value
	{
		p := seven()
		check(*p == 7, "returned pointer")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The returned pointer remains valid and reads 7.

Go extends storage lifetime as needed. Stack-versus-heap placement is an implementation decision and should not be guessed from the lexical block alone.

### Exercise 1: Mutate through a pointer: change one input

**Expected:** The edited run panics with `pointer mutation` because `n == 5` no longer holds.

### Exercise 2: Return a live value: diagnose an edited check

**Expected:** The defective run panics with `returned pointer`; after restoring `check(*p == 7, "returned pointer")`, the returned pointer remains valid and reads 7.

**Verify:** The edited check fails with message `returned pointer` for a state that `*p == 7` accepts.

### Exercise 3: Guard absence

Represent an optional integer with a nil pointer and inspect it without dereferencing.

**Expected:** The pointer is absent.

**Verify:** Your solution must keep `p == nil` true. Control: changing `check(p == nil, "nil pointer")` to `check(p != nil, "nil pointer")` panics with message `nil pointer`; revert it.

### Exercise 4: Allocate a zero target

Use new(int) and compare pointer presence with its stored value.

**Expected:** The pointer is non-nil and its target is 0.

**Verify:** Your solution must keep `p != nil && *p == 0` true. Control: changing `check(p != nil && *p == 0, "new zero")` to `check(p == nil && *p == 0, "new zero")` panics with message `new zero`; revert it.

## Common pitfalls and diagnosis

The two classic pointer bugs are dereferencing nil, which panics, and sharing a target when the caller expected an independent value. A pointer parameter announces mutation, so reviewers should look for `&` at the call site. Conversely, copying `*p` takes a snapshot that does not follow later changes. Do not reason about stack versus heap from the source; Go keeps any reachable value alive.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Mutate through a pointer: change one input

1. Restate the expected observation: The caller value becomes 5.
2. increment receives the address of n. Which variable does `*p = *p + 1` change?
3. Starting from 5, increment makes n equal 6, so `n==5` fails. The pointer worked; the starting value no longer matches the expectation.

### Hint for investigation 2: Return a live value: diagnose an edited check

1. Restate the expected observation: The returned pointer remains valid and reads 7.
2. Go keeps any reachable value alive. Does returning `&n` leave the caller with a dangling pointer?
3. seven returns a pointer to 7, so `*p!=7` is false and check panics. The pointer is valid; the edited condition asserts the opposite of the contract.

### Hint for investigation 3: Guard absence

1. Restate the expected observation: The pointer is absent.
2. A nil pointer has no target. Compare it with nil instead of dereferencing it.
3. Nil is a useful absence marker only when callers check it.

### Hint for investigation 4: Allocate a zero target

1. Restate the expected observation: The pointer is non-nil and its target is 0.
2. new(int) allocates a zero int and returns its address. Which check concerns the pointer, and which the target?
3. Allocation and initialization are separate questions.

### Hint for investigation 5: Separate copy and target

1. Restate the expected observation: The copied integer remains 3 while the target becomes 9.
2. `copied := *p` reads the current value. Does copied change when `*p` is assigned later?
3. Dereferencing to obtain a scalar value copies that scalar.

### Hint for investigation 6: Transfer an optional update

1. Restate the expected observation: The absent call returns false; the present value becomes 8.
2. Handle nil before any dereference. What should the function return in each case?
3. An explicit boolean tells the caller whether the update happened.
