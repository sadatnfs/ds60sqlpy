# dbt-006: Unit fixtures and integration tests

## Level and prerequisites

Beginner. Direct prerequisites: `dbt-003`, `dbt-004`

**Outcome:** Use controlled fixtures to test transformation logic and real-data checks to test integration.

## Question and mechanism

A unit fixture supplies controlled inputs to test a model's transformation logic. An integration test examines relations produced from an actual source or seed. Both are useful, but they answer different questions. A unit fixture can demonstrate aggregation behavior on a boundary case without claiming that the production input has valid keys or complete coverage.

The worked model sums amounts per customer. Its unit fixture contains two orders for one customer, while the actual loaded seed contains a different customer and amount. The expected result belongs to the fixture, not to the seed. Checking that the seed remains unchanged makes the distinction concrete.

The second case deliberately uses the wrong expected total. dbt must report a failed unit test even though the SQL is executable. A test suite should contain examples that would fail under meaningful defects such as missing grouping, wrong keys, incorrect boundaries or duplicated joins. Tests that only repeat the model's own calculation can agree with the same mistake.

## Syntax and data contract

The unit_tests YAML section names the model, supplied inputs and expected rows. The input declaration ref('raw_orders') substitutes a controlled relation for that dependency. The example first prepares the parent schema, then selects test_type:unit. Result artifacts are inspected for the actual pass or fail status.

## Worked case 1: Use a controlled unit population

The fixture amounts 2 and 3 belong to customer 1 and should sum to 5. The loaded source amount 100 belongs to another row and is not used as the fixture expectation. The program verifies that the underlying seed remains 100.

**Expected evidence:** The unit test passes with total 5 and the source seed is unchanged.

```python
import json
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def artifact(root, name):
    return json.loads((root / "target" / name).read_text())


def unit_case(wrong):
    with tempfile.TemporaryDirectory() as d:
        schema = {
            "unit_tests": [
                {
                    "name": "two_orders_same_customer",
                    "model": "totals",
                    "given": [
                        {
                            "input": "ref('raw_orders')",
                            "rows": [{"customer": 1, "amount": 2}, {"customer": 1, "amount": 3}],
                        }
                    ],
                    "expect": {"rows": [{"customer": 1, "total": 99 if wrong else 5}]},
                }
            ]
        }
        p = project(
            d,
            models={
                "totals": (
                    "select customer, sum(amount)::bigint as total from {{ "
                    "ref('raw_orders') }} group by "
                    "customer"
                )
            },
            seeds={"raw_orders": "customer,amount\n2,100\n"},
            schema=schema,
        )
        invoke(p, "seed")
        invoke(p, "test", "--select", "test_type:unit", succeeds=not wrong)
        result = artifact(p, "run_results.json")["results"]
        assert len(result) == 1 and result[0]["status"] == ("fail" if wrong else "pass")
        assert rows(p, "select amount from raw_orders") == [(100,)]
        return {
            "unit_fixture_total": 5,
            "status": result[0]["status"],
            "production_seed_unchanged": 100,
            "wrong_expectation": wrong,
        }


def example_one():
    return unit_case(False)


if __name__ == "__main__":
    print(example_one())
```

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Add a second customer

Supply a fixture with two customer groups.

**Check:** The expected result has one row per customer.

**Hint:** Make the grouping key observable.


### 2. Add a zero amount

Include a zero-valued order for an existing customer.

**Check:** The total is unchanged but row coverage increases.

**Hint:** Some defects do not change additive totals.


### 3. Change a key

Use two distinct customer identifiers with the same display label.

**Check:** They remain separate groups.

**Hint:** Identity is not a label.


### 4. Remove a grouping clause

Introduce a transformation defect and observe failure.

**Check:** The unit test rejects wrong output or SQL.

**Hint:** Tests need a meaningful counterexample.


### 5. Compare test types

Explain what the unit fixture cannot establish about the source.

**Check:** It cannot prove actual source completeness or uniqueness.

**Hint:** Synthetic inputs have controlled properties.


### 6. Build an independent oracle

Calculate expected totals directly from the small input rows.

**Check:** The oracle does not copy the SQL expression verbatim.

**Hint:** Use transparent arithmetic or a different implementation.


## Diagnose errors and misleading results

An empty selected test set is not a passing unit test. Check how many results were returned and their identifiers. Schema preparation errors should be distinguished from a wrong expected row. Do not change expected output merely because the current implementation produced something else.

## Transfer to independent work

Use controlled fixtures to test transformation logic and real-data checks to test integration. Include at least one counterexample that would detect a plausible defect, and retain the source and expected rows needed to explain the result.
