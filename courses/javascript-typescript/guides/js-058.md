## Purpose, vocabulary and mental model

Zoom changes the mapping between data space and the visible viewport. A transform typically contains a scale factor and translation. Panning changes which portion of the data is visible; it does not change the underlying observations. Keep the original scale and data separate from the transformed view.

Simply scaling an SVG group can also enlarge text and marker sizes, which may or may not be intended. Rescaling an axis from the zoom transform can preserve readable labels while changing the displayed data domain. Clipping keeps marks within the intended plot region.

A usable zoom interface needs bounds and a reset. Pointer gestures can conflict with page scrolling, so test the actual browser behavior. Keyboard controls or preset views provide an alternative to wheel and drag gestures. Never use zoom to conceal a misleading initial domain.

## Syntax anatomy and mechanism

`event.transform.rescaleX(baseScale)` creates a scale for the transformed horizontal view. Use that same scale for marks and axis ticks. The base scale remains unchanged so reset has a stable reference.

Set explicit extent and scaleExtent for predictable behavior. The reference applies a known transform programmatically, checks the visible domain narrows and then resets. This establishes the transformation logic; manual interaction acceptance still includes pointer and keyboard behavior.

## Worked example / walkthrough

### Worked example 1: Inspect a known transform

A transform modifies visual coordinates.

```javascript
const t = d3.zoomIdentity.translate(-100, 0).scale(2);
console.log(t.applyX(100));
```

**Expected observation:** 100 because scale and translation combine as 2*100-100.

### Worked example 2: Derive an axis from the view

The original scale remains available for reset.

```javascript
const view = transform.rescaleX(base);
axis.call(d3.axisBottom(view));
```

**Expected observation:** Ticks represent the transformed data domain rather than the unchanged original domain.

## Debugging and common mistakes

Keep three checkpoints separate: the records after parsing, the domain and geometry after transformation, and the visible marks after rendering. A chart can look plausible while silently dropping records or assigning the wrong scale. Inspect counts, IDs, finite coordinates and meaningful expected values before adjusting colors. A missing mark may come from invalid input, a missing selection, an undefined scale result or clipping outside the viewBox.

The controlled failure for this lesson is: Diagnose enlarged labels after scaling the whole group. Its distinguishing evidence is Geometry and text were transformed together. Preserve that failing case when repairing your program. Do not remove an assertion or broaden a scale merely to hide a wrong input. Explain whether a changed value should affect the data, an encoding, a layout or only presentation.

## Accessibility and interpretation

Give the visualization a descriptive title and a short textual summary of the main result. Keep a table or list when exact values matter. Do not encode a critical category only through color; use labels, shapes or position as appropriate. Interactive controls need keyboard operation and clear focus, and motion should respect the user's reduced-motion preference. Automated DOM checks support, but do not replace, a real keyboard and assistive-technology review.

A data scientist must also defend the statistical meaning. State the population, units, aggregation, missing-value policy and uncertainty where relevant. Synthetic points illustrate a mechanism and do not establish a real-world finding. A beautiful visualization should make a valid claim easier to inspect, not make a weak claim appear certain.
