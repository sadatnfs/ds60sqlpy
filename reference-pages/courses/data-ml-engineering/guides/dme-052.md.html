dme-052: Backup, restore and recovery objectives#

Level: Advanced | Prepared runtime: python-core

Direct prerequisites: dme-024, dme-040, dme-049.

Outcome: Create and restore an actual consistent SQLite backup with checked evidence.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

A backup is useful only if the intended state can be restored#

A file named backup does not establish recoverability. A useful backup has a known source, a consistent captured state, an integrity record, a supported restore procedure and tested consumer readback. A restore exercise should identify what data are recovered, what newer data are absent and which operational steps remain outside the test. Otherwise a successful file copy can create false confidence.

SQLite provides an actual backup API that copies a consistent database view while the source database remains open. This is different from casually copying only the main database file while write-ahead logging is in use. Committed information may be represented in associated state until checkpointing, so a raw filesystem copy needs its own carefully understood consistency procedure. This chapter uses the database API directly rather than teaching an unsafe copy shortcut.

The fixture contains identified package events and a declared logical commit hour. It creates a real WAL-mode source database, captures a backup, adds a later source event and restores into a fresh destination. It also performs an integrity check and verifies row population and package totals. All files are owned temporary artifacts. The program does not inspect or replace an existing learner database.

Separate recovery point from recovery time#

A recovery point describes the latest state available from the chosen recovery source. A recovery point objective, or RPO, is the allowed loss window under a declared failure scenario. A recovery time objective, or RTO, is the target time to restore the required service. Objectives are commitments or design targets; one small experiment is an observation under specific conditions.

The number of lost business events is a separate quantity. A two-hour gap can contain no events or millions. Report both the time boundary and the known population difference where possible. Likewise, timing the database restore function excludes detection, approval, infrastructure preparation, application startup, validation and routing unless those phases are explicitly included.

The program records a measured local restore duration using time.perf_counter, but it labels that duration as a small local observation. The logical hours in the fixture are declared scenario times, not wall-clock timestamps generated during the run. Keeping those two time scales distinct prevents a confusing claim that a millisecond local operation demonstrates a multi-hour business recovery promise.

Worked case 1: restore the accepted backup and quantify the gap#

example_one() commits A with two packages at logical hour one and B with three at hour two. It captures a backup at declared hour two. The source then commits C with one package at hour three. The live source now contains three events and six packages, while the backup contains two events and five packages.

The restore function verifies the backup's exact digest, runs SQLite's integrity check and reconciles its row count and total with the manifest before copying it into a fresh destination through the backup API. The restored rows are A2 and B3. They match the expected captured snapshot, not the source's later state. A restore that returned all three rows would be inconsistent with this backup's declared point in time.

The scenario declares a failure at hour four. The recovery-point gap is two hours, and one known source event occurred after the backup. The program reports those facts alongside the measured local restore time. It does not call the missing C event a corruption: that event was never included in the selected backup. Recovering it would require another retained source, such as a later backup or an appropriate log-replay mechanism.

Worked case 2: reject an unsupported or altered backup candidate#

The second case creates an accepted database with A2 and a valid backup. It first changes only the manifest's schema version to an unsupported value and attempts a restore. The function rejects the candidate before creating the destination. A future backup format may require a different reader or migration; guessing at its fields is not a safe recovery strategy.

The case then changes the owned backup bytes while retaining the original digest declaration. The restore again fails before creating its destination. The accepted source database remains unchanged. This separates validating a recovery candidate from replacing the currently accepted state. A failed recovery attempt should not destroy the only working copy merely because the destination name was reused carelessly.

The code requires a fresh restore destination. A production workflow can restore into an isolated location, validate it, then perform an explicit controlled cutover. That extra boundary is especially useful when the old system is partially working or when operators need to compare recovered and current state before choosing which version to serve.

Complete worked program#

Run in Python Core. SQLite performs actual backup and restore operations on owned local files. The integrity and population checks are executed, while the business failure hours remain explicit synthetic scenario inputs.

"""Actual SQLite online backup and restore with explicit recovery-point evidence."""

import hashlib
import sqlite3
import tempfile
import time
from pathlib import Path


def database(path):
    connection = sqlite3.connect(path)
    connection.execute("pragma journal_mode=wal")
    connection.execute(
        "create table if not exists events(id text primary key not null,"
        "packages integer not null,committed_hour integer not null)"
    )
    connection.commit()
    return connection


def rows(connection):
    return connection.execute(
        "select id,packages,committed_hour from events order by id"
    ).fetchall()


def backup(source, path, backup_hour):
    if path.exists():
        raise ValueError("Backup target must be a fresh owned file")
    destination = sqlite3.connect(path)
    try:
        source.backup(destination)
        assert destination.execute("pragma integrity_check").fetchone() == ("ok",)
        snapshot = rows(destination)
    finally:
        destination.close()
    return {
        "schema_version": 1,
        "sha256": hashlib.sha256(path.read_bytes()).hexdigest(),
        "backup_hour": backup_hour,
        "row_count": len(snapshot),
        "packages": sum(row[1] for row in snapshot),
    }


def restore(path, manifest, destination):
    if manifest["schema_version"] != 1 or destination.exists():
        raise ValueError("Unknown backup contract or nonempty restore destination")
    if hashlib.sha256(path.read_bytes()).hexdigest() != manifest["sha256"]:
        raise ValueError("Backup digest mismatch")
    source = sqlite3.connect(path.as_uri() + "?mode=ro", uri=True)
    try:
        if source.execute("pragma integrity_check").fetchone() != ("ok",):
            raise ValueError("Backup integrity check failed")
        snapshot = rows(source)
        if (
            len(snapshot) != manifest["row_count"]
            or sum(row[1] for row in snapshot) != manifest["packages"]
        ):
            raise ValueError("Backup population differs from its manifest")
        target = sqlite3.connect(destination)
        try:
            source.backup(target)
            assert rows(target) == snapshot
        finally:
            target.close()
    finally:
        source.close()
    return snapshot


def example_one():
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        source = database(root / "source.db")
        try:
            with source:
                source.executemany("insert into events values(?,?,?)", [("A", 2, 1), ("B", 3, 2)])
            manifest = backup(source, root / "backup.db", backup_hour=2)
            with source:
                source.execute("insert into events values('C',1,3)")
            started = time.perf_counter()
            recovered = restore(root / "backup.db", manifest, root / "restored.db")
            elapsed = time.perf_counter() - started
            assert recovered == [("A", 2, 1), ("B", 3, 2)] and len(rows(source)) == 3
            return {
                "restored_rows": recovered,
                "restored_packages": 5,
                "source_packages_before_loss": 6,
                "source_events_after_backup": 1,
                "declared_failure_hour": 4,
                "observed_recovery_point_gap_hours": 4 - manifest["backup_hour"],
                "measured_local_restore_seconds": elapsed,
                "local_timing_is_not_a_production_recovery_objective": True,
            }
        finally:
            source.close()


def example_two():
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        source = database(root / "accepted.db")
        try:
            with source:
                source.execute("insert into events values('A',2,1)")
            manifest = backup(source, root / "backup.db", backup_hour=1)
            original = rows(source)
            try:
                restore(
                    root / "backup.db", {**manifest, "schema_version": 2}, root / "unsupported.db"
                )
            except ValueError:
                pass
            else:
                raise AssertionError("An unknown backup schema was accepted")
            (root / "backup.db").write_bytes(b"changed-owned-backup")
            try:
                restore(root / "backup.db", manifest, root / "corrupt-restore.db")
            except ValueError:
                pass
            else:
                raise AssertionError("Changed backup bytes were accepted")
            assert (
                not (root / "unsupported.db").exists()
                and not (root / "corrupt-restore.db").exists()
            )
            assert rows(source) == original
            return {
                "unsupported_and_corrupt_backups_rejected": True,
                "accepted_database_unchanged": original,
                "failed_restore_targets_not_created": True,
            }
        finally:
            source.close()


def main():
    print("A real restored snapshot and its recovery gap:", example_one())
    print("Reject unusable backup candidates before replacing accepted state:", example_two())


if __name__ == "__main__":
    main()

What a complete recovery procedure must include#

A larger system may need database state, object-store manifests, model artifacts, feature registries, encryption-key access, application configuration and deployment definitions. Backing up only one database can leave the service unable to interpret or serve it. Inventory the state required for a coherent recovery and record the relationships between versions.

Backups also need access control, retention and isolation from the failures they are meant to survive. A backup on the same lost disk does not protect against that disk's failure. Replicating a destructive mistake to every active replica does not replace a retained historical recovery point. Conversely, retaining sensitive backups indefinitely can violate the system's data policy. Recovery and retention must be designed together.

A backup manifest can verify expected bytes and population, but it does not establish authorization or protection against someone replacing both the backup and manifest. Trust, encryption and access review are separate concerns. This fixture uses local owned state and demonstrates consistency checks, not a complete backup-security product.

Validate the restored consumer, not only the database file#

PRAGMA integrity_check examines database structure. It does not prove the business data are complete or correct. The program therefore checks identified rows, counts and totals as well. A real recovery should also run representative application reads, verify schema compatibility, check required indexes or extensions and confirm that the accepted version pointer refers to the restored artifacts.

Restore time can change with dataset size, storage throughput, contention and validation cost. A tiny in-memory or temporary-filesystem result should not be extrapolated linearly without measurement. Run representative drills under documented resource limits and preserve the actual phases and durations. A repeated procedure should also test failure handling, not only the best-case path.

After cutover, monitor for missing updates, duplicate replay and stale caches. If a source log is replayed after restoring a snapshot, its starting position must correspond to the restored state. Starting too early requires safe deduplication; starting too late loses events. The checkpoint and outbox chapters explain the identity boundaries needed to make that continuation reliable.

Failure diagnosis and answered interview discussion#

If a restored database opens but totals are wrong, compare its recovery point and source population before assuming file corruption. If the digest differs, preserve the candidate and investigate transfer, retention or unintended mutation. If a restore succeeds but the application fails, inspect schema, configuration and dependent artifact versions. If recovery takes longer than expected, identify which phases were excluded from the original estimate.

An interviewer may ask, “How do you test a backup?” Explain isolated restore, integrity checks, business reconciliation and application readback. If asked the difference between RPO and RTO, identify the recoverable-state gap and the restoration-time target separately. If asked whether replication is enough, discuss the failure scenarios it covers and those requiring retained historical state.

For an answered extension, a backup at hour two followed by no new events before failure still has a two-hour time gap in this scenario, but zero known lost events. The time objective and data-loss population are related measures, not interchangeable labels. A useful recovery report preserves both.
