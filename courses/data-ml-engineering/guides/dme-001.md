# dme-001: From a record to an engineering decision

**Level:** Beginner | **Prepared runtime:** `python-core`

**Direct prerequisites:** None.

**Outcome:** Trace a small record-to-metric pipeline and define its observable contract.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

## Start with the claim, not the tool

A delivery coordinator asks how many packages were assigned to today's deliveries. Three records describe deliveries A, B and C, with two, three and one packages respectively. A short program can add those values. Engineering begins when we ask what must be true before someone should use that answer: what a record represents, where it came from, whether the list is complete, which values are allowed, and what happens when one record is wrong.

A **record** is one described occurrence or entity. Here its grain is one identified delivery. A **field** is a named part of that record, such as `delivery_id` or `packages`. A **dataset** is a collection of records assembled under some rule. The dataset's grain differs from the requested output: three delivery records become one package total. Six packages does not mean six deliveries. Confusing these quantities can produce a perfectly valid program with the wrong interpretation.

A **transformation** maps inputs to outputs. A **contract** states the conditions under which that mapping is meaningful. Our small contract requires an identified delivery and a positive integer package count. The function also detects a repeated valid delivery identity within this input. It returns rejected-record positions and reasons, rather than quietly dropping them. An accepted partial total is called a candidate because it is not published when any supplied record was rejected.

The contract has a deliberate boundary. It checks the supplied collection. It cannot know whether a delivery was omitted before the collection reached the program, whether the producer counted physical packages correctly, or whether the coordinator has permission to see an individual delivery. Those require additional evidence and controls. Later chapters add delivery manifests, lineage, access decisions and operational monitoring. Do not infer those capabilities from this first function.

## How engineering roles connect

Data engineering makes information available with understood identities, timing, structure and operational behavior. Analytics engineering organizes transformed information into reviewed products that consumers can query. A data scientist may use those products to investigate patterns or estimate outcomes. ML engineering connects a model to a repeatable training and inference system, including how its inputs are produced and what happens after deployment. These responsibilities overlap, and job titles vary between organizations.

The same package-total example can be viewed from each role. The ingestion owner asks whether every expected delivery arrived. The transformation owner asks whether a join can duplicate deliveries. An analyst asks whether the total measures the relevant business activity. A model developer asks whether package count was known at prediction time. A serving owner asks whether the feature is sufficiently recent when a request arrives. The useful handoff is a concrete contract and observable result, not a statement that another team “owns the data.”

It helps to draw a short path:

```text
supplied records -> validation -> candidate aggregation -> publication decision
```

Each arrow is a possible failure boundary. A program can validate types while aggregating the wrong field. An aggregation can be correct while using an incomplete population. A computed candidate can exist without permission to publish it. Keeping these questions distinct is more useful than labeling the entire system healthy after one process exits successfully.

## Read the first Python program

A Python dictionary uses braces to associate names with values. `record["packages"]` reads a field, while `record.get("packages")` returns `None` when it is absent. A list keeps multiple records in order. `def` introduces a named function; indented lines belong to that function. Calling `summarize(records)` runs its steps and returns a new result dictionary.

The `for` loop visits supplied records. `enumerate` supplies both a position and a record, which lets a rejection point back to the original input. `if` and `elif` select a branch. `continue` moves to the next record. The set named `seen` tracks delivery identities already accepted in this call. The separate `accepted` and `rejected` lists make the result auditable. These are local variables, so another call starts with fresh collections.

The integer check uses `type(packages) is int`. This is intentional: Python treats booleans as a subclass of integers, but `True` is not a meaningful package count under our contract. A string such as `"4"` is also rejected. That does not mean text formats are unsuitable for ingestion. It means parsing a producer's text representation must be an explicit earlier step, rather than an accidental conversion hidden in this aggregation.

## Worked case 1: A complete valid supplied collection

The first case passes three explicit records. A contributes two packages, B contributes three and C contributes one. All identifiers are distinct and all package counts satisfy the declared contract. The independent arithmetic is

\[
T=2+3+1=6.
\]

Here \(T\) is the total number of packages in the supplied collection. There are three accepted records, not six. The result reports `input_rows=3`, `accepted_rows=3`, `candidate_packages=6`, an empty rejection list and `publishable=True`.

The assertions check the package total and delivery-row count separately. That distinction matters: a later mistake might preserve the total while losing individual identities, or preserve the number of records while summing the wrong values. The code does not connect to a database or publish a dashboard. Its publication flag is the result of this small local rule, which a larger product would combine with completeness, ownership and consumer requirements.

An empty supplied list deserves a separate question. It can be a valid representation of no deliveries, or evidence that an upstream fetch failed. This function alone cannot distinguish those situations. A delivery manifest or upstream status is needed before treating an empty result as a business zero.

## Worked case 2: A plausible value violates the contract

The second case adds delivery D with `packages="4"`. To a person the characters look like a number, but the value is text. The function retains the original position, records a type/meaning diagnostic and leaves the candidate total at six. It reports four supplied records, three accepted records and one rejected record. Publication is withheld.

The reconciliation check is

\[
N_{\mathrm{input}}=N_{\mathrm{accepted}}+N_{\mathrm{rejected}}=3+1=4.
\]

Each \(N\) counts records. This is a useful invariant because a record cannot disappear from the local audit. It does not prove that all expected deliveries were supplied. The changed case also explicitly tests a boolean package value, which must fail the positive-integer contract.

A tempting repair is to add `int(packages)` inside the aggregation. That is a policy decision, not merely a convenient fix. Which text forms are permitted? Are leading signs, decimal points or whitespace valid? Is a conversion failure quarantined? Does the producer promise integers? Chapter 009 handles ingestion under a declared delivery contract. For now, rejecting the unexpected representation makes the mismatch visible.

## Complete worked program

```python
"""Two complete investigations of a small delivery-summary contract."""


def summarize(records):
    accepted = []
    rejected = []
    seen = set()
    for position, record in enumerate(records):
        if not isinstance(record, dict):
            rejected.append({"position": position, "reason": "record must be a mapping"})
            continue
        delivery_id = record.get("delivery_id")
        packages = record.get("packages")
        if not isinstance(delivery_id, str) or not delivery_id.strip():
            rejected.append({"position": position, "reason": "missing delivery identity"})
        elif delivery_id in seen:
            rejected.append({"position": position, "reason": "duplicate delivery identity"})
        elif type(packages) is not int or packages < 1:
            rejected.append({"position": position, "reason": "packages must be a positive integer"})
        else:
            seen.add(delivery_id)
            accepted.append({"delivery_id": delivery_id, "packages": packages})
    total = 0
    for record in accepted:
        total += record["packages"]
    return {
        "input_rows": len(records),
        "accepted_rows": len(accepted),
        "candidate_packages": total,
        "rejected": rejected,
        "publishable": not rejected,
    }


def example_one():
    records = [
        {"delivery_id": "A", "packages": 2},
        {"delivery_id": "B", "packages": 3},
        {"delivery_id": "C", "packages": 1},
    ]
    result = summarize(records)
    assert result["candidate_packages"] == 6 and result["accepted_rows"] == 3
    assert result["publishable"] is True
    return result


def example_two():
    records = [
        {"delivery_id": "A", "packages": 2},
        {"delivery_id": "B", "packages": 3},
        {"delivery_id": "C", "packages": 1},
        {"delivery_id": "D", "packages": "4"},
    ]
    result = summarize(records)
    assert result["input_rows"] == result["accepted_rows"] + len(result["rejected"]) == 4
    assert result["candidate_packages"] == 6 and result["publishable"] is False
    assert result["rejected"][0]["position"] == 3
    assert summarize([{"delivery_id": "Z", "packages": True}])["publishable"] is False
    return result


def main():
    print("Complete valid delivery:", example_one())
    print("Changed input, publication withheld:", example_two())


if __name__ == "__main__":
    main()
```

## Diagnose results before changing the code

If the output says six packages but three deliveries, nothing is wrong: those are different units. If a candidate total is printed while `publishable=False`, do not describe it as the accepted product. It is diagnostic information about the valid subset. If an unknown field appears in an input, this small function ignores it; strict whole-record schemas are introduced later. If a repeated identity is rejected, do not assume the first copy was necessarily the correct physical observation. A later conflict-resolution policy may require rejecting both copies or consulting a source version.

A real incident report should separate what was observed from what remains unknown. “One supplied record had a text package count” is supported. “The producer lost no data” is not supported by this function. “The package count is safe for an operational decision” needs a broader acceptance contract. These distinctions prevent a locally correct example from becoming an exaggerated system claim.

## Where this pattern is useful

Use a small explicit transformation when learning a producer contract, designing a unit test or discussing an output with a consumer. The same structure applies to measurements, inventory events, click records or model requests. As data grows, the implementation may move to SQL, Polars or a distributed engine, but the record grain, allowed values and publication decision still need to be stated.

## Answered interview discussion

**What is the difference between a data pipeline and a data product?** A pipeline is the mechanism that moves and transforms information. A product includes the consumer-facing meaning, interface, ownership and acceptance expectations. A pipeline can finish while its output is unsuitable for a consumer.

**Does a zero process exit prove correctness?** No. It establishes one process-level observation. Numerical checks, population reconciliation and operational requirements establish different facts. The second case returns normally while deliberately reporting that publication is not allowed.

**Would you drop invalid records to keep the job running?** Not without an explicit policy. Quarantine can preserve availability, but the consumer must know whether the result is partial and what was excluded. A silently changed population is especially dangerous for rates and model evaluation.

**How would this become production work?** Identify the producer and consumer contracts, define completeness and freshness, establish ownership, make state and retries explicit, and test the full delivery path. Choosing a larger engine before answering those questions does not resolve them.
