A beginner's mental model for this lesson#

An ordinary view is a saved query: every read reruns the joins. A materialized view runs its query once and stores the rows, like a table filled by CREATE TABLE ... AS, except that PostgreSQL remembers the query so REFRESH MATERIALIZED VIEW can rerun it later. Between refreshes the stored rows do not follow changes to orders or order_items.

The learner view joins 13,085 order lines to products and orders, then groups them into one row per category and calendar month. All six categories sell in every month, so the row count is six times the number of months: 276 on a late-2026 load, from February 2023 through the current month. Its revenue column keeps the unrounded line value unit_price * quantity * (1 - discount), which totals 2,355,647.1235. The header column orders.total_amount sums to 2,355,646.89 because each order was rounded to cents, so reconcile the view against order_items, not against order totals.

Freshness is how far the stored rows lag their sources. It is a fact about time, not about query speed, and the person who relies on the view needs to know when it was last refreshed.

Two worked SQL examples#

Example 1#
CREATE MATERIALIZED VIEW mv_category_month_revenue AS
SELECT
  p.category,
  date_trunc('month', o.order_date)::date AS month,
  SUM(oi.unit_price * oi.quantity * (1 - oi.discount)) AS revenue
FROM
  order_items oi
  JOIN products p ON p.product_id = oi.product_id
  JOIN orders o ON o.order_id = oi.order_id
GROUP BY
  p.category,
  date_trunc('month', o.order_date);

How to read it: This is data definition: the SELECT inside runs once, and psql reports the number of stored rows as a SELECT command tag. The date_trunc expression in GROUP BY must match the one in the select list; the ::date cast only changes how the month is displayed.

Expected result/shape: SELECT 276 on a late-2026 load, one row per (category, month). Check that no pair repeats by grouping the view on both columns with HAVING COUNT(*) > 1, which returns nothing, and that SUM(revenue) equals the same line expression summed over order_items.

Example 2#
SELECT
  *
FROM
  mv_category_month_revenue
ORDER BY
  month DESC,
  revenue DESC
LIMIT 50;

How to read it: The read touches only the stored rows. It sorts by month DESC and then revenue DESC, so the six categories of the newest month come first, ranked by revenue.

Expected result/shape: 50 rows: eight months of six categories, then the two best categories of a ninth month. The first six rows belong to the current, partial month, so their revenue is roughly half of the full month that follows. Within a month, two categories with equal revenue would have no tie-breaker, so add category to the sort if you compare runs.

Deep dive and reference#

What you will learn#

  • Store the result of an expensive query in a materialized view (MV).
  • Refresh cached results when source tables change.
  • Compare freshness, storage, and query cost with querying base tables.

How the learner script uses the current schema#

The script creates mv_category_month_revenue from orders, order_items, and products. Its grain is one row per (category, month), and revenue is line price times quantity after discount. It queries and refreshes the MV, then rolls the object back.

A normal view stores only SQL and executes it on every read. A materialized view stores rows and can be indexed, but those rows are stale until refreshed.

Refresh behavior#

  • REFRESH MATERIALIZED VIEW replaces the stored contents and takes an ACCESS EXCLUSIVE lock, so it blocks reads of that MV during refresh.
  • REFRESH ... CONCURRENTLY keeps the view readable, but needs an already populated view and a unique index on plain columns covering every row (for example (category, month)); only one refresh per view runs at a time. Unlike CREATE INDEX CONCURRENTLY, it may run inside a transaction block. It computes a difference against the old contents, so it can be slower than an ordinary refresh when many rows change.
  • PostgreSQL 17 requires the MAINTAIN privilege on the view (granted to the owner, or through the predefined pg_maintain role) to refresh it.
  • PostgreSQL does not provide general native incremental MV refresh; selective rollup tables are a separate design.

Errors that explain the refresh rules#

Each rule in the previous section has an error message. Run this block after Example 1 has built the view. The savepoint lets the transaction continue after the failure, and the final ROLLBACK removes the index again.

BEGIN;
SAVEPOINT a;

REFRESH MATERIALIZED VIEW CONCURRENTLY mv_category_month_revenue;

-- ERROR: cannot refresh materialized view ... concurrently
-- HINT: Create a unique index with no WHERE clause on one or more columns
ROLLBACK TO a;

CREATE UNIQUE INDEX ON mv_category_month_revenue (category, month);

REFRESH MATERIALIZED VIEW CONCURRENTLY mv_category_month_revenue;

ROLLBACK;

With the unique index in place the concurrent refresh succeeds, even inside a transaction block. A view created WITH NO DATA fails differently: selecting from it reports that it "has not been populated", and a concurrent refresh reports that CONCURRENTLY cannot be used until it is. pg_class.relispopulated shows which state a view is in.

Practice map#

Several prompts above change orders inside the transaction; read the view before and after each REFRESH so you can see which numbers moved and which stayed stale.

Pitfalls and validation#

  • Reconcile the MV's total revenue to the source query before measuring speed.
  • A fast stale result can be wrong for the consumer's freshness requirement.
  • The compact seed may make the raw query as fast as or faster than the MV.
  • Document refresh ownership and failure behavior before relying on an MV.
  • The learner transaction safely removes the demonstration MV at rollback.

Expanded practice lab#

Prompts 3-6 focus on the materialized view's data contract. A new base row is invisible until refresh, so record both data time and refresh time. Concurrent refresh requires a qualifying unique index and cannot be demonstrated as a first population inside this rollback-only lesson.

Reconcile the view to the exact line-revenue definition it materializes; stored order totals are a separate measure. Grouped aggregates emit no row for an absent dimension combination, so any displayed zero must come from an explicit dimension/date spine and outer join.

Exercise 1: Weekly revenue by country#

The view is built inside the file's transaction and stays there for exercises 2 to 6, which all read it. The file's final ROLLBACK removes the view and its index, so nothing is left behind.

BEGIN;
SET search_path TO training, public;

CREATE MATERIALIZED VIEW mv_weekly_country_revenue_solution AS
SELECT
  date_trunc('week', o.order_date)::date AS week,
  c.country,
  SUM(o.total_amount) AS revenue,
  COUNT(*) AS orders
FROM
  orders o
  JOIN customers c USING (customer_id)

The materialized-view plan should avoid source joins and aggregation. On this small dataset, wall-clock differences can be noisy; compare plan work and buffers as well as execution time.

Reasoning and verification#
  • Inputs/evidence: For sql-36 Exercise 2, run EXPLAIN (ANALYZE, BUFFERS) on the base-table aggregate that defines the view, then on SELECT week, country, revenue, orders FROM mv_weekly_country_revenue_solution.
  • Expected result/shape: For sql-36 Exercise 2, expected output: two plans. The base-table plan aggregates all 4362 joined orders in a HashAggregate, while the view plan is a single Seq Scan on the materialized view; both top nodes report the same number of actual rows.
  • Independent verification: For sql-36 Exercise 2, compare the top node's actual rows in both plans (they must match) and the buffers each plan touched; then run both queries without EXPLAIN and confirm that EXCEPT in both directions returns no rows. Timings vary from run to run, so compare buffers and row counts rather than milliseconds.
  • Intermediate relation check: Both top nodes report 1,080 actual rows. The base plan hash-joins 4,362 orders to 500 customers before its HashAggregate; the view plan is one Seq Scan on the stored rows.
  • Clause check: The base plan touches 74 shared buffers, 65 for orders and 9 for customers, while the view scan touches 8. The aggregate is estimated at 4,362 groups but produces 1,080, because the planner has no statistics for the date_trunc expression, the same blind spot Day 35 measured.
  • Alternative/trade-off: One run took about 3.7 ms for the base query and 0.07 ms for the view. The saving is real but small at this size, and it is paid back at every refresh, which reruns the full aggregate.
  • Edge case: Equal results here only show that the view is fresh immediately after it was built. In a running system the same comparison doubles as a freshness test: any rows returned by EXCEPT are changes the view has not caught up with.

Pitfalls#

  • A normal REFRESH MATERIALIZED VIEW blocks concurrent reads of that view. REFRESH ... CONCURRENTLY keeps the view readable, but needs an already populated view and a unique index on plain columns covering every row (for example (category, month)); only one refresh per view runs at a time. Unlike CREATE INDEX CONCURRENTLY, it may run inside a transaction block.
  • Refresh is not automatic. Define freshness ownership and monitoring before using a materialized view for reporting.
  • Materialized views duplicate data and add refresh cost; they are not a default replacement for indexing or query repair.

Exercise 4: Explain concurrent-refresh eligibility#

The unique (week, country) index supplies a stable row identity required by concurrent refresh. Initial population still uses an ordinary refresh, because CONCURRENTLY requires an already populated view. This rollback lab also keeps the ordinary refresh because the view was created inside the uncommitted lesson transaction: no other session can read it, so there is no read availability to preserve, and the concurrent diff-and-apply refresh would only add work.

Reasoning and verification#

-- Exercise 1: weekly revenue by country.

SELECT
  date_trunc('week', o.order_date)::date AS week,
  c.country,
  SUM(o.total_amount) AS revenue,
  COUNT(*) AS orders
FROM
  orders o
  JOIN customers c USING (customer_id)
GROUP BY
  date_trunc('week', o.order_date),
  c.country;

CREATE UNIQUE INDEX idx_mv_weekly_country_solution ON mv_weekly_country_revenue_solution (week, country);

UPDATE
  orders
SET
  total_amount = total_amount + 1
WHERE
  order_id = (
    SELECT
      MIN(order_id)
    FROM
      orders);

SELECT
  (
    SELECT
      SUM(total_amount)
    FROM
      orders) AS live_total,
  (
    SELECT
      SUM(revenue)
    FROM
      mv_weekly_country_revenue_solution) AS stale_mv_total;

  indexdef

  pg_indexes
WHERE
  schemaname = 'training'
  AND tablename = 'mv_weekly_country_revenue_solution';

SELECT

    SELECT
      SUM(total_amount)
    FROM
      orders) AS header_revenue,

    SELECT
      SUM(quantity * unit_price * (1 - discount))
    FROM
      order_items) AS line_revenue;

-- Exercise 6: a spine supplies requested combinations; the outer join turns
-- missing aggregate rows into an explicit display zero by policy.
WITH months AS (
  SELECT DISTINCT
    date_trunc('week', order_date)::date AS week
  FROM
    orders
),
countries AS (
  SELECT DISTINCT
    country
  FROM
    customers
)
SELECT
  m.week,
  c.country,
  COALESCE(v.revenue, 0) AS revenue
FROM
  months m
  CROSS JOIN countries c
  LEFT JOIN mv_weekly_country_revenue_solution v ON v.week = m.week
    AND v.country = c.country
  ORDER BY
    m.week DESC,
    c.country
  LIMIT 20;
