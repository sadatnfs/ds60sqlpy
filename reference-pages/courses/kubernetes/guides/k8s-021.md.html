k8s-021: NetworkPolicy with enforcement evidence#

Level and prerequisites#

Intermediate; about 120 minutes plus review. Direct prerequisites: k8s-018, k8s-020. The chapter separates desired configuration, API acceptance, controller observation and application evidence.

Learning objectives#

Prove a policy changes permitted connectivity on a policy-capable fixture.

Vocabulary and concepts#

A NetworkPolicy describes allowed traffic relationships for selected Pods when the cluster networking implementation enforces it. Creating the API object is not evidence that packets are filtered. The course therefore requires a separately qualified policy-capable CNI and before/after client observations for this host lab.

The example isolates ingress to app=hello and then allows TCP8080 from same-namespace Pods labeled role=lesson-client. Policies are additive:the allowed traffic is the union of applicable allow rules. A deny-all ingress policy plus a matching allow policy does not mean the deny rule overrides the allow. Egress isolation is a separate direction and is not enabled by this ingress-only example.

The normal browser adapter does not admit NetworkPolicy or arbitrary client labels. Its basic hello success cannot establish isolation. This worksheet uses real policy manifests and a synthetic traffic matrix until an exclusive policy-enabled lease supplies the required live capability.

Read selectors and rule composition#

spec.podSelector chooses destination Pods governed by this policy. In an ingress peer, a podSelector without a namespaceSelector refers to Pods in the policy's namespace. A peer containing both namespaceSelector and podSelector combines them, while separate entries in the from list are alternatives. Confusing those shapes can allow more traffic than intended.

policyTypes declares which traffic directions are isolated. An empty ingress list for selected Pods allows no ingress through this policy, but other applicable policies can still allow traffic. Both source egress and destination ingress policies may need to permit a connection when both ends are isolated.

The port rule is TCP8080, matching the application path. DNS egress is not blocked by this ingress-only example. Do not copy a generic default-deny-both-directions manifest and assume name resolution will remain available without an explicit design.

Prove enforcement with paired controls#

Before policy application, both synthetic clients should reach the same healthy backend. After isolation and the explicit allow, only the labeled permitted client should succeed; the other should fail within a bounded timeout. The allowed path is a control showing that the service did not simply stop working for everyone.

If both still succeed, investigate policy support, selectors and direction. If both fail, inspect application readiness, ports and the allow rule before declaring enforcement successful. Retain CNI identity/capability, policy UID and actual client results. A timeout alone does not uniquely identify policy denial.

Use only approved local client/server fixtures in the owned namespace. The host provides the CNI capability; the learner does not install a plugin, modify node networking or test unrelated tenants.

Worked example / walkthrough#

Worked example 1: Combine deny and allow#

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: hello-deny-ingress
spec:
  podSelector:
    matchLabels:
      app: hello
  policyTypes:
  - Ingress
---
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: hello-allow-client
spec:
  podSelector:
    matchLabels:
      app: hello
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          role: lesson-client
    ports:
    - protocol: TCP
      port: 8080

Expected: Selected hello Pods allow same-namespace lesson-client TCP8080 traffic under the combined ingress rules.

Common pitfalls#

NetworkPolicy governs supported network behavior under the implementation's semantics. It is not application authentication, Secret authorization or a virtual-machine boundary. Host/node traffic and implementation-specific behavior need separate understanding.

A passed two-client test proves the observed allowed/denied paths, not every possible protocol or source. Report the exact labels, port, direction and target identities. Leave the live row unavailable when the CNI has not been qualified.

Networking depth supplement#

NetworkPolicy requires an enforcing network implementation. API acceptance proves the policy object was stored, not that a forbidden connection was blocked. A meaningful isolation test has both an allowed owned caller and a denied owned caller, with the exact CNI capability recorded. The deep policy sequence is k8s-058 and k8s-059.

Policy rules are additive. A narrow default-deny policy does not override a different policy that permits a broad set of peers. In one peer entry, namespaceSelector and podSelector combine as conditions; separate entries are alternatives. Review the complete applicable policy set and the YAML list structure before describing the intended access matrix.

DNS is a network dependency. Egress restrictions can block name resolution even while an allowed direct-IP request succeeds. The resolver may be cluster DNS or a node-local cache, and both UDP and TCP behavior can matter. Use the prepared implementation's actual resolver path rather than copying a generic DNS allowance without checking its scope.
