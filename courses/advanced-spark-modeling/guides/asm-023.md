# asm-023: An optimizer rule with a proof obligation

Tutorial mode. Stage: advanced. Direct prerequisites: `asm-022`, `spark-021`.

## Starting point and result

An optimizer rule replaces one expression tree with another that must preserve meaning for every supported input. The teaching project simplifies a duplicate nonnegative clamp on BIGINT values. It avoids tempting floating-point rewrites whose behavior can differ for signed zero, NaN, overflow or exceptions.

## Mechanism: prove a restricted identity

Define \(c(x)=\max(x,0)\) on signed 64-bit integers, with null propagated to null. For any nonnull x, c(x) is nonnegative, so applying c again leaves it unchanged:

\[c(c(x))=c(x).\]

No addition or multiplication occurs, so this clamp cannot overflow. Null also satisfies the rewrite because both paths return null. The rule therefore matches only `ClipCount(inner: ClipCount)` and replaces the outer node with the inner node. It does not rewrite arbitrary functions that happen to have a similar name.

A rule transforms expression trees within a logical plan. It should terminate and avoid oscillating with another rule. This rewrite reduces the number of clamp nodes, providing a simple decreasing measure. It is also idempotent: after one application there is no nested matching pair at that location. Real optimizer batches may apply rules repeatedly, so these properties matter.

## Worked case: observe the actual tree change

The probe queries a nested clamp over a DataFrame column. The analyzed plan contains two `ClipCount` nodes; the optimized plan contains one. Checking the actual node types is stronger than searching a formatted string for a function name. The program asserts the counts and then executes the result.

Using a column avoids a trivial constant-only query that might disappear through unrelated constant folding. The fixture therefore exercises the custom rule's intended structure. It still remains a small exact-version probe, not a general optimizer verification framework.

## Worked case: boundaries, null and a dangerous alternative

Input values include the minimum long, minus one, zero, one, the maximum long and null. Expected results are zero for the first three, the original positive values for the next two and null for the last. These cases cover the sign boundary and representational extremes.

Contrast this with casually rewriting floating `x + 0.0` to x. Signed zero and engine-specific arithmetic semantics can matter, and a rewrite involving reordered expressions can also alter exception or nondeterministic behavior. The lesson is not that every familiar identity is invalid. It is that a rule needs an explicit domain and proof under the engine's actual semantics.

## Failure diagnosis

If the plan changes but results differ, the rewrite is wrong regardless of speed. If results match but the node count stays two, registration or rule matching may be wrong. If optimizer execution loops, inspect whether two rules undo each other's transformations. Keep the exact plan before and after the rule as diagnostic evidence.

## Interview discussion

**Can you rewrite any algebraically equivalent likelihood?** Only after accounting for machine arithmetic, nulls, types, nondeterminism and error behavior. Numerical stability can make one algebraic form preferable, but changing it still requires tests and a declared contract.

**Why test interpreted and generated execution for a rule?** A rewritten tree may select different generated code. Rule correctness includes the execution paths selected by the replacement, not only its printed shape.

# Worked reference: Idempotent clamp proof

This is an editable reading/project reference. It has no ordinary pad Run action.

For BIGINT x, define c(x)=max(x,0), preserving null. If x<0, both c(c(x)) and c(x) are zero. If x>=0, both are x. If x is null, both are null. No arithmetic overflows because comparison and selection do not add or multiply.

The probe uses a range-backed column so local-table constant folding does not erase the expression before the custom rule is inspected. It expects two typed nodes in the analyzed plan and one in the optimized plan, plus identical boundary outputs. This structural observation supplements the proof; it does not replace it.
