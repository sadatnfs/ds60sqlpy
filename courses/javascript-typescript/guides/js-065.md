# js-065: Dashboard state, cross-filtering and reproducible views

## Level and prerequisites

Advanced; about 110 minutes plus independent practice. Direct prerequisites: `js-064`. This is the D3.js specialization within the JavaScript path. Use the original language and browser lessons whenever syntax or DOM behavior is unfamiliar.

## Learning objectives

Build two coordinated views from one state. Design a reproducible saved view. Produce a chart whose data transformation, visual encoding and interaction can be explained and checked independently.

## Purpose, vocabulary and mental model

A dashboard coordinates multiple views around shared analytical state. Filters, selected IDs and display options belong in an explicit model. Each chart should derive its visible records from that model rather than mutating another chart’s DOM as an informal message bus.

Cross-filtering can change denominators. If a category chart selects one group, a rate chart must state whether its denominator is the filtered group or the full population. A dashboard can be internally consistent in code while making a misleading comparison because the analytical universe changed silently.

Pure transformation functions are easier to test than event-heavy code. A filter function takes rows and state and returns a derived result without editing the source. Rendering then consumes that result. This separation helps preserve reproducibility, reset behavior and a clear explanation of what the current view means.

## Syntax anatomy and mechanism

Use one `state` object and an `update(nextState)` function that derives data and renders every view. Native controls dispatch state changes. Keep the original rows immutable by convention or freeze them in a small example. A reset restores a known initial state.

The reference links a category filter to bars and a numeric summary. Programmatic control activation checks state wiring, while manual keyboard review checks the actual user experience. Saving a dashboard view should record filter values and data identity, not only a screenshot.

## Worked example / walkthrough

### Worked example 1: Derive data without mutation

The filter is a pure computation.

```javascript
const derive=(rows,state)=>rows.filter(d=>state.group==="all"||d.group===state.group);
```

**Expected observation:** Source rows remain unchanged; the output reflects the current group choice.

## Debugging and common mistakes

Keep three checkpoints separate: the records after parsing, the domain and geometry after transformation, and the visible marks after rendering. A chart can look plausible while silently dropping records or assigning the wrong scale. Inspect counts, IDs, finite coordinates and meaningful expected values before adjusting colors. A missing mark may come from invalid input, a missing selection, an undefined scale result or clipping outside the viewBox.

The controlled failure for this lesson is: Diagnose a rate denominator changing silently. Its distinguishing evidence is The analytical question changed without a visible label. Preserve that failing case when repairing your program. Do not remove an assertion or broaden a scale merely to hide a wrong input. Explain whether a changed value should affect the data, an encoding, a layout or only presentation.

## Accessibility and interpretation

Give the visualization a descriptive title and a short textual summary of the main result. Keep a table or list when exact values matter. Do not encode a critical category only through color; use labels, shapes or position as appropriate. Interactive controls need keyboard operation and clear focus, and motion should respect the user's reduced-motion preference. Automated DOM checks support, but do not replace, a real keyboard and assistive-technology review.

A data scientist must also defend the statistical meaning. State the population, units, aggregation, missing-value policy and uncertainty where relevant. Synthetic points illustrate a mechanism and do not establish a real-world finding. A beautiful visualization should make a valid claim easier to inspect, not make a weak claim appear certain.
