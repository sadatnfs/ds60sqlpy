# AD-safe branches, transforms and numerical domains

Start with: tmb-045, tmb-004, tmb-027.

Outcome: Distinguish data-controlled logic, parameter-controlled logic and invalid arithmetic.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter checks a piecewise gradient against finite differences and evaluates a stable softplus. The separately prepared [C++ API probes](../projects/tmb-cpp-api/README.md) compile `models/conditional.cpp`, and `check.R` checks its conditional tape crossings; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

Automatic differentiation follows implemented operations. An ordinary C++ branch on fixed observation type can be appropriate, such as selecting an event or censor contribution. A branch on a changing parameter can create a recorded-path problem if later evaluations cross the branch boundary. A supported conditional-expression operation represents the selection inside the derivative machinery, but it does not make a nonsmooth function smooth.

The pinned TMB headers use compatible conditional-expression facilities such as `CppAD::CondExpGt` in their convenience functions. Framework-specific support still needs qualification when moving between CppAD and TMBad. Avoid assuming arbitrary C++ library operations participate in AD.

## Key terms

- **Taping:** Recording the operations performed for one evaluation so derivatives can be computed later; a plain C++ branch on a parameter records only the path taken.
- **Conditional expression:** An AD-aware selection such as `CppAD::CondExpGt` that keeps both branches available inside the derivative machinery.
- **Domain safety:** Building valid intermediate arguments before selection, because an unused branch such as `log(x)` can still be evaluated at an invalid `x`.
- **Smoothness:** Continuity of derivatives; a conditional expression selects branches correctly but cannot make a kinked function such as \(\max(x,0)^2\) twice differentiable.

### Worked case A: a piecewise quadratic

Let \(f(x)=\max(x,0)^2\). Away from zero its derivative is \(2x\) for positive x and zero for negative x; at zero the first derivative exists and is zero, but the second derivative changes discontinuously. The companion checks values and first derivatives on both sides. An AD conditional can select the branch at evaluation time, while a tape built from a plain host-language branch may retain one path.

```cpp
Type positive = CppAD::CondExpGt(x, Type(0), x, Type(0));
Type objective = positive * positive;
```

This is a numerical illustration, not a normalized probability model. Its purpose is to expose branch behavior before using such logic inside an actual likelihood.

### Worked case B: an unused invalid branch can still be dangerous

Writing a conditional expression with `log(x)` as one candidate does not necessarily prevent that candidate expression from being evaluated when x is negative. Construct safe intermediate arguments first, then apply the mathematically intended selection. Do not replace invalid inputs by arbitrary epsilons without explaining how that changes the function.

The companion contrasts a stable softplus identity with naive exponentiation at large x. Stable values are necessary, but derivatives and curvature must also be checked. A positive transform can overflow; a sigmoid can saturate; a probability parameter can become poorly identified near a boundary.

### Answered discussion

**Does AD-safe mean statistically valid?** No. It concerns execution and differentiation, not model meaning. **Can I use branching to repair non-identification?** No. Constraints can define a different model, but they need scientific justification. **Is a data branch always harmless?** If data later change that branch, reconstruct or deliberately retape under a tested contract.

See the [pinned convenience helpers](https://github.com/kaskr/adcomp/blob/master/TMB/inst/include/convenience.hpp). Test crossings and extreme values explicitly; checking only one positive initial point misses these errors.

### Worked case C: reading the gradient table

For \(f(x) = \max(x, 0)^2\) the companion prints four rows (closed-form values):

```text
   x    value   gradient   numeric
-2.0    0.00       0.0       0.0
-0.1    0.00       0.0       0.0
 0.1    0.01       0.2       0.2
 2.0    4.00       4.0       4.0
```

None of the evaluation points lies within \(h = 10^{-6}\) of zero, so each central difference stays on one branch. On the positive branch the function is an exact quadratic, for which a central difference has no truncation error, and the only discrepancy is rounding, far below the \(10^{-7}\) tolerance. A point such as \(x = 5 \times 10^{-7}\) would straddle the kink: the forward evaluation uses \(x^2\) while the backward one returns 0, and the second-derivative estimate there would be meaningless even though the first derivative is still close.

### Worked case D: a plain branch on a recorded tape

A plain C++ `if` on a parameter is executed once while the tape is recorded. Suppose the template is taped at a starting value \(x = 0.5\):

```cpp
Type positive;
if (x > Type(0))
  positive = x; // evaluated once, at x = 0.5
else
  positive = Type(0);
Type objective = positive * positive;
```

The recorded operation sequence is simply `x * x`. Re-evaluating that tape at \(x = -1\) returns 1 and a gradient of \(-2\), while the intended function has value 0 and gradient 0 there (hand-derived). The `CondExpGt` version records both candidates and the comparison, so the same re-evaluation selects 0. Whether a particular TMB build retapes between calls depends on the framework and settings, which is exactly why the lesson asks for a crossing test rather than reasoning about it.

The softplus row has a similar lesson about where overflow happens. `softplus(1000)` returns \(1000 + \log(1 + e^{-1000}) = 1000\), because the second term underflows harmlessly to 0. The naive form computes `exp(1000)`, which overflows to `Inf`, so `log1p(Inf)` is `Inf`. The derivative of softplus is the logistic function, which equals 1 to double precision at \(x = 1000\) and 0.5 at \(x = 0\), where softplus itself is \(\log 2 = 0.693147\). A positive scale written as `softplus(eta)` therefore has a gradient that vanishes for very negative \(\eta\): the transform is stable, but the optimizer receives almost no signal there.

### Where invalid arithmetic hides

The dangerous case is a candidate evaluated before selection. In `CondExpGt(x, Type(0), log(x), Type(0))` the `log(x)` term is computed for every \(x\), so a negative value produces `NaN` in that candidate and, depending on the engine, in its derivative. Writing `log(CondExpGt(x, Type(0), x, Type(1)))` first builds a safe argument (it is 1 when \(x \le 0\), whose log is 0), then takes the log, and gives the intended selection without ever passing a negative value to `log`.

### Base-R companion (runs in the classroom)

```r
f <- function(x) pmax(x, 0)^2;g <- function(x) ifelse(x > 0, 2 * x, 0)
x <- c(-2, -.1, .1, 2);h <- 1e-6
numeric_gradient <- (f(x + h) - f(x - h)) / (2 * h)
print(data.frame(x = x, value = f(x), gradient = g(x), numeric = numeric_gradient));stopifnot(max(abs(g(x) - numeric_gradient)) < 1e-7)
softplus <- function(x) pmax(x, 0) + log1p(exp(-abs(x)))
print(c(stable = softplus(1000), naive = log1p(exp(1000))))
```
