## Schedule requests without changing their histories

A model's numerical function can be correct while a serving system returns the wrong result because it reused the wrong state. Incremental decoding makes this risk visible: cached keys and values summarize a particular prefix under particular model and tokenizer identities. A scheduler decides when each request advances, but it must not change what prefix that request represents. Interleaving is an execution decision, not a license to mix contexts.

The fixture has request A with tokens[2,5,7] and request B with tokens[1,3]. These are supplied input sequences, not newly sampled answers. The program processes them one token at a time in the order A0,B0,A1,B1,A2, then compares each request's concatenated incremental logits with an independent full-prefix evaluation. This tests state isolation under an explicit schedule. It does not implement a production continuous-batching server or measure end-user latency.

### Define a cache as an owned state transition

For one request r, let P_r be its committed token prefix and K_r,V_r the cached key/value arrays. Processing a new token extends the prefix and produces new state. The position offset must equal the length already represented by that cache. A model using learned absolute positions or rotary positions can produce a different result if the same token is assigned the wrong offset, even when every tensor shape is legal.

The fixture's cache key is(request ID, model version, tokenizer version). This makes three compatibility assumptions explicit. A different request cannot reuse another request's private prefix state. A changed model cannot assume old K/V values were computed by its current weights. A changed tokenizer cannot assume that an integer ID still denotes the same input event. Real systems may need additional configuration identity, such as positional scaling, precision, adapter selection or attention layout.

A cache key is a naming convention, not proof that the named state is correct. The program still needs to associate the actual tensors with the key and compare the output against a known computation. Likewise, a model hash identifies bytes only to the extent its hashing procedure covers the relevant state and configuration. The purpose of an identity key is to prevent accidental reuse, not to replace numerical checks.

### Trace the five scheduling actions

At the start, neither request has cached tokens. After A0, A's cache length is 1 and B's is 0. After B0, both are 1. After A1, lengths are 2 and 1. After B1, both are 2. After A2, they are 3 and 2. Each action advances one request only.

| Action | A cache length | B cache length | Newly processed token |
| --- | ---: | ---: | --- |
| A0 | 1 | 0 | A's token 2 at offset 0 |
| B0 | 1 | 1 | B's token 1 at offset 0 |
| A1 | 2 | 1 | A's token 5 at offset 1 |
| B1 | 2 | 2 | B's token 3 at offset 1 |
| A2 | 3 | 2 | A's token 7 at offset 2 |

The final lengths are conservation checks: three A inputs and two B inputs were processed exactly once under this schedule. They do not prove output correctness by themselves. A cache could have the right length but contain keys from another request, wrong positions or another model version. The full-prefix comparison is the independent numerical oracle.

Now imagine using one shared cache variable. After A0, processing B0 would see A's state and offset 1 instead of an empty B prefix at offset 0. The next logits would represent a mixed sequence[2,1], not B's intended prefix[1]. The output might remain finite and have the expected vocabulary shape. This is a semantic state error, so checking for NaNs or tensor dimensions would not catch it.

### Separate prefill from decode work

Prompt prefill processes an existing sequence of input tokens, often with many query positions in one operation. Incremental decode adds newly generated tokens, usually one per active request per step, while reusing prior state. Their computation and latency profiles differ. A large prompt can occupy a scheduler for substantial work before producing the first answer token, even if later decode steps are small.

Useful latency measures therefore identify the event being timed. Time to first token includes queuing, prompt processing and the first generation step. Inter-token latency measures spacing between subsequent emitted tokens. Total completion time includes the requested output length. Throughput counts completed work over an interval and can rise while individual latency worsens. These are different observations, not synonyms for "fast."

The local reference measures none of these serving metrics. Its fixed sequence of five actions teaches the correctness invariant that a scheduler must preserve before performance comparisons matter. A faster schedule that swaps request histories is not an optimization of the same task.

### Batching adds coordinates rather than removing ownership

A batch dimension can place several requests into one tensor operation. Requests may have unequal prefix lengths, so padding, per-request positions and key availability need explicit treatment. If every row is assigned the same cache offset solely because it shares one rectangular tensor, shorter requests can receive incorrect positions. If a padding key remains visible, one request's artificial slots can affect its attention normalizer.

One implementation may keep separate caches and group compatible steps. Another may use packed or paged storage with a mapping from logical request positions to physical blocks. Those designs change storage and scheduling, but the logical invariant remains: the state read for request r must correspond to r's committed prefix under the matching model configuration. Physical adjacency does not imply shared conversational authority.

A useful test compares each batched or interleaved request with an independently evaluated version of the same prefix. Use unequal lengths and distinct token values so a permutation or offset mistake becomes visible. Testing two identical requests of equal length can hide a swapped-row bug because the wrong association produces the same numbers.

### Budgets, cancellation and memory pressure are state policies

The fixture's supplied schedule processes three A tokens and two B tokens and then checks those counts against declared caps. It does not run a general admission loop that dynamically rejects excess work. A production scheduler would need to enforce a cap before advancing a request, update consumed-token accounting, and define what happens when EOS, cancellation or a timeout arrives.

Cancellation should stop future work for the affected request and release only its owned state when the operation is safe to do so. It should not clear every cache merely because one request failed. Conversely, retaining canceled state indefinitely can consume memory or enable accidental reuse if an identifier is recycled. An ownership-aware lifecycle needs terminal states and a clear rule for when an ID becomes reusable.

Under memory pressure, evicting a cache means choosing between recomputation, queuing or refusing new work. Recomputing from a retained permitted prefix can preserve semantics at extra cost. Reusing a different request's cache to avoid allocation cannot. A model/version change may invalidate all relevant cached states, but that is a deliberate compatibility event, not ordinary request cleanup.

### Keep sampling state separate from deterministic model state

The current lesson feeds known tokens and compares logits. A real generator also has a sampling policy, random-number state, stopping rules and output budget. If requests share one mutable random generator, changing their scheduling order can change which random draws each receives. That may alter individual generated texts even when each request's conditional distribution is correct. Reproducibility claims must state whether they concern logits, distributional behavior or exact sampled sequences.

A request-specific random stream can make one kind of replay easier, but it does not fix a wrong K/V association or model mismatch. Test the deterministic forward contract first, then test sampling and stopping separately. The distinction will become especially important in speculative decoding, where the random-draw schedule intentionally changes while the target law is preserved.
