# mle-007: Materialization, online retrieval and freshness decisions

## Level and prerequisites

Intermediate. Direct prerequisites: `mle-006`

**Outcome:** Populate a real online feature store and enforce a consumer freshness contract.

## Question and mechanism

An online store serves feature values for low-latency inference. Materialization moves selected source values into that store. A successful online lookup establishes that a value was retrieved, not that it is fresh enough for the current decision. The application needs a freshness policy with a clearly defined clock and a response for stale or missing inputs.

The first case actually materializes the local Feast view into SQLite and retrieves two customers. The second compares each retained feature timestamp with a declared decision time. One value is one day old and the other three days old; a two-day maximum accepts only the first. The timestamp is included as a feature value so the consumer's policy is directly inspectable.

The fixture uses fixed historical dates to make the calculation reproducible. It does not claim those values are fresh relative to the real execution date. The longer-lived project later uses a recorded training clock and actual serving-time checks. Keep retrieval, freshness and model quality as separate evidence throughout the lifecycle.

## Syntax and data contract

materialize receives an explicit interval and writes the prepared online store. get_online_features retrieves named fields for specified entity rows. The consumer computes age from a retained feature timestamp and applies both a nonfuture condition and an upper bound. A FeatureView TTL does not replace a tested online-serving freshness policy.

## Worked case 1: Populate and read the actual online store

The first case materializes feature versions through a declared endpoint and checks the SQLite file and retrieved values. It uses the real SDK rather than a dictionary standing in for a feature store.

**Expected evidence:** Latest usage values are [20,5] for the two customers.

```python
import os
import tempfile
from datetime import UTC, datetime, timedelta
from pathlib import Path

import pandas as pd


def configure_local_tools():
    os.environ.update(
        FEAST_USAGE="False",
        DO_NOT_TRACK="true",
        MLFLOW_ENABLE_TELEMETRY="false",
        MLFLOW_DISABLE_AGENT_HINT="1",
        DBT_SEND_ANONYMOUS_USAGE_STATS="false",
    )


def make_store(directory):
    configure_local_tools()
    from feast import Entity, FeatureStore, FeatureView, Field, FileSource, ValueType
    from feast.types import Float32, Int64

    root = Path(directory)
    root.mkdir(parents=True, exist_ok=True)
    (root / "feature_store.yaml").write_text(
        "project: classroom\nprovider: local\nregistry: "
        "registry.db\nonline_store:\n  type: sqlite\n  path: "
        "online.db\nentity_key_serialization_version: "
        "3\n"
    )
    stamps = pd.to_datetime(["2024-01-01", "2024-01-03", "2024-01-01"], utc=True)
    data = pd.DataFrame(
        {
            "customer_id": [1, 1, 2],
            "feature_time": stamps,
            "usage": [10.0, 20.0, 5.0],
            "tickets": [1, 2, 3],
            "feature_epoch": [int(t.timestamp()) for t in stamps],
        }
    )
    data.to_parquet(root / "features.parquet", index=False)
    customer = Entity(name="customer", join_keys=["customer_id"], value_type=ValueType.INT64)
    view = FeatureView(
        name="customer_features",
        entities=[customer],
        ttl=timedelta(days=30),
        schema=[
            Field(name="usage", dtype=Float32),
            Field(name="tickets", dtype=Int64),
            Field(name="feature_epoch", dtype=Int64),
        ],
        source=FileSource(path=str(root / "features.parquet"), timestamp_field="feature_time"),
    )
    store = FeatureStore(repo_path=str(root))
    store.apply([customer, view])
    return store


def online_case(directory):
    store = make_store(directory)
    store.materialize(datetime(2023, 12, 31, tzinfo=UTC), datetime(2024, 1, 4, tzinfo=UTC))
    data = store.get_online_features(
        features=["customer_features:usage", "customer_features:feature_epoch"],
        entity_rows=[{"customer_id": 1}, {"customer_id": 2}],
    ).to_dict()
    return store, data


def example_one():
    with tempfile.TemporaryDirectory() as d:
        store, data = online_case(Path(d) / "features")
        try:
            assert data["usage"] == [20.0, 5.0]
            assert (Path(d) / "features/online.db").exists()
            return {"online_usage": data["usage"], "real_sqlite_materialization": True}
        finally:
            store.teardown()


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Apply an independent freshness policy

The second case uses decision time 2024-01-04 and a two-day maximum. It checks the actual ages and decisions. A stored value can therefore be retrievable yet rejected for this prediction.

**Expected evidence:** Ages are 86,400 and 259,200 seconds; freshness decisions are [true,false].

```python
import os
import tempfile
from datetime import UTC, datetime, timedelta
from pathlib import Path

import pandas as pd


def configure_local_tools():
    os.environ.update(
        FEAST_USAGE="False",
        DO_NOT_TRACK="true",
        MLFLOW_ENABLE_TELEMETRY="false",
        MLFLOW_DISABLE_AGENT_HINT="1",
        DBT_SEND_ANONYMOUS_USAGE_STATS="false",
    )


def make_store(directory):
    configure_local_tools()
    from feast import Entity, FeatureStore, FeatureView, Field, FileSource, ValueType
    from feast.types import Float32, Int64

    root = Path(directory)

    (root / "feature_store.yaml").write_text(
        "project: classroom\nprovider: local\nregistry: "
        "registry.db\nonline_store:\n  type: sqlite\n  path: "

        {
            "customer_id": [1, 1, 2],
            "feature_time": stamps,

    )
    store = FeatureStore(repo_path=str(root))
    store.apply([customer, view])
    return store


def online_case(directory):

    store.materialize(datetime(2023, 12, 31, tzinfo=UTC), datetime(2024, 1, 4, tzinfo=UTC))
    data = store.get_online_features(
        features=["customer_features:usage", "customer_features:feature_epoch"],
        entity_rows=[{"customer_id": 1}, {"customer_id": 2}],
    ).to_dict()
    return store, data


def example_two():
    with tempfile.TemporaryDirectory() as d:
        store, data = online_case(Path(d) / "features")
        try:
            decision = int(datetime(2024, 1, 4, tzinfo=UTC).timestamp())
            max_age = 2 * 86400
            ages = [decision - int(value) for value in data["feature_epoch"]]
            accepted = [0 <= age <= max_age for age in ages]
            assert ages == [86400, 259200] and accepted == [True, False]
            return {
                "ages_seconds": ages,
                "freshness_decisions": accepted,
                "retrieval_does_not_replace_consumer_freshness_policy": True,
            }
        finally:
            store.teardown()


if __name__ == "__main__":
    print(example_two())
```


## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Change the decision clock

Move the declared decision time forward by one day.

**Check:** The first value reaches the boundary and the second remains stale.

**Hint:** Compute age from the same feature timestamp.


### 2. Reject future metadata

Give a feature timestamp after the decision time.

**Check:** The age check rejects it.

**Hint:** Freshness requires a valid clock direction.


### 3. Separate publication and observation

Explain why republishing an old value should not automatically reset its data age.

**Check:** The answer retains the measurement/availability clock.

**Hint:** A write timestamp and feature age can differ.


### 4. Handle missing entities

Request an entity absent from the store and define the response.

**Check:** Missing inputs do not silently become observed zeros.

**Hint:** Retrieval can succeed at the protocol level without a feature.


### 5. Inspect materialization scope

Limit the source interval and verify retrieved state.

**Check:** The selected versions are explained.

**Hint:** An interval is part of the ingestion operation.


### 6. Test serving separately

Explain which checks are still needed beyond SDK retrieval.

**Check:** They include schema, transformation and model-version consistency.

**Hint:** The store returns features, not a justified decision.


## Diagnose errors and misleading results

If predictions use stale values, inspect the actual returned timestamp and the consumer policy. A successful materialization is not proof that every entity was covered. A recent write can also carry old information. Keep retrieval status, data age and downstream decision evidence separate.
