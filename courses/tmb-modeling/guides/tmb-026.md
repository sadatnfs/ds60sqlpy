# MakeADFun maps, profiles and safe data changes

Start with: tmb-025, tmb-004, tmb-014.

Outcome: Explain which construction options change parameter dimension, target or recorded operations.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter reconstructs a full parameter vector from a `map`-style factor, so it does not call `MakeADFun`. In the separately prepared [owned project](../projects/tmb-local/README.md), `tests/public_api.R` builds a `TMB::MakeADFun` object with `map = list(log_sigma = factor(NA))` and profiles `mu` with `TMB::tmbprofile`; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

`MakeADFun` is the central construction API. `data` supplies observations and fixed inputs; `parameters` supplies named coordinates and shapes. `map` fixes or ties components. `random` asks for latent integration, normally using Laplace approximation. `profile` profiles selected nuisance components without the corresponding Laplace volume correction. These switches do not merely tune speed: some change the inferential target.

A profile likelihood at a fixed target value minimizes over nuisance parameters. A marginal likelihood integrates over latent variables with their specified density. Both may call an inner optimizer, but their mathematical results differ.

## Key terms

- **map:** A `MakeADFun` argument of factors that fixes components (NA) or ties components with equal levels, changing the free-coordinate dimension.
- **random:** A `MakeADFun` argument naming latent parameters to integrate out, normally by Laplace approximation, which changes the inferential target.
- **profile:** A `MakeADFun` argument naming nuisance components to optimize out without the Laplace volume correction, a different target from integration.
- **Retaping:** Re-recording the operation sequence after data changes; the safe public workflow is to construct a fresh objective rather than mutate internals.

### Worked case A: fixed and tied coordinates

A vector \(\beta=(\beta_1,\beta_2,\beta_3)\) mapped with `factor(c(1,1,NA))` has one free coordinate: the first two components are tied and the third stays at its supplied value. The companion reconstructs this rule explicitly. In a direct native construction:

```r external
obj <- TMB::MakeADFun(data, parameters,
  map = list(beta = factor(c(1, 1, NA))),
  DLL = "reviewed_model"
)
names(obj$par)
```

Check the resulting `par` rather than sending a vector with the old dimension. A tied intercept and slope would generally be an odd scientific assumption even if the code allows it.

### Worked case B: changing data and reconstructing the objective

If a data value changes from positive to negative and controls a C++ branch, recorded operations may change. Changing vector length or category count changes shapes too. The safe public workflow is to construct a fresh objective from the new validated data and current intended parameter starts. The companion shows that two equal-length datasets still have different objective values and identities.

Internal object-environment helpers such as retaping are implementation details, not separately exported public APIs in this pinned namespace. Do not build a stable classroom feature around undocumented mutation of `obj$env$data` or an assumed tape cache. If a specialized workflow deliberately uses internals, pin the source version and test changed values, shapes and branches separately.

### Answered discussion

**Can `checkParameterOrder=FALSE` fix mismatched names?** Suppressing a check does not repair the model contract. **Does `hessian=TRUE` mean every latent/Hessian mode is interchangeable?** No; derivative availability depends on construction and framework. **Can profiling a latent variable replace integrating it?** Only if that different target is what the analysis intends. Keep the distinction in result labels and comparisons.

The [MakeADFun manual](https://cran.r-project.org/web/packages/TMB/TMB.pdf) includes `atomic`, `ADreport`, `intern`, `integrate` and advanced controls. Use the ordinary reviewed settings until a concrete derivative or integration need justifies changing them.

### Worked case C: what the map does to `obj$par`

The companion starts from \(\beta=(2,2,7)\) with `factor(c(1, 1, NA))`. The reconstruction function fills every non-`NA` position from the free vector by factor level, so the single free value 3 produces \((3,3,7)\). A native construction with the same map would expose one fixed coordinate:

```r external
obj <- TMB::MakeADFun(data,
  parameters = list(beta = c(2, 2, 7)),
  map = list(beta = factor(c(1, 1, NA))), DLL = "reviewed_model"
)
length(obj$par) # expected: 1
names(obj$par) # expected: "beta"
obj$fn(3) # objective evaluated at beta = c(3, 3, 7)
```

The comments state expected shapes, not recorded output. The important consequence is the gradient. Because the first two components share one coordinate, `obj$gr(3)` returns a single number equal to the sum of the partial derivatives with respect to \(\beta_1\) and \(\beta_2\), and it contains nothing for \(\beta_3\). A downstream driver that still expects three gradient entries would either fail on a length check or, worse, silently recycle. The third component stays at 7 throughout; if the start had been a placeholder like 0, the fit would condition on that placeholder.

The companion's second block shows why data changes need a fresh object. Datasets `a = (1, 2, 3)` and `b = (1, 2, 9)` have the same length, so a shape check passes, but their toy objectives \(\tfrac12\sum x_i^2\) are 7 and 43. If an analyst edited the data inside an existing object's environment and the template had a branch on a data value, the stored operation sequence could correspond to the old branch while the new values were read. Building a new objective with `MakeADFun` from validated `b` avoids that question entirely.

### Profile versus random on the same coordinate

Suppose a template has a nuisance mean \(\mu\) and a scale. Listing `mu` in `profile` replaces it, at each outer evaluation, by its inner optimum and reports a profile objective; listing it in `random` integrates it with a Laplace correction \(\tfrac12\log\det H\). For a Gaussian mean with known prior, the two differ by that log-determinant term, which depends on the scale parameter. An outer optimizer on the profile objective therefore tends toward a smaller scale estimate than the marginal objective. Labeling the result with the construction options keeps that difference visible.

### Base-R companion (runs in the classroom)

```r
start <- c(2, 2, 7); mapping <- factor(c(1, 1, NA))
reconstruct <- function(free) {
  result <- start; result[!is.na(mapping)] <- free[as.integer(mapping[!is.na(mapping)])]; result
}
print(reconstruct(3));stopifnot(identical(reconstruct(3), c(3, 3, 7)))
a <- c(1, 2, 3);b <- c(1, 2, 9)
print(c(same_length = length(a) == length(b), objective_a = sum(a^2) / 2, objective_b = sum(b^2) / 2))
```
