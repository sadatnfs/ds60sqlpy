## Starting point and result

A compiled TMB model is native machine code linked against an R/TMB/toolchain environment. Its source is portable only to the extent that the code and dependencies support the target. The compiled artifact itself is not universally portable. This chapter explains how the Spark/TMB project prepares and verifies the model rather than compiling unpredictably inside every task.

## Mechanism: the ABI is part of the artifact identity

An application binary interface includes machine architecture, operating-system conventions, calling conventions and library compatibility. A macOS ARM shared library cannot be loaded as a Linux AMD64 model. Even on matching Linux architecture, incompatible R versions, C++ runtime libraries or TMB dependencies can cause load failures or subtler defects.

Compile the model in a controlled preparation environment matching execution. Record source hash, compiler version and flags, R version, TMB version, architecture and dependency image identity. The execution image contains the resulting library and the R wrapper that loads it. A worker should fail clearly if the expected artifact is absent or incompatible rather than fetching an arbitrary replacement over the network.

Do not compile the same model for every row. Compilation is expensive and can race on shared filenames. If a project genuinely supports user-defined model compilation, use isolated source-bound work directories and an explicit preparation step, then cache by the full compatibility key. A source hash alone does not capture the ABI.

## Worked case: prepare once, construct state per process

The owned project's preparation compiles the original teaching model for its Linux target. During a case run, each R process loads that compatible artifact and creates its own `MakeADFun` state for its assigned data. Reusing the immutable compiled code is safe under the contract; reusing a live native objective object across processes is not.

A successful `partition-normal` receipt should identify both compilation and execution evidence. Merely finding a `.so` file does not prove it loads or evaluates correctly. Compare its objective and gradients with a small closed-form normal-model oracle.

## Worked case: reject a mismatched artifact

Consider an ARM64 image handed an AMD64 shared library with the correct filename. The path exists, but the loader cannot execute its machine code. The correct response is a preparation failure that names the incompatible architecture, not a fallback that silently substitutes a Python model and labels the TMB test passed.

Likewise, a stale library built from an older C++ source must not be accepted because its modification time looks recent. Verify the recorded source/compatibility identity. A synthetic `failure-contracts` case can exercise missing-artifact and invalid-output handling without touching learner data.

## Failure diagnosis

Undefined symbols often indicate a dependency or ABI mismatch. A segmentation fault may indicate incompatible native code or a defect in the model; retain process exit status and bounded stderr. A timeout may be optimization cost rather than compilation. Separate build, load, objective evaluation and optimization timestamps in diagnostics.

## Interview discussion

**Can Docker solve all native compatibility issues?** It can make the userspace environment reproducible, but architecture and hardware support still matter. Build and test native targets separately and do not label emulation as native qualification.

**What should be sent through Spark?** Immutable data, configuration and compatible artifact identities. Live pointers, loaded-library handles and AD tapes should remain in the owning process.
