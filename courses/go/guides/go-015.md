# go-015: Generics and constraints without losing semantics

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-014

## Learning objectives

Write a generic function whose constraint admits exactly the operations it needs, including named underlying types. Along the way, explain type parameter, constraint, type inference; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Generics express algorithms whose structure is shared across several types. A type parameter is constrained by the operations the algorithm requires. comparable permits equality and map keys; it does not permit ordering or arithmetic. A constraint using a type set can admit underlying integer types with the ~ operator. Generic code still needs a meaningful domain contract: adding signed integers can overflow, floating equality can surprise, and pointer equality is not deep value equality. Prefer a normal function when only one concrete type is useful. A useful generic abstraction removes real duplication while preserving clear errors and readable call sites.

## Vocabulary and concepts

- **Type parameter:** A placeholder type selected for a generic instantiation.
- **Constraint:** The allowed types and operations for a type parameter.
- **Type inference:** Deriving a type argument from call arguments.

## Syntax anatomy and reasoning

`func first[T any](items []T) (T,bool)` declares a type parameter `T`. `var zero T` obtains its zero value for an empty result. A custom constraint such as `interface { ~int | ~int64 }` admits named types with those underlying types. Type inference often determines `T` from arguments. A constraint belongs to compile-time capability checking; it is not runtime validation of application data.

## Worked example / walkthrough

### Worked example 1: Reuse an element contract

Call first with an integer slice and a string slice.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Count int
type Integer interface{ ~int | ~int64 }

func first[T any](items []T) (T, bool) {
	if len(items) == 0 {
		var zero T
		return zero, false
	}
	return items[0], true
}
func unique[T comparable](items []T) []T {
	seen := map[T]bool{}
	out := []T{}
	for _, x := range items {
		if !seen[x] {
			seen[x] = true
			out = append(out, x)
		}
	}
	return out
}
func sumInts[T Integer](items []T) T {
	var out T
	for _, x := range items {
		out += x
	}
	return out
}

func main() {
	// Reuse an element contract
	{
		a, okA := first([]int{4, 5})
		b, okB := first([]string{"red", "blue"})
		check(okA && okB && a == 4 && b == "red", "generic first")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The results are 4 and red with presence true.

The algorithm needs indexing and length, not knowledge of the element representation. That makes any an honest constraint here.

### Worked example 2: Handle a generic empty value

Call first with an empty integer slice.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Count int
type Integer interface{ ~int | ~int64 }

func first[T any](items []T) (T, bool) {
	if len(items) == 0 {
		var zero T
		return zero, false
	}
	return items[0], true
}
func unique[T comparable](items []T) []T {
	seen := map[T]bool{}
	out := []T{}
	for _, x := range items {
		if !seen[x] {
			seen[x] = true
			out = append(out, x)
		}
	}
	return out
}
func sumInts[T Integer](items []T) T {
	var out T
	for _, x := range items {
		out += x
	}
	return out
}

func main() {
	// Reuse an element contract
	{
		a, okA := first([]int{4, 5})
		b, okB := first([]string{"red", "blue"})
		check(okA && okB && a == 4 && b == "red", "generic first")
	}

	// Handle a generic empty value
	{
		v, ok := first([]int{})
		check(v == 0 && !ok, "empty generic")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The result is zero with presence false.

A zero value alone cannot distinguish an empty input from a first element equal to zero. The boolean preserves that information.

## Common pitfalls and diagnosis

The usual generic mistake is choosing a constraint by habit. any cannot compare, comparable cannot order or add, and a numeric constraint does not make overflow or float equality disappear. Another is assuming comparable means deep equality: two pointers are equal only when they point to the same variable. If only one concrete type is ever used, an ordinary function is clearer.

## Progressive hints

### Hint for investigation 1: Reuse an element contract: change one input

1. Restate the expected observation: The results are 4 and red with presence true.
2. first only indexes and measures the slice. Which constraint does that require?
3. first returns 5 for the edited slice, so `a==4` fails while b is still red. Inference and indexing work; only the input element changed.

### Hint for investigation 2: Handle a generic empty value: diagnose an edited check

1. Restate the expected observation: The result is zero with presence false.
2. An empty slice has no first element. What does `var zero T` hold for int?
3. For an empty slice first returns the zero value 0, so `v!=0` is false and the check panics. The boolean, not the value, reports absence.

### Hint for investigation 3: Preserve stable uniqueness

1. Restate the expected observation: The result is 2 then 1.
2. The map records membership and the slice records order. Which occurrence of 2 is kept?
3. A map tracks membership while the result slice preserves order.

### Hint for investigation 4: Admit a named underlying type

1. Restate the expected observation: The result is Count(7).
2. ~int admits types whose underlying type is int. Does the result keep the name Count?
3. The tilde constraint admits the underlying int representation while preserving the named result type.

### Hint for investigation 5: Test the empty sum identity

1. Restate the expected observation: The result is int64 zero.
2. `var out T` starts at zero for every allowed type. What does the loop add for an empty slice?
3. The identity must make sense for every allowed type.

### Hint for investigation 6: Transfer equality semantics

1. Restate the expected observation: Red and red remain distinct.
2. comparable uses ==. Are Red and red equal strings?
3. comparable uses the language equality operation.
