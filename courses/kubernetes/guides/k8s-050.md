# k8s-050: Service data planes: iptables, IPVS, nftables and eBPF

## Level and prerequisites

Intermediate; about 120 minutes plus optional supervised host observations. Direct prerequisites: `k8s-049`. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

## Learning objectives

Draw the watch-to-packet sequence. Plan an implementation-specific incident review. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

## Purpose, vocabulary and mental model

The Service API describes desired routing behavior. A data-plane implementation turns that intent into packet handling on nodes. kube-proxy is a common component that watches Service and endpoint state and programs the supported backend for the cluster version. Other networking implementations can provide Service routing through eBPF or different mechanisms.

iptables, IPVS and nftables refer to Linux packet-processing facilities with different models and operational properties. Their availability, maturity and support status depend on the Kubernetes and operating-system version. Do not assume every current cluster supports every mode or that an old performance claim applies unchanged.

An eBPF-based implementation can attach programmable logic at particular kernel hooks. That changes how traffic is handled and observed, but it does not eliminate the need for endpoint identity, policy, routing and application acceptance. The API contract and the implementation evidence remain separate layers.

## Mechanism and field-by-field reasoning

Begin diagnosis by identifying the installed implementation, version and active mode. A Service object can be correct while a node’s programmed state is stale or broken. Conversely, reading a packet rule does not prove the application accepts a connection.

The course does not modify node packet tables or switch proxy modes. Use the synthetic control/data-plane sequence and consult the prepared environment’s operator documentation. Any privileged host inspection is a separately authorized capability, not part of a browser lesson.

## Trace the request or control path

```text
Service/EndpointSlice API -> watch/reconciliation -> node data-plane state
packet arrives -> implementation lookup/translation -> selected endpoint -> reply path
```

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

The same Service intent can have different implementations.

```text

implementationA: kube-proxy supported kernel mode
implementationB: CNI-provided eBPF service routing
```

**Expected observation:** The intended mapping is shared; observation tools and failure modes can differ.

### Worked example 2: Classify a stale-node symptom

This is a synthetic incident comparison.

```text

```

## Diagnosis, failure boundaries and common mistakes

The controlled failure in this chapter is: Diagnose one-node-only Service failure. Its distinguishing result is Compare node-local data-plane and policy behavior. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
