# cpp-015: RAII and unique ownership

## Level and prerequisites

Intermediate; 105 minutes. Direct prerequisites: `cpp-014`.

Learner artifact: [cpp-015.cpp](../lessons/cpp-015.cpp). [Case ledger](../fixtures/cpp-015-cases.json). [Solutions](../solutions/cpp-015_solutions.md).

## Learning objectives

Tie resource lifetime to an object and justify unique ownership.

## Vocabulary and concepts

RAII means acquiring a resource in an object and releasing it when that object leaves scope. unique_ptr owns one dynamically allocated object and cannot be copied. Its destructor releases the owned object even when an exception unwinds the scope. The owner must not be confused with a borrowed raw pointer.

<!-- terms:start -->

- **RAII:** acquiring a resource in an object and releasing it when that object leaves scope.
- **`unique_ptr`:** a move-only smart pointer that is the single owner of one dynamically allocated object.
- **`make_unique`:** constructs an object and returns the `unique_ptr` that owns it.
- **ownership transfer:** moving a `unique_ptr`, which hands cleanup responsibility to the destination and leaves the source empty.
- **borrowed raw pointer:** a non-owning pointer to an object managed elsewhere, which must never be used to delete it.

<!-- terms:end -->

## Syntax and mechanism

`std::make_unique<Record>(...)` constructs an owner without a separate raw new. `std::move(owner)` transfers ownership; it does not clone the resource. A destructor should release resources without throwing during stack unwinding.

## Trace the mechanism

At scope entry the unique_ptr becomes responsible for one allocation. Moving it hands that responsibility to another owner; the moved-from pointer no longer releases the object. During exception unwinding the current owner still runs its destructor, which reduces the live count. Count resources at scope boundaries rather than depending on an informal promise to call delete later. Resource lifetime and the lifetime of a borrowed pointer must be drawn separately.

<!-- depth:start -->
## Exclusive ownership and deterministic destruction

A unique_ptr represents one owning responsibility for a dynamically allocated object. The pointee can be borrowed through a raw pointer or reference, but those borrows do not become additional owners. When the unique_ptr is destroyed, its deleter releases the resource. The useful property is not that delete disappeared syntactically; it is that cleanup follows the lifetime of a visible owner on every ordinary scope-exit path.

make_unique<int>(7) constructs an int and returns its owner. Moving p into q transfers that owning responsibility, leaving p empty for unique_ptr's specified move behavior. It does not move the integer 7 to a different allocation in this example. The address can stay the same while the object responsible for cleanup changes. Dereferencing the moved-from p would be invalid because it no longer owns or points to the integer.

The Tracked fixture uses a counter to make lifetime observable. Construction increments live and destruction decrements it. Inside the owner scope, live is 1; after the scope, it is 0. The counter itself must outlive Tracked because Tracked borrows its address. A resource wrapper can still contain an unsafe borrow if that dependency is ignored. RAII solves cleanup ownership, not every possible lifetime relationship automatically.

Exception unwinding destroys fully constructed local owners. If a later operation throws, a unique_ptr already in scope still releases its pointee. By contrast, a raw new followed by a throwing operation before a matching delete can leak. The correct fix is to establish ownership immediately, not to add a delete to one guessed error branch. For non-memory resources, the same structure can use an appropriate custom deleter.

Exclusive ownership is not appropriate for every graph. shared_ptr introduces shared lifetime responsibility and additional costs, while raw pointers can express non-owning access. Choose based on who must keep the object alive, not on which pointer syntax seems easiest. The examples deliberately avoid shared ownership so the transfer and destruction points are inspectable.
<!-- depth:end -->

## Worked example / walkthrough

Example 1 moves a `std::make_unique<int>(7)` into a second owner and checks that the source pointer is now empty. Example 2 uses `Tracked` to count live objects: the counter reads 1 while the owner exists and 0 after its scope closes, with no `delete` written anywhere. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-015-example-1.cpp)

```cpp
#include <cassert>
#include <iostream>
#include <memory>
#include <utility>

struct Tracked {
  int *live;
  explicit Tracked(int &count) : live(&count) { ++*live; }
  ~Tracked() { --*live; }
  Tracked(const Tracked &) = delete;
  Tracked &operator=(const Tracked &) = delete;
};
int main() {
  auto p = std::make_unique<int>(7);
  auto q = std::move(p);
  assert(!p && q && *q == 7);
  std::cout << "cpp-015 example 1 checks passed\n";
  return 0;
}
```

**Expected:** With assertions enabled, the program exits with status 0 and prints:


### Worked example 2

[Complete program 2](../examples/cpp-015-example-2.cpp)

```cpp
#include <cassert>
#include <iostream>
#include <memory>

struct Tracked {
  int *live;
  explicit Tracked(int &count) : live(&count) { ++*live; }
  ~Tracked() { --*live; }
  Tracked(const Tracked &) = delete;
  Tracked &operator=(const Tracked &) = delete;
};
int main() {
  int live = 0;
  {
    auto owner = std::make_unique<Tracked>(live);
    assert(live == 1);
  }
  assert(live == 0);
  std::cout << "cpp-015 example 2 checks passed\n";
  return 0;
}
```

## Exercises

### Exercise 1: Trace ownership

Draw p and q before and after moving unique_ptr<int>(7).

**Expected result/shape:** One live allocation; exactly one owner at each point.

**Verify:** Check the drawing against Worked example 1's assertion `!p && q && *q == 7`: after the move `p` is null, `q` owns the single int 7, and no second allocation appears.

**Progressive hints:** Moving transfers the pointer ownership.

### Exercise 2: Check normal cleanup

Run the Tracked scoped case.

**Expected result/shape:** live=1 inside and 0 afterward.

**Verify:** Print `live` inside the inner scope and after it closes, and confirm the two lines show 1 and 0, matching Worked example 2's assertions.

**Progressive hints:** Destructor cleanup is tied to scope.

### Exercise 3: Check exceptional cleanup

Throw after constructing Tracked and catch outside.

**Expected result/shape:** live=0 after catch.

**Verify:** Create a `std::unique_ptr<Tracked>` inside `try`, throw `std::runtime_error`, and assert `live == 0` in the `catch` block, which shows the destructor ran during unwinding.

**Progressive hints:** Stack unwinding destroys the owner.

### Exercise 4: Reject accidental copy

Try auto q=p with unique_ptr.

**Expected result/shape:** Compile failure; move only when ownership should change.

**Verify:** Compile the scratch line and keep the error about the deleted copy constructor of `std::unique_ptr`; `auto q = std::move(p);` must compile instead.

**Progressive hints:** unique_ptr disables copying by design.

### Exercise 5: Handle empty owner

Default-construct unique_ptr<int> and inspect Boolean state.

**Expected result/shape:** false, with no dereference.

**Verify:** Assert `!std::unique_ptr<int>{}` and confirm the program never applies `*` to the empty pointer.

**Progressive hints:** An empty owner has nothing to destroy.

### Exercise 6: Transfer to a collection

Own three unique_ptr<int> values in a vector then leave scope.

**Expected result/shape:** All three allocations released; no manual delete loop.

**Verify:** Put three `std::unique_ptr<Tracked>` values in a vector inside a scope and assert `live == 3` inside and `live == 0` afterward; the code must contain no `delete`.

**Progressive hints:** Composed RAII owners clean up recursively.

## Self-check

After `auto q = std::move(p)`, why is `p` empty while `q` owns 7? For Example 2, explain what returns `live` to 0 when the scope closes, given that no code calls `delete`.

## Common pitfalls

If live remains 1 after the scope, inspect whether ownership escaped or was released without cleanup. If a moved-from unique_ptr is dereferenced, test its empty state and use the new owner instead. Do not construct two unique_ptr objects from the same raw pointer: that creates two deletion responsibilities for one allocation. A destructor counter proves the fixture lifecycle, not the safety of every borrowed pointer elsewhere in the program.
