Day 48: E-commerce Project, Part 3: Affinity and Attribution#

How to run this lesson#

Open sql-48 from ./classroom (PostgreSQL), choose Whole SQL lesson (psql) and work in your copy at .learning/sql/sql-48/lesson/workspace/sql/postgres-60day/day48_project1_ecommerce_part3.sql. The lesson reads order_items and products for the basket half and events plus orders for the attribution half, all in advanced_sql_training. The script runs inside BEGIN ... ROLLBACK, so nothing it does persists. A clean psql run prints the 50 most frequent product pairs, then a five-row first-touch/last-touch table, then your exercise results. The fixture spaces each customer's events and orders across that customer's lifetime, measured from the moment you loaded it, so a few attribution counts can differ by a handful from the numbers quoted here. Launcher and recovery steps are in the SQL study guide, and the notebook option is in its notebook section.

Level and prerequisites#

  • Level: Advanced

A beginner's mental model for this lesson#

The lesson has two halves that share one discipline: decide what a single row means before you count. In the basket half, one row of items is a distinct (order, product) membership. Joining items to itself on order_id makes one row per pair of products in the same order, and the condition a.product_id < b.product_id keeps each unordered pair once, so product 14 with product 45 is never counted again as 45 with 14 or as 14 with itself. On the course data order_items already has no repeated (order, product) lines, 13,085 lines across 4,362 orders, but the GROUP BY or DISTINCT step is what protects the count when a future order lists a product twice.

In the attribution half the anchor is a purchase event, not an order. Every customer has 40 events that rotate through five types, so there are exactly 4,000 purchase events. A touch is any other event by the same customer in the half-open window [purchase_time - 7 days, purchase_time), and its campaign comes from metadata ->> 'campaign'. Because one purchase can have touches from several campaigns, counting purchases per campaign double-counts, while dividing one credit by the number of distinct campaigns makes the credits sum back to the number of assisted purchases. Read each query in logical clause order, naming the grain after every CTE.

Two worked SQL examples#

Both excerpts come from the learner script and run in order inside its transaction.

Example 1#
WITH items AS (
  SELECT
    order_id,
    product_id
  FROM
    order_items
  GROUP BY
    order_id,
    product_id
),
pairs AS (
  SELECT
    a.product_id AS p1,
    b.product_id AS p2,
    COUNT(*) AS together
  FROM
    items a
    JOIN items b ON a.order_id = b.order_id
      AND a.product_id < b.product_id
  GROUP BY
    a.product_id,
    b.product_id
)
SELECT
  p1.name AS product_a,
  p2.name AS product_b,
  together
FROM
  pairs
  JOIN products p1 ON p1.product_id = pairs.p1
  JOIN products p2 ON p2.product_id = pairs.p2
ORDER BY
  together DESC
LIMIT 50;

How to read it: items collapses order_items to one row per (order, product). pairs self-joins it within each order, keeps a.product_id < b.product_id, and counts orders per pair in together. The outer query only swaps the two ids for product names and keeps the 50 largest counts.

Expected result/shape: 50 rows of product_a, product_b and together. The largest count is 32, and 255 of the 770 pairs share it, so the 50 rows you see are an arbitrary slice of a large tie (Product 101 with Product 132 may appear on one run and not the next). Adding p1, p2 to the ORDER BY makes the slice repeatable.

Example 2#
WITH ev AS (
  SELECT
    e.customer_id,
    e.event_time,
    coalesce(e.metadata ->> 'campaign', 'none') AS campaign
  FROM
    events e
),
first_last AS (
  SELECT
    customer_id,
    (ARRAY_AGG(campaign ORDER BY event_time ASC))[1] AS first_touch,
    (ARRAY_AGG(campaign ORDER BY event_time DESC))[1] AS last_touch
  FROM
    ev
  GROUP BY
    customer_id
)
SELECT
  first_touch,
  last_touch,
  COUNT(*)
FROM
  first_last
GROUP BY
  first_touch,
  last_touch
ORDER BY
  COUNT(*) DESC
LIMIT 50;

How to read it: ev turns every event into (customer, time, campaign), with none as the fallback label. first_last uses two ordered ARRAY_AGG calls per customer and takes element [1] of each, so it keeps the earliest and the latest campaign. The outer query counts customers per (first, last) combination.

Expected result/shape: Five rows of exactly 100 customers each, such as winter to fall and spring to none. The fixture assigns campaigns by a formula on customer id and event number, so each first touch always leads to the same last touch; real data would spread across up to 25 combinations.

Learning objectives#

  • Count each undirected basket pair once per order.
  • Attribute a purchase event across distinct qualifying campaigns under an explicit lookback rule.

Vocabulary and concepts#

  • Market basket: the distinct products associated with one order.
  • Attribution window: the time interval in which a touch can qualify for conversion credit.
  • Fractional credit: one conversion divided across several qualifying touches or campaigns.

Worked example / walkthrough#

Deduplicate products within each order, self-join with a.product_id < b.product_id, and count orders per pair. For attribution, deduplicate campaigns per purchase before dividing one credit by the distinct campaign count; verify allocated credit sums to one for every assisted purchase.

Common mistakes and how to recover#

  • Lesson-specific semantic mistake: Enforce product_id ordering to avoid self-pairs and reversed duplicates. With <> instead of <, every pair appears twice, once in each direction, so the list has 1,540 rows instead of 770; with no condition at all, each product also pairs with itself.
  • Credits that add up to more than the assisted purchases: you divided by the number of touches but grouped by campaign, or forgot DISTINCT on (purchase, campaign). Sum fractional_credit per purchase_event_id; every sum must be exactly 1.
  • A purchase credited to itself: Exercise 3 has no event-type filter, so an upper bound of <= on event_time would let the purchase event count as its own touch. Keep the bound strict and test a touch exactly seven days before.
  • Orders missing from the direct bucket: an inner JOIN LATERAL drops orders with no qualifying touch. Use LEFT JOIN LATERAL ... ON true and confirm the bucket total is 4,362.
  • Generic recovery steps, including psql stopping on the first error, are in the study guide.

Project focus#

  • Form undirected market-basket product pairs.

  • Allocate equal fractional credit across distinct qualifying campaigns.

How the learner script uses the current schema#

The starter deduplicates products within each order and pairs them with a.product_id < b.product_id. It also extracts campaign from events.metadata->>'campaign' and demonstrates each customer's first and last touch by events.event_time.

The setup provides event types page_view, add_to_cart, checkout, purchase, and support. It has no separate sessions or experiment assignment table.

Practice map#

Exercises 1, 2, 3 and 6 build attribution step by step: count assisted purchases, split one credit across distinct campaigns, compare campaign grain with touch grain, and finally give every order exactly one bucket. Exercise 4 returns to baskets with support, confidence and lift, and Exercise 5 shows how LATERAL ... LIMIT 1 stops one touch from claiming several orders. The numbered list above is the contract, repeated unchanged in the learner SQL.

Attribution reasoning#

  • The conversion anchor is a purchase event, not an order. State that definition before comparing results with order revenue.
  • Assisted counts are not additive because one purchase can have several assisting campaigns.
  • Equal credit for a qualifying purchase should sum to exactly one across its distinct campaigns.
  • Decide whether missing campaign metadata, represented as none, should receive credit.

Validation and limits#

  • Enforce product_id ordering to avoid self-pairs and reversed duplicates.
  • The exercise does not establish causal marketing impact.
  • The seven-day half-open window needs explicit boundary tests.
  • Without session IDs, do not imply session-level journeys.

    order_id,
    product_id
  FROM

    product_id

    b.product_id

  p1.name AS product_a,
  p2.name AS product_b,
  together

  pairs
  JOIN products p1 ON p1.product_id = pairs.p1

  together DESC

Exercise 1: Assisted conversions#

SET search_path TO training, public;

WITH purchases AS (
  SELECT
    event_id AS purchase_event_id,
    customer_id,
    event_time AS purchase_time
  FROM
    events
  WHERE
    event_type = 'purchase'
),
qualifying_touches AS (
  SELECT
    p.purchase_event_id,
    p.customer_id,
    COALESCE(t.metadata ->> 'campaign', 'none') AS campaign
  FROM
    purchases p
    JOIN events t ON t.customer_id = p.customer_id
      AND t.event_type <> 'purchase'
      AND t.event_time >= p.purchase_time - interval '7 days'
      AND t.event_time < p.purchase_time
)
  SELECT
    campaign,
    COUNT(DISTINCT purchase_event_id) AS assisted_conversions,
    COUNT(DISTINCT customer_id) AS assisted_customers
  FROM
    qualifying_touches
GROUP BY
  campaign
ORDER BY
  assisted_conversions DESC,
  campaign;

Expected grain: one row per campaign. A purchase can appear under several campaigns, so assisted_conversions is not additive across rows.

Reasoning and verification#
  • Inputs/evidence: For sql-48 Exercise 1, take the 4,000 purchase events from events as conversions and join each one to the same customer's non-purchase events in the half-open window [purchase_time - interval '7 days', purchase_time), reading metadata ->> 'campaign' (with COALESCE(..., 'none')) as the touch's campaign.
  • Expected result/shape: For sql-48 Exercise 1, expected output: one row per campaign. The final columns are campaign, assisted_conversions, and assisted_customers. The final order is assisted_conversions DESC, campaign.
  • Independent verification: For sql-48 Exercise 1, confirm 5 rows on our load (none and summer 264, fall 259, spring 253, winter 251), that qualifying_touches has 1,377 rows covering 702 distinct purchases, and that the five assisted_conversions add up to 1,291, the distinct (purchase, campaign) pairs, not 702. Then, in a transaction, add a customer whose purchase at 2026-01-08 10:00 has an autumn touch exactly 7 days earlier, two summer touches, and a boundary touch at the purchase timestamp; rerun and confirm a new autumn row with 1 and 1, summer rising to 265 and 35, no boundary row, and ROLLBACK.
  • Intermediate relation check: purchases has 4,000 rows, one per purchase event. qualifying_touches has one row per (purchase, touch), so a purchase with four earlier events in its window appears four times; that is why the final SELECT counts DISTINCT purchase_event_id and DISTINCT customer_id instead of rows.
  • Clause check: The join is the whole rule: same customer, a non-purchase event, and event_time in [purchase_time - 7 days, purchase_time). GROUP BY campaign then collapses touches into five rows, and the ORDER BY puts the most assisted campaign first with the name as tie-breaker (none and summer tie at the top on the reference load).
  • Alternative/trade-off: An EXISTS subquery per (purchase, campaign) would avoid the touch-level fan-out entirely, but you would first have to list the campaigns; the join plus COUNT(DISTINCT ...) is easier to inspect one CTE at a time.
  • Edge case: Move one touch to exactly seven days before its purchase and it still counts; move it one second earlier and it drops out. A touch at the same instant as the purchase never counts because the upper bound is strict.

Exercise 2: Equal fractional multi-touch credit#

SET search_path TO training, public;

WITH purchases AS (
  SELECT
    event_id AS purchase_event_id,
    customer_id,
    event_time AS purchase_time
  FROM
    events
  WHERE
    event_type = 'purchase'
),
campaign_touches AS (
  SELECT DISTINCT
    p.purchase_event_id,
    p.customer_id,
    COALESCE(t.metadata ->> 'campaign', 'none') AS campaign
  FROM
    purchases p
    JOIN events t ON t.customer_id = p.customer_id
      AND t.event_type <> 'purchase'
      AND t.event_time >= p.purchase_time - interval '7 days'
      AND t.event_time < p.purchase_time
),
credited AS (
  SELECT
    *,
    1.0 / COUNT(*) OVER (PARTITION BY purchase_event_id) AS fractional_credit
FROM
  campaign_touches
)
SELECT
  campaign,
  ROUND(SUM(fractional_credit), 4) AS attributed_conversions,
  COUNT(DISTINCT purchase_event_id) AS touched_conversions
FROM
  credited
GROUP BY
  campaign
ORDER BY
  attributed_conversions DESC,
  campaign;

For every purchase that has at least one qualifying campaign, credits across its distinct campaigns sum to 1.

Reasoning and verification#
  • Inputs/evidence: For sql-48 Exercise 2, start from the same purchases and seven-day non-purchase touches as Exercise 1, collapse them with SELECT DISTINCT to one row per (purchase, campaign) in campaign_touches, give each row 1.0 / COUNT(*) OVER (PARTITION BY purchase_event_id), and sum that credit by campaign.
  • Expected result/shape: For sql-48 Exercise 2, expected output: one row per campaign. The final columns are campaign, attributed_conversions, and touched_conversions. The final order is attributed_conversions DESC, campaign.
  • Independent verification: For sql-48 Exercise 2, confirm attributed_conversions of 148.5 for summer, 141.25 for fall, 140.25 for none, 139.25 for spring, and 132.75 for winter on our load, that they add up to 702.0000 (one credit per assisted purchase), and that touched_conversions equals Exercise 1's assisted_conversions for every campaign. Then repeat the Exercise 1 transaction: the new purchase has two distinct campaigns, so autumn gets 0.5, summer rises by 0.5 to 149.0000 even though it touched twice, and the total becomes 703 before ROLLBACK.
  • Intermediate relation check: campaign_touches is SELECT DISTINCT on (purchase, customer, campaign), so a purchase reached twice by summer keeps one summer row. credited keeps that row count and adds fractional_credit, which is 1 divided by the number of distinct campaigns for that purchase. Summing it per purchase must give 1, and summing it over all rows must give the number of distinct assisted purchases, roughly 700 on the reference load, the same purchases that Exercise 1 counted once per campaign.
  • Clause check: COUNT(*) OVER (PARTITION BY purchase_event_id) counts the campaign rows of each purchase without collapsing them, so each row can carry its own share. ROUND(SUM(fractional_credit), 4) happens only after grouping by campaign, which keeps rounding error out of the per-purchase division.
  • Alternative/trade-off: Computing the campaign count in a separate grouped CTE and joining it back gives identical numbers; the window version saves a join and keeps the division next to the rows it splits.
  • Edge case: If a purchase had only none touches, it would still receive one full credit under none. Excluding none would leave that purchase uncredited, so decide the policy before comparing the total with Exercise 1.

Reasoning, safety, and pitfalls#

  • The conversion anchor here is a purchase event, not an order. State and test that business definition before comparing this result with order metrics.
  • DISTINCT prevents repeated touches by the same campaign from receiving multiple shares.
  • The half-open interval includes exactly seven days before the purchase but excludes the purchase timestamp itself.
  • Campaign value 'none' makes missing metadata visible; decide whether it should receive attribution in production.

      AND e.event_time < p.purchased_at

-- Exercise 4: distinct baskets prevent duplicate lines from inflating support.
WITH baskets AS (
  SELECT DISTINCT
    order_id,
    product_id
  FROM
    order_items
),
order_count AS (
  SELECT
    COUNT(DISTINCT order_id)::numeric AS n
  FROM
    baskets
),
product_counts AS (
  SELECT
    product_id,
    COUNT(*)::numeric AS baskets
  FROM
    baskets
  GROUP BY
    product_id
),
pairs AS (
  SELECT
    a.product_id AS product_a,
    b.product_id AS product_b,
    COUNT(*)::numeric AS together
  FROM
    baskets a
    JOIN baskets b ON a.order_id = b.order_id
      AND a.product_id < b.product_id
  GROUP BY
    a.product_id,
    b.product_id
)
SELECT
  p.product_a,
  p.product_b,
  ROUND(p.together / n, 4) AS support,
  ROUND(p.together / ca.baskets, 4) AS confidence_a_to_b,
  ROUND(p.together / cb.baskets, 4) AS confidence_b_to_a,
  ROUND((p.together * n) / NULLIF (ca.baskets * cb.baskets, 0), 4) AS lift
FROM
  pairs p
  CROSS JOIN order_count
  JOIN product_counts ca ON ca.product_id = p.product_a
  JOIN product_counts cb ON cb.product_id = p.product_b
ORDER BY
  lift DESC,
  product_a,
  product_b
LIMIT 20;

-- Exercise 5: LATERAL chooses only the next purchase for each touch, preventing
-- one touch from being reused across several later purchases.
SELECT
  e.event_id AS touch_id,
  e.metadata ->> 'campaign' AS campaign,
  next_purchase.order_id,
  next_purchase.order_date
FROM
  events e
  LEFT JOIN LATERAL (
    SELECT
      o.order_id,
      o.order_date
    FROM
      orders o
    WHERE
      o.customer_id = e.customer_id
      AND o.order_date > e.event_time
      AND o.order_date <= e.event_time + interval '7 days'
    ORDER BY
      o.order_date,
      o.order_id
    LIMIT 1) next_purchase ON true
WHERE
  e.metadata ? 'campaign'
ORDER BY
  e.event_id;

-- Exercise 6: start from purchases and LEFT JOIN touches so every purchase
-- receives either a qualifying campaign or the explicit direct bucket.
SELECT
  COALESCE(t.campaign, '(direct)') AS attribution_bucket,
  COUNT(*) AS purchases
FROM
  orders o
  LEFT JOIN LATERAL (
    SELECT
      e.metadata ->> 'campaign' AS campaign
    FROM
      events e
    WHERE
      e.customer_id = o.customer_id
      AND e.event_time >= o.order_date - interval '7 days'
      AND e.event_time < o.order_date
      AND e.metadata ? 'campaign'
    ORDER BY
      e.event_time DESC,
      e.event_id DESC
    LIMIT 1) t ON true
GROUP BY
  COALESCE(t.campaign, '(direct)')
ORDER BY
  purchases DESC,
  attribution_bucket;
