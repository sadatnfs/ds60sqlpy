# c-005: Functions, prototypes and output parameters

## Level and prerequisites

Beginner, approximately 90 minutes plus a later retrieval session. Direct prerequisites: `c-004`

## Learning objectives

## Purpose and mental model

A function contract names inputs, outputs, side effects and failure behavior. A prototype lets the compiler check calls before seeing the implementation. C passes arguments by value, so changing a scalar parameter does not change its caller. A pointer parameter can permit a function to modify a caller-owned object, but the function must state whether null is accepted and what object size is required. Returning a status plus writing through an output pointer is a common C API pattern. On failure, define whether the output remains unchanged rather than leaving callers to guess.

## Vocabulary and concepts

- **Prototype:** A declaration describing a function call interface.
- **Output parameter:** A pointer through which a function returns a value.
- **Failure atomicity:** A contract that failed operations leave specified state unchanged.

## Syntax anatomy and execution trace

static limits a file-scope function to its translation unit. A prototype such as int twice(int x) declares parameter and result types. void in an empty parameter list means no parameters in C17. bool try_area(int w,int h,int *out) can report success and provide an output separately. Validate preconditions before writing through out. Returning a pointer to an automatic local object creates a dangling pointer and must not be used.

## Worked example / walkthrough

### Worked example 1: Call a pure calculation

Evaluate twice for 7 and 0.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int twice(int x) { return 2 * x; }
void reassign(int value) {
  value = 99;
  (void)value;
}
bool try_area(int w, int h, int *out) {
  if (out == NULL || w <= 0 || h <= 0 || w > INT_MAX / h)
    return false;
  *out = w * h;
  return true;
}

int main(void) {
  /* Call a pure calculation */
  {
    CHECK(twice(7) == 14);
    CHECK(twice(0) == 0);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** The results are 14 and 0.

The helper has no external state and its tiny input range avoids overflow. A general API would need a stated range.

### Worked example 2: Return an output on success

Calculate area for width 3 and height 4.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int twice(int x) { return 2 * x; }
void reassign(int value) {
  value = 99;
  (void)value;
}
bool try_area(int w, int h, int *out) {
  if (out == NULL || w <= 0 || h <= 0 || w > INT_MAX / h)
    return false;
  *out = w * h;
  return true;
}

int main(void) {
  /* Call a pure calculation */
  {
    CHECK(twice(7) == 14);
    CHECK(twice(0) == 0);
  }

  /* Return an output on success */
  {
    int out = -1;
    CHECK(try_area(3, 4, &out));
    CHECK(out == 12);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** Success is true and output becomes 12.

The status and result are distinct. The caller checks status before using the new output.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
