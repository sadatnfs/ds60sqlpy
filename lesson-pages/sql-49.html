Day 49: Finance/Operations Project, Part 1: Revenue Forecasting#

How to run this lesson#

Open sql-49 in ./classroom, pick PostgreSQL and run it as a Whole SQL lesson (psql). Your editable copy lives at .learning/sql/sql-49/lesson/workspace/sql/postgres-60day/day49_project2_finance_part1.sql. The file only reads orders in advanced_sql_training, wrapped in BEGIN and ROLLBACK. psql prints four results: 24 months of revenue (newest first), 36 months with year-over-year growth, three future months copied from last year and a six-row trailing average. Order dates are generated relative to the moment the fixture loaded, so the newest month is always a partial one. Launcher details are in the study guide, and the notebook alternative is in its contributor notebook section.

A beginner's mental model for this lesson#

Every query today first squeezes orders into one row per month. On a fresh load the fixture has 46 months, February 2023 through November 2026, with no empty month, and revenue climbs steeply: 1,203.26 in the first month and 170,179.13 in October 2026. The last month stops at the final order date, so it shows only 85,364.67 and looks like a collapse that never happened.

A backtest replays history. For each past month, build the forecast you could have made at the start of that month, then compare it with what came in. Two rules keep it honest. The averaging frame must stop at 1 PRECEDING, because a frame reaching CURRENT ROW puts the month's own revenue into its forecast, which is target leakage. And every model must be graded on the same months: MA(12) and a 12-month seasonal naive need a year of warm-up that MA(6) does not.

MAPE (mean absolute percentage error) averages |actual - forecast| / actual. It reads as "off by 23% on average", but it cannot divide by a zero month, and on a growing series it punishes any model that looks far back. Read each CTE in logical clause order and note its row count before moving on.

Two worked SQL examples#

Both excerpts are the opening queries of the learner script. They describe the series; neither one forecasts or scores anything yet.

Example 1#
WITH monthly AS (
  SELECT
    date_trunc('month', o.order_date)::date AS month,
    SUM(o.total_amount) AS revenue
  FROM
    orders o
  GROUP BY
    1
)
SELECT
  *
FROM
  monthly
ORDER BY
  month DESC
LIMIT 24;

How to read it: monthly truncates each order_date to the first of its month and sums total_amount, so 4,362 orders become 46 rows. The outer query only sorts them newest first and keeps 24; SELECT * exposes exactly the two CTE columns.

Expected result/shape: 24 rows of month and revenue, from 2026-11-01 (85,364.67, partial on a fresh load) back to 2024-12-01 (35,551.24). October 2026, at 170,179.13, is the real peak. No NULL can appear, because every month in the window has orders.

Example 2#
WITH monthly AS (
  SELECT
    date_trunc('month', o.order_date)::date AS month,
    SUM(o.total_amount) AS revenue
  FROM
    orders o
  GROUP BY
    1
)
SELECT
  m.month,
  m.revenue,
  LAG(m.revenue, 12) OVER (ORDER BY m.month) AS prev_year,
  ROUND((m.revenue - COALESCE(LAG(m.revenue, 12) OVER (ORDER BY m.month), 0)) / NULLIF (LAG(m.revenue, 12) OVER (ORDER BY m.month), 0), 4) AS yoy_growth
FROM
  monthly m
ORDER BY
  m.month DESC
LIMIT 36;

How to read it: The same monthly CTE feeds a window. LAG(m.revenue, 12) OVER (ORDER BY m.month) reads the row twelve positions earlier, which is the same calendar month last year only because no month is missing. yoy_growth divides the change by NULLIF of that lagged value; when the lag is NULL the ratio is NULL, whatever the COALESCE in the numerator does.

Expected result/shape: 36 rows from 2026-11-01 back to 2023-12-01 with month, revenue, prev_year and yoy_growth. The two oldest rows, December 2023 and January 2024, have no prev_year and so no growth. October 2026 grew 1.5790 over October 2025, while the partial November shows just 0.0455: a truncation artifact, not a slowdown.

Learning objectives#

  • Backtest moving-average and seasonal-naive forecasts without target leakage.
  • Compare errors on a common scoring population and disclose sparse history.

Vocabulary and concepts#

  • Backtest: evaluate a forecast using only information available before each historical target.
  • Target leakage: using the actual target or future information in its prediction.
  • MAPE: mean absolute percentage error, undefined for zero actuals.

Worked example / walkthrough#

At complete monthly grain, compute MA(6) with a frame ending at 1 PRECEDING, place it beside actual revenue, and score only months with a forecast and nonzero actual. Compare seasonal naive on that same scoring set and retain the number of evaluated months.

Common mistakes and how to recover#

  • Lesson-specific semantic mistake: Return forecast and actual side by side. A MAPE alone hides direction. Exercise 2's columns show seasonal naive under the actual in every scored month, which a single 0.6027 never reveals.
  • Reading a partial month as a drop: on a fresh load November 2026 ends at the last order date. That month alone gives MA(6) an error of 0.6555, and leaving it out moves MA(6)'s MAPE from 0.2281 to 0.2151. Decide which months are complete before grading them.
  • A frame that contains the target: ROWS BETWEEN 5 PRECEDING AND CURRENT ROW still spans six months, but one of them is the answer. Its 0.1696 is not an improvement.
  • Grading models on different months: score MA(6) wherever it has six months of history and it covers 40 months at 0.2519; on the common 34 it is 0.2281. Only the second can sit beside MA(12).
  • Lagging over gaps: LAG(revenue, 12) counts rows. Build the month spine first, as Exercise 4 does, or one missing month shifts a whole year of seasonal forecasts.
  • Generic diagnosis steps live in the study guide's recovery section.

Project focus#

How the learner script uses the current schema#

The starter aggregates orders.total_amount by order month, calculates year-over-year growth with LAG(..., 12), projects future months from last year's matching month, and shows a trailing three-month average.

Practice map#

Exercise 1 is the full backtest and Exercise 2 its month-by-month view. Exercises 3 and 4 isolate the two rules that backtest depends on (no leakage, a complete calendar), and Exercises 5 and 6 use tiny VALUES sets to show where MAPE misleads. The learner file carries the same numbered prompts, each with a first hint.

Backtesting reasoning#

  • Moving windows must end at 1 PRECEDING; including the current actual leaks the answer into its forecast.
  • LAG(revenue, 12) means the previous 12 result rows. Build a complete month calendar first if months can be absent.
  • MAPE is undefined when actual revenue is zero; disclose excluded periods and consider MAE as a companion metric.
  • Compare models over a common scoring window when warm-up history differs.

Validation and limits#

  • Return forecast and actual side by side.
  • Record the number of scored months for each model.
  • The deterministic seed has only a few years of history, so model ranking is a learning result, not evidence of forecast reliability.
  • A historical backtest does not create a production forecast pipeline.

-- Revenue forecasting with time-series patterns
BEGIN;
SET search_path TO training, public;

-- Monthly revenue
WITH monthly AS (
  SELECT
    date_trunc('month', o.order_date)::date AS month,
    SUM(o.total_amount) AS revenue
  FROM
    orders o
  GROUP BY
    1
)
SELECT
  *
FROM
  monthly
ORDER BY
  month DESC
LIMIT 24;

-- YoY growth per month
WITH monthly AS (
  SELECT
    date_trunc('month', o.order_date)::date AS month,
    SUM(o.total_amount) AS revenue
  FROM
    orders o
  GROUP BY
    1
)
SELECT
  m.month,
  m.revenue,
  LAG(m.revenue, 12) OVER (ORDER BY m.month) AS prev_year,
  ROUND((m.revenue - COALESCE(LAG(m.revenue, 12) OVER (ORDER BY m.month), 0)) / NULLIF (LAG(m.revenue, 12) OVER (ORDER BY m.month), 0), 4) AS yoy_growth
FROM
  monthly m
ORDER BY
  m.month DESC
LIMIT 36;

-- Naive seasonal forecast: use last year's month as forecast
WITH monthly AS (
  SELECT
    date_trunc('month', o.order_date)::date AS month,
    SUM(o.total_amount) AS revenue
  FROM
    orders o
  GROUP BY
    1
),
future AS (
  SELECT
    (date_trunc('month', CURRENT_DATE) + (n || ' month')::interval)::date AS month
  FROM
    generate_series(1, 3) AS g (n))
SELECT
  f.month,
  m_prev.revenue AS forecast_revenue
FROM
  future f
  LEFT JOIN monthly m_prev ON m_prev.month = (f.month - interval '12 months')::date
ORDER BY
  f.month;

-- MA(3) forecast: average of last 3 months revenue
WITH monthly AS (
  SELECT
    date_trunc('month', o.order_date)::date AS month,
    SUM(o.total_amount) AS revenue
  FROM
    orders o
  GROUP BY
    1
),
ma AS (
  SELECT
    month,
    revenue,
    ROUND(AVG(revenue) OVER (ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS ma3
  FROM
    monthly
)
SELECT
  *
FROM
  ma
ORDER BY
  month DESC
LIMIT 6;

Exercise 1: MA(6), MA(12), seasonal naive, and MAPE#

SET search_path TO training, public;

WITH monthly_observed AS (
  SELECT
    date_trunc('month', order_date)::date AS month,
    SUM(total_amount) AS revenue
  FROM
    orders
  GROUP BY
    date_trunc('month', order_date)
),
bounds AS (
  SELECT
    MIN(month) AS first_month,
    MAX(month) AS last_month
  FROM
    monthly_observed
),
month_spine AS (
  SELECT
    generate_series(first_month, last_month, interval '1 month')::date AS month
  FROM
    bounds
),
monthly_complete AS (
  SELECT
    spine.month,
    COALESCE(observed.revenue, 0::numeric) AS revenue,
    observed.month IS NOT NULL AS had_source_rows
  FROM
    month_spine spine
    LEFT JOIN monthly_observed observed USING (month)
),
forecast_rows AS (
  SELECT
    month,
    revenue,
    AVG(revenue) OVER (ORDER BY month ROWS BETWEEN 6 PRECEDING AND 1 PRECEDING) AS ma6_forecast,
    COUNT(revenue) OVER (ORDER BY month ROWS BETWEEN 6 PRECEDING AND 1 PRECEDING) AS ma6_history_rows,
    AVG(revenue) OVER (ORDER BY month ROWS BETWEEN 12 PRECEDING AND 1 PRECEDING) AS ma12_forecast,
    COUNT(revenue) OVER (ORDER BY month ROWS BETWEEN 12 PRECEDING AND 1 PRECEDING) AS ma12_history_rows,
    LAG(revenue, 12) OVER (ORDER BY month) AS seasonal_naive
  FROM
    monthly_complete
),
common_scoring_rows AS (
  SELECT
    month,
    revenue,
    ma6_forecast,
    ma12_forecast,
    seasonal_naive,
    0.5 * seasonal_naive + 0.5 * ma6_forecast AS blended_forecast
  FROM
    forecast_rows
  WHERE
    ma6_history_rows = 6
    AND ma12_history_rows = 12
    AND seasonal_naive IS NOT NULL
),
model_scores AS (
  SELECT
    rows.month,
    rows.revenue,
    model.model,
    model.forecast
  FROM
    common_scoring_rows rows
    CROSS JOIN LATERAL (
      VALUES ('MA(6)'::text, rows.ma6_forecast),
        ('MA(12)', rows.ma12_forecast),
        ('seasonal naive', rows.seasonal_naive),
        ('50% seasonal + 50% MA(6)', rows.blended_forecast)) AS model (model, forecast))
SELECT
  model,
  COUNT(*) FILTER (WHERE revenue <> 0) AS scored_rows,
  COUNT(*) FILTER (WHERE revenue = 0) AS zero_actual_rows,
  ROUND(AVG(ABS(revenue - forecast) / NULLIF (revenue, 0)), 4) AS mape
FROM
  model_scores
GROUP BY
  model
ORDER BY
  model;

Expected shape: four model rows scored on the identical complete-history month set. scored_rows and zero_actual_rows make the MAPE denominator explicit.

Reasoning and verification#
  • Inputs/evidence: For sql-49 Exercise 1, aggregate orders by observed month, left-join to month_spine, compute full-window history counts, and reshape four forecasts over common_scoring_rows.
  • Expected result/shape: For sql-49 Exercise 1, expected output: exactly four rows keyed by model, with scored_rows, zero_actual_rows, and mape, ordered by model.
  • Independent verification: For sql-49 Exercise 1, require ma6_history_rows = 6, ma12_history_rows = 12, and a non-NULL twelve-month seasonal value before any model is scored. All four models must have identical eligible months and equal scored_rows; independently recompute each MAPE.
  • Intermediate relation check: monthly_observed has 46 rows and bounds one (2023-02-01 to 2026-11-01). month_spine and monthly_complete also have 46, all with had_source_rows true. forecast_rows keeps 46, common_scoring_rows keeps 34 (2024-02 onward), and the LATERAL list turns those into 136 rows, four per month. GROUP BY model returns 4.
  • Clause check: Each AVG ... ROWS BETWEEN n PRECEDING AND 1 PRECEDING sits beside a COUNT over the same frame. Early frames are short, so ma6_history_rows and ma12_history_rows say whether an average used a full window, and the WHERE in common_scoring_rows demands 6 and 12. NULLIF(revenue, 0) and the two FILTER counts keep a zero month out of MAPE but visible in the output.
  • Alternative/trade-off: On this dense spine the ma12_history_rows = 12 test is redundant: a non-NULL LAG(revenue, 12) already needs 12 earlier rows, and removing the test leaves all four results unchanged. It still earns its place by stating the rule outright. Grading each model on its own available months instead gives MA(6) 40 months and 0.2519, a number that cannot be compared with the others.
  • Edge case: Filter June 2025 out of monthly_observed and the spine brings it back with revenue 0. Each model then reports 33 scored_rows and 1 zero_actual_rows, and every MAPE rises (MA(6) to 0.2533) because the zero sits inside later averaging windows. The partial final month matters too: without it MA(6) scores 0.2151.

Exercise 2: Month-by-month blended forecast#

SET search_path TO training, public;

WITH monthly AS (
  SELECT
    date_trunc('month', order_date)::date AS month,
    SUM(total_amount) AS revenue
  FROM
    orders
  GROUP BY
    date_trunc('month', order_date)
),
forecasted AS (
  SELECT
    month,
    revenue,
    LAG(revenue, 12) OVER (ORDER BY month) AS seasonal_naive,
    AVG(revenue) OVER (ORDER BY month ROWS BETWEEN 6 PRECEDING AND 1 PRECEDING) AS ma6_forecast
  FROM
    monthly
)
SELECT
  month,
  ROUND(revenue, 2) AS actual,
  ROUND(seasonal_naive, 2) AS seasonal_naive,
  ROUND(ma6_forecast, 2) AS ma6_forecast,
  ROUND(0.5 * seasonal_naive + 0.5 * ma6_forecast, 2) AS blended_forecast
FROM
  forecasted
WHERE
  seasonal_naive IS NOT NULL
ORDER BY
  month DESC;
Reasoning and verification#
  • Inputs/evidence: For sql-49 Exercise 2, aggregate orders into 46 calendar months in monthly, then in forecasted add LAG(revenue, 12) as seasonal_naive and AVG(revenue) over ROWS BETWEEN 6 PRECEDING AND 1 PRECEDING as ma6_forecast, and blend them 50/50 for every month that has a value a year earlier.
  • Expected result/shape: For sql-49 Exercise 2, expected output: 34 rows, one per month from 2024-02-01 to 2026-11-01, with columns month, actual, seasonal_naive, ma6_forecast, and blended_forecast, ordered by month DESC, so the partial current month comes first.
  • Independent verification: For sql-49 Exercise 2, confirm 34 distinct months and that forecasted holds exactly 12 rows with a NULL seasonal_naive (2023-02 to 2024-01), which the WHERE removes. Recompute the oldest row by hand: 2024-02 has actual 14,823.22, seasonal_naive 1,203.26 from 2023-02, ma6_forecast 11,859.69 (the mean of 2023-08 to 2024-01), and blended_forecast 6,531.47, their average. Then, in a transaction, delete the 91 orders from 2025-03, rerun, and confirm 33 rows and that 2026-03 now takes 33,302.51 from 2025-02 as its "seasonal" value, a 13-month lag; ROLLBACK.
  • Intermediate relation check: monthly has 46 rows and forecasted keeps all 46, adding seasonal_naive (NULL for the first 12) and ma6_forecast (NULL only for February 2023, then averaging whatever earlier months exist, up to six). The WHERE keeps 34 rows.
  • Clause check: WHERE seasonal_naive IS NOT NULL is the only filter. Seasonal naive needs 12 earlier months, so every surviving row also has a full six-month MA window and no separate count check is needed. ROUND(..., 2) is applied only in the final SELECT, after the blend is computed from unrounded inputs, and ORDER BY month DESC puts the partial month first.
  • Alternative/trade-off: A forward version would forecast the next three calendar months after CURRENT_DATE, holding the latest six-month average flat and blending it with each month a year earlier. That answers a planning question, but it cannot be scored yet, its numbers move with the run date, and the flat average includes the partial current month. The month-by-month backtest used here and in the .sql file shows the blend's past errors, which is what the comparison needs.
  • Edge case: The blend inherits both models' lag. In October 2026 it forecast about 97,200 for an actual of 170,179.13; on the partial November row it overshoots instead (about 111,500 against 85,364.67). A month with no orders would vanish from monthly entirely, and every 12-row lag after it would then reach back 13 months; Exercise 4's spine prevents that.

Reasoning, safety, and pitfalls#

  • Every window ends at 1 PRECEDING; including the current month's actual would leak the answer into its forecast.
  • LAG(..., 12) assumes one row per calendar month. If a month can be absent, join to a complete month calendar first.
  • MAPE excludes zero actuals via NULLIF; disclose how many periods were excluded and compare MAE when zeros are common.
  • Different models have different warm-up periods, so a rigorous comparison should score all models over the same common months.

Exercise 5: Report the MAPE denominator#

NULLIF(actual, 0) excludes undefined percentage errors, and FILTER counts both scored and excluded observations. Never publish MAPE without that context.

Reasoning and verification#
  • Inputs/evidence: For sql-49 Exercise 5, use the toy VALUES fixture (100, 90), (0, 10), (50, 60) of actual and forecast and compute MAPE as AVG(ABS(actual - forecast) / NULLIF(actual, 0)), counting scored rows and excluded zero actuals.
  • Expected result/shape: For sql-49 Exercise 5, expected output: one row with mape 0.1500, scored_rows 2, and excluded_zero_actuals 1. The final columns are mape, scored_rows, and excluded_zero_actuals.
  • Independent verification: For sql-49 Exercise 5, confirm by hand that the two scored errors are 10/100 = 0.10 and 10/50 = 0.20, whose mean is 0.15, and that the zero-actual row adds nothing because NULLIF(actual, 0) makes its ratio NULL, which AVG skips.
  • Intermediate relation check: toy holds three rows. Before averaging, list ABS(actual - forecast) / NULLIF(actual, 0) per row: 0.10, NULL and 0.20. AVG skips the NULL, so it divides 0.30 by 2, not by 3.
  • Clause check: The two FILTER counts split the same three rows by actual <> 0 and actual = 0, so together they equal the input size. A NULL actual would fall into neither count, which is worth a third counter on real data.
  • Alternative/trade-off: WHERE actual <> 0 gives the same 0.1500 but drops the zero row before counting, so excluded_zero_actuals could no longer come from the same query. Weighted MAPE, SUM(ABS(actual - forecast)) / SUM(actual), avoids per-row division: here 30 / 150 = 0.2000, and the zero month's miss of 10 counts instead of vanishing.

Exercise 6: Compare MAE and MAPE#

Reasoning and verification#

  • Clause check: AVG(ABS(actual - forecast)) keeps the currency unit, so 55 means 55 revenue units.   AVG(revenue) OVER (ORDER BY month ROWS BETWEEN 5 PRECEDING AND CURRENT ROW) AS leaky_ma6,
  AVG(revenue) OVER (ORDER BY month ROWS BETWEEN 6 PRECEDING AND 1 PRECEDING) AS honest_ma6
FROM
  monthly
ORDER BY
  month;

-- Exercise 4: generate the calendar first so LAG(...,12) means 12 calendar
-- months. The observed flag distinguishes missing from explicit zero revenue.
WITH bounds AS (
  SELECT
    date_trunc('month', MIN(order_date))::date AS first_month,
    date_trunc('month', MAX(order_date))::date AS last_month
  FROM
    orders
),
spine AS (
  SELECT
    generate_series(first_month, last_month, interval '1 month')::date AS month
  FROM
    bounds
),
actual AS (
  SELECT
    date_trunc('month', order_date)::date AS month,
    SUM(total_amount) AS revenue
  FROM
    orders
  GROUP BY
    date_trunc('month', order_date)
),
complete AS (
  SELECT
    s.month,
    a.revenue,
    (a.month IS NOT NULL) AS had_source_rows
FROM
  spine s
  LEFT JOIN actual a USING (month))
SELECT
  month,
  revenue,
  had_source_rows,
  LAG(revenue, 12) OVER (ORDER BY month) AS seasonal_forecast
FROM
  complete
ORDER BY
  month;

-- Exercise 5: MAPE excludes zero actuals through NULLIF and reports the scoring
-- denominator so the omission is visible.
WITH toy (
  actual,
  forecast
) AS (
  VALUES (100::numeric, 90::numeric),
    (0, 10),
    (50, 60))
SELECT
  ROUND(AVG(ABS(actual - forecast) / NULLIF (actual, 0)), 4) AS mape,
  COUNT(*) FILTER (WHERE actual <> 0) AS scored_rows,
  COUNT(*) FILTER (WHERE actual = 0) AS excluded_zero_actuals
FROM
  toy;

-- Exercise 6: MAE is currency-scale error; MAPE magnifies the small-actual miss.
WITH toy (
  actual,
  forecast
) AS (
  VALUES (1000::numeric, 900::numeric),
    (10, 20))
SELECT
  AVG(ABS(actual - forecast)) AS mae,
  AVG(ABS(actual - forecast) / NULLIF (actual, 0)) AS mape
FROM
  toy;
