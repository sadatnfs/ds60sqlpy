# web-007: Data tables, captions and header relationships

## Level and prerequisites

Beginner; allow about 90 minutes, with extra time for independent practice. Direct prerequisites: `web-006`

## Learning objectives

Build a three-row study table with correct header relationships. Explain when a chart should keep a supporting table. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A table represents data whose meaning depends on row and column relationships. It should not be the default layout tool for unrelated page regions. A caption identifies the table's topic, units or scope. Header cells identify a column or row so a reading tool can associate values with their context. Visual boldness alone cannot establish that relationship.

Keep a table simple when possible. A dataset with two independent header axes can use column and row scope. More complex spans may require explicit header associations and careful testing. For a narrow screen, preserve the relationships instead of hiding important columns. A scrollable region can keep the table intact when the data genuinely needs two dimensions.

## Syntax anatomy and mechanism

Use thead for the header group, tbody for records, th for headers and td for values. `scope="col"` identifies a column header and `scope="row"` identifies a row header. Numeric alignment is presentation, while the units belong in the content. Tables must remain useful when colors or zebra stripes are unavailable.

## Worked example / walkthrough

### Worked example 1: A column header

The header explicitly identifies what the numeric cells measure.

```html
<tr><th scope="col">Subject</th><th scope="col">Minutes</th></tr>
```

**Expected observation:** The second column has a named unit.

### Worked example 2: A row header

The subject identifies the row across its values.

```html
<tr><th scope="row">HTML</th><td>40</td></tr>
```

**Expected observation:** 40 is associated with HTML and the Minutes column.

## Six progressive exercises

### Exercise 1: Explain what a single cell value means with both headers.

**Expected evidence:** 40 means forty minutes of HTML study, not an unlabeled count.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add a caption that states the reporting period.

**Expected evidence:** The visible caption explains the table's scope.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a three-row study table with correct header relationships.

**Expected evidence:** The caption, row headers and column headers identify every value.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Replace a table used to align unrelated navigation and article content.

**Expected evidence:** Use semantic regions plus CSS layout rather than false data relationships.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Inspect the table at a narrow width without deleting data.

**Expected evidence:** A bounded overflow region keeps all columns reachable.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain when a chart should keep a supporting table.

**Expected evidence:** Exact values and nonvisual interpretation often benefit from a tabular equivalent.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not confuse a table caption with an unrelated heading several paragraphs away. Avoid empty header cells when a meaningful label exists. A DOM assertion cannot prove a screen reader's announcement behavior.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain table, caption, column header without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
