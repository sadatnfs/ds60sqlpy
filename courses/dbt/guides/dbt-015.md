# dbt-015: Publication gates after materialization

## Level and prerequisites

Advanced. Direct prerequisites: `dbt-004`, `dbt-011`

**Outcome:** Separate candidate computation from accepted publication.

## Question and mechanism

Materialization and publication are different actions. A model relation may exist even when later tests fail. If consumers must not see invalid data, they need an accepted-output boundary that is updated only after the required evidence passes. A successful SQL statement is insufficient for that decision.

The example builds a candidate relation with key tests and publishes a small JSON output only when the complete invocation and relevant statuses pass. The bad fixture still materializes two rows, but no published file is created. The program checks both facts so it cannot confuse detection with transactional rollback.

This is a local publication gate, not a distributed transaction across a warehouse and an object store. A real deployment needs atomic pointer or version selection, ownership, retry behavior and recovery after uncertain outcomes. The lesson establishes the decision rule and evidence boundary that those mechanisms must implement.

## Syntax and data contract

Check result.success and the relevant run_results statuses before writing the accepted output. Keep the candidate relation separate from the consumer-facing artifact. A publication receipt should identify the data, schema, source version and checks that justified acceptance. A stale successful artifact must not qualify a new candidate.

## Worked case 1: Publish an accepted candidate

The valid two-row fixture passes both key conditions and produces a JSON artifact. The program confirms that the artifact exists only after successful evidence is available.

**Expected evidence:** Two candidate rows are present and publication is true.

```python
import json
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def artifact(root, name):
    return json.loads((root / "target" / name).read_text())


def publication_case(bad):
    with tempfile.TemporaryDirectory() as d:
        schema = {
            "models": [
                {"name": "ready", "columns": [{"name": "id", "data_tests": ["unique", "not_null"]}]}
            ]
        }
        p = project(
            d,
            models={"ready": "select * from {{ ref('events') }}"},
            seeds={"events": "id,value\n1,5\n" + ("1,7\n" if bad else "2,7\n")},
            schema=schema,
        )
        result = invoke(p, "build", succeeds=not bad)
        output = p / "published.json"
        statuses = [row["status"] for row in artifact(p, "run_results.json")["results"]]
        if result.success and all(value in {"pass", "success"} for value in statuses):
            output.write_text(json.dumps(rows(p, "select id,value from ready order by id")))
        assert output.exists() is (not bad)
        assert rows(p, "select count(*) from ready") == [(2,)]
        return {
            "materialized_rows": 2,
            "published": output.exists(),
            "failed_tests_block_publication": bad,
        }


def example_one():
    return publication_case(False)


if __name__ == "__main__":
    print(example_one())
```

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Change the failure condition

Add a domain test that rejects negative amounts.

**Check:** The candidate can be blocked by a meaningful semantic failure.

**Hint:** Key validity is only one dimension.


### 2. Inspect candidate state

Query the bad relation after failure.

**Check:** Its materialized rows are still observable.

**Hint:** Tests may occur after model creation.


### 3. Retain an accepted version

Keep a prior valid artifact while a new candidate fails.

**Check:** The accepted version remains identifiable.

**Hint:** Separate candidate and accepted paths.


### 4. Handle an uncertain write

Describe a publication timeout after the write may have occurred.

**Check:** The response reconciles identity before retrying.

**Hint:** An unknown outcome is not a confirmed failure.


### 5. Record the evidence

Add a compact receipt beside the accepted data.

**Check:** It identifies source, checks and data identity.

**Hint:** A file timestamp is not enough.


### 6. Test a stale artifact

Change source data but reuse an old successful run_results file.

**Check:** A reviewed gate rejects the mismatched evidence.

**Hint:** Bind evidence to the current candidate.


## Diagnose errors and misleading results

If invalid data appears despite a failed build, inspect the consumer-facing boundary. If publication is missing after success, check the exact selected statuses and artifact path. Keep failures visible and reconcile uncertain outcomes before retrying. A gate that simply ignores failed tests is not recovery.

## Transfer to independent work

Separate candidate computation from accepted publication. Demonstrate both paths and retain a source-bound decision record. Extend the mechanism to an atomic version pointer and a tested recovery plan in a durable owned environment.
