# asm-006: Loss, count and gradient summaries

Tutorial mode. Stage: intermediate. Direct prerequisites: `asm-005`, `clp-003`.

## Starting point and result

An optimizer needs an objective value and a gradient evaluated at the same parameter vector. Running one Spark job for every component wastes scheduling and scanning work. This chapter returns a single record containing count, loss, two gradient components and one curvature component. It also checks a central finite-difference calculation independently of Spark.

## Mechanism: summarize the mathematical derivatives

Let \(z_i=\beta_0+\beta_1x_i\), \(p_i=\sigma(z_i)\) and \(r_i=p_i-y_i\). Differentiating the stable Bernoulli objective gives

\[\nabla L(\beta)=\begin{bmatrix}\sum_i r_i\\\sum_i r_ix_i\end{bmatrix},\qquad H_{00}=\sum_i p_i(1-p_i).\]

The intercept corresponds to an implicit feature equal to one. The slope corresponds to the actual feature column. These derivatives are analytic expressions assembled by the author. Spark distributes their evaluation and reduction; it has not differentiated a Python function. The sigmoid is evaluated with a sign branch to avoid exponentiating a large positive number.

Each aggregate is associative in exact arithmetic. Floating-point addition introduces order-dependent rounding, so compare with a specified tolerance. `count(*)` counts all rows, whereas `count(column)` excludes nulls. A production contract must reject or explicitly model missing values before comparing those counts. The fixture schema is explicit and every row is finite.

## Worked case: a two-parameter objective

Five observations with feature values -2, -1, 0, 1 and 3 are evaluated at intercept 0.2 and slope -0.4. The program constructs fresh expressions from these two constants and runs one aggregate action. A serial loop evaluates each row using the same mathematical model but different reduction code. The loss and both components must agree within tight double-precision tolerances.

The driver receives only five scalar fields. It never collects the observation table to optimize it. This is the essential scalability property when the parameter dimension is small. For a million-parameter network, a dense gradient summary itself can become large, and the design must be reconsidered.

## Worked case: a finite-difference oracle catches ordering errors

For each coordinate \(j\), the serial check computes

\[d_j(h)=\frac{L(\beta+h e_j)-L(\beta-h e_j)}{2h},\qquad h=10^{-5}.\]

The two evaluations use identical data and perturb exactly one coordinate. Their difference approximates the corresponding derivative. The fixture asserts an error below \(10^{-8}\), then confirms the intercept and slope derivatives are materially different. If an implementation swaps gradient positions, a mere vector-length check would pass; this fixture exposes the swap.

Finite differences are an oracle for small deterministic examples, not the default distributed optimizer. Tiny \(h\) increases cancellation; large \(h\) increases truncation error. Testing a range of steps is useful when changing loss scale or precision. At non-smooth points, symmetric differences need not represent the intended one-sided derivative.

## Failure diagnosis

Correct loss with a wrong gradient often indicates a missing feature multiplier, a negative-log-likelihood sign error or stale parameter values. A gradient that matches finite differences only after rescaling usually indicates sum-versus-mean confusion. If curvature is negative for this unpenalized logistic intercept, inspect the formula: every term \(p_i(1-p_i)\) is nonnegative.

## Interview discussion

**Can you obtain a Hessian cheaply?** For a small parameter vector, aggregate its analytic components in one pass. The matrix contains quadratic many entries, so transmitting it becomes expensive as dimension grows. Hessian-vector products may be preferable.

**Does an accurate finite difference prove the model is appropriate?** It verifies local numerical implementation of the declared objective. It says nothing about selection bias, identifiability or predictive validity.

## Complete reproducible program

Run this complete source in its declared prepared Spark profile. The fixture is tiny, deterministic and offline. Scala sources are compiled before execution; Python sources use the prepared PySpark environment. These are worked tutorials with no hidden solutions or exams. Runtime: `spark-local-python`.

```python
from __future__ import annotations

import json
import math


def session(name):
    from pyspark.sql import SparkSession

    spark = (
        SparkSession.builder.master("local[2]")
        .appName(name)
        .config("spark.ui.enabled", "false")
        .config("spark.driver.host", "127.0.0.1")
        .config("spark.driver.bindAddress", "127.0.0.1")
        .config("spark.sql.shuffle.partitions", "2")
        .config("spark.sql.adaptive.enabled", "false")
        .config("spark.sql.ansi.enabled", "true")
        .config("spark.sql.session.timeZone", "UTC")
        .getOrCreate()
    )
    if spark.version != "4.0.1":
        spark.stop()
        raise RuntimeError("This worked reference is qualified for Spark 4.0.1")
    spark.sparkContext.setLogLevel("ERROR")
    return spark


def oracle(rows, beta):
    loss, g0, g1 = [], [], []
    for x, y in rows:
        z = beta[0] + beta[1] * x
        p = 1 / (1 + math.exp(-z)) if z >= 0 else math.exp(z) / (1 + math.exp(z))
        loss.append(max(z, 0) + math.log1p(math.exp(-abs(z))) - y * z)
        g0.append(p - y)
        g1.append((p - y) * x)
    return math.fsum(loss), (math.fsum(g0), math.fsum(g1))


def run(spark):
    from pyspark.sql import functions as F

    rows = [(-2.0, 0.0), (-1.0, 1.0), (0.0, 0.0), (1.0, 1.0), (3.0, 1.0)]
    beta = (0.2, -0.4)
    df = spark.createDataFrame(rows, "x double,y double")
    z = F.lit(beta[0]) + F.lit(beta[1]) * F.col("x")
    p = F.when(z >= 0, 1 / (1 + F.exp(-z))).otherwise(F.exp(z) / (1 + F.exp(z)))
    loss = F.greatest(z, F.lit(0.0)) + F.log1p(F.exp(-F.abs(z))) - F.col("y") * z
    r = p - F.col("y")
    out = df.agg(
        F.count("*").alias("n"),
        F.sum(loss).alias("loss"),
        F.sum(r).alias("g0"),
        F.sum(r * F.col("x")).alias("g1"),
        F.sum(p * (1 - p)).alias("h00"),
    ).first()
    expected, g = oracle(rows, beta)
    assert out.n == 5 and math.isclose(out.loss, expected, rel_tol=1e-13)
    assert all(math.isclose(a, b, abs_tol=1e-13) for a, b in zip((out.g0, out.g1), g, strict=True))
    h = 1e-5
    fd = []
    for j in range(2):
        plus = list(beta)
        minus = list(beta)
        plus[j] += h
        minus[j] -= h
        fd.append((oracle(rows, plus)[0] - oracle(rows, minus)[0]) / (2 * h))
    assert max(abs(a - b) for a, b in zip(fd, g, strict=True)) < 1e-8
    assert abs(g[0] - g[1]) > 0.1
    print(
        json.dumps(
            {
                "rows": out.n,
                "loss": out.loss,
                "gradient": g,
                "central_difference": fd,
                "h00": out.h00,
            }
        )
    )


if __name__ == "__main__":
    spark = session("asm-006")
    try:
        run(spark)
    finally:
        spark.stop()
```
