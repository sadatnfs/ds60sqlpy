# dbt-023: Query plans, measured cost and semantic equivalence

## Level and prerequisites

Advanced. Direct prerequisites: `dbt-003`, `dbt-008`, `dbt-022`

**Outcome:** Measure database work with a correctness oracle and a clearly defined interval.

## Question and mechanism

Performance work begins with a correct delivered contract. A query that removes duplicates, drops ordering or changes a filter may run faster because it performs a different computation. Compare values, identities and required ordering before comparing elapsed time. SQL's multiset behavior is particularly important because equal-looking records can represent distinct contributions.

The first case builds a bounded ten-thousand-row relation, executes a grouped query repeatedly and checks its answer with independent Python arithmetic. It also retrieves an actual DuckDB plan. The measured interval covers the query connection/execution path, not the preceding dbt build. Those scopes are reported separately so the timing is not misrepresented as total pipeline cost.

The counterexample applies DISTINCT and changes a total from 17 to 12. It is not a valid optimization for an additive multiset contract. Tiny timings in this classroom are demonstrations of a measurement method, not rankings of databases or capacity promises. A production study needs representative size, distribution, concurrency and failure behavior.

## Syntax and data contract

EXPLAIN returns database planning information; inspect it alongside actual result checks. perf_counter measures a declared interval, and a small repeated sample can report a median without hiding individual variability. Do not assert exact plan text or a guaranteed speed ordering across versions and machines. Materialization, refresh and read costs belong to the complete workload decision.

## Worked case 1: Measure a correctly verified query

The project materializes ten thousand deterministic records and computes five grouped sums over a subset. Every repetition must match an independent oracle. The program confirms that a plan is available and reports a median rather than a universal speed claim.

**Expected evidence:** The five group totals match Python arithmetic and a nonnegative timing summary is reported.

```python
import os
import tempfile
from pathlib import Path
from statistics import median
from time import perf_counter

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def example_one():
    with tempfile.TemporaryDirectory() as d:
        p = project(
            d,
            models={
                "events": (
                    "{{ config(materialized='table') }} select range as id, "
                    "range % 5 as segment, range % 7 as amount from "
                    "range(10000)"
                )
            },
        )
        invoke(p, "build")
        query = (
            "select segment,sum(amount) from events where id < 1000 "
            "group by segment order by segment"
        )
        expected = [(g, sum(i % 7 for i in range(1000) if i % 5 == g)) for g in range(5)]
        timings = []
        for _ in range(3):
            start = perf_counter()
            actual = rows(p, query)
            timings.append(perf_counter() - start)
            assert actual == expected
        plan = rows(p, "explain " + query)
        assert plan and len(str(plan)) > 50 and all(t >= 0 for t in timings)
        return {
            "result": actual,
            "median_query_seconds": median(timings),
            "plan_available": True,
            "dbt_build_time_not_measured_here": True,
        }


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Expose a false optimization

The second project removes a repeated contribution with DISTINCT. Its result is smaller, but the total changes. This makes the semantic cost visible before anyone calls the operation an improvement.

**Expected evidence:** The multiset total is 17; the changed result totals 12.

**Check:** The result remains independently checked.

**Check:** The correct total is 17.

**Hint:** A duplicated value is not necessarily a duplicate event.

## Diagnose errors and misleading results

Near-zero lazy or compile timings may not include query execution. A faster result with different counts or totals is not an equivalent replacement. Check the dataset, cache regime, selected work and result contract before attributing performance to a tool or setting.

## Transfer to independent work

Measure database work with a correctness oracle and a clearly defined interval. Review plans as evidence about this query and version, retain multiset/ordering semantics and include the complete refresh/read workload when choosing materializations.
