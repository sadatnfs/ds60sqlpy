# asm-021: Injecting an exact-version Spark extension

Tutorial mode. Stage: advanced. Direct prerequisites: `asm-020`, `cpp-020`.

## Starting point and result

Spark exposes extension points for functions and query rules, but the `SparkSessionExtensions` API explicitly has no source or binary compatibility guarantee. The owned Catalyst project targets Spark 4.0.1, Scala 2.13 and JDK 17. This is a separately compiled multi-file project. Do not paste its package sources into an ordinary single-file Scala pad and assume the same lifecycle.

## Mechanism: registration precedes query analysis

`TeachingExtensions` implements a function from a session-extension holder to unit. It registers two functions and an optimizer rule. Each function entry binds a SQL identifier, descriptive expression metadata and a builder that receives argument expressions. The builder checks arity and constructs an expression node. The analyzer later checks the node's input types.

The session is created with `withExtensions(new TeachingExtensions)` before `getOrCreate`. Adding an extension after a previously created session has analyzed queries is not equivalent. Extension builders also must not assume every part of session state is already initialized. Initialization order is an API contract, not an incidental placement of code.

The project compiles against jars already present in the prepared image. It does not download arbitrary dependencies during execution. The compile command invokes the matching Scala compiler, packages classes in a JAR and submits the probe with that JAR. Executors must receive the same classes and compatible dependencies in a real cluster.

## Worked case: register and resolve a valid function

The SQL call `teaching_softplus(z)` resolves to the project's `StableSoftplus` node when z is DOUBLE. The probe creates the configured session, runs the function on finite extremes and null, and compares whole-stage modes. The result includes the Spark version and source hashes so a later reader can bind evidence to the compiled source.

A successful run verifies local CPU compilation and execution in the exact environment. It does not establish compatibility with Spark 3, another Scala binary version or a vendor-modified engine. Recompile and rerun the full probe for each supported target rather than relying on a similarly named API.

## Worked case: distinguish arity from type failures

`teaching_softplus(1D, 2D)` has two arguments and is rejected by the function builder. `teaching_softplus(1)` has one integer argument and is rejected by the expression's type check. The project requires an explicit DOUBLE cast rather than silently accepting every numeric type. These are different failures and should produce actionable diagnostics.

In a production extension, define error classes and messages consistently with the target Spark conventions. The teaching probe tests that invalid calls are rejected; it does not promise stable exception wording across unsupported engine versions.

## Failure diagnosis

An unresolved function suggests registration or session-lifecycle problems. A class-not-found error points to JAR distribution or classpath setup. A `NoSuchMethodError` often indicates a binary mismatch even when compilation succeeded against another environment. Retain the exact Spark, Scala and JDK versions with the source and image identifiers.

## Interview discussion

**Why pin all three versions?** Spark internals, Scala binary signatures and JVM capabilities all participate in compilation and execution. Matching only the Spark marketing version is insufficient.

**Should every reusable function become an extension?** No. Prefer public native expressions, UDFs or ML stages when they meet the need. Internal extensions incur upgrade and semantic-maintenance obligations.

# Worked reference: Function registration lifecycle

This is an editable reading/project reference. It has no ordinary pad Run action.

The intended process is: create extension holder, register builders, create a session with those extensions, analyze SQL, plan, execute. A call with one DOUBLE argument resolves to `StableSoftplus`; an INTEGER argument fails the declared type check; two arguments fail arity validation.

Record the actual compile exit, Spark/Scala/JDK identity and probe output. An unresolved function is earlier than execution and cannot be repaired by changing optimizer tolerances. A compiler success without a submitted probe proves only compilation.

See `courses/advanced-spark-modeling/projects/catalyst/README.md` for the bounded offline Docker command. The project compiles its two Scala sources before running the exact-version probe.
