# Python to a compiled TMB boundary

Start with: tmb-022, tmb-007.

Outcome: Call a prepared model while keeping execution, data and native pointers isolated.

The classroom companion runs in the prepared R statistics runtime. It uses base R to expose the mathematics or data contract. Compiling and executing TMB uses the separate [owned project](../projects/tmb-local/README.md); a companion run is not a TMB compiler or rpy2 receipt.

A useful integration boundary is narrow. The Python caller should select a documented model and typed data, then receive numerical results and diagnostics. It should not construct shell commands containing arbitrary C++ text, accept unrestricted library paths from untrusted input, or pretend that an R external pointer can be serialized to another worker.

The owned project provides two paths. `R/evaluate.R` accepts a bounded JSON request for one allowlisted model and evaluates a specified parameter vector. `python/bridge.py` uses embedded R and scoped pandas conversion to fit the original regression model. Both use already prepared libraries. Neither installs packages or compiles a model during a normal evaluation.

### Worked case A: an explicit evaluation request

```json
{
  "schema_version": 1,
  "model": "normal_mean",
  "data": { "y": [1, 2, 4, 7] },
  "parameters": { "mu": 0, "log_sigma": 0 },
  "theta": [2.2, 0.3],
  "random": null
}
```

`parameters` determines declared shapes and initial coordinates. `theta` determines the evaluation point. The response contains the value, gradient, parameter names, row count and software/source identity. This separation supports a Spark driver that changes a shared parameter vector and asks workers for fresh additive contributions. It does not claim to optimize anything merely because an evaluation succeeded.

### Worked case B: stale-library and invalid-data rejection

If a model with the same name is already loaded from another directory, the API rejects it and asks for a fresh R process. If a dataframe contains duplicate IDs, non-finite values or a constant predictor, the Python bridge rejects it before fitting. A caller should retain these failures as explicit results keyed by the attempted input, rather than substituting an older successful fit.

The base-R companion models the fixed flattened coordinate and row-identity checks. Actual bridge acceptance must additionally execute the prepared rpy2 path and compare estimates with an independent least-squares oracle. Test a non-monotonic row-ID order, because an accidental sort can otherwise pass unnoticed.

### Lifecycle and answered discussion

**Can I reuse a process?** Yes with careful ownership, but native objects must remain inside that process and loaded-model identities must match. A fresh bounded process is easier to reason about for isolated examples. **Can I use Spark `mapPartitions`?** It can host a prepared R/TMB boundary when data groups and environment are compatible. Spark supplies scheduling; it does not differentiate through R or its serialization boundary. **Why return gradients rather than an R object?** Plain numerical arrays have an explicit order and can be reduced safely. Native pointers cannot.

See `projects/tmb-local/PROTOCOL.md` for exact request semantics. The Spark/TMB project handles its own group decomposition, retry behavior and numerical parity. A successful local bridge is a prerequisite, not proof of distributed scale or production fault tolerance.

### Complete R companion

```r
request <- list(schema_version = 1L, model = "normal_mean", data = list(y = c(1, 2, 4, 7)), parameters = list(mu = 0, log_sigma = 0), theta = c(2.2, .3))
expected_order <- c("mu", "log_sigma")
stopifnot(identical(names(request$parameters), expected_order), length(request$theta) == 2)
print(setNames(request$theta, expected_order))
ids <- c("r3", "r1", "r2")
returned <- ids
stopifnot(identical(ids, returned))
print(list(correct_order = identical(ids, returned), detect_accidental_sort = !identical(ids, sort(returned))))
```
