# c-035: Signals, interruption and minimal handlers

## Level and prerequisites

Advanced, approximately 120 minutes plus a later retrieval session. Direct prerequisites: `c-034`

## Learning objectives

## Purpose and mental model

A signal is an asynchronous notification delivered to a process or thread under platform rules. A handler can interrupt ordinary execution at an inconvenient point, so it cannot safely call arbitrary library functions or manipulate general shared state. Keep handlers minimal: record a permitted signal flag and let normal control flow perform cleanup. volatile sig_atomic_t is the standard C pattern for a simple handler communication flag, but volatile is not a general thread synchronization mechanism. A synchronous raise in this fixture makes observation deterministic. Production signal handling needs a broader shutdown and interrupted-system-call policy.

## Vocabulary and concepts

- **Signal handler:** A function invoked for an asynchronous signal notification.
- **Async-signal safety:** The restricted operations permitted in signal-handler context.
- **sig_atomic_t:** An integer type usable for simple atomic access in signal handling.

## Syntax anatomy and execution trace

signal installs a handler and returns the previous disposition or SIG_ERR. raise delivers a signal to the running program according to the implementation. A handler receives the signal number. Assign a sig_atomic_t flag and return. Do not call printf, malloc or mutex operations from a portable signal handler. The Linux production alternative sigaction offers more precise disposition control and is a separate POSIX API.

## Worked example / walkthrough

### Worked example 1: Install and restore a handler

Install the lesson handler for SIGINT and restore the previous disposition.

```c
#include <assert.h>
#include <limits.h>
#include <signal.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

volatile sig_atomic_t signal_seen = 0;
void lesson_handler(int number) {
  if (number == SIGINT)
    signal_seen = 1;
}

int main(void) {
  /* Install and restore a handler */
  {
    void (*previous)(int) = signal(SIGINT, lesson_handler);
    CHECK(previous != SIG_ERR);
    CHECK(signal(SIGINT, previous) != SIG_ERR);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** Both operations succeed.

The fixture restores process state instead of leaving a changed signal policy for unrelated later work.

### Worked example 2: Record a raised notification

Raise SIGINT while the lesson handler is installed.

```c
#include <assert.h>
#include <limits.h>
#include <signal.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

volatile sig_atomic_t signal_seen = 0;
void lesson_handler(int number) {
  if (number == SIGINT)
    signal_seen = 1;
}

int main(void) {
  /* Install and restore a handler */
  {
    void (*previous)(int) = signal(SIGINT, lesson_handler);
    CHECK(previous != SIG_ERR);
    CHECK(signal(SIGINT, previous) != SIG_ERR);
  }

  /* Record a raised notification */
  {
    signal_seen = 0;
    void (*previous)(int) = signal(SIGINT, lesson_handler);
    CHECK(previous != SIG_ERR);
    CHECK(raise(SIGINT) == 0);
    CHECK(signal_seen == 1);
    CHECK(signal(SIGINT, previous) != SIG_ERR);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The signal flag becomes one.

The handler only assigns a flag. The ordinary flow performs assertions and restoration after the handler returns.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
