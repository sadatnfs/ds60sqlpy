dme-046: Capacity, latency and cost at the system boundary#

Level: Advanced | Prepared runtime: python-core

Direct prerequisites: dme-018, dme-019, dme-042, dme-043.

Outcome: Compute a bounded workload/capacity model and check its assumptions.

Average load hides the shape of demand#

Capacity planning connects a workload to finite resources and a service objective. A request rate alone is insufficient. You also need service-time distribution, concurrency, burst shape, queue limits, deadlines and the resources each request occupies. A system with low average utilization can still have poor tail latency when many requests arrive together. A system near saturation can become unstable when small variations create queues faster than they drain.

This chapter uses deterministic queue and scan-accounting models. It does not benchmark a machine, quote cloud prices or predict production performance from a tiny fixture. Every time and cost coefficient is declared so the calculations can be checked and changed. Models are useful for identifying which measurements matter and for rejecting impossible designs, but their predictions require validation against actual workloads.

The queue model has identical workers and a fixed service time. It schedules each arriving request on the worker that becomes free first. A request starts at the later of its arrival time and that worker's availability, then finishes after the service interval. Queue waiting is start minus arrival; end-to-end model latency is finish minus arrival. This separates actual service demand from time spent waiting for capacity.

This is a workload accounting ratio, not a complete latency model. Queueing behavior also depends on variability and correlations. Little's law, L=λWL=\lambda WL=λW, relates long-run average population in a stable system to arrival rate and average time in that system under its assumptions. It does not say that every burst experiences the latency predicted from one average number.

The program uses a min-heap of worker availability times. heapq.heappop selects the next free worker; after scheduling, heappush returns its new availability. Sorting arrivals establishes a deterministic order, with original request index breaking ties. The model records each request's arrival, start, finish, waiting and latency, so a reviewer can inspect the schedule rather than trusting only a final percentile.

Worked case 1: identical counts and average demand, different tails#

example_one() compares 20 requests within a declared two-second accounting window. Each request requires 0.1 seconds of service, and four workers are available. The total service demand is two worker-seconds against eight worker-seconds of capacity in that window, giving offered utilization 0.25. One trace spreads arrivals every 0.1 seconds. The other sends all 20 at time zero and then has no additional arrivals in the accounting window.

The steady trace has a 95th-percentile latency of approximately 0.1 seconds. The burst is processed in five waves of four requests. Its 95th-percentile latency is 0.5 seconds, and the maximum wait is 0.4 seconds. Both traces have the same request count and average offered demand over the declared window. Their tail experiences differ because the arrival distribution differs.

The percentile definition is explicit: sort observed latencies and select the nearest-rank position ⌈pn⌉\lceil pn\rceil⌈pn⌉. With 20 observations and p=0.95p=0.95p=0.95, that is the nineteenth value in one-based indexing. Different percentile estimators can interpolate differently on tiny samples, so name the method when comparing results. This deterministic fixture is an illustration, not enough data to estimate a real service's rare tail reliably.

Worked case 2: account for scan amplification without inventing a benchmark#

The second case models a query over partitioned files. Each selected partition has 20 files, each five decimal megabytes. Reading 30 partitions therefore selects 600 files and 3,000 megabytes. Reading one partition selects 20 files and 100 megabytes. The byte amplification is 30, assuming the query can legitimately eliminate the other partitions.

The declared serial timing model charges two milliseconds per file, transfers at 500 megabytes per second and adds 50 milliseconds of fixed work:

The full scan evaluates to 7.25 seconds and the one-partition scan to 0.29 seconds. Those are model outputs, not measured runtimes. Actual readers may overlap requests, cache metadata, decompress at different rates, spill intermediate results or spend more time in later joins. The model intentionally states the serial assumption so it cannot be mistaken for an engine guarantee.

The example also computes illustrative cost units at 0.02 per decimal gigabyte. These are invented accounting units for sensitivity analysis, not a provider's price quote. A real cost estimate must use the actual billing model, including requests, storage, compute, data movement and minimum charges where applicable. A reduction in scanned bytes does not necessarily reduce every billed component proportionally.

Complete worked program#

Run in Python Core. No timers, load generators, external services or billing APIs are involved. The table and report label every result as a declared model.

"""Deterministic queue and scan-cost models with declared units, not runtime benchmarks."""

import heapq
import math


def schedule(arrivals, service, workers):
    if type(workers) is not int or workers < 1 or not math.isfinite(service) or service <= 0:
        raise ValueError("Use positive finite service time and worker capacity")
    if not arrivals or len(arrivals) > 100 or any(not math.isfinite(t) or t < 0 for t in arrivals):
        raise ValueError("Use a bounded nonempty nonnegative arrival trace")
    available = [0.0] * workers
    heapq.heapify(available)
    records = []
    for request, arrival in sorted(enumerate(arrivals), key=lambda item: (item[1], item[0])):
        free = heapq.heappop(available)
        start = max(free, arrival)
        finish = start + service
        heapq.heappush(available, finish)
        records.append(
            {
                "id": request,
                "arrival": arrival,
                "start": start,
                "finish": finish,
                "latency": finish - arrival,
                "waiting": start - arrival,
            }
        )
    return records


def percentile(values, probability):
    if not values or not 0 < probability <= 1:
        raise ValueError("Use a nonempty sample and probability in (0,1]")
    return sorted(values)[math.ceil(probability * len(values)) - 1]


def example_one():
    steady = schedule([i / 10 for i in range(20)], 0.1, 4)
    burst = schedule([0.0] * 20, 0.1, 4)
    steady_p95 = percentile([r["latency"] for r in steady], 0.95)
    burst_p95 = percentile([r["latency"] for r in burst], 0.95)
    assert math.isclose(steady_p95, 0.1) and math.isclose(burst_p95, 0.5)
    assert math.isclose(max(row["waiting"] for row in burst), 0.4)
    return {
        "requests_in_declared_two_second_window": 20,
        "mean_arrivals_per_second": 10,
        "workers": 4,
        "service_seconds": 0.1,
        "average_offered_utilization": 0.25,
        "steady_p95_seconds": steady_p95,
        "burst_p95_seconds": burst_p95,
        "same_average_does_not_determine_tail_latency": True,
    }


def scan_model(partitions, files_per_partition, megabytes_per_file):
    if any(
        type(v) is not int or v < 1 for v in [partitions, files_per_partition, megabytes_per_file]
    ):
        raise ValueError("Use positive integer layout quantities")
    files = partitions * files_per_partition
    megabytes = files * megabytes_per_file
    return {
        "files": files,
        "megabytes": megabytes,
        "modeled_serial_seconds": files * 0.002 + megabytes / 500 + 0.05,
        "illustrative_cost_units": megabytes / 1000 * 0.02,
    }


def example_two():
    full, selected = scan_model(30, 20, 5), scan_model(1, 20, 5)
    assert full["megabytes"] == 3000 and selected["megabytes"] == 100
    assert math.isclose(full["modeled_serial_seconds"], 7.25)
    assert math.isclose(selected["modeled_serial_seconds"], 0.29)
    return {
        "all_partitions": full,
        "one_partition": selected,
        "byte_amplification": 30,
        "assumptions": "serial 2 ms/file + 500 MB/s transfer + 50 ms fixed work; decimal MB",
        "no_real_prices_or_measured_speedup": True,
    }


def main():
    from ds60sqlpy.plot_artifacts import publish_report, publish_table

    first, second = example_one(), example_two()
    print("Average load misses a burst:", first)
    print("A declared scan-layout model:", second)
    publish_table(
        ["scenario", "p95_seconds"],
        [["steady", first["steady_p95_seconds"]], ["burst", first["burst_p95_seconds"]]],
        description=(
            "Deterministic queue model with four workers and 0.1 second "
            "service: steady p95 is 0.1 seconds; burst p95 is 0.5 seconds."
        ),
    )
    publish_report(
        second,
        description=(
            "Illustrative scan accounting with stated file, byte, bandwidth "
            "and cost units; no actual benchmark or price quote."
        ),
    )


if __name__ == "__main__":
    main()

Extend the model only when the added detail matters#

Real service times vary. A few long requests can occupy workers while short requests wait behind them. Separate queues, admission classes or batching can change that behavior, but each policy creates fairness and complexity tradeoffs. If a model has multiple stages, such as feature retrieval, inference and serialization, consider which resources can overlap and which bottleneck limits throughput.

Batching can improve accelerator efficiency while increasing time spent waiting for a batch to fill. Increasing worker count can help until another shared resource becomes limiting, such as memory bandwidth, a database pool or a GPU. A process count larger than physical capacity can also add contention. Measure the system boundary before assuming a resource knob scales linearly.

For data jobs, distinguish scan, shuffle, aggregation and publication. Partition pruning helps only if the question permits eliminating partitions. Compression reduces bytes but costs decompression work. More small files can increase request overhead, while very large files can reduce parallelism or selective-read efficiency. The earlier Parquet and Spark chapters provide actual plan and layout observations that can inform these model terms.

Design an actual measurement#

A useful benchmark states input identity, operation, result contract, runtime versions, hardware, resource limits, warm or cold cache state and repetition policy. It verifies the answer before comparing speed. Record both central tendency and tail behavior where relevant, and separate startup from steady-state work. A fast run that accidentally reads fewer required rows is a correctness failure, not an optimization.

For online services, generate a workload resembling expected arrival patterns rather than only a fixed concurrency loop. Closed-loop clients can slow their sending rate when the service slows, hiding demand that an open arrival process would continue to produce. Record offered, admitted, completed, failed and timed-out work separately. Otherwise rejected or missing requests can make latency look artificially favorable.

Resource measurements also need units and scope. Resident memory differs from Python heap size. GPU allocation differs from total device usage. CPU percentage depends on how many cores the reporting tool treats as 100 percent. A capacity report should explain those conventions so another engineer can reproduce and compare it.

Failure diagnosis and answered interview discussion#

If average utilization is low but p95 is poor, inspect bursts, service-time variability, resource contention and queueing. If adding workers does not increase throughput, identify the shared bottleneck. If a scan model predicts improvement but the query does not speed up, measure the unmodelled stages and verify that pruning actually occurred. If a cost estimate changes dramatically, inspect units and whether the billing boundary matches the measured quantity.

An interviewer may ask, “Can this service handle ten requests per second?” Ask about service-time distribution, bursts, deadline, concurrency and acceptable rejection before answering. If asked what Little's law proves, state its average stable-system relationship and avoid using it as a tail-latency formula. If asked how to compare two layouts, preserve the logical result and measure the terms the layout actually changes.

For an answered extension, doubling the workers from four to eight reduces the burst to three service waves in this simple model, but it does not halve every latency because the 20 requests do not divide evenly into eight-worker waves. Real hardware may scale even less cleanly. Use arithmetic to form a hypothesis, then qualify it through actual measurement.
