# dbt-003: Dependency graphs and materialization choices

## Level and prerequisites

Beginner. Direct prerequisites: `dbt-001`, `dbt-002`

**Outcome:** Choose a materialization using observed database behavior and a stated workload.

## Question and mechanism

ref creates a dependency on another dbt resource and resolves its database relation. That gives dbt a graph it can order and inspect. Hardcoding a table name can bypass this dependency information even when the SQL happens to run. The graph is therefore part of the execution contract, not just a diagram for documentation.

A materialization defines how a model result is represented. A view stores a query definition, a table stores a materialized result, and an ephemeral model is compiled into a dependent query rather than created as its own relation. These choices change storage, freshness, reuse and query cost. They do not change the need to validate grain and values.

The first case uses a staging view and a downstream table, then inspects both the manifest dependency and the actual database relation types. The second uses an ephemeral model to make the absence of a standalone relation explicit. The purpose is to connect configuration to observed behavior rather than memorize names.

## Syntax and data contract

config(materialized='view') or config(materialized='table') declares a model representation. ref('staging') connects the downstream model to its dependency. For an ephemeral input, compiled SQL includes a generated common-table expression. Inspect manifest depends_on nodes and information_schema tables to distinguish graph structure from database objects.

## Worked case 1: Observe the graph and physical objects

The first project links a seed to a staging view and then a materialized total. It verifies the manifest edge, the result 12 and the database object kinds. These checks answer complementary questions.

**Expected evidence:** staging is a view, customer_total is a table, and its dependency names staging.

```python
import json
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def artifact(root, name):
    return json.loads((root / "target" / name).read_text())


def example_one():
    with tempfile.TemporaryDirectory() as d:
        p = project(
            d,
            models={
                "staging": (
                    "{{ config(materialized='view') }} select id, amount from "
                    "{{ ref('raw_orders') }}"
                ),
                "customer_total": (
                    "{{ config(materialized='table') }} select "
                    "sum(amount)::bigint as total from {{ ref('staging') "
                    "}}"
                ),
            },
            seeds={"raw_orders": "id,amount\n1,5\n2,7\n"},
        )
        invoke(p, "build")
        manifest = artifact(p, "manifest.json")
        assert manifest["nodes"]["model.classroom.customer_total"]["depends_on"]["nodes"] == [
            "model.classroom.staging"
        ]
        assert rows(p, "select total from customer_total") == [(12,)]
        kinds = dict(
            rows(
                p,
                (
                    "select table_name, table_type from "
                    "information_schema.tables where "
                    "table_schema='main'"
                ),
            )
        )
        assert kinds["staging"] == "VIEW" and kinds["customer_total"] == "BASE TABLE"
        return {"dependency": "raw_orders -> staging -> customer_total", "total": 12}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Inspect an inlined ephemeral model

The second case builds a dependent model that uses an ephemeral constant. The value reaches the final relation, but the ephemeral model itself is absent from the database object list.

**Expected evidence:** The final answer is 42 and no base relation is created.

## Practice

**Check:** The explicit dependency disappears.

**Hint:** SQL name resolution is not graph declaration.

**Hint:** Check information_schema.

**Hint:** No standalone base table is expected.

## Diagnose errors and misleading results

A relation-not-found error can come from a missing graph edge or an unbuilt dependency. An absent ephemeral relation is expected. A fast view query on tiny data does not establish production performance. Inspect compilation and actual object types before changing orchestration order.
