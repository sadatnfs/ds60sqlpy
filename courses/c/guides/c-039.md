# c-039: Data layout, locality and honest performance experiments

## Level and prerequisites

## Learning objectives

## Purpose and mental model

Memory access patterns can dominate arithmetic cost. An array of structs keeps each record together; a struct of arrays keeps one field across many records contiguous. Which layout is better depends on the operations performed, not a universal rule. Padding, alignment, cache lines and compiler vectorization influence observed performance. Begin with equivalent results and operation counts, then measure representative workloads under controlled builds. Do not publish a speedup based on one tiny timing or assume a particular cache-line size from a diagram. Optimization must preserve bounds, aliasing and numerical contracts.

## Vocabulary and concepts

- **Locality:** Accessing nearby data within a short time interval.
- **Array of structs:** A layout grouping complete records together.
- **Struct of arrays:** A layout grouping each field across records together.

## Syntax anatomy and execution trace

sizeof reports actual object size including padding. offsetof gives a field offset without dereferencing a null pointer. Iterate only over initialized logical elements. restrict can promise nonaliasing to the compiler, but violating that promise is a correctness defect; it is not a harmless performance hint. The fixture compares layouts semantically and intentionally makes no wall-clock threshold assertion.

## Worked example / walkthrough

### Worked example 1: Sum one field in records

Sum x fields from three Point records.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

struct Point {
  int x, y;
};

int main(void) {
  /* Sum one field in records */
  {
    struct Point records[] = {{1, 10}, {2, 20}, {3, 30}};
    int sum = 0;
    for (size_t i = 0; i < 3; i++)
      sum += records[i].x;
    CHECK(sum == 6);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** The result is 6.

This traversal touches a selected field in each record. Whether unused fields waste bandwidth depends on the real layout and workload.

### Worked example 2: Compute the same result by columns

Sum an x column containing 1, 2, 3.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

struct Point {
  int x, y;
};

int main(void) {
  /* Sum one field in records */
  {
    struct Point records[] = {{1, 10}, {2, 20}, {3, 30}};
    int sum = 0;
    for (size_t i = 0; i < 3; i++)
      sum += records[i].x;
    CHECK(sum == 6);
  }

  /* Compute the same result by columns */
  {
    int x[] = {1, 2, 3};
    int y[] = {10, 20, 30};
    int sum = 0;
    for (size_t i = 0; i < 3; i++)
      sum += x[i];
    CHECK(sum == 6 && y[2] == 30);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** The result is also 6.

Equivalent semantics must be established before comparing timings. The y column remains independent storage.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
