# c-023: Hash tables, collisions and explicit occupancy

## Level and prerequisites

Intermediate, approximately 120 minutes plus a later retrieval session. Direct prerequisites: `c-022`

## Learning objectives

Explain collision, probe sequence, load factor. Implement the six investigations with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

A hash table maps a key to a candidate storage position. Different keys can collide, so a hash value is not proof of key equality. Open addressing resolves collisions by probing alternative slots under a bounded policy. Each slot needs occupancy information separate from its stored key and value, because zero may be a legitimate key or value. Deletion in an open-addressed table requires care: clearing a slot can break the search chain for later colliding entries. This small fixed table supports insertion, replacement and lookup, and deliberately does not pretend that naive clearing implements deletion.

## Vocabulary and concepts

- **Collision:** Different keys selecting the same initial hash position.
- **Probe sequence:** The ordered candidate positions searched after a collision.
- **Load factor:** The fraction of table capacity occupied by entries.

## Syntax anatomy and execution trace

The fixture uses unsigned integer keys and linear probing across eight slots. Every probe checks used and then compares the actual key. A probe loop has a capacity bound so a full table cannot cause an infinite search. Inserting an existing key replaces its value without consuming another slot. Production designs choose a load factor, resizing policy, hash function and collision-resistance requirements from their input threat model.

## Worked example / walkthrough

### Worked example 1: Insert and retrieve

Store key 1 with value 7.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

enum { TABLE_CAPACITY = 8 };
struct Entry {
  bool used;
  unsigned key;
  int value;
};
struct Table {
  struct Entry entries[TABLE_CAPACITY];
};
bool table_put(struct Table *t, unsigned key, int value) {
  for (size_t step = 0; step < TABLE_CAPACITY; step++) {
    size_t i = (key % TABLE_CAPACITY + step) % TABLE_CAPACITY;
    struct Entry *e = &t->entries[i];
    if (!e->used || e->key == key) {
      e->used = true;
      e->key = key;
      e->value = value;
      return true;
    }
  }
  return false;
}
bool table_get(const struct Table *t, unsigned key, int *out) {
  for (size_t step = 0; step < TABLE_CAPACITY; step++) {
    size_t i = (key % TABLE_CAPACITY + step) % TABLE_CAPACITY;
    const struct Entry *e = &t->entries[i];
    if (!e->used)
      return false;
    if (e->key == key) {
      *out = e->value;
      return true;
    }
  }
  return false;
}

int main(void) {
  /* Insert and retrieve */
  {
    struct Table t = {0};
    int out = 0;
    CHECK(table_put(&t, 1, 7) && table_get(&t, 1, &out) && out == 7);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** Lookup succeeds with 7.

Lookup checks the actual key rather than trusting the initial slot alone.

```c
int main(void) {
  /* Insert and retrieve */
  {
    struct Table t = {0};
    int out = 0;
    CHECK(table_put(&t, 1, 7) && table_get(&t, 1, &out) && out == 7);
  }

  /* Resolve a collision */
  {
    struct Table t = {0};
    int out = 0;
    CHECK(table_put(&t, 1, 10) && table_put(&t, 9, 90));
    CHECK(table_get(&t, 1, &out) && out == 10);
    CHECK(table_get(&t, 9, &out) && out == 90);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** Both values remain retrievable.

Linear probing finds another free slot while preserving the key distinction.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
