# dbt-025: Recovery, accepted versions and atomic pointers

## Level and prerequisites

Advanced. Direct prerequisites: `dbt-015`, `dbt-019`, `dbt-021`

**Outcome:** Recover a data product through explicit accepted versions and a tested pointer mechanism.

## Question and mechanism

Recovery begins by identifying which state was accepted and which operations may already have happened. A failed candidate build can leave new relations, while consumers should continue using a previously accepted product. Keeping a distinct accepted version makes that decision possible without pretending every build is one global transaction.

The first case creates a consumer-facing view over a versioned accepted table. It changes that pointer inside a real DuckDB transaction and rolls the transaction back. The original value remains visible afterward. This qualifies a local database mechanism, not atomicity across multiple services, filesystems and warehouses.

The second case materializes a candidate 99 that violates a declared maximum 50, while an accepted release retains 42. The failed test does not erase the candidate, and the consumer boundary is intentionally not advanced. A durable operating procedure should also specify ownership, retries, uncertain outcomes, retention and how a rollback restores a compatible set of data and code.

## Syntax and data contract

BEGIN/ROLLBACK delimit the demonstrated database transaction. The accepted relation and publication view have separate names from the candidate. Inspect actual values after the failure or rollback. A model/source version and its validation evidence should travel with the accepted artifact; a name such as latest is insufficient without an identity contract.

## Worked case 1: Roll back a pointer change

The first case temporarily changes the view's visible value inside a transaction, observes the candidate and rolls back. The final query must again return the original version and value. This is actual database behavior on an owned file.

**Expected evidence:** The temporary 99 is visible inside the transaction; rollback restores version 1/value 42.

```python
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def example_one():
    with tempfile.TemporaryDirectory() as d:
        p = project(
            d,
            models={
                "candidate": "{{ config(materialized='table') }} select 1 as version, 42 as value"
            },
        )
        invoke(p, "build")
        with duckdb.connect(str(p / "warehouse.duckdb")) as c:
            c.execute("create schema published")
            c.execute("create table published.release_one as select * from candidate")
            c.execute(
                "create view published.current_product as select * from published.release_one"
            )
            c.execute("begin")
            c.execute(
                "create or replace view published.current_product as "
                "select 2 as version, 99 as "
                "value"
            )
            assert c.execute("select value from published.current_product").fetchone() == (99,)
            c.execute("rollback")
            assert c.execute("select version,value from published.current_product").fetchone() == (
                1,
                42,
            )
        return {"transactional_pointer_rollback": True, "retained_release": [1, 42]}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Retain an accepted product after candidate failure

The second case builds a candidate that fails a data test. Its relation contains 99, but the separately retained accepted release still contains 42. The publication decision remains separate from materialization.

**Expected evidence:** The candidate is rejected and the accepted value remains 42.

```python

def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def example_two():
    with tempfile.TemporaryDirectory() as d:
        p = project(
            d,
            models={"candidate": "{{ config(materialized='table') }} select 1 as id, 42 as value"},
        )
        invoke(p, "build")
        with duckdb.connect(str(p / "warehouse.duckdb")) as c:
            c.execute("create table accepted_release as select * from candidate")
        (p / "models/candidate.sql").write_text(
            "{{ config(materialized='table') }} select 1 as id, 99 as value"
        )
        (p / "tests").mkdir()
        (p / "tests/value_policy.sql").write_text(
            "select * from {{ ref('candidate') }} where value > 50"
        )
        invoke(p, "build", succeeds=False)
        assert rows(p, "select value from candidate") == [(99,)]
        assert rows(p, "select value from accepted_release") == [(42,)]
        return {"candidate_rejected": 99, "accepted_release_unchanged": 42}
```

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Inspect both states

Query candidate and accepted relations after failure.

**Check:** Their different values are explicit.

**Hint:** Do not infer state from the final exit code alone.


### 2. Commit an accepted change

Repeat the pointer transaction under a valid policy and commit it.

**Check:** The new accepted view is visible afterward.

**Hint:** Approval evidence must precede promotion.


### 3. Handle an uncertain response

Describe a client timeout after a possible commit.

**Check:** The response reconciles the intended version before retry.

**Hint:** Unknown outcome is not confirmed rollback.


### 4. Restore compatible components

List what a data/model rollback may need beyond one table.

**Check:** It includes schema, features, model and interface versions.

**Hint:** A technically successful pointer switch can still be incompatible.


### 5. Bound retention

Define how old accepted versions are removed.

**Check:** Ownership and retention rules are explicit.

**Hint:** Cleanup is a separate destructive action.


### 6. Separate transaction scopes

Explain what the local rollback test cannot prove.

**Check:** It does not establish a distributed transaction.

**Hint:** Other services can commit independently.


## Diagnose errors and misleading results

If recovery changes more than intended, stop and identify the candidate, accepted version and actual consumer pointer. A failed test may leave materialized data. A timeout may leave an unknown commit outcome. Reconcile state before retrying or deleting evidence.
