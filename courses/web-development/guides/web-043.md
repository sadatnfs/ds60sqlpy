# web-043: Dates, time zones and deterministic clocks

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-042`

## Learning objectives

Build a deterministic study-session time report. Explain why a numeric offset is not a complete regional time-zone rule. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

An instant identifies a point on the timeline. A local date and time require a time zone and can be ambiguous or nonexistent around daylight-saving transitions. A fixed offset such as +00:00 is not the same as a named region with changing rules. Store and communicate the representation deliberately instead of assuming every day has exactly twenty-four local hours.

DateTimeImmutable returns a new object when modified, which reduces accidental changes to a shared value. Deterministic tests use a fixed clock or an injected instant rather than the current wall time. Otherwise a test can change result at midnight or fail only in another developer's time zone. User-facing formatting belongs at the presentation boundary.

## Syntax anatomy and mechanism

Parse a documented ISO-like timestamp with an explicit offset for the basic example. Convert to another zone for display without changing the represented instant. A duration measured in elapsed seconds differs from a calendar operation such as next day in a region. Validate parsing failures and inspect warnings when accepting externally formatted dates.

## Worked example / walkthrough

### Worked example 1: A fixed instant

The offset removes ambiguity from this example.

```php
$instant = new DateTimeImmutable('2024-01-01T12:00:00+00:00');
```

**Expected observation:** The timestamp represents noon UTC on the stated date.

### Worked example 2: A display conversion

The instant stays the same while its local representation changes.

```php
$local = $instant->setTimezone(new DateTimeZone('America/New_York'));
echo $local->format('Y-m-d H:i P');
```

**Expected observation:** The winter local representation is 2024-01-01 07:00 -05:00.

## Six progressive exercises

### Exercise 1: Explain an instant versus a local clock reading.

**Expected evidence:** An instant is a timeline point; a local reading needs zone context and can be ambiguous.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Convert a fixed instant to a named time zone.

**Expected evidence:** The displayed hour changes but the Unix timestamp remains equal.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a deterministic study-session time report.

**Expected evidence:** The output uses explicit time zones and a fixed input suitable for repeatable tests.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a test that fails around midnight.

**Expected evidence:** Replace ambient current time with a controlled clock or input.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Compare elapsed seconds with a calendar-day operation near a clock change.

**Expected evidence:** They can represent different elapsed durations; document which the application intends.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain why a numeric offset is not a complete regional time-zone rule.

**Expected evidence:** A region can change offsets over time due to daylight saving or policy changes.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not hardcode a region's current offset as a permanent rule. Avoid using the current date in a test that claims deterministic output. Parsing a date-looking string successfully does not prove it matched the application's intended format.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.
