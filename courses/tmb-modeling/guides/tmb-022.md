# Pandas, NumPy and R conversion

Start with: tmb-005, r-019.

Outcome: Define and test a typed data contract before crossing the Python/R boundary.

The classroom companion runs in the prepared R statistics runtime. It uses base R to expose the mathematics or data contract. Compiling and executing TMB uses the separate [owned project](../projects/tmb-local/README.md); a companion run is not a TMB compiler or rpy2 receipt.

A dataframe is more than a rectangular array. Column names, numeric types, missingness, category levels, timestamps and row keys all carry meaning. A conversion that preserves visible values but loses identity or changes missing-value semantics can silently fit the wrong model.

The original bridge accepts exactly three columns in order: `row_id`, `x`, `y`. Keys must be unique nonempty strings. Predictors and outcomes must be finite numerical scalars, with no booleans or missing values. It converts numerical columns to float64, preserves input row order and verifies returned row IDs. It deliberately rejects unsupported schemas rather than guessing how to encode them.

### Worked case A: scoped pandas conversion

Current rpy2 uses a local conversion context:

```python
with (ro.default_converter + pandas2ri.converter).context():
    r_frame = ro.conversion.get_conversion().py2rpy(clean)
```

Only that block uses the pandas converter. The older PyMB project used global converter activation, which is not the pattern used here. Importing our bridge does not start R. The actual `fit_frame` call lazily imports rpy2 and requires the main thread because an embedded R interpreter should not be shared casually among Python threads.

The companion demonstrates R-side row identity and explicit missingness rejection. Actual pandas/rpy2 execution requires the separately prepared compatible Python/R environment and has its own test receipt. A Python import or an R-only dataframe calculation is not evidence of a successful cross-language round trip.

### Worked case B: categories and time zones need explicit policy

Suppose a future model adds a category and timestamp. Encode category levels using a frozen training vocabulary and define how unknown levels are handled. Keep timestamps in an explicit zone, usually UTC, and define whether a calendar day means UTC or local civil time. NumPy arrays omit column names; a pandas index is not automatically a stable model key. Convert keys into an explicit column before any sorting or grouping.

Our small regression bridge does not accept these extra fields. The companion shows an explicit category order and UTC timestamp representation as a contract example, not as a capability of the current bridge. Extending the schema requires versioning and new tests for round trips, unknown categories, daylight-saving boundaries and missingness.

### Diagnostics and answered discussion

**Is conversion zero-copy?** Not generally; object types such as strings can require copying. Budget memory for both representations. **Can an integer ID be stored as a double?** Large integers may exceed exact float64 integer precision. Use strings for keys. **Should missing values be dropped silently?** No. Missingness handling is part of the statistical model and must preserve a traceable row policy.

Read [rpy2's pandas documentation](https://rpy2.github.io/doc/latest/html/pandas.html). The [historical PyMB project](https://github.com/kforeman/PyMB) is useful context, but its wrapper and licensing are separate from this original fixed-model implementation.
