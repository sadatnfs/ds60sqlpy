k8s-045: Pod network namespaces, sidecars and localhost#

Level and prerequisites#

Intermediate; about 120 minutes plus optional supervised host observations. Direct prerequisites: k8s-044. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

Learning objectives#

Draw a sidecar and app port allocation. Defend whether a helper belongs in a sidecar or separate Deployment. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

Purpose, vocabulary and mental model#

Containers in the same Pod share a network namespace. They can communicate through localhost and share the Pod’s port space. Containers in different Pods normally have different network namespaces and Pod addresses. This makes a Pod a unit of co-location and shared networking rather than merely a label grouping unrelated containers.

Loopback always refers to the caller’s network namespace. A sidecar in the same Pod can reach an application bound to 127.0.0.1:8080. A different Pod cannot reach that listener through the first Pod’s loopback address. To accept traffic on the Pod interface, the application generally listens on an appropriate non-loopback address, often 0.0.0.0 for IPv4.

A sidecar is a supporting container associated with an application Pod. It may proxy traffic, collect logs or perform another bounded role. Co-location introduces shared fate, startup and shutdown ordering, resource competition and port conflicts. A sidecar is not automatically a separate security or availability boundary.

Mechanism and field-by-field reasoning#

The containerPort field documents a container’s intended port and can supply a name used elsewhere. It does not start a listener. Two containers in one Pod cannot both bind the same address/port combination independently. Their filesystem namespaces can still differ even though networking is shared.

An emptyDir volume is one way to share files within a Pod, but it is not implied by shared networking and does not survive Pod replacement. Keep the network and storage contracts distinct when explaining a sidecar design.

Worked example / walkthrough#

Worked example 1: Compare two localhost callers#

The same string names different destinations in different Pods.

sidecar in PodA ->127.0.0.1:8080 -> app in PodA
client in PodB ->127.0.0.1:8080 -> PodB itself

Expected observation: Only the same-Pod sidecar reaches PodA through loopback.

Worked example 2: Read a declared port#

This is metadata in a Pod container specification.

ports:
  - name: http
    containerPort: 8080

Expected observation: The field does not cause any process to bind 8080.

Diagnosis, failure boundaries and common mistakes#

The controlled failure in this chapter is: Diagnose two containers binding 0.0.0.0:8080. Its distinguishing result is They compete for the same socket within one Pod namespace. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
