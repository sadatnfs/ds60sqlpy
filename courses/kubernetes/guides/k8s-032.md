# k8s-032: Disruptions and availability budgets

## Level and prerequisites

Advanced; about 135 minutes plus review. Direct prerequisites: `k8s-026`, `k8s-028`.

## Learning objectives

Predict what an eviction budget protects and what it cannot prevent.

## Vocabulary and concepts

A PodDisruptionBudget, abbreviated PDB, constrains supported voluntary evictions of a selected application. It helps coordinate maintenance with the application's available replicas. It does not stop a machine from failing, guarantee scheduling capacity or make a directly deleted Pod survive. The distinction matters because the same observed lost replica can result from very different control paths.

Our example selects app=hello and sets minAvailable 1 while the Deployment desires two replicas. In a simplified healthy snapshot with both Pods available, one voluntary disruption can fit the budget. If only one is healthy, another disruption does not fit. The API status and eviction decision are authoritative for the actual moment, because readiness and in-progress disruptions can change between observations.

The normal browser run does not drain Nodes or issue learner-controlled eviction requests. This advanced lab needs an exclusive multi-node lease and a host operation restricted to one owned worker Node. The application remains namespaced, but Node maintenance is a separate host-level capability with a deadline, cancellation and restoration plan.

### Key terms

- **PodDisruptionBudget:** An object that limits how many selected Pods may be voluntarily disrupted at once, through minAvailable or maxUnavailable.
- **Voluntary disruption:** A deliberate Pod removal, such as a node drain, that respects PodDisruptionBudgets, unlike a node failure.
- **Eviction API:** The API path that removes a Pod only if its PodDisruptionBudget allows it and refuses otherwise.
- **Node drain:** Cordoning a node and evicting its Pods through the Eviction API before maintenance.
- **disruptionsAllowed:** The PodDisruptionBudget status field that reports how many more voluntary disruptions are allowed right now.

## Read budget arithmetic and status

minAvailable is the minimum healthy selected count the budget aims to preserve during supported voluntary disruption. maxUnavailable is an alternative expression; this fixture uses an integer minimum to avoid percentage rounding ambiguity. The selector must match the intended Pods, and an accidentally broad selector changes the application set being counted.

For the teaching trace, \(\text{allowed}=\max(0,\text{healthy}-\text{minimum})\). With healthy 2 and minimum 1, the result is 1. After one Pod becomes unavailable, healthy 1 yields 0. Real PDB status also accounts for controller observation and already disrupted Pods. Do not use a stale handwritten subtraction as permission to evict.

Read currentHealthy, desiredHealthy, disruptionsAllowed and observedGeneration together. A budget with disruptionsAllowed 0 is not necessarily broken: it may be correctly refusing maintenance because replacement capacity or readiness is missing. Diagnose the selected workload before weakening the budget.

## Separate eviction, deletion and node loss

An eviction request uses the Eviction API and can be rejected when the disruption budget would be violated. A direct Pod delete is a different operation and can bypass that protection. A node outage is involuntary; the budget cannot prevent physical or virtual machine failure. Workload redundancy and placement address different parts of availability.

A host drain includes more than the arithmetic: it may make the Node unschedulable and handle several workload classes. The course operation must select one exact owned worker identity and exclude unrelated resources. The learner does not run a broad drain against the active context or add force/delete-data flags to overcome a refusal.

Recovery requires replacements to schedule and become ready on remaining capacity. A two-node label alone does not guarantee spare CPU, topology compatibility or volume attachment. Observe pending reasons and application responses, then restore the intended Node scheduling state through the host-owned operation.

## Worked example / walkthrough

### Worked example 1: Compute a snapshot budget

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: hello-budget
spec:
  minAvailable: 1
  selector:
    matchLabels:
      app: hello
```
With two selected healthy Pods, minimum 1 leaves one potential disruption. With one healthy Pod, it leaves zero.

**Expected:** The arithmetic predicts 1 then 0, subject to actual current PDB status and in-progress operations.

### Worked example 2: Compare protected and unprotected loss

Trace A: Eviction API refuses the last healthy Pod. Trace B: a direct Pod delete removes it. Trace C: the hosting Node disappears. Only A demonstrates the budget enforcing its supported voluntary path.

**Expected:** The PDB is a coordination mechanism for eviction, not a universal prevention of Pod loss.

## Exercises

### Exercise 1: Verify selector scope

Compare app=hello selector against two hello Pods and one unrelated Pod.

**Expected result/shape:** Exactly the two hello Pods contribute to this example.

**Verify:** Apply the selector to each Pod's labels; only selected Pods count toward the budget.

**Progressive hints:** Count selected healthy Pods, not all Pods in the namespace.

### Exercise 2: Predict healthy-count changes

Evaluate healthy counts 2, 1 and 0 with minimum 1.

**Expected result/shape:** Potential disruptions 1, 0, 0 in the simplified model.

**Verify:** Subtract the minimum from each healthy count and replace any negative result with zero.

**Progressive hints:** Clamp the difference at zero.

### Exercise 3: Capture a denied eviction

Use the host allowlisted operation when one selected Pod is healthy.

**Expected result/shape:** Denial is tied to the intended PDB and Pod UID.

**Verify:** Use the Eviction API path, record the 429 response and the PDB it names, and confirm that the Pod UID is unchanged afterwards.

**Progressive hints:** Avoid substituting direct delete.

### Exercise 4: Observe a permitted maintenance path

With the qualified two-replica state, request one bounded owned-worker maintenance operation.

**Expected result/shape:** Allowed disruption, replacement readiness and finite application success are recorded.

**Verify:** Record the evicted Pod UID, the replacement Pod UID with its Ready time, and one application request after replacement.

**Progressive hints:** A successful eviction is only the start of recovery.

### Exercise 5: Diagnose unavailable replacement capacity

Interpret Pending due to requests, affinity or volume placement.

**Expected result/shape:** A specific scheduling/storage cause is named without weakening unrelated policy.

**Verify:** Read the Pending Pod's `FailedScheduling` event and name the single condition the scheduler reported.

**Progressive hints:** Read events and the requested resources.

### Exercise 6: State protection limits and restore

Compare eviction with direct delete/node loss and restore host scheduling state.

**Expected result/shape:** Only the tested voluntary path is claimed; owned Node state is restored.

**Verify:** Confirm that the claim covers only voluntary eviction and that the node's `spec.unschedulable` is back to its original value.

**Progressive hints:** Availability has multiple failure boundaries.

## Self-check

A node crash removed both hello Pods despite hello-budget. Why did the budget not prevent it, and which kind of disruption does it actually coordinate?

## Common pitfalls

A blocked eviction is useful evidence of a protected boundary, not an invitation to delete the Pod directly. Record the budget, selected Pod UID, readiness and response reason. A successful eviction is also not enough: replacement readiness and application behavior must satisfy the end-to-end maintenance goal.

This small kind rehearsal does not establish production high availability, zone failure tolerance or durable storage resilience. Report the specific voluntary maintenance path, finite observations and untested failure modes.
