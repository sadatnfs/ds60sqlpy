# go-034: Build targets, containers and graceful process design

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-033

## Learning objectives

Check the running build target against a supported set and model a graceful shutdown that drains work honestly. Along the way, explain build target, multi-stage build, graceful shutdown; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

An executable is built for a target operating system and architecture. Source portability does not imply one binary runs everywhere. Go can cross-compile many pure-Go programs by choosing GOOS and GOARCH, while cgo and platform-specific dependencies introduce additional constraints. Container images package the executable and its runtime files, but still depend on a compatible kernel and architecture. A small image is useful only if certificates, time-zone needs and diagnostic requirements remain satisfied. Production shutdown must stop accepting new work, cancel or drain owned tasks within a budget, and report incomplete work honestly.

## Vocabulary and concepts

- **Build target:** The operating system and architecture selected for a binary.
- **Multi-stage build:** A build separating toolchain and runtime filesystem stages.
- **Graceful shutdown:** A bounded transition from accepting work to releasing owned resources.

## Syntax anatomy and reasoning

runtime.GOOS and GOARCH describe the running binary target. Build configuration uses environment variables before compilation, not source-level guesses. A multi-stage Dockerfile can compile in a toolchain image and copy the binary into a runtime stage. CGO_ENABLED=0 is appropriate for this standard-library classroom profile; it is not a universal instruction for every dependency. Use an exec-form container entrypoint so the process receives termination signals directly.

## Worked example / walkthrough

### Worked example 1: Inspect the current target

Read runtime target identifiers.

```go
package main

import (
	"fmt"
	"runtime"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Inspect the current target
	{
		check(runtime.GOOS != "" && runtime.GOARCH != "", "target")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Both identifiers are nonempty.

The values describe this executed binary. They do not establish compatibility with another platform.

### Worked example 2: Validate the running deployment tuple

Check the worker's own GOOS/GOARCH pair against an explicit linux/amd64 and linux/arm64 target set.

```go
package main

import (
	"fmt"
	"runtime"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Inspect the current target
	{
		check(runtime.GOOS != "" && runtime.GOARCH != "", "target")
	}

	// Validate the running deployment tuple
	{
		allowed := map[string]bool{"linux/amd64": true, "linux/arm64": true}
		target := runtime.GOOS + "/" + runtime.GOARCH
		check(allowed[target], "running target")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The running Linux tuple is admitted.

A declared target set is a configuration contract, and the classroom worker is a Linux container on amd64 or arm64, so its own tuple must be in the set. Each additional image architecture still needs its own build and execution evidence.

## Exercises

### Exercise 1: Inspect the current target: predict an edited check

Copy worked example 1 into a scratch pad and change `check(runtime.GOOS != "" && runtime.GOARCH != "", "target")` to `check(runtime.GOOS == "" && runtime.GOARCH != "", "target")` inside its check. Before running, predict whether the check still passes and explain why; then restore it.

**Expected:** The changed run panics with `target` because the edited check no longer holds. Restoring the original line brings back the worked observation: both identifiers are nonempty.

**Verify:** Compare your written prediction with the panic message `target` and name the value that made `runtime.GOOS != "" && runtime.GOARCH != ""` false. After restoring the input, the program must print its success line again.

### Exercise 2: Validate the running deployment tuple: debug a regression

A regression changed one token in worked example 2, so one line now reads `allowed := map[string]bool{"linux/amd64": true, "linux/arm65": true}`. Run worked example 2 with that line, use the failure to locate the defect and repair it without changing the check.

**Expected:** Before the repair the program panics with `running target`; after it the line reads `allowed := map[string]bool{"linux/amd64": true, "linux/arm64": true}` again and the running Linux tuple is admitted.

**Verify:** Keep the failing and the repaired runs. Explain why the changed token alters the value tested by `allowed[target]` for this input.

### Exercise 3: Refuse an unsupported tuple

Check plan9/386 and an incomplete linux tuple with the same lookup, keeping linux/arm64 as the control.

**Expected:** Both unsupported tuples are rejected while linux/arm64 is admitted.

**Verify:** Keep a check equivalent to `!supported("plan9", "386") && !supported("linux", "") && supported("linux", "arm64")`. As a control, change `allowed := map[string]bool{"linux/amd64": true, "linux/arm64": true}` to `allowed := map[string]bool{"linux/amd64": true, "linux/arm65": true}`: the run must panic with `unsupported`. Restore the line before continuing.

### Exercise 4: Model stop-accepting before drain

Start with two active tasks, drain the service, try to admit a third task, then finish both tasks.

**Expected:** The third task is refused once draining begins, and the service stops only after both tasks finish.

**Verify:** Keep a check equivalent to `!s.Admit() && s.Active == 2`. As a control, change `s := ServiceState{Accepting: true, Active: 2}` to `s := ServiceState{Accepting: true, Active: 3}`: the run must panic with `drain start`. Restore the line before continuing.

### Exercise 5: Retain unfinished work evidence

Admit one more task to a service already running one, drain it, and allow a shutdown budget of one completion.

**Expected:** One of the two tasks remains unfinished and visible.

**Verify:** Keep a check equivalent to `s.Active == 1`. As a control, change `for i := 0; i < budget; i++ {` to `for i := 0; i <= budget; i++ {`: the run must panic with `unfinished work`. Restore the line before continuing.

### Exercise 6: Transfer deterministic version metadata

Format a version and source revision into a build label.

**Expected:** The result is lesson/1.0 revision=abc123.

**Verify:** Keep a check equivalent to `label == "lesson/1.0 revision=abc123"`. As a control, change `label := fmt.Sprintf("%s/%s revision=%s", "lesson", "1.0", "abc123")` to `label := fmt.Sprintf("%s/%s revision=%s", "lesson", "2.0", "abc123")`: the run must panic with `version`. Restore the line before continuing.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
