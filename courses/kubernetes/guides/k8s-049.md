# k8s-049: EndpointSlices, readiness and backend identity

## Level and prerequisites

Intermediate; about 120 minutes. Direct prerequisites: `k8s-048`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Join eligible endpoint references to current Pod UIDs.
- Prove a replacement backend is actually used.

## Purpose, vocabulary and mental model

EndpointSlices describe sets of network endpoints associated with a Service. They include addresses, ports and condition information, and can reference the Pod supplying an endpoint. The controller uses them to scale endpoint management beyond one monolithic object. A Service can have several slices, so reading only the first is incomplete.

Readiness influences whether a Pod should receive ordinary new Service traffic under the relevant routing behavior. Running is a process phase and does not imply Ready. Endpoint conditions ready, serving and terminating describe related but distinct lifecycle facts. Under the API contract, an omitted ready or serving condition is interpreted as true, and omitted terminating as false. For Pod-backed endpoints, serving follows the Pod Ready condition. Ordinary ready generally expresses serving and not terminating, with documented overrides.

Identity matters during replacement. A new Pod can reuse a familiar name pattern but has a new UID. To prove traffic eligibility belongs to the intended revision, join endpoint target references to current Pod UIDs and inspect actual application behavior. A stale IP list from an earlier run is insufficient.

### Key terms

- **EndpointSlice:** An API object listing a subset of a Service's backend addresses, ports and conditions, which forwarding components read.
- **Endpoint ready condition:** Marks an endpoint that should receive new traffic, normally matching the Pod's readiness.
- **Endpoint serving condition:** Reports whether a backend is still able to serve, even while terminating, so an implementation can fall back to it.
- **Endpoint terminating condition:** Marks an endpoint whose Pod is shutting down.
- **Endpoint targetRef:** A reference from an endpoint to the Pod that backs it, used to trace an address to an object.

## Mechanism and field-by-field reasoning

The following table distinguishes common condition states. It is a contract-reading exercise, not a fabricated runtime result.

| Endpoint state | serving | terminating | ordinary ready |
| --- | --- | --- | --- |
| Serving normally | true | false | true |
| App not ready | false | false | false |
| Still serving while terminating | true | true | false |
| All three conditions omitted | interpreted true | interpreted false | interpreted true |

For publishNotReadyAddresses, ready can be forced true even when ordinary application readiness is false. A proxy may use serving terminating endpoints for draining/fallback when all available endpoints are terminating. These exceptions mean ready alone is not a universal application-health oracle. The ordinary synthetic fixture uses explicit true/false readiness and no publishNotReadyAddresses override.

Select slices by the standard service-name label and aggregate all returned endpoints of the relevant address family and port. Match targetRef.uid where supplied, rather than assuming an address uniquely identifies the expected Pod forever. Preserve slice ownership and resource versions in a diagnostic record.

The fixture includes two endpoint observations, one ready and one not ready. The offline checker classifies them, but actual routing remains an owned runtime observation. Do not manually mark a controller-owned endpoint ready to bypass an app readiness failure.

## Trace the request or control path

```text
Pod readiness + Service selector -> EndpointSlice controller -> endpoint conditions
service data plane consumes endpoint state -> fresh client request proves actual delivery
```

Line one is two inputs feeding one controller: Pod readiness and the Service selector. Its output is a set of endpoint conditions, not traffic. Line two shows the data plane consuming those conditions later, so a slice can already say pod-a is ready while some node has not caught up. Only a fresh request names the backend that actually answered.

## Worked example / walkthrough

### Worked example 1: Read two synthetic endpoints

These are teaching observations, not API output from your cluster.

```json
{
  "endpoints": [
    { "ip": "10.244.1.7", "uid": "pod-a", "ready": true },
    { "ip": "10.244.2.9", "uid": "pod-b", "ready": false }
  ]
}
```

**Expected observation:** Only pod-a is eligible under the simplified ordinary-ready policy used in this fixture.

### Worked example 2: Distinguish process and routing readiness

The state can be Running while the app is not ready.

```text
Pod phase=Running
Ready condition=False
Endpoint ready=False
```

**Expected observation:** A live process is excluded from ordinary new traffic by the stated readiness policy.

[topology.json](../fixtures/networking/topology.json) gives network-study two endpoints: pod-a on node-a marked ready and pod-b on node-b marked not ready. The checker joins them to the Service selector and asserts that pod-a is the only eligible identity, which models the controller's decision. Real slices also carry serving and terminating conditions and can be split across several objects, which the fixture does not show.

## Six progressive exercises

### Exercise 1: Predict the ready endpoint set.

**Expected evidence:** Only the endpoint referencing pod-a.

**Progressive hint:** Read the ready field for both endpoints in topology.json. Which Pod has the value ordinary traffic requires?

### Exercise 2: Aggregate endpoints across two slices.

**Expected evidence:** The result includes every relevant slice without duplicate identities.

**Progressive hint:** One Service can own several slices. Collect every slice with its service-name label, then remove duplicate addresses.

### Exercise 3: Join eligible endpoint references to current Pod UIDs.

**Expected evidence:** Every accepted backend belongs to the intended current workload.

**Progressive hint:** Each endpoint carries a targetRef. Compare its UID with the Pods that exist now, not with names alone.

### Exercise 4: Diagnose Running but no ready endpoints.

**Expected evidence:** Inspect readiness and selector/controller observations.

**Progressive hint:** Running describes the process. Find the condition that decides whether new connections may be sent there.

### Exercise 5: Explain terminating and serving conditions carefully.

**Expected evidence:** They inform draining behavior and are not identical Boolean synonyms.

**Progressive hint:** A terminating Pod can still be serving. Which of the three conditions changes first during graceful shutdown?

### Exercise 6: Prove a replacement backend is actually used.

**Expected evidence:** New UID eligibility plus a fresh source-bound application response.

**Progressive hint:** You need two things: the new UID listed as ready, and a response that only that backend could have produced.

## Diagnosis, failure boundaries and common mistakes

When a Service has no ready endpoints, the reflex is to restart Pods, which erases the evidence. A Pod can be Running and still unready because its /ready probe fails, so read the probe result and the endpoint condition together. Another mistake is reading only the first slice; large and dual-stack Services spread endpoints across several. Do not treat serving and ready as synonyms: during termination an endpoint can be serving but not ready, and some proxies still use it for existing traffic. Join endpoints to Pods by UID, not by name, because a recreated Pod or a StatefulSet member can reuse the old name.

General evidence rules: [diagnosis rules](../STUDY-GUIDE.md#diagnosis-rules).
