## Outcome and mechanism

Define reusable functions with validated inputs, explicit defaults and testable return values.

A function packages a computation behind a named interface. Its formal arguments describe inputs, and its body computes a result. Functions are ordinary R objects: they can be assigned to names and passed to other functions. Reuse is useful when it centralizes a stable policy, not merely when it hides a few lines of arithmetic.

State input length, type, units and missingness rules before writing the formula. A fee function may accept a numeric amount vector and exactly one finite rate between zero and one. That contract differs from accepting a separate rate per observation. Validation should reject the wrong shape before recycling or coercion creates plausible output.

R returns the value of the last evaluated expression unless return is used earlier. Printing a value is a side effect and does not by itself define the best reusable return shape. Prefer returning data that another function can inspect, while the top-level script prints the result for the learner. An early return can make a special empty-input case clear.

Arguments can be matched by name or position, and R has partial matching rules in some contexts. For maintainable calls, use full argument names when their meaning might be unclear. A default is part of the interface: changing it can alter existing callers that omit the argument. Tests should include both default and explicit calls, as well as rejected inputs.

## Vocabulary

| Term | Meaning |
| --- | --- |
| Function | An object that evaluates a body with supplied arguments. |
| Formal argument | A named input in a function definition. |
| Default argument | An expression used when a caller omits an input. |
| Return contract | A stated type, shape and meaning for the result. |

## Read the syntax

function(amount, rate=0.1) declares two arguments, one with a default. stop(..., call.=FALSE) raises a concise input error. return(value) ends evaluation explicitly. Use full names such as rate=0.2 at call sites.

## Worked examples

### Example 1: A vector function with one scalar rate

```r
after_fee <- function(amount, rate = 0.1) {
  stopifnot(is.numeric(amount), is.numeric(rate), length(rate) == 1L, is.finite(rate), rate >= 0, rate <= 1)
  amount * (1 - rate)
}
stopifnot(isTRUE(all.equal(after_fee(c(10, 20)), c(9, 18))))
stopifnot(isTRUE(all.equal(after_fee(10, rate = 0.2), 8)))
print(after_fee(c(10, 20)))
```

**Expected observation:** 9,18.

The default and explicit-rate calls share one declared policy. The amount vector is allowed to vary in length, while the rate is scalar.

### Example 2: Return data separately from printing

```r
summarize_amount <- function(x) {
  stopifnot(is.numeric(x))
  if (length(x) == 0L) return(list(count = 0L, total = 0))
  list(count = length(x), total = sum(x))
}
result <- summarize_amount(c(2, 4))
stopifnot(result$count == 2L, result$total == 6)
stopifnot(summarize_amount(numeric(0))$count == 0L)
print(result)
```

**Expected observation:** Count 2, total 6; empty count 0.

The result is a structured object, so downstream code can use its fields without parsing console text.
