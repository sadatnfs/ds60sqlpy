Day 45: Phase 3 Optimization Project#

How to run this lesson#

Open sql-45 in ./classroom, choose PostgreSQL and run it as a Whole SQL lesson (psql). Your editable copy is .learning/sql/sql-45/lesson/workspace/sql/postgres-60day/day45_phase3_optimization_project.sql. The script opens a transaction in advanced_sql_training, builds idx_orders_order_date_only and finishes with ROLLBACK, so the index never outlives the run. psql prints three EXPLAIN ANALYZE plans rather than business rows: the wrapped-date baseline, the raw-range rewrite and the pre-aggregated variant. Because now() is frozen when BEGIN runs, all three filter against the same 180-day boundary. Launcher steps are in the study guide, and the notebook alternative sits in its contributor notebook section.

A beginner's mental model for this lesson#

The project query answers one business question: how many units did customers in each country buy in the last 180 days? On a fresh load that window holds 1,539 of the 4,362 orders, placed by 410 customers, and the answer has 7 rows. CA leads with 2,152 units and AU trails with 1,947; the 62 Brazilian customers have no orders, so BR never appears. Every faster version must keep printing exactly those 7 rows.

Experimental control means changing one thing at a time while the data, the window and the session stay fixed. The transaction helps: now() returns the moment BEGIN ran, so every statement before ROLLBACK sees the same boundary. Buffer evidence is the Buffers: shared hit=... read=... line that EXPLAIN (ANALYZE, BUFFERS) adds; it counts 8 kB pages touched, which is steadier than milliseconds on a table of only 65 pages. A regression check proves the faster query still returns the same rows; here that is a two-way EXCEPT between the old and new country totals.

The core idea is sargability. date_trunc('day', o.order_date) >= ... hides the column inside a function, so a plain index on order_date cannot serve it. o.order_date >= date_trunc('day', now()) - interval '180 days' moves the arithmetic to the constant side and still selects the same 1,539 orders, because the boundary is a midnight. Read each plan with the logical clause order in mind: the planner may swap scans and joins, but it never changes which rows qualify.

Two worked SQL examples#

Both excerpts come from the top of day45_phase3_optimization_project.sql: the first is the deliberately slow baseline, and the second is the one-line index that the rewrite depends on. Neither prints business rows.

Example 1#
EXPLAIN ANALYZE
SELECT
  c.country,
  SUM(oi.quantity)
FROM
  customers c
  JOIN orders o ON o.customer_id = c.customer_id
  JOIN order_items oi ON oi.order_id = o.order_id
WHERE
  date_trunc('day', o.order_date) >= date_trunc('day', now() - interval '180 days')
GROUP BY
  c.country
ORDER BY
  2 DESC;

How to read it: EXPLAIN ANALYZE really executes the join of customers, orders and order_items, then prints the plan in place of the 7 country rows. The WHERE clause wraps o.order_date in date_trunc('day', ...), so PostgreSQL must compute that function for every order before it can compare. ORDER BY 2 DESC sorts by the second, unnamed column, which psql heads sum.

Expected result/shape: A plan tree, not a table. On our run the orders node was a Seq Scan whose Filter line repeats the date_trunc call and whose Rows Removed by Filter was 2,823, leaving 1,539 orders; the scan read all 65 pages of orders, and the whole plan took about 5 ms. Your timing will differ. Drop EXPLAIN ANALYZE to see the 7 rows, CA with 2,152 first and AU with 1,947 last.

Example 2#
CREATE INDEX IF NOT EXISTS idx_orders_order_date_only ON orders (order_date);

How to read it: The statement builds a B-tree over the raw order_date values. That helps only predicates that compare order_date itself, which is why the script rewrites the filter right after it. IF NOT EXISTS turns a second build into a notice instead of an error, and the closing ROLLBACK removes the index along with everything else.

Expected result/shape: psql prints CREATE INDEX. Before the rollback, SELECT indexdef FROM pg_indexes WHERE indexname = 'idx_orders_order_date_only' shows ... USING btree (order_date); after the script ends, the same query finds nothing. The rewrite uses it on our run: a Bitmap Index Scan on idx_orders_order_date_only feeds a heap scan of 34 of the 65 pages, and the plan took about 2 ms. An expression index on date_trunc('day', order_date) is no shortcut: CREATE INDEX rejects it, because date_trunc on a timestamptz depends on the time zone and is not IMMUTABLE.

Vocabulary and concepts#

  • Experimental control: fixed query semantics, data, parameters, and environment for a comparison.
  • Buffer evidence: shared/local block hits, reads, dirties, and writes reported by BUFFERS.
  • Regression check: proof that a rewrite preserves the defined output.

Worked example / walkthrough#

Capture the function-wrapped date baseline, rewrite it as a raw half-open range, and add one candidate index inside the rollback transaction. Run both forms several times, reconcile country/unit results, and calculate percentage change from comparable observations without promising 70%.

Common mistakes and how to recover#

  • Lesson-specific semantic mistake: Do not skip this worked-model requirement: Capture the function-wrapped date baseline, rewrite it as a raw half-open range, and add one candidate index inside the rollback transaction. Run both forms several times, reconcile country/unit results, and calculate percentage change from comparable observations without promising 70%.
  • Trusting one timing: a 5 ms query on 65 pages moves by a millisecond between runs. Take the median of several runs and lean on buffer counts, which barely change.
  • Pre-aggregating too early: the learner's items CTE sums all 13,085 lines into 4,362 groups before the date filter applies, so on our run it was a little slower (about 5.7 ms) than the plain rewrite (about 2 ms). Aggregating first pays off when it shrinks rows that survive the filter.
  • Comparing different windows: the learner script starts at midnight 180 days ago, while the solution uses CURRENT_TIMESTAMP - interval '180 days'. On our run that is 1,539 versus 1,538 orders, and IN moves from 1,979 to 1,977 units. Only compare plans whose windows match.
  • Assuming an index is used because it exists: the optimized solution query still scans all 97 pages of order_items on our run; idx_order_items_order_quantity_solution appears nowhere in that plan. Find each index in the plan it was built for.
  • Generic diagnosis steps live in the study guide's recovery section.

Deep dive and reference#

Project goal#

Measure a recent country-units query, make its predicate and aggregation more efficient, and attempt to reduce runtime by more than 70% without changing the result.

What the learner script compares#

  1. A baseline whose date filter wraps orders.order_date in date_trunc.
  2. A sargable raw-column date range after adding an orders(order_date) index.
  3. A rewrite that pre-aggregates order_items.quantity by order_id before the country rollup.

All DDL and plans are inside a transaction and roll back.

Evidence to collect#

  • exact SQL and seed/setup version;
  • row counts and country-to-units totals for correctness;
  • EXPLAIN (ANALYZE, BUFFERS) before and after;
  • execution time, shared buffer hits/reads, rows, loops, and scan/join types;
  • candidate index size and expected write cost; and
  • percentage improvement calculated from comparable timings.

Optimization reasoning#

  • A raw order_date >= boundary predicate can use a normal B-tree range.
  • Set-based pre-aggregation avoids repeated line-level work.
  • A covering order-item index may help but remains a measured candidate.
  • Small tables can legitimately use sequential scans.

The 70% target is not guaranteed#

The target is an experiment goal, not a promised result on the compact deterministic seed. Planning overhead, cache state, and small table size can dominate. Report the observed percentage honestly, reconcile outputs, and use a representative-scale dataset before recommending production changes.

Production index creation requires a separate reviewed migration and may need CREATE INDEX CONCURRENTLY; the tutorial transaction intentionally persists nothing.

Expanded practice lab#

The six explicit prompts make this a measured project instead of a single rewrite. Begin with a prediction, capture JSON plans, and prove equivalence with two-way EXCEPT before comparing performance. JSON makes the root execution time and buffer fields machine-readable, but repeated trials and environment notes are still required.

Test the empty-window boundary and document any proposed index as a workload tradeoff, not free speed. The final report must keep three claims separate: same result semantics, observed planner evidence, and timing that may change on different hardware, cache state, cardinality, or PostgreSQL versions.

Day 45 Solution: Performance Optimization Project#

How to study and run this solution#

Open this explanation only after making an honest attempt. The executable companion runs solely against the disposable advanced_sql_training database:

# Linux, macOS, or Windows through WSL 2, from the repository root
psql -X -v ON_ERROR_STOP=1 -d advanced_sql_training \
  -f sql/postgres-60day/solutions/day45_solutions.sql

The .sql file runs in one transaction and rolls back both indexes it creates. In order, it prints the baseline plan, two CREATE INDEX tags, the optimized plan, the Exercise 1 plan, a single JSON plan row for Exercise 2, an empty Exercise 3 result, Exercise 4's lone 0 and Exercise 5's two index rows. Exercise 6 is a comment, not a query. The baseline is the slow statement, around half a second on our run. The general routine is in reading a solution.

Clause-by-clause reading map#

Read each statement in logical clause order. The project has two layers. The first is a before-and-after pair: a baseline that totals order_items.quantity through a correlated subquery, once per recent order, and an optimized query that filters orders in a recent_orders CTE, totals items per recent order in item_totals and joins both to customers. The second layer, Exercises 1 to 5, isolates one claim each: the sargable range, structured plan output, equal results, the empty window and the index inventory. For every plan, note the scan on orders, the scan on order_items, the loop counts and the buffer totals before looking at time.

The deliverable is evidence, not merely a rewritten query: capture a baseline, add plausible indexes, use a sargable predicate and set-based aggregation, then compare actual plans. The executable project answer is day45_solutions.sql.

Baseline and optimized candidate#

BEGIN;
SET search_path TO training, public;

EXPLAIN (
  ANALYZE,
  BUFFERS
)
SELECT
  c.country,
  SUM((
    SELECT
      SUM(oi.quantity)
    FROM order_items oi
    WHERE
      oi.order_id = o.order_id)) AS units
FROM
  orders o
  JOIN customers c USING (customer_id)
WHERE
  o.order_date >= CURRENT_TIMESTAMP - interval '180 days'
GROUP BY
  c.country;

CREATE INDEX idx_orders_recent_customer_solution ON orders (order_date, customer_id, order_id);

CREATE INDEX idx_order_items_order_quantity_solution ON order_items (order_id) INCLUDE (quantity);

EXPLAIN (
  ANALYZE,
  BUFFERS
) WITH recent_orders AS (
  SELECT
    order_id,
    customer_id
  FROM
    orders
  WHERE
    order_date >= CURRENT_TIMESTAMP - interval '180 days'), item_totals AS (
    SELECT
      oi.order_id,
      SUM(oi.quantity) AS units
    FROM
      order_items oi
      JOIN recent_orders ro USING (order_id)
    GROUP BY
      oi.order_id
)
  SELECT
    c.country,
    SUM(it.units) AS units
FROM
  recent_orders ro
  JOIN item_totals it USING (order_id)
  JOIN customers c USING (customer_id)
GROUP BY
  c.country
ORDER BY
  units DESC;

ROLLBACK;

Both statements should return the same country-to-units result. Compare:

  • Execution Time;
  • shared buffer hits and reads;
  • row estimates versus actual rows;
  • correlated-subquery loops in the baseline; and
  • scan and join choices after the indexes are present.

The 70% target#

The learner file sets a goal of reducing runtime by more than 70%. That is a measurement target, not a guaranteed outcome on the compact seed. Small tables often favor sequential scans, and planning overhead can dominate. Record both plans and calculate:

improvement_pct = 100 * (baseline_ms - optimized_ms) / baseline_ms

If the target is not met, report the observed result honestly and test at a representative scale before changing production design.

Reasoning, safety, and pitfalls#

  • The date predicate compares the raw indexed column to a boundary, so it is sargable.
  • Pre-aggregation reduces line items to one row per recent order before the country rollup.
  • INCLUDE (quantity) can enable an index-only access path, but only when the planner considers it cheaper and visibility-map state permits it.
  • The transaction rolls back course-owned indexes. Production index creation requires separate change planning and may need CREATE INDEX CONCURRENTLY.
  • Always reconcile the result values before accepting a faster plan.

Exercise 1: Make the timestamp predicate sargable#

The direct half-open range leaves order_date unwrapped, making the B-tree eligible while preserving a clear time boundary.

Reasoning and verification#
  • Inputs/evidence: For sql-45 Exercise 1, compare the learner baseline predicate date_trunc('day', o.order_date) >= date_trunc('day', now() - interval '180 days') with the half-open range order_date >= date_trunc('day', CURRENT_TIMESTAMP) - interval '180 days' AND order_date < date_trunc('day', CURRENT_TIMESTAMP) + interval '1 day' on orders, reading each through EXPLAIN (ANALYZE, BUFFERS) after the solution indexes are built.
  • Expected result/shape: For sql-45 Exercise 1, expected output: a text plan, not rows. With idx_orders_recent_customer_solution on (order_date, customer_id, order_id) in place, the half-open range becomes an Index Only Scan with an Index Cond on both order_date bounds, while the wrapped baseline stays a Seq Scan on orders with a Filter, because no index stores date_trunc('day', order_date). Run without EXPLAIN, the range returns one row per order_id; its only column is order_id.
  • Independent verification: For sql-45 Exercise 1, run both predicates without EXPLAIN and confirm that EXCEPT in each direction returns 0 rows, so the rewrite keeps exactly the same order_id set (1,539 orders on our load); then run EXPLAIN (COSTS OFF) on each with the solution indexes present and confirm Index Cond for the range and Filter: (date_trunc('day'::text, order_date) >= ...) for the baseline. The plans may differ by machine; the predicate form decides eligibility, not the timing.
  • Intermediate relation check: Run the SELECT order_id ... without EXPLAIN: on a fresh load it returns 1,539 rows and 1,539 distinct order_id values, matching the learner's day-aligned window. The solution's other queries use CURRENT_TIMESTAMP - interval '180 days' without truncation and keep 1,538, so the two windows differ by one order at the edge.
  • Clause check: The WHERE clause compares bare order_date with two constants: midnight 180 days back and the next midnight. date_trunc still appears, but only on the constant side, where it runs once per statement instead of once per row. The SELECT list needs only order_id, the third column of idx_orders_recent_customer_solution, so on our run the plan never visited the table.
  • Alternative/trade-off: date_trunc('day', order_date) >= ... with a matching upper bound returns the same orders and brings back the sequential scan: 65 pages and 2,823 discarded rows on our run, against 9 pages for the range form. An expression index cannot rescue the wrapped version, since date_trunc on a timestamptz is not IMMUTABLE and CREATE INDEX refuses it.
  • Edge case: A 7-day window keeps the Index Only Scan and reads 19 rows from 3 pages; a 1,000-day window is still an Index Only Scan, now 4,160 rows from 19 pages. A covering index can beat a sequential scan even for most of a table. Heap Fetches: 0 relies on a current visibility map, so a table that has not been vacuumed may show heap visits instead.

Exercise 2: Capture structured evidence#

Reasoning and verification#

Run without EXPLAIN, the query returns one row per customer_id with columns customer_id and revenue.
  • Independent verification: For sql-45 Exercise 2, run the query without EXPLAIN and confirm that its row count equals the root Actual Rows (410 on our load) and that SUM(revenue) equals SELECT SUM(total_amount) FROM orders under the same filter; then confirm that Plans[0] is a Bitmap Heap Scan fed by a Bitmap Index Scan on idx_orders_recent_customer_solution, and that without the solution indexes (after ROLLBACK) the same query plans a Seq Scan on orders.

  • Clause check: FORMAT JSON changes only the printing: one row, one column, holding an array with a single object. Its Plan key holds the root node, an Aggregate with "Strategy": "Hashed" and 410 actual rows on our run, and Execution Time is a sibling of Plan. total_amount is not in the composite index, so the scan under the aggregate has to visit the heap; on our run it was a bitmap heap scan over 34 pages.

Exercise 3: Prove semantic equivalence#

Direct and pre-aggregated country totals are compared with EXCEPT in both directions. Both difference sets must be empty before performance matters.

Reasoning and verification#
  • Inputs/evidence: For sql-45 Exercise 3, build direct (orders joined to customers and order_items, last 180 days, SUM(quantity) by country), items (order_items summed by order_id), and preaggregated (orders joined to items and customers with the same filter, summed by country), then compare direct EXCEPT preaggregated and preaggregated EXCEPT direct, labeling each side with difference_side.
  • Expected result/shape: For sql-45 Exercise 3, expected output: 0 rows with columns difference_side, country, and units, because both CTEs return the same 7 country totals (BR has no orders); any disagreement would appear as a labeled row, one per differing country on each side.
  • Independent verification: For sql-45 Exercise 3, run direct and preaggregated alone and confirm 7 rows each with identical (country, units) pairs, such as AU with 1947 on our load; confirm items returns 4,362 rows with unique order_id and SUM(units) of 39257, equal to SELECT SUM(quantity) FROM order_items; then change only the preaggregated interval to '179 days' and confirm rows appear in pairs, one from each difference_side for every country whose total moved.
  • Intermediate relation check: direct joins about 4,665 recent order lines to customers and returns 7 country rows. items ignores the date and collapses all 13,085 lines into 4,362 per-order totals, and preaggregated joins those to the 1,538 recent orders, again returning 7. Each EXCEPT therefore compares 7 (country, units) pairs, and both differences come back empty.
  • Clause check: EXCEPT compares whole rows and removes duplicates, which is a fair test only because each side has one row per country. UNION ALL stacks the two directions, and difference_side labels which CTE contributed an unmatched row; an empty result means every pair appears on both sides.
  • Alternative/trade-off: FROM direct d FULL JOIN preaggregated p USING (country) WHERE d.units IS DISTINCT FROM p.units reports the same mismatches with both totals in one row, which is easier to read. EXCEPT ALL would also expose a duplicated row, which matters once a side can return more than one row per country.
  • Edge case: Shorten only the preaggregated window to 179 days and the query returns 12 rows on our run, one from each side for every country whose total moved. A one-day slip in a boundary is exactly what a fast plan can hide, and this check exposes it.

Exercise 4: Test the empty-window boundary#

An impossible historical window should return no rows for every equivalent shape. An optimization must not manufacture a zero-valued group.

Reasoning and verification#
  • Inputs/evidence: For sql-45 Exercise 4, read from orders with a window that matches no rows, order_date >= TIMESTAMPTZ '1900-01-01 00:00:00+00' AND order_date < TIMESTAMPTZ '1900-01-02 00:00:00+00', and count the matching orders.

  • Intermediate relation check: Run the window as written and again as SELECT c.country, COUNT(*) ... GROUP BY c.country: the first prints one row holding 0 and the second prints no rows. Nothing in the fixture predates early 2023 on a fresh load, so 1 January 1900 is safely empty.
  • Clause check: With no GROUP BY, COUNT(*) collapses the filtered input into exactly one row even when that input is empty. Both timestamptz literals carry +00, which pins the window to UTC midnight whatever the session's TimeZone.
  • Alternative/trade-off: SELECT EXISTS (SELECT 1 FROM orders WHERE ...) answers the same yes-or-no question with false and could stop at the first match. The count is kept because it behaves like the report's own aggregate on empty input.
  • Edge case: Over the same empty window SUM(quantity) and SUM(total_amount) return NULL, not 0. If one version of the report wraps them in COALESCE(..., 0) and another does not, the two disagree on exactly this input, so settle the empty case before optimizing.

The candidate serves date-bounded customer work but consumes storage and makes writes more expensive. Production creation needs a reviewed migration.

Reasoning and verification#
