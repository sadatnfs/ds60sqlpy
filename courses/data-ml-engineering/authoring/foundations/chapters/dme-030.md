# dme-030: Pinot and low-latency analytical serving

## Serving analytics is a workload, not just a SQL dialect

An analytical serving system answers repeated queries for applications, dashboards or operational users under explicit freshness, latency and concurrency requirements. That differs from an occasional large exploratory scan. Apache Pinot is designed for low-latency analytical serving over ingested data. Its architecture includes components that coordinate metadata, route queries and serve data segments. The actual service workshop demonstrates that system; this chapter executes DuckDB oracles to determine what the ingested rows and answers should mean before any serving engine is trusted.

A fast answer can still be wrong if ingestion grain is wrong. An immutable event stream, a stream of entity replacements and a stream of partial updates require different interpretation. A row representing “order A currently contains four packages” must not automatically be added to an earlier row saying “order A contained two packages.” A row representing “two additional packages were added” has a different meaning. The schema and update contract must say which one the producer emits.

Pinot supports ingestion and upsert capabilities subject to its actual table configuration and version. The important design inputs include primary keys, comparison columns, input partitioning, delete behavior and supported reader semantics. This chapter does not manufacture a Pinot result by renaming a Python dictionary. It runs a real SQL reference calculation in DuckDB and labels that evidence accurately. Compare the real Pinot workshop's observed results with this independent oracle.

## Entity state and event history answer different questions

Let \(H_e\) be the update history for entity \(e\), and let \(v\) be a source revision with an explicit ordering. A latest-state query selects

\[
x_e^{*}=x_{e,\max v},
\qquad S_{\mathrm{current}}=\sum_e x_e^{*}.
\]

An append-history query instead sums every ingested row. Neither is inherently wrong; they answer different questions. The append query might count activity if rows represent additive events, while the latest-state query describes the current entity population. The error occurs when the product asks for one interpretation and the pipeline implements the other without saying so.

The fixture uses full entity replacements and source revisions. `current_rows` first checks that repeated `(identity, revision)` pairs have identical content. It then inserts the actual history into DuckDB and builds a view using `row_number()` partitioned by identity and ordered by descending revision. The row numbered one is the latest state. Equal-revision identical duplicates are harmless to the selected content; equal-revision contradictions are rejected before SQL selection can choose arbitrarily.

## Worked case 1: a replayed update inflates an append aggregate

`example_one()` includes A at revision 1 with two paid packages, A at revision 2 with four paid packages, B with three paid packages, C with one cancelled package, and a replay of A revision 1. A current-state report should contain three entities. Filtering current state to paid entities leaves A4 and B3, totaling seven.

Summing all paid history rows instead produces two plus four plus three plus two, or eleven. That result includes both the superseded A value and its replay. The code executes both queries and prints them with explicit labels. It also checks the current entity count so the comparison does not rely only on one aggregate.

The cancelled entity remains part of the current entity population but does not enter the paid-package sum. Filtering before version selection can change semantics in another case: if an entity's latest status becomes cancelled, selecting only paid history first could resurrect its older paid state. The correct ordering for a current-state paid report is to resolve the latest entity state, then apply the status filter. That ordering follows the product question, not an engine-specific trick.

## Worked case 2: a changed grouping key needs retraction

The second case gives A two packages in north and B three in north. A then changes to four packages in south. The current result is north: three and south: four. An append-only regional aggregate retains A's old northern contribution and reports north: five, south: four.

Correcting the aggregate requires either recomputing from current entity state or applying an identified retraction of A's old contribution followed by its new contribution. In arithmetic, north becomes \(5-2=3\), while south becomes \(0+4=4\). The program calculates this independent correction and compares it with the actual latest-state SQL result. It makes the missing old-value dependency explicit.

If upstream preaggregation discarded entity identity and retained only regional totals, a later entity move may no longer contain enough information to reconstruct the old contribution. This is an information-loss problem, not merely a missing index. Preserve the state or event history required by the correction semantics. A data model optimized for one fast query can make another required update impossible to reconcile safely.

## Indexes and ingestion choices follow the workload

After correctness is established, inspect the serving workload: common filters, grouping dimensions, high-cardinality keys, time ranges, query concurrency and freshness targets. Indexes can reduce work for particular access patterns, but they add storage and ingestion cost. A dimension useful for filtering may not justify every available index. Test representative queries and inspect actual plans or metrics in the deployed engine.

Preaggregation can reduce query work when the retained grain supports all required questions. It can also destroy detail needed for new dimensions, distinct counts or corrections. Approximate sketches have their own error and merge contracts. A distinct-count sketch cannot necessarily answer an exact per-entity deletion request. State the approximation and update boundary explicitly rather than presenting every aggregate as an interchangeable number.

Upsert state can consume memory proportional to the entity population and key representation. A table with a small number of rows per query can still maintain a very large primary-key state. Partitioning input by the required identity and following the engine's supported upsert configuration are operational requirements, not optional formatting choices. Avoid copying version-specific settings without checking the real workshop's pinned service and current official documentation.

## Freshness and latency are separate acceptance criteria

A query can return quickly while serving stale data. Measure source event time, ingestion availability and query observation separately. A freshness delay can arise upstream of Pinot, within ingestion, during segment transitions or through a stale consumer cache. Record the path before assigning blame to the query engine. Similarly, a low average latency can hide a poor high-percentile experience under bursts or expensive query mixes.

The tiny DuckDB oracle establishes expected values, not Pinot throughput or availability. A complete serving qualification needs actual ingestion, readback, restart behavior, resource limits and representative concurrent queries. Preserve the oracle because it remains useful when optimizing the real service: a faster plan must return the same declared population and interpretation.

## Failure diagnosis and answered interview discussion

If totals rise after a replay, inspect event identity and append-versus-upsert configuration. If old state reappears, inspect revision ordering and whether status filtering occurred before latest-state selection. If equal revisions disagree, reject the source conflict rather than relying on arrival order. If a moved entity contributes to two groups, inspect the retraction or recomputation path.

An interviewer may ask, “When would you choose Pinot rather than a lake query engine?” Begin with user-facing latency, concurrency, freshness and ingestion requirements, then compare operational and data-model costs. If asked whether a primary key is enough for upsert, explain comparison ordering, partitioning and conflict semantics. If asked why a preaggregate is wrong after updates, show the missing old contribution and the information needed to remove it.

For an answered extension, change A's latest status to cancelled. The correct current paid total becomes B's three packages. A query that filters paid history first can still select an older paid A row and overstate the result. This small counterexample is an effective review test for any replacement-style analytical ingestion pipeline.
