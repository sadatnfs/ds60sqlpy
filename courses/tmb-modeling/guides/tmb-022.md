# Pandas, NumPy and R conversion

Start with: tmb-005, r-019.

Outcome: Define and test a typed data contract before crossing the Python/R boundary.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter checks row identity, missing values, factor levels and a UTC timestamp in an R data frame. pandas and rpy2 conversion runs only in the Python bridge of the separately prepared [owned project](../projects/tmb-local/README.md) (`python/bridge.py`), checked by `tests/bridge_acceptance.py`; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

A dataframe is more than a rectangular array. Column names, numeric types, missingness, category levels, timestamps and row keys all carry meaning. A conversion that preserves visible values but loses identity or changes missing-value semantics can silently fit the wrong model.

The original bridge accepts exactly three columns in order: `row_id`, `x`, `y`. Keys must be unique nonempty strings. Predictors and outcomes must be finite numerical scalars, with no booleans or missing values. It converts numerical columns to float64, preserves input row order and verifies returned row IDs. It deliberately rejects unsupported schemas rather than guessing how to encode them.

## Key terms

- **rpy2:** A Python package that embeds an R interpreter in the Python process and converts objects between the two languages.
- **Scoped converter:** A conversion context such as `localconverter` that applies pandas conversion rules only inside one block instead of activating them globally.
- **Schema contract:** The exact required columns, order and types, here `row_id`, `x` and `y`, with anything else rejected rather than guessed.
- **Row identity:** Stable unique keys carried through conversion and checked on return, so reordering or loss of rows is detected.

### Worked case A: scoped pandas conversion

Current rpy2 uses a local conversion context:

```python external
with (ro.default_converter + pandas2ri.converter).context():
    r_frame = ro.conversion.get_conversion().py2rpy(clean)
```

Only that block uses the pandas converter. The older PyMB project used global converter activation, which is not the pattern used here. Importing our bridge does not start R. The actual `fit_frame` call lazily imports rpy2 and requires the main thread because an embedded R interpreter should not be shared casually among Python threads.

The companion demonstrates R-side row identity and explicit missingness rejection. Actual pandas/rpy2 execution requires the separately prepared compatible Python/R environment and has its own test record. A Python import or an R-only dataframe calculation is not evidence of a successful cross-language round trip.

### Worked case B: categories and time zones need explicit policy

Suppose a future model adds a category and timestamp. Encode category levels using a frozen training vocabulary and define how unknown levels are handled. Keep timestamps in an explicit zone, usually UTC, and define whether a calendar day means UTC or local civil time. NumPy arrays omit column names; a pandas index is not automatically a stable model key. Convert keys into an explicit column before any sorting or grouping.

Our small regression bridge does not accept these extra fields. The companion shows an explicit category order and UTC timestamp representation as a contract example, not as a capability of the current bridge. Extending the schema requires versioning and new tests for round trips, unknown categories, daylight-saving boundaries and missingness.

### Diagnostics and answered discussion

**Is conversion zero-copy?** Not generally; object types such as strings can require copying. Budget memory for both representations. **Can an integer ID be stored as a double?** Large integers may exceed exact float64 integer precision. Use strings for keys. **Should missing values be dropped silently?** No. Missingness handling is part of the statistical model and must preserve a traceable row policy.

Read [rpy2's pandas documentation](https://rpy2.github.io/doc/latest/html/pandas.html). The [historical PyMB project](https://github.com/kforeman/PyMB) is useful context, but its wrapper and licensing are separate from this original fixed-model implementation.

### Worked case C: tracing rows through `validate_rows`

The bridge's `validate_rows` function checks plain Python records before any R object exists. Its error messages are part of the contract, so a caller can test them directly:

```python external
from bridge import validate_rows

good = [
    {"row_id": "r-003", "x": 2.0, "y": 4.1},
    {"row_id": "r-001", "x": 0.0, "y": 0.2},
    {"row_id": "r-002", "x": 1.0, "y": 1.9},
]
validate_rows(good)  # returns the three rows, order kept
validate_rows(good[:2])  # ValueError: Require 3 to 100000 rows
validate_rows(
    good + [dict(good[0], y=float("nan"))]
)  # ValueError: Row IDs must be unique nonempty strings
validate_rows(
    [dict(r, x=1.0) for r in good]
)  # ValueError: Intercept and slope need at least two distinct x values
validate_rows(
    [dict(good[0], y=True)] + good[1:]
)  # ValueError: y must be finite numeric, with no missing values
```

The third call is instructive. Its added row has a missing outcome, but the duplicate `r-003` ID is caught first, because the loop checks identity before field values. A test that expected a missing-value message would fail, and that failure would be correct: the contract defines an order of checks. The fifth call shows why `bool` is rejected explicitly. In Python, `True` is an instance of `int`, so a generic numeric check would accept it as 1.0. The fourth call rejects a constant predictor because the regression design would be singular; this is a statistical check, not a type check.

### Why keys stay strings

A float64 represents every integer exactly only up to \(2^{53}=9007199254740992\). The next integer, 9007199254740993, rounds to the same double, so two distinct numeric keys would collide after conversion. Sensor IDs, database surrogate keys and hashed identifiers can exceed that bound. Requiring nonempty strings makes the identity check exact and lets the bridge compare returned R row IDs with the input list without tolerance. The same reasoning covers timestamps: 2026-01-01 12:00 UTC is 07:00 in New York, and a contract that stored local civil time without a zone could not tell that row from one recorded at 07:00 UTC.

### Base-R companion (runs in the classroom)

```r
frame <- data.frame(row_id = c("r-003", "r-001", "r-002"), x = c(2, 0, 1), y = c(4.1, .2, 1.9), stringsAsFactors = FALSE)
stopifnot(!anyDuplicated(frame$row_id), all(is.finite(frame$x)), all(is.finite(frame$y)))
print(frame)
bad <- frame; bad$y[2] <- NA_real_
print(c(valid_complete = all(is.finite(frame$y)), reject_missing = !all(is.finite(bad$y))))
category <- factor(c("medium", "low"), levels = c("low", "medium", "high"))
print(list(category_levels = levels(category), utc = as.POSIXct("2026-01-01 12:00:00", tz = "UTC")))
```
