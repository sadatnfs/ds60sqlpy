js-015: Testing with Node built-ins#

Level and prerequisites#

Intermediate, approximately 90 minutes. Direct prerequisites: js-014

Learning objectives#

Explain test oracle, negative test, regression, async test lifetime with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Start a real node --test process asserting add(2,3)=5. The final task tests keep fixtures independent.

Purpose and mental model#

Tests make a behavioral claim executable. A useful test fails when a plausible implementation error is introduced. Merely calling a function without checking the result is weak evidence. Node supplies an assertion library and a built-in test runner, so this lesson needs no package installation. The runner discovers declared tests, awaits returned asynchronous work, reports failures, and sets a nonzero process exit status when a test fails.

A test should distinguish setup, action and observation. Fixtures should be small enough to explain the expected result independently. Check a normal case, an empty or boundary case, and a controlled failure. Avoid asserting incidental details such as an entire stack trace or machine-specific duration unless those details are themselves the contract. A failure message should name the behavior that broke.

Async tests must return or await their work. A Promise started and forgotten can outlive its test and create misleading results. Failure testing also needs the right assertion: throws inspects synchronous exceptions; rejects awaits a rejection. This lesson starts an actual node --test child for each exercise, preserving stdout and stderr separately and checking the child status. That proves the runner detected both deliberately passing and deliberately failing fixtures, instead of printing an invented test summary.

Vocabulary and concepts#

Test oracle: An independent expectation used to judge behavior.

Negative test: A test asserting the intended handling of an invalid or failing case.

Regression: A previously repaired behavior breaking again.

Async test lifetime: The work the runner can observe through the returned or awaited Promise.

How to run this lesson#

Use the prepared Node 24.22.1 profile. The classroom saves an ES module as main.mjs and executes it with Node. Only built-in Node or ECMAScript APIs are used. For a prepared native environment, node main.mjs is the same command on PowerShell and POSIX. Browser APIs have separate host requirements.

Save your own learner copy under ignored .learning/expansion/js-015/ or use a saved classroom pad. Record predictions before execution. Each worked program includes its helper definitions. The reference puts the six exercises in separate scopes, so a task cannot silently rely on a variable from a previous task. A successful assertion is silent; the final JSON receipt reports how many exercise blocks completed. A failing assertion must produce a failed process, not a generic success message.

Syntax anatomy and execution trace#

import test from node:test declares tests, while node:assert/strict provides exact assertions. test(name, async () => ...) awaits the returned Promise. assert.deepEqual compares structured values; assert.throws and assert.rejects check distinct failure channels. The child runner uses process.execPath, a fixed argument array and shell:false through spawnSync. A temporary source file belongs to the exercise and is removed in finally. A nonzero child result is expected only in the deliberately broken fixture.

Worked example / walkthrough#

Example A: Run a passing pure-function test#

The child actually evaluates an assertion through the built-in runner. Process status supplies a machine-readable success signal; text is retained for diagnosis.

import { strict as assert } from 'node:assert';
import { mkdtemp, writeFile, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
import { spawnSync } from 'node:child_process';

async function runTests(body) {
  const directory = await mkdtemp(join(tmpdir(), 'course-tests-'));
  try {
    const path = join(directory, 'fixture.test.mjs');
    await writeFile(path, "import test from 'node:test';\nimport { strict as assert } from 'node:assert';\n" + body, 'utf8');
    const result = spawnSync(process.execPath, ['--test', '--test-reporter=tap', path], { encoding: 'utf8', timeout: 10000, maxBuffer: 1024 * 1024 });
    if (result.error) throw result.error;
    if (result.signal) throw new Error(`test process terminated by ${result.signal}`);
    return result;
  } finally {
    await rm(directory, { recursive: true, force: true });
  }
}

export async function verify() {
  // Worked example
  {
    const result = await runTests("test('addition', () => { assert.equal(2 + 3, 5); });");
    assert.equal(result.status, 0, result.stderr + result.stdout);
    assert.match(result.stdout, /# pass 1/u);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: child exit status 0; one passing test.

Example B: Prove a wrong result fails the runner#

A test suite that never fails cannot establish that its checks are connected. This controlled mutation proves that the assertion reaches the runner and influences the exit result.

import { strict as assert } from 'node:assert';
import { mkdtemp, writeFile, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
import { spawnSync } from 'node:child_process';

async function runTests(body) {
  const directory = await mkdtemp(join(tmpdir(), 'course-tests-'));
  try {
    const path = join(directory, 'fixture.test.mjs');
    await writeFile(path, "import test from 'node:test';\nimport { strict as assert } from 'node:assert';\n" + body, 'utf8');
    const result = spawnSync(process.execPath, ['--test', '--test-reporter=tap', path], { encoding: 'utf8', timeout: 10000, maxBuffer: 1024 * 1024 });
    if (result.error) throw result.error;
    if (result.signal) throw new Error(`test process terminated by ${result.signal}`);
    return result;
  } finally {
    await rm(directory, { recursive: true, force: true });
  }
}

export async function verify() {
  // Worked example
  {
    const result = await runTests("test('deliberate regression', () => { assert.equal(2 + 3, 6); });");
    assert.notEqual(result.status, 0);
    assert.match(result.stdout, /# fail 1/u);
    assert.match(result.stdout, /AssertionError/u);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: nonzero child exit; one failing test.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

  1. Prove a wrong result fails the runner. Deliberately assert 2+3=6 in a child fixture. Expected: nonzero child exit; one failing test. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Await an asynchronous test. Declare an async test that awaits Promise resolution before checking the value. Expected: child exit status 0. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Check rejection with rejects. Assert that an async operation rejects with a RangeError. Expected: child exit status 0. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Cover a table of boundary cases. Use a table for sums of empty, singleton and signed arrays. Expected: three passing child tests. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Keep fixtures independent. Create a fresh array inside each test and mutate it in only one test. Expected: two tests pass without shared mutable state. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
