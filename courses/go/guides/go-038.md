# go-038: Resource versions and optimistic concurrency

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-037

## Learning objectives

Implement optimistic concurrency that rejects stale resource versions and rereads current state before a retry. Along the way, explain optimistic concurrency, conflict, field ownership; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Optimistic concurrency protects a write from silently overwriting a newer observation. A client reads an object with resourceVersion, prepares a change and submits the version it observed. If another writer changed the object, the API can reject the stale write with a conflict. The correct response is usually to reread current state, recompute the intended change and retry within a budget. Retrying the identical stale object cannot resolve the conflict. Resource versions are opaque tokens, not counters for client arithmetic. Server-side apply and patch operations have additional field-management contracts that should not be confused with unrestricted last-writer-wins replacement.

## Vocabulary and concepts

- **Optimistic concurrency:** Rejecting a write when its observed version is stale.
- **Conflict:** Evidence that another state change invalidated a write assumption.
- **Field ownership:** Responsibility for a particular part of a shared object.

## Syntax anatomy and reasoning

This fixture represents an object as value plus opaque version. update requires equality with the observed token and returns a new server-selected token. A conflict is a typed outcome distinct from invalid input or access denial. Recompute from the new read rather than blindly replacing fields owned by another controller. Keep retries bounded and preserve context cancellation.

## Worked example / walkthrough

### Worked example 1: Accept a current version

Update value 2 using its current token a.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

var ErrConflict = errors.New("conflict")

type Versioned struct {
	Value   int
	Version string
	Labels  map[string]string
}

func versionUpdate(s *Versioned, observed string, value int, next string) error {
	if s.Version != observed {
		return ErrConflict
	}
	s.Value = value
	s.Version = next
	return nil
}

func main() {
	// Accept a current version
	{
		s := Versioned{Value: 2, Version: "a"}
		err := versionUpdate(&s, "a", 3, "b")
		check(err == nil && s.Value == 3 && s.Version == "b", "current update")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The value changes and token becomes b.

The new token is selected by the simulated server. A real client must not construct the next resourceVersion itself.

### Worked example 2: Reject a stale version

Attempt a write with old token a against current token b.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

var ErrConflict = errors.New("conflict")

type Versioned struct {
	Value   int
	Version string
	Labels  map[string]string
}

func versionUpdate(s *Versioned, observed string, value int, next string) error {
	if s.Version != observed {
		return ErrConflict
	}
	s.Value = value
	s.Version = next
	return nil
}

func main() {
	// Accept a current version
	{
		s := Versioned{Value: 2, Version: "a"}
		err := versionUpdate(&s, "a", 3, "b")
		check(err == nil && s.Value == 3 && s.Version == "b", "current update")
	}

	// Reject a stale version
	{
		s := Versioned{Value: 3, Version: "b"}
		err := versionUpdate(&s, "a", 9, "c")
		check(errors.Is(err, ErrConflict) && s.Value == 3, "conflict")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Conflict is returned and value stays unchanged.

The failed write does not overwrite newer state. The error is useful evidence about the caller assumption.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
