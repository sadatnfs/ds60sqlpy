## The question and the mechanism

Derive a ratio at its declared population and distinguish an undefined ratio from zero.

A ratio inherits the populations and units of both its numerator and denominator. NetRevenue divided by QuantitySold is net revenue per unit, not the mean of order prices or the mean of product-level ratios. Unequal quantities make those averages different. Start with the business definition, then identify the sufficient totals needed for the ratio.

DIVIDE handles zero or blank denominators according to an explicit fallback. Without an alternate result it returns BLANK for an invalid denominator. An alternate zero can be a useful display choice, but it does not make an undefined conversion rate or unit price mathematically zero. The alternate result must be a constant, so a more elaborate policy belongs outside that argument.

For this fixture, 187 divided by 17 is exactly 11 USD per unit. The value is a weighted aggregate: products with more eligible units contribute more weight. A grand total should normally reevaluate the numerator and denominator for the total population. Averaging displayed percentages can be legitimate only when equal group weighting is itself the intended estimand.

## Vocabulary and expression anatomy

The first case calls DIVIDE on two measures. The second uses literal zero denominators so the missing-ratio policy is visible without a hidden data condition. Ordinary division and DIVIDE should not be treated as interchangeable merely because both work for a positive denominator.

Concepts to explain in your own words: **ratio of totals**, **DIVIDE**, **weighted average**, **denominator**, **zero**.

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
    MEASURE Sales[QuantitySold] = SUM ( Sales[Quantity] )
```

### Case A: A ratio of sufficient totals

**Starting context:** All sales; numerator USD and denominator sold units.

```dax
EVALUATE ROW ( "Revenue", [NetRevenue], "Units", [QuantitySold], "NetPerUnit", DIVIDE ( [NetRevenue], [QuantitySold] ) )
```

**Context trace:**

1. Sum net revenue to 187 and quantities to 17.
2. 187 / 17 = 11.
3. The resulting unit is USD per sold unit, not USD per order.

**Hand-derived worked-reference result:**

| Revenue | Units | NetPerUnit |
| --- | --- | --- |
| 187 | 17 | 11 |

Changing the denominator to OrderCount would produce an average order value, a different metric even though its source data are identical.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Explicit undefined-ratio policy

**Starting context:** Literal values distinguish no denominator from a positive denominator with zero outcome.

```dax
EVALUATE ROW ( "DefaultResult", DIVIDE ( 0, 0 ), "ChosenDisplay", DIVIDE ( 0, 0, 0 ), "ZeroNumerator", DIVIDE ( 0, 5 ) )
```

**Context trace:**

1. Zero divided by zero is not a defined observed rate.
2. DIVIDE's default is BLANK; the third argument deliberately replaces it with zero.
3. Zero divided by five is a defined zero rate.

**Hand-derived worked-reference result:**

| DefaultResult | ChosenDisplay | ZeroNumerator |
| --- | --- | --- |
| BLANK | 0 | 0 |

A table showing two zeroes can therefore combine two different situations. Retain an eligibility count or availability marker to preserve that distinction.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Use that year's totals, not the mean of yearly ratios.
2. The whole-model order count is 7.
3. Use DIVIDE without a third argument.
4. The years have 5 and 12 units.
5. A positive denominator establishes observed opportunity.
6. Count assigned or eligible units according to the design, not exposure rows by accident.
