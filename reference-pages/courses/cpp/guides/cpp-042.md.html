Learning objectives#

Deliver a correct concurrent analyzer and defend its lifetime, failure and performance decisions.

Vocabulary and concepts#

The bounded parallel analyzer combines parsing, ownership, concurrency and evidence. A serial oracle establishes the intended result independently of scheduling. A task budget controls worker count and input size. Failure accounting names rejected input and cancelled work rather than hiding them inside an apparently successful total.

Syntax and mechanism#

Partition a fixed input by indices, give each worker an independent subtotal, join, then combine. Shared input is const and remains alive through join. The two-worker example avoids concurrent writes to the same result slot. The full host capstone adds strict input parsing, bounded admission, cancellation and a reproducible release packet.

Trace the mechanism#

The serial oracle supplies a simple independent answer, 21. The two workers read disjoint slices of one const vector and write separate subtotal variables, then the owner joins both before combining 6 and 15. The uneven five-row case exposes a partitioning bug that equal halves can hide. Extending this to parsed input adds another conservation rule: every original row is accepted or rejected, and every accepted task is completed or explicitly cancelled before a report is published.

Worked example / walkthrough#

Worked example 1#

const std::vector<int> rows{1,2,3,4,5,6}; assert(serial_total(rows)==21);

Expected: The independent serial oracle is exactly 21.

Worked example 2#

a.join(); b.join(); assert(first==6 && second==15);

Expected: Two disjoint partitions combine to 21 after both workers finish.

Failure-accounting reference#

The executable answer includes analyze over at most 100 raw rows, strict fields of at most 16 characters, two joined workers and an injected worker failure. Six accepted rows and two rejected rows produce 21 on the normal path. The injected failure publishes no partial total. Its accepted count equals completed plus cancelled plus failed tasks, regardless of scheduling. Cancellation counts may differ across runs, so verify this conservation rule instead of inventing one exact schedule. Thread-creation failure also requests stop and joins the already created worker before propagating the exception.
