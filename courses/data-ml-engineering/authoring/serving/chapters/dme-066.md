# dme-066: Tensor layouts, fusion and attention kernels

A tensor operation is a mathematical instruction; a kernel is an implementation that performs work on a processor. The same high-level attention call can select different kernels depending on device, dtype, shape, memory layout and backend policy. Understanding this separation is essential when a serving trace mentions GEMM, softmax, fused attention or FlashAttention.

The chapter program runs NumPy layout inspection and an exact tiled softmax calculation on CPU. It does not launch CUDA or implement a production FlashAttention kernel. The goal is to understand the numerical and memory mechanisms well enough to read real profiler evidence in the linked CUDA lessons.

## Shape does not determine layout

A tensor's shape gives its logical dimensions. Strides describe how far to move in storage when advancing an index along each dimension. Two arrays can have identical shapes and values but different strides. A transpose often creates a view that reuses storage instead of moving all elements immediately.

For a strided array, an element address can be described as a base address plus a sum of index-stride products. Strides may be expressed in bytes or elements depending on the API. The NumPy example reports bytes. A matrix kernel may accept some stride patterns efficiently and copy or reject others.

Calling `reshape` is not always a zero-cost view. If the desired logical order is incompatible with current strides, a library may allocate and copy. Likewise, `contiguous()` or an equivalent operation can materialize a new buffer. These transformations can be small relative to a large matrix multiplication or dominant for a tiny decode operation.

Before optimizing, inspect whether the pipeline repeatedly transposes, copies and casts the same data. A correct layout change preserves values and indexing semantics. A faster-looking reshape that changes which components are grouped into heads is a correctness bug, even if dimensions still multiply to the same total size.

## Matrix multiplication and memory traffic

Transformer projections and feed-forward layers contain matrix multiplications. Their performance depends on dimensions, reuse, dtype and the available implementation. Large batches can amortize weight reads and launch costs. Single-token decode may instead be constrained by moving weights or cache data relative to the amount of arithmetic performed.

Arithmetic intensity is the ratio of useful operations to bytes moved across a specified memory boundary. A roofline-style analysis compares this ratio with hardware compute and bandwidth limits. The analysis needs a defined boundary, such as accelerator high-bandwidth memory to on-chip storage; counting all bytes without specifying where they move makes the ratio ambiguous.

Fusion combines compatible operations in a kernel or execution region to reduce intermediate writes, reads and launch overhead. It can also reduce flexibility or require particular shapes. A fused result must retain the intended mathematical behavior within an explicit numerical tolerance. Fusion is not inherently better for every workload, and a library call's name does not prove which fusion path was selected.

## Why attention benefits from tiling

The conceptual attention formula computes score matrix \(S=QK^\top/\sqrt{d_h}\), applies a mask and softmax, then multiplies by values. Materializing all \(T^2\) scores and probabilities can create substantial memory traffic. Tiled algorithms process blocks and retain enough running statistics to produce the exact softmax-weighted result without storing the full matrix.

For one query, suppose processed scores have running maximum \(m\), normalizer \(\ell\) and weighted numerator \(u\). A new score tile has local maximum, and the combined maximum becomes \(m'\). Rescale the old statistics and add the new tile:

\[
\ell'=e^{m-m'}\ell+\sum_{j\in\mathrm{tile}}e^{s_j-m'},
\qquad
u'=e^{m-m'}u+\sum_{j\in\mathrm{tile}}e^{s_j-m'}v_j.
\]

The final output is \(u/\ell\). The rescaling keeps exponents numerically manageable while preserving the same normalized result. The program implements this one-query numerical mechanism in NumPy. A real GPU kernel additionally manages tiles, shared memory, synchronization, parallel reductions and hardware-specific data movement.

FlashAttention's importance is not that it changes ordinary dense attention into an arbitrary approximation. Its core approach reorganizes exact attention computation around memory I/O. Floating-point ordering can still create small numerical differences. Claims about speed and memory savings depend on the actual supported kernel, device and shapes.

## Worked case 1: equal values, different byte strides

The first case creates a two-by-three-by-four float64 array and transposes its last two dimensions. The resulting view has shape `(2,4,3)` and byte strides `(96,8,32)`. A contiguous copy has the same shape and values but strides `(96,24,8)`.

The assertions establish both value equality and layout difference. If you inspect only printed values, the distinction is invisible. If you inspect only shape, it is also invisible. A profiler might reveal a copy before a later kernel; the stride evidence explains why it was required.

This case is useful when converting a packed QKV tensor into separate heads. Carefully track the dimension order through reshape, permutation, attention and the final head merge. A misplaced permutation can pass superficial tests on symmetric or constant fixtures, so use distinct values and multiple dimensions.

## Worked case 2: exact online softmax over large scores

The second case uses scores near 1,000, where directly exponentiating all values would overflow ordinary floating-point arithmetic. The conventional stable reference subtracts the global maximum. The tiled implementation instead maintains the running maximum and rescales accumulated statistics when a later tile contains a larger value.

Tile sizes one, two, three and five all produce the same weighted result within a small tolerance. The changed tile sizes test that correctness does not depend on an accidental partition. This is a stronger mechanism check than demonstrating a single convenient two-tile example.

## Reading profiler evidence responsibly

A profile should identify the actual device and operation path. A CPU backend may use an optimized attention operator with a name resembling a GPU algorithm. That name does not prove a CUDA kernel ran. Confirm device activities, synchronization boundaries and the runtime's selected backend.

Separate compilation or graph-capture time from steady-state execution. Warm-up can change dispatch and allocator behavior. Tiny kernels may be dominated by launch or instrumentation overhead, so repeated measurements and appropriate synchronization are necessary. Avoid inserting host reads into the measured loop unless those reads are part of the intended workload.

If a fused attention path is unavailable, inspect documented constraints rather than disabling correctness checks. Shape, mask type, dropout, dtype and device support can affect dispatch. A fallback may remain correct while having different performance. Record that fact instead of reporting the desired kernel as executed.

## Interview discussion

**Why can two tensors with the same shape have different performance?** Their strides, alignment, contiguity and reuse patterns can differ. A kernel may need a copy or may access memory less efficiently.

**How can softmax be computed tile by tile without storing all scores?** Retain a running maximum, normalization sum and weighted numerator, rescaling old statistics whenever the maximum changes. The equations preserve the normalized result.

**What would convince you that a FlashAttention optimization helped a service?** Actual supported-device kernel evidence, correctness comparisons, memory and latency measurements under representative shapes, and end-to-end workload results. A function name or theoretical I/O reduction alone is insufficient.
