# web-010: CSS rules, selectors and the cascade

## Level and prerequisites

Beginner; allow about 90 minutes, with extra time for independent practice. Direct prerequisites: `web-009`

## Learning objectives

Style two note cards using one low-specificity class. Explain why specificity alone does not describe the cascade. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A CSS rule has a selector and a declaration block. The selector chooses elements; each declaration sets a property to a value. Several rules can match the same element. The cascade resolves conflicts using origin, importance, layer order, specificity, scoping proximity where applicable and source order. Specificity is not the entire algorithm. A later rule wins only after the earlier priorities tie.

Inheritance is another mechanism: some properties, such as text color, naturally pass from a parent to children unless overridden. Other properties, such as margins, normally do not. A value inherited from a parent does not beat a declaration directly targeting the child just because the parent selector is more specific. Browser developer tools reveal which rule won and which declaration was crossed out.

## Syntax anatomy and mechanism

Start with low-specificity class selectors for reusable components. `.note` targets a class, `#summary` targets one id, and `p` targets an element type. `color: #17324d` is a declaration. Use the computed-style view to inspect the resolved value. Avoid adding important flags repeatedly to fight a conflict whose origin you have not identified.

## Worked example / walkthrough

### Worked example 1: A reusable rule

A class describes a group of elements.

```css
.note {
  color: #17324d;
  padding: 1rem;
}
```

**Expected observation:** Every element with class note receives those declarations.

### Worked example 2: Equal specificity

Source order decides after the relevant priorities tie.

```css
.note {
  color: blue;
}
.note {
  color: darkred;
}
```

**Expected observation:** Dark red wins for matching elements in this simple unlayered example.

## Six progressive exercises

### Exercise 1: Predict the winning color in the second example.

**Expected evidence:** The later equally specific declaration wins.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Move a shared text color to a parent and inspect inheritance.

**Expected evidence:** Children inherit it unless a direct declaration overrides it.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Style two note cards using one low-specificity class.

**Expected evidence:** Both cards share styling without duplicate ids or inline declarations.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a crossed-out declaration in developer tools.

**Expected evidence:** Identify the winning rule and the cascade reason rather than guessing.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Add a child color rule under a highly specific parent selector.

**Expected evidence:** A direct declaration on the child overrides an otherwise inherited color.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain why specificity alone does not describe the cascade.

**Expected evidence:** Origin, importance and layer ordering can be decided before selector specificity.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Avoid solving an unknown conflict by escalating selectors. Inline style, important declarations and cascade layers have separate priorities. Devtools evidence is more informative than visually similar colors.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain selector, declaration, cascade without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
