k8s-040: Incident response and bounded fault injection#

Level and prerequisites#

Advanced; about 150 minutes plus review. Direct prerequisites: k8s-027, k8s-032, k8s-035. The chapter separates desired configuration, API acceptance, controller observation and application evidence.

Learning objectives#

Choose a reversible investigation from a specific symptom and preserve evidence.

Vocabulary and concepts#

An incident investigation turns a symptom into a testable explanation and a bounded repair. The first useful question is not which command might make the red status disappear, but which observation would distinguish the leading hypotheses. A Service timeout with healthy Pods can result from selectors, ports, network policy or the application path. Restarting every Pod changes evidence without necessarily testing any of those causes.

This chapter injects one synthetic fault: a host-controlled change to the selector of the exact owned Service. The workload remains Ready, but the Service no longer selects it. The investigator records a baseline, the symptom, endpoint/selector evidence, a conditional repair and a post-repair application check. A separate teacher may reveal the chosen fault only after the learner has formed a hypothesis.

The normal browser adapter can demonstrate bounded failures but does not offer an unrestricted fault-injection API or persistent arbitrary edits. The advanced exercise requires an exclusive lease and a fixed host action with a deadline, cancellation, exact target UID and restoration record. No unrelated namespace, Node or cluster setting is changed.

Preserve a useful timeline#

The synthetic timeline uses elapsed seconds from one controlled start. It records Service UID, selector, Ready Pod count and application result. At second 10 the application request times out while one Pod remains Ready. At second 15 the selected endpoint count is zero. Those facts narrow the investigation toward the route rather than proving the application process crashed.

Record observation time separately from event time when logs arrive late. Keep the request path, timeout and relevant object generation/version so that two readers can compare the same operation. Avoid copying tokens or unbounded logs. A small exact field extract often explains the failure better than a large undifferentiated dump.

A good baseline includes a successful application response and the expected selection graph before the fault. Without that control, an after-fault timeout could be an old defect. The experiment should have one declared fault so the causal story is interpretable; if another failure appears, stop and report the confounding condition.

Test hypotheses with minimal observations#

Hypothesis1: the application crashed. Inspect Ready state, termination/restart evidence and the fixed application observation path. Hypothesis2: the Service selects no intended Pods. Compare its selector with Pod labels and observed EndpointSlices. Hypothesis3: the selected backend port is wrong. Compare Service port/targetPort with the container named port. These are distinct checks, not a generic restart ritual.

In the supplied trace, the selector became missing and endpoints fell to zero while Pod readiness remained healthy. Restoring the last verified selector is the minimal repair consistent with the evidence. Use the recorded UID and a current conditional update to avoid overwriting another actor's changes or mutating a replacement object.

After repair, observe endpoints and the ordinary Service response again. A successful API update only says the desired change was accepted. The end-to-end observation closes the incident, while the timeline supports the causal explanation. If the response remains wrong, preserve that result and continue from evidence instead of declaring victory from an update exit code.

Worked example / walkthrough#

Worked example 1: Diagnose healthy Pods with no endpoints#

Before: selector app=hello, one ready Pod labeled app=hello, one endpoint, expected response. During: selector app=missing, same ready Pod, zero endpoints, timeout. Only the selector changed in the controlled experiment.

Expected: The evidence supports a selector mismatch; a Ready Pod does not guarantee Service reachability.

Worked example 2: Close the repair loop#

Restore app=hello on Service UID svc-1 with a current version precondition. Then observe one selected endpoint and the expected payload through the Service at second 30. A replacement Service UID svc-2 would stop the operation instead.

Expected: The same owned route recovers. Identity replacement is a stop condition, not permission to apply the old repair blindly.

Inspect the specific owned object#

Only after the chapter's host capability is provisioned and its resources remain present, use the explicit receipt fields described in host-labs.md. A completed one-shot browser Run has already cleaned its objects. The following read does not provision the missing capability and does not justify changing credentials after a Forbidden result.

POSIX:

: "${LAB_KUBECONFIG:?Use the owned receipt path}"
: "${LAB_CONTEXT:?Use the owned receipt context}"
: "${LAB_NAMESPACE:?Use the owned receipt namespace}"
kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" --namespace "$LAB_NAMESPACE" get endpointslices -l kubernetes.io/service-name=hello -o json

PowerShell:

if (-not $env:LAB_KUBECONFIG -or -not $env:LAB_CONTEXT -or -not $env:LAB_NAMESPACE) { throw 'Owned receipt fields are required.' }
& kubectl --kubeconfig $env:LAB_KUBECONFIG --context $env:LAB_CONTEXT --namespace $env:LAB_NAMESPACE get endpointslices -l kubernetes.io/service-name=hello -o json
if ($LASTEXITCODE -ne 0) { throw 'The scoped observation failed.' }

Retain only the fields needed by this chapter's prediction. A NotFound result may be expected after one-shot cleanup; a Forbidden result may identify a deliberately absent advanced capability. Neither result authorizes an ambient-context fallback.

Exercises#

Exercise 1: Record the baseline#

Capture selector, Pod label, endpoint count and fixed response before the fault.

Expected result/shape: A connected selection graph and successful application control.

Verify: Retain the named field values, identities, counts, diagnostic or written comparison: A connected selection graph and successful application control.

Progressive hints: A later failure needs a known earlier working path.

Exercise 2: Form competing hypotheses#

List crash, selector mismatch and target-port mismatch with a distinguishing observation for each.

Expected result/shape: Three specific evidence checks rather than a generic restart.

Verify: Retain the named field values, identities, counts, diagnostic or written comparison: Three specific evidence checks rather than a generic restart.

Progressive hints: Ask what would be different if each cause were true.

Exercise 3: Interpret the supplied timeline#

Find the field change and the earliest observation supporting its effect.

Expected result/shape: Selector changes at 10; zero endpoints observed at 15 while readiness remains1.

Verify: Retain the named field values, identities, counts, diagnostic or written comparison: Selector changes at 10; zero endpoints observed at 15 while readiness remains1.

Progressive hints: Separate event time from observation time.

Exercise 4: Apply the minimal bounded repair#

Restore the verified selector only if the Service UID and current update precondition match.

Expected result/shape: Owned svc-1 repaired; replacement UID causes refusal.

Verify: Retain the named field values, identities, counts, diagnostic or written comparison: Owned svc-1 repaired; replacement UID causes refusal.

Progressive hints: Read current state before writing.

Exercise 5: Verify application recovery#

Read endpoint selection and the ordinary Service response after the repair.

Expected result/shape: One endpoint and expected payload, with actual timestamps if live.

Verify: Retain the named field values, identities, counts, diagnostic or written comparison: One endpoint and expected payload, with actual timestamps if live.

Progressive hints: API success is not the serving result.

Exercise 6: Write the review and stop conditions#

Summarize cause, evidence, repair, unrelated-state preservation and remaining uncertainty.

Expected result/shape: A timestamped bounded incident packet with no unsupported broad resilience claim.

Verify: Retain the named field values, identities, counts, diagnostic or written comparison: A timestamped bounded incident packet with no unsupported broad resilience claim.

Progressive hints: Include cancellation and restoration behavior.

Self-check#

Explain the mechanism behind the first example, then distinguish it from this boundary case: The same owned route recovers. Identity replacement is a stop condition, not permission to apply the old repair blindly. State which observations are synthetic and which, if any, were read from your owned runtime.

Common pitfalls#

The host operation must know how to restore its own change, including on cancellation or deadline. It should stop if the target UID changes or unrelated state would be affected. Do not broaden the fault into a node outage, policy deletion or credential change to make the lesson more dramatic.

The post-incident review explains contributing conditions and detection gaps without inventing a root cause unsupported by the trace. A finite recovery can validate this selector-repair path; it does not prove resilience to every outage or that the failure will never recur.
