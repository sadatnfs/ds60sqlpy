A beginner's mental model for this lesson#

Day 60 adds no new SQL feature. It asks whether someone who was not in the room could rerun your capstone, get the same numbers and tell which of them to trust. The learner file offers three kinds of proof: quality views that should report zero problems, a customer LTV view that must reconcile to the order headers, and plans that show where the time goes.

An Acceptance criterion is a condition a query can observe, such as "v_dq_customers reports 0 invalid emails" or "summed LTV minus summed orders.total_amount is 0.00". On our run both held: 500 customers with no invalid email, country or name, and an LTV total of 2,355,646.89 that matched the order total to the cent. A criterion no query can check, such as "dashboards feel fast", has to be rewritten before anyone signs it.

An Evidence bundle pairs each claim with its query, the database it ran against, the printed output and one sentence of interpretation. Dates belong in it because several results move on their own: the Finance CTEs filter from date_trunc('year', now()), the Operations plan filters on now() - interval '180 days', and the retention grid takes the six newest signup months in the data, so the same file prints different rows next month.

A Handoff is the note that lets the next owner operate the work: which views exist, which indexes were only tried inside the rolled-back transaction, which numbers follow the clock and who still has to review what. Exercises 6 and 10 turn parts of that note into rows you can query.

When a result surprises you, read the statement in logical clause order and count rows after each CTE before you change anything.

Two worked SQL examples#

Both excerpts are the first statements in day60_final_capstone_part3.sql that print rows. They read views the script creates a few lines earlier inside its BEGIN, so pasted alone into a fresh session they fail with "relation does not exist"; run the whole file.

Example 1#
SELECT
  *
FROM
  v_dq_customers;

How to read it: v_dq_customers is a one-row summary over every customer. Each column is a SUM(CASE ... THEN 1 ELSE 0 END): invalid_email counts a NULL email or one that fails the case-insensitive !~* pattern '^[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}$', invalid_country counts a NULL or anything other than two uppercase letters, and invalid_name counts a NULL or a name that is blank after btrim. SELECT * prints those counts after total.

Expected result/shape: One row with four columns: total 500, and invalid_email, invalid_country and invalid_name all 0 on the course seed. Zero is the passing value, so a nonzero count starts a remediation note rather than an edit to the pattern. On an empty customers table total would be 0 but each SUM(CASE ...) column would print NULL, because SUM over no rows is NULL.

Example 2#
SELECT
  *
FROM
  v_dq_orders;

How to read it: v_dq_orders applies the same pattern to orders: total is COUNT(*), negative_amounts counts rows with total_amount < 0 and missing_customer counts a NULL customer_id. It does not look for zero amounts, future dates or duplicate orders, so a clean result covers exactly those two rules and nothing more.

Expected result/shape: One row: total 4,362, negative_amounts 0 and missing_customer 0. The second zero is guaranteed by the schema rather than found by the view, since customer_id is declared NOT NULL with a foreign key to customers. The first is an observation: there is no CHECK on total_amount, and the smallest amount in the seed is 20.74. Say which is which in the evidence bundle.

Common mistakes and how to recover#

  • Lesson-specific semantic mistake: Do not skip this worked-model requirement: Take customer LTV through the final evidence loop: state one-customer grain and revenue scope, run the view query, reconcile summed LTV with SUM(orders.total_amount), capture the result and environment, and record any exception with owner and next action. Apply the same loop to each deliverable.
  • Comparing the open month with a closed one: v_monthly_revenue gives November 2026 a growth of -0.4984 on our run, a partial month set against October's full 170,179.13. Flag the month as Exercise 4 does, or end the series at the last complete month.
  • Reading future retention cells as churn: the Marketing grid prints 0.0000 for offsets that have not happened yet, 15 of its 42 cells on our run, including offsets 2 to 6 for the October 2026 cohort. Return NULL for months after the current one so that 0 means "observed and gone".
  • Budgeting against a partial month: the Finance table opens with COGS for November 2026, a budget of 576,000.00 against 335,159.36 actual, so most of the -240,840.64 variance is days not yet elapsed. Pro-rate the budget or leave the open month out.
  • Blaming the plan on missing indexes: in the EXPLAIN ANALYZE of v_monthly_revenue, the GroupAggregate expects 4,362 groups and finds
  1. The gap comes from having no statistics on date_trunc('month', order_date); on PostgreSQL 17.12, CREATE STATISTICS on that expression plus ANALYZE orders brought the estimate to 46. None of the six learner indexes changes this plan.
  • Assuming both quality views treat NULL alike: the learner view counts a NULL country or name as invalid, but the solution's FILTER (WHERE country !~ '^[A-Z]{2}$') yields NULL, not true, for a NULL country. They agree today only because both columns are NOT NULL.
  • For any other failure, the recovery checklist starts from the first error and works forward.

Deep dive and reference#

Day 60 defines acceptance criteria rather than discrete exercises. The final submission connects reusable DQ checks, business views, stakeholder outputs, performance evidence, and a written handoff.

Deliverable 1: Data quality#

  • v_dq_customers: total rows plus invalid email, country, and name counts.
  • v_dq_orders: total rows plus negative totals and missing customers.
  • Document every nonzero result with remediation, owner, and severity.

Deliverable 2: Core business views#

  • Customer LTV at one row per customer, retaining zero-order customers with a LEFT JOIN from customers to orders and COALESCE(..., 0).
  • Treat orders.total_amount as the authoritative revenue measure in this capstone. Do not recompute LTV from order_items: a line-based total can omit header-only orders or disagree with header-level adjustments.
  • Monthly order revenue with previous month and safely divided month-over-month growth.
  • Reconcile summed customer LTV to summed orders.total_amount; expected difference on the seed is zero.

Deliverable 3: Stakeholder outputs#

  • Finance: current-year budget versus actual by month/category.
  • Marketing: active customers by signup cohort and lifecycle month 0-6. Select the six latest distinct signup months before expanding the lifecycle grid. Count every signup once in cohort_size, count a customer at most once per activity month, and report active_customers / NULLIF(cohort_size, 0) as retention_rate. Keeping the numerator and denominator visible makes the percentage auditable.
  • Operations: an actual plan for recent units by product category.

Deliverable 4: Performance sign-off#

Capture before/after EXPLAIN (ANALYZE, BUFFERS) for critical queries and record dataset size, PostgreSQL version, indexes, timing, buffers, correctness check, and decision. The requested under-10-second goal applies to the measured learner machine/dataset; the compact seed does not prove production-scale performance.

Deliverable 5: Written handoff#

Document DQ exceptions, model grain, join rationale, KPI definitions, reconciliation, freshness-versus-speed tradeoffs, known limitations, and next steps. Evidence must support every sign-off claim.

--  - DQ checks pass with documented exceptions
--  - Clear documentation of choices and optimizations
BEGIN;
SET search_path TO training, public;

-- 1. DQ Summary Views (re-usable) ------------------------------------------
CREATE OR REPLACE VIEW v_dq_customers AS
SELECT
  COUNT(*) AS total,
  SUM(
    CASE WHEN email IS NULL
      OR email !~* '^[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}$' THEN
      1
    ELSE
      0
    END) AS invalid_email,
  SUM(
    CASE WHEN country IS NULL
      OR country !~ '^[A-Z]{2}$' THEN
      1
    ELSE
      0
    END) AS invalid_country,
  SUM(
    CASE WHEN full_name IS NULL
      OR btrim(full_name) = '' THEN
      1
    ELSE
      0
    END) AS invalid_name
FROM
  customers;

CREATE OR REPLACE VIEW v_dq_orders AS
SELECT
  COUNT(*) AS total,
  SUM(
    CASE WHEN total_amount < 0 THEN
      1
    ELSE
      0
    END) AS negative_amounts,
  SUM(
    CASE WHEN customer_id IS NULL THEN
      1

--
-- A cohort is the customer's signup month. An active customer has at least one

WITH orders_m AS (
  SELECT DISTINCT
    o.customer_id,
    date_trunc('month', o.order_date)::date AS order_month
  FROM
    orders o
),
cohorts AS (
  SELECT
    c.customer_id,
    date_trunc('month', c.created_at)::date AS cohort_month
  FROM
    customers c
),

  SELECT
    cohort_month
  FROM
    cohorts
  GROUP BY
    cohort_month
  ORDER BY
    cohort_month DESC
  LIMIT 6
),
cohort_members AS (
  SELECT
    c.customer_id,
    c.cohort_month
  FROM
    cohorts c
    JOIN latest_six_cohorts latest USING (cohort_month)
),
cohort_sizes AS (
  SELECT
    cohort_month,
    COUNT(*)::numeric AS cohort_size
  FROM
    cohort_members
  GROUP BY
    cohort_month
),

  SELECT
    generate_series(0, 6)::int AS month_offset
),

  SELECT
    cm.cohort_month,
    offsets.month_offset,
    sizes.cohort_size,
    COUNT(DISTINCT om.customer_id) AS active_customers
  FROM
    cohort_members cm
    JOIN cohort_sizes sizes USING (cohort_month)
    CROSS JOIN month_offsets offsets
    LEFT JOIN orders_m om ON om.customer_id = cm.customer_id

    cm.cohort_month, offsets.month_offset, sizes.cohort_size

FROM

ORDER BY
  cohort_month DESC,
