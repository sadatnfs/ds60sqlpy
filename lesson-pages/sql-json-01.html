Learning objectives#

  • Turn a declared JSON array into typed relational columns with JSON_TABLE.
  • Explain the output grain before and after outer-row preservation.
  • Distinguish missing paths, explicit JSON null and conversion errors.
  • Retain quantity coverage when computing monetary results.
  • Add parent-level measures once after reducing child rows to parent grain.

Vocabulary and concepts#

  • Row path: The JSON path that chooses the contexts producing relational rows; $.items[*] selects item contexts here.
  • Column path: A path evaluated relative to one selected row context, such as $.sku or $.qty.
  • Typed projection: Converting selected JSON values into declared SQL types under an explicit empty/error policy.
  • Ordinality: A one-based position assigned to generated rows. It is not a permanent business identity.
  • Null extension: The placeholder row that a LEFT join supplies when an outer document has no matched item rows.
  • Coverage: Evidence that the fields needed to interpret a complete result are available, rather than merely a partial sum being computable.

The main table has one row per document_id. Document one declares two items: P has quantity two at price five, and Q has quantity one at price three. Its document-level shipping fee is four. Document two declares an empty item array and zero shipping. Document three has no items field and shipping two. These states are intentionally different, even though both can yield no item rows.

Syntax anatomy and query reasoning#

JSON_TABLE is a row source. The row path selects contexts, and COLUMNS defines the SQL view of each context. FOR ORDINALITY supplies a position starting at one. Scalar columns name SQL types and extraction paths; their ON EMPTY and ON ERROR clauses state how selected conditions are handled.

This fixture permits omitted quantity to mean one. It does not replace explicit JSON null with one: null remains an unknown SQL quantity. Prices use one declared currency and exact numeric(10,2) values. An invalid price or quantity cannot become zero revenue by accident under the strict worked policy.

Typed projection is not a complete message-schema validator. For example, a conversion may accept a numeric-looking string under its coercion rules. The default lax path mode can also adapt shapes that an application intended to reject. A producer contract may require additional checks on field presence, root shape, array type, range, units and business identity before projection.

Worked example / walkthrough#

Worked case 1: Choose item grain or preserve document grain#
SELECT
  d.document_id,
  j.item_no,
  j.sku,
  j.qty,
  j.unit_price
FROM
  j17_documents AS d
  CROSS JOIN JSON_TABLE (d.payload, '$.items[*]' COLUMNS (item_no FOR ORDINALITY, sku text PATH '$.sku', qty integer PATH '$.qty' DEFAULT 1 ON EMPTY ERROR ON ERROR, unit_price numeric(10, 2)
  PATH '$.price' ERROR ON EMPTY ERROR ON ERROR)) AS j
ORDER BY
  d.document_id,
  j.item_no;

The actual result has two rows: document one's P and Q. The output grain is one generated item position within a document. Empty or absent item selections do not produce cross-joined child rows. A document disappearing from this item relation does not mean it was absent from the input table.

SELECT
  d.document_id,
  j.item_no,
  j.sku,
  j.qty,
  j.unit_price
FROM
  j17_documents AS d
  LEFT JOIN LATERAL JSON_TABLE (d.payload, '$.items[*]' COLUMNS (item_no FOR ORDINALITY, sku text PATH '$.sku', qty integer PATH '$.qty' DEFAULT 1 ON EMPTY ERROR ON ERROR, unit_price numeric(10, 2)
  PATH '$.price' ERROR ON EMPTY ERROR ON ERROR)) AS j ON true
ORDER BY
  d.document_id,
  j.item_no;

The LEFT form produces four rows: two actual items and one null-extended row for each of documents two and three. A placeholder does not become an item. Count the generated item_no, rather than COUNT(*), to measure actual child rows. Keep document_id visible throughout the investigation so a change in grain cannot be hidden by projecting only SKU or price.

The ordered pair (document_id,item_no) identifies positions in this snapshot. JSONB array extraction by integer uses a different, zero-based indexing interface. Reordering an array changes positions, so ordinality alone is not a durable external item identifier across versions.

Worked case 2: Missing, null and malformed values have different policies#
SELECT
  j.item_no,
  j.qty,
  j.qty_present
FROM
  JSON_TABLE ('{"items":[{"qty":null},{}]}', '$.items[*]' COLUMNS (item_no FOR ORDINALITY, qty integer PATH '$.qty' DEFAULT 1 ON EMPTY ERROR ON ERROR, qty_present boolean EXISTS PATH '$.qty')) AS j
ORDER BY
  j.item_no;

The result is (1,NULL,true) followed by (2,1,false). The first field exists but its JSON null becomes SQL NULL in the scalar quantity. The second path is empty, so the declared default supplies one. Presence and scalar value answer different questions.

The script separately supplies quantity text two under ERROR ON ERROR and handles the actual PostgreSQL conversion error 22P02. The reference also demonstrates NULL ON ERROR, which deliberately returns an unknown quantity instead. Neither policy authorizes treating malformed text as zero. A caller must know whether the resulting row is eligible for a complete business total.

Preserve coverage when aggregating#

The practice fixture adds document four with R at price seven and explicit null quantity, plus S at price two with omitted quantity. Under this contract S has quantity one. The known partial line value is therefore two, while the complete order value remains unknown because R's quantity is unknown.

For a fully known order the line calculation is ∑iqipi\sum_i q_i p_i∑i​qi​pi​, with item quantities qiq_iqi​ and unit prices pip_ipi​. SQL SUM ignores NULL inputs. It can therefore return a plausible partial value while omitting an unknown item. Compute unknown counts separately and gate the accepted total on coverage.

Document two's declared empty array can represent a known zero under the stated contract. Document three's absent array does not establish the same fact. Inspect the original document with field-presence and array-type checks before using COALESCE. An outer join preserves a parent identity, but cannot recover meaning that the source never supplied.

Shipping demonstrates another grain boundary. Document one's known line value is thirteen and its parent shipping fee is four, so its complete value is seventeen. Summing the repeated fee at two-item grain would produce twenty-one. Aggregate child values to one row per document first, then add the single parent fee. A typed projection does not prevent this relational multiplication error.

Common pitfalls#

Counting LEFT placeholders inflates item counts. Applying a default to every NULL erases the distinction between omitted and explicitly unknown quantities. Converting errors to NULL and then summing can hide rejected measurements. Adding a parent amount to every child row repeats that amount.

Inspect document IDs, generated positions, scalar types, presence flags and coverage counts before accepting aggregates. Use the full script's deliberate transaction boundary while experimenting. On an unexpected error, preserve the first diagnostic and restore the exercise savepoint rather than changing error policies merely to obtain a numeric result.

The first three documents contain two items, an explicitly empty array and an absent array. CROSS expansion produces only two item rows. LEFT expansion preserves all parent identities and produces four rows: two actual items plus one null-extended placeholder for each unmatched document.

CREATE TEMP TABLE j17_documents (
  document_id integer PRIMARY KEY,
  payload jsonb NOT NULL
) ON COMMIT DROP;

INSERT INTO j17_documents
VALUES
  (1, '{"shipping_fee":4.00,"items":[{"sku":"P","qty":2,"price":5.00},{"sku":"Q","qty":1,"price":3.00}]}'),
  (2, '{"shipping_fee":0.00,"items":[]}'),
  (3, '{"shipping_fee":2.00}'),
  (4, '{"shipping_fee":1.00,"items":[{"sku":"R","qty":null,"price":7.00},{"sku":"S","price":2.00}]}');

CREATE TEMP VIEW j17_lines AS
SELECT
  d.document_id,
  j.item_no,
  j.sku,
  j.qty,
  j.unit_price
FROM
  j17_documents AS d
  CROSS JOIN JSON_TABLE (d.payload, '$.items[*]' COLUMNS (item_no FOR ORDINALITY, sku text PATH '$.sku', qty integer PATH '$.qty' DEFAULT 1 ON EMPTY ERROR ON ERROR, unit_price numeric(10, 2)
  PATH '$.price' ERROR ON EMPTY ERROR ON ERROR)) AS j;

CREATE TEMP VIEW j17_outer AS
SELECT
  d.document_id,
  j.item_no,
  j.sku,
  j.qty,
  j.unit_price
FROM
  j17_documents AS d
  LEFT JOIN LATERAL JSON_TABLE (d.payload, '$.items[*]' COLUMNS (item_no FOR ORDINALITY, sku text PATH '$.sku', qty integer PATH '$.qty' DEFAULT 1 ON EMPTY ERROR ON ERROR, unit_price numeric(10, 2)
  PATH '$.price' ERROR ON EMPTY ERROR ON ERROR)) AS j ON true;

  RETURNS void
  LANGUAGE plpgsql
  AS $assert$
BEGIN
 IF actual IS DISTINCT FROM expected THEN RAISE EXCEPTION 'JSON projection contract failed: %; actual %',label,actual;END IF;
END
$assert$
