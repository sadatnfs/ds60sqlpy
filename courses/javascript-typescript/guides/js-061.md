# js-061: Networks, force simulation and reproducible layouts

## Level and prerequisites

Advanced; about 110 minutes plus independent practice. Direct prerequisites: `js-060`. This is the D3.js specialization within the JavaScript path. Use the original language and browser lessons whenever syntax or DOM behavior is unfamiliar.

## Learning objectives

Build a bounded three-node network. Choose a strategy for a dense network. Produce a chart whose data transformation, visual encoding and interaction can be explained and checked independently.

## Purpose, vocabulary and mental model

A network or graph contains nodes and edges. Unlike a tree, it can contain cycles and multiple routes. A force-directed layout assigns positions by iteratively applying simulated forces such as attraction along links and repulsion between nodes. The result is a layout heuristic, not evidence that geometric distance is a measured relationship strength.

D3 force simulation mutates node objects with position and velocity fields and can replace link endpoint IDs with node references. Copy input records before giving them to a simulation if another component owns immutable source data. Stable node IDs define link identity.

An automatically running simulation has a timer and a lifecycle. For a small deterministic lesson, stop it and advance a fixed number of ticks with a seeded random source. This makes checks repeatable and prevents a background timer from continuing after the lesson result is recorded.

## Syntax anatomy and mechanism

Create node and link copies, configure `forceLink(...).id(d=>d.id)`, charge and centering forces, and call `.stop()` before manual ticks. Each tick updates the layout. A finite position check verifies basic numerical health but does not prove the chosen force parameters produce a useful explanation.

Render links from their resolved source and target nodes and render labeled circles for nodes. A larger graph needs aggregation, filtering, interaction and performance planning. Do not call a dense hairball an informative visualization merely because every edge is drawn.

## Worked example / walkthrough

### Worked example 1: Preserve source ownership

The simulation receives its own mutable copies.

```javascript
const nodes = sourceNodes.map((d) => ({ ...d }));
const links = sourceLinks.map((d) => ({ ...d }));
```

**Expected observation:** Layout mutation does not add x/y fields to the original source objects.

### Worked example 2: Bound simulation work

A fixed tick count replaces an unbounded animation loop.

```javascript
const simulation = d3.forceSimulation(nodes).randomSource(d3.randomLcg(0.5)).stop();
simulation.tick(80);
```

**Expected observation:** The simulation advances 80 steps and has no running timer afterward.

## Debugging and common mistakes

Keep three checkpoints separate: the records after parsing, the domain and geometry after transformation, and the visible marks after rendering. A chart can look plausible while silently dropping records or assigning the wrong scale. Inspect counts, IDs, finite coordinates and meaningful expected values before adjusting colors. A missing mark may come from invalid input, a missing selection, an undefined scale result or clipping outside the viewBox.

The controlled failure for this lesson is: Diagnose a reference that never stops animating. Its distinguishing evidence is The simulation timer lacks a lifecycle boundary. Preserve that failing case when repairing your program. Do not remove an assertion or broaden a scale merely to hide a wrong input. Explain whether a changed value should affect the data, an encoding, a layout or only presentation.

## Accessibility and interpretation

Give the visualization a descriptive title and a short textual summary of the main result. Keep a table or list when exact values matter. Do not encode a critical category only through color; use labels, shapes or position as appropriate. Interactive controls need keyboard operation and clear focus, and motion should respect the user's reduced-motion preference. Automated DOM checks support, but do not replace, a real keyboard and assistive-technology review.

A data scientist must also defend the statistical meaning. State the population, units, aggregation, missing-value policy and uncertainty where relevant. Synthetic points illustrate a mechanism and do not establish a real-world finding. A beautiful visualization should make a valid claim easier to inspect, not make a weak claim appear certain.
