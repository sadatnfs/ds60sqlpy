# go-002: Numeric types, constants and explicit conversions

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-001

## Learning objectives

Predict integer division, narrowing conversions and floating rounding, and reject invalid numeric text instead of defaulting to zero. Along the way, explain concrete type, conversion, truncation; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A type determines which values and operations are valid. int has an implementation-dependent width, while int64 and uint32 declare particular widths. A conversion changes representation; it is not a proof that the original value fits. Untyped numeric constants can retain exact values until context chooses a concrete type. Variables already have concrete types, so mixing integer and floating arithmetic requires an explicit decision. Integer division truncates toward zero. Floating-point values represent a finite set of approximations, and repeated calculations need a tolerance chosen from the domain. Never repair a numerical test with a tolerance large enough to hide a fundamentally wrong algorithm.

## Vocabulary and concepts

- **Concrete type:** The representation and operations attached to a variable.
- **Conversion:** An explicit change to another type.
- **Truncation:** Discarding a fractional component toward zero.

## Syntax anatomy and reasoning

var n int64 fixes the variable's type. float64(n) converts the value; converting after integer division cannot restore a lost fraction. uint8 wraps values during nonconstant conversion modulo its range. A constant that cannot fit its target type is rejected by the compiler. math.Abs gives an absolute difference, and strconv.ParseInt returns both a value and an error when decoding external text.

## Worked example / walkthrough

### Worked example 1: Compare two divisions

Compute 7/2 and float64(7)/2.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Compare two divisions
	{
		a := 7 / 2
		b := float64(7) / 2
		check(a == 3 && b == 3.5, "division")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The results are 3 and 3.5.

Converting before division selects floating arithmetic. float64(7/2) would instead be 3.0 because integer division has already occurred.

### Worked example 2: Expose narrowing

Convert a variable holding 260 to uint8.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Compare two divisions
	{
		a := 7 / 2
		b := float64(7) / 2
		check(a == 3 && b == 3.5, "division")
	}

	// Expose narrowing
	{
		n := 260
		small := uint8(n)
		check(small == 4, "narrowing")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The narrowed value is 4.

The eight-bit unsigned result retains the value modulo 256. A direct constant assignment of 260 to uint8 would be rejected instead of silently accepted.

## Predict before running

Predict types as well as values: what concrete type does `a := 7 / 2` give `a`, and at what point does the 2 in `float64(7) / 2` become a float? For the narrowing case, compute 260 modulo 256 before converting. For signed division, decide whether Go rounds the quotient toward zero or toward negative infinity, then test your answer with the reconstruction identity.

## Common pitfalls and diagnosis

A conversion changes representation; it does not validate. `uint8(n)` silently keeps the low eight bits of a variable, while assigning the constant 260 to a uint8 is a compile error, so learners often expect the run-time conversion to fail the same way. Converting after the operation is the second trap: `float64(7/2)` is already 3. When a float comparison fails, inspect the algorithm before widening the tolerance.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Compare two divisions: change one input

1. Restate the expected observation: The results are 3 and 3.5.
2. Integer division happens before any conversion that wraps the whole expression. Where does float64 sit in each version?
3. 8 / 2 is exactly 4, so `a == 3` is false even though `b` is still 3.5; one check covers both divisions and fails on the first.

### Hint for investigation 2: Expose narrowing: debug a regression

1. Restate the expected observation: The narrowed value is 4.
2. A uint8 holds 0 to 255. Reduce the variable's value modulo 256 before predicting the converted result.
3. 261 modulo 256 is 5, not 4. The narrowing rule did not change, the input did, so restore 260 instead of editing the expected value.

### Hint for investigation 3: Preserve a wide product

1. Restate the expected observation: The product is 2500000000.
2. Both operands are already int64, so the product is computed at that width. Would 32-bit operands hold 2,500,000,000?
3. Choose a width that can represent the result before the operation.

### Hint for investigation 4: Check approximate arithmetic

1. Restate the expected observation: The absolute difference from 0.3 is below 1e-15.
2. 0.1 and 0.2 have no exact binary form. Compare the absolute difference with the tolerance instead of using ==.
3. The tolerance applies to this tiny calculation, not every numerical problem.

### Hint for investigation 5: Reject invalid numeric text

1. Restate the expected observation: Parsing returns a non-nil error.
2. ParseInt returns a value and an error. Which return value tells you that 12x is not a base-ten integer?
3. Ignoring the error can turn malformed input into a misleading default or partial result.

### Hint for investigation 6: Transfer signed division

1. Restate the expected observation: The quotient is -3 and the remainder is -1.
2. The quotient truncates toward zero and the remainder takes the dividend's sign. Check q*2+r against -7.
3. Truncation toward zero differs from floor division for negative operands.
