dme-005: Python functions, collections and state boundaries#

Level: Beginner | Prepared runtime: python-core

Direct prerequisites: dme-001, dme-003.

Outcome: Build a pure transformation with explicit inputs and outputs.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

Make the computation's inputs visible#

A delivery rule identifies records whose delay exceeds a declared threshold. A function named delayed_ids(records, threshold) expresses that operation directly: it receives the records and threshold, then returns the selected identities. A reviewer can ask what each input means and compare the returned list with an independent expectation.

A function is useful when it establishes a clear boundary, not merely when it shortens a file. Hidden global variables, implicit filesystem reads or mutation of a caller's records can make a short function difficult to understand. The goal in this chapter is to connect the function's behavior to explicit inputs and to understand which objects and iteration state survive a call.

The example's delay_minutes values are already numeric and its records already contain the declared fields. The selection function validates the threshold but does not perform a complete record-schema check. That division is deliberate. A larger pipeline should identify where parsing and structural validation occur rather than assuming every helper independently checks every possible input. Chapter 007 introduces strict structural contracts.

Names, arguments, local variables and results#

def delayed_ids(records, threshold): creates a named function. The names in parentheses are parameters. In a call such as delayed_ids(original, 5), the supplied objects are arguments. Indentation defines the function body. A return statement passes a result back to the caller.

The local list named result begins empty for each call. The loop examines each record, compares its delay with the threshold and appends the delivery ID when the condition is true. It does not overwrite delay_minutes or remove rows from the input list. This makes it easier to call the function with different thresholds and compare the results.

The condition uses > rather than >=. That difference is part of the decision rule. With a five-minute grace period, a delivery delayed by exactly five minutes is not selected by this function. If a consumer expects it to be selected, the contract must change. Treating this as an unimportant syntax detail can produce a persistent disagreement between reports and operations.

Python variables refer to objects. Assigning another name does not automatically create an independent copy of a nested collection. A shallow list copy gives you a new outer list but can still contain references to the same inner dictionaries. The first case uses a copy of each flat record for its comparison; the record values here are immutable strings and integers. More deeply nested structures require a deliberate ownership and copying policy.

Pure transformations make comparison easier#

A pure transformation returns the same result for the same relevant inputs and does not produce observable side effects. That property can make testing and retries simpler. It does not imply that every engineering task should be pure: reading a file, committing a transaction and sending a response necessarily interact with an environment.

The useful design question is where those effects occur. A common pattern is to read and validate inputs at a boundary, perform a clear transformation, and then publish the result under a separate policy. This separates a computational question from an operational one. It also makes it possible to compare a candidate transformation against a small trusted oracle without invoking the entire surrounding service.

The selection function scans the supplied records once. For nnn records its work grows linearly with nnn, assuming field lookup and comparison have bounded cost. Its returned list can also grow to nnn identities. These are useful complexity statements, but they do not predict a production runtime in seconds. Data representation, hardware, interpreter overhead and surrounding I/O still matter.

Worked case 1: Change a parameter without changing the input#

The source contains three deliveries: A has zero delay, B has twelve minutes and C has five minutes. With threshold five, only B is selected. With threshold fifteen, none is selected. The exact-boundary record C provides a useful check that the condition means “strictly greater than.”

The first case records a comparison copy of the original flat records, invokes both threshold choices and confirms that the input remains unchanged. It also repeats the five-minute call and expects the same result. This establishes the behavior on the supplied fixture and challenges accidental mutation or hidden accumulation between calls.

Returning a list of identities instead of a count preserves useful information. A count of one might be correct while referring to the wrong delivery. An identity-level oracle can expose that mistake. A later aggregation can count the returned IDs if that is the consumer's question, but starting with identified records makes the selection itself easier to inspect.

This is not an estimate of the proportion of late deliveries in a broader population. The code only evaluates the three supplied records under a declared rule. Sampling, missing records and business eligibility would need their own contracts before interpreting the selection as a population metric.

Iterators have a lifetime#

An iterable can supply an iterator. An iterator carries a position through a sequence of values. A list can be iterated again, while a particular iterator is typically consumed as it is read. A generator is one way to construct an iterator that produces values on demand.

This difference matters in data work. A helper may accept a list during a small test but later receive a generator over a file or API page. Reading it once for a row count can consume the values that the next step expects to process. A second empty result does not mean the original source contained no data.

Materializing an iterator with list(...) stores the values for repeated access, but that costs memory proportional to the materialized data. For a large source, a better policy may be to retain a versioned raw file, perform a single combined pass or design a genuinely replayable source interface. Do not assume that making a computation “lazy” removes the need to reason about resources and state.

Worked case 2: Reusing a consumed iterator and sharing a mutable collection#

The second case creates an iterator over package counts two, three and one. The first sum consumes those values and returns six. Calling sum on that same exhausted iterator returns zero. Both operations run successfully, yet the second result is not a new measurement of package activity.

The repaired path creates a fresh iterator and materializes it into a list. The list can then be summed repeatedly, giving six each time. The distinction is an explicit replay policy: retain the values you intend to revisit, or obtain a new valid source. Reusing an exhausted object is neither of those operations.

The same case defines append_identity with previous=None. When no previous collection is supplied, each call constructs a new list. When a list is supplied, the function makes an explicit shallow copy before adding an identity. The checks show that separate default calls produce ["A"] and ["B"], and that extending a supplied ["A"] produces ["A", "B"] without changing the caller's original list.

This pattern avoids a shared mutable default. A default list created in a function definition can persist between calls, which is sometimes surprising. The example chooses a new result deliberately; it does not imply that shallow copying is sufficient for every nested data structure.

Complete worked program#

"""Functions and collection lifetime make data transformations reviewable."""


def delayed_ids(records, threshold):
    if type(threshold) is not int or threshold < 0:
        raise ValueError("Use a nonnegative integer delay threshold")
    result = []
    for record in records:
        if record["delay_minutes"] > threshold:
            result.append(record["id"])
    return result


def example_one():
    original = [
        {"id": "A", "delay_minutes": 0},
        {"id": "B", "delay_minutes": 12},
        {"id": "C", "delay_minutes": 5},
    ]
    before = [dict(record) for record in original]
    strict = delayed_ids(original, 5)
    lenient = delayed_ids(original, 15)
    assert strict == ["B"] and lenient == [] and original == before
    assert delayed_ids(original, 5) == strict
    return {
        "threshold_5_ids": strict,
        "threshold_15_ids": lenient,
        "input_unchanged": original == before,
    }


def example_two():
    iterator = (value for value in [2, 3, 1])
    first_total = sum(iterator)
    mistaken_second_total = sum(iterator)
    assert first_total == 6 and mistaken_second_total == 0
    fresh_iterator = iter([2, 3, 1])
    materialized = list(fresh_iterator)
    assert sum(materialized) == sum(materialized) == 6

    # A fresh collection is an explicit policy, not a hidden shared default.
    def append_identity(identity, previous=None):
        updated = [] if previous is None else list(previous)
        updated.append(identity)
        return updated

    a, b = append_identity("A"), append_identity("B")
    assert a == ["A"] and b == ["B"]
    previous = ["A"]
    updated = append_identity("B", previous)
    assert previous == ["A"] and updated == ["A", "B"]
    return {
        "first_iterator_total": first_total,
        "exhausted_iterator_total": mistaken_second_total,
        "repeatable_list_total": sum(materialized),
        "separate_outputs": [a, b],
    }


def main():
    print("Explicit input/output function:", example_one())
    print("Collection lifetime changes the result:", example_two())


if __name__ == "__main__":
    main()

Diagnose hidden state#

If repeated calls accumulate unexpected records, inspect shared collections, global variables and mutable defaults. If a later pass sees zero records, inspect whether an iterator or file cursor was already consumed. If a caller's input changes unexpectedly, inspect which functions mutate objects and whether copies are shallow or deep enough for the declared ownership boundary.

Also distinguish a policy mismatch from an implementation mistake. A threshold boundary, case-sensitive identifier comparison or missing-value rule may be implemented exactly as written while differing from the consumer's expectation. Write the rule in ordinary language, test the boundary and retain an identity-level example that both sides can inspect.

A function that is simple locally may acquire new constraints when distributed. A Spark transformation may need to serialize captured objects and execute in another process. A service handler may see concurrent calls. These settings do not invalidate functions; they require explicit attention to lifetime, effects and data availability at the new boundary.

Where this is useful#

Use small explicit functions for feature transformations, validation rules, metric components and decision policies. Keep network, storage and publication effects identifiable. When a workload grows, compare engine implementations against the same semantic contract instead of replacing a clear function with a faster but differently defined operation.

Answered interview discussion#

Why can a function's second call behave differently? Its relevant inputs may include hidden state: a consumed iterator, a shared mutable object, a clock, a random generator or an external system. Identify that state before calling the function deterministic.

Does passing a list copy isolate every change? Only the outer list is new. Nested mutable objects may still be shared. Choose copying or immutability according to the actual data structure and ownership policy.

Should every stream be converted to a list? No. Materialization enables repeated access but consumes memory. A single pass or a durable replayable source can be more appropriate for a large workload.

Why test exact IDs rather than only counts? Counts can match even when the wrong records were selected. A known identity-level oracle gives stronger evidence about the transformation's meaning.
