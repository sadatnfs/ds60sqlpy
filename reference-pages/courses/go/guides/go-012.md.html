go-012: Defer, cleanup and deliberate panic boundaries#

Level and prerequisites#

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-011

Learning objectives#

By the end, explain deferred call, stack unwind, cleanup boundary; implement the six investigations below; and defend the expected result of a changed input before running it. A passing reference is evidence about that program, not a certification of your independent understanding.

Why this mechanism matters#

defer schedules a function call to execute when the surrounding function returns. It is a resource-lifetime tool, not a general background execution mechanism. Deferred calls run in last-in-first-out order, and their arguments are evaluated when the defer statement executes. Closures can instead read variables at the later execution time. panic unwinds the current goroutine's stack, running defers; recover can intercept it only in the appropriate deferred call during that unwind. Expected invalid input should normally be returned as an error. Recovering every panic and returning a success-shaped value conceals defects and can leave callers unable to distinguish completed work from aborted work.

Vocabulary and concepts#

  • Deferred call: A call executed when the surrounding function exits.
  • Stack unwind: Returning through active frames after a panic.
  • Cleanup boundary: The scope that owns and releases a resource.

Syntax anatomy and reasoning#

defer cleanup() registers a call. defer func(){ ... }() registers a closure. A helper function is useful when each loop iteration needs its own cleanup boundary; deferring inside a long loop otherwise accumulates cleanup until the whole function returns. recover returns the active panic value when called correctly from a deferred function. A named return variable can be changed by deferred code, which is powerful but can make flow harder to read.

Worked example / walkthrough#

Worked example 1: Trace cleanup order#

Register first and second cleanup markers and return.

package main

import (
	"fmt"
	"strings"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func deferOrder() (result string) {
	values := []string{}
	defer func() { result = strings.Join(values, ",") }()
	defer func() { values = append(values, "first") }()
	defer func() { values = append(values, "second") }()
	return
}
func deferArgument() (result int) { x := 1; defer func(v int) { result = v }(x); x = 2; return }
func deferClosure() (result int)  { x := 1; defer func() { result = x }(); x = 2; return }
func recoverKnown() (result string) {
	defer func() {
		if v := recover(); v != nil {
			result = fmt.Sprint(v)
		}
	}()
	panic("broken")
}
func cleanedAfterPanic() (cleaned bool) {
	defer func() { recover() }()
	defer func() { cleaned = true }()
	panic("fixture")
}
func scopedCleanup(count *int) { defer func() { *count = *count + 1 }() }

func main() {
	// Trace cleanup order
	{
		check(deferOrder() == "second,first", "defer order")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: The observed order is second then first.

The last registered cleanup runs first. This naturally unwinds nested acquisitions in the opposite order from acquisition.

Worked example 2: Compare captured arguments#

Defer a call with x as an argument, then change x.

package main

import (
	"fmt"
	"strings"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}

func deferClosure() (result int)  { x := 1; defer func() { result = x }(); x = 2; return }

	defer func() {
		if v := recover(); v != nil {
			result = fmt.Sprint(v)
		}
	}()

func cleanedAfterPanic() (cleaned bool) {
	defer func() { recover() }()
	defer func() { cleaned = true }()
	panic("fixture")
}
func scopedCleanup(count *int) { defer func() { *count = *count + 1 }() }

func main() {
	// Trace cleanup order
	{
		check(deferOrder() == "second,first", "defer order")
	}

	// Compare captured arguments
	{
		check(deferArgument() == 1, "argument evaluation")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: The deferred argument retains the earlier value 1.

Call arguments are evaluated at registration. This differs from a closure that refers to x and reads it when the closure later runs.

Common pitfalls and diagnosis#

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from check identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned error is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
