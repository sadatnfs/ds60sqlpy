# web-044: Testing PHP: examples, boundaries and contract evidence

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-043`

## Learning objectives

Create a test table for a bounded study-duration function. Explain why a passing reference is not a bug-free guarantee. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A test compares an observation with an expected contract. A unit test isolates a small behavior; an integration test exercises a boundary such as a database or HTTP server. Both are useful, and neither should be mislabeled as the other. A reference program that prints a success marker without checking the relevant behavior provides weak evidence.

Good cases include ordinary input, an empty or zero boundary, invalid types or ranges, and a previously observed failure. Tests should explain why the expected result is correct instead of repeating the implementation's internal steps. A function and its test can share the same bug if the expected value is computed using the same faulty algorithm.

## Syntax anatomy and mechanism

This course uses a tiny check function that throws RuntimeException on failure, making behavior independent of whether PHP assertions are enabled. Test exceptions by recording whether the expected exception occurred, then check that flag. Do not catch every exception and treat it as the expected one. Full projects can adopt a prepared testing framework, but no dependency installation is needed here.

## Classroom execution and offline inputs

Choose the **PHP CLI** worker in the classroom. The pad is staged as `main.php` and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write `<?php` at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

## Worked example / walkthrough

### Worked example 1: An independent expected value

The result is hand-derived for a tiny fixture.

```php
check(totalMinutes([20, 30]) === 50, 'Wrong total');
```

**Expected observation:** The test compares against an independently known answer.

### Worked example 2: A declared failure

Only the intended exception counts as success.

```php
$rejected = false;
try { totalMinutes([-1]); } catch (InvalidArgumentException) { $rejected = true; }
check($rejected, 'Negative input accepted');
```

**Expected observation:** The invalid-input contract is explicitly exercised.

## Six progressive exercises

### Exercise 1: Classify a pure-function check and a real database transaction check.

**Expected evidence:** The first is unit evidence; the second is integration evidence.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add an empty-input test with an explicit expected result.

**Expected evidence:** The test records the domain policy rather than guessing from the implementation.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Create a test table for a bounded study-duration function.

**Expected evidence:** Normal, zero, invalid and boundary cases have independently justified outcomes.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a test that catches the wrong exception as success.

**Expected evidence:** Catch the declared exception narrowly and let unexpected failures remain failures.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Temporarily introduce a known bug in a learner copy.

**Expected evidence:** A meaningful test fails for the intended reason, then passes after the repair.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain why a passing reference is not a bug-free guarantee.

**Expected evidence:** It qualifies the tested contract and cases; untested integration and environment behavior remain separate.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not disable checks to preserve a success marker. Avoid tests tied only to private implementation details. Record skipped surfaces honestly, especially when CLI logic stands in for an HTTP workflow.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain unit test, integration test, assertion without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
