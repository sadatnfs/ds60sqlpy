# go-045: Leader election, leases and fencing limits

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-044

## Learning objectives

Model lease-based leader election and explain why a fencing check is still needed after a takeover. Along the way, explain lease, split brain, fencing; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Several controller replicas improve availability, but some operations need a single active coordinator. Leader election uses a lease-like coordination record so candidates can observe and renew leadership. It is not a magical exactly-once guarantee. A paused process can continue believing it is leader after another process takes over; external side effects may therefore need fencing tokens or idempotency controls at the destination. Time assumptions, renewal deadlines and shutdown behavior matter. The client-go leader-election package explicitly does not provide fencing by itself. This lesson uses a deterministic logical clock to examine lease policy without sleeping or contacting a cluster.

## Vocabulary and concepts

- **Lease:** A time-bounded claim to coordination authority.
- **Split brain:** Two participants acting as if each has exclusive authority.
- **Fencing:** The destination rejecting operations from an obsolete authority.

## Syntax anatomy and reasoning

A lease model records holder and expiry. A current holder can renew, another candidate must wait until expiry, and a candidate must stop leader-only work when renewal is lost. Real lease acquisition requires optimistic concurrency at the API server, not a local map assignment. A monotonically enforced fencing token belongs at the protected external system; Kubernetes resourceVersion should not be repurposed as a numeric application token.

## Worked example / walkthrough

### Worked example 1: Acquire an empty lease

Let candidate a acquire at logical time 10 for five units.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Lease struct {
	Holder  string
	Expires int
}

func acquire(l *Lease, candidate string, now, duration int) bool {
	if candidate == "" || duration <= 0 {
		return false
	}
	if l.Holder != "" && l.Holder != candidate && now < l.Expires {
		return false
	}
	l.Holder = candidate
	l.Expires = now + duration
	return true
}

func main() {
	// Acquire an empty lease
	{
		l := Lease{}
		check(acquire(&l, "a", 10, 5) && l.Holder == "a" && l.Expires == 15, "acquire")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Holder becomes a and expiry 15.

This local policy model does not implement distributed atomicity. A real update must be protected by the API concurrency contract.

### Worked example 2: Reject a competing candidate

Let b request an unexpired lease held by a.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Lease struct {
	Holder  string
	Expires int
}

func acquire(l *Lease, candidate string, now, duration int) bool {
	if candidate == "" || duration <= 0 {
		return false
	}
	if l.Holder != "" && l.Holder != candidate && now < l.Expires {
		return false
	}
	l.Holder = candidate
	l.Expires = now + duration
	return true
}

func main() {
	// Acquire an empty lease
	{
		l := Lease{}
		check(acquire(&l, "a", 10, 5) && l.Holder == "a" && l.Expires == 15, "acquire")
	}

	// Reject a competing candidate
	{
		l := Lease{Holder: "a", Expires: 15}
		check(!acquire(&l, "b", 12, 5) && l.Holder == "a", "contender")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The request fails and a remains holder.

The contender waits while the current claim remains valid under this model.

## Exercises

### Exercise 1: Acquire an empty lease: predict an edited check

Copy worked example 1, change `check(acquire(&l, "a", 10, 5) && l.Holder == "a" && l.Expires == 15, "acquire")` to `check(acquire(&l, "a", 11, 5) && l.Holder == "a" && l.Expires == 15, "acquire")` inside its check and predict whether it still passes; then restore it.

**Expected:** The edited check panics with `acquire` even though `acquire(&l, "a", 10, 5) && l.Holder == "a" && l.Expires == 15` still holds.

**Verify:** Restoring `check(acquire(&l, "a", 10, 5) && l.Holder == "a" && l.Expires == 15, "acquire")` makes the check pass again with the worked observation: holder becomes a and expiry 15.

### Exercise 2: Reject a competing candidate: debug a regression

A one-token regression in worked example 2 makes a line read `l := Lease{Holder: "a!", Expires: 15}`. Repair it without changing the check.

**Expected:** The defective run panics with `contender`; after restoring `l := Lease{Holder: "a", Expires: 15}`, the request fails and a remains holder.

**Verify:** The failing run shows message `contender`; after the repair `!acquire(&l, "b", 12, 5) && l.Holder == "a"` holds again.

### Exercise 3: Renew current leadership

Let a renew its lease before expiry.

**Expected:** Expiry advances to 18.

**Verify:** Your solution must keep `acquire(&l, "a", 13, 5) && l.Expires == 18` true. Control: changing `check(acquire(&l, "a", 13, 5) && l.Expires == 18, "renew")` to `check(acquire(&l, "a", 14, 5) && l.Expires == 18, "renew")` panics with message `renew`; revert it.

### Exercise 4: Take over after expiry

Let b acquire at the exact expiry boundary.

**Expected:** Holder becomes b.

**Verify:** Your solution must keep `acquire(&l, "b", 15, 5) && l.Holder == "b"` true. Control: changing `l := Lease{Holder: "a", Expires: 15}` to `l := Lease{Holder: "a", Expires: 16}` panics with message `takeover`; revert it.

Compare an old authority token 4 with current token 5.

**Expected:** Only token 5 is accepted by the destination model.

**Verify:** Your solution must keep `!accept(4) && accept(5)` true. Control: changing `accept := func(token int) bool { return token == current }` to `accept := func(token int) bool { return token != current }` panics with message `fencing`; revert it.

## Common pitfalls and diagnosis

Treating leadership as exclusive is the dangerous assumption: a leader that pauses past its lease, for garbage collection or a network stall, wakes up still believing it leads while another replica acts. Leases reduce overlap but cannot prevent it. Protect external side effects with fencing tokens or idempotent writes, and stop work promptly when renewal fails.

## Progressive hints

### Hint for investigation 1: Acquire an empty lease: predict an edited check

1. Restate the expected observation: Holder becomes a and expiry 15.
2. The lease is empty. What do Holder and Expires become?
3. Acquiring at 11 sets Expires to 16, so `l.Expires==15` fails while the holder is still a. The acquisition works; the start time changed.

### Hint for investigation 2: Reject a competing candidate: debug a regression

1. Restate the expected observation: The request fails and a remains holder.
2. a holds the lease until 15. Can b acquire at 12?
3. The lease holder is now a!, so b is still refused but `l.Holder=="a"` fails. Restore the holder name a.

### Hint for investigation 3: Renew current leadership

1. Restate the expected observation: Expiry advances to 18.
2. The holder may renew early. What is the new expiry?
3. Renewal extends a claim; it does not prove a formerly paused process cannot still perform external work.

### Hint for investigation 4: Take over after expiry

1. Restate the expected observation: Holder becomes b.
2. The lease protects its holder only while now is below Expires. Can b acquire at 15?
3. The boundary policy is explicit.

### Hint for investigation 5: Reject a stale fenced operation

1. Restate the expected observation: Only token 5 is accepted by the destination model.
2. The destination accepts only the current token. Which of 4 and 5 passes?
3. The protected destination enforces the token.

### Hint for investigation 6: Transfer invalid-duration refusal

1. Restate the expected observation: No lease is acquired.
2. A nonpositive duration is refused first. Does the holder change?
3. Invalid timing configuration must fail before coordination starts.
