# web-041: Interfaces, composition and replaceable dependencies

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-040`

## Learning objectives

Build a summary service with an injected repository. Explain what remains untested by an in-memory repository. Use interface, composition and dependency injection accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

An interface describes operations a caller can rely on without selecting a specific implementation. Composition builds behavior from collaborating objects. Dependency injection means supplying a dependency rather than constructing an unknown global dependency inside the operation. These techniques help when a real boundary varies, such as storage or time, but unnecessary interfaces can add ceremony to a tiny fixed calculation.

A test double supplies a controlled implementation for a test. An in-memory repository can verify application behavior without a database, but it does not prove SQL syntax, transactions or connection recovery. Keep unit evidence separate from integration evidence. The same interface can make both tests possible without pretending they are identical.

### Key terms

- **Interface:** A named set of method signatures that a class promises to implement, without providing any behavior itself.
- **Composition:** Building behavior by holding other objects and calling them, instead of inheriting from a base class.
- **Dependency injection:** Passing a collaborator, such as a clock or a store, into an object instead of letting the object create it.
- **Test double:** A simple stand-in that implements the same interface as a real collaborator so a test can control its answers.

## Syntax anatomy and mechanism

Define a repository interface with a narrow operation such as countCompleted. The service receives that interface through its constructor. A memory implementation holds synthetic records for this lesson. The service can then be tested with known data and no network. Later PDO lessons qualify the database boundary separately.

## Worked example / walkthrough

### Worked example 1: A narrow dependency

The interface exposes a behavior rather than its storage details.

```php
interface ProgressStore { public function completedCount(): int; }
```

**Expected observation:** A caller can request a count without knowing the storage engine.

### Worked example 2: Composition

The service receives its dependency explicitly.

```php
final class Summary { public function __construct(private ProgressStore $store) {}
  public function label(): string { return $this->store->completedCount() . ' complete'; }
}
```

**Expected observation:** A controlled store makes the summary behavior deterministic.

## Contrast case: a service that builds its own database connection

This summary class works in production, but try writing the zero completed lessons test for it.

```php
final class SummaryFixed {
  public function label(): string {
    $pdo = new PDO('sqlite:/srv/app/progress.sqlite');
    $count = (int) $pdo->query(
      'SELECT COUNT(*) FROM progress WHERE done = 1'
    )->fetchColumn();
    return $count . ' complete';
  }
}
```

The class decides on its own which database file to open, so a test can only run where that exact path exists, and the answer depends on whatever rows happen to be stored there today. There is no way to hand it a store that reports 0 or 3 on demand, so the empty state and the normal state cannot both be checked deterministically. In the CLI worker the file does not exist and the constructor of PDO fails before any summary logic runs. Worked example 2 moves that choice out: the caller passes any `ProgressStore`, a memory store in tests and a PDO store in the application. The label logic is identical in both cases, and only the source of the count changes.

## Debugging and common mistakes

Do not claim database acceptance from a mock. Avoid injecting a giant container that hides dependencies again. Use an interface only when it clarifies a meaningful boundary.

When a test double makes the summary pass with impossible data, compare the double's values with what the real store could return, such as negative counts. When the service cannot be tested without a database, look for a new PDO or connection created inside the class instead of injected.

The shared [debugging routine](../STUDY-GUIDE.md#debugging-php) covers what to record before each repair.
