# Typed vectors, matrices, arrays and sparse inputs

Start with: tmb-040, tmb-002.

Outcome: Design a C++ data contract that preserves dimensions, indices and scientific meaning.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter shows R's column-major array order and the conversion to zero-based indices. The separately prepared [C++ API probes](../projects/tmb-cpp-api/README.md) declare typed inputs such as `DATA_MATRIX(covariance)` and `DATA_SPARSE_MATRIX(precision)` in `models/density_forms.cpp`, and their `check.R` compiles and checks them; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

The R export list does not describe all model-authoring interfaces. A TMB template also uses C++ macros, typed containers and density helpers supplied by its headers. The [C++ family map](../CPP-API-FAMILIES.md) covers the supported teaching families without claiming every Eigen, CppAD or TMBad implementation symbol is part of this course.

`DATA_SCALAR`, `DATA_VECTOR`, `DATA_MATRIX` and `DATA_ARRAY` read fixed numerical inputs. Integer and category interfaces include `DATA_INTEGER`, `DATA_IVECTOR` and `DATA_FACTOR`. `DATA_SPARSE_MATRIX` reads a compatible sparse matrix. Parameter declarations include scalar, vector, matrix and array forms. Their shapes define the free coordinate layout that `MakeADFun` records.

## Key terms

- **Column-major layout:** R's array storage order, in which the first index varies fastest, so a transposed array silently changes model meaning.
- **PARAMETER_ARRAY:** A declaration that preserves parameter array dimensions, whereas `PARAMETER_VECTOR` keeps only a flat sequence.
- **DATA_SPARSE_MATRIX:** A declaration that reads a compatible sparse matrix storing only nonzero coordinates and dimensions.
- **Zero-based index:** C++ indexing that starts at 0, used by `DATA_IVECTOR(group)`, so R labels are converted once and out-of-range values rejected.

### Worked case A: array orientation is part of the model

R arrays use column-major storage. A two-by-three array stores the first column's two elements before the second column. `PARAMETER_ARRAY(u)` preserves dimensions, while `PARAMETER_VECTOR(u)` only preserves a flat sequence. The companion labels each position and verifies the flattening order. An array transpose with unchanged coefficient interpretation can fit a different model even though every value is finite.

```cpp
DATA_ARRAY(observed);
PARAMETER_ARRAY(latent);
Type residual = observed(0, 1) - latent(0, 1);
```

This fragment assumes a two-dimensional array and a validated matching shape. A generic loop should inspect dimensions or flatten consistently. Do not index a three-dimensional array using a two-dimensional scientific interpretation.

### Worked case B: sparse design and factor keys

A group design matrix \(Z\) has one nonzero per row for a simple random intercept. The companion builds an explicit small design and verifies \(Zu\) agrees with group-index lookup. A large sparse representation stores the nonzero coordinates and dimensions rather than every zero. Validate indices and compatible sparse class on the R side before entering C++.

R factor levels are categorical labels; their numerical codes are an implementation detail. `DATA_FACTOR` and explicit zero-based integer-index interfaces need careful conversion and a stable training vocabulary. The existing project uses explicit zero-based `DATA_IVECTOR(group)` and rejects out-of-range groups. Adding new factor levels requires a new objective shape and potentially a new scientific prediction target.

### Answered discussion

**Should parameter-dependent values be converted to double for speed?** That can remove derivative dependence. Keep them in `Type` arithmetic unless a reviewed atomic operation supplies the derivative boundary. **Can integer identifiers be passed as floating-point measurements?** Large keys can lose exactness and should remain explicit strings outside the numerical template. **Are sparse matrices automatically symmetric?** No. Symmetry, definiteness, dimensions and storage representation are separate properties.

See the [template macro reference](https://cran.r-project.org/web/packages/TMB/TMB.pdf) and [typed density source](https://github.com/kaskr/adcomp/blob/master/TMB/inst/include/tmbutils/density.hpp). The course's pinned source hashes identify the actual version reviewed.

### Worked case C: offsets in a three-dimensional array

Extend the companion's two-by-three array to a third axis. With `dim = c(2, 3, 2)`, column-major storage puts the zero-based element \((i, j, k)\) at flat offset \(i + 2j + 6k\), because each column holds 2 values and each slice holds \(2 \times 3 = 6\). In R the same position is one-based:

```r
b <- array(1:12, dim = c(2, 3, 2))
b[2, 3, 1] # zero-based (1, 2, 0): offset 1 + 4 + 0 = 5, value 6
b[1, 2, 2] # zero-based (0, 1, 1): offset 0 + 2 + 6 = 8, value 9
stopifnot(b[2, 3, 1] == 6, b[1, 2, 2] == 9)
```

Both values follow from the offset formula by hand: the array holds \(1, \dots, 12\) in storage order, so the value is the offset plus one. Inside a template, `PARAMETER_ARRAY(latent)` declared from this array keeps the three extents, and `latent(1, 2, 0)` reads the same coordinate as `b[2, 3, 1]`. Reshaping the storage changes meaning silently. `matrix(1:6, 3, 2)[1, 2]` is 4, while the companion's `a[1, 2]` is 3: identical storage, different scientific cell. A shape check in R before `MakeADFun`, such as `stopifnot(identical(dim(observed), c(2L, 3L, 2L)))`, catches that mismatch before it becomes a plausible fit.

### Worked case D: the storage cost of a sparse group design

The companion's \(Z\) is four by three with four nonzeros, so dense storage holds 12 numbers and a triplet form holds 4 (row, column, value) entries. The gap matters at scale. Consider 10,000 observations in 500 groups (hand-derived byte counts):

```text
representation              stored items                          bytes
dense double matrix         10,000 x 500 = 5,000,000 doubles      40,000,000
dgCMatrix (column sparse)   10,000 values (8 bytes each)              80,000
                            10,000 row indices (4 bytes each)         40,000
                            501 column pointers (4 bytes each)         2,004
                            total                                    122,004
```

The sparse form is about 0.3% of the dense size. For a pure random intercept the index vector is smaller still: 10,000 integers, or 40,000 bytes, and the template computes `u(group(i))` without any matrix product. The C++ side of that contract reads:

```cpp
DATA_IVECTOR(group); // zero-based, validated in R
PARAMETER_VECTOR(u);
for (int i = 0; i < group.size(); i++)
  eta(i) += u(group(i));
```

### A factor that drops a level

A common failure arrives with new data. If training groups are `c("a", "b", "c")` and a scoring batch contains only `c("b", "c")`, then `as.integer(factor(c("b", "c")))` returns `1 2`, not `2 3`, because `factor` builds levels from the values present. Subtracting one would send group "b" to `u(0)`, the effect estimated for "a". The fix is to encode against the stored training vocabulary, `match(new_groups, training_levels) - 1L`, and to stop when `match` returns `NA` for an unseen label. That keeps the index contract explicit and makes a new level a visible decision rather than a shifted coefficient.

```r
a <- array(1:6, dim = c(2, 3));print(a);print(as.vector(a));stopifnot(a[2, 2] == 4, identical(as.vector(a), 1:6))

```
