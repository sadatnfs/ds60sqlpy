dme-027: Table formats: snapshots, transactions and concurrency#

Level: Intermediate | Prepared runtime: data-engineering

Direct prerequisites: dme-021, dme-025, dme-026.

Outcome: Investigate snapshot and delete invariants using real local files and a clearly labelled table-format model.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

Files become a table through metadata and rules#

A Parquet file stores rows. A table format adds rules for which files and changes constitute a table version, how readers find a consistent view, and how writers publish updates. Iceberg, Delta Lake and Hudi address overlapping lake-table problems through different metadata, transaction and maintenance designs. They are not just alternative compression codecs, and they should not be treated as interchangeable folders of Parquet files.

A snapshot identifies one accepted logical table state. A reader can pin that snapshot and keep using it while another writer prepares a newer version. Updates and deletes may be represented by rewritten files, separate delete information or other format-specific structures. Compaction and cleanup then manage physical storage without changing the logical answer unexpectedly. The exact feature support depends on the format and the reader/writer implementation.

The worked program is a deliberately small snapshot-table mechanism built with actual Parquet and SQLite. It is not an Iceberg, Delta or Hudi implementation and does not write their metadata formats. It exposes three essential ideas: a committed manifest defines visibility, an atomic parent check prevents a stale publication, and logically deleted data can remain physically present in files retained by an older snapshot. Use the actual Apache workshops for real format APIs and service behavior.

This simple delete set omits the scope, sequence and encoding rules of real equality deletes, position deletes, deletion vectors or merge logs. Those details matter in real systems; the model teaches the invariant without claiming to implement them.

A writer prepares files outside the catalog transaction. It then begins an actual SQLite write transaction, compares the accepted parent snapshot with the one it planned from, inserts the new manifest and updates the current pointer. If the parent changed, the transaction fails. The writer must reread and validate its intended change against the new state. Merely changing the expected-parent number without reconsidering the change would defeat the purpose of the check.

Worked case 1: logical deletion while preserving an old snapshot#

example_one() writes a Parquet file containing A2, B3 and C1, then commits snapshot 1. A pinned reader obtains those three rows and a total of six. A later writer prepares another file containing D4. Snapshot 2 references both files and declares B deleted. Its visible rows are A2, C1 and D4, totaling seven.

Reading snapshot 1 again still returns B3. The original file has not been rewritten or deleted, and the old manifest has no delete for B. This is the central distinction between logical visibility and physical storage. A query against the current snapshot can correctly hide a row while bytes representing that row remain accessible through retained history. Retention and privacy policies must account for that fact rather than assuming a logical DELETE immediately erases every copy.

The program verifies exact identified rows, not only aggregate totals. Two wrong datasets can share a total of seven. It also verifies file hashes before interpreting the snapshot. If a supposedly immutable file changes, the reader rejects it rather than treating the same filename as proof of unchanged content. The temporary fixture keeps the file count small enough to inspect directly.

Worked case 2: two candidates planned from the same parent#

The second case commits snapshot 1 with A2. Two writers then prepare candidates from that parent: one adds B3 and the other adds C100. The first commits snapshot 2. The second tries to commit snapshot 3 while still declaring parent 1, and the catalog rejects it because current is now 2.

The accepted table remains A2 and B3. The C100 Parquet file exists physically but is not referenced by any committed snapshot, so it is not visible through the table. The program lists it as an unreferenced file and deliberately does not delete it. A production cleanup process must distinguish abandoned candidates from active in-progress work and retained historical snapshots. The absence of a file from the current snapshot alone is insufficient evidence that it is safe to remove.

The case is a sequential interleaving of two writer intentions, with a real transactional parent comparison. It does not launch a distributed race or test a remote catalog. This is enough to demonstrate the stale-parent rejection rule. Actual concurrent engine qualification requires multiple clients, catalog-specific conflict handling and readback after failures, which belong to the separate projects.

Complete worked program#

Use data-engineering. SQLite coordinates the local catalog transaction, and Arrow reads and writes real Parquet files. All artifacts stay in the program's owned temporary directory.

"""A local snapshot model with real Parquet and SQLite, not an Iceberg implementation."""

import hashlib
import json
import sqlite3
import tempfile
from pathlib import Path

import pyarrow as pa
import pyarrow.parquet as pq


def catalog(path):
    connection = sqlite3.connect(path)
    connection.execute(
        "create table if not exists snapshots(id integer primary key,manifest text not null)"
    )
    connection.execute(
        "create table if not exists current(id integer primary key,snapshot integer not null)"
    )
    connection.execute("insert or ignore into current values(1,0)")
    connection.commit()
    return connection


def data_file(root, name, rows):
    if not name.isalnum():
        raise ValueError("Invalid fixture name")
    path = root / (name + ".parquet")
    if path.exists():
        raise ValueError("The local data-file contract is immutable")
    table = pa.Table.from_pylist(
        rows, schema=pa.schema([("id", pa.string()), ("packages", pa.int64())])
    )
    pq.write_table(table, path)
    return {"file": path.name, "sha256": hashlib.sha256(path.read_bytes()).hexdigest()}


def read_files(root, manifest):
    result = {}
    for item in manifest["files"]:
        name = item["file"]
        if Path(name).name != name:
            raise ValueError("Files must be owned basenames")
        path = root / name
        if path.is_symlink() or hashlib.sha256(path.read_bytes()).hexdigest() != item["sha256"]:
            raise ValueError("Snapshot data identity changed")
        for row in pq.read_table(path).to_pylist():
            if row["id"] in result:
                raise ValueError("Snapshot contains a duplicated row identity")
            result[row["id"]] = row["packages"]
    for key in manifest["deleted_ids"]:
        result.pop(key, None)
    return dict(sorted(result.items()))


def commit(connection, root, snapshot, parent, files, deleted_ids):
    manifest = {"parent": parent, "files": files, "deleted_ids": sorted(set(deleted_ids))}
    read_files(root, manifest)
    with connection:
        connection.execute("begin immediate")
        observed = connection.execute("select snapshot from current where id=1").fetchone()[0]
        if observed != parent:
            raise ValueError("Snapshot parent changed; replan and validate before retrying")
        connection.execute(
            "insert into snapshots values(?,?)", (snapshot, json.dumps(manifest, sort_keys=True))
        )
        connection.execute("update current set snapshot=? where id=1", (snapshot,))
    return manifest


def read_snapshot(connection, root, snapshot):
    value = connection.execute("select manifest from snapshots where id=?", (snapshot,)).fetchone()
    if value is None:
        raise ValueError("Snapshot is not committed")
    return read_files(root, json.loads(value[0]))


def example_one():
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        connection = catalog(root / "catalog.db")
        try:
            original = data_file(
                root,
                "base",
                [
                    {"id": "A", "packages": 2},
                    {"id": "B", "packages": 3},
                    {"id": "C", "packages": 1},
                ],
            )
            commit(connection, root, 1, 0, [original], [])
            before = read_snapshot(connection, root, 1)
            added = data_file(root, "added", [{"id": "D", "packages": 4}])
            commit(connection, root, 2, 1, [original, added], ["B"])
            after = read_snapshot(connection, root, 2)
            assert before == {"A": 2, "B": 3, "C": 1} and after == {"A": 2, "C": 1, "D": 4}
            assert read_snapshot(connection, root, 1) == before
            return {
                "old_snapshot": before,
                "new_snapshot": after,
                "physical_B_still_in_old_file": True,
            }
        finally:
            connection.close()


def example_two():
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        connection = catalog(root / "catalog.db")
        try:
            base = data_file(root, "base", [{"id": "A", "packages": 2}])
            commit(connection, root, 1, 0, [base], [])
            winner = data_file(root, "winner", [{"id": "B", "packages": 3}])
            orphan = data_file(root, "uncommitted", [{"id": "C", "packages": 100}])
            commit(connection, root, 2, 1, [base, winner], [])
            try:
                commit(connection, root, 3, 1, [base, orphan], [])
            except ValueError:
                pass
            else:
                raise AssertionError("A stale writer committed over a newer snapshot")
            referenced = {
                item["file"]
                for (text,) in connection.execute("select manifest from snapshots")
                for item in json.loads(text)["files"]
            }
            unreferenced = sorted(
                path.name for path in root.glob("*.parquet") if path.name not in referenced
            )
            assert unreferenced == ["uncommitted.parquet"]
            assert connection.execute("select snapshot from current").fetchone() == (2,)
            assert read_snapshot(connection, root, 2) == {"A": 2, "B": 3}
            return {
                "accepted_snapshot": 2,
                "uncommitted_files_not_visible": unreferenced,
                "garbage_collection_was_not_performed": True,
            }
        finally:
            connection.close()


def main():
    print("Snapshots and logical deletion:", example_one())
    print("Concurrent-parent conflict and unreferenced files:", example_two())


if __name__ == "__main__":
    main()

Compare real formats by required guarantees#

Iceberg uses snapshot metadata and catalog-mediated commits, with validation when concurrent changes require retry. Delta Lake maintains a transaction log and uses optimistic conflict detection around supported writes. Hudi coordinates writes and table services through its timeline and concurrency mechanisms. These are architectural starting points; a production choice must inspect supported operations, catalog integrations, engine compatibility and recovery procedures in the exact versions being deployed.

Ask whether your workload is append-heavy, update-heavy or dominated by incremental ingestion. Ask how deletes are represented and which readers understand them. Ask whether schema and partition evolution preserve the identities your consumers need. Ask how compaction interacts with concurrent writers and what happens if maintenance fails halfway through. A format name alone does not answer these questions.

Isolation also needs precise wording. A consistent snapshot read does not imply that every pair of concurrent writes is automatically compatible. Two disjoint appends may be safely rebased under one implementation, while an overwrite based on an old predicate may conflict with a new row. Validation must reflect the operation's read and write sets. Blind retry can produce a committed result that no longer matches the writer's original assumptions.

Maintenance and failure diagnosis#

Compaction rewrites physical layout while aiming to preserve logical content. Snapshot expiration removes historical references according to policy. Orphan cleanup removes data that are no longer referenced or otherwise protected. These are different operations. Combining them into an indiscriminate directory cleanup can destroy valid history or an in-progress write. Retain enough metadata to explain which files remain reachable and why.

If a current query returns a deleted row, verify that the reader understands the format's delete representation and reads through the table metadata rather than globbing raw files. If a time-travel query fails, inspect whether the required snapshot or files were expired. If a concurrent write fails, inspect the actual conflict before retrying. If disk usage remains high after logical deletion, inspect retained snapshots and maintenance policy rather than assuming the delete statement did nothing.

Applications and answered interview discussion#

Snapshot tables support reproducible analytics, ML training datasets, controlled rollback and concurrent lake writes. They can reduce bespoke publication code, but they introduce their own operational responsibilities: metadata growth, maintenance scheduling, reader compatibility and catalog availability. Evaluate those responsibilities alongside query performance.

An interviewer may ask, “Why is a directory of Parquet files not a transactional table?” Explain visibility, concurrent commit coordination, schema evolution and delete semantics. If asked why a failed writer left files behind, explain preparation before commit and the need for safe orphan handling. If asked whether rolling back a snapshot restores an entire application, distinguish table state from external notifications, model deployments and other side effects that may already have happened.

For an answered extension, the losing append could potentially be replanned onto snapshot 2, retaining both B and C if the operation is still valid. An overwrite that intended to replace all rows matching an old condition needs stronger validation. The conflict is a prompt to reevaluate semantics, not merely a transient error to suppress.
