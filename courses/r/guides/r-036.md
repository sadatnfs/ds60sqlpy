## Outcome and mechanism

Combine chunk-level sufficient statistics correctly and distinguish a memory strategy from a performance claim.

A table may be larger than a convenient in-memory intermediate. Processing it in chunks can reduce the peak size of some operations, but only when the output state can be combined correctly. A sum and count are straightforward mergeable state for an observed-value mean. An unweighted mean of chunk means is generally wrong when chunk sizes differ.

Define the state before the loop. Each chunk can return observed count, missing count and observed sum. Combining those fields by addition preserves enough information for the final mean. The final all-missing policy still matters: zero total count should produce the declared missing result rather than an accidental division by zero.

Not every operation is equally mergeable. An exact median requires more distribution information than one number per chunk. A distinct count requires the union of keys or a deliberately chosen approximate sketch with an error contract. A join may require partitioning by keys, external storage or an indexed lookup. Chunking syntax alone does not solve those algorithmic requirements.

Floating-point addition is not perfectly associative. Two mathematically equivalent reduction orders can differ slightly when magnitudes vary greatly. Tests should distinguish harmless representation error from a changed population or weighting rule. These tiny examples establish semantic equivalence and bounded state size; they do not claim measured speed, memory savings on a large production workload or automatic parallel execution.

## Vocabulary

| Term | Meaning |
| --- | --- |
| Chunk | A bounded subset processed under the same transformation contract. |
| Mergeable state | Partial results that can be combined without changing the intended statistic. |
| Associativity | A property allowing grouping of operations without changing exact mathematical meaning. |
| Numerical accumulation | The finite-precision implementation of repeated arithmetic. |

## Read the syntax

Represent state as a named numeric vector or list, update it per chunk, and compute the final statistic once. Test uneven chunk sizes and all-missing input. Use an explicit tolerance when reduction order can change floating-point rounding.

## Worked examples

### Example 1: Combine sums and counts, not means

```r
chunks <- list(c(10), c(20, 30, 40))
state <- c(count = 0, total = 0)
for (chunk in chunks) {
  state <- state + c(count = length(chunk), total = sum(chunk))
}
mean_from_state <- state[["total"]] / state[["count"]]
stopifnot(mean_from_state == 25, mean(vapply(chunks, mean, numeric(1))) == 20)
print(state)
```

**Expected observation:** Count 4, total 100, mean 25.

The two chunks have unequal sizes. Sufficient totals reconstruct the observation mean while averaging the two chunk means changes the weighting.

### Example 2: A chunked missingness ledger

```r
chunks <- list(c(1, NA_real_), c(3, 5), c(NA_real_))
state <- c(observed = 0, missing = 0, total = 0)
for (chunk in chunks) {
  valid <- !is.na(chunk)
  state <- state + c(observed = sum(valid), missing = sum(!valid), total = sum(chunk[valid]))
}
stopifnot(state[["observed"]] == 3, state[["missing"]] == 2, state[["total"]] == 9)
print(state)
```

**Expected observation:** Observed 3, missing 2, total 9.

Each input entry contributes to either observed or missing count. The total uses only observed measurements under the declared policy.

### Example 3: Averaging chunk rates depends on the boundaries

```r
chunks <- list(c(1, NA_real_), c(3, 5), c(NA_real_))
regrouped <- list(c(1, NA_real_, 3), c(5, NA_real_))
mean_of_rates <- function(chunks) mean(vapply(chunks, function(x) mean(is.na(x)), numeric(1)))
pooled_rate <- function(chunks) {
  state <- c(missing = 0, rows = 0)
  for (chunk in chunks) state <- state + c(missing = sum(is.na(chunk)), rows = length(chunk))
  state[["missing"]] / state[["rows"]]
}
stopifnot(mean_of_rates(chunks) == 0.5, isTRUE(all.equal(mean_of_rates(regrouped), 5 / 12)))
stopifnot(pooled_rate(chunks) == 0.4, pooled_rate(regrouped) == 0.4)
print(c(mean_of_rates = mean_of_rates(chunks), pooled = pooled_rate(chunks)))
```

**Expected observation:** mean_of_rates 0.5 and pooled 0.4; after regrouping the first becomes about 0.417 while the pooled rate stays 0.4.

The three chunks have missing rates of one half, zero and one, which average to 0.5. The data contain 2 missing values among 5, a rate of 0.4. Averaging rates weights the single value chunk the same as the two value chunks, and the answer moves when the same five values are split differently: one third and one half average to 5/12. Accumulating the missing count and the row count, then dividing once, gives 0.4 for any boundaries. A missing rate is a mean of indicators, so it follows the same rule as any other mean: merge numerator and denominator, not ratios.

## Tracing the state through three chunks

The reference call `combine(list(c(1, NA_real_), c(3, 5), NA_real_))` updates three numbers per chunk:

```text
step       chunk    valid        observed  missing  total
start                            0         0        0
chunk 1    1, NA    TRUE FALSE   1         1        1
chunk 2    3, 5     TRUE TRUE    3         1        9
chunk 3    NA       FALSE        3         2        9
finalize   mean = 9 / 3 = 3
```

In chunk 3, `chunk[valid]` is empty and `sum(numeric(0))` is 0, so the total stays 9 while the missing count rises. An empty chunk adds zeros to all three entries in the same way.

The state never grows: three numbers describe any number of chunks, and the mean is computed once at the end. That is the memory contract. A reader that loads one chunk at a time from a file only ever needs that chunk plus the state in memory. The reference, however, builds the whole list of chunks before combining, so it demonstrates the arithmetic, not the memory saving. A memory claim needs a reader that streams from disk and a measurement of the running process.

## Progressive hints

1. Divide once after merging.
2. The admitted population stays the same.
3. Check total observed count before division.
4. One median per chunk discards necessary distribution information.
5. Its zero count/sum should not invent an observation.
6. A small arithmetic check is not a benchmark.
