## A restart must preserve the state that determines the next step

Saving model weights is enough for some inference tasks: given the same architecture and input, those weights can reproduce a prediction under the required modes and numerical conditions. Continuing training asks more. The next update may depend on optimizer history, a schedule, random-number state and where the data iterator stopped. A checkpoint is sufficient only relative to the continuation claim being made.

The scalar experiment isolates optimizer history. It trains the parameter w on (w-2)^2 using Adam with learning rate 0.1. Adam maintains a running first moment of gradients, a running second moment of squared gradients and a step count used by bias correction. These values are part of its state. Reconstructing a new Adam object at the same w does not reconstruct those histories automatically.

For intuition, use Adam's default moment coefficients beta1=0.9 and beta2=0.999. At w=0 the gradient is -4. Starting from zero moments gives m1=-0.4 and v1=0.016. Correcting their initial bias gives m_hat=-4 and v_hat=16. The update is approximately -0.1*(-4)/(4+epsilon), moving w to about 0.1. The next gradient is about -3.8, but the moments now combine it with the previous gradient rather than treating it as the first observation. The [Adam API](https://docs.pytorch.org/docs/2.9/generated/torch.optim.Adam.html) defines the stateful update convention used by the fixture.

After two updates, the reference saves both the parameter and optimizer state. It then takes the third step uninterrupted and records the resulting weight. A fresh Python interpreter loads the saved state, reconstructs the parameter and optimizer, and takes the same next step. Comparing those two results tests continuation, not merely the ability to deserialize a file. The separate weights-only branch deliberately starts a new optimizer and produces a different next weight, exposing the missing history.

The new interpreter is important evidence because it cannot accidentally reuse the original in-memory optimizer. The test still has a narrow scope: it uses one deterministic scalar objective and a trusted local checkpoint in a temporary directory. A stochastic training job would additionally need the relevant RNG state, data ordering and scheduler state to make an equivalent next-update claim. A seed written at the top of a script is not a replacement for the exact random state at the interruption point.

Evaluation mode and gradient recording are independent settings. The Dropout example calls eval so that the layer returns the supplied ones unchanged. no_grad would disable construction of a backward graph, but would not by itself change Dropout's training behavior. Conversely, eval does not generally prohibit gradients. A reproducibility report should name the forward mode and the gradient-recording mode separately instead of treating both as one "inference switch."

Finally, checkpoint compatibility includes architecture, parameter names, shapes, optimizer parameter grouping, dtypes and software assumptions. This lesson does not claim arbitrary files are safe to load or every version can resume another version's state. It establishes one owned, bounded restart and demonstrates why saving too little state changes the algorithm.
