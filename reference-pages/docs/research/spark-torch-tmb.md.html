Custom likelihoods, automatic differentiation, Spark and TMB#

Research and implementation snapshot: 2026-10-29.

Spark can support custom maximum-likelihood models with PyTorch or TMB when the objective has a valid decomposition and each worker has a prepared numerical environment. We implemented both paths. The independent R-free package is the primary framework; the R/TMB companion is an optional reference and compatibility path. Spark schedules data work; Torch or TMB computes local derivatives; a driver can combine numeric summaries and optimize one shared parameter vector. Separately, TorchDistributor launches actual Torch and Lightning training processes. These are different execution designs.

The central limit is mathematical: arbitrary storage partitions are not independent statistical units. A covariance edge, shared latent effect or global normalizer can invalidate a naive sum of partition likelihoods. No compiler, UDF or AD library repairs a factorization that changes the model.

This report answers the seven requested research questions, identifies the historical sources inspected, and maps the findings to actual source. The new material comprises 20 custom-likelihood PyTorch chapters, 38 advanced Spark chapters and 48 TMB chapters. All three subjects now pass shared catalog and prerequisite admission. Source implementation, local native execution, classroom/browser integration and final publication are separate stages. The new phase's final shared integration and release are still pending.

1. How Spark can fit custom maximum-likelihood models#

Start by defining the observation unit and the parameters it shares with other units. Four patterns cover many useful designs:

Pattern Mathematical target Appropriate computation Incorrect shortcut
Independent models Separate parameter vector for each group Fit each complete group and retain separate diagnostics Average fitted coefficients and call that the global MLE
Shared additive model One parameter vector, sum of independent contributions Evaluate loss and gradient per partition, combine them, update one driver vector Update a different parameter vector independently in each partition
Group-separable latent model Common fixed parameters, independent latent blocks Integrate each complete block at the same fixed parameters, then sum marginal contributions Optimize shared hyperparameters separately by group
Coupled model Cross-unit covariance, shared states or nonlocal objective terms Preserve the coupled block or use a justified specialized algorithm Drop cross-partition terms and retain the original model's name

For an additive weighted negative log likelihood, our implemented contract is

With lambda zero this is an unpenalized weighted objective; a nonzero penalty changes the estimation target. Integer frequency weights can represent repeated observations. Survey, importance or other fractional weights need their own inferential interpretation rather than being silently treated as ordinary independent replicates.

Each worker returns a row count, total weight, loss sum and gradient sum. The driver validates partition completeness and the exact parameter digest before combining results. The penalty is added once. For a weighted mean, the combined data loss and gradient are divided by the global weight sum before the penalty is applied. This makes the meaning of lambda explicit.

For example, partitions with counts one and three and sums one and nine have a global mean of 2.5. Averaging their local means yields two. The same error can appear in Spark aggregates, Arrow batches and DDP ranks. Repartitioning must not silently change the statistical objective.

The implementation uses Spark's public partition and aggregation mechanisms; these distribute a supplied calculation rather than deriving its statistical validity. Spark also offers a built-in logistic estimator, useful as a reference for supported models but not as an interface for every arbitrary likelihood. See the Spark 4.0.1 programming guide and LogisticRegression API.

The first complete examples deliberately have strong oracles:

  • Stable binary logistic loss uses softplus⁡(z)−yz\operatorname{softplus}(z)-yzsoftplus(z)−yz, where softplus⁡(z)=max⁡(z,0)+log⁡(1+e−∣z∣)\operatorname{softplus}(z)=\max(z,0)+\log(1+e^{-|z|})softplus(z)=max(z,0)+log(1+e−∣z∣). We compare analytic gradients, finite differences and actual Spark reduction.
  • Nonlinear Gaussian regression uses μ(t)=aexp⁡(−bt)+c\mu(t)=a\exp(-bt)+cμ(t)=aexp(−bt)+c, with positive rate and scale represented explicitly. The likelihood includes the log-scale normalization. One public Spark example profiles linear parameters over a finite rate grid; the combined Torch project fits a continuous four-parameter objective and compares with a separate NumPy/SciPy calculation. The grid fit is not described as a continuous global optimizer.
  • The AR(1) example retains the initial-state density and every transition. Restarting the stochastic process at each physical partition produces a different likelihood, which the counterexample demonstrates.

Repeated optimization actions have real costs. Cache immutable input when useful, return small summaries, limit native library threads, and measure scheduling, conversion, arithmetic and reduction separately. A cache is not a transactional snapshot: lost partitions can be recomputed from lineage. Pure task evaluation also avoids counting retried side effects as extra observations.

For group fits, Spark 4.0.1's applyInPandas performs a shuffle and loads complete groups. A check inside the pandas function cannot prevent memory exhaustion that occurred while materializing a giant group. mapInPandas instead provides an iterator of transport batches; a transport batch is not a statistical group. These boundaries are documented in the versioned grouped pandas API and mapInPandas API.

2. What “native automatic differentiation in Spark” means#

There are three distinct claims:

  1. Spark executes derivative formulas. Yes. A SQL expression, Scala aggregate or partition function can compute an analytic gradient.
  2. A derivative engine runs inside Spark tasks. Yes. Our original Scala dual-number example performs bounded forward-mode AD in JVM task code. The prepared Torch and TMB projects perform genuine local AD inside their respective numerical processes.
  3. Spark automatically differentiates an arbitrary DataFrame program through joins, shuffles, UDFs and materialization. The inspected Spark 4.0.1 public APIs do not provide that general facility. Our implementation does not claim to add it.

The distinction is visible at the serialization boundary. A Torch tensor graph or TMB native tape can produce a numeric gradient. Once that gradient and loss are returned as ordinary numbers, they are evidence from an evaluation, not a portable global reverse-mode graph. Wrapping a collected scalar in a new tensor with gradients enabled does not reconnect it to the original distributed data.

The dual-number lesson implements a+bεa+b\varepsilona+bε, with ε2=0\varepsilon^2=0ε2=0, for addition, multiplication and exponential. It correctly propagates derivatives through compositions such as x2+exx^2+e^xx2+ex. That is real AD for its supported operations. It does not differentiate a Spark scheduler, discrete top-k selection or arbitrary third-party function. PyTorch's own autograd mechanics explains its graph-based local derivative mechanism; Spark's expression source describes a query-expression execution interface, a different abstraction.

3. Custom likelihood modeling in PyTorch#

PyTorch is useful for classical statistical optimization as well as neural networks. A model can produce one normalized negative log-likelihood term per observation, then use autograd and a conventional optimizer. The main work is specifying the probability model correctly: support, normalizing terms, parameter constraints, observation dependence and the prediction target.

The new 20-chapter route starts with observation/parameter/likelihood distinctions and proceeds through Gaussian and nonlinear models, logistic and count likelihoods, censoring, heteroskedasticity, mixtures and correlated residuals. It then develops penalties, identifiability, optimizer closures, curvature, prediction and uncertainty. All 20 programs are complete original float64 CPU examples.

Two frequently missed details receive explicit treatment:

  • Estimating a Gaussian scale requires the log-scale normalization as well as the squared residual. Increasing scale must not make every observation artificially favorable for free.
  • Reparameterizing an optimizer variable, such as σ=exp⁡(s)\sigma=\exp(s)σ=exp(s), requires the chain rule but does not automatically add a likelihood Jacobian. A transformed probability density is a different question, where a Jacobian can be required.

Mixtures use stable log-sum calculations. Censored observations contribute probability mass over an unobserved range, not an imputed observation at the censoring threshold. Correlated panels retain their joint structure. These are modeling decisions that AD faithfully differentiates, whether they are right or wrong.

The route checks analytic scores and finite differences, inspects Hessians and profiles, and distinguishes convergence from identification. PyTorch's gradcheck documentation provides a numerical derivative-testing mechanism; passing it does not establish that the scientific model or confidence interval is valid. Closure-based optimization also has an explicit evaluation contract, described by the LBFGS API.

Chapter map: clp-001 through clp-004 establish likelihood and derivative contracts; clp-005 through clp-012 implement distinct distributions and dependence structures; clp-013 through clp-016 cover estimation diagnostics; clp-017 through clp-020 cover prediction, uncertainty, distributed scaling and a nonlinear panel dossier. See the course's validation record for actual numerical execution and the limitations of supplied covariance and plug-in prediction examples.

The package bounds parameters at 64, partition summaries at 4,096 and local batches at 8,192 rows. Those limits express its teaching and driver-memory scope. The model must be deterministic and additive across its declared observation units. A callable that depends on batch composition violates the contract even if its return tensor has the expected shape.

A complete-unit callback returns one joint loss for a whole independent group; it is not a scalar shortcut through the per-row batching interface. The exact Gaussian random-intercept model integrates the latent intercept with Torch linear algebra and matches an independent rank-one oracle. Its declared prediction is a marginal new-group mean, not an inferred existing-group latent effect. The original Gamma-Poisson custom model proves non-Gaussian extensibility through ordinary registration: groups share a Gamma-distributed latent rate, exposures enter the conditional Poisson law, and a closed-form integral supplies the joint NLL. It is not a generic Laplace engine.

Review found that subtracting large Gamma log-normalizers could produce zero loss and score at log shape/rate 100 despite the correct zero-count loss being three. The repaired example uses a bounded integer rising-factorial identity and stable log-domain products. Zero and nonzero count cases at log shape/rate 40, 100 and 300 match the independent Poisson limit. Its explicit total-count and numerical bounds are documented rather than silently clipped during optimization.

Model identity also includes callable defaults, keyword defaults, direct JSON constants and normalized live bytecode, with Python minor compatibility. Replacing a named code object changes identity even when its source file is unchanged; relocating source paths alone does not. Trusted code/configuration remain a requirement. Direct package JSON loading does not import an artifact-selected model, while upstream Spark Pipeline metadata can import stage classes and must come from a trusted source.

5. TMB/adcomp, R/C++, rpy2 and Spark integration#

TMB's architecture fits this problem well. An author writes a C++ template for the objective, R constructs callable value/derivative functions with MakeADFun, and an optimizer such as nlminb performs estimation. REPORT, ADREPORT and sdreport serve different reporting and uncertainty roles. Selected latent variables can be integrated through a Laplace approximation. These mechanisms are documented by the TMB introduction and the authors' methodology paper. The introduction currently displays an older documentation build, so our exact API inventory is tied to installed TMB 1.9.25 rather than that header.

TMB differentiates supported operations expressed with its templated numeric Type; converting a parameter-dependent value to an ordinary double or calling an external routine without a derivative interface can break that computation. The prepared project qualifies the CppAD route. TMBad-specific capabilities and specialized internal integration options have separate preparation boundaries. TMB's OpenMP accumulation is parallelism within a prepared numerical process, not Spark distribution. The documented parallel accumulator has a restricted accumulation contract, and the course checks one/two-thread parity before treating parallel execution as evidence. The current TMB 1.9.25 manual is the reference for installed R API details and distinguishes simulation diagnostics, profiles, inner solvers and reporting methods.

The 48-chapter TMB route includes nine original compiled models and 48 base-R mathematical companions. Native C++/TMB compilation remains a separate project capability. The public API reference maps the installed namespace's 30 exports, nine registered S3 methods and an explicitly labeled non-exported documented helper. It does not say every specialized facility was exercised merely because its name was inventoried. Eight additional chapters, tmb-041 through tmb-048, teach C++ data/container contracts, density and sparse/separable families, stable branches and custom atomic derivatives. Five original native probes test those families separately. See CPP-API-FAMILIES.md, API-REFERENCE.md, api-inventory.json and QUALIFICATION.md.

When group Laplace contributions can be summed#

For complete independent latent groups conditional on shared theta,

At a suitable inner mode with positive-definite latent Hessian,

Evaluate all terms at the same theta, then sum their marginal values and outer derivatives. Shared hyperparameter priors or penalties also need a deliberate once-only placement. Integrating latent effects is different from maximizing the joint density over them. A conditional derivative at a frozen inner mode is not automatically the derivative of the complete marginal objective.

For Gaussian random intercepts the integral is Gaussian, so the Laplace result has an exact independent oracle. For non-Gaussian latent models it is generally an approximation. Correct derivatives of that approximation do not establish its accuracy for the original integral.

A coupled two-variable Hessian makes the limit concrete:

The independent-block curvature term is wrong by 12log⁡(4/3)\tfrac12\log(4/3)21​log(4/3), about 0.14384, before accounting for a potentially wrong inner mode. A spatial field or global latent state crossing partitions therefore needs its coupling retained. Complete connected components, sparse centralized solves within memory, state-space methods or a specialized distributed solver are possible alternatives. Arbitrary partition-local Laplace calls are not.

The implemented Spark/TMB boundary#

The Spark/TMB project contains a reusable prepared-model package, spark_tmb, as well as fixed numerical cases. Trusted model source is registered and compiled during preparation. Runtime requests contain a model ID, validated numerical data and parameters. They do not accept arbitrary C++ source, R expressions, compiler flags or library paths.

Registry v2 contains the original normal and random-intercept models plus prediction-enabled normal-location and linear-regression templates. It declares independent rows or complete groups, scalar/fixed-size-vector parameter blocks, canonical flattened coordinate names, bounded data fields and an optional indexed random vector. Response-free prediction/report semantics must be explicitly registered; a likelihood does not automatically define a forecast. The schema currently uses bounded numeric data vectors and explicit parameter blocks, not an arbitrary matrix/object bridge. Preparation binds source, compiled library, registry and R/TMB/Matrix/architecture identities. An R process loads the compatible library, creates its own native objective, evaluates or fits it, returns detached results and exits. Live R external pointers, DLL handles and tapes are never serialized through Spark.

SparkTMBObjective.evaluate(theta) returns one shared additive objective. fit_independent_units(initial) returns distinct fitted models. The unit ledger checks identifiers, counts and data hashes; it cannot discover that the author incorrectly declared correlated units independent. The bounded interface accepts at most 4,096 observations and 64 fixed parameters per unit payload, with an explicit bound on grouped latent structure. See REGISTERING-MODELS.md for the actual extension contract.

The fixed global-normal-fit example uses model-specific exact conditional updates derived from AD scores. It is not labeled a general nonlinear optimizer. The reusable evaluator supplies a boundary a separately prepared driver optimizer can consume when the objective assumptions hold. The optional reference also includes explicit DataFrame mappings, real ML fit/transform/persistence and a Scala/JVM route through the same validated prepared-model protocol. It consumes the standalone package's pure contracts without importing Torch. These R-bound reference capabilities are qualified separately from the primary R-free package.

The rpy2-frame case separately checks real pandas-to-R conversion and a compiled regression fit. Scoped converters keep conversion policy local; column order, missing values, factor indices and time zones remain explicit schema concerns. Conversion can copy data and is not a zero-cost transport for an entire massive Spark table. This follows the official rpy2 pandas guide.

6. Where PyMC fits#

PyMC is a strong complementary modeling and posterior-inference environment. Its custom-distribution interface can define a log probability, and predictive sampling requires an appropriate generative definition as well. A custom likelihood is not automatically a complete predictive model. The inspected current CustomDist documentation is newer than the classroom's pinned PyMC 5.28.5 runtime, so runnable code must follow the installed version's API, not a moving documentation label.

The target matters more than the library name. With observations one and three, known observation variance one and a normal prior with mean zero/variance one, the MLE of the mean is two. The posterior mean is four-thirds and posterior variance is one-third. The difference is intended prior information, not a framework disagreement. MAP, posterior mean, MLE and a Laplace marginal estimate are different quantities.

Spark may prepare data or orchestrate independent chains, but parallel chains do not make one chain's joint likelihood partition-additive. Likewise, replacing an exact full gradient with an arbitrary minibatch gradient changes the inference algorithm. A specialized stochastic method requires its own justification.

asm-036 develops this comparison and connects to the existing Bayesian route. The synthesis contains an analytic comparison, not a claim that identical Torch, TMB and PyMC programs were all newly executed side by side for every custom model. Use a small matched probabilistic model when doing that comparison.

Suggested reading route and extension choices#

For a Spark practitioner new to custom modeling, start with clp-001 through clp-007, then asm-001 through asm-012. Those chapters establish what the optimizer is minimizing and which parts can be distributed. Continue through the public Scala extension chapters before the optional Catalyst project.

For the TMB route, read tmb-001 through tmb-009, then latent-model chapters tmb-012 through tmb-018, followed by asm-031 through asm-035. Use the historical AFModel comparison to understand architectural choices, then build an original model through the prepared registry instead of importing an old application wholesale. Chapters tmb-025 through tmb-040 provide the deeper API and diagnostic route. Continue through tmb-041 to tmb-048 for the C++ model-authoring families and native derivative checks.

For neural or more general Torch customization, follow asm-026 through asm-030 after the serial likelihood route. Choose the additive driver adapter for small shared parameter vectors and expensive distributed data passes. Choose a training runtime when replicated large parameter vectors, collective updates or accelerators justify it. Preserve an explicit data-delivery and epoch contract in either case.

The next justified extensions would be a qualified real-cluster deployment, measured repeated-evaluation performance, controlled retry/recovery experiments, and a specialized coupled solver if a concrete model demands one. These are new acceptance tasks. The current examples provide the mathematical and runtime boundaries needed to design them without claiming they are already complete.
