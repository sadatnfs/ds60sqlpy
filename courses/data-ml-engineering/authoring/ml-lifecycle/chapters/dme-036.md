# dme-036: Train/serve consistency and safe model interfaces

## Preserve the meaning of a model's inputs

A training pipeline can be correct while a serving integration sends it the wrong information. Column names can match even when units differ. A numerical vector can have the expected length while its positions are reversed. A permissive parser can turn an invalid request into a plausible dataframe and allow the estimator to return a convincing number.

Train/serve consistency means preserving the intended computation and input semantics across those boundaries. It includes the fitted transformations, feature names and order, allowed types, units, category policy and model version. It is a stronger requirement than using the same programming language on both sides.

This chapter places one actual fitted scikit-learn pipeline behind a small JSON function. It does not start an HTTP server inside the pad. The function represents the inference boundary whose behavior can be tested independently. The separate owned service projects provide real process, network and persistence lifecycles.

## Separate validation from prediction

The toy model accepts two named features: `hours` and `region`. Its deployed contract uses schema version one, hours measured in hours, and a closed region set containing north and south. The numerical value must be finite and between zero and one thousand. This chosen bound is part of the demonstration contract, not a universal domain rule.

The classifier is a fitted pipeline containing a numerical scaler, categorical encoder and logistic estimator. Serving uses that same object. The JSON boundary validates a request before constructing a dataframe in the model's declared feature order. Only then does it call `predict_proba`.

Write this composition as

\[
s(r)=f_{\theta}\bigl(T_{\phi}(V(r))\bigr),
\]

where \(r\) is request text, \(V\) validates and constructs the named input, \(T_{\phi}\) is preprocessing with fitted state \(\phi\), and \(f_{\theta}\) is the fitted estimator. The returned \(s(r)\) is the classifier's numerical score. An invalid request has no score under this interface. Validation does not substitute a default prediction.

The example does not establish calibration of that score. Its purpose is to compare computations and prove rejection behavior. Scientific interpretation still requires the evaluation and decision work in chapters 033 and 038.

## Define a strict JSON and numerical contract

The input is bounded to 2,048 UTF-8 bytes. Byte length matters because characters can occupy different numbers of bytes. The parser rejects malformed JSON, duplicate object fields and nonstandard numeric constants such as bare `NaN`. The boundary then checks exact top-level fields and the exact nested feature names.

Duplicate keys are worth testing independently. Some JSON decoders keep the last occurrence, potentially giving two components different interpretations of the same message. The demonstration duplicates an otherwise-valid schema field with the same value. Without the explicit duplicate-field check, the rest of the request would be accepted. This isolates the property being tested.

Python introduces another subtlety: booleans are subclasses of integers. A broad integer test can therefore accept `True` as a measurement of one hour. The example checks exact permitted numeric types instead. It also bounds large integers before passing them to a floating-point finiteness check, so a hundreds-of-digits integer is rejected normally rather than causing a conversion overflow.

These rules distinguish a valid representation from a plausible number. A schema version is an exact integer identifier, not a floating estimate. A category is a member of a declared set, not any string that happens to be encodable. A unit declaration must match the model's interface. Silent coercion would add a different conversion policy that needs its own specification and tests.

## Worked case 1: Reordered JSON fields produce the same score

`example_one()` fits the toy pipeline once on eight original training rows. It scores a dataframe containing seven hours and region north directly through that fitted pipeline. It then sends the equivalent named values through the validated JSON function.

The observed score is approximately 0.6810869445 along both paths. A third request reverses the insertion order of the JSON feature fields. Its score remains the same because the boundary selects values by name and explicitly constructs columns in the order `hours`, then `region`.

This is not permission to ignore order in every model representation. Positional arrays still require a declared ordering. Here the named request object is converted to the model's expected order before scoring. A raw vector `[7, "north"]` and a raw vector `["north", 7]` are not interchangeable merely because their lengths match.

The captured table exposes all three outputs. The program compares them with an absolute tolerance of \(10^{-12}\) and zero relative tolerance. The interface counter reports two prediction calls through the validated function. The separate direct-reference call is outside that counter; it is not presented as a global process-wide inference count.

Keeping the fitted pipeline intact matters as much as the dataframe construction. Recreating a scaler from a current batch or relearning categories at inference time would produce a different computation, even if both sides still used the names `hours` and `region`.

## Worked case 2: Reject eight incompatible requests before scoring

`example_two()` creates another fitted predictor and submits eight deliberately incompatible requests. They change units from hours to minutes, change the schema version, omit a feature, supply a boolean measurement, introduce an unsupported region, supply an extremely large integer, duplicate a JSON field and use a nonfinite JSON constant.

Every request is rejected with a controlled validation error. The prediction counter stays at zero. A test that checked only whether some exception occurred would be weaker: an estimator might crash after receiving malformed inputs. Here the counter establishes that the model was never invoked through the interface for those rejected requests.

The duplicate-field request is otherwise valid, so its rejection demonstrates the parser rule rather than an unrelated missing-feature failure. The large integer is small enough as request text to enter the parser, then fails the numerical bound. The units example contains a perfectly ordinary numeric value; it fails because its declared meaning differs from the deployed model's meaning.

The closed-category policy is intentional. Chapter 035 demonstrated an encoder that could represent an unseen category. This deployed interface instead declares that only north and south are supported. A system can choose either policy, but the serving boundary and its documentation must agree. The existence of a numerical fallback inside a library does not authorize using it operationally.

## Diagnose semantic drift and implementation drift separately

If direct and interface outputs disagree, first compare exact submitted values, dataframe names and ordering, fitted preprocessing, estimator state and package environment. If values and code agree but the results no longer serve the intended decision, investigate population and process changes rather than assuming a parser defect.

A matching unit declaration cannot prove that a producer measured the quantity correctly. A sender can label minutes as hours. The interface checks the declared contract; source instrumentation, integration tests and operational evidence must establish that the declaration is truthful. Physical plausibility checks may help, but they are not a substitute for knowing how data was produced.

Likewise, a contract hash can identify exact metadata without establishing that an artifact came from a trusted producer. Chapter 040 separates byte integrity, structural compatibility and origin trust. Keeping those concerns explicit avoids turning a successful local prediction into an unsupported deployment claim.

## Answered interview discussion

**Why use named fields instead of accepting any vector of the right length?** Names make the intended values inspectable and allow the boundary to construct the model's fixed order. The contract still needs types, units, allowed values and version semantics.

**Why not convert every numeric-looking value automatically?** Conversion can hide producer errors and ambiguous representations. An explicit conversion layer can be useful, but its accepted forms, loss of information and failure behavior should be tested as part of the interface.

**Does using the same pipeline eliminate train/serve skew?** It removes one class of accidental transformation differences. Different upstream feature computation, units, availability, versions or populations can still produce skew.

**What does this example qualify?** It qualifies the actual fitted computation and strict in-process boundary on the stated fixtures. Authentication, HTTP behavior, concurrent capacity, deployment rollback and persistent model activation belong to the owned service workflows.
