nlp-002: Unicode, normalization and loss of information#

Level and prerequisites#

Beginner NLP; about two hours. Direct prerequisite: nlp-001. You should be able to inspect a Python dictionary and explain why a document's identity must survive preprocessing. This chapter teaches the representation choices that come before tokenization or embeddings.

Why the same-looking text can behave differently#

A person sees a word on a screen. A program stores a sequence of symbols. A file stores bytes. These are related representations, but they are not interchangeable. If you compare the wrong representation, two equivalent names may fail to match, a byte count may be mistaken for a token budget, or an extracted span may point to the wrong characters.

A Unicode code point is an integer assigned a meaning in the Unicode standard. A Python str is a sequence of code points. An encoding maps that sequence into bytes; UTF-8 is one such encoding. A grapheme cluster approximates a user-perceived character and can contain several code points. A font shapes those code points into visible glyphs. Neither the number of bytes nor Python's len(text) generally measures what a reader perceives as the number of characters.

This distinction is operational. A storage or transport limit might be in bytes. A tokenizer imposes a model limit in tokens. An annotation tool may record offsets in code points, UTF-16 code units or bytes. Before connecting tools, write down the offset convention. A correct entity span in one convention is not automatically a correct span in another.

Consider two spellings of café. One uses a single precomposed é; the other uses e followed by a combining accent. Their glyphs may look identical. Their code-point sequences and UTF-8 bytes differ. This is a representation issue, not a spelling correction problem.

Worked example: inspect all relevant lengths#

import unicodedata as ud

composed = "café"
decomposed = "cafe\u0301"
for text in (composed, decomposed):
    print(repr(text), len(text), len(text.encode("utf-8")))
    print([f"U+{ord(char):04X}" for char in text])
print(composed == decomposed)
print(ud.normalize("NFC", composed) == ud.normalize("NFC", decomposed))

Expected code-point and byte lengths: (4, 5) for the composed spelling and (5, 6) for the decomposed spelling. Exact string equality is False; equality after NFC normalization is True. The first string ends in U+00E9. The second ends in U+0065 and U+0301. repr helps expose invisible distinctions, while the explicit code-point list makes the observation independent of the font.

encode("utf-8") returns bytes. It does not normalize the text. normalize("NFC", text) returns a new string. It does not mutate the original. These are separate operations, so make each one visible in a preprocessing pipeline. Saving only the normalized string makes some later audits impossible.

Canonical and compatibility equivalence#

Unicode distinguishes canonical equivalence, such as the two accent representations, from compatibility equivalence, which may discard presentation distinctions. NFC performs canonical decomposition followed by composition where appropriate. NFD keeps the canonical decomposed representation. NFKC and NFKD also apply compatibility decomposition.

NFC is often a reasonable interoperability choice for ordinary natural-language text, but the correct policy depends on the task. NFKC can make search more forgiving by mapping full-width letters or circled digits to ordinary forms. It can also erase a distinction relevant to an identifier, a legal transcription or a typography analysis. No normalization form understands the meaning of the document or the rules of your domain.

import unicodedata as ud

raw = "① ﬁ Ａ"
print(ud.normalize("NFC", raw))
print(ud.normalize("NFKC", raw))
print("Straße".casefold())
print(ud.normalize("NFC", "a") == ud.normalize("NFC", "\u0430"))

Expected: NFC preserves ① ﬁ Ａ; NFKC returns 1 fi A; case folding returns strasse; the final comparison is False. The last pair is Latin a versus Cyrillic small а. Normalization is not a general defense against visually confusable identifiers. A domain that uses account names or executable identifiers needs a separate policy for scripts, confusables and allowed characters.

Case folding is a matching transformation, not a faithful display transformation. It can change length, as ß becoming ss demonstrates. Lowercasing and case folding are not identical. Neither removes accents nor resolves all locale-specific interpretation. Preserve the original text for display and evidence, and use an explicitly named transformed field for the intended comparison.

Preprocessing is an information decision#

Let T be a transformation from raw strings to normalized strings. If T(x) = T(y) for distinct raw strings x and y, the transformation is many-to-one. After retaining only T(x), there may be no unique way to recover the original input. That does not make the transformation wrong; it makes the loss part of the model specification.

A useful audit groups raw values by their transformed value. The groups reveal collisions rather than hiding them inside a deduplication step. For NFC, a collision between canonically equivalent accent representations may be desirable. For NFKC, a collision between ① and 1 deserves a task-specific decision. Never assume every collision is either a data error or a harmless duplicate.

from collections import defaultdict
import unicodedata as ud

raw_values = ["1", "①", "café", "cafe\u0301"]
preimages = defaultdict(list)
for raw in raw_values:
    preimages[ud.normalize("NFKC", raw)].append(raw)
print({key: values for key, values in preimages.items() if len(values) > 1})

Expected: one group under 1 containing 1 and ①, and one under café containing its two raw representations. The result is evidence of collisions in this fixture, not a universal estimate of their frequency. To measure frequency in a real corpus, report the sampling unit, number of raw values and number of transformed groups.

Version preprocessing as part of the data pipeline. Record the transformation order, Unicode database version, encoding, case policy and any whitespace rules. Applying case folding before or after another transformation can affect a composed pipeline. Test the composed pipeline's intended invariants, rather than assuming that the individual operations imply them. For each normalization form on these examples, normalizing twice should equal normalizing once; this is an idempotence check, not proof that the form preserves your task's meaning.

Invalid bytes and explicit decoding decisions#

Text files can contain invalid byte sequences, truncated encodings or data mislabeled with the wrong encoding. Python's strict UTF-8 decoder raises an error for invalid input. Replacement mode inserts a replacement character and continues. Ignoring errors removes information. A pipeline that silently “fixes” every invalid record may appear robust while changing the evidence.

raw_bytes = b"caf\xff"
try:
    raw_bytes.decode("utf-8", errors="strict")
except UnicodeDecodeError as error:
    print(error.start, error.end)
print(raw_bytes.decode("utf-8", errors="replace"))

Expected: the failing byte range is [3, 4), and replacement decoding produces caf�. A half-open range includes the start position and excludes the end. An appropriate ingestion policy might quarantine the record while preserving its bytes and source metadata. Another application may explicitly accept replacement for a preview, while marking the text unsuitable for exact extraction. The important requirement is that the policy is visible and repeatable.

Do not infer an encoding solely from whether decoding happened to succeed. Many byte sequences are valid under several encodings. Use source metadata, format specifications and reviewed detection where needed. A successful decoder is evidence about the chosen representation, not necessarily about the intended text.

Offsets, annotations and evidence#

An entity annotation is often a start and end offset into a particular immutable text version. If you normalize, trim or case-fold that text, offsets can become invalid. Suppose a reviewer marks the entire decomposed cafe\u0301 as [0, 5). The NFC version has length 4. Copying the old offsets and calling them normalized-text offsets loses the original contract.

For a small application, the safest design can be to store raw text plus spans into that raw text, and derive a separate normalized field for search. A more advanced system may maintain an alignment map between versions. Such a map must account for composition, expansion and removal, so a simple constant offset is generally insufficient. Avoid pretending that Python slicing will recover the original evidence after arbitrary transformations.

Emoji provide another reminder that code points and visible characters differ. The string 👩‍💻 contains three code points joined into a common displayed sequence. Python 3.12's ordinary string length is 3. A grapheme-aware segmenter requires its own algorithm and versioned behavior; this chapter does not replace one with list(text). Later tokenization lessons distinguish code-point, byte, word and learned-subword representations.

Exercises#

  1. Compare representations. Recreate both spellings of café and inspect equality, code-point counts and UTF-8 byte counts. Expected: raw inequality, lengths (4, 5) and bytes (5, 6). Verify: assert those exact results without relying on how the terminal renders the accent.
  2. Choose canonical normalization. Normalize both spellings with NFC and NFD. Expected: equality within each form, NFC length 4 and NFD length 5. Verify: also assert idempotence for each of the four normalization forms on the supplied fixtures.
  3. Audit compatibility collisions. Group 1, ①, café and cafe\u0301 by NFKC. Expected: exactly two groups of two raw values. Verify: retain the original values and explain which merge depends on a domain policy rather than canonical equivalence alone.
  4. Separate matching from display. Apply case folding to Straße and compare the Latin/Cyrillic a pair under NFC. Expected: strasse has length 7; the cross-script pair remains unequal. Verify: explain why neither observation justifies overwriting a user's display name.
  5. Handle corrupt input deliberately. Decode b"caf\xff" strictly and with replacement. Expected: a UnicodeDecodeError at byte 3 and replacement output ending with U+FFFD. Verify: keep the original bytes and state when you would quarantine rather than accept the record.
  6. Protect span provenance. Store the raw decomposed word, its [0, 5) span and its NFC derivative. Expected: the raw slice reproduces the annotation; the derivative has a different length. Verify: reject a rule that treats the old span as an exact mapping into every transformed version, and give a second counterexample using case folding.

Hints, failure diagnosis and interview reasoning#

For the first exercise, compare len(text) and len(text.encode("utf-8")) as different measurements. For normalization, keep a dictionary with raw, form and normalized fields. For collision detection, use transformed values as grouping keys while retaining a list of raw values. For spans, write the version and coordinate convention next to the numbers before slicing.

If equal-looking strings fail to match, inspect code points before deleting accents. If matching suddenly improves after preprocessing, inspect what new collisions were introduced. If an annotation points at the wrong word, verify the text version and offset convention before blaming the entity model. If a decoder replaces characters, make the replacement count visible in data-quality reports.

Why not normalize everything aggressively? Because invariance is task-dependent. Search may want to ignore a presentation distinction that an identifier audit must preserve. A sound answer names the intended equivalence class and the information that may be discarded.

Does Unicode normalization make text safe? It addresses specified equivalences, not all security or semantic concerns. Confusable scripts, invisible controls, prompt injection and markup interpretation require separate boundaries. Treat text as data at every interface.

Why retain raw text? It supports audit, corrected preprocessing, annotation review and comparison across pipeline versions. Retention must still follow the permitted data lifecycle; provenance is not a reason to retain sensitive data indefinitely.
