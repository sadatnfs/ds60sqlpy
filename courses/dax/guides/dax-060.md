## The question and the mechanism

Assemble a reviewable model change with expected role/context results and explicit unperformed deployment checks.

A reliable semantic-model deliverable includes more than formulas. Retain the data/model specification, relationship directions, date/calendar policies, measure dependencies, role definitions, expected context results and a change rationale. Text-based external formats such as supported PBIP/TMDL projects can assist source control, but a directory of text is not proof that a real engine accepted or securely deployed the model.

This capstone combines the constant-product-cost rewrite with two declared security populations. North's expected revenue is 107 and cost 25; South's expected revenue is 80 and cost 19. The line and grouped cost formulas should agree within each permitted population. An ordinary filter-removal expression must not enlarge a real RLS-restricted population.

The offline result matrix is a specification to be tested, not a release approval. A real release requires observed model loading, role/identity tests, refresh/recovery behavior, query parity and representative performance evidence for the exact revision. Keep synthetic timing examples, hand-derived arithmetic and actual external observations in separate evidence categories. A no-go decision is appropriate when one required boundary remains unverified.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

### Feature and version boundary

These are hand-derived expectations under explicitly specified role policies, not tests of real RLS enforcement. Microsoft documentation reviewed 2026-10-25 distinguishes role-restricted Viewers from workspace Admin/Member/Contributor access. No account, role assignment, model publication or security engine is used by this classroom.

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
    MEASURE Sales[QuantitySold] = SUM ( Sales[Quantity] )
    MEASURE Sales[GrossRevenue] = SUMX ( Sales, Sales[Quantity] * Sales[UnitPrice] )
    MEASURE Sales[OrderCount] = DISTINCTCOUNT ( Sales[OrderID] )
    MEASURE Sales[Cost] = SUMX ( Sales, Sales[Quantity] * RELATED ( Product[UnitCost] ) )
```

### Case A: Expected NorthViewer regression row

**Starting context:** Assume enforced NorthViewer policy on the analytical model; all available dates; constant UnitCost per product.

```dax
EVALUATE ROW ( "Revenue", [NetRevenue], "LineCost", [Cost], "GroupedCost", SUMX ( VALUES ( Product[ProductKey] ), CALCULATE ( SUM ( Sales[Quantity] ) ) * CALCULATE ( MAX ( Product[UnitCost] ) ) ), "AfterCustomerFilterRemoval", CALCULATE ( [NetRevenue], REMOVEFILTERS ( Customer ) ) )
```

**Context trace:**

1. North permits Ada and Cy, giving revenue 51 +56 =107.
2. Their product quantities are 5 Notebook,5 Pen and 2 Mug, costing 10 +5 +10 =25.
3. Both cost forms agree; a real security restriction must remain after ordinary Customer-filter removal.

**Hand-derived worked-reference result:**

| Revenue | LineCost | GroupedCost | AfterCustomerFilterRemoval |
| --- | --- | --- | --- |
| 107 | 25 | 25 | 107 |

This expected row combines numerical parity with a policy boundary. It does not certify either on a live model until actual evidence is recorded.

Hand-derived acceptance specification under an assumed role; not a runtime, security or deployment receipt.

### Case B: Expected SouthViewer regression row

**Starting context:** Assume enforced SouthViewer policy; the same model and measure definitions with a different allowed Customer population.

```dax
EVALUATE ROW ( "Revenue", [NetRevenue], "LineCost", [Cost], "GroupedCost", SUMX ( VALUES ( Product[ProductKey] ), CALCULATE ( SUM ( Sales[Quantity] ) ) * CALCULATE ( MAX ( Product[UnitCost] ) ) ), "AfterCustomerFilterRemoval", CALCULATE ( [NetRevenue], REMOVEFILTERS ( Customer ) ) )
```

**Context trace:**

1. South permits Bo, whose three lines total 80.
2. TwoNotebook units cost 4 and three Mug units cost 15, totaling 19.
3. The grouped result agrees and the restricted revenue remains 80 after ordinary filter removal.

**Hand-derived worked-reference result:**

| Revenue | LineCost | GroupedCost | AfterCustomerFilterRemoval |
| --- | --- | --- | --- |
| 80 | 19 | 19 | 80 |

North plus South reconciles to the unrestricted 187 revenue and 44 cost in this complete fixture. That reconciliation does not replace testing each denied or unmapped identity separately.

Hand-derived role/context matrix only. No actual model publication or security enforcement was performed.

## A deeper model or scope review

A reviewable delivery folder should identify these independent artifacts:

| Artifact | Question it answers |
| --- | --- |
| CSV fixtures and typed model JSON | What rows, keys, relationships and policies are assumed? |
| DAX measure/reference source | Which expressions are being reviewed? |
| Named context/result matrix | What should those expressions mean under each case? |
| Source/model hashes | Which exact bytes does the reference describe? |
| Optional external execution record | What actually happened on a named engine/model/version? |
| Role and refresh acceptance records | Were the intended identity and data-lifecycle boundaries observed? |
| Qualified performance record | Were equivalent results measured under a representative controlled workload? |

The classroom supplies the first four for offline study. Its draft save, source comparison or completion marker does not manufacture the final three. An optional PBIP/TMDL project must follow the current supported external editing contract and exclude credentials, local caches and personal settings.
