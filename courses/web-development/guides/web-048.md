# web-048: Cookies, sessions and a request-to-request lifecycle

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-047`

## Learning objectives

Model session activity and expiry with explicit state transitions. Describe a real HTTP session acceptance test. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A cookie is a small value the browser stores and sends according to its scope and attributes. A common session design stores an unpredictable session identifier in a cookie and keeps application state on the server. The identifier is a bearer credential: possession may allow the server to associate a request with that session. Do not put sensitive application state into an unsigned client value and treat it as trusted.

Session lifetime involves creation, authentication transitions, inactivity, absolute expiry and logout. Regenerating the identifier after privilege changes helps address fixation, but safe concurrency and invalidation policies still matter. HttpOnly limits script access to a cookie, Secure restricts transport to HTTPS, and SameSite controls some cross-site sending behavior. These attributes support different defenses and do not replace authorization.

## Syntax anatomy and mechanism

Configure session behavior before session_start and before output. Prefer cookie-only identifiers and strict session handling. Real session storage can lock during a request, so write-close when the required state update is complete in applications that support concurrent requests. The CLI reference uses a pure state transition to demonstrate expiry; it does not claim to create or test a browser session.

## Classroom execution and offline inputs

Choose the **PHP CLI** worker in the classroom. The pad is staged as `main.php` and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write `<?php` at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

## Worked example / walkthrough

### Worked example 1: A session policy

This is server configuration for an external HTTP adapter.

```php
session_set_cookie_params(['httponly' => true, 'secure' => true, 'samesite' => 'Lax']);
ini_set('session.use_strict_mode', '1');
```

**Expected observation:** A real HTTPS deployment would apply the cookie policy before starting its session.

### Worked example 2: An explicit expiry rule

Time is supplied so the transition is testable.

```php
$expired = $now - $session['last_seen'] > 1800;
```

**Expected observation:** The inactivity policy is visible instead of relying on an unspecified browser lifetime.

## Debugging and common mistakes

Do not claim a session works because an array update passed. Secure cookies need HTTPS in the real deployment; a local HTTP teaching fixture must explain its different transport boundary. Never log live session identifiers.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain cookie, session identifier, session state without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
