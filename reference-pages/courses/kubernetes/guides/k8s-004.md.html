k8s-004: Identity, namespaces and explicit targeting#

Level and prerequisites#

Beginner; about 90 minutes plus review. Direct prerequisites: k8s-003.

Learning objectives#

Demonstrate the difference between a namespace and permission to act in it.

Vocabulary and concepts#

A Kubernetes request has a caller identity, a target API server, a resource scope and an action. Authentication establishes who the caller is. Authorization decides whether that identity may perform the requested verb on the resource. A namespace is a scope for many objects, not a complete security boundary by itself. Cluster-scoped objects such as Nodes and namespaces require separate permissions.

The course uses a private lease for one disposable cluster and namespace. Its namespace name, UID, owner marker and expiry must agree with fresh readback. A familiar name or a selected terminal context is not enough. Names can be reused after deletion, and an ambient kubeconfig can point somewhere unrelated.

This lesson is a reading and explicitly targeted host-observation worksheet. The browser can run a fixed workload under its lease, but it does not accept arbitrary authorization commands or Role manifests. The supplied Role is a real namespaced API example for inspection; it does not grant the learner permission to create roles.

Key terms#

  • RBAC: Role-based access control. A Role lists allowed verbs, API groups and resources inside a namespace, and a RoleBinding grants that Role to a subject.
  • Namespace: A scope that partitions most API object names and namespaced permissions within one cluster, so the same name can exist separately in two namespaces.
  • Caller identity: The authenticated user or ServiceAccount that sends a request. Authorization is decided for that identity, not for whoever typed the command.
  • Owned lease: The course's private reservation of one disposable cluster and namespace, which defines the only target a lab command may change.
  • Kubeconfig context: A named kubeconfig entry that combines a cluster, a user and a default namespace. Selecting it explicitly keeps a command from reaching whatever target was last active.

Read identity and RBAC without confusing scopes#

A Role lists allowed verbs, API groups and resources inside a namespace. A RoleBinding connects that Role to a user, group or ServiceAccount. A ClusterRole can describe cluster-scoped permissions or be bound into a namespace, while a ClusterRoleBinding grants its described scope across the cluster. These are different relationships, not synonyms for administrator access.

The example Role permits only get on the Deployment named hello. It does not permit listing every Deployment, creating a Deployment, reading Secrets or creating a namespace. Kubernetes authorization is additive: another binding could grant more, so a single Role file is not a complete proof of effective permissions. Inspect the actual identity and a self-authorization result in the owned environment.

A resourceNames restriction can constrain named get/delete requests. Creating a resource normally targets a collection before a name is available to authorization, so a resourceNames rule does not generally constrain create in the same way. The broker therefore combines namespace-scoped creation permission with a separate fixed-name manifest validator.

Follow an explicit target receipt#

Before a host observation, obtain the private kubeconfig path, context and namespace from the owned receipt. Use all three explicit flags on every kubectl call and fail if any is missing. The shared host-lab guide provides POSIX and PowerShell syntax. Never switch a default context to make the exercise work.

The namespace UID distinguishes the leased object from a same-name replacement. Compare it together with the owner marker before a mutation or cleanup. Lease expiry is another independent boundary: a valid-looking file does not authorize a run beyond its lifetime. The worker checks that the lease covers both work and cleanup reserve.

Credentials stay outside source, progress and exported evidence. Record nonsecret identity fields and the yes/no result of an authorization check, not the token or kubeconfig contents. A denied namespace creation or Secret read is expected least-privilege evidence in this course.

Worked example / walkthrough#

Worked example 1: Read a narrow Role#

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: lesson-reader
rules:
  - apiGroups:
      - apps
    resources:
      - deployments
    resourceNames:
      - hello
    verbs:
      - get

Expected: The only listed action is get on apps/Deployment hello in the binding namespace.

Worked example 2: Reject a same-name replacement#

Synthetic receipt: namespace lesson-a, UID ns-1, owner owner-a. Fresh observation: namespace lesson-a, UID ns-2, owner owner-a. The name and label match, but the UID does not.

Expected: The target identity is not established; no mutation or cleanup is authorized by this receipt.

Inspect the specific owned object#

Read only while this lesson's objects still exist (owned live reads).

Bash on Linux, macOS or Ubuntu under WSL 2:

From PowerShell, only open WSL 2 and run the Bash block there (why):

Compare metadata.namespace and metadata.uid with your receipt before trusting any kubectl auth can-i answer: a matching name with a new UID is the same-name replacement from Worked example 2. Forbidden on this get means the narrow Role grant is missing or bound elsewhere, which Exercise 4 records as an observed deny.

Exercises#

Exercise 1: Identify the request tuple#

Write the caller, namespace, API group, resource, name and verb for an owned hello Deployment read.

Expected result/shape: A six-field request includes apps/deployments, hello, get and the explicit leased namespace.

Verify: Rewrite the tuple as one kubectl auth can-i get deployments.apps/hello question with explicit --kubeconfig, --context and --namespace flags; each of your six fields must map to one part of that command.

Progressive hints: Separate the resource kind from its API plural and caller identity.

Exercise 2: Read the Role grant#

Compare get hello with list deployments and create namespaces under the example Role.

Expected result/shape: Only get hello is granted by this Role; list and namespace creation are absent.

Verify: For each of the three requests, find a single Role rule whose verbs, resources and resourceNames all match it; a request with no fully matching rule is not granted by this Role.

Progressive hints: Look at verbs, resourceNames and scope independently.

Exercise 3: Check namespace identity#

Compare the ns-1 receipt with the ns-2 readback.

Expected result/shape: Refuse despite the matching namespace name and owner label.

Verify: Decide using metadata.uid alone, then confirm that the matching name and owner label cannot change that decision.

Progressive hints: A name can be reused; the UID identifies this object instance.

Exercise 4: Observe least privilege#

With an explicitly provisioned lease, record an own-namespace permitted action and a denied cluster/Secret action.

Expected result/shape: Actual allow/deny results are recorded separately from source policy; no credentials enter the worksheet.

Verify: Each row of your record must name the verb, resource and namespace and the yes/no answer the server returned under the owned receipt; it must contain no token or kubeconfig text.

Progressive hints: Use the host guide targeting flags and a self-authorization check.

Exercise 5: Bind a ClusterRole inside one namespace#

A RoleBinding in namespace lesson-a references the built-in ClusterRole view. Predict whether the bound identity can list Pods in lesson-a, list Pods in lesson-b and list Secrets in lesson-a.

Expected result/shape: Pods in lesson-a: allowed. Pods in lesson-b: denied, because a RoleBinding grants only inside its own namespace. Secrets in lesson-a: denied, because the default view role excludes Secrets.

Verify: Check the binding's metadata.namespace and the resources listed by the view ClusterRole; a request outside that namespace or for a resource the role omits is denied.

Progressive hints: A RoleBinding may reference a ClusterRole, but the grant stays inside the binding's namespace.

Exercise 6: Explain additive authorization#

Describe why one narrow Role file cannot prove that no other privilege exists.

Expected result/shape: A written answer includes other RoleBindings/ClusterRoleBindings and actual effective authorization evidence.

Verify: Your answer must name at least one binding outside this Role file that could add a permission, and cite kubectl auth can-i --list under the owned receipt as the effective result.

Progressive hints: RBAC grants combine; absence from one file is not a global denial proof.

Self-check#

Why does a RoleBinding that references a ClusterRole still deny Pods in lesson-b, and what extra evidence would you need before saying the leased identity cannot list Deployments anywhere in lesson-a?

Common pitfalls#

Separate missing authentication, an expired lease, a wrong target UID and an authorization denial. They have different repairs. Retrying with an ambient administrator context would change the experiment and bypass the intended boundary. A successful own-namespace read does not prove cluster-wide permission, and a Role YAML file does not prove the server loaded that policy.

The offline checker models only the explicit permission matrix and receipt equality. It makes no API request. A live claim requires the actual owned identity, a fresh namespace readback and positive/negative authorization observations.

Retrieval and transfer#

Without the solution, rebuild the six-field request tuple for get on apps/deployments hello. Then explain how a second RoleBinding in the same namespace could widen the effective answer even though this Role grants only get.
