## Starting point and result

A user-defined function gives Spark a callable implementation for a scalar operation. A native column expression gives Spark an expression tree it already understands. Both can return correct numbers, but they expose different information to analysis and optimization. This lesson compares native squaring with a null-aware Scala UDF, then constructs stable softplus from native functions.

## Mechanism: semantic visibility and language boundaries

The native expression `col("x") * col("x")` is an arithmetic tree. A Scala UDF carries JVM function logic and input/output types, but its internal multiplication is generally opaque to SQL algebraic rewrites. A Python UDF additionally crosses a process and serialization boundary; Arrow can improve transport for supported forms without making the function's body a Catalyst expression.

Null behavior must be deliberate. The example uses boxed `java.lang.Double` in its UDF so a null can be observed and returned. An unexamined primitive signature can have different null-handling behavior. Neither null nor NaN should be casually equated with zero. Native multiplication propagates null, and the reference UDF implements the same policy.

Correctness comes before speed claims. A small local example with JVM startup, class loading and scheduling cannot establish which implementation wins at production scale. Inspect plans to understand boundaries, then benchmark representative data, distributions and resource settings with equivalent outputs.

## Worked case: null-aware square parity

The fixture contains -2, zero, two and null. The program selects the original value, native square and custom square. For each output row, both result columns must either be null or equal. The negative value tests sign behavior, zero tests a boundary and null tests the contract that a numeric-only fixture would miss.

`explain("extended")` reveals the custom function in analysis and what remains after optimization. A tiny local table may be evaluated during optimization, so inspect each plan separately. This is direct planning evidence. It does not show CPU instructions or prove vectorization. The function also remains a user implementation whose semantics the optimizer cannot generally infer from its name.

## Worked case: avoid a UDF for a known expression

Stable softplus is built from `greatest`, `log1p`, `exp` and `abs`. The fixture includes logits -1000, zero and 1000. Results are finite and match zero, log two and 1000 within floating-point representation. Because all operations already exist as native expressions, no custom extension is necessary.

A custom Catalyst expression becomes interesting when an operation genuinely lacks an adequate native form, when exact semantics need a reviewed implementation, or when measured overhead justifies maintenance cost. It should not be the first response to every unfamiliar formula. Introducing engine internals creates a version compatibility obligation that a public expression composition often avoids.

## Failure diagnosis

A UDF result that differs only on null rows usually indicates a signature or missing-value policy issue. A performance regression can come from serialization, lost predicate pushdown, repeated deserialization or inappropriate batch sizes. Inspect the actual plan and stage metrics. Do not diagnose every slow UDF as “Python is slow,” especially when the example is entirely on the JVM.

## Interview discussion

**Can a UDF use an automatic differentiation library internally?** Yes, within its process and supported computation. Spark does not then gain a derivative of the entire query or an optimizer over all partitions.

**Are native functions always fastest?** No universal statement follows. They usually offer useful optimization visibility, but actual performance depends on implementation, data and execution plan. Equivalent semantics and measurement are prerequisites for comparison.
