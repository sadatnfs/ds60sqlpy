# k8s-053: Ingress, HTTP routing and controller ownership

## Level and prerequisites

Advanced; about 120 minutes. Direct prerequisites: `k8s-052`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Draw the full Ingress-to-Pod request path.
- Compare Ingress and a Layer 4 Service.

## Purpose, vocabulary and mental model

Ingress describes HTTP and HTTPS routing intent to Services. It requires an Ingress controller that interprets the resource and implements a proxy path. Creating an Ingress object without a controller does not create a web server or make a hostname reachable.

A host rule matches the HTTP host name, while a path rule matches the URL path according to its pathType. Exact, Prefix and implementation-specific rules are not interchangeable. Prefix matching is based on path elements, not an arbitrary raw string startsWith rule. Rewriting paths is controller-specific behavior rather than a universal core Ingress feature.

The controller itself needs an exposure path, such as a load balancer or a deliberately mapped local port. DNS must point the chosen hostname at that entrypoint. An HTTP route can be configured correctly while public DNS or TLS is still wrong. Diagnose the request as a chain.

### Key terms

- **Ingress controller:** The proxy implementation that watches Ingress objects and actually routes traffic. Without one, Ingress rules do nothing.
- **Host rule:** An Ingress rule that matches requests by HTTP host name.
- **pathType:** The Ingress field that selects path matching: Exact for one path, or Prefix for matching path elements.
- **ingressClassName:** The Ingress field naming which controller should handle the Ingress.

## Mechanism and field-by-field reasoning

Use networking.k8s.io/v1 and specify ingressClassName when the prepared environment requires it. Each backend references a Service and a port in the API, not a Pod directly. That reference does not require every controller to send packets through the Service ClusterIP. A controller can derive eligible Pod endpoints and proxy to them directly, or use the ClusterIP according to its implementation and configuration. Traefik’s documented nativeLB option is one concrete example of these alternatives. The fixture uses a reserved example hostname and is manual-only.

Ingress remains a supported API, while Gateway API offers a more expressive role-oriented model. Neither choice installs its own controller. A learner should understand both the API contract and the selected implementation before relying on annotations.

## Trace the request or control path

```text
browser Host header -> controller listener -> host/path rule -> Service backend reference
actual upstream: direct eligible Pod endpoint OR Service ClusterIP path, by controller configuration
-> Pod listener -> application route
```

The first line is decided by an HTTP proxy, not by Kubernetes itself: it reads the Host header and path, then finds a backend reference. The second line is a choice the controller makes, sending to Pod endpoints directly or through the ClusterIP. The last line belongs to the application, which can still answer 404 for a path the proxy matched.

## Worked example / walkthrough

### Worked example 1: Read a namespaced backend rule

This is a fragment for an explicitly prepared controller.

```yaml
rules:
  - host: study.example.test
    http:
      paths:
        - path: /
          pathType: Prefix
          backend:
            service:
              name: network-study
              port:
                number: 80
```

**Expected observation:** The API backend references Service port 80. The controller may resolve it to Pod listener 8080 directly or route through the ClusterIP, according to its documented upstream mode.

### Worked example 2: Separate proxy route and app route

No rewrite is implied in this example.

```text
client GET /reports -> Ingress forwards /reports -> app receives /reports
app has only / -> app may return 404
```

**Expected observation:** A matched Ingress rule does not guarantee the application implements the forwarded path. The maintained original fixture serves /version with ds60-fixture-v1 plus a newline and /ready with ready plus a newline; / returns 404. Use /version for the positive routing check rather than expecting the root path to succeed.

## Six progressive exercises

### Exercise 1: Predict behavior with no Ingress controller.

**Expected evidence:** The object can exist without any serving proxy.

**Progressive hint:** An Ingress is data. Which process reads that data and turns it into a listening proxy?

### Exercise 2: Distinguish host and path matching.

**Expected evidence:** Host identifies the requested site; path identifies a route within it.

**Progressive hint:** One field selects the site, the other a route within it. Find both fields in ingress.yaml.

### Exercise 3: Draw the full Ingress-to-Pod request path.

**Expected evidence:** The Service backend reference and the actual configured upstream path are distinguished.

**Progressive hint:** After the rule matches, the backend is a Service reference. Draw both upstream modes from the diagram's second line.

### Exercise 4: Diagnose an app 404 after a matched prefix route.

**Expected evidence:** The forwarded path may not exist in the application.

**Progressive hint:** Prefix / matches every path. Does the app implement the path that was forwarded unchanged?

### Exercise 5: Explain why controller annotations are not universal.

**Expected evidence:** They belong to a particular implementation contract.

**Progressive hint:** An annotation is read by one controller's code. What does a different controller do with one it does not know?

### Exercise 6: Compare Ingress and a Layer 4 Service.

**Expected evidence:** Ingress interprets HTTP routing; the Service handles transport endpoint selection.

**Progressive hint:** Which layer reads the URL? A Service never looks past the TCP connection.

## Diagnosis, failure boundaries and common mistakes

A 404 is the most misread result in this lesson. If it carries the controller's default page, no rule matched, so check the Host header and the class. If it comes from the app, the rule matched and the app has no handler for that path; the fixture returns 404 for / by design, so test /version instead. Another error is creating an Ingress and waiting for traffic on a cluster with no controller; the object will sit there unchanged and nothing will report a failure. Copying nginx annotations into a Traefik setup, or the reverse, silently does nothing either.
