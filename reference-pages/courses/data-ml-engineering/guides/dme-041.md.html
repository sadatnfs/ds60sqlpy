dme-041: Batch and online inference as different contracts#

Level: Advanced | Prepared runtime: data-engineering

Direct prerequisites: dme-034, dme-036, dme-040.

Outcome: Compare real batch predictions with a local ASGI request contract.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

The model is only one part of a prediction product#

A fitted model maps features to outputs. A prediction product must also decide which inputs are eligible, which model version is active, how records are identified, what latency is acceptable and how results are retained. Batch inference processes a declared population, often from a versioned snapshot. Online inference handles individual requests under a service contract. They can share the same fitted computation while having different operational responsibilities.

Batch work often emphasizes completeness, throughput, retry-safe publication and population reconciliation. Online work often emphasizes bounded request validation, freshness, availability and response latency. Neither mode is automatically more correct. An online response can use stale features, and a batch run can accidentally omit a cohort. The contract should say what each mode promises and which common invariants must remain identical.

This chapter fits an actual scikit-learn logistic model and invokes it through both a batch function and a real FastAPI ASGI application. ASGI is the Python application interface used by the framework. The test client executes the application's request parsing, validation and handler logic in process. It does not start a TCP listener or qualify a reverse proxy, TLS, load balancer or multi-process deployment. The complete local ML service project covers the longer-lived HTTP surface separately.

Bind identity, feature order and two clocks#

Each observation has a request identity, two numeric features named load and backlog, an event hour and a known hour. The event hour describes when the measurement was observed. The known hour describes when that measurement became available. The decision hour is fixed at 48 in the fixture so outcomes are reproducible. The accepted condition is

Both conditions matter. A measurement observed long ago but arriving now is newly available, not newly observed. Checking only known time would make old data appear fresh. Conversely, a recent observation whose information arrives after the decision is unavailable at that decision. The point-in-time chapter develops this distinction in actual Feast retrieval; here the same rule protects the request boundary.

Pydantic validates the request structure, forbids unexpected fields and bounds numeric values. The batch function validates the same observation model before building a matrix in the reviewed order [load, backlog]. It accepts one to ten unique request identities. Responses include the request identity, probability, model version and decision hour so a consumer can reconcile outputs with inputs rather than trusting list positions alone.

Worked case 1: real fitted-model parity across two interfaces#

The synthetic training fixture contains eight rows with low-feature examples labelled zero and high-feature examples labelled one. It exists to make the inference path executable, not to establish a useful route-risk model. The earlier ML chapters cover train/evaluation separation and acceptance. This program uses the fitted model as a controlled mechanism for comparing interfaces.

example_one() scores two observations in a batch. A has load one and backlog one, observed at hour 46 and known at 48. B has load eight and backlog six, observed at 24 and known at 25. B is exactly at the accepted observation-age boundary. The same observations are then sent through the actual /predict ASGI route with the expected active model version.

The batch and request results match exactly in this execution. In the qualified native runtime, the probabilities are approximately 0.00102 and 0.99896. The program also calculates probabilities independently from the fitted coefficients:

Worked case 2: reject stale data and unavailable versions#

The second case changes one condition at a time. It submits an observation from hour 23 that only became known at hour 48. That is 25 hours old and is rejected with HTTP 422, despite its recent availability. It submits a known hour of 49, after the decision, and receives another 422. It asks for an unavailable model version and receives 409. It adds an unreviewed feature field and receives 422.

These failures are intentionally different from silently correcting the input. The service does not replace an unavailable model with whichever version happens to be loaded. It does not discard extra fields without telling the caller. It does not treat a stale feature as zero. Such fallback policies can be legitimate, but they must be separately defined, observable and evaluated. An implicit fallback changes the prediction product while retaining the appearance of success.

After the invalid requests, a valid baseline request still succeeds. Rejection has not mutated the model or corrupted application state. The result report records actual status codes, making the failure behavior as reviewable as the successful probability. A production caller should handle these statuses according to its business workflow, not retry every validation error indefinitely.

Complete worked program#

Use data-engineering. It fits a small model locally, executes actual batch and ASGI paths, publishes a result table and a compact failure report, and makes no external network requests.

"""Actual fitted-model batch/ASGI parity with explicit feature freshness and version checks."""

import math

import numpy as np
from fastapi import FastAPI, HTTPException
from fastapi.testclient import TestClient
from pydantic import BaseModel, ConfigDict, Field
from sklearn.linear_model import LogisticRegression

MODEL_VERSION = "route-risk-v1"
OBSERVATION_HOUR = 48


class Observation(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)
    request_id: str = Field(min_length=1, max_length=40, pattern=r"^[A-Za-z0-9_-]+$")
    load: float = Field(ge=0, le=20, allow_inf_nan=False)
    backlog: float = Field(ge=0, le=20, allow_inf_nan=False)
    event_hour: int = Field(ge=0)
    known_hour: int = Field(ge=0)


class Request(Observation):
    expected_model: str


def trained_model():
    features = np.array(
        [[0, 0], [1, 1], [2, 1], [3, 2], [6, 5], [7, 6], [8, 7], [9, 8]], dtype=float
    )
    labels = np.array([0, 0, 0, 0, 1, 1, 1, 1])
    return LogisticRegression(C=10, random_state=7).fit(features, labels)


def score(model, records):
    observations = [Observation.model_validate(record) for record in records]
    if not 1 <= len(observations) <= 10 or len({row.request_id for row in observations}) != len(
        observations
    ):
        raise ValueError("Use one to ten uniquely identified observations")
    if any(
        not row.event_hour <= row.known_hour <= OBSERVATION_HOUR
        or not 0 <= OBSERVATION_HOUR - row.event_hour <= 24
        for row in observations
    ):
        raise ValueError("Features must be known by decision time and observed within 24 hours")
    matrix = np.array([[row.load, row.backlog] for row in observations])
    probabilities = model.predict_proba(matrix)[:, 1]
    return [
        {
            "request_id": row.request_id,
            "probability": float(value),
            "model_version": MODEL_VERSION,
            "decision_hour": OBSERVATION_HOUR,
        }
        for row, value in zip(observations, probabilities, strict=True)
    ]


def application(model):
    app = FastAPI(docs_url=None, redoc_url=None, openapi_url=None)

    @app.post("/predict")
    def predict(request: Request):
        if request.expected_model != MODEL_VERSION:
            raise HTTPException(409, "The requested model version is not active")
        try:
            return score(model, [request.model_dump(exclude={"expected_model"})])[0]
        except ValueError as error:
            raise HTTPException(422, str(error)) from error

    return app


def fixture():
    return [
        {"request_id": "A", "load": 1.0, "backlog": 1.0, "event_hour": 46, "known_hour": 48},
        {"request_id": "B", "load": 8.0, "backlog": 6.0, "event_hour": 24, "known_hour": 25},
    ]


def example_one():
    model = trained_model()
    batch = score(model, fixture())
    with TestClient(application(model)) as client:
        online = [
            client.post("/predict", json={**row, "expected_model": MODEL_VERSION}).json()
            for row in fixture()
        ]
    assert batch == online
    independent = [
        1
        / (
            1
            + math.exp(
                -(
                    float(model.intercept_[0])
                    + sum(
                        float(weight) * row[name]
                        for weight, name in zip(model.coef_[0], ["load", "backlog"], strict=True)
                    )
                )
            )
        )
        for row in fixture()
    ]
    assert all(
        math.isclose(row["probability"], expected, abs_tol=1e-12)
        for row, expected in zip(batch, independent, strict=True)
    )
    assert batch[0]["probability"] < 0.5 < batch[1]["probability"]
    return {
        "batch": batch,
        "actual_asgi": online,
        "independent_logistic_formula": independent,
        "network_server_was_not_started": True,
    }


def example_two():
    model = trained_model()
    with TestClient(application(model)) as client:
        baseline = {**fixture()[0], "expected_model": MODEL_VERSION}
        changed = [
            ({**baseline, "event_hour": 23, "known_hour": 48}, 422),
            ({**baseline, "known_hour": 49}, 422),
            ({**baseline, "expected_model": "unavailable-v2"}, 409),
            ({**baseline, "unreviewed_feature": 10}, 422),
        ]
        observed = [client.post("/predict", json=payload).status_code for payload, _ in changed]
        assert observed == [expected for _, expected in changed]
        assert client.post("/predict", json=baseline).status_code == 200
    return {
        "stale_future_version_and_extra_field_statuses": observed,
        "valid_request_still_accepted": True,
    }


def main():
    from ds60sqlpy.plot_artifacts import publish_report, publish_table

    first, second = example_one(), example_two()
    print("Same accepted model through batch and request contracts:", first)
    print("Rejected conditions do not silently change the model:", second)
    publish_table(
        ["request_id", "probability", "model_version"],
        [[row["request_id"], row["probability"], row["model_version"]] for row in first["batch"]],
        description=(
            "Synthetic fitted logistic model: batch and ASGI predictions match by request identity."
        ),
    )
    publish_report(
        second,
        description=(
            "Observed HTTP contract failures for stale/future features, "
            "unavailable versions and extra fields."
        ),
    )


if __name__ == "__main__":
    main()

Operational differences that remain after parity#

Batch parity does not establish online capacity. A model that scores a million rows efficiently in one array may perform poorly when invoked through many tiny concurrent requests. Serialization, validation, feature retrieval, queueing and process startup can dominate a small model's arithmetic. Measure end-to-end latency at the consumer boundary and distinguish it from model-only execution time.

Online parity also does not establish batch completeness. A batch job needs the declared input count, rejected population, output count and stable identifiers. If one record fails validation, decide whether the whole batch is withheld, valid records are published with an explicit partial status, or invalid records enter quarantine. The function here rejects invalid input before scoring; a broader batch product needs a publication policy that matches its use.

Model activation should be explicit. Training a new model, registering it, loading it into a process and routing consumer requests to it are separate events. A response should identify the version that actually scored the request. If a client requires version 1 for reproducibility, returning version 2 with the same response schema is still a contract mismatch. Pinning and controlled rollout are developed in the delivery chapter and full service project.

Diagnose disagreement#

If batch and online predictions differ, compare exact model identity, feature names and order, transformations, types, missing-value handling and time cutoffs before changing model parameters. If outputs are associated with the wrong requests, inspect joins and positional assumptions. If recent arrivals pass despite old measurements, inspect the two clocks. If a new deployment changes all probabilities, check whether preprocessing or a different class column was selected.

If requests fail only outside the in-process client, inspect the real network and process boundary: binding, headers, payload limits, timeouts and proxy behavior. Passing the ASGI test is useful evidence about application logic, but it cannot explain every external transport failure. Preserve both evidence layers rather than using one to dismiss the other.

Applications and answered interview discussion#

This pattern applies to churn scores, demand risk, fraud review queues and recommendation features. A hybrid product might compute most scores in batch and refresh a subset online. It must define which result wins, how old a cached score may be and whether the two paths use equivalent feature and model contracts.

An interviewer may ask, “Can we reuse the training notebook as an API?” Explain the need to isolate fitted state, reviewed preprocessing, bounded inputs, version identity and operational behavior. If asked why online and batch must match, specify the shared inputs and model version; different feature-time contracts can legitimately produce different answers. If asked whether a successful API test proves production readiness, identify the untested network, concurrency, persistence and deployment boundaries.
