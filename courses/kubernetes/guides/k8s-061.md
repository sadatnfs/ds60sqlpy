# k8s-061: Topology, zones and locality-aware traffic

## Level and prerequisites

Advanced; about 120 minutes plus optional supervised host observations. Direct prerequisites: `k8s-060`. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

## Learning objectives

Design a two-zone failure scenario. Defend a locality tradeoff. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

## Purpose, vocabulary and mental model

A topology label describes placement, such as a node or availability zone. Locality-aware routing tries to prefer nearby endpoints to reduce latency or cross-zone traffic, subject to implementation and policy. It is a preference or constraint with tradeoffs, not a guarantee of balanced load or failure tolerance.

Spreading replicas across zones can improve resilience to a zone failure, but only if scheduling, storage and dependencies also span the required failure domains. A local preference can concentrate traffic on a small number of endpoints if placement is uneven. Capacity and availability must be considered together.

Topology features evolve with Kubernetes versions. Fields, hints and traffic-distribution semantics should be read for the actual release and data plane. The lesson teaches the reasoning with a synthetic two-zone example and does not promise that every local kind cluster can reproduce cloud-zone behavior.

## Mechanism and field-by-field reasoning

Separate workload placement from traffic selection. Topology spread constraints influence where Pods can be scheduled; Service routing policy influences which eligible endpoint a caller uses. One does not automatically configure the other.

For the synthetic example, zoneA has two ready app endpoints and zoneB has one. A local-only rule can overload the single endpoint in zoneB even when total cluster capacity appears sufficient. A failover policy must define what happens when a zone has no eligible local endpoint.

## Trace the request or control path

```text
scheduler placement -> endpoint distribution across nodes/zones
caller location + routing policy -> eligible/preferred endpoint set
capacity and failover behavior -> actual latency and availability
```

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

### Worked example 1: Compare two-zone capacity


**Expected observation:** Equal client counts do not imply equal load per endpoint under strict locality.

### Worked example 2: Separate placement and routing

Both decisions need their own configuration.

```text
spread constraint: where replicas may run
traffic preference: where a caller sends requests
failover rule: what happens when nearby endpoints are absent
```

**Expected observation:** A spread configuration alone does not prove local routing.

## Diagnosis, failure boundaries and common mistakes

The controlled failure in this chapter is: Diagnose local preference with insufficient nearby capacity. Its distinguishing result is Inspect endpoint distribution and actual load, not only total replicas. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
