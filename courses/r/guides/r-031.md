## Outcome and mechanism

Build an auditable table transformation whose row population, units and key alignment remain inspectable.

A data pipeline is easier to reason about when each stage has one observable purpose. Start with a typed input table and an explicit row grain. Validate its key, derive any needed fields, apply a documented eligibility mask, then choose an output order and schema. Keep the original input available so a reviewer can reconstruct each exclusion and transformation.

Filtering changes the population. A missing quantity, an invalid price and an intentionally excluded category are different reasons for a row not entering a total. A single final count cannot explain which rule removed which record. For a small pipeline, retain a row-level reason or separate masks; for a larger pipeline, retain bounded counts and representative diagnostics without exposing private data.

Column calculations must use aligned rows. The expression quantity * unit_price - discount computes one line amount from corresponding fields. Sorting only unit_price first would silently pair it with the wrong quantity. Apply permutations to entire data frames and preserve a stable line identifier in every intermediate output.

The transformation should not depend on incidental input order unless order is part of its meaning. Sorting the final output by the stable ID makes comparison reproducible, while testing a permuted input verifies that a commutative aggregate remains unchanged. A sequence-dependent feature, such as a lag, would need an explicit sort and tie-breaking rule before calculation instead.

## Read the syntax

Create named intermediate data frames and masks. Use stopifnot for key/type assumptions, complete logical masks for eligibility, and df[order(df$id),, drop=FALSE] for a deterministic record permutation. Avoid relying on row names as business keys.

## Worked examples

### Example 1: Compute before selecting a known population

```r
lines <- data.frame(id = c("L3", "L1", "L2"), quantity = c(2, 1, NA_real_), price = c(5, 8, 4), discount = c(1, 0, 0))
stopifnot(!anyNA(lines$id), !anyDuplicated(lines$id))
lines$net <- lines$quantity * lines$price - lines$discount
keep <- !is.na(lines$net) & lines$net >= 8
result <- lines[keep, c("id", "net"), drop = FALSE]
result <- result[order(result$id), , drop = FALSE]
stopifnot(identical(result$id, c("L1", "L3")), identical(result$net, c(8, 9)))
print(result)
```

**Expected observation:** L1=8, L3=9.

The missing quantity is excluded explicitly. The final row permutation preserves ID/amount alignment and makes the result deterministic.

### Example 2: A permutation-invariant total

```r
total_net <- function(data) {
  stopifnot(!anyNA(data$id), !anyDuplicated(data$id))
  amount <- data$quantity * data$price - data$discount
  stopifnot(all(is.finite(amount)))
  sum(amount)
}
lines <- data.frame(id = c("L1", "L2"), quantity = c(2, 3), price = c(4, 5), discount = c(1, 2))
stopifnot(total_net(lines) == 20, total_net(lines[2:1, ]) == 20)
print(total_net(lines))
```

**Expected observation:** 20 in either order.

The total is seven plus thirteen regardless of input row order. This invariant would not apply unchanged to a sequence-dependent lag calculation.
