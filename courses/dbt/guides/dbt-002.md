# dbt-002: Seeds, staging and rejected records

## Level and prerequisites

Beginner. Direct prerequisites: `dbt-001`

**Outcome:** Create a staging boundary with complete record accounting.

## Question and mechanism

A seed is a small versioned CSV resource loaded by dbt. It is useful for fixtures and stable reference data; it is not a general replacement for an ingestion system. A staging model then gives source fields deliberate names and types. These are separate boundaries: loading records establishes that they reached a relation, while staging defines how the analysis interprets them.

The first case loads three amounts and verifies their total after staging. The second introduces a malformed token and uses a deliberate permissive conversion with a rejection condition. The raw relation remains available, so accepted rows can be reconciled with the original input. A cleaned table alone would hide the missing contribution and its cause.

A staging layer should preserve enough identity to explain every decision. Do not silently convert bad text to zero or drop an identifier to make a model pass. For a production source, include an ingestion identity, schema version and rejection reason; the classroom fixture keeps the data small enough to inspect directly.

## Syntax and data contract

CSV files belong under seeds/ and are referenced with ref just like dependency-aware relations. A staging model can use explicit casts for mandatory fields and try_cast when a null result is part of a declared rejection policy. The SQL WHERE condition decides which records enter the accepted relation. Compare accepted and rejected counts against the raw seed relation.

## Worked case 1: Load and stage numeric records

The first project builds a seed and its dependent staging model, then queries the actual result. Explicit integer casts make the output contract visible. The manifest also confirms that the input is a seed resource.

**Expected evidence:** Three rows materialize and amount totals 21.

```python
import json
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def artifact(root, name):
    return json.loads((root / "target" / name).read_text())


def example_one():
    with tempfile.TemporaryDirectory() as d:
        p = project(
            d,
            models={
                "orders": (
                    "select id::integer as id, amount::integer as amount from "
                    "{{ ref('raw_orders') }}"
                )
            },
            seeds={"raw_orders": "id,amount\n1,5\n2,7\n3,9\n"},
        )
        invoke(p, "build")
        assert rows(p, "select count(*), sum(amount) from orders") == [(3, 21)]
        seed = artifact(p, "manifest.json")["nodes"]["seed.classroom.raw_orders"]
        assert seed["resource_type"] == "seed"
        return {"seed_rows": 3, "amount_total": 21}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Preserve a malformed input for diagnosis

The second case keeps the raw relation while accepting only successfully parsed amounts. The bad token's record is counted independently, so it cannot disappear from the accounting.

## Diagnose errors and misleading results

A seed can load successfully while a staging cast fails. Conversely, permissive SQL can succeed while excluding important records. Inspect the raw relation, parsed field and rejection count. Do not repair an error by silently widening every field to text or swallowing all conversion failures.

## Transfer to independent work

Create a staging boundary with complete record accounting. State which invalid inputs block publication and which are quarantined, then test both paths using identified records. The same contract will later protect model features from silent data changes.
