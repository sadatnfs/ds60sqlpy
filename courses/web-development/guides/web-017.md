# web-017: Responsive layouts and content-driven breakpoints

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-016`

## Learning objectives

Build a responsive course outline with a readable article. Explain why responsive design is more than media queries. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

Responsive design lets one document work across available sizes and user settings. A breakpoint is a condition where a layout needs to change, not a permanent name for a device. A phone can have a wide landscape viewport; a desktop window can be narrow. Start with content that works in a small space and add more complex arrangements only when enough room exists.

The viewport metadata tells mobile browsers to use the device's layout width rather than a historical wide page assumption. Flexible widths, wrapping and content-driven heights solve many problems before a media query is necessary. A responsive page must also survive enlarged text, translations and long values, not merely a list of screen widths.

## Syntax anatomy and mechanism

Use a base single-column layout and a min-width media query for a wider arrangement. Relative units in queries support a design tied to text scale. Inspect where the content becomes cramped and choose the breakpoint from that evidence. Keep the navigation visible or provide a fully accessible disclosure rather than simply hiding it on small screens.

## Worked example / walkthrough

### Worked example 1: A small-space baseline

The ordinary layout works without a query.

```css
.layout { display: grid; gap: 1rem; }
```

**Expected observation:** Sections stack in one column.

### Worked example 2: An evidence-based enhancement

Add a second column only when content has room.

```css
@media (min-width: 48rem) { .layout { grid-template-columns: 15rem minmax(0, 1fr); } }
```

**Expected observation:** The wider layout gives navigation a bounded column.

## Six progressive exercises

### Exercise 1: Predict the base layout below the breakpoint.

**Expected evidence:** The layout stays in one column.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Choose a breakpoint by resizing actual content.

**Expected evidence:** Record where labels or article width become uncomfortable rather than choosing a device name.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a responsive course outline with a readable article.

**Expected evidence:** The page adapts between stacked and two-column layouts without losing content.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a mobile page rendered as a tiny desktop screenshot.

**Expected evidence:** Check viewport metadata and inflexible widths.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test narrow width together with enlarged text.

**Expected evidence:** All controls and text remain reachable with no required two-axis page scrolling.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain why responsive design is more than media queries.

**Expected evidence:** Intrinsic sizing, wrapping, content order and user settings are fundamental parts of the behavior.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not hide essential actions just because space is limited. Avoid fixed viewport-height panels that trap content behind mobile browser chrome. Test actual text growth and settled layout.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain responsive design, media query, viewport without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
