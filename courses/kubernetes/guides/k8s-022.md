# k8s-022: Volumes, claims and stateful identity

## Level and prerequisites

Intermediate; about 120 minutes plus review. Direct prerequisites: `k8s-010`, `k8s-016`. The chapter separates desired configuration, API acceptance, controller observation and application evidence.

## Learning objectives

Distinguish Pod replacement, persistent data and a storage class's guarantees.

## Vocabulary and concepts

Persistent storage separates data lifetime from a particular Pod. A PersistentVolumeClaim requests storage through an access mode, capacity and StorageClass. A PersistentVolume represents provisioned storage and its lifecycle policy. A StatefulSet adds stable Pod identity and per-replica claim naming, but it does not turn a filesystem into a backup or a complete database recovery system.

The host fixture uses a prequalified StorageClass named lesson-local and a single-replica StatefulSet store. Its claim template data produces a claim associated with store-0. The example explicitly retains claims when the StatefulSet is deleted or scaled down. The normal browser adapter does not create PVCs, StatefulSets or storage classes.

A live persistence test writes a synthetic marker once, records its checksum, replaces the application Pod by exact UID and reads the marker through a separate bounded reader. Re-running an initializer that overwrites the same marker would hide data loss, so initialization and verification must be separate operations.

## Trace claims, volumes and stable identity

The claim requests 16Mi and ReadWriteOnce from lesson-local. That class must exist and be qualified before the lab; the learner does not install a provisioner or mount a personal host directory. A Pending claim can indicate missing class, capacity or binding topology rather than an application bug.

The StatefulSet uses serviceName store-headless and a headless Service for its stable network identity. Its template mounts the claim at /data. The claim template name and StatefulSet/ordinal contribute to the generated claim identity. A replacement Pod can retain the ordinal name while receiving a new Pod UID and reattaching the same claim.

ReadWriteOnce is a volume access-mode contract commonly associated with one node, not a universal promise that only one Pod can mount it. ReadWriteOncePod has different support requirements. Confirm the storage driver and topology rather than infer concurrency guarantees from the word once.

## Prove persistence and retention separately

Record the initial PVC/PV binding, Pod UID, marker bytes or synthetic checksum, and writer completion. After an owned Pod replacement, verify the new Pod UID, the intended same claim/PV relationship and unchanged marker hash. This establishes the observed Pod-replacement persistence path.

Deleting the PVC or StatefulSet introduces different lifecycle rules. The StatefulSet retention policy controls its claims under supported actions; the PV reclaim policy controls what happens to underlying storage after release. Retain can leave data requiring deliberate cleanup, while Delete can remove it through the provisioner. Neither is an independent backup.

The course cluster itself is disposable. A local volume retained inside a node may still disappear when that owned cluster/node is released. A data-retention claim must name the failure and lifecycle boundary it covers.

## Concrete finite marker operations

The separate [exclusive-create writer](../fixtures/k8s-022-marker-writer.json) and [read-only verifier](../fixtures/k8s-022-marker-reader.json) are host-only Job manifests. The writer opens `/data/marker` with mode `xb`, so an existing file causes failure instead of silently overwriting evidence. The reader requires the exact `persistent-demo` bytes followed by a newline and reports their SHA256. It never initializes data.

Both Jobs have one completion, no retry and a 60-second deadline. They use the fixed preloaded image and restricted nonroot settings. Required Pod affinity places them on the node hosting app=store, which makes the single-node ReadWriteOnce attachment assumption explicit; it does not create a storage class or guarantee scheduling. The reader mounts the claim read-only. Run initialization once, replace only the application Pod through the host operation, then run the independent reader. A second writer failure is the intended overwrite guard.

These commands are more general than the normal hello-task contract and are rejected by the browser adapter. Only the separately reviewed storage lease may bind ownership, submit them and clean their recorded UIDs. Their local code checks establish exclusive-write/read semantics, not live persistence.

## Common pitfalls

A healthy Pod or recreated constant file does not prove old data survived. Use a marker whose initialization is not silently repeated, and keep writer/read operations separate. A Bound PVC alone does not prove the application can read the intended bytes.

Do not delete a claim as a routine repair for a Pending Pod. Inspect binding, events, access mode and ownership first. Live storage operations remain unavailable until the host capability and retention choice are explicit.
