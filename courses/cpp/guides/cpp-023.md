## Learning objectives

Separate source compatibility from binary compatibility.

## Vocabulary and concepts

An API is the source-level interface callers use. An ABI is the compiled calling, layout and symbol convention needed to link binaries. C++ standard library objects are risky across independently compiled boundaries. A narrow C interface uses agreed primitive representations, explicit ownership and status codes to reduce coupling. This example uses platform int; a cross-platform serialized format needs its own fixed-width encoding contract.

<!-- terms:start -->

- **API:** the source-level interface that callers compile against.
- **ABI:** the compiled calling, layout and symbol conventions that separately built binaries need to work together.
- **`extern "C"`:** a linkage specification that gives a function C language linkage; it does not make C++ types or exceptions safe for C callers.
- **status code:** an integer result that reports success or a named failure separately from the output value.
- **output pointer:** a parameter through which the function writes its result, here only on success.

<!-- terms:end -->

## Syntax and mechanism

`extern "C"` requests C language linkage for symbols; it does not make arbitrary C++ types portable or safe. Keep exceptions inside the boundary. Rebuilding all dependents can resolve an API-compatible but ABI-incompatible change; a version string alone cannot prove compatibility.

## Trace the mechanism

The caller and library must agree on the function symbol and how its arguments/results cross the machine boundary. extern C reduces name-mangling ambiguity but does not specify all platform ABI details. The caller owns the output integer, while the function owns only the act of validating and assigning it. The overflow case returns before assignment, so the previous output value remains a useful check that failure did not publish a partial result.

<!-- depth:start -->
## C-compatible boundaries and error translation

A C-compatible function boundary is useful when code crosses a language or binary interface. extern "C" changes language linkage conventions for the named function; it does not automatically make every C++ parameter, exception or object layout safe for a C caller. The public signature should use a deliberately constrained representation and a documented ownership/error policy.

add_checked takes two integers and an output pointer, returning a status code. Status 0 means the output was written successfully; status 1 denotes a null output pointer; status 2 denotes signed-int overflow. Both failure paths return before assigning the output, so its previous value is preserved. The interface uses this platform's int representation, not a fixed-width wire format. A caller must check status before consuming the output. Returning an integer sum alone would leave no distinct channel for a failure if every integer value could also be legitimate data.

A null check can reject a missing pointer, but it cannot prove that an arbitrary nonnull pointer points to writable live storage. The caller still has a precondition to supply a valid output object. After an object is destroyed, a dangling address may remain nonnull. C-style interfaces therefore need precise lifetime and buffer-size contracts in addition to defensive null checks.

Exceptions must not escape a boundary that promises not to throw. A wrapper around potentially throwing C++ work should catch exceptions and translate them into the declared status result while preserving cleanup through RAII. noexcept is a promise enforced by termination if an exception escapes, it is not a catch block. Marking a function noexcept without controlling its implementation can make failure less recoverable.

The single-file program proves the illustrated call and error conventions within one C++ executable. It does not prove dynamic loading, ABI compatibility across compilers or successful use by another language. The later opaque-handle and host-library exercises add those boundaries separately. Keep source linkage, linker success and real foreign-consumer acceptance as distinct evidence.
<!-- depth:end -->

## Worked example / walkthrough

Example 1 calls `add_checked(2, 3, &out)` across a C-style boundary and gets status 0 with `out` set to 5. Example 2 passes `nullptr` for the output and gets status 1. The function reports misuse through its return code because an exception must not cross an ABI boundary. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-023-example-1.cpp)

```cpp
#include <cassert>
#include <iostream>
#include <limits>

extern "C" int add_checked(int a, int b, int *out) noexcept {
  if (!out)
    return 1;
  if ((b > 0 && a > std::numeric_limits<int>::max() - b) ||
      (b < 0 && a < std::numeric_limits<int>::min() - b))
    return 2;
  *out = a + b;
  return 0;
}
int main() {
  int out = 0;
  assert(add_checked(2, 3, &out) == 0 && out == 5);
  std::cout << "cpp-023 example 1 checks passed\n";
  return 0;
}
```

**Expected:** With assertions enabled, the program exits with status 0 and prints:

```text

```

extern "C" int add_checked(int a, int b, int *out) noexcept {

## Exercises

### Exercise 1: Separate interfaces

List the add_checked source contract and binary assumptions.

**Expected result/shape:** Names/types/statuses versus compiler/platform/linkage distinguished.

**Verify:** Check that your list puts the `int` parameters, the `out` pointer and statuses 0, 1 and 2 under the source contract, and `extern "C"` linkage, compiler and platform under binary assumptions.

**Progressive hints:** An ABI includes details the header alone cannot prove.

### Exercise 2: Call a valid boundary

Pass 2, 3 and a writable output integer.

**Expected result/shape:** Status 0 and output 5.

**Verify:** Initialize `out` to another value first, then assert `add_checked(2, 3, &out) == 0 && out == 5`, as Worked example 1 does.

**Progressive hints:** Caller owns the destination storage.

### Exercise 3: Reject null output

Pass nullptr for out.

**Expected result/shape:** Status 1, no invalid access.

**Verify:** Assert `add_checked(2, 3, nullptr) == 1`, as Worked example 2 does; the null check must come before any write through `out`.

**Progressive hints:** Validate pointers before dereference.

### Exercise 4: Repair exception leakage

Review a C wrapper that lets std::runtime_error escape.

**Expected result/shape:** Catch inside wrapper and map to a documented status.

**Verify:** Confirm the repaired wrapper catches inside the `extern "C"` function and returns a documented status; `noexcept` alone would call `std::terminate` instead.

**Progressive hints:** Foreign callers cannot assume a compatible exception runtime.

### Exercise 5: Check overflow

Call INT_MAX plus 1.

**Expected result/shape:** Status 2; no overflowing addition.

**Verify:** Assert `add_checked(std::numeric_limits<int>::max(), 1, &out) == 2` and that `out` still holds its previous value.

**Progressive hints:** Check arithmetic before evaluating it.

### Exercise 6: Transfer a shared library

Build the wrapper separately in an owned host project and record compiler/architecture.

**Expected result/shape:** Real link/load receipt plus matching header, no inferred portability.

**Verify:** Record `g++ --version` and `uname -m` next to the successful link and test run, and confirm the header declaration matches the definition's `extern "C"` signature.

**Progressive hints:** The browser single-file run does not exercise a shared-library ABI.

## Self-check

Why does status 0 mean the value 5 was published through the caller-owned pointer? For Example 2, explain why a null output pointer returns status 1 instead of throwing.

## Common pitfalls

If the caller reads output after a nonzero status, it may be using an old value. If a null check passes but access crashes, inspect lifetime and buffer validity rather than assuming nonnull means safe. If an exception crosses a C boundary, add translation at the boundary and preserve a stable error contract. If a symbol cannot be found during linking, check language linkage and the actual exported name separately from runtime pointer behavior.

## Retrieval and transfer
