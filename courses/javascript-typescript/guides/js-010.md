# js-010: Modules and dependency boundaries

## Level and prerequisites

Beginner, approximately 90 minutes. Direct prerequisites: `js-009`

## Learning objectives

Explain live binding, module namespace, resolution, module cache with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Import a mutable counter and its increment function, then inspect the count before and after incrementing. The final task tests respect namespace ownership.

## Purpose and mental model

A module is both a namespace and a dependency boundary. An ES module declares imports and exports before its body executes. The loader resolves dependencies, links the bindings, then evaluates the graph. An imported binding observes the exporting module's current binding; it is not a copied snapshot. Importing the same resolved module URL again normally returns the cached module namespace and does not repeat its initialization.

Node uses .mjs to select ES module syntax explicitly. Relative imports require the intended filename extension. Bare package names use package resolution rules; node: names identify built-in modules. CommonJS uses a different export object and loading model. Interoperability is useful, but guessing that an arbitrary CommonJS property will become a named ES export is fragile. This lesson imports a CommonJS default export deliberately and keeps ESM bindings explicit.

The fixtures create tiny source files in a newly allocated temporary directory, import them, and remove only that directory afterward. They do not install a package or edit the repository. Unique directory URLs avoid accidental cache sharing between exercises. A production module should usually avoid expensive side effects at import time: top-level file writes, network requests or background listeners make dependency loading itself operational work.

## Vocabulary and concepts

**Live binding:** An imported name observes updates made to the exporting binding.

**Module namespace:** The read-only view of a module's exported bindings.

**Resolution:** Mapping a module specifier to the module that will be loaded.

**Module cache:** Reuse of an already loaded module for its resolved identity.

## Syntax anatomy and execution trace

An export declaration exposes a binding. import() returns a Promise for the module namespace, so asynchronous loading must be awaited. pathToFileURL converts a platform filesystem path to a correctly encoded file URL; concatenating file: with a raw path fails for spaces and reserved characters. A namespace property cannot be reassigned by the importer, although exported functions may update their own module state. finally runs cleanup after success and after an import rejection.

## Worked example / walkthrough

### Example A: Observe a live binding

The importer receives a binding view. Copying count into a local number would instead preserve the value read at that moment. The distinction becomes visible only after the exporter changes state.

```javascript
import { strict as assert } from 'node:assert';
import { mkdtemp, writeFile, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
import { pathToFileURL } from 'node:url';

async function withModules(files, use) {
  const directory = await mkdtemp(join(tmpdir(), 'course-modules-'));
  try {
    for (const [name, source] of Object.entries(files))
      await writeFile(join(directory, name), source, 'utf8');
    return await use(directory);
  } finally {
    await rm(directory, { recursive: true, force: true });
  }
}

export async function verify() {
  // Worked example
  {
    await withModules(
      { 'counter.mjs': 'export let count = 0; export function increment() { count += 1; }' },
      async (directory) => {
        const module = await import(pathToFileURL(join(directory, 'counter.mjs')).href);
        assert.equal(module.count, 0);
        module.increment();
        assert.equal(module.count, 1);
      },
    );
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));
```

**Expected:** count changes from 0 to 1 through the imported namespace.
### Example B: Resolve a relative dependency

The relative path is resolved from the importing file, not from the process working directory. Naming the .mjs extension makes the loader contract explicit.

```javascript
import { strict as assert } from 'node:assert';
import { mkdtemp, writeFile, rm } from 'node:fs/promises';
import { tmpdir } from 'node:os';
import { join } from 'node:path';
import { pathToFileURL } from 'node:url';

async function withModules(files, use) {
  const directory = await mkdtemp(join(tmpdir(), 'course-modules-'));
  try {
    for (const [name, source] of Object.entries(files))
      await writeFile(join(directory, name), source, 'utf8');
    return await use(directory);
  } finally {
    await rm(directory, { recursive: true, force: true });
  }
}

export async function verify() {
  // Worked example
  {
    await withModules(
      {
        'math.mjs': 'export const twice = value => 2 * value;',
        'main.mjs': "import { twice } from './math.mjs'; export const answer = twice(4);",
      },
      async (directory) => {
        const module = await import(pathToFileURL(join(directory, 'main.mjs')).href);
        assert.equal(module.answer, 8);
      },
    );
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));
```

**Expected:** answer equals 8.

## Prediction before your attempt

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

## Progressive hints

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
