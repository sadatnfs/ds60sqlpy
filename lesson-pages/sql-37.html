A beginner's mental model for this lesson#

A partitioned table such as big_events holds no rows itself. It is a router: every insert is sent to the one child table whose bound contains the row's event_time, and every query is answered by the children the planner keeps. The children are ordinary tables, so you can count them directly or ask any row where it lives with tableoid::regclass.

The learner load steps forward 83 minutes per row from midnight on January 1, which places 537 rows in big_events_2025_01 and 463 in big_events_2025_02; the last one lands on February 27 at 15:20 UTC. The two planned counts differ only in their upper bound. Mid-January to mid-February crosses the partition line and returns 538. Stopping on January 20 keeps the range inside one child and returns 87.

A partition bound decides placement, and partition pruning is the planner reading those bounds against your WHERE clause. Pruning needs the raw key: WHERE date_trunc('month', event_time) = '2025-01-01' still scans both children, because the planner cannot invert the function to compare it with a bound. Rewrite it as a half-open range on event_time and February disappears from the plan.

Two worked SQL examples#

Example 1: a range that needs both partitions#
EXPLAIN ANALYZE
SELECT
  COUNT(*)
FROM
  big_events
WHERE
  event_time >= timestamptz '2025-01-15 00:00:00+00'
  AND event_time < timestamptz '2025-02-15 00:00:00+00';

How to read it: the half-open range [2025-01-15, 2025-02-15) overlaps the January partition [2025-01-01, 2025-02-01) and the February partition [2025-02-01, 2025-03-01). The planner therefore keeps both partitions under one Append node and applies the Filter inside each scan. The literals carry an explicit +00 offset, so the result does not depend on the session time zone.

Expected result/shape: EXPLAIN ANALYZE prints one text column, QUERY PLAN. On the course seed it shows an Append with two scans: big_events_2025_01 with actual ... rows=295 and big_events_2025_02 with actual ... rows=243. Running the query without EXPLAIN returns one row whose count is 538.

Example 2: a January-only range is pruned#
EXPLAIN ANALYZE
SELECT
  COUNT(*)
FROM
  big_events
WHERE
  event_time >= timestamptz '2025-01-15 00:00:00+00'
  AND event_time < timestamptz '2025-01-20 00:00:00+00';

How to read it: the only change is the upper bound. No February timestamp can satisfy event_time < '2025-01-20', so the planner removes big_events_2025_02 before execution. This is partition pruning: the evidence is the partition name that is missing from the plan, not a faster timing.

Expected result/shape: the plan has no Append node and one scan, Seq Scan on big_events_2025_01, with actual ... rows=87. Running the query without EXPLAIN returns one row whose count is 87.

Vocabulary and concepts#

  • Partition bound: the lower-inclusive, upper-exclusive range accepted by a partition.
  • Partition pruning: planner or executor removal of irrelevant partitions.
  • Sharding: routing data across separate databases or servers.

Deep dive and reference#

What you will learn#

  • Create range partitions and verify partition pruning.
  • Add partition-local indexes and compare access plans.
  • Distinguish in-database partitioning from cross-database sharding.

How the learner script works#

The rollback-only demo creates big_events partitioned by event_time, with January and February 2025 partitions. It inserts 1,000 deterministic rows, one every 83 minutes (537 in January and 463 in February), then plans a January-15-to-February-15 count that needs both partitions and a January-only count that prunes February.

Partition pruning removes partitions whose bounds cannot satisfy a predicate. Use the raw partition key in sargable ranges. Partitioning is primarily a data management and scale technique; it does not guarantee a faster small-table query.

Partitioning versus sharding#

  • Partitioning divides one logical table inside one PostgreSQL database.
  • Sharding routes data across databases or servers and changes joins, transactions, failure handling, and operations.
  • The learner script demonstrates partitioning only. “Sharding” remains an architecture discussion, not a runnable course setup.

Practice map#

The exercises switch to a second table, solution_events, so your answers never collide with the demo. Its loader steps 47 minutes per row over a 120-day window and wraps once after about row 3,676, so January ends up with 1,899 rows while March has 950 and April 919. Expect lopsided months, and use the March count of 950 as your anchor across the first three prompts.

Pitfalls and validation#

  • PostgreSQL range bounds are lower-inclusive and upper-exclusive.
  • An inserted row with no matching partition fails unless a default partition exists.
  • Too many tiny partitions increase planning and maintenance overhead.
  • An index created on the partitioned parent is created on every partition, including partitions attached later; each partition stores its own physical index. CREATE INDEX CONCURRENTLY cannot target the parent, so large online builds use CREATE INDEX ... ON ONLY plus ALTER INDEX ... ATTACH PARTITION.
  • All demo tables and indexes disappear at the learner script's ROLLBACK.

Expanded practice lab#

Prompts 3-6 turn partition pruning into observable evidence. Compare plans with and without the partition-key predicate and inspect tableoid::regclass to see physical row placement. Add the DEFAULT partition only after observing the helpful “no partition found” error for an uncovered date.

Range bounds are [FROM, TO): midnight on February 1 belongs to the February partition, not January. A DEFAULT partition improves ingest availability but also needs monitoring so unexpected dates do not accumulate unnoticed.

Day 37: Solutions: Partitioning#

How to study and run this solution#

Attempt the six prompts against your own copy first; the comparison is only useful once you have predicted which partitions each plan touches. Then run the executable answer, which builds solution_events, works all six exercises in one transaction and ends with ROLLBACK (reading solutions):

psql -X -v ON_ERROR_STOP=1 -d advanced_sql_training \
  -f sql/postgres-60day/solutions/day37_solutions.sql

Every plan prints as a QUERY PLAN column, and the evidence is which child names appear. Timings and buffer counts change from run to run, but the scan list and the actual ... rows= values stay fixed because the load is deterministic.

How these answers fit together#

The learner script proved pruning on two months. These answers repeat that on four months and then probe the edges: an index on the parent that fans out to every child, a row dated June that no named partition covers, and a row placed exactly on the February 1 line.

The 5,000-row load is uneven on purpose. Row n lands (n * 47) % 172800 minutes after New Year, and once n * 47 passes the 120-day mark the offsets restart at January 1. The final row counts by tableoid::regclass are 1,899 for January, 1,233 for February (1,232 from the load plus the boundary row), 950 for March, 919 for April and 1 for the DEFAULT partition. Each child keeps its own (customer_id, event_time) index, which is why the customer 42 lookup in March reads a single small index and returns two rows.

All of this is single-database partitioning. Sharding would place these children on different servers, where a cross-month count becomes a distributed query; nothing here sets that up.

Exercise 1: Add a partition and test pruning#

  event_time timestamptz NOT NULL,
  customer_id int,
  payload jsonb
)
PARTITION BY RANGE (event_time);

CREATE TABLE solution_events_2025_01 PARTITION OF solution_events
FOR VALUES FROM ('2025-01-01 00:00:00+00') TO ('2025-02-01 00:00:00+00');

CREATE TABLE solution_events_2025_02 PARTITION OF solution_events
FOR VALUES FROM ('2025-02-01 00:00:00+00') TO ('2025-03-01 00:00:00+00');

CREATE TABLE solution_events_2025_03 PARTITION OF solution_events
FOR VALUES FROM ('2025-03-01 00:00:00+00') TO ('2025-04-01 00:00:00+00');

CREATE TABLE solution_events_2025_04 PARTITION OF solution_events
FOR VALUES FROM ('2025-04-01 00:00:00+00') TO ('2025-05-01 00:00:00+00');

INSERT INTO solution_events (event_time, customer_id, payload)

  timestamptz '2025-01-01 00:00:00+00' + ((n * 47) % (120 * 24 * 60)) * interval '1 minute',
  1 + ((n * 19 - 1) % 500),
  jsonb_build_object('source_row', n)

  ANALYZE,
  BUFFERS

SELECT
  COUNT(*)
FROM
  solution_events
WHERE
  event_time >= timestamptz '2025-03-01 00:00:00+00'

Reasoning and verification#

Pitfalls#

  • Partition bounds are lower-inclusive and upper-exclusive.
  • An insert outside all bounds fails unless a default partition exists.
  • Put the partition key in filtering predicates so pruning is possible.
  • Too many tiny partitions increase planning and maintenance overhead.
