## The question and the mechanism

Separate an expression's semantics, model cardinality and observed engine performance.

DAX performance involves both expression evaluation and the storage operations serving it. Formula-engine work coordinates expressions and intermediate results; storage-engine work can scan and aggregate encoded columns. This is a useful conceptual split, not a promise that a source function maps to exactly one physical operation in every engine version or storage mode.

Column cardinality is one input to model size and work. ProductKey has three distinct values across eight Sales rows, while SaleID has eight distinct values. Repeated low-cardinality attributes and unique identifiers have different encoding opportunities. The actual memory cost also depends on type, ordering, compression, dictionaries and engine implementation, so row and distinct counts do not themselves measure bytes.

A star schema stores descriptive product attributes separately from fact events. That can support clear filtering and reduce repeated descriptive data, but semantic correctness comes first. Do not remove a necessary unique fact key or meaningful precision merely to reduce cardinality. An optimization claim needs a defined workload, equivalent results and actual measurements on the intended model.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

### Case A: Fact-column cardinalities

**Starting context:** Clean retail fact; no filters; counts describe source cardinality, not physical scan metrics.

```dax
EVALUATE ROW ( "SalesRows", COUNTROWS ( Sales ), "ProductKeys", DISTINCTCOUNT ( Sales[ProductKey] ), "OrderDates", DISTINCTCOUNT ( Sales[OrderDate] ), "SaleIDs", DISTINCTCOUNT ( Sales[SaleID] ) )
```

**Context trace:**

1. There are eight unique sale lines.
2. Three product keys repeat across them, and S1/S2 share one order date.
3. Distinct counts are 3 products,7 order dates and 8 SaleIDs.

**Hand-derived worked-reference result:**

| SalesRows | ProductKeys | OrderDates | SaleIDs |
| --- | --- | --- | --- |
| 8 | 3 | 7 | 8 |

A unique identifier has high cardinality here because it preserves necessary line identity. Its cost must be weighed against correctness and lineage requirements.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Dimension attributes have another grain

**Starting context:** Product dimension, including the unsold Bag member.

```dax
EVALUATE ROW ( "ProductRows", COUNTROWS ( Product ), "Categories", DISTINCTCOUNT ( Product[Category] ), "Colors", DISTINCTCOUNT ( Product[Color] ) )
```

**Context trace:**

1. Four product rows describe four catalog keys.
2. Categories are Paper,Home,Travel and colors are Blue,Red,Green.
3. The dimension's domain includes valid attributes absent from current sales.

**Hand-derived worked-reference result:**

| ProductRows | Categories | Colors |
| --- | --- | --- |
| 4 | 3 | 3 |

A dimension count is not inferred from fact activity. Removing unsold members to shrink a model can change the intended reporting population.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Its key must be unique at the declared grain.
2. Keep the mapping and relationship semantics intact.
3. Separate correctness, workload and measurement.
4. Source syntax is not a complete physical plan.
5. The key supports row identity, duplicate detection and context-transition reasoning.
6. Precision can create many distinct values but may be analytically required.
