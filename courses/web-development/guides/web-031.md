# web-031: PHP begins: interpreter, CLI and server execution

## Level and prerequisites

Beginner; allow about 90 minutes, with extra time for independent practice. Direct prerequisites: `web-001`, `web-009`

## Learning objectives

Write a PHP program that prints a study topic and computed duration. Compare the CLI lifecycle with a server request lifecycle. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

PHP is a programming language whose interpreter executes source instructions. In the classroom, a Linux CLI worker runs one file and captures its output. On a web server, a PHP runtime can instead receive request context and produce an HTTP response. These environments share language syntax but expose different inputs and lifecycle behavior. Printing a string that looks like HTML does not turn a CLI process into a web server.

PHP source begins with an opening tag, and statements commonly end with semicolons. Variables begin with a dollar sign. A comment explains source without executing it. Echo writes output; it does not return a value from a function or save data to a database. We start with literal strings and a tiny computed value so each step is visible.

## Syntax anatomy and mechanism

Use a pure PHP file beginning with `<?php`, followed by `declare(strict_types=1);` before other statements. Strict typing affects certain scalar type coercions at function call boundaries; it does not turn PHP into a statically typed language. Omit the closing tag in a pure PHP file to avoid accidental trailing output. Syntax errors occur before the intended program can run, while runtime errors occur during execution.

## Classroom execution and offline inputs

Choose the **PHP CLI** worker in the classroom. The pad is staged as `main.php` and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write `<?php` at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

## Worked example / walkthrough

### Worked example 1: First output

A string literal becomes text in stdout.

```php
<?php
echo "Hello, classroom.\n";
```

**Expected observation:** One greeting line appears in the CLI output.

### Worked example 2: A named value

A variable makes the data's role explicit.

```php
$minutes = 30;
echo "Planned minutes: " . $minutes . "\n";
```

**Expected observation:** The dot operator concatenates the label and value.

## Six progressive exercises

### Exercise 1: Predict which characters in the greeting source appear in output.

**Expected evidence:** The opening tag and echo keyword do not appear; the string content does.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Change the planned minutes while preserving the label.

**Expected evidence:** Only the numeric portion changes.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Write a PHP program that prints a study topic and computed duration.

**Expected evidence:** The program runs in the CLI worker and produces two clearly labeled values.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a missing semicolon as a parse error.

**Expected evidence:** The interpreter cannot execute the intended statement sequence until syntax is repaired.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Print literal angle brackets and explain the output surface.

**Expected evidence:** The CLI displays text; it does not automatically render a web page.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Compare the CLI lifecycle with a server request lifecycle.

**Expected evidence:** A CLI process receives its prepared inputs; a server integration supplies HTTP context and response handling.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not paste PHP into an HTML-only preview expecting a server interpreter. A closing tag can introduce accidental whitespace output. Keep a syntax failure separate from a successful execution that produced the wrong value.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain PHP, interpreter, CLI without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
