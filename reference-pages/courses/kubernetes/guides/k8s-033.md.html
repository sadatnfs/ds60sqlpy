k8s-033: Autoscaling with a qualified metrics path#

Level and prerequisites#

Advanced; about 135 minutes plus review. Direct prerequisites: k8s-010, k8s-027, k8s-032. The chapter separates desired configuration, API acceptance, controller observation and application evidence.

Learning objectives#

Relate resource requests, measured load and stabilization to an HPA decision.

Vocabulary and concepts#

Horizontal Pod Autoscaling changes a workload's desired replica count using observed metrics and a declared target. It is a feedback loop: measure, compare, choose a desired count, then wait for workload and metrics observations to reflect the change. The extra Pods are not instantaneous capacity, and CPU load is not the same thing as business demand or response-time quality.

This example uses CPU utilization relative to CPU requests. If a Pod requests 100m and uses50m, its utilization for that resource is50 percent. Changing the request to200m while leaving usage 50m changes the ratio to25 percent. A request is therefore part of the autoscaling model as well as a scheduling input. An absent metric is unavailable evidence, not a zero-load observation.

The supplied HPA uses autoscaling/v2, targets Deployment hello, and limits replicas to1 through 2. It requires a qualified metrics API path and a host-provided bounded load generator. The basic module fixture has no such qualification. Its fast HTTP handler is useful for service checks, but arbitrary traffic against it must not be presented as a reliable CPU scaling experiment.

Derive the simple recommendation#

For a complete, current metric sample, a useful first model is desired=ceil(currentReplicas*observedUtilization/targetUtilization). currentReplicas is a count, observed and target use the same percentage units, and ceil rounds upward to a whole Pod. At one replica, observed 80 and target 50 yield ceil1.6=2. At two replicas, observed 20 and target 50 yield ceil0.8=1.

The configured min/max then constrain the recommendation. One replica at 200 percent would suggest4 before the maximum clips it to2. The clip is an important signal: the policy may have reached its budget while demand remains unmet. A stable replica count at the maximum is not evidence of sufficient capacity.

The real controller includes tolerance, readiness/missing-metric treatment, stabilization and scaling policy rules. The checker below deliberately models only the complete-data proportional calculation and range clamp. It must not be used to predict an exact timestamp or every live HPA decision.

Read the manifest and feedback delay#

scaleTargetRef names the object whose scale subresource the HPA controls. minReplicas and maxReplicas bound that desired count. The Resource metric uses cpu and target type Utilization, so the percentage is tied to requests. Metrics that represent raw values or custom external demand have different semantics and must not be substituted without redefining the equation.

The scaleDown behavior keeps a60-second stabilization window and limits reduction to one Pod per60 seconds. This reduces rapid shrink/grow oscillation in the teaching contract. It does not guarantee a scale-down at exactly second 60, because collection, controller reconciliation, readiness and policy timing also matter.

A load step can first raise usage, then trigger a recommendation, then cause scheduling/startup, then distribute load across ready replicas. Record these observations separately. If new Pods are Pending or unready, the desired count can increase without useful serving capacity. Check response failures and latency alongside CPU and replica status.

Worked example / walkthrough#

Worked example 1: Compute and clamp a recommendation#

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hello
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hello
  minReplicas: 1
  maxReplicas: 2
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60
      policies:
      - type: Pods
        value: 1
        periodSeconds: 60

With one replica and80 percent utilization against50 percent, the ideal count is2. With200 percent, ideal4 is limited to maximum 2.

Expected: Both cases request at most2; the second remains potentially capacity-limited.

Common pitfalls#

Use the host-provided fixed load duration, request concurrency and stop limit in an exclusive lease. Record metrics API health, per-Pod requests, sample timestamps and HPA conditions. Define a permissible range and deadline rather than an exact transition second. Stop if the load exceeds the lesson resource budget or the target identity changes.

If metrics are missing, preserve the unavailable condition and fix the qualified measurement path. Do not report zero utilization, remove resource requests to silence a warning or install a metrics component from the learner pad. A single successful scaling step does not establish production sizing, cost efficiency or stability under all workloads.
