nlp-003: Regular expressions and explainable extraction#

Level and prerequisites#

Beginner NLP; about two hours. Direct prerequisites: nlp-001 and nlp-002. You should understand immutable text versions, code-point offsets and the difference between a document and an extracted entity. This chapter uses only Python's standard-library re module.

Extraction starts with an output contract#

Suppose an analyst needs invoice references from support messages. A generative model could produce a plausible invoice number that never appeared in the message. A regular expression offers a different mechanism: it selects substrings that satisfy an explicit pattern. This makes the origin of each result inspectable, but does not guarantee that every match is a real invoice or that every invoice mention matches the pattern.

For this chapter, the annotation policy accepts an ASCII prefix INV in any ordinary ASCII letter case, followed by a hyphen and exactly four ASCII digits. The all-zero number is invalid. A reference must not be embedded in a larger word. Return the raw matched text, its canonical identifier, and a half-open [start, end) span into the unchanged source string. The first pattern intentionally implements only part of that policy so we can measure its errors.

A regular expression describes a set of matching sequences. A match object contains the observed substring, captures and offsets for one match. A capture group selects a subpart of the match. Extraction precision asks what fraction of predicted entities are correct; recall asks what fraction of the annotated entities were found. The unit here is an exact entity span inside a particular document, not a document label.

A rule can be useful without being a complete language understanding system. It might reliably extract a tightly specified reference from a log while failing on a natural-language paraphrase. A subject-matter assistant should preserve this distinction. An extracted ID is evidence of a matching string, not evidence that a referenced invoice exists, is authorized for the current user or has the status described in the surrounding sentence.

Work through the pattern one symbol at a time#

Start with r"\bINV-(?P<number>[0-9]{4})\b".

The r prefix asks Python to create a raw string literal, so backslashes can reach the regex engine without being interpreted as ordinary Python escapes. It does not disable the regex language. \b is a word boundary. INV- matches literal characters. (?P<number>...) creates a named group. [0-9] permits an ASCII digit, and {4} requires exactly four repetitions. The closing boundary helps reject a four-digit prefix inside a longer word-like identifier.

In Python's default string regex mode, word boundaries use Unicode word-character behavior. Underscores are word characters. This means a reference embedded in _INV-1042 does not begin at a word boundary. This may be desirable for this contract, but another log format might treat underscores as delimiters. Test the actual boundary policy instead of assuming that “word” means a linguistic word in every language.

Using [0-9] is deliberate. A shorthand such as \d can match Unicode decimal digits, including forms outside the ASCII invoice specification. A more permissive pattern is not automatically more correct. The correct behavior follows from the domain's representation contract.

Worked example: keep offsets and captures#

import re

text = "Pay INV-1042, then review INV-9012."
pattern = re.compile(r"\bINV-(?P<number>[0-9]{4})\b")
for match in pattern.finditer(text):
    print(match.group(0), match.group("number"), match.span())
    assert text[match.start():match.end()] == match.group(0)

Expected matches are INV-1042 at (4, 12) and INV-9012 at (26, 34). The named groups are the strings 1042 and 9012. Retaining digits as strings preserves leading zeros. An identifier is not necessarily a number on which arithmetic is meaningful.

finditer yields match objects, so it retains span information. findall can return captured groups rather than the complete match when the pattern contains captures. If you change a pattern's grouping and your extraction output changes shape, inspect that API contract. Do not silently guess which tuple field is the canonical identifier.

Compile the pattern once when applying it repeatedly. This makes the rule a named object that can be tested and passed to a function. It is not evidence that the rule has been optimized or that it is safe on every possible input. The present pattern uses bounded repetition and no nested ambiguous repetition; later production rules need their own complexity review and input limits.

Search, match and full match answer different questions#

search looks for a match somewhere in a string. match starts at the beginning. fullmatch requires the entire input to satisfy the pattern. A message containing an invoice should normally be searched. A field that claims to contain only an invoice ID should normally be validated with fullmatch plus any semantic rules.

import re

pattern = re.compile(r"INV-[0-9]{4}")
print(pattern.search("ticket: INV-1042") is not None)
print(pattern.match("ticket: INV-1042") is not None)
print(pattern.fullmatch("INV-1042") is not None)
print(pattern.fullmatch("INV-1042 extra") is not None)

Expected: True, False, True, False. A validator based on search would accept the last string because it contains an ID somewhere. That would implement an extraction contract instead of a field-validation contract. The distinction matters when the extracted value later becomes a database key or an API argument.

Syntax can match while domain meaning fails#

The first pattern accepts INV-0000, although the stated domain policy rejects an all-zero identifier. It also misses inv-7777, although the policy accepts ordinary ASCII case variants. These are useful errors because they expose two different layers: representation matching and semantic validation.

Keep the layers understandable. Match candidate spans, then reject the forbidden numeric string in ordinary Python. Extend only the prefix's permitted letter cases, leaving the source text unchanged. A pattern using [Ii][Nn][Vv] expresses the exact ASCII alternatives. Avoid normalizing the whole document first if the output needs offsets into the raw version.

import re

pattern = re.compile(r"\b[Ii][Nn][Vv]-(?P<number>[0-9]{4})\b")
text = "INV-0000, inv-7777 and INV-10420"
records = []
for match in pattern.finditer(text):
    digits = match.group("number")
    if digits == "0000":
        continue
    records.append({"raw": match.group(0), "id": "INV-" + digits, "span": match.span()})
print(records)

Expected: one record for raw inv-7777, canonical INV-7777, span (10, 18). The all-zero candidate is filtered out. The five-digit candidate has no allowed closing boundary after its first four digits. These decisions are inspectable because the candidate rule, semantic exclusion and canonicalization are separate steps.

This code does not query an invoice database. If existence or authorization matters, that requires a separate checked operation. It also does not decide whether the message is denying, quoting or correcting the reference. “Do not pay INV-1042” still contains an invoice mention. Extracting the mention does not authorize a payment or imply a positive relation.

Evaluate exact spans, not a success printout#

Represent an entity as (document_id, start, end, canonical_id). A predicted entity is a true positive only when that whole tuple appears in the gold set. Then TP = |predicted ∩ gold|, FP = |predicted - gold| and FN = |gold - predicted|. Precision is TP/(TP+FP) and recall is TP/(TP+FN). Specify a convention when a denominator is zero; report the counts as well as the ratio.

Suppose the gold set contains INV-1042, INV-9012 and lowercase inv-7777, while an uppercase-only rule returns the first two and invalid INV-0000. The counts are TP=2\mathrm{TP}=2TP=2, FP=1\mathrm{FP}=1FP=1 and FN=1\mathrm{FN}=1FN=1. Precision and recall are both 23\frac{2}{3}32​. A rule can improve recall by accepting more candidates while reducing precision. The right operating point depends on what happens after extraction and the cost of review.

An exact-span metric is intentionally strict. A partial match can be semantically related but unusable for a downstream evidence link. Other applications may also report overlap-based or entity-level relaxed scores, but do not switch scoring rules after observing a disappointing result. Keep the annotation policy, matching rule and evaluation code versioned together.

Failure cases worth keeping#

Use negative fixtures that distinguish plausible implementations: INV-10420, xINV-1042, _INV-1042, INV-１２３４, INV-0000, a lowercase valid reference, and a document with two valid references. A test containing only INV-1042 would pass many incorrect patterns. Check both the returned IDs and their spans. Reusing the same digits in multiple documents also catches an evaluator that accidentally drops document identity.

Do not attempt to parse arbitrary nested formats with a gradually expanding regex when a parser already defines the structure. Do not interpolate untrusted text into a pattern without deciding whether it is a literal or regex syntax. re.escape is useful when the intended operation is literal matching, but it does not validate the meaning of the matched value. Avoid nested ambiguous repetitions on unbounded input, and do not present the small examples here as a general performance proof.

Run and practice#

Use python-core in the Docker classroom. The learner source is courses/nlp/learners/nlp-003.py. No external corpus or network is required. Save your predicted spans and observed match records beside your draft.

  1. Return provenance with each match. Extract both references in the first worked message. Expected: the exact raw strings, digit groups and spans (4,12) and (26,34). Verify: slicing the original text at each returned span reproduces the raw match.
  2. Reject misleading substrings. Test five-digit, prefixed, underscore-prefixed and non-ASCII-digit forms. Expected: no matches under the stated initial pattern. Verify: preserve a valid adjacent punctuation case that still matches, so the rule is not merely rejecting everything.
  3. Choose the correct API. Compare search, match and fullmatch on a whole message and an ID-only field. Expected: reproduce the four Boolean results in the second worked example. Verify: explain why search is inappropriate for the “only an ID” field contract.
  4. Separate syntax and semantics. Add ASCII case alternatives and reject 0000 while retaining raw offsets. Expected: only inv-7777 from the third worked message, canonicalized to INV-7777 at (10,18). Verify: the original text remains unchanged.
  5. Measure an imperfect extractor. Construct gold and predicted entity sets with two shared correct items, one invalid prediction and one missed lowercase item. Expected: TP=2\mathrm{TP}=2TP=2, FP=1\mathrm{FP}=1FP=1, FN=1\mathrm{FN}=1FN=1, precision=recall=23\mathrm{precision}=\mathrm{recall}=\frac{2}{3}precision=recall=32​. Verify: moving one entity to a different document ID must stop it matching the original entity.
  6. Write the missing semantic contract. Give two messages that contain the same invoice ID but imply different actions, such as a request and a cancellation. Expected: the extractor returns the mention in both, while your explanation rejects the claim that extraction alone determines an authorized action. Verify: specify the separate evidence and validation required for that action.

Progressive hints and interview reasoning#

First inspect group(0), the named capture and the span separately. Next test the shortest invalid string that a tempting pattern would accept. Then calculate TP, FP and FN from explicit sets before dividing. For the final task, distinguish a substring's presence from the relation asserted about it.

Why might a rule be preferable to an LLM here? The identifier format is constrained, the evidence needs exact spans, and a small rule can be tested directly. That answer does not imply rules solve open-ended paraphrase or context. A hybrid system can use the rule for exact identifiers and a separately evaluated component for the surrounding intent.

Why is a format check insufficient? It does not establish existence, ownership, context or permission. Downstream systems must validate those properties explicitly, even if the input was extracted with perfect span accuracy.

What would you inspect after a precision drop? Separate format drift, changed source populations, annotation-policy changes and implementation changes. Review actual false positives with their raw context rather than tuning the regex against only aggregate scores.
