# k8s-061: Topology, zones and locality-aware traffic

## Level and prerequisites

Advanced; about 120 minutes plus optional supervised host observations. Direct prerequisites: `k8s-060`. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

## Learning objectives

Design a two-zone failure scenario. Defend a locality tradeoff. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

## Purpose, vocabulary and mental model

A topology label describes placement, such as a node or availability zone. Locality-aware routing tries to prefer nearby endpoints to reduce latency or cross-zone traffic, subject to implementation and policy. It is a preference or constraint with tradeoffs, not a guarantee of balanced load or failure tolerance.

Spreading replicas across zones can improve resilience to a zone failure, but only if scheduling, storage and dependencies also span the required failure domains. A local preference can concentrate traffic on a small number of endpoints if placement is uneven. Capacity and availability must be considered together.

Kubernetes 1.37 offers two Service-level mechanisms. The `spec.trafficDistribution` field accepts `PreferSameZone`, which sends a caller's traffic to ready endpoints in its own zone and falls back cluster-wide when that zone has none, and `PreferSameNode`, which prefers the caller's node, then its zone, then the cluster. `PreferClose`, the first value to reach GA in 1.33, is now a deprecated alias for `PreferSameZone`. The older `service.kubernetes.io/topology-mode: Auto` annotation assigns zone hints in proportion to allocatable CPU, includes safeguards for small endpoint counts and takes precedence over the field when both are set. Without either, traffic is spread across all ready endpoints. The EndpointSlice controller publishes these preferences as hints, and the service proxy must honor them. The lesson's synthetic two-zone example does not promise that a local kind cluster reproduces cloud-zone behavior.

## Mechanism and field-by-field reasoning

Separate workload placement from traffic selection. Topology spread constraints influence where Pods can be scheduled; Service routing policy influences which eligible endpoint a caller uses. One does not automatically configure the other.

For the synthetic example, zoneA has two ready app endpoints and zoneB has one. A local-only rule can overload the single endpoint in zoneB even when total cluster capacity appears sufficient. A failover policy must define what happens when a zone has no eligible local endpoint.

A spread constraint such as `maxSkew: 1` with `topologyKey: topology.kubernetes.io/zone` and `whenUnsatisfiable: DoNotSchedule` keeps the per-zone counts of matching Pods within one of each other, which is what keeps zone preferences safe. `PreferSameZone` does not rebalance load: a zone with one endpoint sends all of its traffic there. The stricter `internalTrafficPolicy: Local` uses only endpoints on the caller's node and drops traffic when there are none, so it is a requirement rather than a preference.

## Trace the request or control path

```text
scheduler placement -> endpoint distribution across nodes/zones
caller location + routing policy -> eligible/preferred endpoint set
capacity and failover behavior -> actual latency and availability
```

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. ### Worked example 1: Compare two-zone capacity

These are synthetic counts.

```json
{
  "zoneA": { "clients": 10, "ready_endpoints": 2 },
  "zoneB": { "clients": 10, "ready_endpoints": 1 }
}
```

**Expected observation:** Equal client counts do not imply equal load per endpoint under strict locality.

### Worked example 2: Separate placement and routing

The Service field sets a routing preference; the Deployment excerpt sets a scheduling rule. Both use the synthetic hello labels.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: hello
spec:
  selector:
    app: hello
  ports:
    - name: http
      port: 80
      targetPort: http
  trafficDistribution: PreferSameZone
---
# Deployment Pod template excerpt: spec.template.spec
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: DoNotSchedule
    labelSelector:
      matchLabels:
        app: hello
```

**Expected observation:** The spread constraint keeps the per-zone counts of hello Pods within one of each other; the Service field makes each caller prefer ready endpoints in its own zone and fall back cluster-wide only when its zone has none. Neither setting configures the other.

## Diagnosis, failure boundaries and common mistakes

Exercise 4 is this chapter's controlled failure: Diagnose local preference with insufficient nearby capacity. The distinguishing result: Inspect endpoint distribution and actual load, not only total replicas. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
