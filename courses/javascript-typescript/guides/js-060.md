# js-060: Treemaps and area-based composition

## Level and prerequisites

Advanced; about 110 minutes plus independent practice. Direct prerequisites: `js-059`.

## Learning objectives

Build a treemap from leaf values without double counting and judge when area suits the comparison. The central exercise is: Render labeled leaf rectangles.

## Purpose, vocabulary and mental model

A treemap divides a rectangular area into nested regions whose areas represent nonnegative values. It is useful for part-to-whole structure when many categories must fit in a compact view. Exact comparisons are harder than aligned position or length, so a table or labels should support precise reading.

Hierarchy sums need a clear grain. If a parent value already includes its children and you also sum the children, the total can be double-counted. A common input supplies values only at leaves and uses hierarchy.sum to aggregate upward. Missing or negative values require an explicit policy.

Padding and rounding change visible rectangle area, so pixel area may not exactly preserve ratios in tiny charts. This is a rendering tradeoff, not a reason to claim numerical precision from a treemap. The reference checks the hierarchy’s numeric total and nonnegative geometry separately.

### Key terms

- **Treemap:** A layout that divides a rectangle into nested tiles whose areas are proportional to nonnegative values in a hierarchy.
- **Hierarchical sum:** The `node.sum(accessor)` operation that sets each node's value to its own accessor result plus the values of all its descendants. Supplying values only at leaves avoids double counting.
- **Tile bounds:** The `x0`, `y0`, `x1` and `y1` fields a treemap layout adds to each node, so width is `x1 - x0` and height is `y1 - y0`.
- **Padding:** Space reserved between tiles by the layout. It improves readability but means pixel areas no longer match value ratios exactly.

## Syntax anatomy and mechanism

Create the hierarchy, call `.sum(d => d.value || 0)` only under a validated nonnegative-value contract, then apply a treemap layout. Each leaf receives x0,y0,x1,y1 bounds. Width is x1-x0 and height is y1-y0.

Sort deliberately if stable ordering matters. Updating values can substantially rearrange a treemap, making entity tracking difficult. Use stable keys and consider whether a bar chart would better serve the comparison task.

## Worked example / walkthrough

### Worked example 1: Aggregate leaf values

Parents have no independent duplicated amount.

```javascript
const root = d3
  .hierarchy({
    children: [
      { name: "A", value: 2 },
      { name: "B", value: 3 },
    ],
  })
  .sum((d) => d.value || 0);
console.log(root.value);
```

**Expected observation:** 5.

### Worked example 2: Read rectangle geometry

A layout supplies bounds; width and height are differences between them.

```javascript
// js-060 worked example 2: a complete program for the classroom preview.
const host = document.querySelector("#chart");
const output = document.querySelector("#output");
host.replaceChildren();
const check = (condition, message) => {
  if (!condition) throw new Error(message);
};
const svg = d3
  .select(host)
  .append("svg")
  .attr("viewBox", "0 0 640 360")
  .attr("role", "img")
  .attr("aria-label", "Treemaps and area-based composition")
  .style("width", "100%")
  .style("max-width", "640px");
const leaf = { name: "A", x0: 10, x1: 110, y0: 20, y1: 70 };
const g = svg.append("g").attr("transform", "translate(40,40)");
const rect = g
  .append("rect")
  .attr("x", leaf.x0)
  .attr("y", leaf.y0)
  .attr("width", leaf.x1 - leaf.x0)
  .attr("height", leaf.y1 - leaf.y0)
  .attr("fill", "#2563eb");
g.append("text")
  .attr("x", leaf.x0 + 8)
  .attr("y", leaf.y0 + 30)
  .attr("fill", "white")
  .text(`${leaf.name}: ${leaf.x1 - leaf.x0} x ${leaf.y1 - leaf.y0}`);
const box = rect.node().getBBox();
check(box.width === 100 && box.height === 50, "Width and height come from bound differences");
output.textContent = "js-060 worked example 2 complete";
```

**Expected observation:** One 100 by 50 rectangle starting at (10, 20) inside its group, labeled A: 100 x 50.

## Six progressive exercises

### Exercise 1: Predict the hierarchy total.

**Expected evidence:** 5 from leaf values 2 and 3.

**Progressive hint:** The aggregate should match the known leaf sum.

### Exercise 2: Add a zero-valued leaf.

**Expected evidence:** The numeric total stays unchanged and its representation needs an explicit policy.

**Progressive hint:** Zero area can make a category invisible.

### Exercise 3: Render labeled leaf rectangles.

**Expected evidence:** Bounds are finite and widths/heights are nonnegative.

**Progressive hint:** Validate geometry separately from numeric sums.

### Exercise 4: Diagnose parent-plus-child double counting.

**Expected evidence:** The input mixes aggregate and leaf grain.

**Progressive hint:** Choose one source of truth for the sum.

### Exercise 5: Compare treemap and bars for precise ranking.

**Expected evidence:** Bars usually offer easier aligned magnitude comparison.

**Progressive hint:** Treemaps prioritize compact hierarchy and composition.

### Exercise 6: Design a changing treemap with identity preserved.

**Expected evidence:** Stable keys, explicit updates and a readable alternate value list.

**Progressive hint:** Large layout changes can disorient viewers.

## Debugging and common mistakes

When the total is too large, check whether parent nodes carry values: `hierarchy.sum` adds a node's own value to its children's, so a parent of 10 over leaves 2 and 3 totals 15, not 5. Call `sum` before `treemap`, then check that every rectangle has finite, nonnegative width and height and that leaf areas account for the total. ([checkpoints](../STUDY-GUIDE.md#d3-debugging-checkpoints))

Exercise 4 is the controlled failure: Diagnose parent-plus-child double counting. Distinguishing evidence: The input mixes aggregate and leaf grain.

## Accessibility and interpretation

Small rectangles cannot hold labels, so pair the treemap with a sorted list of leaves and values. Label directly where text fits and do not depend on color alone to distinguish branches; a reader should be able to name the largest leaf without seeing the picture. ([accessibility review](../STUDY-GUIDE.md#d3-accessibility-review))

Area is harder to compare than length, so a treemap suits part-to-whole structure, not precise ranking. A zero-valued leaf has no area and disappears, so decide whether to list it separately. Make sure leaf values share one unit and grain, because mixing aggregates with leaves double counts. ([statistical meaning](../STUDY-GUIDE.md#d3-statistical-meaning))
