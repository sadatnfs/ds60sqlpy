## The question and the mechanism

Distinguish sales lines, orders and customers before selecting an aggregation.

Grain is the claim made by one row. Sales has a unique SaleID, while OrderID can occur on several lines. Order 101 contains a notebook and a pen, so counting rows answers how many lines were recorded, not how many orders were placed. A correct arithmetic operation on the wrong unit still produces the wrong metric.

A key identifies the row at its declared grain. The fact's foreign keys identify dimensions that describe it; they are not alternate unique keys for the fact. ProductKey repeats because the same product can be sold again. CustomerKey repeats because one customer can place several orders. A transaction table that accidentally repeats the same SaleID violates the model even if the repeated quantities look plausible.

Before writing a measure, finish the sentence 'one observation represents ...'. Then state whether the metric is additive across the intended groups. Line quantity is additive across disjoint line sets. Distinct orders can span product groups, so summing per-product order counts can double-count a multi-product order. Later totals lessons build on this grain distinction.

## Vocabulary and expression anatomy

COUNTROWS receives a table and counts eligible rows. DISTINCTCOUNT receives one column and counts distinct values in that column, including BLANK if present. Our OrderID values are complete. NetRevenue remains an amount, so a row count, an order count and revenue should use different names rather than one ambiguous 'total'.

Concepts to explain in your own words: **grain**, **key**, **order line**, **distinct count**, **unit**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: Whole model counts

**Starting context:** All Sales rows; one row per SaleID.

```dax
EVALUATE ROW ( "Lines", COUNTROWS ( Sales ), "Orders", DISTINCTCOUNT ( Sales[OrderID] ), "Revenue", [NetRevenue] )
```

**Context trace:**

1. S1 and S2 share OrderID 101.
2. Seven distinct order identifiers remain after counting 101 once.
3. Revenue still includes both legitimate lines of that order.

**Hand-derived worked-reference result:**

| Lines | Orders | Revenue |
| --- | --- | --- |
| 8 | 7 | 187 |

Deduplicating entire orders before summing their lines would lose a product, while counting every line as an order overstates order count. The aggregation must match the question rather than flatten every metric to one grain.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: One multi-line order

**Starting context:** OrderID 101 only; both matching fact rows retained.

```dax
EVALUATE CALCULATETABLE ( ROW ( "Lines", COUNTROWS ( Sales ), "Orders", DISTINCTCOUNT ( Sales[OrderID] ), "Revenue", [NetRevenue] ), Sales[OrderID] = 101 )
```

**Context trace:**

1. S1 contributes Notebook quantity 2 and amount 20.
2. S2 contributes Pen quantity 1 and amount 4.
3. The order has two lines, one identity and revenue 24.

**Hand-derived worked-reference result:**

| Lines | Orders | Revenue |
| --- | --- | --- |
| 2 | 1 | 24 |

This small order is a counterexample to the claim that line count equals order count. Keep it as a fixture when a later model refactor changes joins or grouping.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Read CustomerKey from Sales rather than counting the dimension.
2. Check both row identity and additive amounts.
3. Use a ratio of totals and a safe denominator.
4. Order 101 belongs to two products.
5. DISTINCTCOUNT does not silently discard BLANK.
6. Separate visit identity from charge-line identity.
