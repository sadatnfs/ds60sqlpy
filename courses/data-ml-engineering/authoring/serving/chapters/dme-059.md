# dme-059: Token embeddings, positions and retrieval representations

After tokenization, the serving process has integer IDs. A Transformer cannot multiply a sentence string by its attention weights. It first looks up a vector for each ID and incorporates information about position. These vectors feed the model's layers. They are different from the document or query embeddings that a retrieval system stores in a vector index.

The distinction matters in a request lifecycle. A plain completion request uses the generator's token embedding table. A RAG application may first call a separate retrieval encoder, retrieve documents, construct a prompt, and only then invoke the generator. Combining both operations under the word “embedding” obscures two model identities, two latency budgets and two evaluation problems.

This chapter uses explicit NumPy matrices. You will inspect a row lookup, position addition and an order-losing pooling counterexample. The numerical arrays are hand-authored fixtures, not learned semantic representations. The full workshop uses a real trained token embedding layer and learned absolute positions.

## Row lookup is a parameter operation

Let \(V\) be vocabulary size, \(d\) hidden width, and \(E\in\mathbb{R}^{V\times d}\) the token embedding matrix. For token ID \(t_i\in\{0,\ldots,V-1\}\), the input vector is the row

\[
e_i=E_{t_i,:}.
\]

One-hot multiplication gives an equivalent mathematical description, but an implementation normally uses indexed lookup rather than constructing a giant one-hot array. The table is part of the checkpoint. Its rows are learned through the training objective, and the tokenizer defines which text pieces those rows represent.

Repeated occurrences of the same token initially retrieve the same row. They need not have the same contextual representation after attention and position information are applied. In the phrase `bank of the river`, a later hidden state may depend on neighboring tokens; the initial row for `bank` is still the same parameter row used in another sentence under this model.

An embedding row is not a database record that the server fetches from a remote vector store for every token. In the workshop, the embedding parameter tensor is loaded with the other weights at startup and remains resident. A request supplies indices. A larger distributed deployment might partition an embedding table or use specialized placement, but that is an explicit model-serving design, not an inherent requirement of the lookup operation.

## Position enters the computation

Attention without position information treats input order differently from an ordinary sequence model. The workshop uses a learned position table \(P\in\mathbb{R}^{C\times d}\), with context capacity \(C\). Its initial hidden state is

\[
h_i^{(0)}=E_{t_i,:}+P_{i,:}.
\]

Here \(i\) is the actual model position, including any special tokens. Position zero cannot be reused for every one-token decode call. With a cache containing \(p\) previous positions, the next token must use position \(p\). An off-by-one error can leave tensor shapes valid while making cached inference disagree with full-prefix inference.

Other architectures use sinusoidal encodings, rotary transformations or relative attention biases. These mechanisms are not interchangeable at deployment time. Rotary position embedding, for example, transforms query and key components as a function of position rather than simply adding a learned vector to the input. The serving implementation must reproduce the checkpoint's training-time convention, context extension policy and numerical precision.

For a float32 token table, parameter storage is approximately \(4Vd\) bytes, excluding allocator overhead. Weight tying may reuse an embedding matrix for an output projection, reducing parameters, but tying changes the architecture contract and cannot be assumed. The workshop keeps its output head separately registered and validates every parameter name and shape during loading.

## Worked case 1: a repeated token at different positions

The first case uses four vocabulary rows and a hidden width of two. IDs `[1, 2, 1]` select vectors `[1,2]`, `[3,-1]` and `[1,2]`. Before positions are added, the first and third vectors are identical. After adding the stated position rows, the hidden inputs become `[1,2]`, `[3.1,-0.8]` and `[1.2,2.4]`.

The expected values are small enough to calculate by hand. They catch two errors separately: wrong token row selection and wrong position offsets. A successful shape check alone would miss both. The example also verifies that the four-by-two float64 NumPy fixture occupies 64 data bytes. That dtype is chosen for transparent arithmetic; the actual workshop checkpoint uses float32.

This case applies when debugging a cached decoder whose first token looks plausible but later tokens diverge from the reference. Compare embeddings and positions before examining every attention kernel. A cache can be mathematically correct while the position index feeding it is wrong.

## Worked case 2: pooling loses order

The second case represents two different sequences using the mean of their token vectors. Both contain the same token counts, so both means are identical even though their order differs. Their cosine similarity is one. This proves a limitation of that particular representation, not that all embedding models ignore order.

The case then scores a hand-authored query vector against two hand-authored document vectors using cosine similarity. The first document wins. This is a transparent retrieval-space arithmetic example; it does not show that an untrained mean of generator embedding rows is a useful semantic search model. A real retrieval encoder needs its own training objective, normalization convention, corpus evaluation and versioned index.

## Joining retrieval and generation correctly

A practical RAG path might validate a query, encode it with a retrieval model, search an index, apply access controls and reranking, construct a bounded prompt, and then tokenize for the generator. The query encoder's vocabulary and vector dimension need not match the generator's. Retrieval vectors are typically compared using a defined distance or similarity; token vectors are inputs to the generator's network.

Index entries must record which retrieval encoder produced them. Changing the encoder without rebuilding or deliberately migrating the index can make old document vectors incompatible with new query vectors even when dimensions match. Equal dimension is a shape property, not a semantic compatibility guarantee. Evaluation should measure relevant-document retrieval separately from answer support and correctness.

Prompt construction has another token boundary. Retrieved documents that fit a character limit may exceed the generator's context once separators and instructions are added. The accepted generation receipt should identify the final prompt, while application-level provenance records which documents contributed. The inference workshop intentionally serves a plain prompt; the linked RAG chapters cover the larger orchestration contract.

## Diagnosis and interview discussion

**Are the generator's token embeddings automatically good document embeddings?** No. Their objective and granularity differ. A retrieval representation may be trained to align related queries and documents; token embeddings are learned as part of a generative model. Pooling them is a baseline that needs evaluation, not a guaranteed solution.

**Why can equal token IDs produce different final vectors?** The same initial lookup row is combined with position and contextual information. Attention and feed-forward layers then transform it based on the prefix.

**What would you inspect after a context-length change?** Position implementation, trained position range, scaling policy if any, cache offsets, masks, numerical precision and actual quality on long-context tasks. Increasing an array bound alone does not establish valid extrapolation.

Before moving on, trace one request's tokenizer hash, embedding row range, context position and checkpoint identity. The next chapter explains how those weights reach a ready service and how a failed checkpoint is rejected before any user request runs.
