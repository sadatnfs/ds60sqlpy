## The question and the mechanism

Record a complete context ledger and explain two cells with the same measure definition.

Filter context can come from a query, a visual's rows and columns, a slicer, a page filter or an expression that modifies it. A measure does not know that one selected value was visually prominent and another was hidden in a report pane. All effective filters belong to the question. Record them by table and column before diagnosing a surprising number.

Filters on different dimensions intersect through the fact table. Multiple selected values on one column form an allowed set rather than several independent calculations added together. Selecting North and South admits customers from either region; adding Year 2025 still restricts the eligible sales dates. In contrast, two separate dimensions such as region and product category impose simultaneous conditions.

A result also depends on relationship status and model scope. A Date selection reaches OrderDate through the active relationship in our model. It does not mean ShipDate merely because a page title says 'shipping'. Context traces should name date role, selected keys and remaining facts, not just state that a measure is 'filtered'.

## Vocabulary and expression anatomy

The IN operator expresses membership in a literal value set. CALCULATETABLE provides the two stated filters around a ROW. The measure is identical across cases, so the row-eligibility ledger explains the changed answer. Neither calculation contains row context.

Concepts to explain in your own words: **filter context**, **intersection**, **selection**, **report cell**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: One region in one year

**Starting context:** Customer.Region = North and Date.Year = 2025, using active OrderDate.

```dax
EVALUATE CALCULATETABLE ( ROW ( "Revenue", [NetRevenue] ), Customer[Region] = "North", 'Date'[Year] = 2025 )
```

**Context trace:**

1. North supplies customer keys 10 and 30.
2. Year 2025 removes S1, S2 and S3.
3. S4, S5 and S8 remain: 27 + 20 + 36 = 83.

**Hand-derived worked-reference result:**

| Revenue |
| --- |
| 83 |

The same regional total across all years would be 107. Omitting the year from an explanation would conceal why those two correct values differ.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: A multi-selection retains the year

**Starting context:** Region is the allowed set {North, South}; order year remains 2025.

```dax
EVALUATE CALCULATETABLE ( ROW ( "Revenue", [NetRevenue] ), Customer[Region] IN { "North", "South" }, 'Date'[Year] = 2025 )
```

**Context trace:**

1. The region set admits all three customers with sales.
2. The year filter still excludes the three 2024 lines.
3. S4 through S8 total 123.

**Hand-derived worked-reference result:**

| Revenue |
| --- |
| 123 |

Broadening one filter does not remove the others. The answer does not return to the all-year total 187.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

2. Keep the year and region set while restricting product keys.
3. State each filter's dimension and key effect.
4. Check whether both sides use the same temporal population.
5. A valid dimension selection can have no facts.
6. Hidden filters can still change the query.
