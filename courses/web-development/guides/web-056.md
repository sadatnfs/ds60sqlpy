# web-056: PHP milestone: a tested study-planner application core

## Level and prerequisites

Advanced; allow about 180 minutes, with extra time for independent practice. Direct prerequisites: `web-055`

## Learning objectives

Build a tested planner core with validation and prepared storage. Explain the remaining work before this core becomes a deployed application. Use application service, validation and repository accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

The application core coordinates a use case without pretending to be an HTTP server. It receives a trusted actor identity and untrusted proposed values, validates the proposal, writes through a repository and returns a result. Keeping these boundaries visible makes it possible to reason about what is trusted and which failures prevent a write.

This milestone combines the earlier mechanisms in a small study planner. The database is disposable SQLite memory. The input is synthetic. Validation rejects unsupported topics and out-of-range durations. A prepared statement stores an accepted plan under the supplied actor. A query scopes retrieval by that actor. Rendering and HTTP adaptation remain separate so the same core can later be integrated and tested through a real server.

### Key terms

- **Application service:** A class that carries out one use case by coordinating validation, domain objects and repositories.
- **Repository:** An object that hides storage details behind methods such as find and save.
- **Acceptance matrix:** A table of cases written before implementation, such as valid, invalid and cross-actor input, each with its expected outcome.
- **Domain validation:** Checks inside the application core that reject invalid values whatever interface submitted them.

## Syntax anatomy and mechanism

Write the acceptance matrix before implementation: a valid plan is stored once, invalid input stores nothing, one actor cannot read another's plan, and output has a clear type contract. A production service would add session verification, CSRF where relevant, idempotency, concurrent behavior, migrations and operational controls. Do not infer those properties from this small core.

## Contrast case: storing each field as it validates

This version saves the topic before it checks minutes. Call it with a valid topic and minutes of 500.

```php
function createPlanEager(PDO $db, int $actorId, array $input): void {
  $db->prepare('INSERT INTO plans (owner_id, topic) VALUES (?, ?)')
     ->execute([$actorId, $input['topic']]);
  $id = (int) $db->lastInsertId();

  if ((int) $input['minutes'] > 120) {
    throw new InvalidArgumentException('minutes');
  }
  $db->prepare('UPDATE plans SET minutes = ? WHERE id = ?')
     ->execute([$input['minutes'], $id]);
}
```

The insert runs and commits on its own, then the minutes check throws. The caller sees a rejection, but the table now holds a plan row with a topic and no minutes, which the acceptance matrix says must never happen. Rerunning the request adds another orphan each time. The reference validates every field into a complete value first, then performs one insert, so a rejected request leaves the row count unchanged. If several writes were truly needed, one transaction with rollback would serve the same purpose.

## Debugging and common mistakes

Do not add a success banner that claims the user now has a production service. Preserve invalid cases in the test suite. A synthetic trusted actor is a testing input, not an authentication implementation.

When rejected input still leaves a row behind, the service wrote some fields before validating all of them; validate the whole plan first, then write once. When a cross-owner read returns data, check that the query binds both the plan id and the trusted owner.

The shared [debugging routine](../STUDY-GUIDE.md#debugging-php) covers what to record before each repair.
