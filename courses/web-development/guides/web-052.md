# web-052: Transactions, constraints and concurrent changes

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-051`

## Learning objectives

Implement a version-checked update in a disposable database. Explain the limits of the single-connection concurrency demonstration. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A transaction groups operations into a unit that can commit or roll back. Atomicity means the unit is not partially applied when the transaction aborts under the database's contract. Constraints enforce invariants close to the stored data, where every writer must encounter them. Application checks alone can race when two requests read the same state and then both attempt an update.

Concurrency requires more than wrapping code in begin and commit. Isolation levels, locking and the chosen database determine what other transactions can observe. An optimistic update includes an expected version in its WHERE clause and checks the affected-row count. A zero-row update can mean the record changed or was not accessible; the application must decide how to report and retry safely.

## Syntax anatomy and mechanism

Begin a transaction, perform related writes, commit only after all succeed, and roll back on failure if still in a transaction. Use a database CHECK or UNIQUE constraint where it expresses a durable invariant. The SQLite example demonstrates rollback and a version predicate in one connection; it does not simulate real parallel requests or qualify PostgreSQL isolation.

## Worked example / walkthrough

### Worked example 1: A guarded update

The version is part of the write condition.

```sql
UPDATE plans SET minutes = :minutes, version = version + 1 WHERE id = :id AND version = :expected_version;
```

**Expected observation:** A stale expected version updates no row.

### Worked example 2: Rollback ownership

Failure prevents a partial unit from being accepted.

```php
$db->beginTransaction();
try { /* related writes */ $db->commit(); }
catch (Throwable $error) { if ($db->inTransaction()) $db->rollBack(); throw $error; }
```

**Expected observation:** The transaction is rolled back before the failure propagates.

## Debugging and common mistakes

Do not blindly retry a non-idempotent operation after an ambiguous commit result. A transaction does not eliminate all races under every isolation level. Keep affected-row checks tied to a documented driver and statement contract.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.
