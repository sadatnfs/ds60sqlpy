# Compilation, ABI versions and native lifetime

Start with: tmb-036, tmb-005.

Outcome: Explain how native objects are built, loaded and retired with explicit version and process ownership.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter fingerprints two source-description files and prints the R version and platform; it compiles nothing. In the separately prepared [owned project](../projects/tmb-local/README.md), `R/compile.R` compiles the models and writes a build record (`build-receipt.txt`) of R, TMB, Matrix, RcppEigen and architecture, and `tests/public_api.R` checks `TMB::dynlib()`, `TMB::config()` and `TMB::TMB.Version()` and releases objects with `TMB::FreeADFun()`; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

`TMB.Version()` distinguishes package/API version information from ABI compatibility information. The ABI describes native entry points used by compiled model libraries. Two package versions can sometimes share an ABI, but a matching TMB ABI is only one compatibility condition: architecture, operating system, R and linked native libraries still matter. Our teaching project uses exact pins rather than claiming universal binary interchangeability.

`dynlib(name)` constructs the platform-specific shared-library filename. R's `dyn.load` loads it. `FreeADFun(obj)` releases TMB native allocations associated with an objective; it is not the same operation as unloading the DLL. `config(..., DLL=...)` reads or changes DLL-level configuration. Internal option names are version-sensitive and should not become arbitrary learner-controlled settings.

## Key terms

- **TMB.Version:** The function that reports package and API version separately from native ABI compatibility information.
- **dynlib:** The function that turns a model name into the platform-specific shared-library filename for `dyn.load`.
- **FreeADFun:** The function that releases native memory tied to an objective; it does not unload the DLL.
- **precompile:** A helper that prepares TMB library precompilation and needs write access to the package directory, so it belongs in an image build rather than a read-only learner run.
- **config:** The function that reads or changes DLL-level configuration for a loaded model library.

### Worked case A: one model, two source identities

The companion writes two original source-description files and compares their checksums. Even if a filename remains the same, the build record must identify the source that produced the native library. The prepared API checks the loaded library's resolved path and rejects another copy with the same model name.

`compile` invokes R's native build toolchain. `flags`, `framework`, `openmp`, `safebounds`, `safeunload`, `supernodal`, `longint` and `max.order` configure distinct compiler or library features. The ordinary project qualifies a conservative subset; custom SuiteSparse, long integer indices and specialized derivative orders need separate preparation and tests.

### Worked case B: precompilation is a preparation mutation

`precompile(all=TRUE, clean=FALSE, ...)` prepares TMB's library precompilation mechanism and requires write access to the package directory. Actual precompilation happens when a later model compile uses it. It belongs in an image build or owned development environment, not a read-only learner execution. The companion contrasts writable scratch state with immutable source metadata conceptually, without modifying an installed package.

Never unload a library while live objects can still call into it. A fresh bounded R process gives a straightforward lifecycle: load, construct, evaluate, report, exit. Long-lived services need deliberate ownership and cleanup after failures. Saving an R object does not serialize its executable native allocations portably.

### Answered discussion

**Does `FreeADFun` delete source or learner data?** No. It manages native objective memory. **Does `safeunload` make arbitrary concurrent unloading safe?** It supports TMB's lifecycle machinery but does not remove application ownership responsibilities. **Can I run precompile on a read-only container?** No, not where it needs package writes. Prepare it explicitly if it is part of the chosen build contract.

See [TMB.Version, compile, precompile, dynlib, FreeADFun and config](https://cran.r-project.org/web/packages/TMB/TMB.pdf).

### Worked case C: the checksums and the loaded-path check

`writeLines` appends a newline, so the two files contain the 17 bytes `model revision A\n` and `model revision B\n`. Their MD5 digests are deterministic and can be reproduced with any MD5 tool:

```text
model revision A   15e44445bfc5614f50c8e228af9bbbee
model revision B   c4e409152e5db5cec3e05b8b15ebe5c1
```

The companion prints these digests next to two temporary paths whose names change on every run; only the digests are stable. One changed character produces an unrelated digest, which is why a digest identifies a source revision better than a filename or modification time. `R/evaluate.R` applies the same idea to the real model: its provenance block records the MD5 of `models/<model>.cpp` from the source tree, so a response can be traced to one template revision.

The project's loading code in `R/api.R` adds a second guard on the native side:

```r fragment
library_path <- normalizePath(file.path(build_dir, TMB::dynlib(model)), mustWork = TRUE)
if (!model %in% names(getLoadedDLLs())) dyn.load(library_path)
actual <- normalizePath(getLoadedDLLs()[[model]][["path"]], mustWork = TRUE)
if (!identical(actual, library_path)) stop("A different model library is already loaded; use a fresh R process")
```

R identifies a loaded DLL by its base name. If an earlier step in the same process loaded `normal_mean` from a scratch directory, a later `dyn.load` from the prepared build directory would not replace it, and `MakeADFun(DLL = "normal_mean")` would bind to the scratch copy. Comparing normalized paths turns that silent mix-up into an explicit error whose remedy is the fresh-process lifecycle the guide recommends.

### What the build receipt pins

`R/compile.R` refuses to run unless R is 4.6.1 and TMB is 1.9.25, then compiles each model with `flags = "-O1 -g0"`, `framework = "CppAD"`, `safebounds = TRUE` and `safeunload = TRUE`, enabling OpenMP only for `parallel_gaussian`. It writes `build-receipt.txt` with R, TMB, Matrix and RcppEigen versions, the platform string, the framework and the flags. A library compiled under Matrix 1.7 and loaded beside Matrix 1.8 might still load, since the TMB ABI matches, while sparse routines it shares with Matrix behave differently. The receipt is what lets a reviewer notice that mismatch. The companion's `build_record` is a reduced version of the same idea, with the immutable source and separate scratch directory recorded as explicit flags.

### Base-R companion (runs in the classroom)

```r
paths <- c(tempfile(), tempfile());writeLines("model revision A", paths[1]);writeLines("model revision B", paths[2])
print(tools::md5sum(paths));stopifnot(unname(tools::md5sum(paths)[1]) != unname(tools::md5sum(paths)[2]));unlink(paths)
build_record <- list(R = as.character(getRversion()), architecture = R.version$platform, source_immutable = TRUE, scratch_separate = TRUE)
print(build_record)
```
