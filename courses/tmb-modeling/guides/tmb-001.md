# Why a C++ objective is called from R

Start with: r-012, cpp-001.

Outcome: Trace an observation through the objective, optimizer and returned estimate.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter evaluates a sum-of-squares objective and its gradient at two means for two small datasets. Compiling a C++ objective and calling it from R happens only in the separately prepared [owned project](../projects/tmb-local/README.md): `R/compile.R` builds its nine model templates and `R/api.R` calls them through `TMB::MakeADFun`; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

A model is a probability statement. Its implementation evaluates a scalar objective for a candidate parameter vector. An optimizer repeatedly asks for that value and its derivatives, and a reporting step converts the final parameter vector into scientific quantities. TMB, Template Model Builder, connects these steps: you describe the objective in templated C++, compile a shared library, and use R to supply data, construct derivatives, optimize and interpret results. It does not choose a defensible likelihood or an identifiable parameterization for you.

Start with \(f(\mu)=\frac12\sum_i(y_i-\mu)^2\). The data \(y\) stay fixed during optimization. The parameter \(\mu\) changes. Its derivative is \(f'(\mu)=n\mu-\sum_i y_i\), so its minimum is the sample mean. The factor one half simplifies differentiation. This is a least-squares objective; calling it a full Gaussian negative log likelihood also requires a variance assumption and its normalizing terms.

## Key terms

- **Objective function:** The scalar an optimizer minimizes for a candidate parameter vector; in TMB it is usually a negative log likelihood written in templated C++.
- **Automatic differentiation:** Exact derivatives of the implemented operations, obtained by applying the chain rule to the recorded calculation rather than by finite differences or hand-derived formulas.
- **R and C++ boundary:** The division of labor in which R supplies data and starting values, runs the optimizer and interprets results, while a compiled C++ library evaluates the objective and its derivatives.
- **Gradient:** The vector of partial derivatives of the objective; for the companion objective it is \(n\mu-\sum_i y_i\), which is zero at the sample mean.

### Worked case A: follow the calls

With observations 1, 2 and 6, the value at zero is 20.5 and the derivative is -9. A positive step in the mean lowers the objective. At the optimum 3, the derivative is zero and the value is 7. The companion prints this trace using base R. An actual TMB run replaces the hand-written gradient with `obj$gr`, but the mathematics stays the same.

```r prelude=../projects/tmb-local/R/api.R
obj <- make_objective(
  "normal_mean", list(y = c(1, 2, 6)),
  list(mu = 0, log_sigma = 0)
)
fit <- fit_objective(obj)
```

This project fragment uses two functions from `projects/tmb-local/R/api.R`; it needs the compiled project and estimates the scale as well. `list` constructs a named collection, `$` extracts a field, and `<-` assigns an R object. The optimizer receives functions, not C++ source text. The ordinary R classroom pad runs the base-R companion; it does not compile this project fragment.

### Worked case B: change an observation

Replace 6 by 9. The optimum becomes 4, not a cached previous result. The new objective must contain the new data. Reusing the old objective while displaying a new table is a dangerous integration error because the optimizer can converge perfectly on stale observations. Our fixed JSON interface constructs a fresh objective per request and returns the observation count and model identity.

Compilation converts template source into machine code for one architecture and R installation. `MakeADFun` then constructs an automatic-differentiation representation for data shapes and parameter declarations. These are different preparation stages. An R object holding native pointers is valid only in its process. Saving it with a generic serializer or shipping it to another Spark executor does not transport a working model.

### Diagnostics and answered discussion

**Does C++ make a wrong model correct?** No. It can evaluate a wrong objective and its exact derivative very quickly. First validate tiny values against independently written formulas. **Is automatic differentiation symbolic algebra?** It applies chain rules to executed elementary operations; it is neither finite differencing nor a general proof system. **What should a fit report contain?** Data identity, objective definition, parameterization, software versions, final objective, gradient, convergence status and scientific interpretation. Later chapters add uncertainty and predictive validation.

Read [the TMB introduction](https://kaskr.github.io/adcomp/Introduction.html) for the architecture. Continue by learning the exact C++ data and parameter contract before changing model families.

### Worked case C: three optimizer steps traced by hand

The outcome asks you to follow one observation all the way to the estimate. Write the objective as a sum of per-observation pieces. For \(y=(1,2,6)\), each observation contributes \(\frac12(y_i-\mu)^2\) to the value and \(\mu-y_i\) to the derivative. At \(\mu=0\) the three gradient contributions are \(-1,-2,-6\); they add to the \(-9\) printed by the companion, and the observation 6 supplies two thirds of that pull. This is exactly the bookkeeping TMB performs when `nll -= dnorm(y(i), ...)` runs inside the loop of `normal_mean.cpp`: each pass through the loop adds one observation's term to the scalar and, during taping, one branch of the chain rule.

A fixed-step gradient method makes the trace concrete. The loop below is base R and runs in the classroom pad; it is not what `nlminb` does internally, but it shows how a value and a gradient drive the parameter.

```r
y <- c(1, 2, 6)
f <- function(m) sum((y - m)^2) / 2
g <- function(m) length(y) * m - sum(y)
mu <- 0
for (step in 1:3) {
  mu <- mu - 0.2 * g(mu)
  cat(step, mu, f(mu), g(mu), "\n")
}
```

Because the objective is quadratic, every line can be checked by hand. Using \(\sum_i(y_i-\mu)^2=\sum_i(y_i-3)^2+3(\mu-3)^2=14+3(\mu-3)^2\), the value is \(f(\mu)=7+1.5(\mu-3)^2\) and the update is \(\mu_{k+1}-3=(1-0.2\cdot3)(\mu_k-3)=0.4(\mu_k-3)\).

```text
1 1.8 9.16 -3.6
2 2.52 7.3456 -1.44
3 2.808 7.055296 -0.576
```

The distance to the optimum shrinks from 3 to 1.2, 0.48 and 0.192, a factor 0.4 per step, and the value approaches the minimum 7 from above. Change the step size to 0.7 and the factor becomes \(1-2.1=-1.1\): the iterate overshoots 3, lands on the other side farther away, and diverges while oscillating. The data did not change; only the search rule did. A quasi-Newton method such as `nlminb` estimates curvature, here the constant 3, and a Newton step \(\mu-g(\mu)/3\) reaches 3 from 0 in a single move. That is why the course reports objective, gradient and status together: the same likelihood can be searched well or badly.

### What changes when the data change

Replace 6 with 9 and the gradient at zero becomes \(-12\), the optimum moves to 4 and the minimum value becomes \(\frac12(9+4+25)=19\). Every step of the trace above changes because the data sit inside `f` and `g`. In a TMB workflow the data are bound when `MakeADFun` builds the tape, so a new dataset needs a new objective object; editing the R vector afterward does not reach the already constructed function. When you audit a report, the observation count, the final objective and the gradient at the reported estimate together let a reader recompute this kind of trace and catch a stale objective.

### Base-R companion (runs in the classroom)

```r
y <- c(1, 2, 6)
trace_objective <- function(y) {
  mu <- mean(y)
  data.frame(
    mu = c(0, mu),
    value = vapply(c(0, mu), function(m) sum((y - m)^2) / 2, numeric(1)),
    gradient = vapply(c(0, mu), function(m) length(y) * m - sum(y), numeric(1))
  )
}
print(trace_objective(y))
print(trace_objective(c(1, 2, 9)))
stopifnot(mean(y) == 3, mean(c(1, 2, 9)) == 4)
```
