# asm-038: A custom-model-at-scale review dossier

Tutorial mode. Stage: advanced. Direct prerequisites: `asm-035`, `asm-036`, `asm-037`.

## Starting point and result

The final chapter assembles a reviewable custom-model-at-scale design. A complete design explains the probability model, parameter ownership, valid decomposition, numerical implementation, data delivery, runtime preparation and evidence. Choosing Spark plus a differentiation library is only one part of that design. This is a worked synthesis, not an exam or a certificate of expertise.

## Mechanism: connect each claim to its evidence

Start with the objective, including constants that matter for comparisons, parameter transforms, weights, penalties and missing-data policy. Identify the independent units and any coupled latent structure. Derive the local summaries and global merge operation. Specify the optimizer's coordinates and stop diagnostics. Then define the prepared runtime and artifact/state lifecycle.

Evidence has several levels. Parsed source proves syntax. A serial mathematical oracle checks a bounded numerical claim. Actual Spark execution checks distributed dataflow for that fixture. Compiler/runtime probes check native artifacts. Browser delivery checks the learner surface. Native architecture and real multi-host or GPU acceptance are separate again. A report should name which level supports each statement.

The project investigation record therefore includes source/image hashes, runtime versions, actual topology, accepted/unique IDs, loss and gradient errors, optimizer diagnostics, timing scope and known unsupported cases. “Passed” without those boundaries is too ambiguous to guide a future maintainer or learner.

## Worked case: a global nonlinear Gaussian fit

Assume independent observations follow a nonlinear decay curve with shared amplitude, rate, baseline and scale. Use Spark to prepare validated features and distribute additive likelihood contributions. A prepared Torch or TMB evaluator computes local values and derivatives at one shared parameter vector. The driver combines sums and count/weight information, applies a penalty once if declared and runs the bounded optimizer.

Validate fixed-parameter loss and gradients against serial computation, then compare fitted parameters and stationarity diagnostics. Test unequal partitions, changed batch sizes and invalid inputs. Use a finite-grid or small closed-form subcase to diagnose identifiability. Record that local ARM64 CPU execution is not a GPU or multi-node benchmark.

## Worked case: a hierarchical spatial model

Now let neighboring locations share correlated latent effects. The previous arbitrary partition reduction is invalid if it drops cross-partition covariance. A valid design may prepare data in Spark and solve the coupled model with a sparse TMB formulation on a machine that fits it, or partition by truly independent connected components. A specialized distributed solver is another research project with its own proof and tests.

Compare a small joint model with any proposed approximation. Quantify the determinant and mode differences rather than hiding them behind optimizer convergence. If the scientific question requires posterior uncertainty, evaluate whether a PyMC reference or another Bayesian method is needed. The computational architecture must follow the target, not force the target into a convenient API.

## Failure diagnosis

When an integration fails, locate the layer: data coverage, schema/transport, parameter identity, native compatibility, derivative arithmetic, optimizer behavior or model assumptions. Repair the smallest failing contract and retain a regression case. Increasing resources without identifying the layer often makes a wrong computation more expensive.

## Interview discussion

**How would you explain this system to a reviewer?** Begin with one mathematical objective and show exactly which worker owns each term, where gradients are produced and how duplicates or omissions are detected. Then show the serial oracle and actual execution receipt.

**What remains outside this course's small fixtures?** Production security, operational capacity, larger-scale numerical conditioning and platform-specific performance require their own acceptance. The course supplies mechanisms and bounded implementations that make those questions precise.

## Review actual package studies

The [native modeling studies](../../../packages/spark-tmbad/studies/README.md)
provide executable shared-fit, complete-unit and independent-fit examples.
Their newer guide separates named Gaussian MAP, exact L1, overdispersion,
structural-zero, robust-response and correlated-panel targets. A study identifier
in the design catalog is not automatically an implemented or executed study;
consult the implementation matrix and source-bound observed records.

The named-target comparisons used sixteen independent generated datasets per
scenario, with held-out future responses and analytic optima/KKT checks. The
Gaussian prior and exact L1 targets keep their selected coefficient masks and
fixed known scale explicit. Sum and weighted-mean variants retain the same
statistical target after scaling. A penalty on every optimizer coordinate,
including a log scale, would be a different experiment.

For family comparisons, choose predictive scores that measure the same response
distribution. A beta-binomial and binomial both score counts with their declared
trial totals. A zero-inflated Poisson includes zeros from both its structural
component and ordinary Poisson component; a hurdle model has a separate positive
count normalization. A fitted native beta-binomial comparison reached its
declared precision bound and failed line search. The study retained that failure
and withheld predictions instead of promoting a nearly stationary point to an
accepted fit.

The [optional R reference studies](../../../packages/spark-tmbad/reference/QUALIFICATION.md)
include actual nonlinear, panel and upstream AR(1) conditional forecasts. Their
held-out extension checks that training values and fitted parameters remain
unchanged before evaluating newly generated future outcomes. Each independent
dataset contributes one average over its correlated forecast horizons. Treating
every horizon as an independent replication would understate Monte Carlo error.

Keep two denominators visible. Conditional predictive performance averages only
successful fits. Procedural coverage includes attempted datasets for which the
procedure produced no accepted interval. A low error among successful fits can
coexist with an unacceptable failure rate. Likewise, observing coverage of one
in a small batch, with zero empirical variation, does not establish certain
coverage. These finite simulations demonstrate the computation and its limits;
they are not production-scale benchmarks or universal calibration guarantees.

The source review should therefore retain the generator, exact training/future
data identities, model and prior definitions, runtime artifact, installed package,
all fit outcomes, and the aggregation source. Reusing a dataset under a new seed
label must not create another independent replication. The accepted study
aggregator checks data identities as well as labels and refuses such reuse.

## Reproduce a qualified native study

Follow the [independent package setup](../../../packages/spark-tmbad/docs/PREPARATION.md)
first. The commands below run inside that explicitly prepared Linux environment,
from the copied package directory. They require the matching installed frontend,
native artifact and JAR. They do not install a dependency or start from an
ordinary classroom pad. With the package's Docker image, use its documented
Spark entrypoint or an explicitly selected shell for this command sequence.

```sh
mkdir /work/model-review-01
spark-submit --master 'local[2]' \
  --jars /opt/spark-tmbad/spark-tmbad.jar \
  studies/run_native_extended.py \
  --manifest /opt/spark-tmbad/artifact.json \
  --fixtures studies/fixtures/native020-smoke.json \
  --study sim-003 --replicate 0 \
  --output /work/model-review-01/gaussian-prior-r0.json
spark-submit --master 'local[2]' \
  --jars /opt/spark-tmbad/spark-tmbad.jar \
  studies/run_native_extended.py \
  --manifest /opt/spark-tmbad/artifact.json \
  --fixtures studies/fixtures/native020-smoke.json \
  --study sim-004 --replicate 0 \
  --output /work/model-review-01/exact-l1-r0.json
python studies/aggregate_extended.py \
  --reports /work/model-review-01/gaussian-prior-r0.json \
    /work/model-review-01/exact-l1-r0.json \
  --output /work/model-review-01/summary.json
```

Retain the whole fresh output directory on explicitly mounted owned storage if
the environment is temporary. These two shards are one replication per scenario;
their Monte Carlo errors remain null. Compare their model/target definitions,
analytic optimum or KKT checks, accepted IDs, held-out scores and artifact hashes.
Then read the [observed studies guide](../../../packages/spark-tmbad/studies/README.md)
for the separately retained expanded repetitions and failure accounting.

For correlated groups, `sim-028` uses a complete-unit population fit and separate
existing/new-group forecast targets. `sim-009` instead summarizes independent
group fits without collecting all per-group fitted models to the driver. They
answer different questions even when both have a grouping column. Keep the
group-level failures separate from the number of independent dataset replications.

The [optional R reference](../../../packages/spark-tmbad/reference/README.md)
has a separate prepared library and runtime. Its nonlinear and panel forecasts,
upstream glmmTMB family/covariance cases and conjugate posterior checks do not
make R a dependency of the native package. Use its own commands and exact
qualification index when selecting a serial reference. Never compare a MAP
target to an unpenalized likelihood while labeling the difference numerical error.
