# web-059: Deploying PHP: containers, web servers and operations

## Level and prerequisites

Advanced; allow about 150 minutes, with extra time for independent practice. Direct prerequisites: `web-058`

## Learning objectives

Design a release plan for the study planner with durable storage. Explain what evidence is needed before publishing an image as ready. Use PHP-FPM, reverse proxy and document root accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

A production PHP deployment commonly separates an HTTP server or reverse proxy from a PHP process manager. PHP-FPM manages FastCGI workers; it is not itself a general browser-facing HTTP server. A web server routes appropriate requests to the runtime and serves approved static assets. The public document root should contain only files intended for delivery, keeping source configuration, dependency metadata, private data and secrets outside that boundary.

A container packages a runtime and application, while volumes or external storage hold durable state. Rebuilding an image does not migrate a database automatically. A release needs a plan for schema changes, compatibility, rollback, backup and restore. A backup job reporting success is weaker evidence than an actual restore that recreates the expected data and application behavior.

### Key terms

- **PHP-FPM:** The FastCGI process manager that runs a pool of PHP workers behind a web server.
- **Reverse proxy:** A server, such as nginx, that receives client requests and forwards them to the application.
- **Document root:** The only directory a web server serves directly; source code, secrets and data stay outside it.
- **Secret:** A credential such as a database password that is supplied at runtime and never committed or built into an image.
- **Migration:** A versioned, repeatable change to the database schema, applied as a deliberate deployment step.

## Syntax anatomy and mechanism

Use reviewed locked dependencies and a deliberate image tag or digest policy. Supply secrets through a controlled runtime mechanism rather than baking them into images or committing them. Enable appropriate error logging without displaying internal stack traces publicly. TLS termination and trusted proxy headers require an explicit network ownership policy; do not trust forwarded identity or scheme headers from arbitrary clients.

## Contrast case: deleting a secret in a later image layer

This build copies an environment file, uses it, then removes it. The final container has no .env file. Consider the image history instead.

```text
FROM php:8.4-fpm
COPY .env /app/.env
RUN php /app/bin/warm-cache.php
RUN rm /app/.env

# secret supplied at run time instead
# docker run --env-file ./prod.env app:1.4.2
```

Each instruction creates a layer, and the COPY layer still contains the file even though a later RUN removes it from the merged view. Anyone who can pull the image can extract that layer and read the secret. The fix is not another delete but a different flow: keep the secret out of the build entirely, supply it when the container starts through a controlled mechanism, and rotate any secret that was already pushed in an image.

## Debugging and common mistakes

Do not expose the PHP built-in learning server to the public internet and call it a production architecture. Avoid broad prune commands as deployment recovery. A successful image build cannot establish application correctness or backup recoverability.

A plausible plan or one successful request can hide an untested failure path. Record each request, response and stored state, and repeat the original failing case after every change.
