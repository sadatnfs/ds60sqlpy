## Outcome and mechanism

Execute fixed independent tasks with two local PSOCK workers, preserve deterministic task results and close worker processes on every ordinary exit path.

Parallel evaluation is appropriate when tasks can compute independently and the cost of starting workers and transferring inputs is justified. A PSOCK cluster launches separate R processes and communicates over sockets. Workers do not inherit the caller's whole interactive workspace. Send small explicit inputs and use self-contained task functions; avoid hidden global state, shared output files and dependencies that were never prepared in the worker.

The classroom example uses exactly two local PSOCK workers. The integer worker count denotes local processes, and master is fixed to loopback 127.0.0.1. The job has two CPUs, a three-gigabyte memory limit, a 128-process limit, a 32 MiB scratch allowance and a total deadline of at most 120 seconds. These are resource boundaries for this prepared profile, not an invitation to launch remote workers or allocate one worker per detected host core. The fixed tiny fixtures need no external service or package installation.

An owning function starts the cluster, immediately registers on.exit(stopCluster(...)), evaluates a callback and returns its result. That handler covers normal return and ordinary R errors. A forced timeout or cancellation can terminate the R process before an R cleanup handler runs, so the supervisor must also terminate and reap descendants. The prepared isolated runtime was separately checked for success and forced-timeout cleanup. The lesson's on.exit pattern alone is not proof of that runtime behavior.

parLapply returns results in input order. Its static scheduling and the load-balanced parLapplyLB can assign tasks to different worker processes. A pure deterministic function gives the same result either way. A function using worker-local random state may not: changing task assignment changes which stream a task consumes. clusterSetRNGStream assigns streams to workers, which is useful for a fixed assignment, but does not by itself promise task identity across arbitrary schedules.

The second example assigns an L'Ecuyer-CMRG stream to each task before dispatch. Each task carries an integer identifier and its complete stream state, then resets its worker's RNG to that stream before drawing. Results are reordered by task identifier for comparison. Reversing dispatch order or using load balancing now preserves each task's random values under the same prepared runtime. This is reproducibility of a declared computation, not a claim that arbitrary numerical algorithms are bit-identical across versions and architectures.

Tiny examples are intentionally poor speed benchmarks: process startup can exceed the numerical work. Their purpose is to establish explicit inputs, scheduling-independent identity, bounded concurrency and resource ownership. Profile a real equivalent workload before choosing parallel execution, and retain a sequential reference for debugging. Errors should be surfaced as failed tasks rather than converted silently to zero-valued results.

## Vocabulary

| Term | Meaning |
| --- | --- |
| PSOCK cluster | Separate R processes communicating through sockets. |
| Task purity | A task result depends on explicit inputs rather than shared mutable effects. |
| Serialization | Encoding inputs and results for transfer between R processes. |
| Task-owned RNG stream | A random-number stream assigned to a task identity instead of a worker identity. |
| Cleanup handler | An on.exit action that releases a function-owned resource on ordinary return or error. |

## Read the syntax

makePSOCKcluster(2L,master="127.0.0.1",rscript_args="--vanilla") starts exactly two local fresh R workers. parLapply(cluster,tasks,fun) maps a self-contained function. on.exit(stopCluster(cluster),add=TRUE) belongs immediately after successful construction. nextRNGStream supplies the next L'Ecuyer stream; each task installs its own complete .Random.seed before drawing.

## Worked examples

### Example 1: Compare a deterministic parallel result with a serial reference

```r
with_two_workers <- function(fun) {
  cluster <- parallel::makePSOCKcluster(2L,
    master = "127.0.0.1",
    rscript_args = "--vanilla", setup_timeout = 10, timeout = 30
  )
  on.exit(parallel::stopCluster(cluster), add = TRUE)
  fun(cluster)
}

tasks <- list(1:3, 4:6)
serial <- lapply(tasks, function(x) sum(x^2))
parallel_result <- with_two_workers(function(cluster) {
  parallel::parLapply(cluster, tasks, function(x) sum(x^2))
})
stopifnot(identical(serial, parallel_result), identical(unlist(parallel_result), c(14, 77)))
print(unlist(parallel_result))
```

**Expected observation:** Squared-sum results 14 and 77, equal to the serial computation.

Each task receives its own small vector and returns a scalar. No worker reads an unexported global name. The owning function stops both workers before the result is used. This checks equivalence rather than claiming a speedup.

### Example 2: Random values remain attached to task identities

```r
with_two_workers <- function(fun) {
  cluster <- parallel::makePSOCKcluster(2L,
    master = "127.0.0.1",
    rscript_args = "--vanilla", setup_timeout = 10, timeout = 30
  )
  on.exit(parallel::stopCluster(cluster), add = TRUE)
  fun(cluster)
}
make_tasks <- function(n, seed) {
  old_kind <- RNGkind()
  had_seed <- exists(".Random.seed", envir = .GlobalEnv, inherits = FALSE)
  if (had_seed) old_seed <- get(".Random.seed", envir = .GlobalEnv)
  on.exit(
    {
      do.call(RNGkind, as.list(old_kind))
      if (had_seed) assign(".Random.seed", old_seed, envir = .GlobalEnv)
      else if (exists(".Random.seed", envir = .GlobalEnv, inherits = FALSE)) rm(".Random.seed", envir = .GlobalEnv)
    },
    add = TRUE
  )
  RNGkind("L'Ecuyer-CMRG")
  set.seed(seed)
  stream <- .Random.seed
  tasks <- vector("list", n)
  for (i in seq_len(n)) {
    tasks[[i]] <- list(id = i, seed = stream)
    stream <- parallel::nextRNGStream(stream)
  }
  tasks
}
draw_task <- function(task) {
  assign(".Random.seed", task$seed, envir = .GlobalEnv)
  list(id = task$id, values = stats::rnorm(4))
}
order_results <- function(results) {
  results[order(vapply(results, function(x) x$id, integer(1)))]
}

tasks <- make_tasks(4L, 2026)
results <- with_two_workers(function(cluster) {
  static <- parallel::parLapply(cluster, tasks, draw_task)
  balanced <- parallel::parLapplyLB(cluster, rev(tasks), draw_task)
  list(static = order_results(static), balanced = order_results(balanced))
})
stopifnot(identical(results$static, results$balanced))
stopifnot(!identical(results$static[[1]]$values, results$static[[2]]$values))
print(vapply(results$static, function(x) mean(x$values), numeric(1)))
```

**Expected observation:** Four task means; exact equality by identity across the two schedules.

The same task streams are sent under two scheduling choices and opposite input orders. Sorting by the returned identifier makes the comparison about task identity. Distinct task streams also prevent the mistake of resetting every task to the same seed.

## Reference review

The reference uses three tasks while keeping concurrency fixed at two. It compares a structured result with a sequential oracle and independent arithmetic 14,77,8. The RNG comparison changes both schedule policy and task order, then compares by explicit identifier.

A deliberately failed task is propagated through the owning function, exercising ordinary on.exit cleanup. The separate runtime qualification covers forced timeout and descendant reaping; this script does not claim that catching an error or reaching a final marker proves that every external termination path is safe. Small fixtures demonstrate contracts rather than parallel speed.
