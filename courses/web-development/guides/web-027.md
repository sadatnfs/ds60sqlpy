# web-027: Accessible form feedback with a pure validation function

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-026`

## Learning objectives

Build a local form with preserved input and linked validation feedback. Explain which validation logic must be repeated on the server. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

Validation becomes easier to test when a pure function receives data and returns errors without touching the document. The browser layer then displays those errors and moves focus only when it helps recovery. This separation lets the same input contract be tested with normal, missing and boundary values before considering visual presentation. It does not remove the need for backend validation.

An error summary gives a user an overview after an attempted action. Field-level messages explain how to repair specific values. Connect those messages to controls and preserve entered values. Avoid announcing a long stream of errors on every keystroke. The timing of feedback is a product decision that should reduce confusion rather than punish incomplete typing.

## Syntax anatomy and mechanism

The reference uses a button to validate local values without submitting a form. Convert the input string carefully, reject empty strings before Number conversion and check Number.isFinite. Return an error list, then render it with textContent. Set aria-invalid only after a failed check. A valid result is a local observation, not a stored request.

## Classroom execution and offline inputs

Choose **HTML browser preview** in the classroom. The pad is one complete HTML document with embedded CSS and, where taught, embedded JavaScript. Its preview is isolated from the classroom and recreated on each run. It does not contact a server, submit real forms, read cookies, fetch assets or load a CDN. All fixtures are inline and synthetic. The browser uses its native HTML parser, so classic-script ordering, shared lexical bindings, inline modules and real DOMContentLoaded/load events keep their browser semantics. External module imports remain blocked. Navigation metadata such as base and meta http-equiv is rejected explicitly. On any supported host, the browser renders the document while Docker serves the classroom. No host compiler is needed.

Run your own source after implementing the task. A reference's checks inspect only the named initial conditions. Its success message is not a full accessibility audit, proof of responsive behavior at every size, or evidence that you implemented the solution yourself. Inspect actual output after keyboard input, resizing and changes. Save your source before comparing with a reference. The document and its CSS share one saved pad; HTML and CSS remain different languages within that artifact.

## Worked example / walkthrough

### Worked example 1: A testable rule

Empty input is checked before numeric conversion.

```javascript
function validate(value) {
  if (value.trim() === '') return 'Enter minutes.';
  const minutes = Number(value);
  return Number.isFinite(minutes) && minutes >= 5 && minutes <= 120 ? '' : 'Use 5 to 120 minutes.';
}
```

**Expected observation:** Empty, nonfinite and out-of-range values return a useful error.

### Worked example 2: Safe feedback

The message is data rather than markup.

```javascript
error.textContent = message;
input.setAttribute('aria-invalid', message ? 'true' : 'false');
```

**Expected observation:** The visible and semantic error states agree.

## Six progressive exercises

### Exercise 1: Predict Number('') and explain the validation hazard.

**Expected evidence:** It produces zero, so an explicit empty-input check prevents misleading acceptance or errors.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add the upper-bound case to a validation table.

**Expected evidence:** 120 is accepted and 121 is rejected under the declared inclusive bounds.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a local form with preserved input and linked validation feedback.

**Expected evidence:** A failed attempt identifies the problem without clearing the user's value.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a message shown visually but not associated with its control.

**Expected evidence:** Use a stable message id and aria-describedby on the input.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test empty, whitespace, negative, nonnumeric and valid values.

**Expected evidence:** Each produces the declared result with no uncaught exception.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain which validation logic must be repeated on the server.

**Expected evidence:** All acceptance and authorization rules must be enforced independently of client behavior.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not use a success toast as proof a server saved anything. Avoid inserting untrusted error strings as HTML. Test both the pure rule and the actual focus/announcement behavior.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain validation function, error summary, aria-invalid without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
