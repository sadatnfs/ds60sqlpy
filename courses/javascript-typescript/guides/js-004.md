# js-004: Functions, scope and closures

## Level and prerequisites

Beginner, approximately 90 minutes. Direct prerequisites: `js-003`

## Learning objectives

Explain lexical scope, closure, default parameter, receiver with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Use add with 2, 3 and with negative 1, 1. The final task tests reject an invalid factory configuration.

## Purpose and mental model

Functions define reusable computations, and lexical scope determines which bindings a function can read. A closure retains access to bindings from the environment where it was created. Those bindings can hold state across calls, which is useful for a small counter or factory. Closures do not automatically copy every captured value. A shared var binding in a loop can make several functions observe the same final value, while let creates the intended per-iteration bindings.

Default parameters apply when an argument is undefined, not when it is null. Ordinary function this depends on the callsite; arrow functions capture this lexically. A clear function contract should distinguish arguments, returned values, mutable captured state and receiver dependence. Prefer explicit parameters when a closure would hide important dependencies.

## Vocabulary and concepts

**Lexical scope:** Binding lookup determined by where code is written.

**Closure:** A function retaining access to its surrounding bindings.

**Default parameter:** A fallback used when the supplied argument is undefined.

**Receiver:** The this value used by an ordinary method call.

## Syntax anatomy and execution trace

A function declaration introduces a named callable; an arrow expression creates a function value. Returning a nested function forms a closure over its surrounding bindings. let and const are block-scoped, while var is function-scoped. The default syntax name=value is evaluated when the argument is undefined. Use call or bind only when receiver behavior is part of the contract, not as a substitute for understanding the callsite.

## Worked example / walkthrough

### Example A: Call a pure function

The function depends only on its arguments and changes no external state. Boundary examples can be tested independently.

```javascript
import { strict as assert } from 'node:assert';

function counter(step = 1) {
  if (!Number.isInteger(step) || step <= 0) throw new TypeError('positive integer step required');
  let value = 0;
  return () => { value += step; return value; };
}

export async function verify() {
  // Worked example
  {
    function add(left, right) { return left + right; }
    assert.equal(add(2, 3), 5);
    assert.equal(add(-1, 1), 0);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** 5 and 0.
### Example B: Build independent closures

Each factory call creates a separate captured binding. Equal initial values do not imply shared counter state.

```javascript
import { strict as assert } from 'node:assert';

function counter(step = 1) {
  if (!Number.isInteger(step) || step <= 0) throw new TypeError('positive integer step required');
  let value = 0;
  return () => { value += step; return value; };
}

export async function verify() {
  // Worked example
  {
    const first = counter();
    const second = counter();
    assert.equal(first(), 1);
    assert.equal(first(), 2);
    assert.equal(second(), 1);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** first 1, 2; second 1.

## Prediction before your attempt

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

## Exercises

1. **Call a pure function.** Use add with 2, 3 and with negative 1, 1.
   **Expected:** 5 and 0.
   **Verify:** Record the observed value, exception or browser state and compare it with that expectation.

2. **Build independent closures.** Create two counters; increment the first twice and the second once.
   **Expected:** first 1, 2; second 1.
   **Verify:** Record the observed value, exception or browser state and compare it with that expectation.

3. **Compare let and var loop capture.** Create three closures in a let loop and three in a var loop.
   **Expected:** let returns 0, 1, 2; var returns 3, 3, 3.
   **Verify:** Record the observed value, exception or browser state and compare it with that expectation.

4. **Distinguish undefined from null defaults.** Call a greeting function with no argument, undefined and null.
   **Expected:** default used for the first two; null preserved.

5. **Observe an ordinary receiver.** Call a method through its object and then with an explicit alternate receiver.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

## Progressive hints

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
