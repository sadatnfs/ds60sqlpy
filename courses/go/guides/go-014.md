# go-014: Table-driven tests and useful counterexamples

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-013

## Learning objectives

Write table-driven checks with exact endpoints and a counterexample that rejects a plausible wrong implementation. Along the way, explain test oracle, boundary case, regression case; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Tests are executable claims about behavior. A test should distinguish the intended implementation from a plausible wrong one. Table-driven testing records input and expectation as data, then applies the same assertion logic to each case. Normal cases show use, boundary cases define edges, and invalid cases define failure behavior. A reference example in a single pad uses explicit checks; a real Go test lives in a file ending _test.go and receives *testing.T. Tests must not depend on global ordering, current time or a network service unless those dependencies are deliberately controlled. Coverage describes executed code, not the strength of the assertions.

## Vocabulary and concepts

- **Test oracle:** The independent rule determining an expected result.
- **Boundary case:** An input at the edge of an accepted domain.
- **Regression case:** A retained input that exposes a previously observed defect.

## Syntax anatomy and reasoning

A test table is often a slice of anonymous structs with name, input and want fields. In a prepared project, func TestName(t *testing.T) is discovered by go test, and t.Run creates named subtests. Compare actual and expected values directly; include the case name in failure messages. Fuzz tests describe invariants across generated inputs, but they need a bounded execution budget and persistent regression seeds. Do not treat successful compilation as a behavior test.

## Worked example / walkthrough

### Worked example 1: Build a named table

Test clamp with values below, inside and above the range 0 to 10.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func clamp(x int) int {
	if x < 0 {
		return 0
	}
	if x > 10 {
		return 10
	}
	return x
}
func mutantClamp(x int) int {
	if x < 0 {
		return 0
	}
	if x > 9 {
		return 9
	}
	return x
}

func main() {
	// Build a named table
	{
		cases := []struct{ in, want int }{{-2, 0}, {4, 4}, {12, 10}}
		for _, tc := range cases {
			check(clamp(tc.in) == tc.want, "clamp table")
		}
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The outputs are 0, 4 and 10.

A wrong implementation that only returns its input fails the outside cases; one that always returns an endpoint fails the interior case.

### Worked example 2: Include exact endpoints

Test clamp at 0 and 10.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func clamp(x int) int {
	if x < 0 {
		return 0
	}
	if x > 10 {
		return 10
	}
	return x
}
func mutantClamp(x int) int {
	if x < 0 {
		return 0
	}
	if x > 9 {
		return 9
	}
	return x
}

func main() {
	// Build a named table
	{
		cases := []struct{ in, want int }{{-2, 0}, {4, 4}, {12, 10}}
		for _, tc := range cases {
			check(clamp(tc.in) == tc.want, "clamp table")
		}
	}

	// Include exact endpoints
	{
		check(clamp(0) == 0 && clamp(10) == 10, "endpoints")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Both endpoints are preserved.

Endpoint tests distinguish inclusive boundaries from off-by-one policies. They should be named in the API contract.

## Exercises

### Exercise 1: Build a named table: change one input

Copy worked example 1, change `cases := []struct{ in, want int }{{-2, 0}, {4, 4}, {12, 10}}` to `cases := []struct{ in, want int }{{-2, 1}, {4, 4}, {12, 10}}` and predict the failure before running; then restore the line.

**Expected:** The edited run panics with `clamp table` because `clamp(tc.in) == tc.want` no longer holds.

**Verify:** Restoring `cases := []struct{ in, want int }{{-2, 0}, {4, 4}, {12, 10}}` makes the check pass again with the worked observation: the outputs are 0, 4 and 10.

### Exercise 2: Include exact endpoints: diagnose an edited check

A careless edit rewrote the check in worked example 2 as `check(clamp(1) == 0 && clamp(10) == 10, "endpoints")`. Explain the failure, then restore it.

**Expected:** The defective run panics with `endpoints`; after restoring `check(clamp(0) == 0 && clamp(10) == 10, "endpoints")`, both endpoints are preserved.

**Verify:** The edited check fails with message `endpoints` for a state that `clamp(0) == 0 && clamp(10) == 10` accepts.

### Exercise 3: Check idempotence

Apply clamp twice to values -2, 4 and 12.

**Expected:** Applying it twice gives the same result as once.

**Verify:** Your solution must keep `clamp(clamp(x)) == clamp(x)` true. Control: changing `check(clamp(clamp(x)) == clamp(x), "idempotence")` to `check(clamp(clamp(x)) != clamp(x), "idempotence")` panics with message `idempotence`; revert it.

### Exercise 4: Reject a plausible mutant

Compare the correct clamp with a mutant that incorrectly caps at 9.

**Expected:** Input 10 distinguishes them.

**Verify:** Your solution must keep `clamp(10) != mutantClamp(10)` true. Control: changing `check(clamp(10) != mutantClamp(10), "mutant rejected")` to `check(clamp(10) == mutantClamp(10), "mutant rejected")` panics with message `mutant rejected`; revert it.

### Exercise 5: Cover a range invariant

Check all integer inputs from -20 through 20.

**Expected:** Every result lies between 0 and 10.

**Verify:** Your solution must keep `v >= 0 && v <= 10` true. Control: changing `check(v >= 0 && v <= 10, "range invariant")` to `check(v > 0 && v <= 10, "range invariant")` panics with message `range invariant`; revert it.

### Exercise 6: Transfer a fresh regression

Retain input 11 as a regression for an implementation that forgets the upper cap.

**Expected:** The result is 10.

**Verify:** Your solution must keep `clamp(11) == 10` true. Control: changing `check(clamp(11) == 10, "upper regression")` to `check(clamp(11) != 10, "upper regression")` panics with message `upper regression`; revert it.

## Common pitfalls and diagnosis

A test that passes for the wrong implementation is the main danger. A table built only from interior values passes an off-by-one cap, and a property such as idempotence also passes for a constant function. Pair each property with concrete boundary cases. Another trap is computing the expected value with the code under test; the oracle must come from the specification, not from clamp itself.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Build a named table: change one input

1. Restate the expected observation: The outputs are 0, 4 and 10.
2. Each row pairs an input with a want. Which rows lie outside the 0 to 10 range?
3. clamp(-2) is 0, so the edited row expects the wrong value and the table check fails on its first row. The function is fine; the oracle in the table changed.

### Hint for investigation 2: Include exact endpoints: diagnose an edited check

1. Restate the expected observation: Both endpoints are preserved.
2. An inclusive endpoint maps to itself. What should clamp return at exactly 0 and at exactly 10?
3. clamp(1) returns 1 because 1 is inside the range, so `clamp(1)==0` is false. The endpoint case must test exactly 0, the inclusive lower boundary.

### Hint for investigation 3: Check idempotence

1. Restate the expected observation: Applying it twice gives the same result as once.
2. Idempotence compares clamp(clamp(x)) with clamp(x). Which inputs change on the first call?
3. This is a property rather than a single expected output.

### Hint for investigation 4: Reject a plausible mutant

1. Restate the expected observation: Input 10 distinguishes them.
2. The mutant caps at 9. Which single input lies between the two caps?
3. A test's value is visible when it rejects a realistic defect.

### Hint for investigation 5: Cover a range invariant

1. Restate the expected observation: Every result lies between 0 and 10.
2. Every result must lie in the closed range. Does the loop include both -20 and 20?
3. This bounded exhaustive set supports the invariant for its chosen domain.

### Hint for investigation 6: Transfer a fresh regression

1. Restate the expected observation: The result is 10.
2. 11 is the smallest value above the cap. What must clamp return for it?
3. The smallest counterexample just beyond the boundary often explains the defect better than a large random value.
