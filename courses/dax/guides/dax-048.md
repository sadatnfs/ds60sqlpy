## The question and the mechanism

Distinguish a visual running total from a reusable semantic-model measure.

A visual calculation belongs to a visual and operates over the data and structure supplied to that visual. It does not receive the complete transaction model merely because its expression uses DAX. The fields must be available in that visual's shape, and relationship-dependent functions such as RELATED or USERELATIONSHIP are not available in that scope according to the reviewed documentation.

The synthetic visual snapshot has January 2025 revenue 67 and February 2025 revenue 56. A running sum in ascending month order gives 67 then 123. Reversing the displayed order gives 56 then 123. The same two aggregated values produce different intermediate results because position in the visual is part of the calculation's input.

The reference queries below reproduce the running-sum arithmetic over explicit literal snapshots. They are not executions of Power BI visual calculations. The actual visual expression RUNNINGSUM([Revenue]) belongs to a separately prepared visual with its axis, order and reset behavior defined. Keep model measures for reusable semantic logic and use visual calculations only when their visual-scoped definition fits the question.

## Vocabulary and expression anatomy

The literal Position column makes the visual order explicit. ADDCOLUMNS evaluates a current position, and SUMX sums snapshot values at positions up to it. This expansion explains the arithmetic of the named flat visual. A hierarchical visual can additionally require partition/reset rules that this example does not emulate.

Concepts to explain in your own words: **visual calculation**, **RUNNINGSUM**, **visual order**, **aggregation grain**, **scope**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

### Feature and version boundary

Reviewed 2026-10-25: Microsoft's visual-calculation documentation describes a separate visual-scoped facility available in Desktop and Service. This offline course does not provide that facility, a visual editor or external execution; it supplies explicit snapshots and arithmetic explanations.

### Case A: Ascending month snapshot

**Starting context:** A supplied flat visual snapshot in ascending month order; arithmetic expansion only.

```dax
EVALUATE
VAR VisualRows = DATATABLE ( "Position", INTEGER, "Month", STRING, "Revenue", INTEGER, { { 1, "January2025", 67 }, { 2, "February2025", 56 } } )
RETURN ADDCOLUMNS ( VisualRows, "RunningRevenue", VAR CurrentPosition = [Position] RETURN SUMX ( FILTER ( VisualRows, [Position] <= CurrentPosition ), [Revenue] ) )
ORDER BY [Position]
```

**Context trace:**

1. The first position contains January revenue 67.
2. The second position includes 67 plus February 56.
3. Running values are 67 and 123.

**Hand-derived worked-reference result:**

| Position | Month | Revenue | RunningRevenue |
| --- | --- | --- | --- |
| 1 | January2025 | 67 | 67 |
| 2 | February2025 | 56 | 123 |

The snapshot values are already monthly aggregates. Reaching back to individual Sales rows would change the scope and require model-level logic.

Hand-derived expansion over a named visual snapshot. No Power BI visual was created or executed.

### Case B: Reversed visual order

**Starting context:** The same monthly values in descending month order; no change to their underlying amounts.

```dax
EVALUATE
VAR VisualRows = DATATABLE ( "Position", INTEGER, "Month", STRING, "Revenue", INTEGER, { { 1, "February2025", 56 }, { 2, "January2025", 67 } } )
RETURN ADDCOLUMNS ( VisualRows, "RunningRevenue", VAR CurrentPosition = [Position] RETURN SUMX ( FILTER ( VisualRows, [Position] <= CurrentPosition ), [Revenue] ) )
ORDER BY [Position]
```

**Context trace:**

1. February 56 is now the first visible position.
2. January 67 is added at the second position.
3. The intermediate running value changes from 67 to 56 while the final sum remains 123.

**Hand-derived worked-reference result:**

| Position | Month | Revenue | RunningRevenue |
| --- | --- | --- | --- |
| 1 | February2025 | 56 | 56 |
| 2 | January2025 | 67 | 123 |

A cumulative-looking line can therefore change meaning when sort order changes. State its axis and ordering contract in the report.

Hand-derived expansion of a second visual snapshot, not execution of edited source or visual-calculation APIs.

## A deeper model or scope review

A separately prepared flat visual can use this expression when Revenue is present in its visual shape:

```dax
RunningRevenue = RUNNINGSUM ( [Revenue] )
```

It is a visual-calculation definition, not a persisted semantic-model measure or a complete DAX query. The two query expansions above explain the named snapshots without claiming to reproduce every visual-axis feature.

## Progressive hints

1. The visual-scoped population has one row.
2. Use the declared ascending positions.
3. The formula alone does not specify axis and ordering.
4. Relationship functions require a different evaluation scope.
5. Running accumulation can reset or continue across hierarchy boundaries.
6. The input is displayed aggregate cells, not necessarily raw observations.
