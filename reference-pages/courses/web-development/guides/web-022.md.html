web-022: CSS architecture, layers and maintainable components#

Level and prerequisites#

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: web-021

Learning objectives#

Build a small layered stylesheet with base, component and utility rules. Explain why important declarations complicate layer reasoning. Use cascade layer, component boundary and utility accurately when you explain a normal case and a failure case.

Purpose, vocabulary and mental model#

A stylesheet is easier to change when responsibilities are visible. Base rules describe document defaults, component rules describe reusable structures, and narrowly named utilities make deliberate local adjustments. These categories are a design choice, not a browser feature by themselves. Cascade layers let authors establish an explicit ordering among groups of declarations without continually increasing selector specificity.

For normal author declarations, later layers take priority over earlier layers, and unlayered normal declarations have priority over layered normal declarations. Important declarations reverse layer priority, which is one reason indiscriminate important usage makes reasoning harder. A good architecture keeps selectors understandable and limits the area a change can affect.

Key terms#

  • Cascade layer: A named @layer group of rules; for normal declarations, a later layer wins over an earlier one regardless of specificity.
  • Unlayered declaration: A normal declaration outside every layer, which takes priority over all layered normal declarations.
  • Utility: A narrowly named single-purpose class for a deliberate local adjustment, usually placed in the last layer.
  • Native CSS nesting: Writing a rule inside its parent rule, where & stands for the parent selector, such as &:hover.
  • Where pseudo-class: The :where() wrapper, which gives its selector zero specificity so later rules can override it easily.

Syntax anatomy and mechanism#

Declare the layer order once with @layer base, components, utilities. Put actual rules inside those layers. Native CSS nesting keeps a component's states next to its base rule: inside .note { ... }, the nested &:hover { ... } means .note:hover. Wrapping a selector in :where() sets its specificity to zero, so :where(.note) a is easy for a later component or utility rule to override. Keep component names tied to a useful responsibility such as lesson-card, not a visual accident such as left-blue-box. Test a component in more than one surrounding context to expose accidental ancestor dependencies.

Worked example / walkthrough#

Worked example 1: Explicit ordering#

Layer order establishes a policy before selectors compete within it.

@layer base, components, utilities;
@layer base {
  p {
    color: #172033;
  }
}
@layer components {
  .note {
    color: #0753a4;
    &:hover {
      text-decoration: underline;
    }
  }
}

Expected observation: The component layer can override the earlier base rule, and the nested &:hover rule applies to .note:hover inside the same layer.

Worked example 2: A narrow utility#

The utility's responsibility is explicit.

@layer utilities {
  .text-muted {
    color: #475569;
  }
}

Expected observation: The utility overrides earlier normal layered color declarations.

Contrast case: an unlayered selector beating a layered component#

Someone adds a quick fix outside every layer. Predict the color of .note paragraphs before inspecting.

@layer base, components, utilities;
@layer components {
  .note {
    color: #0753a4;
  }
}
/* quick fix, added outside any layer */
p {
  color: #172033;
}

For normal declarations, unlayered author styles rank above every named layer, and layer order is compared before specificity. The class selector .note is more specific than the type selector p, but that comparison never happens: the unlayered p rule wins, so note paragraphs turn #172033. Moving the quick fix into @layer base restores the intended outcome, because base is declared first and components now outranks it. The Styles panel lists the losing .note declaration as struck through, which is the evidence to look for.

Six progressive exercises#

Exercises 1, 4 and 6 keep their expected answers in the solutions file.

Exercise 1: Predict the layer winner for normal declarations.#

Progressive hint: Read the @layer order statement first, then compare which layer each rule is in.

Exercise 2: Move a component's rules into one named layer.#

Expected evidence: Its styling responsibility is grouped and discoverable.

Progressive hint: Wrap all of the component's rules in one @layer components block.

Exercise 3: Build a small layered stylesheet with base, component and utility rules.#

Expected evidence: The intended overrides work without escalating ids or important flags.

Progressive hint: Declare the three layers once at the top, then fill each layer with simple selectors.

Exercise 4: Diagnose an unlayered rule unexpectedly beating layered normal rules.#

Progressive hint: Find rules that are outside every @layer block.

Exercise 5: Place the component under a different parent.#

Expected evidence: Its behavior does not rely on an accidental deep ancestor selector.

Progressive hint: Move the component into another parent and see whether its styles still apply.

Exercise 6: Explain why important declarations complicate layer reasoning.#

Progressive hint: Mark one declaration !important in an early layer and predict the result.

Debugging and common mistakes#

A named architecture cannot prevent global selectors from leaking. Do not put every exception in an unlayered file because that silently bypasses the policy. Keep examples small enough to trace.

When a layered rule loses unexpectedly, look for an unlayered declaration; normal unlayered styles beat every layer regardless of specificity. When the utility color loses, check the @layer order statement, because the layer declared last wins for normal declarations, not the rule written last in the file.

The shared debugging routine covers what to record before each repair.
