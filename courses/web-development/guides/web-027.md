# web-027: Accessible form feedback with a pure validation function

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-026`

## Learning objectives

Build a local form with preserved input and linked validation feedback. Explain which validation logic must be repeated on the server. Use validation function, error summary and aria-invalid accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

Validation becomes easier to test when a pure function receives data and returns errors without touching the document. The browser layer then displays those errors and moves focus only when it helps recovery. This separation lets the same input contract be tested with normal, missing and boundary values before considering visual presentation. It does not remove the need for backend validation.

An error summary gives a user an overview after an attempted action. Field-level messages explain how to repair specific values. Connect those messages to controls and preserve entered values. Avoid announcing a long stream of errors on every keystroke. The timing of feedback is a product decision that should reduce confusion rather than punish incomplete typing.

### Key terms

- **Validation function:** A function that receives field values and returns a list of errors, kept separate from the code that updates the page.
- **Pure function:** A function whose result depends only on its arguments and that changes nothing outside itself, which makes it easy to test.
- **Error summary:** A list near the top of a form that names each error and links to its field, announced after a failed submission.
- **Aria-invalid:** The `aria-invalid` attribute, which tells assistive technology that a control's current value failed validation.

## Syntax anatomy and mechanism

The reference uses a button to validate local values without submitting a form. Convert the input string carefully: trim it, reject an empty string and require digits only before calling Number, because Number also accepts 0x1e (30), 1e2 (100), 0b111 (7) and 7.5, which the server rule in web-047 rejects. Return an error list, then render it with textContent. Set aria-invalid only after a failed check. A valid result is a local observation, not a stored request.

## Worked example / walkthrough

### Worked example 1: A testable rule

Empty input is checked first, and only whole decimal digits reach Number.

```javascript
function validate(value) {
  const text = value.trim();
  if (text === '') return 'Enter minutes.';
  if (!/^\d{1,3}$/.test(text)) return 'Use whole minutes from 5 to 120.';
  const minutes = Number(text);
  return minutes >= 5 && minutes <= 120 ? '' : 'Use 5 to 120 minutes.';
}
```

**Expected observation:** Empty, nonnumeric, hexadecimal, exponent, fractional and out-of-range values each return a useful error, and ' 30 ' is accepted after trimming.

### Worked example 2: Safe feedback

The message is data rather than markup.

```javascript
error.textContent = message;
input.setAttribute('aria-invalid', message ? 'true' : 'false');
```

**Expected observation:** The visible and semantic error states agree.

## Contrast case: a validator built on Number alone

This shorter rule skips the trim and the digit pattern from worked example 1. Feed it the same test inputs.

```js
function validateLoose(value) {
  const minutes = Number(value);
  if (Number.isNaN(minutes)) return 'Enter minutes.';
  return minutes >= 5 && minutes <= 120 ? '' : 'Use 5 to 120 minutes.';
}
```

`Number('')` and `Number('   ')` are 0, so an empty field reports Use 5 to 120 minutes instead of Enter minutes, which tells the reader the wrong problem. `Number('0x1e')` is 30, `Number('1e2')` is 100 and `Number('7.5')` is 7.5, so all three pass even though the server rule accepts only whole decimal minutes. `Number('0b111')` is 7, which this rule also accepts while the strict rule rejects it for not being plain digits. Worked example 1 rejects all of these before converting.

## Debugging and common mistakes

Do not use a success toast as proof a server saved anything. Avoid inserting untrusted error strings as HTML. Test both the pure rule and the actual focus/announcement behavior.

Keep the failing source, the viewport width and what you observed, then repair one cause at a time. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order, so inspect the element and its computed styles in the browser's developer tools instead of trusting the rendering alone.
