# dme-056: An evidence-backed engineering portfolio

## Make a claim another person can check

An engineering portfolio should demonstrate a problem, a reviewed contract, an implementation, meaningful tests and observed behavior. A screenshot of a successful run can be useful, but it rarely identifies the exact source, input, runtime or failure conditions. A reproducible bundle lets another person inspect those facts and decide what the evidence actually supports.

This capstone creates a small local bundle containing a source program, input file, README and execution receipt. It runs the program in a real child process, records runtime information and compares the output with an independent oracle. It then demonstrates three invalid claims: reusing evidence after source changes, treating a zero exit code as correctness, and using a local result to claim production readiness.

The fixture is intentionally elementary so the evidence model is transparent. Three positive counts, two, three and one, should produce three rows and total six. The same approach scales to the earlier data-product and ML capstones, where the contracts and runtime surfaces are richer. A portfolio does not need to hide small examples; it needs to explain which mechanisms they establish and where additional evidence is required.

## Bind evidence to the work that produced it

The receipt records source and input hashes, Python version, operating-system and machine labels, the command within the bundle, process return code, stdout hash, observed result, independent expected result and pass status. The important relationship is

\[
E\longrightarrow(H(\mathrm{source}),H(\mathrm{input}),\mathrm{runtime},\mathrm{observation}),
\]

where \(E\) is the evidence record. If source or input changes, the old receipt no longer describes the current work. A file modification time or a friendly result name is not an adequate replacement for that binding.

The program computes the oracle separately from the child script's expression. The child uses Python's sum function; the parent accumulates the declared positive counts and checks the row count. This independence is small but deliberate. A test that merely copies the implementation's output into its expected value cannot detect the wrong computation. Larger projects need similarly meaningful oracles, conservation checks, invariants or independently derived reference cases.

The runtime information is what this program can actually observe. It does not infer a Docker image digest, GPU capability or remote deployment topology from a platform string. The surrounding classroom and project checkers can provide additional source-bound native image and service evidence. Keep those records connected without pretending one local receipt contains every layer.

## Worked case 1: execute and validate a reproducible local bundle

`example_one()` writes the input file, reviewed source and a README explaining the command and expected answer. It launches the source through the current Python interpreter with an owned working directory, no interactive stdin and a bounded timeout. The child exits zero and emits a JSON object with three rows and total six.

The parent records the actual observation and validates a claim named `bounded-local-correctness`. Validation checks current source and input identities, process outcome and agreement with the independent oracle. The receipt is written to the bundle and also included in the classroom's structured output. This gives the learner inspectable evidence rather than only a message saying that a test passed.

The bundle in the pad is temporary. Its complete construction is maintained in the worked source, and the JSON receipt can be inspected through the results panel. For a lasting portfolio, copy a maintained full project into a learner-owned workspace, retain its source and checker outputs, and use its documented lifecycle. The data-product and inference-service projects provide such persistent project surfaces. Do not assume temporary pad files remain available after a run merely because their names appear in a report.

## Worked case 2: reject stale evidence, a wrong answer and an unsupported scope

The second case first records a valid receipt, then changes the child source so its total is one too high. Reusing the old receipt fails because its source hash no longer matches. This catches a common documentation mistake: retaining a successful historical result beside changed code and presenting it as current verification.

The changed program is then executed. It exits zero and prints total seven. The parent records that successful process completion but marks the semantic check failed because the independent expected total is six. A zero exit code means the program completed under its own execution rules; it does not prove that it answered the intended question correctly.

Finally, the example attempts a claim of multi-host production readiness. The validator rejects that scope because the receipt contains only bounded local-process evidence. It does not matter whether the local arithmetic had passed: no multi-host service, load, failure or recovery behavior was measured. The result report names all three rejected claims and shows the observed seven versus expected six.

## Organize a portfolio around engineering decisions

A strong project description begins with the consumer problem and acceptance criteria. Explain the input and output grain, time semantics, allowed failures and operational constraints. Show the architecture at the boundaries that matter: durable state, publication, model activation, request handling and recovery. Then explain why the chosen mechanisms fit those constraints and which alternatives were considered.

Include representative successful and failing cases. The unknown-route publication rejection, stale entity revision, missing feature, cancelled request and after-commit process exit are more informative than many copies of the same happy path. Preserve the exact source and inputs for those cases so a reviewer can reproduce the observed result. Explain failures as evidence about a boundary, not as embarrassing details to remove from the report.

A benchmark section should identify hardware, runtime, workload, measurement method and correctness checks. A model section should identify training and evaluation populations, feature availability, metrics, uncertainty and accepted use. A recovery section should identify the failed component, retained state, action taken and verified readback. Each claim should point to evidence at the corresponding level.

## Distinguish evidence tiers

Static parsing and linting can detect certain source defects without executing the behavior. Unit tests can exercise bounded logic and independent oracles. Native runtime tests establish behavior in a declared actual environment. Service tests add protocol and process boundaries. Persistence tests add restart and replacement behavior. Load and recovery exercises add further conditions. These tiers complement one another; none automatically implies every later tier.

Hardware qualification is also specific. CPU correctness does not establish GPU execution, and compilation does not establish kernel correctness or performance. One native architecture does not prove another architecture's runtime behavior. The classroom's optional CUDA and native multi-platform workflows keep those distinctions explicit. A portfolio should do the same rather than turning a capability in source code into an unmeasured performance claim.

Evidence also has a time and version boundary. Dependency upgrades, changed configuration, new data or altered source may require renewed checks. Preserve historical receipts as historical evidence and create new ones for changed candidates. Do not edit an old report's version field to make it look current. The source and input hashes in this example make that mismatch easy to detect.

## Reproducibility is not authorization or authenticity by itself

A JSON receipt can be edited. Matching hashes show consistency with the declared files, not that an independent trusted system created the record. A real release pipeline can add controlled execution, immutable artifact identities and protected publication decisions. The small validator here is a teaching mechanism, not a cryptographic attestation service.

A reproducible result can also be based on inappropriate data or an invalid scientific assumption. Governance and evaluation remain part of the review. Make source provenance, permitted use, population limitations and uncertainty visible. A polished report should help another person challenge the conclusion, not make unsupported certainty harder to notice.

## Applications and answered interview discussion

Use this approach for a public learning project, an internal design review, an interview demonstration or a handoff to another engineer. It reduces the amount of trust a reader must place in narrative alone. The remaining chapters apply the same evidence discipline to the more complex lifecycle of LLM serving, where requests, tokenization, model state, scheduling and streaming outputs create additional boundaries.

An interviewer may ask, “How do I know this result belongs to this code?” Point to source and input identities plus the actual execution record. If asked what a passing test establishes, state its invariant and environment rather than saying “everything works.” If asked what remains unverified, identify specific evidence gaps such as load, another architecture or a persistent service transition.

For an answered extension, change only the input from `[2,3,1]` to `[2,3,4]`. The old receipt must fail its input-identity check even though the source is unchanged. A new run should report total nine under a newly computed independent oracle. Reproducibility follows the complete computation identity, not the source file alone.
