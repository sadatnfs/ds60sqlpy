# k8s-023: Gateway, Ingress and the external route

## Level and prerequisites

Intermediate; about 120 minutes plus review. Direct prerequisites: `k8s-013`, `k8s-017`, `k8s-020`. The chapter separates desired configuration, API acceptance, controller observation and application evidence.

## Learning objectives

Distinguish an internal Service from a host-facing HTTP route and the controller that implements it.

## Vocabulary and concepts

A Service provides an internal backend abstraction; an ingress or gateway controller can expose selected routes through a managed listener. Gateway API separates infrastructure ownership, listener configuration and application route attachment. Creating an HTTPRoute object does not install a controller or create a working external address.

This host lab requires a preinstalled qualified Gateway controller, a host-owned Gateway named lesson-gateway, an owned Service backend and a loopback-only listener. A synthetic TLS case also needs a verified local trust chain and hostname. The normal browser adapter provides none of those cluster/controller operations and does not accept Gateway or Ingress resources.

The real HTTPRoute example matches host lesson.local and path prefix /version, then forwards to hello:8080. It leaves other paths unmatched. The Ingress comparison is a separate fixture with its own ingressClassName; do not assume the two APIs are interpreted by the same controller or apply both to an unreviewed listener.

## Follow Gateway ownership and route status

GatewayClass identifies a controller/infrastructure class and is cluster-scoped. A Gateway selects that class and defines listeners. HTTPRoute attaches through parentRefs and describes request matches and backends. The parent's allowedRoutes policy can restrict which namespaces may attach.

Inspect the route's parent-specific Accepted and ResolvedRefs conditions and their observed generation. A syntactically valid backend reference can still be unresolved or unauthorized. Cross-namespace references may require an explicit ReferenceGrant rather than being permitted by a matching name. The host must provide that capability deliberately; the learner should not widen it during diagnosis.

A positive status is necessary controller evidence, but a bounded client request must still prove routing and payload. A controller can accept a configuration before the data plane is ready, or a backend can be unready.

## Test path, host and TLS independently

For the positive case, connect through the loopback listener using the intended host and /version path. Verify the synthetic certificate against the provided CA and hostname when TLS is enabled. A successful TCP connection or HTTP response obtained by disabling certificate checks does not establish the TLS contract.

An unmatched path should produce the controller's expected no-route behavior, while a matching route should return the fixture's exact version body. A wrong hostname can select another listener/route or fail TLS verification. Record which layer failed rather than calling every negative result an application error.

The ordinary fixture client is HTTP-only and targets hello internally. It cannot prove the external TLS path. A separately qualified host client is required, with its CA file and loopback address from the owned receipt. No public load balancer or external IP is assumed.

## Worked example / walkthrough

### Worked example 1: Read the HTTPRoute

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: hello-route
spec:
  parentRefs:
    - name: lesson-gateway
  hostnames:
    - lesson.local
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /version
      backendRefs:
        - name: hello
          port: 8080
```

**Expected:** The route attaches to lesson-gateway for lesson.local and forwards /version to hello:8080.

### Worked example 2: Compare accepted and delivered

Synthetic status:Accepted=True, ResolvedRefs=True for the current generation. A matching client still receives503 because the backend has no ready endpoints.

**Expected:** Route acceptance and reference resolution do not establish backend application readiness.

## Common pitfalls

A Kubernetes API object is not a running controller. An Ingress class or GatewayClass name must correspond to an installed, qualified implementation. A Service of type ClusterIP does not expose a host port by itself.

Keep listener ownership and cleanup separate from the namespaced route. The learner should remove only its recorded route UID unless the host capability explicitly owns the Gateway/controller lifecycle. Never disable TLS verification or install a remote controller automatically to make the example pass.

## Networking depth supplement

An HTTP routing resource needs an implementation. Ingress requires a selected controller; Gateway API requires supported APIs and a compatible GatewayClass/controller. A route object alone does not create an external listener, assign a usable public address or provision TLS. `k8s-051` through `k8s-055` trace those responsibilities separately.

A complete request path includes caller DNS, external routing, listener/TLS identity, host/path matching, Service port, eligible endpoint and application route. A matched prefix rule can still produce an application404 if the upstream receives a path it does not implement. Path rewriting is an explicit implementation feature, not a universal effect of a matching rule.

Gateway status conditions distinguish attachment acceptance, reference resolution and data-plane programming. They help localize control-plane failures but still need an actual request to qualify behavior. Cross-namespace references and allowed route attachment are authorization boundaries; do not broaden them to make a sample appear accepted.
