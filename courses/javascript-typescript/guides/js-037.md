# js-037: Network retries, idempotency and bounded concurrency

The first investigation is: Fail twice transiently, then succeed, using random value 0.5 and a recording wait. The final task tests honor cancellation before the first attempt.

## Purpose and mental model

A retry is a new attempt after an uncertain or failed operation. It can improve resilience to transient failures, but it also multiplies load and may repeat side effects. Retrying every exception hides programming errors and permanent rejections. An operation needs a retry classification, maximum attempts, delay policy, cancellation behavior and a final failure result. A deadline limits waiting; it does not prove that a remote write did not occur.

Exponential backoff grows the delay between attempts. Full jitter chooses a delay uniformly from zero to a capped exponential bound, spreading clients that would otherwise retry simultaneously. The examples inject the random source and waiting function so expected delays are deterministic. They test a retry policy around a controlled transport fixture, not a real network outage or production recovery claim.

Idempotency associates repeated attempts with one intended operation. A key alone is insufficient if a caller reuses it with different request data. The fixture stores a canonical request representation and its completed result; matching retries reuse that result, while conflicting reuse rejects. Its Map is only in-memory and single-process. It does not survive crashes or solve distributed coordination; a durable service needs a transactionally enforced key/payload/result policy.

Bounded concurrency limits simultaneous owned work. Promise.all over a huge input starts all mapped operations immediately unless scheduling is controlled. The provided worker-loop scheduler starts at most the configured limit and preserves result order. On failure it stops scheduling new work, awaits already started work, then rejects. That is cleanup discipline, not cancellation of external side effects already underway.

## Vocabulary and concepts

**Retry classification:** The policy selecting failures eligible for another attempt.

**Backoff with jitter:** A growing delay bound with randomized spacing inside it.

**Idempotency key:** An identifier linking retries to one intended operation and payload.

**Bounded concurrency:** A limit on simultaneously active owned operations.

## Syntax anatomy and execution trace

retry receives an operation, an injected wait, an injected random function and an AbortSignal. It checks cancellation before each attempt, retries only the explicit transient category and throws the final error on exhaustion. The delay bound is min(cap, base times 2 to the attempt index), and jitter scales it by a sample in [0,1). The bounded map shares a synchronous next-index counter across async workers; each takes an index before awaiting its operation, so no two workers claim the same item.

## Worked example / walkthrough

### Example A: Retry transient failures with deterministic full jitter

The injected wait records policy without sleeping. The result demonstrates classification and arithmetic, not elapsed network latency or a live outage recovery.

```javascript
import { strict as assert } from 'node:assert';
import { setTimeout as delay } from 'node:timers/promises';

async function retry(
  operation,
  {
    attempts = 3,
    base = 100,
    cap = 1000,
    random = Math.random,
    wait = (milliseconds, signal) => delay(milliseconds, undefined, { signal }),
    signal = new AbortController().signal,
  } = {},
) {
  if (!Number.isInteger(attempts) || attempts < 1 || attempts > 5)
    throw new RangeError('attempts from 1 to 5 required');
  if (!Number.isFinite(base) || !Number.isFinite(cap) || base < 0 || cap < 0 || cap > 10000)
    throw new RangeError('finite nonnegative backoff with cap at most 10000 required');
  for (let index = 0; index < attempts; index += 1) {
    signal.throwIfAborted();
    try {
      return await operation(signal);
    } catch (error) {
      if (!error || error.transient !== true || index + 1 === attempts) throw error;
      signal.throwIfAborted();
      const sample = random();
      if (!(sample >= 0 && sample < 1)) throw new RangeError('random sample must be in [0,1)');
      await wait(Math.floor(Math.min(cap, base * 2 ** index) * sample), signal);
    }
  }
  throw new Error('unreachable retry state');
}
class IdempotentStore {
  records = new Map();
  effects = 0;
  apply(key, payload) {
    if (
      typeof key !== 'string' ||
      !key ||
      !Number.isSafeInteger(payload.amount) ||
      payload.amount <= 0
    )
      throw new TypeError('valid key and amount required');
    const canonical = JSON.stringify({ amount: payload.amount });
    const previous = this.records.get(key);
    if (previous) {
      if (previous.canonical !== canonical) throw new Error('idempotency key conflict');
      return { ...previous.result };
    }
    this.effects += 1;
    const result = { sequence: this.effects, amount: payload.amount };
    this.records.set(key, { canonical, result });
    return { ...result };
  }
}
async function mapBounded(values, limit, operation) {
  if (!Number.isInteger(limit) || limit < 1 || limit > 8)
    throw new RangeError('limit from 1 to 8 required');
  const results = new Array(values.length);
  let next = 0;
  let failed = false;
  let failure;
  async function worker() {
    while (!failed && next < values.length) {
      const index = next++;
      try {
        results[index] = await operation(values[index], index);
      } catch (error) {
        if (!failed) {
          failed = true;
          failure = error;
        }
      }
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, values.length) }, worker));
  if (failed) throw failure;
  return results;
}

export async function verify() {
  // Worked example
  {
    let attempts = 0;
    const waits = [];
    const result = await retry(
      async () => {
        attempts += 1;
        if (attempts < 3) throw Object.assign(new Error('temporary'), { transient: true });
        return 'ready';
      },
      {
        wait: async (value) => {
          waits.push(value);
        },
        random: () => 0.5,
      },
    );
    assert.equal(result, 'ready');
    assert.equal(attempts, 3);
    assert.deepEqual(waits, [50, 100]);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));
```

**Expected:** three attempts; delays 50 and 100; result ready.
### Example B: Stop on permanent failure and on exhausted attempts

A retry policy must retain a bounded final failure. Converting exhaustion into a default success would erase the operation's actual outcome.

```javascript

import { setTimeout as delay } from 'node:timers/promises';

  operation,
  {
    attempts = 3,
    base = 100,
    cap = 1000,
    random = Math.random,
    wait = (milliseconds, signal) => delay(milliseconds, undefined, { signal }),
    signal = new AbortController().signal,

  return results;
}

export async function verify() {
  // Worked example
  {
    let permanent = 0;
    await assert.rejects(
      retry(async () => {
        permanent += 1;
        throw new Error('permanent');
      }),
      /permanent/u,
    );
    assert.equal(permanent, 1);
    let transient = 0;
    await assert.rejects(
      retry(
        async () => {
          transient += 1;
          throw Object.assign(new Error('still unavailable'), { transient: true });
        },
        { wait: async () => {} },
      ),
      /still unavailable/u,
    );
    assert.equal(transient, 3);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));
```

**Expected:** permanent attempted once; transient attempted three times and still rejects.

## Prediction before your attempt

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

## Progressive hints

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
