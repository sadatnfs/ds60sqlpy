Repository tour#

DS60 is one local classroom for programming, data, statistics, machine learning and systems. Start learning with the front README and ./classroom. Start development with CONTRIBUTING, then read the closest AGENTS.md. All learner subjects share /classroom; historical day numbers and module IDs remain stable labels rather than a fixed schedule.

Follow one lesson through the system#

  1. Authoring sources define teaching, metadata, learner code and references. Some subjects generate bundles from courses/<subject>/authoring/; others maintain artifacts directly. Read that subject's guidance before editing.
  2. Catalog loaders validate identities, prerequisites, artifact paths and admitted runtimes. Python/SQL/bridge use the legacy catalog. Modern subjects use module plans and authored manifests. The statistics book has a separate tutorial contract.
  3. The shared classroom derives its directory and navigation from those loaders. It loads guides, preserves independent pads/notes/variants, and exposes only the selected lesson's actual capabilities.
  4. Execution uses a fixed prepared worker, a bounded legacy operation, or an opaque browser preview. Reading mode is a real learning mode without a Run operation. Content metadata cannot choose arbitrary commands.
  5. Results and progress retain source identity. Reading a previous result never reruns it. Browser observations, worker verification and self-reported completion remain distinct evidence.
  6. Static readers render the same material offline. They provide navigation and readable source; they do not install dependencies or launch host programs.

Generated, maintained and private files#

Do not hand-edit START_HERE.html, lesson-pages/, reference-pages/ or the legacy curriculum/catalog.json. Run a changed subject's documented generator first, format its source output, then use make generate for shared views. Read content authoring and validation for the complete order and check modes. Not every generator supports --check; use only its documented command.

.learning/ is local learner/contributor state; Docker uses named volumes for its own learning data, PostgreSQL and private runtime state. .classroom/ records launcher selection and image preferences, not a full data backup. Reuse the same project and engine to resume. Build outputs, caches, logs, credentials and Git history do not belong in the portable source ZIP. Historical runtime receipts are immutable observations. Formatting-equivalence records explain reviewed source drift; they are not fresh execution receipts.

Select a safe development loop#

Use ./classroom for prepared Docker behavior, ./classroom resume for strict no-build/no-pull startup, and ./classroom --rebuild for deliberate source or configuration updates. Optional GPU workers require compatible NVIDIA hardware and explicit selection. Ordinary --all excludes them and the owned-cluster adapter. A container build cannot prove hardware readiness.

A contributor can serve the same UI with python scripts/course.py serve --no-browser in the prepared Python environment. It reports actual local capabilities and does not create workers or import Docker progress. The native desktop executable, private editor-launch API and separate module/portal applications have been retired. Windows learners and contributors use WSL 2 for the Linux Docker route.

Use focused behavioral tests first, then the relevant release gates. The full Python suite uses python -m pytest -n 4 --dist loadgroup so shared database tests remain grouped. A UI or runtime change also needs actual prepared-worker/browser checks with disposable state. Preserve learner volumes and unrelated containers.

For new learning paths, follow the authoring skill. For tutoring, use learning with a companion. The implementation checkpoint records durable architecture and operational constraints, not a past developer's session state.
