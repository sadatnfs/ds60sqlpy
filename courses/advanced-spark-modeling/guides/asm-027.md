# asm-027: TorchDistributor with one CPU process

Tutorial mode. Stage: advanced. Direct prerequisites: `asm-026`, `torch-011`.

## Starting point and result

TorchDistributor is a Spark utility for launching a PyTorch training function or script. It is an orchestration bridge, not an arbitrary automatic conversion of DataFrame partitions into a training loader. Start with one CPU process so imports, argument serialization and the training function's contract can be checked without distributed synchronization obscuring basic errors.

## Mechanism: launcher and training code have separate responsibilities

In Spark 4.0.1, the public entrypoint is `TorchDistributor(...).run(...)`. The version's source also contains private helpers; a leading-underscore helper is not a supported public API to build a course contract around. The owned project uses the reviewed public path. The exact installed package and project source determine the supported argument and return behavior.

The launched function must define model construction, deterministic initialization, data loading, loss reduction, optimizer steps and result serialization. A process launch does not choose any of those statistical decisions. For one CPU process, a complete tiny dataset can be constructed locally. That is a bounded fixture, not a proposal to collect an arbitrarily large Spark table.

There are two independent meanings of “local.” Spark can run on one host, and TorchDistributor can use its local mode. A receipt should name both the Spark topology and actual Torch world size. Avoid calling a single process “distributed training” merely because Spark initiated it.

## Worked case: one process establishes the training contract

The project's `torch-distributor` case begins with the same small custom-likelihood logic used in serial checks. Record initial parameters, final parameters, loss reduction and deterministic fixture identity. Compare the numerical result with a serial oracle within tolerance. Confirm the function returns ordinary serializable evidence, not a live CUDA context, open file or Spark session.

This isolates whether the launch mechanism actually reaches the intended training code. An import-only probe cannot establish that an optimizer step ran. Conversely, successful local training outside TorchDistributor does not establish that the Spark launcher path works.

## Worked case: data must be delivered deliberately

Suppose a Spark DataFrame has a million rows, but the launched function constructs a three-row fixture. The launch can succeed while training on only three rows. There is no automatic relationship between the DataFrame variable in the driver and the launched process's loader. A valid data path must specify files, shards, iterator delivery or another supported mechanism and then audit coverage.

For the teaching project, small explicit data and stable IDs make coverage inspectable. For a large workload, avoid silently serializing the whole dataset as a function argument. Plan data locality, storage format, partition-to-rank mapping and memory before increasing process count.

## Failure diagnosis

A function that works in the driver's interpreter but fails after launch may rely on an uninstalled module or captured state. A hang before the first step may be process initialization rather than a loss issue. Retain launcher logs and distinguish preparation, startup, training and result collection. Do not repeatedly spawn nested process groups as a recovery strategy.

## Interview discussion

**Does TorchDistributor replace a DataLoader?** No. It launches execution. The training function still needs an explicit data-loading and sampling contract.

**Why start with one process?** It creates a baseline for numerical behavior and environment preparation. Once that passes, a two-rank discrepancy can be investigated as a synchronization, sharding or scaling issue rather than an unknown serial defect.

## Next step

Use two CPU ranks and derive the gradient scaling. Audit unique observation IDs before interpreting a successful synchronized training run.

# Worked reference: One-process launch evidence

This is an editable reading/project reference. It has no ordinary pad Run action.

The minimum evidence is an actual launched training function, its world size, the IDs it loaded, at least one real optimization step, and a serial numerical comparison. An import check supplies none of the latter facts.

Separate Spark local topology from Torch local mode. A single CPU process is useful baseline execution, but it is not a multi-rank or multi-host qualification. Record whether the selected project case includes additional rank checks rather than assuming them from its name.
