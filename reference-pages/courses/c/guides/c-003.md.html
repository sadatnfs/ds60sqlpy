c-003: Expressions, conversions and sequencing#

Level and prerequisites#

Beginner, approximately 90 minutes plus a later retrieval session. Direct prerequisites: c-002

Learning objectives#

Explain precedence, sequencing, usual arithmetic conversions. Implement the six investigations with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

Purpose and mental model#

An expression can compute a value and sometimes change state. C does not guarantee one universal evaluation order for every operator or function argument. Modifying one scalar more than once without the required sequencing can be undefined behavior. Keep complex updates in separate statements until the ordering is clear. The usual arithmetic conversions also affect comparisons: mixing a negative signed integer with an unsigned value can convert the negative operand into a large unsigned value. Parentheses clarify grouping but do not create sequencing where the language supplies none. Distinguish precedence, associativity and evaluation order.

Vocabulary and concepts#

  • Precedence: Rules grouping operators in an expression.
  • Sequencing: A language-defined order between evaluations.
  • Usual arithmetic conversions: Rules selecting a common arithmetic representation.

Syntax anatomy and execution trace#

&& and || short-circuit and sequence their left operand before a needed right operand. The conditional operator evaluates only its selected second or third operand. Assignment returns the assigned value, so accidental assignment inside a condition can be legal but wrong. ++ changes a value; using it in a larger expression requires careful reasoning. Prefer explicit temporary variables for updates with several observable effects.

Worked example / walkthrough#

Worked example 1: Group before calculating#

Compare 2+34 with (2+3)4.

#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int main(void) {
  /* Group before calculating */
  {
    CHECK(2 + 3 * 4 == 14);
    CHECK((2 + 3) * 4 == 20);
  }
  puts("Worked example checks passed.");
  return 0;
}

Observe: The values are 14 and 20.

Parentheses alter grouping. This example has no side effects, so it does not depend on evaluation order.

Worked example 2: Use a short-circuit guard#

Guard an array access with a false length test.

#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int main(void) {
  /* Group before calculating */
  {
    CHECK(2 + 3 * 4 == 14);
    CHECK((2 + 3) * 4 == 20);
  }

  /* Use a short-circuit guard */
  {
    int values[1] = {7};
    size_t length = 0;
    bool found = length > 0 && values[0] == 7;
    CHECK(!found);
  }
  puts("Worked example checks passed.");
  return 0;
}

Observe: The access is skipped and the condition is false.

The right operand is evaluated only when the left is true. A guard must precede the operation it protects.

Prediction before execution#

Trace each object from initialization through its last valid use. Write down the size of every array, the capacity of every output buffer and the ownership of any allocated storage. Distinguish a compiler diagnostic from a valid runtime rejection and from undefined behavior. Never execute an out-of-bounds access, dangling-pointer read or data race simply to discover what value it happens to print.

Common pitfalls and diagnosis#

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
