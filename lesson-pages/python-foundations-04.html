Build Your First Auditable Data Investigation#

Stable ID: python-foundations-04

Estimated time: 210 minutes, split across sessions as needed.

Level and prerequisites#

Foundation. Direct catalog prerequisites: python-foundations-03, python-10.

You can read CSV, write small functions, validate text records, and run assertions or pytest. This is a project checkpoint, not a race. Complete the stages over several sessions before moving into larger data libraries.

Learning objectives#

  • Turn a question into a small, testable project charter.
  • Separate loading, validation, summarizing, and reporting.
  • Build a local report with counts, totals, rejection evidence, and limitations.
  • Reproduce a result from a fresh process and explain what it proves.

Vocabulary and concepts#

An investigation connects a question to evidence that another person can inspect. Our question is: how many accepted units are recorded for each region in this small source file? This is deliberately narrower than estimating true regional demand. Invalid records, duplicate policy, and absent regions limit what the result can claim. Treat the pipeline like a chain of receipts: each stage names its input, output, and the check that connects them.

  • Charter: a short statement of the question, inputs, assumptions, and acceptance criteria for a project.
  • Stage: one operation with a clear boundary, such as reading text or aggregating validated records.
  • Aggregate: a summary calculated from several records, such as a total.
  • Artifact: a file produced so someone else can inspect or reuse a result.
  • Provenance: information connecting a result to its input and rules.
  • Limitation: a condition that prevents a broader conclusion from being supported by the evidence available.

The tracked beginner orders CSV has seven records. Required columns are id, region, and quantity. Strip outer spaces from id and region, keep both case-sensitive, require nonempty text, and parse a nonnegative integer quantity. Keep the first valid id. Preserve a source row number and raw dictionary for every rejected row. A zero-quantity record remains valid and its region must appear with a zero total if it has no other accepted units.

Do not write a single giant function that reads, cleans, prints, and saves. Start with load_rows(path), analyze_rows(rows), and write_report(report, path). The middle function should depend on data values, not a terminal or current directory. That makes boundary tests possible without repeatedly creating files. The I/O functions can then be tested using temporary paths.

Worked example / walkthrough#

Example A: total after validation, including a real zero#
records = [
    {"id": "A", "region": "north", "quantity": 2},
    {"id": "B", "region": "south", "quantity": 0},
    {"id": "C", "region": "north", "quantity": 5},
]
by_region = {}
for record in records:
    region = record["region"]
    by_region[region] = by_region.get(region, 0) + record["quantity"]
assert by_region == {"north": 7, "south": 0}

The dictionary key is the region; the value is its accumulated integer units. get(region, 0) uses zero only for a group not previously encountered. It does not replace invalid input with zero. A valid south record creates the south entry even though adding its quantity does not increase the total. Expected observation: two regions, with north seven and south zero.

Example B: verify a report independently#
report = {
    "input_count": 7,
    "accepted_count": 4,
    "rejected_count": 3,
    "total_quantity": 11,
    "by_region": {"north": 7, "south": 0, "west": 4},
}
assert report["input_count"] == report["accepted_count"] + report["rejected_count"]
assert report["total_quantity"] == sum(report["by_region"].values())
print(report["total_quantity"])

Expected output is 11. The first assertion checks row conservation; the second checks aggregation conservation. Neither alone proves the input is truthful. Add a manual calculation for this tiny fixture: two plus zero plus five plus four equals eleven. Different checks should challenge different defects. If every check simply calls the same summarizing helper, a bug in that helper could make all checks agree with the same wrong answer.

Reproduction is a feature of the project#

Use Path for file names and an explicit UTF-8 encoding. Resolve the tracked fixture from the documented repository root. When running from another folder, pass its explicit path to load_rows; a copied learner script can still use the same repository-root command. Open CSV with newline="" so the csv module controls newline handling on Windows as well as POSIX systems. JSON output should contain only plain values, sorted keys, and a trailing newline for inspectable diffs.

Keep learner output under .learning/ or artifacts/. The reference demonstration uses a temporary directory that is removed automatically. Never write over the tracked fixture to make a test easier. A written report should name the input contract and contain rejected rows, because an accepted total without its discarded-data context can be misleading. A graph is optional: the first goal is a report whose meaning and accounting you can defend.

At the final checkpoint, close the terminal and run the project again. A result that requires manually executing fragments in a lucky order has a hidden-state problem. Capture the command, report values, and test result. State whether you tested your own implementation or only ran the reference.

Self-check#

Explain why an accepted total of zero can mean a valid zero, an empty source, or an all-rejected source. Which report fields distinguish those cases? Trace one duplicate through the stage boundaries. Rebuild one test using only a two-record in-memory fixture and explain why it does not need filesystem I/O.

Common pitfalls#

If running from another folder loses the fixture, inspect how the default path is derived. If south disappears, check whether a truthiness filter removed quantity zero. If totals are fourteen, inspect duplicate acceptance before changing aggregation. If count checks pass after dropping a rejection, check whether input_count was incorrectly calculated from output rather than source.

Next step#

Keep this small project as a reference for the CLI project and the later pandas EDA project. Add packages only when they solve a named limitation; preserve the plain-data tests and policy explanations when changing the implementation.

Build Your First Auditable Data Investigation: solution reasoning#

Stable ID: python-foundations-04.

Read the guide and attempt the learner artifact first. The executable solution is a comparison implementation. It does not certify your changed program merely because its own demonstration succeeds. Copy the acceptance cases into your attempt, then change one input without changing the intended policy.

The reference uses a pure analysis function between two small file boundaries. Loading validates the exact header rather than guessing at column names. Analysis rejects declared input defects and makes row accounting visible. Report writing is tested through a temporary JSON file and readback. The demonstration does not write learner progress or modify the fixture.

assert 7 == 4 + 3
assert 11 == 7 + 0 + 4

These arithmetic observations are intentionally independent of the helper implementation. They give a small human-checkable oracle. For a large source, the oracle would need a carefully sampled manual audit and broader invariants, not a claim that agreement among two copies of the same calculation proves every input record correct.

Exercise 1. Write a project charter#

The charter asks for recorded accepted units by region, using the three tracked columns and the declared validation and duplicate rules. It promises grouped integer totals, source/accepted/rejected counts, and specific rejection evidence. It does not promise complete demand measurement or correct missing source records. Writing those boundaries first prevents a later chart title from claiming more than the input can establish. A useful unanswered question is why records contain invalid quantities and whether the duplicate id represents a correction, a replay, or an upstream defect.

Exercise 2. Load the tracked CSV#

DictReader returns one dictionary per data row. Open with explicit encoding and newline="" so behavior is portable, then compare fieldnames with the required sequence. The teaching contract rejects reordered, missing, or extra columns instead of guessing. An entirely different contract could allow reordered headers, but its tests would need to say so. The tracked fixture yields seven data rows. The header is not counted as a data row; rejection row numbers in this lab refer to data rows, not physical line numbers in arbitrary quoted CSV.

Exercise 3. Validate and retain rejection evidence#

Validate id and region before using their string methods. Parse quantity and reject negatives. Only after all fields succeed should the identifier enter the seen set. Rejected rows retain their one-based data-row number, reason, and a copy of raw fields. The fixture rejects many at row four, duplicate b at row five, and negative quantity at row six. Accepted rows are a, b, c, and f. A test comparing the original list with an untouched copy detects accidental normalization in place, even when final aggregate totals look right.

Exercise 4. Aggregate to one result per region#

The accepted north quantities two and five sum to seven. The accepted south quantity zero creates a real south entry with total zero. West contributes four from f; the invalid west rows contribute nothing to accepted units but remain in rejection evidence. Total accepted quantity is eleven. The second b row is a duplicate and does not add three. Sorting dictionary keys helps deterministic display and JSON comparison; it does not change the identity or arithmetic policy. Avoid filtering values with if quantity because zero is valid.

Exercise 5. Add independent checks#

Check source-row accounting before looking at totals: seven equals four plus three. Then check that group totals sum to eleven and compare the manual fixture calculation. Empty input yields zero counts, zero units, and no groups. An all-invalid batch also yields zero units but positive input and rejected counts. Those checks reveal different mechanisms. Do not derive input_count from accepted plus rejected and then call their equality an independent test; count the original source rows so a dropped row can make the assertion fail.

Exercise 6. Write and read a local report#

The writer serializes a dictionary with standard JSON-compatible fields, sorted keys, readable indentation, and a trailing newline. The caller supplies the path, and the writer deliberately creates its parent. A temporary directory makes the reference readback safe and repeatable. Compare loaded JSON content with the report rather than only checking that the file exists. File presence proves much less than content equality. The lab does not claim atomic publication or crash durability; the advanced restartable-pipeline module introduces those additional guarantees and limitations.

Exercise 7. Challenge the duplicate policy#

For two valid rows sharing one id, the first is accepted and the second rejected. Reversing their order changes which quantity wins. That result is consistent with first-valid-wins and demonstrates its order sensitivity. If order independence were required, the policy would need a stronger identity/version contract or conflict rejection. Do not hide the discrepancy by sorting solely to make a preferred quantity first. Preserve the conflicting raw row and explain why a real ingestion system should understand whether it represents correction or accidental duplication.

Exercise 8. Present a reproducible conclusion#

A reproducible conclusion gives the exact command, observable test result, accepted total eleven, four accepted rows, and three rejected rows. It also states the validation and duplicate policies and limits the claim to this input. Running a new process checks for hidden session state. It does not certify every operating system or the truth of the source data. A responsible next step would investigate the rejected records with the source owner or add an explicit correction/version field. More elaborate graphics cannot resolve missing source meaning by themselves.

Compare and transfer#

Create a separate temporary input with one valid zero row and compare it with an empty input. Both totals are zero; their source counts and region mappings differ. Present those differences in plain language. Then replace first-valid-wins with conflict rejection in a copy and identify every test whose expected result must change because the policy changed.

"""Small auditable CSV investigation for python-foundations-04."""
 
from __future__ import annotations
 
import csv
import json
from pathlib import Path
from tempfile import TemporaryDirectory
 
FIXTURE = Path("python") / "professional" / "fixtures" / "data" / "beginner_orders.csv"
 
 
def load_rows(path: Path) -> list[dict[str, str]]:
    with path.open(encoding="utf-8", newline="") as handle:
        reader = csv.DictReader(handle)
        if reader.fieldnames != ["id", "region", "quantity"]:
            raise ValueError("expected header: id,region,quantity")
        rows = list(reader)
    if any(
        set(row) != {"id", "region", "quantity"}
        or any(not isinstance(v, str) for v in row.values())
        for row in rows
    ):
        raise ValueError("CSV row does not match the three-field header")
    return rows
 
 
def analyze_rows(rows: list[dict[str, str]]) -> dict[str, object]:
    seen: set[str] = set()
    totals: dict[str, int] = {}
    accepted_count = 0
    rejected: list[dict[str, object]] = []
    for row_number, raw in enumerate(rows, start=1):
        try:
            if not all(
                isinstance(raw.get(key), str) and raw[key].strip()
                for key in ("id", "region", "quantity")
            ):
                raise ValueError("missing or non-text field")
            identifier = raw["id"].strip()
            region = raw["region"].strip()
            try:
                quantity = int(raw["quantity"].strip())
            except ValueError as exc:
                raise ValueError("quantity is not an integer") from exc
            if quantity < 0:
                raise ValueError("quantity is negative")
            if identifier in seen:
                raise ValueError("duplicate id")
            seen.add(identifier)
            accepted_count += 1
            totals[region] = totals.get(region, 0) + quantity
        except ValueError as exc:
            rejected.append({"row_number": row_number, "reason": str(exc), "raw": raw.copy()})
    return {
        "input_count": len(rows),
        "accepted_count": accepted_count,
        "rejected_count": len(rejected),
        "rejected": rejected,
        "total_quantity": sum(totals.values()),
        "by_region": dict(sorted(totals.items())),
        "contract": "nonnegative integer units; case-sensitive id/region; first valid id wins",
    }
 
 
def write_report(report: dict[str, object], path: Path) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)
    path.write_text(json.dumps(report, sort_keys=True, indent=2) + "\n", encoding="utf-8")
 
 
if __name__ == "__main__":
    result = analyze_rows(load_rows(FIXTURE))
    assert (result["input_count"], result["accepted_count"], result["rejected_count"]) == (7, 4, 3)
    assert result["total_quantity"] == 11
    assert result["by_region"] == {"north": 7, "south": 0, "west": 4}
    with TemporaryDirectory() as directory:
        target = Path(directory) / "report.json"
        write_report(result, target)
        assert json.loads(target.read_text(encoding="utf-8")) == result
    print(json.dumps(result, sort_keys=True))
