# web-021: Container queries and reusable responsive components

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-020`

## Learning objectives

Render the same component in wide and narrow slots. Choose between a viewport query and a container query for a sidebar card. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A media query responds to the viewport or device environment. A container query can respond to an ancestor container's size, which is useful when the same component appears in a wide article and a narrow sidebar on the same page. The component should adapt to the space it receives instead of assuming it always spans the viewport.

Size containment changes how a container participates in sizing. Declare it deliberately on an appropriate wrapper, not on every element. A size query targets an eligible ancestor, not the queried element itself. Keep a useful base layout so the component remains readable in environments where the query is unsupported or never matches.

## Syntax anatomy and mechanism

Set `container-type:inline-size` on a wrapper, optionally with a container-name. Inside `@container`, adjust the descendant component when its wrapper is wide enough. Prefer logical dimensions so the design does not unnecessarily assume a writing direction. This chapter demonstrates progressive enhancement; the unqueried stacked card remains functional.

## Worked example / walkthrough

### Worked example 1: Declare the query container

The wrapper supplies the size context.

```css
.slot {
  container-type: inline-size;
}
.card {
  display: grid;
  gap: 1rem;
}
```

**Expected observation:** The card has a usable stacked baseline.

### Worked example 2: Respond to local room

The component's parent width matters, not the page width alone.

```css
@container (min-width: 28rem) {
  .card {
    grid-template-columns: 8rem minmax(0, 1fr);
  }
}
```

**Expected observation:** Only cards in sufficiently wide containers switch layout.

**Expected evidence:** Each instance adapts independently while preserving its content.

**Expected evidence:** Inspect container-type and the relevant ancestor relationship.

**Expected evidence:** The baseline stacked component remains usable.

**Expected evidence:** A container query fits a component whose available space depends on placement.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Containment is not merely a label; it affects sizing behavior. Avoid a component design that becomes unusable unless a modern feature matches. Verify both instances after actual resizing.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.
