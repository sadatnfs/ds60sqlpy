js-020: Unions, narrowing and exhaustiveness#

Level and prerequisites#

Intermediate, approximately 90 minutes. Direct prerequisites: js-019

Learning objectives#

Explain union, narrowing, discriminant, exhaustiveness with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Format both successful value 7 and a failure message. The final task tests expose the runtime limit of an asserted union.

Purpose and mental model#

A union type describes a value that may belong to one of several alternatives. Until code proves which alternative is present, only operations valid for all alternatives are safe. Narrowing uses control flow to refine that set. typeof checks, equality checks, property checks and explicit discriminants can provide evidence. Truthiness is sometimes too coarse: an empty string is still a valid string even though it is falsy.

A discriminated union uses a shared property with distinct literal values, such as kind: success or kind: failure. Each alternative can then carry exactly the fields appropriate to that state. This is more precise than one object with several optional fields, which may admit impossible combinations such as success with no value. A switch over the discriminant connects runtime branching to static knowledge of the payload.

Exhaustiveness means accounting for every alternative. A function accepting never can mark a branch that should be unreachable after complete narrowing. Adding a new union member then creates a compile error at that branch until the handler is updated. This protects checked internal code. A JSON payload still needs validation: a type assertion can inject a value that violates the union and reaches the supposedly impossible branch at runtime.

Vocabulary and concepts#

Union: A value belonging to one of several alternatives.

Narrowing: Refining a type using control-flow evidence.

Discriminant: A shared field whose literal value identifies a variant.

Exhaustiveness: Handling every possible alternative in a closed union.

Syntax anatomy and execution trace#

Use a union operator between alternatives, then compare a literal discriminant with switch or equality. Within each branch, the checker exposes only that variant's fields. assertNever throws in the runtime fallback while requiring a never argument statically. User-defined type predicates can guide narrowing, but TypeScript trusts their declared claim; an incorrect predicate can make unsafe code compile. Prefer simple guards whose runtime checks actually establish the claimed property.

Worked example / walkthrough#

Example A: Handle a result union#

The kind check determines which payload exists. A failure result cannot accidentally be read as if it contained the success value.

import { strict as assert } from 'node:assert';

type Result = { kind: 'success'; value: number } | { kind: 'failure'; message: string };
function assertNever(value: never): never {
  throw new Error('unhandled variant: ' + JSON.stringify(value));
}
function formatResult(result: Result): string {
  switch (result.kind) {
    case 'success': return `value:${result.value}`;
    case 'failure': return `error:${result.message}`;
    default: return assertNever(result);
  }
}

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    assert.equal(formatResult({ kind: 'success', value: 7 }), 'value:7');
    assert.equal(formatResult({ kind: 'failure', message: 'offline' }), 'error:offline');
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: value:7 and error:offline.

Example B: Preserve an empty string during narrowing#

if(value) would merge the empty-string case with absence. A guard should encode the domain distinction, not merely satisfy the checker.

import { strict as assert } from 'node:assert';

type Result = { kind: 'success'; value: number } | { kind: 'failure'; message: string };
function assertNever(value: never): never {
  throw new Error('unhandled variant: ' + JSON.stringify(value));
}
function formatResult(result: Result): string {
  switch (result.kind) {
    case 'success': return `value:${result.value}`;
    case 'failure': return `error:${result.message}`;
    default: return assertNever(result);
  }
}

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    function describe(value: string | undefined): number | 'missing' {
      return value === undefined ? 'missing' : value.length;
    }
    assert.equal(describe(''), 0);
    assert.equal(describe(undefined), 'missing');
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: empty string has length 0; absent value returns missing.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
