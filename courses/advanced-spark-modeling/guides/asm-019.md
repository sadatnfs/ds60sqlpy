# asm-019: Analyzed, optimized and physical plans

Tutorial mode. Stage: advanced. Direct prerequisites: `asm-015`, `spark-021`.

## Starting point and result

Spark SQL represents a query through several plans. Understanding them lets you diagnose whether a custom operation remains visible to optimization and where shuffles, scans and filters occur. The program prints analyzed, optimized and formatted physical plans for a tiny native expression, then compares a semantically equivalent Scala UDF.

## Mechanism: plans answer different questions

The parsed logical plan captures syntax. Analysis resolves names, types and functions against a catalog and schema. Logical optimization applies valid transformations, such as simplifying expressions or moving filters where semantics permit. Physical planning selects executable operators and distribution strategies. Runtime adaptation can alter parts of execution when enabled; this teaching fixture disables adaptive execution to make a small comparison easier to inspect.

A plan is not an execution trace. Reading a logical plan does not prove that a stage ran, and seeing a physical operator does not establish its measured cost. The actual collection action in the example executes the query and validates its result. Production diagnosis combines plans with stage metrics, row counts, shuffle bytes, spill and wall time.

A predicate can move across a projection only when the transformation preserves the necessary semantics. Null handling, nondeterminism and exception behavior can constrain rewrites. Replacing an opaque UDF with a native equivalent may expose more structure, but the optimizer still must respect the operation's declared behavior.

## Worked case: filter and project a range

The input range is zero through eleven. A filter keeps IDs below four, and a projection casts to double and adds one. The executed result is one, two, three and four. Inspect where the filter appears relative to projection, and which attributes are resolved in the analyzed plan. These are actual plans from Spark 4.0.1, not an invented diagram.

The range has a bounded deterministic order in this local fixture. General distributed result order requires an explicit `orderBy` when it matters. Do not turn the fixture's collection order into a general guarantee for an arbitrary DataFrame.

## Worked case: replace arithmetic with a UDF

The second query computes the same increment inside a Scala UDF. Its output must match the native query. The optimized expression displays the custom function boundary, demonstrating that equality of outputs does not imply identical optimizer visibility. Spark cannot generally inspect the closure and prove that it is addition by one.

Do not infer a performance ratio from the printed plans. The example has twelve input rows and substantial fixed startup cost. For a meaningful comparison, measure repeated representative workloads after accounting for warmup, cache state, partitioning and identical materialization actions. Also check whether upstream filters and projections eliminate most work before the custom expression runs.

## Failure diagnosis

An unresolved column is an analysis issue. An unexpected exchange is a distribution requirement or planning choice to investigate. A scan returning fewer rows may be legitimate pushdown or a data-selection bug. A UDF with hidden randomness can invalidate expectations of repeated identical output even when the surrounding plan is unchanged.

## Interview discussion

**Can explain prove a query is fast?** It can reveal costly-looking boundaries and plausible optimizations, but actual speed requires execution measurements. A suspicious operator on ten rows may be irrelevant, while a simple operator over billions can dominate.

**Why distinguish analyzed and optimized plans?** Analysis establishes meaning and types; optimization transforms that resolved meaning. A missing function registration must be fixed before discussing physical performance.

## Complete reproducible program

Run this complete source in its declared prepared Spark profile. The fixture is tiny, deterministic and offline. Scala sources are compiled before execution; Python sources use the prepared PySpark environment. These are worked tutorials with no hidden solutions or exams. Runtime: `spark-local-scala`.

```scala
import org.apache.spark.sql.{SparkSession, DataFrame, Dataset, Encoder, Encoders}
import org.apache.spark.sql.functions._

object Main {
  def main(args: Array[String]): Unit = {
    val spark = SparkSession.builder
      .master("local[2]")
      .appName("advanced-spark-modeling")
      .config("spark.ui.enabled", "false")
      .config("spark.driver.host", "127.0.0.1")
      .config("spark.driver.bindAddress", "127.0.0.1")
      .config("spark.sql.shuffle.partitions", "2")
      .config("spark.sql.adaptive.enabled", "false")
      .config("spark.sql.ansi.enabled", "true")
      .getOrCreate()
    require(spark.version == "4.0.1", "This example targets Spark 4.0.1")
    spark.sparkContext.setLogLevel("ERROR")
    import spark.implicits._
    try {
      val source = spark.range(0, 12, 1, 2).withColumn("x", col("id").cast("double"))
      val query = source.filter(col("id") < 4).select((col("x") + lit(1.0)).as("value"))
      println("ANALYZED\n" + query.queryExecution.analyzed.treeString)
      println("OPTIMIZED\n" + query.queryExecution.optimizedPlan.treeString)
      query.explain("formatted")
      require(query.as[Double].collect().toSeq == Seq(1.0, 2.0, 3.0, 4.0))
      val opaque = udf((x: Double) => x + 1.0)
      val alternative = source.filter(col("id") < 4).select(opaque(col("x")).as("value"))
      require(alternative.as[Double].collect().toSeq == query.as[Double].collect().toSeq)
      println("CUSTOM EXPRESSION PLAN\n" + alternative.queryExecution.optimizedPlan.treeString)
      println("Equal outputs do not imply identical optimizer visibility or measured performance")
    } finally { spark.stop() }
  }
}
```
