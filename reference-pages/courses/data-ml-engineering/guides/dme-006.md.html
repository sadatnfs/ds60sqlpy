dme-006: Tests, invariants and evidence that can falsify a claim#

Level: Beginner | Prepared runtime: python-core

Direct prerequisites: dme-005.

Outcome: Check hand-derived outputs, boundaries and changed inputs.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

A useful test can disagree with the implementation#

A test compares observed behavior with an expectation. If the expectation is computed by repeating the same mistaken algorithm, the test can agree with the implementation and still fail to establish correctness. For data engineering, a useful oracle often comes from a hand-derived small example, an independently implemented method, a declared conservation relationship or a separately validated source.

The package-total function provides a deliberately simple setting. Each supplied record has an identity and a positive integer package count. The total for counts two, three and one is six. An empty collection returns zero under this local aggregation contract, while a negative count is rejected. Whether an empty collection represents a complete delivery still belongs to the upstream completeness contract.

A test case supplies inputs and checks expected behavior. An assertion is a specific condition that must hold. An invariant describes a relationship expected to remain true under some class of changes. A test suite groups cases so they can be run together. A regression test preserves evidence about behavior that should not change unexpectedly. None of these terms implies that every possible input has been examined.

The chapter uses Python's actual standard-library unittest framework. The pad runs real test objects and reads their results. It does not merely print a fictional “tests passed” message. The second case intentionally tests a wrong implementation and checks that the framework detects its failure. The complete tutorial succeeds when that deliberate bug is correctly exposed.

Separate kinds of expectations#

An exact numerical oracle checks a specific answer. For our tiny positive integer fixture, the oracle is

A reconciliation invariant might check that accepted and rejected input rows account for every supplied row. A domain invariant might require a package total to be nonnegative. A metamorphic relationship might require that reordering the same identified records does not change a sum, or that combining two disjoint valid collections adds their totals.

These checks have different strengths. Nonnegativity can reject a negative result, but it cannot distinguish six from nine when both are plausible positive totals. Reordering invariance can hold for a function that returns a constant. A conservation relationship may fail to detect a matching error on both sides if both are derived from the same flawed transformation. Use complementary checks and understand what each could falsify.

Boundary cases make the contract concrete. An empty collection, a count at the minimum allowed value, a missing identity, an invalid type and a duplicate key each ask a different question. You do not need to combine every concern into one enormous test. Small focused cases make it easier to identify which assumption failed.

Tests live at different boundaries#

A unit test exercises a bounded component. An integration test observes cooperating components, such as a database query and its actual schema. A service test can verify an HTTP contract. A lifecycle test can replace containers and check whether durable state survives. These forms of evidence complement one another.

A pure Python test of a retry policy does not demonstrate that a real broker or database implements that policy. A successful Docker build does not demonstrate that a server can answer a request. An HTTP response does not establish that an analytical metric uses the correct population. Name the observation you obtained and avoid silently upgrading it into a broader claim.

Tests also depend on their environment. Dependency versions, interpreter behavior, timezone assumptions, random state and input artifacts can affect results. Reproducibility does not require pretending those dependencies do not exist. Record and control the relevant ones, and use a justified numerical tolerance where exact equality is inappropriate. For exact package counts, however, a tolerance would usually hide rather than explain an error.

Read the test class#

The class inherits from unittest.TestCase, which supplies assertion methods. A method is a function associated with that class; self refers to the current test instance. Methods whose names begin with test_ are discovered by the loader. self.assertEqual compares observed and expected values, while self.assertRaises checks that an operation rejects an input with the expected exception type.

The example collects results explicitly instead of invoking a command-line test runner. This lets both tutorial cases run in one pad and lets the second case inspect an intentionally failing test. In a project, a normal test command would usually return a failing exit status when an unexpected assertion fails. Do not confuse the tutorial's deliberate inspection of a negative case with ignoring a failing project suite.

Worked case 1: Execute a small suite against a stated contract#

The first case defines three actual unittest checks. One verifies the known-row total of six. One verifies the local empty-collection result of zero. One verifies that an invalid negative count raises ValueError. The loader builds a suite from the test class, and TestResult collects its outcomes without requiring an external test package.

The expected evidence is three executed tests, zero failures and zero errors. A failure ordinarily means an assertion disagreed with the observed result. An error ordinarily means an unexpected exception interrupted the test. This distinction helps explain whether the code returned the wrong answer or could not complete the intended observation.

The suite is small on purpose. It provides a readable starting contract, not exhaustive qualification. It does not test every integer, every possible malformed object, an external file parser or a distributed execution environment. A real component would add cases based on its complete input contract and known failure modes.

Notice that the expected value six is written independently of the tested function. Calling the same function a second time to calculate its expected result would not provide an independent oracle. The test must be able to say the implementation is wrong, not merely demonstrate that it is self-consistent.

Worked case 2: A weak invariant permits a wrong answer#

The changed case introduces wrong_total(records), which returns twice the number of records. On the original three-row fixture, this happens to return six, exactly matching the true package total. A test using only that fixture would not distinguish the wrong function from the correct one.

Now delivery C changes from one package to four. There are still three records, so the wrong function still returns six. The independent arithmetic is

The nonnegative-total invariant still passes. Even the number of output values is unchanged. The changed-value oracle reveals the defect because it tests the actual quantity, not a coincidental relationship between record count and package count.

The program runs a real unittest case that expects nine from the wrong function. It then confirms that the framework recorded exactly one failure and no unexpected errors. This is an intentionally observed negative case. The outer tutorial's assertions confirm that the expected failure was detected, so the overall program can finish and explain the diagnostic.

In a normal product test suite, this failure would block acceptance of the wrong implementation. You would not convert the expected value to six merely to make the suite green. First inspect the contract and independently derive the correct answer; then repair the implementation or deliberately review a changed requirement.

Complete worked program#

"""Tests compare independent expected behavior and challenge incomplete invariants."""

import unittest


def package_total(records):
    total = 0
    for _, packages in records:
        if type(packages) is not int or packages < 1:
            raise ValueError("Expected a positive integer package count")
        total += packages
    return total


def example_one():
    class ContractChecks(unittest.TestCase):
        def test_known_rows(self):
            self.assertEqual(package_total([("A", 2), ("B", 3), ("C", 1)]), 6)

        def test_empty(self):
            self.assertEqual(package_total([]), 0)

        def test_invalid(self):
            with self.assertRaises(ValueError):
                package_total([("A", -1)])

    suite = unittest.defaultTestLoader.loadTestsFromTestCase(ContractChecks)
    result = unittest.TestResult()
    suite.run(result)
    assert result.testsRun == 3 and result.wasSuccessful()
    return {
        "actual_unittest_cases": result.testsRun,
        "failures": len(result.failures),
        "errors": len(result.errors),
    }


def example_two():
    def wrong_total(records):
        return len(records) * 2

    baseline = [("A", 2), ("B", 3), ("C", 1)]
    changed = [("A", 2), ("B", 3), ("C", 4)]
    assert wrong_total(baseline) == package_total(baseline) == 6
    assert wrong_total(changed) >= 0  # This weak invariant still passes.
    expected = 2 + 3 + 4
    assert expected == 9 and wrong_total(changed) == 6
    assert package_total(changed) == expected

    class ChangedInputCheck(unittest.TestCase):
        def test_changed_input(self):
            self.assertEqual(wrong_total(changed), 9)

    suite = unittest.defaultTestLoader.loadTestsFromTestCase(ChangedInputCheck)
    result = unittest.TestResult()
    suite.run(result)
    assert result.testsRun == 1 and len(result.failures) == 1 and not result.errors
    return {
        "coincidental_baseline_match": 6,
        "changed_expected": expected,
        "wrong_changed_result": wrong_total(changed),
        "nonnegative_invariant_could_not_detect_error": True,
        "expected_unittest_failures": len(result.failures),
    }


def main():
    print("Run actual contract tests:", example_one())
    print("Falsify a plausible implementation:", example_two())


if __name__ == "__main__":
    main()

Diagnose a failing test without discarding its purpose#

Start by reading the smallest relevant input and expected observation. Determine whether the expectation is independent and whether the test actually represents the intended contract. Then inspect the returned value, exception or missing artifact. A failure caused by an incorrect test expectation is possible, but it should be demonstrated rather than assumed.

Avoid replacing a meaningful assertion with a weaker check just because the weaker one passes. Replacing an exact expected relation with “result is nonempty” can conceal missing rows, wrong identities and duplicate records. Likewise, catching every exception and returning a default value can make a test appear successful while eliminating the very behavior it was meant to verify.

Nondeterministic tests require a separate investigation. A changing clock, uncontrolled random seed, shared state or timing-dependent concurrency can make observations vary. Fix the source of variability or establish an appropriate probabilistic test design. Increasing a sleep or retry count without understanding the mechanism can turn a repeatable defect into an intermittent one.

Where this is useful#

Use known small oracles before optimizing a transformation, changing a query engine, adding parallelism or replacing a dependency. Keep the oracle when moving from a Python model to actual SQL or Spark. Add real integration and lifecycle checks at the boundaries where implementation-specific behavior matters.

A test report should identify the source and inputs it qualified. Once either changes, previous results remain historical evidence but do not automatically qualify the new state. The next chapters connect explicit contracts and content identities to this testing discipline.

Answered interview discussion#

What is a good data-pipeline test? It states the intended grain and meaning, uses known boundary or changed-condition inputs, and checks independently justified results. It should also identify which external boundaries were and were not exercised.

Why is coverage percentage insufficient? Executing a line does not mean a test would detect an incorrect result from it. The wrong-total example can execute every line and pass the original fixture while still violating the intended quantity.

When are property tests useful? They can explore many inputs and relationships, especially for transformations with clear invariants. The property itself must be appropriate and strong enough to expose relevant errors; a trivial invariant can pass a deeply wrong function.

What would you add to this suite? Test the remaining declared type and identity policies, reordered inputs and disjoint-collection addition. Then add actual storage or service integration checks only when those components become part of the contract.
