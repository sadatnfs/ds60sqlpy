# k8s-054: Gateway API, routes and role-separated configuration

## Level and prerequisites

Advanced; about 120 minutes. Direct prerequisites: `k8s-053`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Design a route attachment boundary.
- Plan Gateway acceptance evidence.

## Purpose, vocabulary and mental model

Gateway API separates infrastructure selection, traffic listeners and application routes into distinct resources. A GatewayClass describes a controller-managed class. A Gateway asks for listeners and an entrypoint. An HTTPRoute attaches routing rules to an allowed parent Gateway. This can separate platform responsibilities from application routing ownership.

The resources still require installed APIs and a compatible controller. Status conditions such as Accepted, Programmed and ResolvedRefs describe different aspects of reconciliation. A route being accepted does not prove an actual client request reached the expected application.

Cross-namespace references require deliberate authorization under the API’s rules. ReferenceGrant is one mechanism for allowing supported cross-namespace object references. It should be narrow, naming the intended kinds and relationships. Broad grants or permissive listener attachment can turn an organizational boundary into an accidental shared routing surface.

### Key terms

- **GatewayClass:** A cluster-scoped object naming the controller that implements Gateways of that class.
- **Listener:** A Gateway entry for one port, protocol and optional host name that routes can attach to.
- **ReferenceGrant:** An object in a target namespace that allows routes in another namespace to reference its Services or Secrets.
- **Route status conditions:** Per-parent status such as Accepted and ResolvedRefs that reports whether a route attached and whether its backends were found.

## Mechanism and field-by-field reasoning

The fixture uses gateway.networking.k8s.io/v1 for Gateway and HTTPRoute. The exact supported route features depend on the installed controller and API version. Read parentRefs, listener names, hostnames and backendRefs field by field.

A platform team might own a shared Gateway while an application team owns an HTTPRoute in its namespace. The listener’s allowedRoutes policy controls which routes may attach. This is separate from whether the referenced backend exists and whether traffic succeeds.

## Trace the request or control path

```text
GatewayClass -> controller implementation
Gateway listener <- allowed HTTPRoute parentRef -> Service backend
status conditions -> actual listener/request qualification
```

Read the first two lines as an ownership chain. A GatewayClass names the controller, a Gateway owns listeners, and an HTTPRoute attaches by parentRef only if the listener's allowedRoutes permits its namespace. The third line warns that conditions such as Accepted and ResolvedRefs are reports from that controller. They localize a failure; a request through the listener is still the proof.

## Worked example / walkthrough

### Worked example 1: Read a route backend

The route assumes an explicitly prepared parent named study-gateway.

```yaml
parentRefs:
  - name: study-gateway
hostnames: [study.example.test]
rules:
  - backendRefs:
      - name: network-study
        port: 80
```

**Expected observation:** The route identifies a parent and Service backend; neither resource is created by this fragment.

### Worked example 2: Classify condition failures

These are synthetic controller observations.

```text
Accepted=False: route attachment or policy issue
ResolvedRefs=False: a referenced object or permission is unresolved
Programmed=False: desired data-plane configuration is not ready
```

**Expected observation:** Conditions localize different control-plane failures and still need actual request acceptance afterward.

## Six progressive exercises

### Exercise 1: Name the roles of class, gateway and route.

**Expected evidence:** Implementation class, listener/entrypoint and application routing intent.

**Progressive hint:** Assign each resource to a role: platform provider, cluster operator, application team. What does each own?

### Exercise 2: Predict a route with an unavailable parent.

**Expected evidence:** It cannot establish the intended attached traffic path.

**Progressive hint:** Follow the route's parentRef. If the target is missing or not programmed, what can the route attach to?

### Exercise 3: Design a route attachment boundary.

**Expected evidence:** Listener allowedRoutes and route parentRef agree on intended ownership.

**Progressive hint:** Read allowedRoutes on the listener and parentRefs on the route. Both sides must agree before attachment.

### Exercise 4: Diagnose ResolvedRefs=False.

**Expected evidence:** Inspect backend identity and required reference authorization.

**Progressive hint:** ResolvedRefs is about what the route points at. Check the backend's name, namespace, port and permission to reference it.

### Exercise 5: Explain a narrow cross-namespace grant.

**Expected evidence:** Only the intended source kind/namespace can reference the intended target kind.

**Progressive hint:** A grant lives in the target's namespace and names who may refer in. Keep its from and to lists minimal.

### Exercise 6: Plan Gateway acceptance evidence.

**Expected evidence:** API/controller support, conditions, listener reachability and expected app response.

**Progressive hint:** List what must be true before the first request: types installed, class accepted, listener programmed, route attached.

## Diagnosis, failure boundaries and common mistakes

When a route shows Accepted=False, the usual cause is a parentRef mismatch: a wrong Gateway name, a wrong sectionName, or a listener whose allowedRoutes excludes the route's namespace. Read the reason field before editing anything. ResolvedRefs=False points somewhere else, at a missing backend Service, a wrong port, or a cross-namespace reference without a ReferenceGrant. Do not fix that by widening the grant to every namespace or every kind. And do not assume Gateway API exists because Ingress does; its types are installed separately, and on a cluster without them kubectl reports an unknown resource type rather than an empty list. Record that error as the capability boundary.

Before concluding, record:

- The HTTPRoute `parentRefs` name, namespace and sectionName, beside the Gateway listener they claim to attach to.
- The listener's `allowedRoutes.namespaces` setting and whether the route's namespace falls inside it.
- Each route condition with its status and reason, such as Accepted=False with reason NotAllowedByListeners.
- For a cross-namespace backendRef, the ReferenceGrant's `from` kind and namespace and its `to` kind.

General evidence rules: [diagnosis rules](../STUDY-GUIDE.md#diagnosis-rules).
