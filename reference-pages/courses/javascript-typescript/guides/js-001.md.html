js-001: JavaScript, Node and the browser#

Level and prerequisites#

Beginner, approximately 90 minutes. Direct prerequisites: None. This lesson starts from the language and host distinction.

Learning objectives#

Explain ecmascript, host, es module with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Check that the prepared runtime is Node 24 and that process exists. The final task tests await a real promise result.

Purpose and mental model#

JavaScript is a language; Node and browsers are hosts that provide different APIs around it. Arithmetic, objects, functions and Promises belong to the language. Node adds process information, filesystem access and server APIs. Browsers add a document tree, events, layout and browser storage. Some APIs such as URL and fetch exist in both hosts, but that overlap does not make every program portable. A Node process has no document object to edit.

This course uses ES modules with the .mjs extension for JavaScript. Modules have their own scope and run in strict mode. Imports name dependencies explicitly, and top-level await can wait for asynchronous setup. A file being syntactically valid does not mean its host dependencies exist. The first lesson makes the actual Node version, module identity and missing browser globals observable before introducing larger programs.

Vocabulary and concepts#

ECMAScript: The standardized JavaScript language semantics.

Host: The environment supplying APIs around the language.

ES module: A file with explicit imports/exports and its own strict scope.

How to run this lesson#

Use the prepared Node 24.22.1 profile. The classroom saves an ES module as main.mjs and executes it with Node. Only built-in Node or ECMAScript APIs are used. For a prepared native environment, node main.mjs is the same command on PowerShell and POSIX. Browser APIs have separate host requirements.

Save your own learner copy under ignored .learning/expansion/js-001/ or use a saved classroom pad. Record predictions before execution. Each worked program includes its helper definitions. The reference puts the six exercises in separate scopes, so a task cannot silently rely on a variable from a previous task. A successful assertion is silent; the final JSON receipt reports how many exercise blocks completed. A failing assertion must produce a failed process, not a generic success message.

Syntax anatomy and execution trace#

An import statement loads a declared module binding. The node: prefix identifies a built-in Node module rather than an installed package. const creates a binding that cannot be reassigned, while the object it references may still be mutable. import.meta.url identifies the current ES module. typeof can inspect an undeclared host global without throwing, which is useful for distinguishing Node from a browser without pretending to implement the missing API.

Worked example / walkthrough#

Example A: Inspect the actual host#

The version check verifies the actual process rather than trusting a file extension. The prepared profile is the supported baseline for later host APIs.

import { strict as assert } from 'node:assert';



export async function verify() {
  // Worked example
  {
    assert.equal(Number(process.versions.node.split('.')[0]), 24);
    assert.equal(process.release.name, 'node');
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: major version 24; process.release.name is node.

Example B: Distinguish browser globals#

A browser DOM lesson cannot be validated by a Node run that never had a document. Later browser chapters use separate real HTML fixtures.

import { strict as assert } from 'node:assert';



export async function verify() {
  // Worked example
  {
    assert.equal(typeof document, 'undefined');
    assert.equal(typeof window, 'undefined');
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: both undefined.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

Exercises#

  1. Inspect the actual host. Check that the prepared runtime is Node 24 and that process exists. Expected: major version 24; process.release.name is node. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Distinguish browser globals. Inspect document and window using typeof inside Node. Expected: both undefined. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Use language arithmetic independently of host APIs. Calculate 2+3 and compare the numeric result with a string. Expected: number 5; not strictly equal to string 5. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Inspect module identity. Read import.meta.url and confirm it identifies the current module. Expected: a file URL ending in .mjs in the classroom. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Observe strict module function calls. Call an ordinary function without a receiver and inspect this. Expected: this is undefined. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Await a real Promise result. Resolve 7 through a Promise and await it before checking. Expected: observed value 7 after await. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.

Self-check and retrieval#

Close the solution and explain ECMAScript, Host, ES module using the fixture. Reconstruct one example from a blank saved copy. Change a boundary input and predict the new result before running it. Explain the assumptions under which the mechanism is useful and a situation in which its cost or host requirements make another design preferable. A copied program is useful rehearsal; a fresh case demonstrates transfer.
