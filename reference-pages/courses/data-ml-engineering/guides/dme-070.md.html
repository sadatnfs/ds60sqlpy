dme-070: Cancellation, errors and recovery without replay#

Level: Advanced | Prepared runtime: python-core

Direct prerequisites: dme-069.

Outcome: Preserve resource ownership during cancellation and mark interrupted requests without replay.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

A cancellation request is a control message, not a time machine. It can prevent future work and request that a running operation stop at the next safe boundary. It cannot generally undo a token already emitted or instantly preempt an arbitrary in-flight device kernel. A correct serving lifecycle distinguishes cancellation requested, compute stopped, resources released and terminal record retained.

This chapter uses a small explicit state machine and a recovery example. The full project additionally tests queued cancellation, running cancellation, subscriber timeout, slow-consumer cancellation and injected inference failure. Those tests check reservation release and retained events rather than merely observing a successful cancellation HTTP response.

States and legal transitions#

A request begins queued after admission. It can become running when the worker takes it, or cancelled while still waiting. Running work can end completed, cancelled or error. Terminal states are immutable under the ordinary API. A read of a terminal request has no transition back to running.

It is useful to treat cancellation requested as a flag on active work rather than pretending it is already terminal. The compute loop checks the flag between steps. If cancellation arrives during a matrix operation, the operation must return before the request's cache and reservation can be released safely. The HTTP handler can acknowledge the request while the worker is still cleaning up.

A scheduler that immediately returns the reservation to the free pool may admit another request while the old one still occupies memory. Conversely, forgetting cleanup on an exception leaks capacity. Put ownership changes in a well-defined completion path and test every route to it.

Let R0R_0R0​ be a request's original reserved amount and r(t)r(t)r(t) the amount it still owns. Before completion of cleanup, r(t)=R0r(t)=R_0r(t)=R0​; afterward r(t)=0r(t)=0r(t)=0. Repeated cancellation must not make r(t)r(t)r(t) negative. This simple invariant is more useful than a collection of loosely related boolean flags.

Error categories are part of the interface#

Validation errors happen before admission and should not consume inference resources. Capacity errors likewise mean the request was not admitted. Runtime errors happen after acceptance and need a terminal event tied to the accepted identity. Storage errors can occur before admission or while retaining actual output, and those cases need different treatment.

If the initial request cannot be saved, the service rejects creation and does not start inference. If a later record update fails after real computation, the in-memory result remains real output. The terminal response must report that durability is uncertain and offer an explicit download. It must not pretend execution never happened or automatically rerun it to obtain a cleaner receipt.

The project uses a bounded safe error category for unexpected inference failure. It does not send private stack traces or authentication values to the browser. Diagnostic logs and tests can retain the detailed failure in an appropriate local context. Clear categories help the learner distinguish a model numerical problem from a stream or storage problem.

Queued versus running cancellation#

Cancelling a queued request removes it from the pending FIFO and releases its reservation without calling the model. Cancelling a running request sets its cancellation flag, wakes waiting control paths where necessary, and waits for the compute path to finish. The final reason remains associated with the original request.

A client disconnect is a separate cause. Under this workshop's policy, losing the only subscriber requests cancellation. The terminal record may contain partial output, which remains inspectable later. Another service could choose to keep generating after disconnect, but it would need an explicit durable job policy and bounded retained output. Neither choice should be left to accidental framework behavior.

Timeouts also need names. The subscriber-attach timeout limits how long an admitted request waits for its reader. The backpressure timeout limits how long output waits for the bounded subscriber queue. An operation timeout, if implemented, limits computation. A single generic “timed out” label hides which resource boundary failed.

Worked case 1: a cancellation flag is not released memory#

The first case starts a request in running state with a reservation of 48. Calling cancel() sets a flag, but the request remains running and retains 48. Only kernel_returned() changes it to cancelled and releases the reservation. Calling the completion method again leaves the amount at zero.

The exact assertions demonstrate cooperative cancellation and idempotent cleanup. This is a mechanism model, not a demonstration that Python can interrupt arbitrary device code. In the live project, cancellation is checked around real model steps, and the single compute thread is allowed to return before the scheduler starts the next request.

This case applies to database calls, compiled computations and external services as well as model inference. If an operation cannot be safely interrupted, separate caller cancellation from eventual resource cleanup. The user should see that cancellation was requested without receiving a false promise of instantaneous termination.

Worked case 2: an interrupted record after restart#

The second case contains one unfinished event sequence and one completed sequence. Recovery appends an explicit interruption error to the unfinished request and leaves the completed one unchanged. The generation-call counter stays zero. Recovery does not fill the missing tokens by running the prompt again.

The changed condition matters because a crash may occur after a user saw some output but before the final record was saved. Replaying would create a new execution under an old identity and could duplicate side effects in a larger application. Even when the model itself has no external side effects, the source-bound result and user's expectation would be violated.

"""Cancellation state and interrupted recovery are not automatic retries."""

from dataclasses import dataclass


@dataclass
class Request:
    state: str = "running"
    reserved: int = 48
    cancel_requested: bool = False

    def cancel(self):
        self.cancel_requested = True

    def kernel_returned(self):
        if self.state == "running" and self.cancel_requested:
            self.state = "cancelled"
            self.reserved = 0


def example_one():
    item = Request()
    item.cancel()
    assert item.state == "running" and item.reserved == 48
    item.kernel_returned()
    assert item.state == "cancelled" and item.reserved == 0
    item.kernel_returned()
    assert item.reserved == 0
    print("Cancellation requested first; reservation released exactly once after compute returns.")


def example_two():
    persisted = {"a": ["queued", "started", "token"], "b": ["queued", "started", "completed"]}
    original_b = tuple(persisted["b"])
    calls = 0
    for events in persisted.values():
        if events[-1] not in {"completed", "cancelled", "error"}:
            events.append("error:interrupted_by_restart")
    assert persisted["a"][-1] == "error:interrupted_by_restart"
    assert tuple(persisted["b"]) == original_b
    assert calls == 0
    print("Recovery records interruption; completed history remains unchanged:", persisted)
    print(
        "A new explicit request needs a new identity. "
        "Never infer missing output by rerunning old source."
    )


def main():
    example_one()
    example_two()


if __name__ == "__main__":
    main()

Durable records and failure windows#

An atomic file replacement prevents readers from observing half of a newly written snapshot, provided the filesystem and write protocol meet the stated assumptions. Flushing file and directory metadata improves durability, but no local design can promise survival of every hardware or storage failure. The service should describe what was acknowledged and what remains uncertain.

The workshop validates checksums, source hashes, exact event order, allowed transitions, bounded sizes and file identities on startup. A malformed stored record blocks normal recovery with an explicit error rather than being silently ignored or treated as permission to run. Preserve faulty bytes for diagnosis. Do not broaden exception handling until every corrupted record merely disappears from history.

A completed record is immutable. A repeated read can be verified by hashing its exact bytes before and after container replacement. Container identity may change while record identity remains the same because state is mounted separately. Deleting the state directory is different from replacing a container and is not part of normal resume.

Shutdown and resource scope#

Graceful shutdown stops new admission, requests cancellation of active work and waits for cleanup within a bounded process lifecycle. A hard kill can bypass that cleanup; startup recovery then marks unfinished records interrupted. Test both cases because successful graceful shutdown does not qualify crash recovery.

Cleanup must target only the workshop's owned resources. Never prune unrelated containers, delete a learner's classroom volumes or reset a shared accelerator to recover this local example. The helper's stop and replacement actions preserve its model and state files. Archiving or discarding those files is a separate explicit decision.

Interview discussion#

Why acknowledge cancellation before marking a request terminal? The control request can be accepted while in-flight computation still owns resources. Terminal status should reflect that execution and cleanup have actually stopped.

What should happen if saving a successful result fails? Preserve the real result in memory, report a durability warning and provide an explicit export if possible. Do not rewrite the execution outcome as though nothing ran, and do not silently replay it.

Why is restart recovery a state transition rather than a retry policy? Recovery interprets retained evidence and records interruption. Retrying creates new work and requires explicit authorization and a new or deliberately reconciled identity.
