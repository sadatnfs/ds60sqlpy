## Serialization is a meaning-preservation problem

Serialization turns values into a representation that can be stored or transferred. Reading the representation reconstructs values under a consumer's interpretation. A successful write followed by a successful read does not prove that every important distinction survived: types, precision, timezone information, empty strings, missing values and identifiers can change meaning at the boundary.

The example uses an actual Arrow table and an actual Parquet file through the prepared PyArrow library. It also writes and reads CSV with the standard Python module and creates an explicit JSON representation. Each case checks the particular values and schema it claims to preserve. It does not assume that every reader in another language or engine will choose the same conversion policy automatically.

The two synthetic deliveries have string IDs `001` and `002`, small integer package counts, a decimal distance, an optional note and an aware observation timestamp. Leading zeroes belong to the identifier representation. An empty note is a supplied empty string; a missing note is a different state. The first distance is the declared decimal value 1.20 km, while the second is missing.

## Distinguish memory layout from file layout

Arrow defines typed columnar structures used for in-memory interchange and related transport formats. A column can carry a physical value type and separate validity information. Parquet is a columnar file format with its own encoding, row-group, compression and metadata structures. They work together in many systems, but an Arrow table is not simply another name for a Parquet file.

A **schema** gives fields their names and types. A **columnar** representation groups values from a column rather than storing every complete record as one adjacent row object. This can support efficient analytical processing and selective reads. It does not guarantee that every workload will be faster, that every conversion is zero-copy or that a consumer understands an application's business units.

The fixture uses a 16-bit integer package column to make physical width visible. That choice has a finite representable range. It is appropriate for these tiny declared values, not a recommendation to choose the narrowest type from a small sample and assume future data will fit. Producer, storage and consumer contracts must agree on relevant bounds.

The decimal column has declared precision and scale, and the timestamp column uses millisecond precision with UTC timezone information. These are concrete representation choices. A different precision can round or reject values, and a timestamp without the same time interpretation may describe a different claim even when its printed text looks similar.

## Missingness is separate from an empty value

For the note column, Arrow retains a validity bitmap. In this representation a valid empty string can have no character bytes while still being marked valid. A null can also have no character bytes but is marked invalid. Inspecting only the apparent string length would lose that distinction.

The first two validity bits in the example are true and false. The program reads the actual buffer and checks those bits against the logical values `""` and `None`. This is a small concrete illustration of why a typed format can preserve information that a naive text convention collapses.

The validity bit does not explain why a value is missing. A separate reason or availability field may still be necessary. Physical representation and semantic policy are related layers, not substitutes for each other.

## Worked case 1: Inspect a real Arrow-to-Parquet round-trip

The first case constructs the typed Arrow table, writes a compressed Parquet file in an owned temporary directory and reads it back. The restored schema must equal the original schema, and the restored Python values must equal the original table's values. The package column must remain 16-bit integer data, and the file metadata must report two rows.

The note-column check confirms that the empty string remains valid and the missing note remains null. The timestamps were supplied as aware UTC values at the declared precision, so the fixture does not ask the writer to guess a timezone. The decimal value is constructed from decimal text rather than an already approximated binary float.

The classroom displays the actual restored records as a bounded table. Decimal and timestamp values are explicitly converted for that display interface: the distance becomes decimal text and the timestamp becomes an ISO-format string. The underlying Parquet/Arrow checks happen before this presentation conversion. Do not confuse the display's JSON-compatible values with the exact in-memory Arrow types.

This successful round-trip qualifies the demonstrated library operations and fixture. It does not prove that an arbitrary downstream tool will preserve every logical type or extension. Cross-engine interchange needs an actual readback with the intended consumer and the same relevant invariants.

## Text formats require their own conventions

CSV commonly represents fields as text under a dialect. The default Python writer used here writes both an empty note and a `None` note into empty fields. The corresponding default dictionary reader therefore sees two empty strings. CSV can be used with additional null conventions, but those conventions must be implemented consistently by the intended writer and reader.

A reserved null token can conflict with a real text value unless escaping and interpretation are specified. A reader that automatically infers types can also alter identifiers or numeric precision. A schema file, a controlled dialect or a typed format can make those choices explicit. No format removes the need to understand the actual consumer.

JSON distinguishes strings, numbers, booleans, arrays, objects and nulls, but it does not have native decimal or datetime types. A Python object can therefore contain values that a default JSON encoder cannot serialize directly. A generic conversion of every unknown object to a string may hide mistakes. Prefer an explicit mapping for the specific fields and meanings you intend to exchange.

## Worked case 2: Expose loss and define an explicit portable representation

The changed case writes selected fields to CSV and reads them back. Both note values become empty strings, while the package counts become the text values `"2"` and `"3"`. These are actual observed reader results. They are not evidence that the original missingness and integer types were preserved.

The program then tries to JSON-encode the Arrow table's native Python values and confirms that a type error is raised. It deliberately constructs a portable document that keeps identifiers as strings, writes distance as decimal text or null, and writes timestamps as ISO-format strings. The document also states its schema version and distance representation.

After a JSON round-trip, the first distance can be reconstructed as `Decimal("1.20")` under that declared policy, and the identifier remains `001`. The program does not silently infer these meanings from a bare string. A consumer must read and enforce the corresponding contract.

The structured report also uses actual JSON arrays for schema-name/type pairs. An API may deliberately require JSON-native values even when a general-purpose Python encoder would coerce another container such as a tuple. Knowing one encoder's behavior is not enough to establish another interface's acceptance contract. The final report is validated by the classroom's bounded output interface.

## Complete worked program

```python
"""Real Arrow/Parquet round-trips and explicit text-format interpretation."""

import csv
import io
import json
import tempfile
from datetime import UTC, datetime
from decimal import Decimal
from pathlib import Path

import pyarrow as pa
import pyarrow.parquet as pq


def fixture():
    return pa.table(
        {
            "delivery_id": pa.array(["001", "002"], type=pa.string()),
            "packages": pa.array([2, 3], type=pa.int16()),
            "distance_km": pa.array([Decimal("1.20"), None], type=pa.decimal128(8, 2)),
            "note": pa.array(["", None], type=pa.string()),
            "observed_at": pa.array(
                [datetime(2024, 1, 1, 8, tzinfo=UTC), datetime(2024, 1, 1, 9, tzinfo=UTC)],
                type=pa.timestamp("ms", tz="UTC"),
            ),
        }
    )


def portable_rows(table):
    return [
        {
            **row,
            "distance_km": str(row["distance_km"]) if row["distance_km"] is not None else None,
            "observed_at": row["observed_at"].isoformat(),
        }
        for row in table.to_pylist()
    ]


def example_one():
    table = fixture()
    with tempfile.TemporaryDirectory() as directory:
        path = Path(directory) / "deliveries.parquet"
        pq.write_table(table, path, compression="zstd")
        restored = pq.read_table(path)
        assert restored.schema == table.schema and restored.to_pylist() == table.to_pylist()
        assert restored.column("packages").type == pa.int16()
        note = restored.column("note").combine_chunks()
        mask = note.buffers()[0].to_pybytes()[0]
        validity = [bool(mask & (1 << position)) for position in range(2)]
        assert validity == [True, False] and note.to_pylist() == ["", None]
        return {
            "rows": portable_rows(restored),
            "schema": [[field.name, str(field.type)] for field in restored.schema],
            "note_validity": validity,
            "parquet_rows": pq.read_metadata(path).num_rows,
        }


def example_two():
    table = fixture()
    stream = io.StringIO(newline="")
    writer = csv.DictWriter(stream, fieldnames=["delivery_id", "packages", "note"])
    writer.writeheader()
    writer.writerows({name: row[name] for name in writer.fieldnames} for row in table.to_pylist())
    records = list(csv.DictReader(io.StringIO(stream.getvalue(), newline="")))
    assert [row["note"] for row in records] == ["", ""]
    assert [row["packages"] for row in records] == ["2", "3"]
    try:
        json.dumps(table.to_pylist())
    except TypeError:
        default_json_rejected_native_types = True
    else:
        raise AssertionError("Native Decimal/datetime values require an explicit JSON policy")
    document = {
        "schema_version": 1,
        "distance_representation": "decimal text in kilometers",
        "rows": portable_rows(table),
    }
    decoded = json.loads(json.dumps(document, allow_nan=False))
    assert Decimal(decoded["rows"][0]["distance_km"]) == Decimal("1.20")
    assert decoded["rows"][0]["delivery_id"] == "001"
    return {
        "csv_rows": records,
        "csv_lost_empty_vs_null_note": True,
        "default_json_rejected_native_types": default_json_rejected_native_types,
        "explicit_json_contract": decoded,
    }


def main():
    from ds60sqlpy.plot_artifacts import publish_report, publish_table

    first, second = example_one(), example_two()
    columns = ["delivery_id", "packages", "distance_km", "note", "observed_at"]
    publish_table(
        columns,
        [[row[name] for name in columns] for row in first["rows"]],
        description=(
            "Actual Parquet round-trip of two synthetic deliveries; "
            "empty text and missing values remain "
            "distinct."
        ),
    )
    publish_report(
        {
            "arrow_schema": first["schema"],
            "note_validity": first["note_validity"],
            "text_format_comparison": second,
        },
        description=(
            "Observed Arrow schema, validity bits and declared CSV/JSON conversion behavior."
        ),
    )
    print("Parquet rows:", first["parquet_rows"], "note validity:", first["note_validity"])
    print("CSV note values:", [row["note"] for row in second["csv_rows"]])


if __name__ == "__main__":
    main()
```

## Diagnose a round-trip with independent checks

Inspect values and schema separately. A row count can remain correct while nulls turn into empty strings or identifiers lose leading zeroes. A numeric value can look unchanged while its physical width or precision changes. A timestamp can retain its clock text while losing the information that identifies the intended instant.

Choose assertions according to the intended contract. Exact IDs, declared null positions and integer counts often need exact equality. Numerical approximations may need a justified tolerance. Schema comparisons should state whether metadata, order, nullability or extension information matters to the consumer.

Also separate logical correctness from performance. A compressed file being smaller is not proof that a query reads fewer bytes. A columnar format supports useful physical strategies, but the actual layout, selected columns, predicates and engine behavior determine a particular observation. Chapter 018 inspects those boundaries directly.

The pad's Parquet file is temporary. The retained table and report are source-bound observations, not a persistent copy of the binary file. Use a separately owned project workflow when you need durable file delivery or an actual cross-process transfer test.

## Where this is useful

These checks belong in dataset exchange, feature storage, training snapshots, analytics exports and service responses. They are especially useful when moving between Python, SQL, JVM, Rust or browser consumers, whose default representations and numeric limits can differ.

## Answered interview discussion

**What can be lost in a successful CSV round-trip?** The chosen dialect may collapse missing and empty values, return all fields as text or trigger a consumer's type inference. Check the exact writer/reader contract rather than treating the extension as a schema.

**Does Arrow mean every conversion is zero-copy?** No. Compatibility of types, buffers, chunking and the receiving API matters. Verify the actual conversion and its requirements before making a performance claim.

**Why serialize decimals as text here?** The display/API contract can preserve the declared decimal representation without assuming a browser number has identical decimal semantics. The consumer still needs the explicit unit and parsing policy.

**What is the strongest round-trip check?** It depends on the use. Combine identified-row, type, validity, precision and time-interpretation checks appropriate to the consumer, rather than relying on a single unchanged total.
