# go-010: Methods, interfaces and the typed-nil trap

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-009

## Learning objectives

Define behavior through interfaces and methods, choose value or pointer receivers, and detect the typed-nil interface trap. Along the way, explain method set, interface, dynamic type; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A method associates behavior with a named type. An interface describes a set of methods, and a concrete type satisfies it implicitly by providing that set. This encourages small interfaces defined by the consumer instead of deep inheritance hierarchies. A value receiver receives a copy; a pointer receiver can mutate its target and has a different method set. An interface value contains both dynamic type information and a dynamic value. It is nil only when both are absent. Therefore an interface holding a typed nil pointer is not a nil interface. This matters especially when returning errors or optional implementations across package boundaries.

## Vocabulary and concepts

- **Method set:** The methods available for a type and its pointer form.
- **Interface:** A behavior contract expressed as methods.
- **Dynamic type:** The concrete type stored inside an interface value.

## Syntax anatomy and reasoning

func (c Counter) Value() int declares a value receiver. func (c *Counter) Add(n int) uses a pointer receiver. type Valuer interface { Value() int } declares required behavior. A type assertion value, ok := item.(Concrete) checks a dynamic type safely. Prefer the comma-ok form when failure is expected, rather than a panic-producing assertion.

## Worked example / walkthrough

### Worked example 1: Dispatch through behavior

Store Counter with value 3 in a Valuer interface.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Counter struct{ N int }

func (c Counter) Value() int       { return c.N }
func (c *Counter) Add(n int)       { c.N += n }
func (c Counter) Incremented() int { c.N++; return c.N }

type Valuer interface{ Value() int }
type Fixed int

func (f Fixed) Value() int   { return int(f) }
func readValue(v Valuer) int { return v.Value() }

func main() {
	// Dispatch through behavior
	{
		var v Valuer = Counter{N: 3}
		check(v.Value() == 3, "interface dispatch")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Calling Value returns 3.

The concrete type satisfies the interface without declaring that relationship. The caller depends only on the method contract.

### Worked example 2: Mutate through a method

Call Add on a pointer to Counter starting at 3.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Counter struct{ N int }

func (c Counter) Value() int       { return c.N }
func (c *Counter) Add(n int)       { c.N += n }
func (c Counter) Incremented() int { c.N++; return c.N }

type Valuer interface{ Value() int }
type Fixed int

func (f Fixed) Value() int   { return int(f) }
func readValue(v Valuer) int { return v.Value() }

func main() {
	// Dispatch through behavior
	{
		var v Valuer = Counter{N: 3}
		check(v.Value() == 3, "interface dispatch")
	}

	// Mutate through a method
	{
		c := Counter{N: 3}
		c.Add(2)
		check(c.N == 5, "pointer receiver")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Its value becomes 5.

The language can take the address of this addressable variable for the method call. The pointer receiver makes the mutation effective on the original value.

## Common pitfalls and diagnosis

The typed-nil trap is this lesson's signature bug: a function declares `var p *MyError` and returns it as `error`, so the caller's `err != nil` is true although nothing failed. Return a literal nil instead. Another surprise is a value-receiver method that appears to mutate but changes only its copy. When a single-value type assertion would panic on unexpected input, use comma-ok.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Dispatch through behavior: change one input

1. Restate the expected observation: Calling Value returns 3.
2. Counter's Value method has a value receiver. Does that make Counter satisfy Valuer?
3. The interface now dispatches to a Counter holding 4, so Value returns 4 and `v.Value()==3` fails. Dispatch still works; only the stored value changed.

### Hint for investigation 2: Mutate through a method: debug a regression

1. Restate the expected observation: Its value becomes 5.
2. Add has a pointer receiver. Which value does it modify when called on the addressable variable c?
3. Starting from 4, `Add(2)` yields 6, so `c.N==5` fails. The pointer receiver mutated the original correctly; the starting value is the regression.

### Hint for investigation 3: Trace a value receiver

1. Restate the expected observation: The returned value is 4 but the original remains 3.
2. A value receiver works on a copy. Which counter does `c.N++` inside Incremented change?
3. Changing a value receiver's scalar field changes the copied receiver.

### Hint for investigation 4: Expose typed nil

1. Restate the expected observation: The interface is not nil.
2. An interface value holds a dynamic type and a value. Which of the two is nil here?
3. The interface contains the dynamic type *Counter even though its dynamic pointer is nil.

### Hint for investigation 5: Use safe dynamic inspection

1. Restate the expected observation: The assertion reports false without panicking.
2. Comma-ok reports a mismatch instead of panicking. What does ok hold when the dynamic type is string?
3. A failed dynamic conversion is ordinary evidence when the input type is uncertain.

### Hint for investigation 6: Transfer substitutability

1. Restate the expected observation: Both implementations can be read through one contract.
2. readValue needs only the Value method. What must Fixed provide to be accepted?
3. The consumer should not depend on concrete fields or perform a type switch unless its real contract requires different behavior.
