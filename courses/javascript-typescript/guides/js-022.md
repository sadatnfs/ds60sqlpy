# js-022: Generic functions and constraints

## Level and prerequisites

Intermediate, approximately 90 minutes. Direct prerequisites: `js-021`

## Learning objectives

Explain type parameter, constraint, keyof, indexed access type with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Pass a number and an object through identity. The final task tests avoid pretending a constraint is the exact caller type.

## Purpose and mental model

Generics express a relationship between types across a reusable operation. An identity function returning any loses information about the relationship between input and output. A generic identity function returns the same type T supplied by its caller. The parameter is not a runtime argument or a request to create a new specialized JavaScript function for every type; it is a compile-time relation checked against one implementation.

A constraint gives the implementation only the operations known to exist. T extends {length: number} permits reading length, but does not permit replacing the input with an arbitrary object containing length and claiming it is still the caller's exact T. The caller may have supplied an array, a string or a richer record with additional invariants.

keyof and indexed access types connect property keys to property result types. A generic getProperty<T,K extends keyof T> returns T[K], preserving whether the chosen field is a string or a number. This is useful when the relationship is real. Overly elaborate generics can make an API harder to understand; prefer a concrete parameter type when only one domain shape is needed. Generics cannot validate unknown JSON or prove that an external service honored a claimed schema.

## Vocabulary and concepts

**Type parameter:** A placeholder describing a relationship selected at a call site.

**Constraint:** The minimum structure a generic implementation may rely on.

**Keyof:** A type operator producing the known keys of a type.

**Indexed access type:** A type expression selecting the type associated with a key.

## Syntax anatomy and execution trace

Declare type parameters in angle brackets on the function. T names a caller-selected type; extends constrains its allowed structure. K extends keyof T restricts a key to known properties, and T[K] gives the corresponding value type. A generic function returning the first element should expose T | undefined for an empty input even when the project's indexed-access checking is less strict. Runtime control flow must implement the same absence policy.

## Worked example / walkthrough

### Example A: Preserve identity type and object identity

The generic relationship preserves static information without copying data. Runtime identity is still a separate observation checked by the assertion.

```typescript
import { strict as assert } from 'node:assert';

function identity<T>(value: T): T { return value; }
function getProperty<T, K extends keyof T>(value: T, key: K): T[K] { return value[key]; }
function first<T>(values: readonly T[]): T | undefined { return values.length === 0 ? undefined : values[0]; }
function measuredLength<T extends { length: number }>(value: T): number { return value.length; }
function mapValues<T, U>(values: readonly T[], convert: (value: T) => U): U[] { return values.map(convert); }

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const value: number = identity(7);
    const record = { id: 'A' };
    assert.equal(value, 7);
    assert.equal(identity(record), record);
    function negativeTypeCheck(): void {
      // @ts-expect-error identity preserves number rather than inventing string.
      const text: string = identity(7);
      void text;
    }
    void negativeTypeCheck;
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** number remains 7; object is the same reference.
### Example B: Connect a key to its exact result type

Returning a broad string|number union would lose the connection between the selected key and its payload. T[K] preserves that correlation.

```typescript
import { strict as assert } from 'node:assert';

function identity<T>(value: T): T { return value; }
function getProperty<T, K extends keyof T>(value: T, key: K): T[K] { return value[key]; }
function first<T>(values: readonly T[]): T | undefined { return values.length === 0 ? undefined : values[0]; }
function measuredLength<T extends { length: number }>(value: T): number { return value.length; }
function mapValues<T, U>(values: readonly T[], convert: (value: T) => U): U[] { return values.map(convert); }

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const row = { id: 'A', count: 2 };
    const id: string = getProperty(row, 'id');
    const count: number = getProperty(row, 'count');
    assert.equal(id, 'A');
    assert.equal(count, 2);
    function negativeTypeCheck(): void {
      // @ts-expect-error missing is not a key of this record.
      getProperty(row, 'missing');
    }
    void negativeTypeCheck;
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** id is string A; count is number 2.

## Prediction before your attempt

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

## Progressive hints

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
