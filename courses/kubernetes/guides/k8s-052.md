# k8s-052: LoadBalancer Services: cloud controllers and local limitations

## Purpose, vocabulary and mental model

A load balancer distributes traffic among eligible destinations. A Kubernetes Service of type LoadBalancer asks an integrated implementation to provision or configure an external entrypoint. The API object is a request; a controller and supporting infrastructure must exist to fulfill it.

In a cloud, the controller may create provider resources, addresses, listeners and health checks. A local cluster may have no such integration and leave the external address pending. Local load-balancer implementations have their own routing and address-allocation requirements. The course does not install one or incur cloud resources automatically.

Load balancing is not a database replication mechanism, a certificate authority or application authorization. A reachable address can still route to unready nodes, wrong ports or an app that returns errors. Diagnose controller status, infrastructure health and actual request behavior separately.

## Mechanism and field-by-field reasoning

Inspect Service spec.type, loadBalancerClass when used, traffic policy, ports and status.loadBalancer.ingress. An ingress entry can contain an IP or hostname. Do not assume status arrives immediately or that a returned hostname resolves from every network.

Many implementations use NodePorts, while others can route directly to Pods or use alternate mechanisms. The allocation and routing design is implementation-specific. Changing allocateLoadBalancerNodePorts without knowing the implementation can remove a required path.

## Trace the request or control path

```text
Service intent -> load-balancer controller -> provider/local infrastructure
client -> external listener -> node or Pod backend path -> application
```

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

## Worked example / walkthrough

### Worked example 1: Interpret pending external status

This is a synthetic local-cluster observation.

```text
spec.type=LoadBalancer
status.loadBalancer.ingress=[]
no load-balancer controller is prepared
```

**Expected observation:** Pending status is an unavailable capability, not proof that the app container is broken.

### Worked example 2: Separate listener and application acceptance

A sequence of increasingly strong observations.

```text
external address assigned -> listener reachable -> healthy backend selected
-> expected HTTP route -> expected application body
```

**Expected observation:** Address allocation alone does not establish the final result.

## Diagnosis, failure boundaries and common mistakes

The controlled failure in this chapter is: Diagnose assigned address with no successful requests. Its distinguishing result is Inspect listener, health checks, backend route and app behavior. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
