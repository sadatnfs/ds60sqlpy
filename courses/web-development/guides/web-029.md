# web-029: Browser trust boundaries: text, origins and policy

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-028`

## Learning objectives

Build a small rendering demo that separates text handling from URL policy. Explain the separate roles of escaping, validation, CSP and sandboxing. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

An origin is generally a combination of scheme, host and port. The browser uses origins to separate access to data and documents. The same-origin policy is not a complete application security system; a server still needs authentication, authorization and deliberate cross-origin behavior. CORS is a protocol for relaxing some browser response-reading restrictions, not a mechanism that makes an unsafe endpoint safe.

Injection occurs when data is interpreted as code or structure in a context where it should remain data. textContent avoids HTML parsing for text, while building an href still requires a separate URL policy. Content Security Policy can reduce what a document may load or execute, but it is a defense layer rather than a replacement for correct output handling. The classroom preview is deliberately isolated and network restricted.

## Syntax anatomy and mechanism

Treat rendering contexts separately: HTML text, quoted HTML attribute, URL, JavaScript and CSS each have different rules. This reference renders an attack-shaped string only as text. No attack is performed against another site. A sandboxed iframe can have an opaque origin, so do not assume localStorage, cookies or a same-origin parent API exists inside the preview.

## Classroom execution and offline inputs

Choose **HTML browser preview** in the classroom. The pad is one complete HTML document with embedded CSS and, where taught, embedded JavaScript. Its preview is isolated from the classroom and recreated on each run. It does not contact a server, submit real forms, read cookies, fetch assets or load a CDN. All fixtures are inline and synthetic. The browser uses its native HTML parser, so classic-script ordering, shared lexical bindings, inline modules and real DOMContentLoaded/load events keep their browser semantics. External module imports remain blocked. Navigation metadata such as base and meta http-equiv is rejected explicitly. On any supported host, the browser renders the document while Docker serves the classroom. No host compiler is needed.

## Worked example / walkthrough

### Worked example 1: Data stays text

The potentially meaningful syntax is never parsed as markup.

```javascript
const value = '<img src=x onerror=alert(1)>';
output.textContent = value;
```

**Expected observation:** The source string appears literally and no image element is created.

### Worked example 2: A URL decision

Validate the scheme before using a URL in navigation.

```javascript
const url = new URL('https://example.invalid/notes');
const allowed = url.protocol === 'https:';
```

**Expected observation:** The application explicitly decides which scheme is acceptable; this does not fetch the URL.

## Debugging and common mistakes

Do not advertise a sanitizer based on replacing a few characters in every possible context. Avoid weakening the classroom sandbox to make a remote demo work. A policy failure is evidence about a restricted capability, not a reason to disable all protections.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.
