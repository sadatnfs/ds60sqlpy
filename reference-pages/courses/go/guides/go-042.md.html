go-042: Informer caches, stale reads and safe object copies#

Level and prerequisites#

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-041

Learning objectives#

Read from an informer-style cache safely by copying before mutation, gating on synchronization and queueing keys. Along the way, explain informer, eventual consistency, deep copy; implement the six investigations below; and defend the expected result of a changed input before running it.

Why this mechanism matters#

An informer maintains a local view of API objects and supplies events that can enqueue reconciliation. Its cache improves efficiency but is eventually consistent: a successful write may not be visible in the cache immediately. Wait for initial cache synchronization before relying on its contents. Objects returned from shared caches must be treated as read-only. Mutating them in place can corrupt observations for other consumers without making any API change. DeepCopy before constructing an update, and use the API response or a fresh read when a particular consistency requirement demands it. A cache miss is evidence about that view, not always proof of server-side absence.

Vocabulary and concepts#

  • Informer: A component maintaining a local watch-backed object cache.
  • Eventual consistency: A view that can lag a completed remote update.
  • Deep copy: A copy that separates mutable nested storage.

Syntax anatomy and reasoning#

An informer factory starts shared controllers; WaitForCacheSync confirms initial synchronization or cancellation. Listers read cached objects. The fixture models a cache map and a defensive copy of nested labels. Copying only the outer struct still aliases its map. Event handlers should enqueue keys quickly instead of blocking on long reconciliation or retaining stale object pointers as authoritative state.

Worked example / walkthrough#

Worked example 1: Copy before changing labels#

Copy a cached object and change its app label.

package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Cached struct {
	Labels  map[string]string
	Version string
}

func copyCached(v Cached) Cached {
	out := v
	out.Labels = map[string]string{}
	for k, value := range v.Labels {
		out.Labels[k] = value
	}
	return out
}

func main() {
	// Copy before changing labels
	{
		cached := Cached{Labels: map[string]string{"app": "web"}, Version: "a"}
		copy := copyCached(cached)
		copy.Labels["app"] = "api"
		check(cached.Labels["app"] == "web" && copy.Labels["app"] == "api", "copy")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: The cache still contains the original label.

The copy duplicates the map as well as the struct. An outer assignment alone would still share mutable labels.

Worked example 2: Expose a shallow-copy defect safely#

Assign a struct containing a map and mutate the assigned map sequentially.

package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Cached struct {
	Labels  map[string]string
	Version string
}

func copyCached(v Cached) Cached {
	out := v
	out.Labels = map[string]string{}
	for k, value := range v.Labels {
		out.Labels[k] = value
	}
	return out
}

func main() {
	// Copy before changing labels
	{
		cached := Cached{Labels: map[string]string{"app": "web"}, Version: "a"}
		copy := copyCached(cached)
		copy.Labels["app"] = "api"
		check(cached.Labels["app"] == "web" && copy.Labels["app"] == "api", "copy")
	}

	// Expose a shallow-copy defect safely
	{
		cached := Cached{Labels: map[string]string{"app": "web"}}
		shallow := cached
		shallow.Labels["app"] = "bad"
		check(cached.Labels["app"] == "bad", "shallow counterexample")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: The original observes the unintended change.

This is a deterministic sequential demonstration of aliasing. The real cache rule forbids such mutation, especially across concurrent consumers.

Exercises#

Exercise 1: Copy before changing labels: change one input#

Copy worked example 1, change cached := Cached{Labels: map[string]string{"app": "web"}, Version: "a"} to cached := Cached{Labels: map[string]string{"app!": "web"}, Version: "a"} and predict the failure before running; then restore the line.

Expected: The edited run panics with copy because cached.Labels["app"] == "web" && copy.Labels["app"] == "api" no longer holds.

Verify: Restoring cached := Cached{Labels: map[string]string{"app": "web"}, Version: "a"} makes the check pass again with the worked observation: the cache still contains the original label.

Exercise 2: Expose a shallow-copy defect safely: debug a regression#

A one-token regression in worked example 2 makes a line read shallow.Labels["app!"] = "bad". Repair it without changing the check.

Expected: The defective run panics with shallow counterexample; after restoring shallow.Labels["app"] = "bad", the original observes the unintended change.

Verify: The failing run shows message shallow counterexample; after the repair cached.Labels["app"] == "bad" holds again.

Exercise 3: Represent a stale view#

Deliver only the first of two watch events to a cache that starts at version a.

Expected: The cache shows b while the server's latest version is already c.

Verify: Your solution must keep cache.Version == "b" && events[len(events)-1].Version == "c" true. Control: changing delivered := 1 to delivered := 2 panics with message stale view; revert it.

Exercise 4: Gate on initial synchronization#

Offer one item to a processor before and after the cache reports synced.

Expected: No item is processed before the cache reports synced; one item is processed afterward.

Verify: Your solution must keep process(true) && processed == 1 true. Control: changing return true to return false panics with message after sync; revert it.

Exercise 5: Queue identities instead of objects#

Queue the key of a cached object, then let the store receive a newer version before the key is processed.

Expected: The queued key reads the latest object, version b, not the snapshot taken when it was queued.

Verify: Your solution must keep store[queue[0]].Version == "b" true. Control: changing queue := []string{"lesson/demo"} to queue := []string{"lesson/demo!"} panics with message key identity; revert it.

Exercise 6: Transfer nested-copy independence#

Add a new label to a copied object.

Expected: The original label count is unchanged.

Verify: Your solution must keep len(cached.Labels) == 1 && len(copy.Labels) == 2 true. Control: changing check(len(cached.Labels) == 1 && len(copy.Labels) == 2, "nested copy") to check(len(cached.Labels) != 1 && len(copy.Labels) == 2, "nested copy") panics with message nested copy; revert it.

Common pitfalls and diagnosis#

Mutating an object returned by an informer lister is the classic shared-cache bug: struct assignment copies the map header, not the map, so the change leaks into every reader and corrupts later comparisons. Call DeepCopy before editing. A cache read right after your own write may also be stale; do not treat absence or an old version as proof that the write failed.

General compiler, panic and error diagnosis is in the study guide.

Progressive hints#

Hint for investigation 1: Copy before changing labels: change one input#

  1. Restate the expected observation: The cache still contains the original label.
  2. copyCached builds a new map. Which value does the cache keep?
  3. The cached label key is now app!, so cached.Labels["app"] is empty and the check fails. copyCached still isolates the copy; the fixture lost its app key.

Hint for investigation 2: Expose a shallow-copy defect safely: debug a regression#

  1. Restate the expected observation: The original observes the unintended change.
  2. Assignment copies the map reference. Which map does shallow change?
  3. The write now goes to app!, so cached.Labels["app"] stays web and the counterexample check fails. Restore the app key; the shared map still shows the defect.

Hint for investigation 3: Represent a stale view#

  1. Restate the expected observation: The cache shows b while the server's latest version is already c.
  2. Only one event was delivered. Which version does the cache show?
  3. A lagging cache and a successful server update can coexist.

Hint for investigation 4: Gate on initial synchronization#

  1. Restate the expected observation: No item is processed before the cache reports synced; one item is processed afterward.
  2. process refuses work before sync. What do the two calls return?
  3. A started goroutine is not evidence that its initial list has completed.

Hint for investigation 5: Queue identities instead of objects#

  1. Restate the expected observation: The queued key reads the latest object, version b, not the snapshot taken when it was queued.
  2. The key is resolved when processed. Which version is in the store then?
  3. The next reconciliation obtains current state for the key.

Hint for investigation 6: Transfer nested-copy independence#

  1. Restate the expected observation: The original label count is unchanged.
  2. The copy owns its own map. How many labels does each hold?
  3. Separate nested storage matters for insertion and deletion as well as replacement of an existing value.
