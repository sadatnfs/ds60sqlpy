web-045: Templates and context-specific output escaping#

Level and prerequisites#

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: web-002, web-037, web-044

Learning objectives#

Render a study-card template from synthetic untrusted labels. Explain why validated text still needs output escaping. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

Purpose, vocabulary and mental model#

A template combines trusted structure with data. If a visitor's text is inserted directly into HTML, the browser may interpret it as elements or script-capable attributes. Output escaping represents the data so it remains data in a particular destination context. It is not a one-time cleanup that makes a value safe everywhere. Keep the original validated value and encode it when crossing the output boundary.

For HTML text and ordinary quoted attribute values, htmlspecialchars with explicit flags and UTF-8 is a useful primitive. It is not a JavaScript-string encoder, a CSS sanitizer or a URL policy. A URL in an href needs a separate scheme and destination decision before attribute escaping. Avoid dynamic inline scripts and styles when a simpler data boundary is available.

Syntax anatomy and mechanism#

Define a small e function that calls htmlspecialchars with ENT_QUOTES, ENT_SUBSTITUTE and UTF-8. Use it only for the contexts described by its contract. The CLI reference prints an HTML string as text so you can inspect the escaped bytes; it does not execute that string in a browser. A server template later uses the same contextual boundary before returning a response.

Classroom execution and offline inputs#

Choose the PHP CLI worker in the classroom. The pad is staged as main.php and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write <?php at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

Worked example / walkthrough#

Worked example 1: HTML text escaping#

The angle brackets must remain visitor data.

$name = '<Ada & Bea>';
echo htmlspecialchars($name, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');

Expected observation: The output contains &lt;, &amp; and &gt; references rather than live tags.

Worked example 2: A bounded template#

Only the fixed structure is authored markup.

$html = '<p>Hello, ' . e($name) . '</p>';

Expected observation: The greeting structure is fixed and the name stays text.

Six progressive exercises#

Exercise 1: Predict the escaped form of a name containing < and &.#

Expected evidence: The special syntax characters become HTML character references.

Progressive hint: Trace the smallest example before editing. Name which values are source and which are observations.

Exercise 2: Add an escaping helper with an explicit UTF-8 contract.#

Expected evidence: The helper names its HTML context and handles quotes as well as angle brackets.

Progressive hint: Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

Exercise 3: Render a study-card template from synthetic untrusted labels.#

Expected evidence: The structure stays fixed while labels are escaped at output.

Progressive hint: Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

Exercise 4: Explain why the same helper is insufficient for a JavaScript string.#

Expected evidence: JavaScript has a different parser and escaping rules; use a dedicated serialization boundary.

Progressive hint: Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

Exercise 5: Test quotes, ampersands and an attack-shaped tag string.#

Expected evidence: The resulting HTML string contains escaped data rather than an additional live element.

Progressive hint: Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

Exercise 6: Explain why validated text still needs output escaping.#

Expected evidence: A valid name can contain syntax characters that are meaningful in the destination context.

Progressive hint: Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

Debugging and common mistakes#

Do not escape data once on input and assume it is safe for SQL, JavaScript and HTML alike. Double escaping can corrupt display while still failing another context. Never label an arbitrary strip-tags operation a complete XSS defense.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

Retrieval, transfer and next steps#

Close the worked answers and explain template, HTML text context, escaping without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
