# Compilation, ABI versions and native lifetime

Start with: tmb-036, tmb-005.

Outcome: Build and retire native objects with explicit version and process ownership.

The classroom companion runs in the prepared R statistics runtime. It uses base R to expose the mathematics or data contract. Compiling and executing TMB uses the separate [owned project](../projects/tmb-local/README.md); a companion run is not a TMB compiler or rpy2 receipt.

`TMB.Version()` distinguishes package/API version information from ABI compatibility information. The ABI describes native entry points used by compiled model libraries. Two package versions can sometimes share an ABI, but a matching TMB ABI is only one compatibility condition: architecture, operating system, R and linked native libraries still matter. Our teaching project uses exact pins rather than claiming universal binary interchangeability.

`dynlib(name)` constructs the platform-specific shared-library filename. R's `dyn.load` loads it. `FreeADFun(obj)` releases TMB native allocations associated with an objective; it is not the same operation as unloading the DLL. `config(..., DLL=...)` reads or changes DLL-level configuration. Internal option names are version-sensitive and should not become arbitrary learner-controlled settings.

### Worked case A: one model, two source identities

The companion writes two original source-description files and compares their checksums. Even if a filename remains the same, the build receipt must identify the source that produced the native library. The prepared API checks the loaded library's resolved path and rejects another copy with the same model name.

`compile` invokes R's native build toolchain. `flags`, `framework`, `openmp`, `safebounds`, `safeunload`, `supernodal`, `longint` and `max.order` configure distinct compiler or library features. The ordinary project qualifies a conservative subset; custom SuiteSparse, long integer indices and specialized derivative orders need separate preparation and tests.

### Worked case B: precompilation is a preparation mutation

`precompile(all=TRUE, clean=FALSE, ...)` prepares TMB's library precompilation mechanism and requires write access to the package directory. Actual precompilation happens when a later model compile uses it. It belongs in an image build or owned development environment, not a read-only learner execution. The companion contrasts writable scratch state with immutable source metadata conceptually, without modifying an installed package.

Never unload a library while live objects can still call into it. A fresh bounded R process gives a straightforward lifecycle: load, construct, evaluate, report, exit. Long-lived services need deliberate ownership and cleanup after failures. Saving an R object does not serialize its executable native allocations portably.

### Answered discussion

**Does `FreeADFun` delete source or learner data?** No. It manages native objective memory. **Does `safeunload` make arbitrary concurrent unloading safe?** It supports TMB's lifecycle machinery but does not remove application ownership responsibilities. **Can I run precompile on a read-only container?** No, not where it needs package writes. Prepare it explicitly if it is part of the chosen build contract.

See [TMB.Version, compile, precompile, dynlib, FreeADFun and config](https://cran.r-project.org/web/packages/TMB/TMB.pdf).
