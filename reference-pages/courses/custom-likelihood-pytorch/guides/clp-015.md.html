clp-015: Optimizers and closure semantics#

Tutorial mode. Stage: advanced. Direct prerequisites: clp-006, torch-008.

An optimizer needs an executable contract#

A custom likelihood is often inexpensive enough that deterministic full-batch optimization is a better starting point than stochastic training. Adam and L-BFGS can both minimize differentiable objectives, but their state and evaluation patterns differ. Choosing one by habit without understanding those patterns can create incorrect gradient accumulation, misleading logs or irreproducible line searches.

Adam maintains moving summaries of gradients and squared gradients and typically uses one newly computed gradient per step. L-BFGS approximates inverse curvature from recent parameter and gradient differences. With line search, it may evaluate the objective several times at trial parameter values during a single call to step. Each evaluation must compute the same deterministic function at its current parameters.

Both runs recover the same target mean and final objective 0.04. One optimizer.step call invokes multiple closure evaluations, approximately eleven and nine in the prepared runtime. Those exact counts are implementation-dependent diagnostics, not mathematical requirements. Assertions concern numerical estimates and gradients rather than locking a particular line-search trajectory.

The value returned from this PyTorch L-BFGS step is the original loss value evaluated before its internal updates, not a guarantee of final objective. The example prints it separately from the recomputed final objective. Logging only the returned value can make a successful optimization look unchanged or can attach a stale loss to updated parameters.

Worked case 2: Adam reaches the same scientific target#

Starting again at -1.5, the program takes 600 Adam steps at a fixed modest learning rate. Each step clears accumulated gradients, recomputes loss, backpropagates and updates the parameter. The final fitted mean and score are checked against the same independent target as the L-BFGS runs.

This is a numerical comparison on one tiny deterministic objective. It is not a speed benchmark or evidence that 600 steps is a generally appropriate training budget. The algorithms differ in both objective-evaluation count and per-step work. A fair performance study would specify hardware, tensor sizes, precision, stopping criteria, timing boundaries and repeated measurements.

Closure failures to avoid#

Do not advance a data iterator inside an L-BFGS closure unless the algorithm is explicitly designed for a changing objective. A line search compares values of one function at different candidate points; changing the sample, dropout mask or stochastic augmentation between evaluations violates that interpretation. Similarly, logging code should not mutate parameters or model state in a way that changes the next evaluation.

Gradients accumulate by default. Forgetting to zero them inside the closure can mix derivatives evaluated at different trial parameter values. Reusing a graph after parameter mutation can produce stale derivatives or version-counter errors. Build the objective from current parameters each time. Avoid retaining a graph merely to suppress an error without understanding why it is reused.

Convergence, assumptions and uncertainty#

Check the final objective, gradient norm and physical parameter domain. Compare several justified initial values for nonconvex objectives, and inspect curvature or profiles where scientific identification matters. The two starts here provide a limited check, not a proof of global convergence for arbitrary custom models. Optimization tolerances measure computational accuracy; they do not quantify sampling uncertainty.

Answered review questions#

Why might Adam be useful despite a smooth full-batch objective? It can tolerate difficult scaling and supports stochastic training settings, but its learning rate and stopping behavior still need validation. For small deterministic likelihoods, a curvature-aware optimizer is often a useful comparison.

Can one optimizer iteration equal many likelihood passes? Yes. L-BFGS line search and its internal iteration budget can reevaluate the closure repeatedly. Account for actual evaluations when planning a distributed likelihood whose each evaluation launches a Spark job.

Is a final gradient near zero enough? No. Separation, scale collapse and weak identification from earlier chapters demonstrate why parameter existence, boundaries and scientific meaning must be checked independently.

"""Complete float64 CPU likelihood investigation with original synthetic data."""

from __future__ import annotations

import json

import torch

DTYPE = torch.float64
torch.set_num_threads(1)


def tensor(values):
    return torch.as_tensor(values, dtype=DTYPE)


def objective(raw, y):
    mean = torch.nn.functional.softplus(raw).square()
    return ((y - mean).square() / (2 * 0.5**2)).sum()


def fit(method, initial):
    y = tensor([1.4, 1.5, 1.6])
    raw = tensor(initial).requires_grad_()
    calls = 0
    if method == "lbfgs":
        optimizer = torch.optim.LBFGS(
            [raw],
            max_iter=80,
            tolerance_grad=1e-10,
            tolerance_change=1e-14,
            line_search_fn="strong_wolfe",
        )

        def closure():
            nonlocal calls
            calls += 1
            optimizer.zero_grad()
            loss = objective(raw, y)
            loss.backward()
            return loss

        returned = float(optimizer.step(closure).detach())
        steps = 1
    elif method == "adam":
        optimizer = torch.optim.Adam([raw], lr=0.06)
        steps = 600
        for _ in range(steps):
            optimizer.zero_grad()
            loss = objective(raw, y)
            loss.backward()
            optimizer.step()
            calls += 1
        returned = float(loss.detach())
    else:
        raise ValueError("Choose lbfgs or adam")
    final = objective(raw, y)
    gradient = torch.autograd.grad(final, raw)[0]
    return {
        "mean": float(torch.nn.functional.softplus(raw.detach()).square()),
        "final_objective": float(final.detach()),
        "gradient_abs": abs(float(gradient)),
        "optimizer_steps": steps,
        "objective_evaluations": calls,
        "returned_step_loss": returned,
    }


def run_cases():
    cases = {
        "lbfgs_low": fit("lbfgs", -1.5),
        "lbfgs_high": fit("lbfgs", 1.4),
        "adam_low": fit("adam", -1.5),
    }
    for value in cases.values():
        assert abs(value["mean"] - 1.5) < 2e-5 and value["gradient_abs"] < 3e-4
    assert cases["lbfgs_low"]["objective_evaluations"] > cases["lbfgs_low"]["optimizer_steps"]
    assert cases["lbfgs_low"]["returned_step_loss"] > cases["lbfgs_low"]["final_objective"]
    return {"cases": cases, "closed_form_target_mean": 1.5, "objective_has_fixed_known_scale": True}


if __name__ == "__main__":
    print(json.dumps(run_cases(), sort_keys=True, allow_nan=False))
