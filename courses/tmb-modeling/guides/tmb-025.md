# From an empty template to a reviewed model

Start with: tmb-024.

Outcome: Separate generated scaffolding from a scientifically complete likelihood.

The classroom companion runs in the prepared R statistics runtime. It uses base R to expose the mathematics or data contract. Compiling and executing TMB uses the separate [owned project](../projects/tmb-local/README.md); a companion run is not a TMB compiler or rpy2 receipt.

TMB provides authoring helpers, but scaffolding is not a finished model. `template(file=NULL)` supplies a starting C++ structure; a file argument writes a scaffold. `Rinterface(file)` examines an existing C++ template and produces an R-side skeleton. `runExample()` lists installed examples, and a named example can compile and execute package-provided source in a chosen working area.

These functions are valuable for discovering interfaces. Their output still needs data, parameter starts, domain checks, normalized probability terms, independent numerical references and provenance. The classroom's original models are written independently rather than copied from package examples.

### Worked case A: design the interface before the loop

The companion creates a schema for a regression model: response length, design dimensions, parameter dimensions and intended report quantities. The numerical objective follows only after that schema agrees. For a native authoring session in a disposable directory:

```r
TMB::template(file = "new_model.cpp")
TMB::Rinterface("new_model.cpp")
```

Inspect the actual generated text before running it. A scaffold containing `DATA_VECTOR` tells you what type is expected, but it does not tell you whether missing observations should be rejected, modeled or filtered. Likewise, a declared scale parameter does not establish whether its input is a standard deviation, variance or logarithm.

### Worked case B: package example versus your experiment

A package example can demonstrate a compiler or API feature under its own assumptions. It is not evidence that your new dataset or custom likelihood is correct. The companion compares two input schemas with the same response length but different predictor meanings. Reusing a skeleton without updating the interpretation can produce a valid matrix multiplication for the wrong model.

`runExample(name=..., thisR=..., clean=..., exfolder=..., dontrun=...)` has process and cleanup options. Read their pinned documentation before use, choose an owned disposable directory, and never point cleanup at learner data. Package-provided examples retain their own licensing. No package example source is copied into this book.

### Answered discussion

**Does generating an R interface generate trustworthy starting values?** No. Starts need to respect units, constraints and data range. **Should I invoke every package example as a release test?** Only if it tests a declared capability and its resource/dependency contract is understood. Our numerical acceptance is intentionally based on small original models. **What should be reviewed first?** The observation model, source declarations and tiny known-value calculation, before parallelism or optimization tuning.

See [template, Rinterface and runExample in the pinned manual](https://cran.r-project.org/web/packages/TMB/TMB.pdf). The [API inventory](../API-REFERENCE.md) records exact public signatures and separates helpers from runtime acceptance.

### Complete R companion

```r
schema <- list(response = list(name = "y", length = 4L), design = list(columns = c("intercept", "time"), rows = 4L), parameters = list(beta = 2L, log_sigma = 1L))
stopifnot(schema$response$length == schema$design$rows, schema$parameters$beta == length(schema$design$columns))
print(schema)
other_columns <- c("intercept", "temperature")
print(c(same_shape = length(other_columns) == length(schema$design$columns), same_meaning = identical(other_columns, schema$design$columns)))
```
