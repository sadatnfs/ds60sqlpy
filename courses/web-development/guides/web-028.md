# web-028: Data interfaces: filtering tables and honest visual summaries

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-027`

## Learning objectives

Build a filterable local study table with an explicit empty state. Explain how this table connects to D3 without changing the statistical claim. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A data interface connects records to a representation. Keep the original records separate from the filtered view so a user can clear a filter without reconstructing lost input. A table is useful for exact values; a chart emphasizes patterns. Both need labels, units and a declared handling of missing values. A visually impressive chart can still tell an incorrect story if its filtering or scale is wrong.

This lesson uses a tiny local array and a semantic table. A select changes the derived records, then one render function replaces the table body with safely created cells. An empty result receives an explicit message rather than an unexplained blank area. The JavaScript D3 specialization builds on the same principles for richer scales, joins and interaction; it is a continuation, not a replacement for data validation.

## Syntax anatomy and mechanism

Use array.filter to derive records without mutating the source array. Create cells with createElement and textContent. Count the resulting rows and compare with the stated filter. For later D3 work, preserve stable record identities and separate data transformation from visual encoding. Never imply that a client-side filter is access control over confidential data already sent to the browser.

## Worked example / walkthrough

### Worked example 1: Derived records

Filtering keeps the input array available.

```javascript
const visible = rows.filter(row => row.minutes >= 40);
```

**Expected observation:** Only rows meeting the declared threshold appear in the derived view.

### Worked example 2: A safe table cell

A category name is plain data.

```javascript
const cell = document.createElement('td');
cell.textContent = row.subject;
```

**Expected observation:** Special characters in the name do not create HTML.

## Six progressive exercises

### Exercise 1: Predict the rows retained for a forty-minute threshold.

**Expected evidence:** Only the records whose minutes are at least forty remain.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add a clear filter label and a result count.

**Expected evidence:** The user can identify the active condition and its effect.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a filterable local study table with an explicit empty state.

**Expected evidence:** Changing the selection updates rows and count while preserving the original data.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a filter that permanently removes source records.

**Expected evidence:** Keep immutable input and derive a new view for each render.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test a threshold that returns no records.

**Expected evidence:** The interface explains the empty result and allows the filter to be cleared.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain how this table connects to D3 without changing the statistical claim.

**Expected evidence:** The same validated records can drive a visual encoding with explicit scales, units and an accessible equivalent.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not silently drop missing or invalid values just to obtain a clean chart. A filtered-out record remains in client memory. Review the D3 path from js-043 when adding visualization rather than importing a CDN into this offline fixture.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.
