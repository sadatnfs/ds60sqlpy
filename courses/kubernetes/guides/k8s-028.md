# k8s-028: Capstone 2: stateful change with policy

## Level and prerequisites

Intermediate; about 240 minutes plus review. Direct prerequisites: `k8s-017`, `k8s-018`, `k8s-021`, `k8s-022`, `k8s-023`, `k8s-025`, `k8s-027`. The chapter separates desired configuration, API acceptance, controller observation and application evidence.

## Learning objectives

Release and recover an owned stateful fixture with explicit access and data boundaries.

## Vocabulary and concepts

The intermediate capstone combines a stateless application response, a synthetic persistent marker store, reviewed configuration rendering and measured traffic policy. It is a host-lab integration exercise because the normal browser adapter does not provide the storage, CNI and stateful-update capabilities needed for the whole scenario.

The supplied manifests keep the components explicit:configured hello Deployment/Service, one StatefulSet claim template and two ingress policies. The persistent marker is a file-based synthetic datastore, not a real database service. Its writer and reader operations must be separately bounded and reviewed by the host. A correct frontend response is not evidence that the marker survived, and an unchanged marker is not evidence that network isolation works.

The capstone's acceptance packet connects those independent observations and includes a failed-change recovery. Cleanup respects the declared synthetic-data retention choice and exact resource identities. Releasing the disposable cluster is a separate lifecycle boundary that can remove node-local retained data.

## Plan component and capability dependencies

Before starting, verify the owned namespace UID, qualified StorageClass, policy-capable CNI, approved images and prepared renderer if used. Record which host operation owns cluster-scoped prerequisites and which namespaced resources the learner scenario owns. The current ordinary worker lease does not silently acquire these extra rights.

Initialize the marker once using exclusive creation, record its checksum, and verify the application's initial response. Establish both permitted and denied client paths around the NetworkPolicy change. The source/overlay or chart render should be reviewed as a complete object set before a stateful apply.

A missing capability is reported explicitly. Do not replace a PVC with a personal hostPath, disable policy checks or infer renderer success from the expected-output file merely to produce a complete-looking packet.

## Rehearse one failed change and recover

Choose a bounded failure such as a wrong readiness path in the candidate application revision. Record desired generation, old/new Pod identities, client results and marker checksum before the change. After the failed acceptance gate, restore the reviewed desired configuration and verify the intended application marker and data hash.

The persistent data check must be read-only after initialization. A repair that rewrites the expected marker could conceal data loss. Traffic policy should be retested after recovery because a source change may alter labels used by selectors. A ready application alone does not close every capstone gate.

Keep the failure timeline and cleanup outcome. The host may retain the synthetic PVC for a subsequent recovery lesson only when that retention is explicitly recorded; otherwise final cleanup follows exact object receipts and the chosen reclaim policy.

## Concrete finite marker operations

The separate [exclusive-create writer](../fixtures/k8s-022-marker-writer.json) and [read-only verifier](../fixtures/k8s-022-marker-reader.json) are host-only Job manifests. The writer opens `/data/marker` with mode `xb`, so an existing file causes failure instead of silently overwriting evidence. The reader requires the exact `persistent-demo` bytes followed by a newline and reports their SHA256. It never initializes data.

Both Jobs have one completion, no retry and a60-second deadline. They use the fixed preloaded image and restricted nonroot settings. Required Pod affinity places them on the node hosting app=store, which makes the single-node ReadWriteOnce attachment assumption explicit; it does not create a storage class or guarantee scheduling. The reader mounts the claim read-only. Run initialization once, replace only the application Pod through the host operation, then run the independent reader. A second writer failure is the intended overwrite guard.

These commands are more general than the normal hello-task contract and are rejected by the browser adapter. Only the separately reviewed storage lease may bind ownership, submit them and clean their recorded UIDs. Their local code checks establish exclusive-write/read semantics, not live persistence.

## Common pitfalls

Application response, stored data, authorization, network enforcement and cleanup have different evidence. A single green summary cannot replace the underlying identities, checksums and client results. The fixture is bounded and synthetic, so it does not establish production database durability, HA or a universal isolation guarantee.

The offline reference checks the packet logic only. The full host capstone remains unavailable on the basic one-shot profile even though several of its individual manifests resemble supported browser sources.
