# asm-034: Optimizing global TMB loss and gradient summaries

Tutorial mode. Stage: advanced. Direct prerequisites: `asm-033`, `tmb-007`.

## Starting point and result

A driver-controlled optimizer can use compiled TMB evaluations from Spark workers in the same way it uses Torch or analytic summaries. The integration must return the complete objective and derivative at a shared parameter vector, with a stable parameter order. The fixed `global-normal-fit` project case provides a bounded example with a closed-form oracle.

## Mechanism: one parameter proposal, many local evaluations

At iteration k, the driver owns \(\theta_k\). Every worker evaluates its assigned additive contribution \(L_p(\theta_k)\) and gradient \(g_p(\theta_k)\). The driver forms \(L=\sum_p L_p\) and \(g=\sum_p g_p\), applies any global penalty once and passes the result to its optimizer. An objective evaluation is complete only when all required contributions are present and validated.

The original compiled-TMB project in this chapter runs its objective inside R. Python may invoke a bounded R subprocess or use rpy2 in a prepared process, but those are different runtime contracts. The `rpy2-frame` project case separately qualifies conversion. A successful subprocess case does not prove rpy2 behavior, and importing rpy2 does not prove the compiled model received correctly converted data.

Parameter names, order, transforms and derivative coordinates must be explicit. A derivative with respect to log sigma is not a derivative with respect to sigma. If the outer optimizer expects transformed coordinates, the worker must return derivatives in those coordinates consistently.

## Worked case: recover a global normal mean

For independent observations with known variance, the mean MLE is the global average. Split observations into unequal partitions and compare the distributed fit with the count/sum oracle. A correct optimizer returns the row-weighted result regardless of physical partition count. The receipt should include objective/gradient agreement at several fixed parameters as well as final optimization diagnostics.

Checking only the final estimate is weak: a normal mean has a simple optimum, and some scaling mistakes leave that optimum unchanged. Comparing the full objective and gradient catches duplicated penalties, missing constants and normalization differences that affect other models or uncertainty calculations.

## Worked case: Python DataFrame to R without silent schema changes

The `rpy2-frame` case uses explicit local conversion scope and a bounded frame. Compare row count, column order, numeric values and missing-value representation before constructing the TMB data list. Categorical encodings and R's indexing conventions require particular care. A Python zero-based category index is not automatically the intended R factor or C++ index.

Passing an entire massive Spark DataFrame through the driver to R would defeat the intended distributed data path. Conversion belongs inside a bounded group, partition or explicitly small reference case. Keep those boundaries visible in documentation and evidence.

## Failure diagnosis

An objective gradient with the correct magnitude but wrong sign may come from maximizing log likelihood versus minimizing negative log likelihood. A zero derivative can reflect a dropped parameter or stale native state. A subprocess that exits successfully but emits malformed JSON is still a protocol failure. Validate output shape, finiteness and parameter identity before updating the optimizer.

## Interview discussion

**Can TMB and Spark share one automatic-differentiation tape?** This project does not do that. TMB differentiates local compiled computations; Spark transports numeric contributions; the driver coordinates the outer optimizer.

**Why keep a closed-form normal case?** It detects integration and normalization defects cheaply before a complex nonlinear model makes the source of error ambiguous.

## Execute the independent native package

The [Spark/TMBad package](../../../packages/spark-tmbad/README.md) implements
the same additive ownership rule through a separately prepared runtime: a Scala
adapter controls bounded native TMBad processes, while Python provides a driver
facade. Executors do not use R or Python numerical callbacks for these native
models. Copy the complete package, prepare its matching binary/JAR/wheel, and
follow its installation guide. Opening this reading chapter neither builds that
environment nor starts Spark jobs.

The native registry includes independent row likelihoods and explicitly complete
group models. A shared fit reduces one data objective across partitions; an
independent-group fit estimates a separate parameter vector per group. Both need
stable identifiers and complete coverage, but their statistical targets differ.
The [additional model guide](../../../packages/spark-tmbad/docs/EXTENDED-MODELS.md)
lists field mappings, transforms, count support, mixture meanings and conditional
forecast scopes for the newer families.

An exact small target exposes penalty placement. Take observations \(1,2,4,7\),
fix \(\log\sigma=0\), give \(\mu\) a Gaussian prior with mean one and
precision two, and add \(|\mu|\). Ignoring constants only for this derivative
calculation, the positive-coordinate score is
\(4\mu-14+2(\mu-1)+1=6\mu-15\), so the optimum is \(2.5\).
The smooth part alone has score \(-1\) there. Its nonzero value is consistent
with the exact L1 KKT condition; ordinary smooth-gradient convergence would be
the wrong certificate. The qualified Python and Scala examples retain the full
normalized objective, named prior, fixed coordinate and stationarity fields.

The [extended API example](../../../packages/spark-tmbad/python/examples/validate_extended.py)
fits this target with the proximal solver, evaluates the final point through the
public API, saves/reloads its model, and predicts response-free future rows.
Changing reduction from sum to weighted mean divides the entire target by the
same validated mass. Dividing only data loss would change prior strength.
Applying the prior independently inside every partition would make the estimate
depend on physical partition count.

The [isolated Compose harness](../../../packages/spark-tmbad/integration/README.md)
uses a master, two worker containers and a separate driver. It retains worker
and executor identities, partition ledgers, bounded driver results and an actual
failed/retried task after controlled worker loss. Read the exact accepted receipt
for the source and checks exercised. A local multi-container result establishes
that topology on its native architecture; it does not establish multi-host scale
or the behavior of a different default image.

# Worked reference: Global compiled objective and conversion

This is an editable reading/project reference. It has no ordinary pad Run action.

For known-variance normal observations, the shared mean MLE is the global mean. Test fixed-parameter objective and gradient values as well as the final optimum, because multiplying every loss by a constant may leave the optimum unchanged.

Run the separate `rpy2-frame` case when qualifying Python/R conversion. Compare row count, order, dtype, missing values and category indexing before model construction. A successful R subprocess result does not establish rpy2 conversion, and a pandas conversion case does not establish distributed massive-frame delivery.

```bash
courses/advanced-spark-modeling/projects/spark-tmb/workshop run global-normal-fit
```
