## The question and the mechanism

Trace a raw aggregation and a measure reference inside an iterator without treating context transition as a row pointer.

Context transition converts the values of the current row context into filters. It is not a hidden instruction to remember one physical row object. On a table with duplicated rows, those value filters can match several rows. A unique fact key helps ensure that transitioning a Sales row selects the intended one-line population.

In SUMX(Sales, SUM(Sales[NetAmount])), the inner raw SUM sees no filter generated from the iterator's current row. With no outer filters it returns 187 on every one of eight iterations, producing 1496. CALCULATE around that inner SUM performs the transition, so each unique SaleID admits its own amount and the total is 187.

Calling [NetRevenue] inside row context performs an implicit transition because it is a model measure. This convenience does not remove the need to understand the mechanism. A variable holding a precomputed scalar is different, and a duplicate-key model still needs diagnosis. Prefer simple direct sums when their semantics already fit; use an iterator only for a real row-by-row calculation.

## Vocabulary and expression anatomy

SUMX takes a table and a scalar expression to evaluate for each row. Case A deliberately contrasts raw and transitioned aggregations over unique Sales rows. Case B iterates Customer and invokes a measure. Customer 40's blank result contributes no amount, while the three purchasing customers partition the clean fact data.

Concepts to explain in your own words: **context transition**, **model measure**, **SUMX**, **row identity**, **duplicate rows**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: Eight repetitions versus eight individual amounts

**Starting context:** No outer filters; SUMX creates one Sales row context per unique SaleID.

```dax
EVALUATE ROW ( "RawRepeated", SUMX ( Sales, SUM ( Sales[NetAmount] ) ), "Transitioned", SUMX ( Sales, CALCULATE ( SUM ( Sales[NetAmount] ) ) ) )
```

**Context trace:**

1. Without transition, the inner SUM is 187 for every row.
2. Eight iterations give 8 * 187 = 1496.
3. With transition, the eight selected line amounts sum once each to 187.

**Hand-derived worked-reference result:**

| RawRepeated | Transitioned |
| --- | --- |
| 1496 | 187 |

The two formulas differ in context semantics, not numeric precision. Dividing the wrong result by eight would hide the mistake and fail under another population.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Measure invocation transitions each customer

**Starting context:** No outer filters; a model measure is invoked within each Customer row context.

```dax
EVALUATE ROW ( "CustomerRows", COUNTROWS ( Customer ), "SumOfCustomerRevenue", SUMX ( Customer, [NetRevenue] ) )
```

**Context trace:**

1. Ada contributes 51, Bo 80 and Cy 56.
2. Di has no matching sales and contributes BLANK.
3. 51 + 80 + 56 = 187.

**Hand-derived worked-reference result:**

| CustomerRows | SumOfCustomerRevenue |
| --- | --- |
| 4 | 187 |

This additive reconciliation works because each sale has exactly one valid customer in this fixture. It is not a general theorem that summing any measure over any dimension equals its total.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. The inner raw SUM sees the outer Paper context.
2. A measure supplies the implicit transition.
3. An iterator is unnecessary for a stored additive column.
4. The patch relies on a particular repeated-total mistake.
5. Transition filters by values rather than physical row identity.
6. Separate customer-level values from fact-line allocation weights.
