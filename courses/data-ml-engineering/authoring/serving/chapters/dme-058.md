# dme-058: Bytes, subwords and the tokenizer boundary

A tokenizer is part of the executable model contract. It converts text into integer IDs, and its decoder converts generated IDs back into bytes or text. The same checkpoint paired with a different vocabulary does not merely produce different formatting: ID 300 may select an entirely different embedding row. Tokenizer identity therefore belongs beside checkpoint identity in every reproducible serving record.

This chapter assumes the request contract from the previous chapter. You will trace an exact byte-pair encoding example and decode a Unicode sequence across individual byte deliveries. The pad uses original small fixtures. The workshop trains its own bounded byte-BPE vocabulary from a local synthetic corpus. It does not download a vocabulary or imitate the capabilities of a large pretrained tokenizer.

## Four units that must remain distinct

A byte is an integer from zero through 255. A Unicode code point identifies an abstract character component. A grapheme cluster is closer to what a person perceives as one displayed character, and may contain several code points. A model token is an ID in a tokenizer vocabulary. None of these units is universally interchangeable with another.

For example, `é🙂` contains two code points and six UTF-8 bytes. A byte tokenizer initially needs six ordinary byte IDs. A learned vocabulary might merge some byte sequences and use fewer tokens. A generated token may also end partway through a multi-byte Unicode encoding. Emitting each token as an independently decoded string can then produce decoding errors or unnecessary replacement characters.

UTF-8 is self-synchronizing, but a network receiver still needs an incremental decoder. It retains an incomplete prefix until later bytes arrive. The decoder state is distinct from the model KV cache and the SSE parser buffer. Confusing these three forms of buffering makes streaming bugs difficult to diagnose.

## Building and applying byte-pair merges

Byte-pair encoding begins with a base alphabet and repeatedly replaces a selected adjacent pair with a new symbol. In this workshop the base alphabet is all 256 bytes. Two additional IDs represent BOS and EOS. They are not ordinary byte values and are excluded from learned merge pairs. New merge IDs begin at 258.

Training counts adjacent pairs in the current corpus representation. It chooses the most frequent eligible pair, with a deterministic tie-break, replaces non-overlapping occurrences from left to right, then recounts. Training and application are different operations: serving does not refit merges on each prompt. It applies the saved merge sequence in its learned rank order.

Suppose merge one combines byte IDs 97 and 98, representing `a` and `b`, into ID 258. Merge two combines 258 and 97 into 259. Applying both to `aba ab` yields IDs 259, 32 and 258. Reversing the merge order is not equivalent because the second merge depends on the output of the first. A saved merge graph must refer only to symbols that already exist; a forward or cyclic reference is invalid.

Overlapping pairs require an explicit replacement rule. In `aaa`, the pair `aa` occurs at positions zero and one when counted as adjacent pairs, but both cannot be replaced simultaneously without reusing the middle symbol. Left-to-right non-overlapping replacement yields one merged pair followed by one `a`. This detail affects tokenizer training reproducibility.

The workshop intentionally omits a sophisticated pretokenizer and Unicode normalization. It can merge across whitespace. Those are declared simplifications, not universal BPE properties. Other tokenizers have their own normalization, byte mapping, word-boundary and special-token policies. A serving system must use the policy paired with its checkpoint rather than reconstructing one from a tokenizer family name.

## Token budgets are measured after encoding

Let \(B(x)\) be the UTF-8 byte sequence of prompt \(x\), and let \(T(x)\) be the sequence after saved merges. In the byte-based fixture, merge application never increases sequence length, so

\[
\lvert T(x)\rvert\leq\lvert B(x)\rvert.
\]

This bound does not say that four characters equal one token, or that every Unicode character fits one token. Adding BOS contributes one further model position. A short-looking string containing uncommon Unicode may consume more tokens than an English phrase of similar visual length. The server therefore encodes before checking the context reservation.

Record both the prompt token count and the tokenizer hash. When an update changes the tokenizer, old token counts cannot be assumed valid. Raw prompt preservation also matters: tokens alone cannot always explain normalization or truncation decisions made before encoding.

## Worked case 1: exact merge ordering

The first case explicitly constructs the two merges above. It prints `[259, 32, 258]` and the corresponding byte lengths. Decoding by concatenating vocabulary pieces reconstructs exactly `aba ab`. The independent assertions verify both the forward representation and the byte-level round trip.

Then the case tests `aaa`. Only the first two symbols merge, producing `[258, 97]` under the case's chosen replacement ID. This small changed condition isolates overlap handling. If a custom implementation instead replaces both overlapping pairs, it has consumed a source symbol twice and will fail a round-trip argument.

This kind of exact fixture is useful before performance optimization. Replacing a readable merge loop with a heap or linked-list implementation can change pair ranking or tie-breaking subtly. Preserve a small reference implementation and compare token sequences, not just decoded text: distinct segmentations may decode identically while selecting different model embeddings.

## Worked case 2: six byte deliveries, two characters

The second case feeds the six bytes of `é🙂` into an incremental UTF-8 decoder one byte at a time. The expected visible deltas are an empty string, `é`, three more empty strings, then `🙂`. A final flush contributes nothing. The empty deltas are correct buffering behavior, not missing tokens.

An invalid byte `0xff` is rejected by strict decoding. The live workshop instead uses an explicit replacement policy for generated bytes, because its tiny synthetic model can sample arbitrary byte IDs. It retains token IDs and byte hex values and counts replacement characters. That keeps the display usable without pretending the original byte sequence was valid text. Prompt decoding remains strict.

## Special tokens, prompt templates and inspection

BOS marks the start of a model sequence; EOS is a learned termination option. Neither guarantees that a model understands a conversation role. A chat template is another transformation that may insert role markers and separators before tokenization. If a serving system uses such a template, its version and resulting token budget belong in the accepted request contract.

The workshop has a plain continuation model and a BOS marker. It does not claim system/user role semantics or instruction-following alignment. Literal text that resembles a role delimiter is ordinary text unless the tokenizer and template deliberately define otherwise. This keeps the demonstration faithful to the model actually trained.

For debugging, inspect a short prompt's original bytes, encoded IDs, expanded token pieces and BOS contribution. Do not log private prompts indiscriminately in a production service. An educational synthetic fixture lets you inspect all these boundaries without exposing someone else's data.

## Interview discussion

**Why can a token event contain an empty text delta?** The token may contribute only the beginning of a UTF-8 character, or the display decoder may be holding a possible stop-string prefix. Its token ID and bytes still represent actual generated output.

**Does a tokenizer update preserve model compatibility if vocabulary size stays the same?** No. Equal size does not establish equal ID-to-piece mapping. The checkpoint's embedding rows are learned for particular IDs; the mapping and merge policy must match.

**Why retain byte-level evidence when the UI shows replacement characters?** Replacement is a display decision that loses information. Raw token IDs and byte pieces permit exact diagnosis while the UI explicitly reports its replacement policy.
