js-021: Object types and structural contracts#

Level and prerequisites#

Intermediate, approximately 90 minutes. Direct prerequisites: js-020

Learning objectives#

Explain structural compatibility, excess-property checking, readonly view, optional property with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Pass a wider named object with id and count to a function requiring only id. The final task tests transform a readonly array without mutation.

Purpose and mental model#

TypeScript object types describe the properties an operation requires. Compatibility is largely structural: an object with the required fields can be accepted even if it was not created by a named class. A fresh object literal receives additional excess-property checking, which catches likely misspellings, but assigning the same wider object through a variable can be allowed. Neither rule is a runtime exact-schema validator.

readonly restricts writes through a particular typed view. It does not freeze the runtime object, and another mutable alias may still change it. A shallow readonly property containing a mutable object also leaves that nested object mutable unless its type says otherwise. Readonly arrays prevent mutating methods through their interface, but ordinary copy and transformation operations remain available.

An optional property may be absent. Under this route's strict profile, reading it produces a value that may be undefined. The profile does not enable exactOptionalPropertyTypes, so explicit undefined assignment has different checking behavior from a stricter configuration that distinguishes absence from an explicitly present undefined. Be precise about the actual compiler flags and the wire-format policy. JSON serialization can omit undefined fields, further separating runtime presence from serialized presence.

Vocabulary and concepts#

Structural compatibility: Acceptance based on required members rather than a declared class identity.

Excess-property checking: Extra scrutiny of fresh object literals for unexpected properties.

Readonly view: A type-level restriction on writes through a particular reference.

Optional property: A field that may be absent and must be handled accordingly.

Syntax anatomy and execution trace#

Use property?: Type for optional fields and readonly property: Type for a restricted view. Readonly<T> is shallow: it changes the write permissions of the immediate fields in the type, not the underlying objects. readonly T[] or ReadonlyArray<T> disallows push through that reference. Object.freeze is a runtime operation with its own shallow boundary. Object.hasOwn can distinguish property presence independently of its value.

Worked example / walkthrough#

Example A: Use structural compatibility#

Structural acceptance is useful for small interfaces, but does not strip extra fields. Treating an accepted type as an exact serialization schema can leak fields that still exist at runtime.

import { strict as assert } from 'node:assert';



export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    function label(value: { id: string }): string { return value.id; }
    const wider = { id: 'A', count: 2 };
    assert.equal(label(wider), 'A');
    assert.equal(wider.count, 2);
    function negativeTypeCheck(): void {
      // @ts-expect-error A fresh literal is checked for excess properties.
      label({ id: 'A', count: 2 });
    }
    void negativeTypeCheck;
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: label A; original count remains 2.

Example B: Observe mutation through an alias#

The view and original reference point to the same object. Readonly is a static access restriction, not a historical snapshot or deep immutability guarantee.

import { strict as assert } from 'node:assert';



export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const mutable = { count: 1 };
    const view: Readonly<{ count: number }> = mutable;
    mutable.count = 4;
    assert.equal(view.count, 4);
    function negativeTypeCheck(): void {
      // @ts-expect-error Writes through the readonly view are forbidden.
      view.count = 9;
    }
    void negativeTypeCheck;
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: readonly view observes count changing from 1 to 4.

Prediction before your attempt#

Exercises#

  1. Use structural compatibility. Pass a wider named object with id and count to a function requiring only id. Expected: label A; original count remains 2. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Observe mutation through an alias. Create a readonly view of a mutable record, then mutate the original reference. Expected: readonly view observes count changing from 1 to 4. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Handle absent and zero-valued optional counts. Use a nullish fallback on an optional count. Expected: absent becomes 10; explicit 0 remains 0. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Distinguish runtime presence from undefined. Compare an absent property with an explicitly present undefined property. Expected: hasOwn is false versus true; JSON serializes both as empty objects. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Show shallow readonly and shallow freeze boundaries. Freeze an outer record containing a nested mutable object and update the nested count. Expected: nested count becomes 3; outer object is frozen. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Transform a readonly array without mutation. Accept readonly numbers, return a doubled array, and demonstrate push is rejected statically. Expected: new array 2,4; input remains 1,2. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
