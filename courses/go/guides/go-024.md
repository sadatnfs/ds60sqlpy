# go-024: Goroutines and explicit completion

## Level and prerequisites

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-023

## Learning objectives

Start goroutines and prove their completion with a WaitGroup or channel instead of sleeping. Along the way, explain goroutine, join, happens-before; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A goroutine is a concurrently scheduled execution of a function. Starting one does not make the caller wait for it, and returning from main ends the program even if other goroutines still have work. Concurrency introduces partial ordering: some events must happen before others, while unrelated scheduling remains unspecified. Use communication or synchronization to establish the relationships required by the algorithm. A sleep is a delay, not proof that another goroutine has completed. Every started goroutine needs an owner responsible for its completion or cancellation, otherwise blocked tasks can leak resources and make shutdown unpredictable.

## Vocabulary and concepts

- **Goroutine:** An independently scheduled function execution.
- **Join:** Waiting for owned concurrent work to complete.
- **Happens-before:** A synchronization relationship that orders memory effects.

## Syntax anatomy and reasoning

go function() starts a goroutine. A channel send and receive can transfer a result and establish an ordering relationship. sync.WaitGroup tracks a known set of tasks; Add must happen before a concurrent Wait can conclude. Defer Done inside each task. Do not write a shared ordinary variable concurrently merely because a later print appears to observe the expected value.

## Worked example / walkthrough

### Worked example 1: Join a produced result

Start a goroutine computing 6 times 7 and receive its result.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Join a produced result
	{
		result := make(chan int)
		go func() { result <- 6 * 7 }()
		check(<-result == 42, "goroutine result")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The received value is 42.

The receive waits for the send. The program does not assume the worker has completed merely because enough wall-clock time passed.

### Worked example 2: Wait for several tasks

Start three tasks that signal a buffered completion channel and wait for all of them.

```go
package main

import (
	"fmt"
	"sync"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Join a produced result
	{
		result := make(chan int)
		go func() { result <- 6 * 7 }()
		check(<-result == 42, "goroutine result")
	}

	// Wait for several tasks
	{
		done := make(chan struct{}, 3)
		var wg sync.WaitGroup
		for i := 0; i < 3; i++ {
			wg.Add(1)
			go func() { defer wg.Done(); done <- struct{}{} }()
		}
		wg.Wait()
		check(len(done) == 3, "joined tasks")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Exactly three completion markers are received.

The buffer avoids blocking completion before the parent reads. WaitGroup joins the tasks; the channel stores inspectable completion evidence.

**Expected:** The worker returns ready only after release.

## Common pitfalls and diagnosis

Starting a goroutine without a join is the defining mistake: main may return first, or a test may check a value before it is written. Sleeping to wait for completion only hides the race. A second bug is calling wg.Add inside the goroutine, where Wait can run before Add. Finally, never read a shared variable a goroutine writes unless a channel, WaitGroup or lock orders the two.

## Progressive hints

### Hint for investigation 1: Join a produced result: change one input

1. Restate the expected observation: The received value is 42.
2. Receiving from an unbuffered channel waits for the sender. What value does the goroutine send?
3. The goroutine now sends 7*7, so the receive yields 49 and `<-result==42` fails. The join works; the computation changed.

### Hint for investigation 2: Wait for several tasks: debug a regression

1. Restate the expected observation: Exactly three completion markers are received.
2. wg.Wait returns after every Done. How many signals does the buffered channel hold then?
3. Starting the loop at 1 launches only two tasks, so wg.Wait returns with two markers and `len(done)==3` fails. Restore the initial 0 so three tasks start.

### Hint for investigation 3: Keep state task-local

1. Restate the expected observation: The results sum to 13.
2. Each goroutine receives its own x. Which two squares are sent?
3. The order of a and b is unspecified, so the assertion checks an order-independent property.

### Hint for investigation 4: Establish a start boundary

1. Restate the expected observation: The worker returns ready only after release.
2. The worker blocks on start. Which statement releases it, and what does it send next?
3. Closing a channel can broadcast a one-time event.

### Hint for investigation 5: Reject premature completion

1. Restate the expected observation: The result is unavailable before release and equals 1 afterward.
2. A select with default never blocks. Can the receive case win while the worker still waits?
3. The blocked worker cannot send before the start boundary.

### Hint for investigation 6: Transfer deterministic aggregation

1. Restate the expected observation: The sum is 30.
2. The receiver adds every value. Which four squares make up the sum?
3. Only the receiver mutates sum, so no mutex is required for that accumulator.
