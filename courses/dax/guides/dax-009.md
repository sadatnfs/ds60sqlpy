## The question and the mechanism

Separate a row's stored calculation from a scalar reevaluated for a query context.

A calculated column produces a value for each row when the model processes that calculation. A measure is evaluated for a query context. The same arithmetic may appear in both, but its lifetime and shape differ. A column's values can be used as model attributes; a measure answers a context-dependent question without storing one answer for every future report selection.

Our CSV contains NetAmount as an explicit input column. It was authored from a documented line formula. If you implemented that formula as a calculated column in an external model, each line would use its row's quantity, unit price and line discount during processing. A report selection would choose which stored line amounts contribute, not retroactively rewrite their values.

Calculated tables are another model object, computed during processing and then available as tables. A table expression inside a query is temporary to that expression. Decide between these choices based on semantic lifetime, cardinality and intended reuse rather than naming every intermediate object a measure. The offline classroom shows their definitions and consequences; it does not create these objects in a live engine.

## Vocabulary and expression anatomy

Case A reconstructs two row amounts with SELECTCOLUMNS so the stored and derived numbers can be compared. Case B asks for a measure under customer and date filters. The Date relationship uses OrderDate. The filter changes eligible lines; the definition of the line amount remains fixed.

Concepts to explain in your own words: **calculated column**, **measure**, **refresh**, **query context**, **stored value**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
    MEASURE Sales[QuantitySold] = SUM ( Sales[Quantity] )
```

### Case A: Stored row amounts and their formula

**Starting context:** Two first SaleID values; each projection evaluates its own Sales row.

```dax
EVALUATE SELECTCOLUMNS ( TOPN ( 2, Sales, Sales[SaleID], ASC ), "Line", Sales[SaleID], "Stored", Sales[NetAmount], "Reconstructed", Sales[Quantity] * Sales[UnitPrice] - Sales[Discount] )
ORDER BY [Line]
```

**Context trace:**

1. S1: 2 times 10 minus 0 equals 20.
2. S2: 1 times 5 minus 1 equals 4.
3. The supplied NetAmount column agrees with the documented row formula.

**Hand-derived worked-reference result:**

| Line | Stored | Reconstructed |
| --- | --- | --- |
| S1 | 20 | 20 |
| S2 | 4 | 4 |

Agreement verifies this tiny fixture's arithmetic. It does not prove that a source system applies every discount or tax policy correctly.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: A measure over a selected population

**Starting context:** North customers and order year 2025.

```dax
EVALUATE CALCULATETABLE ( ROW ( "Revenue", [NetRevenue], "Quantity", [QuantitySold] ), Customer[Region] = "North", 'Date'[Year] = 2025 )
```

**Context trace:**

1. Eligible lines are S4, S5 and S8.
2. Their stored amounts are 27, 20 and 36, totaling 83.
3. Their quantities are 3, 4 and 2, totaling 9.

**Hand-derived worked-reference result:**

| Revenue | Quantity |
| --- | --- |
| 83 | 9 |

The context changes the measure result from 187 to 83. It does not change S4's line value from 27 into a regional total.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Filtering visibility does not rewrite an excluded row.
2. Only Ada's two early lines are North in that year.
3. Use columns from the current Sales row.
4. Repeated group aggregates change the grain.
5. A key identifies stored members; a measure changes with context.
6. Distinguish a persisted classification from a selected-context ratio.
