# C++ model families and end-to-end acceptance

Start with: tmb-047, tmb-024.

Outcome: Plan a qualified custom template using the appropriate authoring families.

The classroom companion runs in the prepared R statistics runtime. It uses base R to expose the mathematics or data contract. Compiling and executing TMB uses the separate [owned project](../projects/tmb-local/README.md); a companion run is not a TMB compiler or rpy2 receipt.

A custom TMB model is built from interface declarations, typed arithmetic, normalized density terms, derivative rules, sparse or dense structure, report/simulation definitions and a native process boundary. The [C++ API-family map](../CPP-API-FAMILIES.md) links these families to the chapters, existing original models and appropriate validation. It deliberately excludes a promise to teach every private Eigen or AD-engine symbol.

This course now combines a complete pinned R API inventory with a model-authoring map. The two are complementary: knowing `MakeADFun` is not enough to write a correct C++ objective, and writing a density is not enough to manage optimization, uncertainty and library lifetime.

### Worked case A: a correlated multi-sensor likelihood

Start with a typed response matrix and explicit row/column meaning. Decide whether covariance is dense, sparse precision or separable across axes. Write the normalized density, choose scientifically justified scales and transforms, and compare a tiny evaluation against a dense independent formula. Then test parameter derivatives, data-shape rejection, optimizer behavior and selected uncertainty reports.

The companion constructs a small acceptance plan with distinct checks for array order, covariance/precision meaning, normalizers and gradients. Each check addresses a concrete failure mode. A successful compiler invocation cannot replace them.

### Worked case B: an optimized custom primitive

Suppose the same model needs a costly special operation. First implement a transparent typed reference. Derive a candidate atomic's forward and reverse rules, compare them across the domain, and verify the higher derivative orders required by the actual latent integration. Only then compare tape size, runtime and memory under a fixed workload.

The companion shows that an API family may be explained, have an algebraic oracle and still lack a compiled runtime receipt. That state is acceptable when labeled; it must not be promoted to “all paths pass” because another original model happened to use the same library.

### Answered discussion

**What is covered comprehensively?** The public R function surface and the model-authoring families needed for original scalar, vector, multivariate, sparse, separable, latent and custom-derivative workflows. **What remains open-ended?** Every possible probability model, private dependency symbol, specialized build and hardware configuration. **How does a future contributor extend this safely?** Add original source and a distinct mathematical oracle, preserve old lesson IDs, update the family/API maps, and qualify the exact native and learner-facing surfaces before changing capability claims.

The original nine-model project, public API probe, Python bridge and advanced Spark integration provide separate evidence layers. Their shared scientific principle is explicit ownership of data, parameters, latent variables, native objects and results.
