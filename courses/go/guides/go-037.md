# go-037: Reconciliation as an idempotent control loop

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-036

## Learning objectives

Write a reconcile function that plans only the changes needed and becomes a no-op once state has converged. Along the way, explain reconciliation, idempotence, convergence; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A controller repeatedly compares desired and observed state and takes a bounded step toward convergence. Reconciliation is level-based: it should ask what is true now rather than assume it received every historical event. Events are hints that work may be needed, not an exactly-once command log. A successful reconcile can be a no-op when the object already satisfies intent. Repeating it should not create duplicate side effects. Separate a pure decision function from the API adapter so planning can be tested deterministically. External operations need ownership, idempotency keys and explicit handling of uncertain outcomes.

## Vocabulary and concepts

- **Reconciliation:** Repeatedly moving observed state toward desired state.
- **Idempotence:** Repeating an operation has the same intended effect as performing it once.
- **Convergence:** Approaching a stable state satisfying declared intent.

## Syntax anatomy and reasoning

Represent desired and observed state as small values, then return a typed action such as create, update or none. Avoid embedding API calls inside every conditional. The adapter performs an action, records evidence and schedules another observation. A real controller often converges over several reconciliations rather than blocking until every resource becomes ready. Status should describe observed facts, including the generation to which they apply.

## Worked example / walkthrough

### Worked example 1: Plan a missing child

Observe no child for a desired replica count of 3.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func plan(wanted int, exists bool, current int) string {
	if wanted < 0 {
		return "invalid"
	}
	if !exists {
		return "create"
	}
	if wanted != current {
		return "update"
	}
	return "none"
}

func main() {
	// Plan a missing child
	{
		check(plan(3, false, 0) == "create", "missing child")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The action is create.

The planner reports intent without performing a cluster mutation. The adapter still needs an exact owner identity.

### Worked example 2: Plan a changed child

Observe an existing child with count 2 while desired is 3.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func plan(wanted int, exists bool, current int) string {
	if wanted < 0 {
		return "invalid"
	}
	if !exists {
		return "create"
	}
	if wanted != current {
		return "update"
	}
	return "none"
}

func main() {
	// Plan a missing child
	{
		check(plan(3, false, 0) == "create", "missing child")
	}

	// Plan a changed child
	{
		check(plan(3, true, 2) == "update", "changed child")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The action is update.

The update is justified by a current difference, not by assuming a prior event was delivered once.

## Common pitfalls and diagnosis

Edge-triggered thinking is the trap: a reconciler that acts on what an event says happened, such as replica added, instead of reading current state. Events can be dropped, merged or replayed, so the loop must compute from observation every time. Validate intent before acting, and treat an existing child as normal; a reconcile that always creates fails on its second run.

## Progressive hints

### Hint for investigation 1: Plan a missing child: predict an edited check

1. Restate the expected observation: The action is create.
2. No child exists yet. Which branch of plan runs after validation?
3. With exists set to true, plan compares 3 with 0 and returns update, so `=="create"` fails. The planner is right; the edited observation claims a child already exists.

### Hint for investigation 2: Plan a changed child: diagnose an edited check

1. Restate the expected observation: The action is update.
2. The child exists but holds 2. Which comparison decides the action?
3. A child at 3 already matches desired, so plan returns none and `=="update"` fails. Restore the observed count of 2.

### Hint for investigation 3: Make convergence a no-op

1. Restate the expected observation: The action is none.
2. Observed equals desired. What does a converged plan return?
3. A repeated event should not produce duplicate writes after convergence.

### Hint for investigation 4: Reject invalid desired state

1. Restate the expected observation: The planner returns invalid.
2. Validation runs before existence is checked. What does a negative count produce?
3. A persistent validation error should be surfaced to the user rather than retried forever as if it were a transient API outage.

### Hint for investigation 5: Simulate a converging step

1. Restate the expected observation: The next plan is none.
2. After the update is applied, current equals desired. What is the second plan?
3. The state transition shows convergence for this simple model.

### Hint for investigation 6: Transfer scale-to-zero

1. Restate the expected observation: The planner requests update, then converges at zero.
2. Zero is valid desired state. Which actions take 2 to 0 and then settle?
3. Zero can be a valid desired value.
