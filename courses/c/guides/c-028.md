# c-028: Headers, translation units and reproducible builds

## Level and prerequisites

Intermediate, approximately 120 minutes plus a later retrieval session. Direct prerequisites: `c-027`

## Learning objectives

Split a program into a header and translation units with one definition per symbol and reproducible behavior. Along the way, explain declaration, definition and linkage. Implement the six investigations, from the "call a declared API" case to the "transfer repeatable builds to repeatable behavior" case, with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

A multi-file C project separates declarations in headers from definitions in source files. Each source file is compiled independently, so a header is the shared contract the compiler uses at every call site. The linker later resolves external definitions. Defining a non-static global function in a header included by several files can create duplicate definitions. Omitting a required source object can create an unresolved symbol. Include guards prevent repeated declarations inside one translation unit, but do not fix incorrect cross-file ownership. A reproducible build records compiler mode, warnings, source dependencies and link libraries explicitly.

## Vocabulary and concepts

- **Declaration:** A statement describing a name and its type.
- **Definition:** The source that provides an object or function implementation.
- **Linkage:** The rules connecting declarations of the same entity across scopes or files.

## Syntax anatomy and execution trace

A header declares a function prototype under an include guard. One .c file defines that function, and a caller includes the header. Compile each source with -c to produce an object, then link the objects into one executable. Put libraries after the objects that reference them when the linker requires left-to-right resolution. The browser pad remains one main.c; the separate fixture demonstrates actual headers, source files, tests and a Makefile.

## Worked example / walkthrough

### Worked example 1: Call a declared API

Use the stats_sum prototype before its definition.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int stats_sum(const int *values, size_t length);
int stats_sum(const int *values, size_t length) {
  int sum = 0;
  for (size_t i = 0; i < length; i++)
    sum += values[i];
  return sum;
}

int main(void) {
  /* Call a declared API */
  {
    int values[] = {2, 4, 6};
    CHECK(stats_sum(values, 3) == 12);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** Summing 2, 4, 6 returns 12.

A compatible declaration lets the compiler validate the call independently of where the definition appears.

### Worked example 2: Use an empty API contract

Sum a zero-length view.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int stats_sum(const int *values, size_t length);
int stats_sum(const int *values, size_t length) {
  int sum = 0;
  for (size_t i = 0; i < length; i++)
    sum += values[i];
  return sum;
}

int main(void) {
  /* Call a declared API */
  {
    int values[] = {2, 4, 6};
    CHECK(stats_sum(values, 3) == 12);
  }

  /* Use an empty API contract */
  {
    CHECK(stats_sum(NULL, 0) == 0);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The result is zero.

The interface explicitly permits this empty case and the implementation makes no pointer access.

## Exercises

How the hints, control edits and regressions below work: [Work an exercise](../STUDY-GUIDE.md#work-an-exercise).

### Exercise 1: Call a declared API: change one input

In worked example 1, change `int values[] = {2, 4, 6};` to `int values[] = {3, 4, 6};`. Predict which value the CHECK on `stats_sum(values, 3) == 12` sees, then run and restore.

**Expected:** `Check failed` at `stats_sum(values, 3) == 12`; restoring `int values[] = {2, 4, 6};` passes again.

**Verify:** Name the value that made `stats_sum(values, 3) == 12` false, where worked example 1 showed that summing 2, 4, 6 returns 12.

**Progressive hints:** First trace `values` from initialization. Then compute what the CHECK sees with `int values[] = {3, 4, 6};` in place.

### Exercise 2: Use an empty API contract: diagnose an edited check

Worked example 2's CHECK now reads `CHECK(stats_sum(NULL, 0) != 0);`. Explain why it fails although the result is zero, then restore it.

**Expected:** `Check failed` until the CHECK reads `CHECK(stats_sum(NULL, 0) == 0);` again, though the result is zero.

**Verify:** Explain why `CHECK(stats_sum(NULL, 0) != 0);` rejects a state that `stats_sum(NULL, 0) == 0` accepts, using your failing and repaired runs.

**Progressive hints:** First work out what `stats_sum` returns here. Then compare `CHECK(stats_sum(NULL, 0) != 0);` with worked example 2's original line.

### Exercise 3: Compare two callers

Call the same helper with two separate arrays.

**Expected:** The results are 3 and 7.

**Verify:** Keep a CHECK equivalent to `stats_sum(a, 2) == 3 && stats_sum(b, 2) == 7`. Control edit: changing `int a[] = {1, 2}, b[] = {3, 4};` to `int a[] = {2, 2}, b[] = {3, 4};` must fail it; then restore it.

**Progressive hints:** First trace `a` and `b` from initialization. Then recall: Reusable code should not depend on one caller-owned array or hidden previous state.

### Exercise 4: Retain caller data

Sum an array and inspect its elements afterward.

**Expected:** The input remains unchanged.

**Verify:** Keep a CHECK equivalent to `values[0] == 2 && values[1] == 4`. Control edit: changing `int values[] = {2, 4};` to `int values[] = {3, 4};` must fail it; then restore it.

**Progressive hints:** First trace `values` from initialization. Then recall: The const-qualified input contract communicates read-only access through the API.

### Exercise 5: Check a one-element boundary

Sum one negative value.

**Expected:** The result is -3.

**Verify:** Keep a CHECK equivalent to `stats_sum(values, 1) == -3`. Control edit: changing `int values[] = {-3};` to `int values[] = {-4};` must fail it; then restore it.

**Progressive hints:** First trace `values` from initialization. Then recall: The API handles its stated signed data range; this small fixture avoids overflow.

### Exercise 6: Transfer repeatable builds to repeatable behavior

Call the pure helper twice on the same input.

**Expected:** Both results equal 6.

**Verify:** Keep a CHECK equivalent to `first == 6 && second == 6`. Control edit: changing `int values[] = {1, 2, 3};` to `int values[] = {2, 2, 3};` must fail it; then restore it.

**Progressive hints:** First trace `first` and `second` from initialization. Then recall: Stable input and a pure function produce stable behavior.

## Common pitfalls and diagnosis

Defining a non-`static` variable in a header: every file that includes it gets a definition, and the link fails with a duplicate symbol. Put the `extern` declaration in the header and exactly one definition in a `.c` file.

General diagnosis order and the pointer checklist: [Diagnose failures](../STUDY-GUIDE.md#diagnose-failures).
