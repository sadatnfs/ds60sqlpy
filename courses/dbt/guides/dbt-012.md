# dbt-012: Model versions and semantic compatibility

## Level and prerequisites

Intermediate. Direct prerequisites: `dbt-003`, `dbt-011`

**Outcome:** Manage a semantic model change with explicit consumer versioning.

## Question and mechanism

A model version identifies a particular contract. Consumers can reference an explicit version or follow the declared latest version. Those choices have different change behavior. An explicit version supports a controlled migration; following latest can be appropriate only when the consumer accepts the change policy.

The first case gives two versions the same column name and numeric type but different values. A stable consumer requests version 1 and receives 100, while an unversioned consumer follows version 2 and receives 80. This is intentionally a semantic change, not a parser or dtype error. A type-compatible change can still alter a model feature, dashboard metric or business decision.

The second case makes the meaning explicit: gross 100 minus returns 20 yields net 80. The dependency graph records where the calculation came from, but it does not decide whether a consumer intended gross or net. Versioning, descriptions, comparison evidence and a migration plan work together.

## Syntax and data contract

The model metadata declares latest_version and its versions, with defined_in pointing to the implementation files. ref('customer_value', version=1) selects an explicit contract. A plain ref follows the declared latest version. Inspect both the resolved database result and manifest dependency information.

## Worked case 1: Resolve explicit and latest consumers

The first project builds both versions and two consumers. Their results demonstrate the consequence of version selection while keeping the output type unchanged. The example avoids implying that a version number automatically guarantees compatibility.

**Expected evidence:** The explicit v1 consumer returns 100; the latest v2 consumer returns 80.

```python
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def example_one():
    with tempfile.TemporaryDirectory() as d:
        schema = {
            "models": [
                {
                    "name": "customer_value",
                    "latest_version": 2,
                    "versions": [
                        {"v": 1, "defined_in": "customer_value_v1"},
                        {"v": 2, "defined_in": "customer_value_v2"},
                    ],
                }
            ]
        }
        p = project(
            d,
            models={
                "customer_value_v1": "select 100 as value",
                "customer_value_v2": "select 80 as value",
                "stable_consumer": "select value from {{ ref('customer_value', version=1) }}",
                "latest_consumer": "select value from {{ ref('customer_value') }}",
            },
            schema=schema,
        )
        invoke(p, "build")
        assert rows(p, "select value from stable_consumer") == [(100,)]
        assert rows(p, "select value from latest_consumer") == [(80,)]
        return {"explicit_v1": 100, "latest_v2": 80}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Name the semantic difference

The second project computes a net quantity from its defined components and records the dependency edge. It provides enough meaning to explain why a consumer might need a different version or retraining.

**Expected evidence:** Net is 80, derived from gross 100 and returns 20.

def example_two():

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Pin a consumer

Change the latest consumer to request version 1 explicitly.

**Check:** It returns 100.

**Hint:** Use the version argument.


### 2. Change latest selection

Declare version 1 as latest in the fixture.

**Check:** The unversioned consumer follows that declaration.

**Hint:** Latest is project metadata.


### 3. Add a type-compatible defect

Change the value while keeping the same type and name.

**Check:** Schema checks alone can still pass.

**Hint:** Meaning is not captured by dtype.


### 4. Design a model migration

Explain what a trained model needs when its input changes from gross to net.

**Check:** The answer includes feature version and validation.

**Hint:** The old coefficients were trained under a different meaning.


### 5. Inspect lineage

Find the dependency for the net model in the manifest.

**Check:** It points to the declared base model.

**Hint:** Lineage records a relationship.


### 6. Retain rollback information

List the artifacts needed to restore a previous consumer contract.

**Check:** They identify source, model version and validated data/interface.

**Hint:** A version label alone is insufficient.


## Diagnose errors and misleading results

If a result changes without a schema error, inspect semantic definitions and version resolution. An unversioned ref can follow a new latest contract intentionally. If a pinned consumer fails after removal of an old version, follow the migration policy instead of silently retargeting it.
