# js-066: D3 capstone: an accessible, tested analytical dashboard

## Level and prerequisites

Advanced; about 180 minutes plus independent practice. Direct prerequisites: `js-065`. This is the D3.js specialization within the JavaScript path. Use the original language and browser lessons whenever syntax or DOM behavior is unfamiliar.

## Learning objectives

Build and defend an accessible, tested analytical dashboard with independent checks and stated evidence limits. The central exercise is: Build a complete accessible dashboard from a blank pad. Produce a chart whose data transformation, visual encoding and interaction can be explained and checked independently.

## Purpose, vocabulary and mental model

The final D3 project combines a validated dataset, explicit transformations, consistent scales, keyed rendering and accessible controls. Its goal is an analytical explanation that a reader can inspect, not merely an attractive screenshot. Every visible claim should have a named source row grain, unit and aggregation policy.

Testing a visualization has several layers. Pure data tests verify filters and summaries. DOM or Canvas checks verify mark count and geometry. Interaction tests verify state changes and keyboard routes. Visual review catches clipping, illegible labels and misleading emphasis. No single screenshot or assertion covers all of these.

The reference is a small category dashboard with a filter, sorted bars, exact text values and a total summary. It uses no network input and offers a deterministic completion marker. Your independent project should change the dataset and question, then defend the encoding and limitations without copying the reference blindly.

### Key terms

- **Acceptance check:** An explicit test the finished dashboard must pass, such as a filtered total, a mark count, a keyboard route or the completion marker.
- **Accessibility review:** Manual checking of keyboard operation, focus, narrow screens, reduced motion and assistive technology output, which automated DOM checks support but do not replace.
- **Data provenance:** The documented origin, row grain, units and transformations behind each visible claim in the dashboard.
- **Visual regression:** An unintended change in the rendered appearance, such as clipped or illegible labels, found by reviewing the output rather than by data assertions.

## Syntax anatomy and mechanism

Keep the chart’s source data, derived data and view state separate. This capstone measures its container width and uses that width in its viewBox, keeping labels at a readable 14-pixel logical size instead of shrinking a fixed 640-unit chart. A ResizeObserver schedules geometry writes on a guarded animation frame when the container changes width. Keeping writes outside the observer callback avoids a resize-notification feedback loop. It disconnects and cancels pending animation work when the preview page leaves. The table adds explicit cell padding and alignment so headers and values remain distinct. Validate IDs and finite nonnegative values before rendering. Reconcile marks by stable ID. Add a native group selector and reset. Provide a text table that remains useful without interpreting color.

The reference asserts baseline totals, filtered totals, mark counts, reset behavior and source preservation. It intentionally does not claim to automate screen-reader usability or statistical validity. Perform the manual narrow-screen, keyboard and interpretation checks before calling your own project complete.

## Worked example / walkthrough

### Worked example 1: Write independent acceptance conditions

These checks describe behavior rather than implementation details, and each is computed from the fixture.

```javascript
const rows = [
  { group: "A", hours: 3 },
  { group: "A", hours: 5 },
  { group: "B", hours: 4 },
  { group: "B", hours: 8 },
];
const expected = { allCount: 4, allTotal: 20, groupATotal: 8 };
const actual = {
  allCount: rows.length,
  allTotal: d3.sum(rows, (d) => d.hours),
  groupATotal: d3.sum(
    rows.filter((d) => d.group === "A"),
    (d) => d.hours,
  ),
};
console.log(Object.keys(expected).filter((key) => actual[key] !== expected[key]));
```

**Expected observation:** An empty list: every acceptance condition holds, and each one could fail on its own for a meaningful user-visible error.

### Worked example 2: State the analytical claim

A clear caption names scope and limitations; it is shown as text and stored in the SVG description.

```javascript
// js-066 worked example 2: a complete program for the classroom preview.
const host = document.querySelector("#chart");
const output = document.querySelector("#output");
host.replaceChildren();
const check = (condition, message) => {
  if (!condition) throw new Error(message);
};
const svg = d3
  .select(host)
  .append("svg")
  .attr("viewBox", "0 0 640 360")
  .attr("role", "img")
  .attr("aria-label", "D3 capstone: an accessible, tested analytical dashboard")
  .style("width", "100%")
  .style("max-width", "640px");
const caption =
  "Synthetic study hours by learner group; totals describe this fixture, not a population estimate.";
const rows = [
  { group: "A", hours: 3 },
  { group: "A", hours: 5 },
  { group: "B", hours: 4 },
  { group: "B", hours: 8 },
];
const totals = [
  ...d3.rollup(
    rows,
    (values) => d3.sum(values, (d) => d.hours),
    (d) => d.group,
  ),
];
svg.append("desc").text(caption);
svg
  .selectAll("rect")
  .data(totals)
  .join("rect")
  .attr("x", 120)
  .attr("y", (d, i) => 60 + i * 90)
  .attr("height", 50)
  .attr("width", ([, total]) => total * 30)
  .attr("fill", "#2563eb");
svg
  .selectAll("text")
  .data(totals)
  .join("text")
  .attr("x", 20)
  .attr("y", (d, i) => 92 + i * 90)
  .text(([group, total]) => `${group}: ${total} h`);
d3.select(host).append("p").text(caption);
check(
  svg.select("desc").text() === caption,
  "The SVG carries the caption for assistive technology",
);
check(totals.map(([, total]) => total).join(",") === "8,12", "Totals describe only this fixture");
output.textContent = "js-066 worked example 2 complete";
```

**Expected observation:** Two labeled bars, A: 8 h and B: 12 h, with the caption shown below the chart and stored in the SVG description.

## Six progressive exercises

### Exercise 1: Predict baseline and filtered totals.

**Expected evidence:** All records total 20; groupA totals 8.

**Progressive hint:** Calculate from the source rows before running.

### Exercise 2: Change one value and update the independent expectations.

**Expected evidence:** The corresponding bar, text row and total change together.

**Progressive hint:** A coordinated update should preserve identity and affect only derived values implied by the source change.

### Exercise 3: Build a complete accessible dashboard from a blank pad.

**Expected evidence:** Controls, marks, text values and summary agree.

**Progressive hint:** The project integrates earlier mechanisms.

### Exercise 4: Introduce a duplicate-ID failure and repair the input.

**Expected evidence:** Validation refuses ambiguous identity before rendering.

**Progressive hint:** Do not remove the identity check to obtain a success marker.

### Exercise 5: Perform keyboard and narrow-screen review.

**Expected evidence:** All controls are reachable, labels readable and essential information available without hover.

**Progressive hint:** Automated checks cannot prove the full human experience.

### Exercise 6: Defend the finished analysis and its evidence limits.

**Expected evidence:** Explain data grain, cleaning, scales, aggregation, interactions and untested surfaces.

**Progressive hint:** Expert practice includes knowing what the chart does not establish.

## Debugging and common mistakes

Keep three checkpoints separate: the records after parsing, the domain and geometry after transformation, and the visible marks after rendering. A chart can look plausible while silently dropping records or assigning the wrong scale. Inspect counts, IDs, finite coordinates and meaningful expected values before adjusting colors. A missing mark may come from invalid input, a missing selection, an undefined scale result or clipping outside the viewBox.

The controlled failure for this lesson is: Introduce a duplicate-ID failure and repair the input. Its distinguishing evidence is Validation refuses ambiguous identity before rendering. Preserve that failing case when repairing your program. Do not remove an assertion or broaden a scale merely to hide a wrong input. Explain whether a changed value should affect the data, an encoding, a layout or only presentation.

## Accessibility and interpretation

Give the visualization a descriptive title and a short textual summary of the main result. Keep a table or list when exact values matter. Do not encode a critical category only through color; use labels, shapes or position as appropriate. Interactive controls need keyboard operation and clear focus, and motion should respect the user's reduced-motion preference. Automated DOM checks support, but do not replace, a real keyboard and assistive-technology review.

A data scientist must also defend the statistical meaning. State the population, units, aggregation, missing-value policy and uncertainty where relevant. Synthetic points illustrate a mechanism and do not establish a real-world finding. A beautiful visualization should make a valid claim easier to inspect, not make a weak claim appear certain.

## Retrieval and transfer

Close the solution and explain acceptance, accessibility, data provenance using a new small dataset. Reconstruct one example from a blank pad. Predict the effect of one missing value, empty input or reordered record before execution. Retain the source and observation separately from the explanation so a future reader can reproduce the case.
