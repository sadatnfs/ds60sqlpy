A queue stores requests that are waiting for a resource. It does not create that resource. An unbounded queue can turn a brief burst into excessive latency, memory growth and client timeouts, followed by retries that make the burst worse. A serving system needs an explicit admission policy and an exact rule for releasing every reservation.

This chapter assumes the prompt and output token budget from earlier chapters. The pad models reservations and FIFO waiting times. The real workshop implements one compute slot, at most two additional waiting requests, a bounded per-request context and a bounded retained-history count. The simulation is useful for reasoning; the workshop's API and cancellation tests supply actual service evidence.

## Three different limits

A request-count limit bounds the number of active requests. A token reservation bounds potential cache growth. A storage limit bounds retained request records and events. These controls protect different resources and should not be collapsed into one “maximum requests” setting.

Suppose request \(i\) reserves \(r_i=P_i+N_i\) model positions, where \(P_i\) is its prompt count including BOS and \(N_i\) its allowed continuation. With active set \(A\), admission requires both

\[
|A|<K,\qquad \sum_{i\in A}r_i+r_{\mathrm{new}}\leq R,
\]

where \(K\) is the active request-count limit and \(R\) the total token reservation budget. The live workshop also requires each request to fit its individual context. The token sum is a conservative accounting model, not an exact allocator measurement.

A request enters the active set only after its original source is safely admitted. A rejected request owns no model resources. A queued request owns a reservation even before its first model operation. A running request retains ownership until its compute and cache cleanup finish. Counting only running kernels would miss promised future growth from queued requests.

The conservation invariant is simple: every accepted reservation is released exactly once. Duplicate release can make accounting negative and admit work that does not fit. Missing release can leave the server permanently full after cancellation or error. Check normal completion, queued cancellation, running cancellation, subscriber loss, timeout, compute failure and service shutdown separately.

## FIFO and head-of-line blocking

FIFO preserves arrival order among admitted waiting requests. It is easy to explain and prevents a stream of new short jobs from continually overtaking an older job. It can also produce head-of-line blocking: a long request at the front delays several short ones.

With one worker and arrival time \(a_i\), service duration \(s_i\), start time \(b_i\) and completion time \(c_i\), a simple FIFO model is

\[
b_i=\max(a_i,c_{i-1}),\qquad c_i=b_i+s_i,\qquad w_i=b_i-a_i.
\]

The waiting time \(w_i\) is not model computation. It contributes to user latency, so reporting only kernel time can make an overloaded server appear fast. The service's admission/start events make this distinction visible.

Prioritizing short jobs can reduce mean latency if lengths are predictable, but may starve long jobs. Priority classes need explicit policy, fairness and abuse considerations. Continuous batching changes the scheduling unit from whole requests to decode iterations, but it also introduces cache and batch management complexity. Later chapters compare these policies without claiming that the simple live workshop implements them.

## Average occupancy is not a burst guarantee

Little's law relates long-run average in-system population \(L\), arrival rate \(\lambda\) and time in system \(W\) under the required stable accounting assumptions:

\[
L=\lambda W.
\]

It is a relationship among averages over a defined system boundary. It does not tell you that a queue of size \(L\) will never overflow. Arrival bursts, variable service times and correlated long prompts determine tails and rejection probability. Measure those features rather than treating the mean as a capacity certificate.

A `429` response can communicate that no capacity was admitted. A retry hint is advice, not permission for an uncontrolled retry loop. Clients should use bounded retries with backoff where the operation contract permits them, preserve the original idempotency key for unknown outcomes and allow the user to stop. Retrying every rejected request immediately can synchronize a retry storm.

## Worked case 1: count and token reservations

The first case creates three possible active slots but a total token budget of 180. Requests `a` and `b` reserve 80 and 60 tokens. A proposed 50-token request `c` is rejected because 190 exceeds the token budget, even though a count slot remains. Cancelling `b` releases 60, so `c` can be admitted. The queue becomes `a`, then `c`, and the total is 130.

The example finally releases both accepted requests and checks that ownership is empty. This is more informative than merely asserting that enqueue succeeded. It verifies a complete lifecycle for the mechanism. In the real project, a test also checks reservation totals after running cancellation and after an injected inference failure.

The changed condition demonstrates why a count-only limit is insufficient. Two large requests may need more memory than three small ones. Conversely, a token-only limit can admit too many tiny requests and overwhelm per-request objects or stream connections. Both limits are useful.

## Worked case 2: a long request ahead of short requests

The second case admits three requests at time zero with service durations ten, one and one. FIFO waiting times are zero, ten and eleven. Their order is fair by arrival time but expensive for the short requests. The code computes the timeline directly, then evaluates a separate Little's-law example with arrival rate 0.5 and mean time four, producing mean occupancy two.

Do not combine these two fixtures into a claimed performance measurement. The first is a deterministic queue trace; the second is average accounting under stated assumptions. Neither models a real GPU, network stack or variable-length generation workload. Their role is to make the quantities precise before designing measurements.

```python
"""Admission capacity is a conservation law, not an unbounded Python queue."""

from collections import deque


class Reservations:
    def __init__(self, slots=3, tokens=180):
        self.slots = slots
        self.tokens = tokens
        self.pending = deque()
        self.owned = {}

    def admit(self, identity, budget):
        if (
            identity in self.owned
            or len(self.owned) >= self.slots
            or sum(self.owned.values()) + budget > self.tokens
        ):
            return False
        self.owned[identity] = budget
        self.pending.append(identity)
        return True

    def release(self, identity):
        self.owned.pop(identity)
        if identity in self.pending:
            self.pending.remove(identity)


def example_one():
    queue = Reservations()
    assert queue.admit("a", 80)
    assert queue.admit("b", 60)
    assert not queue.admit("c", 50)
    queue.release("b")
    assert queue.admit("c", 50)
    assert list(queue.pending) == ["a", "c"]
    assert sum(queue.owned.values()) == 130
    queue.release("a")
    queue.release("c")
    assert not queue.owned
    print("Token and count reservations return to zero after explicit release.")


def example_two():
    arrivals = [0.0, 0.0, 0.0]
    service = [10.0, 1.0, 1.0]
    clock = 0.0
    waiting = []
    for arrival, duration in zip(arrivals, service, strict=True):
        started = max(clock, arrival)
        waiting.append(started - arrival)
        clock = started + duration
    assert waiting == [0.0, 10.0, 11.0]
    print("FIFO waits for long-first requests:", waiting)
    rate, mean_time = 0.5, 4.0
    mean_in_system = rate * mean_time
    assert mean_in_system == 2.0
    print("Little's-law steady-state mean occupancy:", mean_in_system)
    print("This average does not certify a finite queue against bursts.")


def main():
    example_one()
    example_two()


if __name__ == "__main__":
    main()
```

## The workshop's practical boundaries

The actual scheduler reserves one running position plus two waiting positions. A newly created request must attach its stream within a bounded grace period. Otherwise it is cancelled and its reservation is released. This prevents an abandoned creation response from occupying capacity indefinitely. The single active worker processes admitted requests in FIFO order.

Completed records no longer occupy compute reservations, but still occupy bounded history storage. When the dedicated history is full, the service rejects new admissions with an actionable storage explanation. It does not silently delete previous work. Archiving or replacing a project state directory is an explicit operator decision outside the ordinary request lifecycle.

Capacity is also bounded at the HTTP server: connection concurrency and body sizes have independent limits. These do not replace the model queue. A socket waiting for bytes and a request waiting for a GPU are different resources with different timeouts.

## Interview discussion

**When should a cancelled running request release its reservation?** After its in-flight operation has returned and request-owned state is no longer in use. Releasing immediately at the HTTP cancellation response can overcommit the device while the old kernel still runs.

**Does FIFO guarantee good latency?** It guarantees a particular order, not a latency bound. Long service times and bursts can create large waits. State the fairness objective and measure tail latency separately.

**Why bound retained history if the compute queue is bounded?** Finished requests leave the queue but can accumulate on disk indefinitely. Persistent storage needs its own policy and admission failure mode.
