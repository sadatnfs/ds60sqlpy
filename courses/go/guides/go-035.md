# go-035: Kubernetes objects, metadata, spec and status

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-034

## Learning objectives

Decode Kubernetes object JSON and separate desired spec from observed status, name from UID and equality from version order. Along the way, explain desired state, observed state, object uid; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Kubernetes exposes typed API resources through a declarative control plane. An object has an identity and metadata, desired configuration in spec, and observed information in status. A controller does not assume a successful API write means the requested real-world state already exists. metadata.uid distinguishes an object incarnation from a later object reusing the same name. generation tracks desired-state changes for resources that support that convention, while resourceVersion supports concurrency and watch semantics. Treat resourceVersion as opaque. This lesson decodes synthetic Deployment-shaped JSON to make these distinctions concrete without using credentials or contacting a cluster.

## Vocabulary and concepts

- **Desired state:** The configuration requested by a user or controller.
- **Observed state:** The state last reported by a controller.
- **Object UID:** A unique identity for one object incarnation.

## Syntax anatomy and reasoning

apiVersion identifies the API group and version; kind identifies an object kind. metadata.namespace plus name locates a namespaced object, while uid identifies its incarnation. Spec and status should have separate Go fields and responsibilities. Pointer fields can distinguish an omitted desired value from an explicit zero. JSON tags bind the Go representation to wire names. A struct here models only the selected fields and is not the full generated Kubernetes API type.

## Worked example / walkthrough

### Worked example 1: Decode desired and observed replicas

Decode a fixture requesting 3 replicas with 2 ready.

```go
package main

import (
	"encoding/json"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Metadata struct {
	Name      string `json:"name"`
	Namespace string `json:"namespace"`
	UID       string `json:"uid"`
	Version   string `json:"resourceVersion"`
}
type Deployment struct {
	APIVersion string   `json:"apiVersion"`
	Kind       string   `json:"kind"`
	Metadata   Metadata `json:"metadata"`
	Spec       struct {
		Replicas *int `json:"replicas"`
	} `json:"spec"`
	Status struct {
		Ready int `json:"readyReplicas"`
	} `json:"status"`
}

func main() {
	// Decode desired and observed replicas
	{
		var d Deployment
		err := json.Unmarshal([]byte(`{"apiVersion":"apps/v1","kind":"Deployment","metadata":{"name":"demo","namespace":"lesson","uid":"u1"},"spec":{"replicas":3},"status":{"readyReplicas":2}}`), &d)
		check(err == nil && d.Spec.Replicas != nil && *d.Spec.Replicas == 3 && d.Status.Ready == 2, "spec status")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Desired is 3 while ready is 2.

The accepted object and the observed rollout are different evidence. A controller must reconcile the gap.

### Worked example 2: Distinguish omitted from explicit zero

Decode one absent replicas field and one replicas zero.

```go
package main

import (
	"encoding/json"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Metadata struct {
	Name      string `json:"name"`
	Namespace string `json:"namespace"`
	UID       string `json:"uid"`
	Version   string `json:"resourceVersion"`
}
type Deployment struct {
	APIVersion string   `json:"apiVersion"`
	Kind       string   `json:"kind"`
	Metadata   Metadata `json:"metadata"`
	Spec       struct {
		Replicas *int `json:"replicas"`
	} `json:"spec"`
	Status struct {
		Ready int `json:"readyReplicas"`
	} `json:"status"`
}

func main() {
	// Decode desired and observed replicas
	{
		var d Deployment
		err := json.Unmarshal([]byte(`{"apiVersion":"apps/v1","kind":"Deployment","metadata":{"name":"demo","namespace":"lesson","uid":"u1"},"spec":{"replicas":3},"status":{"readyReplicas":2}}`), &d)
		check(err == nil && d.Spec.Replicas != nil && *d.Spec.Replicas == 3 && d.Status.Ready == 2, "spec status")
	}

	// Distinguish omitted from explicit zero
	{
		var a, b Deployment
		check(json.Unmarshal([]byte(`{"spec":{}}`), &a) == nil, "decode")
		check(json.Unmarshal([]byte(`{"spec":{"replicas":0}}`), &b) == nil, "decode")
		check(a.Spec.Replicas == nil && b.Spec.Replicas != nil && *b.Spec.Replicas == 0, "presence")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Only the explicit zero has a non-nil pointer.

Defaulting and an intentional scale-to-zero request have different meanings. A plain integer field would lose that distinction before validation.

## Common pitfalls and diagnosis

Treating spec as fact is the main error: spec is what someone asked for, while status is what a controller observed, and the two lag each other. Another is using a non-pointer field for an optional value, so an absent field and an explicit zero look identical. Object keys must include the namespace, and resourceVersion is an opaque token: compare it only for equality.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Decode desired and observed replicas: change one input

1. Restate the expected observation: Desired is 3 while ready is 2.
2. spec and status decode into separate fields. Which number does each hold?
3. The fixture now requests 4 replicas, so `*d.Spec.Replicas==3` fails while ready is still 2. Decoding works; the desired count changed.

### Hint for investigation 2: Distinguish omitted from explicit zero: diagnose an edited check

1. Restate the expected observation: Only the explicit zero has a non-nil pointer.
2. A pointer stays nil when its key is absent. Which decode sets it?
3. The second fixture now carries replicas 1, so b's pointer is non-nil but points at 1 and `*b.Spec.Replicas==0` fails. Restore the explicit zero.

### Hint for investigation 3: Separate name and incarnation

1. Restate the expected observation: Their names match but their identities differ.
2. The names match but the UIDs differ. Are these the same incarnation?
3. Cleanup based only on name can delete a replacement object that the operation never owned.

### Hint for investigation 4: Keep namespaces in a key

1. Restate the expected observation: The key is alpha/demo for the first object and differs from the second object's key.
2. The key joins namespace and name. Do alpha and beta produce the same key?
3. Names are unique within a namespaced resource scope, not across the whole cluster.

### Hint for investigation 5: Treat versions as opaque

1. Restate the expected observation: Both tokens are retained exactly; they differ, and string order even places 10 before 9, so only equality is meaningful.
2. The tokens are strings. Which one does byte order place first?
3. Do not increment, subtract or numerically order resourceVersion.

### Hint for investigation 6: Transfer readiness reasoning

1. Restate the expected observation: Only the equal complete state satisfies this simplified predicate.
2. The predicate requires ready to equal desired. Which state satisfies it?
3. A real Deployment readiness check also considers generation and conditions.
