# k8s-058: NetworkPolicy ingress, selectors and additive rules

## Level and prerequisites

Advanced; about 120 minutes. Direct prerequisites: `k8s-057`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Build an allowed/denied flow matrix.
- Design real isolation acceptance.

## Purpose, vocabulary and mental model

NetworkPolicy describes allowed network relationships for selected Pods. It requires a network implementation that enforces the API. Creating the object on a cluster without enforcement does not prove isolation. The policy is primarily about supported network traffic, not HTTP user identity or arbitrary application authorization.

Policies are additive. Once a Pod is isolated for a direction, the union of applicable allow rules determines permitted traffic for that direction. There is no general ordered deny rule that overrides a later allow in the ordinary API. A policy can select all Pods in one namespace with an empty podSelector, while namespace scope remains important.

Selector composition is subtle. A single peer containing both namespaceSelector and podSelector requires both conditions. Separate peers represent alternatives. Confusing these forms can allow far more callers than intended. This lesson makes that Boolean logic explicit with a small synthetic matrix.

### Key terms

- **namespaceSelector:** A NetworkPolicy peer field that selects source or destination namespaces by their labels.
- **Peer composition:** How selectors combine: a namespaceSelector and podSelector in the same peer must both match, while separate peers mean either may match.
- **Policy isolation:** A Pod becomes isolated in a direction once any policy selects it for that direction, after which only allowed traffic passes.
- **Additive allow rules:** Policies that select the same Pod combine their allows, so one policy cannot deny what another permits.

## Mechanism and field-by-field reasoning

A policy’s podSelector selects the destination Pods for ingress rules. Each from item describes an allowed source. Ports constrain the destination transport port. Namespace labels are selected on Namespace objects, not copied from Pod labels by assumption.

For a connection between two Pods, the source Pod’s egress policy and the destination Pod’s ingress policy must both permit it when those directions are isolated. A direction with no applicable isolation does not restrict that connection through NetworkPolicy. Reply traffic belonging to a permitted connection is implicitly allowed; that does not authorize an unrelated new reverse-direction connection.

The fixture provides an allow-client policy as a manual-only example. It does not claim that the ordinary local kind network enforces NetworkPolicy. The offline checker validates selector logic and fields; a live test requires both an allowed and a denied owned client under a known enforcing implementation.

## Trace the request or control path

```text
policy selects destination Pods -> ingress isolation applies
allowed source peer AND allowed destination port -> candidate permitted flow
all applicable allow rules combine by union; actual CNI must enforce
```

Read the first line from the destination's side: once a policy selects network-study Pods for ingress, everything is denied except what some rule allows. The second line is one rule, where a peer and a port must both match. The third line says rules from every applicable policy are unioned, and none of it happens unless the plugin enforces policy.

## Worked example / walkthrough

### Worked example 1: Read an AND peer

Both namespace and Pod labels must match this one peer.

```yaml
from:
  - namespaceSelector:
      matchLabels:
        study-role: client
    podSelector:
      matchLabels:
        role: tester
```

**Expected observation:** A tester in a nonmatching namespace is not allowed by this peer.

### Worked example 2: Contrast OR peers

Two list items are alternatives.

```yaml
from:
  - namespaceSelector:
      matchLabels:
        study-role: client
  - podSelector:
      matchLabels:
        role: tester
```

**Expected observation:** The namespaceSelector-only branch permits all Pods in matching namespaces. The podSelector-only branch permits role=tester Pods only in the NetworkPolicy’s own namespace. Their union is broader than the combined AND peer; it does not mean testers in every namespace.

## Six progressive exercises

### Exercise 1: Predict the AND selector result for a wrong namespace.

**Expected evidence:** It does not match even if the Pod role is tester.

**Progressive hint:** Both selectors sit in one peer. Does the wrong-namespace caller satisfy both at once?

### Exercise 2: Compare separate peers with a combined peer.

**Expected evidence:** Separate entries create alternatives; combined selectors narrow one peer.

**Progressive hint:** Rewrite the peer as two list items, a dash before each selector. Is the result narrower or broader?

### Exercise 3: Build an allowed/denied flow matrix.

**Expected evidence:** Caller namespace, Pod labels, target port and expected result are explicit.

**Progressive hint:** One row per client case in topology.json: namespace label, Pod label, port and your prediction.

### Exercise 4: Diagnose a policy object with unrestricted actual traffic.

**Expected evidence:** The implementation may not enforce policy or another allow rule may apply.

**Progressive hint:** First ask whether the plugin enforces policy at all, then list every policy that selects the destination.

### Exercise 5: Explain additive allow semantics.

**Expected evidence:** Multiple policies can broaden the union of permitted flows.

**Progressive hint:** Policies never subtract. What does a second policy allowing another peer do to the first one's set?

### Exercise 6: Design real isolation acceptance.

**Expected evidence:** One allowed and one denied owned flow under a named enforcing CNI.

**Progressive hint:** One allowed flow is not enough. Name the denied flow that must fail and the plugin that enforces it.

## Diagnosis, failure boundaries and common mistakes

One indentation mistake changes everything: a dash before podSelector turns an AND peer into two OR peers and quietly admits every Pod in client namespaces plus testers in the policy's own namespace. Read the YAML structure, not just the labels. Another mistake is matching the Service port 80 in policy rules; policy sees the Pod port 8080 after translation. Seeing traffic flow despite a policy usually means the plugin does not enforce NetworkPolicy or another policy allows it. Never delete policies to diagnose; read all of them and build the union by hand.
