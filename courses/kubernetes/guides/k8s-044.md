## Purpose, vocabulary and mental model

CIDR notation combines an address with a prefix length, such as 10.244.0.0/16. The prefix describes which leading bits identify the network. A longer prefix describes a smaller address set. CIDR membership is a binary relationship, not a string-prefix test.

Clusters need address planning for nodes, Pods and Services, and may interact with a host LAN, VPN or cloud network. Overlapping ranges can make a destination ambiguous or route traffic to the wrong place. A configuration can be valid YAML while its network plan is unusable in the actual environment.

Pod and Service CIDRs serve different purposes. Pod ranges allocate workload endpoints according to the CNI and cluster design. Service ranges allocate virtual service destinations. A Service IP should not be assumed to appear as an ordinary Pod interface address. Dual-stack adds another family of addresses and routes rather than replacing these distinctions.

## Mechanism and field-by-field reasoning

Use an IP-address library for membership and overlap reasoning. In a/24 IPv4 network there are 256 numeric addresses, but usable allocations depend on the system’s rules and reservations. Do not turn the arithmetic count into a guaranteed Kubernetes capacity claim.

A routing table chooses a next hop according to destination and policy, commonly preferring the most specific matching prefix. An overlapping VPN route can affect traffic before it reaches a cluster component. Investigate the caller’s route context rather than changing Kubernetes selectors to fix a host routing conflict.

## Worked example / walkthrough

### Worked example 1: Check membership using the standard library

This is an offline calculation.

```python
from ipaddress import ip_address, ip_network

network = ip_network("10.244.0.0/16")
print(ip_address("10.244.1.7") in network)
print(ip_address("10.96.0.20") in network)
```

**Expected observation:** True thenFalse; no packet is sent.

### Worked example 2: Detect an overlap

A more specific prefix can still overlap a broader one.

```python
from ipaddress import ip_network

print(ip_network("10.0.0.0/8").overlaps(ip_network("10.244.0.0/16")))
```

**Expected observation:** True; address planning must account for both ranges.

## Diagnosis, failure boundaries and common mistakes

The controlled failure in this chapter is: Diagnose a VPN route overlapping the Pod range. Its distinguishing result is The caller can select an unintended route before cluster delivery. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
