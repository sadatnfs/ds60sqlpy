# dme-020: Orchestration, dependencies and safe retries

## A workflow is more than a sequence of functions

A data workflow has dependencies, observable outputs and failure boundaries. Suppose validation must succeed before aggregation, and aggregation must succeed before publication. That dependency graph is a directed acyclic graph, or DAG. “Directed” means an edge has an upstream and downstream direction. “Acyclic” means following dependencies cannot return to the same node. A cycle such as validation requiring publication while publication requires validation has no valid starting order.

A scheduler decides which tasks may run and when. An orchestrator usually adds durable state, retries, logs, parameterized runs and operational controls. Airflow is one actual orchestration platform, covered in the separate service workshop. This chapter executes a small explicit mechanism using Python's `TopologicalSorter` and real local files. It does not start Airflow, emulate its complete behavior or qualify a distributed scheduler. Keeping the mechanism visible helps explain what a larger platform must preserve.

The graph is `validate -> aggregate -> publish`. Validation accepts a complete bounded list of positive integer counts. Aggregation computes the row count and total. Publication writes a JSON product containing those values and a run identity. The identity binds both the input values and the exact reviewed program bytes. If the data or transformation changes, the work belongs to a different run rather than silently inheriting old success markers.

## Separate attempts, completion and effects

An attempt means execution was started. A completed checkpoint means the orchestrator recorded an accepted result. An effect means something changed outside the current stack frame, such as a file being published. These three facts can disagree after interruption. A task may write its effect successfully and crash before its completion checkpoint is saved. Treating the absence of a success marker as proof that nothing happened can duplicate the effect on retry.

The program stores a ledger with per-run `steps` and `attempts`. Before performing a task, it records the attempt. After obtaining a result, it saves the value and a content hash. A resumed completed step verifies that its stored value still matches its hash. Dependencies must have accepted checkpoints before downstream work begins. The final read also compares the actual publication with the accepted publish checkpoint; a stale success marker cannot make corrupted output trustworthy.

Let \(I\) be a run identity and \(E(I)\) the intended published effect. The desired retry property is

\[
\operatorname{apply}(I,E);\operatorname{apply}(I,E)
\equiv\operatorname{apply}(I,E),
\]

where equivalence concerns the accepted external state, not whether the function was called once. Attempts can increase while the accepted effect remains unchanged. If the same identity names a different effect, the program rejects the conflict instead of guessing which value is correct.

## Worked case 1: resume after a completed dependency

`example_one()` starts with counts two, three and one. It deliberately raises an exception after validation has been checkpointed. At that moment, the ledger contains one accepted validation result, but aggregation and publication have not completed. The caller catches the expected exception, then invokes the same pipeline again with the same input and source identity.

The second invocation walks the topological order. It verifies and reuses validation, runs aggregation once and publishes once. The result reports three rows and six packages. The attempt counts are one for each step. A third invocation produces the same result and does not increase attempts, because all accepted checkpoints and the publication still agree. This distinguishes reuse of completed work from an indiscriminate restart of the entire pipeline.

The program uses owned temporary files, so the example models restart by reentering the function with durable files intact. It does not claim a killed process or machine outage in this case. The earlier atomic-publication chapter executes a real child-process failure. Evidence should be stated at the level actually exercised. Here the important observation is that recorded task state controls resumption and is checked against recorded content.

## Worked case 2: reconcile publication after an uncertain outcome

The second case moves the failure boundary. Publication writes its product file, then raises before saving the publish-step checkpoint. The consumer-visible file already exists, but the workflow ledger does not yet say the step completed. A retry sees an incomplete task. It increments the publish attempt count to two, reads the existing file and compares its contents with the effect expected for this exact run identity.

Because the bytes describe the expected product, the retry accepts the existing effect and records completion. There is still only one product file for that run. Its bytes are unchanged across recovery. The accepted total remains six, while the attempt history truthfully reports two publish attempts. This is reconciliation: examining the external effect before deciding whether more work is necessary. It is not a claim that distributed message delivery happened exactly once.

The case then changes the input from two, three, one to two, three, four. The run identity changes, and the new total is nine. A second versioned product is created while the original remains present. Reusing the old aggregate merely because the step name is still `aggregate` would be incorrect. Checkpoints must be scoped to the inputs and transformation they describe, not just to a friendly task label or calendar date.

## What this mechanism does not provide

A production orchestrator needs more than these three functions. It may need concurrent workers, leases or heartbeats, bounded queues, authorization, schedule calendars, backpressure, retry budgets, task timeouts, cancellation and durable operational history. Concurrent writers would also require coordination around the shared ledger. A local `Path.replace` does not prevent two independent processes from overwriting each other's updates. Power-loss durability requires additional filesystem and storage reasoning beyond process-level replacement.

Hash checks establish consistency with a recorded value; they do not establish who authorized that value. An attacker able to replace both data and its stored hash can create a matching pair. The later artifact chapter separates integrity from trust. Similarly, a temporary-path test does not qualify a shared object store's conditional-update semantics. The full data-product project and real orchestration workshop have their own lifecycle and service boundaries.

## Diagnose retry problems using the state transitions

If the total doubles after retry, inspect whether publication performs an append without an operation identity. If output changes while the identity stays constant, inspect missing inputs such as current time, environment flags or mutable external files. If a task is marked complete but its product is absent or corrupt, compare actual output with the accepted checkpoint before moving forward. The correct response may be a failed integrity check, not silently rewriting history.

If dependencies seem to run out of order, inspect graph edges. The mapping used by `TopologicalSorter` lists each node's predecessors. Reversing that interpretation changes the execution order. A task that reads “latest” data can also violate the intended dependency even if the graph looks correct, because “latest” can move between attempts. Bind an explicit dataset or partition version and retain it in the run identity.

## Applications and answered interview discussion

This pattern applies to analytical builds, feature computation, periodic exports and model evaluation. It makes a workflow explainable: a reviewer can identify the input, completed dependencies, attempted work, accepted outputs and recovery action. Keep operational attempts separate from business events. A retry counter is useful for diagnosis, but it must not change the package total being published.

An interviewer may ask, “The job failed after writing its output. Should we rerun it?” The careful answer is to inspect the operation identity and output first, then reconcile or safely retry under an idempotent contract. If asked whether a successful orchestrator task proves good data, explain that execution success and data acceptance are separate. The task must include meaningful row, type, completeness and business checks before its output becomes a trusted dependency.

For a useful changed condition, modify the accepted product file after a successful run and call the pipeline again. The final consistency check should reject it despite every step being marked complete. That failure teaches why a status badge cannot replace readback of the actual artifact.
