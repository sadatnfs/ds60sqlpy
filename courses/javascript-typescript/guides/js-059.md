## Purpose, vocabulary and mental model

A hierarchy represents parent-child relationships without cycles. A tree has one root and a unique path from that root to each node. This differs from a general network, where nodes can have several relationships and cycles. Choosing a tree layout for data that is not a tree can hide important structure.

`d3.hierarchy` wraps nested input in nodes with parent, children, depth and traversal methods. Layout algorithms add geometry to these wrapper nodes. The original data remains available as node.data. A tree layout uses topology, not a numeric magnitude, to position nodes.

The reference visualizes a small learning taxonomy. Labels explain the nodes, and links show parent-child relationships. A hierarchy can be deep or broad, so a reusable view must address label collisions, collapse state and keyboard navigation rather than assuming every tree fits one screen.

## Syntax anatomy and mechanism

Construct the hierarchy from an object whose children field contains nested objects. Apply `d3.tree().size([height,width])` to compute coordinates. For a left-to-right tree, use the layout y coordinate as horizontal position and x as vertical position.

`root.links()` returns source-target pairs; `d3.linkHorizontal` converts each pair into a path. Check node and edge counts: a connected tree with n nodes has n-1 parent edges. This is a structural invariant, not a visual preference.

## Worked example / walkthrough

### Worked example 1: Count a tiny hierarchy

The wrapper exposes descendants and links.

```javascript
const root = d3.hierarchy({ name: "Root", children: [{ name: "A" }, { name: "B" }] });
console.log(root.descendants().length, root.links().length);
```

**Expected observation:** 3 nodes and 2 parent links.

### Worked example 2: Distinguish topology from magnitude

A tree layout does not require a size value.

```javascript
d3.tree().size([250, 450])(root);
console.log(root.children.every((d) => d.depth === 1));
```

**Expected observation:** true; depth is a structural property.

## Debugging and common mistakes

Keep three checkpoints separate: the records after parsing, the domain and geometry after transformation, and the visible marks after rendering. A chart can look plausible while silently dropping records or assigning the wrong scale. Inspect counts, IDs, finite coordinates and meaningful expected values before adjusting colors. A missing mark may come from invalid input, a missing selection, an undefined scale result or clipping outside the viewBox.

The controlled failure for this lesson is: Diagnose using a tree for a cyclic relationship graph. Its distinguishing evidence is The data model does not satisfy tree assumptions. Preserve that failing case when repairing your program. Do not remove an assertion or broaden a scale merely to hide a wrong input. Explain whether a changed value should affect the data, an encoding, a layout or only presentation.

## Accessibility and interpretation

Give the visualization a descriptive title and a short textual summary of the main result. Keep a table or list when exact values matter. Do not encode a critical category only through color; use labels, shapes or position as appropriate. Interactive controls need keyboard operation and clear focus, and motion should respect the user's reduced-motion preference. Automated DOM checks support, but do not replace, a real keyboard and assistive-technology review.

A data scientist must also defend the statistical meaning. State the population, units, aggregation, missing-value policy and uncertainty where relevant. Synthetic points illustrate a mechanism and do not establish a real-world finding. A beautiful visualization should make a valid claim easier to inspect, not make a weak claim appear certain.
