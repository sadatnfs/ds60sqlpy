js-027: Typed async workflows and errors#

Level and prerequisites#

Advanced, approximately 120 minutes. Direct prerequisites: js-026

Learning objectives#

Explain result channel, rejection channel, error translation, batch outcome policy with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Look up a known id and an absent id. The final task tests reject unresolved and unnarrowed access.

Purpose and mental model#

Promise<T> describes a fulfilled value. JavaScript rejection reasons are not captured by a second built-in error type parameter, so caught failures must still be inspected. Expected domain failures can instead be represented as a discriminated Result value. Unexpected operational failures may continue to reject. An API must explain which failure channel it uses, especially if it uses both.

Promise<Result<T>> introduces two decisions: await completion, then inspect the result. A failed Result is a fulfilled Promise containing an explicit failure value. It does not trigger catch. Conversely, a rejected Promise does not become a Result unless implementation code catches and translates it. Failing to distinguish these channels can turn an expected missing record into an unhandled rejection or turn a genuine programming error into misleading business data.

Cancellation remains a runtime cooperation protocol. A signal annotation proves that a compatible object was supplied, not that the operation observes it. The examples cancel a real timer and translate only its documented AbortError category. Batch operations must also choose whether to stop at the first rejection or retain every outcome. allSettled preserves outcome records, but rejected records must not be mistaken for valid values.

Vocabulary and concepts#

Result channel: An explicit success/failure value.

Rejection channel: A Promise failure propagated through throw or reject.

Error translation: Mapping a recognized failure into a documented result.

Batch outcome policy: The treatment of partial success and failure across several operations.

Syntax anatomy and execution trace#

A Result union carries either ok:true with value or ok:false with an error category. Narrow ok before reading the payload. An async function wraps a returned result in a Promise. Catch variables are unknown under strict checking. instanceof Error permits reading message, while matching a documented name or code determines whether translation is appropriate. Re-throw unrecognized failures to retain diagnosis.

Worked example / walkthrough#

Example A: Await and narrow a result#

Await establishes completion; the discriminant establishes domain success. Both conditions are needed before accessing the payload.

import { strict as assert } from 'node:assert';
import { setTimeout as delay } from 'node:timers/promises';

type Result<T> = { ok: true; value: T } | { ok: false; error: 'not_found' | 'cancelled' | 'operational' };
async function lookup(id: string): Promise<Result<number>> {
  return id === 'A' ? { ok: true, value: 7 } : { ok: false, error: 'not_found' };
}
async function waitForValue(signal: AbortSignal): Promise<Result<number>> {
  try {
    const value = await delay(1000, 7, { signal });
    return { ok: true, value };
  } catch (error: unknown) {
    if (error instanceof Error && error.name === 'AbortError') return { ok: false, error: 'cancelled' };
    throw error;
  }
}

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const present = await lookup('A');
    if (!present.ok) throw new Error(present.error);
    assert.equal(present.value, 7);
    assert.deepEqual(await lookup('missing'), { ok: false, error: 'not_found' });
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: known value 7; absent error not_found.

Example B: Show a failure result does not invoke catch#

A result value is ordinary fulfilled data even when it describes a domain failure. The caller must branch on it explicitly.

import { strict as assert } from 'node:assert';
import { setTimeout as delay } from 'node:timers/promises';

type Result<T> = { ok: true; value: T } | { ok: false; error: 'not_found' | 'cancelled' | 'operational' };
async function lookup(id: string): Promise<Result<number>> {
  return id === 'A' ? { ok: true, value: 7 } : { ok: false, error: 'not_found' };
}
async function waitForValue(signal: AbortSignal): Promise<Result<number>> {
  try {
    const value = await delay(1000, 7, { signal });
    return { ok: true, value };
  } catch (error: unknown) {
    if (error instanceof Error && error.name === 'AbortError') return { ok: false, error: 'cancelled' };
    throw error;
  }
}

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    let caught = 0;
    const result = await lookup('missing').catch(() => { caught += 1; return { ok: false as const, error: 'operational' as const }; });
    assert.equal(caught, 0);
    assert.deepEqual(result, { ok: false, error: 'not_found' });
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: catch count 0; result still not_found.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

  1. Reject unresolved and unnarrowed access. Demonstrate both errors in an uncalled compile-time check. Expected: expected diagnostics for value before await or before narrowing. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
