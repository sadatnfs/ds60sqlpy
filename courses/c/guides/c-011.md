# c-011: Scope, storage duration and object lifetime

## Level and prerequisites

Beginner, approximately 90 minutes plus a later retrieval session. Direct prerequisites: `c-010`

## Learning objectives

Distinguish scope from storage duration and return only addresses whose objects outlive the call. Along the way, explain scope, storage duration and reentrancy. Implement the six investigations, from the "trace block shadowing" case to the "transfer initialized aggregation" case, with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

Scope determines where a name is visible; lifetime determines when its object exists. They are related but different. An automatic local object usually lasts until its block ends. A static-storage object exists for the program duration even when its name is visible only inside one function. Allocated storage has a lifetime controlled by allocation and release, taught next. A pointer does not extend any of these lifetimes automatically. Returning an automatic local address is invalid after return, while returning a static object address can be valid but introduces shared mutable state and reentrancy concerns.

## Vocabulary and concepts

- **Scope:** The region where a name can be used.
- **Storage duration:** The category governing how long storage is retained.
- **Reentrancy:** Whether an operation can be entered again without corrupting shared execution state.

## Syntax anatomy and execution trace

A block can shadow an outer variable with the same name. static inside a function preserves one object across calls and zero-initializes it before execution. A file-scope static declaration also restricts linkage to the translation unit. These are different uses of the same keyword. Keep automatic variables explicitly initialized before reading them. Do not use the value of a pointer after its target lifetime has ended.

## Worked example / walkthrough

### Worked example 1: Trace block shadowing

Declare an outer value 3 and a separate inner value 7.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int next_count(void) {
  static int count = 0;
  count++;
  return count;
}
const int *static_value(void) {
  static const int value = 7;
  return &value;
}
int local_count(void) {
  int count = 0;
  count++;
  return count;
}

int main(void) {
  /* Trace block shadowing */
  {
    int value = 3;
    {
      int value = 7;
      CHECK(value == 7);
    }
    CHECK(value == 3);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** After the inner block, the outer remains 3.

The names are the same but designate distinct objects. Shadowing can be legal while still reducing readability.

### Worked example 2: Retain static state

Call a function with one static counter twice.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int next_count(void) {
  static int count = 0;
  count++;
  return count;
}
const int *static_value(void) {
  static const int value = 7;
  return &value;
}
int local_count(void) {
  int count = 0;
  count++;
  return count;
}

int main(void) {
  /* Trace block shadowing */
  {
    int value = 3;
    {
      int value = 7;
      CHECK(value == 7);
    }
    CHECK(value == 3);
  }

  /* Retain static state */
  {
    CHECK(next_count() == 1);
    CHECK(next_count() == 2);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** It returns 1 and then 2.

The counter is initialized once and survives function returns. This shared state would require synchronization if called concurrently.

### Exercise 1: Trace block shadowing: change one input

In worked example 1, change `int value = 3;` to `int value = 4;`. Predict which value the CHECK on `value == 3` sees, then run and restore.

**Expected:** `Check failed` at `value == 3`; restoring `int value = 3;` passes again.

**Verify:** Name the value that made `value == 3` false, where worked example 1 showed that after the inner block, the outer remains 3.

**Progressive hints:** First trace `value` from initialization. Then compute what the CHECK sees with `int value = 4;` in place.

### Exercise 2: Retain static state: diagnose an edited check

Worked example 2's CHECK now reads `CHECK(next_count() != 2);`. Explain why it fails although it returns 1 and then 2, then restore it.

**Expected:** `Check failed` until the CHECK reads `CHECK(next_count() == 2);` again, though it returns 1 and then 2.

**Verify:** Explain why `CHECK(next_count() != 2);` rejects a state that `next_count() == 2` accepts, using your failing and repaired runs.

**Progressive hints:** First work out what `next_count` returns here. Then compare `CHECK(next_count() != 2);` with worked example 2's original line.

### Exercise 3: Return a static address

Get a pointer to a static read-only value.

**Expected:** The target remains valid and equals 7.

**Verify:** Keep a CHECK equivalent to `*p == 7`. Control edit: `CHECK(*p != 7);` must fail; then restore it.

**Progressive hints:** First trace `p` from initialization. Then recall: The target lifetime spans the program. const restricts mutation through this pointer but does not make every static design automatically thread-safe.

### Exercise 4: Keep automatic state per call

Call a function with an initialized local counter twice.

**Expected:** Both calls return 1.

**Verify:** Keep a CHECK equivalent to `local_count() == 1 && local_count() == 1`. Control edit: `CHECK(local_count() != 1 && local_count() == 1);` must fail; then restore it.

**Progressive hints:** First work out what `local_count` returns here. Then recall: Each call creates a fresh automatic object.

### Exercise 5: Separate visibility from lifetime

Retain a value copy obtained from an inner block.

**Expected:** The copied scalar remains 9 afterward.

**Verify:** Keep a CHECK equivalent to `copy == 9`. Control edit: changing `int local = 9;` to `int local = 10;` must fail it; then restore it.

**Progressive hints:** First trace `copy` from initialization. Then recall: The scalar copy has its own lifetime.

### Exercise 6: Transfer initialized aggregation

Initialize an accumulator before processing an empty range.

**Expected:** The result is the defined zero identity.

**Verify:** Keep a CHECK equivalent to `total == 0`. Control edit: changing `int total = 0;` to `int total = 1;` must fail it; then restore it.

**Progressive hints:** First trace `total` from initialization. Then recall: Reading an uninitialized automatic accumulator would not be repaired by an empty loop.

## Common pitfalls and diagnosis

Assuming a `static` local resets on every call, or returning a pointer to an automatic local. Shadowing a name in an inner block hides the outer object without changing it, which reads like a mutation that never happened.
