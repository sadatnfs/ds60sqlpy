# dme-009: File ingestion, manifests and resumable delivery

**Level:** Intermediate | **Prepared runtime:** `data-engineering`

**Direct prerequisites:** `dme-002`, `dme-007`, `dme-008`.

**Outcome:** Ingest a declared CSV/JSON delivery with checksums and row reconciliation.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

## Accept a delivery under a declared contract

Receiving a file is not the same as accepting a dataset. A producer can deliver a truncated file, repeat a previously delivered batch, change a representation or supply records that conflict with accepted state. Ingestion connects those physical bytes to a declared logical population and a durable acceptance decision.

The example uses a small CSV delivery containing identified deliveries, numeric route IDs and positive package counts. The producer manifest names the batch, its exact byte digest, its expected row count and the reviewed transformation version. The consumer validates those properties before inserting records into an actual DuckDB database. The database stores both the accepted records and the batch receipt.

The ordinary pad uses an in-memory database and owned temporary files. Replaying a batch within that database is real idempotent behavior for this fixture. It does not establish restart persistence, because the database disappears when the program exits. A complete project must place its accepted state in the declared persistent location and test recovery against that actual location.

## Separate the identities

A **delivery identity** names a business record. A **batch identity** names a transfer or ingestion unit. A **content digest** names exact bytes. A **transformation identity** names the reviewed interpretation applied to those bytes. These identities serve different purposes and should not be substituted casually.

A repeated batch identity with the same accepted content and interpretation can be recognized as a replay. The same batch identity with different content is a conflict. A new batch containing an already accepted business identity may also be a conflict under an append-only model. It might instead represent a legitimate correction, but that requires a declared change-data or upsert contract. The next chapter on change events develops that different policy.

A filename alone is a weak identity. A producer might replace the contents of `deliveries.csv` while a consumer still assumes it is the old batch. A timestamp in a filename can help an operator, but it does not prove uniqueness, completeness or byte integrity. The manifest makes the chosen checks explicit and testable.

The transformation version is also checked, not merely copied into an audit table. This example accepts one reviewed parser/validation contract. It does not allow a caller to relabel unchanged execution as an arbitrary new transformation. A larger workflow should connect that version to its actual reviewed source and dependency identities, as discussed in the previous chapter.

## Parse text before treating it as typed data

CSV carries text fields under a delimiter, quoting and newline convention. The parser in this example expects a specific header and uses Python's real `csv.DictReader`. It validates row width and delivery identity, then accepts only the declared canonical positive-integer text forms for route and package fields. The explicit conversion to Python integers occurs after those representation checks.

These rules are intentionally narrow. A producer that uses different quoting, headers, integer representations or encodings needs a reviewed parser contract. Silently accepting every convenient representation can conceal a producer change. Conversely, rejecting a legitimate representation is a compatibility decision that should be discussed rather than blamed on the file format itself.

The reader bounds the actual byte read before parsing, rather than loading an arbitrarily large file and checking its size afterward. The manifest also bounds the expected row count for this teaching fixture. A real large-file system would use streaming or partitioned ingestion under explicit resource controls; increasing this small bound is not by itself a scalable architecture.

A matching digest confirms agreement with the expected byte identity. It does not prove that the producer's expected row count is a true description of the business population. That declaration needs its own source and ownership. The consumer can check whether the received file matches the declaration, while remaining honest about that trust boundary.

## Put accepted records and receipts in one transaction

The consumer first validates the file and derives typed rows. It then checks whether the batch has already been accepted under the same content and transformation identity. A matching receipt returns `already-applied`; a conflicting identity is rejected.

For a new batch, the consumer begins an actual DuckDB transaction. It inserts the delivery rows and the acceptance receipt, then commits. If a constraint or another error prevents completion, it rolls back. This connects the effect and the receipt within one database transaction. Recording the receipt before an unrelated effect, or committing the rows separately from the receipt, would create different failure windows.

The contract is append-only for business delivery identities. The table's primary key therefore protects previously accepted deliveries from an accidental conflicting insert. Database constraints complement the earlier parsing checks: a syntactically valid file can still conflict with existing accepted state.

A declared empty batch can be valid when its complete header, digest and expected row count agree. The ingestion function avoids calling `executemany` with an empty parameter collection and can record such a batch explicitly. An empty result obtained because an upstream request failed is a different situation. Do not infer business emptiness from missing data or missing status.

## Worked case 1: Accept once, then reconcile a replay

The first case writes three CSV rows for deliveries A, B and C, with package counts two, three and one. It constructs the corresponding manifest and calls the consumer. The first result is `accepted`. The second call uses the same batch, bytes and transformation identity, and returns `already-applied`.

The actual table still has three rows and six packages. The independent reconciliation is

\[
N_{\mathrm{accepted}}=3,
\qquad
T=2+3+1=6.
\]

The second invocation does not add another six packages. This matters when a caller is uncertain whether an earlier attempt completed. Before repeating an effect, the consumer can consult an identified accepted receipt. This is a local transactional example; a remote service or broker would need a corresponding actual recovery contract and tests.

The consumer does not label every repeated business identity a replay. Reusing a batch identity with different bytes or a different interpretation is a conflict. Repeating a delivery ID in another append-only batch is also not automatically safe. The identities and their scopes must match the intended operation.

## Worked case 2: Reject corrupted, incomplete and conflicting deliveries

The changed case first accepts the valid batch. It then truncates the file while retaining the old manifest. The byte digest no longer matches, so the consumer rejects the candidate before it can reuse the accepted receipt or alter the database.

Next, the case creates a new file whose digest is valid but whose declared expected population is wrong. The file contains one row, while its manifest claims two. The row-count check rejects it. This distinguishes byte integrity from population reconciliation: a checksum alone cannot prove that a file contains all declared records.

Finally, a two-row candidate first inserts a new delivery D and then conflicts with the already accepted delivery A. The actual database constraint raises an error. The transaction rollback removes the candidate's partial effect, so the accepted table still contains only A, B and C, and the batch-receipt table still contains only the original accepted batch.

That final check is important. Looking only for the expected exception would not prove that the earlier insert was undone. The program reads back the accepted identities and receipt count after failure. It verifies the state the next consumer would observe.

## Complete worked program

```python
"""Actual CSV delivery validation and transactional DuckDB ingestion."""

import csv
import hashlib
import io
import re
import tempfile
from pathlib import Path

import duckdb


def delivery(path, batch_id, text, expected_rows):
    raw = text.encode("utf-8")
    path.write_bytes(raw)
    return {
        "batch_id": batch_id,
        "sha256": hashlib.sha256(raw).hexdigest(),
        "expected_rows": expected_rows,
        "transform": "positive-package-csv-v1",
    }


def database():
    connection = duckdb.connect(":memory:")
    connection.execute(
        "create table deliveries(delivery_id varchar primary "
        "key, route_id integer, packages "
        "integer)"
    )
    connection.execute(
        "create table batches(batch_id varchar primary key, input_sha varchar, transform varchar)"
    )
    return connection


def ingest(connection, path, manifest):
    if (
        not isinstance(manifest, dict)
        or set(manifest) != {"batch_id", "sha256", "expected_rows", "transform"}
        or not isinstance(manifest["batch_id"], str)
        or not manifest["batch_id"].strip()
        or type(manifest["expected_rows"]) is not int
        or not 0 <= manifest["expected_rows"] <= 100
        or manifest["transform"] != "positive-package-csv-v1"
    ):
        raise ValueError("Use this bounded, versioned delivery contract")
    with path.open("rb") as stream:
        raw = stream.read(4097)
    if len(raw) > 4096 or hashlib.sha256(raw).hexdigest() != manifest["sha256"]:
        raise ValueError("Delivery bytes do not match the bounded manifest")
    reader = csv.DictReader(io.StringIO(raw.decode("utf-8"), newline=""))
    if reader.fieldnames != ["delivery_id", "route_id", "packages"]:
        raise ValueError("Unexpected CSV header contract")
    rows = []
    for record in reader:
        if set(record) != {"delivery_id", "route_id", "packages"} or any(
            value is None for value in record.values()
        ):
            raise ValueError("Unexpected row width")
        if not record["delivery_id"].strip():
            raise ValueError("Missing delivery identity")
        if any(
            re.fullmatch(r"[1-9][0-9]*", record[name]) is None for name in ("route_id", "packages")
        ):
            raise ValueError("Declared numeric text must be a canonical positive integer")
        rows.append((record["delivery_id"], int(record["route_id"]), int(record["packages"])))
    if len(rows) != manifest["expected_rows"]:
        raise ValueError("Delivery row count differs from its declared population")
    existing = connection.execute(
        "select input_sha, transform from batches where batch_id=?", [manifest["batch_id"]]
    ).fetchone()
    identity = (manifest["sha256"], manifest["transform"])
    if existing is not None:
        if existing != identity:
            raise ValueError("An accepted batch identity cannot name different input or logic")
        return "already-applied"
    connection.execute("begin transaction")
    try:
        if rows:
            connection.executemany("insert into deliveries values (?, ?, ?)", rows)
        connection.execute(
            "insert into batches values (?, ?, ?)", [manifest["batch_id"], *identity]
        )
        connection.execute("commit")
    except Exception:
        connection.execute("rollback")
        raise
    return "accepted"


def example_one():
    with tempfile.TemporaryDirectory() as directory, database() as connection:
        path = Path(directory) / "delivery.csv"
        manifest = delivery(
            path, "batch-a", "delivery_id,route_id,packages\nA,10,2\nB,10,3\nC,20,1\n", 3
        )
        first = ingest(connection, path, manifest)
        replay = ingest(connection, path, manifest)
        rows, packages = connection.execute(
            "select count(*),sum(packages) from deliveries"
        ).fetchone()
        assert (first, replay, rows, packages) == ("accepted", "already-applied", 3, 6)
        return {"first": first, "replay": replay, "accepted_rows": rows, "packages": packages}


def example_two():
    with tempfile.TemporaryDirectory() as directory, database() as connection:
        path = Path(directory) / "delivery.csv"
        good = delivery(
            path, "batch-a", "delivery_id,route_id,packages\nA,10,2\nB,10,3\nC,20,1\n", 3
        )
        ingest(connection, path, good)
        path.write_bytes(path.read_bytes()[:-4])
        try:
            ingest(connection, path, good)
        except ValueError:
            checksum_rejected = True
        else:
            raise AssertionError("Changed input must not reuse the old delivery receipt")
        short = delivery(path, "batch-b", "delivery_id,route_id,packages\nD,20,4\n", 2)
        try:
            ingest(connection, path, short)
        except ValueError:
            population_rejected = True
        else:
            raise AssertionError("A matching byte hash cannot prove declared row completeness")
        conflict = delivery(path, "batch-c", "delivery_id,route_id,packages\nD,20,4\nA,10,9\n", 2)
        try:
            ingest(connection, path, conflict)
        except duckdb.ConstraintException:
            transaction_rejected = True
        else:
            raise AssertionError("The existing delivery identity must not be overwritten")
        identities = connection.execute(
            "select delivery_id from deliveries order by delivery_id"
        ).fetchall()
        assert identities == [("A",), ("B",), ("C",)]
        assert connection.execute("select count(*) from batches").fetchone() == (1,)
        return {
            "checksum_rejected": checksum_rejected,
            "population_rejected": population_rejected,
            "transaction_rejected": transaction_rejected,
            "retained_accepted_ids": identities,
        }


def main():
    print("Validated actual ingestion and replay:", example_one())
    print("Bad deliveries do not replace accepted state:", example_two())


if __name__ == "__main__":
    main()
```

## Diagnose ingestion failures by boundary

A digest mismatch concerns received bytes and the expected delivery identity. A row-count mismatch concerns the declared population. A parser failure concerns representation. A type or value failure concerns the interpreted record contract. A uniqueness violation concerns the relationship between candidate and accepted identities. These failures need different remedies.

Do not make a failed candidate pass by silently updating the manifest or dropping a conflicting record. Investigate whether the producer changed, the transfer was incomplete, the batch was replayed, or the business operation is actually a correction. Retain bounded diagnostics and the appropriate source identity so the problem can be reproduced without copying sensitive payloads indiscriminately.

A receipt in the wrong store is also a warning sign. If the effect and acceptance marker cannot commit together, define how to reconcile their disagreement. Later chapters examine the outbox pattern and unknown outcomes across system boundaries.

## Where this is useful

This pattern applies to scheduled file drops, analytical exports, training data snapshots and batch API extraction. The implementation can move to a different engine, but the producer declaration, identity policy, acceptance transaction and failure readback remain necessary design questions.

## Answered interview discussion

**What does idempotent ingestion mean here?** Repeating the same identified accepted batch does not apply its records again. It does not mean all arbitrary repeated commands are safe, or that different payloads sharing an ID should be accepted.

**Why store a batch receipt with the data?** It allows the consumer to reconcile whether the effect was accepted. One transaction prevents the demonstrated partial-insert failure from leaving a misleading success receipt or an unrecorded accepted effect.

**Is a checksum enough to prove completeness?** It checks exact bytes against an expected identity. Completeness also depends on a population declaration and evidence about the producer's collection process.

**How would you support corrections?** Define the business/version identity and update semantics explicitly. An append-only primary-key failure should not be replaced with an unconditional overwrite merely to make an ingestion job finish.
