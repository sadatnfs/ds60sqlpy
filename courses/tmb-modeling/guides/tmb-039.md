# Benchmarking explicit and automatic parallelism

Start with: tmb-038, tmb-020.

Outcome: Measure a named operation while keeping thread policy and numerical correctness visible.

The classroom companion runs in the prepared R statistics runtime. It uses base R to expose the mathematics or data contract. Compiling and executing TMB uses the separate [owned project](../projects/tmb-local/README.md); a companion run is not a TMB compiler or rpy2 receipt.

`benchmark(obj, n=10, expr=NULL, cores=NULL)` measures selected model operations across thread counts. Its `plot.parallelBenchmark` method can display speedup or elapsed time. A timing object is evidence about a particular environment, input and operation, not a universal claim that C++ or more threads are faster.

The default benchmark distinguishes objective, gradient and sparse-Hessian/factorization work where applicable. A custom expression can time another operation. Record whether compilation, tape construction, data conversion and cold-start loading are included or excluded. Comparing a warm gradient to a cold end-to-end script exaggerates speedup.

### Worked case A: speedup and efficiency

The companion uses an explicitly hypothetical timing table and computes speedup \(T_1/T_p\) and efficiency \(T_1/(pT_p)\). It labels the table as an arithmetic illustration, not a machine benchmark. A real run should retain repeated measurements, input sizes and the exact expression.

`openmp(n, DLL=...)` controls a model library's OpenMP threads. It does not control every BLAS/LAPACK thread pool. `max=TRUE` depends on the configured environment and platform. For a reproducible benchmark, use explicit small counts and record native and BLAS settings separately.

### Worked case B: automatic parallelization is a different mode

`openmp(autopar=TRUE)` is experimental, requires TMBad and an OpenMP-enabled compile, and can supersede explicit parallel constructs according to the manual. Compare its value and gradient to a serial reference before measuring speed. The existing CppAD `parallel_accumulator` receipt does not qualify this automatic mode.

The companion uses Amdahl's law to show how a serial fraction limits ideal speedup. Real workloads add scheduling, memory-bandwidth and cache effects. For a small objective, overhead can dominate useful arithmetic, so a slower two-thread run may be the expected result rather than a bug.

Timer resolution also matters. A two-evaluation probe of the four-row Gaussian model produced zero elapsed times, making relative-speedup plotting undefined. The bounded API probe therefore uses 10,000 tiny evaluations per timed operation so its plotting input is measurable. This is a timing-resolution fix, not a claim that the workload became more representative or that one thread is faster than another.

### Answered discussion

**Can I benchmark with all available threads inside every Spark task?** That can oversubscribe the executor. Allocate concurrency across layers first. **Should I report the fastest single run?** Prefer a defined statistic across repeats and explain variability. **Can a plot establish numerical correctness?** No. Keep parity tests and timing receipts separate, and never disable failure checks solely to improve the chart.

See [benchmark and openmp](https://cran.r-project.org/web/packages/TMB/TMB.pdf). The project qualifies actual one/two-thread explicit-accumulator parity; measured speed and automatic parallelization require their own evidence.

### Complete R companion

```r
threads <- c(1, 2, 4);illustrative_seconds <- c(1, .62, .48)
print(data.frame(kind = "hypothetical arithmetic", threads = threads, seconds = illustrative_seconds, speedup = illustrative_seconds[1] / illustrative_seconds, efficiency = illustrative_seconds[1] / (threads * illustrative_seconds)))
serial_fraction <- .25
print(data.frame(threads = threads, ideal_amdahl_speedup = 1 / (serial_fraction + (1 - serial_fraction) / threads)))
stopifnot(1 / serial_fraction == 4)
```
