# k8s-064: A packet-path troubleshooting method from DNS to response

## Level and prerequisites

Advanced; about 120 minutes. Direct prerequisites: `k8s-063`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Build a three-hypothesis table for Service failure.
- Perform a single-fault incident walkthrough.

## Purpose, vocabulary and mental model

Troubleshooting is a sequence of discriminating observations. Start with the caller, intended name, protocol, port and expected application result. Then identify the first layer where actual behavior differs from the model. Changing several layers at once can make the symptom disappear without explaining the cause.

A useful request ladder separates name resolution, route reachability, transport connection, TLS identity, proxy routing and application semantics. Kubernetes adds controller and endpoint state that helps explain those steps. A successful test at one layer should not be promoted into a claim about every later layer.

Controlled comparisons are powerful. If direct Pod traffic succeeds but Service traffic fails, focus on selector/endpoints/data-plane differences. If an internal Service request succeeds but external traffic fails, inspect the external listener and routing path. Each comparison requires the same intended application and an owned permitted probe.

### Key terms

- **Request ladder:** An ordered set of checks for name resolution, route reachability, transport connection, TLS identity, proxy routing and application semantics.
- **Controlled comparison:** Changing one variable between two otherwise identical requests, so a difference in outcome points to that variable.
- **First failing layer:** The first rung of the request ladder where actual behavior differs from the model, which is where diagnosis should focus.
- **Layer-scoped evidence:** A successful test proves only its own layer, so it cannot be promoted into a claim about every later layer.

## Mechanism and field-by-field reasoning

Use a hypothesis table with expected observation if true, expected observation if false and the smallest safe check. Preserve the failure before repair. Avoid broad all-namespace commands and packet captures when an exact field or short request answers the question.

A timeout is ambiguous: it can involve dropped packets, no route, DNS delay, a stalled TLS handshake or an application that never responds. A refused connection, TLS error and HTTP status narrow the phase differently. Read the actual diagnostic rather than translating every failure into service down.

## Trace the request or control path

```text
name -> DNS answer -> route -> TCP connect -> TLS -> proxy rule -> app handler -> expected body
parallel control evidence: Service selector -> EndpointSlices -> Pod readiness/revision
```

The first line is a ladder: each rung must work before the next can even be tested, so localize by finding the highest rung that succeeds. The second line runs in parallel and explains ladder failures; an empty EndpointSlice, for example, explains a failed connect. Climb with bounded probes, one hypothesis at a time.

## Worked example / walkthrough

### Worked example 1: Compare two paths

The synthetic probes use the same app revision.

```text
PodIP:8080 succeeds
ClusterIP:80 fails
next: inspect Service targetPort, eligible endpoints and node data plane
```

**Expected observation:** The application listener is less likely to be the first failing component.

### Worked example 2: Write a falsifiable hypothesis

A useful hypothesis predicts a distinct observation.

```text
hypothesis: Service selector matches no Pods
if true: matching Pod set and ready endpoints are empty
if false: investigate port mapping or data plane next
```

**Expected observation:** The proposed read can disprove the hypothesis without changing the system.

## Six progressive exercises

### Exercise 1: Order the request ladder.

**Expected evidence:** DNS, route, transport, optional TLS, proxy/application route and body.

**Progressive hint:** Each rung needs the one below it. Start from the name and finish at the body.

### Exercise 2: Interpret connection refused versus timeout.

**Expected evidence:** Refusal narrows listener/connectivity behavior; timeout remains broader.

**Progressive hint:** A refusal means something answered with a reset; a timeout means nothing answered. Which narrows the location more?

### Exercise 3: Build a three-hypothesis table for Service failure.

**Expected evidence:** Selector, targetPort and data-plane hypotheses each have distinct evidence.

**Progressive hint:** One row per hypothesis, each with the read that would prove it wrong. Keep the reads separate.

### Exercise 4: Diagnose internal success with external failure.

**Expected evidence:** Inspect the added external listener/routing/TLS layers.

**Progressive hint:** Internal requests work, so Service, endpoints and app are fine. Which layers does the external path add?

### Exercise 5: Explain why a stale successful receipt is insufficient.

**Expected evidence:** It may belong to another revision, namespace or caller path.

**Progressive hint:** Which revision, namespace and caller produced the old receipt, and has any of them changed?

### Exercise 6: Perform a single-fault incident walkthrough.

**Expected evidence:** One controlled fault, preserved failure, targeted repair and rechecked invariant.

**Progressive hint:** Break one thing on purpose, preserve the failure, repair only that, then recheck the original invariant.

## Diagnosis, failure boundaries and common mistakes

The biggest troubleshooting mistake is changing several things at once. Restarting Pods, editing the Service and widening a policy together leaves no way to know what fixed it, or what new problem appeared. Change one thing per hypothesis. Another is skipping rungs: if DNS fails, no amount of reading app logs helps. Watch for stale proof as well; a success from yesterday's revision or another namespace says nothing about today's path. Write each hypothesis so a single read can falsify it before any repair.

Before concluding, record:

- The highest ladder rung that succeeded and the first that failed, from DNS answer to expected body.
- Refused versus timed out for a failing connect, since refusal narrows the search and a timeout does not.
- The parallel control reads: selector match, EndpointSlice addresses and readiness for the current revision.
- One hypothesis per change, with the read that could disprove it and the result after the change.

General evidence rules: [diagnosis rules](../STUDY-GUIDE.md#diagnosis-rules).
