## Why this mechanism matters

Labels attach identity and grouping information to objects. A selector expresses a membership rule, not an ownership proof. A Service selects matching Pods and exposes a stable service abstraction while actual endpoints change. Pods with the same labels can still belong to different controllers, and a broad selector can unintentionally combine workloads. Namespace scope, readiness and EndpointSlice state also affect usable service endpoints. This lesson models equality selectors and readiness filtering with tiny records. It does not emulate kube-proxy, DNS or packet routing; those mechanisms are taught and exercised in the Kubernetes networking path.

## Vocabulary and concepts

- **Label:** A key/value pair used to organize and select objects.
- **Selector:** A predicate identifying matching objects.
- **Endpoint readiness:** Whether a selected backend is eligible to serve traffic.

## Syntax anatomy and reasoning

A map of required label pairs represents an AND of equality tests in this small model. Missing and empty-valued labels must be distinguished with comma-ok. Kubernetes additionally supports set-based selectors and API-specific selector forms. Stable application identity should be separate from rollout-specific labels when a Service must survive Deployment replacement. Never use label matching alone as permission to delete an object.

## Worked example / walkthrough

### Worked example 1: Match all required labels

Match app=web and tier=frontend against a Pod containing both.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type PodView struct {
	Labels map[string]string
	Ready  bool
}

func matches(labels, selector map[string]string) bool {
	for k, want := range selector {
		got, ok := labels[k]
		if !ok || got != want {
			return false
		}
	}
	return true
}

func main() {
	// Match all required labels
	{
		check(matches(map[string]string{"app": "web", "tier": "frontend"}, map[string]string{"app": "web", "tier": "frontend"}), "match")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The selector matches.

All selector pairs must match. Treating the requirements as OR would admit unintended workloads.

### Worked example 2: Reject a missing label

Require tier when the Pod has only app.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type PodView struct {
	Labels map[string]string
	Ready  bool
}

func matches(labels, selector map[string]string) bool {
	for k, want := range selector {
		got, ok := labels[k]
		if !ok || got != want {
			return false
		}
	}
	return true
}

func main() {
	// Match all required labels
	{
		check(matches(map[string]string{"app": "web", "tier": "frontend"}, map[string]string{"app": "web", "tier": "frontend"}), "match")
	}

	// Reject a missing label
	{
		check(!matches(map[string]string{"app": "web"}, map[string]string{"app": "web", "tier": "frontend"}), "missing")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The selector does not match.

A missing required key is not a wildcard. Presence is part of the equality contract.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
