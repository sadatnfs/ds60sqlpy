# MakeADFun values and gradients

Start with: tmb-005, torch-005.

Outcome: Compare automatic derivatives against an analytic and numerical oracle.

The classroom companion runs in the prepared R statistics runtime. It uses base R to expose the mathematics or data contract. Compiling and executing TMB uses the separate [owned project](../projects/tmb-local/README.md); a companion run is not a TMB compiler or rpy2 receipt.

`MakeADFun` constructs a model object whose `par` contains the initial fixed coordinates, `fn` evaluates the objective and `gr` evaluates its gradient. With random effects, `fn` is usually the Laplace-approximated marginal objective. Without them, it is the C++ scalar objective. Always state which target is being differentiated.

For the normal model with \(s=\log\sigma\), define \(r_i=y_i-\mu\) and \(S=\sum_i r_i^2\). Then

\[
\frac{\partial f}{\partial\mu}=-e^{-2s}\sum_i r_i,
\qquad \frac{\partial f}{\partial s}=n-e^{-2s}S.
\]

These formulas provide an independent oracle. An AD gradient is exact for the implemented elementary operations up to floating-point effects, but that does not establish that the implemented objective matches the intended likelihood.

### Worked case A: central differences at an ordinary point

The companion checks both gradient components at \((\mu,s)=(2.2,0.3)\). A central difference estimates component \(j\) by \([f(\theta+h e_j)-f(\theta-h e_j)]/(2h)\). It requires two evaluations per parameter. Compare over several step sizes, not a single magic tolerance. Truncation dominates large steps; cancellation and rounding dominate very small steps.

```r
obj <- make_objective("normal_mean", list(y = c(1, 2, 4, 7)),
                      list(mu = 2.2, log_sigma = .3))
cbind(ad = obj$gr(obj$par), numerical = finite_gradient(obj$fn, obj$par))
```

`finite_gradient` is defined in the project acceptance script. This project fragment requires a compiled library. The companion implements its own base-R oracle so the formula can be studied immediately.

### Worked case B: check away from the optimum

At a fitted optimum both a correct and an accidentally zero gradient can appear small. Repeat the check at a clearly displaced mean and scale. A wrongly detached parameter or an omitted likelihood term becomes easier to detect. Also permute the proposed parameter vector deliberately and inspect the names returned by the API; a gradient with the right length but the wrong coordinate order is unusable.

For a random-effect model, finite differences must let the inner latent optimizer converge at each perturbed fixed vector. Otherwise they compare different levels of inner approximation noise. Use a fixed deterministic dataset, tight justified inner tolerances, and record failures. Do not force a finite-difference agreement by making the tolerance so large that meaningful errors disappear.

### Diagnostics and answered discussion

**Why check values before gradients?** Two functions can have identical gradients but different constants, and normalization constants matter for integration. **Can I compare gradients in different parameterizations?** Only after applying the chain rule. A gradient with respect to sigma is not a gradient with respect to log sigma. **What about non-smooth branches?** Branches on fixed data can encode observation types. Parameter-dependent branches and clipping require careful treatment; a tape can represent one branch's operations without resolving the intended non-smooth mathematics.

Read the [TMB theory paper](https://arxiv.org/abs/1509.00660) for how derivative calculations support both likelihood optimization and Laplace approximations.

### CppAD and TMBad are implementation choices, not different statistical targets

TMB 1.9.25 supports `framework="CppAD"` and `framework="TMBad"` at compilation. This project qualifies CppAD first. A framework change rebuilds the template; changing an R option after a library is already compiled does not rewrite its native implementation. Both frameworks should agree on the same supported objective and derivatives within numerical tolerance, but features and resource costs differ.

The `intern=TRUE` MakeADFun path places more of the Laplace calculation inside AD machinery and requires TMBad. Differentiating a Laplace approximation can require higher derivatives of the joint objective; some special functions need a sufficiently high `max.order` at compilation. The current manual describes up to fourth-order requirements for a Hessian of an internally differentiated Laplace approximation. Raising this setting blindly increases compilation cost and binary size. Choose it for the actual derivative target and verify a tiny oracle first. This course does not claim that the unexecuted TMBad variant passed because its CppAD variant passed.

### Complete R companion

```r
y <- c(1, 2, 4, 7)
fn <- function(p) -sum(dnorm(y, p[1], exp(p[2]), log = TRUE))
gr <- function(p) c(sum(p[1] - y) / exp(2 * p[2]), length(y) - sum((y - p[1])^2) / exp(2 * p[2]))
central <- function(p, h) vapply(seq_along(p), function(j) {
  a <- b <- p; a[j] <- a[j] + h; b[j] <- b[j] - h
  (fn(a) - fn(b)) / (2 * h)
}, numeric(1))
for (p in list(c(2.2, .3), c(-1, 1))) {
  errors <- vapply(c(1e-2, 1e-4, 1e-6), function(h) max(abs(central(p, h) - gr(p))), numeric(1))
  print(errors)
  stopifnot(errors[2] < 1e-5)
}
```
