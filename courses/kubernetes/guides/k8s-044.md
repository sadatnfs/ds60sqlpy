## Purpose, vocabulary and mental model

CIDR notation combines an address with a prefix length, such as 10.244.0.0/16. The prefix describes which leading bits identify the network. A longer prefix describes a smaller address set. CIDR membership is a binary relationship, not a string-prefix test.

Clusters need address planning for nodes, Pods and Services, and may interact with a host LAN, VPN or cloud network. Overlapping ranges can make a destination ambiguous or route traffic to the wrong place. A configuration can be valid YAML while its network plan is unusable in the actual environment.

Pod and Service CIDRs serve different purposes. Pod ranges allocate workload endpoints according to the CNI and cluster design. Service ranges allocate virtual service destinations. A Service IP should not be assumed to appear as an ordinary Pod interface address. Dual-stack adds another family of addresses and routes rather than replacing these distinctions.

### Key terms

- **CIDR notation:** Writing an address block as a prefix and length, such as 10.0.0.0/16, where the length counts the fixed leading bits.
- **Subnet:** A contiguous address block within a larger range, such as the Pod range assigned to one node.
- **Most specific route:** When several routes match a destination, the one with the most specific matching prefix is chosen.
- **Address overlap:** Two ranges that share addresses, which makes it ambiguous where a packet should go.
- **Service CIDR:** The address range from which ClusterIPs are allocated, which must not overlap Pod or node ranges.

## Mechanism and field-by-field reasoning

Use an IP-address library for membership and overlap reasoning. In a/24 IPv4 network there are 256 numeric addresses, but usable allocations depend on the system’s rules and reservations. Do not turn the arithmetic count into a guaranteed Kubernetes capacity claim.

A routing table chooses a next hop according to destination and policy, commonly preferring the most specific matching prefix. An overlapping VPN route can affect traffic before it reaches a cluster component. Investigate the caller’s route context rather than changing Kubernetes selectors to fix a host routing conflict.

## Trace the request or control path

```text
caller destination -> routing lookup -> most specific applicable route -> next hop
address plan: node network | Pod CIDR | Service CIDR | host/VPN ranges
```

The first line is the decision every sender makes: compare the destination with the routing table and let the longest matching prefix win. The second line lists the ranges that must never compete in that lookup. If a host or VPN route covers part of 10.244.0.0/16, the more specific route can carry traffic away before any Kubernetes component sees it.

## Worked example / walkthrough

### Worked example 1: Check membership using the standard library

This is an offline calculation.

```python
from ipaddress import ip_address, ip_network

network = ip_network("10.244.0.0/16")
print(ip_address("10.244.1.7") in network)
print(ip_address("10.96.0.20") in network)
```

**Expected observation:** True, then False; no packet is sent.

### Worked example 2: Detect an overlap

A more specific prefix can still overlap a broader one.

```python
from ipaddress import ip_network

print(ip_network("10.0.0.0/8").overlaps(ip_network("10.244.0.0/16")))
```

**Expected observation:** True; address planning must account for both ranges.

## Six progressive exercises

### Exercise 1: Predict Pod-IP membership in the fixture CIDR.

**Expected evidence:** 10.244.1.7 belongs to 10.244.0.0/16.

**Progressive hint:** Write the /16 as its first and last address. Membership is just whether 10.244.1.7 falls between them.

### Exercise 2: Compare/16 and/24 address set sizes.

**Expected evidence:** The/24 is the smaller, more specific network.

**Progressive hint:** Each extra prefix bit halves the set. Count the bits between /16 and /24 before computing sizes.

### Exercise 3: Build a nonoverlapping synthetic address-plan table.

**Expected evidence:** Node, Pod and Service ranges plus host/VPN ranges are compared.

**Progressive hint:** List every range a packet from your laptop might match, including ones Kubernetes never mentions, such as a home router.

### Exercise 4: Diagnose a VPN route overlapping the Pod range.

**Expected evidence:** The caller can select an unintended route before cluster delivery.

**Progressive hint:** Longest prefix match picks the route. Compare the VPN prefix length with the cluster route for the same destination.

### Exercise 5: Explain why 256 addresses do not guarantee 256 allocatable endpoints.

**Expected evidence:** Reservation and implementation rules reduce or constrain allocation.

**Progressive hint:** Network and broadcast addresses, per-node slicing and max-pods settings all come out of the same block.

### Exercise 6: Defend an address plan for a second local cluster.

**Expected evidence:** Ranges and routes avoid collisions with the first cluster and host networks.

**Progressive hint:** Put the first cluster's ranges beside the proposed ones and check every pair, not only Pod against Pod.

## Diagnosis, failure boundaries and common mistakes

Overlap problems rarely look like routing problems. When a VPN on the host installs a route that covers the Pod or Service range, tools on the host that reach into a local cluster send packets into the tunnel instead, while everything inside the cluster keeps working, so people blame the Service or the app. The opposite mistake is assuming a /24 per node gives 256 usable Pods; reserved addresses, the plugin's allocation scheme and the kubelet's max-pods setting all reduce that. Also avoid checking membership by eye on string prefixes: 10.244.1.7 and 10.24.41.7 look alike and only one is inside 10.244.0.0/16. Compute with ipaddress, and keep the result next to the exact range you tested.
