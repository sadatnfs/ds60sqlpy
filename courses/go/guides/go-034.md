# go-034: Build targets, containers and graceful process design

## Why this mechanism matters

An executable is built for a target operating system and architecture. Source portability does not imply one binary runs everywhere. Go can cross-compile many pure-Go programs by choosing GOOS and GOARCH, while cgo and platform-specific dependencies introduce additional constraints. Container images package the executable and its runtime files, but still depend on a compatible kernel and architecture. A small image is useful only if certificates, time-zone needs and diagnostic requirements remain satisfied. Production shutdown must stop accepting new work, cancel or drain owned tasks within a budget, and report incomplete work honestly.

## Vocabulary and concepts

- **Build target:** The operating system and architecture selected for a binary.
- **Multi-stage build:** A build separating toolchain and runtime filesystem stages.
- **Graceful shutdown:** A bounded transition from accepting work to releasing owned resources.

## Syntax anatomy and reasoning

runtime.GOOS and GOARCH describe the running binary target. Build configuration uses environment variables before compilation, not source-level guesses. A multi-stage Dockerfile can compile in a toolchain image and copy the binary into a runtime stage. CGO_ENABLED=0 is appropriate for this standard-library classroom profile; it is not a universal instruction for every dependency. Use an exec-form container entrypoint so the process receives termination signals directly.

## Worked example / walkthrough

### Worked example 1: Inspect the current target

Read runtime target identifiers.

```go
package main

import (
	"fmt"
	"runtime"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type ServiceState struct {
	Accepting bool
	Active    int
}

func main() {
	// Inspect the current target
	{
		check(runtime.GOOS != "" && runtime.GOARCH != "", "target")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** Both identifiers are nonempty.

The values describe this executed binary. They do not establish compatibility with another platform.

### Worked example 2: Validate a supported deployment tuple

Check linux/amd64 and linux/arm64 against an explicit target set.

```go
package main

import (
	"fmt"
	"runtime"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type ServiceState struct {
	Accepting bool
	Active    int
}

func main() {
	// Inspect the current target
	{
		check(runtime.GOOS != "" && runtime.GOARCH != "", "target")
	}

	// Validate a supported deployment tuple
	{
		allowed := map[string]bool{"linux/amd64": true, "linux/arm64": true}
		check(allowed["linux/amd64"] && allowed["linux/arm64"], "targets")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** Both tuples are admitted.

A declared target set is a configuration contract. Each image architecture still needs real build and execution evidence.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
