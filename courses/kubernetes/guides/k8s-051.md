# k8s-051: NodePort and the path through a node

## Level and prerequisites

Intermediate; about 120 minutes. Direct prerequisites: `k8s-050`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Draw the local-engine NodePort path.
- Compare NodePort with a deliberate loopback port-forward.

## Purpose, vocabulary and mental model

A NodePort Service allocates a port from the cluster’s configured NodePort range and makes the Service available through relevant node addresses according to the data-plane configuration. It usually also has a ClusterIP. A client addresses nodeIP:nodePort, and traffic is directed to an eligible backend.

A node address must actually be reachable from the client. Desktop cluster nodes may be containers or VMs behind additional network boundaries. A valid NodePort allocation does not automatically open a host firewall, publish a VM port or create an internet route. Local and cloud setups therefore have different external paths.

The commonly seen range 30000 through 32767 is a default, not a universal constant. Explicit allocations must fit the configured range and avoid collisions. Do not expose a teaching service publicly just to make a diagram seem more realistic.

### Key terms

- **NodePort Service:** A Service type that opens the same port on every node and forwards it to the Service's backends.
- **NodePort range:** The range from which node ports are allocated, 30000 through 32767 by default.
- **Node address:** The node IP a client must reach to use a NodePort, which may be private and unreachable from outside.
- **External reachability:** Whether a client outside the cluster can actually route to a node address and port through every firewall on the path.

## Mechanism and field-by-field reasoning

Read port as the ClusterIP-facing Service port, targetPort as the Pod listener and nodePort as the node-facing port. The application still listens at its target endpoint. externalTrafficPolicy can affect endpoint selection and source address behavior, covered in a later chapter.

The example uses nodePort 30080 only in a manual fixture. The ordinary classroom adapter does not admit this wider networking operation. A local kind setup needs deliberately prepared port mappings or another supported access route before host-browser acceptance is possible.

## Trace the request or control path

```text
external client -> reachable nodeIP:30080 -> Service data plane -> PodIP:8080
internal client -> ClusterIP:80 -> same logical Service -> eligible Pod
```

Two entry points share one logical Service. The external line enters at a node address and node port, and that node's data plane forwards to any ready Pod, possibly on another node. The internal line never touches 30080. Both end at the Pod listener 8080. When a laptop request times out, check the first arrow, reaching the node, before anything inside the cluster.

## Worked example / walkthrough

### Worked example 1: Read all three ports

This is a manual-only Service fragment.

```yaml
type: NodePort
ports:
  - port: 80
    targetPort: 8080
    nodePort: 30080
```

**Expected observation:** Three different roles; none changes the app listener automatically.

### Worked example 2: Find the missing desktop hop

The node may not be the laptop network namespace.

```text
laptop -> desktop VM -> kind node container -> NodePort -> Pod
missing VM/container port mapping can block the first hops
```

**Expected observation:** The Kubernetes object can be valid while the laptop has no route to it.

## Six progressive exercises

### Exercise 1: Label port, targetPort and nodePort.

**Expected evidence:** 80, 8080 and 30080 serve distinct path positions.

**Progressive hint:** Follow a packet from outside: which number does it carry at the node, after the Service, and at the process?

### Exercise 2: Predict whether a private node is publicly reachable.

**Expected evidence:** No public route is implied by NodePort allocation.

**Progressive hint:** Allocating a port on a node changes nothing about who can route to that node. Where does the node address live?

### Exercise 3: Draw the local-engine NodePort path.

**Expected evidence:** Include VM or node-container boundaries when present.

**Progressive hint:** On a local engine the node is itself a container or VM. Draw that boundary between your host and the node.

### Exercise 4: Diagnose timeout before traffic reaches the node.

**Expected evidence:** Inspect host/VM route and mapping rather than Pod selectors first.

**Progressive hint:** A timeout before the node means Kubernetes never saw the packet. Check the host-side mapping first.

### Exercise 5: Explain the NodePort range as configurable.

**Expected evidence:** The common default is not a guaranteed cluster setting.

**Progressive hint:** The range is an API server flag. Must every cluster keep the same default?

### Exercise 6: Compare NodePort with a deliberate loopback port-forward.

**Expected evidence:** They have different scopes, lifetimes and routing mechanisms.

**Progressive hint:** Compare who can use each path, how long it lasts and which process carries the bytes.

## Diagnosis, failure boundaries and common mistakes

People often open localhost:30080 in a browser and conclude NodePort is broken. With kind or a desktop VM, the node is not localhost unless a port mapping was configured when the cluster was created. Another mistake is hard-coding 30080 everywhere; leave the field empty and the API allocates from the configured range, and that range itself can differ between clusters. Do not confuse NodePort with port-forward either: port-forward tunnels through the API server to one Pod and stops when the command ends, while NodePort opens the port on every node. Never open every node port in a firewall to test a theory.

Before concluding, record:

- All three numbers in one row: Service port 80, targetPort 8080 and nodePort 30080, each with its role.
- The node address you actually dialed, and whether your laptop has a route or a kind port mapping to it.
- The cluster's configured NodePort range, if you can read it, instead of assuming the 30000 to 32767 default.
- Whether the same request through ClusterIP port 80 succeeds from inside the cluster, which separates node reachability from backend health.

General evidence rules: [diagnosis rules](../STUDY-GUIDE.md#diagnosis-rules).
