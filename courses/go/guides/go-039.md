# go-039: List-watch continuity, bookmarks and expired history

## Level and prerequisites

## Why this mechanism matters

A watch streams changes after a chosen observation point, but it is not an infinite durable event log. A controller normally obtains a list snapshot and continues from its resourceVersion so the initial state and later events connect coherently. Connections end, history can expire, and clients must recover by relisting when the server cannot continue from an old version. Bookmarks can advance the known position without carrying an ordinary object mutation; they are not guaranteed periodic heartbeats. Treat events as prompts to reconcile current state. Never assume every intermediate transition is delivered exactly once or that a disconnected watch proves no changes occurred.

## Vocabulary and concepts

- **List snapshot:** A collection observed at a defined API version point.
- **Watch bookmark:** A progress marker without an ordinary object update.
- **Expired history:** A watch position the server can no longer continue.

## Syntax anatomy and reasoning

This offline reducer handles ADDED, MODIFIED, DELETED, BOOKMARK and an explicit expired-history signal. Ordinary events update a keyed cache; bookmarks only advance the token. Expiration invalidates continuity and requires a fresh list rather than fabricated incremental recovery. The real API uses Status errors and HTTP responses whose interpretation belongs to client-go or a carefully reviewed client.

## Worked example / walkthrough

### Worked example 1: Apply an added object

Apply ADDED for demo with value 2.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type WatchEvent struct {
	Kind, Key, Version string
	Value              int
}
type WatchState struct {
	Items     map[string]int
	Version   string
	NeedsList bool
}

func newWatch() WatchState { return WatchState{Items: map[string]int{}} }
func applyWatch(s *WatchState, e WatchEvent) error {
	switch e.Kind {
	case "ADDED", "MODIFIED":
		s.Items[e.Key] = e.Value
	case "DELETED":
		delete(s.Items, e.Key)
	case "BOOKMARK":
	case "EXPIRED":
		s.NeedsList = true
		return errors.New("relist required")
	default:
		return errors.New("unknown event")
	}
	s.Version = e.Version
	return nil
}

func main() {
	// Apply an added object
	{
		s := newWatch()
		check(applyWatch(&s, WatchEvent{Kind: "ADDED", Key: "demo", Value: 2, Version: "a"}) == nil && s.Items["demo"] == 2, "add")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The cache gains demo=2.

The key identifies current state. Reconciliation should inspect that state rather than treat addition as an irreversible once-only command.

### Worked example 2: Apply a modification

Add then modify the same key.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type WatchEvent struct {
	Kind, Key, Version string
	Value              int
}
type WatchState struct {
	Items     map[string]int
	Version   string
	NeedsList bool
}

func newWatch() WatchState { return WatchState{Items: map[string]int{}} }
func applyWatch(s *WatchState, e WatchEvent) error {
	switch e.Kind {
	case "ADDED", "MODIFIED":
		s.Items[e.Key] = e.Value
	case "DELETED":
		delete(s.Items, e.Key)
	case "BOOKMARK":
	case "EXPIRED":
		s.NeedsList = true
		return errors.New("relist required")
	default:
		return errors.New("unknown event")
	}
	s.Version = e.Version
	return nil
}

func main() {
	// Apply an added object
	{
		s := newWatch()
		check(applyWatch(&s, WatchEvent{Kind: "ADDED", Key: "demo", Value: 2, Version: "a"}) == nil && s.Items["demo"] == 2, "add")
	}

	// Apply a modification
	{
		s := newWatch()
		_ = applyWatch(&s, WatchEvent{Kind: "ADDED", Key: "demo", Value: 2, Version: "a"})
		check(applyWatch(&s, WatchEvent{Kind: "MODIFIED", Key: "demo", Value: 3, Version: "b"}) == nil && s.Items["demo"] == 3, "modify")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The cached value becomes 3.

The newest observed value replaces the prior value for this simplified cache. A production informer also manages resource typing and synchronization.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
