dme-019: Spark partitions, shuffles and skew#

Level: Intermediate | Prepared runtime: spark-local-python

Direct prerequisites: dme-017, dme-018.

Outcome: Execute and inspect a real Spark aggregation and its physical shuffle boundary.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

What makes an analytical operation distributed#

Spark represents a DataFrame as a logical plan whose work can be divided among tasks. A partition is a portion of data assigned to one task at a stage of execution. It is not necessarily a file, a machine or a permanent slice of a table. The same dataset can have one partitioning before a join and another afterward. The driver coordinates the application, while executors carry out tasks and hold intermediate data. In this chapter, both roles run on one local machine through actual Spark local[2]; we are studying Spark's execution mechanisms without pretending to have tested a multi-node cluster.

Some transformations can operate independently on each partition. Filtering rows and computing a column from fields in the same row often fit this pattern. Grouping by a key requires all contributions for that key to be combined. When those contributions begin in different partitions, Spark moves or organizes data across a shuffle boundary. In a physical plan, an Exchange node exposes a redistribution step. A shuffle can involve serialization, disk spill, network transfer on a cluster and extra scheduling work.

The important question is not whether a job has any shuffle. Many correct analytical questions require one. Ask whether the shuffle uses the right grain, whether data volume can be reduced before it, whether a small relation can be broadcast for a join, and whether a few keys create disproportionate work. A query that avoids a shuffle by discarding necessary records is not an optimization.

Skew is a distribution problem#

Our fixture contains 22 records: 20 for key hot, one for cold-a and one for cold-b. The hot values are the integers 1 through 20, whose independent sum is

The cold values are five and seven. Repartitioning by the group key sends all hot records to the same hash partition. Increasing the number of partitions does not split one identical key by itself. If the longest partition takes much longer than the others, the stage waits for that straggler. A crude stage lower bound is T≥max⁡jTjT\geq\max_j T_jT≥maxj​Tj​, even when average partition work is small.

Rows per partition are only a proxy for work. A wide row, expensive expression or high-cardinality aggregate can make two equally sized partitions cost very different amounts. We count rows here because they make skew visible, not because row count predicts all performance. Actual tuning should inspect task time, bytes, spills, CPU, memory and output sizes under a representative workload.

Worked case 1: observe a real shuffle and a hot key#

example_one() creates a typed Spark DataFrame, repartitions it by key and groups it to sum values. It collects only the three-row result to the Python driver. The expected dictionary is hot: 210, cold-a: 5, cold-b: 7. That dictionary comes from arithmetic over the fixture, so Spark's result is checked independently of Spark's own aggregation implementation.

The example also counts rows in the physical partitions and inspects the executed plan for an exchange. In the qualified local run, four partitions contained 1, 0, 1 and 20 records. The exact order of those counts is not a portable promise. Hash assignment and plan details can change with an engine version or configuration. The stable lesson is that all 20 records of the hot key stay together under key-only partitioning and the accepted totals remain correct.

Spark is lazy: defining transformations builds a plan, while actions such as collect() and partition counting cause computation. Reading a plan alone is not the same as executing it. The program triggers actions and checks their outputs. It disables adaptive execution for this small diagnostic so that the planned four-partition comparison remains easier to inspect. That setting is a teaching choice, not a recommendation to disable adaptive query execution in production.

Worked case 2: salted partial sums followed by reconciliation#

The second example adds a deterministic salt for the hot key. The 20 hot records are assigned to four logical buckets with five records each. It first aggregates by (key, salt), then groups the partial results by the original key and sums again. The final answer must still be 210, five and seven. The extra field changes the intermediate work distribution but must not change the result grain.

This works because sum decomposes into partial sums:

with each original record assigned to exactly one bucket. The same idea supports count and min/max. For a mean, carry both sum and count, then divide the global sum by the global count. Averaging unweighted bucket averages is generally wrong when bucket populations differ. Exact median and arbitrary user functions require different reasoning; do not assume every aggregate has a compact associative summary.

Logical buckets are not physical partitions. In the qualified run, the salted physical partition row counts were 10, 12, 0 and 0 despite four balanced hot salt groups. Hash collisions can map several composite keys to one partition. The example prints both observations so learners do not confuse a balanced salt assignment with guaranteed balanced task execution. At this scale, the extra aggregation may cost more than it saves. No timing speedup is claimed.

Complete worked program#

Use the prepared Spark Python profile. The classroom runs the program through Spark's submission mechanism, not an arbitrary Python interpreter. main() shares one local Spark session across the two cases and closes it afterward. No cluster credentials, downloaded packages or external datasets are required.

"""Actual local Spark shuffles and a correctness-preserving salted aggregation."""

from contextlib import contextmanager

from pyspark.sql import SparkSession
from pyspark.sql import functions as F


@contextmanager
def session(existing=None):
    if existing is not None:
        yield existing
        return
    spark = (
        SparkSession.builder.master("local[2]")
        .appName("dme-shuffle-contract")
        .config("spark.ui.enabled", "false")
        .config("spark.ui.showConsoleProgress", "false")
        .config("spark.driver.host", "127.0.0.1")
        .config("spark.driver.bindAddress", ("127.0.0.1"))
        .config("spark.sql.adaptive.enabled", "false")
        .config("spark.sql.shuffle.partitions", ("4"))
        .getOrCreate()
    )
    spark.sparkContext.setLogLevel("ERROR")
    try:
        yield spark
    finally:
        spark.stop()


def records():
    return [("hot", number, number + 1) for number in range(20)] + [
        ("cold-a", 20, 5),
        ("cold-b", 21, 7),
    ]


def frame(spark):
    return spark.createDataFrame(records(), "group_name string, event_id long, amount long")


def partition_counts(data):
    return data.rdd.mapPartitions(lambda values: [sum(1 for _ in values)]).collect()


def totals(data):
    return {row["group_name"]: int(row["total"]) for row in data.orderBy("group_name").collect()}


def example_one(existing=None):
    with session(existing) as spark:
        data = frame(spark).repartition(4, "group_name")
        counts = partition_counts(data)
        result = data.groupBy("group_name").agg(F.sum("amount").alias("total"))
        actual = totals(result)
        plan = result._jdf.queryExecution().executedPlan().toString()
        assert actual == {"cold-a": 5, "cold-b": 7, "hot": 20 * 21 // 2}
        assert len(counts) == 4 and sum(counts) == 22 and max(counts) >= 20
        assert "Exchange" in plan
        return {
            "group_totals": actual,
            "observed_partition_rows": counts,
            "executed_plan_has_exchange": True,
            "scope": ("actual local[2] Spark, not a distributed-cluster performance claim"),
        }


def example_two(existing=None):
    with session(existing) as spark:
        salted = (
            frame(spark)
            .withColumn(
                "salt",
                F.when(F.col("group_name") == "hot", F.pmod(F.col("event_id"), F.lit(4))).otherwise(
                    F.lit(0)
                ),
            )
            .repartition(4, ("group_name"), ("salt"))
        )
        first = salted.groupBy("group_name", "salt").agg(
            F.sum("amount").alias("subtotal"), F.count("*").alias("records")
        )
        hot_counts = [
            int(row["records"])
            for row in first.filter(F.col("group_name") == "hot").orderBy("salt").collect()
        ]
        combined = first.groupBy("group_name").agg(F.sum("subtotal").alias("total"))
        actual = totals(combined)
        counts = partition_counts(salted)
        assert hot_counts == [5, 5, 5, 5] and sum(counts) == 22
        assert actual == {"cold-a": 5, "cold-b": 7, "hot": sum(range(1, 21))}
        return {
            "group_totals": actual,
            "hot_records_per_logical_salt": hot_counts,
            "observed_physical_partition_rows": counts,
            "no_timing_speedup_was_claimed": True,
        }


def main():
    with session() as spark:
        print("A real shuffle with a hot key:", example_one(spark))
        print("Two-stage aggregation retains the independent total:", example_two(spark))


if __name__ == "__main__":
    main()

Diagnosing failures at the right layer#

If importing pyspark fails in a plain Python environment, first check that the Spark profile is selected. A source file cannot install the runtime by declaring a lesson title. If Spark cannot establish its local driver connection, inspect loopback binding and the prepared environment before rewriting the aggregation. A local networking failure is distinct from a wrong group total.

If salted totals differ, check that salt affects only intermediate partitioning and that the second aggregation removes it from the output grain. Verify every input identity appears exactly once. For a salted join, it is often necessary to replicate the smaller matching side across salts; careless replication can multiply output rows. This chapter uses aggregation, where the decomposition is simpler. A join optimization needs its own row-grain and multiplicity proof.

If the plan changes after enabling adaptive execution, inspect the actual final plan and metrics. Adaptive query execution can modify shuffle partitioning and certain join strategies based on observed information. It is not a universal repair for every user-defined skew pattern. Changing several configuration knobs at once makes the causal effect of each change difficult to interpret. Preserve one baseline and compare one justified change at a time.

When to use the mechanism#

Skew analysis matters for popular customers, large tenants, common null keys, default values, geographic concentration and high-volume event categories. Start by measuring the key-frequency distribution. A missing-value bucket can become a hot key because many invalid records share the same placeholder. Filtering or quarantining invalid records before a shuffle may improve both correctness and performance, provided the rejected population remains accounted for.

An interview may ask, “We doubled executors, but one task still dominates. Why?” Explain that one large key can remain a single bottleneck, and propose inspecting the task distribution before adding resources. If asked about salting, describe the second reconciliation stage and its correctness condition, not only the random extra column. Deterministic salt is useful for repeatable diagnosis; random assignment needs controlled seeding and still cannot fix an invalid aggregation law.

The broader Spark module covers joins, execution plans and resource choices in more detail. This chapter supplies a compact real execution you can use to explain why data distribution belongs in an engineering design review alongside SQL correctness.
