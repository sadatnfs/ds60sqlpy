# web-046: HTTP requests, response models and routing

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-045`

## Learning objectives

Build a pure router for health and lesson-summary requests. Explain what a CLI response model does not prove. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

HTTP separates a request from its response. A request includes a method, target and headers, and may contain a body. A response includes a status code, headers and body. The method expresses intended semantics: GET should retrieve a representation without requesting a state change, while POST commonly submits data for processing. The server must still enforce its own rules regardless of a client-supplied method or path.

Routing selects application behavior from the request method and path. Keep routing separate from the domain calculation so logic can be tested without a live server. A 404 means the requested resource or route is not found; a 405 means the resource exists but the method is unsupported. The application should not return 200 for every failure merely because it produced a page.

## Syntax anatomy and mechanism

The CLI reference receives a synthetic request array and returns a response array. This is a model of an HTTP boundary, not an actual network exchange. A real adapter would read the server-provided environment, validate it, set status and headers before body output, and send the body. Content-Type should describe the response representation, and error bodies should match the declared format.

## Classroom execution and offline inputs

Choose the **PHP CLI** worker in the classroom. The pad is staged as `main.php` and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write `<?php` at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

## Worked example / walkthrough

### Worked example 1: A response value

The model makes the three response parts visible.

```php
$response = ['status' => 200, 'headers' => ['Content-Type' => 'text/plain; charset=utf-8'], 'body' => 'Ready'];
```

**Expected observation:** The body is text and the status describes success.

### Worked example 2: Method-aware routing

The same path can reject an unsupported operation.

```php
if ($path === '/health' && $method === 'GET') { return ['status' => 200, 'body' => 'ok']; }
```

**Expected observation:** A health retrieval is explicitly distinct from other requests.

## Six progressive exercises

### Exercise 1: Identify status, headers and body in the response model.

**Expected evidence:** They are separate fields with different protocol responsibilities.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add a not-found response for an unknown path.

**Expected evidence:** The unknown route returns 404 instead of pretending to be a successful page.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a pure router for health and lesson-summary requests.

**Expected evidence:** Known GET routes return their declared representations and unsupported requests are rejected.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose headers sent after body output in a real adapter.

**Expected evidence:** Response metadata must be established before output begins, subject to the runtime's buffering behavior.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test a known path with the wrong method.

**Expected evidence:** The route returns 405 and identifies allowed methods where appropriate.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain what a CLI response model does not prove.

**Expected evidence:** It does not qualify actual networking, server configuration, cookie handling or browser behavior.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not trust a route parameter as an authorized identity. Avoid state changes triggered by GET. A printed response array cannot establish that a real server sent those headers.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation.
