dme-043: Observability, SLOs and error budgets#

Level: Advanced | Prepared runtime: python-core

Direct prerequisites: dme-042.

Outcome: Compute request-based service indicators with explicit eligible denominators.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

Measure the consumer's promised outcome#

Observability is the ability to investigate a system through evidence such as metrics, logs, traces and recorded state. A service-level indicator, or SLI, measures a particular aspect of the service experience. A service-level objective, or SLO, sets a target for that indicator over a defined population and period. An error budget expresses how much unsuccessful service is compatible with that target. These definitions are useful only when the underlying event and denominator are explicit.

For a prediction API, availability might mean a valid response to an eligible request. Timely success might require both a valid response and latency within a threshold. For a data pipeline, a useful indicator might measure complete accepted publications before a deadline. A process being alive or a container being healthy is not automatically the outcome the learner or consumer needs. Infrastructure metrics help diagnosis, while product-facing indicators describe the promise.

This chapter performs exact arithmetic over synthetic request observations. It does not deploy Prometheus, scrape a live service or claim a production reliability level. The example makes denominator and window choices visible so that a later monitoring implementation can be checked against an independent calculation. A dashboard should implement a reviewed definition, not become the place where the definition is accidentally invented.

Eligible requests and bad events#

The fixture records request time, eligibility, status and latency in milliseconds. Eligibility is declared before the metric is calculated. Synthetic health checks and invalid-input requests are excluded under this example's policy. Service overload remains eligible: returning an overload response to a legitimate request is still a failure to provide the promised service. A 4xx code should not automatically disappear from reliability accounting.

For target SSS, the permitted bad-event fraction is 1−S1-S1−S, and the corresponding budget in this observed population is N(1−S)N(1-S)N(1−S). A burn ratio compares the observed bad-event fraction with that permitted fraction:

A burn ratio of one matches the target's bad-event rate. Five means the observed window consumes budget at five times that rate under the same request-based definition. It does not by itself say how much of a longer-period budget remains; that requires the longer-period population and observations. An empty eligible population has no observed success fraction, so the function rejects it instead of reporting a misleading 100 percent.

Worked case 1: availability passes while timely success fails#

example_one() creates 1,000 eligible requests. Five return 503. Twenty different requests succeed but take 300 milliseconds, exceeding the 200-millisecond limit. All other eligible requests succeed in 100 milliseconds. Two additional fixture requests are explicitly excluded from the denominator.

Availability is 995 out of 1,000, or 99.5 percent. Timely success is 975 out of 1,000, or 97.5 percent, because it requires both success and acceptable latency. The bad-event count for that combined indicator is 25. At a 99.5 percent target, the observed population's allowed bad count is five, giving burn ratio five. The implementation uses Fraction for this calculation so binary floating-point rounding does not obscure the exact arithmetic.

The failure categories do not overlap in the fixture, but the implementation counts good events directly rather than adding error and slow-request counts. That matters when an unsuccessful request is also slow: adding both categories would count one request twice. Define the compound good-event predicate and derive bad events from its complement. You may still report diagnostic categories separately, provided their overlap is understood.

Worked case 2: a recent burst is diluted by a broad window#

The second fixture contains one request per model time unit for 1,000 units. Ten requests fail, all in the last 200 units, with four in the last 20. The whole-period burn ratio is two. The last-200 window burns at ten, and the last-20 window burns at forty. Each result uses its own explicit eligible denominator.

The illustrative alert rule requires at least 20 observations in the short window, at least 200 in the longer window, short-window burn above 14 and longer-window burn above six. Both conditions are met. The thresholds are chosen to make the mechanism inspectable, not presented as a universal paging policy. A real alert design must consider the SLO period, traffic rate, incident response time, false positives and the cost of delayed detection.

Using both windows helps distinguish a sustained recent problem from a single transient observation while retaining responsiveness. The broad whole-period average still contains useful context, but it should not be the only signal when recent experience has deteriorated sharply. The output table shows all three burn ratios so the contrast is visible without reading a long log.

Complete worked program#

Run in Python Core. All observations are bounded synthetic records, and the program publishes a table plus a JSON report. No external monitoring system is contacted.

"""Request-based SLO arithmetic over declared observations, not a live monitoring service."""

from fractions import Fraction


def indicators(requests, latency_limit=200):
    eligible = [row for row in requests if row["eligible"]]
    if not eligible:
        raise ValueError("An empty eligible population has no observed service rate")
    available = sum(200 <= row["status"] < 400 for row in eligible)
    timely_success = sum(
        200 <= row["status"] < 400 and row["latency_ms"] <= latency_limit for row in eligible
    )
    return {
        "eligible": len(eligible),
        "excluded": len(requests) - len(eligible),
        "available": available,
        "timely_success": timely_success,
        "bad": len(eligible) - timely_success,
    }


def burn(summary, target=Fraction(995, 1000)):
    if not 0 < target < 1:
        raise ValueError("The target must leave a positive error budget")
    return Fraction(summary["bad"], summary["eligible"]) / (1 - target)


def example_one():
    rows = [
        {
            "time": i,
            "eligible": True,
            "status": 503 if i < 5 else 200,
            "latency_ms": 300 if 5 <= i < 25 else 100,
        }
        for i in range(1000)
    ]
    rows.extend(
        [
            {"time": 1000, "eligible": False, "status": 200, "latency_ms": 10},
            {"time": 1000, "eligible": False, "status": 400, "latency_ms": 10},
        ]
    )
    result = indicators(rows)
    assert result == {
        "eligible": 1000,
        "excluded": 2,
        "available": 995,
        "timely_success": 975,
        "bad": 25,
    }
    assert burn(result) == 5
    allowed = Fraction(result["eligible"]) * (1 - Fraction(995, 1000))
    assert allowed == 5
    return {
        "observations": result,
        "availability_rate": 0.995,
        "timely_success_rate": 0.975,
        "allowed_bad_requests_at_target": int(allowed),
        "latency_and_success_burn": float(burn(result)),
        "policy": (
            "health and invalid-input fixture requests excluded; service overload remains eligible"
        ),
    }


def example_two():
    bad = {810, 820, 830, 840, 850, 860, 982, 987, 992, 997}
    rows = [
        {"time": i, "eligible": True, "status": 503 if i in bad else 200, "latency_ms": 100}
        for i in range(1000)
    ]
    whole = indicators(rows)
    slow = indicators([row for row in rows if row["time"] >= 800])
    fast = indicators([row for row in rows if row["time"] >= 980])
    assert (whole["bad"], slow["bad"], fast["bad"]) == (10, 10, 4)
    rates = {
        "whole": float(burn(whole)),
        "last_200": float(burn(slow)),
        "last_20": float(burn(fast)),
    }
    assert rates == {"whole": 2.0, "last_200": 10.0, "last_20": 40.0}
    alert = (
        fast["eligible"] >= 20 and slow["eligible"] >= 200 and burn(fast) > 14 and burn(slow) > 6
    )
    assert alert
    return {
        "burn_by_window": rates,
        "both_windows_pass_declared_alert_rule": alert,
        "thresholds_are_illustrative_not_a_universal_paging_policy": True,
    }


def main():
    from ds60sqlpy.plot_artifacts import publish_report, publish_table

    first, second = example_one(), example_two()
    print("Separate availability from timely success:", first)
    print("A recent burst needs shorter windows:", second)
    publish_table(
        ["window", "burn_ratio"],
        [[key, value] for key, value in second["burn_by_window"].items()],
        description=(
            "Declared synthetic observation windows burn the 0.5 percent "
            "bad-request budget at 2, 10 and 40 times the target rate."
        ),
    )
    publish_report(
        first,
        description=(
            "Explicit eligible denominators, separate availability and "
            "latency success, and error-budget arithmetic."
        ),
    )


if __name__ == "__main__":
    main()

Metrics, logs and traces answer different questions#

A metric summarizes a quantity over labels and time. It can show that error rate increased. A structured log can record a particular rejected request or publication decision. A trace can connect spans across components and reveal where time was spent. These forms of evidence complement one another, but each can mislead when its scope is unclear.

Do not put unbounded request IDs into metric labels; that can create excessive time-series cardinality. Keep identifiers in bounded logs or traces with appropriate access and retention instead. Do not log raw features or sensitive payloads simply because they might be useful during an incident. Record reviewed metadata, error categories, version identities and timing boundaries sufficient for diagnosis while respecting the data policy.

Latency measurements also require a boundary. Model-only execution excludes queueing, feature retrieval and serialization. Server-side request latency may exclude a proxy or client connection delay. A user-facing SLO should measure the relevant experience and preserve component timings for diagnosis. Comparing numbers measured at different boundaries can make an optimization appear successful while the consumer's latency remains unchanged.

Missing observations are not successful requests#

Monitoring can fail. Logs may be sampled, metrics may be dropped and clocks may be inconsistent. A missing request record is not evidence of success. Track telemetry coverage and distinguish measured rates from population-wide claims. If only completed requests produce latency observations, timed-out or abandoned requests can disappear and make the service look faster than it is.

Request-based and time-based SLOs also differ. One bad minute during peak traffic can affect far more users than one bad minute overnight. Conversely, a low-traffic critical workflow may need a deadline-oriented or synthetic-probe indicator because request counts are sparse. Choose the indicator around the consumer promise, then state how periods with no eligible events are handled.

A budget policy should define operational consequences, such as slowing risky releases, investigating recurring causes or prioritizing reliability work. The arithmetic alone does not decide organizational action. It supplies a shared measure for making that decision deliberately rather than relying on the loudest incident or a favorable average.

Failure diagnosis and answered interview discussion#

If an indicator improves while users complain more, inspect the denominator, eligibility changes, measurement boundary and missing events. If availability looks good while requests feel slow, compare timely success with status-only success. If alerts fire repeatedly on tiny populations, inspect sample counts and whether the signal is actionable. If a rolling window hides a burst, compare shorter and longer windows without abandoning the declared long-period objective.

An interviewer may ask, “What is the difference between an SLI and an SLO?” Describe the measured ratio and the target separately, including population and period. If asked what burn rate means, derive it from the bad-event fraction rather than memorizing a threshold. If asked whether all 4xx responses should be excluded, explain that legitimate overload can represent a service failure even though the status family is client-oriented.

For an answered extension, make one of the five failed requests slow as well. The combined bad-event count should remain 25 if the previously slow successful population is unchanged. A calculation that reports 26 has double-counted one request, demonstrating why good-event predicates are safer than casually adding error counters.
