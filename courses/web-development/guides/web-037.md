## Purpose, vocabulary and mental model

A PHP string is a sequence of bytes. UTF-8 is an encoding that represents characters using one or more bytes, so strlen counts bytes rather than user-perceived characters. A visible character can also consist of multiple code points, such as a letter with a combining mark. Code-point count and grapheme count are therefore different concepts. Choose the measure that matches the product requirement.

This worker does not assume every optional internationalization extension. The examples use valid UTF-8 and demonstrate byte-level behavior plus a Unicode-aware regular expression. Production text normalization, locale-aware sorting and grapheme handling need deliberate library and extension choices. Do not truncate arbitrary UTF-8 bytes and then assume the result remains valid text.

### Key terms

- **UTF-8:** An encoding that stores each Unicode code point in one to four bytes, with ASCII characters taking one byte.
- **Byte length:** The count `strlen()` returns, which is the number of bytes, not the number of visible characters, for non-ASCII text.
- **Code point:** One Unicode value, counted by `mb_strlen()` when the encoding is UTF-8.
- **Grapheme:** What a reader perceives as one character, which can combine several code points, such as a letter with an accent mark.

## Syntax anatomy and mechanism

Use explicit UTF-8 when escaping HTML output. JSON requires valid Unicode data and can fail on invalid UTF-8. A Unicode regular expression with the u modifier interprets the pattern as UTF-8, but it is not a universal grapheme library. The mbstring functions count and cut by code point instead of byte: `mb_strlen('café')` is 4 while `strlen('café')` is 5, and `mb_strcut` truncates to a byte budget without splitting a character. PHP 8.4 adds `mb_trim`, `mb_ltrim` and `mb_rtrim` for Unicode whitespace. A code point is still not always one visible character, because an accent can be a separate combining code point. Keep validation, normalization and output encoding separate because they solve different problems.

## Worked example / walkthrough

### Worked example 1: Bytes are not letters

The example's encoding is UTF-8.

```php
$text = 'é';
echo strlen($text);
```

**Expected observation:** The byte length is 2 for this UTF-8 source character.

### Worked example 2: Safe JSON text

The encoder validates its input representation.

```php
$json = json_encode(['label' => 'café'], JSON_THROW_ON_ERROR | JSON_UNESCAPED_UNICODE);
```

**Expected observation:** The result is valid JSON that preserves the readable Unicode label.

## Contrast case: byte slicing a multibyte label

Both lines try to keep the first four characters of a short label, then encode it as JSON.

```php expect-error
$label = 'café';
$bytes = substr($label, 0, 4);
$chars = mb_substr($label, 0, 4, 'UTF-8');

echo json_encode(['label' => $chars], JSON_THROW_ON_ERROR | JSON_UNESCAPED_UNICODE), "\n";
echo json_encode(['label' => $bytes], JSON_THROW_ON_ERROR), "\n";
```

In UTF-8 'café' is five bytes because é uses two. `substr` counts bytes, so `$bytes` keeps c, a, f and only the first byte of é, which is not valid UTF-8. `mb_substr` counts code points and keeps the full word. The first `json_encode` prints the label normally. The second throws a `JsonException` for malformed UTF-8 because JSON requires valid Unicode. Without the throw flag, it would return false instead, which is easy to miss.

## Debugging and common mistakes

Do not promise that a regex character count equals a user's perceived character count. Avoid silently replacing invalid data without a declared policy. Text encoding matters before both rendering and storage.

Keep the failing source, its input and the exact output, then repair one cause at a time. PHP can produce correct-looking text while missing an invalid-input branch, so rerun the empty, wrong-type and boundary cases after every fix.
