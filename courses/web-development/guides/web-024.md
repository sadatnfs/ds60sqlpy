# web-024: HTML and CSS milestone: an accessible learning portal

## Level and prerequisites

Intermediate; allow about 180 minutes, with extra time for independent practice. Direct prerequisites: `web-023`

## Learning objectives

Build a complete offline portal with three paths and local destinations. Explain the portal's remaining backend requirements. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A portal combines structure, navigation and repeated components around a user goal. Begin with the tasks: finding a topic, understanding prerequisites, choosing an action and reading progress. The information architecture groups content so those tasks are discoverable. A beautiful collection of cards is not enough if every label is vague or the reading order hides the main choice.

This milestone integrates the earlier mechanisms without requiring a framework. Semantic headings establish the outline, native links provide navigation, Grid or Flexbox distributes cards, and tokens maintain consistent spacing and color. Progress labels remain textual. The project uses synthetic data and does not claim persistent accounts or a working backend.

## Syntax anatomy and mechanism

Write acceptance criteria before styling: one main region, descriptive page title, reachable navigation, distinct card headings, no color-only status, a narrow-width layout and a usable zoomed view. Implement the smallest coherent page, then audit the settled state at multiple widths. Keep appearance checks separate from structural checks because each can pass while the other fails.

## Classroom execution and offline inputs

Choose **HTML browser preview** in the classroom. The pad is one complete HTML document with embedded CSS and, where taught, embedded JavaScript. Its preview is isolated from the classroom and recreated on each run. It does not contact a server, submit real forms, read cookies, fetch assets or load a CDN. All fixtures are inline and synthetic. The browser uses its native HTML parser, so classic-script ordering, shared lexical bindings, inline modules and real DOMContentLoaded/load events keep their browser semantics. External module imports remain blocked. Navigation metadata such as base and meta http-equiv is rejected explicitly. On any supported host, the browser renders the document while Docker serves the classroom. No host compiler is needed.

Run your own source after implementing the task. A reference's checks inspect only the named initial conditions. Its success message is not a full accessibility audit, proof of responsive behavior at every size, or evidence that you implemented the solution yourself. Inspect actual output after keyboard input, resizing and changes. Save your source before comparing with a reference. The document and its CSS share one saved pad; HTML and CSS remain different languages within that artifact.

## Worked example / walkthrough

### Worked example 1: A meaningful card

The heading and link describe the same destination.

```html
<article><h2>HTML foundations</h2><p>Beginner. No prerequisites.</p><a href="#html">Read HTML foundations</a></article>
```

**Expected observation:** A reader knows the topic, entry requirement and next action.

### Worked example 2: Adaptive collection

The layout supports a changing number of topics.

```css
.topics { display: grid; grid-template-columns: repeat(auto-fit, minmax(min(100%, 15rem), 1fr)); gap: 1rem; }
```

**Expected observation:** Cards adapt without per-card coordinates.

## Six progressive exercises

### Exercise 1: Write three learner tasks before drawing the interface.

**Expected evidence:** Find a topic, assess its prerequisites and choose a clear next action.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Define a small token set for the page.

**Expected evidence:** Spacing, text and surface choices are consistent and named by role.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a complete offline portal with three paths and local destinations.

**Expected evidence:** All cards, navigation and headings are meaningful, keyboard reachable and responsive.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Audit one deliberately vague link and one broken fragment.

**Expected evidence:** Replace the vague label and repair the target relationship.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Review narrow width, zoom, keyboard and print behavior.

**Expected evidence:** Retain observations for each surface instead of claiming a universal pass from one screenshot.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain the portal's remaining backend requirements.

**Expected evidence:** Persistent identity, saved progress and authorization need a server and storage contract beyond this static page.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not invent working progress persistence in static HTML. Avoid screenshots as the sole accessibility evidence. A capstone should explain choices and limitations, not just imitate a reference's colors.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain information architecture, component system, responsive audit without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
