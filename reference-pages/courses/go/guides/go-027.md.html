go-027: Mutexes, atomics and shared-state invariants#

Level and prerequisites#

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-026

Learning objectives#

By the end, explain critical section, compound invariant, atomic operation; implement the six investigations below; and defend the expected result of a changed input before running it. A passing reference is evidence about that program, not a certification of your independent understanding.

Why this mechanism matters#

A mutex protects a state invariant across several operations. Every relevant access must follow the same protocol: locking writes while reading without synchronization can still race. Atomic operations protect specific values and ordering relationships, but do not automatically make a multi-field transaction atomic. Prefer a mutex for a compound invariant that must be inspected and changed together. Never copy a mutex after use. Keep critical sections small, avoid calling unknown callbacks while holding a lock, and define lock ordering when several locks are unavoidable. A correct observed count is not by itself proof of correct synchronization.

Vocabulary and concepts#

  • Critical section: Code accessing state while holding its lock.
  • Compound invariant: A relationship involving several state values.
  • Atomic operation: An indivisible operation with synchronization semantics.

Syntax anatomy and reasoning#

sync.Mutex uses Lock and Unlock; defer Unlock after acquisition handles early returns. atomic.Int64 supplies typed Load, Store and Add. sync.Once runs one initialization function. Keep synchronized state in a pointer-owned holder so it is not copied accidentally. count++ on an ordinary shared integer is a read-modify-write sequence, not an atomic operation.

Worked example / walkthrough#

Worked example 1: Protect a concurrent count#

Run four workers doing 100 protected increments each.

package main

import (
	"fmt"
	"sync"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type LockedCount struct {
	mu sync.Mutex
	n  int
}

func (c *LockedCount) Inc()       { c.mu.Lock(); defer c.mu.Unlock(); c.n++ }
func (c *LockedCount) Value() int { c.mu.Lock(); defer c.mu.Unlock(); return c.n }

type Pair struct {
	mu   sync.Mutex
	A, B int
}

func (p *Pair) Transfer(n int)       { p.mu.Lock(); defer p.mu.Unlock(); p.A -= n; p.B += n }
func (p *Pair) Snapshot() (int, int) { p.mu.Lock(); defer p.mu.Unlock(); return p.A, p.B }

func main() {
	// Protect a concurrent count
	{
		c := &LockedCount{}
		var wg sync.WaitGroup
		for i := 0; i < 4; i++ {
			wg.Add(1)
			go func() {
				defer wg.Done()
				for j := 0; j < 100; j++ {
					c.Inc()
				}
			}()
		}
		wg.Wait()
		check(c.Value() == 400, "count")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: The joined final count is 400.

Reads and writes use the same lock. The join establishes task completion before inspection.

Worked example 2: Use a typed atomic#

Add 3 and 4 through atomic.Int64.

package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type LockedCount struct {
	mu sync.Mutex
	n  int
}

func (c *LockedCount) Inc()       { c.mu.Lock(); defer c.mu.Unlock(); c.n++ }
func (c *LockedCount) Value() int { c.mu.Lock(); defer c.mu.Unlock(); return c.n }

type Pair struct {
	mu   sync.Mutex
	A, B int
}

func (p *Pair) Transfer(n int)       { p.mu.Lock(); defer p.mu.Unlock(); p.A -= n; p.B += n }
func (p *Pair) Snapshot() (int, int) { p.mu.Lock(); defer p.mu.Unlock(); return p.A, p.B }

func main() {
	// Protect a concurrent count
	{
		c := &LockedCount{}
		var wg sync.WaitGroup
		for i := 0; i < 4; i++ {
			wg.Add(1)
			go func() {
				defer wg.Done()
				for j := 0; j < 100; j++ {
					c.Inc()
				}
			}()
		}
		wg.Wait()
		check(c.Value() == 400, "count")
	}

	// Use a typed atomic
	{
		var n atomic.Int64
		n.Add(3)
		n.Add(4)
		check(n.Load() == 7, "atomic")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: Load returns 7.

Use the atomic access API consistently. Mixing it with ordinary conflicting accesses undermines the protocol.

Common pitfalls and diagnosis#

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from check identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned error is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
