# dme-026: Lake file organization, manifests and evolution

## A collection of files needs an acceptance boundary

A data lake stores datasets in files, often in object storage. Parquet supplies an efficient columnar representation, but Parquet alone does not tell a consumer which files belong to a particular accepted dataset version. A directory may contain old files, new candidates, retries and abandoned outputs. Reading every matching filename can combine incompatible generations or duplicate records after compaction.

A manifest is an explicit inventory of the files in a dataset version. The small manifest here records each basename, SHA-256 digest and expected row count. The reader verifies those facts before combining the files. It rejects repeated file entries and duplicate delivery identities. This makes the dataset boundary concrete: the answer is derived from the declared file set, not from whatever a broad directory scan happens to discover.

The example executes actual Arrow Parquet writes and a DuckDB Parquet read. The manifest itself is a Python list in the bounded fixture, so this is not a table-format transaction implementation. There is no concurrent writer, remote catalog or automatic snapshot protocol. The next chapter adds a local snapshot mechanism, while the Apache table-format workshops supply actual engine integrations. Here we focus on the subtle difference between a readable mixed schema and a compatible data product.

## Schema compatibility has a direction

A schema describes fields and types; a consumer contract also includes required values, grain, units and interpretation. Adding an optional field can preserve an old consumer that reads only its original fields. Requiring that new field immediately can break a new consumer reading historical files that never contained it. “Backward compatible” should therefore specify who reads which version.

Our original schema has string `delivery_id` and 64-bit integer `packages`. A later file adds string `region`. Older records do not acquire real regional knowledge merely because a new schema has a region column. They must remain null unless a separate, justified historical enrichment supplies that information. The combined logical schema is

\[
(\mathrm{delivery\_id}:\text{string},\quad
\mathrm{packages}:\text{int64},\quad
\mathrm{region}:\text{nullable string}).
\]

The code checks required Arrow field types before DuckDB reads the files. It also verifies non-null identifiers and package counts, nonnegative counts, expected population and unique delivery grain. A union-by-name operation aligns fields by names, but it does not decide whether a new numeric unit, duplicated record or missing required observation is acceptable. Those decisions remain explicit validation rules.

## Worked case 1: read an additive field without inventing history

`example_one()` writes an old Parquet file containing A with two packages and B with three. It writes a new file containing C with one package and region `north`. Both files are listed exactly once in the manifest with their actual content digests and row counts. DuckDB reads the listed paths using `union_by_name=True` and projects a consistent output shape.

The accepted rows are A: two with unknown region, B: three with unknown region, and C: one with region north. An old consumer projecting only identity and packages still obtains A2, B3 and C1, totaling six. A consumer interested in region can see which rows lack that information rather than having them silently assigned to north or an invented default. Missing historical knowledge and a real category named “unknown” should not be conflated without a reviewed interpretation.

The reader orders by delivery identity for a deterministic printed comparison. This does not require the physical files to be written in that order. The manifest verifies each file independently, then verifies the combined relation. Two individually valid files can still contain the same delivery ID, so file-level checks alone cannot prove dataset-level grain. Both layers are needed.

## Worked case 2: readable changes that violate the consumer contract

The second case begins with an original file that has no region field. A new consumer requests `require_region=True`. The reader rejects the result because historical region values are unavailable. This is a compatibility failure even though the old Parquet file is perfectly readable. Requiring a field is a semantic migration, not merely a convenience flag.

Next, the program writes another file where `packages` is floating-point with value 3.5. An analytical engine might be able to find a common numeric type, but the reviewed contract requires integer package counts. The reader rejects the type drift before accepting a combined dataset. If the business genuinely changes to fractional units, introduce a new explicit unit and migration rather than letting coercion silently redefine “packages.”

Finally, the fixture overwrites the bytes of the original file while retaining its old manifest entry. Digest verification rejects that file before it is trusted as the declared version. The demonstration changes only owned temporary data. It shows why an accepted manifest must bind actual bytes, while also acknowledging that a hash is not a signature: a writer able to replace both data and manifest can produce another internally consistent pair. Approval and trust belong to an additional publication boundary.

## Evolution beyond adding one column

Renaming a column is not always equivalent to adding a new one. A name-based reader can interpret a rename as deletion plus an unrelated addition. A table format with field identities may track the logical field across a rename, subject to its own supported operations. Similarly, changing an integer width, timestamp unit or timezone can require a compatibility rule beyond matching a friendly type name.

Dropping a field can break historical consumers or rollback. Reusing a dropped field's name for a different meaning is especially dangerous because a name-based query may continue to execute successfully. Document field semantics, units and version transitions alongside schemas. A query that runs without an exception is not evidence that it measures the same quantity as before.

Partition evolution adds another dimension. New files may be partitioned differently from old ones while representing the same logical table. Readers need metadata capable of interpreting both layouts. Hard-coding one directory convention throughout every consumer creates migration coupling. Established table formats provide richer metadata for these concerns, but their exact guarantees depend on the chosen format, catalog, engine and feature version.

## Failure diagnosis

If totals double after compaction, check whether both old and compacted files entered the manifest. If new columns appear null unexpectedly, inspect which file generations actually contain them. If a duplicate identity appears only after combining files, inspect the dataset-level grain check rather than blaming Parquet serialization. If a file passes its digest check but has the wrong unit, inspect the schema and business contract: integrity and meaning are separate.

If a consumer sees inconsistent output across retries, pin the manifest identity for the whole read. Re-resolving “latest” for each file can combine generations even when every individual object is valid. If a file is absent, fail the declared snapshot or invoke an explicit recovery policy; quietly skipping it turns a complete dataset into an unmarked partial result.

## Applications and answered interview discussion

Manifests are useful for training datasets, batch exports, reproducible analytical tables and controlled data sharing. Their inventory can also support provenance and cleanup, provided retention accounts for older accepted versions and active consumers. Avoid turning a manifest into a giant unbounded object for extremely large tables; mature formats use hierarchical metadata and indexes to scale discovery.

An interviewer may ask, “Does schema evolution mean every old reader keeps working?” Explain the direction of compatibility and identify required fields, types and semantic changes. If asked why union-by-name is insufficient, show the fractional-package case: alignment is technically possible but contradicts the domain. If asked how to reproduce a result, provide the exact manifest, file identities, transformation version and runtime environment rather than a mutable directory path.

For an answered extension, suppose C also appears in the old file. The reader must reject the combined duplicate grain even if both file digests match. A checksum validates bytes against an inventory; it does not certify that the inventory describes a nonduplicated business population.
