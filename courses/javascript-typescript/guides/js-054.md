# js-054: Reusable and responsive chart components

## Level and prerequisites

Intermediate; about 110 minutes plus independent practice. Direct prerequisites: `js-053`.

## Learning objectives

Write a reusable chart component with an explicit render contract, empty state and responsive sizing. The central exercise is: Implement a reusable bar renderer.

## Purpose, vocabulary and mental model

A reusable chart component has an explicit input, output and lifecycle. It should not depend on a hidden global dataset or append another entire chart every time a caller updates it. A useful render contract specifies data shape, dimensions, identity, empty state and cleanup.

Responsive display is not the same as recomputing every data transformation on every resize. An SVG viewBox can scale an existing coordinate system to fit a container. More complex charts may need width-dependent tick density or label layout. Decide which parts change with available space and which analytical quantities remain invariant.

The reference renders into a caller-owned group and updates a keyed join. It checks that a second render does not duplicate marks and that an empty input produces a readable message. This is a foundation for dashboards whose views share state without sharing accidental DOM mutations.

### Key terms

- **Chart component:** A function that renders into a caller-owned container from explicit arguments such as data and size, and can be called again to update the same marks.
- **Render contract:** The documented expectations of a component: accepted data shape, dimensions, identity key, empty state and cleanup.
- **Responsive viewBox:** An SVG viewBox that lets one logical coordinate system scale to the container width, so layout math stays in fixed units while the display size changes.
- **Empty state:** What a component shows when it receives no records, such as a readable message instead of blank space or stale marks.
- **ResizeObserver:** A browser API that reports element size changes through a callback. A component that creates one must disconnect it when the component is removed.

## Syntax anatomy and mechanism

Pass the container selection, data and size as arguments. Validate dimensions and records at the boundary. Compute scales from current input and update managed nodes. Keep the surrounding SVG and accessibility summary under clear ownership.

A ResizeObserver can detect actual container size, but it has a lifecycle and can trigger repeated callbacks. Disconnect it when the component is removed. The reference uses two explicit widths for deterministic acceptance; a real responsive integration should also be manually tested at narrow and wide browser sizes.

## Worked example / walkthrough

### Worked example 1: Define a small render contract

The function signature makes dependencies visible, and invalid geometry fails before any drawing.

```javascript
function renderBars(group, rows, width) {
  if (!(width > 0)) throw new Error("positive width required");
  // Derive scales and reconcile only nodes owned by this component.
  return rows.length;
}
try {
  renderBars(null, [], 0);
} catch (error) {
  console.log(error.message);
}
```

**Expected observation:** positive width required: the caller supplies current rows and dimensions, and the function does not fetch or use hidden app state.

### Worked example 2: Separate empty state from invalid geometry

Two bars from an earlier render are replaced by an empty state; an empty dataset needs no min or max domain calculation.

```javascript
// js-054 worked example 2: a complete program for the classroom preview.
const host = document.querySelector("#chart");
const output = document.querySelector("#output");
host.replaceChildren();
const check = (condition, message) => {
  if (!condition) throw new Error(message);
};
const svg = d3
  .select(host)
  .append("svg")
  .attr("viewBox", "0 0 640 360")
  .attr("role", "img")
  .attr("aria-label", "Reusable and responsive chart components")
  .style("width", "100%")
  .style("max-width", "640px");
const group = svg.append("g").attr("transform", "translate(40,40)");
group
  .selectAll("rect")
  .data([3, 6])
  .join("rect")
  .attr("y", (d, i) => i * 40)
  .attr("height", 30)
  .attr("width", (d) => d * 40)
  .attr("fill", "#2563eb");
const rows = [];
if (rows.length === 0) {
  group.selectAll("rect").remove();
  group
    .selectAll("text.empty")
    .data([null])
    .join("text")
    .attr("class", "empty")
    .attr("y", 20)
    .text("No observations");
}
check(group.selectAll("rect").size() === 0, "Stale bars must be removed");
check(group.select("text.empty").text() === "No observations", "The empty state must be visible");
output.textContent = "js-054 worked example 2 complete";
```

**Expected observation:** The two earlier bars disappear and the visible text No observations replaces them.

## Six progressive exercises

### Exercise 1: Predict mark count after two renders.

**Expected evidence:** It equals current record count, not the sum of all prior counts.

**Progressive hint:** A component updates its owned nodes.

### Exercise 2: Change width while retaining data.

**Expected evidence:** Geometry changes while values and identity remain stable.

**Progressive hint:** Responsive layout is a presentation transformation.

### Exercise 3: Implement a reusable bar renderer.

**Expected evidence:** Explicit inputs, keyed marks and a documented empty state.

**Progressive hint:** A small contract makes the component testable outside a large dashboard.

### Exercise 4: Diagnose duplicate SVG trees after resize.

**Expected evidence:** The update path creates new roots rather than updating an owned tree.

**Progressive hint:** Choose a single owner for the SVG root and reconcile its children.

### Exercise 5: Render an empty dataset after nonempty data.

**Expected evidence:** Stale marks disappear and the no-data message appears.

**Progressive hint:** Empty-state behavior must work on updates, not just initial load.

### Exercise 6: Plan real narrow-screen acceptance.

**Expected evidence:** Readable labels, no clipping, keyboard access and stable data meaning.

**Progressive hint:** A scaled screenshot alone can conceal unreadable text.

## Debugging and common mistakes

If resizing doubles the chart, check whether the component creates its `svg` root on every call. A component should select or create one owned root, then join marks inside it. Count `svg` elements and marks after two renders and after an empty render: one root, marks for current records only, and a visible no-data message. ([checkpoints](../STUDY-GUIDE.md#d3-debugging-checkpoints))

Exercise 4 is the controlled failure: Diagnose duplicate SVG trees after resize. Distinguishing evidence: The update path creates new roots rather than updating an owned tree.

## Accessibility and interpretation

A component reused in many places should accept its title and summary text as inputs rather than hard-coding them. At narrow widths, check that labels wrap or shorten rather than overlap, and that the empty state is announced as text rather than shown only as a blank area. ([accessibility review](../STUDY-GUIDE.md#d3-accessibility-review))

A reusable component must not change what the data say when its container changes size: a narrower view may hide some tick labels but should not alter the domain or drop records. Document the render contract, including required inputs, so callers cannot silently pass a different denominator or grain. ([statistical meaning](../STUDY-GUIDE.md#d3-statistical-meaning))
