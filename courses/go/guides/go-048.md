# go-048: Capstone: a reliable, resumable controller design

## Level and prerequisites

Advanced. Allow about 180 minutes, then revisit the transfer case later. Prerequisites: go-047

## Learning objectives

Design a resumable controller that converges from any starting state, refuses replacement objects and survives restarts. Along the way, explain control-loop invariant, resumability, operational contract; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

The capstone combines desired-state validation, exact identity, idempotent planning, cancellation and durable observations. A controller is successful when repeated observations converge without duplicating effects or damaging resources it does not own. Begin with an explicit state diagram and classify each operation as pure, read-only, idempotent mutation or potentially uncertain external side effect. Record what an operation observed and what it requested, not an invented certainty that the whole system is ready. Production readiness also includes minimal RBAC, bounded queues, useful status, metrics, graceful shutdown and a recovery runbook. This offline capstone proves a small orchestration model; the prepared client-go project and owned Kubernetes module supply the separate real-system learning routes.

## Vocabulary and concepts

- **Control-loop invariant:** A property preserved across every reconcile attempt.
- **Resumability:** Recovering useful work from durable state after interruption.
- **Operational contract:** The documented behavior under startup, failure, recovery and shutdown.

## Syntax anatomy and reasoning

The model stores UID, desired count, current count and a write counter. reconcileCap first checks cancellation, then ownership, then input validity, and finally changes state only when needed. The ordering prevents invalid or unauthorized work from reaching mutation. A real adapter adds optimistic concurrency, API errors, status subresources and cleanup. Preserve these boundaries when replacing the in-memory store rather than moving all logic into one untestable function.

## Worked example / walkthrough

### Worked example 1: Converge from a different state

Reconcile owned UID u1 from count 1 to desired 3.

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type CapState struct {
	UID             string
	Current, Writes int
}

func reconcileCap(ctx context.Context, s *CapState, expectedUID string, wanted int) error {
	if err := ctx.Err(); err != nil {
		return err
	}
	if s.UID != expectedUID {
		return errors.New("ownership mismatch")
	}
	if wanted < 0 {
		return errors.New("invalid count")
	}
	if s.Current != wanted {
		s.Current = wanted
		s.Writes++
	}
	return nil
}

func main() {
	// Converge from a different state
	{
		s := CapState{UID: "u1", Current: 1}
		err := reconcileCap(context.Background(), &s, "u1", 3)
		check(err == nil && s.Current == 3 && s.Writes == 1, "converge")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The count becomes 3 with one write.

The mutation is justified by a current difference under a verified identity.

### Worked example 2: Repeat without duplicate writes

Run the same desired state twice.

```go
package main

import (
	"context"
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type CapState struct {
	UID             string
	Current, Writes int
}

func reconcileCap(ctx context.Context, s *CapState, expectedUID string, wanted int) error {
	if err := ctx.Err(); err != nil {
		return err
	}
	if s.UID != expectedUID {
		return errors.New("ownership mismatch")
	}
	if wanted < 0 {
		return errors.New("invalid count")
	}
	if s.Current != wanted {
		s.Current = wanted
		s.Writes++
	}
	return nil
}

func main() {
	// Converge from a different state
	{
		s := CapState{UID: "u1", Current: 1}
		err := reconcileCap(context.Background(), &s, "u1", 3)
		check(err == nil && s.Current == 3 && s.Writes == 1, "converge")
	}

	// Repeat without duplicate writes
	{
		s := CapState{UID: "u1", Current: 1}
		check(reconcileCap(context.Background(), &s, "u1", 3) == nil, "first")
		check(reconcileCap(context.Background(), &s, "u1", 3) == nil && s.Writes == 1, "idempotent")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Only the first call writes.

Repeated notification is normal. Converged state should remain a no-op.

## Exercises

### Exercise 1: Converge from a different state: change one input

Copy worked example 1, change `err := reconcileCap(context.Background(), &s, "u1", 3)` to `err := reconcileCap(context.Background(), &s, "u1", 4)` and predict the failure before running; then restore the line.

**Expected:** The edited run panics with `converge` because `err == nil && s.Current == 3 && s.Writes == 1` no longer holds.

**Verify:** Restoring `err := reconcileCap(context.Background(), &s, "u1", 3)` makes the check pass again with the worked observation: the count becomes 3 with one write.

### Exercise 2: Repeat without duplicate writes: diagnose an edited check

A careless edit rewrote the check in worked example 2 as `check(reconcileCap(context.Background(), &s, "u1", 4) == nil, "first")`. Explain the failure, then restore it.

**Expected:** The defective run panics with `idempotent`; after restoring `check(reconcileCap(context.Background(), &s, "u1", 3) == nil, "first")`, only the first call writes.

**Verify:** The edited check fails with message `idempotent` for a state that `reconcileCap(context.Background(), &s, "u1", 3) == nil && s.Writes == 1` accepts.

### Exercise 3: Refuse a replacement object

Supply expected UID old while observed UID is new.

**Expected:** No write occurs and an ownership error is returned.

**Verify:** Your solution must keep `err != nil && s.Current == 1 && s.Writes == 0` true. Control: changing `s := CapState{UID: "new", Current: 1}` to `s := CapState{UID: "new", Current: 2}` panics with message `ownership`; revert it.

### Exercise 4: Preserve state on invalid intent

Request a negative count.

**Expected:** The operation fails without mutation.

**Verify:** Your solution must keep `err != nil && s.Current == 1 && s.Writes == 0` true. Control: changing `s := CapState{UID: "u1", Current: 1}` to `s := CapState{UID: "u1", Current: 2}` panics with message `invalid`; revert it.

### Exercise 5: Cancel before new work

Pass an already-canceled context.

**Expected:** No write occurs and cancellation is retained.

**Verify:** Your solution must keep `errors.Is(err, context.Canceled) && s.Writes == 0` true. Control: changing `check(errors.Is(err, context.Canceled) && s.Writes == 0, "cancel")` to `check(errors.Is(err, context.Canceled) && s.Writes != 0, "cancel")` panics with message `cancel`; revert it.

### Exercise 6: Transfer restart reasoning

Copy the converged durable state into a new controller invocation.

**Expected:** The restarted invocation makes no additional write.

**Verify:** Your solution must keep `reconcileCap(context.Background(), &restored, "u1", 3) == nil && restored.Writes == 1` true. Control: changing `s := CapState{UID: "u1", Current: 3, Writes: 1}` to `s := CapState{UID: "u1", Current: 4, Writes: 1}` panics with message `restart`; revert it.

## Common pitfalls and diagnosis

A capstone controller usually fails at the edges, not on the happy path: writing even when observed state already matches, acting on a recreated object with the same name, mutating before validating intent, or starting new work after cancellation. Order the checks as context, ownership, validation, then a write only when state differs. Count writes in tests to prove idempotence.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Converge from a different state: change one input

1. Restate the expected observation: The count becomes 3 with one write.
2. Current differs from desired. What do Current and Writes become?
3. Reconciling to 4 sets Current to 4, so `s.Current==3` fails while Writes is 1. Convergence works; the desired count changed.

### Hint for investigation 2: Repeat without duplicate writes: diagnose an edited check

1. Restate the expected observation: Only the first call writes.
2. The second call finds Current already 3. Does it write again?
3. The second call now wants 4, so it performs a second write and `s.Writes==1` fails. Restore 3 so the repeat matches the converged state.

### Hint for investigation 3: Refuse a replacement object

1. Restate the expected observation: No write occurs and an ownership error is returned.
2. The expected UID differs from the observed one. Does any field change?
3. A reusable name cannot authorize modification of a replacement incarnation.

### Hint for investigation 4: Preserve state on invalid intent

1. Restate the expected observation: The operation fails without mutation.
2. Validation runs before any write. What happens to Current?
3. Validation occurs before state changes.

### Hint for investigation 5: Cancel before new work

1. Restate the expected observation: No write occurs and cancellation is retained.
2. The context check runs first. Is any write recorded?
3. The caller retains control of the work lifetime.

### Hint for investigation 6: Transfer restart reasoning

1. Restate the expected observation: The restarted invocation makes no additional write.
2. The restored state already matches. Does Writes change?
3. Recovery reads current durable state rather than replaying an assumed unfinished command.
