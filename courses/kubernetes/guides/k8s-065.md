# k8s-065: Service meshes, multi-cluster traffic and architectural limits

## Level and prerequisites

Advanced; about 120 minutes. Direct prerequisites: `k8s-064`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Draw a two-cluster request path.
- Defend whether a mesh is justified for a workload.

## Purpose, vocabulary and mental model

A service mesh adds traffic-management, identity or observability capabilities around application communication through a particular implementation. It may use sidecar proxies, node-level components or other designs. It does not remove the underlying need for Pod networking, Service discovery, healthy endpoints and application correctness.

Mutual TLS authenticates both ends of a connection under an identity system. It is not the same as application authorization for a business action. A mesh can establish workload identities while the application still needs to decide whether a caller may read a specific record.

Multi-cluster communication introduces additional discovery, routing, identity and failure-domain boundaries. Overlapping Pod CIDRs, different trust roots, regional latency and partial outages complicate the design. A working single-cluster demo does not qualify a cross-region platform.

### Key terms

- **Service mesh:** An infrastructure layer, often sidecar proxies, that adds traffic management, identity or observability around service communication.
- **Mutual TLS:** TLS in which both ends present certificates and authenticate each other under an identity system.
- **Workload identity:** A cryptographic identity for a workload that policies can authorize, separate from its changing IP address.
- **Multi-cluster:** Running services across several clusters, which adds discovery, routing, identity and failure-domain boundaries such as different trust roots.
- **Retry amplification:** Retries at several layers multiplying load during a failure, which can turn a partial outage into a full one.

## Mechanism and field-by-field reasoning

Draw the actual data and control planes. A mesh control plane distributes configuration and identity material; proxies or equivalent components handle traffic. Failure of one plane can have different effects from failure of the other. Policies and retries must account for idempotency and retry amplification.

This chapter is design and reading practice. The course does not install a mesh, connect clusters or create cloud networks. Use synthetic diagrams to compare when a mesh capability is justified and when application-level libraries or simpler routing are sufficient.

## Trace the request or control path

```text
appA -> local traffic component -> authenticated transport -> remote traffic component -> appB
control plane distributes policy/identity; underlying network still carries packets
second cluster adds discovery, routing and trust boundaries
```

The first line adds two traffic components to the path, one beside each app, and the hop between them is mutually authenticated TLS. The second line is easy to forget: the mesh control plane hands out identities and policy, but the underlying network still carries every packet. The third line multiplies each boundary when a second cluster joins.

## Worked example / walkthrough

### Worked example 1: Separate identity and authorization

A valid workload identity is only one input to policy.

```text
mTLS peer identity: serviceA
application action: read account 123
authorization decision: separate policy for that action
```

**Expected observation:** An authenticated service is not automatically allowed every business operation.

### Worked example 2: Trace retry amplification

The numbers are synthetic.

```text
client makes at most 3 total attempts
proxy makes at most 3 upstream attempts per client attempt
upstream may receive up to 9 attempts without coordinated budgets
```

**Expected observation:** Retries at multiple layers can multiply load and duplicate unsafe operations.

## Six progressive exercises

### Exercise 1: Identify mesh control and data planes.

**Expected evidence:** Configuration/identity distribution versus actual traffic handling.

**Progressive hint:** One part decides policy and certificates; the other handles every byte. Which part sits beside the app?

### Exercise 2: Distinguish mTLS and business authorization.

**Expected evidence:** Peer identity versus permission for a domain-specific action.

**Progressive hint:** mTLS tells the server who is calling. Does it say whether that caller may perform this specific action?

### Exercise 3: Draw a two-cluster request path.

**Expected evidence:** Discovery, inter-cluster route, trust and application hops are named.

**Progressive hint:** Name each hop: discovery of the remote service, the path between clusters, the trust check and the app call.

### Exercise 4: Diagnose retry amplification.

**Expected evidence:** Uncoordinated retry budgets multiply attempts and load.

**Progressive hint:** Count the layers that retry: client, sidecar, gateway. Multiply their attempts.

### Exercise 5: Explain overlapping CIDR risk across clusters.

**Expected evidence:** Address routing can become ambiguous without a deliberate connectivity design.

**Progressive hint:** If both clusters use 10.244.0.0/16, what does a route to 10.244.1.7 mean?

### Exercise 6: Defend whether a mesh is justified for a workload.

**Expected evidence:** Name required capabilities, operational cost and simpler alternatives.

**Progressive hint:** List the capabilities you need, then check whether something simpler already provides them.

## Diagnosis, failure boundaries and common mistakes

Adopting a mesh only for encryption often adds more operational risk than it removes; NetworkPolicy plus application TLS may be enough. When a call fails under strict mTLS, people disable strict mode cluster-wide; read the peer identity and the authorization policy instead. Retry settings at the client, the sidecar and an edge gateway multiply, so three attempts at each of three layers can reach the backend 27 times and duplicate unsafe writes. Joining clusters whose Pod CIDRs overlap breaks direct routing unless the mesh deliberately uses gateways.

Before concluding, record:

- The peer identity presented on the failing hop and the authorization rule that admitted or rejected it.
- Retry counts and timeouts at the client, the sidecar and the gateway, multiplied into a worst case.
- Pod and Service CIDRs of both clusters, checked for overlap before any cross-cluster route is trusted.
- The capability that justifies the mesh, and the simpler alternative you rejected with your reason.
