# CppAD, TMBad and derivative order

Start with: tmb-026, tmb-006.

Outcome: Choose an AD framework for a specific tested derivative target.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter checks first and second finite-difference derivatives of a smooth function. The separately prepared [owned project](../projects/tmb-local/README.md) compiles every model with `framework = "CppAD"` in `R/compile.R`; no TMBad build is part of the project; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

Automatic differentiation is implemented by a concrete library, data representation and set of supported operations. TMB can compile a template using CppAD or TMBad. The statistical objective should remain the same when both support the chosen operations, but memory use, special-function support and higher-order derivative paths can differ.

The framework is selected at compilation. A library built with CppAD is not transformed into TMBad by changing an R option after loading it. Use a fresh native build and compare values, gradients and required curvature against the same independent oracle.

## Key terms

- **CppAD:** An established C++ automatic differentiation library that TMB can compile a template against; this course's native test record covers it.
- **TMBad:** TMB's own automatic differentiation engine, selected with `framework="TMBad"` at compilation, which some paths such as `intern=TRUE` require.
- **intern:** A `MakeADFun` option that performs the Laplace approximation inside the compiled tape; it requires TMBad and can need higher-order special-function derivatives.
- **Derivative order:** How many times an operation must be differentiated; differentiating the Laplace log determinant needs third-order joint derivatives, and `compile(max.order=...)` sets the generated order for certain special functions.

### Worked case A: first and second derivatives agree

The companion differentiates a simple nonlinear scalar function analytically and checks first and second central differences at two points. It demonstrates the target of a framework comparison without pretending to execute either AD backend. In a prepared experimental build directory, compile a copied original model with `framework="TMBad"` and repeat the existing acceptance checks before claiming support.

### Worked case B: why Laplace derivatives require more machinery

The Laplace objective contains a log determinant of a second derivative with respect to latent states. Differentiating that correction requires third-order joint derivatives; taking another derivative can require fourth-order quantities. The companion shows first through fourth derivatives of a small polynomial so the levels are explicit.

TMB's `compile(max.order=...)` controls generated derivative order for certain special functions, not a universal degree of mathematical accuracy. The current manual notes that `intern=TRUE` requires TMBad and that a Hessian of the internal Laplace approximation can need fourth-order special-function support. Increasing `max.order` increases compile time and binary size, so start from a specific required operation.

Automatic parallelization via `openmp(autopar=TRUE)` is experimental and requires a TMBad/OpenMP build. It differs from the explicit `parallel_accumulator` already qualified in the CppAD project. Treat it as a separate capability with separate numerical and resource evidence.

### Answered discussion

**Is TMBad statistically more accurate than CppAD?** Framework choice is not a replacement for model adequacy or approximation analysis. **Do fourth derivatives make Laplace exact?** No. They can differentiate the approximation more completely; the approximation can still be biased. **Can compiler flags such as fast math be enabled casually?** They can change floating-point assumptions and exceptional-value behavior. Requalify exact arithmetic and domain failures before considering them.

See [the pinned compile and MakeADFun documentation](https://cran.r-project.org/web/packages/TMB/TMB.pdf). This course's current native test record covers CppAD. TMBad, internal Laplace and automatic parallelization remain explicitly separate until their own runs are recorded.

### Worked case C: the derivative targets the companion checks

For \(f(x)=e^x+x^4\), the analytic first derivative is \(e^x+4x^3\) and the second is \(e^x+12x^2\). At the two test points:

```text
x      f'(x)        f''(x)       (closed-form values, rounded)
-0.4   0.414320     2.590320
 0.7   3.385753     7.893753
```

At \(x=-0.4\), the quartic term pulls the first derivative down by \(4(0.064)=0.256\) from \(e^{-0.4}=0.670320\); at \(x=0.7\), it adds \(4(0.343)=1.372\) to \(e^{0.7}=2.013753\). The companion prints the difference between central differences and these values. With step \(10^{-4}\), the first-difference truncation error is roughly \(h^2 f'''(x)/6\), well under the \(10^{-6}\) tolerance that `stopifnot` enforces. The second difference divides by \(h^2=10^{-8}\), so cancellation in floating point can leave an error near \(10^{-8}\) or larger; that is why the companion asserts only on the first derivative. An AD framework comparison would replace these finite differences with each backend's exact derivatives and compare both against the same analytic column, with a tolerance near machine precision rather than \(10^{-6}\).

The last line evaluates the derivative ladder of \(x^4\) at 0.5: first 0.5, second 3, third 12, fourth 24. A Laplace objective uses the second derivative of the joint objective inside \(\log\det H\); its gradient needs the third; a Hessian of the Laplace objective needs the fourth. For a quartic term the fourth derivative is a constant 24, but a special function such as a log-gamma or incomplete beta has a nonconstant fourth derivative that the library must implement. That is the case where `max.order` and framework choice become concrete.

### Running the comparison in a prepared build

A framework comparison copies an original model and compiles it twice into separate directories:

```r external
TMB::compile("normal_mean.cpp", framework = "CppAD")
TMB::compile("normal_mean.cpp", framework = "TMBad")
```

Each build then answers the same acceptance request, for instance the `normal_mean` objective at \(\theta=(2.2,0.3)\), whose closed-form value 12.493260 and gradient \((-2.853821,-11.235011)\) are derived in chapter 23. Agreement of both builds with that oracle, and not agreement between the builds alone, is the evidence that the second framework supports this model. Disagreement in the tenth digit is expected floating-point variation; disagreement in the third digit points to an unsupported operation or a build that loaded the wrong library.

### Base-R companion (runs in the classroom)

```r
f <- function(x) exp(x) + x^4
for (x in c(-.4, .7)) {
  h <- 1e-4
  numeric_first <- (f(x + h) - f(x - h)) / (2 * h)
  numeric_second <- (f(x + h) - 2 * f(x) + f(x - h)) / h^2
  print(c(x = x, first_error = numeric_first - (exp(x) + 4 * x^3), second_error = numeric_second - (exp(x) + 12 * x^2)))
  stopifnot(abs(numeric_first - (exp(x) + 4 * x^3)) < 1e-6)
}
x <- .5
print(c(first = 4 * x^3, second = 12 * x^2, third = 24 * x, fourth = 24))
```
