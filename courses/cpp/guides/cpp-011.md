# cpp-011: Files, streams and scoped resources

## Level and prerequisites

Beginner; 105 minutes. Direct prerequisites: `cpp-006`, `cpp-009`.

Learner artifact: [cpp-011.cpp](../lessons/cpp-011.cpp). [Case ledger](../fixtures/cpp-011-cases.json). [Solutions](../solutions/cpp-011_solutions.md).

## Learning objectives

Read a text fixture while distinguishing EOF, parse failure and an I/O error.

## Vocabulary and concepts

A stream is an interface that moves characters between a program and a source or destination. RAII ties resource cleanup to scope exit. EOF means there is no more input, while a bad I/O state means a device operation failed. The loop must ask whether a read succeeded before using the buffer.

<!-- terms:start -->

- **stream:** an object that moves characters between a program and a source or destination and records whether its last operation succeeded.
- **`getline`:** extracts the next line and reports through the stream whether that extraction succeeded.
- **EOF:** the condition that no more input remains, which is set only after a read attempts to go past the available data.
- **bad I/O state:** a stream condition meaning an underlying device operation failed, which differs from reaching EOF.
- **RAII:** tying resource cleanup to scope exit, so a file stream closes its file when the stream object is destroyed.

<!-- terms:end -->

## Syntax and mechanism

`while (std::getline(input,line))` reads one line, then enters the body only on success. Testing eof before reading processes stale data after a failed read. File paths are resolved against the process working directory, which can differ from the source directory.

## Trace the mechanism

The getline expression reads before the body. With 10-newline-20-newline it succeeds twice; the next attempt discovers EOF and the body does not run. An eof-first loop asks yesterday's state and can reuse yesterday's buffer. For real files, opening failure, clean EOF and a bad device state are different observations. Record the resolved filename before diagnosing a missing file; changing main.cpp's location cannot change the process working directory.

## Streams, EOF and resource lifetime

A stream has both data and state. getline attempts to extract the next line and reports whether that extraction succeeded. The loop condition must test the result of the read before using the line. The pattern while(!input.eof()) checks a state that may not become true until a read attempts to go beyond the available input, so it can process a stale or failed buffer on the final iteration.

A newline is a separator, not necessarily a required terminator for the final record. The first complete program reads 10 and 20 from a string containing two newline separators. The second reads 30 from a final line with no trailing newline. Both are successful line extractions. A completely empty stream yields no line, while a stream containing one newline yields one empty line. Your data grammar must decide whether an empty record is valid or rejected.

EOF and bad I/O are different conditions. Reaching the end of an otherwise valid input is expected. A device or stream-buffer failure needs an error path. The reference checks bad() after the loop to distinguish that failure from ordinary exhaustion. A file reader must also check whether opening the file succeeded before treating it as a useful source; an unopened stream should not be reported as a valid empty dataset.

RAII ties the file resource to the stream object's lifetime. An ifstream closes its resource when destroyed, including during exception unwinding. That prevents a forgotten close on one error path, but it does not validate the data read or guarantee a successful write. For output, inspect the stream state after writing and closing when the contract needs confirmation that output was accepted by the stream.

A relative file path is resolved against the process working directory. Compiling a source in one folder does not make runtime reads relative to that source file. Record the input path and working directory when diagnosing a missing file. The browser runner stages a single source and has a controlled filesystem; a host file exercise must use an owned fixture directory and the explicit commands in the compile/run guide.

## Run and inspect

The pad reads three in-memory streams: `"10\n20\n"` gives exactly `{"10", "20"}`, an empty stream gives no lines and `"30"` without a final newline gives one line. Nothing touches the filesystem, so a failure here is a read-loop bug, never a path or working-directory problem. Pad routine: [study guide](../STUDY-GUIDE.md#run-a-lesson-pad). Commands and flags: [compile and run tutorial](../compile-and-run.md).

## Worked example / walkthrough

Example 1 reads `"10\n20\n"` through a `std::istringstream` and gets two lines. Example 2 reads `"30"` with no trailing newline and still gets one line, because `std::getline` returns the final partial line before it reports end of input. Neither example opens a file, so the working directory cannot change these results. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-011-example-1.cpp)

```cpp
#include <cassert>
#include <iostream>
#include <sstream>
#include <stdexcept>
#include <string>
#include <vector>

std::vector<std::string> read_lines(std::istream &input) {
  std::vector<std::string> out;
  std::string line;
  while (std::getline(input, line))
    out.push_back(line);
  if (input.bad())
    throw std::runtime_error("read failed");
  return out;
}
int main() {
  std::istringstream input("10\n20\n");
  auto lines = read_lines(input);
  assert(lines.size() == 2);
  std::cout << "cpp-011 example 1 checks passed\n";
  return 0;
}
```

**Expected:** With assertions enabled, the program exits with status 0 and prints:

```text

```

## Exercises

### Exercise 1: Trace successful reads

Read the literal 10-newline-20-newline fixture.

**Expected result/shape:** Two records [10, 20].

**Verify:** Assert `read_lines` on the fixture returns exactly `{"10", "20"}`; the final newline must not create a third, empty record.

**Progressive hints:** getline determines whether a record exists.

### Exercise 2: Handle empty input

Run read_lines on an empty string stream.

**Expected result/shape:** Zero records, ordinary EOF.

**Verify:** Assert `read_lines(input).empty()` for an empty `std::istringstream` and that no `std::runtime_error` is thrown, because end of input without `bad()` is not a read failure.

**Progressive hints:** Empty input is not automatically an I/O device error.

### Exercise 3: Write an owned file

In a new scratch directory write two lines, close, reopen and read.

**Expected result/shape:** The reopened bytes represent 10 and 20 exactly once.

**Verify:** After closing the `std::ofstream`, read the file back through `read_lines` and assert the result is `{"10", "20"}`; any other size means the write was not flushed or was appended twice.

**Progressive hints:** Close or flush before reading through a second stream.

### Exercise 4: Repair eof-first looping

Compare while(!eof()) with the supplied successful-read loop.

**Expected result/shape:** The repaired loop has two records and no stale extra line.

**Verify:** Run both loops on the 10-newline-20-newline fixture: the eof-first loop records a third, empty line, while the `getline` loop must produce exactly two records.

**Progressive hints:** EOF becomes known only after a read attempts the boundary.

### Exercise 5: Check open failure

Open missing-file.txt for input in a new empty scratch directory.

**Expected result/shape:** is_open false or stream failure; report the path and stop.

**Verify:** Assert `!std::ifstream("missing-file.txt").is_open()`, and check that your error message names `missing-file.txt` and that no record is processed afterward.

**Progressive hints:** A missing file must not silently become an empty successful report.

### Exercise 6: Transfer the path contract

Run from two working directories with the same relative filename.

**Expected result/shape:** Different resolved locations; explicit supplied path selects one file.

**Verify:** Print `std::filesystem::absolute("input.txt")` from each working directory and confirm the two paths differ, then pass one absolute path explicitly and confirm both runs read the same file.

**Progressive hints:** The current directory, not main.cpp location, anchors relative paths.

## Self-check

Why does `"10\n20\n"` produce exactly two lines and not a stale third? For Example 2, explain why `std::getline` still returns `"30"` when no newline ends the input.

## Common pitfalls

If the last record repeats, look for an eof-before-read loop. If a final unterminated line disappears, inspect whether the parser requires a newline accidentally. If a missing file reports zero accepted rows and success, the open failure was probably ignored. If only Windows input fails, define carriage-return handling explicitly rather than silently altering bytes without a format contract. Test empty input, an empty line and no-final-newline as three different fixtures.

## Retrieval and transfer

Close the source and redo Exercise 6: the same relative file name resolves to different files from two working directories, and an explicit path selects one. Explain why the in-memory pad never met this problem. Then name what a deployed program must decide about paths, permissions and file encodings.
