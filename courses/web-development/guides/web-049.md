# web-049: CSRF defenses and deliberate state-changing requests

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-048`

## Learning objectives

Build a state-change decision that checks method, token and authorization. Explain the relationship between CSRF, SameSite and XSS. Use CSRF, synchronizer token and constant-time comparison accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

Cross-site request forgery exploits a browser's ability to send credentials with a request that the user did not intend. A state-changing endpoint must distinguish an authorized user's deliberate action from a request induced by another site. A synchronizer-token design stores an unpredictable token in the user's server session and requires the same token in the submitted form or appropriate request header.

The token must be generated with a cryptographically secure source, kept out of URLs and checked before changing state. SameSite cookies and origin checks can add protection but do not eliminate the need to understand the application's request paths. XSS can undermine CSRF defenses because malicious script running in the application's own origin may access tokens or perform actions.

### Key terms

- **CSRF:** Cross-site request forgery, an attack where another site makes the user's browser send an authenticated state-changing request.
- **Synchronizer token:** A random per-session value embedded in each form and checked on submission, which a cross-site page cannot read.
- **Constant-time comparison:** Comparing secrets with `hash_equals()`, whose timing does not reveal where two strings first differ.
- **SameSite:** A cookie attribute that keeps the browser from sending the cookie with most cross-site requests, a defense in depth rather than a replacement for tokens.

## Syntax anatomy and mechanism

Generate token bytes with random_bytes and encode them for transport. Compare a validated submitted string with the known session token using hash_equals. Reject absent, wrong-type and empty values before a state change. The deterministic CLI fixture uses a clearly fake fixed token to test comparison logic; it is not a production token generator or proof of a browser defense.

## Classroom execution and offline inputs

The worked examples generate a production token from 32 random bytes and compare a submitted token exactly. You build validCsrf and a mayChange decision that requires POST, a matching string token and an owner match before any state change.

## Worked example / walkthrough

### Worked example 1: Production token generation

The value should be unpredictable and bound to the session.

```php
$token = bin2hex(random_bytes(32));
```

**Expected observation:** A real server obtains a 64-character hexadecimal token from 32 random bytes.

### Worked example 2: Comparison at the boundary

The trusted token is the first argument.

```php
$valid = is_string($submitted) && hash_equals($sessionToken, $submitted);
```

**Expected observation:** Only an exact matching submitted string is accepted.

## Contrast case: loose comparison when the session has no token

The session expired, so no token is stored. A forged request omits the token field too.

```php
$sessionToken = $_SESSION['csrf'] ?? null;
$submitted = $_POST['csrf'] ?? null;

if ($submitted == $sessionToken) {
  // state change runs here
}

$valid = is_string($sessionToken) && $sessionToken !== ''
  && is_string($submitted) && hash_equals($sessionToken, $submitted);
```

Both variables are null, and `null == null` is true, so the loose version performs the state change for a request that carried no token at all. The strict version first requires both values to be nonempty strings, so the same request fails before any comparison. `hash_equals` then compares in time that does not depend on where the strings first differ. It requires two strings, which is another reason the type checks come first.

## Six progressive exercises

Exercises 1, 4 and 6 keep their expected answers in the solutions file.

### Exercise 1: Explain why a hidden form field alone does not prevent CSRF.

**Progressive hint:** Ask whether an attacker's page could include the same hidden field.

### Exercise 2: Add wrong-type and missing-token rejection.

**Expected evidence:** Array, null and absent values cannot reach a successful comparison.

**Progressive hint:** Check the type and emptiness of the submitted token before comparing.

### Exercise 3: Build a state-change decision that checks method, token and authorization.

**Expected evidence:** Only a deliberate allowed POST with matching token can reach the mutation branch.

**Progressive hint:** Combine three checks: the method, the token and whether the actor owns the object.

### Exercise 4: Diagnose a token placed in a URL.

**Progressive hint:** List every place a URL is recorded on its way to the server.

### Exercise 5: Test mismatched, empty and matching synthetic tokens.

**Expected evidence:** Only the exact nonempty expected token passes the local comparison contract.

**Progressive hint:** Compare the matching token with a token that differs by one character and an empty token.

### Exercise 6: Explain the relationship between CSRF, SameSite and XSS.

**Progressive hint:** Ask what each mechanism stops and what a same-origin script can still do.

## Debugging and common mistakes

Do not reuse the fixed teaching token in a live server. Do not let a CSRF pass stand in for authorization. Never mutate state before completing the token decision and then try to undo it afterward.

When a wrong token is accepted, check that both values are strings and that comparison uses hash_equals, since a loose comparison with a missing session token can pass. When a GET request reaches the mutation, the method check is missing or placed after the change.

The shared [debugging routine](../STUDY-GUIDE.md#debugging-php) covers what to record before each repair.
