# asm-020: Generated operator code and evaluation fallback

Tutorial mode. Stage: advanced. Direct prerequisites: `asm-019`, `spark-026`.

## Starting point and result

Whole-stage code generation combines supported physical operators into generated JVM code, reducing some interpretation and virtual-call overhead. It is not a universal compiler for every library invoked from Spark. This chapter prints generated code for native arithmetic and verifies equivalent results with whole-stage generation disabled.

## Mechanism: compiled operators retain SQL semantics

The physical engine may fuse adjacent supported operations into one generated stage. The generated source includes field access, null tracking, arithmetic and output handling. JVM compilation then turns that source into executable code. Unsupported expressions or operators can introduce boundaries or fallback behavior. A Scala UDF may still be called from generated code without its internal semantics becoming an optimizer-visible expression.

Changing `spark.sql.codegen.wholeStage` affects whole-stage fusion. It does not mean every remaining operation is interpreted by Python, nor does disabling it remove all generated projections everywhere. Use precise claims: this experiment compares the configured whole-stage modes for the declared query.

Generated and non-fused execution must preserve the same semantics. Code generation is not permission to ignore nulls, overflow policy, input types or exceptions. A custom expression with separate evaluated and generated implementations must test both. Divergence is a correctness defect even if one implementation is faster.

## Worked case: square plus one

For integers zero through nine, the query computes \(x^2+1\). With whole-stage code generation enabled, `explain("codegen")` prints the relevant generated source. Collecting results executes the query. The expected values are calculated independently using Scala arithmetic over the same bounded range.

The integers are deliberately small, so multiplication cannot overflow a long. This isolates the mechanism. Larger values require an explicit overflow contract, especially when ANSI settings change error behavior. A proof over the small fixture does not establish semantics for every long integer.

## Worked case: turn fusion off and compare

The program changes the configuration, creates a fresh query and collects it. Reusing an already materialized result would not test the new mode. The two result sequences must match exactly for this integer fixture. The physical plan in the second mode explains which operator structure remains.

No speed claim is made. The cost of starting Spark and compiling a tiny expression can overwhelm the arithmetic. A useful benchmark should include warmup, enough data, repeated measured actions, resource limits and complete output validation. Generated-code size and compilation time can also become costs for very wide expressions.

## Failure diagnosis

If toggling code generation changes results, inspect whether the two queries truly use the same source, schema and configuration. For custom expressions, compare null handling and type casts in both paths. If compilation fails, retain the generated source and exact exception rather than silently changing modes and claiming equivalence. If performance worsens, check compilation overhead and code-size limits before adding more custom fusion.

## Interview discussion

**Does codegen make Spark an automatic differentiation framework?** No. It generates executable code for supported query operations. Derivative rules, parameter tracking and differentiation of a computation graph are separate mechanisms.

**Can generated code call a custom function?** Yes. That does not necessarily inline or algebraically understand the function. Distinguish a call inside generated execution from a custom Catalyst expression with explicit semantics.

## Complete reproducible program

Run this complete source in its declared prepared Spark profile. The fixture is tiny, deterministic and offline. Scala sources are compiled before execution; Python sources use the prepared PySpark environment. These are worked tutorials with no hidden solutions or exams. Runtime: `spark-local-scala`.

```scala
import org.apache.spark.sql.{SparkSession, DataFrame, Dataset, Encoder, Encoders}
import org.apache.spark.sql.functions._

object Main {
  def main(args: Array[String]): Unit = {
    val spark = SparkSession.builder
      .master("local[2]")
      .appName("advanced-spark-modeling")
      .config("spark.ui.enabled", "false")
      .config("spark.driver.host", "127.0.0.1")
      .config("spark.driver.bindAddress", "127.0.0.1")
      .config("spark.sql.shuffle.partitions", "2")
      .config("spark.sql.adaptive.enabled", "false")
      .config("spark.sql.ansi.enabled", "true")
      .getOrCreate()
    require(spark.version == "4.0.1", "This example targets Spark 4.0.1")
    spark.sparkContext.setLogLevel("ERROR")
    import spark.implicits._
    try {
      val input = spark.range(0, 10, 1, 2)
      def query = input.select((col("id") * col("id") + lit(1L)).as("value"))
      spark.conf.set("spark.sql.codegen.wholeStage", "true")
      val generated = query
      generated.explain("codegen")
      val expected = generated.as[Long].collect().toSeq
      spark.conf.set("spark.sql.codegen.wholeStage", "false")
      val interpreted = query
      interpreted.explain("formatted")
      require(interpreted.as[Long].collect().toSeq == expected)
      require(expected == (0L until 10L).map(x => x * x + 1L))
      println(
        "Whole-stage on/off parity passed; codegen output is compiler evidence, not a timing benchmark"
      )
    } finally { spark.stop() }
  }
}
```
