# web-049: CSRF defenses and deliberate state-changing requests

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-048`

## Learning objectives

Build a state-change decision that checks method, token and authorization. Explain the relationship between CSRF, SameSite and XSS. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

Cross-site request forgery exploits a browser's ability to send credentials with a request that the user did not intend. A state-changing endpoint must distinguish an authorized user's deliberate action from a request induced by another site. A synchronizer-token design stores an unpredictable token in the user's server session and requires the same token in the submitted form or appropriate request header.

The token must be generated with a cryptographically secure source, kept out of URLs and checked before changing state. SameSite cookies and origin checks can add protection but do not eliminate the need to understand the application's request paths. XSS can undermine CSRF defenses because malicious script running in the application's own origin may access tokens or perform actions.

## Syntax anatomy and mechanism

Generate token bytes with random_bytes and encode them for transport. Compare a validated submitted string with the known session token using hash_equals. Reject absent, wrong-type and empty values before a state change. The deterministic CLI fixture uses a clearly fake fixed token to test comparison logic; it is not a production token generator or proof of a browser defense.

## Classroom execution and offline inputs

Choose the **PHP CLI** worker in the classroom. The pad is staged as `main.php` and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write `<?php` at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

## Worked example / walkthrough

### Worked example 1: Production token generation

The value should be unpredictable and bound to the session.

```php
$token = bin2hex(random_bytes(32));
```

**Expected observation:** A real server obtains a 64-character hexadecimal token from 32 random bytes.

### Worked example 2: Comparison at the boundary

The trusted token is the first argument.

```php
$valid = is_string($submitted) && hash_equals($sessionToken, $submitted);
```

**Expected observation:** Only an exact matching submitted string is accepted.

## Six progressive exercises

### Exercise 1: Explain why a hidden form field alone does not prevent CSRF.

**Expected evidence:** The server must verify an unpredictable session-bound value, not merely the presence of a field.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add wrong-type and missing-token rejection.

**Expected evidence:** Array, null and absent values cannot reach a successful comparison.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a state-change decision that checks method, token and authorization.

**Expected evidence:** Only a deliberate allowed POST with matching token can reach the mutation branch.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a token placed in a URL.

**Expected evidence:** URLs can leak through logs, history and referrers, so use the appropriate body or header channel.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test mismatched, empty and matching synthetic tokens.

**Expected evidence:** Only the exact nonempty expected token passes the local comparison contract.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain the relationship between CSRF, SameSite and XSS.

**Expected evidence:** They are distinct mechanisms; SameSite supports CSRF defenses while same-origin script injection can defeat them.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not reuse the fixed teaching token in a live server. Do not let a CSRF pass stand in for authorization. Never mutate state before completing the token decision and then try to undo it afterward.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain CSRF, synchronizer token, constant-time comparison without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
