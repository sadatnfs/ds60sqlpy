# dme-050: Capstone: late data, replay and backfill repair

## Reconcile incremental state with a full recomputation

An incremental pipeline updates accepted state as events arrive. A batch recomputation derives the same intended state from the full retained history. When both are available on a small fixture, their agreement is a powerful correctness check. The implementations should be independent enough to catch a shared conceptual mistake: one uses actual database transitions, while the other scans and orders a finite history directly in Python.

This capstone stores source events and current entity state in a real SQLite file. Events have a source event ID, entity ID, source revision, route and package count. A source event ID identifies one delivered change. An entity ID identifies the business object whose state can evolve. A source revision orders that entity's replacements. These identities must remain separate: replaying the same event is different from accepting a newer state for the same entity.

The current-state table holds one row per entity. Its route aggregate should equal a full-history oracle that selects the latest consistent revision of each entity:

\[
S_r=\sum_{e:\,r_e^{*}=r}p_e^{*},
\qquad (r_e^{*},p_e^{*})=\operatorname{latest}_{v}(H_e).
\]

An append sum over every event is not the same quantity. It would include superseded values and repeated deliveries. The source history remains valuable for audit and recomputation, while the current table supports efficient state queries.

## Preserve history and current state atomically

`apply` accepts a bounded batch and validates event shape, positive revisions, known routes and positive package counts. Inside one SQLite write transaction, it checks whether each source event ID has already been recorded. Identical replay returns a replay decision. Reusing that event ID with different content is rejected.

The code also checks historical `(entity, revision)` content, even when that revision is older than the currently accepted state. Two different source event IDs must not assert contradictory values for the same entity revision. Looking only at the current row would miss a conflict in an older revision. Preserving consistent history matters because a later rebuild or investigation may depend on those older records.

A newly identified event enters the event log. It replaces current state only when its entity revision is newer. An older or identical state cannot overwrite a newer accepted state. The transaction covers both the event log and current table, so a later conflict in the same batch rolls back earlier changes from that batch. This avoids a partially applied delivery whose receipt appears wholly rejected.

## Worked case 1: replay does not create new business state

`example_one()` starts with A at revision 1 carrying two packages on route 10, B carrying three on route 10, and C carrying one on route 20. A revision 2 changes A's package count to four. The history then repeats A's original source event. There are five arrival positions but only four unique source events and three current entities.

The accepted route totals are 10: seven and 20: one. The independent oracle reconstructs the same result from the finite history. It deduplicates source identities, rejects contradictory revision content and selects the latest revision per entity before grouping. The database result and oracle must agree exactly on route keys and integer values.

Reapplying the entire history produces only replay decisions and leaves the current totals unchanged. The event log does not grow merely because transport or a caller repeats an already accepted delivery. This is more precise than saying “the job is idempotent”: the example states which event identities and contents are held fixed and which accepted state is expected to remain stable.

## Worked case 2: restart, move an entity and reject a partial conflicting batch

The second case writes the initial three events, closes the connection and reopens the same database file. This is actual durable state across connection lifetime, not an in-memory set preserved by a Python variable. It then accepts A revision 2 with four packages on route 20 and replays the old A event.

The correct totals become route 10: three and route 20: five. A's old two-package contribution is no longer part of north, while its new four-package contribution joins C's one in south. Grouping the current table implements the required retraction and replacement without treating the new state as an additive fact. The full-history oracle agrees after the route change.

The example then submits a batch that first adds D and then reuses B's existing event ID with a conflicting count of 100. The conflict rejects the transaction. D does not remain as a partial effect, the event log still has four unique events, and the current table still has three entities. The accepted route totals remain three and five. This changed condition tests atomic rejection after some work has already occurred inside the transaction.

## Late data and backfills need one interpretation

A late arrival can be an old source event, a new correction with a higher revision, or a previously unseen event that belongs to an earlier business interval. Those cases require different actions. Arrival time alone does not decide which state wins. The source's revision and event contract must supply the authority, while the pipeline records when the information became available for historical decisions.

A full recomputation can repair derived state when the retained history is complete and consistent. It cannot recover events that were never captured or reconstruct deleted information without another source. Before rebuilding, establish the source snapshot, retention horizon and transformation version. The earlier backfill chapter uses explicit partition revisions to prevent a broad historical repair from overwriting newer accepted corrections.

For a large system, recomputing all history on every event is impractical. The small independent oracle remains useful in unit tests, sampled reconciliation and bounded incident investigations. Production reconciliation may compare partition counts, keyed hashes or aggregates, then narrow discrepancies to specific entities. Aggregate checks can locate a problem but should not be mistaken for a full identity-level proof.

## Deletion and source capture remain separate boundaries

This capstone uses positive full-state replacements. A deletion would need an explicit tombstone and ordering rule, as introduced in the change-data chapter. Removing a current row without retaining a sufficient deletion version can allow an older replay to recreate it. Retention of source history and tombstones must be coordinated with the supported replay horizon.

The code applies already supplied synthetic events. It does not capture a live database's change log. Actual CDC requires source configuration, offsets, snapshots, transaction boundaries and recovery semantics at the capture connector. A perfectly correct state-application function cannot compensate for missing or reordered source information that violates its declared input contract. Use the actual Apache broker and service workshops for those transport observations.

## Diagnose divergence before choosing a repair

If incremental totals differ from the batch oracle, first compare the source event population and entity revisions. A missing event, duplicate effect, changed route and conflicting revision produce different signatures. Inspect whether the source event ID was reused, whether a stale revision overwrote a newer row, and whether a failed batch left partial changes.

If a rebuild matches aggregates but not entity identities, do not declare success. Two mistakes can cancel numerically. If the source history itself contains contradictory equal revisions, preserve the conflict and request an authoritative correction rather than choosing the most recently ingested row arbitrarily. A repair that silently changes the conflict rule can make future replay disagree with the original accepted state.

## Applications and answered interview discussion

This pattern applies to entity-state materialization, operational feature tables and analytical serving from replacement events. It also provides a disciplined way to test an incremental optimization against a simpler complete calculation. Preserve the simpler oracle even after the production implementation becomes more sophisticated.

An interviewer may ask, “How do you know the streaming result matches batch?” Explain shared semantics, independent implementations, exact fixture comparisons and broader reconciliation. If asked how late events are handled, distinguish replay, stale state and higher-revision correction. If asked why an event log and current table are both useful, explain historical evidence versus efficient current queries and the transaction that keeps them consistent.

For an answered extension, send a different event ID that claims A revision 1 had 200 packages after revision 2 is already current. The current total might otherwise stay unchanged, but the historical conflict must still be rejected. Future rebuild correctness depends on a consistent history, not only on today's visible total.
