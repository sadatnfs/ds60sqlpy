# k8s-062: Probes, graceful draining and rollout traffic continuity

## Level and prerequisites

Advanced; about 120 minutes. Direct prerequisites: `k8s-061`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Design a graceful shutdown timeline.
- Define rollout traffic-continuity acceptance.

## Purpose, vocabulary and mental model

Startup, readiness and liveness probes answer different questions. A startup probe can allow an application time to initialize before other probe behavior begins. Readiness indicates whether the Pod should receive ordinary new traffic. Liveness asks whether restarting the container is an appropriate recovery action.

A dependency outage is not always a reason to restart every client. If a liveness check fails whenever a database is briefly unavailable, the system can create a restart storm without repairing the database. Probe design should reflect the application’s recovery capabilities and failure modes.

Graceful termination coordinates endpoint eligibility, connection draining and process shutdown. Removing readiness does not instantly terminate every existing connection or guarantee every proxy has updated. A rollout must account for propagation, in-flight requests, termination grace periods and the application’s own shutdown behavior.

### Key terms

- **Restart storm:** Many restarts at once, often from a too strict probe or a shared dependency failure, which adds load and slows recovery.
- **Graceful termination:** A shutdown in which a Pod stops receiving new traffic, finishes in-flight work and exits before it is forcibly killed.
- **Connection draining:** Letting existing connections finish while no new ones arrive, so in-flight requests are not cut off.
- **Termination grace period:** The time between the termination signal and forced termination. Shutdown work must fit inside it.

## Mechanism and field-by-field reasoning

Set probe paths, ports, timeouts and thresholds according to measured startup and request behavior. A failure threshold is not a proof that an application will recover by the next attempt. Keep startup allowance separate from a per-request deadline.

During a rollout, inspect desired generation, updated replicas, ready endpoints and actual responses from the intended revision. An old healthy replica can keep a Service responding while the new revision fails. A 200 response alone does not prove rollout completion.

## Trace the request or control path

```text
new Pod starts -> startup condition -> readiness -> eligible new traffic
old Pod terminates -> readiness/endpoint transition -> drain -> process exits
existing connections and controller propagation need bounded handling
```

Read the first line as gates in order: a startup probe must pass before the others count, then readiness admits the Pod to new traffic. The second line runs in reverse for the old Pod: it leaves the endpoint set, drains in-flight work and exits. The third line warns that endpoint removal reaches every node only after a delay.

## Worked example / walkthrough

### Worked example 1: Classify three probe purposes

The same endpoint should not be copied blindly into all three roles.

```text
startup: initialization is complete
readiness: can accept intended work now
liveness: restart is a justified recovery action
```

**Expected observation:** Each check has a different operational consequence.

### Worked example 2: Diagnose a masked failed rollout

This is a synthetic observation.

```text
old revision: 2 Ready Pods
new revision: 2 Pods failing readiness
Service request: 200 from old revision
```

**Expected observation:** Availability can remain while the intended new revision is not accepted.

## Six progressive exercises

### Exercise 1: Predict a readiness failure consequence.

**Expected evidence:** Ordinary new Service eligibility changes without necessarily restarting the container.

**Progressive hint:** Readiness and liveness have different consequences. Which restarts the container and which only changes traffic?

### Exercise 2: Choose a startup allowance for a slow initializer.

**Expected evidence:** A bounded measured initialization window with separate request deadlines.

**Progressive hint:** Measure how long initialization actually takes, then set the window from that measurement plus a margin.

### Exercise 3: Design a graceful shutdown timeline.

**Expected evidence:** Stop new work, drain bounded in-flight work and exit before forced termination.

**Progressive hint:** Order the shutdown: stop accepting, finish running work, exit. Place the grace period and preStop on that line.

### Exercise 4: Diagnose 200 responses during a failed new rollout.

**Expected evidence:** Identify the serving revision and new-revision readiness separately.

**Progressive hint:** A 200 proves some Pod answered. Which revision does that Pod belong to?

### Exercise 5: Explain why database-dependent liveness can be harmful.

**Expected evidence:** It may restart healthy clients without fixing the unavailable dependency.

**Progressive hint:** If the database is down, what does restarting the web container fix?

### Exercise 6: Define rollout traffic-continuity acceptance.

**Expected evidence:** Current revision becomes ready, expected responses succeed and old resources drain/clean up.

**Progressive hint:** Name the evidence for the new revision, the responses during the switch and the fate of the old ReplicaSet.

## Diagnosis, failure boundaries and common mistakes

Using liveness for dependency checks is the most damaging probe mistake: a database outage then restarts every web Pod in a loop, adding load and fixing nothing. Keep liveness for a wedged process. Another mistake is declaring a rollout fine because requests still return 200; old Pods can carry all traffic while the new revision fails readiness, so read updatedReplicas and the ReplicaSet revision. On shutdown, a process that exits the instant it receives SIGTERM drops in-flight requests, because endpoint removal reaches nodes later; a short preStop pause or a graceful drain covers that gap.

Before concluding, record:

- Each probe's endpoint, periodSeconds and failureThreshold, plus its consequence: a restart or removal from endpoints.
- The startup allowance as failureThreshold times periodSeconds, compared with the measured initialization time.
- `terminationGracePeriodSeconds` beside any preStop delay and the app's own drain deadline; all three must fit.
- updatedReplicas, readyReplicas and the ReplicaSet revision that served each successful response.

General evidence rules: [diagnosis rules](../STUDY-GUIDE.md#diagnosis-rules).
