# web-001: A web page: source, browser and server

## Level and prerequisites

Beginner; allow about 90 minutes, with extra time for independent practice. Direct prerequisites: None. This lesson explains the necessary vocabulary.

## Learning objectives

Build a complete document with a title, one heading and two paragraphs. Trace a requested page from source to visible output. Use HTML, CSS and HTTP accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

HTML is a markup language: it names the structure and meaning of a document. CSS is a style language that controls how that structure is presented. JavaScript is a programming language executed by the browser or another host. PHP is a programming language commonly executed by a server. A visitor receives the server's response, not the PHP source that generated it. These layers can cooperate without becoming interchangeable.

A browser parses HTML into a document tree, applies style rules and paints pixels. A server accepts a request and returns a response. Opening a local preview exercises the browser portion; it does not demonstrate a network request, authentication or a server database. Our first document is deliberately small enough to inspect every character and every visible element.

### Key terms

- **HTML:** The markup language that names the structure and meaning of a document, such as headings, paragraphs and links.
- **CSS:** The style language that controls how HTML structure is presented, including color, spacing and layout.
- **Browser:** The program that requests resources, parses HTML and CSS into trees and renders the page a reader sees.
- **Server:** A program that answers HTTP requests by returning resources such as an HTML document, a stylesheet or an image.
- **HTTP:** The request and response protocol a browser uses to ask a server for a resource and receive a status, headers and a body.

## Syntax anatomy and mechanism

An element such as `<p>Hello</p>` has an opening tag, content and a closing tag. The tag names the kind of content. A document begins with `<!doctype html>` to request standards rendering, then an `html` root containing `head` metadata and `body` visible content. The `title` labels the browser document, while an `h1` labels the visible topic. Whitespace in ordinary text is generally collapsed, so source indentation helps humans without creating layout.

## Worked example / walkthrough

### Worked example 1: One paragraph

Read the tag boundaries before considering appearance.

```html
<p>Hello, web.</p>
```

**Expected observation:** One text paragraph; the angle-bracket markup is not shown.

### Worked example 2: Metadata and visible content

Both titles matter, but they occupy different places.

```html
<title>My course notes</title>
<h1>Learning the web</h1>
```

**Expected observation:** The document title and visible heading can differ.

## Contrast case: a misnested paragraph the parser repairs

Paste this fragment into the body of the starter document and open the Elements panel instead of View Source.

```html
<p>First idea
<div>A block inside the paragraph</div>
</p>
```

A `div` cannot live inside a `p`, so the parser closes the paragraph as soon as it meets `<div>`. The tree then holds a paragraph containing only First idea, a sibling `div`, and a second, empty paragraph created from the stray `</p>`. View Source still shows one paragraph, which is why this lesson asks you to read the parsed tree. Replace the `div` with a `span` and the repair disappears: one paragraph with two text runs. The visible words barely change, so only the tree reveals the difference.

## Six progressive exercises

Exercises 1, 4 and 6 keep their expected answers in the solutions file.

### Exercise 1: Predict which text from the first example is visible.

**Progressive hint:** Separate what belongs to the head, such as the title, from what the browser paints in the body.

### Exercise 2: Change a paragraph without changing the document title.

**Expected evidence:** The visible body changes while the browser document title remains the same.

**Progressive hint:** Find which element feeds the tab label and which feeds the page, then edit only the second.

### Exercise 3: Build a complete document with a title, one heading and two paragraphs.

**Expected evidence:** The preview contains one main heading and two paragraphs inside the body.

**Progressive hint:** Start from the doctype, then html with lang, head with charset and title, and body; add the heading and paragraphs last.

### Exercise 4: Explain why PHP source pasted into an HTML page does not execute in the browser preview.

**Progressive hint:** Ask which program reads this file in the preview and whether it understands `<?php`.

### Exercise 5: Remove the styling and inspect what remains useful.

**Expected evidence:** Document structure and readable text remain; meaning does not depend on CSS.

**Progressive hint:** Delete the style element temporarily and read the page from top to bottom.

### Exercise 6: Trace a requested page from source to visible output.

**Progressive hint:** List the stages in order: bytes received, tree built, styles applied, pixels painted.

## Debugging and common mistakes

Do not call every file a website or every successful preview a deployed server. Inspect the actual title and body separately. Closing a paragraph with the wrong tag may be repaired by the parser, producing a different tree than the source suggests.

When text appears in the tab but not the page, it is in the title element inside head, which the browser never paints in the body. When a stray closing tag seems to do nothing, open the Elements panel: the parser has already rebuilt the tree, and that rebuilt tree, not your source, is what the page uses.

The shared [debugging routine](../STUDY-GUIDE.md#debugging-html) covers what to record before each repair.

## Retrieval, transfer and next steps

Without notes, say what the browser does with a tag it reads and what it does with the text between tags. Then explain why the page title and the main heading can disagree, why PHP source shows as plain text in this preview, and which request in your trace would happen only when a real server is involved.

Revisit the worked examples when an output is predictable but unexplained ([review loop](../STUDY-GUIDE.md#review-loop)).
