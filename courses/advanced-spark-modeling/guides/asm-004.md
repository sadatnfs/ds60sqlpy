# asm-004: Whole-group memory, shuffle and skew

Tutorial mode. Stage: beginner. Direct prerequisites: `asm-003`, `spark-022`.

## Starting point and result

Parallel independent fitting can fail for a reason unrelated to the optimizer: one group does not fit in a worker's memory. This chapter separates group size, partition count, Arrow batch size and numerical parameter count. It uses ordinary Spark aggregations to inspect a deliberately skewed tiny table, then estimates the memory that an analogous wide real group would require.

The memory figures are a lower-bound planning calculation, not a measured peak or an attempt to crash a container. The worked program has only twenty-two rows. It demonstrates that repartitioning does not alter the largest scientific group and that sufficient statistics can produce a mean without ever materializing the entire group in Python.

## Mechanism: shuffle placement does not split a whole-group function

A grouped operation first brings equal keys together. A function that expects a complete pandas DataFrame for each key needs that group's data in one process. Many executor partitions can distribute *different* groups, but a single hot key remains one group. Adding executors cannot make an intrinsically whole-group operation use several workers unless you redesign its algorithm.

For a rough dense numeric lower bound, a group with \(n_g\) rows and \(d\) float64 columns holds \(8n_gd\) bytes of raw values. The true peak can be larger because JVM buffers, Arrow arrays, pandas objects, temporary feature matrices, optimizer workspaces and model libraries coexist. A dense Hessian adds order \(d^2\) storage; a covariance over observations adds order \(n_g^2\), which is a different danger.

Arrow controls transfer and conversion. The configured Arrow record-batch size is not a universal maximum group size for grouped pandas execution. A batch iterator such as mapInPandas offers a different contract, but it cannot magically fit a whole-group algorithm in streaming memory. The algorithm must carry a sufficient state between batches or explicitly own complete groups.

Before preparing a group fit, compute \(n_g\), null counts, feature widths and an explicit admissibility rule. A rule based only on average group size ignores the tail that causes the failure.

## Worked case 1: a hot group remains hot

The reference creates sixteen rows under key hot and three small groups of two rows each. Spark reports a maximum group count of sixteen whether the table is repartitioned to one or four physical partitions. The shuffled output has four group rows, but the hypothetical complete-group function still receives sixteen hot records.

Scale the same pattern to two million rows with fifty float64 features. The raw numeric payload alone is \(800{,}000{,}000\) bytes, about \(763\) MiB. If the worker's actual available memory budget is smaller, the function is inadmissible before accounting for copies. The reference reports this lower bound against an explicit illustrative budget rather than pretending to measure a real group's heap.

An independent model can be correct statistically and still be operationally impossible on the chosen worker. The response is to reject or separately route the oversize group, simplify its model, use a streaming sufficient state, or choose a truly distributed within-group algorithm. Splitting the rows and averaging fitted coefficients does not preserve an arbitrary model.

## Worked case 2: replace materialization with sufficient statistics

The Gaussian mean model from the previous chapter requires \((n_g,s_g)\). Spark's built-in count and sum can compute those summaries using partial aggregation before the shuffle and a final merge after it. The final mean is \(s_g/n_g\), and the reference compares each result with a tiny serial keyed oracle.

This algorithm reduces memory from storing all group rows to storing a fixed-size aggregate state per active key. That is a mathematical redesign, not merely a faster serialization format. If the model also needs a known-variance Gaussian likelihood at a trial mean, add the squared sum \(q_g=\sum y_i^2\); then \(\sum(y_i-\mu)^2=q_g-2\mu s_g+n_g\mu^2\).

The shortcut has a boundary. A general nonlinear likelihood may not have a small exact sufficient state. Approximate sketches, sampled fits or time-window truncation can be useful, but they change the information or objective and need their own validation. For correlated time series, a state-space filter may supply a bounded sequential state, while an arbitrary dense covariance model may not.

## Failure diagnosis

If increasing shuffle partitions leaves one task slow or failing, inspect the key distribution rather than assuming the scheduler is broken. A single group may dominate both memory and work. If a Python worker dies with no useful Python exception, retain container/executor diagnostics and look for memory termination before blaming the model formula.

A memory estimate using only the serialized file size is too optimistic. Compressed columnar data often expands during feature construction. Count rows and calculate the representation you actually materialize. Include solver matrices and copies in the budget.

The example deliberately raises and catches a rejection for an oversize hypothetical group. It does not catch every exception and substitute a fit. A production output table should preserve an explicit rejected status and reason for that group.

## Interview discussion

**Will repartitioning by a hot key split its group across machines?** It ensures equal keys are together for a key-based operation. It does not divide a whole-group function among machines. Salting may divide aggregation work only when you have a valid mergeable summary.

**Does Arrow solve the memory problem?** Arrow can reduce conversion cost and represent data efficiently. It does not remove the need to hold the input and workspace required by the chosen algorithm. Batch processing is useful only if the computation can consume batches correctly.

**When is salting safe for model fitting?** When the salted pieces produce summaries with a proven merge law, such as count, sum and squared sum for this Gaussian calculation. It is not generally safe to independently fit each salted piece and average coefficients.

## Complete reproducible program

Run this complete source in its declared prepared Spark profile. The fixture is tiny, deterministic and offline. Scala sources are compiled before execution; Python sources use the prepared PySpark environment. These are worked tutorials with no hidden solutions or exams. Runtime: `spark-local-python`.

```python
from __future__ import annotations

import json


def session(name):
    from pyspark.sql import SparkSession

    spark = (
        SparkSession.builder.master("local[2]")
        .appName(name)
        .config("spark.ui.enabled", "false")
        .config("spark.driver.host", "127.0.0.1")
        .config("spark.driver.bindAddress", "127.0.0.1")
        .config("spark.sql.shuffle.partitions", "2")
        .config("spark.sql.adaptive.enabled", "false")
        .config("spark.sql.ansi.enabled", "true")
        .config("spark.sql.session.timeZone", "UTC")
        .getOrCreate()
    )
    if spark.version != "4.0.1":
        spark.stop()
        raise RuntimeError("This worked reference is qualified for Spark 4.0.1")
    spark.sparkContext.setLogLevel("ERROR")
    return spark


def dense_numeric_lower_bound(rows, columns):
    if not isinstance(rows, int) or not isinstance(columns, int) or rows < 0 or columns < 1:
        raise ValueError("nonnegative rows and positive numeric width required")
    return 8 * rows * columns


def run(spark):
    from pyspark.sql import functions as F

    rows = [("hot", float(i)) for i in range(16)]
    rows += [(f"small-{g}", float(i)) for g in range(3) for i in (1, 3)]
    frame = spark.createDataFrame(rows, "group string, y double")
    observed = []
    for partitions in (1, 4):
        result = (
            frame.repartition(partitions)
            .groupBy("group")
            .agg(F.count("*").alias("n"), F.sum("y").alias("total"))
        )
        summaries = result.orderBy("group").collect()
        assert max(r.n for r in summaries) == 16
        for row in summaries:
            original = [value for group, value in rows if group == row.group]
            assert row.n == len(original)
            assert row.total / row.n == sum(original) / len(original)
        observed.append({"physical_partitions": partitions, "largest_group": 16})
        if partitions == 4:
            result.explain("formatted")
    estimate = dense_numeric_lower_bound(2_000_000, 50)
    budget = 512 * 1024 * 1024
    assert estimate == 800_000_000 and estimate > budget
    print(
        json.dumps(
            {
                "group_ownership": observed,
                "raw_float64_bytes": estimate,
                "illustrative_budget_bytes": budget,
                "admit_whole_group": False,
                "note": "memory lower bound, not an observed OOM",
            }
        )
    )


if __name__ == "__main__":
    spark = session("asm-004")
    try:
        run(spark)
    finally:
        spark.stop()
```
