## The question and the mechanism

Reconcile unmatched facts without confusing the stored dimension with its semantic blank member.

VALUES and DISTINCT can look identical on clean data, which makes a missing-key fixture essential. On a column, VALUES can include the blank member introduced by a regular relationship when fact keys do not match its dimension. DISTINCT over the stored dimension column does not add that relationship-generated member. The difference concerns the model, not merely duplicated text values.

The named unknown-member model adds S9 with product key 999 and net amount 7. Product still stores four keys, 1 through 4. The semantic blank member groups the unmatched fact rather than silently discarding it. It is not an actual product with key zero, and it is different from the valid unsold Bag product.

A complete reconciliation should include known-product revenue 187 and unknown-product revenue 7, totaling 194. An inner join that drops S9 can make a seemingly tidy product report understate recorded activity. Conversely, counting the synthetic blank member as an ordinary catalog SKU can misstate the inventory of real products. State which population each metric represents.

## Vocabulary and expression anatomy

COUNTROWS exposes the size of the two returned value tables. The second query filters the semantic ProductKey to BLANK and separately returns the unfiltered fact amount. The source assumes the regular relationship and deliberately unmatched key declared in this model, not a limited relationship or a repaired source.

Concepts to explain in your own words: **VALUES**, **DISTINCT**, **blank member**, **referential integrity**, **reconciliation**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: Stored keys versus semantic members

**Starting context:** Unknown-member model; stored Product keys 1..4; Sales also has key 999.

```dax
EVALUATE ROW ( "ValuesMembers", COUNTROWS ( VALUES ( Product[ProductKey] ) ), "StoredDistinctKeys", COUNTROWS ( DISTINCT ( Product[ProductKey] ) ) )
```

**Context trace:**

1. DISTINCT sees the four stored Product keys.
2. The unmatched regular relationship introduces one semantic blank member for VALUES.
3. VALUES therefore has five members, not a new stored row with key 999.

**Hand-derived worked-reference result:**

| ValuesMembers | StoredDistinctKeys |
| --- | --- |
| 5 | 4 |

The unknown member can represent multiple unmatched keys. It does not tell you how many distinct bad source codes exist; inspect fact-minus-dimension keys for that diagnostic.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Reconcile the unknown amount

**Starting context:** Unknown-member model; the first expression selects its semantic blank Product member.

```dax
EVALUATE ROW ( "UnknownRevenue", CALCULATE ( [NetRevenue], ISBLANK ( Product[ProductKey] ) ), "AllRevenue", [NetRevenue] )
```

**Context trace:**

1. S9 is the only unmatched product fact and contributes 7.
2. Known-product facts still contribute 187.
3. The full fact total is 194, including the unknown bucket.

**Hand-derived worked-reference result:**

| UnknownRevenue | AllRevenue |
| --- | --- |
| 7 | 194 |

An explicit unknown bucket preserves a useful data-quality signal. Replacing it with an invented valid product would conceal a modeling issue.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. No unmatched Product key is present there.
2. Several unmatched codes can map to one semantic blank member.
3. Keep the unknown bucket separate from known members.
4. One member is generated by relationship semantics.
5. Bag has a real dimension key but no facts.
6. The fact may arrive before its descriptive record.
