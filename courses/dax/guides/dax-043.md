## The question and the mechanism

Build a small reusable measure family with explicit units and dependency boundaries.

A measure family should reuse stable definitions rather than copy a long formula into every report. NetRevenue, Cost, Profit and NetMargin form a small dependency graph: profit subtracts compatible currency amounts, and margin divides profit by revenue. A change to the cost policy then has a visible dependency path instead of several subtly different pasted implementations.

Our synthetic Product.UnitCost is constant per product for the modeled period. Within a Sales row, RELATED retrieves that product's cost through the many-to-one relationship. Multiplying by quantity gives a line cost. This assumption is deliberately simple: a real historical-cost requirement would need the effective cost at the transaction date, not an overwritten current product attribute.

Keep the resulting margin numeric. Its display can be a percentage through a format property or a supported dynamic format string. FORMAT would instead return text. Formatting is not the source of the metric's meaning: NetMargin is profit per unit of revenue, and every term in its dependency graph must use the same population and compatible currency policy.

## Vocabulary and expression anatomy

The reference defines each dependency once. RELATED uses the row context created by SUMX to locate the product's UnitCost. The measure graph is acyclic: NetRevenue and Cost feed Profit, then Profit and NetRevenue feed NetMargin. A dynamic format expression belongs to formatting metadata, not inside the numeric margin formula.

Concepts to explain in your own words: **measure dependency**, **RELATED**, **cost grain**, **numeric measure**, **format property**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
    MEASURE Sales[QuantitySold] = SUM ( Sales[Quantity] )
    MEASURE Sales[GrossRevenue] = SUMX ( Sales, Sales[Quantity] * Sales[UnitPrice] )
    MEASURE Sales[OrderCount] = DISTINCTCOUNT ( Sales[OrderID] )
    MEASURE Sales[Cost] = SUMX ( Sales, Sales[Quantity] * RELATED ( Product[UnitCost] ) )
    MEASURE Sales[Profit] = [NetRevenue] - [Cost]
    MEASURE Sales[NetMargin] = DIVIDE ( [Profit], [NetRevenue] )
```

### Case A: Whole-model profit graph

**Starting context:** Clean retail model; current UnitCost is explicitly constant per product; all amounts USD.

```dax
EVALUATE ROW ( "Revenue", [NetRevenue], "Cost", [Cost], "Profit", [Profit], "Margin", [NetMargin] )
```

**Context trace:**

1. Line costs are 4,1,10,6,4,5,4,10, totaling 44.
2. Profit is 187 -44 =143.
3. Margin is 143/187, evaluated from the same all-row population.

**Hand-derived worked-reference result:**

| Revenue | Cost | Profit | Margin |
| --- | --- | --- | --- |
| 187 | 44 | 143 | 0.7647058824 |

The margin is a numeric ratio, not the text produced by a percent formatter. Its meaning would change if costs and revenues used different filters.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: The same family under Blue

**Starting context:** Blue products only; the same measure definitions and cost assumptions.

```dax
EVALUATE CALCULATETABLE ( ROW ( "Revenue", [NetRevenue], "Cost", [Cost], "Profit", [Profit], "Margin", [NetMargin] ), Product[Color] = "Blue" )
```

**Context trace:**

1. Notebook cost is 14 and Mug cost is 25, totaling 39.
2. Blue revenue 163 minus 39 gives profit 124.
3. The filtered margin is 124/163, not the unfiltered 143/187.

**Hand-derived worked-reference result:**

| Revenue | Cost | Profit | Margin |
| --- | --- | --- | --- |
| 163 | 39 | 124 | 0.7607361963 |

A reusable definition remains context-dependent. Reuse should preserve a formula's policy while allowing the question's population to change.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Its revenue 24 and cost 5 belong to the same product population.
2. There are seven Notebook units in this fixture.
3. Separate base currency measures from a dimensionless ratio.
4. FORMAT returns text.
5. Profit can exist without a defined margin ratio.
6. Returns, discounts and taxes need compatible grain and units.
