## The question and the mechanism

Produce a model-quality ledger that separates an invalid dimension key from an unmatched fact key.

A model-quality review starts with grain and identity, not a large measure catalog. A duplicate key on the one side prevents the intended regular one-to-many relationship. It is not a reason to arbitrarily choose one descriptive row. An unmatched foreign key is a different defect: a regular relationship can represent unmatched facts through a synthetic blank member on the dimension side.

This lesson uses the named unknown-member fixture, which adds S9 with ProductKey 999 and amount 7. Product still contains keys 1 through 4. The unmatched amount must remain visible in a reconciliation: known products contribute 187 and the unmatched line contributes 7, so total sales are 194. Hiding the unknown bucket would make a catalog report disagree with the fact total.

The first worked case builds a deliberately duplicated diagnostic table inside the query. It does not claim that an invalid one-side relationship was loaded successfully. The second case inspects the actual missing key. Record a disposition for each issue: repair upstream identity, establish a legitimate composite grain, or explicitly expose unknown facts. Do not confuse a model-design decision with an engine execution receipt.

## Vocabulary and expression anatomy

DATATABLE introduces a literal typed table for the duplicate diagnostic. SELECTCOLUMNS projects just the key before DISTINCT counts it. EXCEPT returns values in its first table that are absent from the second. The comparison uses raw fact ProductKey values and DISTINCT over stored dimension keys, so the missing code 999 is visible.

Concepts to explain in your own words: **referential integrity**, **duplicate key**, **unknown member**, **model validation**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

### Case A: A duplicate-key diagnostic, not a loaded dimension

**Starting context:** A query-local candidate table; it is not related to Sales.

```dax
EVALUATE
VAR Candidate = DATATABLE ( "Key", INTEGER, "Label", STRING, { { 1, "Notebook" }, { 1, "Other label" }, { 2, "Pen" } } )
RETURN ROW ( "Rows", COUNTROWS ( Candidate ), "UniqueKeys", COUNTROWS ( DISTINCT ( SELECTCOLUMNS ( Candidate, "Key", [Key] ) ) ) )
```

**Context trace:**

1. The candidate contains keys 1, 1 and 2.
2. Projecting Key then taking DISTINCT leaves 1 and 2.
3. Three rows and two keys prove the one-row-per-key contract fails.

**Hand-derived worked-reference result:**

| Rows | UniqueKeys |
| --- | --- |
| 3 | 2 |

This diagnostic explains why the intended dimension cannot be accepted as unique. Summing its labels or choosing the first row is not a principled repair.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: An unmatched fact key

**Starting context:** Unknown-member model; no filters; S9 references absent ProductKey 999.

```dax
EVALUATE EXCEPT ( VALUES ( Sales[ProductKey] ), DISTINCT ( Product[ProductKey] ) )
```

**Context trace:**

1. Fact keys are 1, 2, 3 and 999.
2. Stored Product keys are 1, 2, 3 and 4.
3. The fact-minus-dimension set contains only 999.

**Hand-derived worked-reference result:**

| ProductKey |
| --- |
| 999 |

An unmatched key is not the same as an absent fact. S9 still represents seven dollars of recorded activity, subject to the explicit unknown-member policy.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Add the unmatched amount without discarding valid lines.
2. The key would exist on both sides.
3. Separate duplicate identity from missing membership.
4. A matching total can conceal an excluded population.
5. A dimension member can exist without a matching fact.
6. Identify the assigned unit separately from repeated events.
