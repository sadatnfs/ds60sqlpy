# web-035: Arrays, records, keys and transformations

## Level and prerequisites

Beginner; allow about 90 minutes, with extra time for independent practice. Direct prerequisites: `web-034`

## Learning objectives

Filter and summarize study records without changing the originals. Explain the risk of a lingering foreach reference. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

PHP's array is an ordered map: it associates keys with values and preserves an iteration order. It can represent a list or a keyed record, but these are different data contracts. A list of study rows should not accidentally become an object-shaped JSON value because filtered numeric keys were left nonconsecutive. Key coercion can also matter, so avoid treating arbitrary external strings as interchangeable with integer indices.

Transformations are easier to reason about when they do not mutate the original data unexpectedly. Map computes a derived value for each record; filter keeps records satisfying a predicate. Validate expected fields before arithmetic. A missing key is different from a known null field and should be handled according to the record contract.

## Syntax anatomy and mechanism

Use explicit string keys for records, such as subject and minutes. `array_filter` preserves keys, so `array_values` is useful when the intended result is a fresh list. `array_map` applies a function to values. A foreach by reference can leave a lingering reference to the last item; avoid it unless mutation is necessary and understood.

## Worked example / walkthrough

### Worked example 1: A small record

Keys name the meaning of each value.

```php
$row = ['subject' => 'CSS', 'minutes' => 55];
echo $row['subject'];
```

**Expected observation:** The named field produces CSS.

### Worked example 2: A filtered list

Reindexing preserves the intended list shape.

```php
$visible = array_values(array_filter($rows, fn(array $row): bool => $row['minutes'] >= 40));
```

**Expected observation:** The result uses consecutive list indices.

## Six progressive exercises

### Exercise 1: Explain how a list differs from a keyed record.

**Expected evidence:** A list models ordered values; a record's named keys identify fields.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add a second validated study row.

**Expected evidence:** Every row has the declared subject and integer-minutes fields.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Filter and summarize study records without changing the originals.

**Expected evidence:** The derived list contains only qualifying rows and retains consecutive indices.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose JSON output changing from an array to an object shape.

**Expected evidence:** Inspect numeric key gaps after filtering and reindex when the contract is a list.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test an empty result and a missing required field.

**Expected evidence:** Empty lists are valid where declared; malformed records are rejected explicitly.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain the risk of a lingering foreach reference.

**Expected evidence:** A reference variable can still alias the last element and cause later assignments to mutate it.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not assume every array is a list. Avoid weakly typed mixed records whose missing fields become warnings during rendering. Keep mutation deliberate and test the original data after transformations.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain array, ordered map, key without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
