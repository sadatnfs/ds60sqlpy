# web-050: Password hashing and authentication boundaries

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-049`

## Learning objectives

Build a password-verification demonstration without printing the hash or secret. List the additional controls required around a real login. Use password hash, salt and verification accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

Passwords should not be stored as plaintext or encrypted with a reversible key merely so the application can compare them. A password hash is designed to make verification possible without retaining the original password and to impose a computational cost on guessing. Use a maintained password-hashing API rather than inventing a hash-plus-salt scheme. The encoded result records the algorithm and parameters needed for verification.

Authentication establishes an identity claim; it does not decide which objects that identity may access. A complete login flow also needs transport security, rate limiting, useful but nonrevealing errors, session rotation and account-recovery design. One successful hash comparison is only a primitive test, not a complete authentication system.

### Key terms

- **Password hash:** The string `password_hash()` returns, a deliberately slow one-way digest that records its algorithm, cost and salt.
- **Salt:** Random data mixed into each hash, so equal passwords produce different hashes and precomputed tables fail.
- **Password verification:** Checking a candidate with `password_verify()`, which reuses the algorithm and salt stored in the hash.
- **Rehash:** Replacing a stored hash after a successful login when `password_needs_rehash()` reports an outdated algorithm or cost.

## Syntax anatomy and mechanism

Use password_hash and password_verify. Allow storage large enough for future encoded formats, and use password_needs_rehash during a deliberate migration policy. Current OWASP guidance prefers Argon2id with at least 19 MiB of memory, 2 iterations and 1 degree of parallelism, then scrypt; bcrypt remains acceptable for existing systems with a work factor of 10 or more, and it only uses the first 72 bytes of input. The prepared `php:8.4` image is built with Argon2 support, so the example uses PASSWORD_ARGON2ID with those minimums: memory_cost is in KiB, so 19456 is 19 MiB. In PHP 8.4, PASSWORD_DEFAULT is still bcrypt, with its default cost raised from 10 to 12. password_needs_rehash reports a hash made with an older algorithm or weaker parameters, so it can be replaced after the next successful login. Production parameters still require measurement on the actual servers.

## Worked example / walkthrough

### Worked example 1: Hash and verify

The library generates the salt and records the algorithm and parameters in the encoded hash.

```php
$options = ['memory_cost' => 19456, 'time_cost' => 2, 'threads' => 1];
$hash = password_hash('synthetic-demo-passphrase', PASSWORD_ARGON2ID, $options);
$valid = password_verify('synthetic-demo-passphrase', $hash);
$upgrade = password_needs_rehash($hash, PASSWORD_ARGON2ID, $options);
```

**Expected observation:** `$valid` is true and `$upgrade` is false. The stored string starts with `$argon2id$` and records `m=19456,t=2,p=1`, so no plaintext or separate salt column is needed.

### Worked example 2: A wrong candidate

Verification does not reveal the original phrase.

```php
$wrong = password_verify('different-phrase', $hash);
```

**Expected observation:** The wrong candidate returns false.

## Contrast case: a fast unsalted hash

Two learners chose the same passphrase. Compare what each storage method writes for them.

```php
$phrase = 'synthetic-demo-passphrase';

$a = hash('sha256', $phrase);
$b = hash('sha256', $phrase);
var_export($a === $b);

$c = password_hash($phrase, PASSWORD_ARGON2ID);
$d = password_hash($phrase, PASSWORD_ARGON2ID);
var_export($c === $d);
var_export(password_verify($phrase, $d));
```

The SHA-256 digests are identical, so the first comparison is true. Anyone with the table can see that both learners share a password, and a precomputed list of common phrases matches them all at once. SHA-256 is also designed to be fast, so guessing is cheap. `password_hash` picks a new random salt for each call, so the two stored strings differ and the comparison is false. `password_verify` still accepts the correct phrase, because the salt and parameters are stored inside each string.

## Debugging and common mistakes

Never copy the teaching passphrase into a real account or print password hashes as routine diagnostics. Do not invent a manual salt. A stronger hashing parameter cannot compensate for an unbounded public login endpoint.

When password_verify always fails, check that you are verifying against the stored hash string and not hashing the candidate again for comparison. When password_needs_rehash reports true for a fresh hash, compare the algorithm and options you passed to hash and to rehash.

The shared [debugging routine](../STUDY-GUIDE.md#debugging-php) covers what to record before each repair.
