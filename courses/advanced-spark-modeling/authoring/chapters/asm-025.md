## Starting point and result

A query engine can evaluate derivative formulas without retaining a global automatic-differentiation graph. This distinction prevents a misleading architecture: collect a scalar loss from Spark, wrap it in a tensor and expect gradients through the original distributed work. The program evaluates a simple objective and its analytic gradient to make the boundary concrete.

## Mechanism: numeric summaries cross the boundary

For \(L(\theta)=\tfrac12\sum_i(\theta x_i-1)^2\), the derivative is \(g(\theta)=\sum_i x_i(\theta x_i-1)\). Spark aggregates both expressions at a fixed theta. The returned Row contains ordinary doubles. It does not contain the distributed operator graph, per-task intermediate tensors or a backward communication schedule.

A local AD engine can compute each partition's derivative before serialization. The driver can then sum the numeric gradients and pass them to an optimizer. That is a valid distributed gradient-evaluation architecture. It is different from differentiating the entire Spark query, including joins, sorts, discrete grouping, retries and materialization, as one global tape.

Some relational operations have useful differentiable analogues under specified assumptions. A weighted sum is straightforward; a hard top-k selection or changing join cardinality is more complicated. A general differentiable query system would need explicit derivative rules, parameter provenance, communication semantics and handling of nondifferentiable choices. This course does not pretend that a custom Catalyst node supplies all of those features.

## Worked case: compare an aggregate gradient with a serial difference

At theta 0.5 and features one, two and four, the objective is 0.625 and the analytic gradient is 3.5. Spark computes them in one aggregate action. A separate serial central difference agrees with the gradient within tolerance. This verifies the numerical expression and reduction for the declared fixture.

The gradient can be used by a driver optimizer exactly like the logistic summary in asm-007. Each new theta requires reevaluating the appropriate row expressions. Retaining an old numeric result while changing a local variable does not update the objective.

## Worked case: materialization freezes an evaluation

The program keeps the collected loss at theta 0.5, then computes the serial objective at theta 0.6. The values differ. The earlier scalar remains the result for its original parameter. Creating a new tensor from that scalar would introduce a new leaf unrelated to the Spark feature data.

To use PyTorch, compute local losses from parameter tensors inside each task, obtain gradients there, detach them deliberately and return validated numeric summaries. Alternatively, use real distributed training with a collective communication system. The combined projects teach both approaches without conflating their graphs or data-delivery responsibilities.

## Failure diagnosis

A tensor with `requires_grad=True` but no connection to model parameters is not evidence of end-to-end differentiation. An optimizer receiving an all-zero gradient may be using detached results, stale values or a missing derivative rule. Inspect the local computation graph before introducing additional Spark parallelism.

## Interview discussion

**Can Spark aggregate automatic gradients?** Yes. A partition can use a prepared AD library and return loss/count/gradient summaries. Correct normalization, parameter identity and coverage remain the application's responsibility.

**Why use distributed training instead?** Large parameter vectors, GPU computation and frequent gradient synchronization may fit DDP or another training runtime better than repeated Spark actions. That decision follows objective structure and measured costs, not a universal preference.
