Day 53: Data Warehouse Project, Part 2: SCD Type 2#

A beginner's mental model for this lesson#

Customers change. When customer 1 moves from the standard segment to gold, a report about October should still see the segment customer 1 had in October, and a report about November should see gold. Overwriting the row loses the first answer; Day 53 keeps both.

SCD Type 2 (slowly changing dimension, Type 2) keeps history by adding rows instead of overwriting them. The solution's change stamps an end date on customer 1's standard row in dim_customer, sets its is_current to false and inserts a gold row beside it, so the dimension grows from 501 rows to 502.

A business key is the source identity every version shares: both rows carry customer_id 1. The surrogate customer_sk differs per version (1 for the standard row, a fresh sequence number for the gold row), and the surrogate is what fact rows store, so each sale points at one specific version.

A validity interval is the span of days one version applies, from valid_from to valid_to. Both ends are inclusive in this course and a NULL valid_to means the version is still open. Inclusive ends force the closed row to stop one day before its successor starts; if both rows claimed the boundary day, a sale on that day would match two versions.

The learner file starts its ten new customer versions today, and no order is dated today or later (the newest is 23 November 2026 on our fixture), so every historical sale still belongs to an old version. The solution backdates its change 30 days instead, which splits customer 1's sales across two versions and gives the as-of join something to prove. Read that join in logical clause order: the FROM side is one row per order line, every dimension join must add exactly one partner, and 13,085 lines in must stay 13,085 out.

Two worked SQL examples#

Both excerpts come from day53_project3_dwh_part2_scd.sql and run inside its BEGIN, after SET search_path TO dwh, training, public, so dim_customer resolves to the Day 52 table while the source is named in full as training.customers. Everything they write disappears at the final ROLLBACK.

Example 1#
CREATE TEMP TABLE changed_customers AS
SELECT
  c.customer_id,
  c.full_name,
  c.country,
  CASE WHEN c.segment = 'platinum' THEN
    'gold'
  ELSE
    'platinum'
  END AS segment
FROM
  training.customers c
ORDER BY
  c.customer_id
LIMIT 10;

How to read it: CREATE TEMP TABLE ... AS SELECT runs a query and stores its rows in a session-only table, changed_customers, that vanishes when the connection closes. The CASE invents a change for the first ten customers by customer_id: a platinum customer drops to gold and everyone else becomes platinum. Name and country are copied unchanged, so segment is the only attribute that can differ from the current dimension row.

Expected result/shape: psql prints SELECT 10, not a result grid. The stored segments for customers 1 to 10 read platinum, platinum, platinum, gold, platinum, platinum, platinum, gold, platinum, platinum: customers 4 and 8 were platinum in the source and drop to gold. All ten now differ from their dimension rows, so all ten will version. To see them, add SELECT * FROM changed_customers ORDER BY customer_id before the ROLLBACK.

Example 2#
WITH current_dim AS (
  SELECT
    dc.*
  FROM
    dim_customer dc
  WHERE
    dc.is_current
),
diffs AS (
  SELECT
    s.customer_id,
    s.full_name,
    s.country,
    s.segment
  FROM
    changed_customers s
    JOIN current_dim dc ON dc.customer_id = s.customer_id
  WHERE
    coalesce(s.full_name, '') <> coalesce(dc.full_name, '')
    OR coalesce(s.country, '') <> coalesce(dc.country, '')
    OR coalesce(s.segment, '') <> coalesce(dc.segment, '')
),
closed AS (
  UPDATE
    dim_customer dc
  SET
    valid_to = CURRENT_DATE -1,
    is_current = FALSE
  FROM
    diffs d
  WHERE
    dc.customer_id = d.customer_id
    AND dc.is_current
  RETURNING
    dc.customer_id)
  -- A new version carries every attribute, including the Day 52 country_sk.
  -- The scalar lookup returns NULL for a country missing from dim_country (the
  -- NOT NULL rule then rejects the whole statement, so no row is closed) and
  -- raises an error if dim_country repeats a code. An inner join would instead
  -- drop that customer's new version after its old row had been closed.
  INSERT INTO dim_customer (customer_id, full_name, country, segment, country_sk, valid_from, valid_to, is_current)
  SELECT
    d.customer_id,
    d.full_name,
    d.country,
    d.segment,
    (
      SELECT
        co.country_sk
      FROM
        dim_country co
      WHERE
        co.country_code = d.country), CURRENT_DATE, NULL, TRUE
  FROM
    diffs d;

How to read it: Example 2 is a data-changing CTE chain, not a displayed query result. The CTEs current_dim, diffs, and closed identify changed customers, close each former current row, and insert one successor into dim_customer that carries every attribute, including the country_sk that Day 52 Exercise 1 made mandatory. Because the close and the insert are one statement, a failed country_sk lookup undoes the close as well. Read the command tag for the inserted-row count, then verify one current version per customer and non-overlapping validity periods; a successful command tag alone does not prove Type-2 history is correct.

Expected result/shape: The whole chain prints one tag, INSERT 0 10; the UPDATE inside closed reports nothing of its own, yet it runs, because PostgreSQL executes every data-changing CTE once and to completion even when the final statement never reads it. Afterward customers 1 to 10 each own two rows: the original, now closed at yesterday, and a new one from today with valid_to NULL. The first check prints 511 versions on our run (500 originals, the -1 unknown member from the Day 52 solution and 10 new rows) with 0 mismatched country keys. The second lists customers 1 to 10 with 2 versions each; first_seen is the customer's created_at date (8 October 2026 for customer 1, 9 May 2026 for customer 10) and last_seen is today, since the open row's NULL valid_to becomes CURRENT_DATE.

Learning objectives#

  • Close one current dimension version and insert its successor atomically.
  • Resolve facts to the dimension version valid on their event date.

Vocabulary and concepts#

  • SCD Type 2: slowly changing dimension design that preserves version history as new rows.
  • Business key: stable source identity shared by all versions.
  • Validity interval: the dates or timestamps for which one version applies.

Worked example / walkthrough#

For one changed customer, locate exactly one current row, set its valid_to to the day before the new version, and insert the successor at CURRENT_DATE. Then as-of join a fact date using inclusive bounds and verify it resolves to one surrogate key, not zero and not two.

Common mistakes and how to recover#

  • Lesson-specific semantic mistake: Temporal fact mapping count must equal source item count.
  • Writing the answers below the learner's own change: the learner section already versioned customer 1 today, so pasting the solution's statements above the learner ROLLBACK closes that new row at 25 October, before it began. On our run that version showed invalid_range true, the overlap check returned one pair, and the fact table held 13,095 rows for 13,085 lines, because customer 1's ten later lines matched two versions. Run the exercises on the Day 52 state, as the solution file does, or remove the learner change first.
  • Joining on is_current: after the change, a join on customer_id plus dc.is_current sends all 15 of customer 1's lines to the gold version, including the 5 sold while customer 1 was standard. The count still reads 13,085, so only a per-customer check exposes it.
  • Closing at today instead of yesterday: valid_to = CURRENT_DATE makes the old and new rows both valid today, and any order dated today would map twice. Keep the - 1.
  • Running without Day 52: when dwh.dim_customer is missing, the solution's DO block stops with Run Day 52 (the learner file or day52_solutions.sql) before Day 53; run and commit Day 52, then rerun the whole file.
  • null value in column "country_sk" (SQLSTATE 23502): a new version needs the Day 52 country key. Look it up in dim_country for the version's own country, and add a missing country code to dim_country before the load rather than dropping the NOT NULL rule.
  • Anything else goes through the first-error checklist before you edit a later statement.

Deep dive and reference#

Project focus#

  • Detect changed customer and product attributes.
  • Close the old current row and insert a new version.
  • Map historical facts to the dimension version valid on the fact date.

Preconditions and state#

Run Day 52 first in the same database, either its learner file or day52_solutions.sql. Day 53 reads the committed dwh schema but performs its changes inside a transaction and rolls them back.

The file's first statements restore the Day 52 Exercise 1 contract: every dim_customer version has a NOT NULL country_sk that points at dim_country. They are idempotent. After a Day 52 run that completed Exercise 1, they print two NOTICE lines, INSERT 0 0, and UPDATE 0; after the Day 52 base load alone, they create and backfill the link (INSERT 0 8, UPDATE 500) inside the rolled-back transaction. IF NOT EXISTS adopts an existing table without checking its shape, so the SCD2 insert looks country_sk up with a scalar subquery: a country missing from dim_country yields NULL, which the NOT NULL rule rejects with SQLSTATE 23502, and a repeated country code raises SQLSTATE 21000.

The learner stages deterministic changes for ten customers and ten products. For each changed business key, the current row closes at CURRENT_DATE - 1, and the replacement starts at CURRENT_DATE.

Practice map#

Exercise 2 has to run first: its backdated change creates the second customer 1 version that Exercises 1, 3, 4 and 5 inspect, which is why the solution file places it above Exercise 1. Exercise 6 stands alone on two literal ranges. Everything sits inside one transaction that ends in ROLLBACK, so Day 54 still reads the Day 52 warehouse whatever you try here. The prompts, expected tags and checks above are the contract both solution files answer.

SCD reasoning#

  • Close and insert are one atomic transaction.
  • customer_id and product_id are business keys; their surrogate keys identify versions.
  • Inclusive bounds require the old row to end one day before the new row starts.
  • A production dimension should prevent more than one current row per business key and overlapping validity ranges.

Validation and limits#

  • Temporal fact mapping count must equal source item count.
  • A lower count signals a date/version gap; a higher count signals overlapping versions.
  • Audit defaults cover inserts but do not explain update actors; set them on close operations too.
  • The course uses date-grain validity. Timestamp-effective changes require a different boundary model.

  country_code text NOT NULL UNIQUE

INSERT INTO dim_country (country_code)
SELECT DISTINCT
  c.country
FROM
  training.customers c
WHERE
  NOT EXISTS (
    SELECT
      1
    FROM
      dim_country co
    WHERE
      co.country_code = c.country)
ORDER BY
  c.country;

ALTER TABLE dim_customer
  ADD COLUMN IF NOT EXISTS country_sk int REFERENCES dim_country (country_sk);

UPDATE
  dim_customer dc
SET
  country_sk = co.country_sk
FROM
  dim_country co
WHERE
  co.country_code = dc.country
  AND dc.country_sk IS NULL;

Exercise 1: Resolve dimension versions by fact date#

The exercise requires the customer and product surrogate keys whose validity intervals contain each source order date.

BEGIN;
SET search_path TO dwh, training, public;

CREATE TEMP TABLE fact_sales_temporal_solution AS
SELECT
  o.order_id,
  oi.order_item_id,
  dd.date_key,
  dc.customer_sk,
  dp.product_sk,
  oi.quantity,
  oi.unit_price,
  oi.discount,
  oi.unit_price * oi.quantity * (1 - oi.discount) AS amount
FROM
  training.orders o
  JOIN training.order_items oi USING (order_id)
  JOIN dim_date dd ON dd.date_actual = o.order_date::date
  JOIN dim_customer dc ON dc.customer_id = o.customer_id
    AND o.order_date::date >= dc.valid_from
    AND o.order_date::date <= COALESCE(dc.valid_to, 'infinity'::date)
  JOIN dim_product dp ON dp.product_id = oi.product_id
    AND o.order_date::date >= dp.valid_from
    AND o.order_date::date <= COALESCE(dp.valid_to, 'infinity'::date);

SELECT
  (
    SELECT
      COUNT(*)
    FROM
      fact_sales_temporal_solution) AS mapped_fact_rows,
  (
    SELECT
      COUNT(*)
    FROM
      training.order_items) AS source_item_rows;

ROLLBACK;

Expected result: mapped_fact_rows equals source_item_rows. A lower count means a date or dimension-version gap; a higher count means overlapping validity ranges caused one fact to match more than one version.

The executable solution also stages a deterministic customer change effective 30 days ago, closes the previous current row at effective_date - 1, inserts a new current row, and then performs this temporal mapping.

Reasoning and verification#
  • Inputs/evidence: For sql-53 Exercise 1, map every training.order_items row to dim_date, to the dim_customer version whose valid_from <= order_date::date <= COALESCE(valid_to, 'infinity'), and to the matching dim_product version, after the Exercise 2 change gave customer 1 a second version.
  • Expected result/shape: For sql-53 Exercise 1, expected output: the temporary table fact_sales_temporal_solution, one row per order_item_id, with columns order_id, order_item_id, date_key, customer_sk, product_sk, quantity, unit_price, discount, and amount; the check row reports mapped_fact_rows = 13085, source_item_rows = 13085, and customer_versions = 2.
  • Independent verification: For sql-53 Exercise 1, confirm that SELECT COUNT(DISTINCT order_item_id) FROM fact_sales_temporal_solution also returns 13,085, so no item was duplicated by overlapping versions or lost in a validity gap; for customer 1, check that orders dated before the change map to the closed version's customer_sk and later orders to the current one.
  • Intermediate relation check: For sql-53 Exercise 1, count rows after the orders to order_items join (13,085) and again after each dimension join; any change in the count points at a missing date row or an overlapping or missing version.
  • Clause check: For sql-53 Exercise 1, the solution uses CREATE TEMP TABLE ... AS SELECT over training.orders JOIN training.order_items USING (order_id) plus three dimension joins with validity predicates, followed by a scalar-subquery check row.
  • Alternative/trade-off: For sql-53 Exercise 1, storing daterange(valid_from, valid_to, '[]') and joining with @> o.order_date::date expresses the same rule and can use a GiST index, at the cost of a range column the rest of the warehouse must understand.

Reasoning, state, and pitfalls#

  • valid_from <= fact_date <= COALESCE(valid_to, infinity) matches the course's inclusive-date convention.

  • Every new version must carry country_sk, the Day 52 Exercise 1 key. Exercise 5: Gate unchanged reruns#

IS DISTINCT FROM compares nullable attributes safely. The replay must use the same staged desired state that produced the new version, not the unchanged base table, otherwise the deliberate segment change looks like a new change again.

WITH desired_customer_state AS (
  SELECT
    customer_id,
    full_name,
    country,
    segment
  FROM
    staged_customer_change
)
SELECT
  COUNT(*) AS unchanged_rows_that_would_version
FROM
  dim_customer current_version
  JOIN desired_customer_state desired USING (customer_id)
WHERE
  current_version.is_current
  AND (current_version.full_name IS DISTINCT FROM desired.full_name
    OR current_version.country IS DISTINCT FROM desired.country
    OR current_version.segment IS DISTINCT FROM desired.segment);

-- Exercise 1: rebuild a fact-key mapping by choosing the dimension versions
-- whose validity intervals contain each order date.
CREATE TEMP TABLE fact_sales_temporal_solution AS
SELECT
  o.order_id,
  oi.order_item_id,
  dd.date_key,
  dc.customer_sk,
  dp.product_sk,
  oi.quantity,
  oi.unit_price,
  oi.discount,
  oi.unit_price * oi.quantity * (1 - oi.discount) AS amount
FROM
  training.orders o
  JOIN training.order_items oi USING (order_id)
  JOIN dim_date dd ON dd.date_actual = o.order_date::date
  JOIN dim_customer dc ON dc.customer_id = o.customer_id
    AND o.order_date::date >= dc.valid_from
    AND o.order_date::date <= COALESCE(dc.valid_to, 'infinity'::date)
  JOIN dim_product dp ON dp.product_id = oi.product_id
    AND o.order_date::date >= dp.valid_from
    AND o.order_date::date <= COALESCE(dp.valid_to, 'infinity'::date);

SELECT
  (
    SELECT
      COUNT(*)
    FROM
      fact_sales_temporal_solution) AS mapped_fact_rows,
  (
    SELECT
      COUNT(*)
    FROM
      training.order_items) AS source_item_rows,
  (
    SELECT
      COUNT(*)
    FROM
      dim_customer
    WHERE
      customer_id = 1) AS customer_versions;

-- Exercise 3: date-grain closed intervals cannot represent two ordered changes
-- on one date without an invalid or overlapping range. Surface that limitation.
SELECT
  customer_id,
  valid_from,
  valid_to,
  (valid_to IS NOT NULL
    AND valid_to < valid_from) AS invalid_range
FROM
  dim_customer
WHERE
  customer_id = 1
ORDER BY
  valid_from;

-- Exercise 4: each pair is compared once. Inclusive validity ranges overlap
-- when neither ends before the other begins.
SELECT
  a.customer_id,
  a.customer_sk AS version_a,
  b.customer_sk AS version_b,
  a.valid_from AS a_from,
  a.valid_to AS a_to,
  b.valid_from AS b_from,
  b.valid_to AS b_to
FROM
  dim_customer a
  JOIN dim_customer b ON b.customer_id = a.customer_id
    AND b.customer_sk > a.customer_sk
    AND a.valid_from <= COALESCE(b.valid_to, 'infinity'::date)
    AND b.valid_from <= COALESCE(a.valid_to, 'infinity'::date)
  ORDER BY
    a.customer_id,
    version_a,
    version_b;
