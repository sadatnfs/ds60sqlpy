# go-001: From source text to a checked Go program

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: No previous Go knowledge. Read source as plain text and distinguish editing from executing.

## Learning objectives

Compile and run a one-file Go program and replace a printed claim with a checked value. Along the way, explain package, entrypoint, assertion; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A Go program is source text organized into packages. A runnable executable needs package main and a function named main with no arguments or return values. The compiler checks names and types before any statement executes. A successful build creates machine code for a particular operating system and processor architecture; the source file itself is not the executable. Inside a single goroutine, statements follow the program's control flow. Printing a reassuring message proves only that a print statement ran. A useful reference instead computes a result and checks an independently known expectation. This distinction becomes important when later lessons contain cancellation, partial failure and distributed state.

## Vocabulary and concepts

- **Package:** A collection of source files compiled together.
- **Entrypoint:** The function invoked when this executable starts.
- **Assertion:** An explicit check of a claimed program property.

## Syntax anatomy and reasoning

package declares the compilation unit's package. import makes another package available under a name such as fmt. func main() declares the entrypoint; braces delimit its body. A short declaration with := creates a variable and infers its type. fmt.Sprintf constructs text while fmt.Println writes it. Go inserts many semicolons automatically, so keep an opening brace on the declaration line. The helper check(condition, message) panics on false; its message should identify the broken claim.

## Worked example / walkthrough

### Worked example 1: Predict a first value

Bind greeting to Hello, Go and check its exact text.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Predict a first value
	{
		greeting := "Hello, Go"
		check(greeting == "Hello, Go", "greeting")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** greeting equals Hello, Go.

The quotes delimit a string literal; they are not part of the stored value. Matching the exact text catches a changed greeting even if printing would still look reasonable.

### Worked example 2: Compute before formatting

Add 2 and 3, then format total=5.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Predict a first value
	{
		greeting := "Hello, Go"
		check(greeting == "Hello, Go", "greeting")
	}

	// Compute before formatting
	{
		total := 2 + 3
		line := fmt.Sprintf("total=%d", total)
		check(total == 5 && line == "total=5", "format")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The integer is 5 and the text is total=5.

The arithmetic result and its presentation are separate values. %d formats a decimal integer, and a wrong formatting verb can produce diagnostic text rather than the intended representation.

## Predict before running

Before running worked example 1, decide what would report a change to the literal "Hello, Go!": the compiler or the check? For worked example 2, predict what `line` would contain if `%d` were replaced by `%s`, and whether `total` would change at all. For the statement-order investigation, write the value of `count` after each of its three statements.

## Exercises

### Exercise 1: Predict a first value: change one input

Copy worked example 1, change `greeting := "Hello, Go"` to `greeting := "Hello, Go!"` and predict the failure before running; then restore the line.

**Expected:** The edited run panics with `greeting` because `greeting == "Hello, Go"` no longer holds.

**Verify:** Restoring `greeting := "Hello, Go"` makes the check pass again with the worked observation: greeting equals Hello, Go.

### Exercise 2: Compute before formatting: debug a regression

A one-token regression in worked example 2 makes a line read `total := 2 - 3`. Repair it without changing the check.

**Expected:** The defective run panics with `format`; after restoring `total := 2 + 3`, the integer is 5 and the text is total=5.

**Verify:** The failing run shows message `format`; after the repair `total == 5 && line == "total=5"` holds again.

### Exercise 3: Trace statement order

Start count at 1, add 1, then multiply by 3.

**Expected:** The final count is 6.

**Verify:** Your solution must keep `count == 6` true. Control: changing `count := 1` to `count := 2` panics with message `order`; revert it.

### Exercise 4: Distinguish zero initialization

Declare an int and a bool without explicit values.

**Expected:** The values are 0 and false.

**Verify:** Your solution must keep `n == 0 && !ready` true. Control: changing `check(n == 0 && !ready, "zero values")` to `check(n != 0 && !ready, "zero values")` panics with message `zero values`; revert it.

### Exercise 5: Repair a naming assumption

Bind total and Total to different integers and compare them.

**Expected:** The names refer to distinct variables.

**Verify:** Your solution must keep `total != Total` true. Control: changing `check(total != Total, "case-sensitive names")` to `check(total == Total, "case-sensitive names")` panics with message `case-sensitive names`; revert it.

## Common pitfalls and diagnosis

The first-lesson mistake is treating a printed line as proof. `fmt.Println(greeting)` looks right whether or not the value matches the contract; only `check` compares it with an independently known value. Go also refuses to compile an unused variable or import, so deleting a check can turn a run-time panic into a compile error about an unused name. Read that error as a sign that a value is no longer inspected.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Predict a first value: change one input

1. Restate the expected observation: greeting equals Hello, Go.
2. The quotes delimit the value. Which exact characters, including punctuation, does the comparison require?
3. The edited value has one more character than the literal in the check, so the equality is false and `check` panics before the success message prints.

### Hint for investigation 2: Compute before formatting: debug a regression

1. Restate the expected observation: The integer is 5 and the text is total=5.
2. Separate the arithmetic from the formatting: which value in the check does the edited line change first?
3. With subtraction, `total` is -1 and `line` is total=-1, so the check fails. Restore the plus sign rather than editing the expected text.

### Hint for investigation 3: Trace statement order

1. Restate the expected observation: The final count is 6.
2. Write the value of count after each statement; multiplication sees whatever the previous line left behind.
3. Multiplication observes the already-incremented value.

### Hint for investigation 4: Distinguish zero initialization

1. Restate the expected observation: The values are 0 and false.
2. Every Go type has a zero value. What are the zero values of int and bool?
3. Every declared Go variable has a defined zero value.

### Hint for investigation 5: Repair a naming assumption

1. Restate the expected observation: The names refer to distinct variables.
2. Go identifiers are case sensitive. How many distinct variables do the two declarations create?
3. Identifier case matters.

### Hint for investigation 6: Transfer to a receipt

1. Restate the expected observation: The checked result is amount=24.
2. Compute the product as an integer first, then choose the verb that formats an integer in decimal.
3. This combines calculation and representation while keeping the expected result independently inspectable.
