## A backfill is a historical computation with a contract

A backfill recomputes a bounded part of history using an explicitly chosen source and transformation. It might repair a late file, correct a bug, populate a new feature or rebuild a table after a schema migration. It is not simply “run the job again.” A safe backfill must define which dates it owns, what source version it uses, whether its input is complete for that interval, and how it interacts with newer work already accepted by the system.

We use calendar-day partitions and a half-open interval \([a,b)\). The start is included and the end is excluded. A backfill from January 2 to January 3 therefore owns January 2 only. Half-open intervals compose naturally: \([a,b)\) and \([b,c)\) cover adjacent time ranges without both owning the boundary. For timestamp data, the timezone and conversion to a business date also belong to the contract. The example accepts explicit ISO dates, avoiding an implicit dependence on the machine's local timezone.

The source is a complete finite snapshot of identified package events. Each event has an ID, day and positive integer count. A revision is an ordered source-snapshot version supplied by the caller. Higher means newer under this declared policy; it is not an arbitrary string sorted by accident. The target records a package total, source revision and canonical input hash for each day. These three pieces let the pipeline distinguish a replay, a newer correction and an attempted overwrite by stale work.

## Replacement versus addition

A complete-snapshot backfill computes a replacement total. It does not add the new total to the previous total. If yesterday's partition contains three packages and a corrected complete snapshot contains seven, the accepted value should become seven, not ten. Incremental deltas can also be valid, but they require a different event and replay contract. Mixing the two interpretations is a common source of double counting.

For day \(d\), let \(E_d^{(v)}\) be the events in source revision \(v\). The candidate total is

\[
S_d^{(v)}=\sum_{e\in E_d^{(v)}}\mathrm{packages}(e).
\]

The target accepts the candidate if its revision is newer than the accepted revision. An equal revision is a replay only when its canonical input hash matches. A lower revision is skipped. This is one explicit correction policy; another system might fail an entire stale run instead. The important requirement is that the policy be documented and tested, not silently selected by whichever job finishes last.

The program bounds an interval to ten days to prevent accidental unbounded work inside the pad. It checks event identities before aggregation. Each day's events are sorted before JSON hashing, so a harmless source-row reordering does not manufacture a new content identity. The hash includes event IDs and counts: equal totals with different membership remain distinguishable. All selected partition updates happen inside one real DuckDB transaction.

## Worked case 1: repair one day and replay the repair

The baseline snapshot contains A with two packages on January 1, B with three on January 2, and C with one on January 3. Revision 1 populates all three days. The correction adds event D with four packages on January 2. The backfill owns only \([\text{January 2},\text{January 3})\) and uses revision 2.

The expected partition values are January 1: two at revision 1; January 2: seven at revision 2; January 3: one at revision 1. The exclusive end is important: January 3 remains untouched. Repeating the same correction with the same revision produces a `replayed` decision. It does not insert another partition row or add seven to the existing value. The primary key on day also makes the target grain explicit.

A zero-event day inside a declared complete snapshot has a replacement total of zero. That interpretation is safe only because completeness is part of this example's source contract. A missing file or an incomplete API response must not be converted into a complete empty snapshot. The ingestion chapters explain how manifests and population checks establish that earlier boundary. Backfill correctness depends on those upstream facts, not only on the arithmetic in this function.

## Worked case 2: preserve a newer correction during an older broad run

The second case starts from the baseline, then accepts a newer January 3 correction at revision 5, changing its package count to nine. A broad revision 2 backfill subsequently covers all three days using the older baseline values. January 1 and January 2 advance from revision 1 to revision 2. January 3 remains nine at revision 5 and receives a `stale-skipped` decision.

This models a realistic race in completion order: a large historical repair may finish after a smaller, newer correction. Wall-clock completion is not the authority for which data are newest. The source revision and ownership policy decide. The resulting table can legitimately contain different revisions for different days; a per-partition version is more informative than one global “last updated” timestamp for the whole table.

The case then submits changed January 2 content under the already accepted revision 2. That identity conflict is rejected. The surrounding transaction rolls back any changes from that attempt, and the target remains equal to the snapshot taken before the conflict. A system that simply overwrites on equal revision would conceal contradictory history. A system that treats equal totals as identical would also miss changed event membership, which can matter for audit and later corrections.

## Complete worked program

Run this program in the data-engineering profile. It uses an actual in-memory DuckDB transaction and deterministic synthetic source snapshots. It does not start an orchestrator or schedule background historical jobs.

```python
"""Actual bounded partition backfills with explicit half-open windows and source revisions."""

import hashlib
import json
from datetime import date, timedelta

import duckdb


def database():
    connection = duckdb.connect(":memory:")
    connection.execute(
        "create table partitions(day date primary key, packages integer,"
        "source_revision integer, input_sha varchar)"
    )
    return connection


def backfill(connection, events, start, end, revision):
    first, last = date.fromisoformat(start), date.fromisoformat(end)
    if not 0 < (last - first).days <= 10 or type(revision) is not int or revision < 1:
        raise ValueError("Use a bounded half-open day interval and positive source revision")
    if len({row["id"] for row in events}) != len(events):
        raise ValueError("The declared complete source snapshot has duplicated event IDs")
    buckets = {first + timedelta(days=index): [] for index in range((last - first).days)}
    for row in events:
        day = date.fromisoformat(row["day"])
        if type(row["packages"]) is not int or row["packages"] < 1:
            raise ValueError("Package events must be positive integer observations")
        if day in buckets:
            buckets[day].append((row["id"], row["packages"]))
    decisions = []
    connection.execute("begin")
    try:
        for day, rows in sorted(buckets.items()):
            identity = hashlib.sha256(
                json.dumps(sorted(rows), separators=(",", ":")).encode()
            ).hexdigest()
            total = sum(value for _, value in rows)
            prior = connection.execute(
                "select source_revision,input_sha from partitions where day=?", [day]
            ).fetchone()
            if prior is not None and revision < prior[0]:
                decisions.append((str(day), "stale-skipped"))
                continue
            if prior is not None and revision == prior[0]:
                if prior[1] != identity:
                    raise ValueError("One partition revision cannot name conflicting input")
                decisions.append((str(day), "replayed"))
                continue
            connection.execute(
                "insert into partitions values(?,?,?,?) on conflict(day) do update set "
                "packages=excluded.packages,source_revision=excluded.source_revision,"
                "input_sha=excluded.input_sha",
                [day, total, revision, identity],
            )
            decisions.append((str(day), "updated"))
        connection.execute("commit")
    except Exception:
        connection.execute("rollback")
        raise
    return decisions


def rows(connection):
    return [
        (str(day), packages, revision)
        for day, packages, revision in connection.execute(
            "select day,packages,source_revision from partitions order by day"
        ).fetchall()
    ]


def fixture():
    return [
        {"id": "A", "day": "2024-01-01", "packages": 2},
        {"id": "B", "day": "2024-01-02", "packages": 3},
        {"id": "C", "day": "2024-01-03", "packages": 1},
    ]


def example_one():
    with database() as connection:
        backfill(connection, fixture(), "2024-01-01", "2024-01-04", 1)
        corrected = [*fixture(), {"id": "D", "day": "2024-01-02", "packages": 4}]
        decision = backfill(connection, corrected, "2024-01-02", "2024-01-03", 2)
        replay = backfill(connection, corrected, "2024-01-02", "2024-01-03", 2)
        assert decision == [("2024-01-02", "updated")] and replay == [("2024-01-02", "replayed")]
        assert rows(connection) == [
            ("2024-01-01", 2, 1),
            ("2024-01-02", 7, 2),
            ("2024-01-03", 1, 1),
        ]
        return {
            "partitions": rows(connection),
            "exclusive_end_day_unchanged": True,
            "repeat": replay,
        }


def example_two():
    with database() as connection:
        backfill(connection, fixture(), "2024-01-01", "2024-01-04", 1)
        newest = [{**row, "packages": 9} if row["id"] == "C" else row for row in fixture()]
        backfill(connection, newest, "2024-01-03", "2024-01-04", 5)
        decision = backfill(connection, fixture(), "2024-01-01", "2024-01-04", 2)
        assert rows(connection) == [
            ("2024-01-01", 2, 2),
            ("2024-01-02", 3, 2),
            ("2024-01-03", 9, 5),
        ]
        assert decision[-1] == ("2024-01-03", "stale-skipped")
        before = rows(connection)
        conflicting = [{**row, "packages": 30} if row["id"] == "B" else row for row in fixture()]
        try:
            backfill(connection, conflicting, "2024-01-01", "2024-01-03", 2)
        except ValueError:
            pass
        else:
            raise AssertionError("Equal revision with changed input must be rejected")
        assert rows(connection) == before
        return {
            "decisions": decision,
            "retained_partition_versions": rows(connection),
            "conflicting_revision_rejected": True,
        }


def main():
    print("A bounded correction with an exclusive end:", example_one())
    print("Older backfill cannot overwrite newer accepted correction:", example_two())


if __name__ == "__main__":
    main()
```

## Time, concurrency and publication boundaries

Real backfills may be too large for one transaction. Then the unit of acceptance might be one partition, with a separate manifest describing which partition versions form a complete publication. Readers should not infer a coherent global snapshot from whichever files happen to exist midway through a run. Decide whether mixed-version reads are acceptable and expose that decision in the consumer contract.

Concurrent writers also need database or catalog coordination. This example uses one connection and a transaction. It does not qualify multi-process optimistic conflict resolution in a remote lake catalog. A production implementation may compare an expected partition version atomically, acquire a bounded lock, or create a new table snapshot. Merely reading a revision and later writing a file leaves a race between the check and the update.

Source revisions must have a real ordering meaning. A hash identifies content but has no chronological ordering. A UUID is unique but not necessarily ordered. A timestamp can be ambiguous if clocks differ or multiple publications share a timestamp. Use a source sequence or another reviewed version rule, and distinguish that rule from an ingestion timestamp used for observability.

## Failure diagnosis

If a boundary day is processed twice, inspect inclusive versus exclusive endpoint handling. If a total doubles, inspect whether the code adds a complete snapshot instead of replacing it. If a new correction disappears, compare the accepted source revision with the overwriting job's revision. If equal revisions produce different results, investigate changed source membership, transformation code or hidden configuration before allowing another write.

A backfill should retain a decision summary: updated partitions, replayed partitions, stale skips, rejected inputs and the exact interval. A success exit with zero updates may be correct if everything was already accepted, but it should be distinguishable from selecting an empty interval accidentally. This example rejects zero-length intervals and returns per-day decisions so those cases cannot be silently conflated.

## Applications and answered interview discussion

Use these ideas when rebuilding daily aggregates, feature tables, billing reports or training snapshots. Backfills also need operational planning: rate limits, resource isolation, dependencies and a strategy for avoiding overload of live workloads. A correct historical answer that starves the production service still needs a better execution plan.

An interviewer may ask, “How can an old backfill avoid overwriting fresh data?” Explain source versions, partition ownership and an atomic conditional acceptance mechanism. If asked whether a backfill is idempotent, state which input, transformation and revision are held fixed, then show why a repeated run has the same accepted state. “We use upsert” alone is incomplete because an upsert can still overwrite a newer value or accept conflicting content.

For an answered extension, a correction that removes an event from a complete snapshot must recompute the replacement total from the remaining membership. Subtracting an inferred delta without an identified correction history is harder to audit and replay. Choose one update interpretation and carry it through ingestion, storage and recovery.
