## Vocabulary and concepts

Data layout determines which values are adjacent in memory. Array-of-structs stores complete records together; struct-of-arrays groups each field separately. Locality can reduce memory traffic when a calculation uses one field, while another workload may favor complete records. Allocation count is a separate cost from algorithmic work.

<!-- terms:start -->

- **data layout:** the arrangement that determines which values sit next to each other in memory.
- **array of structures:** a layout that stores complete records together.
- **structure of arrays:** a layout that stores each field in its own sequence.
- **locality:** accessing nearby memory, which can reduce memory traffic when a calculation reads one field.
- **allocation count:** the number of dynamic allocations, a cost separate from algorithmic work.

<!-- terms:end -->

## Data layout follows the access pattern

An array of structures stores complete records together. A structure-of-arrays layout stores each field in its own sequence. Neither layout is universally faster. The useful question is which fields the operation reads and in what order. Summing only value can benefit from dense values, while operations that need id and value together may favor a record layout.

The first example stores three Sample records with IDs 1, 2, 3 and values 10, 20, 30. It visits each record and adds value. The second stores just the values and uses accumulation. Both must produce 60 before any timing comparison is meaningful. Equal totals are a basic correctness check; in a richer transformation, also verify that identity-to-value relationships remain intact.

reserve(rows.size()) can avoid repeated growth allocations while materializing a values vector. It changes capacity, not size. push_back constructs the actual elements. Writing `values[0]` immediately after reserve on an empty vector would violate the element-access contract. This is a concrete link between performance-oriented allocation control and the ownership rules from cpp-007.

Data movement has a cost. Creating a separate values sequence may improve repeated scans but require an upfront copy and additional memory. If only one tiny scan is performed, the conversion cost can dominate. A benchmark should state whether layout conversion is included and how many queries reuse the result. Otherwise two timings can describe different amounts of work.

Hardware cache behavior, alignment, compiler vectorization and input size influence performance. The tiny fixture teaches representation and equality of results, not a cache-speed claim. Measure a representative bounded workload in the intended build configuration, and keep the original data contract visible while changing layout.

## Worked example / walkthrough

Example 1 sums the value field of three `{id, value}` rows stored together, an array of structs, and gets 60. Example 2 copies the values into their own vector, a structure of arrays, and gets the same 60. Equal answers make the layouts comparable; only the access pattern can separate them. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-034-example-1.cpp)

```cpp
#include <cassert>
#include <iostream>
#include <vector>

struct Sample {
  int id;
  int value;
};
int main() {
  std::vector<Sample> rows{{1, 10}, {2, 20}, {3, 30}};
  int sum = 0;
  for (const auto &row : rows)
    sum += row.value;
  assert(sum == 60);
  std::cout << "cpp-034 example 1 checks passed\n";
  return 0;
}
```

### Worked example 2

[Complete program 2](../examples/cpp-034-example-2.cpp)

#include <cassert>
#include <iostream>
#include <numeric>
#include <vector>

struct Sample {
  int id;
  int value;
};
int main() {
  std::vector<int> values{10, 20, 30};
  assert(std::accumulate(values.begin(), values.end(), 0) == 60);

## Exercises

### Exercise 1: Draw both layouts

Sketch three records as AoS and as separate ID/value vectors.

**Expected result/shape:** Same three logical rows with different physical grouping.

**Verify:** Check that both sketches contain the pairs (1, 10), (2, 20) and (3, 30), with the first interleaving ID and value and the second storing all IDs, then all values.

**Progressive hints:** Representation must preserve the row relationship.

### Exercise 2: Prove result equality

Sum values in both representations.

**Expected result/shape:** 60 from each.

**Verify:** Assert both sums equal 60, as Worked examples 1 and 2 do, using the same three values in each layout.

**Progressive hints:** Correctness is checked before performance.

### Exercise 3: Inspect reserve

Reserve 100 on an empty vector, then inspect size.

**Expected result/shape:** Size 0; capacity at least 100.

**Verify:** Assert `v.size() == 0` and `v.capacity() >= 100` after `v.reserve(100)`; do not assert an exact capacity.

**Progressive hints:** Reserved storage is not constructed logical elements.

### Exercise 4: Repair an unfair comparison

One candidate omits the value 30.

**Expected result/shape:** Reject timing comparison until both checksums equal 60.

**Verify:** Print each candidate's checksum before timing and assert both equal 60; the candidate without 30 produces 30, which must stop the comparison.

**Progressive hints:** Doing less work can falsely look faster.

### Exercise 5: Measure bounded work

Repeat one-field summation with a fixed row cap and build mode.

**Expected result/shape:** Same checksum, duration units and repetitions recorded.

**Verify:** Record the row cap, build flags, number of repetitions and each duration with its unit, and assert the checksum is identical in every repetition.

**Progressive hints:** Layout benefits depend on access pattern and hardware.

### Exercise 6: Transfer the workload

Now request ID and value together for every row.

**Expected result/shape:** Reassess the locality hypothesis without assuming SoA always wins.

**Verify:** Measure combined ID and value access in both layouts with the same row cap and repetitions, and state whether your earlier one-field result still holds.

**Progressive hints:** The useful representation follows the query pattern.

## Self-check

Why do three full records keep identity and value together? For Example 2, explain what the separate values vector gives up, and which access pattern would make each layout the better choice.

## Common pitfalls

If a layout optimization changes which value belongs to an ID, the transformation is wrong even when the total happens to match. If reserve appears to create elements, inspect size separately. If a benchmark excludes conversion for one layout but includes it for another, state that asymmetry before comparing. If a tiny fixture shows unstable timing, do not extrapolate a production speedup from it.
