# AD-safe branches, transforms and numerical domains

Start with: tmb-045, tmb-004, tmb-027.

Outcome: Distinguish data-controlled logic, parameter-controlled logic and invalid arithmetic.

The classroom companion runs in the prepared R statistics runtime. It uses base R to expose the mathematics or data contract. Compiling and executing TMB uses the separate [owned project](../projects/tmb-local/README.md); a companion run is not a TMB compiler or rpy2 receipt.

Automatic differentiation follows implemented operations. An ordinary C++ branch on fixed observation type can be appropriate, such as selecting an event or censor contribution. A branch on a changing parameter can create a recorded-path problem if later evaluations cross the branch boundary. A supported conditional-expression operation represents the selection inside the derivative machinery, but it does not make a nonsmooth function smooth.

The pinned TMB headers use compatible conditional-expression facilities such as `CppAD::CondExpGt` in their convenience functions. Framework-specific support still needs qualification when moving between CppAD and TMBad. Avoid assuming arbitrary C++ library operations participate in AD.

### Worked case A: a piecewise quadratic

Let \(f(x)=\max(x,0)^2\). Away from zero its derivative is \(2x\) for positive x and zero for negative x; at zero the first derivative exists and is zero, but the second derivative changes discontinuously. The companion checks values and first derivatives on both sides. An AD conditional can select the branch at evaluation time, while a tape built from a plain host-language branch may retain one path.

```cpp
Type positive = CppAD::CondExpGt(x, Type(0), x, Type(0));
Type objective = positive * positive;
```

This is a numerical illustration, not a normalized probability model. Its purpose is to expose branch behavior before using such logic inside an actual likelihood.

### Worked case B: an unused invalid branch can still be dangerous

Writing a conditional expression with `log(x)` as one candidate does not necessarily prevent that candidate expression from being evaluated when x is negative. Construct safe intermediate arguments first, then apply the mathematically intended selection. Do not replace invalid inputs by arbitrary epsilons without explaining how that changes the function.

The companion contrasts a stable softplus identity with naive exponentiation at large x. Stable values are necessary, but derivatives and curvature must also be checked. A positive transform can overflow; a sigmoid can saturate; a probability parameter can become poorly identified near a boundary.

### Answered discussion

**Does AD-safe mean statistically valid?** No. It concerns execution and differentiation, not model meaning. **Can I use branching to repair non-identification?** No. Constraints can define a different model, but they need scientific justification. **Is a data branch always harmless?** If data later change that branch, reconstruct or deliberately retape under a tested contract.

See the [pinned convenience helpers](https://github.com/kaskr/adcomp/blob/master/TMB/inst/include/convenience.hpp). Test crossings and extreme values explicitly; checking only one positive initial point misses these errors.

### Complete R companion

```r
f <- function(x) pmax(x, 0)^2;g <- function(x) ifelse(x > 0, 2 * x, 0)
x <- c(-2, -.1, .1, 2);h <- 1e-6
numeric_gradient <- (f(x + h) - f(x - h)) / (2 * h)
print(data.frame(x = x, value = f(x), gradient = g(x), numeric = numeric_gradient));stopifnot(max(abs(g(x) - numeric_gradient)) < 1e-7)
softplus <- function(x) pmax(x, 0) + log1p(exp(-abs(x)))
print(c(stable = softplus(1000), naive = log1p(exp(1000))))
```
