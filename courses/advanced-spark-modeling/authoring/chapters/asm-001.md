## Starting point and result

A Spark program has two kinds of work: deciding which computation to perform, and evaluating pieces of that computation on data. Before discussing a fast custom likelihood, locate those responsibilities. This chapter assumes you can read a DataFrame schema and a small Python function. It does not assume experience writing an optimizer or a distributed training loop.

The worked program creates twelve synthetic observations with three input partitions. It computes one sum through an action, inspects a query plan and repeats the same scientific calculation with a different physical partition count. The intended result is exact: the squares of the integers from zero through eleven sum to \(506\). The size is deliberately small enough that a separate Python calculation is a credible oracle. A successful local run demonstrates Spark execution and partition invariance for this case; it says nothing about cluster speed.

## Mechanism: driver, executors, partitions and actions

The **driver** owns the Spark session, constructs query expressions, submits jobs and receives small results. An **executor** runs tasks on partitions. A partition is a physical slice of the records at a particular stage, not necessarily a person, a country, a time series or any other scientifically meaningful group. A task evaluates one stage's work for one partition. A shuffle changes which executor or partition owns records before a later stage.

Calling select or filter constructs a lazy query. The expression \(x^2\) is a description that Spark can analyze and optimize. Calling collect, count or first on an aggregate asks for a result and therefore can trigger execution. The optimizer may combine adjacent expressions or move a valid filter earlier. It cannot infer that a scientific approximation you invented is correct.

For a likelihood, one driver evaluation might receive parameters \(\theta\), construct row contributions \(\ell_i(\theta)\), aggregate them across all partitions and return a scalar \(L(\theta)\). The optimizer that chooses the next \(\theta\) may live entirely on the driver. Spark distributes each evaluation; it does not automatically distribute the optimizer's control flow. A Python loop performing twenty evaluations may therefore launch twenty actions. This distinction explains both a useful architecture and its scheduling cost.

The session in the reference uses local mode with two worker threads, even when the DataFrame has three partitions. Threads and partitions are different quantities: a thread can process several tasks over time. The two-thread limit prevents a tiny teaching example from consuming an entire machine.

## Worked case 1: one objective action

Imagine the toy objective \(L=\sum_{i=0}^{11}x_i^2\). The driver knows the function and small parameter state; the observations remain in the DataFrame. The reference builds the square expression, gives the action a job-group label, then asks Spark for a count and sum in one aggregation.

The count is not decoration. A scalar loss of \(506\) is uninterpretable if half the observations disappeared or each appeared twice. A trustworthy objective contract carries its observation count alongside the value. The reference checks both twelve records and the independent sum of squares. It also checks that Spark recorded at least one job under the action's label. A job count is diagnostic evidence, not a stable API promise that one action always creates exactly one job.

The result arrives as one small row. Collecting that aggregate is different from collecting the entire training table. A real implementation may collect a vector of ten gradients or a ten-by-ten Hessian, provided the parameter dimension is bounded. It should not collect every feature row simply to avoid thinking about distributed aggregation.

## Worked case 2: change placement, keep the estimand

The second case evaluates the same observations after repartitioning to one, two and three partitions. Every result must retain \(n=12\) and \(L=506\). Repartitioning can change execution order and floating-point rounding, but it must not change which observation contributes or which model is being fit.

This example uses integer squares small enough to be represented exactly. Later chapters use floating-point likelihoods and compare within a justified tolerance. Exact equality in this toy problem does not justify requiring identical floating-point bits from a real cluster.

Contrast physical partitioning with statistical grouping. If the twelve observations belong to two subjects with correlated residuals, assigning one subject to each partition might make a convenient complete-group calculation possible. Arbitrarily splitting a subject would not make those residuals independent. A partition is chosen for computation; the observation unit and dependence model come from the scientific question.

## Failure diagnosis

A large driver memory spike after collect usually means the program collected raw records, not bounded sufficient summaries. A scalar objective that changes dramatically with partition count suggests dropped rows, duplicated rows, partition-local normalization or a stateful side effect. Small last-bit changes alone are usually a floating-point reduction question.

A driver print statement cannot tell you how many times an executor function ran. Executor code may be retried and its output can be interleaved. Use structured result rows and source-bound execution evidence. Do not treat log line order as record order.

The reference stops only its own Spark session in a finally block. A notebook retaining a prior session may otherwise hide changed configuration. If the version check fails, prepare the declared runtime explicitly instead of deleting the check.

## Interview discussion

**Does more partitioning make a model more statistically accurate?** No. Partitioning changes placement and scheduling. Statistical accuracy depends on the objective, data and inference assumptions. More partitions may improve utilization or make scheduling overhead worse.

**Where does a custom optimizer run?** It can run on the driver while each loss/gradient evaluation is distributed. A Spark action supplies numerical summaries; the driver decides the next trial vector. This architecture is appropriate when the parameter vector is modest and the objective decomposes.

**Why return a count with a loss?** Count and, when relevant, weight totals let the caller detect a changed data population. They also distinguish a sum objective from a mean objective and make gradient scaling auditable.
