## The question and the mechanism

Choose between forcing a value and respecting an existing selection on the same column.

The ordinary Boolean-filter behavior of CALCULATE replaces an existing selection on the same column. KEEPFILTERS changes that policy to intersection. It is not a universal instruction to preserve every report feature; it applies to the filter argument it wraps. Naming the policy makes a measure's interaction with user selections predictable.

Under an existing Blue selection, forcing Red gives Pen revenue 24. Keeping Blue while additionally requiring Red yields an empty product set because no product has both values in our fixture. BLANK is therefore a meaningful result, not a syntax failure. The measure is expressing 'Red within the current selection', rather than 'Red regardless of the selected color'.

A broader current selection can still overlap the new restriction. If Blue and Red are selected, KEEPFILTERS(Blue) retains the blue subset and gives 163. This is useful for measures that quantify an interesting subgroup without silently expanding the population chosen by a learner or report user. Explain that contract in the metric name and tooltip.

## Vocabulary and expression anatomy

KEEPFILTERS wraps the Boolean condition inside CALCULATE. The outer CALCULATETABLE supplies a simulated selection for this named reference. In each case, enumerate the original allowed colors, intersect with the new set, then propagate the remaining product keys to Sales.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: A disjoint subgroup stays empty

**Starting context:** Original allowed color {Blue}; compare replacement with intersection by {Red}.

```dax
EVALUATE CALCULATETABLE ( ROW ( "ForcedRed", CALCULATE ( [NetRevenue], Product[Color] = "Red" ), "RedWithinSelection", CALCULATE ( [NetRevenue], KEEPFILTERS ( Product[Color] = "Red" ) ) ), Product[Color] = "Blue" )
```

**Context trace:**

1. Replacement changes the allowed set to Red and admits Pen.
2. Intersection computes {Blue} intersect {Red}, an empty set.
3. ForcedRed is 24; the selected-subgroup result is BLANK.

**Hand-derived worked-reference result:**

| ForcedRed | RedWithinSelection |
| --- | --- |
| 24 | BLANK |

An intersection measure should not escape its selected population to manufacture a nonblank result.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: An overlapping subgroup is retained

**Starting context:** Original allowed colors {Blue, Red}; restrict to Blue without expanding selection.

```dax
EVALUATE CALCULATETABLE ( ROW ( "SelectedRevenue", [NetRevenue], "BlueWithinSelection", CALCULATE ( [NetRevenue], KEEPFILTERS ( Product[Color] = "Blue" ) ) ), Product[Color] IN { "Blue", "Red" } )
```

**Context trace:**

1. All products with recorded sales are Blue or Red, totaling 187.
2. Intersecting with Blue removes Pen's 24.
3. Notebook and Mug remain and total 163.

**Hand-derived worked-reference result:**

| SelectedRevenue | BlueWithinSelection |
| --- | --- |
| 187 | 163 |

KEEPFILTERS does not freeze the original total. It can narrow a population while preserving the fact that the starting selection is an outer constraint.

## Progressive hints

1. Intersect the two color sets.
2. Keep only colors also present in the original {Blue, Red} set.
3. Wrap the condition defining the subgroup.
4. That is a change of population policy.
5. It intersects with the context that exists at its evaluation point.
6. Ask whether failure counts should remain inside the selected cohort.
