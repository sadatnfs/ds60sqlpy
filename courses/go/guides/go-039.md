# go-039: List-watch continuity, bookmarks and expired history

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-038

## Learning objectives

Apply list-watch events to a local cache and restart from a fresh list when watch history has expired. Along the way, explain list snapshot, watch bookmark, expired history; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A watch streams changes after a chosen observation point, but it is not an infinite durable event log. A controller normally obtains a list snapshot and continues from its resourceVersion so the initial state and later events connect coherently. Connections end, history can expire, and clients must recover by relisting when the server cannot continue from an old version. Bookmarks can advance the known position without carrying an ordinary object mutation; they are not guaranteed periodic heartbeats. Treat events as prompts to reconcile current state. Never assume every intermediate transition is delivered exactly once or that a disconnected watch proves no changes occurred.

## Vocabulary and concepts

- **List snapshot:** A collection observed at a defined API version point.
- **Watch bookmark:** A progress marker without an ordinary object update.
- **Expired history:** A watch position the server can no longer continue.

## Syntax anatomy and reasoning

This offline reducer handles ADDED, MODIFIED, DELETED, BOOKMARK and an explicit expired-history signal. Ordinary events update a keyed cache; bookmarks only advance the token. Expiration invalidates continuity and requires a fresh list rather than fabricated incremental recovery. The real API uses Status errors and HTTP responses whose interpretation belongs to client-go or a carefully reviewed client.

## Worked example / walkthrough

### Worked example 1: Apply an added object

Apply ADDED for demo with value 2.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type WatchEvent struct {
	Kind, Key, Version string
	Value              int
}
type WatchState struct {
	Items     map[string]int
	Version   string
	NeedsList bool
}

func newWatch() WatchState { return WatchState{Items: map[string]int{}} }
func applyWatch(s *WatchState, e WatchEvent) error {
	switch e.Kind {
	case "ADDED", "MODIFIED":
		s.Items[e.Key] = e.Value
	case "DELETED":
		delete(s.Items, e.Key)
	case "BOOKMARK":
	case "EXPIRED":
		s.NeedsList = true
		return errors.New("relist required")
	default:
		return errors.New("unknown event")
	}
	s.Version = e.Version
	return nil
}

func main() {
	// Apply an added object
	{
		s := newWatch()
		check(applyWatch(&s, WatchEvent{Kind: "ADDED", Key: "demo", Value: 2, Version: "a"}) == nil && s.Items["demo"] == 2, "add")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The cache gains demo=2.

The key identifies current state. Reconciliation should inspect that state rather than treat addition as an irreversible once-only command.

### Worked example 2: Apply a modification

Add then modify the same key.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type WatchEvent struct {
	Kind, Key, Version string
	Value              int
}
type WatchState struct {
	Items     map[string]int
	Version   string
	NeedsList bool
}

func newWatch() WatchState { return WatchState{Items: map[string]int{}} }
func applyWatch(s *WatchState, e WatchEvent) error {
	switch e.Kind {
	case "ADDED", "MODIFIED":
		s.Items[e.Key] = e.Value
	case "DELETED":
		delete(s.Items, e.Key)
	case "BOOKMARK":
	case "EXPIRED":
		s.NeedsList = true
		return errors.New("relist required")
	default:
		return errors.New("unknown event")
	}
	s.Version = e.Version
	return nil
}

func main() {
	// Apply an added object
	{
		s := newWatch()
		check(applyWatch(&s, WatchEvent{Kind: "ADDED", Key: "demo", Value: 2, Version: "a"}) == nil && s.Items["demo"] == 2, "add")
	}

	// Apply a modification
	{
		s := newWatch()
		_ = applyWatch(&s, WatchEvent{Kind: "ADDED", Key: "demo", Value: 2, Version: "a"})
		check(applyWatch(&s, WatchEvent{Kind: "MODIFIED", Key: "demo", Value: 3, Version: "b"}) == nil && s.Items["demo"] == 3, "modify")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The cached value becomes 3.

The newest observed value replaces the prior value for this simplified cache. A production informer also manages resource typing and synchronization.

## Common pitfalls and diagnosis

Treating a watch as a durable log is the main error: connections drop and history expires, so a client that only resumes from its last version eventually gets an expired error and must relist. Another mistake is ignoring bookmarks, which advance the version without objects. Deletes must be idempotent, and unknown event types should fail loudly rather than be guessed at.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Apply an added object: predict an edited check

1. Restate the expected observation: The cache gains demo=2.
2. ADDED stores the key with its value. What does demo hold?
3. The event now carries value 3, so the cache holds demo=3 and `s.Items["demo"]==2` fails. Applying the event works; the payload changed.

### Hint for investigation 2: Apply a modification: diagnose an edited check

1. Restate the expected observation: The cached value becomes 3.
2. MODIFIED replaces the stored value. What is demo after the second event?
3. The modification now carries 4, so the cache holds 4 and `s.Items["demo"]==3` fails. Restore the value 3 in the event.

### Hint for investigation 3: Advance a bookmark

1. Restate the expected observation: The version advances and no item is created.
2. A bookmark carries a version but no object. What changes?
3. A bookmark supplies continuity information, not an object named by an empty key.

### Hint for investigation 4: Invalidate expired continuity

1. Restate the expected observation: The state requests a relist.
2. EXPIRED sets a flag and returns an error. What do err and NeedsList hold?
3. Continuing from an unavailable position can miss state changes.

### Hint for investigation 5: Delete current membership

1. Restate the expected observation: The cache remains empty.
2. delete on a missing key is a no-op. How many items remain?
3. Idempotent removal tolerates repeated signals.

### Hint for investigation 6: Transfer unknown-event refusal

1. Restate the expected observation: An error is returned without accepting invented semantics.
