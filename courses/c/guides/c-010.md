# c-010: Structs, enums and tagged domain values

## Level and prerequisites

Beginner, approximately 90 minutes plus a later retrieval session. Direct prerequisites: `c-009`

## Learning objectives

Model domain values with structs, enums and tagged unions, and reject an invalid tag instead of guessing. Along the way, explain struct, discriminator and padding. Implement the six investigations, from the "use named fields" case to the "transfer invalid-tag diagnosis" case, with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

A struct groups named fields into one object. An enum gives meaningful names to integer constants, but it does not automatically prevent every other integer value from appearing in the representation. A tagged union pairs a discriminator with a union whose active interpretation depends on that tag. This can model alternatives without allocating a class hierarchy, but every reader must check the tag before interpreting the stored payload. Struct assignment copies fields, including pointer values rather than their targets. Struct padding and representation are implementation details, so bytewise comparison or raw struct serialization is not a general semantic equality policy.

## Vocabulary and concepts

- **Struct:** A value composed of named fields.
- **Discriminator:** A tag identifying which alternative a value represents.
- **Padding:** Implementation-inserted storage between or after fields.

## Syntax anatomy and execution trace

struct Point names a type unless a typedef adds a shorter alias. A designated initializer uses .field=value. The dot operator accesses a struct value; -> accesses through a struct pointer. A union shares storage among alternatives. Switch on an enum tag and handle unexpected values explicitly. Compare meaningful fields rather than relying on memcmp over padding bytes.

## Worked example / walkthrough

### Worked example 1: Use named fields

Construct Point with x 2 and y 3.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

struct Point {
  int x, y;
};
enum ValueTag { VALUE_INT, VALUE_TEXT };
struct Value {
  enum ValueTag tag;
  union {
    int integer;
    const char *text;
  } data;
};
bool valid_tag(enum ValueTag tag) {
  return tag == VALUE_INT || tag == VALUE_TEXT;
}

int main(void) {
  /* Use named fields */
  {
    struct Point p = {.x = 2, .y = 3};
    CHECK(p.x + p.y == 5);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The field sum is 5.

Designated initialization preserves field meaning even if declaration order changes.

### Worked example 2: Copy scalar fields

Copy a Point and change the copied x.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

struct Point {
  int x, y;
};
enum ValueTag { VALUE_INT, VALUE_TEXT };
struct Value {
  enum ValueTag tag;
  union {
    int integer;
    const char *text;
  } data;
};
bool valid_tag(enum ValueTag tag) {
  return tag == VALUE_INT || tag == VALUE_TEXT;
}

int main(void) {
  /* Use named fields */
  {
    struct Point p = {.x = 2, .y = 3};
    CHECK(p.x + p.y == 5);
  }

  /* Copy scalar fields */
  {
    struct Point a = {2, 3};
    struct Point b = a;
    b.x = 9;
    CHECK(a.x == 2 && b.x == 9);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The original x stays 2.

Scalar fields are copied into independent struct storage. Pointer fields would still designate their original targets.

## Exercises

How the hints, control edits and regressions below work: [Work an exercise](../STUDY-GUIDE.md#work-an-exercise).

### Exercise 1: Use named fields: change one input

In worked example 1, change `struct Point p = {.x = 2, .y = 3};` to `struct Point p = {.x = 3, .y = 3};`. Predict which value the CHECK on `p.x + p.y == 5` sees, then run and restore.

**Expected:** `Check failed` at `p.x + p.y == 5`; restoring `struct Point p = {.x = 2, .y = 3};` passes again.

**Verify:** Name the value that made `p.x + p.y == 5` false, where worked example 1 showed that the field sum is 5.

**Progressive hints:** First trace `p` from initialization. Then compute what the CHECK sees with `struct Point p = {.x = 3, .y = 3};` in place.

### Exercise 2: Copy scalar fields: debug a regression

Worked example 2 now has a line reading `struct Point a = {3, 3};`. Repair it so that the original x stays 2 again.

**Expected:** `Check failed` at `a.x == 2 && b.x == 9` until the line reads `struct Point a = {2, 3};` again.

**Verify:** Explain how `struct Point a = {3, 3};` changes the value `a.x == 2 && b.x == 9` tests, using your failing and repaired runs.

**Progressive hints:** First trace `a` and `b` from initialization. Then compare `struct Point a = {3, 3};` with worked example 2's original line.

### Exercise 3: Interpret an integer alternative

Create a tagged number with an integer payload.

**Expected:** The checked payload is 7.

**Verify:** Keep a CHECK equivalent to `v.tag == VALUE_INT && v.data.integer == 7`. Control edit: changing `struct Value v = {.tag = VALUE_INT, .data.integer = 7};` to `struct Value v = {.tag = VALUE_INT, .data.integer = 8};` must fail it; then restore it.

**Progressive hints:** First trace `v` from initialization. Then recall: The tag establishes which union member this design permits the reader to interpret.

### Exercise 4: Interpret a text alternative

Create a tagged value containing a borrowed string.

**Expected:** The text is ready.

**Verify:** Keep a CHECK equivalent to `v.tag == VALUE_TEXT && strcmp(v.data.text, "ready") == 0`. Control edit: changing `struct Value v = {.tag = VALUE_TEXT, .data.text = "ready"};` to `struct Value v = {.tag = VALUE_TEXT, .data.text = "ready!"};` must fail it; then restore it.

**Progressive hints:** First trace `v` from initialization. Then recall: The text pointer borrows static string-literal storage.

### Exercise 5: Compare semantic fields

Compare two equal Points by x and y.

**Expected:** Semantic equality is true.

**Verify:** Keep a CHECK equivalent to `a.x == b.x && a.y == b.y`. Control edit: changing `struct Point a = {2, 3}, b = {2, 3};` to `struct Point a = {3, 3}, b = {2, 3};` must fail it; then restore it.

**Progressive hints:** First trace `a` and `b` from initialization. Then recall: Field comparison ignores padding.

### Exercise 6: Transfer invalid-tag diagnosis

Pass an unexpected discriminator to a validator.

**Expected:** The validator rejects it.

**Verify:** Keep a CHECK equivalent to `!valid_tag((enum ValueTag)99)`. Control edit: `CHECK(valid_tag((enum ValueTag)99));` must fail; then restore it.

**Progressive hints:** First work out what `valid_tag` returns here. Then recall: An enum name list is not a runtime input validator.

## Common pitfalls and diagnosis

Trusting an `enum` variable to hold only its listed names: any integer can arrive from input or a cast. Switch on the tag with a `default` that reports an invalid value, and read only the union member the tag says was stored.
