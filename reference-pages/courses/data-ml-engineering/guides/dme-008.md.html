dme-008: Source, dependency and data identities for reproducible work#

Level: Beginner | Prepared runtime: python-core

Direct prerequisites: dme-002, dme-006, dme-007.

Outcome: Build a reviewable source/data/configuration hash manifest.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

A result needs more than a filename#

A file named final_result.json does not explain which inputs or program produced it. If that name is reused tomorrow, the old report may point to new bytes. Reproducible engineering therefore records identities for the relevant source, inputs, configuration and execution environment, along with the observations actually obtained.

An artifact is a produced or retained object such as a dataset, model, configuration file or report. A manifest describes the objects expected in a particular collection and their identities. A content hash deterministically summarizes bytes under a specified algorithm. A version label is a human or system name that may refer to an artifact. These concepts are related, but a convenient label is not automatically an immutable content identity.

The complete program uses real files and SHA-256 hashes. It does not simulate a Git server or claim to publish a software release. The first case records four local files and actually executes the recorded reviewed transformation source. The second case changes an input and checks that the old identity no longer qualifies it.

This small exercise is useful because the same questions recur in a large workflow: which data snapshot was used, which code ran, which configuration mattered, which environment was prepared and which checks were observed? A large platform can store these answers, but it cannot make an unrecorded assumption reproducible by assigning a job number afterward.

What a hash establishes#

A SHA-256 digest changes when the hashed bytes change, except for the algorithm's theoretical possibility of a collision. For ordinary artifact-integrity checks, this provides a useful way to detect mismatched bytes. It does not establish that the producer was trusted, that the data is correct or that a computation actually used the artifact it names.

If an attacker can replace both an artifact and its expected digest, comparing them does not authenticate the source. Trust must come from a separately established process, such as a controlled publication channel, reviewed provenance or a suitable signature policy. This chapter uses locally authored trusted source and synthetic data; it does not present a hash as a security boundary for arbitrary code.

Byte identity is also different from semantic equivalence. Two JSON files can represent the same values while differing in whitespace or key order. Their byte hashes differ. Canonical serialization can reduce some representational differences, but a generic normalization is not proof that two datasets or programs mean the same thing. Row order, precision, duplicates, schema and units may matter to a consumer.

Source control and environment control solve different problems#

Git records versioned source changes and relationships between commits. Read-only commands such as git status, git diff and git log help a contributor inspect a checkout. A commit identifier is useful only when it corresponds to the actual source used for the run. Uncommitted edits, generated files and external inputs can still change behavior.

The ordinary pad in this chapter does not require a Git executable and does not modify the classroom repository. Git work belongs in an explicitly owned contributor or project directory. Do not experiment with destructive Git commands against your learning checkout merely to reproduce a small example. A source manifest in this pad is a concrete local artifact check, not a fabricated Git history.

Dependency controls address another boundary. A requirements declaration states a set of desired packages; a reviewed lock records resolved identities under supported platform constraints. A container image adds a packaged filesystem and runtime environment. A human-readable image tag is still a name that can move. Exact image digests and source identities provide stronger references when recorded by the surrounding build and runtime tooling.

Inside the pad, the program records the actual Python version, implementation and operating-system name. This is an illustrative environment record, not a complete inventory of every native library or kernel behavior. A full classroom qualification also needs the prepared worker image and platform evidence collected by the host tooling. The pad does not obtain that evidence by mounting an engine socket.

Worked case 1: Record and execute a small computation bundle#

The first case creates an owned temporary directory containing input values [2, 3, 1], a reviewed transform.py function, a configuration declaring package units, and an environment record. It hashes each file and stores the digests under stable relative names. Building the manifest from a reversed filename list yields the same mapping because the manifest orders the names explicitly.

The program then verifies that each recorded file exists and still has the expected bytes. It executes the reviewed transformation file with runpy.run_path, obtains the compute function from that program's namespace, and calls it on the parsed input. The observed result is six, which is checked against an independent hand-derived expectation.

This source execution is deliberate and local. The transformation text was authored in the example; it is not an untrusted downloaded program or a model artifact loaded with arbitrary deserialization. Executing unknown code would require a different trust decision. A matching hash alone would not make such code safe.

The returned evidence includes the result, input identity and recorded filenames. The temporary directory is removed after the case, so the output is an explanation of a bounded investigation rather than a durable external release. A real project would store the accepted manifest and artifacts in its declared persistent state and verify them again when consumed.

Worked case 2: Changed values invalidate the old claim#

The changed case first records an input file containing [2, 3, 1], then replaces its last value with four. The old expected digest no longer matches. The verifier raises a clear error before the old identity can be used to qualify the new bytes.

The new values sum to nine. That new result does not retroactively change the original observation of six. Both observations belong to different input states. An evaluation report, cache entry or model comparison that reuses the old input identity for the new values would therefore be misleading even if every individual file remained syntactically valid.

The case then removes formatting spaces while retaining the same new values [2,3,4]. The byte identity changes again, while the parsed sum remains nine. This second comparison shows why a changed hash is evidence of changed bytes, not necessarily changed numerical meaning. If a system wants a semantic identity, it must define and validate the relevant normalization rather than assuming one automatically.

The assertions establish both distinctions: changed data rejects an old byte identity, and differently formatted bytes can represent the same simple JSON values. Neither observation proves that a complete distributed workflow has been reproduced. It is a bounded foundation for the larger artifact, checkpoint and publication contracts developed later.

Complete worked program#

"""Actual content identities for a bounded reproducible computation bundle."""

import hashlib
import json
import platform
import runpy
import tempfile
from pathlib import Path


def fingerprint(path):
    return hashlib.sha256(path.read_bytes()).hexdigest()


def manifest(root, paths):
    return {name: fingerprint(root / name) for name in sorted(paths)}


def verify(root, recorded):
    changed = [
        name
        for name, digest in recorded.items()
        if not (root / name).is_file() or fingerprint(root / name) != digest
    ]
    if changed:
        raise ValueError("Recorded inputs changed: " + ", ".join(changed))


def example_one():
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        (root / "input.json").write_text("[2, 3, 1]\n", "utf-8")
        (root / "transform.py").write_text(
            "def compute(values):\n    return sum(values)\n", "utf-8"
        )
        (root / "configuration.json").write_text('{"unit": "packages"}\n', "utf-8")
        (root / "environment.json").write_text(
            json.dumps(
                {
                    "python": platform.python_version(),
                    "implementation": platform.python_implementation(),
                    "system": platform.system(),
                },
                sort_keys=True,
            )
            + "\n",
            "utf-8",
        )
        names = ["input.json", "transform.py", "configuration.json", "environment.json"]
        recorded = manifest(root, names)
        assert recorded == manifest(root, list(reversed(names)))
        verify(root, recorded)
        namespace = runpy.run_path(str(root / "transform.py"))
        result = namespace["compute"](json.loads((root / "input.json").read_text("utf-8")))
        assert result == 6
        return {
            "result": result,
            "input_identity": recorded["input.json"],
            "recorded_files": sorted(recorded),
            "verified": True,
        }


def example_two():
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        (root / "input.json").write_text("[2, 3, 1]\n", "utf-8")
        recorded = manifest(root, ["input.json"])
        (root / "input.json").write_text("[2, 3, 4]\n", "utf-8")
        try:
            verify(root, recorded)
        except ValueError:
            rejected = True
        else:
            raise AssertionError("An old result cannot qualify changed input bytes")
        new = manifest(root, ["input.json"])
        assert new != recorded
        assert sum(json.loads((root / "input.json").read_text("utf-8"))) == 9
        (root / "input.json").write_text("[2,3,4]\n", "utf-8")
        reformatted = manifest(root, ["input.json"])
        assert reformatted != new
        assert sum(json.loads((root / "input.json").read_text("utf-8"))) == 9
        return {
            "old_claim_rejected": rejected,
            "new_result": 9,
            "identity_changed": True,
            "hash_is_not_source_authentication": True,
            "same_values_can_have_different_byte_identities": True,
        }


def main():
    print("A reviewable local computation bundle:", example_one())
    print("Changed data invalidates the old result:", example_two())


if __name__ == "__main__":
    main()

Diagnose reproducibility failures#

Start by identifying which claim failed. Is an artifact missing, are its bytes different, did the program or configuration change, or did the environment produce a different numerical result from otherwise matching inputs? These are different investigations and may need different remedies.

Do not silently update an expected hash to match an unexplained new artifact. That removes the discrepancy without explaining it. Retain the previous identity, determine why the object changed and decide whether the new object needs fresh qualification. Similarly, a test report from an older source revision remains historical evidence; it is not automatically a pass for the current checkout.

Some numerical workloads permit small differences across hardware or library implementations. Record the relevant tolerance and reason about whether it preserves the required decision. Exact integer totals, identifiers and schema fields usually have different equality requirements. A tolerance should explain numerical approximation, not hide a wrong dataset or a unit conversion error.

Where this is useful#

Use content identities for raw deliveries, feature snapshots, model artifacts, local caches, backup manifests and release receipts. Use source control to review how code and configuration changed. Use explicit runtime records to identify the execution environment. Combine these records with actual tests and readback instead of treating any single identifier as complete qualification.

These ideas also support incident response. A retained manifest can help determine whether a bad result came from changed source, changed input, an incompatible artifact or an unsupported environment. That is more useful than a mutable filename and a screenshot of a successful command.

Answered interview discussion#

Does the same random seed make a training run reproducible? It controls one source of variation. Data order, source, dependencies, hardware, parallel execution and configuration can still matter. Record the complete relevant contract and distinguish exact from tolerance-based comparison.

Does a matching hash prove an artifact is safe? It proves agreement with the expected byte identity under the chosen hash check. Source trust and authorization are separate questions.

Why keep relative artifact names? They describe the logical bundle without embedding one machine's absolute paths. The consumer still needs a declared location and access policy for the actual bytes.

What should happen after an input changes? Invalidate incompatible cached or qualified results, compute under the new identity and retain the appropriate fresh evidence. Do not relabel the old observation as if it came from the new input.
