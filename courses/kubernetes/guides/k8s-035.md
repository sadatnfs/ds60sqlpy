# k8s-035: Watches and optimistic concurrency

## Level and prerequisites

Advanced; about 120 minutes plus review. Direct prerequisites: `k8s-003`, `k8s-018`, `k8s-030`.

## Learning objectives

Handle resource-version conflicts and watch expiration without losing state.

## Vocabulary and concepts

A read-modify-write operation can lose another client's change if it assumes the object stayed unchanged after reading. Kubernetes uses resourceVersion for optimistic concurrency. The client submits a conditional update based on the version it read; if the stored object changed, the server can reject the stale update with 409 Conflict. The correct recovery is to read current state and recompute the intended change, not repeatedly force the old snapshot over newer state.

resourceVersion is an opaque token supplied by the server. Treat it as a string for the API contract. Do not increment it, subtract two versions to estimate elapsed time or use it as a user-defined clock. UID identifies an object lifetime, while resourceVersion identifies a state version within API semantics. Recreating the same name can change UID and invalidate an operation's ownership assumptions.

A watch streams changes after a starting point, reducing repeated full-list work. It can disconnect, deliver repeated information or expire beyond the server's retained history. A robust observer rebuilds a current snapshot when required and reconciles from that state. The normal course credential does not offer arbitrary watch/update operations; this is a host-scoped advanced activity with an offline trace model.

### Key terms

- **resourceVersion:** An opaque string identifying the stored version of an object, used for concurrency checks and for resuming watches.
- **Optimistic concurrency:** Updating with the resourceVersion you read, so the server rejects the write if someone changed the object since.
- **409 Conflict:** The HTTP status returned when an update carries a stale resourceVersion. The client should reread and reapply its intent.
- **Watch:** A long-lived API request that streams changes after a given resourceVersion.
- **Relist:** Fetching a fresh full list after a watch reports 410 Gone, because the requested resourceVersion is too old.

## Trace a conflict without losing intent

Client A and client B read the same ConfigMap UID u1 at token rv-A with message hello. B writes reviewer and receives a new token rv-B. A then tries an update carrying rv-A. The server returns conflict because A's premise is stale. A should reread u1 at rv-B and decide whether its intended change still makes sense.

Recomputation is important when the edit is relative, such as adding one approved entry or merging a field. Replacing the entire old object can erase B's unrelated field changes. A bounded retry budget prevents an indefinitely contended object from holding a lesson operation forever. Cancellation must stop retries and leave the current object recoverable.

If A rereads the same name with UID u2, this is a replacement object. The course ownership contract stops instead of updating it. A resourceVersion comparison alone does not authorize mutation across identity replacement.

## Recover a watch from current state

A typical observer obtains a list snapshot and its resourceVersion, then watches from that point. It maintains a local view as matching events arrive. A bookmark can indicate progress in the stream; it does not describe a new workload object that should be created or counted as an application event.

When the server reports that the requested history is too old, commonly 410 Gone, relist and rebuild the current view before watching again. Replaying an imagined sequence of missing events is unsafe because those events are not available. A level-driven reconciler can act on the new snapshot without needing every intermediate transition.

Deleting and recreating a name must replace the local identity entry, not silently merge old-owner state with the new object. Duplicate events should not double-count side effects. Watches provide observation, not an exactly-once external action guarantee.

## Worked example / walkthrough

### Worked example 1: Replay a stale conditional update

Store: UID u1, resourceVersion rv-B, message reviewer. Request: expected UID u1, expected token rv-A, new message hello. Identity matches, version does not. Refuse with conflict and preserve reviewer.

**Expected:** The stale request changes nothing. A reread is required before a new bounded attempt.

### Worked example 2: Rebuild after expired history

Local cache holds hello-config UID u1. Watch reports 410. A fresh list now contains hello-config UID u2, message reviewer. Replace the cache from the snapshot, then resume observation with its list token.

**Expected:** The current cache contains u2 only; no invented intermediate event or old-UID mutation is permitted.

## Exercises

### Exercise 1: Separate name, UID and version

Explain the role of hello-config, u1 and rv-A.

**Expected result/shape:** Name addresses an object; UID its lifetime; resourceVersion is an opaque API token.

**Verify:** For each identifier, state what changes when the object is deleted and recreated with the same name.

**Progressive hints:** A reused name is not a reused identity.

### Exercise 2: Predict the conflict

Apply an rv-A update to stored rv-B with the same UID.

**Expected result/shape:** 409-style conflict with current data unchanged.

**Verify:** Read the stored object after the attempt; its resourceVersion and data must match the state before the attempt.

**Progressive hints:** The precondition is checked before mutation.

### Exercise 3: Recompute after reread

Read rv-B and preserve unrelated fields while reconsidering the intended message edit.

**Expected result/shape:** A new conditional request uses current state and a bounded retry count.

**Verify:** Confirm that the new request carries the current resourceVersion, preserves unrelated fields and has a retry limit.

**Progressive hints:** Do not resend the old whole-object snapshot.

### Exercise 4: Stop on replacement identity

Reread the same name with UID u2 when the lease expected u1.

**Expected result/shape:** Refuse the mutation across object replacement.

**Verify:** Compare the readback UID with the recorded UID before any write.

**Progressive hints:** Ownership follows the recorded UID.

### Exercise 5: Recover from watch expiration

Replace a stale cache with a supplied fresh list after 410.

**Expected result/shape:** Current u2 snapshot retained; watcher restarts from the new list token.

**Verify:** Confirm that the cache was replaced by the list result and that the watch resumed from the list's resourceVersion.

**Progressive hints:** Relist instead of guessing missed events.

### Exercise 6: Handle bookmarks and duplicates

Classify a bookmark and a repeated modified event.

**Expected result/shape:** Bookmark advances progress; duplicate state does not repeat external effects.

**Verify:** Check that the duplicate event triggers no second external effect.

**Progressive hints:** Observation events are not a transaction log.

## Self-check

Your watch failed because its history expired. Why do you relist rather than replay the missing events, and how does a bookmark help a watcher avoid that failure?

## Common pitfalls

A conditional replace, a patch with appropriate preconditions and server-side apply have different merge/ownership semantics. This lesson models compare-and-swap on a tiny object; it does not teach that every PATCH automatically prevents lost updates. Specify the actual API operation and precondition when reviewing a live client.

A supplied 409 or 410 trace is a deterministic teaching fixture. A live receipt must include the exact owned identity, request outcome and bounded recovery observation without exposing credentials. Do not enable broad watch or write permissions merely to make a reading exercise runnable in the normal module pad.

## Retrieval and transfer
