## Learning objectives

## Vocabulary and concepts

An auditable CLI is a command-line program whose inputs, accepted values, rejected records and output can be reconciled. Parsing and business validation are separate steps. Integer cents avoid decimal rounding ambiguity. The ledger keeps every input accounted for instead of silently discarding bad text.

<!-- terms:start -->

- **auditable CLI:** a command-line program whose inputs, accepted values, rejected records and output can be reconciled.
- **business validation:** the domain rule applied after a field parses as an integer, such as rejecting a negative reading.
- **conservation check:** the equation accepted plus rejected equals input rows, which catches dropped or uncounted records.
- **fatal operation failure:** an error such as a missing input file or an exceeded input budget that stops the run instead of counting as a rejected row.
- **integer cents:** whole-number currency units that avoid decimal rounding ambiguity.

<!-- terms:end -->

## Syntax and mechanism

Parse each complete field with from_chars, require the entire string to be consumed, then add only valid nonnegative values. Maintain accepted and rejected counts independently from the sum. Returning nonzero is appropriate for a fatal file failure; per-row rejection can be a documented partial-report policy.

## Trace the mechanism

Reconciliation is a conservation rule: input_count equals accepted_count plus rejected_count. The total alone is too weak because losing a valid zero changes count without changing money. Keep one ledger row for every raw input before grouping. The malformed suffix 25x is a useful negative control because a convenient prefix parser produces an apparently reasonable but incorrect amount. The capstone succeeds only when another learner can repeat both the normal result and the rejected shortcut.

## A small CLI with an explicit data contract

The capstone is a pipeline with boundaries: obtain raw lines, validate each field, classify each record, aggregate accepted values, then publish a report. Each stage has a different failure policy. A malformed row contributes to rejected count; a missing input file or exceeded input budget is a fatal operation failure. Treating both as an empty successful dataset would make operational errors indistinguishable from legitimate data.

The five-row fixture contains 10, 0, bad, -2 and 25. Under the declared nonnegative integer grammar, three rows are accepted and two rejected. The accepted values sum to 35. The conservation equation accepted+rejected=input rows is an independent check: a correct total can still hide a dropped zero or an uncounted malformed row. Preserve all three report values rather than testing only the sum.

Parsing and aggregation should not be interleaved in a way that publishes partially trusted values. For 10x, a prefix conversion may yield 10, but full consumption fails and the row must not contribute. For 0, optional presence is true even though the number is zero. For -2, integer parsing succeeds but the domain policy rejects negative readings. These are three different branches that the reference exercises.

The browser example uses an embedded deterministic vector. The separate executable reference also supports --input FILE for a host file-driven run. It caps row count and line length, checks open/read failures and returns status 2 for fatal errors. The ordinary successful report returns 0. A malformed row is counted under the declared report policy rather than necessarily aborting the whole file. That policy must be stated, because strict-all-or-nothing ingestion would be a different product.

File format is part of the interface. These fixtures are one decimal reading per line, not CSV with headers, quoted fields or comma-separated records. A filename ending in csv does not turn the parser into a CSV implementation. The working directory controls relative path resolution, while the command-line argument chooses the file. Keep the source path, executable path and input path distinct in the handoff.

A bounded program also needs a publication rule. The report should be emitted only after the reader has finished within its budget and any fatal I/O condition has been checked. Otherwise a caller may mistake a partial total printed before a later failure for the final answer. The capstone's fixed output schema gives another program an inspectable contract without requiring it to infer meaning from a mixture of progress text and data.

## Worked example / walkthrough

Example 1 runs `parse_reading` over the rows `"10"`, `"0"`, `"bad"`, `"-2"` and `"25"` and keeps a ledger: 3 accepted, 2 rejected, total 35. Example 2 isolates the edge cases, showing that `"0"` is a valid reading while `"10x"` is rejected outright instead of being read as 10. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-014-example-1.cpp)

```cpp
#include <cassert>
#include <charconv>
#include <iostream>
#include <optional>
#include <string>
#include <string_view>
#include <system_error>
#include <vector>

std::optional<int> parse_reading(std::string_view s) {
  int n = 0;
  auto [p, e] = std::from_chars(s.data(), s.data() + s.size(), n);
  if (e != std::errc{} || p != s.data() + s.size() || n < 0)
    return {};
  return n;
}
int main() {
  const std::vector<std::string> rows{"10", "0", "bad", "-2", "25"};
  int accepted = 0, rejected = 0;
  long long total = 0;
  for (const auto &raw : rows) {
    if (auto value = parse_reading(raw)) {
      ++accepted;
      total += *value;
    } else {
      ++rejected;
    }
  }
  assert(accepted == 3 && rejected == 2 && total == 35);
  std::cout << "accepted=" << accepted << " rejected=" << rejected
            << " total=" << total << "\n";
  std::cout << "cpp-014 example 1 checks passed\n";
  return 0;
}
```

**Expected:** With assertions enabled, the program exits with status 0 and prints:

```text
accepted=3 rejected=2 total=35
cpp-014 example 1 checks passed
```

## Exercises

### Exercise 1: Define the input contract

Write the grammar and rejection policy for the five rows.

**Expected result/shape:** Nonnegative base-10 whole fields; bad and -2 rejected.

**Verify:** Apply your written grammar to each of the five rows by hand and confirm it accepts exactly 10, 0 and 25 and gives a reason for rejecting `bad` and `-2`.

**Progressive hints:** Syntax and domain checks have separate reasons.

### Exercise 2: Implement the ledger

Store raw row, accepted value or rejection reason.

**Expected result/shape:** 5 ledger entries, 3 accepted, 2 rejected.

**Verify:** Assert the ledger has 5 entries, 3 holding a value and 2 holding a reason, and confirm each entry keeps its original raw text.

**Progressive hints:** Every source row needs an accountable outcome.

### Exercise 3: Produce the report

Calculate accepted count and exact total.

**Expected result/shape:** accepted=3 rejected=2 total=35.

**Verify:** Compare your printed line with Worked example 1's assertion `accepted == 3 && rejected == 2 && total == 35`; the total is a `long long` and includes the accepted 0.

**Progressive hints:** Counts and total are independent contracts.

### Exercise 4: Inject trailing junk

Replace 25 with 25x.

**Expected result/shape:** accepted=2 rejected=3 total=10.

**Verify:** Change only the last row to `25x`: the original assertion now aborts, and with it updated to 2, 3 and 10 the program prints `accepted=2 rejected=3 total=10`.

**Progressive hints:** Full consumption changes the row disposition.

### Exercise 5: Test empty input

Run no rows through the same pipeline.

**Expected result/shape:** 0 accepted, 0 rejected, total 0.

**Verify:** Use an empty `rows` vector and assert `accepted == 0`, `rejected == 0` and `total == 0` without adding a special case for empty input.

**Progressive hints:** An empty valid file differs from a failed file open.

### Exercise 6: Hand off reproducibility

Package source, fixture, commands, test results and limitations.

**Expected result/shape:** Reviewer reproduces the 5-row ledger and failed suffix case.

**Verify:** Have someone follow only your package in a fresh directory and confirm they see `accepted=3 rejected=2 total=35` and, for the `25x` case, `accepted=2 rejected=3 total=10`.

**Progressive hints:** The handoff needs observed statuses, not just source inspection.

## Self-check

Why does the five-row ledger end with three accepted, two rejected and total 35? For Example 2, explain why `"0"` is accepted while `"10x"` is rejected rather than read as 10.

## Common pitfalls

When total 35 passes but counts do not, inspect zero handling and rejected-row accounting. When a missing file reports success, check the file-open guard and process exit code. When a suffix is accepted, inspect both from_chars outputs. When a large input consumes too much memory before rejection, enforce line/row budgets during reading rather than after loading the entire file. A learner should be able to explain which errors are per-record rejections and which prevent publication of any final report.
