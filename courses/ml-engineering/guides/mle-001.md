# mle-001: Define the decision and the data-product contract

## Level and prerequisites

Beginner. Direct prerequisites: `python-ml-02`

**Outcome:** Define an ML product through its decision, information boundary and accepted artifacts.

## Question and mechanism

An ML system begins with a decision, a population and an information boundary. A model score is only one component. In this course the synthetic decision is whether to offer optional support to a customer. The row grain is one customer decision, the features describe usage, tickets and region, and the outcome becomes available four hours after the prediction cutoff. These are declared teaching assumptions, not observations about a real business.

The distinction between features and labels is essential. A target column can be present in an offline development table while remaining unavailable at prediction time. Its physical presence does not make it a valid input. The first case records an explicit feature list and checks that the target is excluded. It also verifies that the synthetic label-availability clock is later than the decision clock.

An artifact graph makes workflow dependencies explicit. Validation precedes features, which precede training, evaluation and publication. A completed training step cannot by itself authorize publication. The second case identifies the next eligible stage from its actual completed dependencies. Later lessons add real libraries and a durable service, while preserving this decision logic.

## Syntax and data contract

The contract is a small structured object containing row grain, prediction time, feature names, target, horizon, purpose and owner. A hash records its exact serialized identity; it does not prove that its assumptions are appropriate. The dependency map names required predecessor artifacts. Readiness is computed from completed prerequisites rather than from a fixed sleep or a successful process at another stage.

## Worked case 1: Separate prediction inputs from future labels

The first case generates the shared synthetic dataset and checks identifiers, declared feature fields and label timing. The contract states hours as the time unit. Keeping this record with the workflow prevents a later author from treating every column as an interchangeable predictor.

**Expected evidence:** There are 120 unique decisions; label is excluded from features and labels become available after their cutoffs.

```python
import hashlib
import json

import numpy as np
import pandas as pd


def digest(data):
    return hashlib.sha256(
        json.dumps(data, sort_keys=True, separators=(",", ":"), allow_nan=False).encode()
    ).hexdigest()


def dataset():
    rng = np.random.default_rng(17)
    n = 120
    usage = rng.uniform(1, 100, n)
    tickets = rng.poisson(2, n)
    region = np.where(np.arange(n) % 2 == 0, "north", "south")
    logit = 0.9 * tickets - 0.035 * usage + (region == "north") * 0.3
    probability = 1 / (1 + np.exp(-logit))
    label = (rng.random(n) < probability).astype(int)
    cutoff = np.arange(n) + 100
    return pd.DataFrame(
        {
            "id": np.arange(n),
            "customer_id": np.arange(n) % 12,
            "cutoff": cutoff,
            "available_at": cutoff - 2,
            "label_available_at": cutoff + 4,
            "usage": usage,
            "tickets": tickets,
            "region": region,
            "label": label,
        }
    )


def example_one():
    contract = {
        "unit": "one customer decision",
        "prediction_time": "cutoff",
        "feature_columns": ["usage", "tickets", "region"],
        "label": "label",
        "label_horizon_hours": 4,
        "decision": "offer optional support",
        "owner": "learning team",
    }
    frame = dataset()
    assert frame["id"].is_unique and all(
        name in frame.columns for name in contract["feature_columns"]
    )
    assert "label" not in contract["feature_columns"]
    assert (frame["label_available_at"] > frame["cutoff"]).all()
    return {"contract": contract, "records": len(frame), "contract_hash": digest(contract)}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Require evaluation before publication

The second case marks validation, feature preparation and training complete. Evaluation is ready, while publication is not. This is a bounded dependency calculation, not a claim that a distributed orchestrator has been deployed.

**Expected evidence:** The only next ready stage is evaluate.

```python
def example_two():
    dependencies = {
        "validate": set(),
        "features": {"validate"},
        "train": {"features"},
        "evaluate": {"train"},
        "publish": {"evaluate"},
    }
    completed = {"validate", "features", "train"}
    ready = sorted(
        name
        for name, parents in dependencies.items()
        if name not in completed and parents <= completed
    )
    assert ready == ["evaluate"] and "publish" not in ready
    return {"ready": ready, "publication_requires_evaluation": True}


if __name__ == "__main__":
    print(example_two())
```

## Diagnose errors and misleading results

A surprisingly strong score may indicate a poorly defined decision or target leakage. An incomplete pipeline can also look successful if publication is tied only to a training exit code. Inspect the contract and dependency graph before choosing another algorithm.
