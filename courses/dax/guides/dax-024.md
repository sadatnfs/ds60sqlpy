## The question and the mechanism

Differentiate share of an explicitly selected population from share of all model products.

ALLSELECTED is useful for selected or visual totals, but it is not a command that reads pixels from a report. Its behavior depends on query and evaluation contexts. In the named query below, an outer filter selects Notebook and Pen, while SUMMARIZECOLUMNS creates one result row for each selected product. Removing the current grouping effect while retaining the outer selection yields a selected denominator of 91.

REMOVEFILTERS(Product[Product]) expresses a different policy: it removes that product-name restriction, including the outer selection in this example, giving denominator 187. Shares of 67/91 and 24/91 sum to one across the selected products. Shares of 67/187 and 24/187 describe their contribution to a larger population and need not sum to one within the visible subset.

Do not generalize this simple query into a rule that ALLSELECTED always means the current slicer. Iterators can introduce shadow filter contexts, and nested evaluations can change which context is restored. When designing a visual-total calculation, specify the exact query shape, selected domain and grouping columns. Advanced reuse should preserve that contract rather than inserting ALLSELECTED into an arbitrary iterator.

## Vocabulary and expression anatomy

Both cases use the same outer product-name selection and grouping. The first denominator uses ALLSELECTED on the grouping column. The second uses REMOVEFILTERS on that column. No year or region filters are present; if they were, their treatment would need to be stated separately.

Concepts to explain in your own words: **ALLSELECTED**, **visual total**, **query grouping**, **outer selection**, **shadow context**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: Share of the selected product set

**Starting context:** Outer selection {Notebook, Pen}; query groups by Product.Product; no nested iterator in the measure.

```dax
EVALUATE CALCULATETABLE ( SUMMARIZECOLUMNS ( Product[Product], "Revenue", [NetRevenue], "SelectedTotal", CALCULATE ( [NetRevenue], ALLSELECTED ( Product[Product] ) ), "Share", DIVIDE ( [NetRevenue], CALCULATE ( [NetRevenue], ALLSELECTED ( Product[Product] ) ) ) ), Product[Product] IN { "Notebook", "Pen" } )
ORDER BY Product[Product]
```

**Context trace:**

1. The outer selected population totals 67 + 24 = 91.
2. Each product group supplies its own numerator.
3. ALLSELECTED removes this grouping restriction while preserving the named outer selection.

**Hand-derived worked-reference result:**

| Product | Revenue | SelectedTotal | Share |
| --- | --- | --- | --- |
| Notebook | 67 | 91 | 0.7362637363 |
| Pen | 24 | 91 | 0.2637362637 |

The sum of the two shares is one because the displayed groups partition this selected population. That conclusion depends on this exact denominator and query shape.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Share of all products instead

**Starting context:** Same selected rows; the denominator removes the Product.Product restriction entirely.

```dax
EVALUATE CALCULATETABLE ( SUMMARIZECOLUMNS ( Product[Product], "Revenue", [NetRevenue], "AllProductTotal", CALCULATE ( [NetRevenue], REMOVEFILTERS ( Product[Product] ) ), "Share", DIVIDE ( [NetRevenue], CALCULATE ( [NetRevenue], REMOVEFILTERS ( Product[Product] ) ) ) ), Product[Product] IN { "Notebook", "Pen" } )
ORDER BY Product[Product]
```

**Context trace:**

1. The visible numerators remain 67 and 24.
2. The denominator includes Mug's 96 as well, totaling 187.
3. The selected rows' shares sum to 91/187, not one.

**Hand-derived worked-reference result:**

| Product | Revenue | AllProductTotal | Share |
| --- | --- | --- | --- |
| Notebook | 67 | 187 | 0.3582887701 |
| Pen | 24 | 187 | 0.128342246 |

This can be exactly the intended comparison to the full catalog. A chart should label the denominator so a partial sum is not mistaken for an error.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. The selected denominator becomes the same product population.
2. The selected denominator is their sum.
3. Decide whether year remains part of the selected population.
4. An iterator can change the available shadow context.
5. Separate display behavior from query/filter context.
6. A denominator change changes the question.
