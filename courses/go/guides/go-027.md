# go-027: Mutexes, atomics and shared-state invariants

## Level and prerequisites

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-026

## Learning objectives

Protect shared invariants with a mutex, sync.Once or typed atomics and explain which operations each one makes safe. Along the way, explain critical section, compound invariant, atomic operation; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A mutex protects a state invariant across several operations. Every relevant access must follow the same protocol: locking writes while reading without synchronization can still race. Atomic operations protect specific values and ordering relationships, but do not automatically make a multi-field transaction atomic. Prefer a mutex for a compound invariant that must be inspected and changed together. Never copy a mutex after use. Keep critical sections small, avoid calling unknown callbacks while holding a lock, and define lock ordering when several locks are unavoidable. A correct observed count is not by itself proof of correct synchronization.

## Vocabulary and concepts

- **Critical section:** Code accessing state while holding its lock.
- **Compound invariant:** A relationship involving several state values.
- **Atomic operation:** An indivisible operation with synchronization semantics.

## Syntax anatomy and reasoning

sync.Mutex uses Lock and Unlock; defer Unlock after acquisition handles early returns. atomic.Int64 supplies typed Load, Store and Add. sync.Once runs one initialization function. Keep synchronized state in a pointer-owned holder so it is not copied accidentally. count++ on an ordinary shared integer is a read-modify-write sequence, not an atomic operation.

## Worked example / walkthrough

### Worked example 1: Protect a concurrent count

Run four workers doing 100 protected increments each.

```go
package main

import (
	"fmt"
	"sync"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type LockedCount struct {
	mu sync.Mutex
	n  int
}

func (c *LockedCount) Inc()       { c.mu.Lock(); defer c.mu.Unlock(); c.n++ }
func (c *LockedCount) Value() int { c.mu.Lock(); defer c.mu.Unlock(); return c.n }

type Pair struct {
	mu   sync.Mutex
	A, B int
}

func (p *Pair) Transfer(n int)       { p.mu.Lock(); defer p.mu.Unlock(); p.A -= n; p.B += n }
func (p *Pair) Snapshot() (int, int) { p.mu.Lock(); defer p.mu.Unlock(); return p.A, p.B }

func main() {
	// Protect a concurrent count
	{
		c := &LockedCount{}
		var wg sync.WaitGroup
		for i := 0; i < 4; i++ {
			wg.Add(1)
			go func() {
				defer wg.Done()
				for j := 0; j < 100; j++ {
					c.Inc()
				}
			}()
		}
		wg.Wait()
		check(c.Value() == 400, "count")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The joined final count is 400.

Reads and writes use the same lock. The join establishes task completion before inspection.

### Worked example 2: Use a typed atomic

Add 3 and 4 through atomic.Int64.

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type LockedCount struct {
	mu sync.Mutex
	n  int
}

func (c *LockedCount) Inc()       { c.mu.Lock(); defer c.mu.Unlock(); c.n++ }
func (c *LockedCount) Value() int { c.mu.Lock(); defer c.mu.Unlock(); return c.n }

type Pair struct {
	mu   sync.Mutex
	A, B int
}

func (p *Pair) Transfer(n int)       { p.mu.Lock(); defer p.mu.Unlock(); p.A -= n; p.B += n }
func (p *Pair) Snapshot() (int, int) { p.mu.Lock(); defer p.mu.Unlock(); return p.A, p.B }

func main() {
	// Protect a concurrent count
	{
		c := &LockedCount{}
		var wg sync.WaitGroup
		for i := 0; i < 4; i++ {
			wg.Add(1)
			go func() {
				defer wg.Done()
				for j := 0; j < 100; j++ {
					c.Inc()
				}
			}()
		}
		wg.Wait()
		check(c.Value() == 400, "count")
	}

	// Use a typed atomic
	{
		var n atomic.Int64
		n.Add(3)
		n.Add(4)
		check(n.Load() == 7, "atomic")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Load returns 7.

Use the atomic access API consistently. Mixing it with ordinary conflicting accesses undermines the protocol.

## Exercises

### Exercise 1: Protect a concurrent count: change one input

Copy worked example 1, change `for i := 0; i < 4; i++ {` to `for i := 1; i < 4; i++ {` and predict the failure before running; then restore the line.

**Expected:** The edited run panics with `count` because `c.Value() == 400` no longer holds.

**Verify:** Restoring `for i := 0; i < 4; i++ {` makes the check pass again with the worked observation: the joined final count is 400.

### Exercise 2: Use a typed atomic: debug a regression

A regression changed `n.Add(3)` to `n.Add(4)` in worked example 2. Repair it without changing the check.

**Expected:** The defective run panics with `atomic`; after restoring `n.Add(3)`, load returns 7.

**Verify:** The failing run shows message `atomic`; after the repair `n.Load() == 7` holds again.

### Exercise 3: Protect a pair relationship

Transfer 3 between two balances initially 5 and 5.

**Expected:** The balances become 2 and 8; their sum remains 10.

**Verify:** Your solution must keep `a == 2 && b == 8 && a+b == 10` true. Control: changing `check(a == 2 && b == 8 && a+b == 10, "pair")` to `check(a == 2 && b == 8 && a-b == 10, "pair")` panics with message `pair`; revert it.

### Exercise 4: Initialize once

Call the same sync.Once initializer three times.

**Expected:** Its body runs once.

**Verify:** Your solution must keep `n == 1` true. Control: changing `n := 0` to `n := 1` panics with message `once`; revert it.

### Exercise 5: Reject a stale atomic expectation

Perform compare-and-swap twice using the original expected value.

**Expected:** The first succeeds and the second fails.

**Verify:** Your solution must keep `!n.CompareAndSwap(2, 4) && n.Load() == 3` true. Control: changing `check(n.CompareAndSwap(2, 3), "CAS")` to `check(n.CompareAndSwap(2, 4), "CAS")` panics with message `stale`; revert it.

Read an unchanged protected pair twice.

**Expected:** Both snapshots preserve total 10.

**Verify:** Your solution must keep `a+b == 10 && c+d == 10` true. Control: changing `check(a+b == 10 && c+d == 10, "snapshot")` to `check(a-b == 10 && c+d == 10, "snapshot")` panics with message `snapshot`; revert it.

## Common pitfalls and diagnosis

Locking writes but reading without the lock is still a data race, and the race detector, not a passing run, is the evidence. A second mistake is protecting each field of a compound invariant separately, so another goroutine can observe A decreased before B increased. Atomics suit single values; use a mutex when several fields must change together, and copy no struct that contains a mutex.

## Progressive hints

### Hint for investigation 1: Protect a concurrent count: change one input

1. Restate the expected observation: The joined final count is 400.
2. Each Inc locks before incrementing. How many increments do four workers make?
3. Starting the loop at 1 starts three workers, so the count is 300 and `c.Value()==400` fails. Locking works; the number of workers changed.

### Hint for investigation 2: Use a typed atomic: debug a regression

1. Restate the expected observation: Load returns 7.
2. atomic.Int64 adds without a lock. What does Load return after both additions?
3. The first Add now adds 4, so Load returns 8 and `n.Load()==7` fails. The atomic operations are correct; restore the 3.

### Hint for investigation 3: Protect a pair relationship

1. Restate the expected observation: The balances become 2 and 8; their sum remains 10.
2. Transfer changes both fields under one lock. What do A, B and their sum become?
3. One lock protects both fields.

### Hint for investigation 4: Initialize once

1. Restate the expected observation: Its body runs once.
2. sync.Once runs its function at most once. How many times does n increase?
3. Once is not a retry mechanism.

### Hint for investigation 5: Reject a stale atomic expectation

1. Restate the expected observation: The first succeeds and the second fails.
2. CompareAndSwap succeeds only when the current value equals the expected one. What is it after the first swap?
3. A stale expectation detects changed state.

### Hint for investigation 6: Transfer safe observation

1. Restate the expected observation: Both snapshots preserve total 10.
2. Snapshot reads both fields under the lock. Can an unchanged pair ever show another total?
3. An accessor hides locking without exposing mutable internals.
