dme-060: Safe checkpoints, startup loading and readiness#

Level: Intermediate | Prepared runtime: python-core

Direct prerequisites: dme-059.

Outcome: Reject changed or incompatible checkpoint tensors before readiness and explain startup-only loading.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

A trained model becomes a serving artifact only when its architecture, parameter tensors, tokenizer and preparation metadata are packaged consistently. “The weights downloaded” is not a readiness condition. A server must verify the expected artifact, instantiate the correct architecture, load compatible tensors, place them on the intended device and run a small functional warm-up before admitting inference.

The default workshop avoids pretrained downloads. Its preparation command trains a 39,552-parameter causal Transformer on the checked-in synthetic corpus, saves numerical arrays in a bounded NPZ archive and writes a hash-bound manifest and tokenizer. Actual parameter count follows the configuration and vocabulary; changing those changes the count. The model's limited training is suitable for learning mechanics, not for making claims about a capable assistant.

The pad demonstrates hash and shape validation using a very small numerical checkpoint. The full project adds stronger archive-member and header validation. You should be able to explain which evidence each stage establishes and why loading normally occurs once per process startup, rather than for every prompt.

A checkpoint is a set of related contracts#

The architecture specifies layer count, width, attention heads, expansion dimension, vocabulary size and context length. The state dictionary maps exact parameter names to tensors. The tokenizer maps IDs to byte pieces and special markers. Training metadata identifies the synthetic corpus, preparation settings and measured training behavior. A manifest binds their files with cryptographic hashes.

Let WjW_jWj​ denote parameter tensor jjj, with declared shape sjs_jsj​ and dtype djd_jdj​. Loading requires the actual name set to equal the expected name set, not merely contain some useful names. Each tensor must have shape sjs_jsj​, dtype djd_jdj​, finite numerical values and a bounded byte count. Missing or unexpected parameters indicate an architecture mismatch even if some layers could be filled with defaults.

A file hash detects a changed byte sequence. It does not establish the publisher's identity unless the expected digest is obtained through a trusted channel. Here the learner prepares a local artifact and retains its manifest. In a production distribution system, signed metadata, trusted registries, provenance review and access control may provide additional assurance. Do not confuse accidental-corruption detection with complete supply-chain authentication.

Numerical serialization without code execution#

Python pickle can serialize general objects and may execute code while loading. That is unnecessary for a fixed numerical checkpoint. The workshop stores float32 arrays and loads with allow_pickle=False. It never extracts arbitrary archive paths onto the filesystem. It checks the exact ZIP member set, total uncompressed size, each array header and the architecture's expected shape before creating model tensors.

Compression introduces a separate size boundary. A small compressed file can describe much more uncompressed data. Limiting only the archive's on-disk bytes does not bound allocation. A declared array header can also claim dimensions that do not match the remaining member bytes. The full loader validates those relationships before calling the numerical array reader.

NPZ is convenient for a tiny educational model. Large serving systems may use tensor-specific formats, memory mapping, sharded checkpoints and distributed loading. Those techniques change I/O and peak-memory behavior, but they do not remove the need to verify names, shapes, dtypes and model-tokenizer compatibility. A format name is not a substitute for a complete loader contract.

Startup phases and readiness#

A useful startup timeline separates process creation, file validation, architecture construction, weight loading, device placement and warm-up. The workshop reports loading and warm-up durations separately. Its readiness endpoint becomes useful only after the application lifespan has completed these steps and initialized the request store and scheduler.

Liveness asks whether the process is responsive enough to inspect or recover. Readiness asks whether it should receive new work. A process can be alive while loading weights or rejecting a corrupted checkpoint. Reporting ready before validation finishes sends user traffic into a race with initialization. Repeatedly restarting a slow but valid loading process can also prevent it from ever becoming ready.

Warm-up executes real model operations and checks cached-versus-full logits and causal behavior. It can reveal shape, device or masking mistakes. It is not a quality benchmark, a maximum-load test or a proof of all kernels on all input sizes. Warm-up may populate allocator or backend caches, so distinguish cold-start timings from subsequent request timings.

Weights remain resident after startup. Each accepted request owns its token tensors, temporary activations and KV cache. Reloading all weights per request would add repeated I/O and memory transfers and could introduce version inconsistency under concurrency. Deliberate model switching is a separate operation with its own capacity and readiness contract.

Worked case 1: verify, then multiply#

The first example stores a two-by-two float32 weight matrix in memory as an NPZ archive, computes its SHA-256 digest, reloads only the expected weight array and checks the numerical result of multiplying by [2,1]. The expected output [4,10] is independent of the serialization implementation and can be derived by hand.

The program prints the archive byte count, digest and loaded shape. The digest identifies those exact archive bytes; it is not an expected universal value for every serializer version. What must remain stable is the comparison between the produced artifact and its declared digest, followed by the numerical result.

This is analogous to a startup smoke check: it establishes that the loader can recover the intended parameters and perform a known operation. It does not establish that the matrix is a good predictive model. Keep functional and scientific evidence separate.

Worked case 2: changed bytes and changed shape#

The second case changes the final byte of the archive and expects hash validation to reject it. It then supplies the original valid bytes while asking for a four-by-one shape. The hash matches, but shape validation rejects the model contract. These are different failure modes, and both must block readiness.

Silently reshaping a tensor to make its element count fit is dangerous. A four-by-one array and a two-by-two array contain the same number of elements but implement different operations. Similarly, permissively loading a partial state dictionary can leave random weights in an apparently running model. The workshop requires an exact state match.

"""Hash-bound safe numerical checkpoints and deliberate corruption rejection."""

import hashlib
import io
import json

import numpy as np


def load(raw, expected_hash, shape):
    if len(raw) > 10000 or hashlib.sha256(raw).hexdigest() != expected_hash:
        raise ValueError("size or hash mismatch")
    with np.load(io.BytesIO(raw), allow_pickle=False) as arrays:
        if arrays.files != ["weight"]:
            raise ValueError("unexpected parameter names")
        matrix = arrays["weight"]
        if matrix.dtype != np.float32 or matrix.shape != shape or not np.isfinite(matrix).all():
            raise ValueError("shape, dtype or finiteness mismatch")
        return matrix.copy()


def example_one():
    source = np.array([[1.0, 2.0], [3.0, 4.0]], dtype=np.float32)
    buffer = io.BytesIO()
    np.savez_compressed(buffer, weight=source)
    raw = buffer.getvalue()
    digest = hashlib.sha256(raw).hexdigest()
    loaded = load(raw, digest, (2, 2))
    np.testing.assert_array_equal(loaded @ np.array([2.0, 1.0]), [4.0, 10.0])
    print(json.dumps({"checkpoint_bytes": len(raw), "sha256": digest, "shape": list(loaded.shape)}))
    return raw, digest


def example_two():
    raw, digest = example_one()
    damaged = raw[:-1] + bytes([raw[-1] ^ 1])
    for contents, shape in [(damaged, (2, 2)), (raw, (4, 1))]:
        try:
            load(contents, digest, shape)
        except ValueError as error:
            print("Rejected:", error)
        else:
            raise AssertionError("Invalid checkpoint reached readiness")
    print("The full project also validates archive members and array headers before allocation.")


def main():
    example_one()
    example_two()


if __name__ == "__main__":
    main()

Operational diagnosis#

If a service fails before readiness, inspect the error stage. A missing file differs from a hash mismatch, an unexpected tensor member, an unavailable device or a failed warm-up. Preserve the faulty assets for diagnosis rather than overwriting them during an automatic “repair.” The preparation command does not silently retrain an existing model directory.

If a service starts slowly only on the first run, compare cold filesystem access, decompression, placement and backend initialization. If every request shows the same startup cost, confirm that weights are not being loaded inside the request handler. Instrument stage boundaries rather than attributing all wall time to the Transformer.

Interview discussion#

Why verify both a hash and tensor shape? The hash checks byte identity against an expected artifact. Shape checks compatibility with the architecture being instantiated. A perfectly intact checkpoint can still be the wrong checkpoint for that architecture.

What belongs in readiness? Required asset validation, successful model placement, a bounded functional check, usable state storage and initialized admission control. Readiness should not wait for an expensive benchmark on every startup, but it must not claim service capability before these dependencies exist.

Can safe numerical serialization prove that a model is safe or accurate? No. It reduces code-execution and allocation risks in loading. Behavioral evaluation, data provenance and deployment policy are separate responsibilities.

Continue to placement and transfer accounting. That chapter separates the one-time movement of resident weights from the per-request movement of inputs, outputs and caches.
