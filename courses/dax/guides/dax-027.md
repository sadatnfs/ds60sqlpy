## The question and the mechanism

Explain why a virtual column's model identity matters in addition to its visible values.

Data lineage associates a virtual column with a model column. A direct projection of Product[ProductKey] can preserve that association, so the resulting key table can filter Product when used in CALCULATE. A computed expression over those keys can contain the same visible numbers while losing that direct model-column lineage.

This distinction prevents a misleading values-only review. Two tables displaying 1 and 2 are not guaranteed to have the same filtering effect. One may represent Product keys; the other may be an unrelated calculated value table. Column names alone do not repair the association.

TREATAS explicitly assigns a table's values to selected target model columns. It is useful for disconnected selections and carefully designed virtual relationships. Match the number and order of columns, data types and target meaning. Values absent from the target domain are ignored, so missing mappings still deserve a data-quality check rather than an assumption that every input value matched.

## Vocabulary and expression anatomy

The first table projects ProductKey directly from Paper products. The second adds zero to each key, creating an expression-derived column with the same numbers but no retained direct lineage. TREATAS then states that those values should filter Product[ProductKey]. The result is a semantic comparison, not a runtime or performance receipt.

Concepts to explain in your own words: **data lineage**, **direct projection**, **computed column**, **TREATAS**, **virtual relationship**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: A direct key projection retains its model identity

**Starting context:** No outer filters; direct projection of the two Paper ProductKey values.

```dax
EVALUATE
VAR PaperKeys = SELECTCOLUMNS ( FILTER ( Product, Product[Category] = "Paper" ), "Key", Product[ProductKey] )
RETURN ROW ( "CandidateRows", COUNTROWS ( PaperKeys ), "Revenue", CALCULATE ( [NetRevenue], PaperKeys ) )
```

**Context trace:**

1. The projected values are 1 and 2.
2. The direct model-column projection retains ProductKey lineage.
3. Using that table as a filter selects Paper sales and revenue 91.

**Hand-derived worked-reference result:**

| CandidateRows | Revenue |
| --- | --- |
| 2 | 91 |

The result depends on the association with ProductKey, not on the output alias Key.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Restore an explicitly detached mapping

**Starting context:** Expression-derived values {1,2}; compare a lineage-free table filter with an explicit target mapping.

```dax
EVALUATE
VAR DetachedKeys = SELECTCOLUMNS ( FILTER ( Product, Product[Category] = "Paper" ), "Key", Product[ProductKey] + 0 )
RETURN ROW ( "WithoutTarget", CALCULATE ( [NetRevenue], DetachedKeys ), "WithTarget", CALCULATE ( [NetRevenue], TREATAS ( DetachedKeys, Product[ProductKey] ) ) )
```

**Context trace:**

1. Adding zero preserves the numbers but changes the projected expression's lineage contract.
2. Without a model target, that detached column does not select the Product rows for revenue.
3. TREATAS maps the values to ProductKey, restoring the intended 91.

**Hand-derived worked-reference result:**

| WithoutTarget | WithTarget |
| --- | --- |
| 187 | 91 |

This is why copying a virtual table's printed rows does not fully document a DAX expression. Record its originating columns or explicit target mapping.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Only values present in the target domain become effective filters.
2. The model-column origin is distinct from its display name.
3. TREATAS states the intended target explicitly.
4. Type compatibility does not establish semantic identity.
5. Column count and position matter.
6. A list of identifiers is initially disconnected unless the model says otherwise.
