go-024: Goroutines and explicit completion#

Level and prerequisites#

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-023

Learning objectives#

By the end, explain goroutine, join, happens-before; implement the six investigations below; and defend the expected result of a changed input before running it. A passing reference is evidence about that program, not a certification of your independent understanding.

Why this mechanism matters#

A goroutine is a concurrently scheduled execution of a function. Starting one does not make the caller wait for it, and returning from main ends the program even if other goroutines still have work. Concurrency introduces partial ordering: some events must happen before others, while unrelated scheduling remains unspecified. Use communication or synchronization to establish the relationships required by the algorithm. A sleep is a delay, not proof that another goroutine has completed. Every started goroutine needs an owner responsible for its completion or cancellation, otherwise blocked tasks can leak resources and make shutdown unpredictable.

Vocabulary and concepts#

  • Goroutine: An independently scheduled function execution.
  • Join: Waiting for owned concurrent work to complete.
  • Happens-before: A synchronization relationship that orders memory effects.

Syntax anatomy and reasoning#

go function() starts a goroutine. A channel send and receive can transfer a result and establish an ordering relationship. sync.WaitGroup tracks a known set of tasks; Add must happen before a concurrent Wait can conclude. Defer Done inside each task. Do not write a shared ordinary variable concurrently merely because a later print appears to observe the expected value.

Worked example / walkthrough#

Worked example 1: Join a produced result#

Start a goroutine computing 6 times 7 and receive its result.

package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Join a produced result
	{
		result := make(chan int)
		go func() { result <- 6 * 7 }()
		check(<-result == 42, "goroutine result")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: The received value is 42.

The receive waits for the send. The program does not assume the worker has completed merely because enough wall-clock time passed.

Worked example 2: Wait for several tasks#

Start three tasks that signal a buffered completion channel and wait for all of them.

package main

import (
	"fmt"
	"sync"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Join a produced result
	{
		result := make(chan int)
		go func() { result <- 6 * 7 }()
		check(<-result == 42, "goroutine result")
	}

	// Wait for several tasks
	{
		done := make(chan struct{}, 3)
		var wg sync.WaitGroup
		for i := 0; i < 3; i++ {
			wg.Add(1)
			go func() { defer wg.Done(); done <- struct{}{} }()
		}
		wg.Wait()
		check(len(done) == 3, "joined tasks")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: Exactly three completion markers are received.

The buffer avoids blocking completion before the parent reads. WaitGroup joins the tasks; the channel stores inspectable completion evidence.

Common pitfalls and diagnosis#

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from check identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned error is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
