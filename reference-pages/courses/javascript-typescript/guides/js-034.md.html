js-034: Memory, performance and profiling#

Level and prerequisites#

Advanced, approximately 120 minutes. Direct prerequisites: js-033

Learning objectives#

Explain measurement boundary, monotonic clock, retention, event-loop delay with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Sum a fixed numeric range and record elapsed duration. The final task tests enable and disable a real delay monitor.

Purpose and mental model#

Performance measurement begins with a correctness contract and a question. A faster implementation that computes a different answer is not an improvement. Wall-clock duration includes scheduling, warmup, JIT compilation, garbage collection and surrounding system load. A single tiny measurement cannot establish a robust speed ranking. Use repeated observations, representative inputs and clearly defined boundaries; retain raw samples instead of reporting only an attractive minimum.

performance.now provides a monotonic clock suitable for elapsed intervals. Date.now measures wall-clock time and can change when the system clock is adjusted. Named marks and measures help identify phases, but their entries also occupy a timeline until cleared. A library should clear only the marks it owns, not another component's measurements.

Memory counters describe different domains. heapUsed concerns managed JavaScript heap use, external and arrayBuffers describe other tracked allocations, and rss concerns resident process memory. Clearing a Map removes its references but does not guarantee immediate garbage collection or a visible drop in rss. A retained-reference count can prove an ownership change without pretending it measures reclaimed physical memory.

Event-loop utilization and delay measure related but distinct behavior. Utilization estimates active versus idle event-loop time under its API definition; delay measures how late scheduled monitoring callbacks run. Neither directly states CPU usage for every worker or the cause of a stall. This lesson records bounded real observations and asserts their shape and validity, not platform-specific performance thresholds. Profiling is a separate investigation after a reproducible workload identifies the problem.

Vocabulary and concepts#

Measurement boundary: The exact work included in a recorded interval.

Monotonic clock: A clock suited to elapsed time without wall-clock adjustments.

Retention: References that keep objects reachable.

Event-loop delay: Observed lateness in scheduled loop activity.

Syntax anatomy and execution trace#

Measure a known-correct function using start/end performance.now values. Summarize repeated samples with a declared statistic such as median while preserving all samples. process.memoryUsage returns byte counters that should not be subtracted indiscriminately as independent categories. performance.mark and measure use unique names and finally cleanup. monitorEventLoopDelay must be enabled and later disabled; a short or heavily delayed run may have too few samples, which is an evidence limit rather than a reason to invent a result.

Worked example / walkthrough#

Example A: Measure only a checked computation#

Correctness is checked independently of the measured time. No assertion says the operation must be faster than a machine-dependent threshold.

import { strict as assert } from 'node:assert';
import { performance, monitorEventLoopDelay } from 'node:perf_hooks';
import { setTimeout as delay } from 'node:timers/promises';

function sumTo(length) {
  let total = 0;
  for (let value = 1; value <= length; value += 1) total += value;
  return total;
}

export async function verify() {
  // Worked example
  {
    const start = performance.now();
    const result = sumTo(10000);
    const elapsed = performance.now() - start;
    assert.equal(result, 50005000);
    assert.ok(Number.isFinite(elapsed) && elapsed >= 0);
    console.log(JSON.stringify({ operation: 'sumTo10000', elapsedMs: elapsed }));
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: correct sum 50005000; finite nonnegative elapsed time.

Example B: Preserve repeated samples and summarize them#

Five tiny trials illustrate record keeping, not a statistically robust benchmark. A real comparison needs workload control, enough repetitions and an analysis of variability.

import { strict as assert } from 'node:assert';
import { performance, monitorEventLoopDelay } from 'node:perf_hooks';
import { setTimeout as delay } from 'node:timers/promises';

function sumTo(length) {
  let total = 0;
  for (let value = 1; value <= length; value += 1) total += value;
  return total;
}

export async function verify() {
  // Worked example
  {
    const samples = [];
    for (let trial = 0; trial < 5; trial += 1) {
      const start = performance.now();
      assert.equal(sumTo(1000), 500500);
      samples.push(performance.now() - start);
    }
    const sorted = [...samples].sort((a, b) => a - b);
    const median = sorted[2];
    assert.equal(samples.length, 5);
    assert.ok(samples.every(value => Number.isFinite(value) && value >= 0));
    assert.ok(median >= sorted[0] && median <= sorted[4]);
    console.log(JSON.stringify({ samplesMs: samples, medianMs: median }));
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: five finite samples; median lies between minimum and maximum.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

  1. Preserve repeated samples and summarize them. Measure five checked runs and compute their median. Expected: five finite samples; median lies between minimum and maximum. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Expected: finite utilization between 0 and 1; no speed or CPU-percentage claim. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Enable and disable a real delay monitor. Collect a short delay-monitor interval and report whether samples exist. Expected: monitor disabled afterward; sample count reported honestly. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
