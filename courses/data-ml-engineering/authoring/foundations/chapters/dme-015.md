# dme-015: Atomic publication and consistent consumer views

## Preparation and publication are different state transitions

A computation can produce candidate files before a consumer should use them. If the consumer discovers candidates by listing a directory and choosing a recent filename, it can encounter incomplete or unvalidated work. A publication contract instead defines which prepared version is accepted and how a reader resolves that version consistently.

This chapter uses actual local files and a real child process. Each prepared version has its own directory containing data and a manifest. A small current pointer names the accepted version and the exact manifest identity. Readers open that pointer once, follow the named version and validate its recorded bytes before using the data.

The example assumes one declared publisher on one local filesystem. Its pointer replacement is not a distributed compare-and-swap protocol. It does not test machine power loss, directory synchronization or remote object-store behavior. Those are distinct guarantees. Naming this boundary is part of understanding the implementation rather than a reason to avoid learning the mechanism.

## Treat versions as immutable inputs to readers

`prepare_version` creates a new directory and refuses to overwrite one that already exists. It writes a bounded list of positive integer package counts, computes the exact data digest and writes a manifest with the version and row count. This separates a prepared candidate from the accepted pointer.

The helper's normal workflow does not rewrite a published version. A reader can therefore retain the version it selected even if another version becomes current later. If old versions are removed too early, an in-progress reader may lose the files it needs. Retention and garbage collection must respect the consumer lifecycle rather than treating “not latest” as equivalent to “unused.”

Directory naming alone does not make bytes physically immutable. A privileged or mistaken writer can still change them, which the second case deliberately does. The manifest and pointer checks provide integrity evidence against the accepted identities. They do not authenticate an attacker who can replace every artifact and every expected identity.

The code also validates version names before using them as path components and bounds the actual file reads. Its filenames and schema are fixed for this teaching project. A general artifact service would need a fuller ownership, authorization and storage contract.

## Replace a small pointer after validation

Activation first reads and validates the candidate version. It then writes a complete pending pointer and replaces the current pointer path. A same-filesystem replacement gives readers an old or new complete pointer rather than an intentionally edited half-pointer. The exact operating-system/filesystem contract matters; do not assume that a remote storage API provides an identical operation.

The pointer records a manifest digest, and the manifest records a data digest. In a simplified chain,

\[
\text{accepted pointer}\rightarrow h_{\mathrm{manifest}}
\rightarrow h_{\mathrm{data}}.
\]

Each digest identifies specific bytes under SHA-256. The chain connects the chosen version to the bytes read by the consumer. It does not establish that the package counts are true measurements or that every expected record arrived upstream.

Atomicity and durability also differ. An operation can avoid an intermediate visible pointer state without proving that all data survives a sudden power failure. The reference does not perform a full durability protocol with explicit file and directory synchronization. Its actual failure case is a child process exiting after preparing files but before activation.

## Readers must use one resolved version

The `current` function reads one pointer into memory. It validates the named manifest and data, checks the row count and numeric schema, and derives the result from those captured values. It does not repeatedly reread a changing current pointer between individual file accesses.

That distinction matters when a product consists of multiple files. If a reader fetches “current” independently for every file, it can combine artifacts from different versions. A manifest can name the complete accepted set so the reader follows one coherent release. A larger product still needs to verify that every listed file belongs to the declared schema and publication.

The current example has one data file so the state transition is easy to inspect. The same reasoning extends to a model and its feature schema, a partition collection or a set of analytical outputs. The complexity of the product should not make its acceptance boundary implicit.

## Worked case 1: A real process exits before activation

The first case prepares and activates version one, containing package counts two, three and one. Its accepted total is six. It then starts a real child Python process that loads the reviewed local helper code, prepares version two with counts two, three and four, and deliberately exits with status seven before activating it.

The parent checks that actual exit status and reads the accepted product. It is still version one with three rows and six packages. The prepared version-two files exist, but their presence alone does not change what the consumer is allowed to read.

The parent then validates and activates the already prepared version two. The next read returns version two with three rows and nine packages. This shows a recovery path that reconciles the completed stage instead of blindly repeating every earlier command.

The child performs a controlled nonzero exit. It is an actual process failure at a specified boundary, but it is not a simulated disk controller, an abrupt power-loss experiment or proof of remote filesystem behavior. A complete owned service needs actual stop/resume and replacement checks in addition to this local file mechanism.

## Worked case 2: Corruption blocks activation and consumption

The changed case activates a valid version one and records the accepted pointer bytes. It prepares version two, then deliberately modifies the candidate data file by appending whitespace. The parsed values would remain the same, but the expected byte identity no longer matches.

Activation rejects that candidate, and the pointer bytes remain exactly unchanged. Reading the accepted version still returns six packages. The program therefore checks both the failure and the retained consumer state; observing an exception alone would not prove that the old pointer survived.

The case then changes the active version-one data bytes. The reader detects the mismatch and rejects the read. A preserved pointer does not make corrupted referenced data healthy. The demonstration returns a diagnostic flag for this expected rejection instead of publishing a convenient default result.

This behavior is intentionally conservative about the declared byte contract. The previous chapter showed that semantic equivalence and byte identity can differ. If a system wants to accept alternative encodings as equivalent, that policy must be defined and qualified explicitly. Silently ignoring an integrity discrepancy is not such a policy.

## Diagnose failures by publication phase

If preparation fails, inspect which candidate files exist and whether a complete manifest was written. If activation fails, inspect whether the accepted pointer changed. If a reader fails, inspect the selected pointer, manifest and content identities separately. Do not collapse these observations into a single “job failed” label when deciding how to recover.

A prepared directory already existing on retry is useful evidence. It may represent completed work, incomplete work or a conflicting attempt. Reconcile it under the version contract. Deleting it reflexively can discard the information needed to understand an uncertain outcome.

Concurrent publishers require a stronger coordination policy than this example provides. A unique pending filename avoids one kind of collision, but it does not by itself prevent a stale writer from replacing a newer accepted pointer. A lock, transaction, lease or conditional update must be chosen and tested for the actual storage system and failure model.

## Where this is useful

This pattern helps reason about analytical releases, model artifacts, configuration bundles, feature snapshots and backups. The consumer should resolve an accepted identity and verify the declared artifact set. The surrounding system must separately define who may publish, how acceptance is decided, how old versions are retained and how failed attempts are inspected.

## Answered interview discussion

**Why is an atomic rename insufficient for a complete data product?** It governs a particular local namespace operation. The product also needs validated immutable content, a coherent manifest, an acceptance policy and appropriate durability/retention behavior.

**What is safe to retry after the child exits?** Reconcile the prepared candidate and then repeat only the necessary acceptance step under the declared identity. Repeating an operation that already completed can otherwise overwrite or duplicate work.

**Does a digest make an artifact trusted?** It establishes agreement with an expected byte identity. The expected identity's authority and the artifact's semantic correctness are separate requirements.

**Why keep old versions after a new one is current?** Existing readers, rollback, audit and recovery may still require them. A reviewed retention policy decides when they can be removed.
