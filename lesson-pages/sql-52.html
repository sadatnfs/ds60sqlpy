Day 52: Data Warehouse Project, Part 1: Star Schema#

How to run this lesson#

In ./classroom, choose PostgreSQL, open sql-52 and run it with Whole SQL lesson (psql). This is the file in the course that keeps its work on purpose: it drops and recreates the dwh schema inside advanced_sql_training, loads four tables and ends with COMMIT, so Days 53 and 54 can read what you build. A snippet run would skip the BEGIN, the schema reset and that COMMIT. A beginner's mental model for this lesson#

A warehouse lets you answer "revenue by month and category" without writing a five-table join each time. Day 52 builds the smallest useful one: a star schema with one fact table in the middle and three dimensions around it.

A fact table holds measurements at one declared grain. Here fact_sales has one row per source order line: 13,085 rows for 4,362 orders, because 3,490 orders have two to five lines and only 872 have a single line. Each row carries quantity, unit_price, discount and a discounted amount, plus three keys that point outward.

A dimension holds the descriptive attributes those keys point to. dim_date has one row per calendar day with year, quarter, month, day name and a weekend flag; dim_customer has one row per customer version with country and segment; dim_product has one row per product version with category, price and cost. Grouping facts by dim_product.category and dim_date.month is exactly what the script's last query does.

A surrogate key is a number the warehouse invents for each dimension row, such as customer_sk, instead of reusing the source's customer_id. Today the two line up (customer 1 gets customer_sk 1) because every customer has one version. Day 53 adds a second version for changed customers, and then one customer_id owns two customer_sk values; that is why facts store the surrogate. dim_date is the exception, keyed by the readable yyyymmdd integer, 20230213 through 20271125 on our run.

When a count looks wrong, walk the load in logical clause order and count rows after each join; every later warehouse check repeats that habit.

Two worked SQL examples#

Both excerpts are CREATE TABLE statements from day52_project3_dwh_part1.sql. They run after CREATE SCHEMA dwh and SET search_path TO dwh, training, public, so the unqualified names land in the new schema rather than in training.

Example 1#
CREATE TABLE dim_date (
  date_key INT PRIMARY KEY, -- yyyymmdd
  date_actual DATE NOT NULL,
  year INT NOT NULL,
  quarter INT NOT NULL,
  month INT NOT NULL,
  day INT NOT NULL,
  day_name TEXT NOT NULL,
  is_weekend BOOLEAN NOT NULL
);

How to read it: dim_date is a calendar, not a copy of any source table. date_key is the primary key and stores the day as an integer such as 20261123, which keeps fact rows readable and turns a range of keys into a range of days. Every attribute is NOT NULL because the load derives each one from the date: extract(quarter ...), to_char(d, 'Dy') for names like Mon, and extract(isodow ...) >= 6 for Saturday and Sunday. Nothing in the definition prevents a missing day; the script avoids gaps by filling the table from generate_series, one row per day.

Expected result/shape: The statement prints CREATE TABLE. Rows arrive later with INSERT 0 1747 on our run: the calendar runs from the earlier of the first order (13 February 2023) and two years before today, to the later of the last order and one year after today, so the count grows by one for each day you wait before rerunning. 498 of those days have is_weekend true. A quick proof of one row per day is SELECT COUNT(*) = COUNT(DISTINCT date_actual) FROM dim_date, which should print t.

Example 2#
CREATE TABLE dim_customer (
  customer_sk INT PRIMARY KEY DEFAULT nextval('dim_customer_sk_seq'),
  customer_id INT NOT NULL, -- business key
  full_name TEXT,
  country TEXT,
  segment TEXT,
  valid_from DATE NOT NULL,
  valid_to DATE,
  is_current BOOLEAN NOT NULL DEFAULT TRUE
);

How to read it: dim_customer is shaped for history before it has any. customer_sk draws from dim_customer_sk_seq, while customer_id is the business key and is deliberately not unique: a changed customer will later own two rows with the same customer_id. valid_from, valid_to and is_current describe each version's life span, and today's load gives every row valid_from equal to the customer's created_at date, valid_to NULL and is_current true. dim_product follows the same pattern for products.

Expected result/shape: Again only CREATE TABLE; the load then prints INSERT 0 500, one version per customer. On our run all 500 surrogates matched their customer_id, a coincidence of insert order that no query should rely on. The load's COALESCE(c.segment, 'standard') never fires on this fixture: the four segments hold 125 customers each and none is NULL.

Learning objectives#

  • Declare fact and dimension grains before creating a star schema.
  • Load surrogate keys and validate every fact-to-dimension relationship.

Vocabulary and concepts#

  • Fact table: measurements/events at a declared business grain.
  • Dimension: descriptive attributes joined to facts through keys.
  • Surrogate key: warehouse-owned identifier for a dimension row or version.

Worked example / walkthrough#

Write the grain beside every table before loading it. Load dim_date and the customer/product dimensions, then map each source order item to exactly one date, customer, and product key in fact_sales. Compare fact row count with source order_items and check every key resolves once before committing Day 52.

Common mistakes and how to recover#

  • Lesson-specific semantic mistake: fact_sales rows must equal source order_items rows.
  • Joining every customer version: the fact load matches dim_customer with AND dc.is_current. Today the filter changes nothing because each customer has one row, but once Day 53 adds versions, dropping it would duplicate every sale of a changed customer. Keep it, or match on the version valid at order_date the way Exercise 2 does for payments.
  • Rerunning over work you care about: the first statement after BEGIN is DROP SCHEMA IF EXISTS dwh CASCADE. Anything you added to dwh by hand, including committed Day 53 or 54 experiments, disappears on the rerun.
  • Expecting a fixed calendar: dim_date is sized from CURRENT_DATE, so its row count (1,747 on our run) and last key change from day to day. Compare key coverage, not raw counts, between two runs.
  • Reading the revenue table as complete: the last query groups 46 months by 6 categories into 276 rows, and LIMIT 50 keeps only the newest. March 2026 is cut after two categories, Home at 19,422.55 and Sports at 17,326.99, so a March total read from this output would be wrong.
  • Loading facts before their dimension rows: fact_sales declares REFERENCES on all three keys, so inserting facts first fails with a foreign-key error. The script's order (dates, customers, products, then facts) is part of the design.
  • When the error is none of these, the first-error checklist keeps you from editing later statements before the real cause is fixed.

Stateful behavior#

Day 52 is intentionally different from most lessons. It drops and recreates only the course-owned dwh schema, builds its base warehouse, and commits it for Days 53 and 54. Do not run it against a dwh schema containing unrelated work.

The base grains are:

  • dim_date: one row per calendar date;
  • dim_customer: Type-2-ready versions keyed by customer_sk;
  • dim_product: Type-2-ready versions keyed by product_sk; and
  • fact_sales: one row per source order_item_id.

  • fact_payments rows must equal source payments rows.

-- BEGINNER WORKFLOW - sql-52: Project 3 DWH Part 1

-- Primary objects in the worked examples: dim_date, dim_customer, dim_product, fact_sales, training.orders.
-- Success means the first error never appears, psql exits 0, result keys and
-- control totals match the stated contract, and verification passes. This stateful lesson ends with COMMIT and preserves only the course-owned dwh schema.

-- Topics: Star schema design (facts/dimensions) and initial loads
BEGIN;
SET search_path TO training, public;

-- This three-day project is intentionally stateful. Re-running Day 52 resets
-- only the course-owned dwh schema, then commits it for Days 53 and 54.
DROP SCHEMA IF EXISTS dwh CASCADE;

CREATE SCHEMA dwh;

SET search_path TO dwh, training, public;

-- Dimension tables (surrogate keys)
CREATE TABLE dim_date (
  date_key INT PRIMARY KEY, -- yyyymmdd
  date_actual DATE NOT NULL,
  year INT NOT NULL,
  quarter INT NOT NULL,
  month INT NOT NULL,
  day INT NOT NULL,
  day_name TEXT NOT NULL,
  is_weekend BOOLEAN NOT NULL
);

CREATE SEQUENCE dim_customer_sk_seq;

CREATE TABLE dim_customer (
  customer_sk INT PRIMARY KEY DEFAULT nextval('dim_customer_sk_seq'),
  customer_id INT NOT NULL, -- business key
  full_name TEXT,
  country TEXT,
  segment TEXT,
  valid_from DATE NOT NULL,
  valid_to DATE,
  is_current BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE SEQUENCE dim_product_sk_seq;

CREATE TABLE dim_product (
  product_sk INT PRIMARY KEY DEFAULT nextval('dim_product_sk_seq'),
  product_id INT NOT NULL, -- business key
  name TEXT,
  category TEXT,
  price NUMERIC(10, 2),
  cost NUMERIC(10, 2),
  valid_from DATE NOT NULL,
  valid_to DATE,
  is_current BOOLEAN NOT NULL DEFAULT TRUE
);

-- Fact table
CREATE TABLE fact_sales (
  order_id INT NOT NULL,
  order_item_id INT NOT NULL,
  date_key INT NOT NULL REFERENCES dim_date (date_key),
  customer_sk INT NOT NULL REFERENCES dim_customer (customer_sk),
  product_sk INT NOT NULL REFERENCES dim_product (product_sk),
  quantity INT NOT NULL,
  unit_price NUMERIC(10, 2) NOT NULL,
  discount NUMERIC(5, 2) NOT NULL,
  amount NUMERIC(12, 2) NOT NULL
);

-- Populate dim_date for every source order plus a useful planning horizon.
-- Deriving the bounds from the source prevents old facts from missing a date key.
WITH bounds AS (
  SELECT
    LEAST (MIN(order_date)::date, (CURRENT_DATE - interval '2 years')::date) AS start_date,
    GREATEST (MAX(order_date)::date, (CURRENT_DATE + interval '1 year')::date) AS end_date
  FROM
    training.orders
),
cal AS (
  SELECT
    generate_series(start_date, end_date, interval '1 day')::date AS d
  FROM
    bounds)
INSERT INTO dim_date (date_key, date_actual, year, quarter, month, day, day_name, is_weekend)
SELECT
  extract(year from d)::int * 10000 + extract(month from d)::int * 100 + extract(day from d)::int,
  d,
  extract(year from d)::int,
  extract(quarter from d)::int,
  extract(month from d)::int,
  extract(day from d)::int,
  to_char(d, 'Dy'),
  (extract(isodow from d)::int >= 6)
FROM
  cal;

-- Initial load for customer dimension (Type 2 structure; initial current rows)
INSERT INTO dim_customer (customer_id, full_name, country, segment, valid_from, valid_to, is_current)
SELECT
  c.customer_id,
  c.full_name,
  c.country,
  COALESCE(c.segment, 'standard') AS segment,
  c.created_at::date,
  NULL,
  TRUE
FROM
  training.customers c;

-- Initial load for product dimension
INSERT INTO dim_product (product_id, name, category, price, cost, valid_from, valid_to, is_current)
SELECT
  p.product_id,
  p.name,
  p.category,
  p.price,
  p.cost,
  p.created_at::date,
  NULL,
  TRUE
FROM
  training.products p;

-- Load fact from existing orders/items (map to dims using current rows)
WITH oi AS (
  SELECT
    oi.order_item_id,
    oi.order_id,
    o.order_date::date AS od,
    o.customer_id,
    oi.product_id,
    oi.quantity,
    oi.unit_price,
    oi.discount,
    (oi.unit_price * oi.quantity * (1 - oi.discount)) AS amount
  FROM
    training.order_items oi
    JOIN training.orders o ON o.order_id = oi.order_id
),
keys AS (
  SELECT
    oi.*,
    (extract(year from oi.od)::int * 10000 + extract(month from oi.od)::int * 100 + extract(day from oi.od)::int) AS date_key,
    dc.customer_sk,
    dp.product_sk
  FROM
    oi
    JOIN dim_customer dc ON dc.customer_id = oi.customer_id
      AND dc.is_current
    JOIN dim_product dp ON dp.product_id = oi.product_id
      AND dp.is_current)
  INSERT INTO fact_sales (order_id, order_item_id, date_key, customer_sk, product_sk, quantity, unit_price, discount, amount)
  SELECT
    order_id,
    order_item_id,
    date_key,
    customer_sk,
    product_sk,
    quantity,
    unit_price,
    discount,
    amount
  FROM
    keys;

-- Sample star query
SELECT
  dd.year,
  dd.month,
  dp.category,
  ROUND(SUM(fs.amount), 2) AS revenue
FROM
  fact_sales fs
  JOIN dim_date dd ON dd.date_key = fs.date_key
  JOIN dim_product dp ON dp.product_sk = fs.product_sk
GROUP BY
  dd.year,
  dd.month,
  dp.category
ORDER BY
  dd.year DESC,
  dd.month DESC,
  revenue DESC
LIMIT 50;

Clause-by-clause reading map#

Each warehouse answer begins at the table whose grain its output keeps, so name that table and its row meaning first, then trace the statement in logical clause order. Three warehouse rules tie the six answers together:

  • Grain is a count you can repeat. The grain and reconciliation queries set COUNT(*) beside COUNT(DISTINCT order_item_id) and beside training.order_items, and the payment check repeats that comparison against training.payments.
  • A dimension join must hit exactly one row. The payment load joins dim_customer on customer_id plus a valid_from/valid_to range, so each payment finds the one version valid on its date even after Day 53 adds more.
  • A missing key is a policy, not an accident. The unknown-member answer reserves -1 and routes to it explicitly with COALESCE, while the late-date answer refuses that shortcut for dates and lists the misses instead.

Day 52 is intentionally stateful. Unlike most course files, it commits a course-owned dwh schema so Days 53 and 54 can use it. Re-running the learner file or solution resets only that schema with DROP SCHEMA dwh CASCADE.

Exercise 1: Add dim_country#

The solution:

  1. creates dwh.dim_country(country_sk, country_code);
  2. loads distinct country codes from training.customers;
  3. adds country_sk to dwh.dim_customer;
  4. backfills it through the existing text country code;
  5. adds a foreign key and makes the new key non-null.

This preserves the original country attribute in each Type 2 customer row while also providing a conformed country key. Expected grain is one row per country code in dim_country; every customer-dimension version has exactly one country_sk.

The NOT NULL rule is a contract for every later load: Day 53's SCD2 inserts must supply country_sk for each new version. Day 53 also starts by adding this same link, inside its rolled-back transaction, when a warehouse was built by the Day 52 learner base alone.

  • Independent verification: For sql-52 Exercise 1, right after the backfill, confirm that SELECT COUNT(*) FROM dim_country is 8, that no dim_customer row has a NULL country_sk, and that joining dim_customer to dim_country on country_sk gives country_code = country on every row; after a savepoint, an INSERT into dim_customer without country_sk must fail with SQLSTATE 23502, then roll back to the savepoint.

Exercise 2: Add fact_payments#

The answer creates one row per source payment with:

  • payment_id as the idempotent fact key;
  • order_id as a degenerate operational reference;
  • the payment-day date_key;
  • the customer version whose validity range contains payment_date;
  • amount and method as measures/attributes.

The table declares the fact grain and its dimension keys, and the load joins each payment to its order, its payment date, and the customer version that was valid on that date:

SET search_path TO dwh, training, public;

CREATE TABLE fact_payments (
  payment_id bigint PRIMARY KEY,
  order_id int NOT NULL,
  date_key int NOT NULL REFERENCES dim_date (date_key),
  customer_sk int NOT NULL REFERENCES dim_customer (customer_sk),
  amount numeric(12, 2) NOT NULL,
  method text NOT NULL
);

INSERT INTO fact_payments (payment_id, order_id, date_key, customer_sk, amount, method)
SELECT
  p.payment_id,
  p.order_id,
  dd.date_key,
  dc.customer_sk,
  p.amount,
  p.method
FROM
  training.payments p
  JOIN training.orders o USING (order_id)
  JOIN dim_date dd ON dd.date_actual = p.payment_date::date
  JOIN dim_customer dc ON dc.customer_id = o.customer_id
    AND p.payment_date::date >= dc.valid_from
    AND p.payment_date::date <= COALESCE(dc.valid_to, 'infinity'::date);

Exercise 3: State the sales fact grain#

The query lists payments outside dim_date. The chosen policy is fail and extend the dimension because silently mapping a real accounting date to unknown would destroy time analysis.
