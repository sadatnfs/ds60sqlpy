# web-046: HTTP requests, response models and routing

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-045`

## Learning objectives

Build a pure router for health and lesson-summary requests. Explain what a CLI response model does not prove. Use request method, path and status code accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

HTTP separates a request from its response. A request includes a method, target and headers, and may contain a body. A response includes a status code, headers and body. The method expresses intended semantics: GET should retrieve a representation without requesting a state change, while POST commonly submits data for processing. The server must still enforce its own rules regardless of a client-supplied method or path.

Routing selects application behavior from the request method and path. Keep routing separate from the domain calculation so logic can be tested without a live server. A 404 means the requested resource or route is not found; a 405 means the resource exists but the method is unsupported. The application should not return 200 for every failure merely because it produced a page.

### Key terms

- **Request method:** The verb of an HTTP request, such as GET or POST, that states the intended action.
- **Status code:** The three-digit result of a response; 404 means nothing exists at the path, while 405 means the path exists but not for that method.
- **Header:** A name and value pair such as `Content-Type` or `Allow` that describes a request or response.
- **Route:** A mapping from a method and path to the handler that produces the response.

## Syntax anatomy and mechanism

The CLI reference receives a synthetic request array and returns a response array. This is a model of an HTTP boundary, not an actual network exchange. A real adapter would read the server-provided environment, validate it, set status and headers before body output, and send the body. Content-Type should describe the response representation, and error bodies should match the declared format. RFC 9110 requires general-purpose servers to support GET and HEAD, so the reference answers HEAD with the same status and headers but an empty body, and its 405 response lists both in the Allow header.

## Worked example / walkthrough

### Worked example 1: A response value

The model makes the three response parts visible.

```php
$response = ['status' => 200, 'headers' => ['Content-Type' => 'text/plain; charset=utf-8'], 'body' => 'Ready'];
```

**Expected observation:** The body is text and the status describes success.

### Worked example 2: Method-aware routing

The same path can reject an unsupported operation.

```php
if ($path === '/health' && $method === 'GET') { return ['status' => 200, 'body' => 'ok']; }
```

**Expected observation:** A health retrieval is explicitly distinct from other requests.

## Contrast case: a router that ignores the method

This shorter router checks only the path. Send it GET, HEAD and DELETE requests for the same path.

```php
function routeLoose(array $request): array {
  if ($request['path'] === '/health') {
    return ['status' => 200, 'body' => 'ok'];
  }
  return ['status' => 404, 'body' => 'Not found'];
}

var_export(routeLoose(['method' => 'DELETE', 'path' => '/health']));
```

The DELETE request receives status 200 with body ok, so a client that sent the wrong method is told it succeeded. HEAD also receives a body, which HTTP forbids for HEAD responses. The reference router checks both path and method, answers HEAD with the GET status and an empty body, and returns 405 with an `Allow: GET, HEAD` header for other methods. That header tells the client which methods exist. The printed array is a model; a real server would still need to send these values over the network.

## Debugging and common mistakes

Do not trust a route parameter as an authorized identity. Avoid state changes triggered by GET. A printed response array cannot establish that a real server sent those headers.

When the wrong status comes back, print the full response array from route rather than only the body, and check that method and path are both matched. In a real adapter, a headers already sent warning means output reached the client before header(), often a stray echo or whitespace.

The shared [debugging routine](../STUDY-GUIDE.md#debugging-php) covers what to record before each repair.
