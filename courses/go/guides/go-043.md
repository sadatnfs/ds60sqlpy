# go-043: Finalizers, deletion and exact ownership

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-042

## Learning objectives

Use a finalizer to finish exact-owner cleanup before deletion completes, without removing other controllers' finalizers. Along the way, explain finalizer, deletion timestamp, owned incarnation; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Deletion can require coordination with an external resource whose lifetime is not handled by Kubernetes garbage collection. A finalizer records that cleanup must complete before the API object is removed. Once deletionTimestamp is set, the controller performs its owned cleanup and removes only its own finalizer after success. Removing the finalizer first can orphan the external resource; retaining it forever can leave an object stuck terminating. Cleanup must be idempotent and identify the exact owned incarnation, not merely a reusable name. Owner references support Kubernetes garbage collection, but they are not a general substitute for finalizing resources outside the cluster.

## Vocabulary and concepts

- **Finalizer:** A deletion gate requiring a controller to finish cleanup.
- **Deletion timestamp:** Evidence that deletion was requested and finalization may be underway.
- **Owned incarnation:** The exact UID-bound resource created by an operation.

## Syntax anatomy and reasoning

A finalizer is a qualified string in metadata.finalizers. The state machine first ensures the finalizer exists during normal operation, then observes deletion, performs bounded cleanup and removes its own entry. Preserve other controllers' entries. An already absent external resource can count as successful cleanup only when the ownership check and absence observation are reliable. Never remove unrelated finalizers as a generic repair shortcut.

## Worked example / walkthrough

### Worked example 1: Register cleanup responsibility

Inspect a normal object without the controller finalizer.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func finalAction(deleting, hasFinalizer, cleaned, owned bool) string {
	if !owned {
		return "ownership-error"
	}
	if !deleting {
		if !hasFinalizer {
			return "add-finalizer"
		}
		return "reconcile"
	}
	if !hasFinalizer {
		return "done"
	}
	if !cleaned {
		return "cleanup"
	}
	return "remove-own-finalizer"
}

func main() {
	// Register cleanup responsibility
	{
		check(finalAction(false, false, false, true) == "add-finalizer", "register")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The next action is add-finalizer.

Register responsibility before creating an external resource that would otherwise be orphaned during deletion.

### Worked example 2: Retain a healthy object

Inspect a nondeleting object whose finalizer is present.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func finalAction(deleting, hasFinalizer, cleaned, owned bool) string {
	if !owned {
		return "ownership-error"
	}
	if !deleting {
		if !hasFinalizer {
			return "add-finalizer"
		}
		return "reconcile"
	}
	if !hasFinalizer {
		return "done"
	}
	if !cleaned {
		return "cleanup"
	}
	return "remove-own-finalizer"
}

func main() {
	// Register cleanup responsibility
	{
		check(finalAction(false, false, false, true) == "add-finalizer", "register")
	}

	// Retain a healthy object
	{
		check(finalAction(false, true, false, true) == "reconcile", "normal")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The action is reconcile.

A finalizer does not itself request deletion. Normal desired-state work continues while deletion has not begun.

## Common pitfalls and diagnosis

Removing the finalizer before cleanup succeeds is the orphaning bug: the API object disappears and nothing remembers the external resource. The opposite bug, never removing it, leaves the object stuck terminating. Remove only your own finalizer, never the whole list, and confirm the object is the incarnation you own; a recreated object with the same name has a different UID.
