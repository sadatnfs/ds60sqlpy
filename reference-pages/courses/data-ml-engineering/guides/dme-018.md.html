dme-018: Columnar layout, partition pruning and bounded reads#

Level: Intermediate | Prepared runtime: data-engineering

Direct prerequisites: dme-013, dme-017.

Outcome: Inspect real partitioned Parquet fragments selected by a predicate.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

Logical rows and physical files are different layers#

A dataset is a logical collection of observations. Its storage layout determines where the bytes representing those observations live. Four rows might occupy one file, two files organized by date, or four tiny files. The logical answer to a question should remain the same across those layouts. Performance, listing overhead, memory behavior and operational complexity can change substantially.

Parquet stores columns in an encoded format and divides files into row groups. A row group contains a horizontal range of rows, with separately stored column chunks. A reader asking for two fields can often avoid decoding other fields. File and row-group statistics can help eliminate ranges that cannot satisfy a predicate. Those mechanisms are distinct from directory partitioning, where a value such as a date is encoded in the path. A Hive-style directory might be named day=2024-01-01; this naming convention does not require a running Hive service.

Our fixture writes four identified deliveries across two days. Each has delivery_id, day and packages. The question is deliberately small: return only delivery identities and counts for January 1. We inspect actual Arrow dataset fragments selected by that date predicate, and then read the actual projected rows. A fragment is a dataset component such as a Parquet file. Counting selected fragments gives concrete evidence about planning. It does not directly measure physical bytes transferred from a disk or object store.

Understand pruning, projection and filtering#

Partition pruning excludes files whose partition values cannot match a predicate. Projection chooses output columns. Row filtering excludes nonmatching rows within the remaining data. These operations interact, but they should not be collapsed into a vague statement that the query “reads less.” A reader might still access file footers, list directories, allocate buffers or read a row group containing some unwanted rows. Compression, caching and storage request granularity also affect the physical work.

Worked case 1: select one real date partition#

example_one() writes two rows per file. Since each day has exactly two records, the resulting dataset contains two fragments. The predicate ds.field("day") == "2024-01-01" selects one fragment. The read projects only delivery_id and packages, producing records {delivery_id: 1, packages: 2} and {delivery_id: 2, packages: 3}. The independent total is five packages, but the program compares identified rows as well so that two wrong records with the same sum cannot pass.

The returned columns do not include day, even though the filter uses it. A filter field and an output field need not be identical. Arrow can obtain the partition value from the directory expression and use it during planning. The program also queries January 3, a date absent from the declared dataset. It observes zero selected fragments and an empty result. This is an empty query result, not proof that a real upstream system had zero deliveries that day. A completeness manifest would be needed to distinguish absent ingestion from a complete zero-event day.

The code sorts returned records by identity only for deterministic comparison. File ordering and parallel scan ordering are not a stable business contract. The temporary directory is deleted after the example, so rerunning creates a fresh layout instead of picking up leftover files from a prior attempt. This makes the physical comparison reproducible without asking learners to delete arbitrary directories on their own machines.

Worked case 2: more files with the same logical answer#

The second example writes the identical four observations twice in two separate owned directories. One layout permits two rows per file; the other permits only one. The first contains two total fragments and selects one for January 1. The second contains four total fragments and selects two. Both return precisely the same identified rows and the same package total.

This changed condition isolates file topology from data meaning. More small files create more objects to discover and open. They can also introduce more scheduling work in a distributed engine. However, the program makes no claim that the two-file read is a particular number of milliseconds slower. At four rows, interpreter startup, cache state and measurement noise can dominate. A benchmark built from this tiny fixture would mostly measure overhead unrelated to a realistic analytical workload.

The lesson is not “always make one huge file.” Extremely large files can limit parallelism or make small selective requests expensive. Extremely fine partitions can create a huge directory or catalog population, and many empty or tiny partitions. Select a partition dimension that matches common filters, then choose file and row-group sizes based on observed query patterns, ingestion cadence and compaction cost. Date partitioning is understandable here because users filter by date; partitioning by a unique delivery ID would create a directory for almost every record.

Complete worked program#

The data-engineering profile supplies Arrow and Parquet support. All files belong to the program's temporary directory; no object-store account or network access is used.

"""Inspect real partitioned Parquet selection without inventing IO measurements."""

import tempfile
from pathlib import Path

import pyarrow as pa
import pyarrow.dataset as ds


def write_layout(root, rows_per_file):
    table = pa.table(
        {
            "delivery_id": [1, 2, 3, 4],
            "day": ["2024-01-01", "2024-01-01", "2024-01-02", ("2024-01-02")],
            ("packages"): [2, 3, 4, 1],
        }
    )
    partitioning = ds.partitioning(pa.schema([("day", pa.string())]), flavor="hive")
    ds.write_dataset(
        table,
        root,
        format="parquet",
        partitioning=partitioning,
        max_rows_per_file=rows_per_file,
        max_rows_per_group=rows_per_file,
        use_threads=False,
        existing_data_behavior="error",
    )
    return ds.dataset(root, format="parquet", partitioning=partitioning)


def selected(dataset, day):
    predicate = ds.field("day") == day
    fragments = list(dataset.get_fragments(filter=predicate))
    table = dataset.to_table(
        columns=["delivery_id", "packages"], filter=predicate, use_threads=False
    )
    rows = sorted(table.to_pylist(), key=lambda row: row["delivery_id"])
    return {
        "selected_fragments": len(fragments),
        "all_fragments": len(list(dataset.get_fragments())),
        ("columns"): table.column_names,
        ("rows"): rows,
    }


def example_one():
    with tempfile.TemporaryDirectory() as directory:
        dataset = write_layout(Path(directory) / "by-day", 2)
        result = selected(dataset, "2024-01-01")
        assert result["selected_fragments"] == 1 and result["all_fragments"] == 2
        assert result["columns"] == ["delivery_id", "packages"]
        assert result["rows"] == [
            {"delivery_id": 1, "packages": 2},
            {"delivery_id": 2, "packages": 3},
        ]
        absent = selected(dataset, "2024-01-03")
        assert absent["selected_fragments"] == 0 and absent["rows"] == []
        return {
            "observed_selection": result,
            "absent_partition_rows": absent["rows"],
            ("bytes_read_were_not_measured"): True,
        }


def example_two():
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        compact = selected(write_layout(root / "compact", 2), "2024-01-01")
        fragmented = selected(write_layout(root / "small-files", 1), "2024-01-01")
        assert compact["rows"] == fragmented["rows"]
        assert (compact["all_fragments"], fragmented["all_fragments"]) == (2, 4)
        assert (compact["selected_fragments"], fragmented["selected_fragments"]) == (1, 2)
        assert sum(row["packages"] for row in fragmented["rows"]) == 2 + 3
        return {
            "compact_selected_files": compact["selected_fragments"],
            "small_file_selected_files": fragmented[("selected_fragments")],
            ("same_identified_result"): compact[("rows")],
            ("timing_claim_requires_a_separate_measurement"): True,
        }


def main():
    print("Actual partition selection and projection:", example_one())
    print("Same result, different file topology:", example_two())


if __name__ == "__main__":
    main()

Diagnosing a pruning surprise#

If a query returns the correct rows but selects every file, inspect the partition schema and predicate before changing the engine. A string date compared with a timestamp expression may not produce the simple partition constraint you expected. A transformation wrapped around the partition field may be harder to push into the scanner than a direct bounded predicate. Confirm the physical layout actually contains the intended directory values and that the reader uses the same partitioning convention.

If a scan returns duplicate delivery IDs, inspect the list of data files and the ingestion manifest. A directory can contain old and new publications simultaneously; a broad glob may read both. Compaction must replace a file set through a controlled snapshot boundary, not merely add larger files beside the small originals. The next storage chapters introduce manifests and snapshots for precisely this reason. File names alone do not identify which data version a consumer should accept.

If memory grows despite a projected scan, distinguish scanning from collecting. to_table() materializes the selected output in memory. A streaming reader or batch iterator can bound processing differently, but a later operation that collects all batches can erase that advantage. Record the size of intermediate and final results separately. A filtered result with a billion matching rows is still a billion-row result.

Applications and interview discussion#

This reasoning applies to lake ingestion, training-data preparation, local analytical notebooks and distributed SQL. It also helps estimate operational cost: a high-frequency job that opens thousands of tiny files may spend more effort on request overhead than on arithmetic. Use workload observations to justify compaction, and verify that compaction preserves keys, values, schema and accepted snapshot identity.

An interviewer may ask, “Why did partitioning fail to speed up our query?” Explain that partitioning helps only when filters eliminate substantial work and overhead does not dominate. Ask which partitions and columns the query selected, how many files were opened, whether the data were cached, and whether a large shuffle followed the scan. If asked whether a query plan proves fewer bytes were read, distinguish planned elimination from measured IO. A plan is valuable evidence, but it is not a storage meter.

For an answered extension, imagine a report requests both days. Both layouts then select all their fragments. Date pruning provides no elimination for that request, while projection can still avoid unused columns. The answer follows directly from the workload rather than a general rule that partitioned data are always faster.
