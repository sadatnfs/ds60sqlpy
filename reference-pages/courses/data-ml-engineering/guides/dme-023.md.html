dme-023: Stream windows, watermarks and state lifetime#

Level: Intermediate | Prepared runtime: python-core

Direct prerequisites: dme-014, dme-021, dme-022.

Outcome: Trace a bounded event-time window mechanism under out-of-order arrivals.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

A stream needs rules for incomplete time#

A finite batch has an obvious end: the declared input has been read. An ongoing stream does not. If a dashboard groups events into five-minute windows, when should it publish a result? Event time is when the event happened according to the source. Processing time is when the computation handles it. Network delay, retries, clock errors and disconnected clients can make those orders differ. An event for an earlier interval may arrive after a later event.

A watermark is a progress assertion used by an event-time computation. It tells the operator how far the system considers event-time progress to have advanced under its source and lateness policy. It is not proof that no older event can ever arrive. A late-event policy specifies what happens when one does: update a still-open result, route it to a side output, discard it with accounting, or trigger a separate correction process. The choice affects both data accuracy and state cost.

This chapter implements a small bounded window mechanism with Python data structures. It is not a Flink server, Kafka consumer or Spark streaming job. Its trigger conventions are stated explicitly so you can reason about them without assuming they exactly match every engine's timestamp edge rules. The separate Apache streaming project provides the actual service execution surface. Here we can inspect every state transition and independently calculate every result.

Windows, progress and retained state#

A tumbling window divides time into nonoverlapping intervals of width www. For a nonnegative integer timestamp ttt, the window start is

Our width is five abstract time units. Timestamp four belongs to [0,5)[0,5)[0,5), while timestamp five belongs to [5,10)[5,10)[5,10). The units could represent minutes in a real application, but the program does not sleep or depend on wall-clock time. A caller explicitly advances the watermark, which must never move backward.

The model emits a first result when the watermark reaches the window end. It retains that window's accumulated state for a grace period of two additional units. While retained, an arriving event can produce a revised result. When the watermark reaches end plus grace, the state is removed. A later event for that expired interval goes to the late list. This list is an inspectable side output for the bounded fixture, not a durable production dead-letter queue.

Each output has window start, revision and total. Revisions increase when a window result changes. A downstream materializer stores the newest revision for each window and rejects contradictory values at the same revision. The result is a changing table keyed by window, not an append-only list of independent totals. That distinction is necessary when a previously published aggregate can be corrected.

Worked case 1: out-of-order input with explicit progress#

example_one() receives a value of three at timestamp two, then a value of two at timestamp one. The arrival order is reversed relative to event time, but both events belong to the first window. Advancing the watermark to five emits a total of five for window start zero. An event at timestamp six with value one belongs to the next window. Advancing to ten emits that window's total of one.

Finally, the watermark advances to twelve. The first window has already passed its retention deadline of seven, and the second now reaches its deadline of twelve. No window state remains. The materialized results are {0: 5, 5: 1}. The late side output is empty because no event arrived after its window's retention deadline.

Notice that the two events in the first window did not need to be sorted before aggregation. Addition is order-insensitive for these exact integer values. A stateful operation such as “last status” would need a source-order or event-time tie policy. Window membership alone does not define the semantics of every aggregate. The program intentionally uses a sum so the timing and state-lifetime mechanisms remain visible without a second ambiguous ordering rule.

Worked case 2: a late correction followed by expiry#

The second case starts with the same two early values and advances the watermark to five. The first emitted result is revision 1 with total five. An event at timestamp three with value four then arrives. It is late relative to the first emission, but the watermark is still below the cleanup boundary of seven. The retained state becomes nine and the model emits revision 2 for the same window.

A correct materializer replaces the earlier value with nine. An append-and-sum consumer would add five and nine and report fourteen, which double counts the earlier observations. The program calculates and prints this wrong value explicitly, then checks that the revision-aware result is nine. A stream of change records is not automatically a stream of additive facts. Consumers must know whether an output is an insert, replacement, retraction or delta.

The watermark next advances to seven, removing the first window's state. An event at timestamp four with value 100 arrives afterward and is sent to the late side output. The accepted window result stays nine, and the rejected-late population contains that exact event. The program does not quietly claim the true historical total remains nine. Nine is the total accepted under this bounded-lateness policy; the late record is evidence that a later correction path may be needed.

Complete worked program#

Use Python Core. This deterministic model has no background event source, no network and no wall-clock waits. Its arrays retain only the tiny fixture's observations so every transition can be inspected.

"""A bounded event-time mechanism model, not an executed streaming engine."""

from dataclasses import dataclass, field


@dataclass
class WindowState:
    total: int = 0
    emitted: bool = False
    revision: int = 0


@dataclass
class Windows:
    width: int = 5
    grace: int = 2
    watermark: int = 0
    states: dict[int, WindowState] = field(default_factory=dict)
    changes: list[tuple[int, int, int]] = field(default_factory=list)
    late: list[tuple[int, int]] = field(default_factory=list)

    def __post_init__(self):
        if (
            type(self.width) is not int
            or self.width < 1
            or type(self.grace) is not int
            or self.grace < 0
        ):
            raise ValueError("Width must be positive and grace nonnegative integer time units")

    def emit(self, start, state):
        state.emitted = True
        state.revision += 1
        self.changes.append((start, state.revision, state.total))

    def event(self, timestamp, value):
        if type(timestamp) is not int or timestamp < 0 or type(value) is not int:
            raise ValueError("Use nonnegative integer event times and integer values")
        start = timestamp // self.width * self.width
        end = start + self.width
        if self.watermark >= end + self.grace:
            self.late.append((timestamp, value))
            return "late-side-output"
        state = self.states.setdefault(start, WindowState())
        state.total += value
        if self.watermark >= end:
            self.emit(start, state)
        return "accepted"

    def advance(self, watermark):
        if type(watermark) is not int or watermark < self.watermark:
            raise ValueError("Watermarks are monotone integer progress assertions")
        self.watermark = watermark
        for start, state in list(self.states.items()):
            end = start + self.width
            if watermark >= end and not state.emitted:
                self.emit(start, state)
            if watermark >= end + self.grace:
                del self.states[start]


def materialize(changes):
    accepted = {}
    for start, revision, total in changes:
        prior = accepted.get(start)
        if prior is None or revision > prior[0]:
            accepted[start] = (revision, total)
        elif revision == prior[0] and total != prior[1]:
            raise ValueError("One window revision cannot name two values")
    return {start: total for start, (_, total) in sorted(accepted.items())}


def example_one():
    windows = Windows()
    windows.event(2, 3)
    windows.event(1, 2)
    windows.advance(5)
    windows.event(6, 1)
    windows.advance(10)
    windows.advance(12)
    result = materialize(windows.changes)
    assert result == {0: 5, 5: 1} and windows.states == {} and windows.late == []
    return {"accepted_windows": result, "change_log": windows.changes, "retained_state": 0}


def example_two():
    windows = Windows()
    windows.event(1, 2)
    windows.event(2, 3)
    windows.advance(5)
    windows.event(3, 4)
    assert windows.changes == [(0, 1, 5), (0, 2, 9)]
    windows.advance(7)
    assert windows.event(4, 100) == "late-side-output"
    assert materialize(windows.changes) == {0: 9} and windows.late == [(4, 100)]
    assert sum(total for _, _, total in windows.changes) == 14
    return {
        "upserted_result": materialize(windows.changes),
        "wrong_append_sum": 14,
        "late_side_output": windows.late,
        "retained_state": len(windows.states),
    }


def main():
    print("Event time and explicit progress:", example_one())
    print("Revision-aware sink and expired state:", example_two())


if __name__ == "__main__":
    main()

Why watermarks are operational decisions#

In a partitioned source, a combined watermark often depends on progress across input partitions. A quiet partition can hold back progress unless the engine applies a reviewed idleness policy. Marking a slow partition idle too aggressively can let results finalize before its delayed events arrive. Waiting forever preserves the possibility of including every event but prevents bounded state and timely output. This is a product and system tradeoff, not a magic parameter with one universal value.

A rough state estimate is proportional to active keys, state per key and the number of retained windows. Increasing allowed lateness can increase both correction coverage and memory or durable-state cost. High-cardinality keys multiply that cost. Our model uses a single aggregate per time window and therefore omits key explosion, checkpoint storage and distributed backpressure. The later capacity chapters and real engine workshop make those additional boundaries explicit.

The output revision also needs a recovery contract. After a crash, restoring state and replaying input must not create a contradictory revision for the same accepted output identity. Production engines connect checkpoints, source positions and sink semantics to address this. A Python dictionary that survives only until process exit does not provide those guarantees. The next chapter introduces actual local checkpoint transactions before moving to larger service systems.

Failure diagnosis and useful questions#

If totals are too high after late events, inspect whether the sink adds replacement totals. If state grows without bound, inspect whether watermark progress stalls or cleanup never runs. If late data disappear, verify whether they are counted and retained somewhere observable. If a timestamp exactly at five lands in the first window, inspect the interval boundary; our half-open convention puts it in the second.

If events contain seconds but the watermark is expressed in milliseconds, all timing comparisons can be wrong while still using valid integers. Record units in the source contract. If source clocks can jump forward, one extreme timestamp must not automatically finalize all previous windows without a reviewed watermark strategy. Progress assertions need validation just as business records do.

An interviewer may ask, “Does a watermark guarantee completeness?” Explain that it encodes a policy or estimate of event-time progress and late records can still arrive. If asked how to support corrections, describe retained state, output revisions and a sink that understands updates. If asked why not retain state forever, discuss bounded resources, recovery time, privacy and the separate historical backfill path.

For an answered extension, suppose the late value four arrives only after watermark seven. Under this model it joins the side output rather than producing revision 2. The accepted result stays five, while the correction pipeline has two pieces of evidence: the earlier result and the late event. A broader historical recomputation can then produce a new accepted snapshot under a separate revision policy.
