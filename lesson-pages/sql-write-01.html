Learning objectives#

  • Choose a change-application statement from a declared feed contract.
  • Keep business identity separate from update eligibility.
  • Read actual inserted, updated and deleted rows without assuming output order.
  • Reject ambiguous source versions and incomplete deletion snapshots.
  • Distinguish converged state from a general concurrency or exactly-once claim.

Vocabulary and concepts#

  • Business key: The identifier for the fact being updated; sku identifies one stock record here.
  • Source version: A producer-defined ordered version for that key. A larger number is newer under this fixture's contract.
  • Complete snapshot: An authoritative representation of every in-scope current key at a declared source boundary.
  • Partial event feed: A set of changes that does not say that absent keys were deleted.
  • Conflict target: A uniqueness rule used by INSERT ... ON CONFLICT to identify an existing row.
  • Candidate change row: A source/target relationship classified by the MERGE identity match before its action conditions are evaluated.

The initial target contains A with quantity ten/version one, B with three/version one and Z with five/version one. The source contains A twelve/version two, B three/version one and C one/version one. All quantities describe one synthetic stock unit; versions are ordered integers, not wall-clock timestamps.

State the feed's meaning before selecting SQL. If the source is complete and authoritative, Z's absence can authorize deletion. If it is a partial feed, absence says nothing about Z. The same three visible source rows can therefore lead to different legitimate final states under different source contracts.

Syntax anatomy and action selection#

MERGE INTO target USING source ON identity relates the two populations. In this lesson ON t.sku=s.sku answers whether the business key already exists. A matched row can then be eligible for an update only when its source version advances. That second question belongs in WHEN MATCHED AND ....

Putting the version comparison inside ON changes identity classification. An equal-version B can appear unmatched by the target even though its primary key already exists. An insert branch can then encounter a uniqueness error. Moving an eligibility condition between ON and WHEN is therefore not a harmless formatting preference.

Action clauses also have an order: the first applicable action is selected for a candidate. A condition that claims a row earlier can prevent a later clause from being used. Keep source-only deletion, target-missing insertion and matched-row updates explicit rather than assuming the engine infers an intended sync policy.

Worked example / walkthrough#

Worked case 1: Apply a complete authoritative snapshot#
MERGE INTO w17_stock AS t
  USING w17_feed AS s ON t.sku = s.sku
  WHEN MATCHED AND s.source_version > t.source_version THEN
    UPDATE SET quantity = s.quantity, source_version = s.source_version
  WHEN NOT MATCHED BY SOURCE THEN
    DELETE
  WHEN NOT MATCHED BY TARGET THEN
    INSERT (sku, quantity, source_version) VALUES (s.sku, s.quantity, s.source_version) RETURNING
  merge_action () AS action, t.sku, t.quantity, t.source_version;

The actual changed-row output contains A as UPDATE, C as INSERT and Z as DELETE. B does not change because its version is equal. An unchanged row has no changed RETURNING row. Insert/update output describes new target values; deleted Z describes the deleted values. The statement does not promise a display order for this action stream. The following ordered target query establishes the final state: A twelve/version two, B three/version one and C one/version one.

This is a synchronization policy for the declared complete source. A row-count manifest can catch truncation, but matching a count alone does not prove that the correct keys were delivered or that the producer's boundary is authoritative. Completeness needs evidence from the source system and its identity rules.

Worked case 2: Apply partial changes through a uniqueness conflict#
INSERT INTO w17_stock AS t (sku, quantity, source_version)
VALUES
  ('A', 14, 3),
  ('B', 999, 1),
  ('D', 4, 1)
ON CONFLICT (sku)
  DO UPDATE SET
    quantity = excluded.quantity,
    source_version = excluded.source_version
  WHERE
    excluded.source_version > t.source_version
  RETURNING
    sku, quantity, source_version;

excluded describes the proposed values for a uniqueness conflict. A advances to fourteen/version three. B's stale proposal of 999 is skipped by the update condition. D is inserted. C remains present because this statement does not interpret absence as deletion. In this worked sequence, the final keys are A, B, C and D with quantities fourteen, three, one and four.

The learner script also attempts to modify A twice from two source rows in one MERGE. PostgreSQL raises a cardinality violation. The explicitly handled subtransaction preserves the earlier target state. Source row order is not a latest-version selection policy. The practice repair selects one unique newest source version per key before applying changes.

Choosing a statement and a concurrency claim#

ON CONFLICT uses the selected uniqueness mechanism for its insert/conflict path. MERGE expresses several source/target action classes, including source absence. They do not have identical guarantees under a concurrent target insert. In particular, do not infer an automatic uniqueness-conflict retry policy from MERGE syntax. Isolation, constraints and competing operations still matter.

This default lesson runs in one session. It demonstrates actual mutation, version eligibility, cardinality errors and converged state. It does not claim to have executed a two-session race or delivered an event exactly once across a network. The separately owned concurrency lesson supplies that additional execution surface when deliberately selected.

Common pitfalls#

Treating a partial feed as a snapshot can delete valid keys. Hiding duplicates with an unordered DISTINCT can choose an arbitrary version. Adding more WHEN clauses cannot repair a wrong identity predicate. Inspect both source uniqueness and target key meaning before changing action syntax.

If a statement fails, retain the first error and restore the exercise savepoint. Do not continue from an unverified target state. The final ROLLBACK removes these temporary mutations. Use RETURNING and ordered verification queries to understand changes, rather than accepting a plausible command tag as proof.

Self-check#

  • Explain why matching business identity in ON differs from testing version eligibility in WHEN. Give the target keys produced by the partial versus complete feed.
  • Reconstruct which INSERT, UPDATE and DELETE rows actually appear in RETURNING, and why an unchanged target can remain without an action row.
  • Demonstrate the duplicate-source error and the second-run zero-change assertion. State why neither an equal total nor convergence alone proves general concurrent exactly-once delivery.
