## Why this mechanism matters

Generics express algorithms whose structure is shared across several types. A type parameter is constrained by the operations the algorithm requires. comparable permits equality and map keys; it does not permit ordering or arithmetic. A constraint using a type set can admit underlying integer types with the ~ operator. Generic code still needs a meaningful domain contract: adding signed integers can overflow, floating equality can surprise, and pointer equality is not deep value equality. Prefer a normal function when only one concrete type is useful. A useful generic abstraction removes real duplication while preserving clear errors and readable call sites.

## Vocabulary and concepts

- **Type parameter:** A placeholder type selected for a generic instantiation.
- **Constraint:** The allowed types and operations for a type parameter.
- **Type inference:** Deriving a type argument from call arguments.

## Syntax anatomy and reasoning

`func first[T any](items []T) (T,bool)` declares a type parameter `T`. `var zero T` obtains its zero value for an empty result. A custom constraint such as `interface { ~int | ~int64 }` admits named types with those underlying types. Type inference often determines `T` from arguments. A constraint belongs to compile-time capability checking; it is not runtime validation of application data.

## Worked example / walkthrough

### Worked example 1: Reuse an element contract

Call first with an integer slice and a string slice.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Count int
type Integer interface{ ~int | ~int64 }

func first[T any](items []T) (T, bool) {
	if len(items) == 0 {
		var zero T
		return zero, false
	}
	return items[0], true
}
func unique[T comparable](items []T) []T {
	seen := map[T]bool{}
	out := []T{}
	for _, x := range items {
		if !seen[x] {
			seen[x] = true
			out = append(out, x)
		}
	}
	return out
}
func sumInts[T Integer](items []T) T {
	var out T
	for _, x := range items {
		out += x
	}
	return out
}

func main() {
	// Reuse an element contract
	{
		a, okA := first([]int{4, 5})
		b, okB := first([]string{"red", "blue"})
		check(okA && okB && a == 4 && b == "red", "generic first")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** The results are 4 and red with presence true.

The algorithm needs indexing and length, not knowledge of the element representation. That makes any an honest constraint here.

### Worked example 2: Handle a generic empty value

Call first with an empty integer slice.

```go
package main

import (
	"fmt"
)

	if !ok {
		panic(message)
	}
}

type Count int
type Integer interface{ ~int | ~int64 }

func first[T any](items []T) (T, bool) {
	if len(items) == 0 {
		var zero T
		return zero, false
	}
	return items[0], true
}
func unique[T comparable](items []T) []T {
	seen := map[T]bool{}
	out := []T{}
	for _, x := range items {
		if !seen[x] {
			seen[x] = true
			out = append(out, x)
		}
	}
	return out
}
func sumInts[T Integer](items []T) T {
	var out T
	for _, x := range items {
		out += x
	}
	return out
}

func main() {
	// Reuse an element contract
	{
		a, okA := first([]int{4, 5})
		b, okB := first([]string{"red", "blue"})
		check(okA && okB && a == 4 && b == "red", "generic first")
	}

	// Handle a generic empty value
	{
		v, ok := first([]int{})
		check(v == 0 && !ok, "empty generic")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** The result is zero with presence false.

A zero value alone cannot distinguish an empty input from a first element equal to zero. The boolean preserves that information.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
