# go-040: Work queues, retry budgets and error classification

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-039

## Learning objectives

## Why this mechanism matters

A controller queue decouples event ingestion from reconciliation. Repeated events for one key can be coalesced because reconciliation reads the latest state. A failing key should not spin in a tight loop or prevent unrelated keys from progressing. Rate-limited retry combines an increasing delay with a cap and often jitter; cancellation and a maximum work policy prevent unlimited resource use. Permanent invalid input differs from a transient API failure. Success should clear retry history so an old failure does not penalize a repaired object forever. This lesson models scheduling decisions without sleeping or claiming a full implementation of client-go workqueue semantics.

## Vocabulary and concepts

- **Coalescing:** Combining repeated notifications for the same work key.
- **Backoff:** Increasing delay after repeated transient failures.
- **Retry budget:** A bound on attempts or elapsed work.

## Syntax anatomy and reasoning

A queue key usually names a namespace and object name, not a pointer to a stale object. The worker gets a key, defers Done, reconciles and either Forget on success or schedules a rate-limited retry. The fixture uses integer delay units to test a capped exponential policy deterministically. Production jitter should be tested with an injected source rather than a fixed assumption about wall-clock timing.

## Worked example / walkthrough

### Worked example 1: Calculate increasing delay

Inspect attempts 0, 1 and 2.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func delay(attempt int) int {
	if attempt < 0 {
		return 1
	}
	if attempt >= 3 {
		return 8
	}
	return 1 << attempt
}
func retryable(class string) bool { return class == "transient" }

func main() {
	// Calculate increasing delay
	{
		check(delay(0) == 1 && delay(1) == 2 && delay(2) == 4, "growth")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The delays are 1, 2 and 4 units.

The first attempt and retry numbering must be documented. Ambiguous numbering creates off-by-one operational behavior.

### Worked example 2: Cap the delay

Inspect attempts beyond the configured cap.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func delay(attempt int) int {
	if attempt < 0 {
		return 1
	}
	if attempt >= 3 {
		return 8
	}
	return 1 << attempt
}
func retryable(class string) bool { return class == "transient" }

func main() {
	// Calculate increasing delay
	{
		check(delay(0) == 1 && delay(1) == 2 && delay(2) == 4, "growth")
	}

	// Cap the delay
	{
		check(delay(3) == 8 && delay(10) == 8, "cap")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The delay never exceeds 8 units.

A cap prevents exponential growth from becoming impractical or overflowing. It does not replace a total retry budget.

### Exercise 3: Coalesce duplicate keys

Enqueue alpha twice and beta once in a set model.

**Expected:** There are two pending identities.

**Verify:** Keep a check equivalent to `len(pending) == 2`. As a control, change `for _, key := range []string{"alpha", "alpha", "beta"} {` to `for _, key := range []string{"alpha!", "alpha", "beta"} {`: the run must panic with `coalesce`. Restore the line before continuing.

### Exercise 4: Separate invalid from transient

Classify a validation failure and a timeout-like failure.

**Expected:** Only the transient class is retried.

**Verify:** Keep a check equivalent to `!retryable("invalid") && retryable("transient")`. As a control, change `check(!retryable("invalid") && retryable("transient"), "classification")` to `check(!retryable("invalid") && retryable("transient!"), "classification")` inside that check: it must panic with `classification`, which shows the check can fail. Restore it.

### Exercise 5: Reset successful history

Clear a key after successful reconciliation.

**Expected:** Its next failure starts at the first delay.

**Verify:** Keep a check equivalent to `delay(attempts["demo"]) == 1`. As a control, change `check(delay(attempts["demo"]) == 1, "reset")` to `check(delay(attempts["demo"]) != 1, "reset")` inside that check: it must panic with `reset`, which shows the check can fail. Restore it.

### Exercise 6: Transfer a total budget

Spend a total waiting budget of 10 units on retries whose delays come from delay(attempt).

**Expected:** Three retries fit (1+2+4=7 units); the fourth delay of 8 would exceed the budget.

**Verify:** Keep a check equivalent to `attempts == 3 && spent == 7`. As a control, change `if spent+d > 10 {` to `if spent-d > 10 {`: the run must panic with `budget`. Restore the line before continuing.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
