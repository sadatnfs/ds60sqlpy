## Purpose, vocabulary and mental model

The Service API describes desired routing behavior. A data-plane implementation turns that intent into packet handling on nodes. kube-proxy is a common component that watches Service and endpoint state and programs the supported backend for the cluster version. Other networking implementations can provide Service routing through eBPF or different mechanisms.

On Linux, kube-proxy programs exactly one backend, chosen by its configuration. In Kubernetes 1.37 the default is iptables: a KUBE-SERVICES chain jumps to a per-Service KUBE-SVC chain, which picks a per-endpoint KUBE-SEP chain with random-probability rules, and that chain rewrites the destination (DNAT) to the Pod address. The nftables backend, GA since Kubernetes 1.33 and requiring Linux kernel 5.13 or later, keeps its rules in one `kube-proxy` table with verdict maps and processes endpoint changes more efficiently; the documentation says a future release will make it the default and recommends setting the mode explicitly. In nftables mode NodePort Services answer only on the node's primary addresses by default, not on 127.0.0.1. The IPVS backend uses kernel virtual servers plus iptables helpers; it has been deprecated since Kubernetes 1.35, and the current documentation schedules it to be disabled by default in 1.40 and removed in 1.43, so new clusters should choose nftables or iptables.

An eBPF-based implementation can attach programmable logic at particular kernel hooks. That changes how traffic is handled and observed, but it does not eliminate the need for endpoint identity, policy, routing and application acceptance. The API contract and the implementation evidence remain separate layers.

### Key terms

- **kube-proxy:** The node component that programs Service forwarding rules from Services and EndpointSlices.
- **iptables mode:** A kube-proxy mode that writes Service forwarding rules as Linux iptables chains.
- **nftables mode:** A kube-proxy mode that programs Service forwarding rules through the Linux nftables framework.
- **eBPF data plane:** A forwarding implementation, often part of the network plugin, that handles Services with kernel eBPF programs instead of kube-proxy rules.
- **DNAT:** Destination network address translation, which rewrites a packet's destination from the Service address to a chosen backend.

## Mechanism and field-by-field reasoning

Begin diagnosis by identifying the installed implementation, version and active mode. On a kubeadm-style cluster, including kind, the `mode` field inside the `config.conf` key of the kube-system `kube-proxy` ConfigMap names the backend; an empty value means the release default. A Service object can be correct while a node’s programmed state is stale or broken. Conversely, reading a packet rule does not prove the application accepts a connection.

The course does not modify node packet tables or switch proxy modes. Use the synthetic control/data-plane sequence and consult the prepared environment’s operator documentation. Any privileged host inspection is a separately authorized capability, not part of a browser lesson.

## Trace the request or control path

```text
Service/EndpointSlice API -> watch/reconciliation -> node data-plane state
packet arrives -> implementation lookup/translation -> selected endpoint -> reply path
```

The first line is asynchronous: a watcher on every node notices Service and EndpointSlice changes and rewrites local state, whether iptables chains, nftables maps, IPVS tables or eBPF maps. The second line happens per packet with no API call at all. A slow or broken watcher leaves one node with stale rules while the API looks perfectly correct.

## Worked example / walkthrough

### Worked example 1: Identify the active mode before reading rules

This is a synthetic, abbreviated transcript. The first command reads configuration through the API; the nft commands need a separately authorized shell on one node.

```text
$ kubectl -n kube-system get configmap kube-proxy -o jsonpath='{.data.config\.conf}' | grep '^mode'
mode: nftables
node-a# nft list map ip kube-proxy service-ips
  10.96.0.20 . tcp . 80 : goto service-AB12CD34-lesson/hello/tcp/http
node-a# nft list chain ip kube-proxy service-AB12CD34-lesson/hello/tcp/http
  numgen random mod 2 vmap { 0 : goto endpoint-EF56GH78-lesson/hello/tcp/http__10.244.1.7/8080, 1 : goto endpoint-IJ90KL12-lesson/hello/tcp/http__10.244.2.9/8080 }
```

**Expected observation:** The Service address and port map to one service chain, which picks one of two endpoint chains at random; each endpoint chain then rewrites the destination to a Pod address. In iptables mode the same roles appear as KUBE-SVC and KUBE-SEP chains in `iptables-save -t nat` output.

### Worked example 2: Classify a stale-node symptom

```text
app endpoint responds directly from an allowed probe
```

**Expected observation:** Investigate node-specific routing/policy state without assuming the Service spec is wrong.

## Six progressive exercises

### Exercise 1: Distinguish Service API and data plane.

**Expected evidence:** Desired routing objects versus actual packet handling.

**Progressive hint:** One is a stored object you can read with kubectl; the other is state in each node's kernel. Which one handles packets?

### Exercise 2: Identify why proxy-mode advice is version-sensitive.

**Expected evidence:** In Kubernetes 1.37 iptables is the default, nftables has been GA since 1.33 and needs kernel 5.13 or later, and IPVS has been deprecated since 1.35 with removal scheduled, so advice depends on the release and the node kernel.

**Progressive hint:** Read the expected answer's release timeline: defaults and deprecations moved between 1.33 and 1.35.

### Exercise 3: Draw the watch-to-packet sequence.

**Expected evidence:** API observation, reconciliation, programmed state and packet decision are separate.

**Progressive hint:** Number the steps from API write to packet decision and mark where a delay could leave a node behind.

### Exercise 4: Diagnose one-node-only Service failure.

**Expected evidence:** Compare node-local data-plane and policy behavior.

**Progressive hint:** If the Service spec were wrong, every node would fail. What can differ between one node and the others?

### Exercise 5: Explain why eBPF is not an application correctness proof.

**Expected evidence:** It is an implementation technique for specific kernel behavior.

**Progressive hint:** eBPF changes how lookups run in the kernel. Does that tell you anything about the response body?

### Exercise 6: Plan an implementation-specific incident review.

**Expected evidence:** Record active mode, versions, owned probe results and permitted diagnostics.

**Progressive hint:** Before reading any rules, write down the mode, the versions and which diagnostics the operator approved.

## Diagnosis, failure boundaries and common mistakes

Reading iptables output before confirming the proxy mode wastes time: an nftables or eBPF cluster may have almost no relevant iptables rules, and that absence proves nothing. Another mistake is copying advice from an older release; IPVS deprecation and nftables graduation changed what is normal. When only one node fails, resist editing the Service. The API object is shared by every node, so compare the failing node's programmed state and proxy logs with a healthy node instead. Never flush rules or restart a node's proxy outside the operator's approved procedure, because that destroys the stale state you were trying to observe.
