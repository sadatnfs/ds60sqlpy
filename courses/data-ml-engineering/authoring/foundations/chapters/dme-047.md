# dme-047: Incidents, retries, failure domains and degraded service

## Recovery behavior can amplify the original failure

A dependency becomes slow, callers time out, and each caller retries. Those extra attempts increase load on the struggling dependency, making it slower still. If several layers independently retry, one user action can generate many downstream calls. A recovery mechanism designed without a workload budget can turn a partial failure into a wider incident.

A timeout limits how long one caller waits at a particular boundary. It does not prove that the downstream effect failed or that downstream computation stopped. A retry creates another attempt. It is appropriate only when the operation's semantics and remaining deadline permit it. A circuit breaker temporarily avoids calls to a dependency after observed failures, then allows a controlled recovery probe. These mechanisms solve related but distinct problems.

This chapter executes explicit local state-machine models over predetermined outcomes. No remote service is contacted and no clock sleeps occur. The program counts attempted dependency calls and exposes every breaker transition. The earlier request-lifecycle and outbox chapters execute the real cancellation and transaction boundaries that a deployed retry design must also respect. Here we study policy interaction without generating actual failure traffic.

## Closed, open and half-open states

In the closed state, calls are permitted. The model allows at most two attempts per logical request and tracks consecutive failed attempts across requests. Three failed attempts open the breaker. In the open state, requests receive an explicitly labelled fallback without contacting the dependency. After a five-unit cooldown, one request enters a half-open state and may make one probe. A successful probe closes the breaker and resets its failure count; a failed probe reopens it.

These thresholds are illustrative. A production breaker might use a rolling failure fraction, minimum request population, separate error categories and a bounded number of probes. It also needs concurrency control so many callers do not all become the recovery probe at once. The model is single-threaded and uses an explicit monotone integer clock. It rejects backward time rather than silently extending or shortening the cooldown.

A breaker changes the amount of attempted work; it does not establish that the dependency is permanently broken. It should also not conflate validation failures with infrastructure failures. Retrying a malformed request rarely helps, and opening a shared breaker because one caller sent invalid input can deny service to unrelated valid callers. Classify failures according to the operation contract.

## Worked case 1: bound attempts and probe recovery

`example_one()` supplies dependency outcomes of three failures followed by two successes. At model time zero, the first logical request uses its two allowed attempts, both fail, and it returns fallback. The breaker remains closed because the threshold is three failed attempts. At time one, the next request's first failure reaches the threshold, opens the breaker and stops further attempts for that request.

At time two, the breaker is still cooling down and returns fallback without increasing the call count. At time six, five units have elapsed since opening at one. The half-open probe succeeds, so the breaker closes. At time seven, another request succeeds normally. Across five logical requests, the dependency was called five times, and the program records the state and cumulative count after each step.

The fallback is a string describing a policy outcome; it does not invent a prediction, return hidden stale data or mutate a business record. A real fallback must have its own semantics. It might return a retained result with a visible age, simplify a noncritical feature, queue work for later or fail explicitly. Treating every fallback as equivalent to a fresh successful prediction would conceal degraded service from consumers and reliability metrics.

With more retrying layers, multiplication can grow quickly. If layer \(i\) allows \(a_i\) attempts, the worst-case attempt count can approach \(\prod_i a_i\) for the nested call pattern. A shared end-to-end deadline and deliberate retry owner can reduce this amplification. The correct budget depends on latency objectives, operation cost and the likelihood of transient recovery, not simply on a default copied into every library.

A request budget is not an idempotency guarantee. Four unsafe mutations can be four duplicate business effects. Retrying a read or a conditional identified effect has different semantics from replaying an unguarded payment, notification or state update. Use the operation identity and reconciliation boundary described earlier before optimizing retry counts.

## Deadlines, backoff and jitter

A total deadline should include waiting, connection setup, attempts, backoff and response handling. Giving each nested layer the full original timeout can exceed the caller's intended deadline. Propagate the remaining budget where the protocol supports it, and stop starting new attempts when there is insufficient time for a useful result. Record whether a timeout occurred before admission, during computation or while returning a response.

Backoff spaces repeated attempts. Exponential backoff increases a delay with attempt number, usually with a cap. Jitter varies delays so many callers do not retry in synchronized waves. For example, a design might sample a delay from a bounded interval whose upper limit grows with the attempt number. The program does not implement sleeping because this chapter's deterministic model focuses on attempt accounting; a real client policy must test its actual timing behavior separately.

Backoff cannot create capacity that does not exist. A persistently overloaded dependency may need load shedding, reduced demand or additional resources. Retries are most useful for a bounded transient failure when the operation is safe to repeat. A configuration error, incompatible schema or denied permission usually requires correction, not repeated traffic.

## Failure domains and graceful degradation

A failure domain is a set of components that can fail together because they share a resource or dependency. Several replicas on one host share that host's fate. Several services using one overloaded database can fail together even if their own processes are healthy. An incident investigation should map the actual shared boundaries rather than counting containers as independent protection.

A degraded mode should preserve a meaningful contract. A stale cached feature might be acceptable for a low-risk ranking component under a bounded age, while another decision may require explicit unavailability. Label the mode, version and freshness so consumers can interpret it. Test that fallback does not expose unauthorized data or bypass validation merely because the primary dependency failed.

Circuit breakers can themselves become operational hazards if their state is opaque or their recovery policy is wrong. Monitor rejected calls, probe outcomes, open duration and the affected dependency identity. A single global breaker may combine unrelated failure populations; one breaker per request can fail to protect a shared dependency. Choose the scope around the resource and workload being protected.

## Incident evidence and diagnosis

If load rises after errors begin, compare logical requests with downstream attempts. If traffic returns in periodic waves, inspect synchronized retry delays. If a service stays degraded after its dependency recovers, inspect cooldown and probe behavior. If clients report duplicate effects, inspect idempotency and uncertain outcomes rather than only adjusting backoff.

During an incident, preserve a timeline of observed signals, actions and readbacks. Distinguish a plausible hypothesis from a confirmed cause. A rollback that coincides with recovery is useful evidence, but it may not prove the released code caused the problem if another dependency recovered at the same time. Follow-up work should reproduce or narrow the mechanism and add meaningful checks where possible.

## Applications and answered interview discussion

These patterns apply to feature retrieval, model serving, data ingestion APIs and orchestration calls. They are also relevant to LLM clients, where retries can consume significant compute and may repeat stateful tool actions. The later serving chapters connect attempt budgets to token and request capacity.

An interviewer may ask, “Where should retries live?” Explain end-to-end budgets, the operation's safe-repeat contract and coordination across layers. If asked what a circuit breaker guarantees, describe the state machine and protected scope without claiming it fixes the dependency. If asked whether timeout means failure, explain the unknown-outcome boundary and how an operation ledger or readback resolves it.
