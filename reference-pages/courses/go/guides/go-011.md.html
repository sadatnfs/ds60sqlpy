go-011: Errors as values and preserving causal context#

Level and prerequisites#

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-010

Learning objectives#

By the end, explain sentinel error, wrapping, recovery policy; implement the six investigations below; and defend the expected result of a changed input before running it. A passing reference is evidence about that program, not a certification of your independent understanding.

Why this mechanism matters#

Errors describe unsuccessful operations without forcing every failure into panic recovery. A function returning a value and error makes the caller choose what to do next. The error chain should preserve both human context and a machine-inspectable cause. Wrapping with fmt.Errorf and %w adds context while errors.Is and errors.As can inspect underlying identity or type. Comparing formatted text is brittle because wording is presentation, not a stable contract. A nil error means the operation succeeded according to its API; it does not prove every downstream interpretation is valid. Handle failures where you can add useful context, recover deliberately or report them accurately.

Vocabulary and concepts#

  • Sentinel error: A named error value used as an identity contract.
  • Wrapping: Adding context while preserving an underlying cause.
  • Recovery policy: A deliberate response to a particular failure class.

Syntax anatomy and reasoning#

errors.New constructs an error value. fmt.Errorf("read: %w", err) wraps an existing cause. errors.Is follows supported wrapping relationships to compare a sentinel; errors.As finds an error assignable to a target type. Return nil for a successful error result, not an interface containing a typed nil pointer. Avoid logging and returning the same error at every layer because repeated messages can obscure the causal chain.

Worked example / walkthrough#

Worked example 1: Preserve a cause#

Wrap ErrMissing with a record-reading context.

package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

var ErrMissing = errors.New("missing record")
var ErrDenied = errors.New("access denied")

type LimitError struct{ Max int }

func (e *LimitError) Error() string { return fmt.Sprintf("limit %d", e.Max) }

func main() {
	// Preserve a cause
	{
		err := fmt.Errorf("read record: %w", ErrMissing)
		check(errors.Is(err, ErrMissing), "wrapped cause")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: errors.Is still recognizes ErrMissing.

%w exposes the cause to the error-inspection protocol. Replacing it with %v would format the cause as text but lose that wrapping relationship.

Worked example 2: Reject text equality#

Construct two separate errors with the same wording.

package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

var ErrMissing = errors.New("missing record")
var ErrDenied = errors.New("access denied")

type LimitError struct{ Max int }

func (e *LimitError) Error() string { return fmt.Sprintf("limit %d", e.Max) }

func main() {
	// Preserve a cause
	{
		err := fmt.Errorf("read record: %w", ErrMissing)
		check(errors.Is(err, ErrMissing), "wrapped cause")
	}

	// Reject text equality
	{
		a := errors.New("missing")
		b := errors.New("missing")
		check(!errors.Is(a, b), "identity not text")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: Their identities differ.

A matching message does not establish the same error contract. Use an exported sentinel or typed error only when callers should rely on that distinction.

Common pitfalls and diagnosis#

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from check identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned error is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
