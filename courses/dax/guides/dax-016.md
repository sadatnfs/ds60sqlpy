## The question and the mechanism

Explain why sibling filter arguments differ from deliberately nested evaluation.

DAX filter arguments are expressions evaluated in the incoming context; they are not a series of imperative assignments executed left to right. If one filter expression uses MAX(Product[ProductKey]), that scalar is determined from its evaluation context, not automatically from the effect of a neighboring Color filter.

Start with Paper. Its visible keys are 1 and 2, so MAX is 2. A single CALCULATE that adds Blue and also restricts ProductKey to that incoming maximum requests a blue product with key 2. None exists. A learner imagining that Blue runs first will incorrectly predict key 1 and revenue 67.

Nesting can intentionally establish a new context before another expression is evaluated. An outer Blue calculation changes the context received by the inner calculation; MAX then sees only the blue Paper product. Make the nesting express a business question rather than using it as a trial-and-error fix. Write the contexts as successive ledgers before trusting a complicated expression.

## Vocabulary and expression anatomy

Both cases begin in Paper. Case A puts Color and the MAX-derived key in sibling filter arguments. Case B puts the Blue modifier in an outer CALCULATE so the inner key expression sees the changed context. MAX is a scalar aggregation allowed in this column-filter construction; its value must still be traced at the correct time.

Concepts to explain in your own words: **evaluation order**, **nested CALCULATE**, **filter argument**, **captured scalar**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: Sibling filters use the incoming key maximum

**Starting context:** Incoming Product.Category = Paper; sibling Color and ProductKey filters.

```dax
EVALUATE CALCULATETABLE ( ROW ( "IncomingMaxKey", MAX ( Product[ProductKey] ), "Revenue", CALCULATE ( [NetRevenue], Product[Color] = "Blue", Product[ProductKey] = MAX ( Product[ProductKey] ) ) ), Product[Category] = "Paper" )
```

**Context trace:**

1. Paper's incoming keys are 1 and 2; MAX is 2.
2. Blue and ProductKey 2 are then applied together with the retained category.
3. Pen is key 2 but Red, so the resulting product set is empty.

**Hand-derived worked-reference result:**

| IncomingMaxKey | Revenue |
| --- | --- |
| 2 | BLANK |

BLANK is the coherent answer to those combined constraints. It is not evidence that MAX or the relationship failed.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Nested context before computing the key

**Starting context:** Paper first; outer CALCULATE applies Blue before the inner key expression is evaluated.

```dax
EVALUATE CALCULATETABLE ( ROW ( "Revenue", CALCULATE ( CALCULATE ( [NetRevenue], Product[ProductKey] = MAX ( Product[ProductKey] ) ), Product[Color] = "Blue" ) ), Product[Category] = "Paper" )
```

**Context trace:**

1. Paper plus Blue leaves ProductKey 1.
2. The inner MAX therefore evaluates to 1.
3. Notebook revenue is 67.

**Hand-derived worked-reference result:**

| Revenue |
| --- |
| 67 |

The formulas answer differently sequenced questions. Do not call them interchangeable rewrites merely because they mention the same functions and columns.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.
