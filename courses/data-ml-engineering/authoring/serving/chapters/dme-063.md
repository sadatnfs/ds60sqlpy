# dme-063: Prefill, causal attention and a correct KV cache

A causal Transformer predicts the next token from an existing prefix. The first serving pass processes the prompt and produces logits for its final position. This phase is usually called prefill. Later passes add one generated token at a time. Recomputing all earlier keys and values on every pass is unnecessary when the model and prefix are unchanged, so the server retains a key/value cache for each layer and request.

This chapter runs actual Torch attention on the prepared CPU profile. It compares cached single-query computation with full causal attention and with an independent explicit softmax formula. A second check changes a future value vector and verifies that earlier outputs remain unchanged. These are correctness tests, not GPU throughput measurements.

## Shapes describe the computation

For one layer, let query, key and value tensors have dimensions batch \(B\), heads \(H\), time and head width \(d_h\). A prompt of \(T\) tokens has query shape \((B,H,T,d_h)\) and matching key/value shapes. Attention for each head is

\[
A=\operatorname{softmax}\left(\frac{QK^\top}{\sqrt{d_h}}+M\right)V.
\]

The softmax normalizes across the key positions available to each query. The causal mask \(M\) is zero for allowed positions and negative infinity for future positions. During full prefill, query position \(i\) may attend only to keys at positions no later than \(i\). The output at the last prompt position supplies the distribution for the first generated token.

The query/key dot product is scaled by \(\sqrt{d_h}\). The value tensor determines what weighted content is combined. Query and key similarities do not themselves constitute the output representation. Attention heads are later combined and transformed by the rest of the layer.

## What the cache contains

A KV cache stores the past keys and values produced by each layer for the particular request prefix. It does not store arbitrary retrieved documents, and it does not normally store the model weights. In the workshop it is a list of per-layer tensor pairs, each with shape \((B,H,p,d_h)\), where \(p\) is the number of processed positions.

After generating a token, the next decode pass embeds that token at position \(p\), computes its query/key/value tensors and appends the new key and value to the layer's cache. The new query attends to the entire available prefix, including its own current key. Earlier cache entries are reused because causal computation prevents future tokens from changing them.

This reasoning assumes the model is in evaluation mode, dropout is disabled, the prefix and position convention are unchanged, and cached entries have the expected dtype/device. Training mode with stochastic dropout can invalidate a naive full-versus-cached comparison. Reusing a cache from another request is both a correctness and isolation error.

The simple workshop concatenates tensors to grow a contiguous cache. This is readable and suitable for a tiny context, but repeatedly allocates and copies. A production implementation may reserve capacity, use blocks or page caches. Those storage strategies must preserve the same attention semantics. Later paging chapters separate that allocator problem from this numerical contract.

## The rectangular causal-mask trap

A one-token cached decode has a query time dimension of one and a key time dimension of \(p+1\). In the Torch interface used here, asking for a generic top-left causal mask on this rectangular matrix allows the first query row to see only the first key position. That is wrong for a query representing the end of the prefix.

For this exact one-new-token implementation, all cached keys are already valid past-or-current positions. The decode call therefore uses `is_causal=False` with the cache consisting only of those valid positions. Prefill still uses `is_causal=True`. A multi-token chunked decode needs an explicit offset-aware mask; simply disabling causality for several new queries would expose future tokens within the chunk.

This is why a successful tensor operation and plausible-looking output are weak evidence. The wrong mask can satisfy every shape check. A cached-versus-full numerical comparison exposes the semantic error directly.

## Worked case 1: compare every prefix position

The first case creates fixed random query, key and value tensors with two heads, five positions and head width four. It calculates one full causal attention result. It then processes each position as a single query against its available key/value prefix, concatenating the five outputs.

The two results must agree within a small floating-point tolerance. The test uses the same Q/K/V fixture so the comparison isolates attention and masking rather than a trained model's quality. It then deliberately applies `is_causal=True` to the final single-query/full-key rectangle and asserts that this wrong result differs from the correct final output.

The changed condition demonstrates a realistic serving defect. It is not a failure of the attention formula; it is a mismatch between the query's logical position and the API's mask alignment. The full project performs a stronger model-level comparison that also includes embeddings, positions, all layers and the output head.

## Worked case 2: an independent formula and a future perturbation

The second case calculates scores explicitly, applies a lower-triangular mask, normalizes with softmax and multiplies by values. It compares that result with Torch's scaled-dot-product attention. This provides an independently expressed oracle rather than calling the same function twice under identical arguments.

Next it adds 1,000 to the final value vector. Outputs at earlier positions must remain exactly unchanged in this fixture because their mask excludes that position. The final position may change. This test catches future-information leakage, an error that can make training or evaluation look deceptively strong while violating autoregressive serving semantics.

## Computation and memory growth

Full attention conceptually forms \(T\times T\) scores per head. Prefill therefore has a quadratic attention component in prompt length, although optimized kernels can avoid materializing the entire matrix. Single-token decode uses one query against a growing prefix, so its attention work increases with cache length. Other components, including projections and feed-forward networks, have their own costs.

For \(L\) layers, \(H_{KV}\) KV heads, head width \(d_h\), cached tokens \(T\) and element width \(b\) bytes, raw KV storage is

\[
M_{KV}=2LH_{KV}d_hTb.
\]

The factor two counts keys and values. This is per sequence and excludes allocation overhead. Grouped-query attention changes \(H_{KV}\), while the number of query heads can remain larger. Increasing maximum continuation length affects both admission reservations and potential decode cost.

## Diagnosis and interview discussion

**Why can past key/value tensors be reused?** Under causal evaluation, later tokens cannot affect earlier hidden states. Their keys and values are therefore fixed for an unchanged model, prefix and position convention.

**What would you test before enabling a cache optimization?** Full-versus-cached logits across several prefix lengths, position offsets, causal perturbations, dtype/device agreement, request isolation and context-limit failures. Compare under declared tolerances and deterministic settings.

**Why is prefill different from decode?** Prefill processes many prompt queries together; cached decode adds one or a small number of queries to existing keys and values. Their shapes, memory traffic and scheduling needs differ even within the same model.
