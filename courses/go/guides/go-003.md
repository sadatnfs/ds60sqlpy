# go-003: Decisions, loops and invariants

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-002

## Learning objectives

Write loops with an explicit invariant that handle empty input, exact boundaries and early exit correctly. Along the way, explain invariant, short circuit, half-open interval; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Control flow determines which statements execute. A condition is a boolean expression, not a number used as a truth value. Go's for statement covers counting loops, condition-controlled loops and collection iteration. The safest way to reason about a loop is to name an invariant: a statement true before the first iteration and preserved by every iteration. In a prefix sum, the accumulator contains exactly the elements already visited. Empty input is therefore not an exceptional accident; the initial accumulator already represents its result. Short-circuit operators also affect execution, which makes a guard before a potentially unsafe operation meaningful.

## Vocabulary and concepts

- **Invariant:** A property maintained across every loop iteration.
- **Short circuit:** Skipping an operand after the result is determined.
- **Half-open interval:** A range including its start and excluding its end.

## Syntax anatomy and reasoning

if condition { ... } selects a branch. && skips the right operand when the left is false. for i := 0; i < len(items); i++ visits a half-open index interval. break leaves the innermost loop; continue skips to its next iteration. switch compares one expression against alternatives and does not fall through by default. A boundary using <= instead of < often attempts one extra iteration.

## Worked example / walkthrough

### Worked example 1: Trace a prefix sum

Sum 2, 4 and 6 while checking every visited prefix.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Trace a prefix sum
	{
		items := []int{2, 4, 6}
		sum := 0
		for _, x := range items {
			sum += x
		}
		check(sum == 12 && len(items) == 3, "sum")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The final sum is 12 and three elements were visited.

The accumulator starts at the additive identity. Each iteration includes exactly one new value; double addition or a skipped element breaks the independently known total.

### Worked example 2: Handle empty data

Apply the same summation to an empty slice.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Trace a prefix sum
	{
		items := []int{2, 4, 6}
		sum := 0
		for _, x := range items {
			sum += x
		}
		check(sum == 12 && len(items) == 3, "sum")
	}

	// Handle empty data
	{
		sum := 0
		for _, x := range []int{} {
			sum += x
		}
		check(sum == 0, "empty sum")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The result is 0 with no special invented element.

The loop body never runs. A correct initial state makes the empty case follow from the same algorithm rather than a separate patch.

## Common pitfalls and diagnosis

Loop bugs usually come from an accumulator that starts in the wrong state or a boundary operator chosen without a requirement. Starting `sum` at 1, or patching the empty case with a special branch, hides an invariant mistake. Writing `>` where the requirement says a score of 60 passes fails only at the exact boundary, so always test that value. A guard protects an index only when it is evaluated first.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Trace a prefix sum: change one input

1. Restate the expected observation: The final sum is 12 and three elements were visited.
2. After visiting k elements, what does sum contain? Check that invariant against the visited prefix, not only the final total.
3. The edited elements add up to 13, so `sum == 12` fails while the length condition still holds; both conditions share the message sum.

### Hint for investigation 2: Handle empty data: debug a regression

1. Restate the expected observation: The result is 0 with no special invented element.
2. Count how many times the loop body executes for an empty slice. What must sum hold before the loop?
3. With an initial value of 1, the empty loop leaves sum at 1. The additive identity 0 makes the empty case correct without a special branch.

### Hint for investigation 3: Use a safe guard

1. Restate the expected observation: The condition is false and no indexing occurs.
2. `&&` stops at the first false operand. Which operand must run first to make indexing safe?
3. Reversing the operands would index before proving a valid position.

### Hint for investigation 4: Find the first match

1. Restate the expected observation: Its index is 1.
2. The -1 sentinel means not found. What stops a later match from overwriting the first one?
3. Without break, the later match replaces the first one.

### Hint for investigation 5: Classify an exact boundary

1. Restate the expected observation: The boundary belongs to the passing branch.
2. Read the requirement as a boundary: is a score exactly equal to the threshold inside the passing set?
3. Boundary tests distinguish >= from >.

### Hint for investigation 6: Transfer to a filtered count

1. Restate the expected observation: Exactly 2 values satisfy the predicate.
2. continue skips the rest of one iteration. Is zero negative, and should the predicate count it?
3. continue avoids the increment for negative inputs.
