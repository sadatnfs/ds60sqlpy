# k8s-064: A packet-path troubleshooting method from DNS to response

## Level and prerequisites

Advanced; about 120 minutes plus optional supervised host observations. Direct prerequisites: `k8s-063`. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

## Learning objectives

Build a three-hypothesis table for Service failure. Perform a single-fault incident walkthrough. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

## Purpose, vocabulary and mental model

Troubleshooting is a sequence of discriminating observations. Start with the caller, intended name, protocol, port and expected application result. Then identify the first layer where actual behavior differs from the model. Changing several layers at once can make the symptom disappear without explaining the cause.

A useful request ladder separates name resolution, route reachability, transport connection, TLS identity, proxy routing and application semantics. Kubernetes adds controller and endpoint state that helps explain those steps. A successful test at one layer should not be promoted into a claim about every later layer.

Controlled comparisons are powerful. If direct Pod traffic succeeds but Service traffic fails, focus on selector/endpoints/data-plane differences. If an internal Service request succeeds but external traffic fails, inspect the external listener and routing path. Each comparison requires the same intended application and an owned permitted probe.

## Mechanism and field-by-field reasoning

Use a hypothesis table with expected observation if true, expected observation if false and the smallest safe check. Preserve the failure before repair. Avoid broad all-namespace commands and packet captures when an exact field or short request answers the question.

A timeout is ambiguous: it can involve dropped packets, no route, DNS delay, a stalled TLS handshake or an application that never responds. A refused connection, TLS error and HTTP status narrow the phase differently. Read the actual diagnostic rather than translating every failure into service down.

## Trace the request or control path

```text
name -> DNS answer -> route -> TCP connect -> TLS -> proxy rule -> app handler -> expected body
parallel control evidence: Service selector -> EndpointSlices -> Pod readiness/revision
```

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

## Worked example / walkthrough

### Worked example 1: Compare two paths

The synthetic probes use the same app revision.

```text
PodIP:8080 succeeds
ClusterIP:80 fails
next: inspect Service targetPort, eligible endpoints and node data plane
```

**Expected observation:** The application listener is less likely to be the first failing component.

### Worked example 2: Write a falsifiable hypothesis

A useful hypothesis predicts a distinct observation.

```text
hypothesis: Service selector matches no Pods
if true: matching Pod set and ready endpoints are empty
if false: investigate port mapping or data plane next
```

**Expected observation:** The proposed read can disprove the hypothesis without changing the system.

## Diagnosis, failure boundaries and common mistakes

The controlled failure in this chapter is: Diagnose internal success with external failure. Its distinguishing result is Inspect the added external listener/routing/TLS layers. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
