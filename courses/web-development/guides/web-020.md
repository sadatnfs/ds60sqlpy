# web-020: Transitions, motion and reduced-motion preferences

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-019`

## Learning objectives

Build a card interaction with a static reduced-motion alternative. Explain why transform does not guarantee a fast page. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

Motion can explain a change, but it can also distract, delay a task or cause discomfort. A transition interpolates between property values when state changes. An animation uses named keyframes over time. Neither should be required to understand essential content. Begin with the static usable state and add restrained motion only when it improves orientation.

Animating layout-affecting properties can trigger repeated layout work, while transform and opacity often allow more efficient compositing. This is not a guarantee of smooth performance because element size, painting and the device still matter. Measure actual behavior rather than assuming that a property name proves efficiency. Continuous decorative motion rarely helps a reading task.

## Syntax anatomy and mechanism

Specify the properties to transition instead of transition:all, which can animate unrelated future changes. The prefers-reduced-motion media query lets a page respond to a user's preference. A reduced-motion rule can remove movement while retaining a color or outline change. Do not use a tiny but nonzero duration as a universal accessibility strategy; understand the interaction's required events and states.

## Worked example / walkthrough

### Worked example 1: A restrained state transition

Only the intended visual property is animated.

```css
.card { transition: transform 120ms ease; }
.card:hover { transform: translateY(-2px); }
```

**Expected observation:** Pointer hover produces a small positional cue.

### Worked example 2: Respect the preference

The static state stays fully usable.

```css
@media (prefers-reduced-motion: reduce) { .card { transition: none; } .card:hover { transform: none; } }
```

**Expected observation:** The positional motion is removed for the reduced-motion preference.

## Six progressive exercises

### Exercise 1: Identify the difference between a transition and keyframe animation.

**Expected evidence:** A transition follows a property change; an animation follows a named timeline.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Limit a transition to one intentional property.

**Expected evidence:** Unrelated style changes no longer animate automatically.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a card interaction with a static reduced-motion alternative.

**Expected evidence:** The card remains understandable and usable without movement.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose an animation that hides information until it finishes.

**Expected evidence:** Make the essential content available without waiting for motion.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test with reduced motion enabled and with keyboard focus.

**Expected evidence:** Motion is reduced and the focus indicator still communicates interaction.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain why transform does not guarantee a fast page.

**Expected evidence:** The full rendering workload, content size and device determine performance.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not make reduced motion disable the action itself. Avoid infinite animations in reading material. Test the preference in a real browser because source presence does not prove the rule won the cascade.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain transition, transform, animation without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
