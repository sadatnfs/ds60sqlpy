tf-034: Robustness, privacy and model evidence#

Level and prerequisites#

Advanced; approximately 120 minutes. Direct prerequisites: tf-033. The prerequisite sequence introduces the notation used here; revisit its worked examples if an axis, probability or gradient is unfamiliar.

Learning objectives#

Bound a reliability or privacy claim to the observations actually collected. The central investigation is concrete: Build an error table over fixed perturbations, rare groups and a duplicate-data counterexample; draft a model card for the tiny classifier. The finish condition is The report names the evaluation unit, each tested group, sample count and untested conditions. It makes no differential-privacy or production-safety claim from a small red-team set. A useful explanation connects the calculation to the reason it is needed, rather than treating a function name as a definition.

Purpose and mental model#

A robustness report records which conditions were actually tested and which failures occurred. It does not convert a finite list of successful checks into a guarantee. Group metrics need counts, because zero errors among one rare-group observation is very weak evidence. Perturbations should preserve the intended label when interpreted as robustness tests; otherwise they define a new task. Duplicate records can make a score look more certain without adding independent evidence. Privacy claims require their own mechanisms and analysis. The absence of names in a synthetic fixture, or a successful perturbation test, is not proof of differential privacy or production safety.

Vocabulary and concepts#

Robustness: Behavior under specified changes to inputs or conditions.

Subgroup: A declared subset whose performance is evaluated separately.

Model card: A structured account of intended use, evidence and limitations.

Syntax anatomy and reasoning sequence#

Represent each result with a stable record ID, group, expected label and prediction. Aggregate integer errors and counts before calculating rates. Compare the set of unique IDs with row count to detect exact repetitions. Keep a model-card dictionary with intended use, evaluated units and untested conditions. A model card summarizes evidence; it is not itself a validation method.

Robustness needs a unit, a denominator and a failure policy#

In the supplied group ledger, group A has one success among two records and group B has zero among one. Those are observed fractions with denominators 2 and 1. They do not support precise comparisons of underlying population rates. An absent group has no observed denominator; its result is unknown, not zero percent or one hundred percent.

Duplicates can make the apparent sample size larger than the information content. Eight rows representing three unique identities provide eight row observations but only three identity units under an identity-level analysis. Choose the unit that matches the decision. When repeated records from one identity share errors, treating them as independent can understate uncertainty. Report both row counts and unique-ID counts when both matter.

A perturbation test asks whether behavior changes under a specific input change. The target must remain valid, or be transformed consistently. An image flip may preserve an object category but reverse a left/right label; a text rewrite can accidentally change a negation. Mechanical success of a transformation does not establish semantic equivalence. Keep the assumption beside each test case.

Average pass rate and severity are different summaries. Nine passing cases out of ten give 90 percent, but one severe failure can still block a release under the stated policy. Preserve the failure description and affected unit instead of letting an aggregate erase it. Likewise, duplicate and exposure checks are useful privacy controls, but passing a small checklist is not a proof of privacy or a substitute for a defined threat model.

Worked example / walkthrough#

Example A: Count errors by group#

Both numerator and denominator are visible. Reporting only rates would conceal the fact that groupB has a single observation.

import numpy as np

rows=[('a','A',1,1),('b','A',1,0),('c','B',0,0)]
report={g:(sum(t!=p for i,k,t,p in rows if k==g),sum(k==g for i,k,t,p in rows)) for g in ['A','B']}
assert report=={'A':(1,2),'B':(0,1)}

Expected: A1/2 errors; B0/1.

Example B: Expose duplicate confidence#

Duplicating a correct observation can improve a row-weighted score without testing a new case. Identity-aware evaluation prevents artificial increases in apparent evidence.

import numpy as np

rows=[('a','A',1,1),('b','A',1,0),('c','B',0,0)]
report={g:(sum(t!=p for i,k,t,p in rows if k==g),sum(k==g for i,k,t,p in rows)) for g in ['A','B']}
assert report=={'A':(1,2),'B':(0,1)}
repeated=rows+[rows[-1]]*5
assert len(repeated)==8 and len({r[0] for r in repeated})==3

Expected: 8 rows but only3 unique IDs.

Common pitfalls and diagnosis#

If a percentage looks surprisingly stable, inspect duplicate identities and subgroup denominators. If an empty group displays a numeric rate, inspect the missing-data policy. For perturbation failures, check that the transformation preserved the intended target before calling the model nonrobust. Keep severe individual failures visible beside aggregate scores.
