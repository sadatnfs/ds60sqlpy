# c-018: File streams, short operations and reliable closure

## Level and prerequisites

Intermediate, approximately 120 minutes plus a later retrieval session. Direct prerequisites: `c-017`

## Learning objectives

Explain stream state, short read, eof indicator. Implement the six investigations with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

A FILE stream buffers I/O and tracks state such as end-of-file and errors. A read operation reports what happened; feof predicts nothing before an attempted read reaches the end. A short read can mean EOF or an error, so inspect stream state appropriately. Writes and close operations can fail, especially when buffered data is flushed. Resource ownership includes closing the stream on every completed path, not merely after the happy-path computation. These examples use tmpfile, which creates an owned temporary stream removed on closure. They do not read or overwrite learner files.

## Vocabulary and concepts

- **Stream state:** The position, buffering and error indicators associated with FILE.
- **Short read:** Fewer elements returned than requested.
- **EOF indicator:** State set after a read encounters the end of a stream.

## Syntax anatomy and execution trace

fwrite and fread return element counts, not necessarily byte counts unless element size is one. fseek or rewind changes position; rewind also clears error and EOF indicators. fgetc returns int so every unsigned-char value remains distinct from EOF. fgets reads a bounded line and retains a newline when one fits. fclose releases the stream and may report a final write failure.

## Worked example / walkthrough

### Worked example 1: Round-trip an owned stream

Write abc, rewind and read three bytes.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int main(void) {
  /* Round-trip an owned stream */
  {
    FILE *f = tmpfile();
    CHECK(f != NULL);
    CHECK(fwrite("abc", 1, 3, f) == 3);
    rewind(f);
    char data[4] = {0};
    CHECK(fread(data, 1, 3, f) == 3 && strcmp(data, "abc") == 0);
    CHECK(fclose(f) == 0);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** Three bytes return and match abc.

The terminator comes from initialized output storage, not from fread. Binary reads do not automatically append a string terminator.

### Worked example 2: Observe a short read

Request four bytes from a two-byte stream.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int main(void) {
  /* Round-trip an owned stream */
  {
    FILE *f = tmpfile();
    CHECK(f != NULL);
    CHECK(fwrite("abc", 1, 3, f) == 3);
    rewind(f);
    char data[4] = {0};
    CHECK(fread(data, 1, 3, f) == 3 && strcmp(data, "abc") == 0);
    CHECK(fclose(f) == 0);
  }

  /* Observe a short read */
  {
    FILE *f = tmpfile();
    CHECK(f != NULL);
    CHECK(fwrite("ab", 1, 2, f) == 2);
    rewind(f);
    char data[4];
    size_t n = fread(data, 1, 4, f);
    CHECK(n == 2 && feof(f) && !ferror(f));
    CHECK(fclose(f) == 0);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** Two bytes return and EOF becomes set.

The count is the primary evidence. EOF explains why the remaining requested bytes were unavailable.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
