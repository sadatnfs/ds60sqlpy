js-039: Functional core and state machines#

Level and prerequisites#

Advanced, approximately 120 minutes. Direct prerequisites: js-038

Learning objectives#

Explain state machine, event, functional core, replay with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Start a queued job and complete it with value 7. The final task tests preserve input state and validate success values.

Purpose and mental model#

A state machine makes allowed transitions explicit. Instead of several independent booleans such as started, failed and done, a discriminated union represents one coherent state. An event requests a transition; a pure transition function either produces the next valid state or rejects an invalid event for the current state. This prevents combinations such as simultaneously running and completed from being expressible in ordinary checked code.

A functional core computes decisions without performing I/O. An outer shell can persist the decision, send a message or render it. Keeping the transition pure makes replay and failure analysis straightforward: the same initial state and event sequence should produce the same final state. It does not make external side effects automatically exactly once. The shell still needs a durable transaction and idempotency policy if it coordinates real storage or remote work.

The fixture models a bounded job lifecycle: queued, running, succeeded, failed or cancelled. Starting increments an attempt count. A failed job may retry only while fewer than three attempts have been started. Succeeded and cancelled are terminal. Cancellation is a state transition in this pure model; it does not physically stop a worker or cancel a socket. An integration layer must connect the decision to those operational actions and report their outcomes.

Readonly types express the intended consumer view. The tests also verify that transition does not mutate the input object, because static annotations alone do not prove runtime immutability. Invalid numeric results remain a runtime domain problem even when success carries a TypeScript number.

Vocabulary and concepts#

State machine: A set of coherent states and allowed transitions between them.

Event: A request to transition under the current state.

Functional core: Pure decision logic separated from I/O effects.

Replay: Recomputing state from an initial value and an event sequence.

Syntax anatomy and execution trace#

Each state has kind plus common id and attempt fields. Events form another closed union. switch narrows the event, and state guards define where it is legal. New objects are returned with spread or explicit fields. A never guard protects event exhaustiveness. replay uses reduce to apply the same transition repeatedly. The attempt invariant is checked before retrying, not after accidentally starting a fourth attempt.

Worked example / walkthrough#

Example A: Complete one valid job lifecycle#

The transition sequence carries the attempt count forward. Completion is accepted only after a start established the running state.

import { strict as assert } from 'node:assert';

type Base = { readonly id: string; readonly attempt: number };
type State = Base & ({ readonly kind: 'queued' } | { readonly kind: 'running' } | { readonly kind: 'succeeded'; readonly value: number } | { readonly kind: 'failed'; readonly reason: string } | { readonly kind: 'cancelled'; readonly reason: string });
type Event = { type: 'start' } | { type: 'complete'; value: number } | { type: 'fail'; reason: string } | { type: 'retry' } | { type: 'cancel'; reason: string };
function initial(): State { return { id: 'A', attempt: 0, kind: 'queued' }; }
function assertNever(value: never): never { throw new Error('unknown event: ' + JSON.stringify(value)); }
function transition(state: State, event: Event): State {
  if (state.kind === 'succeeded' || state.kind === 'cancelled') throw new Error('terminal state');
  switch (event.type) {
    case 'start':
      if (state.kind !== 'queued') throw new Error('invalid transition to running');
      return { id: state.id, attempt: state.attempt + 1, kind: 'running' };
    case 'complete':
      if (state.kind !== 'running') throw new Error('invalid transition to succeeded');
      if (!Number.isFinite(event.value)) throw new RangeError('finite result required');
      return { ...state, kind: 'succeeded', value: event.value };
    case 'fail':
      if (state.kind !== 'running') throw new Error('invalid transition to failed');
      return { ...state, kind: 'failed', reason: event.reason };
    case 'retry':
      if (state.kind !== 'failed') throw new Error('invalid transition to queued');
      if (state.attempt >= 3) throw new Error('retry budget exhausted');
      return { id: state.id, attempt: state.attempt, kind: 'queued' };
    case 'cancel': return { id: state.id, attempt: state.attempt, kind: 'cancelled', reason: event.reason };
    default: return assertNever(event);
  }
}
function replay(state: State, events: readonly Event[]): State { return events.reduce(transition, state); }

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const started = transition(initial(), { type: 'start' });
    const completed = transition(started, { type: 'complete', value: 7 });
    assert.deepEqual(completed, { id: 'A', attempt: 1, kind: 'succeeded', value: 7 });
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: succeeded with attempt 1 and value 7.

Example B: Reject a result arriving before start#

An unexpected event is visible rather than silently ignored. Ignoring it could hide ordering or duplicate-delivery defects in an outer integration.

import { strict as assert } from 'node:assert';

type Base = { readonly id: string; readonly attempt: number };
type State = Base & ({ readonly kind: 'queued' } | { readonly kind: 'running' } | { readonly kind: 'succeeded'; readonly value: number } | { readonly kind: 'failed'; readonly reason: string } | { readonly kind: 'cancelled'; readonly reason: string });
type Event = { type: 'start' } | { type: 'complete'; value: number } | { type: 'fail'; reason: string } | { type: 'retry' } | { type: 'cancel'; reason: string };
function initial(): State { return { id: 'A', attempt: 0, kind: 'queued' }; }
function assertNever(value: never): never { throw new Error('unknown event: ' + JSON.stringify(value)); }
function transition(state: State, event: Event): State {
  if (state.kind === 'succeeded' || state.kind === 'cancelled') throw new Error('terminal state');
  switch (event.type) {
    case 'start':
      if (state.kind !== 'queued') throw new Error('invalid transition to running');
      return { id: state.id, attempt: state.attempt + 1, kind: 'running' };
    case 'complete':
      if (state.kind !== 'running') throw new Error('invalid transition to succeeded');
      if (!Number.isFinite(event.value)) throw new RangeError('finite result required');
      return { ...state, kind: 'succeeded', value: event.value };
    case 'fail':
      if (state.kind !== 'running') throw new Error('invalid transition to failed');
      return { ...state, kind: 'failed', reason: event.reason };
    case 'retry':
      if (state.kind !== 'failed') throw new Error('invalid transition to queued');
      if (state.attempt >= 3) throw new Error('retry budget exhausted');
      return { id: state.id, attempt: state.attempt, kind: 'queued' };
    case 'cancel': return { id: state.id, attempt: state.attempt, kind: 'cancelled', reason: event.reason };
    default: return assertNever(event);
  }
}
function replay(state: State, events: readonly Event[]): State { return events.reduce(transition, state); }

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const queued = initial();
    assert.throws(() => transition(queued, { type: 'complete', value: 7 }), /invalid transition/u);
    assert.deepEqual(queued, { id: 'A', attempt: 0, kind: 'queued' });
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: invalid transition error; original remains queued.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

Exercises#

  1. Complete one valid job lifecycle. Start a queued job and complete it with value 7. Expected: succeeded with attempt 1 and value 7. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Reject a result arriving before start. Send complete directly to queued. Expected: invalid transition error; original remains queued. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Enforce the retry budget. Fail three started attempts and try to retry once more. Expected: attempt 3 remains failed; further retry rejects. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Keep cancellation terminal. Cancel a running job, then deliver a late completion. Expected: cancelled state remains; late completion rejects. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Replay deterministically from the same history. Replay start, failure, retry, start and completion twice. Expected: both runs produce the same succeeded attempt-2 state. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Preserve input state and validate success values. Compare input before and after a transition, then reject NaN as a result. Expected: input unchanged; new object returned; NaN rejects. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
