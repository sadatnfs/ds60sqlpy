# dme-028: Catalogs, discovery, ownership and access decisions

## Discovery is a decision boundary

A catalog helps people and applications find datasets and understand their meaning. It may record names, schemas, owners, descriptions, versions, locations, lineage and access information. Some catalogs also participate directly in table commits; others primarily support search and governance. These roles should be distinguished. A searchable entry saying “approved” does not by itself enforce storage access, and a metastore entry does not necessarily explain who is accountable for a business definition.

The local example uses an actual DuckDB database to store dataset metadata. It has one dataset named `deliveries`, owned by the synthetic `data-team`, with separately registered versions and one accepted-version pointer. It also contains a small application policy mapping roles to resource actions. The program exercises these checks directly, but it does not configure DuckDB database roles, authenticate a real user or enforce cloud IAM. A caller who bypasses the application and accesses the underlying database is outside this policy boundary.

That limitation is central to the lesson. Catalog policy is useful only when the relevant access path actually checks it. A production design must connect identity, authorization, storage and query execution. Merely hiding a dataset in a UI does not stop someone with direct object-store credentials from reading its files. Conversely, granting storage access does not establish that the data are approved for a particular training or reporting purpose.

## Separate registration, acceptance and resolution

Registration records a candidate dataset version. Acceptance identifies the version that passed the maintained consumer contract. Resolution returns the currently accepted metadata to an authorized consumer. A new version can be registered without immediately replacing the accepted one. This permits validation, review and compatibility checks before consumers observe it.

The maintained contract declares delivery ID grain, package units and required fields. A candidate may add a field such as region, but it may not silently change package counts into kilograms or remove required identity fields. The resolver returns dataset name, owner, accepted version, contract and a declared artifact digest. The digest in this fixture is metadata, not proof that an artifact was opened and verified. The previous chapter demonstrates actual file readback; a real catalog-backed reader needs both layers.

An authorization decision can be represented as

\[
\operatorname{allow}(p,r,a,c),
\]

where \(p\) is a principal, \(r\) a resource, \(a\) an action and \(c\) relevant context such as purpose or environment. This fixture simplifies the principal to a supplied role and checks dataset plus action. It intentionally does not pretend that a caller-provided role string is authentication. In a real service, a trusted identity layer must establish the principal before policy evaluation.

## Worked case 1: a candidate does not become current by existing

`example_one()` registers version 1 under the package-count contract and activates it through the curator role. An analyst resolves version 1. The program then registers version 2 with an additive region field and a different declared artifact digest. Before activation, the analyst still resolves version 1. This proves that discovery of a candidate and acceptance for consumers are separate state transitions.

The curator activates version 2 while declaring that version 1 is the expected current version. The transaction compares that expectation with the catalog's actual state, checks the candidate's contract and moves the accepted pointer. A later analyst resolution returns version 2 and retains the dataset owner. The owner is not the same thing as a particular runtime credential; it identifies accountability for the product's definition and operation.

The example is intentionally explicit about the artifact digest. It uses a synthetic 64-character declaration so the catalog shape is visible without pretending to have performed a storage read. A real consumer must resolve the metadata, fetch the exact artifact or manifest through an authorized path, verify its integrity and apply the declared schema. Catalog resolution is one step in that chain, not a substitute for all of it.

## Worked case 2: reject unauthorized, stale and incompatible activation

The second case registers a candidate that changes the units from packages to kilograms. It attempts activation through three different failure conditions. An analyst lacks publish permission. A curator with the wrong expected current version has a stale view of the catalog. A curator with the correct current version still cannot activate the incompatible unit change. Each failure leaves the accepted version at 1.

The case also tries to resolve the dataset through an unapproved trainer role. That read is denied by the synthetic application policy. Permission to use data for one activity should not be assumed to grant every other activity. The program's role names are only teaching fixtures, but the separation encourages an engineering design that asks what resource and action were actually authorized.

These failures should remain distinguishable in operational evidence. An authorization denial may require a policy review. A stale version may require rereading and replanning. A unit mismatch requires a semantic migration or a differently named product. Treating every rejection as a generic retryable database error can create noisy loops or bypass pressure while failing to solve the underlying issue.

## Complete worked program

Use data-engineering. The catalog is an actual in-memory DuckDB database with parameterized queries and transactions. It is discarded after each case and does not connect to a remote metastore or identity service.

## Metadata quality and organizational ownership

A useful catalog entry explains the row grain, refresh cadence, expected availability, known limitations, source lineage and contact or ownership role. A schema listing column names is not enough to decide whether a dataset is suitable for an experiment or model. A field named `revenue` might mean booked revenue, collected cash, net revenue or a forecast. A catalog can make that ambiguity visible, but people still need a maintained definition and a change process.

Ownership also includes operational duties: responding to quality incidents, approving incompatible changes, maintaining retention policy and identifying consumers before retirement. An owner field that points to an abandoned team does not provide a functioning escalation path. Use durable team or service ownership where appropriate and keep it reviewed. Avoid embedding private personal details in a public teaching repository; the fixture uses only synthetic roles.

Data classification and policy can evolve independently of the physical schema. A newly discovered sensitive field may require restricted access even if its type did not change. An approved data source may become unavailable or unsuitable for a new purpose. Treat catalog updates as reviewed changes with provenance and auditable decisions, not only as text edits in a search interface.

## Integration boundaries and failure diagnosis

If a consumer resolves the wrong version, inspect whether it reads the accepted pointer or simply chooses the largest registered version. If a stale publisher overwrites a newer decision, inspect whether the expected-version comparison and update occur atomically. If an unauthorized user reads files despite a catalog denial, inspect the direct storage path and credential scope. The application policy may be correct while the overall access design is incomplete.

If a candidate passes a structural schema check but changes meaning, inspect units, grain and definitions. If a catalog entry points to corrupted bytes, verify the artifact rather than assuming metadata registration certified it. If metadata becomes unavailable, decide whether consumers may use a previously pinned accepted version and for how long. A cache can improve availability but must not silently ignore revocation or incompatible policy changes.

## Applications and answered interview discussion

Catalogs matter when teams share analytical tables, features, training snapshots and governed exports. They help reduce duplicated discovery work and make dependencies explicit. They also create a natural review point for dataset retirement and compatibility changes, provided actual consumers use the maintained resolution contract.

An interviewer may ask, “Is a catalog an authorization system?” Explain that some products integrate enforcement, but metadata visibility, application checks and underlying storage permissions are distinct boundaries. If asked how a consumer should choose a version, describe explicit acceptance and pinning rather than “latest registered.” If asked what belongs in a data contract, include grain, units, nullability, completeness, availability and ownership alongside field types.

For an answered extension, a kilogram-based product may be legitimate, but it should not replace a package-count contract under the same interpretation. Introduce a reviewed new contract and coordinate consumers, or publish it as a separate product. Compatibility is about what the consumer can safely infer, not whether both quantities fit in a numeric column.
