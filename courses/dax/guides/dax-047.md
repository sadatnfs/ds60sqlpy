## The question and the mechanism

Predict whether a UDF receives a precomputed value or an expression evaluated under its own modifier.

A value parameter is evaluated before the function body uses it. An expression parameter can defer evaluation into the function body, where a changed filter context can matter. This resembles the variable-versus-measure distinction, but it is now an explicit part of the function's parameter contract.

Course.BlueValue receives a numeric scalar by VAL and then places that scalar inside a Blue CALCULATE. With no incoming filters, the scalar is already 187, so it remains 187. Course.BlueExpression receives the expression by EXPR and evaluates it under the Blue modifier, producing 163. The function body looks similar, but the parameter mode changes its semantics.

Under an incoming Red selection, the eager value is 24 while the deferred expression still becomes 163 because the function's Blue filter replaces the same Color column. This is a context-transforming API, so its name and documentation should disclose that behavior. Reference parameters have their own required expression-mode rules; do not assume every type can use every passing mode.

## Vocabulary and expression anatomy

The signatures explicitly say SCALAR NUMERIC VAL or SCALAR NUMERIC EXPR. The source passes [NetRevenue] in both calls. The body uses CALCULATE(amount,Product[Color]="Blue"). Microsoft's current documentation distinguishes the row/filter-context inheritance of eager and deferred arguments; these cases use filter context only and do not generalize to an arbitrary caller's row context.

Concepts to explain in your own words: **VAL**, **EXPR**, **eager evaluation**, **deferred evaluation**, **filter context**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

### Feature and version boundary

Microsoft's DAX UDF documentation, reviewed on 2026-10-25, states general availability in Power BI Desktop and Service from June 2026 and database compatibility level 1702 or higher. These offline definitions are not engine-tested here. UDF availability is distinct from calendar-based time intelligence's preview status.

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
    MEASURE Sales[QuantitySold] = SUM ( Sales[Quantity] )
    MEASURE Sales[GrossRevenue] = SUMX ( Sales, Sales[Quantity] * Sales[UnitPrice] )
    MEASURE Sales[OrderCount] = DISTINCTCOUNT ( Sales[OrderID] )
    FUNCTION Course.BlueValue = ( amount : SCALAR NUMERIC VAL ) =>
        CALCULATE ( amount, Product[Color] = "Blue" )
    FUNCTION Course.BlueExpression = ( amount : SCALAR NUMERIC EXPR ) =>
        CALCULATE ( amount, Product[Color] = "Blue" )
```

### Case A: Unfiltered caller

**Starting context:** No incoming filter; both calls receive the same written measure argument with different parameter modes.

```dax
EVALUATE ROW ( "EagerValue", Course.BlueValue ( [NetRevenue] ), "DeferredExpression", Course.BlueExpression ( [NetRevenue] ) )
```

**Context trace:**

1. VAL evaluates [NetRevenue] before the body and passes 187.
2. Changing color around that scalar cannot recreate its original expression.
3. EXPR evaluates the measure under Blue and returns 163.

**Hand-derived worked-reference result:**

| EagerValue | DeferredExpression |
| --- | --- |
| 187 | 163 |

Parameter annotations change observable behavior. They are not merely documentation for an otherwise identical function.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Red caller and a Blue-transforming function

**Starting context:** Incoming Color=Red; the function body requests Color=Blue.

```dax
EVALUATE CALCULATETABLE ( ROW ( "EagerValue", Course.BlueValue ( [NetRevenue] ), "DeferredExpression", Course.BlueExpression ( [NetRevenue] ) ), Product[Color] = "Red" )
```

**Context trace:**

1. The eager argument is evaluated in Red and becomes 24.
2. The deferred argument is evaluated after the body's Color replacement.
3. Its Blue result is 163, not a Red-and-Blue intersection.

**Hand-derived worked-reference result:**

| EagerValue | DeferredExpression |
| --- | --- |
| 24 | 163 |

A function intended to stay inside the caller's population would need a different filter policy, such as an appropriate intersection, plus its own tests.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. The value is computed before entering the function.
2. Apply the selection policy after distinguishing parameter modes.
3. Name the column modified and the argument mode.
4. The same written call can now evaluate in a different context.
5. The current cases intentionally use filter context only.
6. A precomputed value cannot be shifted to another period after the fact.
