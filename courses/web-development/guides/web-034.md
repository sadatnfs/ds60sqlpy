# web-034: Conditions, loops and bounded control flow

## Level and prerequisites

Beginner; allow about 90 minutes, with extra time for independent practice. Direct prerequisites: `web-033`

## Learning objectives

Build a bounded weekly-duration summary with a route label. Explain match versus switch for a typed mapping. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

Control flow determines which statements execute and how often. A branch chooses among alternatives, while a loop repeats a body for a sequence or condition. A loop needs a termination argument: a bounded collection, an advancing counter or another condition that is guaranteed to change. The classroom enforces execution limits, but a good program should still have its own understandable bound.

Guard clauses reject invalid conditions before the main computation. They reduce nesting and make accepted input clearer. A match expression compares strictly and returns a value; it differs from a switch statement's traditional loose comparison behavior and fall-through possibilities. Use the construct whose semantics fit the task rather than choosing the shortest spelling.

## Syntax anatomy and mechanism

A foreach loop visits array values and can also expose keys. A for loop makes initialization, condition and update explicit. In a match expression, each arm maps a condition to a result, and a default arm handles other values when that is appropriate. Do not silently map invalid input to a valid default if the contract requires rejection.

## Classroom execution and offline inputs

Choose the **PHP CLI** worker in the classroom. The pad is staged as `main.php` and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write `<?php` at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

## Worked example / walkthrough

### Worked example 1: A bounded accumulation

The loop visits a finite array once.

```php
$total = 0;
foreach ([20, 30, 15] as $minutes) { $total += $minutes; }
```

**Expected observation:** The total becomes 65.

### Worked example 2: A deliberate mapping

Strict matching preserves the distinction between labels.

```php
$label = match ('beginner') { 'beginner' => 'Start here', 'advanced' => 'Project work', default => 'Review route' };
```

**Expected observation:** The result is Start here.

## Six progressive exercises

### Exercise 1: Trace the accumulator after each iteration.

**Expected evidence:** It progresses through 20, 50 and 65.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add a guard against negative durations.

**Expected evidence:** Invalid values fail before they enter the total.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a bounded weekly-duration summary with a route label.

**Expected evidence:** The total and label follow the declared cases and terminate predictably.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a while loop whose condition never changes.

**Expected evidence:** Identify the missing progress step and replace it with a bounded iteration where possible.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test an empty collection.

**Expected evidence:** The total is zero without a special invalid array access.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain match versus switch for a typed mapping.

**Expected evidence:** Match returns a value and compares strictly; switch has different comparison and fall-through rules.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not rely on a worker timeout as the algorithm's termination strategy. Avoid changing the collection unexpectedly while iterating. A default arm should not conceal an unknown state that needs an error.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain branch, loop, guard clause without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
