Track qualification#

Every language and subject track is reviewed against one shared rubric (CURR-06) and carries an honest runtime capability ledger (CURR-05). The results live in curriculum/track-qualification.json, which is curated by hand and is the authoritative record. docs/implementation/runtime-reference-evidence.json is a historical record of earlier local runs and is not consulted by these checks.

The ledger records judgments only. Every measured value is recomputed by scripts/check_track_qualification.py from curriculum/coverage-matrix.json, the runtime profile registry (scripts/check_module_references.py) and the CI profile groups (scripts/ci_profiles.py), so a record cannot claim more than the sources support.

Thresholds behind the measured gap codes are the matrix thresholds documented in docs/coverage-matrix.md (guide 1050 words, 2 examples, 3 terms, 6 exercises, solution 700 words). R8 compares the track's current templated_words total with its templated_baseline, the per-track sum at commit b1847ca7e6f36bc851f39daa8e98a96770d371dc (the first commit carrying the metric, catalog total 835280). Each record cites that source in templated_baseline_source. The baseline is a ceiling, not a target: R8 stops a track from adding boilerplate but does not prove the remaining templated prose is gone.

Statuses#

  • pass: the criterion is met. For R1 to R7 the matrix must measure zero rows.
  • na: the criterion does not apply, only where the table allows it, never while the matrix measures rows for it, and always with a justification.
  • accepted-gap: a known shortfall accepted for this track. Allowed only on R1 to R7. The record lists the exact lesson IDs; the check recomputes them from the matrix and requires the lists to be equal.
  • gap: open work. It carries a justification and no lesson list, because the matrix itself is the open queue and a stored list would go stale while content changes. A gap stays consistent when the measured rows shrink; the closure plan recomputes it.
  • not-assessed: allowed only on R11.

Every status other than pass needs a justification of at least 40 characters. No string in the ledger may contain an em dash or an en dash.

Threshold#

A track meets its threshold when every criterion is pass, a justified na, or a justified accepted-gap within the cap, and R11 may also be a justified not-assessed. R1, R2 and R10 must be pass; they accept no gaps. The cap is 10 percent of the track's lessons, checked with integers: len(lessons) * 10 <= track_rows. Accepted gaps always name exact lesson IDs.

tests/test_track_qualification.py::test_every_track_meets_threshold checks this for each track as a plain test with no expected-failure marks. All 40 tracks meet the threshold; a track that falls below it fails the test.

Human review#

R11 is never recorded as pass without a named reviewer and a date. Until a person has read the track for clarity, the honest status is not-assessed with a justification that says so.

Runtime capability ledger#

Each record has a runtime block:

  • profiles: exactly the runtime profiles the matrix lists for the track. Each profile has a route derived from the registry and the narrowest result label that route can claim. Ordinary profiles also name their CI group.
  • unavailable: every profile outside the ordinary worker set (except core lessons), with the reason registered in EXTERNAL_REASONS, word for word.
  • guide_examples: what checks the guide code. Guide code blocks are not executed in this phase; content rendering checks cover them. Track notes name the extra checks that do exist (C++ expected outputs, JavaScript syntax checks, statistics fence parity).
  • walkthrough_outputs_checked: true exactly when the track uses at least one ordinary CI group and a recorded CI run qualified every one of them. Tracks with no ordinary group (core python, sql and bridge, dax, cuda, docker, kubernetes and spark-deployment) record false and carry no evidence.
  • evidence: present exactly when walkthrough_outputs_checked is true. It holds ci_run (the app-build.yml run database ID), commit (that run's full head SHA) and groups (the ordinary CI groups the track uses, all of which concluded success in their job and Qualify complete references step).

Live tracing is limited to the core Python and SQL lessons. No universal automatic tracer exists, and no record, label or document may claim one. An authored track records a floor equal to the number of stages that contain an ordinary-profile lesson (3 today). R9 pass on an authored track requires courses/<track>/walkthroughs.json to cover each of those stages.

Recording CI evidence#

scripts/record_track_runtime_evidence.py --run RUN reads one app-build.yml run and records runtime.evidence, walkthrough_outputs_checked: true and an R10 pass for every track whose ordinary CI groups all succeeded. The run's commit must be available locally, and the course content and reference checker in the working tree must equal that commit. --dry-run prints the plan and writes nothing.

Every recorded track cites run 45399494825 at commit 0770e8fd4c58030c20d8267ed3820eb630d1442f. The 2.0.0 release commit (a4354ff8bf50bd2ea48d7eff2c130b75fb34dcc6) later changed runtime files (Spark 4.3.0, torch 2.15.0, Debian 13 Python). Its app-build.yml run skipped the ordinary qualification jobs because the commit was marked for publication, so the recorder has no newer run to read. The same references, walkthrough expected outputs included, were qualified on amd64 and arm64 by the release publish run 45460757558 before any image was promoted. The recorder does not read publish runs, so that run is not cited in the ledger.

Running the checks#

.venv/bin/python scripts/check_track_qualification.py --track go
.venv/bin/python scripts/check_track_qualification.py --check

--track prints each criterion with its measured count, the runtime ledger, any consistency errors and the reasons the track is below threshold. --check validates every record and exits 1 on any inconsistency. Neither mode writes files. After content changes, regenerate the matrix through its owning workflow, then run --check and edit the affected records by hand.
