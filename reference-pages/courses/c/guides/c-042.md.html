c-042: Capstone: a validated data pipeline with explicit ownership#

Level and prerequisites#

Advanced, approximately 120 minutes plus a later retrieval session. Direct prerequisites: c-041

Learning objectives#

Explain data contract, batch atomicity, operational evidence. Implement the six investigations with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

Purpose and mental model#

The capstone combines parsing, range checks, bounded storage, deterministic aggregation and failure-atomic output. A production C component is understandable when each boundary states its grammar, ownership, resource limit and failure behavior. This fixture accepts a narrow line format name,count with one comma, a short nonempty ASCII name and a nonnegative decimal count. It deliberately rejects quoting and multiline fields rather than pretending to implement full CSV. A real general-purpose CSV reader needs the richer format contract. The pipeline validates every record before committing its summary, so one malformed record cannot publish a partial total as if the batch completed.

Vocabulary and concepts#

  • Data contract: The grammar, ranges and meaning required at a data boundary.
  • Batch atomicity: Publishing a summary only after all required records are accepted.
  • Operational evidence: Source-bound diagnostics and results explaining what actually completed.

Syntax anatomy and execution trace#

parse_record separates a bounded name from a complete decimal value using strtol and an end pointer. summarize stages row count and total, checks addition before updating, and commits only when every row is valid. The output remains unchanged on failure. The separately prepared stats project illustrates headers and tests; this capstone keeps its full deterministic data path within the ordinary one-file pad.

A false check terminates with a nonzero result; a passing check produces no output. Unlike the standard assert macro, this helper is not removed by NDEBUG. Worked example / walkthrough#

Worked example 1: Summarize valid records#

Process alpha,3 and beta,4.

#include <assert.h>
#include <errno.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

struct Summary {
  size_t rows;
  unsigned total;
};
bool parse_record(const char *line, unsigned *out) {
  if (line == NULL || out == NULL)
    return false;
  const char *comma = strchr(line, ',');
  if (comma == NULL || comma == line || (size_t)(comma - line) > 15 ||
      strchr(comma + 1, ',') != NULL)
    return false;
  for (const char *p = line; p < comma; p++)
    if (!((*p >= 'a' && *p <= 'z') || (*p >= 'A' && *p <= 'Z')))
      return false;
  if (comma[1] < '0' || comma[1] > '9')
    return false;
  errno = 0;
  char *end = NULL;
  unsigned long value = strtoul(comma + 1, &end, 10);
  if (errno == ERANGE || *end != '\0' || value > UINT_MAX)
    return false;
  *out = (unsigned)value;
  return true;
}
bool summarize(const char *const *rows, size_t count, struct Summary *out) {
  if (out == NULL || (count > 0 && rows == NULL) || count > 100)
    return false;
  struct Summary staged = {0};
  for (size_t i = 0; i < count; i++) {
    unsigned value = 0;
    if (!parse_record(rows[i], &value) || value > UINT_MAX - staged.total)
      return false;
    staged.total += value;
    staged.rows++;
  }
  *out = staged;
  return true;
}

int main(void) {
  /* Summarize valid records */
  {
    const char *rows[] = {"alpha,3", "beta,4"};
    struct Summary out = {0};
    CHECK(summarize(rows, 2, &out) && out.rows == 2 && out.total == 7);
  }
  puts("Worked example checks passed.");
  return 0;
}

Observe: Two rows produce total 7.

The total represents the complete accepted batch, not merely a successful prefix.

Observe: The batch fails and the previous summary remains unchanged.

Staging prevents a partial total from masquerading as a successful batch result.

Prediction before execution#

Trace each object from initialization through its last valid use. Write down the size of every array, the capacity of every output buffer and the ownership of any allocated storage. Distinguish a compiler diagnostic from a valid runtime rejection and from undefined behavior. Never execute an out-of-bounds access, dangling-pointer read or data race simply to discover what value it happens to print.

Common pitfalls and diagnosis#

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
