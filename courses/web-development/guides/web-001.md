# web-001: A web page: source, browser and server

## Level and prerequisites

Beginner; allow about 90 minutes, with extra time for independent practice. Direct prerequisites: None. This lesson explains the necessary vocabulary.

## Learning objectives

Build a complete document with a title, one heading and two paragraphs. Trace a requested page from source to visible output. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

HTML is a markup language: it names the structure and meaning of a document. CSS is a style language that controls how that structure is presented. JavaScript is a programming language executed by the browser or another host. PHP is a programming language commonly executed by a server. A visitor receives the server's response, not the PHP source that generated it. These layers can cooperate without becoming interchangeable.

A browser parses HTML into a document tree, applies style rules and paints pixels. A server accepts a request and returns a response. Opening a local preview exercises the browser portion; it does not demonstrate a network request, authentication or a server database. Our first document is deliberately small enough to inspect every character and every visible element.

## Syntax anatomy and mechanism

An element such as `<p>Hello</p>` has an opening tag, content and a closing tag. The tag names the kind of content. A document begins with `<!doctype html>` to request standards rendering, then an `html` root containing `head` metadata and `body` visible content. The `title` labels the browser document, while an `h1` labels the visible topic. Whitespace in ordinary text is generally collapsed, so source indentation helps humans without creating layout.

## Classroom execution and offline inputs

Choose **HTML browser preview** in the classroom. The pad is one complete HTML document with embedded CSS and, where taught, embedded JavaScript. Its preview is isolated from the classroom and recreated on each run. It does not contact a server, submit real forms, read cookies, fetch assets or load a CDN. All fixtures are inline and synthetic. The browser uses its native HTML parser, so classic-script ordering, shared lexical bindings, inline modules and real DOMContentLoaded/load events keep their browser semantics. External module imports remain blocked. Navigation metadata such as base and meta http-equiv is rejected explicitly. On any supported host, the browser renders the document while Docker serves the classroom. No host compiler is needed.

Run your own source after implementing the task. A reference's checks inspect only the named initial conditions. Its success message is not a full accessibility audit, proof of responsive behavior at every size, or evidence that you implemented the solution yourself. Inspect actual output after keyboard input, resizing and changes. Save your source before comparing with a reference. For visual experiments, explicitly turn on Live preview: the page refreshes after a short pause in typing, while Pause updates keeps the last rendered version and Stop preview cancels pending refreshes. Desktop, tablet and phone presets resize the same preview without rerunning it. Automatic previews do not create saved runs; choose Save observation or Run when you want to retain an exact source-and-output record. Changing lessons, opening history or reloading turns live execution off. The document and its CSS share one saved pad; HTML and CSS remain different languages within that artifact.

## Worked example / walkthrough

### Worked example 1: One paragraph

Read the tag boundaries before considering appearance.

```html
<p>Hello, web.</p>
```

**Expected observation:** One text paragraph; the angle-bracket markup is not shown.

### Worked example 2: Metadata and visible content

Both titles matter, but they occupy different places.

```html
<title>My course notes</title>
<h1>Learning the web</h1>
```

**Expected observation:** The document title and visible heading can differ.

## Six progressive exercises

### Exercise 1: Predict which text from the first example is visible.

**Expected evidence:** Only Hello, web. appears as paragraph text.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Change a paragraph without changing the document title.

**Expected evidence:** The visible body changes while the browser document title remains the same.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a complete document with a title, one heading and two paragraphs.

**Expected evidence:** The preview contains one main heading and two paragraphs in a main region.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Explain why PHP source pasted into an HTML page does not execute on a PHP server.

**Expected evidence:** A browser preview parses HTML; no PHP interpreter or server request was involved.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Remove the styling and inspect what remains useful.

**Expected evidence:** Document structure and readable text remain; meaning does not depend on CSS.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Trace a requested page from source to visible output.

**Expected evidence:** Distinguish server response bytes, parsed document tree, applied style and painted output.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not call every file a website or every successful preview a deployed server. Inspect the actual title and body separately. Closing a paragraph with the wrong tag may be repaired by the parser, producing a different tree than the source suggests.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain HTML, CSS, HTTP without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
