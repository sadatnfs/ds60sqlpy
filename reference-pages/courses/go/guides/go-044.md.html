go-044: Service accounts, RBAC and least-authority controllers#

Level and prerequisites#

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-043

Learning objectives#

By the end, explain authentication, authorization, least authority; implement the six investigations below; and defend the expected result of a changed input before running it. A passing reference is evidence about that program, not a certification of your independent understanding.

Why this mechanism matters#

Authentication establishes who is calling; authorization determines which operations that identity may perform. A ServiceAccount gives an in-cluster workload an identity, and RBAC binds subjects to rules over API groups, resources, verbs and sometimes resource names. A Role applies within a namespace; a ClusterRole can describe cluster-scoped permissions or be bound within a namespace. A RoleBinding and ClusterRoleBinding have different scopes. Avoid wildcard grants when a controller only needs a few resource operations. Read access to Secrets is sensitive even though it does not mutate objects. Network reachability and RBAC are separate gates: an allowed identity can still have a broken network path.

Vocabulary and concepts#

  • Authentication: Establishing the identity of a request.
  • Authorization: Deciding whether that identity may perform an operation.
  • Least authority: Granting only the permissions required for a task.

Syntax anatomy and reasoning#

Rules name API resource plurals such as pods, and subresources such as deployments/status. get, list and watch are different verbs. A controller updating status needs the appropriate subresource permission rather than unrestricted object replacement. The fixture checks an explicitly limited rule model; Kubernetes authorization has richer semantics and additive bindings. Validate actual access using the owned cluster and intended identity rather than a privileged developer context.

Worked example / walkthrough#

Worked example 1: Admit a required read#

Allow get on pods in the lesson namespace.

package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Rule struct {
	Namespace, Resource string
	Verbs               []string
}

func allowed(r Rule, namespace, resource, verb string) bool {
	if r.Namespace != namespace || r.Resource != resource {
		return false
	}
	for _, v := range r.Verbs {
		if v == verb {
			return true
		}
	}
	return false
}

func main() {
	// Admit a required read
	{
		rule := Rule{Namespace: "lesson", Resource: "pods", Verbs: []string{"get", "list", "watch"}}
		check(allowed(rule, "lesson", "pods", "get"), "read")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: The request is admitted by the local rule model.

The rule expresses resource and namespace scope in addition to the verb. Matching only one component would overgrant access.

Worked example 2: Reject an unneeded mutation#

Try delete against the read-only rule.

package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Rule struct {
	Namespace, Resource string
	Verbs               []string
}

func allowed(r Rule, namespace, resource, verb string) bool {
	if r.Namespace != namespace || r.Resource != resource {
		return false
	}
	for _, v := range r.Verbs {
		if v == verb {
			return true
		}
	}
	return false
}

func main() {
	// Admit a required read
	{
		rule := Rule{Namespace: "lesson", Resource: "pods", Verbs: []string{"get", "list", "watch"}}
		check(allowed(rule, "lesson", "pods", "get"), "read")
	}

	// Reject an unneeded mutation
	{
		rule := Rule{Namespace: "lesson", Resource: "pods", Verbs: []string{"get"}}
		check(!allowed(rule, "lesson", "pods", "delete"), "mutation")
	}
	fmt.Println("Worked example checks passed.")
}

Observe: The request is rejected.

A read-oriented controller should not inherit deletion authority merely for convenience.

Common pitfalls and diagnosis#

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from check identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned error is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
