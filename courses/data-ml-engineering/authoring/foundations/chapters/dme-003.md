# dme-003: Values, units, missingness and clocks

## A number is not yet a measurement

The value `1000` can mean meters, kilometers, milliseconds, an identifier or a count. A programming language can store it without knowing which interpretation is intended. Engineering contracts therefore need more than a column name and a numeric type: they need units, precision, allowed ranges, identity rules and timing assumptions.

Consider delivery distances recorded as 1.20 km, 2.30 km and one unknown value. The first two measurements sum to 3.50 km. That arithmetic is straightforward, but a useful mean requires a population choice. Are we describing the two known distances, or claiming a mean over all three deliveries? An unknown distance is not automatically zero, and a zero distance is not automatically invalid. These choices change the meaning of the result.

A **type** describes how a value is represented and what operations the program supports. An integer is suitable for an exact package count. A string can preserve a delivery identifier whose leading characters matter. A floating-point value supports efficient numerical computation but usually approximates a decimal fraction in binary. Python's `Decimal` can represent declared decimal text exactly, although division can still require rounding under a chosen arithmetic context. None of these representations makes an inaccurate physical observation accurate.

Identifiers deserve special care. If `0017` is an identifier, converting it to an integer can discard a meaningful representation. Taking the mean of delivery identifiers has no useful measurement interpretation. Conversely, storing a quantity as text can hide invalid or inconsistent formats until a later computation fails. Choose the type according to the contract, rather than treating every digit sequence as a number.

## Keep the unit attached to the field

A column named `distance_km` is more informative than a column named `value`, but a name alone is not a complete control. The producer, schema and consumer must agree on the unit. An upstream switch from kilometers to meters can preserve the numeric type while multiplying the physical interpretation by one thousand. Range checks can help detect such changes, but they cannot establish the correct unit for every plausible number.

An explicit conversion uses a known relationship:

\[
1\ \mathrm{km}=1000\ \mathrm{m}.
\]

The conversion is justified only after the input unit is known. The same issue occurs with seconds versus milliseconds, fractions versus percentages, bytes versus larger storage units, and rates per request versus rates per customer. Record the denominator as carefully as the numerator. A system can be internally consistent about its calculations while consistently using the wrong business quantity.

The example constructs decimals from strings such as `Decimal("1.20")`. This preserves the supplied decimal value. Constructing a decimal from an already rounded binary float can preserve that float's approximation instead. For machine-learning arrays, ordinary floating-point types are often appropriate; use justified tolerances when comparing numerical results. For identifiers and exact discrete counts, a tolerance would usually be the wrong repair.

## Missingness needs a policy and a reason

Python uses `None` to represent the missing value in this example. Other tools may use SQL `NULL`, floating-point NaN or a dedicated validity bitmap. These representations are not interchangeable without an explicit conversion policy. In particular, NaN is a floating-point value with special comparison behavior, while a missing field may mean that no measurement was supplied at all.

One missing marker can conceal several distinct situations: a sensor failed, a field does not apply, an observation has not arrived yet, or access to it was withheld. Later chapters preserve reason codes and availability times. For now, the program retains both the number of known values and the total number of supplied rows. This makes the denominator visible instead of silently presenting a partial collection as the full population.

Let \(K\) be the set of row positions with known distances. The mean among known values is

\[
\bar{x}_{K}=\frac{\sum_{i\in K}x_i}{|K|}.
\]

Here each \(x_i\) is measured in kilometers, and \(|K|\) counts known observations. This quantity describes the observed subset. Estimating the full-population mean would require additional assumptions or information about the missing values. If long routes are more likely to lose their readings, the known subset can differ systematically from the full collection.

## Time values also need an interpretation

A timestamp string with a UTC offset identifies an instant when its date and clock fields are valid. `2024-01-01T10:00:00+02:00` and `2024-01-01T08:00:00+00:00` describe the same instant. Their displayed clock readings differ because their offsets differ. Converting an aware timestamp to UTC changes its representation while preserving that instant.

A timestamp without an offset or timezone is **naive**. It may represent a useful local wall-clock value, but it does not by itself identify an unambiguous instant. Attaching UTC to it is an interpretation, not a demonstrated conversion. You need to know what the producer meant. A fixed offset also does not encode the full calendar rules of a regional timezone, including daylight-saving transitions and ambiguous local times.

Engineering systems additionally distinguish what the timestamp describes. Event time, receipt time, processing time and label-availability time can all differ. A valid UTC timestamp does not prove that it is the correct clock for a calculation. Chapter 014 develops that distinction; this chapter establishes how to avoid losing the basic representation and unit information first.

## Worked case 1: Equal instants and a declared observed subset

The first case parses two aware timestamps and converts one to UTC. Both compare equal as instants. The expected observation is `same_instant=True`; it does not mean their original text representations are identical or that every regional timezone has a fixed offset.

The same case keeps distances 1.20 km and 2.30 km and excludes the explicitly missing value from the known subset. The known sum is 3.50 km, the known-row count is two and the supplied-row count is three. The mean among known values is 1.75 km. Each quantity is returned separately, so a consumer can see the coverage as well as the estimate.

This is not an imputation example. No replacement value is invented. The program computes a defined quantity on observed data and exposes its denominator. A real application might require full coverage before publication, permit a partial result with a coverage label, or use a reviewed model to handle missingness. Those policies need to be chosen for the intended decision.

## Worked case 2: Guessing a timezone or a zero changes the claim

The changed case parses a timestamp with no timezone information. Instead of guessing UTC, it raises and catches an explicit contract error. The tutorial records that the naive time was rejected. In an ingestion pipeline, that record could be quarantined with its original producer metadata while the interpretation is resolved.

It also compares the known-value mean with a zero-imputed mean. Replacing the missing distance with zero changes the denominator from two to three while leaving the sum at 3.50 km:

\[
\frac{3.50}{2}=1.75,
\qquad
\frac{3.50}{3}=\frac{7}{6}\approx1.1667.
\]

These are answers to different questions. The smaller value is not a more complete observation merely because every row now contains a number. The program prints the decimal calculation as text, so its finite representation should not be confused with exact equality to the repeating fraction. The assertions check the exact known mean and the fact that the two policies differ.

## Diagnose apparently reasonable results

If two timestamps look different, compare their interpreted instants after checking the offset contract. If two timestamps look identical, do not assume that they came from the same timezone or represented the same event boundary. If arithmetic differs slightly in a numerical array, inspect the data type and numerical tolerance before rounding everything indiscriminately.

If a mean improves after missing values are replaced, inspect what changed: the values, the denominator, the selected population or all three. A missing distance could have been much larger than the known values. No calculation on the two known values can establish the missing value's physical meaning. Similarly, a text field that parses as an integer may still be an identifier rather than a quantity.

## Where this is useful

These checks belong at API boundaries, file ingestion, joins between systems, feature creation and metric reporting. They are especially valuable when two individually correct systems use different conventions. Documenting units and clocks early is usually easier than diagnosing an apparently accurate model trained on mismatched information later.

## Answered interview discussion

**Why not fill every missing numeric value with zero?** Zero is a substantive value. It may mean no activity, not an unknown measurement. The policy can change averages, rates, model behavior and which population the output describes.

**Are decimal types always better than floats?** No. Choose representation according to exactness requirements, numerical workload, storage and interoperability. Decimal arithmetic still has rounding rules, and exact arithmetic does not remove measurement error.

**Can I fix a naive timestamp by setting its timezone to UTC?** Only if UTC is the established producer interpretation. Otherwise you are inventing information. First determine the intended timezone or offset and the clock's semantic role.

**What should a metric response include?** At minimum, define its quantity, units, population/time window and denominator. When observations are missing or late, include coverage and the stated handling policy rather than only a convenient final number.
