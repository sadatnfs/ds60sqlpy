# go-030: Algorithms, benchmarks and allocation-aware design

## Level and prerequisites

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-029

## Learning objectives

Implement a binary search with correct boundaries and compare work and allocation instead of guessing performance. Along the way, explain complexity, monotone predicate, preallocation; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Performance work starts with a behavioral contract and representative input. Complexity predicts growth in work, while a benchmark measures a particular implementation and environment. A linear scan visits each item; binary search repeatedly narrows a sorted interval. Faster execution is useful only if it preserves the result and failure policy. Preallocating slice capacity can avoid growth allocations, but preallocating length creates real zero elements. Tiny timings are noisy. Separate setup from measurement, repeat a representative workload, record environment and check results outside the timing loop. A profile should answer a hypothesis about where time or allocations are spent.

## Vocabulary and concepts

- **Complexity:** How work grows with input size.
- **Monotone predicate:** A predicate changing from false to true at most once over ordered indices.
- **Preallocation:** Reserving storage before appending.

## Syntax anatomy and reasoning

sort.Search finds the first index where a monotone predicate becomes true, or n when none does. It does not sort or validate input. make([]int,0,n) reserves capacity with zero length; make([]int,n) creates n elements. Prepared project benchmarks use testing.B in _test.go files; pprof investigates CPU or allocation evidence rather than establishing a universal speed ranking.

## Worked example / walkthrough

### Worked example 1: Find a lower boundary

Find the first value at least 5 in 2, 4, 6, 8.

```go
package main

import (
	"fmt"
	"sort"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Find a lower boundary
	{
		items := []int{2, 4, 6, 8}
		i := sort.Search(len(items), func(i int) bool { return items[i] >= 5 })
		check(i == 2, "boundary")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The index is 2.

Sorting makes the predicate monotone. The same expression over unsorted input violates the algorithm precondition.

### Worked example 2: Represent no match

Search for a value at least 9 in the same data.

```go
package main

import (
	"fmt"
	"sort"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Find a lower boundary
	{
		items := []int{2, 4, 6, 8}
		i := sort.Search(len(items), func(i int) bool { return items[i] >= 5 })
		check(i == 2, "boundary")
	}

	// Represent no match
	{
		items := []int{2, 4, 6, 8}
		i := sort.Search(len(items), func(i int) bool { return items[i] >= 9 })
		check(i == len(items), "not found")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The index equals the collection length.

The sentinel is not a valid element index. Check it before indexing.

## Predict before running

Predict length and capacity after one append to make([]int,0,4), and how many times the predicate runs on an empty interval. Then predict which of two duplicates the lower boundary finds.

## Common pitfalls and diagnosis

sort.Search requires a monotone predicate over sorted data: once true, it must stay true. Searching unsorted data, or using an equality predicate, returns a plausible but wrong index. Also handle the not-found case, where the result equals len(items) and indexing it panics. In benchmarks, use representative inputs, exclude setup from timing and keep the result so the compiler cannot discard the work.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Find a lower boundary: change one input

1. Restate the expected observation: The index is 2.
2. The predicate is false for 2 and 4 and true from 6 on. Which index is first true?
3. With 5 at index 1, the first value at least 5 is now at index 1, so `i==2` fails. The search is correct; the data moved the boundary.

### Hint for investigation 2: Represent no match: debug a regression

1. Restate the expected observation: The index equals the collection length.
2. No element reaches 9. What does sort.Search return when the predicate is never true?
3. Changing 8 to 9 makes the last element qualify, so Search returns 3 and `i==len(items)` fails. Restore 8 so no element reaches 9.

### Hint for investigation 3: Separate length and capacity

1. Restate the expected observation: Length is 1, capacity is 4.
2. make sets length 0 and capacity 4. What does one append change?
3. Starting with length four would create four logical zeros before the appended value.

### Hint for investigation 4: Count linear work

1. Restate the expected observation: There are five visits and the sum is 15.
2. The loop visits each element once. How many visits, and what sum?
3. Operation counting supplies structural evidence without inventing a universal wall-clock threshold.

### Hint for investigation 5: Handle empty search

1. Restate the expected observation: Index is 0 and the predicate is never called.
2. Search over zero elements has nothing to test. How many predicate calls occur?
3. The empty interval has a valid insertion position without accessing any element.

### Hint for investigation 6: Transfer duplicate boundaries

1. Restate the expected observation: The first duplicate has index 1.
2. The predicate is true for both 3s. Which index is the first true one?
3. A lower bound is more precise than any matching index.
