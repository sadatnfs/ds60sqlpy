## Learning objectives

Balance reusable templates with comprehensible ownership and diagnostics.

## Vocabulary and concepts

Composing generic interfaces means combining type constraints, ranges and ownership rules without hiding lifetime requirements. A range parameter can be traversable without being reusable. A returned owning vector is safer for long-lived results than a view over an unknown temporary. Concepts express admissible operations; prose still defines semantics.

<!-- terms:start -->

- **input range:** a range that may support only one pass, so reading an element can consume the source.
- **single-pass algorithm:** an algorithm that visits each element once, which keeps it correct for input ranges.
- **owning return:** returning a vector with its own storage, which stays valid even when the caller passed a temporary.
- **dangling view:** a view whose underlying storage has already been destroyed.
- **semantic contract:** the meaning of an operation that a concept cannot express, so prose and tests must state it.

<!-- terms:end -->

## Syntax and mechanism

`template<std::ranges::input_range R>` allows a single-pass source. Avoid traversing it once to count and again to compute unless you require forward_range. Copying accepted values into vector<int> gives a clear owning result independent of input lifetime.

## Trace the mechanism

A generic input_range may provide only one traversal. Counting it first can consume an iterator source, leaving no elements for the real operation. The implementation therefore filters and appends in one pass. An owning vector return makes temporary input safe and avoids a borrowed view escaping its owner. Type constraints should describe the weakest capability actually needed, while the written contract explains ordering, multiplicity and lifetime.

<!-- depth:start -->
## Generic pipelines must respect traversal and ownership

An input range may support only one pass. Reading an element can advance a stream-like source irreversibly. An implementation that first counts elements and then loops again to transform them can consume the source during its preliminary scan. A vector permits repeated traversal, but testing only vectors can hide that stronger accidental requirement.

keep_positive accepts an input_range and performs one pass. For each observed value, it appends only values greater than zero to an owning output vector. The input [-1, 0, 2, 2] produces [2, 2]. Multiplicity and order are preserved among retained elements. Zero is intentionally excluded here, unlike the earlier nonnegative examples; the predicate is part of the named contract.

The owning return value is important when the caller passes a temporary vector. The function reads the input while it is alive and returns independent storage. Returning a filtered view into that temporary would require a different lifetime argument and could dangle under an unsafe design. Generic code still needs concrete ownership reasoning.

The range concept expresses traversal capability, but this small function also assumes elements can be used in the integer comparison and appended as int without violating the intended value domain. A fully general library should either constrain those operations more precisely or document the supported element type/range. Calling something generic does not mean every possible range element type is semantically appropriate.

Materialization costs memory proportional to retained values. A production pipeline with unbounded input needs an admission or output-size budget. A lazy view can avoid storing all results, but shifts lifetime and traversal obligations to the consumer. Choose that tradeoff deliberately. The complete programs establish small finite behavior and safe owning results, not an unbounded streaming system.
<!-- depth:end -->

## Worked example / walkthrough

Example 1 passes `{-1, 0, 2, 2}` to `keep_positive` and gets `{2, 2}`: zero is not positive, and duplicates survive because filtering keeps every qualifying element. Example 2 passes an empty input and gets an empty result, the boundary a generic interface must handle without a special case. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-037-example-1.cpp)

```cpp
#include <cassert>
#include <iostream>
#include <ranges>
#include <vector>

template <std::ranges::input_range R> std::vector<int> keep_positive(R &&xs) {
  std::vector<int> out;
  for (auto x : xs)
    if (x > 0)
      out.push_back(x);
  return out;
}
int main() {
  auto out = keep_positive(std::vector<int>{-1, 0, 2, 2});
  assert((out == std::vector<int>{2, 2}));
  std::cout << "cpp-037 example 1 checks passed\n";
  return 0;
}
```

## Exercises

### Exercise 1: State range requirements

Explain why one pass is sufficient for keep_positive.

**Expected result/shape:** Input-range traversal only, no size prepass.

**Verify:** Check your explanation against the function body: one `for` loop reads each element once, and nothing calls `std::ranges::size` or traverses `xs` again.

**Progressive hints:** A single-pass source cannot promise a second traversal.

### Exercise 2: Preserve multiplicity

Filter [-1, 0, 2, 2] with >0.

**Expected result/shape:** [2, 2].

**Verify:** Assert `keep_positive(std::vector<int>{-1, 0, 2, 2}) == std::vector<int>{2, 2}`, as Worked example 1 does; the duplicate 2 must appear twice.

**Progressive hints:** Generic code still needs explicit bag semantics.

### Exercise 3: Retain ownership

Call with a temporary vector and use result afterward.

**Expected result/shape:** Result remains valid and owns its elements.

**Verify:** Store `auto out = keep_positive(std::vector<int>{3, -1});` and assert `out == std::vector<int>{3}` on a later line, after the temporary is destroyed.

**Progressive hints:** An owning return separates result lifetime from input lifetime.

### Exercise 4: Repair two-pass design

Review counting an input_range then traversing it again.

**Expected result/shape:** Use one pass or require forward_range with justification.

**Verify:** Run the reviewed function on a single-pass source such as `std::views::istream<int>` over a `std::istringstream`, and confirm the second traversal sees no elements.

**Progressive hints:** Constraints must match actual operations.

### Exercise 5: Check empty input

Use an empty vector and an empty span.

**Expected result/shape:** Both yield empty vectors.

**Verify:** Assert `keep_positive(std::vector<int>{}).empty()` and `keep_positive(std::span<const int>{}).empty()`.

**Progressive hints:** Different range types share the same semantic boundary.

### Exercise 6: Transfer a projection

Filter records by their points while retaining complete records.

**Expected result/shape:** Output retains IDs, values and duplicate qualifying rows.

**Verify:** Use input with two qualifying records that have equal points, and assert the output keeps both with every field unchanged.

**Progressive hints:** A projection should not accidentally erase domain identity.

## Self-check

Why is the owned result `[2, 2]`, keeping both twos after the temporary input dies? For Example 2, explain why an empty input needs no special case in `keep_positive`.

## Common pitfalls

If a stream-like input produces no output after a counting pass, inspect whether it was consumed twice. If a returned result dangles, look for a view borrowing temporary storage. If zero unexpectedly survives, compare >0 with >=0 rather than changing the fixture. If generic inputs narrow large values into int, fix the element-type/range contract instead of relying on a permissive conversion.

## Retrieval and transfer

Close the source and redo Exercise 6: filter records by points while keeping each whole record. Explain why the generic interface should take a predicate on the record rather than on one field. Then name what changes for a very large input, where a lazy view may beat building a new vector.
