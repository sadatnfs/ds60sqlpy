# go-037: Reconciliation as an idempotent control loop

## Why this mechanism matters

A controller repeatedly compares desired and observed state and takes a bounded step toward convergence. Reconciliation is level-based: it should ask what is true now rather than assume it received every historical event. Events are hints that work may be needed, not an exactly-once command log. A successful reconcile can be a no-op when the object already satisfies intent. Repeating it should not create duplicate side effects. Separate a pure decision function from the API adapter so planning can be tested deterministically. External operations need ownership, idempotency keys and explicit handling of uncertain outcomes.

## Vocabulary and concepts

- **Reconciliation:** Repeatedly moving observed state toward desired state.
- **Idempotence:** Repeating an operation has the same intended effect as performing it once.
- **Convergence:** Approaching a stable state satisfying declared intent.

## Syntax anatomy and reasoning

Represent desired and observed state as small values, then return a typed action such as create, update or none. Avoid embedding API calls inside every conditional. The adapter performs an action, records evidence and schedules another observation. A real controller often converges over several reconciliations rather than blocking until every resource becomes ready. Status should describe observed facts, including the generation to which they apply.

## Worked example / walkthrough

### Worked example 1: Plan a missing child

Observe no child for a desired replica count of 3.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func plan(wanted int, exists bool, current int) string {
	if wanted < 0 {
		return "invalid"
	}
	if !exists {
		return "create"
	}
	if wanted != current {
		return "update"
	}
	return "none"
}

func main() {
	// Plan a missing child
	{
		check(plan(3, false, 0) == "create", "missing child")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The action is create.

The planner reports intent without performing a cluster mutation. The adapter still needs an exact owner identity.

### Worked example 2: Plan a changed child

Observe an existing child with count 2 while desired is 3.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func plan(wanted int, exists bool, current int) string {
	if wanted < 0 {
		return "invalid"
	}
	if !exists {
		return "create"
	}
	if wanted != current {
		return "update"
	}
	return "none"
}

func main() {
	// Plan a missing child
	{
		check(plan(3, false, 0) == "create", "missing child")
	}

	// Plan a changed child
	{
		check(plan(3, true, 2) == "update", "changed child")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The action is update.

The update is justified by a current difference, not by assuming a prior event was delivered once.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
