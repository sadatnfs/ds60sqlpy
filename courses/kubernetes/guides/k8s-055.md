# k8s-055: TLS termination, certificates and upstream identity

## Level and prerequisites

Advanced; about 120 minutes plus optional supervised host observations. Direct prerequisites: `k8s-054`. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

## Learning objectives

Design a no-secret TLS evidence record. Plan a two-hop trust policy. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

## Purpose, vocabulary and mental model

TLS protects a transport connection through encryption and peer authentication according to a trust model. A server certificate binds a public key to identities such as DNS names. The client must validate the requested name, certificate chain and validity conditions. Encryption without meaningful identity verification does not establish the intended server.

TLS termination means a component decrypts the client connection and may open another connection upstream. A load balancer, Ingress controller or Gateway can terminate TLS. The proxy-to-application hop then has its own protocol and trust requirements. Client-to-proxy encryption does not automatically encrypt the upstream hop.

SNI communicates the requested server name during the TLS handshake so a listener can select an appropriate certificate. HTTP Host routing occurs after a successful HTTP-capable connection. A certificate mismatch and an HTTP 404 are failures at different stages and need different diagnosis.

## Mechanism and field-by-field reasoning

Kubernetes commonly stores certificate/key material in a Secret referenced by the controller configuration. Secret base64 encoding is not encryption. Do not include a private key in a lesson fixture or print Secret data during inspection. The fixture uses no real certificate and does not request one from an external authority.

For a real owned lab, validate the hostname, listener protocol, certificate reference, controller support and upstream policy. Never teach disabling certificate verification as the normal solution to a mismatched name. A self-signed teaching certificate needs an explicitly scoped trust setup, not global trust changes.

## Trace the request or control path

```text
client DNS name -> TLS handshake/SNI -> certificate validation -> proxy
proxy -> separate upstream HTTP or TLS connection -> app response
```

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

## Worked example / walkthrough

### Worked example 1: Classify two failures

These are intentionally synthetic symptoms.

```text
TLS name mismatch: client cannot verify requested identity
HTTP404: an HTTP server responded but route/content was not found
```

**Expected observation:** The second occurs after a successful enough transport exchange to receive HTTP.

### Worked example 2: Trace two encrypted hops

Each connection has its own peer identity.

```text
browser --TLS(server name A)--> Gateway
Gateway --TLS(upstream identity B)--> app
```

**Expected observation:** Validating A does not automatically validate B.

## Diagnosis, failure boundaries and common mistakes

The controlled failure in this chapter is: Diagnose certificate mismatch separately from 404. Its distinguishing result is Identity validation versus HTTP routing/content. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
