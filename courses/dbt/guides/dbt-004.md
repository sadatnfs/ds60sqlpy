# dbt-004: Data tests and the meaning of a failed build

## Level and prerequisites

Beginner. Direct prerequisites: `dbt-002`, `dbt-003`

**Outcome:** Use data tests as explicit evidence for a declared contract.

## Question and mechanism

Data tests express conditions that a relation should satisfy. A not-null test checks presence, while a unique test checks a key candidate. They are useful safeguards, but passing them does not prove that every value is correct. A table can have unique identifiers and still use the wrong currency, time window or join.

A build can materialize a model before a test fails. That is an important operational boundary: detecting a bad result is different from preventing every consumer from seeing it. The second case deliberately creates duplicate identifiers, observes a failed test and verifies that the relation still exists. A later publication gate will use successful test artifacts to decide whether to expose a product.

Failure recovery should preserve the cause. Correct the fixture or transformation under a stated contract, rerun the required resources and inspect new results. Do not change a uniqueness test into a row-count test merely to obtain a green status. The expected key is part of the data model.

## Syntax and data contract

Model column metadata can declare data_tests such as not_null and unique. build includes selected tests in dependency order. target/run_results.json records statuses for the invocation. Check the returned success value and each relevant result; a model status success can coexist with a test status fail in the same build.

## Worked case 1: Pass two independent key conditions

The first case builds a two-row table and checks that both not-null and uniqueness tests pass. It also queries the row count directly. The program does not infer data quality solely from process exit.

**Expected evidence:** Two test results pass and the table contains two rows.

```python
import json
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def artifact(root, name):
    return json.loads((root / "target" / name).read_text())


def example_one():
    with tempfile.TemporaryDirectory() as d:
        schema = {
            "models": [
                {
                    "name": "orders",
                    "columns": [{"name": "id", "data_tests": ["not_null", "unique"]}],
                }
            ]
        }
        p = project(
            d,
            models={"orders": "select * from {{ ref('raw_orders') }}"},
            seeds={"raw_orders": "id,amount\n1,5\n2,7\n"},
            schema=schema,
        )
        invoke(p, "build")
        statuses = [r["status"] for r in artifact(p, "run_results.json")["results"]]
        assert statuses.count("pass") == 2
        assert rows(p, "select count(*) from orders") == [(2,)]
        return {"tests_passed": 2, "rows": 2}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Observe failure and repair

The duplicate fixture fails uniqueness while leaving a materialized table. The program then changes the second identifier, rebuilds and checks new success/pass statuses. The first failure remains an explicit part of the investigation.

**Expected evidence:** Duplicate data is rejected by the test; the corrected rebuild passes.

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Create a null key

Add a record with an absent identifier.

**Check:** The not-null test fails.

**Hint:** Uniqueness and presence are different conditions.


### 2. Keep duplicate payloads

Use two equal rows with the same id and amount.

**Check:** Uniqueness still fails.

**Hint:** Identical content does not make two rows one record.


### 3. Inspect failure artifacts

Find the failed test identifier in run_results.

**Check:** The artifact names the failing condition.

**Hint:** Do not inspect only the final console line.


### 4. Check materialized state

Query the bad table after the failed build.

**Check:** It still exists in this local case.

**Hint:** Tests can run after materialization.


### 5. Repair the contract

Fix the source identity and rerun the build.

**Check:** Both tests pass on new evidence.

**Hint:** Do not weaken the requirement.


### 6. Add a quantity check

Propose a test that key checks would miss.

**Check:** It checks a meaningful domain or reconciliation rule.

**Hint:** Unique rows can still have wrong totals.


## Diagnose errors and misleading results

When a build fails, distinguish compilation, model execution and test failure. Check which relations were already materialized and whether publication was blocked. Avoid treating warning severity as an automatic acceptable outcome; it should follow a reviewed policy, not a desire for successful status.

## Transfer to independent work

Use data tests as explicit evidence for a declared contract. Demonstrate a known violation, inspect the materialized state and repair the source or transformation without weakening the assertion. Carry test outcomes into the later publication decision.
