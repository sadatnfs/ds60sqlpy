# viz-004: Filters, hover identity and linked inspection

## Level and prerequisites

Intermediate. Direct prerequisites: `viz-001`, `viz-003`. JavaScript event-handler vocabulary is explained in `js-029`; the Python route uses declarative Plotly menus rather than a live Python callback server.

## Keep data identity outside display position

Eight users have IDs u0 through u7, groups A/B, a pretreatment activity value and an observed outcome. Split the records into two traces, using circles for A and squares for B. Store user ID and group in `customdata`. A point's position in a filtered trace is not its persistent identity.

Filtering is exploratory. It changes what is visible, not which users were randomized or which population a causal estimate targets. The full source table remains visible and explicitly labeled as all records. This avoids a stale table silently pretending to describe only a selected chart subset.

## Worked case: a reversible group filter

Python defines three `updatemenus` buttons using the `update` method and visibility masks [true,true], [true,false], [false,true]. These are serialized figure instructions that work in the offline renderer. No Dash application or Python event loop is required.

The JavaScript variant uses named native buttons in a labeled group and `Plotly.restyle` to apply the same masks. Their `aria-pressed` states identify the current choice. Tab moves focus and Enter or Space activates a button, without depending on an operating-system popup. Await the update promise before reporting the new visible state. `uirevision` names a stable data/view identity so appropriate user view state can survive supported updates; it does not guarantee preservation after the underlying dataset changes.

## Contrasting case: selected point identity

The browser reference can listen for `plotly_selected` and extract each point's `customdata` user ID. It deduplicates and announces those IDs in a live status region. An empty or missing event clears selection. Using `pointNumber` as a global user ID would be wrong after traces are split or reordered.

Selection describes inspected points, not an independent statistical subgroup. Repeatedly exploring filters until a favorable contrast appears consumes analysis freedom. Preserve prespecified primary analyses and label exploratory findings accordingly.

## Six progressive exercises

1. **Trace groups.** List the four IDs in group B. Expected evidence: u4,u5,u6,u7. Hint: derive identity from records, not rendered order.
2. **Implement filters.** Add All/A/B controls. Expected evidence: eight or four visible points and reversible return to All. Hint: visibility masks have one entry per trace.
3. **Preserve hover identity.** Reorder input rows and keep correct IDs in hover. Expected evidence: every coordinate still maps to its original user. Hint: move entire records together.
4. **Debug selection clearing.** Handle an empty selection without an exception or stale announcement. Expected evidence: a clear no-selection state. Hint: event data may be absent; Python readers can explain the equivalent state transition without inventing callbacks.
5. **Review keyboard and table access.** Focus a JavaScript group button with Tab and activate it with Enter or Space; read all source rows without hover. Expected evidence: visible label, focus, pressed state and status, plus eight table rows. Hint: inspect behavior, not only DOM existence.
6. **Transfer to missing groups.** Remove all B records. Expected evidence: an explicit empty B view with no fabricated points and a correct full source table. Hint: empty data is a legitimate state, not a reason to reuse old points.

## Lifecycle and evidence

The browser reference purges its owned Plotly graph when the preview leaves. A new Run is a new source-bound observation. Viewing history must not execute the old source. Python and JavaScript variants keep separate saved drafts; changing language must not overwrite one with the other.
