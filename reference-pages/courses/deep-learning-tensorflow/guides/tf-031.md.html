tf-031: Graphs, retracing and measurement#

Status: authored beta content. The manifest inventories complete teaching files; runtime readiness remains a separate, measured property.

Level and prerequisites#

Advanced; approximately 120 minutes. Direct prerequisites: tf-030. The prerequisite sequence introduces the notation used here; revisit its worked examples if an axis, probability or gradient is unfamiliar.

Learning objectives#

Separate trace/setup cost from steady-state execution and preserve equivalent results. The central investigation is concrete: Wrap the stateless tensor function f(x)=x*x+1 with tf.function; record tracing counts for repeated float32 signatures and a float64 signature, then measure warmup separately. The finish condition is For x=[1,2], both eager and graph outputs are [2,5]. Repeated equal signatures reuse a trace; changed dtype is reported separately. No universal speedup is asserted. A useful explanation connects the calculation to the reason it is needed, rather than treating a function name as a definition.

Purpose and mental model#

tf.function traces Python code into a graph specialized for input signatures. Tracing is a setup activity; graph execution is the repeated tensor computation. Repeated calls with compatible shapes and dtypes can reuse a trace, while a new dtype often requires another graph. A Python print inside the function runs during tracing, not once per tensor execution. Benchmarking the first call together with later calls mixes compilation/setup costs with steady-state work. The tiny function here is useful for checking equivalence and trace behavior, not for claiming a universal speedup. A graph can be slower for a small workload or faster after sufficient reuse.

Vocabulary and concepts#

Trace: Construction of a graph from Python execution and input signatures.

Signature: Input structure, dtype and shape constraints for graph reuse.

Warmup: Initial calls excluded from steady-state measurement.

Syntax anatomy and reasoning sequence#

Decorate a pure tensor function with tf.function. experimental_get_tracing_count reports how many concrete traces were constructed. Use tf.constant with explicit dtype and compare eager and graph outputs. Materialize .numpy() before ending a timing interval when needed to ensure the computation completed. Avoid using Python lists with changing values as an accidental signature source.

Worked example / walkthrough#

Example A: Check eager arithmetic#

The arithmetic provides a simple independent oracle. Correctness must be established before timing a graph implementation.

import numpy as np
import tensorflow as tf

x=tf.constant([1.,2.],tf.float32); eager=x*x+1
np.testing.assert_array_equal(eager.numpy(),[2,5])

Expected: output[2,5].

Example B: Compile and compare#

The first call includes graph construction. An output match establishes this fixture computation, not performance or general input compatibility.

import numpy as np
import tensorflow as tf

@tf.function
def f(value): return value*value+1
np.testing.assert_array_equal(f(x).numpy(),eager.numpy()); first=f.experimental_get_tracing_count()
assert first>=1

Expected: graph output equals eager output.

Exercises#

  1. Check eager arithmetic. Evaluate x*x+1 at float32[1,2]. Expected: output[2,5]. Verify: Save the assertion results for exercise 1, including output[2,5].
  1. Compile and compare. Wrap the same expression in tf.function and compare output. Expected: graph output equals eager output. Verify: Save the assertion results for exercise 2, including graph output equals eager output.
  1. Reuse an equal signature. Call with float32[3,4] and inspect trace count. Expected: output[10,17]; trace count unchanged. Verify: Save the assertion results for exercise 3, including output[10,17]; trace count unchanged.
  1. Change dtype deliberately. Call with float64[1,2] and inspect trace count and output dtype. Expected: float64 result[2,5]; at least one new trace. Verify: Save the assertion results for exercise 4, including float64 result[2,5]; at least one new trace.
  1. Measure only warmed calls. After warmup, time10 repeated float32 calls and materialize outputs. Expected: 10 finite outputs and nonnegative elapsed time. Verify: Save the assertion results for exercise 5, including 10 finite outputs and nonnegative elapsed time.
  1. Separate shape contracts. Create a function with a variable-length float32 vector signature; call lengths2 and3. Expected: one trace reused; outputs have lengths2 and3. Verify: Save the assertion results for exercise 6, including one trace reused; outputs have lengths2 and3.

Common pitfalls and diagnosis#

When a result disagrees, locate the first intermediate value that violates this explanation. Inspect shapes and identities before aggregates, and inspect counts before averages. Preserve the original fixture and introduce only one controlled change at a time. If an arithmetic identity passes but a data-boundary condition fails, the experiment is still invalid. If a runtime is unavailable, record the unexecuted code as unverified rather than replacing its output with the expected text. The separate explanation discusses why the tempting alternative in each case changes the result.
