dme-002: Files, paths, processes and the Linux container boundary#

Level: Beginner | Prepared runtime: python-core

Direct prerequisites: dme-001.

Outcome: Read and write owned UTF-8 files through explicit paths.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

Identify which computer and process owns the work#

A browser classroom can involve several distinct places: the browser on your host, the Linux application container, a selected worker container and the temporary directory used for one program. A file that exists in one place does not automatically exist in the others. A path printed by a Python program normally describes that program's filesystem view, not a file you can immediately open in your host's Downloads directory.

A process is a running program with its own execution state. Python is a process; it can start another process and observe that child's output and exit status. A working directory is the directory used to interpret relative paths. An environment variable is a named string supplied to a process. A filesystem path identifies a location within that process's accessible filesystem. These concepts exist independently of a particular editor or programming language.

A container packages an execution environment and applies configured isolation/resource rules. It is not a second browser window and it is not proof that every possible action is safe. This classroom runs trusted local learning code under a reviewed worker contract. It does not claim to be a public multi-tenant service for arbitrary hostile programs. It also does not mount a Docker engine socket into ordinary lesson workers.

For learners on Windows, the supported host route uses WSL 2 and a Linux-container Docker engine. macOS and Linux also run the lesson computation inside Linux containers. The host setup differs, but the program in this chapter uses the same Linux worker behavior. Do not paste a host path into a worker and assume it refers to the same file. Moving data across a boundary requires an explicit supported interface or owned project mount.

Paths are part of the input contract#

A relative path such as incoming/deliveries.json is interpreted from the current working directory. If a scheduler, test runner or container starts the process elsewhere, that same text may identify another file or no file at all. An absolute path identifies its location within the current filesystem view. It still says nothing about whether a host application can see that location.

The first example creates an owned temporary directory, creates its incoming child and writes a small JSON document. Path objects make path composition explicit: root / "incoming" / "deliveries.json" joins components without manually assembling separator characters. write_text(..., encoding="utf-8") states how characters become bytes. The non-ASCII route name café checks that the text survives this encoding choice.

The with tempfile.TemporaryDirectory() block gives the directory a bounded lifetime. Leaving the block removes it. That is appropriate for an ordinary pad demonstration, where fresh state makes repeated runs independent. It is not a persistence mechanism. The classroom separately retains submitted source and bounded run results. A complete owned project uses a documented state directory or volume when files must outlive a process or container.

A child process has three important observations#

A subprocess can produce standard output, standard error and an exit status. Standard output usually carries the normal result stream. Standard error usually carries diagnostics. Neither convention is universally enforced, so a consumer must use the program's documented contract. An exit code of zero conventionally indicates success; a nonzero code indicates a failure or another documented condition.

subprocess.run executes an argument list and waits for completion. The first list element identifies the executable. The remaining elements are separate arguments. Using sys.executable selects the current Python interpreter rather than guessing whether python or python3 points to a compatible installation. This matters when multiple interpreters are installed.

The examples do not invoke a shell. A list of arguments is not assembled as a shell command string, so filenames and program text are passed as arguments rather than being reinterpreted as shell operators. cwd explicitly selects the child's working directory. capture_output=True keeps the two streams available for inspection. text=True requests decoded text. The timeout bounds these particular tiny examples; it does not establish a universal production timeout policy.

Worked case 1: A file read with explicit ownership and location#

The first case writes a JSON document containing a route name and six packages. It then starts a real child Python process, supplies the document's complete path as a separate argument, and sets the child's working directory to the owned temporary directory. The child reads UTF-8 text, parses JSON and prints the package count.

The expected observations are an output string containing 6, an empty error stream and exit code zero. The parent also reads the original document and checks that café remains intact. These are two different checks: the child's observation verifies a real process/file interaction, while the parent check verifies the expected text value in the source file.

The absolute path does not make the file durable. The temporary directory still disappears after the example. Nor does it show that a remote worker can read the file. Both processes execute in the same prepared worker filesystem. A distributed job would need to deliver the input through an actual shared storage or transfer mechanism and verify that delivery separately.

The program uses check=True, which means a nonzero exit would raise CalledProcessError instead of being accidentally ignored. That is useful here because this case expects success. In a diagnostic case where failure is expected, it is often clearer to capture the result and inspect it explicitly, as the next example does.

Worked case 2: A process prints output and still fails#

The second child prints candidate rows: 3 to standard output, prints contract rejected to standard error and exits with status three. All three actions are real. The parent checks the exact streams and status. It then calls check_returncode() and confirms that the nonzero status raises an exception.

This case shows why a log line that looks successful is insufficient evidence. A worker may discover a problem only after producing preliminary output. A wrapper that returns only stdout can hide the diagnostic and accidentally label the run successful. A wrapper that concatenates streams without preserving the exit status can create a similarly misleading result.

The code catches the expected exception so the complete tutorial can finish and explain the failure. That is not a recommendation to catch every exception and continue production work. Here the failure is deliberately part of the test. In a real pipeline the caller must decide whether to stop, quarantine a unit of work, retry under an idempotency policy, or escalate an unknown outcome. Printing an error and returning a normal success result without documenting that decision is not recovery.

Complete worked program#

"""Actual owned file operations and child processes, without a shell or network."""

import json
import subprocess
import sys
import tempfile
from pathlib import Path


def example_one():
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        data = root / "incoming" / "deliveries.json"
        data.parent.mkdir()
        data.write_text(
            json.dumps({"route": "café", "packages": 6}, ensure_ascii=False), encoding="utf-8"
        )
        result = subprocess.run(
            [
                sys.executable,
                "-c",
                "import json,pathlib,sys; "
                "print(json.loads(pathlib.Path(sys.argv[1]).read_text("
                "encoding='utf-8'))['packages'])",
                str(data),
            ],
            cwd=root,
            capture_output=True,
            text=True,
            check=True,
            timeout=5,
        )
        assert result.stdout.strip() == "6" and result.stderr == ""
        assert json.loads(data.read_text("utf-8"))["route"] == "café"
        return {
            "absolute_path_read_from_explicit_working_directory": True,
            "child_output": result.stdout.strip(),
            "exit_code": result.returncode,
        }


def example_two():
    with tempfile.TemporaryDirectory() as directory:
        result = subprocess.run(
            [
                sys.executable,
                "-c",
                "import sys; print('candidate rows: 3'); "
                "print('contract rejected', file=sys.stderr); sys.exit(3)",
            ],
            cwd=directory,
            capture_output=True,
            text=True,
            check=False,
            timeout=5,
        )
        assert result.returncode == 3 and result.stdout.strip() == "candidate rows: 3"
        assert result.stderr.strip() == "contract rejected"
        try:
            result.check_returncode()
        except subprocess.CalledProcessError as error:
            assert error.returncode == 3
        else:
            raise AssertionError("A nonzero process must not be reported as success")
        return {
            "stdout": result.stdout.strip(),
            "stderr": result.stderr.strip(),
            "exit_code": result.returncode,
            "publishable": False,
        }


def main():
    print("Owned files and a successful child:", example_one())
    print("Output is not a success signal:", example_two())


if __name__ == "__main__":
    main()

Diagnose common path and process mistakes#

A FileNotFoundError should prompt you to inspect the exact path and working directory used by the failing process. Check whether the file exists in the worker, whether a parent directory was created and whether the source was delivered to that environment. Do not begin by weakening permissions or giving the container broad access to your host.

An encoding error is different from a missing file. Bytes must be decoded under an appropriate declared encoding. UTF-8 is a useful explicit contract, but labeling arbitrary bytes UTF-8 does not convert them correctly. A malformed JSON error means the file was found and decoded but did not satisfy the expected serialization syntax. A valid JSON document can still violate the semantic data contract from the previous chapter.

A timeout leaves another question: did the operation have a side effect before interruption? subprocess.run manages its direct child for this local example, but a remote API or independent service may have committed work before the caller stopped waiting. Later chapters distinguish confirmed failure from unknown outcome and show why request identities and reconciliation are needed before replaying an operation.

Where these mechanisms are useful#

Use explicit paths and process observations when wrapping a compiler, a data-validation command, a model-conversion tool or an existing script. A well-designed wrapper records which executable and arguments were used, preserves meaningful diagnostics and treats the exit status according to a documented contract. It should also bound input/output size and execution resources appropriately for the actual workload.

For a long-lived workshop, use the separate project instructions rather than modifying this pad to start an unbounded daemon. The project should state its source mount, writable state, published address, ownership marker and cleanup behavior. Stopping a process, removing a container and deleting its data are different operations.

Answered interview discussion#

Why might a script work in an editor but fail in a scheduler? The interpreter, working directory, environment, available files or permissions may differ. Reconstruct those inputs explicitly before assuming the code itself changed.

Should stderr always make a run fail? No. Some programs write warnings or progress there even when they succeed. Preserve the stream and interpret it with the exit status and the tool's own documented behavior.

Why avoid shell=True for a normal argument list? An unnecessary shell adds another language and parsing boundary. A direct argument list makes it clearer which bytes are program arguments. Shell features can be useful when deliberately required, but they should not be introduced by concatenating unreviewed strings.

What does this example prove about persistence? Only that two processes in one worker can exchange an owned local file during its lifetime. Durable storage across container replacement needs a different state contract and a real replacement/readback test.
