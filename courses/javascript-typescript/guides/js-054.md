# js-054: Reusable and responsive chart components

## Level and prerequisites

Intermediate; about 110 minutes plus independent practice. Direct prerequisites: `js-053`. This is the D3.js specialization within the JavaScript path. Use the original language and browser lessons whenever syntax or DOM behavior is unfamiliar.

## Learning objectives

Implement a reusable bar renderer. Plan real narrow-screen acceptance. Produce a chart whose data transformation, visual encoding and interaction can be explained and checked independently.

## Purpose, vocabulary and mental model

A reusable chart component has an explicit input, output and lifecycle. It should not depend on a hidden global dataset or append another entire chart every time a caller updates it. A useful render contract specifies data shape, dimensions, identity, empty state and cleanup.

Responsive display is not the same as recomputing every data transformation on every resize. An SVG viewBox can scale an existing coordinate system to fit a container. More complex charts may need width-dependent tick density or label layout. Decide which parts change with available space and which analytical quantities remain invariant.

The reference renders into a caller-owned group and updates a keyed join. It checks that a second render does not duplicate marks and that an empty input produces a readable message. This is a foundation for dashboards whose views share state without sharing accidental DOM mutations.

## Syntax anatomy and mechanism

Pass the container selection, data and size as arguments. Validate dimensions and records at the boundary. Compute scales from current input and update managed nodes. Keep the surrounding SVG and accessibility summary under clear ownership.

A ResizeObserver can detect actual container size, but it has a lifecycle and can trigger repeated callbacks. Disconnect it when the component is removed. The reference uses two explicit widths for deterministic acceptance; a real responsive integration should also be manually tested at narrow and wide browser sizes.

## Worked example / walkthrough

### Worked example 1: Define a small render contract

The function signature makes dependencies visible.

```javascript
function renderBars(group, rows, width){
  if(!(width>0)) throw new Error("positive width required");
  // Derive scales and reconcile only nodes owned by this component.
}
```

**Expected observation:** The caller supplies current rows and dimensions; the function does not fetch or use hidden app state.

### Worked example 2: Separate empty state from invalid geometry

An empty dataset needs no min/max domain calculation.

```javascript
if(rows.length===0){
  group.selectAll("rect").remove();
  group.selectAll("text.empty").data([null]).join("text").attr("class","empty").text("No observations");
}
```

**Expected observation:** A visible no-data message replaces stale marks.

## Debugging and common mistakes

Keep three checkpoints separate: the records after parsing, the domain and geometry after transformation, and the visible marks after rendering. A chart can look plausible while silently dropping records or assigning the wrong scale. Inspect counts, IDs, finite coordinates and meaningful expected values before adjusting colors. A missing mark may come from invalid input, a missing selection, an undefined scale result or clipping outside the viewBox.

The controlled failure for this lesson is: Diagnose duplicate SVG trees after resize. Its distinguishing evidence is The update path creates new roots rather than updating an owned tree. Preserve that failing case when repairing your program. Do not remove an assertion or broaden a scale merely to hide a wrong input. Explain whether a changed value should affect the data, an encoding, a layout or only presentation.

## Accessibility and interpretation

Give the visualization a descriptive title and a short textual summary of the main result. Keep a table or list when exact values matter. Do not encode a critical category only through color; use labels, shapes or position as appropriate. Interactive controls need keyboard operation and clear focus, and motion should respect the user's reduced-motion preference. Automated DOM checks support, but do not replace, a real keyboard and assistive-technology review.

A data scientist must also defend the statistical meaning. State the population, units, aggregation, missing-value policy and uncertainty where relevant. Synthetic points illustrate a mechanism and do not establish a real-world finding. A beautiful visualization should make a valid claim easier to inspect, not make a weak claim appear certain.
