## Text crosses several representation boundaries

The word "character" is convenient in everyday language but too imprecise for a model pipeline. A person sees rendered glyphs. Python stores a string as a sequence of Unicode code points. A file or network message encodes that sequence as bytes. A tokenizer then groups some representation into tokens and assigns vocabulary IDs. Confusing these layers can produce wrong length limits, broken round trips or mismatched model inputs before a single neural operation runs.

Start with the literal strings in Example A. The three letters in cat are three code points and three UTF-8 bytes. The four code points in café require five UTF-8 bytes because its precomposed accented letter uses two bytes. The smile symbol is one code point but four bytes. These facts explain why len(text) and len(text.encode("utf-8")) answer different questions. Neither expression is, in general, a complete algorithm for counting user-perceived characters or model tokens.

Encoding and decoding define a reversible boundary when their contract is respected. The program encodes a valid string with UTF-8, then decodes those bytes with UTF-8, recovering the exact string. The bytes are a representation of the code-point sequence, not a second linguistic interpretation of it. A tokenizer may also be reversible, but that depends on its normalization, unknown-token and special-token policies. "The output looks the same" is weaker than an exact round trip.

Example B deliberately constructs two different strings that can look alike. One contains a single precomposed é code point. The other contains e followed by a combining acute accent. Their code-point sequences and UTF-8 bytes differ. NFC normalization maps these two particular spellings to the same composed form. Once only the normalized result remains, it no longer tells us which original sequence was supplied. This is an intentional many-to-one transformation, unlike lossless encoding of the original string.

Normalization can be useful for consistent search or duplicate detection, but it must follow the task's identity policy. A data pipeline may need the raw text for provenance and a normalized form for matching. Keeping both allows us to inspect whether a transformation changed an identifier, quotation or offset. If a system cites a substring by byte offsets and another component later normalizes the text, the old offsets may no longer identify the same span. Version the transformation and define whether offsets refer to raw bytes, code points or tokenizer positions.

For language models, these distinctions affect both capacity and evaluation. A byte-based base vocabulary can represent many new spellings through byte sequences, but different text may require different numbers of tokens after merging. A fixed context budget counts model tokens, not visible words or Unicode code points. The tiny examples here do not predict token counts for an arbitrary production tokenizer; they teach the representation boundaries that make such counts meaningful. [Python's Unicode documentation](https://docs.python.org/3.12/howto/unicode.html) defines the string/encoding behavior used by these exercises.
