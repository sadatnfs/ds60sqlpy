# asm-022: Writing a Catalyst likelihood expression

Tutorial mode. Stage: advanced. Direct prerequisites: `asm-021`, `spark-026`.

## Starting point and result

A Catalyst expression must define its input contract, output type, null behavior, evaluation and child replacement. If it provides generated code, that code must implement the same function. The project's `StableSoftplus` is deliberately small enough to review completely while exercising these obligations.

## Mechanism: one function, two execution implementations

For finite z, softplus is \(\log(1+e^z)\). The equivalent stable form is

\[f(z)=\max(z,0)+\log(1+e^{-|z|}).\]

When z is positive, factoring \(e^z\) from the logarithm gives the identity; when z is negative, the original exponential is already bounded. The maximum and absolute value keep the exponential argument nonpositive. This avoids overflow for large finite positive inputs.

`UnaryExpression` supplies one child and null-propagation structure. `nullSafeEval` receives a nonnull DOUBLE and computes the formula. `doGenCode` uses `nullSafeCodeGen` to place corresponding Java arithmetic inside the engine's null-handling scaffold. `withNewChildInternal` returns a copied node with a rewritten child, allowing tree transformations to preserve the expression's identity and behavior.

The input check accepts only `DoubleType`. This avoids accidental reinterpretation of integers or decimals. The fixture focuses on finite values and null. If extending the contract to NaN and infinities, specify and test those cases explicitly. Mathematical limits and IEEE representations do not automatically agree with every rewritten arithmetic form.

## Worked case: finite extremes and the origin

At z=-1000, the stable result rounds to zero. At z=1000, it is 1000. At zero, it is log two. The probe checks these values and a null row with whole-stage generation enabled and disabled. Null must remain null, not become zero or a Java exception.

Comparing both paths is essential. A correct Scala evaluation method can coexist with a broken generated Java fragment, particularly after a type or nullability change. The probe prints generated code for inspection and actually executes the query, so the evidence goes beyond compilation alone.

## Worked case: rejection is part of correctness

The SQL literal one is INTEGER, so the function rejects it unless explicitly cast to DOUBLE. This may seem strict, but it makes the implemented domain transparent. A future coercion rule could be added deliberately, with decimal range and precision tests. Silent implicit conversion should not be inferred from the mathematical formula.

The expression is useful for a logistic objective, but the rest of that objective still needs correct labels, weights, count accounting and derivatives. A stable primitive cannot repair a duplicated partition penalty or a missing observation.

## Failure diagnosis

If only the code-generated path fails, inspect generated casts, temporary variables and null propagation. If both paths overflow at a finite positive extreme, someone probably replaced the stable expression with `log(1+exp(z))`. If an optimizer substitutes an expression with different nullability, the surrounding generated code may make invalid assumptions.

## Interview discussion

**Why not copy an internal Spark expression wholesale?** A minimal original implementation is easier to audit, attribute and maintain. Internal source is a reference for the exact API, not a license to ignore its compatibility constraints.

**Does adding a likelihood expression add autograd?** No. The node computes a value. Derivatives require separately defined rules or a differentiation engine, and global parameter updates remain an orchestration problem.

## Next step
