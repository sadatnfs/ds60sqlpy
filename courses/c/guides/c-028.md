# c-028: Headers, translation units and reproducible builds

## Level and prerequisites

Intermediate, approximately 120 minutes plus a later retrieval session. Direct prerequisites: `c-027`

## Learning objectives

Explain declaration, definition, linkage. Implement the six investigations with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

A multi-file C project separates declarations in headers from definitions in source files. Each source file is compiled independently, so a header is the shared contract the compiler uses at every call site. The linker later resolves external definitions. Defining a non-static global function in a header included by several files can create duplicate definitions. Omitting a required source object can create an unresolved symbol. Include guards prevent repeated declarations inside one translation unit, but do not fix incorrect cross-file ownership. A reproducible build records compiler mode, warnings, source dependencies and link libraries explicitly.

## Vocabulary and concepts

- **Declaration:** A statement describing a name and its type.
- **Definition:** The source that provides an object or function implementation.
- **Linkage:** The rules connecting declarations of the same entity across scopes or files.

## Syntax anatomy and execution trace

A header declares a function prototype under an include guard. One .c file defines that function, and a caller includes the header. Compile each source with -c to produce an object, then link the objects into one executable. Put libraries after the objects that reference them when the linker requires left-to-right resolution. The browser pad remains one main.c; the separate fixture demonstrates actual headers, source files, tests and a Makefile.

## Worked example / walkthrough

### Worked example 1: Call a declared API

Use the stats_sum prototype before its definition.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int stats_sum(const int *values, size_t length);
int stats_sum(const int *values, size_t length) {
  int sum = 0;
  for (size_t i = 0; i < length; i++)
    sum += values[i];
  return sum;
}

int main(void) {
  /* Call a declared API */
  {
    int values[] = {2, 4, 6};
    CHECK(stats_sum(values, 3) == 12);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** Summing 2, 4, 6 returns 12.

A compatible declaration lets the compiler validate the call independently of where the definition appears.

  /* Call a declared API */

**Observe:** The result is zero.

The interface explicitly permits this empty case and the implementation makes no pointer access.

## Prediction before execution

Trace each object from initialization through its last valid use. Write down the size of every array, the capacity of every output buffer and the ownership of any allocated storage. Distinguish a compiler diagnostic from a valid runtime rejection and from undefined behavior. Never execute an out-of-bounds access, dangling-pointer read or data race simply to discover what value it happens to print.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
