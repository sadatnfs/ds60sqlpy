k8s-063: Observability: events, logs, metrics and traces#

Level and prerequisites#

Advanced; about 120 minutes plus optional supervised host observations. Direct prerequisites: k8s-062. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

Learning objectives#

Build a correlated synthetic request packet. Plan privacy-aware observability for a teaching service. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

Purpose, vocabulary and mental model#

Observability uses system outputs to reason about internal behavior. Events describe notable Kubernetes lifecycle observations. Logs record application or component messages. Metrics summarize numeric measurements over time. Traces connect spans of a request across components. Each signal has different retention, sampling and interpretation limits.

A metric’s labels define its dimensions. High-cardinality labels such as every raw user ID or request token can create operational cost and privacy risk. Aggregation can hide a failing subgroup, while excessive detail can overwhelm the system. Choose dimensions that support the diagnostic question.

A trace ID can connect a browser request to proxy and application work when propagation is implemented. It is not a secret or authorization token, and it should not be confused with a Kubernetes resource UID. Time synchronization and sampling affect how confidently signals can be correlated.

Mechanism and field-by-field reasoning#

Begin with a named symptom and time window. Read only relevant namespace objects, bounded logs and the minimal metric dimensions needed. A Pod event about scheduling does not prove a later HTTP request’s outcome. A request latency spike can involve DNS, connection setup, queueing or handler work.

The fixture supplies synthetic event and request records to practice correlation. Actual metrics stacks and distributed tracing require separately prepared components. The lesson does not install observability operators or collect all-cluster data automatically.

Trace the request or control path#

one request identity -> proxy observation -> app observation -> data operation
resource UID/generation -> controller events
time window + bounded metrics -> compare symptoms and hypotheses

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

Diagnosis, failure boundaries and common mistakes#

The controlled failure in this chapter is: Diagnose a latency metric without assuming app CPU is the cause. Its distinguishing result is Break down DNS, connection, queueing and handler phases. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
