# go-044: Service accounts, RBAC and least-authority controllers

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-043

## Learning objectives

Derive a least-authority RBAC rule set from a controller's actual reads and writes. Along the way, explain authentication, authorization, least authority; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Authentication establishes who is calling; authorization determines which operations that identity may perform. A ServiceAccount gives an in-cluster workload an identity, and RBAC binds subjects to rules over API groups, resources, verbs and sometimes resource names. A Role applies within a namespace; a ClusterRole can describe cluster-scoped permissions or be bound within a namespace. A RoleBinding and ClusterRoleBinding have different scopes. Avoid wildcard grants when a controller only needs a few resource operations. Read access to Secrets is sensitive even though it does not mutate objects. Network reachability and RBAC are separate gates: an allowed identity can still have a broken network path.

## Vocabulary and concepts

- **Authentication:** Establishing the identity of a request.
- **Authorization:** Deciding whether that identity may perform an operation.
- **Least authority:** Granting only the permissions required for a task.

## Syntax anatomy and reasoning

Rules name API resource plurals such as pods, and subresources such as deployments/status. get, list and watch are different verbs. A controller updating status needs the appropriate subresource permission rather than unrestricted object replacement. The fixture checks an explicitly limited rule model; Kubernetes authorization has richer semantics and additive bindings. Validate actual access using the owned cluster and intended identity rather than a privileged developer context.

## Worked example / walkthrough

### Worked example 1: Admit a required read

Allow get on pods in the lesson namespace.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Rule struct {
	Namespace, Resource string
	Verbs               []string
}

func allowed(r Rule, namespace, resource, verb string) bool {
	if r.Namespace != namespace || r.Resource != resource {
		return false
	}
	for _, v := range r.Verbs {
		if v == verb {
			return true
		}
	}
	return false
}

func main() {
	// Admit a required read
	{
		rule := Rule{Namespace: "lesson", Resource: "pods", Verbs: []string{"get", "list", "watch"}}
		check(allowed(rule, "lesson", "pods", "get"), "read")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The request is admitted by the local rule model.

The rule expresses resource and namespace scope in addition to the verb. Matching only one component would overgrant access.

### Worked example 2: Reject an unneeded mutation

Try delete against the read-only rule.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Rule struct {
	Namespace, Resource string
	Verbs               []string
}

func allowed(r Rule, namespace, resource, verb string) bool {
	if r.Namespace != namespace || r.Resource != resource {
		return false
	}
	for _, v := range r.Verbs {
		if v == verb {
			return true
		}
	}
	return false
}

func main() {
	// Admit a required read
	{
		rule := Rule{Namespace: "lesson", Resource: "pods", Verbs: []string{"get", "list", "watch"}}
		check(allowed(rule, "lesson", "pods", "get"), "read")
	}

	// Reject an unneeded mutation
	{
		rule := Rule{Namespace: "lesson", Resource: "pods", Verbs: []string{"get"}}
		check(!allowed(rule, "lesson", "pods", "delete"), "mutation")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The request is rejected.

A read-oriented controller should not inherit deletion authority merely for convenience.

## Exercises

### Exercise 1: Admit a required read: change one input

Copy worked example 1, change `rule := Rule{Namespace: "lesson", Resource: "pods", Verbs: []string{"get", "list", "watch"}}` to `rule := Rule{Namespace: "lesson!", Resource: "pods", Verbs: []string{"get", "list", "watch"}}` and predict the failure before running; then restore the line.

**Expected:** The edited run panics with `read` because `allowed(rule, "lesson", "pods", "get")` no longer holds.

**Verify:** Restoring `rule := Rule{Namespace: "lesson", Resource: "pods", Verbs: []string{"get", "list", "watch"}}` makes the check pass again with the worked observation: the request is admitted by the local rule model.

### Exercise 2: Reject an unneeded mutation: diagnose an edited check

A careless edit rewrote the check in worked example 2 as `check(allowed(rule, "lesson", "pods", "delete"), "mutation")`. Explain the failure, then restore it.

**Expected:** The defective run panics with `mutation`; after restoring `check(!allowed(rule, "lesson", "pods", "delete"), "mutation")`, the request is rejected.

**Verify:** The edited check fails with message `mutation` for a state that `!allowed(rule, "lesson", "pods", "delete")` accepts.

### Exercise 3: Reject cross-namespace access

Use the lesson rule against another namespace.

**Expected:** The local model rejects it.

**Verify:** Your solution must keep `!allowed(rule, "other", "pods", "get")` true. Control: changing `check(!allowed(rule, "other", "pods", "get"), "namespace")` to `check(allowed(rule, "other", "pods", "get"), "namespace")` panics with message `namespace`; revert it.

Check a pods-only rule against secrets.

## Common pitfalls and diagnosis

Granting a controller cluster-admin, or the verb * on all resources, to make an error go away is the usual mistake; a bug or a stolen token then has unlimited reach. Grant the exact verbs, resources and namespace the code uses. Remember that list on secrets reveals their contents, watch is separate from list, and a status subresource grant does not permit spec updates.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Admit a required read: change one input

1. Restate the expected observation: The request is admitted by the local rule model.
2. Namespace, resource and verb all match. Is get listed?
3. The rule now names namespace lesson!, so a request in lesson matches nothing and the read is refused. The model is right; the grant names the wrong namespace.

### Hint for investigation 2: Reject an unneeded mutation: diagnose an edited check

1. Restate the expected observation: The request is rejected.
2. The rule lists only get. Is delete among its verbs?
3. delete is not granted, so allowed returns false and the check without negation fails. Restore `!` so the test asserts refusal.

### Hint for investigation 3: Reject cross-namespace access

1. Restate the expected observation: The local model rejects it.
2. The rule names lesson. Does it match another namespace?
3. Namespace boundaries should be explicit.

### Hint for investigation 4: Separate resource and subresource

1. Restate the expected observation: The whole-object update is rejected.
2. deployments/status and deployments are different resources. Which request matches?
3. Status reporting and desired-state mutation are different authorities.

### Hint for investigation 5: Treat secret reads as authority

1. Restate the expected observation: Secret read access is rejected.
2. The rule covers pods only. Does secrets match it?
3. Read-only does not mean harmless.

### Hint for investigation 6: Transfer verb distinction

1. Restate the expected observation: Only list is admitted.
2. Only list is granted. Does watch match it?
3. A list request and a long-lived watch have separate permission checks.
