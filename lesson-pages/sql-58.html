Day 58: Final Capstone, Part 1: Ingestion and Data Quality#

How to run this lesson#

In ./classroom, choose PostgreSQL, open sql-58 and run it with Whole SQL lesson (psql). The learner file is rollback-only: it opens BEGIN in advanced_sql_training, sets search_path to training, public, lands three messy customer rows in a temporary staging table, cleans and validates them, upserts the good ones into customers and ends with ROLLBACK, so customers still holds its 500 fixture rows afterward. Your editable copy is .learning/sql/sql-58/lesson/workspace/sql/postgres-60day/day58_final_capstone_part1.sql in the Docker learning volume. A clean run prints BEGIN, SET, CREATE TABLE, INSERT 0 3, a three-row cleaned grid, INSERT 0 2 from the upsert, a one-row data-quality count, CREATE TABLE and INSERT 0 10 for the country map, a three-row mapping grid and ROLLBACK. Run the file as a whole: pasting the upsert on its own, outside the BEGIN, would commit customers 501 and 502 for real, and every later run would then insert nothing because ON CONFLICT (email) DO NOTHING finds them. psql stops at the first error and the open transaction dies with it. Launch and reset steps are in the classroom section of the study guide; a JupyterLab alternative is described under the contributor notebook route.

A beginner's mental model for this lesson#

Every value in a real feed arrives as text, and some of it is wrong. Day 58's learner file lands three customers whose problems are visible on sight: ' Customer 501 ' is padded, 'CUSTOMER501@EXAMPLE.COM ' is upper case with a trailing space, ' us ' is a padded lowercase country, '03-01-2025' is a date whose day and month could be read either way, and 'invalid-email' is not an address at all.

Raw staging means landing that text exactly as received, in a table whose six columns are all TEXT, so the load itself cannot fail on a bad date or broken JSON. Cleaning then happens in queries that read the staging table and leave it untouched, so a reviewer can always set ' us ' beside the US it became.

A rejection reason names why a row was not accepted. The learner file only computes two flags, email_valid and country_valid; customer 503 gets email_valid false and the upsert skips it without a word. The solution goes further and labels each staged row with one outcome such as invalid_email or accepted, so a rejected row can be explained and repaired instead of vanishing.

The upsert count is the number INSERT ... ON CONFLICT reports. The learner upsert prints INSERT 0 2: the emails of customers 501 and 502 are new, and 503 never reaches the insert because the WHERE drops it. With DO NOTHING, repeating that statement inside the same transaction would print INSERT 0 0. The solution's DO UPDATE reports 3 on every repeat instead, because an updated row counts the same as an inserted one.

Read the cleaning query in logical clause order: FROM stg_customers_raw supplies three rows, the cleaned CTE rewrites each column without changing the count, and validated adds two boolean columns. The grid statement never filters. The upsert repeats both CTEs inside a derived table v and filters only at WHERE v.email_valid AND v.country_valid. Three rows in, three rows on screen, two rows written.

Two worked SQL examples#

Both excerpts are the first two statements after SET search_path TO training, public in day58_final_capstone_part1.sql. They run inside the file's BEGIN, and the staging table is TEMP, so it would disappear at the end of the session even without the closing ROLLBACK.

Example 1#
CREATE TEMP TABLE stg_customers_raw (
  full_name TEXT,
  email TEXT,
  country TEXT,
  segment TEXT,
  created_at TEXT,
  attributes TEXT
);

How to read it: CREATE TEMP TABLE builds a session-only table. Every column, including created_at and attributes, is TEXT on purpose: a timestamptz column would interpret '03-01-2025' under the session DateStyle at load time (as 1 March 2025 in an ISO, MDY session), and a jsonb column would refuse a malformed document before anyone could record why. Typing waits for the cleaning query, where each conversion is guarded.

Expected result/shape: psql prints CREATE TABLE and no grid. Running \d stg_customers_raw right after it lists six nullable text columns with no key and no constraint, so nothing about this table can turn an input row away.

Example 2#

VALUES

  ('Customer 503', 'invalid-email', 'DE', 'silver', '2025-01-05T12:34:56Z', '{"channel":"store"}');

How to read it: The three VALUES rows are the test cases for everything after them. Row 1 has padding or case problems in its name, email, country and segment; row 2 has a NULL segment and the ambiguous date; row 3 has a well-formed ISO timestamp ending in Z but an email with no @. Each attributes string is valid JSON, so the learner's ::jsonb cast succeeds. Put 'not-json' in that column and the cast would stop the whole file.

Expected result/shape: psql prints INSERT 0 3. The cleaned grid that follows shows what those rows become in a UTC session: 501 as customer501@example.com, US, segment GOLD (trimmed but still upper case) and 2025-01-03 10:00; 502 with segment NULL and created_at 2025-01-03 00:00, because the DD-MM-YYYY branch reads '03-01-2025' as 3 January; 503 with 2025-01-05 12:34:56 and email_valid false. All three rows have country_valid true.

Learning objectives#

  • Preserve raw staged input while deriving validated, normalized fields.

Vocabulary and concepts#

  • Raw staging: an input-preserving landing area before typed transformation.
  • Rejection reason: a stable explanation for why a record was not accepted.
  • Upsert count: affected rows under the interface's defined insert/update semantics.

Worked example / walkthrough#

For each timestamp format, test a format-specific regular expression before casting. Keep raw text and parsed value together, collect explicit rejection reasons, and upsert only accepted rows inside the rollback-only transaction. Return staged, valid, invalid, and affected counts that reconcile.

Common mistakes and how to recover#

  • Lesson-specific semantic mistake: checking quality on raw text while loading cleaned text. The learner's data-quality query reads stg_customers_raw directly and reports invalid_email 2 and invalid_country 1, yet the upsert has just accepted customer 501. The raw 'CUSTOMER501@EXAMPLE.COM ' fails the regex only because of its trailing space, and upper(' us ') is ' US ', which is not in the country list. Count rejections from the same cleaned relation the load reads.
  • A date that parses to the wrong day: the learner's DD-MM-YYYY branch turns '03-01-2025' into 3 January, while a plain cast in an ISO, MDY session gives 1 March 2025. Neither raises an error, so only a declared format per source protects you.
  • One bad JSON string ends the run: the learner's COALESCE(NULLIF(trim(attributes), ''), '{}')::jsonb replaces only NULL or blank text. 'not-json' raises invalid input syntax for type json (SQLSTATE 22P02), and under ON_ERROR_STOP the transaction is gone. Test with attributes IS JSON first, as the solution does.
  • Two staged rows for one email: ON CONFLICT (email) DO UPDATE fails with ON CONFLICT DO UPDATE command cannot affect row a second time, while DO NOTHING succeeds and keeps whichever duplicate the insert reaches first. Rank the rows and send one winner per email.
  • A NULL flag that is neither accepted nor rejected: in the learner file a NULL email gives a NULL email_valid, the upsert's WHERE drops the row, and the data-quality CASE WHEN NOT (...) counts it as 0. The solution writes IS TRUE for acceptance and IS NOT TRUE for rejection, so every row lands in exactly one bucket.
  • psql stopped partway: read the first error, rerun the whole file from BEGIN, and use the failure recovery checklist for container or path problems.

Deep dive and reference#

Capstone focus#

  • Stage messy customer text without losing the raw input.
  • Normalize names, email, country, segment, timestamps, JSON, and phone.
  • Validate records, upsert accepted customers, and return a DQ summary.

How the learner script works#

The rollback-only starter creates stg_customers_raw, inserts three varied records, parses three timestamp patterns, validates email/country, upserts valid rows by unique email, reports invalid counts, and demonstrates a country map.

Practice map#

The ten numbered exercises above are the practice set. The first three are the capstone deliverables and build on each other: the parser and the phone rule feed the cleaned table that the ingestion procedure fills. Exercises 4 to 10 then read that cleaned table, or the staging table behind it, after one CALL, so build and call the procedure before attempting them. A workable order after the procedure is 6 then 4 (normalize, then rank), 7 and 9 (keep the evidence for quarantined values), 5 and 10 (count outcomes), and 8 (replay) last. The data checks quote numbers from the solution's four seed rows, so load those rows when you want to compare.

Pipeline reasoning#

  • Guard every timestamp cast with a format-specific regex; ambiguous dates need an explicit locale policy.
  • Preserve rejection reasons and raw text in a real pipeline.
  • Normalize before comparing unique email values.
  • ON CONFLICT (email) counts affected inserts/updates but does not distinguish them without additional logic.
  • The learner file defaults only NULL or blank attributes to {}; invalid text such as 'not-json' makes its ::jsonb cast fail. The solution keeps the raw string, stores NULL and sets json_valid false instead.

Schema and safety limits#

training.customers has no phone column. Validate phone in staging, but do not invent a destination. Persisting phone requires a reviewed schema migration. The sample phone regex is intentionally narrow and is not global normalization.

Keep the entire demonstration in a transaction and roll it back. A procedure is appropriate for side effects and can expose INOUT counts; a table-returning function would be a different interface.

BEGIN;
SET search_path TO training, public;

-- 1. Simulate messy incoming data (staging)
CREATE TEMP TABLE stg_customers_raw (
  full_name TEXT,
  email TEXT,
  country TEXT,
  segment TEXT,
  created_at TEXT,
  attributes TEXT
);

INSERT INTO stg_customers_raw (full_name, email, country, segment, created_at, attributes)
VALUES
  ('  Customer 501  ', 'CUSTOMER501@EXAMPLE.COM ', ' us ', ' GOLD ', '2025/01/03 10:00', '{"channel":"Web","referrer":"SEO"}'),
  ('Customer 502', 'customer-502@example.com', 'GB', NULL, '03-01-2025', '{"channel":"mobile","referrer":"email"}'),
  ('Customer 503', 'invalid-email', 'DE', 'silver', '2025-01-05T12:34:56Z', '{"channel":"store"}');

-- 2. Clean and conform the staging data into canonical types
WITH cleaned AS (
  SELECT
    trim(full_name) AS full_name,
    lower(trim(email)) AS email,
    upper(trim(country)) AS country,
    nullif (trim(segment), '') AS segment,
    (
      -- attempt to parse multiple formats
      CASE WHEN created_at ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}' THEN
        created_at::timestamptz
      WHEN created_at ~ '^[0-9]{2}-[0-9]{2}-[0-9]{4}$' THEN
        to_timestamp(created_at, 'DD-MM-YYYY')
      WHEN created_at ~ '^\d{4}/\d{2}/\d{2}' THEN
        to_timestamp(created_at, 'YYYY/MM/DD HH24:MI')
      ELSE
        NULL
      END) AS created_at,
    COALESCE(NULLIF (trim(attributes), ''), '{}')::jsonb AS attributes
  FROM
    stg_customers_raw
),
validated AS (
  SELECT
    *,
    (email ~* '^[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}$') AS email_valid,
    (country IN ('US', 'CA', 'GB', 'DE', 'FR', 'IN', 'AU', 'BR')) AS country_valid
  FROM
    cleaned
)
SELECT
  *

Clause-by-clause reading map#

Read the solution as one pipeline with three relations, each of which you can query on its own.

  • stg_customer_ingest_solution is the raw staging table: four rows, every value as text, plus an identity column source_row_number (1 to 4) so each row keeps an identity even when its email is garbage.
  • cleaned_customer_ingest_solution holds one row per staged row. The procedure truncates it and refills it from a normalized CTE that trims and lowercases email, maps USA and U S to US, lowercases segment, parses created_at with the guarded function, strips the phone to digits and tests attributes IS JSON; the outer SELECT of that INSERT adds phone_valid, email_valid and country_valid. Four rows in, four rows out: cleaning never filters.
  • The upsert reads only rows whose checks all pass, numbers each email's rows with ROW_NUMBER(), and inserts the rank-1 rows into customers.

Follow each query in logical order. Order matters most in the upsert: its WHERE removes invalid rows before the window function runs, so an invalid but newer row can never outrank a valid one, and winner_rank = 1 is applied only after ranking. The counting queries reread the cleaned table with IS NOT TRUE, so a NULL flag counts as a rejection instead of disappearing.

The three capstone deliverables are additional timestamp parsing, phone normalization/validation, and a stored procedure that cleans, validates, upserts, and returns load counts. The full transaction-safe answer is day58_solutions.sql.

-- handling, and STABLE volatility after SET LOCAL TIME ZONE 'UTC'. STABLE is
-- required because parsing timestamptz can depend on session settings.
CREATE OR REPLACE PROCEDURE ingest_customer_stage_solution (INOUT upserted_rows integer, INOUT invalid_rows integer)
LANGUAGE plpgsql
AS $procedure$

  TRUNCATE cleaned_customer_ingest_solution;

  INSERT INTO cleaned_customer_ingest_solution
  WITH normalized AS (
    SELECT source_row_number,
           trim(full_name) AS full_name,
           lower(trim(email)) AS email,
           CASE upper(trim(country))
             WHEN 'USA' THEN 'US'
             WHEN 'U S' THEN 'US'
             ELSE upper(trim(country))
           END AS country,
           lower(NULLIF(trim(segment), '')) AS segment,
           pg_temp.try_parse_customer_timestamp(created_at) AS parsed_created_at,
           regexp_replace(phone, '[^0-9]', '', 'g') AS phone_digits,
           attributes AS raw_attributes,
           CASE WHEN attributes IS JSON THEN attributes::jsonb END AS attributes,
           attributes IS JSON AS json_valid

         full_name,
         email,
         country,
         segment,
         parsed_created_at,
         phone_digits,
         phone_digits ~ '^[0-9]{10,15}$' AS phone_valid,
         email ~* '^[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}$' AS email_valid,
         country IN ('US','CA','GB','DE','FR','IN','AU','BR') AS country_valid,
         raw_attributes,
         attributes,
         json_valid
  FROM normalized;

  SELECT COUNT(*)
  INTO invalid_rows
  FROM cleaned_customer_ingest_solution
  WHERE email_valid IS NOT TRUE
     OR country_valid IS NOT TRUE
     OR phone_valid IS NOT TRUE
     OR json_valid IS NOT TRUE
     OR created_at IS NULL
     OR full_name IS NULL
     OR full_name = '';

  WITH valid_rows AS (
    SELECT *
    FROM cleaned_customer_ingest_solution
    WHERE email_valid IS TRUE
      AND country_valid IS TRUE
      AND phone_valid IS TRUE
      AND json_valid IS TRUE
      AND created_at IS NOT NULL
      AND full_name <> ''
  ), deduped AS (
    SELECT valid_rows.*,
           ROW_NUMBER() OVER (
             PARTITION BY email
             ORDER BY created_at DESC, source_row_number DESC

    FROM valid_rows

         segment,

Reasoning, safety, and limits#

  • Exact-format regex guards, round-trip formatting, and caught datetime exceptions prevent malformed strings from aborting the batch. The parser is STABLE, not IMMUTABLE, because timestamptz parsing is session-sensitive. Ambiguous dates such as 03/04/2026 still require an explicit locale policy.
  • Invalid JSON remains visible in raw_attributes, produces json_valid = false, and keeps parsed attributes as SQL NULL; it never becomes an accepted unexplained empty object.
  • Validation uses IS TRUE and rejection uses IS NOT TRUE, so an unknown Boolean cannot slip through either population.
  • Valid rows are ranked by normalized email before ON CONFLICT; this avoids PostgreSQL trying to update the same target twice in one statement. The stable source_row_number breaks equal-timestamp ties.
  • ON CONFLICT (email) makes repeat loads deterministic, but the procedure's upserted_rows counts rows affected, not inserts versus updates separately.
  • The update preserves the existing customers.created_at as the immutable first-seen/signup timestamp; profile corrections update descriptive fields.
  • The canonical training.customers table has no phone column. The solution validates phone in staging but does not discard the schema boundary by inventing a destination. Persisting phone requires a reviewed migration.
  • The phone regex is intentionally narrow; use country-aware normalization for international data.

-- Parse only the supported formats, in a declared source time zone, and turn
-- malformed-but-regex-shaped input into NULL rather than aborting the batch.
SET LOCAL TIME ZONE 'UTC';

CREATE OR REPLACE FUNCTION pg_temp.try_parse_customer_timestamp (raw_value text)
  RETURNS timestamptz
  LANGUAGE plpgsql
  -- Parsing text as timestamptz depends on session time-zone/date settings even
  -- though this lesson pins UTC above. STABLE is the honest volatility promise;
  -- IMMUTABLE would let PostgreSQL cache a value across changed settings.
  STABLE
  AS $function$
DECLARE
  parsed_value timestamptz;
BEGIN
  IF raw_value ~ '^[0-9]{4}/[0-9]{2}/[0-9]{2} [0-9]{2}:[0-9]{2}$' THEN
    parsed_value := to_timestamp(raw_value, 'FXYYYY/MM/DD HH24:MI');
    IF to_char(parsed_value AT TIME ZONE 'UTC', 'YYYY/MM/DD HH24:MI') <> raw_value THEN
      RETURN NULL;
    END IF;
  ELSIF raw_value ~ '^[0-9]{2}/[0-9]{2}/[0-9]{4} [0-9]{2}:[0-9]{2}$' THEN
    parsed_value := to_timestamp(raw_value, 'FXMM/DD/YYYY HH24:MI');
    IF to_char(parsed_value AT TIME ZONE 'UTC', 'MM/DD/YYYY HH24:MI') <> raw_value THEN
      RETURN NULL;
    END IF;
  ELSIF raw_value ~ '^[0-9]{2}-[A-Za-z]{3}-[0-9]{4} [0-9]{2}:[0-9]{2}$' THEN
    parsed_value := to_timestamp(raw_value, 'FXDD-Mon-YYYY HH24:MI');
    IF lower(to_char(parsed_value AT TIME ZONE 'UTC', 'DD-Mon-YYYY HH24:MI'))
       <> lower(raw_value) THEN
      RETURN NULL;
    END IF;
  ELSIF raw_value ~ '^[0-9]{4}-[0-9]{2}-[0-9]{2}[ T][0-9]{2}:[0-9]{2}' THEN
    parsed_value := raw_value::timestamptz;
  ELSE
    RETURN NULL;
  END IF;
  RETURN parsed_value;
EXCEPTION
  WHEN datetime_field_overflow OR invalid_datetime_format THEN
    RETURN NULL;
END
$function$

-- Exercise 2: phone text is normalized to digits and validated in staging;

CREATE OR REPLACE PROCEDURE ingest_customer_stage_solution (INOUT upserted_rows integer, INOUT invalid_rows integer)
LANGUAGE plpgsql
AS $procedure$
BEGIN
  TRUNCATE cleaned_customer_ingest_solution;

  INSERT INTO cleaned_customer_ingest_solution
  WITH normalized AS (
    SELECT source_row_number,
           trim(full_name) AS full_name,
           lower(trim(email)) AS email,
           CASE upper(trim(country))
             WHEN 'USA' THEN 'US'
             WHEN 'U S' THEN 'US'
             ELSE upper(trim(country))
           END AS country,
           lower(NULLIF(trim(segment), '')) AS segment,
           pg_temp.try_parse_customer_timestamp(created_at) AS parsed_created_at,
           regexp_replace(phone, '[^0-9]', '', 'g') AS phone_digits,
           attributes AS raw_attributes,
           CASE WHEN attributes IS JSON THEN attributes::jsonb END AS attributes,
           attributes IS JSON AS json_valid
    FROM stg_customer_ingest_solution
  )
  SELECT source_row_number,
         full_name,
         email,
         country,
         segment,
         parsed_created_at,
         phone_digits,
         phone_digits ~ '^[0-9]{10,15}$' AS phone_valid,
         email ~* '^[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}$' AS email_valid,
         country IN ('US','CA','GB','DE','FR','IN','AU','BR') AS country_valid,
         raw_attributes,
         attributes,
         json_valid
  FROM normalized;

  SELECT COUNT(*)
  INTO invalid_rows
  FROM cleaned_customer_ingest_solution
  WHERE email_valid IS NOT TRUE
     OR country_valid IS NOT TRUE
     OR phone_valid IS NOT TRUE
     OR json_valid IS NOT TRUE
     OR created_at IS NULL
     OR full_name IS NULL
     OR full_name = '';

  -- PostgreSQL cannot update the same conflict target twice in one
  -- INSERT ... ON CONFLICT statement. Rank validated normalized rows first,
  -- then send exactly one winner per email to the upsert.
  WITH valid_rows AS (
    SELECT *
    FROM cleaned_customer_ingest_solution
    WHERE email_valid IS TRUE
      AND country_valid IS TRUE
      AND phone_valid IS TRUE
      AND json_valid IS TRUE
      AND created_at IS NOT NULL
      AND full_name <> ''
  ), deduped AS (
    SELECT valid_rows.*,
           ROW_NUMBER() OVER (
             PARTITION BY email
             ORDER BY created_at DESC, source_row_number DESC
           ) AS winner_rank
    FROM valid_rows
  )
  INSERT INTO customers(full_name, email, country, created_at, segment, attributes)
  SELECT full_name,
         email,
         country,
         created_at,
         segment,
         attributes
  FROM deduped
  WHERE winner_rank = 1
  ON CONFLICT (email) DO UPDATE
  SET full_name = EXCLUDED.full_name,
      country = EXCLUDED.country,
      segment = EXCLUDED.segment,
      -- `created_at` is the immutable first-seen/signup timestamp; a replay or
      -- profile correction must not rewrite it.
      attributes = EXCLUDED.attributes;

  GET DIAGNOSTICS upserted_rows = ROW_COUNT;
END
$procedure$
;
