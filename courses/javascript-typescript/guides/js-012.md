# js-012: Promises and the event loop

## Level and prerequisites

Beginner, approximately 90 minutes. Direct prerequisites: `js-011`

## Learning objectives

Explain settlement, reaction, microtask, promise composition with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Record executor, synchronous continuation and then reaction. The final task tests observe fifo microtasks before an awaited timer.

## Purpose and mental model

A Promise records one eventual settlement: fulfillment with a value or rejection with a reason. Creating a Promise does not schedule its executor for later; the executor runs immediately. Reactions registered with then run asynchronously after the current synchronous work. This distinction explains why a log inside an executor can precede a log after construction while a then reaction follows both.

Node combines ECMAScript Promise jobs with host scheduling. This lesson proves only orderings that its setup establishes: synchronous statements finish before registered Promise reactions, and an awaited timer completes before code that follows that await. It deliberately avoids asserting a universal order between setTimeout and setImmediate, whose relative execution depends on context. Microtasks can delay other work if they continually schedule more microtasks.

Promise.all preserves input order in its result, even when operations finish in another order. Its rejection does not cancel the other operations. allSettled preserves both successes and failures when the application needs a complete outcome report. Await every owned operation or attach an intentional rejection handler. A fire-and-forget task is still running work with potential failure and cleanup responsibilities.

## Vocabulary and concepts

**Settlement:** The transition to fulfilled or rejected state.

**Reaction:** A handler scheduled after Promise settlement.

**Microtask:** A queued job processed at a microtask checkpoint.

**Promise composition:** Combining multiple eventual results under a defined failure policy.

## Syntax anatomy and execution trace

new Promise(executor) invokes executor immediately. resolve settles a value, adopting a supplied Promise's eventual state when relevant. then returns a new Promise; returning a value fulfills that chain and throwing rejects it. await suspends only the current async function, not the entire process. finally observes completion without replacing the original result unless it throws or returns a rejected Promise. A missing return in a then callback can lose an intended nested dependency.

## Worked example / walkthrough

### Example A: Trace executor and reaction ordering

The executor is synchronous; the registered reaction is not. The intermediate assertion makes that distinction visible before the await resumes.

```javascript
import { strict as assert } from 'node:assert';
import { setTimeout as delay } from 'node:timers/promises';

export async function verify() {
  // Worked example
  {
    const trace = [];
    const pending = new Promise((resolve) => {
      trace.push('executor');
      resolve(3);
    });
    const observed = pending.then((value) => {
      trace.push('reaction');
      return value;
    });
    trace.push('sync');
    assert.deepEqual(trace, ['executor', 'sync']);
    assert.equal(await observed, 3);
    assert.deepEqual(trace, ['executor', 'sync', 'reaction']);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));
```

**Expected:** executor, sync, reaction.
### Example B: Compose values and rejection recovery

Throwing inside a reaction rejects the Promise returned by then. catch is a rejection reaction; its returned string fulfills the next Promise rather than rethrowing the failure.

```javascript
import { strict as assert } from 'node:assert';
import { setTimeout as delay } from 'node:timers/promises';

export async function verify() {
  // Worked example
  {
    const result = await Promise.resolve(4)
      .then((value) => value * 2)
      .then((value) => {
        throw new Error(`bad value ${value}`);
      })
      .catch((error) => error.message);
    assert.equal(result, 'bad value 8');
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));
```

**Expected:** recovered message is bad value 8.

## Prediction before your attempt

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

## Progressive hints

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
