## The question and the mechanism

Distinguish membership operations from bag concatenation and preserve a deliberate key population.

Virtual-table operations are not interchangeable with the similarly named operations in every SQL dialect. DAX UNION combines rows and retains duplicates. INTERSECT and EXCEPT have their own duplicate and lineage rules, including dependence on argument order. On small distinct key sets, membership is easy to reason about; on duplicated rows, count semantics need explicit attention.

Paper products have keys 1 and 2; Blue products have keys 1 and 3. Their intersection is key 1, Paper minus Blue is key 2, and their concatenation contains 1,2,1,3. Taking DISTINCT after UNION gives the three unique keys 1,2,3. That extra DISTINCT is a semantic operation, not merely presentation cleanup.

Before using a table result to filter another expression, state its grain and originating columns. Set membership can be appropriate for qualifying identities, while duplicate-bearing rows can represent repeated events. Removing duplicates from an event table may erase legitimate activity; retaining them in a list of eligible entities can inflate later iteration.

## Worked cases

### Case A: Intersection and one-sided difference

**Starting context:** Distinct Paper keys{1,2} and Blue keys{1,3} from the clean model.

```dax
EVALUATE
VAR PaperKeys = CALCULATETABLE ( VALUES ( Product[ProductKey] ), Product[Category] = "Paper" )
VAR BlueKeys = CALCULATETABLE ( VALUES ( Product[ProductKey] ), Product[Color] = "Blue" )
RETURN ROW ( "IntersectionRows", COUNTROWS ( INTERSECT ( PaperKeys, BlueKeys ) ), "PaperOnlyRows", COUNTROWS ( EXCEPT ( PaperKeys, BlueKeys ) ) )
```

**Context trace:**

1. The shared key is 1, so the intersection has one row.
2. Key 2 belongs to Paper but not Blue.
3. Reversing the difference would return key 3 instead, a different population.

**Hand-derived worked-reference result:**

| IntersectionRows | PaperOnlyRows |
| --- | --- |
| 1 | 1 |

A count of one in both differences does not mean the selected entities are identical. Retain the actual key sets in a review trace.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: UNION keeps repeated membership rows

**Starting context:** Concatenate the two two-row key tables; key 1 occurs in each input.

```dax
EVALUATE
VAR PaperKeys = CALCULATETABLE ( VALUES ( Product[ProductKey] ), Product[Category] = "Paper" )
VAR BlueKeys = CALCULATETABLE ( VALUES ( Product[ProductKey] ), Product[Color] = "Blue" )
VAR Combined = UNION ( PaperKeys, BlueKeys )
RETURN ROW ( "CombinedRows", COUNTROWS ( Combined ), "DistinctKeys", COUNTROWS ( DISTINCT ( Combined ) ) )
```

**Context trace:**

1. UNION produces four rows, including key 1 twice.
2. DISTINCT removes repeated key rows, leaving 1,2,3.
3. The two counts represent memberships versus unique product identities.

**Hand-derived worked-reference result:**

| CombinedRows | DistinctKeys |
| --- | --- |
| 4 | 3 |

If the downstream calculation iterates the concatenation, key 1 can contribute twice. A filter set and an iterator's row population should not be conflated.

## Progressive hints

1. The first argument defines the population from which rows are removed.
2. UNION does not deduplicate.
3. State that uniqueness is part of the entity-list contract.
4. Fact lines and product identities have different grains.
5. Columns match by position and need compatible meaning.
6. A person can belong to several audiences.
