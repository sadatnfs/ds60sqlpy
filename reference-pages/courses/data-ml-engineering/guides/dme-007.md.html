dme-007: Structural schemas and semantic data contracts#

Level: Beginner | Prepared runtime: data-engineering

Direct prerequisites: dme-003, dme-005, dme-006.

Outcome: Validate a strict typed input and a compatible additive schema change.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

A schema is an executable part of an agreement#

A producer and consumer need to agree on which fields exist, how values are represented and what those values mean. A structural schema can validate names, types, required fields and some value constraints. A semantic contract also states the row grain, identity, units, timing, population and compatibility expectations. A structural check is useful evidence, but it cannot discover every unstated business assumption.

This chapter uses actual Pydantic validation in the prepared data-engineering worker. A model class describes the accepted input, model_validate checks a supplied object and ValidationError reports a rejected object. The examples use already parsed Python dictionaries. Parsing a wire format and validating the parsed values are related but distinct steps.

The initial delivery schema requires a nonempty delivery identity and a positive integer package count. Its configuration enables strict validation and forbids unknown fields. These are deliberate choices for this local interface. Another interface might permit extra metadata or explicitly coerce a documented text representation, but those behaviors should be reviewed rather than inherited accidentally.

Strict validation is not the same as universal correctness. A positive integer can still be the wrong physical package count. A nonempty string can still identify the wrong delivery. A correctly typed field can contain information that was unavailable at prediction time. The contract should name which claims the validator enforces and which require other evidence.

Read the model declarations#

class DeliveryV1(BaseModel) defines a Pydantic model with the declared fields. The annotation delivery_id: str describes a string field. Field(min_length=1, pattern=r".*\S.*") requires at least one non-whitespace character. The pattern is a small regular-expression rule; it does not otherwise define which business identities are valid. packages: int = Field(ge=1) declares an integer at least one. These constraints are checked by Pydantic; a plain Python type hint by itself would not perform the same runtime validation.

ConfigDict(strict=True, extra="forbid") asks this model to reject undeclared conversions and extra input fields. A string "2" is therefore not silently treated as an integer two in the example. Pydantic's behavior can depend on the validation entrypoint and data type, so do not turn this specific parsed-dictionary result into an unsupported claim about every possible JSON or date conversion.

model_dump() produces a dictionary representation of a validated instance. It does not turn the object into a signed artifact, an accepted business publication or proof of upstream completeness. It is a useful explicit serialization boundary whose shape can be examined in a test.

The second schema inherits the first schema's fields and adds priority, whose permitted values are "normal", "urgent" or None. The default is None, so an old input without that new field has a defined interpretation. A default should represent an intentional meaning, such as “unspecified,” rather than quietly inventing a business observation.

Compatibility has a direction#

A schema change can be compatible for one direction of communication and incompatible for another. Ask which reader receives which writer's data. A new reader accepting an old record is different from an old reader accepting a newly added field. Words such as backward or forward compatible are useful only when the writer/reader relationship is stated clearly.

Adding an optional field often allows a new reader to consume old records. It does not guarantee that a strict old reader accepts new records containing that field. Renaming a field can break a consumer even if the new field has the same type. Changing a field's unit can preserve every structural type while changing the numerical interpretation dramatically.

Compatibility also includes consumer behavior. A dashboard may tolerate a missing optional description, while a decision service requires a value before it can act. A default may preserve parsing while changing downstream decisions. A full migration therefore needs tests of the intended consumers, not merely a successful schema parser.

Worked case 1: A new reader accepts old data, but the reverse fails#

The first case passes {"delivery_id": "A", "packages": 2} to DeliveryV2. Validation succeeds and produces an object with priority=None. The new reader has enough information to apply the default deliberately, and the inherited package contract remains intact.

The same case then sends a record containing priority="urgent" to the strict old DeliveryV1 reader. That reader rejects the undeclared field. The program checks the actual validation error category and reports that this direction is not accepted. Both outcomes are expected under the declared configurations.

This is why a rollout plan matters. You might deploy new readers before new writers, maintain separate versioned interfaces, or allow extra fields under a reviewed policy. Each choice has different tradeoffs. Silently assuming that every consumer will ignore a new field can break a strict service, while allowing every extra field can conceal spelling mistakes or unintended sensitive data.

The fixture does not claim to have migrated a distributed fleet. It demonstrates real local validation behavior for two reader versions. A production migration needs evidence about which versions are deployed, how records are routed and what happens during rollback. Chapter 048 returns to those operational questions.

A numeric type cannot establish a unit#

Suppose one system measures distance in meters and another expects kilometers. The input number 1000 is structurally a valid number under either interpretation. A schema that only says distance: float cannot determine which interpretation the producer intended.

A useful contract can require an explicit unit field or encode the unit in a carefully controlled versioned interface. In the example, KilometerDistance requires unit="km" and a nonnegative distance. This does not discover physical truth; it enforces the declared receiver contract and makes a contradictory label rejectable.

That conversion should happen in an explicit transformation with known input units. Relabeling 1000 meters as 1000 kilometers would preserve a valid numeric type while multiplying the physical claim by one thousand.

Worked case 2: Reject a semantic mismatch instead of hiding it#

The changed case first validates a bare distance=1000 under the unqualified numeric model. It succeeds. This is evidence that the structural model accepted a number, not that the number was interpreted correctly.

The reviewed kilometer model then receives distance=1000.0, unit="m" and rejects it because the unit conflicts with its declared contract. A deliberately converted value distance=1.0, unit="km" succeeds. The caller can see both the rejection and the explicit corrected representation.

Finally, the case passes the text package count "2" to the strict delivery schema and confirms that it is rejected. This complements the first chapter's manual validation using an actual schema library. A producer that legitimately supplies numeric text would need a documented parsing stage before strict validation, or a deliberately different validation policy.

These checks do not solve every semantic problem. A producer could incorrectly label a meter value as kilometers, and the local unit-field validator would not know. Reconciliation with the source, range checks, monitoring and ownership are still necessary. State the boundary of the check rather than calling it a complete guarantee.

Complete worked program#

"""Strict structural validation and directional semantic compatibility."""

from typing import Literal

from pydantic import BaseModel, ConfigDict, Field, ValidationError


class DeliveryV1(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")
    delivery_id: str = Field(min_length=1, pattern=r".*\S.*")
    packages: int = Field(ge=1)


class DeliveryV2(DeliveryV1):
    priority: Literal["normal", "urgent"] | None = None


def example_one():
    old_record = {"delivery_id": "A", "packages": 2}
    new_reader = DeliveryV2.model_validate(old_record)
    assert new_reader.packages == 2 and new_reader.priority is None
    try:
        DeliveryV1.model_validate({**old_record, "priority": "urgent"})
    except ValidationError as error:
        assert any(item["type"] == "extra_forbidden" for item in error.errors())
    else:
        raise AssertionError("This strict old reader must reject the extra field")
    return {
        "new_reader_accepts_old_record": new_reader.model_dump(),
        "old_reader_accepts_new_field": False,
    }


def example_two():
    class UnqualifiedDistance(BaseModel):
        distance: float

    class KilometerDistance(BaseModel):
        model_config = ConfigDict(strict=True, extra="forbid")
        distance: float = Field(ge=0)
        unit: Literal["km"]

    bare = UnqualifiedDistance.model_validate({"distance": 1000})
    assert bare.distance == 1000.0
    try:
        KilometerDistance.model_validate({"distance": 1000.0, "unit": "m"})
    except ValidationError:
        rejected_wrong_unit = True
    else:
        raise AssertionError("The receiver declared kilometers, not meters")
    corrected = KilometerDistance.model_validate({"distance": 1.0, "unit": "km"})
    try:
        DeliveryV1.model_validate({"delivery_id": "A", "packages": "2"})
    except ValidationError:
        rejected_implicit_cast = True
    else:
        raise AssertionError("Strict validation must not hide an undeclared conversion")
    return {
        "unqualified_number_was_structurally_valid": bare.distance,
        "wrong_unit_rejected": rejected_wrong_unit,
        "explicit_conversion": corrected.model_dump(),
        "implicit_cast_rejected": rejected_implicit_cast,
    }


def main():
    print("Compatibility has a direction:", example_one())
    print("A type alone does not specify meaning:", example_two())


if __name__ == "__main__":
    main()

Diagnose contract failures#

When a new deployment rejects old data, inspect required fields, defaults and validation entrypoints. When an old deployment rejects new data, inspect added fields and extra-field policy. When both versions parse but decisions change, inspect units, denominator definitions, enum meanings and downstream assumptions.

A validation error is often useful evidence about a broken interface, not an inconvenience to suppress. Preserve a bounded diagnostic and the rejected record's identity under the appropriate privacy policy. Avoid logging complete sensitive payloads indiscriminately. A quarantine record should help someone locate and understand the problem without expanding access to the underlying data.

Versioning should communicate a meaningful contract change. Incrementing a version string does not by itself implement migration, and keeping the same version does not make an incompatible change safe. Test representative producers and consumers, including changed-condition inputs and rollback behavior.

Answered interview discussion#

Is schema validation enough to prevent data leakage? No. A field can be correctly typed but unavailable at the decision cutoff. Availability and target definitions require additional temporal and modeling checks.

Is adding an optional field always safe? A new reader may accept old records using a default, while a strict old reader rejects records containing the extra field. State the direction and test the actual consumers.

When would you allow coercion? When the producer representation and accepted conversion rules are explicit. Validate the converted result and preserve a diagnostic for unsupported forms rather than relying on convenient implicit behavior.

What should happen after rejection? Follow a declared policy: stop publication, quarantine an identified record, return a documented client error or use a reviewed fallback. Ignoring the error without changing the claimed result is not a contract policy.
