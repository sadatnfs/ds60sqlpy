## Vocabulary and concepts

A C++ source file is editable text. Compilation checks language rules and translates each translation unit to object code. Linking joins object code and library definitions into an executable. Running starts a process from that executable. A failure in one phase is not evidence that later phases ran.

The terminal is an interface for requesting a program and reading its streams; a displayed transcript is not itself a command you have executed. Paths identify files relative to a working directory or an absolute location. This reading lesson uses supplied transcripts so no compiler installation is required. Keep a distinction among what source states, what a tool accepted and what a process actually observed.

- **source:** human-editable C++ text, usually .cpp
- **object file:** compiled code that still needs linking
- **executable:** a linked program file
- **stdout/stderr:** separate normal-output and diagnostic streams
- **exit status:** the process result code, with 0 normally signaling success

## Worked example / walkthrough

### Worked example 1: Follow one successful request

Changing hello.cpp affects a future build. It cannot alter a previous stdout transcript.

```text
input: hello.cpp
compile: hello.o
link: hello
run stdout: hello, learner
run exit: 0
```

**Expected:** There are three build phases (compile, link, run) after you write the input, and one successful process observation.

### Worked example 2: Stop at the first failed phase

A tool reporting an error did run; the program being compiled did not thereby run.

```text
compile: error: expected semicolon
object file: not produced
link: not run
process: not run
```

**Expected:** This is a compile failure, with no runtime exit evidence.

## Exercises

### Exercise 1: Name each artifact

Classify editable text, object file, executable and printed line.

**Inputs/evidence:** `hello.cpp`, `hello.o`, `hello` and the output `hello, learner`.

**Expected result/shape:** Source/object/executable/output in that order.

**Verify:** Label all four without treating the executable as source.

**Progressive hints:**

1. Start with the file a learner edits.
2. Object code is an intermediate.
3. Output comes after execution.

### Exercise 2: Read a relative path

Resolve a source path from a named working directory.

**Inputs/evidence:** Working directory course; relative path lessons/hello.cpp.

**Expected result/shape:** The intended file is course/lessons/hello.cpp.

**Verify:** Draw the joined path and explain why changing the working directory changes a relative path.

**Progressive hints:**

1. Locate the base directory.
2. Append the relative components.
3. Do not prepend another unrelated current folder.

### Exercise 3: Classify a syntax error

Identify the first failing phase in a missing-semicolon transcript.

**Inputs/evidence:** Compiler rejects std::cout line; no object emitted.

**Expected result/shape:** Compile failure; linking and learner-process execution not established.

**Verify:** State which artifact is absent and avoid claiming a runtime crash.

**Progressive hints:**

1. Which tool reported the error?
2. No object means no successful next phase.
3. Repair source syntax before rerunning the build.

### Exercise 4: Classify a link error

Explain undefined reference after compilation succeeds.

**Inputs/evidence:** `hello.o` exists; linker says a called function has no definition.

**Expected result/shape:** Link failure; no new executable established.

**Verify:** Identify the missing definition or omitted object as the next check.

**Progressive hints:**

1. Compilation and linking are separate.
2. A name can be declared without a definition.
3. Check definitions and target source lists.

### Exercise 5: Read a runtime failure

Compare stdout with exit status.

**Inputs/evidence:** Program prints started then exits 2.

**Expected result/shape:** The process ran and failed its declared contract despite producing text.

**Verify:** Record both started and exit 2; do not call output alone success.

**Progressive hints:**

1. Output can be partial.
2. Exit status is independent evidence.
3. Preserve the nonzero result.

### Exercise 6: Transfer the phase trace

A source edit is saved but the old executable is run. Predict the stale greeting.

**Inputs/evidence:** Old executable prints hello, learner; source now says hello, reviewer; no rebuild.

**Expected result/shape:** The old executable still prints hello, learner.

**Verify:** Name the missing build step and keep source/build/run receipts separate.

**Progressive hints:**

1. Which artifact did the process start from?
2. Saving and compiling are different.
3. Rebuild the edited source before rerunning.

## Common pitfalls

Do not paste a diagnostic as though it were a command. Do not infer a successful link from one existing object file, or a correct program from exit 0 alone. Avoid overwriting source when choosing an executable output path.

A frequent mix-up is reading a stale executable. If the compile step fails but an older `hello` from a previous build is still on disk, running it prints the old greeting and exits 0, which looks like success for the new source. Check the timestamp of the compile output, or delete `hello` before rebuilding, so that a run transcript can only come from the build you just traced. The same reasoning explains Worked example 2: no new object file means no new evidence about the program.
