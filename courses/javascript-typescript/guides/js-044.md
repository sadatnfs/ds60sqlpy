# js-044: Selections and data joins: enter, update and exit

## Learning objectives

Write a render function using a data join. Apply the same pattern to an HTML list. Produce a chart whose data transformation, visual encoding and interaction can be explained and checked independently.

## Purpose, vocabulary and mental model

A selection is a group of DOM nodes, not a copy of their HTML. A data join relates an array of records to selected nodes. Records without corresponding nodes enter; nodes with corresponding records update; surplus nodes exit. This makes repeated rendering a reconciliation operation rather than an instruction to append duplicates forever.

The selector describes the nodes you intend to manage. `selectAll('circle')` can begin empty; the subsequent data join creates the required nodes. `join('circle')` handles the common enter/update/exit case. Attribute callbacks then assign geometry from each bound record.

A render function should produce the intended state when called again. Calling append for every record on every update leaves stale marks and inflates counts. Start with a small sequence, such as three values followed by two, and verify both node count and attributes after the second render.

## Syntax anatomy and mechanism

`selection.data(values).join('circle')` binds the current values and returns the merged entered/updated selection. Without a key, matching is by index within a group. This can be correct when positions are identities, but the next lesson shows why stable entity IDs often need keys.

An attribute callback `(d, i) => ...` receives the record as d and its current group index as i. Returning undefined for a required coordinate can remove or invalidate the intended attribute. Inspect the derived values before blaming SVG rendering.

## Worked example / walkthrough

### Worked example 1: Reconcile a changing count

This fragment assumes an existing svg selection.

```javascript
function draw(values) {
  svg.selectAll("circle").data(values).join("circle").attr("r", d => d);
}
draw([5, 10, 15]);
draw([8, 12]);
```

**Expected observation:** Two circles remain; their radii are 8 and 12.

### Worked example 2: Contrast unconditional append

This is the bug to reason about, not the reference strategy.

```javascript
for (const value of [5, 10]) {
  svg.append("circle").attr("r", value);
}
```

**Expected observation:** Calling this loop twice creates four circles because it does not reconcile existing nodes.

## Debugging and common mistakes

Keep three checkpoints separate: the records after parsing, the domain and geometry after transformation, and the visible marks after rendering. A chart can look plausible while silently dropping records or assigning the wrong scale. Inspect counts, IDs, finite coordinates and meaningful expected values before adjusting colors. A missing mark may come from invalid input, a missing selection, an undefined scale result or clipping outside the viewBox.

The controlled failure for this lesson is: Diagnose a chart that doubles its nodes on every click. Its distinguishing evidence is It uses unconditional append or selects the wrong managed nodes. Preserve that failing case when repairing your program. Do not remove an assertion or broaden a scale merely to hide a wrong input. Explain whether a changed value should affect the data, an encoding, a layout or only presentation.

## Accessibility and interpretation

Give the visualization a descriptive title and a short textual summary of the main result. Keep a table or list when exact values matter. Do not encode a critical category only through color; use labels, shapes or position as appropriate. Interactive controls need keyboard operation and clear focus, and motion should respect the user's reduced-motion preference. Automated DOM checks support, but do not replace, a real keyboard and assistive-technology review.

A data scientist must also defend the statistical meaning. State the population, units, aggregation, missing-value policy and uncertainty where relevant. Synthetic points illustrate a mechanism and do not establish a real-world finding. A beautiful visualization should make a valid claim easier to inspect, not make a weak claim appear certain.
