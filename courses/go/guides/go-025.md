# go-025: Channels, buffering and close ownership

## Level and prerequisites

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-024

## Learning objectives

Design channel ownership so exactly one sender closes, receivers detect closure, and buffering is bounded. Along the way, explain backpressure, channel closure, directional channel; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A channel connects producers and consumers with typed communication. An unbuffered send completes when a receiver participates; a buffered channel retains values up to its capacity. Buffering changes backpressure, not ownership of referenced objects sent through the channel. Closing means no more values will be sent. Receivers drain buffered values before observing closure. The producer that knows all sending is finished should own close. A receiver normally must not close the channel merely because it is done reading. Sending after close panics. A send or receive on a nil channel blocks forever, and a select skips such a case; closing a nil channel panics.

## Vocabulary and concepts

- **Backpressure:** A producer slowing when a consumer cannot accept more.
- **Channel closure:** The declaration that no further sends will occur.
- **Directional channel:** A type restricting sending or receiving.

## Syntax anatomy and reasoning

make(chan int, 2) creates a two-element buffer. value, ok := <-ch distinguishes a delivered value from the zero value after closure. range ch receives until closed and drained. chan<- int restricts a parameter to sending; <-chan int restricts it to receiving. len(ch) is a transient observation rather than a synchronization protocol.

## Worked example / walkthrough

### Worked example 1: Drain before iteration ends

Buffer 2 and 3, close and sum the channel.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Drain before iteration ends
	{
		ch := make(chan int, 2)
		ch <- 2
		ch <- 3
		close(ch)
		sum := 0
		for v := range ch {
			sum += v
		}
		check(sum == 5, "drain")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Both values arrive and the sum is 5.

Close does not erase buffered values. Iteration ends after those values have been received.

### Worked example 2: Distinguish zero from closed

Send zero, close, then receive twice with comma-ok.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Drain before iteration ends
	{
		ch := make(chan int, 2)
		ch <- 2
		ch <- 3
		close(ch)
		sum := 0
		for v := range ch {
			sum += v
		}
		check(sum == 5, "drain")
	}

	// Distinguish zero from closed
	{
		ch := make(chan int, 1)
		ch <- 0
		close(ch)
		a, okA := <-ch
		b, okB := <-ch
		check(a == 0 && b == 0 && okA && !okB, "closed presence")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The first zero has ok true; the second has ok false.

Value equality cannot distinguish a delivered zero from the post-closure zero. The boolean carries completion information.

## Common pitfalls and diagnosis

Closing a channel from the receiver, or from one of several senders, is the classic ownership bug: a later send panics. Only the sender that knows no more values will come should close. A related surprise is treating a receive of zero as a real message; use comma-ok when closure matters. Buffering also does not copy referenced data, so a slice sent through a channel is still shared.
