# k8s-057: Headless Services and stateful peer discovery

## Level and prerequisites

Advanced; about 120 minutes. Direct prerequisites: `k8s-056`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Draw a stateful peer discovery sequence.
- Design a stateful replacement check.

## Purpose, vocabulary and mental model

A headless Service has clusterIP None and does not provide the ordinary virtual-IP load-balancing abstraction. With a selector, DNS can return endpoint addresses so clients discover individual backends. This is useful when an application protocol needs peer identity rather than an anonymous interchangeable service endpoint.

A StatefulSet provides stable Pod identities and ordered-management semantics under its configuration. Stable names do not mean a Pod process never changes, and storage retention does not guarantee application replication or consistency. A replacement Pod can have a new UID while keeping a stable logical name.

Stateful systems often need bootstrap discovery before every peer is ready. publishNotReadyAddresses can alter which endpoints are published, but it also exposes clients to peers that are not ready for ordinary work. Use it only with a protocol that understands the distinction between discovery and serving.

### Key terms

- **Headless Service DNS:** DNS records for a headless Service that return Pod addresses and, with a StatefulSet, per-Pod names.
- **Stable network identity:** A StatefulSet Pod's name and DNS record, which persist when the Pod is replaced even though its IP may change.
- **Governing Service:** The headless Service named in a StatefulSet's serviceName field, which publishes its per-Pod DNS records.
- **publishNotReadyAddresses:** A Service field that publishes DNS records for Pods before they are ready, for peers that must find each other during startup.

## Mechanism and field-by-field reasoning

The headless Service fixture names the same selector but sets clusterIP to None. Its A/AAAA answers identify Pod addresses directly. There is no virtual-IP proxy translating Service port 80 into targetPort 8080: a client using those addresses must connect to the actual endpoint listener 8080. A client using SRV discovery must honor the returned endpoint port and target. A/AAAA records carry addresses only, so those clients need the listener port from their application configuration. For this fixture, request `http://network-study-headless:8080/version`; the successful body is ds60-fixture-v1 plus a newline. The named-port SRV query uses _http._tcp.network-study-headless with the actual namespace and cluster domain, and a capable client honors each returned target/port. Merely requesting `headless-name:80` would not reach this fixture’s 8080 listener.

A StatefulSet’s serviceName ties its network identity to a governing Service. DNS names depend on Pod identity, service, namespace and cluster domain.

A client receiving several addresses must implement its own selection, retries and protocol semantics. DNS returning three peers does not guarantee a quorum, leader election or replicated data. Those are application properties that require separate evidence.

## Trace the request or control path

```text
headless Service DNS -> individual endpoint addresses -> client peer protocol
StatefulSet logical name stays stable; Pod UID/process can be replaced
```

There is no virtual address in this diagram. DNS for the headless Service returns the Pod addresses themselves, and the client picks one and speaks its own protocol to port 8080. The second line separates the stable name a StatefulSet gives each member from the process and UID behind it, which every replacement changes.

## Worked example / walkthrough

### Worked example 1: Read the headless setting

This is a manual fixture fragment.

```yaml
clusterIP: None
selector:
  app: network-study
ports:
  - name: http
    port: 80
    targetPort: http
```

**Expected observation:** The Service does not allocate an ordinary ClusterIP virtual destination.

### Worked example 2: Separate logical and process identity

A replacement changes a concrete instance.

```text
logical peer: store-0
before Pod UID: uid-old
after Pod UID: uid-new
retained claim: explicit persistent storage identity
```

**Expected observation:** Stable naming and retained storage are distinct from an unchanged process.

## Six progressive exercises

### Exercise 1: Predict the DNS role of a headless Service.

**Expected evidence:** Discovery can return individual backend addresses.

**Progressive hint:** Without a ClusterIP, what is left for a DNS answer to contain?

### Exercise 2: Distinguish StatefulSet name and Pod UID.

**Expected evidence:** A stable logical name can refer to a replacement instance.

**Progressive hint:** Replace one StatefulSet member in your head. Which comes back the same, the name or the UID?

### Exercise 3: Draw a stateful peer discovery sequence.

**Expected evidence:** Resolve peer addresses, establish identity and run the application protocol.

**Progressive hint:** Order the steps: resolve peers, confirm which peer is which, then connect. Where does the application protocol begin?

### Exercise 4: Diagnose treating headless DNS as automatic load balancing.

**Expected evidence:** The client owns address selection and connection behavior.

**Progressive hint:** When DNS returns several addresses, who chooses the destination? Is there a proxy in between?

### Exercise 5: Explain publishNotReadyAddresses tradeoffs.

**Expected evidence:** Discovery may include peers not ready for normal serving.

**Progressive hint:** Some members must find each other before they can serve. Who else would see those unready addresses?

### Exercise 6: Design a stateful replacement check.

**Expected evidence:** Logical identity, new UID, intended volume and application-level data result.

**Progressive hint:** After replacement, check the logical name, the new UID, the volume claim and a data read from the application.

## Diagnosis, failure boundaries and common mistakes

Treating a headless Service like a ClusterIP leads to clients that resolve once, cache one address and keep calling a Pod that no longer exists. The client owns selection, retry and re-resolution. Another mistake is connecting to port 80 because the Service says 80; there is no proxy to translate, so connect to the listener port. Assuming a stable name means unchanged data is risky too: the name returns after replacement, but only the persistent volume carries state, and only an application read proves it. Turning on publishNotReadyAddresses for ordinary clients sends them to members that are still starting.
