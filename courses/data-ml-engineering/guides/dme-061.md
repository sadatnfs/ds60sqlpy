# dme-061: Device placement, transfers and precision budgets

**Level:** Intermediate | **Prepared runtime:** `llm-torch-cpu`

**Direct prerequisites:** `dme-060`.

**Outcome:** Verify actual CPU placement and calculate bounded weight-transfer and KV-memory estimates.

A model needs a location for its weights and a compatible location for the tensors used by each operation. Choosing a device affects memory capacity, transfer paths, kernel availability and timing. It does not change the requirement to validate results. A program that imports a GPU library or prints a device name has not yet demonstrated that an intended GPU operation executed correctly.

The default inference workshop runs a real Transformer on CPU on both supported Linux architectures. The declared lesson profile here is the prepared Torch CPU worker. It performs actual tensor multiplication on CPU and separately calculates a hypothetical accelerator memory budget. The calculation is explicitly analytical: it is not a measured GPU transfer or a claim about a particular machine.

## Resident weights and request-local tensors

At startup, the loader reconstructs parameter tensors, validates them and places them on the chosen device. Those weights normally remain resident for many requests. A request adds its token indices, position indices, temporary activations and key/value cache. Outputs may eventually cross back to the host for sampling, logging or text formatting, depending on the implementation.

If weights occupy \(M_W\) bytes, request caches occupy \(M_K\), temporary operations need \(M_T\), and framework/allocator state occupies \(M_A\), a useful first approximation is

\[
M_{\mathrm{required}}=M_W+M_K+M_T+M_A.
\]

This is a budget model, not a guarantee that all memory can be allocated contiguously or that peak lifetimes align favorably. Fragmentation, reserved allocator blocks, driver allocations and concurrent workloads can cause a failure even when a simple sum appears to fit. Keep headroom and inspect actual peaks under representative shapes.

For a parameter count \(n\) and storage width \(b\) bytes per parameter, \(M_W\approx nb\). This omits quantization metadata and duplicated parameters. Training often needs gradients and optimizer state; inference typically does not. Accidentally retaining autograd graphs during serving can therefore create memory growth that has nothing to do with the intended KV cache.

## Transfer accounting

Moving \(S\) bytes across a link with sustained useful bandwidth \(B\) bytes per second has an idealized lower bound \(S/B\) seconds. Actual transfer latency also includes submission, synchronization, contention and protocol overhead. Advertised hardware bandwidth and measured application bandwidth are different quantities.

A seven-billion-parameter model stored at two bytes per parameter has 14 billion weight bytes before metadata. At an assumed 25 billion useful bytes per second, the lower-bound transfer is 0.56 seconds. This is already large compared with many request latency targets. Repeating that transfer for every prompt would waste the benefit of keeping the model resident. It also ignores file reading, decompression and allocation.

Input token IDs are usually small compared with the weights, but transfer synchronization can still dominate a tiny model. Moving each intermediate result to CPU inside a decode loop may force device synchronization and prevent overlap. Before optimizing transfers, draw which tensors live on which device at each stage and identify which host reads force completion.

Pinned host memory can support more effective asynchronous host-to-device transfers on supported accelerators. A nonblocking API request alone does not prove overlap. The memory type, stream dependencies and actual consumer schedule must permit it. The linked CUDA lessons cover real stream and pinned-memory experiments; this CPU lesson does not silently activate them.

## Precision is an operation contract

Float32, float16, bfloat16 and quantized integer representations have different ranges, precision and kernel support. Smaller storage may reduce memory traffic, but not every operation benefits equally. Accumulation dtype can differ from storage dtype. Softmax normalization, reductions and large-magnitude activations may need special care.

A correct precision evaluation compares outputs, loss or task metrics under the actual model and input distribution. A small absolute tensor error might be harmless in one stage and change an argmax near a tie in another. The serving receipt should identify relevant dtype policy, especially when comparing releases.

The workshop fixes float32 parameters and cache tensors to keep its numerical contract inspectable. It does not claim mixed-precision acceleration. A deliberate future GPU adaptation should pin compatible dependencies, select an actual device, allocate tensors, run a kernel, synchronize and verify a CPU-readable result. Requesting CUDA on an unavailable CPU image must fail explicitly rather than fall back while presenting CPU timings as GPU evidence.

## Worked case 1: actual CPU tensor placement

The first program case builds a three-by-four matrix containing integers zero through eleven in float32 and multiplies it by `[1,0,-1,2]`. The expected result is `[4,12,20]`. The program explicitly places both operands on CPU and verifies the resulting device and numerical output.

The arithmetic is deliberately simple. It separates three claims: Torch imported, tensors were placed on the declared device, and the operation produced the correct result. On a real accelerator qualification, all three claims still need evidence, plus synchronization and host readback. Merely observing `cuda.is_available()` would cover only capability discovery.

This case is useful when a mixed-device error appears. Check every operand, including indices, masks, cached tensors and newly created constants. A default tensor constructor can create a CPU tensor inside an otherwise device-resident computation. Silent host transfers in a convenience function can also hide a placement mistake by making the program slow instead of failing.

## Worked case 2: a model and cache budget

The second case calculates the hypothetical 0.56-second weight-transfer lower bound. It then computes the key/value storage for 32 layers, eight KV heads, head width 128, 4,096 tokens and two bytes per element. Two represents keys and values. The result is 536,870,912 bytes, or 0.5 GiB, for one request.

Notice that the formula uses KV heads, not necessarily query heads. Grouped-query attention can have fewer key/value heads than query heads. Replacing eight KV heads with a larger query-head count would overestimate that component; ignoring the head count entirely would underestimate it. The formula still omits cache page metadata, allocator overhead and temporary attention buffers.

```python
"""Actual CPU placement and a separate analytical transfer/capacity budget."""

import torch


def example_one():
    torch.set_num_threads(2)
    source = torch.arange(12, dtype=torch.float32).reshape(3, 4)
    weight = torch.tensor([[1.0], [0.0], [-1.0], [2.0]])
    result = source.to("cpu") @ weight.to("cpu")
    torch.testing.assert_close(result[:, 0], torch.tensor([4.0, 12.0, 20.0]))
    assert result.device.type == "cpu"
    print("Executed device:", result.device, "result:", result[:, 0].tolist())
    print("CPU evidence does not qualify CUDA or Apple GPU execution.")


def example_two():
    parameter_count = 7_000_000_000
    weights = parameter_count * 2
    bandwidth_bytes_per_second = 25_000_000_000
    theoretical_transfer_seconds = weights / bandwidth_bytes_per_second
    assert abs(theoretical_transfer_seconds - 0.56) < 1e-12
    layers, heads, head_width, tokens, bytes_per_element = 32, 8, 128, 4096, 2
    kv = 2 * layers * heads * head_width * tokens * bytes_per_element
    assert kv == 536_870_912
    print("Hypothetical lower-bound transfer seconds:", theoretical_transfer_seconds)
    print("Hypothetical per-request KV GiB:", kv / 2**30)
    print(
        "Allocator state, temporary tensors, driver reservations and "
        "synchronization need separate budgets."
    )


def main():
    example_one()
    example_two()


if __name__ == "__main__":
    main()
```

## Platform boundaries

A Linux container on a Mac does not convert an Apple GPU into an NVIDIA CUDA device. The workshop's CPU mode remains useful there. Windows uses WSL 2 and a Linux Docker engine; optional NVIDIA acceleration additionally needs a compatible Windows driver and engine/runtime integration. Native Linux requires its own compatible driver and container access. Architecture support for an image and support for a GPU backend are separate questions.

Do not install a large accelerator toolchain merely because this chapter is opened. The ordinary project prepares CPU dependencies only. If an optional artifact is unsupported on a platform, retain the analytical and CPU reference route and describe the supported external environment explicitly. Failure to qualify one GPU combination does not invalidate the CPU mechanism evidence.

## Interview discussion

**Why is an asynchronous copy not necessarily overlapped with computation?** Its source memory, destination device, stream ordering and consumer dependencies may still serialize it. Host reads can also introduce synchronization. A timeline must demonstrate overlap.

**Why can an inference server run out of memory after several requests when the model fits?** Request caches, temporary tensors, autograd graphs, retained results or allocator behavior can accumulate. Inspect ownership and peak lifetimes rather than only counting parameters.

**What does a CPU correctness check establish for a GPU deployment?** It provides a useful reference result and some architectural validation. It does not establish GPU kernel availability, precision behavior, synchronization correctness or performance.

Continue with admission queues. Once a per-request budget is understood, the server must decide when it can safely promise resources to another request.
