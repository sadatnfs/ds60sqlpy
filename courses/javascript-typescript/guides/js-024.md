# js-024: Runtime validation and unknown input

## Level and prerequisites

Intermediate, approximately 90 minutes. Direct prerequisites: `js-023`

## Learning objectives

Explain unknown input, schema validation, domain validation, diagnostic path with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Parse an order with two line items and inspect the typed success. The final task tests exercise numeric and string boundaries.

## Purpose and mental model

An external payload should enter typed code as unknown. JSON parsing establishes syntactic validity, but the result may be null, an array, a primitive or an object with the wrong fields. A runtime validator must inspect the shape and domain constraints before producing a trusted typed value. A type assertion skips this work; it cannot turn malformed input into valid data.

This lesson validates a small order with an id and an array of line items. Each item has a nonempty SKU and a positive safe-integer quantity. The validator returns a discriminated result instead of throwing for expected user-data errors, and includes a path such as items[1].quantity so the caller can identify the failing field. It copies accepted records so later edits to the original JSON object do not invalidate the already validated value.

Validation depth and resource budgets must be chosen together. An arbitrary recursive schema can consume excessive stack, CPU or memory. Here the structure has two bounded levels, at most twenty items, and bounded string lengths. Unknown extra keys are rejected deliberately. This is an exact fixture schema, not a claim that every API should reject forward-compatible fields. A permissive protocol might retain or ignore extras under a documented versioning policy.

## Vocabulary and concepts

**Unknown input:** A value whose structure has not yet been established.

**Schema validation:** Runtime checks for the required object and collection shape.

**Domain validation:** Checks for business constraints beyond primitive types.

**Diagnostic path:** A stable field location identifying where validation failed.

### Trust and object provenance

These boundaries assume JSON-like passive data produced by JSON.parse or the controlled literals in the exercises. An arbitrary same-process object can contain getters or proxies that execute code on property reads. Treating hostile executable objects as inert JSON requires a different trust boundary. The validator is not advertised as a security sandbox for arbitrary JavaScript objects. The CLI or HTTP layer must also bound the raw payload before JSON.parse, since a post-parse item limit cannot undo memory already spent parsing an enormous request.

## Syntax anatomy and execution trace

A record guard checks typeof object, non-null and non-array before exposing string-key access as unknown. Domain checks then establish primitive types and bounds. The success branch carries an Order value; the failure branch carries a code, path and message. The JSON wrapper separates parse failure from schema failure. When validating an array, check each element and build a new typed output; do not cast the entire array after inspecting only the first row.

## Worked example / walkthrough

### Example A: Validate and copy a complete order

The successful branch provides a typed value only after all fields pass. The result contains new objects, separating validation from later mutation of the input graph.

```typescript
import { strict as assert } from 'node:assert';

type LineItem = { sku: string; quantity: number };
type Order = { id: string; items: LineItem[] };
type Failure = { ok: false; code: 'json' | 'schema'; path: string; message: string };
type Validation = { ok: true; value: Order } | Failure;
function record(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null && !Array.isArray(value);
}
function fail(path: string, message: string): Failure { return { ok: false, code: 'schema', path, message }; }
function shortText(value: unknown): value is string {
  return typeof value === 'string' && value.length > 0 && value.length <= 40;
}
function validateOrder(value: unknown): Validation {
  if (!record(value) || Object.keys(value).sort().join(',') !== 'id,items') return fail('$', 'exact order object required');
  if (!shortText(value.id)) return fail('id', 'nonempty id up to 40 code units required');
  if (!Array.isArray(value.items) || value.items.length > 20) return fail('items', 'at most 20 items required');
  const items: LineItem[] = [];
  for (let index = 0; index < value.items.length; index += 1) {
    const item: unknown = value.items[index];
    if (!record(item) || Object.keys(item).sort().join(',') !== 'quantity,sku') return fail(`items[${index}]`, 'exact line item required');
    if (!shortText(item.sku)) return fail(`items[${index}].sku`, 'bounded nonempty SKU required');
    if (typeof item.quantity !== 'number' || !Number.isSafeInteger(item.quantity) || item.quantity <= 0) return fail(`items[${index}].quantity`, 'positive safe integer required');
    items.push({ sku: item.sku, quantity: item.quantity });
  }
  return { ok: true, value: { id: value.id, items } };
}
function parseOrder(text: string): Validation {
  let value: unknown;
  try { value = JSON.parse(text); }
  catch { return { ok: false, code: 'json', path: '$', message: 'invalid JSON syntax' }; }
  return validateOrder(value);
}

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const raw: unknown = { id: 'A', items: [{ sku: 'X', quantity: 2 }, { sku: 'Y', quantity: 3 }] };
    const result = validateOrder(raw);
    if (!result.ok) throw new Error(result.message);
    assert.equal(result.ok, true);
    assert.equal(result.value.items.reduce((sum, item) => sum + item.quantity, 0), 5);
    assert.notEqual(result.value, raw);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** success with total quantity 5; independent copied item records.
### Example B: Report a nested domain failure precisely

Checking every element prevents a valid first row from legitimizing invalid later rows. A stable path is more useful to the caller than a generic invalid input message.

```typescript
import { strict as assert } from 'node:assert';

type LineItem = { sku: string; quantity: number };
type Order = { id: string; items: LineItem[] };
type Failure = { ok: false; code: 'json' | 'schema'; path: string; message: string };
type Validation = { ok: true; value: Order } | Failure;
function record(value: unknown): value is Record<string, unknown> {
  return typeof value === 'object' && value !== null && !Array.isArray(value);
}
function fail(path: string, message: string): Failure { return { ok: false, code: 'schema', path, message }; }

  if (!record(value) || Object.keys(value).sort().join(',') !== 'id,items') return fail('$', 'exact order object required');

    const item: unknown = value.items[index];
    if (!record(item) || Object.keys(item).sort().join(',') !== 'quantity,sku') return fail(`items[${index}]`, 'exact line item required');
    if (!shortText(item.sku)) return fail(`items[${index}].sku`, 'bounded nonempty SKU required');

  try { value = JSON.parse(text); }
  catch { return { ok: false, code: 'json', path: '$', message: 'invalid JSON syntax' }; }
  return validateOrder(value);
}

export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const result = validateOrder({ id: 'A', items: [{ sku: 'X', quantity: 2 }, { sku: 'Y', quantity: 0 }] });
    assert.equal(result.ok, false);
    if (result.ok) throw new Error('expected rejection');
    assert.equal(result.code, 'schema');
    assert.equal(result.path, 'items[1].quantity');
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** failure code schema and path items[1].quantity.

## Prediction before your attempt

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

## Progressive hints

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
