js-033: Worker threads and CPU-bound work#

Level and prerequisites#

Advanced, approximately 120 minutes. Direct prerequisites: js-032

Learning objectives#

Explain worker thread, structured clone, transfer, worker lifecycle with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Sum integers 1 through 10000 in a worker and inspect its thread id. The final task tests reject data that cannot be cloned.

Purpose and mental model#

An async function does not automatically move CPU work off the main JavaScript thread. A long synchronous loop inside an async function still blocks that thread until it yields or completes. Worker threads provide separate JavaScript execution contexts for CPU work. They are useful when the computation is large enough to justify startup, messaging and coordination costs. They do not make ordinary asynchronous file or network I/O inherently faster.

Messages normally use structured cloning. The receiver obtains its own copy of supported values, so mutating a received object does not change the sender's original object. Some values, such as functions, cannot be cloned. A transfer list can instead move ownership of an ArrayBuffer: the sender's buffer is detached, and the receiver gains access to its bytes. Transfer is an ownership change, not a shared mutable alias. SharedArrayBuffer has different synchronization requirements and is not used here.

A worker's lifecycle includes message, error and exit events. Receiving a result is not by itself proof that a worker has stopped. The helper terminates its owned worker in finally and applies a waiting timeout. A worker that exits without producing a result is a failure under this helper's contract. The examples use small fixed authored worker programs; eval:true is used only to keep those trusted fixtures self-contained. It must not be supplied with untrusted source text.

Workers share a process-level trust context and available host capabilities. They are not a security sandbox for arbitrary hostile JavaScript. Resource limits constrain selected V8 resources, not every possible process or external allocation. These tests establish actual thread messaging, ownership and teardown, not a speedup claim.

Vocabulary and concepts#

Worker thread: A separate JavaScript execution context for concurrent work.

Structured clone: Copying supported data across a message boundary.

Transfer: Moving ownership of a transferable object and detaching the sender view.

Worker lifecycle: Startup, messaging, errors, completion and termination ownership.

Syntax anatomy and execution trace#

new Worker creates the thread. workerData supplies a cloned or transferred initial payload. parentPort sends the result to the parent. A transferList names the exact ArrayBuffer ownership to move. Parent code listens for result, error and premature exit, then cleans up listeners and terminates the worker. Use process and thread identifiers only as observations of the actual run, not as fixed expected numbers.

Worked example / walkthrough#

Example A: Perform bounded CPU work in a real worker#

The result came through an actual worker message. The tiny workload illustrates mechanics and may be slower than a direct loop because startup costs dominate.

import { strict as assert } from 'node:assert';
import { Worker } from 'node:worker_threads';

async function runWorker(source, data, transferList = []) {
  const worker = new Worker(source, { eval: true, workerData: data, transferList, resourceLimits: { maxOldGenerationSizeMb: 32 } });
  let timer;
  try {
    return await new Promise((resolve, reject) => {
      timer = setTimeout(() => reject(new Error('worker result timeout')), 10000);
      worker.once('message', resolve);
      worker.once('error', reject);
      worker.once('exit', code => reject(new Error(`worker exited without a result: ${code}`)));
    });
  } finally {
    clearTimeout(timer);
    await worker.terminate();
  }
}

export async function verify() {
  // Worked example
  {
    const result = await runWorker(`const { parentPort, workerData, threadId } = require('node:worker_threads');
    let sum = 0; for (let value = 1; value <= workerData; value += 1) sum += value;
    parentPort.postMessage({ sum, threadId });`, 10000);
    assert.equal(result.sum, 50005000);
    assert.ok(result.threadId > 0);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: sum 50005000; worker thread id positive.

Example B: Transfer a buffer and observe detachment#

The sender loses access because ownership moved. Treating a detached buffer as still usable would create an invalid lifetime assumption.

import { strict as assert } from 'node:assert';
import { Worker } from 'node:worker_threads';

async function runWorker(source, data, transferList = []) {
  const worker = new Worker(source, { eval: true, workerData: data, transferList, resourceLimits: { maxOldGenerationSizeMb: 32 } });
  let timer;
  try {
    return await new Promise((resolve, reject) => {
      timer = setTimeout(() => reject(new Error('worker result timeout')), 10000);
      worker.once('message', resolve);
      worker.once('error', reject);
      worker.once('exit', code => reject(new Error(`worker exited without a result: ${code}`)));
    });
  } finally {
    clearTimeout(timer);
    await worker.terminate();
  }
}

export async function verify() {
  // Worked example
  {
    const buffer = Uint8Array.from([1, 2, 3]).buffer;
    const result = await runWorker(`const { parentPort, workerData } = require('node:worker_threads');
    const bytes = new Uint8Array(workerData); bytes[0] = 9; parentPort.postMessage([...bytes]);`, buffer, [buffer]);
    assert.equal(buffer.byteLength, 0);
    assert.deepEqual(result, [9, 2, 3]);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: parent byteLength 0; returned bytes 9,2,3.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

Exercises#

  1. Perform bounded CPU work in a real worker. Sum integers 1 through 10000 in a worker and inspect its thread id. Expected: sum 50005000; worker thread id positive. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Transfer a buffer and observe detachment. Send an ArrayBuffer by transfer list, modify its first byte in the worker and return the bytes. Expected: parent byteLength 0; returned bytes 9,2,3. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Distinguish cloning from shared mutation. Send an object, mutate the worker copy and compare the original. Expected: worker returns 9; parent remains 1. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Propagate an actual worker exception. Run an authored worker that throws a fixture error. Expected: parent Promise rejects with worker fixture failed. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Terminate an owned worker that remains alive. Start a worker that reports ready and keeps an interval open, then terminate it. Expected: ready observed; terminate resolves with an exit code. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Reject data that cannot be cloned. Try to pass a function through workerData. Expected: DataCloneError before useful worker execution. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
