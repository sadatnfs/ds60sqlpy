# k8s-055: TLS termination, certificates and upstream identity

## Level and prerequisites

Advanced; about 120 minutes. Direct prerequisites: `k8s-054`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Design a no-secret TLS evidence record.
- Plan a two-hop trust policy.

## Purpose, vocabulary and mental model

TLS protects a transport connection through encryption and peer authentication according to a trust model. A server certificate binds a public key to identities such as DNS names. The client must validate the requested name, certificate chain and validity conditions. Encryption without meaningful identity verification does not establish the intended server.

TLS termination means a component decrypts the client connection and may open another connection upstream. A load balancer, Ingress controller or Gateway can terminate TLS. The proxy-to-application hop then has its own protocol and trust requirements. Client-to-proxy encryption does not automatically encrypt the upstream hop.

SNI communicates the requested server name during the TLS handshake so a listener can select an appropriate certificate. HTTP Host routing occurs after a successful HTTP-capable connection. A certificate mismatch and an HTTP 404 are failures at different stages and need different diagnosis.

### Key terms

- **Server certificate:** The certificate a server presents to prove its name, which the client checks against its trusted roots and the requested host.
- **Certificate chain:** The server certificate plus intermediate certificates that link it to a root the client trusts.
- **SNI:** Server Name Indication, the TLS field that carries the requested host name so a proxy can choose the right certificate.
- **Upstream hop:** The connection from a proxy to its backend, which needs its own TLS and trust settings separate from the client hop.

## Mechanism and field-by-field reasoning

Kubernetes commonly stores certificate/key material in a Secret referenced by the controller configuration. Secret base64 encoding is not encryption. Do not include a private key in a lesson fixture or print Secret data during inspection. The fixture uses no real certificate and does not request one from an external authority.

For a real owned lab, validate the hostname, listener protocol, certificate reference, controller support and upstream policy. Never teach disabling certificate verification as the normal solution to a mismatched name. A self-signed teaching certificate needs an explicitly scoped trust setup, not global trust changes.

## Trace the request or control path

```text
client DNS name -> TLS handshake/SNI -> certificate validation -> proxy
proxy -> separate upstream HTTP or TLS connection -> app response
```

The first line happens before any HTTP exists: the client sends the name it expects as SNI, receives a certificate and checks both the name and the chain. The second line is a new connection from the proxy to the app, plain HTTP or a second TLS session with its own identity. A browser padlock describes the first hop only.

## Worked example / walkthrough

### Worked example 1: Classify two failures

These are intentionally synthetic symptoms.

```text
TLS name mismatch: client cannot verify requested identity
HTTP 404: an HTTP server responded but route/content was not found
```

**Expected observation:** The second occurs after a successful enough transport exchange to receive HTTP.

### Worked example 2: Trace two encrypted hops

Each connection has its own peer identity.

```text
browser --TLS(server name A)--> Gateway
Gateway --TLS(upstream identity B)--> app
```

**Expected observation:** Validating A does not automatically validate B.

## Six progressive exercises

### Exercise 1: Predict whether a matching IP is enough for a DNS certificate.

**Expected evidence:** The requested name must satisfy certificate identity validation.

**Progressive hint:** A certificate lists the names it is valid for. Is an address match the same as a name match?

### Exercise 2: Locate the TLS termination point.

**Expected evidence:** The component that decrypts the client connection.

**Progressive hint:** Find the component holding the private key for the client-facing name. Decryption happens there.

### Exercise 3: Design a no-secret TLS evidence record.

**Expected evidence:** Names, certificate metadata and status without private key bytes.

**Progressive hint:** Record only what a handshake shows anyone: subject names, issuer, validity dates and the validation result.

### Exercise 4: Diagnose certificate mismatch separately from 404.

**Expected evidence:** Identity validation versus HTTP routing/content.

**Progressive hint:** One failure happens before any HTTP exchange; the other needs a working HTTP exchange to exist at all.

### Exercise 5: Explain why base64 Secret data is not encrypted protection.

**Expected evidence:** Encoding is reversible representation, not confidentiality.

**Progressive hint:** Decode a base64 string. Did you need a key to do it?

### Exercise 6: Plan a two-hop trust policy.

**Expected evidence:** Client-facing identity and upstream identity are both explicit.

**Progressive hint:** Write two trust rows: what the client verifies about the proxy, and what the proxy verifies about the app.

## Diagnosis, failure boundaries and common mistakes

A certificate error and an HTTP 404 are often lumped together as the site being down. They come from different layers: a name mismatch fails the handshake before any request is sent, while a 404 requires a successful handshake first. Another mistake is disabling verification with `curl -k` to get past a mismatch; that removes the very evidence you need. Never paste private keys, Secret YAML or key material into a worksheet, and remember base64 is an encoding anyone can reverse. Finally, do not assume the hop from proxy to Pod is encrypted because the client's hop is. Check the proxy's upstream configuration, which is a separate setting with its own trust anchor and its own failure messages in the proxy's log.

Before concluding, record:

- The hostname the client sent as SNI and the names in the certificate's subjectAltName list.
- The certificate's issuer and its notBefore and notAfter dates, read as metadata with no key bytes.
- Which component decrypts the client connection, and whether its upstream hop is plain HTTP or a second TLS session.
- The layer of each failure: handshake errors arrive before any status line, HTTP codes such as 404 only after it.
