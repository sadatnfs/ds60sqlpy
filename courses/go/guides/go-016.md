## Why this mechanism matters

A function value can be stored, passed and called like other values. A closure also refers to variables from its surrounding scope. That makes callbacks concise, but it makes lifetime and mutation worth tracing explicitly. Two closures can intentionally share one variable; two independent constructor calls can create separate state. A callback contract should describe when it is called, whether it may stop iteration and whether it can retain supplied values. Iterator-style APIs can avoid allocating intermediate slices, but early termination and cleanup must still be well defined. Do not confuse deferred execution with concurrent execution: a closure is not a goroutine by itself.

## Vocabulary and concepts

- **Closure:** A function value that refers to surrounding variables.
- **Callback:** A function supplied for another operation to invoke.
- **Early termination:** Ending traversal once the caller has enough evidence.

## Syntax anatomy and reasoning

func(int) int is a function type. An anonymous func literal creates a function value. Returning a closure from makeCounter retains access to its captured count. A visitor returning bool can stop a traversal when false. Passing a function as a parameter makes selection policy explicit without an interface type when only one operation is needed.

## Worked example / walkthrough

### Worked example 1: Capture a changing variable

Create a closure referring to factor, change factor, then call it.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func makeCounter() func() int { n := 0; return func() int { n++; return n } }
func mapInts(items []int, f func(int) int) []int {
	out := make([]int, len(items))
	for i, x := range items {
		out[i] = f(x)
	}
	return out
}
func visit(limit int, f func(int) bool) {
	for i := 1; i <= limit; i++ {
		if !f(i) {
			return
		}
	}
}

func main() {
	// Capture a changing variable
	{
		factor := 2
		multiply := func(x int) int { return factor * x }
		factor = 3
		check(multiply(4) == 12, "capture variable")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** The closure uses the new factor 3.

The closure refers to the variable rather than freezing its initial value. Explicitly copying a value into a new binding produces a different contract.

### Worked example 2: Create independent counters

Construct two counter closures and call the first twice.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func makeCounter() func() int { n := 0; return func() int { n++; return n } }
func mapInts(items []int, f func(int) int) []int {
	out := make([]int, len(items))
	for i, x := range items {
		out[i] = f(x)
	}
	return out
}
func visit(limit int, f func(int) bool) {
	for i := 1; i <= limit; i++ {
		if !f(i) {
			return
		}
	}
}

func main() {
	// Capture a changing variable
	{
		factor := 2
		multiply := func(x int) int { return factor * x }
		factor = 3
		check(multiply(4) == 12, "capture variable")
	}

	// Create independent counters
	{
		a, b := makeCounter(), makeCounter()
		check(a() == 1 && a() == 2 && b() == 1, "independent closures")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** The first returns 1 then 2; the second starts at 1.

Each constructor invocation creates its own captured state. Sharing a single returned closure would share that state instead.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
