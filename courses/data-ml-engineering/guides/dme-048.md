## A deployment changes a running contract

Shipping new code is not only copying a file or starting another container. Consumers may depend on data schemas, API fields, feature definitions, model versions and persistent state. A new implementation can be locally correct and still break an existing consumer. A rollback can also fail if the old code can no longer read the state left by the new version.

An expand-and-contract migration separates introducing compatible structure from removing obsolete structure. First expand the schema or interface so old and new consumers can coexist. Populate or validate the new information. Activate the new consumer only when its contract is satisfied. Retire old fields or paths later, after the supported consumers and rollback requirements no longer need them. This sequencing creates room to observe and recover without requiring every component to switch at one instant.

The program performs an actual SQLite schema expansion, backfill and transactional consumer-version activation. It does not deploy Kubernetes workloads or configure a production load balancer. Those deployment mechanisms are covered in their own modules. Here the database and reader behavior make compatibility and rollback concrete enough to test independently of infrastructure.

## Separate schema, data and reader versions

The starting table has one row per delivery with identity and package count. Reader version 1 selects those two fields. The schema expansion adds a nullable region field. Reader version 2 requires identity, package count and a nonempty region for every row. A separate deployment table records which reader contract is currently accepted.

Adding the column is not the same as completing its data. Existing rows initially have null region values. Reader 1 can continue to operate because its projection remains available. Reader 2 must wait until the required region backfill is complete. The compatibility condition is directional:

\[
\operatorname{read}_{v1}(D_{\mathrm{expanded}})
=\operatorname{read}_{v1}(D_{\mathrm{original}}),
\]

while successful \(\operatorname{read}_{v2}\) additionally requires its new field invariant. A database statement can succeed even when a proposed application contract is not yet satisfied. Activation therefore calls the candidate reader's validation before changing the accepted version.

The accepted-version change happens inside an actual SQLite write transaction. The caller supplies the expected current reader version. If another decision has changed it, activation fails rather than overwriting the newer state blindly. The program supports only reviewed reader versions 1 and 2; an unknown version is rejected rather than interpreted through an accidental default branch.

## Worked case 1: expand, reject premature activation, then backfill

`example_one()` begins with A2, B3 and C1. It records reader 1's exact result, adds the region column and confirms that reader 1 still returns the same rows. This is the compatibility check that allows the migration to proceed while the old consumer remains active.

The example then tries to activate reader 2 before filling the new field. Validation fails because region is missing. The accepted reader remains 1. The failure does not remove the expanded column or fabricate default regions. The system has entered a legitimate intermediate migration state: new structure exists, old consumers work, and the new consumer is not yet ready.

Next, the program backfills A and B to north and C to south. Reader 2 now returns A2/north, B3/north and C1/south and can be activated. Reader 1 still returns A2, B3 and C1 after activation. Both views remain meaningful, which is valuable when different consumers roll out at different times or when an operator needs to return to the old reader.

The fixture uses a complete reviewed mapping. A production backfill would need source identity, population reconciliation, retry behavior and possibly bounded batches. The historical backfill chapter supplies those mechanisms. Do not treat a default string filled into every row as a valid substitute for missing business knowledge merely to satisfy a non-null constraint.

## Worked case 2: rollback preserves the expanded schema

The second case expands and backfills the table, then activates reader 2. It attempts to activate reader 3, which has no implemented contract. That attempt fails and the accepted version remains 2. A deployment reference should name an actual reviewed implementation, not merely a numerically higher version.

The example then explicitly rolls back to reader 1 using expected current version 2. The accepted reader becomes 1 and returns the original two-field result. The region column and its values remain present, and reader 2 would still be able to read them. Rollback does not drop useful columns or erase information created during the compatible migration.

This distinction prevents an unnecessary destructive reversal. Returning traffic to old compatible code is often safer than immediately undoing every schema change. Some migrations are not backward compatible, and some external effects cannot be reversed at all. A rollback plan must identify those cases before activation. The example deliberately chooses an additive migration so the preserved compatibility can be demonstrated rather than assumed.

## Complete worked program

Use data-engineering. The program executes real SQLite DDL, DML and transactions in an owned in-memory database. No existing learner database, Docker deployment or external service is changed.

```python
"""Actual SQLite expand/backfill/activate/rollback with versioned consumer contracts."""

import sqlite3


def database():
    connection = sqlite3.connect(":memory:")
    connection.execute(
        "create table deliveries(id text primary key not null,packages integer not null)"
    )
    connection.executemany("insert into deliveries values(?,?)", [("A", 2), ("B", 3), ("C", 1)])
    connection.execute("create table deployment(id integer primary key,reader integer not null)")
    connection.execute("insert into deployment values(1,1)")
    connection.commit()
    return connection


def read(connection, version):
    if version == 1:
        return connection.execute("select id,packages from deliveries order by id").fetchall()
    if version == 2:
        result = connection.execute(
            "select id,packages,region from deliveries order by id"
        ).fetchall()
        if any(region is None or not region for _, _, region in result):
            raise ValueError("New reader requires a complete region backfill")
        return result
    raise ValueError("Unsupported consumer contract version")


def expand(connection):
    fields = {row[1] for row in connection.execute("pragma table_info(deliveries)")}
    if "region" not in fields:
        with connection:
            connection.execute("alter table deliveries add column region text")


def activate(connection, version, expected):
    with connection:
        connection.execute("begin immediate")
        current = connection.execute("select reader from deployment where id=1").fetchone()[0]
        if current != expected:
            raise ValueError("Accepted reader version changed")
        result = read(connection, version)
        connection.execute("update deployment set reader=? where id=1", (version,))
    return result


def fill_regions(connection):
    with connection:
        connection.executemany(
            "update deliveries set region=? where id=?",
            [("north", "A"), ("north", "B"), ("south", "C")],
        )


def example_one():
    connection = database()
    try:
        baseline = read(connection, 1)
        expand(connection)
        assert read(connection, 1) == baseline
        try:
            activate(connection, 2, 1)
        except ValueError:
            pass
        else:
            raise AssertionError("Incomplete migration was activated")
        assert connection.execute("select reader from deployment").fetchone() == (1,)
        fill_regions(connection)
        new = activate(connection, 2, 1)
        assert new == [("A", 2, "north"), ("B", 3, "north"), ("C", 1, "south")]
        assert read(connection, 1) == baseline
        return {
            "old_reader_while_schema_expands": baseline,
            "new_reader_after_backfill": new,
            "early_activation_rejected": True,
        }
    finally:
        connection.close()


def example_two():
    connection = database()
    try:
        expand(connection)
        fill_regions(connection)
        activate(connection, 2, 1)
        try:
            activate(connection, 3, 2)
        except ValueError:
            pass
        else:
            raise AssertionError("Unimplemented consumer version was activated")
        assert connection.execute("select reader from deployment").fetchone() == (2,)
        rolled_back = activate(connection, 1, 2)
        assert rolled_back == [("A", 2), ("B", 3), ("C", 1)]
        assert "region" in {row[1] for row in connection.execute("pragma table_info(deliveries)")}
        assert read(connection, 2) == [("A", 2, "north"), ("B", 3, "north"), ("C", 1, "south")]
        return {
            "accepted_reader_after_rollback": 1,
            "retained_additive_schema": True,
            "new_field_values_preserved": True,
            "rollback_did_not_drop_columns_or_reverse_external_effects": True,
        }
    finally:
        connection.close()


def main():
    print("Separate schema expansion, backfill and consumer activation:", example_one())
    print("Compatible rollback preserves useful new data:", example_two())


if __name__ == "__main__":
    main()
```

## Release strategy and acceptance evidence

A release should bind source, dependencies, image identity, configuration and the data or model contracts it expects. A mutable tag alone does not identify the bytes that were tested. Preserve the exact candidate identity through qualification and activation. If the candidate changes after testing, the previous test evidence no longer proves that new candidate's behavior.

Canary delivery routes a limited population through a candidate while observing reviewed indicators. Blue-green delivery keeps separate environments and changes routing between them. Shadow evaluation computes candidate results without using them for the primary decision. Each strategy has a different state and cost boundary. Shadowing a state-changing operation can still create effects unless the shadow path is deliberately isolated; duplicating a request is not automatically safe.

A release gate should include compatibility, correctness and operational evidence relevant to the change. A model activation may need evaluation and feature-contract checks. A schema migration may need old/new reader tests and rollback readback. A server release may need cancellation, resource and persistence checks. A generic “build succeeded” badge is only one part of that evidence.

## Contract the old structure only when safe

Removing an old column or endpoint is a separate change from adding the new one. Identify consumers, observe actual use and agree on the retirement boundary. Keep a plan for delayed clients and retained snapshots. A consumer inventory can be incomplete, so use operational evidence and explicit ownership rather than assuming no one uses an old field because it is absent from one repository search.

Schema and model migrations can also affect stored drafts, checkpoints and cached results. Preserving stable lesson and operation identities in this classroom is an example of that broader responsibility. A new UI or runtime should not silently reinterpret old saved state under a different contract. Versioned readers or explicit migrations make that transition reviewable.

Some changes need a forward repair rather than a rollback. If a new system emitted externally visible events or irreversibly transformed data, running old code may not restore the prior world. Document which effects are reversible, which are compensatable and which require a separate correction process. An honest recovery plan is more useful than a rollback command whose scope is unclear.

## Failure diagnosis and answered interview discussion

If old consumers fail immediately after a schema expansion, inspect whether the change was actually additive and whether they rely on `SELECT *`, field position or strict response shape. If activation succeeds before a backfill completes, inspect the acceptance gate. If rollback loses new data, inspect whether it unnecessarily drops expanded structure. If a stale operator action overwrites a newer release decision, inspect the expected-version comparison.

An interviewer may ask, “How would you deploy a required new field without downtime?” Explain expand, populate, validate, activate and later contract, with old/new reader evidence. If asked whether rollback means reversing the migration, distinguish code routing from persistent state and external effects. If asked what was tested, identify the exact candidate and the relevant behavior rather than citing a broad test count without scope.

For an answered extension, adding a new required field with a non-null database constraint immediately may fail because old rows have no value. The safer additive phase permits temporary nulls under the old reader, then validates a complete backfill before the new reader requires the field. The temporary flexibility is controlled migration state, not permission to ignore the final contract.
