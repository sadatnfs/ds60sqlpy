A beginner's mental model for this lesson#

A B-tree index is a sorted copy of one or more column values, each entry pointing at a row in the table (the heap). Looking up country = 'US' in the index is fast, but every match still needs a trip to the heap for the other columns. An index pays off when it lets PostgreSQL skip most pages of the table; when the matching rows are spread over every page anyway, a plain sequential scan is cheaper.

The tables in this lesson are small, and that makes the trade-off visible:

Table Rows Pages Filter used here Rows matched
products 300 3 category = 'Electronics' 50 (1 in 6)
customers 500 9 country = 'US' 63 (1 in 8)
orders 4,362 65 last 30 days about 209
payments 3,836 29 last 180 days about 1,340

On a three-page table no index can save much, so products keeps its sequential scan. On orders, a 30-day window touches 16 of 65 pages through a bitmap scan, which is a real saving. PostgreSQL makes this choice from selectivity, the fraction of rows it expects a predicate to keep, and from the table's size. Your job is to read its choice, not to force it.

Two worked SQL examples#

Example 1#
CREATE INDEX idx_orders_total_amount ON orders (total_amount);

How to read it: CREATE INDEX builds a B-tree over orders.total_amount and prints CREATE INDEX. That tag proves only that the index exists. The learner file then plans total_amount > 500 LIMIT 100, and the plan ignores the new index: 2,410 of 4,362 orders match, so the first 100 are found after reading about 183 rows from the heap.

Expected result/shape: The command tag, then a Limit over a Seq Scan on orders with Rows Removed by Filter: 83. To see the index itself, query pg_indexes WHERE indexname = 'idx_orders_total_amount' before the ROLLBACK; it is about 112 kB, nearly twice the 65-page table footprint of each column it covers.

Example 2#
CREATE INDEX idx_orders_order_date ON orders (order_date);

How to read it: The second index is on order_date, and its filter, the last 30 days, keeps only about 209 orders. This time the planner uses the index: a Bitmap Index Scan collects matching row locations, and a Bitmap Heap Scan visits only the pages that hold them.

Expected result/shape: Bitmap Heap Scan on orders above Bitmap Index Scan on idx_orders_order_date, with an Index Cond on order_date and Heap Blocks: exact=16, about a quarter of the table. The third plan, country = 'US' on customers, also uses a bitmap scan but visits all 9 heap pages, so the index saves nothing there.

Learning objectives#

  • Match a B-tree index to equality, range, and ordering requirements.
  • Explain a planner choice using selectivity, table size, projection, and measured cost.

Vocabulary and concepts#

  • Selectivity: the fraction of rows a predicate is expected to return.
  • Index scan: an access path that uses index entries to locate heap rows.
  • Index-only scan: a plan that can satisfy selected values from the index, subject to visibility checks.

Deep dive and reference#

What you will learn#

  • Create B-tree indexes for equality and range predicates.
  • Observe planner choices before and after an index exists.
  • Explain why a valid index can remain unused on a small or unselective query.

How the learner script uses the current schema#

Inside a rollback-only transaction, the script creates indexes on orders.total_amount, orders.order_date, and customers.country. It then executes matching filters with EXPLAIN ANALYZE. No course index persists after the final ROLLBACK.

B-tree is PostgreSQL's default and supports equality, ranges, ordering, IN and IS NULL. It serves an anchored pattern such as LIKE 'abc%' only in the C collation or through a text_pattern_ops index. The classroom's advanced_sql_training database uses the en_US.utf8 collation (check with SELECT datcollate FROM pg_database WHERE datname = current_database();), so a default B-tree on a text column does not help that predicate. A hash index is mentioned only as a contrast; B-tree already handles the equality lookup on customers.email.

Planner and index concepts#

  • Selective predicates benefit most because they fetch a small fraction of the table.
  • Every index adds storage and write/vacuum work. “Index every column” is not a sound policy.
  • An index-only scan also depends on selected columns and visibility-map state.
  • SELECT * can make heap access necessary even when a filter uses an index.
  • On the compact seed, a sequential scan may correctly be cheaper.

What the three learner indexes cost and buy#

Before the ROLLBACK, measure the indexes with pg_relation_size. The two orders indexes are 114,688 bytes each, 14 pages of 8 kB, beside a 65-page table. The customers(country) index is 2 pages beside a 9-page table. Every INSERT into orders now writes three B-trees instead of one heap page and a primary key, and every UPDATE that changes an indexed column writes a new index entry as well.

SELECT
  indexrelid::regclass AS index_name,
  pg_relation_size(indexrelid) / 8192 AS pages
FROM
  pg_index
WHERE
  indexrelid::regclass::text LIKE 'idx_%';

The plans show what that cost buys. A bitmap scan works in two passes: the Bitmap Index Scan walks the B-tree and marks every page that holds a match, then the Bitmap Heap Scan reads those pages once each in physical order. Recheck Cond is printed because a bitmap can become lossy under memory pressure; with Heap Blocks: exact=... no recheck was needed.

The two bitmap plans in the learner file differ in what they save. The 209 recent orders sit on 16 of the 65 orders pages, so the index lets PostgreSQL skip three quarters of the table. The 63 US customers are customer_id 1, 9, 17 and so on, one in every eight rows, so they appear on all 9 customers pages. That plan reads the index and then the whole table, and a sequential scan would have cost about the same. pg_stats.correlation for customers.country is 0.12, close to zero: the physical order of rows says almost nothing about the country order.

Pitfalls and validation#

  • Use only the setup's valid order statuses: placed, paid, shipped, delivered, and returned.
  • Do not disable sequential scans as proof that an index is beneficial.
  • Index names are schema-local; use exercise-specific names to avoid collisions.
  • The learner transaction rolls all index experiments back safely.

Expanded practice lab#

Prompts 3-6 separate index eligibility from a planner's cost decision. First measure category frequency: on a compact table, reading every page can be cheaper than bouncing through an index. Use a half-open timestamp range for the payment-date index so boundary semantics are explicit.

lower(country) is a different indexed expression from country; an expression index must match the query expression. Finally, remember that an index's physical order never replaces ORDER BY in the SQL result contract.

  • Clause check: The block drops Exercise 1's index, plans the query, re-creates the index and plans it again. On this seed both plans are Seq Scan on products over 3 buffers; only the planning buffers differ.
  • Alternative/trade-off: Planning with EXPLAIN alone would skip execution and still show whether the index is chosen; ANALYZE, BUFFERS adds the 3-page read count that explains why it is not.
  • Edge case: Two identical plans are the expected outcome here, not a failed experiment. Record them as evidence that the table is too small for this index to matter.

Pitfalls#

  • Do not use SET enable_seqscan = off as proof that an index is useful; it changes the planner's choices instead of demonstrating normal behavior.
  • A B-tree handles equality and ordered range predicates, so a hash index is rarely needed for a basic equality lookup.
  • Index names share a schema namespace, which is why the solution uses unique, exercise-specific names.
  • Indexes created in the learner script are rolled back at the end of that script and are not available on later days.

Exercise 4: Index a timestamp range#

The solution indexes payment_date and uses [start, end) bounds. Half-open windows compose cleanly without double-counting a boundary timestamp.

Reasoning and verification#
  • Inputs/evidence: For sql-32 Exercise 4, read payments (3,836 rows on 29 pages), create idx_payments_date_solution on payment_date, and plan SELECT payment_id, amount for the half-open window payment_date >= CURRENT_TIMESTAMP - interval '180 days' AND payment_date < CURRENT_TIMESTAMP.
  • Expected result/shape: For sql-32 Exercise 4, expected output: a Bitmap Heap Scan on payments over a Bitmap Index Scan on idx_payments_date_solution with both bounds in the Index Cond, 1,340 actual rows on this load, and Heap Blocks: exact=29. The final columns are payment_id, and amount.
  • Independent verification: For sql-32 Exercise 4, confirm the same window counted without EXPLAIN matches the plan's actual rows (1,340 on this load), and that the two adjacent half-open windows of 180 to 90 days and 90 to 0 days ago add up to it (632 + 708); then on VALUES (timestamp '2026-01-01 00:00:00') confirm BETWEEN places that instant in both one-day windows that meet at midnight, while >= start AND < end places it only in the later one.
  • Intermediate relation check: payments has 3,836 rows on 29 pages, and the 180-day window keeps about 1,340 of them. Count them without EXPLAIN first.
  • Clause check: The plan is a Bitmap Heap Scan on payments over a Bitmap Index Scan on idx_payments_date_solution, with both bounds in the Index Cond and Heap Blocks: exact=29.
  • Alternative/trade-off: BETWEEN start AND end includes both ends, so two adjacent windows would count a payment at the shared boundary twice. >= start AND < end assigns each instant to exactly one window.
  • Edge case: The bitmap scan visits all 29 heap pages, so it saves almost nothing over a sequential scan on this table. A 7-day window would touch far fewer pages.

Exercise 5: Match an expression index#

An index on country does not store lower(country). The solution indexes that exact expression and repeats it exactly in the predicate.

Reasoning and verification#
  • Inputs/evidence: For sql-32 Exercise 5, read customers (500 rows, country codes stored in uppercase), create idx_customers_lower_country_solution on the expression lower(country), and plan SELECT customer_id FROM customers WHERE lower(country) = 'us'.
  • Expected result/shape: For sql-32 Exercise 5, expected output: a Bitmap Heap Scan on customers over a Bitmap Index Scan on idx_customers_lower_country_solution with Index Cond: (lower(country) = 'us'::text), an estimate of rows=2, and 63 actual rows. The final columns are customer_id.
  • Independent verification: For sql-32 Exercise 5, confirm COUNT(*) with lower(country) = 'us' and with country = 'US' both return 63; then, inside BEGIN ... ROLLBACK, show that a plain index on customers (country) alone leaves the plan as Seq Scan on customers with Filter: (lower(country) = 'us'::text), and that running ANALYZE customers after creating the expression index raises its estimate from rows=2 to rows=63.
  • Intermediate relation check: SELECT COUNT(*) FROM customers WHERE lower(country) = 'us' returns 63, the same as country = 'US', because every stored code is uppercase.
  • Clause check: The plan uses Bitmap Index Scan on idx_customers_lower_country_solution with Index Cond: (lower(country) = 'us'::text), but estimates rows=2 against 63 actual rows.
  • Alternative/trade-off: If the data is always uppercase, country = 'US' with a plain index on country is simpler. The expression index is for input you cannot normalize.
  • Edge case: The rows=2 estimate is the default guess for an expression without statistics. Run ANALYZE customers; after creating the index and the estimate becomes 63, because ANALYZE gathers statistics on indexed expressions too.

Exercise 6: Preserve the ordering contract#

The unordered query is intentionally nondeterministic. Only the query with ORDER BY country, customer_id promises reproducible presentation order; an index's incidental scan order is not a substitute.

Reasoning and verification#
  • Inputs/evidence: For sql-32 Exercise 6, read customers twice with LIMIT 10: once with no ORDER BY, as a control, and once with ORDER BY country, customer_id; no index is created for this answer.
  • Expected result/shape: For sql-32 Exercise 6, expected output: 10 rows from each query; the unordered control happens to return customers 1 to 10 cycling through US, CA, GB, DE, FR, IN, AU, and BR, while the ordered query returns the first ten of the 62 AU customers, ids 7, 15, 23, 31, 39, 47, 55, 63, 71, and 79. The final columns are customer_id, and country. The final order is country, customer_id.
  • Independent verification: For sql-32 Exercise 6, confirm the ordered ids match SELECT customer_id FROM customers WHERE country = 'AU' ORDER BY customer_id LIMIT 10; then, inside BEGIN ... ROLLBACK, run UPDATE customers SET country = country WHERE customer_id = 1 and confirm the unordered control now returns ids 2 to 11 while the ordered query still returns 7 through 79.
  • Intermediate relation check: The unordered query happens to return customers 1 to 10, cycling through US, CA, GB, DE, FR, IN, AU and BR, which is insertion order and nothing more.
  • Clause check: The ordered query sorts by country, then customer_id, and returns ten AU customers: 7, 15, 23 and so on, every eighth id.
  • Alternative/trade-off: An index on (country, customer_id) could return the ordered rows without a sort, but the ORDER BY must stay; the index only makes it cheaper.
  • Edge case: After an UPDATE moves some rows to new pages, the unordered query can return a different ten rows. The ordered one cannot, because customer_id breaks every tie.

When the category index starts to win#

The products answers keep a sequential scan because the table is three pages. To see the same index chosen, build a throwaway table 1,000 times larger inside a transaction, with one rare category added:

BEGIN;
CREATE TEMP TABLE big_products AS
SELECT
  g AS product_id,
  CASE WHEN g % 1000 = 0 THEN
    'Garden'
  ELSE
    (ARRAY['Apparel', 'Beauty', 'Books', 'Electronics', 'Home', 'Sports'])[1 + g % 6]
  END AS category
FROM
  generate_series(1, 300000) AS g;

CREATE INDEX ON big_products (category);

ANALYZE big_products;

EXPLAIN (
  ANALYZE,
  BUFFERS
)
SELECT
  product_id
FROM
  big_products
WHERE
  category = 'Garden';

ROLLBACK;

The table is 1,664 pages. 'Garden' matches 300 rows, and the bitmap scan reads 3 index pages plus the 300 heap pages that hold them, about a fifth of the table. 'Electronics' matches 50,000 rows; the planner still picks a bitmap scan, but it touches 1,622 of the 1,664 pages, so almost all of the saving is in skipping the filter check on the other 250,000 rows. The same index is a big win for the rare value and a small one for the common value. That is the selectivity argument from the third answer, made visible.
