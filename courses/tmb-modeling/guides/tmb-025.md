# From an empty template to a reviewed model

Start with: tmb-024.

Outcome: Separate generated scaffolding from a scientifically complete likelihood.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter checks a declared data and parameter schema. In the separately prepared [owned project](../projects/tmb-local/README.md), `tests/public_api.R` prints the scaffold from `TMB::template()` and the interface that `TMB::Rinterface()` derives from `models/normal_mean.cpp`; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

TMB provides authoring helpers, but scaffolding is not a finished model. `template(file=NULL)` supplies a starting C++ structure; a file argument writes a scaffold. `Rinterface(file)` examines an existing C++ template and produces an R-side skeleton. `runExample()` lists installed examples, and a named example can compile and execute package-provided source in a chosen working area.

These functions are valuable for discovering interfaces. Their output still needs data, parameter starts, domain checks, normalized probability terms, independent numerical references and provenance. The classroom's original models are written independently rather than copied from package examples.

## Key terms

- **template():** A TMB helper that supplies a minimal C++ starting structure, or writes it to a file when one is named.
- **Rinterface():** A helper that reads an existing C++ template and generates an R-side skeleton for its data and parameters.
- **runExample():** A helper that lists installed package examples or compiles and runs a named one in a chosen working area.
- **Scaffold:** Generated starting code that still lacks data, starting values, domain checks, normalized densities and independent numerical references.

### Worked case A: design the interface before the loop

The companion creates a schema for a regression model: response length, design dimensions, parameter dimensions and intended report quantities. The numerical objective follows only after that schema agrees. For a native authoring session in a disposable directory:

```r
TMB::template(file = "new_model.cpp")
TMB::Rinterface("new_model.cpp")
```

Inspect the actual generated text before running it. A scaffold containing `DATA_VECTOR` tells you what type is expected, but it does not tell you whether missing observations should be rejected, modeled or filtered. Likewise, a declared scale parameter does not establish whether its input is a standard deviation, variance or logarithm.

### Worked case B: package example versus your experiment

A package example can demonstrate a compiler or API feature under its own assumptions. It is not evidence that your new dataset or custom likelihood is correct. The companion compares two input schemas with the same response length but different predictor meanings. Reusing a skeleton without updating the interpretation can produce a valid matrix multiplication for the wrong model.

`runExample(name=..., thisR=..., clean=..., exfolder=..., dontrun=...)` has process and cleanup options. Read their pinned documentation before use, choose an owned disposable directory, and never point cleanup at learner data. Package-provided examples retain their own licensing. No package example source is copied into this book.

### Answered discussion

**Does generating an R interface generate trustworthy starting values?** No. Starts need to respect units, constraints and data range. **Should I invoke every package example as a release test?** Only if it tests a declared capability and its resource/dependency contract is understood. Our numerical acceptance is intentionally based on small original models. **What should be reviewed first?** The observation model, source declarations and tiny known-value calculation, before parallelism or optimization tuning.

See [template, Rinterface and runExample in the pinned manual](https://cran.r-project.org/web/packages/TMB/TMB.pdf). The [API inventory](../API-REFERENCE.md) records exact public signatures and separates helpers from runtime acceptance.

### Worked case C: from the schema to declarations

The companion's schema says the response `y` has length 4, the design has columns `intercept` and `time` with 4 rows, and the parameters are a length-2 `beta` and a scalar `log_sigma`. Each line of that schema maps onto one declaration in a reviewed template:

```cpp external
#include <TMB.hpp>
template <class Type> Type objective_function<Type>::operator()() {
  DATA_VECTOR(y);         // schema: response, length 4
  DATA_MATRIX(X);         // schema: design, 4 rows, columns intercept and time
  PARAMETER_VECTOR(beta); // schema: beta, length 2, same order as X columns
  PARAMETER(log_sigma);   // schema: scalar on the log scale
  Type sigma = exp(log_sigma);
  vector<Type> mu = X * beta;
  Type nll = -sum(dnorm(y, mu, sigma, true));
  REPORT(mu);
  return nll;
}
```

This is a sketch of what review should produce, not output from `TMB::template()`. The generated scaffold does not know that `X` has exactly two columns, that their order must match `beta`, or that `log_sigma` is a logarithm of a standard deviation rather than a variance. Those three facts come from the schema, and the companion's `stopifnot` line enforces two of them in R before any compilation: response length equals design rows (4 = 4), and the `beta` length equals the number of design columns (2 = 2).

The second check in the companion prints `same_shape = TRUE` and `same_meaning = FALSE` for the alternative columns `intercept` and `temperature`. The template above would compile and evaluate against that design without complaint, because `X * beta` only needs a 4 by 2 matrix. The fitted slope would then be a temperature effect stored under a name a reader expects to be a time trend. Shape agreement is a necessary check that the C++ side can perform; meaning agreement must be carried by column names held in R and compared before the objective is built.

### What a reviewer still adds after the scaffold

Three decisions are absent from any generated skeleton. First, the observation density: `dnorm(..., true)` is normalized, so the objective includes the \(\tfrac12\log(2\pi)\) constant per observation and can be compared with an independent R log likelihood. Second, missing-value policy: a `NA` in `y` would propagate into `nll` and the optimizer would see a non-finite value, so validation belongs before construction. Third, a tiny known-value check: with `beta = (0, 0)`, `log_sigma = 0` and `y = (1, 2, 4, 7)`, the objective is \(2\log(2\pi) + 70/2 = 3.675754 + 35 = 38.675754\) (hand-derived), which a reviewer can compare with R's `-sum(dnorm(y, 0, 1, log = TRUE))` before trusting any optimization.

### Base-R companion (runs in the classroom)

```r
schema <- list(response = list(name = "y", length = 4L), design = list(columns = c("intercept", "time"), rows = 4L), parameters = list(beta = 2L, log_sigma = 1L))
stopifnot(schema$response$length == schema$design$rows, schema$parameters$beta == length(schema$design$columns))
print(schema)
other_columns <- c("intercept", "temperature")
print(c(same_shape = length(other_columns) == length(schema$design$columns), same_meaning = identical(other_columns, schema$design$columns)))
```
