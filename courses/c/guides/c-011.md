# c-011: Scope, storage duration and object lifetime

## Level and prerequisites

Beginner, approximately 90 minutes plus a later retrieval session. Direct prerequisites: `c-010`

## Learning objectives

## Purpose and mental model

Scope determines where a name is visible; lifetime determines when its object exists. They are related but different. An automatic local object usually lasts until its block ends. A static-storage object exists for the program duration even when its name is visible only inside one function. Allocated storage has a lifetime controlled by allocation and release, taught next. A pointer does not extend any of these lifetimes automatically. Returning an automatic local address is invalid after return, while returning a static object address can be valid but introduces shared mutable state and reentrancy concerns.

## Vocabulary and concepts

- **Scope:** The region where a name can be used.
- **Storage duration:** The category governing how long storage is retained.
- **Reentrancy:** Whether an operation can be entered again without corrupting shared execution state.

## Syntax anatomy and execution trace

A block can shadow an outer variable with the same name. static inside a function preserves one object across calls and zero-initializes it before execution. A file-scope static declaration also restricts linkage to the translation unit. These are different uses of the same keyword. Keep automatic variables explicitly initialized before reading them. Do not use the value of a pointer after its target lifetime has ended.

## Worked example / walkthrough

### Worked example 1: Trace block shadowing

Declare an outer value 3 and a separate inner value 7.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int next_count(void) {
  static int count = 0;
  count++;
  return count;
}
const int *static_value(void) {
  static const int value = 7;
  return &value;
}
int local_count(void) {
  int count = 0;
  count++;
  return count;
}

int main(void) {
  /* Trace block shadowing */
  {
    int value = 3;
    {
      int value = 7;
      CHECK(value == 7);
    }
    CHECK(value == 3);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** After the inner block, the outer remains 3.

The names are the same but designate distinct objects. Shadowing can be legal while still reducing readability.

### Worked example 2: Retain static state

Call a function with one static counter twice.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int next_count(void) {
  static int count = 0;
  count++;
  return count;
}
const int *static_value(void) {
  static const int value = 7;
  return &value;
}
int local_count(void) {
  int count = 0;
  count++;
  return count;
}

int main(void) {
  /* Trace block shadowing */
  {
    int value = 3;
    {
      int value = 7;
      CHECK(value == 7);
    }
    CHECK(value == 3);
  }

  /* Retain static state */
  {
    CHECK(next_count() == 1);
    CHECK(next_count() == 2);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** It returns 1 and then 2.

The counter is initialized once and survives function returns. This shared state would require synchronization if called concurrently.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
