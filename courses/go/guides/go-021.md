# go-021: Command-line contracts and configuration precedence

## Level and prerequisites

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-020

## Learning objectives

Implement a command-line interface with flag that applies explicit precedence and rejects unknown or invalid options. Along the way, explain precedence, flag set, validation boundary; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A command-line interface translates external strings into validated application configuration. Defaults, flags, environment and configuration files need an explicit precedence order; silently mixing them creates surprising deployments. Parse configuration once at the boundary and pass a typed value to the program. The browser pad has no arbitrary argument channel, so this lesson uses an isolated flag.FlagSet with synthetic argument slices. This exercises the real parser without changing the process global flags. A production CLI also needs clear help, stable exit codes, redacted diagnostics and a documented distinction between malformed input and runtime failure.

## Vocabulary and concepts

- **Precedence:** The declared order in which configuration sources override one another.
- **Flag set:** An isolated collection of command-line options.
- **Validation boundary:** The point where external input becomes trusted typed configuration.

## Syntax anatomy and reasoning

flag.NewFlagSet with ContinueOnError returns parse failures instead of exiting the process. IntVar binds a flag to storage, Parse accepts a []string and Args returns positional leftovers. SetOutput can redirect diagnostics to a buffer for tests. Do not call os.Exit from a library helper, because it prevents its caller from controlling cleanup and testing. Validate ranges after parsing: the parser can accept a negative integer even if the domain forbids it.

## Worked example / walkthrough

### Worked example 1: Apply an explicit flag

Parse -count=3 with a default of 1.

```go
package main

import (
	"errors"
	"flag"
	"fmt"
	"io"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func parseArgs(args []string) (int, []string, error) {
	f := flag.NewFlagSet("lesson", flag.ContinueOnError)
	f.SetOutput(io.Discard)
	n := 1
	f.IntVar(&n, "count", 1, "positive count")
	if err := f.Parse(args); err != nil {
		return 0, nil, err
	}
	if n < 1 {
		return 0, nil, errors.New("positive count required")
	}
	return n, f.Args(), nil
}

func main() {
	// Apply an explicit flag
	{
		n, args, err := parseArgs([]string{"-count=3"})
		check(err == nil && n == 3 && len(args) == 0, "flag")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The resulting count is 3.

The synthetic argument slice tests the actual parser while remaining independent of the classroom process arguments.

### Worked example 2: Retain a default

Parse no arguments.

```go
package main

import (
	"errors"
	"flag"
	"fmt"
	"io"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func parseArgs(args []string) (int, []string, error) {
	f := flag.NewFlagSet("lesson", flag.ContinueOnError)
	f.SetOutput(io.Discard)
	n := 1
	f.IntVar(&n, "count", 1, "positive count")
	if err := f.Parse(args); err != nil {
		return 0, nil, err
	}
	if n < 1 {
		return 0, nil, errors.New("positive count required")
	}
	return n, f.Args(), nil
}

func main() {
	// Apply an explicit flag
	{
		n, args, err := parseArgs([]string{"-count=3"})
		check(err == nil && n == 3 && len(args) == 0, "flag")
	}

	// Retain a default
	{
		n, _, err := parseArgs(nil)
		check(err == nil && n == 1, "default")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The count remains 1.

A default is an intentional contract, not an accidental zero value. Changing it can alter existing workflows even when parsing code is unchanged.

## Common pitfalls and diagnosis

Two command-line mistakes recur. Calling the global flag.Parse from a library or test makes behavior depend on process state and can exit on a bad flag; use a FlagSet with ContinueOnError. The second is skipping validation after parsing: the flag package checks syntax, not that a count is positive. Document the precedence of defaults, environment and flags instead of letting the last writer win by accident.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Apply an explicit flag: change one input

1. Restate the expected observation: The resulting count is 3.
2. The flag value overrides the default. What do n and the remaining arguments hold?
3. The edited arguments parse to n equal to 4, so `n==3` fails while err is nil. Parsing works; the input no longer matches the claim.

### Hint for investigation 2: Retain a default: diagnose an edited check

1. Restate the expected observation: The count remains 1.
2. With no arguments the default stands. Which value does parsing leave in n?
3. Parsing no arguments succeeds, so err is nil and `err!=nil` is false. The default path is a success path; the check must require `err==nil`.

### Hint for investigation 3: Reject an unknown option

1. Restate the expected observation: Parsing returns an error.
2. ContinueOnError returns errors instead of exiting. What does an undefined flag produce?
3. Unknown-flag rejection catches misspellings.

### Hint for investigation 4: Preserve positional arguments

1. Restate the expected observation: The remaining argument is input.csv.
2. Flag parsing stops at the first non-flag argument. What does f.Args() return?
3. Flags and positional arguments have distinct roles.

### Hint for investigation 5: Reject a domain-invalid count

1. Restate the expected observation: The operation returns a domain error.
2. The flag syntax is valid. Which rule after parsing rejects -1?
3. Successful integer parsing does not imply an acceptable concurrency, retry or item-count budget.

### Hint for investigation 6: Transfer precedence

1. Restate the expected observation: The explicit setting wins.
2. An explicit flag is applied after the default. Which value wins?
3. In a larger program, document whether flags override environment or files.
