## Why this mechanism matters

A function separates a computation from its callers. Its contract names accepted inputs, returned values, mutation and failure. Go passes arguments by value. For an integer this copies the integer; for a slice it copies a descriptor whose backing storage may still be shared. Multiple return values make a result plus error a normal language pattern. Named return variables are real local variables, not a replacement for clear control flow. A pure function depends only on its inputs and does not mutate shared state, which usually makes boundary tests simpler. Design the contract before deciding whether a pointer or a collection is convenient.

## Vocabulary and concepts

- **Parameter:** A local variable initialized from an argument value.
- **Pure function:** A function whose result depends only on its inputs without external mutation.
- **Precondition:** An input requirement checked before calculation.

## Syntax anatomy and reasoning

func twice(x int) int declares a parameter and a return type. return ends the invocation. (int, error) declares two returned values, which callers normally bind together and check before using the result. A variadic parameter ...int accepts zero or more values; within the function it is a slice. A return from a helper returns only from that helper, not the caller.

## Worked example / walkthrough

### Worked example 1: Implement a pure helper

Implement twice and check inputs 7 and 0.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func twice(x int) int { return 2 * x }
func positiveArea(w, h int) (int, error) {
	if w <= 0 || h <= 0 {
		return 0, errors.New("positive dimensions required")
	}
	return w * h, nil
}
func reassign(x int) { x = 99 }
func bounds(a, b int) (int, int) {
	if a < b {
		return a, b
	}
	return b, a
}
func total(values ...int) int {
	n := 0
	for _, v := range values {
		n += v
	}
	return n
}

func main() {
	// Implement a pure helper
	{
		check(twice(7) == 14 && twice(0) == 0, "twice")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** The results are 14 and 0.

The zero case confirms the helper calculates from its input rather than returning a memorized positive result.

### Worked example 2: Return an explicit failure

Implement positiveArea that rejects a nonpositive dimension.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func twice(x int) int { return 2 * x }
func positiveArea(w, h int) (int, error) {
	if w <= 0 || h <= 0 {
		return 0, errors.New("positive dimensions required")
	}
	return w * h, nil
}
func reassign(x int) { x = 99 }
func bounds(a, b int) (int, int) {
	if a < b {
		return a, b
	}
	return b, a
}
func total(values ...int) int {
	n := 0
	for _, v := range values {
		n += v
	}
	return n
}

func main() {
	// Implement a pure helper
	{
		check(twice(7) == 14 && twice(0) == 0, "twice")
	}

	// Return an explicit failure
	{
		area, err := positiveArea(3, 4)
		check(err == nil && area == 12, "area")
		_, err = positiveArea(0, 4)
		check(err != nil, "invalid area")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** 3 by 4 returns 12; zero width returns an error.

The error describes a domain policy. Another geometry API might allow zero area, but its contract must say so.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
