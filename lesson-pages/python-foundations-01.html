Read a Program, Trace Its State, and Predict Its Output#

Stable ID: python-foundations-01

Estimated time: 120 minutes, split across sessions as needed.

Level and prerequisites#

Foundation. Direct catalog prerequisites: python-01.

You only need to open a Python file, run the course interpreter, and find its terminal output. This module introduces names, assignment, strings, numbers, and prediction before Day 2 adds more types. You do not need loops, functions, or a notebook.

Learning objectives#

  • Distinguish source text, a running program, and terminal output.
  • Trace the value attached to each name after every executed line.
  • Separate a number from text that displays the same digits.
  • Use tiny predictions and fresh runs to diagnose state mistakes.

Vocabulary and concepts#

A program is a list of instructions stored as text. Running the file asks an interpreter to perform those instructions. Reading a line does not execute it, and changing the file does not retroactively change a run that already ended. Imagine a desk with labeled notes: a name tells you which note to read, while assignment replaces the value that the label currently refers to. Keep a trace table on paper with one row per executed line. This is useful even when the program is too short to need a debugger.

  • Source code: the text instructions you edit and save in a .py file.
  • Value: a piece of data, such as the number 4 or the text "four".
  • Name: a label, such as quantity, that currently refers to a value.
  • Assignment: an instruction using = that binds the left name to the evaluated right side. It is an action, not an algebraic equality claim.
  • Expression: source that evaluates to a value, such as quantity + 2.
  • Output: information a running program writes, commonly through print.

Python normally performs these top-level statements from top to bottom. A blank line creates visual space. A line starting with # is a comment for a reader. A comment is not an instruction, so writing the expected answer in a comment cannot make an incorrect calculation pass. Choose descriptive names; number_of_boxes helps a future reader more than x when boxes are the topic.

Worked example / walkthrough#

Example A: replacement does not update earlier calculations#

Predict both printed numbers before running this complete example:

quantity = 3
unit_price = 4
subtotal = quantity * unit_price
quantity = 5
print(subtotal)
print(quantity * unit_price)

The right side of subtotal = quantity * unit_price is evaluated when that line runs. * multiplies two numbers. Python stores the resulting value under subtotal; it does not store an automatically updating spreadsheet formula. The later assignment changes quantity but does not re-execute the earlier line. print(...) calls a built-in display operation; parentheses surround the value to display. The expected output is 12 on one line, then 20. Your trace should show subtotal staying at 12 after quantity changes.

Example B: text and numbers obey different operations#
number = 4
text = "4"
print(number + 2)
print(text + "2")
print(type(number).__name__)
print(type(text).__name__)

Expected output is 6, 42, int, and str, in that order. Quotes create text; the quotes themselves are not part of the stored text. + adds numbers but joins strings. type(value).__name__ asks the interpreter for a readable type label; treat it as an inspection tool for now. A type describes what operations a value supports. Removing quotes changes meaning, even if the terminal displays similar digits. Do not try to memorize every type today.

A reliable trace routine#

Read a single statement, identify the names on its right side, substitute their current values, and calculate that expression. Only then update the left name. For a print, write an output row without changing other rows. If a name has never been assigned in the current run, stop: the interpreter cannot invent its intended value. A saved file run starts a new process with new top-level state. A notebook can keep old state between cells, so a fresh file run is a useful reference when cell results look surprising.

Before each exercise, create two columns labeled prediction and observation. A disagreement is useful evidence. Locate the first line where the trace differs, rather than making several edits until an answer looks plausible. Re-running with identical input should produce identical output for every example here. If it does not, first check that you saved and ran the same file.

Exercises#

  1. Trace a reassignment. Trace apples = 2; pears = apples + 3; apples = 9 as three separate lines. Do not run until your trace is complete. State both final values.

Verify: apples equals 9 and pears equals 5; the trace records pears being calculated before apples changes.

Hint: A name stores the current result, not the history of its formula.

  1. Separate calculation from display. Create boxes = 4, items_per_box = 6, and a calculated items. Display a human-readable label followed by the value. Repeat with zero boxes.

Verify: The terminal contains totals 24 and 0 in the two runs; changing the label does not change either calculated number.

Hint: Use print("Items:", items) to display a label and a value.

  1. Predict text joining. Predict the output of "3" + "7" and of 3 + 7. Explain how you can prove the difference if the output alone is confusing.

Verify: The first value equals the string "37"; the second equals integer 10. Inspection reports str and int respectively.

Hint: Quotes are part of the source language that creates a string.

  1. Find the first invalid line. In a fresh script, put print(balance) before balance = 10. Capture the final exception line, then make the smallest ordering change that permits a run.

Verify: Before repair the exception class is NameError; after repair a fresh run prints 10 exactly once.

Hint: Walk through time, not the visual distance between lines.

  1. Test a stale calculation. Calculate total = 2 * 5, change the quantity to 3 under a separate name, and compare the old total with a new calculation. Do not edit the expected values to hide a disagreement.

Verify: Your trace contains an old total of 10 and a recomputed total of 15, and identifies the line that recalculates the result.

Hint: Assign quantity before using it, then explicitly repeat the calculation.

  1. Distinguish comments from actions. Add a comment that predicts a total of 100 beside code that actually calculates 4 * 5. Run the file, then repair the comment while preserving correct code.

Verify: The output remains 20 before and after the comment repair; your observation names the multiplication as the executed operation.

Hint: A comment can be wrong without causing an exception.

  1. Make a minimal reproduction. Copy just the three statements needed to show that copied = original for an integer keeps its old value after original is reassigned. Use original values 8 and 11.

Verify: The new script prints original 11 and copied 8, with no dependency on previous interactive commands.

Hint: Copied here is another name for the earlier integer value; mutable containers come later.

  1. Transfer the trace to a receipt. Starting with three tickets at seven units each and a two-unit discount on the whole order, calculate the payable amount. Then test no tickets and no discount. Use clear names.

Verify: The normal payable value is 19; the empty-order value is 0. A written trace explains why the discount is applied once to the order.

Hint: Write the intended arithmetic in plain language before translating it.

Self-check#

Close the examples. Explain why changing a quantity does not update an earlier subtotal. Recreate a three-line trace using different numbers. Then describe what quotes, =, and parentheses contribute to the statements you typed. Read your prediction before running, rather than reconstructing it afterward.

Common pitfalls#

If the output looks unchanged after editing, save the file and inspect the terminal command's filename. If NameError appears, read the named identifier and find its first assignment in execution order. If text joins when you expected arithmetic, inspect the two operand types. If a notebook disagrees with a script, restart its kernel and run cells in order before modifying the calculation. These checks distinguish a state problem from a setup problem.

Next step#

Continue with Day 2, where you add conversions, Boolean values, comparisons, and formatting. Keep the trace habit for branches and loops. It remains useful when a future program has many more lines.

Read a Program, Trace Its State, and Predict Its Output: solution reasoning#

Stable ID: python-foundations-01.

Read the guide and attempt the learner artifact first. The executable solution is a comparison implementation. It does not certify your changed program merely because its own demonstration succeeds. Copy the acceptance cases into your attempt, then change one input without changing the intended policy.

The useful result of this lesson is an accurate model of execution order. Eight correct terminal values without an explanation would miss that goal. The runnable solution uses straight-line statements so it works before loops or user-defined functions have been introduced. Its assertions compare actual values with independent expected numbers. An assertion is a check that raises an error when its condition is false; the next lessons will explain its full testing role. Never change a correct expected value simply to silence it.

apples = 2
pears = apples + 3
apples = 9
assert (apples, pears) == (9, 5)

Exercise 1. Trace a reassignment#

After the first line, apples refers to 2. The second line reads that 2, adds 3, and binds pears to 5. The final line replaces apples with 9. Pears remains 5 because there is no later assignment to it. A common false trace writes pears as 12 by treating Python as a spreadsheet. Record the values at the time each statement executes. Compare the observed pair (9, 5) with your written prediction and explain the first disagreement rather than only copying the final pair.

Exercise 2. Separate calculation from display#

Use meaningful names for both inputs and keep the calculation separate from its presentation. Four boxes with six items each gives 24; zero boxes gives 0 under the same multiplication rule. print("Items:", items) combines display arguments without converting the stored number into text. Replacing the label with another phrase cannot affect multiplication. A useful extra probe changes items per box to one. That distinguishes a real input-based formula from accidentally typing the expected result as a constant.

Exercise 3. Predict text joining#

Quotes create the strings "3" and "7". Joining them produces the two-character string "37". The unquoted integers are added to produce 10. Inspecting type names verifies the operation domain independently of how the terminal renders digits. Do not use the visual appearance of a value as proof that it is numeric. Later, explicit conversion will turn suitable digit strings into numbers. For now, preserve the distinction and explain why adding an integer to a string would need a declared conversion decision.

Exercise 4. Find the first invalid line#

A new script has no earlier balance assignment. The first print(balance) therefore raises NameError and stops execution before reaching the assignment below it. Move balance = 10 above the print, then run the saved file again. The output is 10 once. Moving the print is also valid if it preserves the intended order. An interactive session that already contains balance can hide this defect; a fresh process is the important boundary check. Capture the exception class, not a machine-specific absolute filename.

Exercise 5. Test a stale calculation#

The initial multiplication produces 10. Changing a quantity later changes only that name, so the stored total remains 10. A second multiplication using quantity three and unit price five produces 15. The reference explicitly performs that second calculation and verifies both totals. This behavior is useful when preserving an earlier snapshot, but surprising when expecting a live total. The fix is to decide which state you need and calculate at the correct time. Re-running only a display statement cannot recompute an earlier expression.

Exercise 6. Distinguish comments from actions#

The interpreter ignores the comment. It multiplies four by five and displays 20 regardless of whether the nearby comment incorrectly predicts 100. Repair the explanation to match observed behavior without changing a correct formula. Comments help humans and can become stale independently from code. This exercise teaches two kinds of review: running a check proves what the program did on that input, while reading the explanation checks whether the prose accurately describes it. Neither kind of evidence completely replaces the other.

Exercise 7. Make a minimal reproduction#

Assign original to 8, assign copied from original, and then reassign original to 11. Both assignments initially refer to the integer value 8; the final reassignment changes only original. The comparison result is (11, 8). This is about immutable integer values and rebinding names. Do not generalize it into a claim that assignment deeply copies every Python object. Lists and other mutable containers can share state, a separate topic in the data-structure lessons. A minimal reproduction deliberately excludes irrelevant input or display code.

Exercise 8. Transfer the trace to a receipt#

Three tickets at seven units each costs 21. Subtracting the whole-order discount once gives 19. A line-by-line trace should show a subtotal followed by a payable amount, rather than hiding both operations in an unexplained constant. For no tickets and no discount the same arithmetic gives zero. If a future business rule disallows negative totals, that becomes an explicit branch and boundary test. It is not implied here. State the current input assumptions and avoid adding policies that the exercise did not request.

Compare and transfer#

Change the receipt to four tickets at five units with a three-unit order discount. Predict the subtotal 20 and payable amount 17 before running. Explain which earlier values remain unchanged if you later reassign ticket count. If your script and notebook disagree, use a fresh run as evidence and inspect execution history before changing arithmetic.
