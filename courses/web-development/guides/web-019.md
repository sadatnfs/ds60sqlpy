# web-019: Pseudo-classes, pseudo-elements and stateful styling

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-018`

## Learning objectives

Build a preferences list whose selected state is visible and semantic. Explain why CSS state cannot authorize a server action. Use pseudo-class, pseudo-element and attribute selector accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

A pseudo-class selects an element based on a condition such as focus, checked state or its position among siblings. A pseudo-element represents a stylable part associated with an element, such as before or after. Generated decorative content can enrich presentation, but essential instructions should exist as real document content because generated content has inconsistent accessibility implications.

State should remain grounded in a real control or application contract. Styling a checkbox's checked state makes use of built-in behavior. A decorative class named active does not prove that a control is selected, and CSS cannot perform server authorization. Use native state first and add custom state only with a clear interaction model.

### Key terms

- **Pseudo-class:** A selector keyword after one colon, such as `:hover` or `:checked`, that matches elements by state or position.
- **Pseudo-element:** A selector after two colons, such as `::before`, that styles part of an element or content generated for it.
- **Attribute selector:** A selector such as `[aria-current="page"]` that matches elements by the presence or value of an attribute.
- **Focus-within:** The `:focus-within` pseudo-class, which matches an element when it or any descendant has focus.
- **User-invalid:** The `:user-invalid` pseudo-class, which matches an invalid control only after the user has interacted with it.

## Syntax anatomy and mechanism

`:focus-within` matches a container while one of its descendants has focus. `input:checked + span` selects a neighboring label fragment after a checked input. Attribute selectors can target a declared state, but the application is responsible for keeping that state accurate. `:has()` selects an element by what it contains, so `.field:has(input:user-invalid)` styles a whole field group when its input is invalid. `:user-invalid` matches only after the person has interacted with the control, unlike `:invalid`, which also matches an untouched required field on page load. `:is()` takes the specificity of its most specific argument, while `:where()` always contributes zero specificity, which makes it useful for easily overridden defaults. Hover must be an enhancement because touch and keyboard interactions may not provide the same hover behavior.

## Worked example / walkthrough

### Worked example 1: A focused group and an invalid field

The container helps the user locate the current task and shows an error only after interaction.

```css
.field:focus-within {
  border-color: #0753a4;
}
.field:has(input:user-invalid) {
  border-color: #9c3200;
}
```

**Expected observation:** The field group changes while its descendant is focused, and turns to the error color only after the user has left the input in an invalid state.

### Worked example 2: A native checked state

The checkbox remains the actual control.

```css
input:checked + span {
  font-weight: 700;
}
```

**Expected observation:** The adjacent label becomes bold when checked.

## Contrast case: an instruction that exists only in generated content

Both fields look the same on screen. Copy the page text and inspect the accessibility tree for each one.

```html
<style>
  .hint-a::before {
    content: "Use your student number. ";
  }
</style>
<p class="hint-a"></p>

<p id="hint-b">Use your student number.</p>
<input aria-describedby="hint-b" />
```

The first instruction is painted by `::before`, so it does not exist in the DOM text. Copying the page omits it, some assistive technology announces it inconsistently, and if the stylesheet fails to load the instruction disappears. The second is a real paragraph that also becomes the input's description through `aria-describedby`. Keep generated content for decoration such as icons or separators, and put anything a person must read into HTML.

## Six progressive exercises

Exercises that ask you to predict, explain, compare or diagnose keep their answers in the solutions file. The others show the evidence to look for.

### Exercise 1: Distinguish a condition selector from generated content.

**Progressive hint:** Ask whether the selector matches an element that already exists or styles a part that has no element.

### Exercise 2: Add focus-within feedback around a labeled input.

**Expected evidence:** The group is highlighted while the control has focus.

**Progressive hint:** Wrap the label and input in one container and style the container with :focus-within.

### Exercise 3: Build a preferences list whose selected state is visible and semantic.

**Expected evidence:** Native checkboxes carry the state and text styling reinforces it.

**Progressive hint:** Use native checkboxes and style the adjacent label text with :checked + span.

### Exercise 4: Remove an essential instruction placed only in ::before and restore it as HTML.

**Expected evidence:** The instruction becomes real document content available independently of generated decoration.

**Progressive hint:** Move the instruction text into the HTML and keep ::before only for decoration.

### Exercise 5: Operate the controls without hover.

**Expected evidence:** All actions and state information remain usable by keyboard and touch.

**Progressive hint:** Use only Tab, Space and Enter, then try a touch screen without hover.

### Exercise 6: Explain why CSS state cannot authorize a server action.

**Progressive hint:** Ask who controls the CSS once the page reaches the browser.

## Debugging and common mistakes

A hover-only menu can exclude keyboard users. Generated text can be skipped or announced unexpectedly. Keep meaningful text in the document and let CSS reinforce it.

Keep the failing source, the viewport width and what you observed, then repair one cause at a time. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order, so inspect the element and its computed styles in the browser's developer tools instead of trusting the rendering alone.
