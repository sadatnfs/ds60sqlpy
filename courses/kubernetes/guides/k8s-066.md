# k8s-066: Networking capstone: publish, protect, trace and recover

## Level and prerequisites

Advanced; about 120 minutes. Direct prerequisites: `k8s-065`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Produce a complete architecture and acceptance packet.
- Teach the system and defend its evidence limits.

## Purpose, vocabulary and mental model

The final networking project asks you to explain one complete application path and its failure boundaries. The application has a Deployment, an internal Service, a deliberately prepared external routing layer, TLS where the chosen lab supports it, and a narrow network policy. Every capability must be named rather than assumed.

Start with the synthetic fixture and produce a design packet even when no advanced cluster is available. A live extension requires an explicitly owned target, installed controller support, an enforcing network implementation and a reviewed resource ledger. A source-only design is valuable, but it must not be labeled as an executed production deployment.

The strongest learning outcome is independent diagnosis. You should be able to trace a request, identify a wrong selector or port, distinguish readiness from process state, explain public versus internal addresses, and recover from one controlled failure while preserving data and cleanup ownership.

### Key terms

- **Design packet:** The capstone's written design, with a diagram, manifests, ownership ledger, checks and limitations that align.
- **Resource ledger:** A reviewed list of every object to create, its owner and how it is cleaned up.
- **Acceptance matrix:** A table of checks across source validation, admission, controller conditions, endpoints, requests, policy flows, rollout and cleanup.
- **Controlled fault:** Exactly one field changed in a copied source, used to show that the checks detect it and that recovery works.
- **Cleanup ownership:** Deleting only the resources recorded as owned by the exercise, so shared objects survive.

## Mechanism and field-by-field reasoning

Build an acceptance matrix across source validation, API admission, controller conditions, endpoint identity, internal request, external request, allowed/denied policy flows, rollout revision and cleanup. Mark unavailable capabilities explicitly. No row is automatically implied by another.

Use the same source and object identities throughout a run. Record a fresh response from the intended revision after a repair. For stateful extensions, add independent data recovery evidence rather than assuming network success preserves records. The capstone is a bounded learning project, not a certificate of universal Kubernetes expertise.

## Trace the request or control path

```text
client -> DNS -> external listener/TLS -> HTTP route -> Service -> ready Pod -> response
policy gates intended flows; observability links request and resource identities
controlled failure -> localized diagnosis -> targeted repair -> fresh acceptance -> owned cleanup
```

The first line is the full request ladder from client to response, and every arrow needs a named component and a piece of evidence. The second line runs beside it: policy decides which arrows may exist, and observability ties a request to resource identities. The third line is the incident loop the capstone rehearses, ending with owned cleanup.

## Worked example / walkthrough

### Worked example 1: Prepare the acceptance matrix

This is a template, not a claim that the rows passed.

```text
source/manifest validation
controller and API capability
current ready endpoint UIDs
internal app request
external DNS/TLS/route request
allowed and denied policy flows
new revision after rollout
UID-aware owned cleanup
```

**Expected observation:** Each row needs actual evidence or an explicit not-run boundary.

### Worked example 2: Choose one controlled fault

The exercise changes exactly one field in a copied source.

```text
fault: Service targetPort points to 8081 while app listens on 8080
observe: endpoints/ports and failed request
repair: restore intended target mapping
recheck: fresh response from current revision
```

**Expected observation:** The repair addresses the identified mismatch without broadening exposure or permissions.

## Run boundary and the owned host lab

The capstone uses every networking fixture together: deployment and service for the internal hop, ingress or gateway for the edge, network-policy for isolation and topology.json for the client cases. Run the checker from the [fixture README](../fixtures/networking/README.md) first as the baseline. Then mark each acceptance row as passed with live evidence, synthetic only, or not run because the capability is missing.

The [fixture checker](../fixtures/networking/README.md) makes no API calls; on Windows use WSL 2.

```sh
: "${LAB_KUBECONFIG:?Use the private path from the owned receipt}"
: "${LAB_CONTEXT:?Use the exact context from the owned receipt}"
: "${LAB_NAMESPACE:?Use the namespace from the owned receipt}"
kubectl --kubeconfig "$LAB_KUBECONFIG" --context "$LAB_CONTEXT" --namespace "$LAB_NAMESPACE" get deployment,service,networkpolicy -l course-fixture=deep-networking -o custom-columns=KIND:.kind,NAME:.metadata.name,UID:.metadata.uid,GENERATION:.metadata.generation
```

This read builds the ownership ledger: kind, name, UID and generation for each retained fixture object. Cleanup later compares against these UIDs, never just names or labels. Add Ingress or Gateway rows only if those APIs exist in your lease. Read rules: [owned live reads](../STUDY-GUIDE.md#owned-live-reads).

## Six progressive exercises

### Exercise 1: Predict the entire request path with address and port roles.

**Expected evidence:** Every hop names its caller, destination and responsible component.

**Progressive hint:** Start at the client and stop at the response body. Each arrow needs a caller, a destination and an owner.

### Exercise 2: Classify available and unavailable lab capabilities.

**Expected evidence:** Controllers, policy enforcement, dual-stack and external routing are explicit.

**Progressive hint:** For each row of the fixture README's capability table, ask whether this lab has it. Missing ones become explicit rows.

### Exercise 3: Produce a complete architecture and acceptance packet.

**Expected evidence:** Diagram, manifests, ownership ledger, checks and limitations align.

**Progressive hint:** Check that diagram, manifests, ledger and checks name the same objects, ports and limits.

### Exercise 4: Diagnose and repair the single target-port fault.

**Expected evidence:** The first incorrect mapping is found and a fresh request verifies repair.

**Progressive hint:** Compare the Service's targetPort with the container's named port. The first mismatch you find is the fault.

### Exercise 5: Verify isolation with both positive and negative flows.

**Expected evidence:** Allowed traffic succeeds and the denied owned case fails under an enforcing CNI.

**Progressive hint:** Use one allowed and one denied client case from topology.json, both under a plugin known to enforce policy.

### Exercise 6: Teach the system and defend its evidence limits.

**Expected evidence:** Explain mechanisms, current results, untested platforms and scoped cleanup.

**Progressive hint:** Teach from the packet: which results are live, which are synthetic and which platforms you never tested.

## Diagnosis, failure boundaries and common mistakes

Capstones fail on evidence more often than on YAML. Marking a row passed because the object was created confuses API acceptance with traffic. Another mistake is repairing the target-port fault while also restarting Pods and widening the policy; the fresh request then no longer proves which change fixed it. Test isolation with a denied flow as well as an allowed one. During cleanup, delete by recorded UID through the reviewed procedure, never by namespace or by a broad label such as course-fixture.

General evidence rules: [diagnosis rules](../STUDY-GUIDE.md#diagnosis-rules).
