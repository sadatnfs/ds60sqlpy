# go-026: Select, contexts and cancellation trees

## Level and prerequisites

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-025

## Learning objectives

Combine select with context cancellation and deadlines so that work stops promptly and reports why. Along the way, explain context tree, deadline, cooperation; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Cancellation is cooperative: a context signals that work should stop, but does not forcibly interrupt every function. Pass context as the first parameter to work whose lifetime belongs to its caller. Derived contexts form a tree, so canceling a parent cancels descendants. Always call the returned cancel function when the owned operation ends, including early success, to release associated resources. A select can wait for work or cancellation, but if both cases are ready its choice is not a priority rule. Check required preconditions explicitly when already-canceled work must never begin.

## Vocabulary and concepts

- **Context tree:** Parent-child cancellation relationships.
- **Deadline:** An absolute time after which work is no longer wanted.
- **Cooperation:** An operation checking and respecting a stop signal.

## Syntax anatomy and reasoning

context.WithCancel returns a child and cancel function. Done closes on cancellation; Err explains cancellation or deadline expiry. WithDeadline accepts a past time for deterministic testing. A select arm receiving from ctx.Done cooperates with cancellation. Context values carry request-scoped metadata, not optional function arguments, authentication guarantees or mutable application state.

## Worked example / walkthrough

### Worked example 1: Cancel a child

Create a cancelable context and cancel it.

```go
package main

import (
	"context"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Cancel a child
	{
		ctx, cancel := context.WithCancel(context.Background())
		cancel()
		check(ctx.Err() == context.Canceled, "cancel")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Err returns context.Canceled.

Cancellation is visible through Err and the closed Done channel. Repeated cancel calls are safe.

### Worked example 2: Propagate parent cancellation

Derive a child and cancel its parent.

```go
package main

import (
	"context"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Cancel a child
	{
		ctx, cancel := context.WithCancel(context.Background())
		cancel()
		check(ctx.Err() == context.Canceled, "cancel")
	}

	// Propagate parent cancellation
	{
		parent, cancel := context.WithCancel(context.Background())
		child, stop := context.WithCancel(parent)
		defer stop()
		cancel()
		check(parent.Err() == context.Canceled && child.Err() == context.Canceled, "tree")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Both contexts become canceled.

A child cannot extend work beyond the lifetime requested by its parent.

## Exercises

### Exercise 1: Cancel a child: predict an edited check

Copy worked example 1, change `check(ctx.Err() == context.Canceled, "cancel")` to `check(ctx.Err() != context.Canceled, "cancel")` inside its check and predict whether it still passes; then restore it.

**Expected:** The edited check panics with `cancel` even though `ctx.Err() == context.Canceled` still holds.

**Verify:** Restoring `check(ctx.Err() == context.Canceled, "cancel")` makes the check pass again with the worked observation: err returns context.Canceled.

### Exercise 2: Propagate parent cancellation: diagnose an edited check

A careless edit rewrote the check in worked example 2 as `check(parent.Err() != context.Canceled && child.Err() == context.Canceled, "tree")`. Explain the failure, then restore it.

**Expected:** The defective run panics with `tree`; after restoring `check(parent.Err() == context.Canceled && child.Err() == context.Canceled, "tree")`, both contexts become canceled.

**Verify:** The edited check fails with message `tree` for a state that `parent.Err() == context.Canceled && child.Err() == context.Canceled` accepts.

### Exercise 3: Keep child cancellation local

Cancel a child of a live parent.

**Expected:** The child is canceled; the parent is unchanged.

**Verify:** Your solution must keep `child.Err() != nil && parent.Err() == nil` true. Control: changing `check(child.Err() != nil && parent.Err() == nil, "child")` to `check(child.Err() == nil && parent.Err() == nil, "child")` panics with message `child`; revert it.

### Exercise 4: Test an expired deadline

Construct a context with a deadline at Unix time zero.

**Expected:** Err is context.DeadlineExceeded.

**Verify:** Your solution must keep `ctx.Err() == context.DeadlineExceeded` true. Control: changing `check(ctx.Err() == context.DeadlineExceeded, "deadline")` to `check(ctx.Err() != context.DeadlineExceeded, "deadline")` panics with message `deadline`; revert it.

### Exercise 5: Refuse already canceled work

Call a helper that checks its context before calculation.

**Expected:** It returns cancellation without a result.

**Verify:** Your solution must keep `v == 0 && err == context.Canceled` true. Control: changing `check(v == 0 && err == context.Canceled, "refusal")` to `check(v != 0 && err == context.Canceled, "refusal")` panics with message `refusal`; revert it.

**Expected:** It returns 8 without error.

## Common pitfalls and diagnosis

Contexts are cooperative, so the common mistake is assuming cancellation interrupts work: a function that never checks ctx.Err or ctx.Done keeps running. Another is discarding the cancel function, which leaks timers and children until the parent ends; go vet reports this. Do not store a context in a struct for later calls, and do not use context values for ordinary optional parameters.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Cancel a child: predict an edited check

1. Restate the expected observation: Err returns context.Canceled.
2. Calling cancel marks the context done. Which sentinel does Err report afterward?
3. After cancel, Err is exactly context.Canceled, so `!=` is false and the check panics. The context behaves correctly; the edited comparison asserts the opposite.

### Hint for investigation 2: Propagate parent cancellation: diagnose an edited check

1. Restate the expected observation: Both contexts become canceled.
2. Cancellation flows from parent to child. What do both Err calls return?
3. Canceling the parent sets its Err to context.Canceled, so `parent.Err()!=context.Canceled` is false and the tree check fails. Restore `==` for the parent too.

### Hint for investigation 3: Keep child cancellation local

1. Restate the expected observation: The child is canceled; the parent is unchanged.
2. Canceling a child never reaches upward. What does the parent's Err return?
3. Cancellation propagates downward.

### Hint for investigation 4: Test an expired deadline

1. Restate the expected observation: Err is context.DeadlineExceeded.
2. A deadline in the past is already expired. Which sentinel does Err report?
3. The past deadline avoids flaky sleeps.

### Hint for investigation 5: Refuse already canceled work

1. Restate the expected observation: It returns cancellation without a result.
2. contextValue checks Err before computing. What does it return for a canceled context?
3. A preflight check expresses the already-canceled policy.

### Hint for investigation 6: Transfer successful work

1. Restate the expected observation: It returns 8 without error.
2. With a live context the check passes. What is twice 4?
3. Long loops or I/O must cooperate during work as well.
