# dbt-014: Documentation, catalogs, exposures and ownership

## Level and prerequisites

Advanced. Direct prerequisites: `dbt-003`, `dbt-004`

**Outcome:** Build documentation that joins observed structure with authored meaning and ownership.

## Question and mechanism

Documentation has both structural and semantic parts. A database catalog can identify a column's physical type, while a project description explains what the value means. Neither substitutes for the other. A field named total needs a grain, unit, time window and inclusion policy before a consumer can interpret it reliably.

The first case generates real dbt documentation artifacts after building a mart. The catalog records the observed database column, and the manifest records a declared exposure depending on that mart. An exposure represents a downstream use such as a dashboard or application. It improves lineage and ownership visibility, but it does not prove that an external consumer is currently healthy or actually using the declared version.

The second case demonstrates a structurally documented but semantically undescribed model. Its integer type is available, yet its description is empty. A documentation build can therefore succeed while important meaning remains absent. Treat generated artifacts as a foundation for review, not an automatic substitute for authored definitions.

## Syntax and data contract

docs generate inspects the built project and writes catalog.json alongside manifest.json. Model and column descriptions live in schema metadata. An exposure names its type, owner and ref-based dependencies. The classroom inspects these JSON artifacts locally; it does not start a separate docs web server or claim that arbitrary generated HTML is a trusted worker result.

## Run the lesson

Open this subject in `/classroom`, then show its code and notes. The prepared `data-engineering` worker runs `main.py` in a fresh temporary directory. The examples use installed packages and synthetic local fixtures; no account, cloud service, network request or package download is required. Save source and notes before switching lessons. Temporary databases, project files and tracking artifacts are recreated by each complete program and removed after the job. The classroom retains the submitted source and bounded output, not an indefinitely running external service. The guide distinguishes this local execution from the deployment decisions that need an owned production environment.



## Worked case 1: Connect physical and declared information

The first case checks a total column in the catalog and the exposure's dependency in the manifest. It combines observed database structure with declared project meaning without confusing the two.

**Expected evidence:** The catalog contains total and the decision-report exposure depends on mart.

```python
import json
import os
import tempfile
from pathlib import Path

import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def artifact(root, name):
    return json.loads((root / "target" / name).read_text())


def example_one():
    with tempfile.TemporaryDirectory() as d:
        schema = {
            "models": [
                {
                    "name": "mart",
                    "description": "One total for this synthetic fixture.",
                    "columns": [{"name": "total", "description": "Sum of declared amount values."}],
                }
            ],
            "exposures": [
                {
                    "name": "decision_report",
                    "type": "dashboard",
                    "depends_on": ["ref('mart')"],
                    "owner": {"name": "Classroom team"},
                }
            ],
        }
        p = project(
            d,
            models={"mart": "select sum(amount)::bigint as total from {{ ref('orders') }}"},
            seeds={"orders": "id,amount\n1,5\n2,7\n"},
            schema=schema,
        )
        invoke(p, "build")
        invoke(p, "docs", "generate")
        catalog = artifact(p, "catalog.json")
        manifest = artifact(p, "manifest.json")
        assert "model.classroom.mart" in catalog["nodes"]
        assert "total" in catalog["nodes"]["model.classroom.mart"]["columns"]
        exposure = manifest["exposures"]["exposure.classroom.decision_report"]
        assert exposure["depends_on"]["nodes"] == ["model.classroom.mart"]
        return {"catalog_column": "total", "exposure_dependency": "mart"}


if __name__ == "__main__":
    print(example_one())
```

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Write a complete definition

Describe total with its grain, units and inclusion rule.

**Check:** A reader can interpret the quantity without guessing.

**Hint:** A column name alone is insufficient.


### 2. Add a downstream consumer

Declare a second exposure with its owner and dependency.

**Check:** The new edge appears in the manifest.

**Hint:** Use ref-based lineage.


### 3. Inspect physical type

Read the catalog's type for a column.

**Check:** It matches the built database representation.

**Hint:** Compilation alone does not create the catalog observation.


### 4. Find an undocumented field

Create a model column without a description.

**Check:** The documentation gap remains visible.

**Hint:** Success of docs generate is not prose completeness.


### 5. Separate lineage from execution

Explain what an exposure cannot establish.

**Check:** It cannot prove the external dashboard ran successfully.

**Hint:** Declared relationships differ from runtime observations.


### 6. Export a compact review record

Select useful metadata from the generated artifacts.

**Check:** The record contains meaning, ownership and dependency identifiers.

**Hint:** Do not dump an entire large manifest into a user message.


## Diagnose errors and misleading results

A missing catalog node may mean the model was not materialized or the wrong environment was inspected. An empty description is an authored-content gap. An exposure pointing to the wrong model is a lineage defect even if the database query succeeds. Diagnose these separately.

## Transfer to independent work

Build documentation that joins observed structure with authored meaning and ownership. Review a consumer's dependency and record which claims are declarations versus runtime evidence. This creates a useful handoff for analysts, data scientists and operators.
