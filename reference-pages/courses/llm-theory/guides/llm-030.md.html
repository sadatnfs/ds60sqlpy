llm-030: Pretraining data provenance and evaluation contamination#

Status: authored beta content. The manifest inventories complete teaching files; runtime readiness remains a separate, measured property.

Level and prerequisites#

Advanced; approximately 120 minutes. Direct prerequisites: llm-029. The prerequisite sequence introduces the notation used here; revisit its worked examples if an axis, probability or gradient is unfamiliar.

Learning objectives#

Specify provenance and removal policies before training or evaluating on collected text. The central investigation is concrete: Build a manifest for local authored snippets with source, permission, split and duplicate-family fields; analyze a benchmark-answer contamination case. The finish condition is All fixture documents have provenance and a split. Benchmark answers and derived paraphrases are excluded from the training/selection source set. A useful explanation connects the calculation to the reason it is needed, rather than treating a function name as a definition.

Purpose and mental model#

Pretraining data provenance records where a document came from, what use is permitted and how it enters the experiment. A filename or download timestamp alone cannot answer these questions. Evaluation contamination includes exact benchmark answers and derived paraphrases entering training or selection sources. Deduplication helps but does not establish permission, privacy or semantic independence. The local fixture contains authored snippets so no external collection or permission decision is required. The goal is to design a reviewable manifest and identify when a source should be excluded or investigated, not to issue legal conclusions about an unknown corpus.

Vocabulary and concepts#

Provenance: A record of origin and transformations for a data item.

Permission field: An explicit documented basis or unresolved status for use.

Derived contamination: Assessment information entering through paraphrases or transformed copies.

How to run this lesson#

Use the reading worksheet. Write a reasoned response for each case; no execution or model download is required.

Start by reading Example A without running it. Write the intermediate quantities and their units on paper. Run the entire example in a fresh process, not only the final line in a notebook with hidden variables. Example B changes an assumption that matters to this mechanism. Compare both observations before starting independent work. An assertion failure is a request to inspect an assumption, not a reason to widen every tolerance. For float64 arithmetic use an absolute tolerance of 1e-12 unless an exercise gives another bound. TensorFlow and PyTorch float32 comparisons use 1e-6. Integer counts, identities and boolean decisions should be exact.

Syntax anatomy and reasoning sequence#

A useful record has document_id,source,permission,split,family andcontent_hash. Source identifies origin; permission records an explicit basis or unresolved status. Split states intended information use. Family groups related derivatives. Audit the complete dependency path, including tokenizer fitting and prompt selection, because contamination can occur before gradient training.

Common pitfalls and diagnosis#

When a result disagrees, locate the first intermediate value that violates this explanation. Inspect shapes and identities before aggregates, and inspect counts before averages. Preserve the original fixture and introduce only one controlled change at a time. If an arithmetic identity passes but a data-boundary condition fails, the experiment is still invalid. If a runtime is unavailable, record the unexecuted code as unverified rather than replacing its output with the expected text. The separate explanation discusses why the tempting alternative in each case changes the result.
