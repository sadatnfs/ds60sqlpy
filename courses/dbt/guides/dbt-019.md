# dbt-019: Targets, environments and owned database routing

## Level and prerequisites

Advanced. Direct prerequisites: `dbt-003`, `dbt-014`

**Outcome:** Run a project against an explicitly identified owned target and verify its actual destination.

## Question and mechanism

A target selects a named execution environment from a profile. A project can use the same model definitions while changing database or schema routing and other adapter settings. That flexibility must not turn into ambient selection of a valuable database. Every example here uses one newly created local DuckDB file; dev and prod are synthetic schema labels inside it.

The first case builds the same model into separate schemas and returns target.name as data so the routing is visible. The result demonstrates environment selection without implying that two schemas in one file provide the isolation, access control or durability of independent production systems.

The second case requests an undefined target and expects failure. Falling back silently to another environment would make the observation ambiguous and could be dangerous in a real project. Keep target identity, database ownership and credentials explicit, and separate source configuration from secrets when adapting the project outside the classroom.

## Syntax and data contract

profiles.yml defines named outputs and a default target. --target chooses an output explicitly. target.name is available during template compilation and can be useful for bounded environment logic, but core business semantics should not drift accidentally between environments. The example changes schema routing while preserving the declared calculation.

## Worked case 1: Observe explicit routing

The project builds into dev and prod schemas in the same owned file. Each relation reports its selected environment and the answer 42. Both are queried independently after execution.

**Expected evidence:** dev.answer and prod.answer contain the corresponding target label and 42.

```python
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def targets(p):
    config = yaml.safe_load((p / "profiles.yml").read_text())
    original = config["classroom"]["outputs"]["dev"]
    config["classroom"]["outputs"] = {
        name: {**original, "schema": name} for name in ("dev", "prod")
    }
    (p / "profiles.yml").write_text(yaml.safe_dump(config))


def example_one():
    with tempfile.TemporaryDirectory() as d:
        p = project(
            d, models={"answer": "select '{{ target.name }}' as environment, 42::integer as answer"}
        )
        targets(p)
        invoke(p, "build", "--target", "dev")
        invoke(p, "build", "--target", "prod")
        assert rows(p, "select environment,answer from dev.answer") == [("dev", 42)]
        assert rows(p, "select environment,answer from prod.answer") == [("prod", 42)]
        return {"same_file_owned_test_database": True, "separate_schemas": ["dev", "prod"]}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Reject an unknown environment

The second case names a target absent from the profile. The invocation must fail without creating a successful run-results artifact. This preserves uncertainty rather than guessing which output was intended.

**Expected evidence:** The unknown target is rejected before a successful model run.

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Inspect the destination

Identify the exact file and schema selected for each target.

**Check:** Both are owned local fixtures.

**Hint:** A target name alone is not a destination.


### 2. Preserve calculation semantics

Return the same numeric result in both targets.

**Check:** The result remains 42.

**Hint:** Routing and business logic are different concerns.


### 3. Change the default

Select another default target but still pass --target explicitly.

**Check:** The explicit selection wins for the invocation.

**Hint:** Inspect the actual command.


### 4. Reject missing configuration

Remove an output and attempt to select it.

**Check:** The command fails clearly.

**Hint:** No fallback is appropriate.


### 5. Separate secrets

Describe how real credentials should be supplied.

**Check:** They are outside maintained public fixtures and logs.

**Hint:** The classroom profile needs no secrets.


### 6. Compare isolation claims

Explain what two schemas in one file do not establish.

**Check:** They do not provide independent failure domains or access control.

**Hint:** Namespacing is one mechanism.


## Diagnose errors and misleading results

If a model appears in the wrong place, inspect target selection and generated schema naming before editing SQL. If credentials are missing in an external project, use the approved environment setup rather than copying secrets into the model. Stop when destination ownership is unclear.

## Transfer to independent work

Run a project against an explicitly identified owned target and verify its actual destination. Preserve calculation semantics across routing changes, reject unknown environments and document the additional isolation requirements of real deployments.
