# c-001: Source, compilation, linking and checked execution

## Level and prerequisites

Beginner, approximately 90 minutes plus a later retrieval session. Direct prerequisites: None. Begin with the difference between source text, a compiler and a running process.

## Learning objectives

Explain translation unit, linker, assertion. Implement the six investigations with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

C source is text describing declarations and operations. The preprocessor handles directives, the compiler translates a translation unit, and the linker combines machine-code objects with required libraries. The executable is a separate artifact from main.c. A syntax error prevents compilation; an unresolved symbol prevents linking; an assertion can fail only after execution begins. These stages require different diagnoses. C does not automatically validate every runtime memory operation, so successful compilation is a starting point rather than a safety proof. Begin with independently checked scalar results before learning pointers and resource ownership.

## Vocabulary and concepts

- **Translation unit:** The source after preprocessing, compiled as one unit.
- **Linker:** The tool resolving references among compiled objects and libraries.
- **Assertion:** An explicit runtime check of a claimed property.

## Syntax anatomy and execution trace

#include makes header declarations available. int main(void) is an entrypoint with no parameters; returning zero signals successful termination. Braces form a block and semicolons finish most statements. printf formats values, while puts writes a string plus a newline. assert from assert.h checks a condition when NDEBUG is not defined. %d expects an int, and a mismatched format argument can be undefined behavior.

## Worked example / walkthrough

### Worked example 1: Check a first value

Store 2 plus 3 in an int.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int seven(void) { return 7; }

int main(void) {
  /* Check a first value */
  {
    int total = 2 + 3;
    CHECK(total == 5);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** The stored value is 5.

The expectation is known independently of the program. A print statement alone would not reject a wrong calculation.

### Worked example 2: Format a checked result

Format total=5 into a bounded character buffer.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

int seven(void) { return 7; }

int main(void) {
  /* Check a first value */
  {
    int total = 2 + 3;
    CHECK(total == 5);
  }

  /* Format a checked result */
  {
    char out[16];
    int n = snprintf(out, sizeof out, "total=%d", 5);
    CHECK(n == 7);
    CHECK(strcmp(out, "total=5") == 0);
  }
  puts("Worked example checks passed.");
  return 0;
}

```

**Observe:** The result length is 7 and text is total=5.

snprintf returns the length that would be required, excluding the terminating null byte. A caller must compare it with capacity before treating output as complete.

## Prediction before execution

Trace each object from initialization through its last valid use. Write down the size of every array, the capacity of every output buffer and the ownership of any allocated storage. Distinguish a compiler diagnostic from a valid runtime rejection and from undefined behavior. Never execute an out-of-bounds access, dangling-pointer read or data race simply to discover what value it happens to print.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
