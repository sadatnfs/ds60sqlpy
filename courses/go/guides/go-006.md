# go-006: Maps, presence and deterministic ordering

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-005

## Learning objectives

Distinguish a missing map key from a stored zero value and produce a deterministic report from map data. Along the way, explain key, presence bit, deterministic order; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A map associates keys with values. Reading an absent key returns the value type's zero value, which can be indistinguishable from a present key whose value is zero. The comma-ok form retains the presence information. Map iteration order is deliberately unspecified; reproducible reports must extract and sort keys rather than rely on an observed order. Maps share mutable storage when assigned, and ordinary maps are not safe for concurrent mutation without synchronization. A nil map can be read but cannot accept an assignment. Treat these properties as part of the data model when building counters, caches and configuration overlays.

## Vocabulary and concepts

- **Key:** A comparable value identifying a map entry.
- **Presence bit:** The boolean distinguishing an existing entry from absence.
- **Deterministic order:** An explicitly chosen ordering independent of map iteration.

## Syntax anatomy and reasoning

map[string]int declares string keys and integer values. value, ok := counts[key] distinguishes absence from zero. make initializes writable map storage. delete removes a key and is harmless if the key is absent. range gives key/value pairs in an unspecified order. Use sort.Strings on extracted keys before producing ordered output.

## Worked example / walkthrough

### Worked example 1: Distinguish zero from missing

Read present key zero and absent key missing with comma-ok.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Distinguish zero from missing
	{
		m := map[string]int{"zero": 0}
		a, okA := m["zero"]
		b, okB := m["missing"]
		check(a == b && okA && !okB, "presence")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Both values are 0, but only zero is present.

A numeric value alone cannot represent both absence and an intentional zero without losing information.

### Worked example 2: Build a frequency table

Count red, blue and red.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Distinguish zero from missing
	{
		m := map[string]int{"zero": 0}
		a, okA := m["zero"]
		b, okB := m["missing"]
		check(a == b && okA && !okB, "presence")
	}

	// Build a frequency table
	{
		m := map[string]int{}
		for _, v := range []string{"red", "blue", "red"} {
			m[v]++
		}
		check(m["red"] == 2 && m["blue"] == 1, "counts")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** red has count 2 and blue has count 1.

Missing counts start at the zero value, which is useful here because zero is the correct additive identity.

## Common pitfalls and diagnosis

Using `m[k] == 0` to mean absent is the classic map bug: it confuses a stored zero with a missing key, so use comma-ok when presence matters. The second trap is a report or test that passes because the map happened to iterate in one order; Go randomizes iteration deliberately, so sort the keys. Finally, assigning into a nil map panics, so initialize it with make or a literal first.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Distinguish zero from missing: change one input

1. Restate the expected observation: Both values are 0, but only zero is present.
2. An absent key returns the zero value. Which second return value distinguishes it from a stored 0?
3. With the stored value 1, `a` is 1 while the absent read `b` is 0, so `a==b` fails. Presence is unchanged; the zero-value coincidence the check relies on is gone.

### Hint for investigation 2: Build a frequency table: debug a regression

1. Restate the expected observation: red has count 2 and blue has count 1.
2. `m[v]++` on a missing key starts from the zero value. Why is that correct for counting?
3. The first word is now red!, a different key, so red is counted once. The counting logic is fine; the input no longer repeats a word.

### Hint for investigation 3: Sort report keys

1. Restate the expected observation: The first output key is alpha.
2. Map iteration order is unspecified. Which step turns the collected keys into a reproducible order?
3. Sorting makes the presentation contract explicit.

### Hint for investigation 4: Observe assigned map aliasing

1. Restate the expected observation: Both names observe the changed entry.
2. A map variable refers to shared storage. Does `b := a` copy the entries?
3. The assignment does not recursively clone map entries.

### Hint for investigation 5: Remove an absent key safely

1. Restate the expected observation: The map ends empty without a failure.
2. delete on a missing key is defined behavior. What does the map hold after both deletions?
3. Idempotent deletion is helpful for cleanup: repeating the same intent does not introduce a new error for an already absent entry.

### Hint for investigation 6: Transfer nil read behavior

1. Restate the expected observation: The value is 0 and presence is false.
2. A nil map has no storage. Is reading from it allowed, and what does comma-ok report?
3. This safe read does not mean a nil map is writable.
