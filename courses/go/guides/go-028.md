# go-028: Bounded worker pools and result ordering

## Level and prerequisites

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-027

## Learning objectives

Build a bounded worker pool that returns results in input order and leaves no goroutine running. Along the way, explain concurrency bound, task identity, fan-in; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A worker pool limits active execution but does not create infinite capacity. Queues, in-flight tasks and result buffers all consume resources. Give each task an identity so completion order can differ from presentation order. A collector can place results by index to produce a deterministic final sequence. The producer owns input closure, workers process tasks, and a joiner closes results after all senders exit. Cancellation and partial failure need an explicit policy rather than silently losing tasks. This example performs bounded integer work and joins every goroutine. It illustrates coordination without claiming that more workers always make a program faster.

## Vocabulary and concepts

- **Concurrency bound:** The maximum number of active workers.
- **Task identity:** A stable key linking result and input.
- **Fan-in:** Combining results from multiple producers.

## Syntax anatomy and reasoning

A jobs channel carries indexed tasks. Start a bounded number of workers, feed jobs and close input. A WaitGroup tracks workers; close results only after Wait completes. Assign each result to its input index. Reject zero workers before starting the pipeline, otherwise a producer may block forever with no consumer.

## Worked example / walkthrough

### Worked example 1: Preserve input order

Square 3, 1 and 2 with two workers.

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type squareTask struct{ Index, Value int }

func parallelSquares(items []int, workers int) ([]int, error) {
	if workers < 1 || workers > 8 {
		return nil, errors.New("workers must be 1 through 8")
	}
	jobs := make(chan squareTask)
	results := make(chan squareTask)
	var wg sync.WaitGroup
	for i := 0; i < workers; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for task := range jobs {
				task.Value *= task.Value
				results <- task
			}
		}()
	}
	go func() {
		for i, v := range items {
			jobs <- squareTask{i, v}
		}
		close(jobs)
	}()
	go func() { wg.Wait(); close(results) }()
	out := make([]int, len(items))
	for result := range results {
		out[result.Index] = result.Value
	}
	return out, nil
}

func main() {
	// Preserve input order
	{
		v, err := parallelSquares([]int{3, 1, 2}, 2)
		check(err == nil && len(v) == 3 && v[0] == 9 && v[1] == 1 && v[2] == 4, "order")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The result is 9, 1, 4.

Indices restore presentation order. Channel arrival order is not the input-order contract.

### Worked example 2: Handle empty input

Run the pool on an empty slice.

```go
package main

import (
	"errors"
	"fmt"
	"sync"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type squareTask struct{ Index, Value int }

func parallelSquares(items []int, workers int) ([]int, error) {
	if workers < 1 || workers > 8 {
		return nil, errors.New("workers must be 1 through 8")
	}
	jobs := make(chan squareTask)
	results := make(chan squareTask)
	var wg sync.WaitGroup
	for i := 0; i < workers; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for task := range jobs {
				task.Value *= task.Value
				results <- task
			}
		}()
	}
	go func() {
		for i, v := range items {
			jobs <- squareTask{i, v}
		}
		close(jobs)
	}()
	go func() { wg.Wait(); close(results) }()
	out := make([]int, len(items))
	for result := range results {
		out[result.Index] = result.Value
	}
	return out, nil
}

func main() {
	// Preserve input order
	{
		v, err := parallelSquares([]int{3, 1, 2}, 2)
		check(err == nil && len(v) == 3 && v[0] == 9 && v[1] == 1 && v[2] == 4, "order")
	}

	// Handle empty input
	{
		v, err := parallelSquares(nil, 2)
		check(err == nil && len(v) == 0, "empty")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** It returns an empty result and terminates.

Every channel reaches its owned closure point even when no jobs exist.

## Common pitfalls and diagnosis

Appending results in completion order is the usual bug: it passes with one worker and fails intermittently with several. Give each task an index and place results by it. The other common failure is a deadlock from closing results too early, or never, because the closer does not wait for every worker. An unbounded number of workers is not a pool; validate the bound before starting goroutines.

## Progressive hints

### Hint for investigation 1: Preserve input order: change one input

1. Restate the expected observation: The result is 9, 1, 4.
2. Results are placed by Index, not arrival. Which square belongs at position 0?
3. The first input is now 4, so `v[0]` is 16 and `v[0]==9` fails while 1 and 4 stay in place. Ordering is correct; the first input changed.

### Hint for investigation 2: Handle empty input: diagnose an edited check

1. Restate the expected observation: It returns an empty result and terminates.
2. With no jobs, every worker exits at once. What closes results so the collector ends?
3. Empty input is a success, so err is nil and `err!=nil` is false. The pool returns an empty slice without error; restore `err==nil`.

### Hint for investigation 3: Reject absent capacity

1. Restate the expected observation: The call returns an error immediately.
2. The bound is validated before any goroutine starts. What does zero workers return?
3. Validation before goroutine creation prevents a deadlock instead of attempting to recover from it.

### Hint for investigation 4: Compare serial semantics

1. Restate the expected observation: Both produce the same sequence.
2. Placement by index removes timing from the output. Do one and three workers differ?
3. Scheduling changes while the calculation contract stays fixed.

### Hint for investigation 5: Retain duplicate tasks

1. Restate the expected observation: All three results are retained.
2. Each task carries its own index. Are three equal inputs merged into one result?
3. Positional task identity avoids accidentally deduplicating legitimate repeated work.

### Hint for investigation 6: Transfer idle-worker cleanup

1. Restate the expected observation: One result equals 25 and all workers exit.
2. Idle workers exit when jobs closes. How many results does one input produce?
3. Idle workers stop when input closes.
