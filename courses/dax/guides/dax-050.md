## The question and the mechanism

Estimate candidate-table size without confusing a logical table with measured physical work.

A final one-row answer can be produced from a much larger intermediate population. CROSSJOIN forms combinations of its input tables, while grouping observed facts can produce only combinations that actually occur. Before writing an iterator over a virtual table, state its grain and estimate its candidate size.

Our four products and four customers form sixteen possible pairs, but only six distinct product/customer pairs appear in Sales. Adding every one of 731 calendar dates produces 11696 possible product/customer/date combinations, while the eight fact lines contain eight distinct observed combinations at that three-column grain. The gap is a logical cardinality observation, not a claim that an engine necessarily materializes every candidate.

Some queries legitimately require a complete scaffold, including zero-activity cells. Others need only observed combinations. Choosing the smaller table without considering missing and eligible populations can change the answer. Performance review must therefore preserve the intended population before comparing any physical-plan or timing evidence.

## Vocabulary and expression anatomy

CROSSJOIN returns combinations of the supplied distinct dimension values. SUMMARIZE over Sales returns observed fact groups at the specified grain. The output counts are hand-reconciled from the fixture; they are not counters captured from a real query plan.

Concepts to explain in your own words: **materialization**, **CROSSJOIN**, **observed combinations**, **intermediate grain**, **cardinality**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

### Case A: Possible customer/product pairs

**Starting context:** No filters; dimension population 4 products by 4 customers; observed pair grain from Sales.

```dax
EVALUATE ROW ( "CandidatePairs", COUNTROWS ( CROSSJOIN ( VALUES ( Product[ProductKey] ), VALUES ( Customer[CustomerKey] ) ) ), "ObservedPairs", COUNTROWS ( SUMMARIZE ( Sales, Sales[ProductKey], Sales[CustomerKey] ) ) )
```

**Context trace:**

1. The full dimension product is 4 times 4 =16 pairs.
2. Observed pairs are(1,10),(2,10),(3,20),(2,30),(1,20),(3,30).
3. Repeated purchases of the same pair do not add a new pair, leaving six observed groups.

**Hand-derived worked-reference result:**

| CandidatePairs | ObservedPairs |
| --- | --- |
| 16 | 6 |

The ten unobserved pairs may matter for a coverage report even though they contribute no current revenue. Their inclusion is a question of semantics.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Adding a complete calendar dimension

**Starting context:** Whole two-year Date dimension has 731 days; compare possible versus observed product/customer/date cells.

```dax
EVALUATE ROW ( "CandidateCells", COUNTROWS ( CROSSJOIN ( VALUES ( Product[ProductKey] ), VALUES ( Customer[CustomerKey] ), VALUES ( 'Date'[Date] ) ) ), "ObservedCells", COUNTROWS ( SUMMARIZE ( Sales, Sales[ProductKey], Sales[CustomerKey], Sales[OrderDate] ) ) )
```

**Context trace:**

1. The possible-cell count is 4 *4 *731 =11696.
2. Each of the eight sales lines has a distinct product/customer/order-date combination in this fixture.
3. The observed grouping therefore has eight cells.

**Hand-derived worked-reference result:**

| CandidateCells | ObservedCells |
| --- | --- |
| 11696 | 8 |

These are logical table sizes. Engine optimizations may avoid constructing the full product, and a source-only exercise cannot establish the physical materialization or elapsed time.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. The customer dimension still has four members.
2. The selected Date dimension has 31 days.
3. Unobserved combinations can be part of the requested output.
4. Logical expression cardinality is not a captured execution plan.
5. A missing fact group may still represent an eligible unit.
6. Multiply declared dimension sizes before choosing an iterator scaffold.
