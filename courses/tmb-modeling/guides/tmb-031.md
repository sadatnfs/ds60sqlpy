# Simulation APIs and score consistency

Start with: tmb-030, tmb-019.

Outcome: Distinguish generative consistency, estimation bias and approximation bias.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter simulates score statistics with `rnorm`. In the separately prepared [owned project](../projects/tmb-local/README.md), `tests/public_api.R` calls `obj$simulate()` and `TMB::checkConsistency(obj, n = 100)` on the compiled normal model; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

A model's simulation method should generate observations according to the same probability distribution that its likelihood evaluates. A `SIMULATE` block provides that generative code. TMB's `checkConsistency` compares simulation-based score behavior with identities implied by normalized densities and can inspect marginal approximation effects.

Under suitable regularity conditions, the expectation of the score is zero. For NLL \(f_\theta\), this means \(E_\theta[\nabla_\theta f_\theta(Y)]=0\). A missing normalizer can violate this identity even when a fitted curve looks plausible. With random effects, joint score checks and approximate marginal score checks answer different questions.

## Key terms

- **SIMULATE block:** Template code that generates observations from the same probability model the likelihood evaluates, run when `obj$simulate` is called.
- **Score identity:** The fact that the expected gradient of a correctly normalized NLL at the true parameters is zero.
- **checkConsistency:** The TMB function that simulates datasets and tests whether score behavior matches the identity, exposing missing normalizers or simulator mismatches.
- **summary.checkConsistency:** The method that reports detailed joint and marginal results, partly on parameter-bias scales, from a consistency diagnostic.

### Worked case A: centered Gaussian score

The companion simulates datasets from a known normal distribution and computes the mean score at the generating mean. Its average should be close to zero relative to Monte Carlo uncertainty, not literally zero. Increasing replicates reduces simulation error but does not change the model.

In the prepared project, the normal template's `obj$simulate` returns generated `y`; `checkConsistency(obj, n=...)` builds a bounded diagnostic object. `print` and `summary` methods display different levels of detail. Keep the number of simulated datasets and whether each was refitted in the saved record.

### Worked case B: omit a scale normalizer

For a flawed objective containing only squared standardized residuals, the log-scale derivative has negative expectation rather than zero. The companion compares this with the full normal log-scale score \(n-\sum_i r_i^2/\sigma^2\). This is a specific diagnostic failure, not a generic p-value exercise.

The manual cautions that a sufficiently large marginal-score experiment can detect approximation error even for a useful Laplace approximation. `summary.checkConsistency` expresses part of this on parameter-bias scales. A formal rejection is evidence to interpret, not permission to hide failures or widen tolerances until green.

### Answered discussion

**Does `estimate=TRUE` merely print extra output?** It requests repeated fitting and can be much more expensive. **Can a deterministic fixture establish generative consistency?** No. It establishes exact arithmetic on chosen values; simulation tests another layer. **Do print and summary methods rerun estimation?** They summarize an existing diagnostic object; preserve that object and its settings for reproducibility.

The [checkConsistency manual](https://cran.r-project.org/web/packages/TMB/TMB.pdf) documents its beta status. Pin the API and avoid unbounded replicate counts in ordinary learner runs.

### Worked case C: what the three score averages should show

The companion draws 100 datasets of 20 normal observations with \(\mu=1\) and \(\sigma=2\). Each replicate records three quantities, and their theoretical expectations and Monte Carlo standard errors follow from the normal model (hand-derived):

```text
quantity            expectation   sd per replicate          MC standard error (B = 100)
mean_score          0             sqrt(20)/2 = 2.236        0.224
scale_score         0             sqrt(2*20) = 6.325        0.632
missing_normalizer  -20           sqrt(2*20) = 6.325        0.632
```

The printed `rowMeans` should therefore land within a few tenths of 0 for the first row, within roughly one to two units of 0 for the second, and within roughly one to two units of \(-20\) for the third. The second printed vector estimates exactly these standard errors from the simulated replicates. The assertion `mean(scores[3, ]) < -10` leaves a margin of about 16 standard errors, so it is not a fragile seed-dependent test.

The scale score and the flawed derivative differ by exactly \(n=20\), the derivative of the omitted term \(n\log\sigma\). Because \(\sum(y_i-\mu)^2/\sigma^2\) has a chi-square distribution with 20 degrees of freedom, its mean is 20, so the full score averages zero and the flawed one averages \(-20\). An optimizer using the flawed objective would push \(\log\sigma\) without limit toward larger values, since the derivative is negative everywhere.

### The same check in TMB

In a prepared project, the native equivalent asks the template to simulate and then evaluates gradients:

```r
obj <- TMB::MakeADFun(list(y = numeric(20)), list(mu = 1, log_sigma = log(2)), DLL = "normal_mean")
chk <- TMB::checkConsistency(obj, n = 100)
summary(chk)
```

The project's `normal_mean.cpp` has a `SIMULATE` block that redraws each `y(i)` with `rnorm(mu, sigma)` and reports `y`, so its generator matches the likelihood's density. If that block drew from a normal with standard deviation 1 instead of \(\sigma\), the simulated data would disagree with the likelihood, and the scale component of the score test would fail even though the likelihood itself is correct. A failing summary therefore points to two candidate files, the likelihood and the simulator, and the companion's hand-coded scores help decide which one is wrong.

### Bias, not just consistency

`checkConsistency` with `estimate=TRUE` refits each simulated dataset. For this model, the maximum likelihood estimate of \(\sigma^2\) divides by \(n\), so its expectation is \(\tfrac{19}{20}(4)=3.8\) rather than 4 (hand-derived). On the log scale, \(E[\log\hat\sigma]-\log\sigma=\tfrac12[\psi(10)+\log 2-\log 20]=\tfrac12(2.251753+0.693147-2.995732)=-0.025\) (hand-derived), where \(\psi\) is the digamma function. That is estimation bias in a correctly specified model. A summary that reports a small negative bias on `log_sigma` is consistent with the textbook result and does not indicate a broken template.

### Base-R companion (runs in the classroom)

```r
set.seed(3131);n <- 20;B <- 100;mu <- 1;sigma <- 2
scores <- replicate(B, {
  y <- rnorm(n, mu, sigma);c(mean_score = sum(mu - y) / sigma^2, scale_score = n - sum((y - mu)^2) / sigma^2, missing_normalizer = -sum((y - mu)^2) / sigma^2)
})
print(rowMeans(scores));print(apply(scores, 1, sd) / sqrt(B))
stopifnot(mean(scores[3, ]) < -10)
```
