# js-002: Values, coercion and precise comparisons

## Level and prerequisites

Beginner, approximately 90 minutes. Direct prerequisites: `js-001`

## Learning objectives

Predict coercion and equality results, expose floating-point approximation and reject ambiguous numeric input. Along the way, explain coercion, strict equality, safe integer, bigint with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. Exercises 1 and 2 start from the worked examples; the authored investigations begin with this task: Use NaN, +0 and -0 with strict equality and Object.is. The final task tests reject ambiguous numeric input.

## Purpose and mental model

JavaScript values have runtime types, and operators can perform implicit conversion. The plus operator adds numbers but concatenates when string conversion applies. Strict equality avoids the broad coercion of loose equality, but it still has specific semantics for NaN and signed zero. Object.is provides another comparison contract. Choose the relation required by the domain rather than assuming one operator means every notion of same.

Numbers use binary floating-point arithmetic and have a finite safe-integer range. Exact decimal fractions such as 0.1 are generally approximate. BigInt represents arbitrary-size integers but cannot be mixed with Number arithmetic without an explicit conversion policy. null and undefined are distinct values commonly used for absence; neither should be silently converted to a domain count. Validate external numeric text before calculation instead of relying on a convenient coercion.

## Vocabulary and concepts

**Coercion:** An implicit conversion performed by an operator or API.

**Strict equality:** A comparison that does not broadly convert different primitive types.

**Safe integer:** An integer exactly distinguishable within the Number representation.

**BigInt:** An arbitrary-size integer type with separate arithmetic rules.

## Syntax anatomy and execution trace

typeof reports primitive categories but typeof null is the historical string object. Number.isNaN tests NaN without coercing its argument. Number.isFinite rejects non-number values and infinities. Object.is distinguishes +0 and -0 while treating NaN as equal to itself. BigInt literals end in n. JSON does not serialize BigInt by default, so an explicit wire-format policy is needed.

## Worked example / walkthrough

### Example A: Trace plus versus numeric conversion

The same symbol has different behavior when a string participates. Explicit conversion makes the intended numeric operation visible.

```javascript
import { strict as assert } from 'node:assert';

function parseFinite(text) {
  if (typeof text !== 'string' || text.trim() === '')
    throw new TypeError('nonblank numeric text required');
  const value = Number(text);
  if (!Number.isFinite(value)) throw new TypeError('finite number required');
  return value;
}

export async function verify() {
  // Worked example
  {
    assert.equal(2 + 3, 5);
    assert.equal(2 + '3', '23');
    assert.equal(Number('3') + 2, 5);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));
```

**Expected:** 5, string 23, and 5.
### Example B: Inspect absence and NaN

The typeof null result is a language legacy, not evidence that null has usable object properties. Number.isNaN avoids converting arbitrary text.

```javascript
import { strict as assert } from 'node:assert';

function parseFinite(text) {
  if (typeof text !== 'string' || text.trim() === '')
    throw new TypeError('nonblank numeric text required');
  const value = Number(text);
  if (!Number.isFinite(value)) throw new TypeError('finite number required');
  return value;
}

export async function verify() {
  // Worked example
  {
    assert.equal(typeof null, 'object');
    assert.equal(typeof undefined, 'undefined');
    assert.equal(Number.isNaN(NaN), true);
    assert.equal(Number.isNaN('not a number'), false);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));
```

**Expected:** null reports object; undefined reports undefined; only numeric NaN passes isNaN.

## Exercises

1. **Trace plus versus numeric conversion: predict an edited check.** Copy Example A into a scratch `main.mjs` and change `assert.equal(Number('3') + 2, 5);` to `assert.equal(Number('3') + 3, 5);` inside its check. Before running it, predict whether the check still passes and explain why; then restore it.
   **Expected:** The changed run fails with an `AssertionError` at `assert.equal(Number('3') + 3, 5);`. Restoring `assert.equal(Number('3') + 2, 5);` brings back: 5, string 23, and 5.
   **Verify:** Compare your written prediction with the reported `AssertionError`, including its actual and expected values, and explain why the edited check rejects the values that `assert.equal(Number('3') + 2, 5)` accepts. After restoring the line, the program prints its `{"checks":1,"status":"passed"}` receipt again.

2. **Inspect absence and NaN: diagnose an edited check.** A careless edit changed a check in Example B so that it reads `assert.equal(Number.isNaN('not a number'), true);`. Run Example B with that line, explain why the edited check now fails for the same program state, and restore it.
   **Expected:** Before the repair the run fails with an `AssertionError` at `assert.equal(Number.isNaN('not a number'), true);`. Restoring `assert.equal(Number.isNaN('not a number'), false);` brings back: null reports object; undefined reports undefined; only numeric NaN passes isNaN.
   **Verify:** Keep the failing and the repaired runs. Explain why the edited check rejects the same program state that `assert.equal(Number.isNaN('not a number'), false)` accepts.

3. **Compare equality contracts.** Use NaN, +0 and -0 with strict equality and Object.is.
   **Expected:** NaN!==NaN; Object.is(NaN, NaN) is true; +0===-0; Object.is distinguishes zeros.
   **Verify:** Keep a check equivalent to `assert.equal(NaN === NaN, false)`. As a control, change `assert.equal(NaN === NaN, false);` to `assert.equal(NaN !== NaN, false);` inside it: the run must fail with an `AssertionError`, which shows the check can fail. Restore it.

4. **Expose floating-point approximation.** Add 0.1 and 0.2 and compare with 0.3 under an explicit tolerance.
   **Expected:** strict equality false; absolute error below 1e-15.
   **Verify:** Keep a check equivalent to `assert.ok(Math.abs(value - 0.3) < 1e-15)`. As a control, change `const value = 0.1 + 0.2;` to `const value = 0.1 - 0.2;`: the run must fail with an `AssertionError` at that check. Restore the line before continuing.

5. **Protect integer identity.** Compare the two integers just beyond Number.MAX_SAFE_INTEGER and then use BigInt.
   **Expected:** Number collapses a difference; BigInt preserves it.
   **Verify:** Keep a check equivalent to `assert.equal(max + 1, max + 2)`. As a control, change `assert.equal(max + 1, max + 2);` to `assert.equal(max - 1, max + 2);` inside it: the run must fail with an `AssertionError`, which shows the check can fail. Restore it.

6. **Reject ambiguous numeric input.** Validate finite nonblank numeric text and reject blank, Infinity and mixed BigInt arithmetic.
   **Expected:** valid 12 accepted; invalid cases throw.
   **Verify:** Keep a check equivalent to `assert.equal(parseFinite('12'), 12)`. As a control, change `assert.equal(parseFinite('12'), 12);` to `assert.equal(parseFinite('13'), 12);` inside it: the run must fail with an `AssertionError`, which shows the check can fail. Restore it.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.
