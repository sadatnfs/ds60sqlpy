# go-005: Arrays, slices and backing-storage ownership

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-004

## Learning objectives

Predict when two slices share a backing array and make independent copies or capacity-limited appends on purpose. Along the way, explain backing array, capacity, aliasing; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

An array includes its length in its type and owns a fixed sequence of elements. A slice is a descriptor containing a pointer into backing storage, a length and a capacity. Copying that descriptor does not copy the elements. Two slices can therefore observe each other's mutations. append may reuse available storage or allocate new storage; code must not depend on which choice happens unless it controls the capacity contract. A full slice expression can restrict capacity and force a later append to allocate. The practical question is not whether a value looks like a collection, but who can mutate the same storage and for how long.

## Vocabulary and concepts

- **Backing array:** The element storage referenced by one or more slices.
- **Capacity:** The available length from a slice start within its backing storage.
- **Aliasing:** Multiple references to the same mutable storage.

## Syntax anatomy and reasoning

`[]int` constructs a slice type; `[3]int` constructs an array type. `values[a:b]` selects indices a through b-1. `len` is the visible element count and `cap` is the maximum length before reallocation is required. `copy(dst, src)` copies the smaller length and returns that count. append returns a new slice descriptor, so retain the returned value. A nil slice has length zero and can be appended to.

## Worked example / walkthrough

### Worked example 1: Observe shared storage

Take the first two elements of 1, 2, 3 and change the first through the slice.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Observe shared storage
	{
		values := []int{1, 2, 3}
		view := values[:2]
		view[0] = 9
		check(values[0] == 9, "alias")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The original first element becomes 9.

Slicing constructs a view over existing storage. It does not give the new variable independent ownership of its elements.

### Worked example 2: Make an independent copy

Copy 1, 2, 3 into a new slice and mutate that copy.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Observe shared storage
	{
		values := []int{1, 2, 3}
		view := values[:2]
		view[0] = 9
		check(values[0] == 9, "alias")
	}

	// Make an independent copy
	{
		values := []int{1, 2, 3}
		cloned := append([]int(nil), values...)
		cloned[0] = 9
		check(values[0] == 1 && cloned[0] == 9, "copy")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The original stays 1 while the copy starts 9.

Appending into initially nil storage allocates enough backing storage for these nonempty values. Nested pointers would still require a deeper copy policy.

## Common pitfalls and diagnosis

The classic slice bug is assuming that `view := values[:2]`, or passing a slice to a function, creates an independent collection. Writes through either name change the shared backing array, and an append that fits within capacity can overwrite elements a caller still considers its own. When ownership matters, copy explicitly or cap capacity with a full slice expression, then test by mutating one view and checking the other.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Observe shared storage: change one input

1. Restate the expected observation: The original first element becomes 9.
2. values[:2] creates a new descriptor, not new elements. Which backing array does view point into?
3. Writing `view[1]` changes `values[1]`, not `values[0]`, so the first element stays 1 and the alias check fails. The aliasing still exists; the edit moved it.

### Hint for investigation 2: Make an independent copy: debug a regression

1. Restate the expected observation: The original stays 1 while the copy starts 9.
2. Appending to a nil slice must allocate. Does the copy share any storage with values afterward?
3. With 2 as the original first element, `values[0]==1` is false even though the copy is still independent. Restore the input; the copy is not the defect.

### Hint for investigation 3: Restrict append capacity

1. Restate the expected observation: The original second element remains 2.
2. The third index sets capacity. How much room does limited have before append must allocate?
3. The three-index form caps available capacity at one.

### Hint for investigation 4: Inspect a truncated copy

1. Restate the expected observation: Exactly two elements are copied.
2. copy writes the smaller of the two lengths. What is the destination's length here?
3. Capacity alone does not determine how many elements copy writes; the destination length is the bound.

### Hint for investigation 5: Grow an empty slice

1. Restate the expected observation: The result has length 1 and value 7.
2. A nil slice has length 0 and no backing array. Does append need anything besides the nil value?
3. Nil is an empty slice value with no backing array.

### Hint for investigation 6: Transfer array semantics

1. Restate the expected observation: The original array remains unchanged.
2. An array value contains its elements. What exactly does assigning a to b copy?
3. Array assignment copies every element, unlike slice-descriptor assignment.
