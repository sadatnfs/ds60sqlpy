== java-001
run: Exercise 6 asks the system Java compiler for diagnostics at run time, so this lesson needs a full JDK rather than a bare runtime; every other check works on literals only.
predict: Before running Example A, say exactly which line it prints and whether the assertion on `message` could fail even when the text appears on screen. For Example B, decide whether `total` holds the number 5 or the text "5" when `line` is built, and what `"total=" + 2 + 3` would produce instead (it is `total=23`, because the left operand is already a `String`). For Exercise 5, predict whether `javac` or the running JVM rejects a division by a variable that holds 0.
pitfalls: The classic first mistake is treating a compiler error and a runtime exception as the same event. A missing semicolon stops `javac`, so no class file is written and nothing prints; a division by zero compiles cleanly and then throws `ArithmeticException` while `main` runs. A second trap is launching with plain `java Main`: every `assert` is skipped silently and the run looks green, which is exactly what Exercise 4 is built to detect. Finally, a public class named `Main` in a file with any other name is a compile error, not a runtime one.
retrieval: Without the guide, name the stage, `javac` or the JVM, that reports a missing semicolon and the stage that reports a division by zero, and explain why `main` must be `static`. Then describe what a launch without `-ea` would do to the six checks and how Exercise 4 turns that silent mistake into a visible failure.
after: Break a different rule in the Exercise 6 source, such as using an undeclared variable, and confirm that the compiler again reports an ERROR diagnostic while no class runs.
hint1: First note that the edit changes the value stored in `message`, not the assertion. Then compare the new text with the literal inside `equals` character by character; `equals` compares the whole content, so one extra `!` is enough. Finally, decide whether `println` still runs before the assertion and what it shows.
hint2: First compute `total` and then `line` by hand from the two statements above the assertion. Then compare that text with the literal in the edited assertion. Finally, decide which side is wrong here: the program state, or the claim the assertion makes about it.
hint3: First write the value of `count` after each of the three statements. Then check that your table reaches 6 only because the increment runs before the multiplication. Finally, predict what swapping the last two statements would produce and why order matters even in a single thread.
hint4: First recall that the expression inside `assert` is evaluated only when assertions are enabled. Then use that fact: an assignment inside the assertion changes a flag only under `-ea`. Finally, throw an explicit error when the flag is still false, so a plain `java Main` launch cannot pass quietly.
hint5: First keep the divisor 0 in a variable and divide by it inside a `try` block. Then catch exactly `ArithmeticException` and set a flag in the handler; a broad `catch (Exception e)` would also swallow unrelated bugs. Finally, assert on the flag after the `catch`, which proves the program continued past the failure.
hint6: First obtain the compiler with `ToolProvider.getSystemJavaCompiler()` and give it source text for a class whose `return` statement lacks a semicolon. Then collect diagnostics with a `DiagnosticCollector` and keep the boolean the compilation task returns. Finally, assert that the task returned false and that at least one diagnostic has kind `ERROR`.
