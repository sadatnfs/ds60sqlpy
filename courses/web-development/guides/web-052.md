# web-052: Transactions, constraints and concurrent changes

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-051`

## Learning objectives

Implement a version-checked update in a disposable database. Explain the limits of the single-connection concurrency demonstration. Use transaction, atomicity and constraint accurately when you explain a normal case and a failure case.

## Purpose, vocabulary and mental model

A transaction groups operations into a unit that can commit or roll back. Atomicity means the unit is not partially applied when the transaction aborts under the database's contract. Constraints enforce invariants close to the stored data, where every writer must encounter them. Application checks alone can race when two requests read the same state and then both attempt an update.

Concurrency requires more than wrapping code in begin and commit. Isolation levels, locking and the chosen database determine what other transactions can observe. An optimistic update includes an expected version in its WHERE clause and checks the affected-row count. A zero-row update can mean the record changed or was not accessible; the application must decide how to report and retry safely.

### Key terms

- **Transaction:** A group of statements that succeed or fail together, started with `beginTransaction()` and ended with `commit()` or `rollBack()`.
- **Atomicity:** The property that a transaction applies all of its changes or none of them.
- **Constraint:** A database rule such as `NOT NULL`, `UNIQUE` or `CHECK` that rejects invalid rows whatever the application code does.
- **Rollback:** Undoing every change made so far in the current transaction, typically after a failure.
- **Optimistic concurrency:** Updating a row only when its stored version still matches, so a stale edit changes zero rows instead of overwriting newer data.

## Syntax anatomy and mechanism

Begin a transaction, perform related writes, commit only after all succeed, and roll back on failure if still in a transaction. Use a database CHECK or UNIQUE constraint where it expresses a durable invariant. The SQLite example demonstrates rollback and a version predicate in one connection; it does not simulate real parallel requests or qualify PostgreSQL isolation.

## Worked example / walkthrough

### Worked example 1: A guarded update

The version is part of the write condition.

```sql
UPDATE
  plans
SET
  minutes = :minutes,
  version = version + 1
WHERE
  id = :id
  AND version = :expected_version;
```

**Expected observation:** A stale expected version updates no row.

### Worked example 2: Rollback ownership

Failure prevents a partial unit from being accepted.

```php fragment
$db->beginTransaction();
try { /* related writes */ $db->commit(); }
catch (Throwable $error) { if ($db->inTransaction()) $db->rollBack(); throw $error; }
```

**Expected observation:** The transaction is rolled back before the failure propagates.

## Contrast case: two writes from the same stale version

Two editors loaded plan 1 at version 3. Each submits a change. Run both updates in sequence with the same expected version.

```php fragment
$sql = 'UPDATE plans SET minutes = :minutes, version = version + 1
        WHERE id = :id AND version = :expected_version';
$stmt = $db->prepare($sql);

$stmt->execute(['minutes' => 30, 'id' => 1, 'expected_version' => 3]);
$first = $stmt->rowCount();

$stmt->execute(['minutes' => 45, 'id' => 1, 'expected_version' => 3]);
$second = $stmt->rowCount();
```

The first update matches the row, sets minutes to 30 and moves the version to 4, so `$first` is 1. The second update still expects version 3, which no longer exists, so it matches nothing and `$second` is 0. Without the version predicate the second editor's 45 would silently overwrite the 30. With it the application learns about the conflict, but only if it reads the affected row count and reports it. A zero count with no exception is the whole signal.

## Six progressive exercises

Exercises that ask you to predict, explain, compare or diagnose keep their answers in the solutions file. The others show the evidence to look for.

### Exercise 1: Explain atomicity without claiming every transaction is serializable.

**Progressive hint:** Separate all-or-nothing from what concurrent transactions can see.

### Exercise 2: Add a database constraint for nonnegative minutes.

**Expected evidence:** The database rejects invalid writes even if an application check is missed.

**Progressive hint:** Add a CHECK constraint on the minutes column.

### Exercise 3: Implement a version-checked update in a disposable database.

**Expected evidence:** The first expected version succeeds and the repeated stale version affects zero rows.

**Progressive hint:** Run the same update twice with the original version number.

### Exercise 4: Diagnose accepting a zero-row update as success.

**Progressive hint:** Read rowCount() after the update and decide what zero means.

### Exercise 5: Force a failure after a write and verify rollback.

**Expected evidence:** The stored value remains the pre-transaction value.

**Progressive hint:** Throw after the first write inside the transaction, then read the value again.

### Exercise 6: Explain the limits of the single-connection concurrency demonstration.

**Progressive hint:** Ask whether one connection running statements in order can create a race.

## Debugging and common mistakes

Do not blindly retry a non-idempotent operation after an ambiguous commit result. A transaction does not eliminate all races under every isolation level. Keep affected-row checks tied to a documented driver and statement contract.

Keep the failing source, its input and the exact output, then repair one cause at a time. PHP can produce correct-looking text while missing an invalid-input branch, so rerun the empty, wrong-type and boundary cases after every fix.
