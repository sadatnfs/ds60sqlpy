dme-072: Operating the inference workshop and defending a release decision#

Level: Advanced | Prepared runtime: python-core

Direct prerequisites: dme-071.

Outcome: Operate the complete local service and defend a source-bound CPU release decision with explicit limits.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

An inference service is complete only when its model, API, scheduler, transport, saved state and operating procedure agree. A successful generation is one observation. A defensible release decision also needs invalid-input behavior, capacity bounds, cancellation, errors, exact readback and a clear statement of unsupported hardware or scale.

This capstone connects the sixteen serving chapters to the separate inference-service project. It is a tutorial with complete worked source and answered discussion, not an exam gate. The pad builds a small evidence-based decision memo. The project provides actual locally trained weights, a browser, HTTP/SSE endpoints and explicit Docker lifecycle commands for hands-on inspection.

What the project actually implements#

Preparation trains an original tiny Transformer on the checked-in synthetic corpus, learns a byte-BPE tokenizer, validates cached inference and saves bounded numerical weights. Startup loads those assets once, verifies hashes and shapes, warms the model and opens its dedicated request store. The default device is CPU. No pretrained model, provider account or runtime package download is required.

A request is strictly validated, tokenized and admitted under a one-running-plus-two-waiting reservation policy. The model performs real prefill and incremental cached decode. Selected IDs become bounded token events with bytes, text deltas and compute durations. The browser parses real SSE, offers cancellation and downloads exact retained records. Completed history can be read after container replacement without generation.

The implementation is intentionally small. It does not include continuous batching, paged attention, a quantized integer kernel, speculative multi-token serving, distributed tensor parallelism or a public multi-tenant identity system. Those mechanisms have been explained and modeled separately. Calling the workshop production-ready at arbitrary scale would exceed its evidence.

Prepare an owned copy#

Use the project's README for exact commands. Copy the workshop into a directory you own before preparing model and state files. The helper's prepare action explicitly builds its small HTTP layer from an existing CPU Torch classroom image, then trains model assets only when they do not already exist. Existing assets are verified rather than silently replaced.

The initial settings include a project name, loopback browser port and optional pacing. They are saved with that owned copy. Ordinary start, stop, resume and replace actions do not publish images or discard model/history files. resume starts the exact existing containers. replace creates replacement containers from the existing image while retaining the mounted files.

Keep source, model assets, private token and request state conceptually separate. The Docker build context excludes learner state and credentials. A container is an execution instance; its image is a packaged filesystem; the mounted state is what preserves history. Deleting the state directory is not a normal way to update the image.

Trace one request end to end#

Start with a short synthetic prompt. Inspect the startup model and tokenizer hashes, parameter count, context and device. Submit the prompt once and retain the returned request ID. Follow its queued event, started event, token events and terminal event. Compare token IDs, byte pieces and visible text rather than assuming one event equals one character.

Read the exact JSON record and check that it contains the original accepted parameters and source hash. Read the completed event stream again and verify that the generation-call count is unchanged. Then stop and resume the service, and finally replace its container while preserving files. Read the original record from the fresh process and compare bytes, not merely the displayed text.

Next change one condition at a time. Request too many context tokens and expect validation rejection. Fill the bounded reservations and expect capacity rejection. Cancel queued work and confirm the model never starts it. Cancel running work and confirm a terminal cancellation and released reservation after the in-flight operation returns. Reuse a key with changed source and expect a conflict.

The maintained checker automates these bounded observations for an explicitly disposable service. Its readback mode uses the original report and submits no new work. It does not infer success from a process exit code alone; it checks source identity, event sequence, exact receipts and unchanged model-call counters.

Worked case 1: a bounded local release memo#

The first pad example defines six required evidence categories: same source, cached equivalence, bounded admission, cancellation release, exact replay and no external downloads. With all six marked true, the decision permits the stated local CPU scope. GPU qualification remains false because no actual GPU probe is present.

The memo includes a source digest and explicit limitations: synthetic corpus, one CPU slot, no pretrained quality claim and no GPU benchmark. These limitations define the claim being made. They are not excuses for missing correctness checks inside that scope.

The program's booleans are a transparent decision mechanism, not proof that the project passed. A real memo must link each category to actual reports, hashes and observations. The surrounding project tests and retained evidence supply those facts during qualification.

Worked case 2: correct arithmetic but leaked cancellation capacity#

The second case keeps most evidence positive but sets cancellation release to false. The decision blocks the local release and names that failing category. Passing model arithmetic cannot compensate for a scheduler that becomes permanently full after users cancel requests.

This changed condition illustrates an operational failure that a model-only test suite would miss. The right response is to reproduce and fix the ownership bug, then rerun the affected lifecycle checks and relevant integration path. It is not to remove cancellation from the release criteria or hide the failure behind successful sample text.

"""Source-bound release decisions require independent functional and operational evidence."""

import hashlib
import json


def decide(evidence):
    required = {
        "same_source",
        "cache_equivalence",
        "bounded_admission",
        "cancellation_release",
        "exact_replay",
        "no_external_downloads",
    }
    missing = sorted(required - evidence.keys())
    failed = sorted(key for key in required & evidence.keys() if evidence[key] is not True)
    return {
        "ship_local_cpu": not missing and not failed,
        "missing": missing,
        "failed": failed,
        "gpu_qualified": evidence.get("actual_gpu_probe") is True,
    }


def example_one():
    evidence = dict.fromkeys(
        [
            "same_source",
            "cache_equivalence",
            "bounded_admission",
            "cancellation_release",
            "exact_replay",
            "no_external_downloads",
        ],
        True,
    )
    decision = decide(evidence)
    assert decision["ship_local_cpu"] and not decision["gpu_qualified"]
    source = b"synthetic locally trained inference workshop"
    memo = {
        "source_sha256": hashlib.sha256(source).hexdigest(),
        "decision": decision,
        "limitations": [
            "synthetic corpus",
            "one CPU slot",
            "no pretrained quality claim",
            "no GPU benchmark",
        ],
    }
    print(json.dumps(memo, indent=2))


def example_two():
    evidence = {
        "same_source": True,
        "cache_equivalence": True,
        "bounded_admission": True,
        "cancellation_release": False,
        "exact_replay": True,
        "no_external_downloads": True,
    }
    decision = decide(evidence)
    assert not decision["ship_local_cpu"] and decision["failed"] == ["cancellation_release"]
    print("Block release:", decision)
    print("Passing model arithmetic cannot compensate for leaked reservations after cancellation.")


def main():
    example_one()
    example_two()


if __name__ == "__main__":
    main()

A practical decision memo structure#

State the exact source and image identity, model/tokenizer hashes, platform and tested device. Describe the supported user workflow and the resources it owns. List the functional checks, invalid-input cases, numerical comparisons, API/browser observations and persistence stages. Distinguish unit mechanisms from actual Docker execution and from actual browser delivery.

Report timing scope and workload rather than one context-free tokens-per-second number. State whether pacing was enabled, how many tokens were requested and produced, and whether the run ended by EOS, stop string, budget, cancellation or error. CPU results cannot qualify CUDA kernels. A single architecture run cannot establish both AMD64 and ARM64 native behavior.

Name remaining limitations and the next evidence needed for expansion. A real batching engine would need request-row mapping and fairness tests. A paged cache would need ownership and copy-on-write tests plus supported kernel execution. A public deployment would need a different identity, transport and abuse model. A stronger language model would need data and behavior evaluation beyond the mechanics demonstrated here.

Interview diagnosis scenarios#

The first request is slow, later requests are fast. What do you inspect? Separate checkpoint I/O, placement, warm-up, allocator/backend initialization and actual request queueing. Verify weights load at startup and that cold/warm measurements use the same boundary.

Generated text is correct in retained token bytes but arrives in one burst. What do you inspect? SSE framing, framework/proxy buffering, client incremental decoding and transport flushing. Do not assume the model generated every token at once.

After cancellation, new requests always receive capacity errors. What is likely? A reservation or active-work entry was not released on that exit path. Trace queued and running cancellation separately and verify cleanup exactly once.

After replacement, history looks similar but its source hash changed. Is that acceptable? No. Retained history must preserve original source and identity. Similar displayed text is insufficient; investigate a migration, reconstruction or replay defect.

An optimized CPU attention operator has a Flash-like name. Does this qualify GPU inference? No. Confirm actual device execution, supported kernels, synchronization and readback. Operator naming is not hardware evidence.

Further development boundaries#

A learner can extend this project by first stating a new invariant and a bounded acceptance test. Examples include a documented top-p policy, richer token inspection or a new metrics export. Large changes such as continuous batching or a different accelerator should begin with a separate design and reference implementation. Preserve the original simple service as a correctness comparison where useful.

Do not turn a completed record into an automatic background job. Do not broaden the Docker helper to manage unrelated containers or mount the engine socket into the service. Keep dependency preparation explicit and runtime operation offline. These boundaries make the workshop understandable and reproducible while leaving room for deliberate future systems work.
