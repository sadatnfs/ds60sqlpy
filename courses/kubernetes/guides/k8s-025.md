# k8s-025: Helm values without hidden side effects

## Level and prerequisites

Intermediate; about 120 minutes plus review. Direct prerequisites: `k8s-019`, `k8s-024`.

## Learning objectives

Treat a chart render as reviewable manifests rather than an opaque install.

## Vocabulary and concepts

Helm renders parameterized chart templates and can manage release lifecycle through the Kubernetes API. Rendering a chart locally and installing a release are different operations. An install may create release metadata, execute lifecycle hooks or include cluster-scoped resources, so a successful template command is not permission to run the full lifecycle.

The vendored lesson-hello chart has no remote dependencies, plugins, hooks or CRDs. Its values schema restricts replicas to one or two and the image to the approved fixture 0.2.0. The only template is a fixed Deployment. A prepared pinned Helm binary can render this local input offline; the browser does not execute Helm commands.

The lesson emphasizes reviewing the rendered objects rather than trusting a chart name or a friendly values file. A template can hide resource kinds, annotations and field changes that are not obvious from one setting. The default expected JSON is a declared output target, not a fabricated Helm execution receipt.

### Key terms

- **Helm chart:** A package of templates, default values and metadata that Helm renders into Kubernetes manifests.
- **Values schema:** The values.schema.json file in a chart that constrains the accepted input shape before templates render.
- **Template rendering:** Combining chart templates with values to produce manifests. Reviewing the rendered output shows exactly what would be applied.
- **Helm hook:** A chart resource annotated to run at a release lifecycle point, such as before install or after upgrade.
- **Release:** One installed instance of a chart in a namespace, with its own release metadata and revision history.

## Read chart metadata, values and templates

Chart.yaml describes chart identity and version; appVersion is descriptive application metadata and does not pin image bytes by itself. values.yaml supplies defaults, and values.schema.json constrains the accepted input shape. The template inserts .Values.replicas and a quoted image string into an otherwise fixed Deployment.

With a qualified local Helm binary, use helm template hello courses/kubernetes/fixtures/helm/lesson-hello and retain the rendered output in an owned scratch directory. No dependency update or download is required. Record the actual Helm version because rendering and validation behavior can vary across major versions.

The default output requests one replica. An allowed replicas=2 override should change that field only. An unapproved image or extra values key should fail the schema or subsequent manifest review rather than silently broaden the workload.

## Review hooks, CRDs and release side effects

A hook is commonly marked by helm.sh/hook annotations and can run at release lifecycle points. A chart can also contain CRDs or other cluster-scoped objects. Local rendering does not execute those hooks, but hiding them from review can make a later install surprising. Inspect all rendered documents and the chart's vendored contents.

Helm release storage and lifecycle permissions are broader than applying one reviewed Deployment. The normal worker deliberately lacks those capabilities. A rendered object that matches the fixed source allowlist can be reviewed as ordinary YAML, but that does not mean the worker supports helm install or upgrade.

A negative fixture containing a hook Job or ClusterRole should fail the course review before any lifecycle operation. Do not run plugins or fetch a chart from an unrecorded remote source to satisfy a missing dependency.

## Worked example / walkthrough

### Worked example 1: Trace one values substitution

Default values replicas 1 and approved image 0.2.0 produce the expected fixed Deployment. An override to replicas 2 changes only spec.replicas in this chart.

**Expected:** The rendered resource set remains one Deployment with no namespace escape or new lifecycle object.

### Worked example 2: Detect a hidden hook

A rendered Job contains metadata.annotations.helm.sh/hook=post-install. Even if its name sounds harmless, it represents a lifecycle action absent from the ordinary Deployment contract.

**Expected:** Reject it from this course operation before install; rendering itself does not execute the hook.

## Exercises

### Exercise 1: Inventory the vendored chart

List metadata, values, schema, template and expected output.

**Expected result/shape:** One local template, no dependencies/plugins/hooks/CRDs.

**Verify:** Compare your inventory with a directory listing; the chart must have no `charts/` dependencies, no `crds/` directory and exactly one template.

**Progressive hints:** Inspect the complete directory, not only values.yaml.

### Exercise 2: Render the default locally

Use already prepared pinned Helm and compare output with expected-default.json.

**Expected result/shape:** One Deployment with replicas 1 and approved image; record actual renderer receipt or unavailable status.

**Verify:** Record `helm version` and diff the `helm template` output against `expected-default.json` structurally.

**Progressive hints:** No network dependency step is part of this fixture.

### Exercise 3: Review an allowed override

Render replicas 2 and diff the full object.

**Expected result/shape:** Only spec.replicas changes.

**Verify:** Diff the default and override renders; only one field path may differ.

**Progressive hints:** Schema validation and full diff serve different checks.

### Exercise 4: Reject invalid values

Try replicas 3, an unapproved image or an extra unknown key in a scratch values file.

**Expected result/shape:** Schema/review rejection before any cluster operation.

**Verify:** Render each scratch values file and record which schema rule rejects it before any cluster operation.

**Progressive hints:** Read enum, const and additionalProperties restrictions.

### Exercise 5: Detect lifecycle resources

Review a supplied hook annotation or cluster-scoped kind.

**Expected result/shape:** The output is outside the normal worker contract and is not installed.

**Verify:** Search the rendered output for `helm.sh/hook` annotations and for any kind other than Deployment.

**Progressive hints:** A chart can produce more than its headline Deployment.

### Exercise 6: Hand off a reviewed render

Record chart/values hashes, renderer version, full diff and separate apply/application acceptance.

**Expected result/shape:** A reviewer can reproduce the local render and identify the exact owned runtime boundary.

**Verify:** A reviewer must reproduce the render from your chart hash, values hash and renderer version without contacting a cluster.

**Progressive hints:** Do not equate helm template with helm install.

## Self-check

Suppose the rendered output contains a Job annotated `helm.sh/hook: pre-install`. Why did rendering not run it, why does the course reject it anyway, and which part of the chart inventory should have caught it?

## Common pitfalls

Pin chart contents, dependency inputs, values, renderer version and rendered output identity. A chart version string alone can be reused or refer to changed bytes. Diff the complete output before applying, including security and namespace fields.

If Helm is unavailable, the live render row remains unavailable while the source/expected-output reasoning can be completed offline. A valid render is not API acceptance, reconciliation or application correctness. Those remain separate owned operations with their own cleanup receipts.
