# dme-021: Transactions, idempotency and the outbox pattern

## Two writes create a failure boundary

Imagine an application records a shipment and then notifies an analytical consumer. A naive implementation first updates its database and then sends a message. If the process stops between those actions, the shipment exists but the consumer never learns about it. Reversing the order creates the opposite failure: a consumer may act on a message even though the source database update later fails. Both writes are necessary, but two separate success responses do not create one atomic operation.

A database transaction groups changes within a database's supported transaction boundary. Either the transaction commits its changes or it rolls them back. An outbox places the business change and an identified pending event in that same database transaction. A separate delivery step reads pending events and sends them onward. The event can then be retried because it remains recorded until delivery is acknowledged.

The outbox does not magically make two databases one transaction. After a consumer commits an effect, its acknowledgement can be lost. The producer may resend the same event. An inbox or deduplication table at the consumer records accepted event identities together with their effects. If both changes are in the consumer's transaction, replaying an identical event can return the previous outcome without applying the effect again. The identity must also be checked against content: reusing the same key for a different event is a conflict, not a harmless retry.

## Name the invariants before reading the code

The producer has a `state` table holding a unit count and an `outbox` table with `event_id`, `units` and `sent`. The consumer has a `projection` count and an `inbox` of accepted event identities and values. A projection is a derived view used by another part of a system. Here it is intentionally just a counter, so every effect is easy to inspect.

For distinct accepted event identities \(A\), the desired consumer invariant is

\[
\mathrm{projection}=\sum_{e\in A}\mathrm{units}(e).
\]

The sum is over unique accepted events, not delivery attempts. At the producer, changing the state by \(u\) and inserting the corresponding outbox record must be atomic. At the consumer, recording the event in the inbox and incrementing the projection by \(u\) must be atomic. The two transactions are independent, so pending delivery and already-applied delivery can temporarily coexist across the databases.

The code uses actual SQLite databases in separate local files. `BEGIN IMMEDIATE` starts a write transaction before checking for an existing identity, preventing another writer from slipping an update between the check and the write in this database. The `with connection:` context commits on successful completion and rolls back when an exception leaves the block under the prepared Python transaction behavior. Parameter placeholders bind values without constructing SQL from event strings.

## Worked case 1: failure between state change and event insertion

`example_one()` attempts to create `event-a` with three units. The deliberately injected exception occurs after updating the producer count but before inserting the outbox row. Because those actions belong to one transaction, the exception rolls the state change back. The observed producer count is zero and the outbox contains zero events. This is an actual database rollback, not merely a diagram of atomicity.

The example then retries the same operation without the injected failure. The transaction commits a producer count of three and one outbox event. A further request using `event-a` and the same three-unit content returns `replayed`; it does not increment the count again. If that identity were reused with a different number of units, the function would raise a conflict. An identifier represents a particular logical operation, not permission to overwrite its history.

The case changes a specific failure boundary while keeping the business request constant. That is useful for understanding atomicity: compare the observed state before commit, after rollback and after a successful retry. A broad `try/except` that swallowed the error and committed the remaining work would break the invariant. The caller catches the expected demonstration exception only after the transaction has already rolled back.

## Worked case 2: the consumer commits but acknowledgement is missing

The second case creates the producer event, then dispatches it to the consumer. `consume` writes the inbox entry and increments the consumer projection to three in one actual transaction. The delivery function deliberately raises after that commit but before marking the producer's outbox event as sent. The producer still sees a pending event; the consumer already has its effect.

The program closes and reopens the consumer database to demonstrate that its inbox is durable across connection lifetime. The next dispatch sends the same identified event again. The consumer sees `event-a` with the same three-unit payload and returns `replayed`. Its projection remains three and its inbox contains one identity. The producer can now mark the outbox row as sent. Two deliveries produced one accepted effect, while the pending marker accurately represented the producer's earlier uncertainty.

The transport in this example is an ordinary function call. No Kafka broker, queue service, remote network or distributed transaction protocol is running. The lost-acknowledgement boundary is injected explicitly. This lets us execute the two real local transaction boundaries without pretending to qualify broker redelivery, network partitions or cross-machine durability. The Apache streaming workshop is the place to observe a real broker separately.

## Ordering, retention and concurrency

An outbox row's existence solves durable intent, not every delivery requirement. If changes for one entity must be consumed in source order, include an entity identity and sequence and define stale-event behavior. Our independent positive increments commute, so their delivery order does not affect the final total. Account balances, status transitions and replacements may not commute. Sorting event IDs lexically is not a general substitute for a source sequence.

Inbox retention creates another boundary. If old deduplication records are deleted while a producer can still replay those events, old effects can be applied again. A retention policy must be coordinated with the maximum replay horizon, source compaction and recovery procedures. Keeping every event forever is not automatically appropriate either; storage, privacy and operational requirements still apply. State the horizon rather than promising unlimited replay safety.

Multiple dispatchers need a way to claim work and handle expired claims. Multiple consumers need transaction isolation around identity checks and effects. An in-memory set is insufficient after restart. Also distinguish database effects from external effects: recording an inbox row and sending an email cannot usually be committed in one SQLite transaction. If the email provider supports idempotency keys, use and verify that boundary; otherwise duplicate or uncertain delivery remains a product decision requiring reconciliation.

## Diagnose the common mistakes

If the producer count changes but no event exists, inspect whether the outbox insert used the same connection and transaction. If the consumer projection doubles after replay, inspect whether the inbox insert and effect were committed together and whether the event identity stayed stable. If retries are rejected despite representing the same operation, compare canonical content and source identity; an incidental timestamp added on each attempt can make repeated payloads look different.

If the producer marks an event sent before the consumer accepts it, a later failure can lose delivery. If it marks sent afterward, uncertain acknowledgement can cause redelivery. The second ordering is compatible with an idempotent consumer. There is no placement of a simple Boolean update that eliminates both failure windows without additional coordination. The design makes uncertainty recoverable rather than denying it exists.

## Applications and answered interview discussion

Use the pattern for database-originated notifications, analytical change feeds and state transitions that need eventual downstream propagation. It can also support reliable handoff between local components. It is not necessary for every pure transformation: a deterministic file computation with no external side effects may need only a content identity and atomic publication.

An interviewer may ask, “Does an outbox give exactly-once processing?” Explain the specific effect boundary: committed source intent, potentially repeated delivery, and a consumer transaction that records identity with the effect. Avoid a global guarantee that includes unrelated external services. If asked why content must be stored with the identity, explain that accepting the same ID with different content silently loses a real conflict. Reliability includes detecting contradictory requests, not only suppressing duplicates.
