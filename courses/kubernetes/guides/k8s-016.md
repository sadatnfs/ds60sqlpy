# k8s-016: Init containers and ephemeral shared files

## Level and prerequisites

Intermediate; about 105 minutes plus review. Direct prerequisites: `k8s-005`, `k8s-009`.

## Learning objectives

Explain container ordering and the lifetime of emptyDir data.

## Vocabulary and concepts

An ordinary init container completes before the application containers start. It can prepare a synthetic file or validate a prerequisite. An emptyDir volume belongs to the Pod lifetime and can be shared by its containers. Restarting an application container normally preserves that volume, while replacing the Pod creates a different emptyDir.

The supplied real Pod manifest is an explicit host-lab example. The browser adapter does not admit initContainers, emptyDir or arbitrary command bodies. A teacher must review the exact fixed commands and provide the owned capability before live use. The finite example writes the Pod UID into a marker, then deliberately makes the reader fail once and succeed on its next container attempt.

The marker makes lifetime observable: it matches the same Pod UID across the application restart and changes when a new Pod is created. A constant hello marker alone would be weaker evidence because a new init container could recreate identical bytes after replacement.

### Key terms

- **Init container:** A container that runs to completion before the application containers start. Each init container must succeed before the next one begins.
- **emptyDir:** A volume created empty for a Pod and shared by its containers. It survives container restarts and is removed with the Pod.
- **Container restart:** The kubelet starting a new process for a container in the same Pod, which keeps the Pod UID and its emptyDir data.
- **Pod replacement:** A controller creating a new Pod with a new UID, which starts with a fresh emptyDir.
- **Lifetime marker:** A file holding the Pod UID that shows whether data survived a container restart or belongs to a replaced Pod.

## Trace initialization and shared-volume ownership

The init container prepare mounts work at /work and writes marker using the downward-API POD_UID value. The application read mounts the same Pod volume. fsGroup 65532 gives the nonroot process the intended volume access in the scoped fixture; readOnlyRootFilesystem still protects the image filesystem but does not make every mounted volume read-only.

restartPolicy OnFailure allows the deliberately failing application container to restart. The first attempt writes an attempt flag and exits 2; the next sees that flag and exits 0. The completed ordinary init container is not rerun merely because that application container restarts. The Pod active deadline 60 bounds the host experiment.

Do not confuse this ordinary init sequence with a restartable sidecar-style init container, which has different lifecycle semantics. The manifest intentionally uses a finite ordinary init command and no external network or real data.

## Observe container restart versus Pod replacement

Record Pod UID, init termination state, application restart count and the marker printed by each attempt. Within one Pod, the marker should remain that Pod UID and the attempt flag should survive. A new Pod has a new UID and a fresh volume; its init step creates a new marker and its application begins the finite sequence again.

A Pod name can be reused after deletion, so name equality is not evidence of volume continuity. A Deployment replacement also creates a new Pod even if its template is unchanged. This is why emptyDir is appropriate for scratch/shared per-Pod work, not durable data that must survive replacement.

The host must delete only the exact recorded Pod UID and observe completion/cleanup within its deadline. No broad hostPath or personal directory is mounted. The example's write access is confined to a small synthetic emptyDir.

## Exercises

### Exercise 1: Draw container order

Identify init completion as a prerequisite for the application reader.

**Expected result/shape:** prepare completes before read starts.

**Verify:** Read `status.initContainerStatuses` before `status.containerStatuses`; the application container cannot start before the init container finishes.

**Progressive hints:** Inspect initContainerStatuses separately from application statuses.

### Exercise 2: Trace the shared volume

Match volume name work across Pod, init and application mounts.

**Expected result/shape:** Both containers access the same /work emptyDir within one Pod.

**Verify:** Match the name in `spec.volumes` with every `volumeMounts` entry; all mounts of the same name share one emptyDir.

**Progressive hints:** Volume identity is separate from container filesystem identity.

### Exercise 3: Observe one application restart

Use the exact teacher-provided finite fixture and retain UID, marker and restart count.

**Expected result/shape:** Same Pod UID/marker across the failed first and successful next application attempt.

**Verify:** Compare Pod UID, marker and restartCount across the two attempts; only restartCount may change.

**Progressive hints:** The attempt flag is evidence that the volume survived the container restart.

### Exercise 4: Compare a new Pod

Replace only the recorded owned Pod under the host capability.

**Expected result/shape:** New Pod UID, new marker and fresh attempt sequence.

**Verify:** Confirm that the new record has a different Pod UID and a different marker, and that the old marker is absent.

**Progressive hints:** A reused name does not preserve emptyDir.

### Exercise 5: Diagnose an init failure

Review a missing mount or denied write in prepare.

**Expected result/shape:** Application absence is explained by init failure; the smallest mount/permission repair is identified.

**Verify:** Inspect the init container's state and reason first; the missing application container is a consequence, not a second fault.

**Progressive hints:** Do not begin with application readiness or loosen all privileges.

### Exercise 6: State the storage limit

Explain why this marker is neither persistent storage nor a backup.

**Expected result/shape:** emptyDir lifetime is tied to the Pod; durability and independent recovery require later storage/backup contracts.

**Verify:** Name the event that deletes the data and one storage mechanism from a later lesson that would survive it.

**Progressive hints:** Ask what happens when the Pod object is replaced.

## Self-check

The read container restarted once and still found the marker, but after the Pod was deleted the marker was gone. Explain both outcomes from the emptyDir lifetime and name the storage contract that would keep it.

## Common pitfalls

If the init container fails, the application may never start; inspect initContainerStatuses rather than expecting application logs. If the marker cannot be written, inspect the volume mount and nonroot permissions before relaxing the security context globally. A missing file in the application can indicate a different mount name or path.

The offline script checks a lifetime model only. A live claim needs the actual UID and restart/log evidence. Neither a persisted marker in emptyDir nor a successful Pod restart is a backup or proof of PVC behavior.

## Retrieval and transfer
