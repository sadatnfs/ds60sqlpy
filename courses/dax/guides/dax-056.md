## The question and the mechanism

Distinguish a removable analytical filter from an engine-enforced role restriction.

A report filter expresses a query choice. A user who can issue another query can remove or change that choice. Row-level security instead restricts rows through the semantic model's security context for applicable identities and roles. An expression such as REMOVEFILTERS cannot be treated as permission to retrieve rows that a real RLS policy denies.

The two cases deliberately use different stated contexts. An unrestricted model with an ordinary North report filter shows 107, but removing that report filter returns 187. Under the declared NorthViewer policy, the permitted Customer population is North, so both the ordinary revenue measure and a customer-filter-removal attempt are expected to stay at 107.

This classroom does not enforce those model roles. The second result is a policy-based hand derivation, not a penetration test or an observed security guarantee. In a real Power BI service, workspace-role distinctions also matter: an unrestricted owner/administrator result is not a valid substitute for testing the intended Viewer. Keep identity, role membership, relationship propagation and model version in the acceptance record.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

### Case A: An ordinary filter can be removed

**Starting context:** Unrestricted model; North is only an ordinary report/query filter.

```dax
EVALUATE CALCULATETABLE ( ROW ( "SelectedRevenue", [NetRevenue], "AfterRemovingCustomerFilters", CALCULATE ( [NetRevenue], REMOVEFILTERS ( Customer ) ) ), Customer[Region] = "North" )
```

**Context trace:**

1. The report filter selects Ada and Cy, whose revenue totals 107.
2. REMOVEFILTERS(Customer) removes that analytical selection.
3. Bo's 80 becomes eligible, restoring 187.

**Hand-derived worked-reference result:**

| SelectedRevenue | AfterRemovingCustomerFilters |
| --- | --- |
| 107 | 187 |

The removable filter never constituted an access-control boundary.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Expected behavior under an enforced NorthViewer role

**Starting context:** Assume a role-restricted Viewer with the declared NorthViewer RLS policy enforced by a compatible engine; no ordinary Customer filter is needed.

```dax
EVALUATE ROW ( "VisibleRevenue", [NetRevenue], "AfterRemovingCustomerFilters", CALCULATE ( [NetRevenue], REMOVEFILTERS ( Customer ) ) )
```

**Context trace:**

1. The security policy permits Customer 10 and 30 only.
2. The expected fact population totals 51 +56 =107.
3. Removing ordinary Customer filters must not remove the security restriction.

**Hand-derived worked-reference result:**

| VisibleRevenue | AfterRemovingCustomerFilters |
| --- | --- |
| 107 | 107 |

These expected values belong in a real role-test matrix. Their presence in a source file does not prove that the external role was configured or applied.

Hand-derived security-policy expectation only. The classroom has not executed an RLS engine or authenticated this synthetic role.
