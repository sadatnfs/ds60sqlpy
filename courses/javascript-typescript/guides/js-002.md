# js-002: Values, coercion and precise comparisons

## Level and prerequisites

Beginner, approximately 90 minutes. Direct prerequisites: `js-001`

## Learning objectives

Explain coercion, strict equality, safe integer, bigint with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Compare 2+3, 2+string 3, and Number(string 3)+2. The final task tests reject ambiguous numeric input.

## Purpose and mental model

JavaScript values have runtime types, and operators can perform implicit conversion. The plus operator adds numbers but concatenates when string conversion applies. Strict equality avoids the broad coercion of loose equality, but it still has specific semantics for NaN and signed zero. Object.is provides another comparison contract. Choose the relation required by the domain rather than assuming one operator means every notion of same.

Numbers use binary floating-point arithmetic and have a finite safe-integer range. Exact decimal fractions such as 0.1 are generally approximate. BigInt represents arbitrary-size integers but cannot be mixed with Number arithmetic without an explicit conversion policy. null and undefined are distinct values commonly used for absence; neither should be silently converted to a domain count. Validate external numeric text before calculation instead of relying on a convenient coercion.

## Vocabulary and concepts

**Coercion:** An implicit conversion performed by an operator or API.

**Strict equality:** A comparison that does not broadly convert different primitive types.

**Safe integer:** An integer exactly distinguishable within the Number representation.

**BigInt:** An arbitrary-size integer type with separate arithmetic rules.

## Syntax anatomy and execution trace

typeof reports primitive categories but typeof null is the historical string object. Number.isNaN tests NaN without coercing its argument. Number.isFinite rejects non-number values and infinities. Object.is distinguishes +0 and -0 while treating NaN as equal to itself. BigInt literals end in n. JSON does not serialize BigInt by default, so an explicit wire-format policy is needed.

## Worked example / walkthrough

### Example A: Trace plus versus numeric conversion

The same symbol has different behavior when a string participates. Explicit conversion makes the intended numeric operation visible.

```javascript
import { strict as assert } from 'node:assert';

function parseFinite(text) {
  if (typeof text !== 'string' || text.trim() === '') throw new TypeError('nonblank numeric text required');
  const value = Number(text);
  if (!Number.isFinite(value)) throw new TypeError('finite number required');
  return value;
}

export async function verify() {
  // Worked example
  {
    assert.equal(2 + 3, 5);
    assert.equal(2 + '3', '23');
    assert.equal(Number('3') + 2, 5);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** 5, string 23, and 5.
### Example B: Inspect absence and NaN

The typeof null result is a language legacy, not evidence that null has usable object properties. Number.isNaN avoids converting arbitrary text.

```javascript
import { strict as assert } from 'node:assert';

function parseFinite(text) {
  if (typeof text !== 'string' || text.trim() === '') throw new TypeError('nonblank numeric text required');
  const value = Number(text);
  if (!Number.isFinite(value)) throw new TypeError('finite number required');
  return value;
}

export async function verify() {
  // Worked example
  {
    assert.equal(typeof null, 'object');
    assert.equal(typeof undefined, 'undefined');
    assert.equal(Number.isNaN(NaN), true);
    assert.equal(Number.isNaN('not a number'), false);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

```

**Expected:** null reports object; undefined reports undefined; only numeric NaN passes isNaN.

## Common pitfalls and diagnosis

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

## Progressive hints

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
