# Multivariate normals and Gaussian Markov fields

Start with: tmb-042, tmb-015.

Outcome: Choose covariance or precision interfaces and verify equivalent tiny densities.

The classroom companion runs in the prepared R statistics runtime. It uses base R to expose the mathematics or data contract. Compiling and executing TMB uses the separate [owned project](../projects/tmb-local/README.md); a companion run is not a TMB compiler or rpy2 receipt.

A multivariate normal can be represented by covariance \(\Sigma\) or precision \(Q=\Sigma^{-1}\). These interfaces are not interchangeable arguments. The normalized NLL is
\[
\tfrac q2\log(2\pi)+\tfrac12\log|\Sigma|+\tfrac12u^T\Sigma^{-1}u
=\tfrac q2\log(2\pi)-\tfrac12\log|Q|+\tfrac12u^TQu.
\]

TMB's `density::MVNORM` family uses a covariance matrix and is intended for manageable dense problems. `density::GMRF` uses a sparse precision representation and supports structured Gaussian fields. Passing a precision matrix where a covariance is expected changes both the quadratic form and normalizer.

### Worked case A: two representations, one density

The companion evaluates the same two-dimensional normal using covariance and precision formulas and verifies agreement. It also prints the incorrect result obtained by interpreting precision as covariance. This small oracle should precede a large sparse model.

```cpp
Type dense_nll = density::MVNORM(covariance)(state);
Type sparse_nll = density::GMRF(precision)(state);
```

These are API patterns, not a suggestion to add both terms for the same state. Adding both would double-model that state. A comparison variant should select one representation at a time or report their difference as a diagnostic.

### Worked case B: a singular precision

A difference-only random-walk precision has a null direction. Without a constraint or a proper initial-level distribution, it does not define a normalized Gaussian density over every coordinate. The companion compares the singular matrix with a properly anchored one. A sparse Cholesky failure can be a correct indication of an improper model rather than a library installation problem.

`GMRF` options involving normalization or powers/order affect the model and computational path. Do not disable normalization merely to avoid an expensive determinant when estimating precision parameters. If a constant is truly parameter-independent for a narrowly defined target, document that derivation and keep normalized references for integration checks.

### Answered discussion

**Can any positive diagonal matrix be treated as a covariance?** It must be symmetric positive definite as a whole. **Does sparse precision imply sparse covariance?** Usually not; conditional dependence can be local while marginal dependence is widespread. **When should I avoid explicit inversion?** For large matrices, use factorization and solves. Our explicit inverse is only a tiny pedagogical oracle.

See the [MVNORM and GMRF density-family implementation](https://github.com/kaskr/adcomp/blob/master/TMB/inst/include/tmbutils/density.hpp). Hardware scale claims require actual memory and factorization measurements on the intended graph.

### Complete R companion

```r
Sigma <- matrix(c(2, .5, .5, 1), 2, 2);Q <- solve(Sigma);u <- c(.3, -.4);constant <- length(u) * log(2 * pi) / 2
ld <- function(M) as.numeric(determinant(M, logarithm = TRUE)$modulus)
a <- constant + ld(Sigma) / 2 + drop(t(u) %*% solve(Sigma, u)) / 2
b <- constant - ld(Q) / 2 + drop(t(u) %*% Q %*% u) / 2
wrong_precision_as_covariance <- constant + ld(Q) / 2 + drop(t(u) %*% solve(Q, u)) / 2
print(c(covariance_form = a, precision_form = b, wrong_precision_as_covariance = wrong_precision_as_covariance))
stopifnot(abs(a - b) < 1e-12, abs(wrong_precision_as_covariance - a) > .1)
D <- matrix(c(-1, 1, 0, 0, -1, 1), 2, 3, byrow = TRUE);intrinsic <- crossprod(D);proper <- intrinsic;proper[1, 1] <- proper[1, 1] + 1
print(list(intrinsic = eigen(intrinsic, symmetric = TRUE)$values, anchored = eigen(proper, symmetric = TRUE)$values))
```
