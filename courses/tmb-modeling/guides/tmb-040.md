# An API-complete workflow and qualification map

Start with: tmb-039, tmb-024.

Outcome: Navigate every pinned public TMB API without overstating untested features.

**Where this runs.** In the classroom, the base-R companion at the end of this chapter prints an evidence map and the checks still required. In the separately prepared [owned project](../projects/tmb-local/README.md), `tests/acceptance.R` and `tests/public_api.R` are the executable checks, and the [qualification ledger](../QUALIFICATION.md) records where they actually ran; a companion run is not a TMB compiler or rpy2 receipt, so its output is not evidence that a compiled model or the rpy2 bridge ran.

A comprehensive course needs a map of the actual public package, not an unbounded promise to cover every implementation symbol. The pinned TMB 1.9.25 NAMESPACE declares 30 explicit exports. It also registers S3 methods, including `confint` for profile objects and `as.list` for uncertainty reports. The manual documents `GK`, which is not an explicit export in that namespace. The maintained [API reference](../API-REFERENCE.md) lists exact signatures, purpose, cautions and chapter placement for these distinct surfaces.

The workflow begins with a scientific observation model and ends with a qualified result. Authoring helpers create scaffolds; compile and native-lifetime helpers prepare execution; `MakeADFun` constructs the target; optimizers find parameters; reporting and profile functions quantify selected uncertainty; simulation and OSA tools criticize the model; parallel and sparse controls change execution details. Each step has a separate failure mode and evidence record.

## Key terms

- **API inventory:** The maintained list of the pinned TMB 1.9.25 public surface: 30 explicit exports plus registered S3 methods, each mapped to a chapter.
- **Registered S3 method:** A method such as `confint` for profiles or `as.list` for reports, reached through a generic function rather than a direct export.
- **Evidence map:** A table of workflow layers, such as formula, source, compiled model and rpy2, each with an explicit status such as derived, authored or separate run record.
- **Model lifecycle:** The sequence from observation model through authoring, compilation, construction, optimization, uncertainty and criticism, each with its own failure modes.

### Worked case A: a small fully qualified model

For the original normal model, derive its full density, validate input, compile a source-identified library, compare values and derivatives, recover known MLEs, inspect curvature, use report methods and compare a profile/root interval to an independent formula. The companion assembles these evidence layers as a table with explicit statuses. A source file and a successful import are not replacements for the execution rows.

### Worked case B: an advanced prepared-only capability

Suppose you add a custom latent process requiring automatic normalization and one-step predictive residuals. The existing normal model's test record does not qualify those features. Define the required flag/indicator template conventions, prepare the new source, test a tiny oracle and record actual runtime results. Until then, mark the API explanation as taught and its particular project implementation as prepared or untested.

This distinction lets learners study the entire API now while keeping product capability claims precise. The course covers all public function families, but does not claim that every combination of framework, specialized sparse build, integration method, debugger and hardware is exercised in the ordinary classroom runtime.

### Answered discussion

**Is API coverage the same as mastery?** No. Learners must connect each tool to a statistical question and diagnose its limitations. **How should a future TMB upgrade be handled?** Compare exports and signatures against the maintained inventory, inspect behavior changes, rebuild native models and rerun exact numerical and failure checks. **Should undocumented internals be forbidden?** Research sometimes needs them, but they require explicit source pinning and cannot silently become a stable learner-facing contract.

The companion is an honest evidence map. The owned project's qualification ledger and release records supply actual statuses. Continue to the advanced Spark integration only after the local compiled model and process boundary are trustworthy.

### Worked case C: reading the evidence map

The companion prints six layers and their statuses, then compares two checklists. `setdiff(required, recorded)` returns `c("uncertainty", "invalid input")` in that order, because `setdiff` keeps the order of its first argument:

```text
layer                    status
formula                  derived
source                   authored
compiled model           separate run record
native numerical checks  separate run record
rpy2                     separate run record
Spark integration        separate run record

recorded:        value, gradient, optimizer
still_required:  uncertainty, invalid input
```

Only the first two rows are fully determined by files a learner can read: the formula can be checked by hand, and the source exists in `models/`. The other four depend on running code in a prepared environment, so the companion deliberately refuses to call them passed. The checklist shows the same honesty at a finer grain. A model whose value, gradient and optimizer recovery have been recorded still lacks uncertainty evidence, such as an `sdreport` standard error compared with the closed-form \(\hat\sigma/\sqrt n\) for `normal_mean`, and failure evidence, such as a non-finite `y` being rejected before native evaluation. Calling the model qualified at that point would overstate the record by two rows.

### Mapping chapters to rows for `normal_mean`

For the course's simplest model, each still-required row has a specific source. Uncertainty evidence comes from chapter 28's `sdreport` methods and chapter 30's root interval, whose closed-form endpoints 1.540036 and 5.459964 for known \(\sigma=2\) provide an oracle. Invalid-input evidence comes from chapter 22's bridge checks and the R validation that `make_objective` runs before `MakeADFun`. The `public_api.R` probe already lists tags such as `"benchmark-plot"` and `"native-object-release"`; a release record should show which tags passed on which build, alongside the build receipt and source MD5 from chapter 37. When TMB is upgraded, the whole table resets to "separate run record" until each row is rerun, because a new ABI or changed default can affect any of them.

### When a row moves from pending to recorded

A row changes status only when an artifact exists that a reviewer can open: a log from `tests/acceptance.R` with its PASS line, the build receipt, and the request and response JSON for any rpy2 or Spark call. A screenshot of a console or a sentence in a pull request is not enough, because neither ties the result to a source MD5 or a build. For Spark integration, the record also needs the executor count and the per-executor thread setting, since the same code can pass with one executor and oversubscribe a node with eight.

### Base-R companion (runs in the classroom)

```r
evidence <- data.frame(layer = c("formula", "source", "compiled model", "native numerical checks", "rpy2", "Spark integration"), status = c("derived", "authored", "separate run record", "separate run record", "separate run record", "separate run record"))
print(evidence)
required <- c("value", "gradient", "optimizer", "uncertainty", "invalid input")
recorded <- c("value", "gradient", "optimizer")
print(list(recorded = recorded, still_required = setdiff(required, recorded)))
stopifnot(identical(setdiff(required, recorded), c("uncertainty", "invalid input")))
```
