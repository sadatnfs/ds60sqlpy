## The question and the mechanism

Define a small reusable function with a clear parameter domain and default behavior.

A user-defined function packages an expression behind named parameters. This differs from a measure, which obtains its evaluation context from the model/query rather than accepting an ordinary explicit argument list. A UDF can help centralize a stable calculation rule, but it still needs a documented domain, units and error policy.

The original example Course.NetAfterFee accepts a numeric amount and an optional numeric fee rate. The default rate is 0.1; values outside 0..1 deliberately return BLANK. This rule is a teaching policy, not a universal financial convention. Returning BLANK is distinguishable from a valid zero at a 100-percent fee.

The function definition and two calls can live in query scope using DEFINE FUNCTION on a compatible engine. Persisting a function in a semantic model is a separate authoring action. The classroom saves the source text and explains its result; it neither compiles the definition nor proves compatibility with a particular external model.

## Vocabulary and expression anatomy

FUNCTION introduces the name and parameter list, the arrow separates the signature from its body, and the default expression follows the optional parameter's equals sign. NUMERIC is a scalar subtype annotation. The query supplies explicit output names so default, explicit and invalid-domain cases cannot be confused.

Concepts to explain in your own words: **FUNCTION**, **UDF**, **numeric parameter**, **default argument**, **compatibility**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

### Feature and version boundary

Microsoft's DAX UDF documentation, reviewed on 2026-10-25, states general availability in Power BI Desktop and Service from June 2026 and database compatibility level 1702 or higher. These offline definitions are not engine-tested here. UDF availability is distinct from calendar-based time intelligence's preview status.

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
    MEASURE Sales[QuantitySold] = SUM ( Sales[Quantity] )
    MEASURE Sales[GrossRevenue] = SUMX ( Sales, Sales[Quantity] * Sales[UnitPrice] )
    MEASURE Sales[OrderCount] = DISTINCTCOUNT ( Sales[OrderID] )
    FUNCTION Course.NetAfterFee = ( amount : NUMERIC, feeRate : NUMERIC = 0.1 ) =>
        IF ( feeRate >= 0 && feeRate <= 1, amount * ( 1 - feeRate ), BLANK() )
```

### Case A: Default and explicit rates

**Starting context:** All-row revenue 187; fee-rate domain 0..1; default rate 0.1.

```dax
EVALUATE ROW ( "DefaultFee", Course.NetAfterFee ( [NetRevenue] ), "ExplicitTwentyPercent", Course.NetAfterFee ( [NetRevenue], 0.2 ) )
```

**Context trace:**

1. The omitted rate uses 0.1, giving 187*(1-0.1)=168.3.
2. An explicit 0.2 overrides that default.
3. 187*(1-0.2)=149.6.

**Hand-derived worked-reference result:**

| DefaultFee | ExplicitTwentyPercent |
| --- | --- |
| 168.3 | 149.6 |

A default argument is part of the function contract. Changing it can alter every call that omits the parameter, even if the call source itself stays unchanged.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: A valid zero and an invalid rate

**Starting context:** Same function; compare boundary rate 1 with out-of-domain rate 1.2.

```dax
EVALUATE ROW ( "FullFee", Course.NetAfterFee ( 100, 1 ), "InvalidRate", Course.NetAfterFee ( 100, 1.2 ) )
```

**Context trace:**

1. Rate 1 is inside the declared domain and leaves zero amount.
2. Rate 1.2 violates the rule.
3. The invalid-domain branch returns BLANK, not a fabricated negative net amount.

**Hand-derived worked-reference result:**

| FullFee | InvalidRate |
| --- | --- |
| 0 | BLANK |

A caller should retain a validation signal if BLANK could be mistaken for no activity. A more elaborate error policy belongs in the function's documented contract.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Zero fee is a valid boundary.
2. Only calls omitting the argument use the changed default.
3. Types do not fully describe business meaning.
4. Measures and UDFs have different invocation contracts.
5. Availability and compatibility are separate inputs.
6. Avoid hiding population choices inside a deceptively generic function.
