# dbt-007: Jinja macros and compiled SQL evidence

## Level and prerequisites

Intermediate. Direct prerequisites: `dbt-001`, `dbt-003`

**Outcome:** Review a macro through its source, emitted SQL and actual result.

## Question and mechanism

A dbt macro generates SQL during compilation. It can reduce repeated logic and centralize a reviewed calculation, but it is not a Python row function executed once for each database record. The generated SQL is what the database evaluates. Inspecting compiled SQL is therefore an important part of understanding and debugging a macro.

The ratio macro receives SQL expressions for a numerator and denominator. It emits a CASE expression that returns null for a zero denominator and performs floating division otherwise. That is a declared undefined-rate policy, not a universal rule. A different consumer might reject zero-trial groups or expose a separate status field. The macro should make the choice visible rather than hide it behind a convenient name.

Template arguments also have trust and quoting boundaries. A trusted model expression is different from an arbitrary user-supplied string. Reusing text in SQL does not automatically make it a safe identifier or a bound parameter. The lesson uses fixed authored expressions and an owned local database. External input needs a separately designed validation and parameterization boundary.

## Syntax and data contract

A macro is declared with Jinja macro/endmacro blocks and called inside double-brace expressions. The example's arguments are trusted column-expression strings. compile expands the macro into ordinary SQL; build then evaluates it. An undefined macro is a compilation error, which should be diagnosed before reasoning about database rows.

## Worked case 1: Inspect a complete expansion

The valid project generates rates for a normal count and a zero denominator. It checks actual values and reads compiled SQL to verify that the macro call has been expanded. Both the source abstraction and the executed expression remain inspectable.

**Expected evidence:** The rates are 0.25 andnull; compiled SQL contains CASE logic rather than the macro call.

```python
import os
import tempfile
from pathlib import Path

import duckdb
import yaml


def project(directory, models=None, seeds=None, schema=None, snapshots=None, macros=None):
    os.environ["DBT_SEND_ANONYMOUS_USAGE_STATS"] = "false"
    os.environ["DBT_USE_COLORS"] = "false"
    os.environ["DO_NOT_TRACK"] = "true"
    root = Path(directory) / "project"
    root.mkdir(parents=True)
    for folder in ("models", "seeds", "snapshots", "macros"):
        (root / folder).mkdir()
    config = {
        "name": "classroom",
        "version": "1.0",
        "config-version": 2,
        "profile": "classroom",
        "model-paths": ["models"],
        "seed-paths": ["seeds"],
        "snapshot-paths": ["snapshots"],
        "macro-paths": ["macros"],
    }
    (root / "dbt_project.yml").write_text(yaml.safe_dump(config))
    output = {
        "type": "duckdb",
        "path": str(root / "warehouse.duckdb"),
        "schema": "main",
        "threads": 1,
        "settings": {"threads": 2, "memory_limit": "256MB"},
    }
    (root / "profiles.yml").write_text(
        yaml.safe_dump({"classroom": {"target": "dev", "outputs": {"dev": output}}})
    )
    for name, sql in (models or {"answer": "select 42::integer as answer"}).items():
        (root / "models" / (name + ".sql")).write_text(sql)
    for name, csv in (seeds or {}).items():
        (root / "seeds" / (name + ".csv")).write_text(csv)
    if schema:
        (root / "models/schema.yml").write_text(yaml.safe_dump({"version": 2, **schema}))
    if snapshots:
        (root / "snapshots/snapshots.yml").write_text(
            yaml.safe_dump({"version": 2, "snapshots": snapshots})
        )
    for name, sql in (macros or {}).items():
        (root / "macros" / (name + ".sql")).write_text(sql)
    return root


def invoke(root, *arguments, succeeds=True):
    from dbt.cli.main import dbtRunner

    result = dbtRunner().invoke(
        [
            "--quiet",
            "--no-use-colors",
            "--no-send-anonymous-usage-stats",
            *arguments,
            "--project-dir",
            str(root),
            "--profiles-dir",
            str(root),
            "--no-partial-parse",
        ]
    )
    if succeeds:
        assert result.success, str(result.exception)
    else:
        assert not result.success, "The deliberately invalid fixture was accepted."
    return result


def rows(root, sql):
    with duckdb.connect(str(root / "warehouse.duckdb"), read_only=False) as connection:
        return connection.execute(sql).fetchall()


def example_one():
    with tempfile.TemporaryDirectory() as d:
        macro = (
            "{% macro safe_ratio(n, d) %} case when {{ d }} = 0 then "
            "null else cast({{ n }} as double) / {{ d }} end {% "
            "endmacro %}"
        )
        p = project(
            d,
            models={
                "rates": (
                    "select id, {{ safe_ratio('successes', 'trials') }} as "
                    "rate from {{ ref('counts') "
                    "}}"
                )
            },
            seeds={"counts": "id,successes,trials\n1,1,4\n2,0,0\n"},
            macros={"safe_ratio": macro},
        )
        invoke(p, "build")
        assert rows(p, "select rate from rates order by id") == [(0.25,), (None,)]
        compiled = (p / "target/compiled/classroom/models/rates.sql").read_text()
        assert "case when" in compiled and "safe_ratio" not in compiled
        return {"rates": [0.25, None], "macro_expanded": True}


if __name__ == "__main__":
    print(example_one())
```


## Worked case 2: Stop on an undefined abstraction

**Expected evidence:** Compilation fails before model execution.

## Practice

Make each requested change in a saved copy. Compare both the expected result and the deliberately changed assumption. The separate reference explains the answers.


### 1. Change the zero policy

Return a separate invalid-denominator flag alongside the rate.

**Check:** Zero-trial rows remain identifiable.

**Hint:** A null value alone can have several causes.


### 2. Check integer behavior

Use 1 success and 4 trials and inspect the result type.

**Check:** The rate is 0.25 rather than an integer truncation.

**Hint:** Read the generated cast.


### 3. Review macro inputs

Explain why arbitrary user text should not become a SQL expression.

**Check:** The answer identifies the trust boundary.

**Hint:** Template substitution is not parameter binding.


### 4. Inspect compiled code

Locate the CASE expression under target/compiled.

**Check:** The generated expression is readable.

**Hint:** The database does not execute the macro name.


### 5. Test a negative denominator

Define a policy for negative trial counts.

**Check:** The policy explicitly rejects or classifies the invalid domain.

**Hint:** Zero handling is not full domain validation.


### 6. Version shared logic

Describe what should be reviewed when the macro changes.

**Check:** Affected consumers and their semantics are identified.

**Hint:** A shared helper has a dependency surface.


## Diagnose errors and misleading results

If compilation fails, inspect macro discovery, names and argument syntax. If results are wrong, inspect the compiled SQL and numeric domain. Do not patch a macro by suppressing undefined names or replacing every exceptional denominator with zero. That can produce clean output while changing the analytical question.

## Transfer to independent work

Review a macro through its source, emitted SQL and actual result. Keep domain assumptions explicit and test contrasting numeric cases. Use abstraction to make a calculation consistent without hiding the evidence needed to validate it.
