# web-038: Structured data, streams and bounded file handling

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-037`

## Learning objectives

Parse a small study record and round-trip it through a temporary stream. Explain why user-controlled paths need an ownership policy. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

JSON is a data format, not a PHP object model or a validation system. Decoding can produce syntactically valid data with the wrong fields, wrong types or an unexpectedly deep structure. Treat parsing and contract validation as separate steps. The examples use tiny inline JSON and a temporary stream so no host path or persistent file is required.

A stream represents a readable or writable sequence of bytes. File operations can fail, return partial results or expose sensitive data if paths are chosen carelessly. In an application, accept an identifier and map it to an owned location instead of accepting an arbitrary user-supplied filesystem path. Bound size before reading untrusted content into memory, and close resources when finished.

## Syntax anatomy and mechanism

Use JSON_THROW_ON_ERROR so invalid JSON becomes an exception instead of an ambiguous null result. Pass true when an associative-array representation is intended, then validate each required field. `php://temp` provides a temporary stream suitable for this local demonstration. Check resource creation and write results, rewind before reading, and close in a finally block.

## Classroom execution and offline inputs

Choose the **PHP CLI** worker in the classroom. The pad is staged as `main.php` and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write `<?php` at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

## Worked example / walkthrough

### Worked example 1: Parse then validate

Syntactic JSON validity is only the first step.

```php
$data = json_decode('{"minutes":30}', true, 32, JSON_THROW_ON_ERROR);
if (!is_int($data['minutes'] ?? null)) throw new InvalidArgumentException('Expected integer minutes');
```

**Expected observation:** The record is accepted only after the field contract passes.

### Worked example 2: A temporary stream

The resource belongs to this process.

```php
$stream = fopen('php://temp', 'w+');
fwrite($stream, 'notes');
rewind($stream);
echo stream_get_contents($stream);
```

**Expected observation:** Reading after rewind returns notes.

## Six progressive exercises

### Exercise 1: Explain why valid JSON can still be invalid application input.

**Expected evidence:** It may contain the wrong structure, types, ranges or required fields.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add a bounded decoding depth and explicit parse errors.

**Expected evidence:** Malformed or too-deep input produces an intentional failure.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Parse a small study record and round-trip it through a temporary stream.

**Expected evidence:** The field contract passes and the returned bytes match the encoded value.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose an empty read caused by the stream cursor position.

**Expected evidence:** Rewind before reading from the beginning.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Reject an unexpected field type and an oversized input string.

**Expected evidence:** The program checks both byte budget and data contract before use.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain why user-controlled paths need an ownership policy.

**Expected evidence:** A path can escape the intended data area or expose unrelated files; identifiers should map through a reviewed boundary.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not disable warnings to hide failed I/O. A file existing does not prove that its content matches the schema. The lesson's temporary stream does not establish durable persistence across worker runs.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain JSON, stream, resource without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
