## The question and the mechanism

Explain what a revenue number means by identifying the model, grain and eligible rows.

A semantic model is a set of typed tables, relationships and calculation definitions. It is not the report picture. A visual asks the model a question; a measure gives a scalar answer for the question's current context. A query can ask for a table of such answers. Keeping these objects separate prevents a common beginner mistake: treating a number on a page as if it were stored in the formula itself.

Our synthetic retailer records one order line per Sales row. NetAmount is Quantity times UnitPrice minus a discount for the entire line. Every ordinary retail amount is USD. Product and Customer describe the keys on those lines. The complete Date table describes calendar days. The eight lines total 187, but that number alone does not tell us whether returns, tax or an unobserved month belong in the question. Here tax and refunds are excluded by the fixture contract.

This classroom provides source editing, saved notes and fixed worked references. It does not host a semantic-model engine. The two result tables below explain this exact reference and fixture. Change your draft to explore an idea, then compare your reasoning with the explanation; the displayed numbers do not change into results of your edit. This distinction is part of learning reproducible analysis, not a temporary missing compiler.

## Vocabulary and expression anatomy

Read the reference from its declarations to its query. DEFINE MEASURE introduces a query-local measure named NetRevenue on Sales. SUM accepts one numeric column and adds its eligible values. EVALUATE expects a table, so ROW wraps a scalar in a one-row table with a named output column. Case B uses CALCULATETABLE to give that same question an explicit ProductKey filter. Its detailed context rules arrive in stage three; here trace the selected rows first.

Concepts to explain in your own words: **semantic model**, **fact**, **dimension**, **measure**, **query**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: All eight lines

**Starting context:** No filters; regular active relationships; USD sales-line grain.

```dax
EVALUATE ROW ( "NetRevenue", [NetRevenue] )
```

**Context trace:**

1. Eligible lines are S1 through S8.
2. Add 20 + 4 + 40 + 27 + 20 + 20 + 20 + 36.
3. The total is 187 USD before returns and tax.

**Hand-derived worked-reference result:**

| NetRevenue |
| --- |
| 187 |

The answer is attached to a defined population of lines. It is not proof that every business revenue policy has been represented. Changing the question to refunded revenue would require another fact or calculation.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Notebook product only

**Starting context:** ProductKey 1; the Product-to-Sales relationship is active and single-direction.

```dax
EVALUATE CALCULATETABLE ( ROW ( "NetRevenue", [NetRevenue] ), Product[ProductKey] = 1 )
```

**Context trace:**

1. ProductKey 1 identifies Notebook, not all products in the Paper category.
2. The key filter admits Sales S1, S4 and S7.
3. 20 + 27 + 20 = 67 USD.

**Hand-derived worked-reference result:**

| NetRevenue |
| --- |
| 67 |

The measure text did not change. Its eligible rows did. A report selection must be part of the explanation whenever someone compares this 67 with the overall 187.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Add the Quantity column, not the distinct products.
2. Find ProductKey 3 before adding amounts.
3. ROW supplies the table; SUM supplies a scalar.
4. Identify the deductions actually represented.
5. Separate a saved source file from a derived result.
6. A source file and a calculation result are different artifacts.
