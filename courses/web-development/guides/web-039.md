# web-039: Exceptions, errors and useful failure boundaries

## Level and prerequisites

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: `web-038`

## Learning objectives

Build a failure-aware parser with explicit success and error paths. Explain the difference between learner diagnostics and public production errors. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

An exception interrupts the ordinary flow and can be handled by a matching catch block. It is useful when a function cannot fulfill its contract. A catch block should either recover meaningfully, translate the error into an appropriate boundary response or rethrow it. Catching every failure and returning a normal-looking value can corrupt downstream reasoning.

PHP has different error categories, and not every warning automatically becomes an exception. Runtime configuration and library behavior matter. A production error boundary should avoid exposing stack traces, secrets or internal paths to visitors while retaining an appropriate diagnostic record for maintainers. The local classroom output is a teaching surface, not a production logging policy.

## Syntax anatomy and mechanism

Catch specific exceptions near an operation when a specific recovery exists. Use finally for cleanup that should happen whether the operation succeeds or fails. Keep validation errors distinct from unexpected internal failures. An invalid user field can produce a clear correction; an unavailable database may require a generic retry message and internal diagnosis.

## Classroom execution and offline inputs

Choose the **PHP CLI** worker in the classroom. The pad is staged as `main.php` and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write `<?php` at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

## Worked example / walkthrough

### Worked example 1: An explicit contract failure

The caller can distinguish invalid input from a normal result.

```php
function requirePositive(int $value): int {
  if ($value <= 0) throw new InvalidArgumentException('Use a positive value');
  return $value;
}
```

**Expected observation:** Zero and negative values raise a declared exception.

### Worked example 2: Cleanup independent of success

Finally expresses ownership of a cleanup step.

```php
try { $result = requirePositive(0); }
catch (InvalidArgumentException $error) { echo $error->getMessage(); }
finally { echo "\nAttempt finished\n"; }
```

**Expected observation:** The useful error is shown and the final step still runs.

## Six progressive exercises

### Exercise 1: Trace the statements executed after requirePositive(0).

**Expected evidence:** The function throws, the matching catch runs and finally executes.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add a specific catch around a recoverable validation error.

**Expected evidence:** The caller presents a correction without hiding unrelated failures.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a failure-aware parser with explicit success and error paths.

**Expected evidence:** Valid data returns a result; invalid data produces a clear classified failure.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a catch-all that returns zero for every failure.

**Expected evidence:** A fabricated normal value hides the difference between valid zero and broken processing.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test cleanup after both success and exception.

**Expected evidence:** Owned resources are released in either path.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain the difference between learner diagnostics and public production errors.

**Expected evidence:** Detailed local diagnostics support learning, while public responses should avoid sensitive internal detail.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not catch Throwable merely to print success. Avoid including secrets in exception messages. A handler that returns a valid-looking fallback must have a genuine domain reason and an observable warning where appropriate.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain exception, Throwable, try-catch without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
