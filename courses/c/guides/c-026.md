# c-026: Bounded string builders and failure-atomic appends

## Level and prerequisites

Intermediate, approximately 120 minutes plus a later retrieval session. Direct prerequisites: `c-025`

## Learning objectives

## Purpose and mental model

Building text incrementally requires an invariant connecting length, capacity and termination. A valid builder keeps length below capacity and stores a null character at data[length]. An append must prove enough remaining space for both payload and terminator before copying. Failure should preserve the existing valid string rather than leave a half-written result that looks complete. Avoid repeated strcat scans when the current length is already known. This fixed-capacity builder makes the resource budget visible and rejects overflow; a dynamic builder would additionally need allocation failure and pointer-invalidation policies.

## Vocabulary and concepts

- **Builder invariant:** The relationship between stored length, capacity and terminator.
- **Failure-atomic append:** An append that leaves the prior string unchanged on rejection.
- **Overlap contract:** Whether input and output memory ranges may share bytes.

## Syntax anatomy and execution trace

The builder owns a fixed character array and a length. append_text obtains the source length, checks it against capacity-1-length, then copies payload plus terminator with memcpy. The subtraction form avoids overflowing length+incoming+1. Source and destination must not overlap for this helper. Initial zero state is a valid empty string, which makes construction and cleanup simple.

## Worked example / walkthrough

### Worked example 1: Append two fragments

Append red then space sky.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

struct Builder {
  char data[16];
  size_t len;
};
bool append_text(struct Builder *b, const char *source) {
  size_t incoming = strlen(source);
  if (b->len >= sizeof b->data || incoming > sizeof b->data - 1 - b->len)
    return false;
  memcpy(b->data + b->len, source, incoming + 1);
  b->len += incoming;
  return true;
}

int main(void) {
  /* Append two fragments */
  {
    struct Builder b = {0};
    CHECK(append_text(&b, "red") && append_text(&b, " sky"));
    CHECK(b.len == 7 && strcmp(b.data, "red sky") == 0);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The result is red sky with length 7.

The stored length avoids rescanning previous content before every append.

**Observe:** Length and content remain unchanged.

The empty append is a successful no-op, not an error or a new terminator-free state.

## Common pitfalls and diagnosis

Begin with the first relevant compiler warning or error. A declaration mismatch can cause many later diagnostics, so fix one cause at a time. If a check fails, compare actual and expected values and identify the earliest state transition that differs from the intended invariant. A program that compiles can still contain undefined behavior. A program that ran once without crashing can still access invalid memory.

For every pointer, identify its target object, bounds, alignment, lifetime and whether mutation is permitted. For every library call, inspect its return value before using output. For every owned resource, identify one release on each completed path. The worked examples and solutions explain the lesson-specific counterexamples; keep those distinctions rather than replacing a rejected input with a plausible default.
