## Purpose and mental model

<!-- textbook-foundations-start -->

### Text crosses several representation boundaries

The word "character" is convenient in everyday language but too imprecise for a model pipeline. A person sees rendered glyphs. Python stores a string as a sequence of Unicode code points. A file or network message encodes that sequence as bytes. A tokenizer then groups some representation into tokens and assigns vocabulary IDs. Confusing these layers can produce wrong length limits, broken round trips or mismatched model inputs before a single neural operation runs.

Start with the literal strings in Example A. The three letters in cat are three code points and three UTF-8 bytes. The four code points in café require five UTF-8 bytes because its precomposed accented letter uses two bytes. The smile symbol is one code point but four bytes. These facts explain why len(text) and len(text.encode("utf-8")) answer different questions. Neither expression is, in general, a complete algorithm for counting user-perceived characters or model tokens.

Encoding and decoding define a reversible boundary when their contract is respected. The program encodes a valid string with UTF-8, then decodes those bytes with UTF-8, recovering the exact string. The bytes are a representation of the code-point sequence, not a second linguistic interpretation of it. A tokenizer may also be reversible, but that depends on its normalization, unknown-token and special-token policies. "The output looks the same" is weaker than an exact round trip.

Example B deliberately constructs two different strings that can look alike. One contains a single precomposed é code point. The other contains e followed by a combining acute accent. Their code-point sequences and UTF-8 bytes differ. NFC normalization maps these two particular spellings to the same composed form. Once only the normalized result remains, it no longer tells us which original sequence was supplied. This is an intentional many-to-one transformation, unlike lossless encoding of the original string.

Normalization can be useful for consistent search or duplicate detection, but it must follow the task's identity policy. A data pipeline may need the raw text for provenance and a normalized form for matching. Keeping both allows us to inspect whether a transformation changed an identifier, quotation or offset. If a system cites a substring by byte offsets and another component later normalizes the text, the old offsets may no longer identify the same span. Version the transformation and define whether offsets refer to raw bytes, code points or tokenizer positions.

For language models, these distinctions affect both capacity and evaluation. A byte-based base vocabulary can represent many new spellings through byte sequences, but different text may require different numbers of tokens after merging. A fixed context budget counts model tokens, not visible words or Unicode code points. The tiny examples here do not predict token counts for an arbitrary production tokenizer; they teach the representation boundaries that make such counts meaningful. [Python's Unicode documentation](https://docs.python.org/3.12/howto/unicode.html) defines the string/encoding behavior used by these exercises.

## Trace the representation boundary before tokenization

A displayed mark, a Unicode code point, an encoded byte and a model token are different units. The precomposed letter é is U+00E9 and occupies two UTF-8 bytes, C3 A9 in hexadecimal. The decomposed spelling e followed by U+0301 occupies two code points and three UTF-8 bytes, 65 CC81. Both can render as one visible accented letter. A code-point count of one versus two therefore says nothing by itself about what a reader sees. Emoji sequences, combining marks and joiners produce further cases where one displayed grapheme spans multiple code points.

UTF-8 assigns a variable-length byte sequence to each Unicode scalar value. ASCII letters use one byte; many accented letters use two; the smile in Example A uses four. A strict encode/decode round trip preserves the represented Unicode string when the input is valid. It does not automatically preserve an original external file's line endings, byte-order mark, encoding choice or normalization history if earlier processing changed them. Define the boundary being tested: raw bytes→decoded string→re-encoded UTF-8 is a stronger byte claim than string→UTF-8→same string.

A byte-level tokenizer can split a multibyte code point across tokens. For é, one token might contain C3 and the next A9. Decoding either byte alone under strict UTF-8 fails, while concatenating the token bytes first reconstructs the valid sequence. The same issue appears when streaming generated tokens to a display: use an incremental decoder or buffer incomplete byte sequences instead of replacing each incomplete fragment independently. Replacement decoding can turn one valid cross-token character into several replacement marks, changing the eventual text.

Normalization changes the equality relation. NFC maps canonically equivalent strings to a composed representation where possible. The composed/decomposed é pair then agrees, but retaining only the normalized result cannot reveal which raw spelling arrived. NFC does not generally perform case folding, remove accents or equate unrelated look-alike characters. Compatibility normalization forms have a different contract and can erase distinctions that canonical normalization preserves. Do not add such transformations merely because they reduce the number of unique strings. The [Unicode normalization specification](https://www.unicode.org/reports/tr15/) defines these distinctions; the lesson uses only a small fixed canonical-equivalence example.

Consider duplicate detection. A raw-byte hash keeps the two accented spellings distinct, while a hash of their NFC UTF-8 encoding can identify them as the same canonical content. Both choices can be correct for different purposes. A source archive may need byte identity; an evaluation split may need canonicalized near-duplicate grouping to avoid putting equivalent text in both train and test. Retain the raw source identifier and transformation policy so the grouping is auditable. A content hash is not encryption and does not authorize access to the underlying text.

Token offsets must declare their coordinate system. If a span begins after café, its boundary can be four code points but five UTF-8 bytes from the start of that word. Applying a code-point offset directly to a byte buffer can cut inside a multibyte sequence. Applying offsets from normalized text to raw source text can select the wrong range even when the display looks similar. Extraction and citation systems should carry an explicit mapping or validate the quoted span against the exact source representation used to compute offsets.

The empty string illustrates why validation belongs to the current operation. It has a perfectly valid empty UTF-8 representation and a successful round trip. A later average over token losses may reject zero active targets. Rejecting empty text everywhere would conflate encoding validity with a downstream statistical requirement; accepting it into a mean without a defined denominator would make the opposite mistake.

**Interview reasoning:** "If the decoded text looks right, is the pipeline lossless?" Appearance alone cannot distinguish canonical spellings, dropped invalid bytes, line-ending changes or replacement decoding. Establish losslessness by comparing the promised representation under a strict policy. When normalization is intentional, state the equivalence being preserved and retain enough provenance to explain which original distinctions were discarded.

## Vocabulary and concepts

**Code point:** one Unicode numeric element in a Python string; it is not necessarily a complete displayed grapheme.

**UTF-8 byte:** one eight-bit unit in a variable-length encoding of Unicode text.

**Round trip:** encoding and decoding under a stated strict policy and obtaining the original representation.

**NFC normalization:** a Unicode canonical-composition policy that can merge equivalent code-point sequences.

**Replacement decoding:** a lossy policy that substitutes a replacement character for malformed bytes instead of preserving them.

## Syntax or reasoning anatomy

text.encode("utf-8") turns a string into bytes. payload.decode("utf-8") performs strict decoding by default and raises when byte sequences are invalid. len(text) counts Python code points; len(payload) counts bytes. Neither expression universally counts displayed characters or language-model tokens.

unicodedata.normalize("NFC", text) creates a normalized string rather than changing the original object. A hash of raw bytes identifies raw content; a hash of normalized bytes identifies the chosen canonicalized representation. Keep the policies labeled. The optional hash is not encryption, permission or a privacy guarantee. An empty string has a valid empty encoding, even though a later token-loss mean would still need a nonempty target denominator.

## Worked example / walkthrough

Run Examples A and B in order in one scratch file, then run that complete file in a fresh process. Example B may reuse the imports, helpers and fixture state established in Example A. Do not treat an isolated later block as a standalone program.

### Example A: Inspect bytes and code points

Compare three fixed strings and round-trip their exact UTF-8 payloads.

```python
texts = ["cat", "café", "🙂"]
counts = [(len(text), len(text.encode("utf-8"))) for text in texts]
assert counts == [(3, 3), (4, 5), (1, 4)]
assert all(text.encode("utf-8").decode("utf-8") == text for text in texts)
print(counts)
```

**Expected:** The accented word and smile require more bytes than code points. These are exact counts for the literal examples, not a general grapheme-counting algorithm.

### Example B: A deliberate identity change

Compare composed and decomposed spellings before and after NFC.

```python
import unicodedata

composed = "é"
# Construct directly to avoid a platform-dependent source-file normalization step.
decomposed = "e" + chr(0x0301)
assert composed != decomposed
assert composed.encode("utf-8") != decomposed.encode("utf-8")
assert unicodedata.normalize("NFC", decomposed) == composed
print(len(composed), len(decomposed))
```

**Expected:** Raw identity differs, while the explicit normalization makes these two fixtures agree. Retaining the normalized string cannot reconstruct which original spelling was supplied.

## Common pitfalls

If a count changes after export, inspect whether the file was decoded with a different codec or normalized. If a displayed string looks unchanged, compare repr, code points or encoded hex rather than assuming byte identity. If invalid bytes seem to disappear, inspect whether a replacement or ignore error policy was used.

A normalization policy can help detect canonical duplicates, but it does not identify every near-duplicate document or semantic paraphrase. Hash equality depends on the chosen representation, not on natural-language meaning. Keep original provenance where the task requires it, avoid collecting private text, and never describe a plain content hash as anonymization or encryption.
