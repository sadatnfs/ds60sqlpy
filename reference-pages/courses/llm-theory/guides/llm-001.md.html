llm-001: Language-model claims and evaluation units#

Level and prerequisites#

Beginner within this subject; estimated time: 75 minutes. Direct prerequisite: python-16. The entry Python course supplies basic functions, lists, dictionaries, testing and NumPy arrays. This unit introduces its subject terms explicitly; it requires no service account, model weights, GPU or database.

Learning objectives#

Separate predicting tokens from evidence of knowledge, reasoning or reliability. By the end, you can produce the exact observations below, explain one plausible wrong result and transfer the reasoning to a new fixed fixture without copying a solution. Keep your first prediction alongside the actual evidence so a changed conclusion remains visible.

Purpose and mental model#

What a language model actually supplies#

Imagine asking an assistant, "Which date does this contract give for renewal?" Several different things must happen. The document must be available. Its text must be represented as symbols the model accepts. The model must produce an answer in the requested form. Finally, someone or something must determine whether that answer is supported by the correct clause. A fluent sentence tells us that the generation step produced plausible language. It does not, by itself, establish the other steps. This distinction is the starting point for studying language models rather than merely using their interfaces.

A token is one element of the model's vocabulary. It might represent a word, part of a word, punctuation or a byte sequence, depending on the tokenizer. A prefix is the ordered list of tokens already supplied. A next-token language model assigns a probability to every possible next token, conditional on that prefix. If the vocabulary has V entries, its immediate output can be understood as V numbers that sum to one. Generation repeatedly chooses an entry, appends it to the prefix and asks for another distribution. The word "large" concerns scale; it does not change this basic prediction interface.

The model's numerical output and the application's answer are therefore different objects. A distribution may favor the token that starts a wrong date because that continuation fits patterns learned during training. Conversely, a low-probability but permitted continuation may happen to be correct. Training attempts to improve a specified prediction objective over data. An application then combines that trained mechanism with prompts, retrieval, tools, decoding rules and output checks. Later chapters make each of these parts inspectable, so a failure can be located rather than attributed vaguely to "the AI."

The three-record worksheet below introduces another distinction before any architecture: the unit of evidence. The first two records belong to one family and are both correct; the third belongs to a second family and is wrong. There are three rows, but only two represented families. To compute the row average, add the three correctness indicators and divide by three, giving 2/3. To give each family equal weight, first compute its own average, obtaining 1 and 0, then average those two values, giving 1/2. We have not discovered that one formula is mathematically wrong. We have discovered that the formulas answer different questions.

This matters whenever examples are related. A hundred paraphrases of one document can be useful for checking consistency, yet they do not demonstrate coverage of a hundred unrelated document types. The same discipline applies to mechanism tests. A three-token attention calculation can establish exact arithmetic and expose a mask bug. It cannot establish reliable contract interpretation. We will use small fixtures because they reveal mechanisms, then state precisely where new data or a larger experiment would be needed.

Keep three questions separate as you read: what quantity does the algorithm compute, what observation did the code actually produce, and what real-world conclusion would that observation support? Those questions let a beginner use equations and tests as evidence without treating every successful run as a certificate of intelligence.

From a fluent answer to a defensible measurement#

A useful model claim identifies a task, an input distribution, an observable outcome and a decision. Consider a document assistant asked to extract the renewal date from a contract. The task is not simply "write good text." The input is a particular version of a document, the desired output is a date or an explicit abstention, and the correctness rule must specify which clause governs. A fluent date with no supporting clause can fail the task even when every sentence is grammatical. Conversely, a terse structured answer can succeed. Fix that contract before choosing a score.

Let c_i be 1 when question i passes the declared rule and 0 otherwise. Record accuracy is sum_i c_i / N for N questions. If questions belong to G source families, equal-family accuracy is (1/G) sum_g [(1/n_g) sum_(i in g) c_i]. Here n_g is the number of questions in family g. These formulas differ only in weighting, but that difference changes the population represented by the summary. Equal-family weighting can suit a target where each source family matters equally. Record weighting can suit a workload whose actual question frequencies resemble the sample. Neither formula automatically chooses the right deployment distribution.

In the worked table, adding eight more correct paraphrases to family A changes record accuracy from 2/3 to 10/11, while the equal-family value remains 1/2. The apparent record improvement did not add a new source family or fix the failure in B. This is an exact arithmetic counterexample to treating every added row as independent evidence. Group-aware splitting keeps related source material together; family-weighted reporting answers a weighting question. These are complementary controls. Weighting alone cannot repair a train/test overlap.

When comparing two versions, retain paired outcomes on the same questions. Suppose version A is right on q1 and q2, and version B is right on q1 and q3. Both score 2/3, but one previously successful case regressed while one failure improved. A single aggregate hides that exchange. Record the changed cases, their source families and failure categories. A paired comparison controls which cases were asked; it does not remove uncertainty about unobserved families or guarantee that the reference answers are valid.

Abstention changes the decision contract too. If an assistant answers two of three questions correctly and abstains on the third, answer-only accuracy is 2/2, coverage is 2/3, and answered-correct fraction over all requests is 2/3. The 100 percent figure alone conceals a third of requests receiving no answer. When unsupported answers are costly, that may be a useful tradeoff, but it must be a deliberate policy with coverage and error costs reported together. A system that abstains on every request has no defined answer-only accuracy; assigning it a perfect score would be a denominator mistake.

Mechanism tests and empirical tests catch different faults. A causal-mask test can show that later token values do not affect an earlier output under the supplied computation. It cannot show that a training corpus excluded the evaluation answer. A held-out answer check can expose a factual error without identifying the exact internal mechanism that caused it. Start diagnosis at the narrowest supported statement: what changed, which condition was violated, and which alternative explanations remain. Avoid translating a passed component test into a broader claim about knowledge or reasoning.

For data-science work, keep the numerical analysis independently executable. An LLM can suggest a query, summarize a result or propose an interpretation, but a generated explanation does not establish that the query ran against the intended dataset, that an estimator's assumptions hold, or that a correlation is causal. Preserve dataset/version identity, executable code and computed outputs separately from narrative. The applied assistant route develops that distinction through grounded claims and retrieval and answer evaluation.

Interview reasoning: "Would more evaluation questions settle the reliability question?" More independent, representative observations can improve an estimate. More copies of an easy family may mainly change its weight. First inspect provenance, relatedness, coverage and the correctness rule, then decide what new cases would challenge the current conclusion. The three-row lesson table is enough to demonstrate the weighting mechanism; it is not enough to establish a stable population estimate.

Vocabulary and concepts#

Mechanism claim: a statement about a specified computation or information boundary, checked against that implementation and its assumptions.

Empirical claim: a statement about observed behavior on a named evaluation set, metric and unit.

Unsupported claim: a conclusion extending beyond the evidence or conditions actually checked.

Evaluation unit: the item weighted by a metric, such as token, question, source document or question family.

Counterexample: a concrete case contradicting a universal statement; one fluent false answer is enough to refute fluency always means truth.

Syntax or reasoning anatomy#

Read an evidence statement as subject, conditions, observation, unit and limitation. For example, on these three question records, two answers match the supplied references reports a count and a denominator. It does not claim two-thirds of all future questions will be correct. Architecture or code inspection may support a mask property, but that property does not establish factuality.

A worksheet should retain question ID, source family, reference answer, observed answer, correctness rule and result. A family-weighted score first aggregates within each family and then gives each family equal weight. A record-weighted score gives every record equal weight. Both can be valid, but they answer different questions. Decide the unit before seeing which score looks better.

Worked example / walkthrough#

Example A: One table, two declared units#

There are three authored questions. Two near-paraphrases belong to family A and are correct; one question from family B is incorrect.

ID   Family   Correct
q1   A        yes
q2   A        yes
q3   B        no
Record-weighted accuracy: 2/3
Family means: A=1, B=0
Equal-family accuracy: (1+0)/2 = 1/2

Expected: Neither number is fabricated, but reporting one without its unit hides the weighting policy. The table also cannot estimate performance across a broad population.

Example B: A fluent answer can be wrong#

Use an arithmetic question so no remote fact lookup or model is needed.

Question: What is 7 + 8?
Reference: 15
Observed answer: The result of adding seven and eight is thirteen.
Fluent wording: yes
Correct by the arithmetic reference: no

Expected: A polished sentence is not a correctness test. Conversely, one incorrect answer does not prove every answer is wrong; it refutes a universal fluency-implies-truth claim.

Prediction before your attempt#

Before executing or calculating, write the result you expect from the normal fixture and which changed condition would invalidate it. Save that prediction. Afterward, name the first observation that supported or contradicted it rather than rewriting your original answer to match the reference.

Exercises#

  1. Classify six claims. Classify these: a fixed mask blocks later keys; a table has 2/3 correct records; all future outputs are true; this fixture has no observed failures; no observed failures means zero risk; a supplied score matrix has one row per query. Expected: Mechanism, empirical, unsupported, empirical, unsupported, mechanism, in that order. Verify: Write the evidence type and a test or counterexample next to all six statements; do not substitute a single reliability label.
  1. Compute two accuracies. Use q1=A/correct, q2=A/correct, q3=B/incorrect and compute record-weighted versus equal-family accuracy. Expected: Record-weighted 2/3 and equal-family 1/2. Verify: Inspect the three correctness values and the two separate family means before calculating the final averages.
  1. Challenge fluent correctness. Use the 7+8 answer in the walkthrough. State which universal claim it contradicts and which broad negative claim it does not establish. Expected: It contradicts fluent answers are always correct; it does not show that every answer is false. Verify: Record reference 15, observed 13 and the single failed equality as the counterexample.
  1. Detect repeated evidence. Duplicate q1 using the same ID and family. Decide whether the duplicate should count as another independent question. Expected: A repeated question ID is rejected; related but distinct IDs must remain in their family for grouped evaluation. Verify: Capture the duplicate-ID ValueError in the optional reference checker or identify the repeated row explicitly in writing.
  1. Refuse an empty accuracy. Evaluate no questions and decide whether accuracy is zero, one, or undefined. Expected: The mean is undefined; the reference raises ValueError for an empty evaluation. Verify: Retain the empty-set diagnosis and then recompute the original 2/3 table to show the valid result remains available.
  1. Transfer to a new family balance. Use three correct questions from family A and one incorrect question from family B. Compare record and family weighting, then write a bounded report. Expected: Record-weighted accuracy 3/4; equal-family accuracy 1/2. The report names four records and two families. Verify: Inspect a four-row table, both denominators and a statement that unseen families remain untested.

Progressive hints#

  • Hint 1: Underline what is being claimed: code behavior, a finite observation, or a universal conclusion.
  • Hint 2: Write each denominator in words before doing division.
  • Hint 3: Keep repeated question IDs distinct from different IDs in the same family; both affect how evidence should be counted.

Common pitfalls#

If two reports disagree, inspect the evaluation unit before deciding one model is better. A token-weighted metric, question accuracy and equal-family average need not match. If a result improves after adding paraphrases of an easy question, check whether the report is measuring repeated evidence rather than broader coverage.

If a component test passes, retain the exact property it checked. Causal attention can be correct while a tokenizer was fit on validation text or an answer cites unsupported material. If zero failures are observed, record how many cases were tested and which conditions were missing. A finite result is useful; describing it as zero possible risk discards the limitation that makes the result interpretable.

Self-check#

Without the examples, distinguish a mechanism claim from an empirical claim using one new sentence each. Then explain how a family-weighted metric can differ from a record-weighted one without either calculation being arithmetically wrong.

Evidence review#

Use a 0, 1 or 2 score for each of five dimensions: the declared data/observation contract, a correct normal-case derivation, diagnosis of the changed fixture, explicit handling of the invalid case, and a fresh explanation of the evidence boundary. Normally seek 8/10 with no zero for the contract or claim boundary, then require a new transfer example. This is a human learning rubric, not an automatic certification or completion awarded by a single successful Run.
