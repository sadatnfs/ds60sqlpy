web-042: Namespaces, project layout and Composer boundaries#

Level and prerequisites#

Intermediate; allow about 110 minutes, with extra time for independent practice. Direct prerequisites: web-041

Learning objectives#

Design a small project layout with source, tests and a public entrypoint. Describe a deliberate dependency update and lockfile review. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

Purpose, vocabulary and mental model#

A namespace groups names so two libraries can use similar class names without colliding. It is a naming mechanism, not a directory, a security sandbox or an automatic package installer. Autoloading is a separate mechanism that resolves a class name to source when needed. Composer commonly manages package dependencies and generates an autoloader for a project.

A dependency manifest describes requirements, while a lockfile records a resolved dependency set. Reproducible deployment uses the reviewed lockfile and installed artifacts, with an explicit update process for security and compatibility. Opening a lesson must not download packages. The classroom single-file PHP worker has no arbitrary Composer project support, so the runnable example demonstrates namespaces in one file and the project workflow remains an external design.

Syntax anatomy and mechanism#

PHP namespace declarations have placement rules. A bracketed namespace block can coexist with an explicitly bracketed global namespace in a single-file teaching program. Production projects should use a coherent autoloading convention rather than a manual chain of untrusted includes. A user-controlled include path can become code execution, so package and file resolution belong to reviewed application code.

Classroom execution and offline inputs#

Choose the PHP CLI worker in the classroom. The pad is staged as main.php and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write <?php at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

Worked example / walkthrough#

Worked example 1: A qualified name#

The namespace differentiates this class from another Label class.

namespace Learning;
final class Label { public static function text(): string { return 'Study'; } }

Expected observation: The fully qualified class name is Learning\Label.

Worked example 2: A project contract#

This is configuration for a separately prepared project, not a pad command.

{"autoload":{"psr-4":{"Learning\\":"src/"}}}

Expected observation: The convention maps a namespace prefix to the project's source directory after autoloader generation.

Six progressive exercises#

Exercise 1: Explain what a namespace does and does not install.#

Expected evidence: It groups names; it does not fetch code or create an autoloader by itself.

Progressive hint: Trace the smallest example before editing. Name which values are source and which are observations.

Exercise 2: Compare a short imported name with its fully qualified name.#

Expected evidence: Both can refer to the same class when the import is explicit.

Progressive hint: Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

Exercise 3: Design a small project layout with source, tests and a public entrypoint.#

Expected evidence: Application code and tests stay separate from the server's public document root.

Progressive hint: Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

Exercise 4: Diagnose a missing class despite a correct namespace declaration.#

Expected evidence: Check source availability and autoload configuration separately from naming.

Progressive hint: Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

Exercise 5: Explain why an untrusted include filename is dangerous.#

Expected evidence: It can cause unintended code to be loaded or executed outside the reviewed project.

Progressive hint: Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

Exercise 6: Describe a deliberate dependency update and lockfile review.#

Expected evidence: Resolve changes explicitly, review packages and licenses, test the result and deploy the recorded set.

Progressive hint: Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

Debugging and common mistakes#

Do not paste a namespace declaration after arbitrary executable code and expect it to work. The runnable reference illustrates qualified built-in naming and layout data, not an installed Composer project. A lockfile does not eliminate the need for ongoing dependency review.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

Retrieval, transfer and next steps#

Close the worked answers and explain namespace, autoloading, Composer without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
