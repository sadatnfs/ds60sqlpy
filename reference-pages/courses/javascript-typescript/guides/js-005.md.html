js-005: Arrays and immutable transformations#

Level and prerequisites#

Beginner, approximately 90 minutes. Direct prerequisites: js-004

Learning objectives#

Explain transformation, reduction, shallow copy, mutation with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Double 1, 2, 3, 4 and keep results above 4. The final task tests copy records for a specific edit.

Purpose and mental model#

Array operations differ in whether they mutate the container, return a new container or reuse referenced objects. map transforms values, filter selects them, and reduce combines them under an explicit accumulator contract. A new array does not necessarily contain new objects: shallow copies preserve nested references. sort mutates its array and uses string ordering by default, which can misorder numbers. toSorted returns a sorted copy in the prepared Node 24 runtime.

An immutable transformation means preserving the prior value needed by the application, not merely using const. const prevents rebinding the variable but does not freeze its array. Choose mutation or copying based on ownership and history requirements. Test both returned results and the original input when preservation is part of the contract.

Vocabulary and concepts#

Transformation: A rule producing new values from existing elements.

Reduction: Combining elements into one accumulator result.

Shallow copy: A new container retaining references to nested objects.

Mutation: Changing the state of an existing object.

Syntax anatomy and execution trace#

map receives value, index and array; avoid passing a callback that unintentionally interprets the extra arguments. filter keeps elements whose predicate is truthy. reduce needs an identity for an empty input unless absence is handled separately. Use (a, b)=>a-b for numeric ordering. Spread or slice copies the outer array only; copy nested records deliberately when they will be edited.

Worked example / walkthrough#

Example A: Map and filter without changing input#

The pipeline returns new arrays while retaining the original numeric fixture. Object-valued elements would need an additional ownership analysis.

import { strict as assert } from 'node:assert';



export async function verify() {
  // Worked example
  {
    const original = [1, 2, 3, 4];
    const result = original.map(value => value * 2).filter(value => value > 4);
    assert.deepEqual(result, [6, 8]);
    assert.deepEqual(original, [1, 2, 3, 4]);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: 6, 8; original array unchanged.

Example B: Supply a reduction identity#

The identity defines the empty case. Omitting it would make an empty array throw and change the callback's initial state.

import { strict as assert } from 'node:assert';



export async function verify() {
  // Worked example
  {
    assert.equal([].reduce((sum, value) => sum + value, 0), 0);
    assert.equal([1, 2, 3].reduce((sum, value) => sum + value, 0), 6);
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: 0 and 6.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

Exercises#

  1. Map and filter without changing input. Double 1, 2, 3, 4 and keep results above 4. Expected: 6, 8; original array unchanged. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Supply a reduction identity. Sum an empty array and 1, 2, 3 using initial 0. Expected: 0 and 6. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Expose default sort coercion. Sort 10, 2, 1 with default and numeric comparators. Expected: default 1, 10, 2; numeric 1, 2, 10. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Preserve an array while sorting. Use toSorted on 3, 1, 2 and inspect both arrays. Expected: sorted 1, 2, 3; original 3, 1, 2. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Expose a shallow copy alias. Spread an array containing one object and mutate that object through the copy. Expected: original nested value also changes. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Copy records for a specific edit. Map records to new objects before changing one field. Expected: edited record changes; original record stays 1. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
