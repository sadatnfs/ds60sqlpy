# go-017: Readers, writers and bounded streaming

## Level and prerequisites

Intermediate. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-016

## Learning objectives

Stream data through io.Reader and io.Writer with explicit size limits and exact record framing. Along the way, explain reader, short read, input budget; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

io.Reader and io.Writer describe data movement independently of where bytes are stored. A reader can return some bytes and an error together; process the bytes before deciding whether the error ends the stream. One Read call is not guaranteed to fill a buffer. io.ReadFull expresses a different contract: obtain exactly the requested length or report why that was impossible. Streaming avoids loading an entire input into memory, but it is only bounded when the caller limits input, buffering and output. A limit reached is not automatically valid end-of-document evidence. Keep transport completion separate from format validation.

## Vocabulary and concepts

- **Reader:** An interface supplying bytes incrementally.
- **Short read:** A successful read returning fewer bytes than requested.
- **Input budget:** The maximum amount of input an operation permits.

## Syntax anatomy and reasoning

Read receives a byte slice and returns n and err. Only the first n bytes contain this call's data. io.EOF means the stream has ended; io.ErrUnexpectedEOF means a fixed-size request ended after partial data. io.Copy repeatedly transfers data and returns a count plus error. io.LimitReader caps visible bytes. bytes.Buffer provides an in-memory reader/writer useful for deterministic tests.

## Worked example / walkthrough

### Worked example 1: Copy a stream

Copy alpha from a strings.Reader into bytes.Buffer.

```go
package main

import (
	"bytes"
	"fmt"
	"io"
	"strings"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Copy a stream
	{
		var out bytes.Buffer
		n, err := io.Copy(&out, strings.NewReader("alpha"))
		check(err == nil && n == 5 && out.String() == "alpha", "copy")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Five bytes are copied and output is alpha.

The consumer depends on Reader and Writer behavior rather than a particular file or socket implementation.

### Worked example 2: Require a full record

Read exactly four bytes from a two-byte source.

```go
package main

import (
	"bytes"
	"fmt"
	"io"
	"strings"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func main() {
	// Copy a stream
	{
		var out bytes.Buffer
		n, err := io.Copy(&out, strings.NewReader("alpha"))
		check(err == nil && n == 5 && out.String() == "alpha", "copy")
	}

	// Require a full record
	{
		buf := make([]byte, 4)
		n, err := io.ReadFull(strings.NewReader("ab"), buf)
		check(n == 2 && err == io.ErrUnexpectedEOF, "partial record")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Two bytes arrive and ErrUnexpectedEOF is returned.

Partial data is useful evidence, but it is not a complete fixed-width record. Treating any positive n as completion would accept truncation.

## Predict before running

## Exercises

### Exercise 1: Copy a stream: change one input

Copy worked example 1, change `n, err := io.Copy(&out, strings.NewReader("alpha"))` to `n, err := io.Copy(&out, strings.NewReader("alpha!"))` and predict the failure before running; then restore the line.

**Expected:** The edited run panics with `copy` because `err == nil && n == 5 && out.String() == "alpha"` no longer holds.

**Verify:** Restoring `n, err := io.Copy(&out, strings.NewReader("alpha"))` makes the check pass again with the worked observation: five bytes are copied and output is alpha.

### Exercise 2: Require a full record: debug a regression

A one-token regression in worked example 2 makes a line read `n, err := io.ReadFull(strings.NewReader("ab!"), buf)`. Repair it without changing the check.

**Expected:** The defective run panics with `partial record`; after restoring `n, err := io.ReadFull(strings.NewReader("ab"), buf)`, two bytes arrive and ErrUnexpectedEOF is returned.

**Verify:** The failing run shows message `partial record`; after the repair `n == 2 && err == io.ErrUnexpectedEOF` holds again.

### Exercise 3: Bound visible input

Read at most three bytes from abcdef.

**Expected:** The visible result is abc.

**Verify:** Your solution must keep `err == nil && string(v) == "abc"` true. Control: changing `v, err := io.ReadAll(io.LimitReader(strings.NewReader("abcdef"), 3))` to `v, err := io.ReadAll(io.LimitReader(strings.NewReader("abcdef"), 4))` panics with message `limit`; revert it.

### Exercise 4: Detect excess data

Read a four-byte budget for a three-byte maximum.

**Expected:** A four-byte result proves the maximum was exceeded.

**Verify:** Your solution must keep `err == nil && len(v) > 3` true. Control: changing `check(err == nil && len(v) > 3, "excess input")` to `check(err != nil && len(v) > 3, "excess input")` panics with message `excess input`; revert it.

### Exercise 5: Preserve an empty stream

Copy an empty reader to a buffer.

**Expected:** The count is zero and there is no error.

**Verify:** Your solution must keep `err == nil && n == 0 && out.Len() == 0` true. Control: changing `check(err == nil && n == 0 && out.Len() == 0, "empty copy")` to `check(err != nil && n == 0 && out.Len() == 0, "empty copy")` panics with message `empty copy`; revert it.

## Common pitfalls and diagnosis

Treating one Read as a whole message, or any positive n as a complete record, are the classic stream bugs; both accept truncated input from slow or chunked sources. Another is discarding the bytes returned alongside an error. A LimitReader also truncates silently: reading exactly the maximum cannot tell you whether more data followed, so read one extra byte when excess must be rejected.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Copy a stream: change one input

1. Restate the expected observation: Five bytes are copied and output is alpha.
2. io.Copy reports the number of bytes written. How many bytes are in alpha?
3. alpha! has six bytes, so Copy reports 6 and `n==5` fails along with the output comparison. Copying works; the input changed.

### Hint for investigation 2: Require a full record: debug a regression

1. Restate the expected observation: Two bytes arrive and ErrUnexpectedEOF is returned.
2. ReadFull wants exactly len(buf) bytes. What does it return when the source ends early?
3. Three bytes arrive from ab!, so n is 3, not 2, while the error is still ErrUnexpectedEOF. Restore the two-byte source; ReadFull behaves correctly.

### Hint for investigation 3: Bound visible input

1. Restate the expected observation: The visible result is abc.
2. LimitReader stops after n bytes. Which bytes of abcdef are visible?
3. The limit controls resource use.

### Hint for investigation 4: Detect excess data

1. Restate the expected observation: A four-byte result proves the maximum was exceeded.
2. The budget is one more than the maximum. What does a four-byte result prove?
3. Reading maximum plus one distinguishes exactly-at-limit data from truncated over-limit input without unbounded allocation.

### Hint for investigation 5: Preserve an empty stream

1. Restate the expected observation: The count is zero and there is no error.
2. An empty source is still a valid stream. What should Copy return for count and error?
3. An empty stream can be valid transport input even when an application later requires at least one record.

### Hint for investigation 6: Transfer exact framing

1. Restate the expected observation: The header is AB and payload is xyz.
2. Both ReadFull calls consume the same reader. Where does the second read begin?
3. Explicit frame lengths prevent a reader from guessing where one logical object ends.
