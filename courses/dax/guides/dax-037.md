## The question and the mechanism

Specify tie behavior separately from deterministic ordering and selection size.

Ranking answers where a value sits within a declared comparison population. It does not inherently guarantee a unique position for every row. Equal scores can share a rank; dense ranking continues with the next distinct rank, while skip ranking leaves a gap corresponding to tied positions. Choose the policy before interpreting a leaderboard.

Our literal candidate table contains 100,80,80 and 50. Dense ranks are 1,2,2,3; skip ranks are 1,2,2,4. A Top 2 selection based only on score can include all three rows at or above the tied cutoff. That behavior differs from selecting exactly two rows with an additional unique ordering key.

A tie-breaker is a decision rule, not evidence that one tied candidate has a better score. Alphabetical Name is used only to make the tiny fixture deterministic. In an actual model, specify a meaningful, stable unique key and disclose whether a limited display excludes equally scored members. Numerical precision also matters: floating-point values that look equal after formatting may not compare as exactly equal.

## Vocabulary and expression anatomy

RANKX iterates Candidates and evaluates Score for its ranking distribution. DESC requests higher scores first; DENSE and SKIP choose the gap policy. TOPN's second ordering expression resolves the tie when an exact-sized set is intended. The outer ORDER BY establishes display order independently.

Concepts to explain in your own words: **RANKX**, **dense rank**, **skip rank**, **TOPN**, **tie-breaker**.

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    VAR Candidates = DATATABLE ( "Name", STRING, "Score", INTEGER,
        { { "Alpha", 100 }, { "Beta", 80 }, { "Gamma", 80 }, { "Delta", 50 } } )
```

### Case A: Dense and skip ranks

**Starting context:** Query-local candidate fixture; descending score; four unique names and one score tie.

```dax
EVALUATE ADDCOLUMNS ( Candidates, "DenseRank", RANKX ( Candidates, [Score], , DESC, DENSE ), "SkipRank", RANKX ( Candidates, [Score], , DESC, SKIP ) )
ORDER BY [Score] DESC, [Name] ASC
```

**Context trace:**

1. Alpha has the only score 100 and rank 1.
2. Beta and Gamma share score 80 and rank 2.
3. Delta follows the tie at dense rank 3 or skip rank 4.

**Hand-derived worked-reference result:**

| Name | Score | DenseRank | SkipRank |
| --- | --- | --- | --- |
| Alpha | 100 | 1 | 1 |
| Beta | 80 | 2 | 2 |
| Gamma | 80 | 2 | 2 |
| Delta | 50 | 3 | 4 |

The shared ranks are intentional. Displaying Beta before Gamma does not make its dense rank smaller.

### Case B: Tied cutoff versus a deliberate tie-breaker

**Starting context:** Same candidate table; compare score-only selection with score plus unique Name ordering.

```dax
EVALUATE ROW ( "TopTwoByScoreRows", COUNTROWS ( TOPN ( 2, Candidates, [Score], DESC ) ), "TopTwoWithTieBreakerRows", COUNTROWS ( TOPN ( 2, Candidates, [Score], DESC, [Name], ASC ) ) )
```

**Context trace:**

1. The second score position is 80 and two candidates share it.
2. Score-only TOPN includes Alpha, Beta and Gamma.
3. Adding Name as a tie-breaker selects Alpha and Beta exactly.

**Hand-derived worked-reference result:**

| TopTwoByScoreRows | TopTwoWithTieBreakerRows |
| --- | --- |
| 3 | 2 |

A user-facing Top N specification must say whether ties are all included or resolved by a secondary key.

## Progressive hints

1. There is no longer a tie at 80.
2. Only one candidate has the highest score.
3. A region-specific rank and a global rank are different questions.
4. Formatting does not necessarily change the stored numeric values.
5. RANKX has documented blank treatment; business eligibility can still differ.
6. An exact capacity requires a disclosed tie-break rule.
