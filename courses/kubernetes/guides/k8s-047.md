# k8s-047: ClusterIP Services and Layer 4 routing

## Level and prerequisites

Intermediate; about 120 minutes plus optional supervised host observations. Direct prerequisites: `k8s-046`. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

## Learning objectives

Trace a fresh TCP request through the Service. Design a stable endpoint for replacing Pods. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

## Purpose, vocabulary and mental model

A ClusterIP Service gives clients a stable virtual endpoint for a changing set of backends. The selector usually identifies Pods by labels. The Service port is what clients address; targetPort identifies the backend listener, either numerically or through a named container port. A Service does not select an image name or Deployment name directly.

Layer 4 routing concerns transport connections such as TCP. It does not normally choose a backend by HTTP path or rewrite an application URL. HTTP-aware routing belongs to a proxy or controller with that capability. A long-lived TCP connection can continue using one backend even if individual requests are numerous.

A Service can exist with no eligible endpoints. Its ClusterIP allocation is not a health certificate. Read the selector, matching Pod labels, readiness and EndpointSlices, then issue a fresh request from the intended caller. Each observation narrows a different possible failure.

## Mechanism and field-by-field reasoning

The fixture uses Service port 80 and named targetPort http, resolving to containerPort 8080 on the selected Pod. Named ports help avoid duplicating a number but still need a matching declaration and real listener. Protocol defaults and transport type should be explicit when teaching non-TCP workloads.

A selectorless Service can be paired with manually managed EndpointSlices, but it has a different ownership model and extra restrictions. This introductory fixture uses selectors so the controller maintains endpoints. Do not manually edit controller-owned slices to hide a wrong selector.

## Trace the request or control path

```text
client -> ClusterIP:80 -> service data plane -> ready endpoint PodIP:8080
selector labels -> endpoint controller -> EndpointSlice addresses and ports
```

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

## Worked example / walkthrough

### Worked example 1: Read the complete routing fields

This is a Service fragment from the maintained fixture.

```yaml
type: ClusterIP
selector:
  app: network-study
ports:
  - name: http
    port: 80
    targetPort: http
```

**Expected observation:** Clients use 80; the named backend port resolves to the app listener 8080.

### Worked example 2: Compare a selector mismatch

Only the labels changed.

```text
Service selector: app=network-study
Pod labels: app=wrong
result: no matching backend Pods
```

**Expected observation:** The Service can retain its virtual IP while traffic has no eligible destination.

## Diagnosis, failure boundaries and common mistakes

The controlled failure in this chapter is: Diagnose a ClusterIP with no ready endpoints. Its distinguishing result is Inspect selector matches and readiness before external routing. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
