# dme-032: Governance, minimization, retention and review

## Governance changes what a system is allowed to do

A technically correct query can still be inappropriate for its purpose. Governance defines responsibilities and constraints around collection, access, use, retention, sharing and review. For an engineer, those decisions must become concrete system boundaries: which fields are collected, which principals can perform which actions, which outputs are released, how long copies remain and how decisions are recorded. A policy paragraph that no execution path checks does not enforce itself.

This chapter uses entirely synthetic person labels and an illustrative local policy. It is not a legal standard, a compliance certification or a universal privacy recipe. The program performs actual DuckDB queries and deletion, while explicitly showing what those local actions do not accomplish. The aim is to learn how to translate a declared policy into observable behavior and to recognize residual risk rather than label data “safe” after one transformation.

Three ideas are especially important. Minimization limits data to what a task needs. Purpose restriction distinguishes one approved use from another. Retention limits how long data remain available under a declared policy. These ideas interact: a short retention period does not justify collecting unnecessary fields, and removing direct identifiers does not necessarily prevent identification through other attributes.

## Define the synthetic release contract

The fixture has four observations with a person label, region, age band, package count and observation date. The approved analytical purpose is capacity planning. The application exposes an aggregate grouped by region and age band to an analyst role, and it releases only groups with at least two people. Direct person labels are absent from that released table. An unapproved trainer role and model-training purpose are denied by the synthetic application check.

For group \(g\), let \(n_g\) be its observed population and \(s_g\) its package total. The illustrative release rule is

\[
\operatorname{release}(g)=\mathbf{1}[n_g\geq 2].
\]

This threshold makes a suppression mechanism easy to inspect; it does not guarantee anonymity. A group of two can still reveal information when an observer knows one member's value, when repeated queries enable differencing, or when another dataset narrows the possibilities. A production release policy needs a threat model and review appropriate to the data and use, not blind adoption of the number two.

The program keeps suppressed-group accounting separate from released values. That helps explain why the output population is smaller without exposing each suppressed person's package count. Even suppression counts can leak information in some contexts, so this is an educational diagnostic, not a claim that every metadata field is harmless to publish.

## Worked case 1: minimize the released table and reject another purpose

`example_one()` groups the four synthetic observations. North and age band 20s contains two people with two and three packages, giving a released total of five. South/30s and south/40s each contain one person and are suppressed. The actual result table therefore has one row: north, 20s, two people, five packages.

The program also attempts the same operation under an unapproved training purpose and role. The application denies it. This demonstrates that technical access to a function need not imply permission for every use of its data. In a real service, trusted authentication must establish the principal, and all relevant access paths must enforce the policy. Here the role and purpose strings are synthetic function arguments, so this is an application-policy example rather than a secure identity system.

The output helper publishes the bounded aggregate as an accessible table. The table description explains the released and suppressed populations. A learner can inspect the result without needing to infer tuple positions from raw stdout. No real personal data are used, and no external sharing operation is performed.

## Worked case 2: pseudonyms remain linkable, and retention is local

The second case replaces direct person labels with deterministic HMAC-derived pseudonyms using an explicitly synthetic classroom key. HMAC is a keyed hash construction. The example truncates the result for readability and does not propose this exact representation as a production identity design. A real system needs key management, collision analysis, rotation and a purpose-specific linkage policy.

The retained region and age-band combinations still uniquely match person-c and person-d in a separate synthetic lookup. The program recovers those labels through the quasi-identifying attributes without reversing the HMAC. This demonstrates why pseudonymization is not the same as anonymization. Protecting a direct identifier does not remove information in other fields or prevent linkage to external knowledge.

The case then applies a declared seven-day local retention rule at an explicit reference date of January 11. The inclusive cutoff is January 4; rows earlier than that are deleted. The January 1 observation is removed, leaving three rows. The audit reports before: four, after: three and removed: one. Using an explicit reference date makes the example reproducible instead of changing its result whenever a learner runs it.

The operation deletes rows from this local table only. It does not delete backups, exported files, logs, feature snapshots or trained models. The report states that boundary directly. A real deletion or retention workflow needs an inventory of relevant copies and a policy for each; a successful SQL DELETE on one table cannot certify that all downstream information disappeared.

## Access, purpose and the minimum necessary output

Minimization can happen at several stages. A source collector can avoid acquiring an unnecessary field. A transformation can discard fields before producing a shared dataset. A query layer can expose a reviewed aggregate rather than raw records. Earlier minimization can reduce the number of copies that require protection later, but it must preserve the information necessary for the legitimate task and its quality checks.

Purpose restriction also affects ML workflows. Data approved for a limited operational report should not automatically become training data for an unrelated model. Training can create persistent artifacts and new inference risks. A model's feature list, training population, retention assumptions and approved use should be reviewed together. The later ML lifecycle chapters connect those decisions to model cards, registries and activation gates.

Authorization and audit serve different roles. An authorization check decides whether an action may proceed. An audit record explains what was attempted, allowed or denied under which policy version. Logging a prohibited action after it succeeds is not enforcement. Conversely, an unexplained denial without sufficient operational context can be difficult to review or correct. Avoid placing sensitive payloads or credentials into the audit trail while retaining the minimum evidence needed for accountability.

## Retention and deletion require an inventory

A dataset can propagate into staging tables, analytical publications, caches, notebook exports, backups, metrics and model artifacts. Lineage helps locate descendants, but the policy must distinguish copies that can be rebuilt, records that must be retained for a defined reason and artifacts that need separate review. The exact obligations depend on the organization and use; this tutorial teaches engineering mechanisms rather than prescribing legal requirements.

Logical deletion and physical erasure can occur at different times. Snapshot tables may retain earlier files, databases may retain pages or logs until maintenance, and backups may follow a separate schedule. A system should describe its actual retention lifecycle and verify the promised boundary. Do not tell a consumer that data are gone from every location merely because the current query no longer returns them.

A retention job also needs correctness checks. Define the cutoff precisely, including timezone and inclusive/exclusive handling. Record the eligible population and the number removed. Preserve enough non-sensitive evidence to detect accidental over-deletion. Test recovery procedures separately where recovery is permitted; a retention policy and an unrestricted restore of expired data can conflict if the design ignores that interaction.

## Diagnose privacy and governance mistakes

If a released aggregate identifies a singleton, inspect grouping dimensions and suppression rules. If a hashed identifier is easily guessed, inspect whether the input space is small and whether a secret keyed construction was actually used. Even a well-managed keyed pseudonym does not fix linkage through unique attributes. If denied users can query raw files directly, inspect storage credentials and bypass paths rather than only the UI policy.

If retention removes the wrong date, inspect reference time, units and boundary comparisons. If a downstream report still contains expired observations, inspect lineage and publication caches. If a team treats a successful local deletion as complete compliance evidence, list the unexamined copies and obtain the appropriate review. Precision about scope is more useful than a broad assurance unsupported by readback.

## Applications and answered interview discussion

These mechanisms matter for data products, experimentation, customer analytics and ML pipelines. Governance is part of engineering quality because misuse, uncontrolled copies and unclear ownership can invalidate an otherwise technically impressive system.

An interviewer may ask, “Are hashed IDs anonymous?” Explain linkage and the difference between direct identifiers, pseudonyms and quasi-identifiers. If asked how to implement retention, describe an explicit clock, scope inventory, bounded deletion, audit and downstream handling. If asked whether an aggregate is safe, explain that group size alone does not settle disclosure risk, especially under repeated queries and auxiliary information.
