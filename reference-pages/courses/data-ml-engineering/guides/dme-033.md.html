dme-033: Frame an ML decision and establish a baseline#

Level: Intermediate | Prepared runtime: data-engineering

Direct prerequisites: dme-032.

Outcome: Train and evaluate a real baseline for an explicitly defined synthetic decision.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

Start with the decision and its population#

A prediction becomes useful when somebody can explain what changes because of it. Suppose a synthetic service receives cases that might need review. A positive label means a case truly needed review; a positive action means the system sent it for review. These statements concern different things. The label describes an outcome, while the action consumes resources and can change a person's experience. The first engineering question is therefore the decision, its eligible population and its consequences. Choosing a classifier comes afterward.

State what one row represents, when its inputs are available, when the decision must happen and when its outcome becomes observable. A model trained on resolved cases can be unsuitable for newly arriving cases if resolution affects which rows appear in training. Likewise, an input measured after review cannot be used to make an earlier review decision. The time and population contracts from the preceding chapters continue to apply even when the next operation is called machine learning.

This chapter uses a small original simulation. Two numerical inputs influence a binary outcome; a group variable changes the input distribution and outcome mechanism. The group label is synthetic and has no demographic interpretation. The program fits a real classifier, but the data and cost values do not establish external operational performance. They make a decision calculation observable and reproducible.

Keep fitting, selection and final evaluation separate#

The program generates 2,048 cases and fixes an original random seed. It assigns 1,024 cases to training, 512 to validation and 512 to final testing, with explicit disjoint-index checks. The classifier is a pipeline: a scaler learns numerical input statistics from training rows, and logistic regression learns its coefficients from those same rows. No transformation is fitted on the validation or test population.

The validation set answers a specific selection question: which of nineteen declared thresholds gives the smallest observed validation cost? The tie rule prefers the smaller threshold. The final test set answers a different question: what happened when the selected decision rule was applied to previously unused cases? Looking at test costs and then changing the threshold would turn testing into another selection round.

The grid is deliberately small and visible. Searching a much larger collection of models, features and thresholds creates more selection opportunities. A single final test result does not account automatically for every earlier development choice. Record the selection procedure and preserve the evaluation population, rather than reporting only the winning score.

Worked case 1: A high-accuracy baseline has high missed-case cost#

example_one() fits both a most-frequent-class baseline and the actual logistic pipeline. The baseline predicts zero for every test row. Of 512 held-out cases, 103 have positive outcomes. Its accuracy is approximately 0.7988 because it correctly classifies the 409 negatives. It misses all 103 positives, so its cost is 9×103/512=1.8105468759\times103/512=1.8105468759×103/512=1.810546875 units per case.

The validation procedure selects threshold 0.10.10.1. At that unchanged threshold, the learned decision rule misses eight positives and sends 197 unnecessary reviews on the final test set. Its accuracy is approximately 0.5996, while its cost is

The lower accuracy is compatible with the lower declared cost. More negative cases are deliberately sent for review to reduce costly missed positives. The example establishes the arithmetic and the behavior of this simulation. It does not prove that nine is the correct cost ratio, that review capacity is sufficient, or that this model should be deployed.

The Plotly output shows validation cost against threshold. Its accessible table exposes every plotted threshold and its error counts. The curve uses validation observations only. The test metrics are reported afterward and are not used to move the selected point.

Worked case 2: The same decisions have a different aggregate interpretation#

example_two() retains the selected threshold and examines the same held-out decisions in two disjoint synthetic groups. Group zero contains 285 cases and costs approximately 0.54035 per case. Group one contains 227 cases and costs approximately 0.50661 per case. Recombining their costs with the observed group proportions recovers the overall 0.525390625 value exactly within numerical tolerance.

If a future population were ten percent group zero and ninety percent group one, the mixture calculation would give approximately 0.50998 cost units per case. The program labels the necessary assumption: performance within each group has stayed unchanged. This is a reweighting calculation, not an observed future result. If outcome prevalence, input quality or decision effectiveness also changes within a group, changing mixture weights alone is insufficient.

The captured table has one row per disjoint group. It retains row counts, positive counts and both kinds of error so the reader can reconstruct each cost. A difference between these synthetic groups does not establish a causal effect of group membership. In real applications, group analysis also requires appropriate privacy, uncertainty, policy and scientific interpretation.

Complete worked program#

"""A decision baseline, validation-only threshold selection and held-out cohorts."""

import json

import numpy as np
import plotly.graph_objects as go
from sklearn.dummy import DummyClassifier
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

from ds60sqlpy.plot_artifacts import publish_table


def counts(labels, predictions):
    labels, predictions = np.asarray(labels), np.asarray(predictions)
    false_negative = int(np.sum((labels == 1) & (predictions == 0)))
    false_positive = int(np.sum((labels == 0) & (predictions == 1)))
    rows = len(labels)
    assert rows > 0
    return {
        "rows": rows,
        "positives": int(labels.sum()),
        "false_negatives": false_negative,
        "false_positives": false_positive,
        "accuracy": float(np.mean(labels == predictions)),
        "cost_per_row": (9 * false_negative + false_positive) / rows,
    }


def example_one():
    rng = np.random.default_rng(2033)
    groups = rng.integers(0, 2, 2048)
    features = rng.normal(size=(2048, 2))
    features[:, 1] += 0.8 * groups
    logits = 1.6 * features[:, 0] - 0.8 * features[:, 1] - 2.0 + 0.7 * groups
    probabilities = 1 / (1 + np.exp(-logits))
    labels = (rng.random(2048) < probabilities).astype(int)
    order = rng.permutation(len(labels))
    train, validation, test = order[:1024], order[1024:1536], order[1536:]
    assert not set(train) & set(validation) and not set(train) & set(test)
    assert not set(validation) & set(test)
    model = make_pipeline(StandardScaler(), LogisticRegression(random_state=33))
    model.fit(features[train], labels[train])
    baseline = DummyClassifier(strategy="most_frequent").fit(features[train], labels[train])
    validation_probability = model.predict_proba(features[validation])[:, 1]
    curve = []
    for threshold in np.round(np.arange(0.05, 0.96, 0.05), 2):
        metrics = counts(labels[validation], validation_probability >= threshold)
        curve.append({"threshold": float(threshold), **metrics})
    selected = min(curve, key=lambda row: (row["cost_per_row"], row["threshold"]))
    default_validation = next(row for row in curve if row["threshold"] == 0.5)
    assert selected["cost_per_row"] <= default_validation["cost_per_row"]
    test_probability = model.predict_proba(features[test])[:, 1]
    learned = counts(labels[test], test_probability >= selected["threshold"])
    majority = counts(labels[test], baseline.predict(features[test]))
    assert majority["false_positives"] == 0 and majority["false_negatives"] == majority["positives"]
    return {
        "summary": {
            "train_rows": len(train),
            "validation_rows": len(validation),
            "test_rows": len(test),
            "selected_threshold": selected["threshold"],
            "selected_on_validation_only": True,
            "majority_baseline": majority,
            "held_out_learned_decision": learned,
        },
        "curve": curve,
        "test_rows": [
            {"group": int(group), "label": int(label), "probability": float(probability)}
            for group, label, probability in zip(
                groups[test], labels[test], test_probability, strict=True
            )
        ],
    }


def example_two(first=None):
    first = example_one() if first is None else first
    threshold = first["summary"]["selected_threshold"]
    rows = first["test_rows"]
    cohorts = []
    for group in (0, 1):
        selected = [row for row in rows if row["group"] == group]
        metrics = counts(
            [row["label"] for row in selected],
            [row["probability"] >= threshold for row in selected],
        )
        cohorts.append({"cohort": f"group {group}", **metrics})
    assert sum(row["rows"] for row in cohorts) == len(rows)
    reconstructed = sum(row["cost_per_row"] * row["rows"] for row in cohorts) / len(rows)
    original = first["summary"]["held_out_learned_decision"]["cost_per_row"]
    assert np.isclose(reconstructed, original)
    shifted_mix = 0.1 * cohorts[0]["cost_per_row"] + 0.9 * cohorts[1]["cost_per_row"]
    return {
        "cohorts": cohorts,
        "original_cost_per_row": original,
        "reweighted_10_90_cost_per_row": shifted_mix,
        "reweighting_assumes_unchanged_within_group_performance": True,
        "threshold_reselected_on_test": False,
    }


def main():
    first = example_one()
    second = example_two(first)
    curve = first["curve"]
    figure = go.Figure(
        go.Scatter(
            x=[row["threshold"] for row in curve],
            y=[row["cost_per_row"] for row in curve],
            mode="lines+markers",
            name="Validation cost per row",
        )
    )
    figure.update_layout(
        title="Select a decision threshold using validation data only",
        xaxis_title="Probability threshold",
        yaxis_title="Synthetic cost units per validation row",
        meta={
            "description": "Validation cost: false negatives cost nine; false positives cost one.",
            "table": {
                "columns": ["threshold", "false negatives", "false positives", "cost per row"],
                "rows": [
                    [r["threshold"], r["false_negatives"], r["false_positives"], r["cost_per_row"]]
                    for r in curve
                ],
            },
        },
    )
    figure.show()
    columns = ["cohort", "rows", "positives", "false_negatives", "false_positives", "cost_per_row"]
    publish_table(
        columns,
        [[row[column] for column in columns] for row in second["cohorts"]],
        description="Disjoint held-out cohorts at the unchanged validation-selected threshold",
    )
    print(json.dumps({"case_one": first["summary"], "case_two": second}, allow_nan=False))
    print("dme-033: two decision cases passed")


if __name__ == "__main__":
    main()

Diagnose the decision before changing the estimator#

If the most-frequent baseline looks impressive, inspect positive prevalence and recall before praising accuracy. If a cost calculation changes when row count changes, check whether you are comparing total cost with cost per case. If an apparently better threshold was selected using the final test population, preserve that result as development evidence and obtain a new untouched evaluation population before making a final acceptance claim.

The seed and fitted parameters support reproduction; they do not make the cost ratio objective. The group mixture calculation supports an explicit conditional scenario; it does not forecast future behavior. An engineering report should name these differences clearly enough that a reviewer can reconstruct both the calculation and its limits.

Answered interview discussion#

Why begin with a trivial baseline? It reveals how much performance comes from population imbalance or a simple policy. A complex model that cannot improve a relevant baseline under the decision objective has not earned its operational complexity.

Why not always use threshold 0.5? That rule encodes particular assumptions about probability meaning and relative consequences. The decision boundary should follow the declared objective and be evaluated with an independent selection procedure.

Can a higher AUC settle this decision? No. AUC concerns ordering across thresholds. The operating decision also depends on calibration, costs, capacity, population and the chosen threshold. An improved ranking can still yield an unsuitable action policy.

What would you request before deployment? Confirm decision-time data availability, validate the cost and capacity model, examine a suitable recent evaluation population, inspect meaningful cohorts, establish monitoring and rollback, and test the actual serving interface. This chapter qualifies a bounded local investigation.
