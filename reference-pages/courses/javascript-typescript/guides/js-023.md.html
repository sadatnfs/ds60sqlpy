js-023: Mapped, conditional and utility types#

Level and prerequisites#

Intermediate, approximately 90 minutes. Direct prerequisites: js-022

Learning objectives#

Explain mapped type, conditional type, distributivity, type derivation with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Create a boolean flag type from id and count fields. The final task tests check a configuration with satisfies.

Purpose and mental model#

Type operators can derive one static description from another, reducing duplicated declarations that drift apart. A mapped type iterates over a type's property keys, changing their value types or modifiers. Pick selects known fields, Omit excludes them, Partial makes immediate properties optional, and Readonly restricts immediate writes. These operators change the checker-visible shape, not the runtime object. Assigning a wider record to Omit<SecretRecord, 'secret'> does not remove the secret bytes.

Conditional types select a result type based on an assignability relation. When the checked side is a naked type parameter, applying the conditional to a union distributes across its members. Wrapping both sides in tuples changes the test to treat the union as a whole. This matters when a utility unexpectedly returns a union of arrays rather than one array whose elements may have several types.

infer introduces a type variable extracted from a matched shape, such as the element type of an array. Built-in utilities such as ReturnType and Awaited express common relations. They do not inspect runtime values, execute a function, wait for a Promise or validate an endpoint response. Use type-level transformations to model real API relationships; keep runtime selection, validation and serialization explicit.

Vocabulary and concepts#

Mapped type: A type constructed by transforming a set of property keys.

Conditional type: A type-level branch based on assignability.

Distributivity: Applying a conditional independently to members of a union.

Type derivation: Describing one API shape in terms of another without runtime transformation.

A useful boundary for advanced types#

A utility should preserve a relationship the program actually implements. If a response mapper claims to omit private fields but returns the same object, the type has become misleading documentation. If a conditional type takes several minutes to understand and serves one call site, a simple named type may be easier to maintain. Check compiler diagnostics on changed types, runtime serialization on changed values, and the cost of explaining the API to another developer. These are separate forms of evidence.

Syntax anatomy and execution trace#

A mapped type uses [K in keyof T] to visit each property key. A modifier such as readonly or an optional question mark affects the generated property declaration. A conditional T extends U ? X : Y chooses a static result; infer names a matched component. The satisfies operator checks compatibility while retaining the expression's more specific inferred shape. It can catch missing or extra literal keys without replacing the runtime object or adding validation code.

Worked example / walkthrough#

Example A: Map a record into field flags#

The mapped type follows the source keys, so adding a field to Row creates a new required flag. The actual object still needs to be constructed by ordinary code.

import { strict as assert } from 'node:assert';



export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    type Row = { id: string; count: number };
    type Flags<T> = { [K in keyof T]: boolean };
    const flags: Flags<Row> = { id: true, count: false };
    assert.deepEqual(flags, { id: true, count: false });
    function negativeTypeCheck(): void {
      // @ts-expect-error Every Row key must have a flag.
      const incomplete: Flags<Row> = { id: true };
      void incomplete;
    }
    void negativeTypeCheck;
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: id true and count false; a missing flag is a compile error.

Example B: Prove Omit does not remove runtime secrets#

Type erasure makes this a concrete data-exposure risk. The public object must be constructed with an explicit field allowlist before serialization.

import { strict as assert } from 'node:assert';



export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    type RecordWithSecret = { id: string; secret: string };
    const full: RecordWithSecret = { id: 'A', secret: 'fixture-only' };
    const view: Omit<RecordWithSecret, 'secret'> = full;
    assert.equal(Object.hasOwn(view, 'secret'), true);
    const publicRecord: Pick<RecordWithSecret, 'id'> = { id: full.id };
    assert.equal(Object.hasOwn(publicRecord, 'secret'), false);
    assert.equal(JSON.stringify(publicRecord), '{"id":"A"}');
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: typed view still has secret at runtime; explicit projection does not.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
