Learning objectives#

  • Build a compound continuation predicate that matches a complete result order.
  • Handle nullable sort columns explicitly and test page boundaries.
  • Separate traversal correctness, snapshot policy, and measured plan behavior.

Vocabulary and concepts#

A page is a bounded portion of an ordered result. OFFSET names a position; a cursor names the last returned sort value and identity. Positions shift when earlier rows are inserted or deleted. A cursor can continue from its boundary without counting how many rows currently precede it. That solves one traversal problem, but it does not freeze the dataset or make mutable ordering columns safe. This lesson treats those as separate contracts.

  • Cursor: A cursor is a saved continuation boundary containing every field needed to reproduce the final order.
  • Keyset pagination: Keyset pagination filters strictly beyond that boundary before taking another bounded page.
  • Total order: A total order resolves all ties so two distinct result rows never compare equally under the declared ordering columns.
  • Snapshot: A snapshot is the database visibility view used for a statement or transaction.
  • Watermark: A watermark is an application-defined boundary declaring which input belongs to a run.
  • Sealed prefix: A sealed prefix is an ingestion segment that its owner promises is complete and immutable.

The six events have unique event_id, explicit event timestamps in UTC, and an illustrative received_seq belonging to a sealed prefix. Two events share a timestamp and one has no event timestamp. The main order is occurred_at descending, unknown timestamps last, event_id descending. Event_id resolves ties but is not a claim about event time. Record the cursor from the final returned row, not from a maximum computed independently of the page. Do not turn the cursor into executable SQL; application code binds its typed values.

Syntax anatomy and query reasoning#

For two non-NULL descending keys, (occurred_at, event_id) < (cursor_time, cursor_id) expresses lexicographic continuation: earlier timestamp, or equal timestamp and smaller identity. The WHERE inequality must agree with the final ORDER BY direction. A timestamp-only boundary would skip the second event at a tie. Using <= would repeat the cursor row. Reversing one sort direction requires an expanded Boolean predicate rather than blindly using the same row-comparison shortcut.

Row comparison with a NULL field does not supply the explicit missing-value order of ORDER BY. Handle the NULL tail as a deliberate phase. From a known timestamp cursor, include known values below the cursor plus every NULL timestamp. From a NULL cursor, remain in the NULL phase and compare only event_id. Store the phase and the identity as part of the cursor contract. This keeps traversal aligned with DESC NULLS LAST without inventing a fake timestamp that could collide with real data.

An immutable sealed-prefix fence can exclude later arrivals in this fixture. A bare PostgreSQL sequence maximum is not generally such a fence: sequence allocation order is not commit order, and a transaction with an earlier value can commit later. A fixed cutoff also does not prevent deletion or sort-key updates within its range. For a stable export, consider a bounded REPEATABLE READ transaction or an explicitly materialized immutable input. Long snapshots have operational costs, so the owner must define duration, failure recovery, and retention. A cursor alone promises continuation under stated mutations, never an automatically exact snapshot of changing business data.

Worked example / walkthrough#

Run these in the complete learner file so the temporary fixture and transaction are present. The fixture values are fixed; the examples never depend on the current clock. Predict each result before running it.

Example 1: Save the whole boundary from the first page#
SELECT
  event_id,
  occurred_at
FROM
  scale_events
ORDER BY
  occurred_at DESC NULLS LAST,
  event_id DESC
LIMIT 2;

The first page returns IDs 6 and 3. The continuation boundary is the second row, timestamp 11:00 UTC and event_id 3. Both values are required by the complete order. LIMIT bounds the result, and the index is a possible access path rather than a guarantee that this six-row example will use it. The event timestamp can differ from arrival order.

Expected: Two event rows, columns event_id, occurred_at: IDs 6 then 3; cursor (2024-01-01 11:00+00,3).

Example 2: Continue across a tied timestamp#
SELECT
  event_id,
  occurred_at
FROM
  scale_events
WHERE (occurred_at, event_id) < (TIMESTAMPTZ '2024-01-01 11:00+00', 3)
ORDER BY
  occurred_at DESC NULLS LAST,
  event_id DESC
LIMIT 2;

The known-value comparison admits IDs 2,1,5, then the row cap returns 2 and 1. Their equal timestamps remain distinct because identity is the second comparison key. This short example deliberately does not finish the NULL phase; the later exercise adds that policy. The final returned boundary becomes (10:00,1), so continuing from timestamp alone would lose or repeat a tied event.

Expected: Two event rows, columns event_id, occurred_at: IDs 2 then 1, both 10:00 UTC.

Common pitfalls#

  • If a timestamp tie is skipped or repeated, inspect both the inequality and the final identity direction; adding only ORDER BY does not fix the boundary.
  • If NULL events disappear, write the known and NULL cursor phases explicitly; row comparison does not inherit NULLS LAST.
  • If late rows leak into a run, distinguish a genuine sealed input prefix from a maximum sequence value and from a stable database snapshot.

  occurred_at

  event_id,
  occurred_at
FROM

The assertion checks the full ordered identity list and also checks that none belongs to page one. This exercise intentionally handles known timestamps only. Presenting it as a complete all-row export would be wrong because a NULL timestamp does not participate in ordinary tuple inequality the way ORDER BY places it.

Exercise 3: Cross into the unknown-timestamp phase#

SELECT
  event_id,
  occurred_at
FROM
  scale_events
WHERE
  occurred_at < TIMESTAMPTZ '2024-01-01 09:00+00'
  OR (occurred_at = TIMESTAMPTZ '2024-01-01 09:00+00'
    AND event_id < 5)
  OR occurred_at IS NULL
ORDER BY
  occurred_at DESC NULLS LAST,
  event_id DESC
LIMIT 2;

The expanded predicate names the two known-value continuation cases and the separate unknown phase. This matches the presentation policy rather than relying on an arbitrary sentinel timestamp. Once the saved cursor itself is NULL, remaining known timestamps are already behind the traversal and must not be revisited; compare event_id only among NULL timestamp rows. The assertion verifies that ID 4 is returned with its missing timestamp intact and that the next phase is empty on the fixture. A real cursor should encode enough state to choose the appropriate predicate safely. Adding NULLS LAST to ORDER BY alone never repairs a WHERE predicate that excludes every NULL.

Exercise 6: Prove bounded traversal covers the static fixture#

WITH ordered AS (
  SELECT
    event_id,
    row_number() OVER (ORDER BY occurred_at DESC NULLS LAST,
      event_id DESC) AS position
  FROM
    scale_events
)
SELECT
  ((position - 1) / 2 + 1)::integer AS batch_no,
  array_agg(event_id ORDER BY position) AS event_ids,
  count(*) AS row_count
FROM
  ordered
GROUP BY
  (position - 1) / 2 + 1
ORDER BY
  batch_no;

ROW_NUMBER assigns a unique position under the same total order, and integer division groups consecutive pairs into manifest batches. This makes a simple independent oracle for a fixed fixture: compare actual cursor pages against the listed batches. Computing positions for the whole input on every request would give up the bounded continuation behavior being taught, so the oracle is a verification tool rather than the implementation. The assertion checks the complete expected manifest and total row coverage. For real workloads separately measure representative EXPLAIN plans and latency without forcing an index choice. EXPLAIN ANALYZE executes its statement; do not adapt the example to writes without acknowledging that effect.

Inputs/evidence: For sql-scale-01 Exercise 6, Build a deterministic batch manifest over all six rows with a batch size of two using row_number only as a validation oracle. Return batch_no, event_ids, row_count. Explain why this oracle is not the production cursor algorithm.
