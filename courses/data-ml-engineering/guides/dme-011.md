## A change stream and a current table answer different questions

A current delivery table tells us the latest accepted state of each delivery. A change stream tells us that states changed. Summing every value that appears in such a stream is usually different from summing the current table. An update containing five packages may replace an earlier value of two; it does not necessarily mean five additional packages were delivered.

**Change-data capture**, or CDC, is the process of obtaining changes from a source system under a defined capture contract. Database logs, application events and periodic snapshots expose different information and failure boundaries. A database-log connector can preserve changes that a periodic snapshot never observes, but it also has to handle source positions, transaction boundaries, retention and restart behavior.

The executable example does not capture a PostgreSQL write-ahead log or run a broker. It applies declared synthetic change events to an actual local SQLite table. This isolates the consumer-side state contract so that ordering, replay and deletion can be inspected precisely. The Apache workshops provide separate actual service environments; their behavior is not inferred from this small consumer.

## Define what an event means

Our event supplies a delivery identity, a source version, an operation and, for an upsert, an absolute package count. The source version increases within one delivery's authoritative history. It is not a globally ordered transaction log position and it is not inferred from a wall clock. A delete carries a tombstone rather than a package measurement.

The consumer uses three version relationships. If the incoming version is greater than the stored version, it can replace the stored state under the declared contract. If the versions are equal and the payloads agree, the event is a replay. If the versions are equal but their meaning differs, there is a conflict. A smaller incoming version is stale and does not replace newer accepted state.

For one identified entity, the intended acceptance condition is

\[
s_{\mathrm{incoming}}>s_{\mathrm{stored}},
\]

where each \(s\) is a source version in the same ordering domain. This comparison is useful only when that domain is trustworthy. Two independent producers both issuing version one need an authority or merge rule. Resetting a version counter after restoring a source can also require an epoch or another explicit identity. A bare integer does not solve those problems automatically.

A delta event has a different contract. If an event means “add one package,” retaining only the latest event would lose earlier increments. Such an operation needs identified event application and an appropriate aggregation policy. Do not use an absolute-state upsert algorithm for a delta stream merely because both contain numeric fields.

## Protect the state decision inside the transaction

The example validates the basic event fields, begins an immediate SQLite transaction, reads the prior state and applies the chosen update. The transaction owns the version check and the resulting state change together. This makes the read/modify decision explicit instead of leaving an unprotected gap between a check and a write.

Each call owns its transaction boundary. It should not be nested casually inside another active transaction with an incompatible ownership assumption. A batch consumer may choose a larger atomic unit, but that requires a corresponding API and acknowledgement policy. The example uses one connection and a small sequence of calls; it does not benchmark concurrent distributed writers.

The SQL upsert targets the delivery primary key and updates the stored version, delete flag and package value. Query values are passed as bound parameters. A delivery identity is therefore treated as data rather than being concatenated into executable SQL. The table is a current-state projection with retained tombstones, not a complete immutable event archive.

## Worked case 1: Apply an update and recognize a replay

The first case creates delivery A at version one with two packages, replaces A at version two with five packages, repeats that exact version-two event, and creates B with three packages. The observed statuses are `applied`, `applied`, `replayed`, `applied`.

The current table contains A with five packages and B with three. Its total is

\[
T_{\mathrm{current}}=5+3=8.
\]

Adding every supplied upsert value would instead give fifteen. That would mix historical states and a replay with the current-state question. The independent oracle checks the identified final rows, not merely the number of processed messages.

The replay returns a status without repeating the state change. This is useful when a consumer sees an event again after an uncertain acknowledgement or restart. It is still only a consumer-side property. The demonstration has not shown that a real source connector delivered every change, that a broker preserved the required ordering, or that a downstream side effect was committed atomically with this state.

Those boundaries need their own evidence. A system can have an idempotent state projection and still send a duplicate notification if that notification is performed outside the acceptance transaction. The outbox chapter develops that distinction.

## Why a delete needs remembered state

Physically removing the only record of a delivery's accepted version can make an older event look new again. A tombstone preserves enough version information to reject that stale resurrection. It represents an intentional deletion under the source contract, not an unknown package count that should be imputed with zero.

Tombstones also require a retention policy. Keeping them forever has a cost; removing them too soon can permit old events to recreate deleted state. The safe horizon depends on source retention, replay windows, backups and the actual delivery guarantees. It cannot be selected solely from the age of the current table row.

An application may retain a fuller immutable change archive for audit, replay or historical analysis. That archive has a different grain from the current projection. Preserve the distinction when naming tables and explaining queries to consumers.

## Worked case 2: Reject stale resurrection and conflicting meaning

The second case creates A and B, then applies a version-three delete for A. The consumer retains A's version-three tombstone. A later arrival of an older version-two upsert with ninety-nine packages is classified as stale and cannot recreate A.

Repeating the same version-three delete is a recognized replay. Supplying an upsert with that same version and a different payload is rejected as a conflict. The current visible relation remains only B with three packages, while the physical state table still remembers A's delete flag and source version.

These are actual SQLite reads and writes. The code reads back both the visible relation and the tombstone metadata after the attempted changes. That distinguishes a rejected exception from a demonstrated retained-state outcome. The source-version logic is intentionally inspectable on a handful of events before it is connected to a larger capture system.

The case does not establish a complete restart protocol because this particular database is in memory. Persistent consumers must store their state and source position under a reviewed recovery policy and test actual replacement. The later owned project and recovery chapters make those boundaries explicit.

## Complete worked program

```python
"""Apply declared synthetic change events to actual local SQLite state."""

import sqlite3


def database():
    connection = sqlite3.connect(":memory:")
    connection.execute(
        "create table state(delivery_id text primary key, "
        "source_version integer not null, deleted integer not "
        "null, packages integer)"
    )
    return connection


def apply_event(connection, delivery_id, version, operation, packages=None):
    if not isinstance(delivery_id, str) or not delivery_id.strip():
        raise ValueError("A delivery identity is required")
    if type(version) is not int or version < 1 or operation not in {"upsert", "delete"}:
        raise ValueError("Invalid source version or operation")
    if operation == "upsert" and (type(packages) is not int or packages < 1):
        raise ValueError("Upserts require a positive integer package count")
    if operation == "delete" and packages is not None:
        raise ValueError("A delete carries a tombstone, not a package measurement")
    incoming = (version, int(operation == "delete"), packages)
    with connection:
        connection.execute("begin immediate")
        prior = connection.execute(
            ("select source_version,deleted,packages from state where delivery_id=?"),
            (delivery_id,),
        ).fetchone()
        if prior is not None:
            if version < prior[0]:
                return "stale"
            if version == prior[0]:
                if incoming != prior:
                    raise ValueError("One source version names conflicting changes")
                return "replayed"
        connection.execute(
            (
                "insert into state values(?,?,?,?) on "
                "conflict(delivery_id) do update set "
                "source_version=excluded.source_version,deleted=excluded"
                ".deleted,packages=excluded.packages"
            ),
            (delivery_id, *incoming),
        )
    return "applied"


def visible(connection):
    return connection.execute(
        "select delivery_id,packages from state where deleted=0 order by delivery_id"
    ).fetchall()


def example_one():
    connection = database()
    try:
        outcomes = [
            apply_event(connection, "A", 1, "upsert", 2),
            apply_event(connection, "A", 2, "upsert", 5),
            apply_event(connection, "A", 2, "upsert", 5),
            apply_event(connection, "B", 1, "upsert", 3),
        ]
        assert outcomes == ["applied", "applied", "replayed", "applied"]
        assert visible(connection) == [("A", 5), ("B", 3)]
        return {"outcomes": outcomes, "current_rows": visible(connection), "package_total": 8}
    finally:
        connection.close()


def example_two():
    connection = database()
    try:
        apply_event(connection, "A", 1, "upsert", 2)
        apply_event(connection, "B", 1, "upsert", 3)
        apply_event(connection, "A", 3, "delete")
        assert apply_event(connection, "A", 2, "upsert", 99) == "stale"
        assert apply_event(connection, "A", 3, "delete") == "replayed"
        try:
            apply_event(connection, "A", 3, "upsert", 7)
        except ValueError:
            conflict_rejected = True
        else:
            raise AssertionError("An equal source version cannot change its meaning")
        assert visible(connection) == [("B", 3)]
        assert connection.execute(
            "select source_version,deleted from state where delivery_id='A'"
        ).fetchone() == (3, 1)
        return {
            "visible_rows": visible(connection),
            "tombstone_version": 3,
            ("stale_resurrection_rejected"): True,
            ("conflict_rejected"): conflict_rejected,
            ("scope"): ("synthetic event application; no WAL capture or broker was run"),
        }
    finally:
        connection.close()


def main():
    print("Ordered identified change application:", example_one())
    print("Deletes still need version memory:", example_two())


if __name__ == "__main__":
    main()
```

## Diagnose gaps between capture and application

A source snapshot and a log stream need a consistent handoff. If changes occur between an uncoordinated snapshot and the chosen log starting position, a consumer can miss or duplicate updates. A capture tool's documented snapshot and position semantics matter; they should not be replaced with an arbitrary timestamp guess.

Acknowledgement order creates another failure window. Advancing a source checkpoint before the effect commits can lose work after a failure. Committing the effect before advancing the checkpoint can replay work, which the consumer must reconcile safely. An external side effect introduces another boundary unless it participates in the same acceptance mechanism.

When state looks wrong, inspect the entity key, source-version domain, event meaning, operation type and retained tombstones. Check whether an update was treated as an increment, whether a stale version overwrote a new one, or whether deletion removed the information needed to reject an old event.

## Where this is useful

These ideas apply to search indexes, analytical projections, feature tables, caches and replicated application views. The implementation can be a broker consumer, a stream processor or a batch replay, but it still needs a declared ordering and identity contract. A periodic dbt snapshot is another useful tool, yet it records observed states at its observation points and should not be described as capturing every intermediate database change.

## Answered interview discussion

**Does CDC automatically give exactly-once effects everywhere?** No. Capture, transport, consumer state and external effects have separate boundaries. Explain which operation is identified, where its acceptance commits and how replay is reconciled.

**Why retain a tombstone?** It preserves the accepted deletion version so an older event cannot look like a new entity. Its retention horizon must be compatible with replay and recovery behavior.

**Can a timestamp replace a source version?** Only under a justified source contract. Clock skew, ties, corrections and multiple producers can make timestamp order unsuitable as an authoritative version order.

**When would an upsert algorithm be wrong?** When events describe increments or another operation whose meaning depends on applying multiple identified events, rather than replacing an absolute state image.
