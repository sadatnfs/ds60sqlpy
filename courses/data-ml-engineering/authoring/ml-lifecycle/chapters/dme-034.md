# dme-034: Point-in-time feature retrieval and the feature-store boundary

## Reconstruct what the decision could have known

A training row usually describes a decision made in the past. Its features must represent information available for that decision. Joining a label to the newest feature value in today's database can answer a different question. A correction written tomorrow may improve the historical database while making an earlier decision impossible to reproduce honestly.

Separate two clocks before introducing a feature store. The event time says when a feature observation applies to the world. The availability time says when a decision system could use that version of the observation. A corrected January measurement can have January event time and February availability time. Neither timestamp is inherently wrong. They describe different facts.

A request row has a third relevant value: the decision timestamp. This chapter calls it the request time because each row represents one historical request for features. The program uses actual Feast 0.67.0 APIs and a local Parquet source, then compares the returned values with a separate Python oracle. It does not simulate a feature store by renaming a dataframe join.

## Define the eligible feature population

Let \(k\) identify an entity, \(t\) be its request time, \(e_i\) a feature record's event time, \(a_i\) that record's availability time, and \(\tau\) the allowed feature age. For this chapter the eligible records satisfy

\[
k_i=k,\qquad t-\tau\le e_i\le t,\qquad a_i\le t.
\]

Among eligible versions, choose the latest event time, breaking an event-time tie by the latest availability time. The fixture has no conflicting records with identical entity, event time and availability time. A real producer with such conflicts needs another deterministic version rule or explicit rejection. A timestamp alone does not settle every possible conflict.

The age window is seven days, measured backward from each historical request. It is independent of the wall clock when the tutorial runs. Running a January fixture in October does not make all January historical lookups invalid. This retrieval TTL also does not remove rows from the Parquet file. Age eligibility and storage retention are separate contracts.

The meaning of \(a_i\) matters as much as the comparison. If a source's creation timestamp records a database write but the online feature became available later, that timestamp can still admit unavailable information. The example deliberately defines `known_at` as availability for the decision. Adopting the same column name elsewhere does not establish that operational meaning.

## The prepared Feast default does not enforce both clocks

`FileSource` declares `feature_time` as its event timestamp and `known_at` as its created timestamp. A `FeatureView` declares the account entity, value schema and seven-day TTL. Registering these objects gives the store an explicit contract for this local source.

In the prepared release, the default historical retrieval constrains event time. Its created timestamp resolves duplicate event-time versions, but the default does not independently exclude a version created after the request. The actual `get_historical_features` method supports `filter_by_created_timestamp=True`. This chapter sets that argument explicitly when it needs the availability cutoff.

The distinction is observable rather than inferred from the method's name. An entity may receive a more recent correction of an old event. Default retrieval can select that correction for an earlier request. The explicit option can recover the earlier available version. A missing created timestamp is excluded by the enabled option; the program does not invent an availability time for it.

Do not assume every offline store supports the same option. The prepared file backend is actually executed here. When moving the example to another store, test the same oracle and require an explicit supported implementation. Catching an unsupported-operation exception and silently rerunning with the option disabled would change the data contract.

## Worked case 1: A future correction looks historically valid

Account one has a January 1 feature value of ten, available at 01:00 that day. A correction changes that same event's value to ninety-nine, but the correction is only available on January 4. Another feature observation applies on January 3, has value twenty and is available at 01:00 on January 3.

`example_one()` requests account one's features at the start of January 2 and January 4. The default retrieval returns `[99.0, 20.0]`. The first value uses a correction that did not yet exist for the January 2 decision. Enabling the availability cutoff returns `[10.0, 20.0]`, matching the independent oracle.

The January 4 request still receives twenty. A newly available correction to the older January 1 event does not automatically outrank a later January 3 event. Event ordering and version ordering answer different questions. The program makes that ordering explicit so a reader can explain why ninety-nine is not the correct answer for either availability-aware request.

The oracle uses a small direct scan over timezone-aware Python datetimes. It independently filters eligible records and chooses their latest event/version pair. It does not reuse Feast's join implementation. Agreement between two separately expressed mechanisms gives more useful evidence than checking only that a retrieval job exited normally.

## Worked case 2: Preserve missing requests and test the exact boundary

`example_two()` asks for nine request rows. The first two reproduce the available values ten and twenty. Five other requests cover an unknown account, a request before recorded history, a request outside the age window, a feature with unknown availability time and a request made before the first value became available. Their feature values remain missing.

Account three supplies the final boundary cases. Its value of 3.5 applies and becomes available at the start of January 1. A request at the start of January 8 is exactly seven days later and receives 3.5. A request one microsecond after that boundary receives no eligible value. The prepared native file-store execution agrees with the declared inclusive lower boundary in both cases.

The final list is `[10.0, 20.0, None, None, None, None, None, 3.5, None]`. All nine request identities remain represented. Some retrieval paths can omit unmatched rows, so the program restores the authoritative request population through an explicit one-to-one left merge on `request_id`. It verifies returned identity uniqueness before merging. This does not manufacture a feature; it preserves the fact that a requested feature is missing.

Replacing those missing values with zero would invent a measurement and change its meaning. If later modeling uses imputation, that is a separate fitted transformation with its own policy and provenance. Chapter 035 covers that stage. The captured table uses JSON null for missing values, rather than nonfinite numeric placeholders.

## Diagnose time and coverage separately

An unexpected ninety-nine can indicate an availability-filter error even when event time and TTL are correct. An unexpected twenty can indicate that the reader is ranking all versions by creation time rather than ranking events first. A missing January result can indicate that somebody compared timestamps to the current wall clock. A lost request row can indicate an inner join or a backend omission rather than an absent input request.

Check timezone and precision before changing an inequality. The fixture uses UTC-aware timestamps and explicitly exercises microsecond precision. That does not qualify every timestamp type, database precision or timezone conversion. A pipeline that truncates microseconds can turn the just-expired request into an exact-boundary request. Preserve the units and precision across ingestion, storage and retrieval.

A successful historical feature join does not train a model, materialize an online store or prove that the actual serving service had the same values. Those are additional operations. The optional end-to-end projects trace publication and serving state explicitly; ordinary Run remains a bounded local investigation.

## Answered interview discussion

**Is an event-time point-in-time join always enough?** Only when its inputs really were available under the assumed event-time contract. Backfills and delayed publication require an availability rule as well. State and test the rule instead of relying on a reassuring API name.

**What is a created timestamp for?** Its meaning belongs to the source contract. In the prepared store it can resolve event-time duplicates and, with the explicit option, enforce a cutoff. It still needs to reflect the availability relevant to the decision being reconstructed.

**Why preserve rows with no features?** They belong to the request population. Dropping them can change label prevalence and hide coverage failures. A consumer needs to distinguish missing features from missing requests.

**What makes the oracle independent?** It expresses the contract as a direct scan with plain datetimes, rather than invoking the same store query twice. Its assumptions and boundaries are visible and separately checked against actual store output.
