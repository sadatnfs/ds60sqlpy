# web-030: Browser quality: tests, performance and independent review

## Level and prerequisites

Advanced; allow about 140 minutes, with extra time for independent practice. Direct prerequisites: `web-029`

## Learning objectives

Create a quality report for the portal from web-024. Explain what evidence would justify a production readiness claim. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

Quality is a set of observable contracts. A structural test can check that a button has a label. An interaction test can check that it changes the intended value. A visual inspection can reveal clipping after resizing. An assistive-technology review can expose an announcement problem. No single kind of test proves all of these. Plan the evidence around the behavior you claim.

Performance also requires a defined workload and measurement boundary. Loading, parsing, scripting, layout, painting and network transfer contribute differently. A tiny function timer is not page-load performance. Warm caches, device speed, background activity and instrumentation affect measurements. Report the conditions and distributions instead of declaring an arbitrary universal millisecond target.

## Syntax anatomy and mechanism

Use explicit assertions that throw on failure rather than relying only on console.assert. Keep a deterministic fixture for logic tests and a separate manual checklist for keyboard, zoom, narrow width, print and reduced motion. Measure a bounded task with performance.now only when explaining that local task. Do not interpret a microbenchmark as a production capacity claim.

## Classroom execution and offline inputs

Choose **HTML browser preview** in the classroom. The pad is one complete HTML document with embedded CSS and, where taught, embedded JavaScript. Its preview is isolated from the classroom and recreated on each run. It does not contact a server, submit real forms, read cookies, fetch assets or load a CDN. All fixtures are inline and synthetic. The browser uses its native HTML parser, so classic-script ordering, shared lexical bindings, inline modules and real DOMContentLoaded/load events keep their browser semantics. External module imports remain blocked. Navigation metadata such as base and meta http-equiv is rejected explicitly. On any supported host, the browser renders the document while Docker serves the classroom. No host compiler is needed.

Run your own source after implementing the task. A reference's checks inspect only the named initial conditions. Its success message is not a full accessibility audit, proof of responsive behavior at every size, or evidence that you implemented the solution yourself. Inspect actual output after keyboard input, resizing and changes. Save your source before comparing with a reference. For visual experiments, explicitly turn on Live preview: the page refreshes after a short pause in typing, while Pause updates keeps the last rendered version and Stop preview cancels pending refreshes. Desktop, tablet and phone presets resize the same preview without rerunning it. Automatic previews do not create saved runs; choose Save observation or Run when you want to retain an exact source-and-output record. Changing lessons, opening history or reloading turns live execution off. The document and its CSS share one saved pad; HTML and CSS remain different languages within that artifact.

## Worked example / walkthrough

### Worked example 1: An actionable assertion

Failure stops the claimed successful path.

```javascript
if (document.querySelectorAll('main').length !== 1) { throw new Error('Expected one main region'); }
```

**Expected observation:** A structural mismatch becomes an explicit failure.

### Worked example 2: A bounded measurement

The label states exactly what was timed.

```javascript
const start = performance.now();
const values = [3, 1, 2].toSorted((a, b) => a - b);
console.log('Local sorting task ms:', performance.now() - start);
```

**Expected observation:** The number describes one tiny local task, not total page performance.

## Six progressive exercises

### Exercise 1: Map a label, interaction and layout claim to different evidence.

**Expected evidence:** Use structural checks, actual interaction and visual inspection respectively.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Turn one silent assumption into a throwing assertion.

**Expected evidence:** A violated invariant produces a clear failure message.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Create a quality report for the portal from web-024.

**Expected evidence:** The report records source revision, tested conditions, observations and remaining limitations.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a test that passes before an interaction later throws.

**Expected evidence:** Inspect the settled state and errors after all representative actions.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Repeat the review after narrow resizing and a saved-page reload.

**Expected evidence:** The interface remains usable and the learner distinguishes persisted source from transient preview state.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain what evidence would justify a production readiness claim.

**Expected evidence:** It requires broader integration, security, accessibility, operational and workload-specific performance evidence than one local reference run.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Avoid tests that merely search for a success string without exercising behavior. Do not erase a failure transcript when retrying. A successful browser run applies to that tested browser and source, not automatically to all devices.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain acceptance test, rendering pipeline, performance measurement without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
