# go-014: Table-driven tests and useful counterexamples

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-013

## Learning objectives

Write table-driven checks with exact endpoints and a counterexample that rejects a plausible wrong implementation. Along the way, explain test oracle, boundary case, regression case; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Tests are executable claims about behavior. A test should distinguish the intended implementation from a plausible wrong one. Table-driven testing records input and expectation as data, then applies the same assertion logic to each case. Normal cases show use, boundary cases define edges, and invalid cases define failure behavior. A reference example in a single pad uses explicit checks; a real Go test lives in a file ending _test.go and receives *testing.T. Tests must not depend on global ordering, current time or a network service unless those dependencies are deliberately controlled. Coverage describes executed code, not the strength of the assertions.

## Vocabulary and concepts

- **Test oracle:** The independent rule determining an expected result.
- **Boundary case:** An input at the edge of an accepted domain.
- **Regression case:** A retained input that exposes a previously observed defect.

## Syntax anatomy and reasoning

A test table is often a slice of anonymous structs with name, input and want fields. In a prepared project, func TestName(t *testing.T) is discovered by go test, and t.Run creates named subtests. Compare actual and expected values directly; include the case name in failure messages. Fuzz tests describe invariants across generated inputs, but they need a bounded execution budget and persistent regression seeds. Do not treat successful compilation as a behavior test.

## Worked example / walkthrough

### Worked example 1: Build a named table

Test clamp with values below, inside and above the range 0 to 10.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func clamp(x int) int {
	if x < 0 {
		return 0
	}
	if x > 10 {
		return 10
	}
	return x
}
func mutantClamp(x int) int {
	if x < 0 {
		return 0
	}
	if x > 9 {
		return 9
	}
	return x
}

func main() {
	// Build a named table
	{
		cases := []struct{ in, want int }{{-2, 0}, {4, 4}, {12, 10}}
		for _, tc := range cases {
			check(clamp(tc.in) == tc.want, "clamp table")
		}
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The outputs are 0, 4 and 10.

A wrong implementation that only returns its input fails the outside cases; one that always returns an endpoint fails the interior case.

### Worked example 2: Include exact endpoints

Test clamp at 0 and 10.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func clamp(x int) int {
	if x < 0 {
		return 0
	}
	if x > 10 {
		return 10
	}
	return x
}
func mutantClamp(x int) int {
	if x < 0 {
		return 0
	}
	if x > 9 {
		return 9
	}
	return x
}

func main() {
	// Build a named table
	{
		cases := []struct{ in, want int }{{-2, 0}, {4, 4}, {12, 10}}
		for _, tc := range cases {
			check(clamp(tc.in) == tc.want, "clamp table")
		}
	}

	// Include exact endpoints
	{
		check(clamp(0) == 0 && clamp(10) == 10, "endpoints")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** Both endpoints are preserved.

Endpoint tests distinguish inclusive boundaries from off-by-one policies. They should be named in the API contract.

## Exercises

### Exercise 1: Build a named table: change one input

Copy worked example 1 into a scratch pad and change `cases := []struct{ in, want int }{{-2, 0}, {4, 4}, {12, 10}}` to `cases := []struct{ in, want int }{{-2, 1}, {4, 4}, {12, 10}}`. Before running, predict which check fails and which value it now sees; then run it and restore the original line.

**Expected:** The changed run panics with `clamp table` because `clamp(tc.in) == tc.want` no longer holds. Restoring the original line brings back the worked observation: the outputs are 0, 4 and 10.

**Verify:** Compare your written prediction with the panic message `clamp table` and name the value that made `clamp(tc.in) == tc.want` false. After restoring the input, the program must print its success line again.

### Exercise 2: Include exact endpoints: diagnose an edited check

A careless edit changed the check in worked example 2 so that it reads `check(clamp(1) == 0 && clamp(10) == 10, "endpoints")`. Run worked example 2 with that line, explain why the edited check now fails for the same program state, and restore it.

**Expected:** Before the repair the program panics with `endpoints`; after it the line reads `check(clamp(0) == 0 && clamp(10) == 10, "endpoints")` again and both endpoints are preserved.

**Verify:** Keep the failing and the repaired runs. Explain why the edited check rejects the same program state that `clamp(0) == 0 && clamp(10) == 10` accepts.

### Exercise 3: Check idempotence

Apply clamp twice to values -2, 4 and 12.

**Expected:** Applying it twice gives the same result as once.

**Verify:** Keep a check equivalent to `clamp(clamp(x)) == clamp(x)`. As a control, change `check(clamp(clamp(x)) == clamp(x), "idempotence")` to `check(clamp(clamp(x)) != clamp(x), "idempotence")` inside that check: it must panic with `idempotence`, which shows the check can fail. Restore it.

### Exercise 4: Reject a plausible mutant

Compare the correct clamp with a mutant that incorrectly caps at 9.

**Expected:** Input 10 distinguishes them.

**Verify:** Keep a check equivalent to `clamp(10) != mutantClamp(10)`. As a control, change `check(clamp(10) != mutantClamp(10), "mutant rejected")` to `check(clamp(10) == mutantClamp(10), "mutant rejected")` inside that check: it must panic with `mutant rejected`, which shows the check can fail. Restore it.

### Exercise 5: Cover a range invariant

Check all integer inputs from -20 through 20.

**Expected:** Every result lies between 0 and 10.

**Verify:** Keep a check equivalent to `v >= 0 && v <= 10`. As a control, change `check(v >= 0 && v <= 10, "range invariant")` to `check(v > 0 && v <= 10, "range invariant")` inside that check: it must panic with `range invariant`, which shows the check can fail. Restore it.

### Exercise 6: Transfer a fresh regression

Retain input 11 as a regression for an implementation that forgets the upper cap.

**Expected:** The result is 10.

**Verify:** Keep a check equivalent to `clamp(11) == 10`. As a control, change `check(clamp(11) == 10, "upper regression")` to `check(clamp(11) != 10, "upper regression")` inside that check: it must panic with `upper regression`, which shows the check can fail. Restore it.

Implement these in the answer-free learner source. Keep one independent check per claim. A task can require tracing, construction, a changed input or a deliberate safe failure. Do not run a data race, corrupt memory or contact a shared cluster merely to demonstrate why it would be wrong.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
