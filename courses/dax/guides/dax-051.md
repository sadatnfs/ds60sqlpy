## The question and the mechanism

Find a context where two similar predicates differ before treating one as an optimization.

Replacing a table filter with a simple column predicate can change filter replacement behavior. FILTER(Sales,Sales[Quantity]>=2) iterates Sales as visible in its incoming context. A plain Boolean filter on Quantity in CALCULATE can replace an existing Quantity filter. They can agree on an unfiltered fixture while disagreeing on a selected population.

With no incoming filters, both constructions select lines with quantity at least two, totaling 163. Under an incoming Quantity=1 selection, the visible Sales rows contain no line satisfying the table predicate, so the table-filter form returns BLANK. The plain column predicate replaces that Quantity selection and admits the larger-quantity lines, returning 163 instead.

KEEPFILTERS on the column predicate expresses intersection and matches the empty result in this stated context. That is useful evidence for this case, not a universal equivalence theorem for every table expression, relationship or expanded-table effect. A performance refactor needs a semantic test grid before any timing result can justify it.

## Vocabulary and expression anatomy

The three expressions differ in how they form and apply their filter. Case A is an ordinary agreement case. Case B supplies the counterexample with an existing same-column selection. No runtime performance is measured by either query.

Concepts to explain in your own words: **semantic equivalence**, **FILTER**, **Boolean predicate**, **KEEPFILTERS**, **regression context**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: An unfiltered agreement case

**Starting context:** No existing Quantity filter; all three forms select quantity at least two.

```dax
EVALUATE ROW ( "TableFilter", CALCULATE ( [NetRevenue], FILTER ( Sales, Sales[Quantity] >= 2 ) ), "ColumnFilter", CALCULATE ( [NetRevenue], Sales[Quantity] >= 2 ), "IntersectingColumn", CALCULATE ( [NetRevenue], KEEPFILTERS ( Sales[Quantity] >= 2 ) ) )
```

**Context trace:**

1. S2 and S 6 have quantity 1 and contribute 4 +20 =24.
2. Removing those lines from 187 leaves 163.
3. The three forms agree in this incoming context.

**Hand-derived worked-reference result:**

| TableFilter | ColumnFilter | IntersectingColumn |
| --- | --- | --- |
| 163 | 163 | 163 |

Agreement on an unfiltered example does not establish interchangeability under interactive selections.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: The same-column selection exposes a difference

**Starting context:** Incoming Sales.Quantity=1; compare filtering current rows with replacing or intersecting that column selection.

```dax
EVALUATE CALCULATETABLE ( ROW ( "TableFilter", CALCULATE ( [NetRevenue], FILTER ( Sales, Sales[Quantity] >= 2 ) ), "ColumnFilter", CALCULATE ( [NetRevenue], Sales[Quantity] >= 2 ), "IntersectingColumn", CALCULATE ( [NetRevenue], KEEPFILTERS ( Sales[Quantity] >= 2 ) ) ), Sales[Quantity] = 1 )
```

**Context trace:**

1. The incoming visible fact rows are S2 and S 6, both quantity 1.
2. FILTER over those rows finds no quantity>=2 line, while the plain Boolean predicate replaces the original selection.
3. KEEPFILTERS intersects incompatible quantity conditions and also yields BLANK.

**Hand-derived worked-reference result:**

| TableFilter | ColumnFilter | IntersectingColumn |
| --- | --- | --- |
| BLANK | 163 | BLANK |

A rewrite that changes BLANK to 163 is not an optimization of the same calculation. It is a change in the question.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. The original population already satisfies the predicate.
2. Identify S4 and S 5.
3. Include selections that agree, overlap and conflict with the predicate.
4. A changed result is not evidence of better performance or correctness.
5. Whole-table filters can carry additional columns and expanded-table effects.
6. Result parity needs population, multiplicity, null and boundary checks.
