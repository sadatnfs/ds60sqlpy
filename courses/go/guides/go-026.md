## Why this mechanism matters

Cancellation is cooperative: a context signals that work should stop, but does not forcibly interrupt every function. Pass context as the first parameter to work whose lifetime belongs to its caller. Derived contexts form a tree, so canceling a parent cancels descendants. Always call the returned cancel function when the owned operation ends, including early success, to release associated resources. A select can wait for work or cancellation, but if both cases are ready its choice is not a priority rule. Check required preconditions explicitly when already-canceled work must never begin.

## Vocabulary and concepts

- **Context tree:** Parent-child cancellation relationships.
- **Deadline:** An absolute time after which work is no longer wanted.
- **Cooperation:** An operation checking and respecting a stop signal.

## Syntax anatomy and reasoning

context.WithCancel returns a child and cancel function. Done closes on cancellation; Err explains cancellation or deadline expiry. WithDeadline accepts a past time for deterministic testing. A select arm receiving from ctx.Done cooperates with cancellation. Context values carry request-scoped metadata, not optional function arguments, authentication guarantees or mutable application state.

## Worked example / walkthrough

### Worked example 1: Cancel a child

Create a cancelable context and cancel it.

```go
package main

import (
	"context"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func contextValue(ctx context.Context, x int) (int, error) {
	if err := ctx.Err(); err != nil {
		return 0, err
	}
	return 2 * x, nil
}

func main() {
	// Cancel a child
	{
		ctx, cancel := context.WithCancel(context.Background())
		cancel()
		check(ctx.Err() == context.Canceled, "cancel")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** Err returns context.Canceled.

Cancellation is visible through Err and the closed Done channel. Repeated cancel calls are safe.

### Worked example 2: Propagate parent cancellation

Derive a child and cancel its parent.

```go
package main

import (
	"context"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func contextValue(ctx context.Context, x int) (int, error) {
	if err := ctx.Err(); err != nil {
		return 0, err
	}
	return 2 * x, nil
}

func main() {
	// Cancel a child
	{
		ctx, cancel := context.WithCancel(context.Background())
		cancel()
		check(ctx.Err() == context.Canceled, "cancel")
	}

	// Propagate parent cancellation
	{
		parent, cancel := context.WithCancel(context.Background())
		child, stop := context.WithCancel(parent)
		defer stop()
		cancel()
		check(parent.Err() == context.Canceled && child.Err() == context.Canceled, "tree")
	}
	fmt.Println("Worked example checks passed.")
}

```

**Observe:** Both contexts become canceled.

A child cannot extend work beyond the lifetime requested by its parent.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
