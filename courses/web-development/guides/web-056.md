# web-056: PHP milestone: a tested study-planner application core

## Level and prerequisites

Advanced; allow about 180 minutes, with extra time for independent practice. Direct prerequisites: `web-055`

## Learning objectives

Build a tested planner core with validation and prepared storage. Explain the remaining work before this core becomes a deployed application. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

The application core coordinates a use case without pretending to be an HTTP server. It receives a trusted actor identity and untrusted proposed values, validates the proposal, writes through a repository and returns a result. Keeping these boundaries visible makes it possible to reason about what is trusted and which failures prevent a write.

This milestone combines the earlier mechanisms in a small study planner. The database is disposable SQLite memory. The input is synthetic. Validation rejects unsupported topics and out-of-range durations. A prepared statement stores an accepted plan under the supplied actor. A query scopes retrieval by that actor. Rendering and HTTP adaptation remain separate so the same core can later be integrated and tested through a real server.

## Syntax anatomy and mechanism

Write the acceptance matrix before implementation: a valid plan is stored once, invalid input stores nothing, one actor cannot read another's plan, and output has a clear type contract. A production service would add session verification, CSRF where relevant, idempotency, concurrent behavior, migrations and operational controls. Do not infer those properties from this small core.

## Classroom execution and offline inputs

Choose the **PHP CLI** worker in the classroom. The pad is staged as `main.php` and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write `<?php` at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

## Six progressive exercises

### Exercise 1: Draw the trust boundary around actor identity and form values.

**Expected evidence:** The adapter verifies identity; the application validates proposed domain values.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Write the acceptance matrix before implementing the service.

**Expected evidence:** Normal, invalid and cross-owner cases have explicit observations.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build a tested planner core with validation and prepared storage.

**Expected evidence:** Accepted plans persist in the disposable database and rejected inputs create no rows.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a service that writes before validating all fields.

**Expected evidence:** Move complete validation before mutation or ensure a correctly owned transaction aborts the entire unit.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test cross-owner retrieval and an invalid duration.

**Expected evidence:** No other actor's row is exposed and the invalid request changes no stored state.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain the remaining work before this core becomes a deployed application.

**Expected evidence:** Real HTTP, session, CSRF, persistence, concurrency, accessibility and operational acceptance remain separate integration tasks.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not add a success banner that claims the user now has a production service. Preserve invalid cases in the test suite. A synthetic trusted actor is a testing input, not an authentication implementation.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain application service, validation, repository without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
