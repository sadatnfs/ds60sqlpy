web-058: Uploads, filesystem ownership and outbound side effects#

Level and prerequisites#

Advanced; allow about 150 minutes, with extra time for independent practice. Direct prerequisites: web-057

Learning objectives#

Write an upload design with separate validation, storage and retrieval boundaries. Explain which tests are needed before enabling uploads or email. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

Purpose, vocabulary and mental model#

Accepting a file creates a new trust boundary. A client-supplied filename, extension and MIME label are untrusted claims. A safe design sets a byte limit, allows only needed formats, checks actual content as appropriate, generates its own storage name and keeps uploads outside executable public directories. An image parser can itself have vulnerabilities, so format validation is part of a broader dependency and isolation policy.

Filesystem paths should be derived from an owned identifier and a controlled root, not concatenated from arbitrary request text. Avoid making user uploads executable or allowing path traversal into application source. Storage quotas, retention and deletion behavior matter because a valid file can still exhaust resources. The default classroom pad does not accept uploaded files, and this lesson does not add an upload endpoint.

Syntax anatomy and mechanism#

PHP's upload APIs distinguish actual HTTP-uploaded files from arbitrary paths, but successful movement does not prove the content is safe. Treat sending email, calling a payment service or publishing a message as explicit side effects with credentials and failure handling. An outbox design can record an intended external action in the same database transaction as a domain update, then process it with idempotency controls. It does not magically make an external network action exactly once.

Classroom execution and offline inputs#

This is a reading and design worksheet with an optional external project lab. The classroom saves the worksheet but does not start an HTTP server, install packages or control Docker from its pad. Work from the supplied synthetic examples first. A command is a proposal until you deliberately execute it against your own disposable local project. The maintained optional fixture is courses/web-development/fixtures/php-http-lab/; read its README before preparing it. Do not expose that learning server to the internet or reuse real account data.

Worked example / walkthrough#

Worked example 1: An owned storage name#

This is a design fragment, not a complete upload handler.

$storedName = bin2hex(random_bytes(16)) . '.bin';
$destination = $ownedUploadDirectory . DIRECTORY_SEPARATOR . $storedName;

Expected observation: The original user filename does not choose the server path.

Worked example 2: An explicit side-effect record#

The record expresses an intention awaiting controlled delivery.

{"event_id":"synthetic-42","kind":"study_reminder","status":"pending","attempts":0}

Expected observation: A worker can track attempts without pretending the remote effect already happened.

Six progressive exercises#

Exercise 1: List the untrusted claims in an uploaded file request.#

Expected evidence: Filename, extension, declared media type, content and size all require a deliberate policy.

Progressive hint: Trace the smallest example before editing. Name which values are source and which are observations.

Exercise 2: Design a maximum size and allowlist for one required format.#

Expected evidence: The policy rejects unnecessary formats and enforces a bounded resource budget.

Progressive hint: Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

Exercise 3: Write an upload design with separate validation, storage and retrieval boundaries.#

Expected evidence: Files receive generated names, stay outside executable public paths and have ownership and retention rules.

Progressive hint: Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

Exercise 4: Diagnose concatenating ../../ into a storage path.#

Expected evidence: User input must not determine an unrestricted filesystem location.

Progressive hint: Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

Exercise 5: Model a timeout after a remote service may have accepted an action.#

Expected evidence: The outcome is ambiguous; retries need idempotency or reconciliation instead of assuming failure means nothing happened.

Progressive hint: Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

Exercise 6: Explain which tests are needed before enabling uploads or email.#

Expected evidence: Exercise actual HTTP upload handling, malformed content, size limits, ownership, cleanup and controlled external-service failure behavior.

Progressive hint: Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

Debugging and common mistakes#

Do not copy this lesson's fragments into a live upload service without the full surrounding contract. Avoid teaching extensions as proof of content type. Never send real email, credentials or files while merely reading a lesson.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

Retrieval, transfer and next steps#

Close the worked answers and explain upload boundary, MIME validation, path traversal without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
