# k8s-059: Egress policy, DNS dependencies and external destinations

## Level and prerequisites

Advanced; about 120 minutes. Direct prerequisites: `k8s-058`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Design a minimal egress matrix.
- Plan an egress qualification after NAT.

## Purpose, vocabulary and mental model

Egress policy controls selected Pods' outgoing traffic under an enforcing implementation. A deny-by-default design begins by selecting the workloads and then allowing the dependencies they actually require. It can expose hidden dependencies such as DNS, metadata endpoints, package downloads or external APIs.

DNS is itself network traffic. Blocking it can make every named dependency fail even while a direct allowed IP connection works. UDP is common for DNS, but TCP can also be required. The correct DNS target and policy depend on the cluster’s DNS deployment and any node-local cache.

An IP allowlist is not the same as a domain-name policy. External services can change addresses, use shared infrastructure or return several families. The standard NetworkPolicy API does not provide a general hostname allowlist. Implementation extensions must be named and qualified separately.

### Key terms

- **Egress policy:** A NetworkPolicy rule set that limits outbound connections from the selected Pods.
- **DNS dependency:** Pods still need to reach cluster DNS over UDP and TCP, so a strict egress policy must allow it explicitly.
- **ipBlock:** A NetworkPolicy peer that allows an address range in CIDR form, typically for destinations outside the cluster.
- **Hostname allowlist:** Permitting egress by DNS name. The standard NetworkPolicy API cannot express it, although some implementations add it.

## Mechanism and field-by-field reasoning

A policy with policyTypes Egress and an empty egress list isolates selected Pods without permitting outgoing flows through that policy. Additional applicable policies can add allowances. A source egress allowance is not sufficient when the destination is ingress-isolated: the destination must also permit the connection. Replies for a permitted connection are implicitly allowed, while a new reverse connection is evaluated as a new flow. Peer and port rules should be derived from the actual dependency map.

ipBlock represents CIDR-based address ranges with optional exclusions. Address translation can affect which IP an implementation evaluates at a boundary, so test the actual traffic path. Do not promise identical pre-NAT or post-NAT behavior across every plugin and Service combination.

## Trace the request or control path

```text
app -> DNS query -> resolver -> dependency address
app -> allowed transport -> internal/external dependency
policy must permit each required leg, not just the final hostname
```

The first line is a dependency people forget: before the app can call anything by name, it sends a DNS query, and that query is itself egress. The second line is the real call. The third line is the rule that follows: an egress policy must allow every leg, including DNS on UDP and TCP 53, not just the final destination.

## Worked example / walkthrough

### Worked example 1: Read a default-deny egress policy fragment

This is a manual design input.

```yaml
podSelector:
  matchLabels:
    app: network-study
policyTypes: [Egress]
egress: []
```

**Expected observation:** Selected Pods have no outgoing allowance from this policy; other applicable policies still matter.

### Worked example 2: Classify a DNS-dependent failure

The synthetic comparison localizes the missing dependency.

```text
direct permitted IP request succeeds
name resolution times out
DNS egress is not allowed
```

**Expected observation:** The app route may be healthy while discovery is blocked.

## Six progressive exercises

### Exercise 1: Predict the effect of an empty egress list.

**Expected evidence:** It contributes no allowed outgoing flows for selected Pods.

**Progressive hint:** An empty egress list permits nothing. What does that mean when a selected Pod looks up a name?

### Exercise 2: Include DNS in a dependency map.

**Expected evidence:** Resolver destination and UDP/TCP requirements are explicit.

**Progressive hint:** Before the real call, the app queries a resolver. Find its Service and both protocols it uses.

### Exercise 3: Design a minimal egress matrix.

**Expected evidence:** Only named required internal or external flows are permitted.

**Progressive hint:** Start from deny-all, add one rule per named dependency including DNS, and check nothing else slipped in.

### Exercise 4: Diagnose named-request failure with direct-IP success.

**Expected evidence:** Inspect DNS egress and resolver behavior first.

**Progressive hint:** If the address works and the name does not, the policy may allow the destination but not the resolver.

### Exercise 5: Explain why an IP block is not a hostname policy.

**Expected evidence:** It matches addresses, which may not be stable or exclusive to one service.

**Progressive hint:** An ipBlock matches addresses. What happens when the provider moves the hostname to another address?

### Exercise 6: Plan an egress qualification after NAT.

**Expected evidence:** Record implementation, observed addresses and both allowed/denied cases.

**Progressive hint:** After NAT the destination may see another source. Record one allowed and one denied case under the named plugin.

## Diagnosis, failure boundaries and common mistakes

The most frequent egress mistake is forgetting DNS: a default-deny egress policy plus an allow rule for the database still breaks every request that uses a hostname. Allow the cluster DNS Pods on UDP and TCP 53. Another mistake is writing an ipBlock for a SaaS hostname; providers change addresses and share them across customers, so the rule is both brittle and broad. When a caller fails despite matching the destination's ingress rule, check the caller's own egress before editing the destination, exactly as the egress-blocked case shows.

Before concluding, record:

- Every leg of one named request: the resolver address on UDP and TCP 53, then the dependency address and port.
- Each egress policy that selects the Pod, since allowances from several policies add together.
- Paired results for the same destination by hostname and by direct IP, which separate DNS from transport.
- The source address the destination observed after NAT, if an external allow list depends on it.
