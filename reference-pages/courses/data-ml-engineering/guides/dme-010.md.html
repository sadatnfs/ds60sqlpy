dme-010: HTTP APIs, pagination, retries and idempotency#

Level: Intermediate | Prepared runtime: data-engineering

Direct prerequisites: dme-007, dme-009.

Outcome: Exercise an actual local ASGI pagination contract without network access.

Open the worked program in the classroom code pad. This tutorial exposes complete examples and answered discussions without an exam gate. The pad has fresh temporary state; separately documented projects use their own owned lifecycle.

Treat an API response as a contract#

An HTTP API connects a caller to an application's declared operations. A request has a method, target, headers and sometimes a body. A response has a status, headers and sometimes a body. A successful transport exchange still needs a correct interpretation: which records were returned, which population they represent, whether an effect occurred and whether retrying could repeat it.

This chapter exercises actual FastAPI routing, request validation and response serialization through TestClient. It does not start a listening network server. DNS, TCP, TLS, proxies and real connection loss are therefore outside this pad's evidence. The separate owned project workflow tests real loopback HTTP. Keeping those boundaries explicit prevents an application-level check from being described as a complete network deployment.

The application stores a tiny synthetic collection in memory. Its state is protected by a lock within this one process. That guard makes the local read/modify decisions coherent when handlers use threads, but it is not a cross-process database transaction or durable receipt store. Restarting this program discards the collection, snapshots and idempotency receipts.

Methods and statuses describe different outcomes#

The example uses GET to read pages and POST to request creation of an identified delivery. HTTP method semantics help a caller reason about retries, but POST does not automatically become retry-safe because two payloads look identical. The application must define whether and how a repeated request identity maps to an earlier effect.

For this particular contract, a new delivery returns status 201. A recognized replay returns status 200 with a replay indicator. A conflicting reuse of identity returns 409. A malformed cursor returns 400, an unavailable snapshot returns 410, and invalid or missing declared request fields produce validation errors with status 422. These are observed choices in this application, not a claim that every API uses the same response body or policy.

The body model requires a nonblank bounded delivery ID and a positive bounded integer package count. Unknown fields are forbidden and the parsed body is validated strictly. The idempotency key is a required bounded header. FastAPI maps the Python parameter name to the corresponding hyphenated HTTP header name, and header names are interpreted under HTTP's case-insensitive rules.

A client should distinguish a permanent request problem from a temporary failure. Repeating a malformed request without changing it is usually not a useful retry policy. Temporary throttling or service failures may justify bounded backoff under the API's documented rules. Cancellation, maximum attempts, deadlines and any retry guidance also belong in that policy. None of those choices removes the need to reconcile an effect that may already have occurred.

Pagination defines a population over time#

A paginated API returns part of a collection and some way to request another part. A simple numeric offset can be adequate for a stable collection. It becomes dangerous when the collection changes between requests and the caller assumes the pages form one consistent snapshot.

The demonstration begins with deliveries A, B and C sorted by identity, with a page size of two. After the caller reads A and B, a new delivery 0 is inserted before them in the sort order. Reading offset two from the current collection now returns B and C. The combined result is A, B, B, C: four records, but the wrong identities for either the old or new population.

The safer route in this example creates a bounded snapshot and returns a cursor identifying that snapshot and a position within it. Later requests continue through the same captured collection. New deliveries belong to a subsequent snapshot. This is one explicit consistency policy; an API could offer a different one if it documented and tested its semantics.

The cursor is a readable teaching representation, not a cryptographic authorization mechanism. Real APIs need to bind cursor interpretation to the relevant query, authorization context and lifetime. This example rejects malformed, out-of-range, unknown or expired snapshot references, and retains only a small number of snapshots to keep the fixture bounded.

Worked case 1: Preserve the initial population across a mutation#

The first case reads page one from both the unsafe offset route and the snapshot route. It then creates delivery 0 through the actual POST handler. The unsafe second page duplicates B because the offset is now applied to a different ordered population.

The snapshot cursor instead returns the remaining original delivery C. Combining its two pages yields exactly A, B and C, with no next cursor. A fresh snapshot begins with 0 and A, demonstrating that the new record is visible under a new population identity rather than being lost globally.

This connects directly to the earlier testing chapter: a plausible count is weaker evidence than the intended identity-level result.

The fixture's snapshots are in memory and were created inside one application process. The case does not establish a distributed database snapshot or a production retention policy. A larger API must connect its cursor to the actual backing store's consistency and lifecycle behavior.

Retrying an effect requires an identity policy#

The create operation fingerprints the validated request content and associates it with a caller-supplied idempotency key. When the same key and content reappear, the application returns the stored result instead of creating another delivery. When the same key names different content, it rejects the conflict.

This is more precise than deduplicating by a convenient payload field after the fact. An operation identity should describe the intended effect under a documented scope. It also needs a lifetime: if a key expires while a caller might still retry, the system must define what happens. The example retains its small receipt collection only for the life of the process.

The business delivery ID supplies an additional constraint. A new idempotency key does not authorize creation of a second conflicting delivery with the same business ID. Request identity and entity identity answer different questions, just as batch identity and record identity did in the ingestion chapter.

Worked case 2: Reconcile a request after a deliberately ignored response#

The second case sends a request to create delivery D with four packages and deliberately does not use the first response. This models a caller that does not know the outcome. It is not an executed TCP failure; the local handler really ran, while response loss is represented by discarding the result in the test.

The caller repeats the same content with the same idempotency key. The application returns status 200 and the stored delivery with replayed=True. There is only one D in the collection. Reusing that key with nine packages returns 409, and the accepted value remains four.

The case also checks an unknown snapshot and a create request without the required header. These return the declared error statuses rather than silently choosing a new population or an untracked effect. The response body and the actual stored state are both inspected, so the test checks more than a status code.

This local receipt policy does not survive a process restart. A real ingestion or prediction service that needs retry safety across replacement must store its accepted effect and receipt durably and reconcile them after failure. The transactional ingestion example demonstrates one database boundary; the full owned project connects these ideas to real HTTP and persistence.

Complete worked program#

"""Actual local ASGI request contracts; no network server is started."""

import hashlib
import json
from threading import RLock

from fastapi import FastAPI, Header, HTTPException, Query
from fastapi.responses import JSONResponse
from fastapi.testclient import TestClient
from pydantic import BaseModel, ConfigDict, Field


class Delivery(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")
    delivery_id: str = Field(min_length=1, max_length=32, pattern=r".*\S.*")
    packages: int = Field(ge=1, le=100_000)


def application():
    app = FastAPI(docs_url=None, redoc_url=None)
    lock = RLock()
    state = {
        "rows": {
            key: {"delivery_id": key, "packages": value}
            for key, value in [("A", 2), ("B", 3), ("C", 1)]
        },
        "snapshots": {},
        "next_snapshot": 0,
        "receipts": {},
    }

    def current_rows():
        with lock:
            return [dict(state["rows"][key]) for key in sorted(state["rows"])]

    @app.get("/unsafe-pages")
    def unsafe_pages(offset: int = Query(0, ge=0)):
        with lock:
            return {"items": current_rows()[offset : offset + 2]}

    @app.get("/deliveries")
    def pages(cursor: str | None = None):
        with lock:
            if cursor is None:
                state["next_snapshot"] += 1
                snapshot = "s" + str(state["next_snapshot"])
                state["snapshots"][snapshot] = current_rows()
                if len(state["snapshots"]) > 4:
                    del state["snapshots"][next(iter(state["snapshots"]))]
                offset = 0
            else:
                try:
                    snapshot, raw_offset = cursor.split(":")
                    offset = int(raw_offset)
                    if offset < 0:
                        raise ValueError("Negative offset")
                except ValueError:
                    raise HTTPException(400, "Malformed cursor") from None
            if snapshot not in state["snapshots"]:
                raise HTTPException(410, "Snapshot expired or unknown")
            rows = state["snapshots"][snapshot]
            if offset > len(rows):
                raise HTTPException(400, "Cursor offset is outside its snapshot")
            next_offset = offset + 2
            next_cursor = f"{snapshot}:{next_offset}" if next_offset < len(rows) else None
            return {
                "items": rows[offset:next_offset],
                "next_cursor": next_cursor,
                "snapshot": snapshot,
            }

    @app.post("/deliveries")
    def create(record: Delivery, idempotency_key: str = Header(min_length=1, max_length=64)):
        with lock:
            document = record.model_dump()
            identity = hashlib.sha256(json.dumps(document, sort_keys=True).encode()).hexdigest()
            prior = state["receipts"].get(idempotency_key)
            if prior is not None:
                if prior["identity"] != identity:
                    raise HTTPException(409, "Idempotency key reused with different content")
                return JSONResponse(
                    {"delivery": prior["delivery"], "replayed": True}, status_code=200
                )
            if record.delivery_id in state["rows"]:
                raise HTTPException(409, "Delivery already exists")
            state["rows"][record.delivery_id] = document
            state["receipts"][idempotency_key] = {"identity": identity, "delivery": document}
            return JSONResponse({"delivery": document, "replayed": False}, status_code=201)

    return app, state


def identities(response):
    assert response.status_code == 200
    return [row["delivery_id"] for row in response.json()["items"]]


def example_one():
    app, _ = application()
    with TestClient(app) as client:
        unsafe_first = identities(client.get("/unsafe-pages?offset=0"))
        first = client.get("/deliveries")
        stable_first = identities(first)
        created = client.post(
            "/deliveries",
            json={"delivery_id": "0", "packages": 1},
            headers={"Idempotency-Key": "insert-0"},
        )
        assert created.status_code == 201
        unsafe_second = identities(client.get("/unsafe-pages?offset=2"))
        second = client.get("/deliveries", params={"cursor": first.json()["next_cursor"]})
        stable = stable_first + identities(second)
        assert stable == ["A", "B", "C"] and second.json()["next_cursor"] is None
        assert unsafe_first + unsafe_second == ["A", "B", "B", "C"]
        assert identities(client.get("/deliveries")) == ["0", "A"]
        return {
            "stable_start_population": stable,
            "unsafe_offset_result": unsafe_first + unsafe_second,
            "new_record_belongs_to_a_new_snapshot": "0",
        }


def example_two():
    app, state = application()
    with TestClient(app) as client:
        payload = {"delivery_id": "D", "packages": 4}
        headers = {"Idempotency-Key": "request-D"}
        # Discard a successful application response to model an unknown client outcome.
        client.post("/deliveries", json=payload, headers=headers)
        replay = client.post("/deliveries", json=payload, headers=headers)
        conflict = client.post(
            "/deliveries", json={"delivery_id": "D", "packages": 9}, headers=headers
        )
        assert replay.status_code == 200 and replay.json()["replayed"] is True
        assert replay.json()["delivery"] == payload and conflict.status_code == 409
        assert len(state["rows"]) == 4 and state["rows"]["D"]["packages"] == 4
        assert client.get("/deliveries?cursor=unknown:0").status_code == 410
        assert client.post("/deliveries", json=payload).status_code == 422
        return {
            "replayed_status": replay.status_code,
            "conflict_status": conflict.status_code,
            "one_created_delivery": state["rows"]["D"],
            "network_failure_was_modeled_not_executed": True,
        }


def main():
    print("Pagination under a changed population:", example_one())
    print("Retry identity at the actual application boundary:", example_two())


if __name__ == "__main__":
    main()

Diagnose API failures without inventing certainty#

A validation error, a conflict, an expired cursor, a server failure and a timeout are different observations. Record the operation identity and the bounded diagnostic needed to investigate them. Do not log credentials or complete sensitive request bodies merely because a request failed.

When an outcome is unknown, first determine whether the server can identify the intended operation and report its accepted result. Blindly repeating a non-idempotent action can duplicate an effect. Conversely, refusing every retry can make a system unnecessarily unavailable. The correct decision depends on the operation's actual identity and acceptance contract.

For pagination problems, inspect ordering, mutation between pages, cursor scope and snapshot lifetime. A query can return individually valid rows while the collected result fails to represent a coherent population. Retain source identities and coverage checks rather than relying only on a final row count.

Where this is useful#

These mechanisms apply to extraction APIs, ingestion endpoints, feature services and model requests. They also clarify tests: application routing and serialization can be exercised locally, while real network, authentication, concurrency and restart behavior need their corresponding actual environments.

Answered interview discussion#

When is an offset cursor unsafe? When the caller assumes a stable population but insertions, deletions or ordering changes move records between page requests. Define a snapshot or another explicit continuation contract.

Why compare request content for a reused key? Otherwise a key could accidentally or deliberately refer to two different intended effects. Returning the old result for changed content would conceal that conflict.

What does an in-memory idempotency map guarantee? Only the declared behavior within its process and lifetime. Durable or multi-replica operation requires a shared acceptance policy and actual persistence/concurrency evidence.

Does TestClient prove TLS and network recovery work? No. It proves the exercised application contract through a real in-process ASGI exchange. Network and container lifecycle checks are separate observations.
