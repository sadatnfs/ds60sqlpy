## Learning objectives

Choose an optimization from growth behavior and measured constraints.

## Vocabulary and concepts

Algorithmic complexity describes how work grows as input grows. A representation can change that work: repeated linear search differs from building an index once. A benchmark compares defined workloads under measured conditions. For tiny collections, index setup may outweigh faster lookup, so asymptotic reasoning and actual budgets both matter.

<!-- terms:start -->

- **algorithmic complexity:** how work grows with input size under a stated model.
- **index:** a structure built once, such as a map of counts, so that later queries cost less than a linear scan.
- **amortized cost:** index construction work spread across the repeated queries that actually reuse the index.
- **benchmark:** a comparison of defined workloads under measured conditions.
- **`map::operator[]`:** access that inserts a value-initialized mapped value when the key is absent, unlike `find`.

<!-- terms:end -->

## Syntax and mechanism

A map associates one key with one value, so repeated keys need an explicit aggregation or rejection policy. Building counts with ++counts[x] preserves multiplicity. Compare outputs and operation counts before reporting elapsed-time differences.

## Trace the mechanism

Index building has an upfront cost that can be repaid across repeated queries. A map count preserves both occurrences of key 2; a set would answer a different question. The seemingly read-like `counts[9]` inserts a missing key with zero, whereas find does not change the map. That behavioral difference can contaminate an experiment and the data contract. Report index construction separately from lookup work and keep the queried answers identical.

## Algorithmic work and index side effects

Complexity describes how work grows with input size under a stated model. A linear scan visits elements to answer a query. An index spends work and memory building a reusable structure so later queries can be cheaper. The right choice depends on the number of queries, update frequency, key distribution and required semantics, not only a big-O label.

The map fixture counts occurrences of 2, 3, 2, 4. The count for 2 is 2, which preserves multiplicity. A set would retain only membership and answer a different question. The index construction traverses every input and updates counts. That upfront work must be included when comparing one query with a direct scan, and can be amortized only when the index is actually reused.

map::find is an observation that does not insert a missing key. operator[] can insert a value-initialized mapped value when the key is absent. The second complete program demonstrates this difference: find(9) leaves size unchanged, while `counts[9]` creates a new zero entry. A read-like expression can therefore mutate the data and distort later measurements or reports.

Ordering is also part of the container contract. std::map maintains an ordering by its comparator, whereas unordered alternatives have different iteration and performance properties. Do not rely on unspecified order when emitting a deterministic report. If output order matters, choose or impose it deliberately rather than inheriting it accidentally from one implementation run.

A useful performance comparison checks identical answers first, then records index build cost, lookup count and memory tradeoffs. It includes missing keys and repeated keys because they exercise different paths. A faster method that drops duplicate events or inserts new data during lookup does not satisfy the original contract.

## Worked example / walkthrough

Example 1 counts `{2, 3, 2, 4}` in a `std::map`: the count for 2 is 2 and three keys exist. Example 2 shows `find(9)` leaving the map untouched while `operator[]` on 9 inserts a zero entry and grows the size by one, so a lookup can silently become a write. Build rules: [study guide](../STUDY-GUIDE.md#worked-examples).

### Worked example 1

[Complete program 1](../examples/cpp-035-example-1.cpp)

```cpp
#include <cassert>
#include <iostream>
#include <map>
#include <vector>

int main() {
  std::map<int, int> counts;
  for (int x : std::vector<int>{2, 3, 2, 4})
    ++counts[x];
  assert(counts.at(2) == 2 && counts.size() == 3);
  std::cout << "cpp-035 example 1 checks passed\n";
  return 0;
}
```

### Worked example 2

[Complete program 2](../examples/cpp-035-example-2.cpp)

```cpp
#include <cassert>
#include <iostream>
#include <map>

int main() {
  std::map<int, int> counts{{2, 2}, {3, 1}, {4, 1}};
  const auto before = counts.size();
  assert(counts.find(9) == counts.end());
  assert(counts.size() == before);
  assert(counts[9] == 0 && counts.size() == before + 1);
  std::cout << "cpp-035 example 2 checks passed\n";
  return 0;
}
```

**Expected:** With assertions enabled, the program exits with status 0 and prints:

## Exercises

### Exercise 1: Count linear work

Search four rows for key 2 once.

**Expected result/shape:** Four comparisons and count 2.

**Verify:** Increment a comparison counter inside the loop over `{2, 3, 2, 4}` and assert it ends at 4 with a match count of 2.

**Progressive hints:** A scan inspects every element for a complete count.

### Exercise 2: Build an index

Build frequency map for [2, 3, 2, 4].

**Expected result/shape:** Three keys with counts 2, 1, 1.

**Verify:** Assert `counts.size() == 3`, `counts.at(2) == 2`, `counts.at(3) == 1` and `counts.at(4) == 1`, extending Worked example 1's assertion.

**Progressive hints:** The representation preserves duplicate multiplicity.

### Exercise 3: Compare repeated queries

Compare 100 full scans with one index build plus 100 lookups.

**Expected result/shape:** Same answers; setup and lookup work reported separately.

**Verify:** Assert both approaches return the same count for each of the 100 queries, then report the index-building work separately from the lookup work.

**Progressive hints:** Amortization depends on number of queries.

### Exercise 4: Repair mutating lookup

Use `counts[9]` to inspect absence, then repair with find.

**Expected result/shape:** operator[] inserts zero; find leaves key count unchanged.

**Verify:** Assert `counts.size()` grows by one after `counts[9]` but not after `counts.find(9) == counts.end()`, as Worked example 2 does.

**Progressive hints:** Read syntax can mutate a map.

### Exercise 5: Check empty data

Build and query an empty frequency index.

**Expected result/shape:** No key 2 and zero matching rows.

**Verify:** Assert `counts.empty()`, `counts.find(2) == counts.end()` and `counts.count(2) == 0` for an index built from no rows.

**Progressive hints:** Avoid accidental insertion during an absence check.

### Exercise 6: Transfer sorted storage

Compare binary search on a sorted vector with map lookup.

**Expected result/shape:** Sorting cost, duplicate range and lookup budget documented.

**Verify:** Use `std::equal_range` on the sorted vector and assert its length for key 2 equals `counts.at(2)`, then record the one-time sort cost next to the per-query cost.

**Progressive hints:** The best choice depends on updates and query frequency.

## Self-check

Why does the index hold 2->2, 3->1, 4->1 after counting `{2, 3, 2, 4}`? For Example 2, explain why `find(9)` leaves the size alone while `counts[9]` grows it by one.

## Common pitfalls

If a map grows during a supposedly read-only report, search for operator[] on missing keys. If duplicates disappear, check whether a set replaced a count map. If two approaches give different answers, resolve semantics before timing. If an index helps only after many queries, report the build cost and reuse threshold instead of presenting lookup-only timing as the total task cost.
