# c-038: C11 atomics and release-acquire publication

## Level and prerequisites

Advanced, approximately 120 minutes plus a later retrieval session. Direct prerequisites: `c-037`

Implement the six investigations, from the "inspect fetch-add semantics" case to the "transfer an atomic exchange" case, with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

Atomic types make individual accesses participate in a defined concurrency model. They are not interchangeable with volatile, and they do not automatically protect a multi-field invariant. The default sequentially consistent operations are a useful starting point. Weaker memory orders require a proof connecting the writer and reader. A release store can publish preceding writes to a reader whose acquire load observes that store. A relaxed counter can count independent events without publishing unrelated memory. Lock-free status is implementation-dependent; atomic does not mean every operation avoids a lock on every platform.

## Vocabulary and concepts

- **Atomic object:** An object accessed through the C atomic operation contract.
- **Memory order:** The ordering guarantees requested by an atomic operation.
- **Publication:** Making initialized non-atomic state visible through synchronization.

## Syntax anatomy and execution trace

atomic_int declares an atomic integer and atomic_init initializes it before sharing. atomic_fetch_add returns the previous value. atomic_compare_exchange_strong updates only when the current value matches expected and writes the observed value back to expected on failure. memory_order_release and memory_order_acquire form a publication relationship when the acquire observes the release. Avoid hand-built lock-free containers until ownership, reclamation and ABA hazards are understood.

## Worked example / walkthrough

### Worked example 1: Inspect fetch-add semantics

Add 3 to an atomic integer initially 2.

```c
#include <assert.h>
#include <limits.h>
#include <pthread.h>
#include <sched.h>
#include <stdatomic.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

struct Publication {
  atomic_bool ready;
  int value;
};
void *atomic_publisher(void *argument) {
  struct Publication *p = argument;
  p->value = 42;
  atomic_store_explicit(&p->ready, true, memory_order_release);
  return NULL;
}

int main(void) {
  /* Inspect fetch-add semantics */
  {
    atomic_int value;
    atomic_init(&value, 2);
    int old = atomic_fetch_add(&value, 3);
    CHECK(old == 2 && atomic_load(&value) == 5);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The returned old value is 2 and current value is 5.

The return value is the prior state. Confusing it with the new value can create off-by-one ticketing logic.

### Worked example 2: Compare and exchange successfully

Replace expected value 2 with 7.

```c
#include <assert.h>
#include <limits.h>
#include <pthread.h>
#include <sched.h>
#include <stdatomic.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

struct Publication {
  atomic_bool ready;
  int value;
};
void *atomic_publisher(void *argument) {
  struct Publication *p = argument;
  p->value = 42;
  atomic_store_explicit(&p->ready, true, memory_order_release);
  return NULL;
}

int main(void) {
  /* Inspect fetch-add semantics */
  {
    atomic_int value;
    atomic_init(&value, 2);
    int old = atomic_fetch_add(&value, 3);
    CHECK(old == 2 && atomic_load(&value) == 5);
  }

  /* Compare and exchange successfully */
  {
    atomic_int value;
    atomic_init(&value, 2);
    int expected = 2;
    CHECK(atomic_compare_exchange_strong(&value, &expected, 7));
    CHECK(atomic_load(&value) == 7);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The operation succeeds and stores 7.

The update is conditional on the observed state, not an unconditional assignment.

### Exercise 1: Inspect fetch-add semantics: change one input

In worked example 1, change `atomic_init(&value, 2);` to `atomic_init(&value, 3);`. Predict which value the CHECK on `old == 2 && atomic_load(&value) == 5` sees, then run and restore.

**Expected:** `Check failed` at `old == 2 && atomic_load(&value) == 5`; restoring `atomic_init(&value, 2);` passes again.

**Verify:** Name the value that made `old == 2 && atomic_load(&value) == 5` false, where worked example 1 showed that the returned old value is 2 and current value is 5.

**Progressive hints:** First trace `old` and `value` from initialization. Then compute what the CHECK sees with `atomic_init(&value, 3);` in place.

### Exercise 2: Compare and exchange successfully: diagnose an edited check

Worked example 2's CHECK now reads `CHECK(atomic_compare_exchange_strong(&value, &expected, 8));`. Explain why it fails although the operation succeeds and stores 7, then restore it.

**Expected:** `Check failed` until the CHECK reads `CHECK(atomic_compare_exchange_strong(&value, &expected, 7));` again, though the operation succeeds and stores 7.

**Verify:** Explain why `CHECK(atomic_compare_exchange_strong(&value, &expected, 8));` rejects a state that `atomic_load(&value) == 7` accepts, using your failing and repaired runs.

**Progressive hints:** First trace `value` from initialization. Then compare `CHECK(atomic_compare_exchange_strong(&value, &expected, 8));` with worked example 2's original line.

### Exercise 3: Inspect failed compare-exchange

Attempt replacement with stale expected value 2 when current is 3.

**Expected:** It fails and expected becomes 3.

**Verify:** Keep a CHECK equivalent to `expected == 3 && atomic_load(&value) == 3`. Control edit: changing `atomic_init(&value, 3);` to `atomic_init(&value, 4);` must fail it; then restore it.

**Progressive hints:** First trace `expected` and `value` from initialization. Then recall: The API returns current observation through expected, which a retry loop must handle deliberately.

### Exercise 4: Count independent events

Perform ten relaxed increments before reading in the same thread.

**Expected:** The count is 10.

**Verify:** Keep a CHECK equivalent to `atomic_load_explicit(&count, memory_order_relaxed) == 10`. Control edit: changing `for (int i = 0; i < 10; i++)` to `for (int i = 0; i <= 10; i++)` must fail it; then restore it.

**Progressive hints:** First trace `count` and `memory_order_relaxed` from initialization. Then recall: This fixture demonstrates the counter API, not publication of unrelated memory.

### Exercise 5: Publish initialized data

Use a release flag from a worker and acquire it before reading its payload.

**Expected:** The payload is 42.

**Verify:** Keep a CHECK equivalent to `p.value == 42`. Control edit: changing `atomic_init(&p.ready, false);` to `atomic_init(&p.ready, true);` must fail it; then restore it.

**Progressive hints:** First trace `p` from initialization. Then recall: The payload read follows the acquire observation of the release store.

### Exercise 6: Transfer an atomic exchange

Replace a flag value and inspect the returned prior state.

**Expected:** The old state is false and the new state true.

**Verify:** Keep a CHECK equivalent to `!old && atomic_load(&ready)`. Control edit: changing `atomic_init(&ready, false);` to `atomic_init(&ready, true);` must fail it; then restore it.

**Progressive hints:** First trace `old` and `ready` from initialization. Then recall: Exchange is one atomic operation.

## Common pitfalls and diagnosis

Publishing data through a plain `bool ready` flag is a data race even if it seems to work. A relaxed store cannot publish initialized data either; pair a release store with an acquire load of the same atomic object.
