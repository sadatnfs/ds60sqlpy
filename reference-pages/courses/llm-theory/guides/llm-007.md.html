Purpose and mental model#

Learn a useful alphabet without memorizing every word#

A vocabulary containing every possible word cannot anticipate all names, misspellings, compounds and new technical terms. A vocabulary containing only tiny units can represent more strings, but may require long sequences. Subword tokenization explores the middle ground: retain a small base alphabet and learn larger recurring units that make common sequences shorter. The model then predicts those units rather than assuming that a token must be a complete word.

The toy byte-pair procedure starts with individual UTF-8 byte values, represented as one-element tuples. Byte 97 is a, 98 is b and 99 is c. The integer 256 in the fixture is a special boundary marker, not a byte that can be passed directly to bytes(...). A token can later become a tuple of several base values; for example, (97,98) represents the concatenated bytes for ab. This transparent representation lets us inspect exactly what a merge preserves.

The training corpus contains ab and ac, each followed by its boundary marker. The neighboring pairs are a+b, b+boundary, a+c and c+boundary, each observed once. A frequency rule alone cannot choose among this tie. The reference uses lexical ordering of the integer tuples, which chooses a+b. That tie rule is part of the fitted tokenizer's reproducibility: the order in which a dictionary happens to return candidates should not silently determine the vocabulary.

Applying the selected rule scans left to right. When two adjacent tokens match the chosen pair, the algorithm emits their concatenation and advances by two positions. Otherwise it emits the current token and advances by one. The ab example becomes [(97,98),(256,)]. No byte was deleted; the grouping changed. Overlapping pair occurrences require this explicit scan policy. Counting pair frequencies and replacing pairs are related operations, but a count table alone does not specify how overlapping matches are rewritten.

After training, encoding a new input applies the frozen rules. The validation word ad contains no a+b pair, so its three initial units remain unchanged. Byte 100 is still representable through the base alphabet even though no a+d merge was learned. Fitting a new merge because this validation string appeared would change the preprocessing model using held-out information. A tokenizer has learned state just as a count model does: its rule list, rule order, vocabulary IDs and preprocessing choices must be saved and versioned.

The subword research paper supplies the motivation for learned subword units; the course's byte tuples and deterministic tie policy are a deliberately small inspectable implementation. Compression is not the same as discovering meaning. A frequent string fragment may be useful to represent as one token without corresponding to a linguistic root, and two semantically related words need not share a learned unit. The next chapter assigns vectors to the resulting IDs; learning how those vectors support prediction is a separate process.

BPE learns a sequence of rewrites, not a meaning dictionary#

The starting symbols in this lesson are byte tuples. A one-byte token a is(97,), and a merged token ab is(97,98). The tuple records the payload, while a production vocabulary normally assigns a separate integer token ID to that payload. Payload and ID should not be confused: changing an ID can change the selected embedding row even if the human-readable token text looks identical. The special end-of-word symbol256 is deliberately outside the byte range0..255 and is handled separately by the decoder.

A training iteration counts adjacent token pairs in the current segmentation, chooses one pair and rewrites its nonoverlapping occurrences. Counts must be recomputed after rewriting because the neighbors have changed. With words ab and ac, the observed pairs are(a,b),(b,end),(a,c),(c,end), each once. The declared lexicographic rule on integer tuples chooses(a,b), independently of input order. A different tie rule can produce a different first merge and later vocabulary, so the rule is part of reproducibility rather than an unimportant implementation detail.

An overlap counterexample is the word aaa, represented as a,a,a,end. The pair(a,a) occurs twice as an adjacent pattern: positions 0-1 and 1-2. A single left-to-right nonoverlapping replacement can merge only the first pair, producing aa,a,end. It must not use the middle a twice and produce aa,aa,end, which would decode to four a bytes instead of three. Pair frequency is the selection statistic; realized replacement count can be smaller when occurrences overlap. Byte conservation is an independent invariant that catches this mistake.

The saved merge order determines encoding. Suppose the learned rules include(a,b)→ab and(ab,c)→abc. Starting from a,b,c, applying them in that order yields abc. Applying the second rule first finds no ab token yet and leaves ab,c after the later rule. An unordered set of possible merged payloads does not reproduce the trained tokenizer. The lesson's sequential application is a deliberately transparent rewrite policy; compatibility with an external tokenizer also depends on its pre-tokenization, merge-ranking convention, boundary handling and special tokens.

Byte fallback addresses representation coverage, not semantic competence. The unseen d in validation word ad still has base byte100, so the sequence can be encoded without fitting an a+d merge. This does not mean the model learned how to use d in that context. Encoding coverage and predictive quality are separate questions. Likewise, a byte vocabulary does not imply that each token can be decoded as a complete Unicode character independently; concatenate payload bytes and apply the declared decoding policy.

Training text composition affects which merges become common. If one domain's repeated boilerplate dominates counts, the tokenizer may compress it well while representing another domain with longer sequences. Under a fixed token budget, different segmentations expose different amounts of source text to the model. Longer segmentation can also increase attention work and alter per-token loss denominators. These are reasons to measure token lengths and task coverage on a held-out corpus, not reasons to refit on that corpus after seeing inconvenient lengths.

A tokenizer/model artifact should bind at least normalization, pre-tokenization, byte/special-token definitions, ordered merges, ID assignment and the associated embedding/output vocabulary. Two tokenizers with the same vocabulary size can disagree completely about row identity. A hash of only an unordered token list misses merge-order changes. The immutable rule list in the example is a small proxy for that larger artifact contract, not proof that arbitrary pretrained tokenizers are interchangeable.

Interview reasoning: "Why not learn a new merge for every unknown validation word?" That would change the representation after observing evaluation data and could introduce IDs without trained embedding/output rows. The proper action is to apply the frozen policy and report its behavior. If domain adaptation justifies a new tokenizer, treat it as a new model/pipeline experiment with a fresh fitting split and compatibility plan. The original subword motivation is described in Sennrich, Haddow and Birch; this byte-tuple implementation uses its own explicit teaching conventions.

Vocabulary and concepts#

Base symbol: a fixed original encoding unit; here one UTF-8 byte ID, plus the separately declared end marker.

Merge rule: an ordered neighboring-token pair replaced by its concatenated token.

Tie policy: a deterministic rule selecting one candidate when pair counts are equal.

Frozen tokenizer: a fixed representation policy and ordered merge list used without fitting on evaluation text.

Nonoverlapping replacement: left-to-right pair replacement that consumes each matched occurrence once rather than reusing one position twice.

Syntax or reasoning anatomy#

Represent byte a as (97,) and byte b as (98,). Merging the pair creates (97,98), preserving their underlying byte sequence. The marker (256,) records the word boundary and is removed by the matching decoder. A merge can include the end marker, but no training pair crosses from one word into the next because each word has its own symbol sequence.

Count every neighboring pair over the current training tokenization, choose the highest count with the declared lexical tie-break, replace its nonoverlapping occurrences, and repeat up to the small merge budget. Save the ordered rules, not just an unordered vocabulary set. Encoding new text applies each saved rule in order. The fixed byte base supplies unseen byte fallback without changing the learned rules or their hash.

Example A: Inspect and apply the tied first merge#

Count byte-token neighbors, choose the documented tie and replace without overlap.

from collections import Counter

corpus = [[(97,), (98,), (256,)], [(97,), (99,), (256,)]]
counts = Counter(pair for word in corpus for pair in zip(word, word[1:]))
maximum = max(counts.values())
pair = min(pair for pair, count in counts.items() if count == maximum)
assert pair == ((97,), (98,))


def merge_once(tokens, chosen):
    result, index = [], 0
    while index < len(tokens):
        if index + 1 < len(tokens) and (tokens[index], tokens[index + 1]) == chosen:
            result.append(tokens[index] + tokens[index + 1])
            index += 2
        else:
            result.append(tokens[index])
            index += 1
    return result


assert merge_once(corpus[0], pair) == [(97, 98), (256,)]
print(pair, merge_once(corpus[0], pair))

Expected: Each candidate count is one. Lexical integer-tuple ordering selects a+b, whose replacement preserves the underlying bytes. Training input order cannot decide a tie accidentally.

Example B: A frozen rule leaves a new byte unmerged#

Reuse the selected rule on validation word ad without calling a fitting function.

rules = [pair]
before = tuple(rules)
validation = [(97,), (100,), (256,)]
for chosen in rules:
    validation = merge_once(validation, chosen)
assert validation == [(97,), (100,), (256,)]
assert tuple(rules) == before
assert bytes(value for token in validation[:-1] for value in token).decode("utf-8") == "ad"
print(validation)

Expected: The d byte is supported by the fixed base. Encoding leaves the learned rule list unchanged; appearing in validation does not justify fitting an a+d merge.

Progressive hints#

  • Hint 1: Write each word as its own byte-token sequence with an end marker.
  • Hint 2: Resolve count ties before replacing tokens, and advance past both positions of a matched pair.
  • Hint 3: The encoding path applies saved rules; only the fitting path may create a new rule.

Common pitfalls#

If two fits disagree, compare candidate counts, the declared tie order and the sequence of already applied rules. Sorting only the final vocabulary cannot recover a different merge history. If a decoder loses characters, inspect whether replacement reused overlapping positions or whether the end marker was confused with a real byte.

If validation improves after refitting the tokenizer, it has influenced representation selection. Freeze rules and base policy first. A byte-level toy tokenizer is not automatically a production tokenizer: it lacks a complete text segmentation, special-token and vocabulary-ID policy. The next unit separates token IDs from embedding feature coordinates. Do not pass arbitrary byte-tuple tokens directly into a learned lookup table without a declared mapping.
