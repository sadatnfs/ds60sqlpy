k8s-059: Egress policy, DNS dependencies and external destinations#

Level and prerequisites#

Advanced; about 120 minutes plus optional supervised host observations. Direct prerequisites: k8s-058. This is the deep networking and operations extension; it preserves the original Kubernetes sequence and its separately qualified browser operations.

Learning objectives#

Design a minimal egress matrix. Plan an egress qualification after NAT. Trace the exact caller, destination, control-plane object and data-plane behavior that would support your conclusion.

Purpose, vocabulary and mental model#

Egress policy controls selected Pods' outgoing traffic under an enforcing implementation. A deny-by-default design begins by selecting the workloads and then allowing the dependencies they actually require. It can expose hidden dependencies such as DNS, metadata endpoints, package downloads or external APIs.

DNS is itself network traffic. Blocking it can make every named dependency fail even while a direct allowed IP connection works. UDP is common for DNS, but TCP can also be required. The correct DNS target and policy depend on the cluster’s DNS deployment and any node-local cache.

An IP allowlist is not the same as a domain-name policy. External services can change addresses, use shared infrastructure or return several families. The standard NetworkPolicy API does not provide a general hostname allowlist. Implementation extensions must be named and qualified separately.

Mechanism and field-by-field reasoning#

A policy with policyTypes Egress and an empty egress list isolates selected Pods without permitting outgoing flows through that policy. Additional applicable policies can add allowances. A source egress allowance is not sufficient when the destination is ingress-isolated: the destination must also permit the connection. Replies for a permitted connection are implicitly allowed, while a new reverse connection is evaluated as a new flow. Peer and port rules should be derived from the actual dependency map.

ipBlock represents CIDR-based address ranges with optional exclusions. Address translation can affect which IP an implementation evaluates at a boundary, so test the actual traffic path. Do not promise identical pre-NAT or post-NAT behavior across every plugin and Service combination.

Trace the request or control path#

app -> DNS query -> resolver -> dependency address
app -> allowed transport -> internal/external dependency
policy must permit each required leg, not just the final hostname

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

Worked example / walkthrough#

Worked example 1: Read a default-deny egress policy fragment#

This is a manual design input.

podSelector:
  matchLabels:
    app: network-study
policyTypes: [Egress]
egress: []

Expected observation: Selected Pods have no outgoing allowance from this policy; other applicable policies still matter.

Worked example 2: Classify a DNS-dependent failure#

The synthetic comparison localizes the missing dependency.

direct permitted IP request succeeds
name resolution times out
DNS egress is not allowed

Expected observation: The app route may be healthy while discovery is blocked.

Diagnosis, failure boundaries and common mistakes#

The controlled failure in this chapter is: Diagnose named-request failure with direct-IP success. Its distinguishing result is Inspect DNS egress and resolver behavior first. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
