web-059: Deploying PHP: containers, web servers and operations#

Level and prerequisites#

Advanced; allow about 150 minutes, with extra time for independent practice. Direct prerequisites: web-058

Learning objectives#

Design a release plan for the study planner with durable storage. Explain what evidence is needed before publishing an image as ready. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

Purpose, vocabulary and mental model#

A production PHP deployment commonly separates an HTTP server or reverse proxy from a PHP process manager. PHP-FPM manages FastCGI workers; it is not itself a general browser-facing HTTP server. A web server routes appropriate requests to the runtime and serves approved static assets. The public document root should contain only files intended for delivery, keeping source configuration, dependency metadata, private data and secrets outside that boundary.

A container packages a runtime and application, while volumes or external storage hold durable state. Rebuilding an image does not migrate a database automatically. A release needs a plan for schema changes, compatibility, rollback, backup and restore. A backup job reporting success is weaker evidence than an actual restore that recreates the expected data and application behavior.

Syntax anatomy and mechanism#

Use reviewed locked dependencies and a deliberate image tag or digest policy. Supply secrets through a controlled runtime mechanism rather than baking them into images or committing them. Enable appropriate error logging without displaying internal stack traces publicly. TLS termination and trusted proxy headers require an explicit network ownership policy; do not trust forwarded identity or scheme headers from arbitrary clients.

Classroom execution and offline inputs#

This is a reading and design worksheet with an optional external project lab. The classroom saves the worksheet but does not start an HTTP server, install packages or control Docker from its pad. Work from the supplied synthetic examples first. A command is a proposal until you deliberately execute it against your own disposable local project. The maintained optional fixture is courses/web-development/fixtures/php-http-lab/; read its README before preparing it. Do not expose that learning server to the internet or reuse real account data.

Six progressive exercises#

Exercise 1: Explain why PHP-FPM is not interchangeable with the development HTTP server.#

Expected evidence: FPM manages FastCGI workers and needs an appropriate HTTP-facing integration.

Progressive hint: Trace the smallest example before editing. Name which values are source and which are observations.

Exercise 2: Draw the public document root and private application directories.#

Expected evidence: Only intended static assets and entrypoints are directly served.

Progressive hint: Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

Exercise 3: Design a release plan for the study planner with durable storage.#

Expected evidence: The plan covers configuration, secrets, migration, health, write/read acceptance, backup and rollback.

Progressive hint: Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

Exercise 4: Diagnose secrets copied into an image layer.#

Expected evidence: Removing them in a later layer does not reliably erase earlier layer content; rotate exposed secrets and rebuild correctly.

Progressive hint: Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

Exercise 5: Describe a restore test in a separate disposable environment.#

Expected evidence: Recovered data and application behavior must be checked without overwriting the active store.

Progressive hint: Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

Exercise 6: Explain what evidence is needed before publishing an image as ready.#

Expected evidence: Source, dependency, runtime, browser, data recovery and target-environment checks need explicit results and limits.

Progressive hint: Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

Debugging and common mistakes#

Do not expose the PHP built-in learning server to the public internet and call it a production architecture. Avoid broad prune commands as deployment recovery. A successful image build cannot establish application correctness or backup recoverability.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

Retrieval, transfer and next steps#

Close the worked answers and explain PHP-FPM, reverse proxy, document root without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
