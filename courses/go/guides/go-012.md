# go-012: Defer, cleanup and deliberate panic boundaries

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-011

## Learning objectives

Predict defer order and argument capture, and keep cleanup running when a deliberate panic is recovered at a boundary. Along the way, explain deferred call, stack unwind, cleanup boundary; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

defer schedules a function call to execute when the surrounding function returns. It is a resource-lifetime tool, not a general background execution mechanism. Deferred calls run in last-in-first-out order, and their arguments are evaluated when the defer statement executes. Closures can instead read variables at the later execution time. panic unwinds the current goroutine's stack, running defers; recover can intercept it only in the appropriate deferred call during that unwind. Expected invalid input should normally be returned as an error. Recovering every panic and returning a success-shaped value conceals defects and can leave callers unable to distinguish completed work from aborted work.

## Vocabulary and concepts

- **Deferred call:** A call executed when the surrounding function exits.
- **Stack unwind:** Returning through active frames after a panic.
- **Cleanup boundary:** The scope that owns and releases a resource.

## Syntax anatomy and reasoning

defer cleanup() registers a call. defer func(){ ... }() registers a closure. A helper function is useful when each loop iteration needs its own cleanup boundary; deferring inside a long loop otherwise accumulates cleanup until the whole function returns. recover returns the active panic value when called correctly from a deferred function. A named return variable can be changed by deferred code, which is powerful but can make flow harder to read.

## Worked example / walkthrough

### Worked example 1: Trace cleanup order

Register first and second cleanup markers and return.

```go
package main

import (
	"fmt"
	"strings"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func deferOrder() (result string) {
	values := []string{}
	defer func() { result = strings.Join(values, ",") }()
	defer func() { values = append(values, "first") }()
	defer func() { values = append(values, "second") }()
	return
}
func deferArgument() (result int) { x := 1; defer func(v int) { result = v }(x); x = 2; return }
func deferClosure() (result int)  { x := 1; defer func() { result = x }(); x = 2; return }
func recoverKnown() (result string) {
	defer func() {
		if v := recover(); v != nil {
			result = fmt.Sprint(v)
		}
	}()
	panic("broken")
}
func cleanedAfterPanic() (cleaned bool) {
	defer func() { recover() }()
	defer func() { cleaned = true }()
	panic("fixture")
}
func scopedCleanup(count *int) { defer func() { *count = *count + 1 }() }

func main() {
	// Trace cleanup order
	{
		check(deferOrder() == "second,first", "defer order")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The observed order is second then first.

The last registered cleanup runs first. This naturally unwinds nested acquisitions in the opposite order from acquisition.

### Worked example 2: Compare captured arguments

Defer a call with x as an argument, then change x.

```go
package main

import (
	"fmt"
	"strings"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func deferOrder() (result string) {
	values := []string{}
	defer func() { result = strings.Join(values, ",") }()
	defer func() { values = append(values, "first") }()
	defer func() { values = append(values, "second") }()
	return
}
func deferArgument() (result int) { x := 1; defer func(v int) { result = v }(x); x = 2; return }
func deferClosure() (result int)  { x := 1; defer func() { result = x }(); x = 2; return }
func recoverKnown() (result string) {
	defer func() {
		if v := recover(); v != nil {
			result = fmt.Sprint(v)
		}
	}()
	panic("broken")
}
func cleanedAfterPanic() (cleaned bool) {
	defer func() { recover() }()
	defer func() { cleaned = true }()
	panic("fixture")
}
func scopedCleanup(count *int) { defer func() { *count = *count + 1 }() }

func main() {
	// Trace cleanup order
	{
		check(deferOrder() == "second,first", "defer order")
	}

	// Compare captured arguments
	{
		check(deferArgument() == 1, "argument evaluation")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The deferred argument retains the earlier value 1.

Call arguments are evaluated at registration. This differs from a closure that refers to x and reads it when the closure later runs.

For the recovered panics, predict which deferred calls run, in what order, and what each helper returns.

## Exercises

### Exercise 1: Trace cleanup order: predict an edited check

Copy worked example 1, change `check(deferOrder() == "second,first", "defer order")` to `check(deferOrder() == "second,first!", "defer order")` inside its check and predict whether it still passes; then restore it.

**Expected:** The edited check panics with `defer order` even though `deferOrder() == "second,first"` still holds.

**Verify:** Restoring `check(deferOrder() == "second,first", "defer order")` makes the check pass again with the worked observation: the observed order is second then first.

### Exercise 2: Compare captured arguments: diagnose an edited check

A careless edit rewrote the check in worked example 2 as `check(deferArgument() != 1, "argument evaluation")`. Explain the failure, then restore it.

**Expected:** The defective run panics with `argument evaluation`; after restoring `check(deferArgument() == 1, "argument evaluation")`, the deferred argument retains the earlier value 1.

**Verify:** The edited check fails with message `argument evaluation` for a state that `deferArgument() == 1` accepts.

### Exercise 3: Compare a closure read

Defer a closure reading x, then change x to 2.

**Expected:** The closure observes 2.

**Verify:** Your solution must keep `deferClosure() == 2` true. Control: changing `check(deferClosure() == 2, "closure read")` to `check(deferClosure() != 2, "closure read")` panics with message `closure read`; revert it.

### Exercise 4: Contain a deliberate panic

Panic with the known value broken inside a helper that recovers it.

**Expected:** The helper reports broken explicitly.

**Verify:** Your solution must keep `recoverKnown() == "broken"` true. Control: changing `check(recoverKnown() == "broken", "recovered value")` to `check(recoverKnown() != "broken", "recovered value")` panics with message `recovered value`; revert it.

## Common pitfalls and diagnosis

A defer inside a loop in a long-running function is the common resource leak: every deferred release waits until the outer function returns. Move the body into a helper so each iteration has its own cleanup boundary. The second mistake is recovering everywhere: catching all panics and returning a success-shaped value hides defects. Recover only at a deliberate boundary, and remember that deferred arguments are fixed at the defer statement.

## Progressive hints

### Hint for investigation 1: Trace cleanup order: predict an edited check

1. Restate the expected observation: The observed order is second then first.
2. Deferred calls form a stack. Which registration runs first when the function returns?
3. The deferred calls still produce second,first; the edited literal adds a !, so the comparison is false. The order is unchanged; the claim is wrong.

### Hint for investigation 2: Compare captured arguments: diagnose an edited check

1. Restate the expected observation: The deferred argument retains the earlier value 1.
2. Arguments to a deferred call are evaluated at the defer statement. What is x at that moment?
3. deferArgument returns 1 because its argument was evaluated at registration, so `!=1` is false and the check panics. The contract is that the earlier value is kept.

### Hint for investigation 3: Compare a closure read

1. Restate the expected observation: The closure observes 2.
2. A closure reads the variable itself when it runs. What is x when the function returns?
3. The closure refers to the variable.

### Hint for investigation 4: Contain a deliberate panic

1. Restate the expected observation: The helper reports broken explicitly.
2. recover returns the panic value only inside a deferred function during unwinding. What does the helper store?
3. The recovery boundary converts this deliberate fixture into inspectable evidence.

### Hint for investigation 5: Preserve cleanup during failure

1. Restate the expected observation: The cleanup marker is still set.
2. Unwinding runs every deferred call. Which marker is set before the recovery completes?
3. Stack unwinding runs deferred cleanup before the outer recovery returns.

### Hint for investigation 6: Transfer function-scoped cleanup

1. Restate the expected observation: All three markers are present after the loop.
2. Each helper call is its own function with its own deferred call. When does each marker run?
3. A helper creates a cleanup boundary per iteration.
