# go-009: Pointers, mutation and allocation lifetimes

## Level and prerequisites

Beginner. Allow about 90 minutes, then revisit the transfer case later. Prerequisites: go-008

## Learning objectives

Use pointers to share or update state on purpose, guard nil, and separate copying a value from mutating a target. Along the way, explain pointer, dereference, reachability; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A pointer contains the address of a value. Passing a pointer still copies the pointer value, but both copies identify the same target. This is useful when mutation is the intended contract and dangerous when callers expect isolation. Go's garbage collector keeps reachable objects alive, so returning a pointer to a local variable is valid; the compiler decides where storage must live. That does not make every pointer safe to use: nil has no target and dereferencing it panics. Ordinary Go pointers do not support arithmetic. Use a value receiver or an independent copy when shared mutation is unnecessary, and make optional pointer semantics explicit.

## Vocabulary and concepts

- **Pointer:** A value identifying another value in memory.
- **Dereference:** Reading or writing the target of a pointer.
- **Reachability:** Whether live program state still refers to an allocated object.

## Syntax anatomy and reasoning

&value obtains an address and *pointer dereferences it. In a type, *Point means a pointer to Point. new(T) returns a pointer to a zero T; it does not initialize maps or channels stored inside T. Selectors automatically follow a pointer to a struct, so p.X is convenient syntax for field access through p. A nil check guards dereference only when no unsynchronized writer can change the state between those operations.

## Worked example / walkthrough

### Worked example 1: Mutate through a pointer

Create an integer 4 and increment it through a helper receiving its address.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func increment(p *int) { *p = *p + 1 }
func seven() *int      { n := 7; return &n }
func setIfPresent(p *int, v int) bool {
	if p == nil {
		return false
	}
	*p = v
	return true
}

func main() {
	// Mutate through a pointer
	{
		n := 4
		increment(&n)
		check(n == 5, "pointer mutation")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The caller value becomes 5.

The helper changes the shared target, not the caller variable that stores the pointer. The mutation contract must be visible at the call site.

### Worked example 2: Return a live value

Return a pointer to a local integer initialized to 7.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

func increment(p *int) { *p = *p + 1 }
func seven() *int      { n := 7; return &n }
func setIfPresent(p *int, v int) bool {
	if p == nil {
		return false
	}
	*p = v
	return true
}

func main() {
	// Mutate through a pointer
	{
		n := 4
		increment(&n)
		check(n == 5, "pointer mutation")
	}

	// Return a live value
	{
		p := seven()
		check(*p == 7, "returned pointer")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The returned pointer remains valid and reads 7.

Go extends storage lifetime as needed. Stack-versus-heap placement is an implementation decision and should not be guessed from the lexical block alone.

## Exercises

### Exercise 1: Mutate through a pointer: change one input

Copy worked example 1 into a scratch pad and change `n := 4` to `n := 5`. Before running, predict which check fails and which value it now sees; then run it and restore the original line.

**Expected:** The changed run panics with `pointer mutation` because `n == 5` no longer holds. Restoring the original line brings back the worked observation: the caller value becomes 5.

**Verify:** Compare your written prediction with the panic message `pointer mutation` and name the value that made `n == 5` false. After restoring the input, the program must print its success line again.

### Exercise 2: Return a live value: diagnose an edited check

A careless edit changed the check in worked example 2 so that it reads `check(*p != 7, "returned pointer")`. Run worked example 2 with that line, explain why the edited check now fails for the same program state, and restore it.

**Expected:** Before the repair the program panics with `returned pointer`; after it the line reads `check(*p == 7, "returned pointer")` again and the returned pointer remains valid and reads 7.

**Verify:** Keep the failing and the repaired runs. Explain why the edited check rejects the same program state that `*p == 7` accepts.

### Exercise 3: Guard absence

Represent an optional integer with a nil pointer and inspect it without dereferencing.

**Expected:** The pointer is absent.

**Verify:** Keep a check equivalent to `p == nil`. As a control, change `check(p == nil, "nil pointer")` to `check(p != nil, "nil pointer")` inside that check: it must panic with `nil pointer`, which shows the check can fail. Restore it.

### Exercise 4: Allocate a zero target

Use new(int) and compare pointer presence with its stored value.

**Expected:** The pointer is non-nil and its target is 0.

**Verify:** Keep a check equivalent to `p != nil && *p == 0`. As a control, change `check(p != nil && *p == 0, "new zero")` to `check(p == nil && *p == 0, "new zero")` inside that check: it must panic with `new zero`, which shows the check can fail. Restore it.

### Exercise 5: Separate copy and target

Copy the integer behind a pointer, then change the original target.

**Expected:** The copied integer remains 3 while the target becomes 9.

**Verify:** Keep a check equivalent to `copied == 3 && n == 9`. As a control, change `n := 3` to `n := 4`: the run must panic with `copy target`. Restore the line before continuing.

### Exercise 6: Transfer an optional update

Implement setIfPresent so a nil pointer is a harmless no-op and a present pointer changes.

**Expected:** The absent call returns false; the present value becomes 8.

**Verify:** Keep a check equivalent to `setIfPresent(&n, 8) && n == 8`. As a control, change `check(setIfPresent(&n, 8) && n == 8, "present update")` to `check(setIfPresent(&n, 9) && n == 8, "present update")` inside that check: it must panic with `present update`, which shows the check can fail. ## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
