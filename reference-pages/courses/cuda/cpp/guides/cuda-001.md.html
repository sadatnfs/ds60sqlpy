Purpose, vocabulary and mental model#

A CPU is optimized to make progress on a comparatively small number of complicated instruction streams. A GPU spends more of its resources on throughput across many pieces of work. This is a design distinction, not a rule that the GPU wins. A dependency means that one result must exist before another calculation can start. Pixel brightness updates have independent destinations; a running account balance has a dependency between successive balances. There can still be a parallel prefix algorithm for that balance, but changing the algorithm is real work. Include loading data, launching kernels and returning results when deciding whether acceleration helps a person waiting for an answer.

Mathematical contract#

Tnew=Tserial+Tparallels+TtransferT_{\mathrm{new}}=T_{\mathrm{serial}}+\frac{T_{\mathrm{parallel}}}{s}+T_{\mathrm{transfer}}

Times use the same units; s is the speedup of only the parallel portion. Launch and other overhead must also be included when present.

Worked example 1: trace the mechanism#

Suppose an application spends 20 seconds parsing and 80 seconds transforming pixels. An imagined GPU makes the transform ten times faster and adds 4 seconds of transfers. The new time is 20+8+4=3220 + 8 + 4 = 32 seconds, so the application speedup is 3.125. The tenfold kernel improvement is not the application improvement. Even an infinitely fast transform leaves 24 seconds under these assumptions.

The complete CPU model below intentionally models only the named arithmetic, layout, dependency or capability decision. It does not model GPU scheduling, caches, instruction timing or device memory visibility.

cpu = 20 + 80
gpu = 20 + 80 / 10 + 4
assert gpu == 32
assert cpu / gpu == 3.125
assert 100 / 40 == 2.5
print({"CPU_seconds": cpu, "modeled_GPU_seconds": gpu, "speedup": cpu / gpu})

Expected observation: Every assertion succeeds. A representative CPU output is:

{'CPU_seconds': 100, 'modeled_GPU_seconds': 32.0, 'speedup': 3.125}

Tiny floating-point display differences across platforms are acceptable only where the explicit assertions use a tolerance; integers, shapes and ordering must still satisfy their exact contracts. A printed hypothetical duration is a model output, not a measured GPU benchmark.

Worked example 2: change a meaningful condition#

For one tiny request, suppose CPU arithmetic costs 2 microseconds, while GPU submission and transfers cost 30 microseconds before arithmetic. A 0.2 microsecond kernel gives 30.2 microseconds end to end. Batching 1,000 independent requests may amortize overhead, but it changes waiting time and memory usage. Neither result follows from a core count.

Before applying this example to your own program, write down which inputs are read, which result is produced, and the condition that makes the comparison valid. Keep the original case as a regression check when changing a boundary.

Common mistakes and diagnosis#

A tempting but incorrect claim in this chapter is: more GPU cores imply every program becomes faster.

For the concrete failure exercise, a report compares a 2 ms CPU request against a 0.1 ms kernel and claims 20 times faster. Identify the missing observations. Preserve the original input and the stage where behavior diverged. Compare with the CPU model or dependency diagram before changing hardware configuration. A compiler result, synthetic timing model, profiler counter and returned numeric answer support different claims. Record unavailable hardware honestly.
