## Purpose, vocabulary and mental model

The Container Network Interface, or CNI, is a plugin interface used in container networking. In Kubernetes, the chosen network implementation prepares Pod interfaces and connectivity according to cluster configuration. CNI is an interface and ecosystem, not one universal packet-forwarding algorithm.

Cross-node Pod traffic can use routed networks, encapsulation overlays or other implementation-specific mechanisms. An overlay wraps an inner packet in an outer packet so the underlying network can transport it between nodes. Encapsulation consumes header space, affecting the maximum transmission unit, or MTU, available to the inner traffic.

A small request may succeed while a large payload fails when MTU discovery, fragmentation or policy is misconfigured. This is different from a Service selector problem. Diagnose with bounded traffic and actual implementation evidence rather than changing cluster networking from a generic tutorial.

### Key terms

- **Container Network Interface:** The plugin specification the container runtime calls to attach a Pod's network namespace to the network and assign its address.
- **Overlay network:** A virtual network that carries Pod traffic between nodes inside outer packets addressed from node to node.
- **Encapsulation:** Wrapping a Pod packet inside an outer packet with node addresses, which adds header bytes to every packet.
- **Maximum transmission unit:** The largest packet a link carries without fragmentation. Encapsulation reduces the space left for the inner packet.
- **Path MTU discovery:** How a sender learns the smallest MTU on a path. If its error messages are blocked, large packets fail while small ones still work.

## Mechanism and field-by-field reasoning

Separate the Pod-facing interface, node routing or overlay endpoint, underlay network and destination Pod interface. The control plane may show Ready Pods while the cross-node data path is broken. CNI setup failures can also prevent Pod sandbox creation before the app starts.

The synthetic topology uses two nodes and two Pod subnets to make the hop sequence visible. It does not claim that every CNI assigns per-node CIDRs in the same way. Optional live observations require the exact prepared CNI and permissions; the course does not install or replace network plugins.

## Trace the request or control path

```text
PodA -> nodeA Pod interface -> route/encapsulation -> underlay -> nodeB -> PodB
inner payload + overlay headers must fit the effective path MTU
```

Read the first line as two layers. PodA and PodB addresses ride inside; when an overlay encapsulates, node addresses such as 192.0.2.10 and 192.0.2.11 carry the packet across the underlay. The second line is the budget: every encapsulation header is paid for out of the same path MTU, so large payloads are the first to fail.

### Worked example 2: Reason about header budget

This arithmetic is synthetic.

```python
underlay_mtu = 1500
overhead = 50
print(underlay_mtu - overhead)
```

**Expected observation:** 1450 bytes before further constraints; actual overhead depends on the implementation.

## Six progressive exercises

### Exercise 1: Distinguish CNI interface and network implementation.

**Expected evidence:** A plugin contract versus a concrete routing/policy system.

**Progressive hint:** One is a specification for how a runtime asks for an interface; the other is software that builds routes. Which is which?

### Exercise 2: Label inner and outer addresses.

**Expected evidence:** Pod endpoints inside, node transport endpoints outside in the overlay example.

**Progressive hint:** In worked example 1, find the header added on node-a and removed on node-b. Its addresses are the outer pair.

### Exercise 3: Draw a two-node request path.

**Expected evidence:** Pod interfaces, node forwarding and underlay hops are explicit.

**Progressive hint:** Start at PodA's interface and do not skip the node. Each hand-off between namespaces or machines is one arrow.

### Exercise 4: Diagnose small-request success with large-payload failure.

**Expected evidence:** Investigate MTU and path behavior in addition to app limits.

**Progressive hint:** Small and large requests take the same route. What changes with payload size along that route?

### Exercise 5: Explain why Ready does not prove cross-node reachability.

**Expected evidence:** Readiness may be a local check with a narrower path.

**Progressive hint:** Where does the kubelet send the readiness request from, and how far does that packet travel?

### Exercise 6: Plan a CNI-specific qualification without replacing the plugin.

**Expected evidence:** Read configuration, state the implementation and run only owned bounded probes.

**Progressive hint:** Name the plugin and version from the receipt first, then choose reads and probes that leave its configuration untouched.

## Diagnosis, failure boundaries and common mistakes

The MTU symptom in Exercise 4 is confusing because health checks keep passing: small probe responses fit, while a large JSON body or a TLS certificate chain stalls. Do not raise application timeouts or blame the server first. Compare one small and one large bounded request between Pods on different nodes and see whether size alone flips the result. Another error is treating CNI as a product name. Two clusters can both say CNI and use different routing, encapsulation and policy engines, so advice copied from one may be wrong for the other. Never replace or reconfigure the plugin to test a theory; ask the operator for its documented mode and MTU.
