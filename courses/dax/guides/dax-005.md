## The question and the mechanism

Distinguish scalar expressions, table expressions and named model measures in a readable query.

A DAX query returns tables. EVALUATE introduces a table expression; a scalar such as SUM(Sales[NetAmount]) is not itself a result table. ROW creates one named row from scalar expressions, while SELECTCOLUMNS projects names and expressions over rows of an input table. This shape distinction explains many apparent syntax problems before a learner memorizes more functions.

A column reference such as Sales[NetAmount] identifies a column. A measure reference such as [NetRevenue] requests a scalar evaluation in the current context. Double quotes delimit text such as output labels. Single quotes delimit table names when needed, as in 'Date'[Date]. Square brackets delimit identifiers; they are not Python list indexing.

Do not infer ordering from a table expression's internal implementation. TOPN chooses a set according to ordering criteria, while an outer ORDER BY specifies the presentation of the returned query table. Use a unique tie-breaker when a stable top set matters. Choosing a table and presenting its rows are separate obligations.

## Vocabulary and expression anatomy

The first query uses a label/value pair in ROW. The second takes the first two unique SaleID values, projects them as Line and Amount, and orders the final table by Line. These are small inspectable query objects; they do not persist calculated tables in the semantic model.

Concepts to explain in your own words: **EVALUATE**, **ROW**, **SELECTCOLUMNS**, **TOPN**, **ORDER BY**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: A scalar wrapped as a table

**Starting context:** No filters; one named scalar in a one-row query result.

```dax
EVALUATE ROW ( "RevenueUSD", [NetRevenue] )
```

**Context trace:**

1. SUM produces one scalar in the current context.
2. ROW assigns that scalar the output name RevenueUSD.
3. EVALUATE returns the one-row table, not a stored model column.

**Hand-derived worked-reference result:**

| RevenueUSD |
| --- |
| 187 |

Output aliases belong to this query. Renaming RevenueUSD does not rename the NetRevenue measure or change its arithmetic.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: A projected two-row result

**Starting context:** No filters; smallest two unique SaleID values, then explicit output ordering.

```dax
EVALUATE
SELECTCOLUMNS ( TOPN ( 2, Sales, Sales[SaleID], ASC ), "Line", Sales[SaleID], "Amount", Sales[NetAmount] )
ORDER BY [Line] ASC
```

**Context trace:**

1. SaleID is unique, so the two smallest keys select exactly S1 and S2.
2. SELECTCOLUMNS evaluates each projected expression for its input row.
3. The outer ORDER BY makes the displayed sequence S1 then S2.

**Hand-derived worked-reference result:**

| Line | Amount |
| --- | --- |
| S1 | 20 |
| S2 | 4 |

The result is two rows because the input selection has two rows. It is not a sum and not a measure definition. The amount column retains each line's value.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

## Progressive hints

1. Identify which argument needs table shape.
2. Add a new output-name/expression pair.
3. Selection and final ordering both need a direction.
4. A result alias is not a persisted measure.
5. Rows at the cutoff can share the ordering value.
6. Ask when the rows are produced and retained.
