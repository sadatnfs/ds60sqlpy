## The question and the mechanism

Distinguish a positional row window from a calendar interval and identify the ordering contract.

A positional window selects rows according to an ordering and partition definition. Two rows do not automatically mean two days: our first two sales lines share the same order date. A calendar window answers a date-membership question, while a positional window answers a row-location question. Choose the mechanism that matches the requested unit.

WINDOW can describe absolute bounds from the start or end of a relation, or relative bounds around a current row. INDEX selects a particular position; OFFSET selects a position relative to the current row. Relative forms need an unambiguous current-row match. ORDERBY, PARTITIONBY and MATCHBY describe different aspects of that contract and should not be treated as decorative options.

The worked queries use absolute bounds with an explicit relation and unique SaleID ordering, avoiding hidden visual-axis assumptions. This keeps the first and last two rows inspectable. A running comparison over real dates should order by a date plus a unique tie-breaker, and a customer-specific window should state its partition. Do not rely on an engine-selected extra ordering column without reviewing what it means.

## Vocabulary and expression anatomy

ABS makes the bounds positions within the explicitly supplied relation. Positive positions count from the start; negative positions count from the end. ALL supplies the SaleID/NetAmount relation for the named whole-model example. ORDERBY defines its order and the outer ORDER BY defines the returned table's display.

Concepts to explain in your own words: **WINDOW**, **INDEX**, **OFFSET**, **ORDERBY**, **absolute versus relative**.

## Model and context contract

The ordinary star follows Product → Sales, Customer → Sales and Date → Sales through OrderDate. The ShipDate relationship is inactive unless a case explicitly activates it. Filters flow from the one side to the many side. Additional analytical tables have only the relationships declared in their named model; a similar column name does not create a relationship.

```text
Product (one)  --> Sales (many) <-- Customer (one)
                       ^
                       | active OrderDate
                    Date (one)
                       | inactive ShipDate
                       +------> Sales
```

All amounts in ordinary Sales are USD after the line discount, before tax and returns. The Date fixture is complete for 2024 and 2025; a short result table is a selected slice, not the whole calendar. JSON `null` in the worked-results sidecar means DAX BLANK, not the text "null".

## Worked cases

### Case A: First two positions

**Starting context:** Whole clean-model Sales relation ordered by unique SaleID; absolute positions 1 through 2.

```dax
EVALUATE SELECTCOLUMNS ( WINDOW ( 1, ABS, 2, ABS, ALL ( Sales[SaleID], Sales[NetAmount] ), ORDERBY ( Sales[SaleID], ASC ) ), "Line", Sales[SaleID], "Amount", Sales[NetAmount] )
ORDER BY [Line]
```

**Context trace:**

1. The first two keys are S1 and S 2.
2. Both rows belong to order 101 and date 2024-01-02.
3. The window contains two lines, not two distinct dates; amounts are 20 and 4.

**Hand-derived worked-reference result:**

| Line | Amount |
| --- | --- |
| S1 | 20 |
| S2 | 4 |

A two-row average here would average order lines. It would not represent average revenue for two calendar days.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: Last two positions

**Starting context:** Same explicit relation and ordering; last two absolute positions.

```dax
EVALUATE SELECTCOLUMNS ( WINDOW ( -2, ABS, -1, ABS, ALL ( Sales[SaleID], Sales[NetAmount] ), ORDERBY ( Sales[SaleID], ASC ) ), "Line", Sales[SaleID], "Amount", Sales[NetAmount] )
ORDER BY [Line]
```

**Context trace:**

1. Position-1 identifies S8; position-2 identifies S7.
2. The inclusive window includes both rows.
3. Their amounts total 56, but the relation contract remains line-based.

**Hand-derived worked-reference result:**

| Line | Amount |
| --- | --- |
| S7 | 20 |
| S8 | 36 |

The result happens to align with two successive sale dates. That coincidence does not make the operator a date-window function.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case C: INDEX chooses one absolute position

**Starting context:** One unpartitioned relation ordered by the unique SaleID; no outer row required.

```dax
EVALUATE INDEX ( 1, ALL ( Sales[SaleID], Sales[NetAmount] ), ORDERBY ( Sales[SaleID], ASC ) )
```

**Context trace:**

1. ALL exposes all eight line identities and amounts.
2. The declared unique order starts with S1.
3. Absolute position one therefore returns S1 and amount 20.

**Hand-derived worked-reference result:**

| SaleID | NetAmount |
| --- | --- |
| S1 | 20 |

INDEX selects a position in the declared order. Position zero or a position beyond this eight-row relation would return an empty table.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case D: OFFSET identifies a previous row

**Starting context:** The outer context identifies S4; the relation contains every SaleID in ascending unique order.

```dax
EVALUATE CALCULATETABLE ( OFFSET ( -1, ALL ( Sales[SaleID] ), ORDERBY ( Sales[SaleID], ASC ) ), Sales[SaleID] = "S4" )
```

**Context trace:**

1. The outer filter supplies exactly one current SaleID: S4.
2. The explicit ALL relation permits movement outside that current-row selection.
3. Moving one position backward reaches S3; a backward move from S1 would be empty.

**Hand-derived worked-reference result:**

| SaleID |
| --- |
| S3 |

OFFSET needs an unambiguous current-row contract. Adding columns, partitions or ties can change matching requirements; specify MATCHBY where identity differs from sort columns.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

2. The preceding SaleID in this declared order is S 3.
3. Separate partition membership from within-partition order.
4. Several lines share amount 20.
5. The requested relative position can lie outside the partition.
6. Three observations can span unequal elapsed time.
