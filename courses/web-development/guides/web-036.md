# web-036: Functions, contracts, closures and reusable logic

## Level and prerequisites

Beginner; allow about 90 minutes, with extra time for independent practice. Direct prerequisites: `web-035`

## Learning objectives

Build reusable duration calculation and display functions. Explain when a closure improves a transformation. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

A function gives a named operation explicit inputs and an output. A useful contract states accepted values, returned meaning and failure behavior. Type declarations communicate and enforce part of that contract at runtime, but a positive duration requirement needs an explicit value check in addition to an int type. Small pure functions are easy to test because their result depends on inputs rather than hidden global state.

A closure is a function value that can be passed to another function. Arrow functions capture variables from their surrounding scope by value automatically, while ordinary anonymous functions use an explicit use clause for capture. Avoid hidden mutable dependencies when a simple parameter would make the relationship clearer.

## Syntax anatomy and mechanism

Separate formatting from calculation so each can be tested independently. Return values are not the same as echo output. A function that echoes a result may be difficult to compose, while a function that returns a value lets a caller choose how to display it. Use exceptions for invalid inputs when the contract treats them as errors, and document predictable alternate results when absence is normal.

## Classroom execution and offline inputs

Choose the **PHP CLI** worker in the classroom. The pad is staged as `main.php` and executes as a bounded Linux process, with prepared PHP and PDO SQLite. Write `<?php` at the beginning; a pure PHP file needs no closing tag. Output appears as text. PHP-generated HTML is escaped output here, not automatically injected into a browser. No host PHP installation is required for the Docker route.

The supplied requests, identities, sessions and database fixtures are synthetic local inputs. CLI runs are fresh processes, not persistent HTTP requests. A dictionary that represents a cookie or request is not a real browser cookie. SQLite examples use an in-memory database and do not connect to the classroom PostgreSQL service. Network servers, uploads, mail, Composer downloads and production credentials are outside this pad's contract. Later delivery lessons provide an explicitly separate loopback server lab. A successful function test does not qualify that server integration.

## Worked example / walkthrough

### Worked example 1: A typed calculation

The range check complements the type declaration.

```php
function doubleMinutes(int $minutes): int {
  if ($minutes < 0) throw new InvalidArgumentException('Negative minutes');
  return $minutes * 2;
}
```

**Expected observation:** A valid integer produces a doubled integer; a negative value fails.

### Worked example 2: A small closure

The operation is passed as data to a transformation.

```php
$doubled = array_map(fn(int $value): int => $value * 2, [10, 20]);
```

**Expected observation:** The result is [20, 40].

## Six progressive exercises

### Exercise 1: Explain the difference between returning and echoing a value.

**Expected evidence:** Returning supplies data to the caller; echo writes output as a side effect.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Add a value-range guard to a typed function.

**Expected evidence:** The function rejects invalid integers even though they satisfy the declared type.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Build reusable duration calculation and display functions.

**Expected evidence:** Calculations can be tested without capturing output, then formatted at the boundary.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Diagnose a result depending on an undocumented global.

**Expected evidence:** Pass the dependency explicitly or isolate the stateful boundary.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Test zero, a normal value and a negative input.

**Expected evidence:** Each follows the stated contract and the failure is intentional.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain when a closure improves a transformation.

**Expected evidence:** A short callback can express a local operation while keeping its inputs and captured context clear.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not hide output, database access and validation inside one large function merely to reduce file count. A type declaration cannot enforce every domain rule. Keep function names aligned with the actual responsibility.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.

## Retrieval, transfer and next steps

Close the worked answers and explain function, parameter, return type without using their names as definitions. Reconstruct the central example from a blank pad or worksheet. Use one new value, one empty or missing case and one adversarial or unusual boundary. State which result would disprove your explanation. When a behavior belongs to the browser, observe it in the browser; when it belongs to an HTTP server, keep that evidence separate from a CLI simulation.

Before moving on, keep a short learning record: your prediction, source revision, actual result, explanation and unresolved limitation. Revisit a direct prerequisite if you can reproduce output but cannot explain the mechanism. The path has milestones, not a fixed daily schedule, and a saved completion marker is a personal progress record rather than a professional certification.
