# web-057: A real local HTTP lab: sessions, forms and persistent notes

## Level and prerequisites

Advanced; allow about 150 minutes, with extra time for independent practice. Direct prerequisites: `web-056`

## Learning objectives

Run the owned lab and create one synthetic note through the browser. Explain which properties this local server has not qualified. Explain the mechanism, a normal case and a failure case in your own words, then retain source and observations separately.

## Purpose, vocabulary and mental model

The earlier PHP pads isolated language and application logic. A real HTTP lab adds a browser, request headers, cookies, server process and persistent storage. Each boundary introduces behavior that a pure function cannot prove. The maintained optional fixture runs a local PHP development server in its own Linux container and binds its published port to host loopback. It is a learning server, not an internet deployment.

The fixture stores synthetic notes under an anonymous browser session. That demonstrates session continuity and separation, not verified user identity. A session cookie carries an identifier; the server stores the session and a random owner key. Prepared statements store notes in SQLite. A form includes a CSRF token, the server validates it before writing, and successful POST handling redirects to a GET page. Source, database and session state have distinct lifetimes.

## Worked example / walkthrough

### Worked example 1: Prepare the owned lab

Run from a new learner copy of the fixture after reading its README.

```bash
docker compose --project ds60-web-study up --build --detach
curl --fail http://127.0.0.1:18088/health
```

**Expected observation:** An actual bounded HTTP request returns the lab's health response.

### Worked example 2: Observe the redirect

The browser network panel exposes the real protocol sequence.

```text
GET / -> HTML form + session cookie
POST /notes with valid token -> 303 Location: /
GET / -> stored synthetic note
```

**Expected observation:** The POST and follow-up GET are separate requests.

## Six progressive exercises

### Exercise 1: Draw the lifecycle from browser cookie to server session to stored note.

**Expected evidence:** The cookie identifies session state; the session supplies an owner key and CSRF token; the database stores the owned note.

**Progressive hint:** Trace the smallest example before editing. Name which values are source and which are observations.

### Exercise 2: Inspect the real Content-Type and redirect status.

**Expected evidence:** Record actual response headers instead of inferring them from PHP source.

**Progressive hint:** Change only the named feature. Compare with the unchanged example and explain any unaffected behavior.

### Exercise 3: Run the owned lab and create one synthetic note through the browser.

**Expected evidence:** The note survives a page reload and appears after a successful POST-redirect-GET sequence.

**Progressive hint:** Sketch the structure or data contract first. Reuse the mechanism from the examples without copying the reference.

### Exercise 4: Submit a request with a missing or wrong CSRF token.

**Expected evidence:** The server returns a rejection and inserts no note.

**Progressive hint:** Keep the failing input. Identify the first layer where the observed result differs from the intended contract.

### Exercise 5: Stop and resume the lab without deleting volumes.

**Expected evidence:** The same browser session can recover its notes while the named data and session volumes remain.

**Progressive hint:** Predict the boundary before running it. Add an explicit check or manual observation that would detect a regression.

### Exercise 6: Explain which properties this local server has not qualified.

**Expected evidence:** It does not establish production TLS, verified accounts, multi-instance concurrency, internet hardening or high availability.

**Progressive hint:** Explain your choice to someone who has not seen the code. Include one limitation and the evidence needed to remove it.

## Debugging and common mistakes

Do not start a second copy on an occupied port or delete an unrelated project to free it. A health response proves the process answered, not that note creation, CSRF rejection and persistence work. Anonymous session ownership must never be described as a production login system.

Keep the source that produced the failure, the relevant input or viewport, and the actual observation. Repair one cause and repeat the original case before adding a new one. A browser can recover malformed HTML, silently ignore a CSS declaration or display a plausible layout with the wrong reading order. PHP can produce correct-looking text while missing an invalid-input branch. A successful parse or an initial reference marker therefore answers a narrower question than the full lesson objective.
