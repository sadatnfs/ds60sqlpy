# asm-005: Stable global logistic likelihood in Spark SQL

Tutorial mode. Stage: intermediate. Direct prerequisites: `asm-002`, `clp-007`.

## Starting point and result

A binary response is one or zero. Logistic regression models its probability with a linear predictor, not a linear probability: \(z_i=\beta_0+x_i\beta_1\) and \(p_i=1/(1+\exp(-z_i))\). This chapter constructs a global objective entirely from Spark SQL columns. There is no Python function invoked for each row. The tiny fixture is deliberately extreme so that numerical behavior is observable before an optimizer magnifies it.

## Mechanism: logits avoid unstable probability logarithms

The Bernoulli negative log likelihood is \(-y_i\log p_i-(1-y_i)\log(1-p_i)\). Directly computing these logarithms can encounter zero after rounding. Algebra gives \(\ell_i=\operatorname{softplus}(z_i)-y_i z_i\), where

\[\operatorname{softplus}(z)=\max(z,0)+\log(1+\exp(-|z|)).\]

The exponential argument is never positive. `log1p` computes the logarithm accurately when its argument is small. A Spark `Column` is an expression describing work, not an array of values on the driver. Combining `greatest`, `abs`, `exp` and `log1p` builds a plan; `agg(...).first()` executes it and returns one bounded result row. Avoid substituting Python `max` for the SQL expression constructor.

With nonnegative observation weights, the objective is \(L=\sum_i w_i\ell_i\). Weight meanings matter. Frequency weights reproduce repeated observations; survey weights and importance weights need their own inferential justification. An optimizer may minimize a weighted mean or a weighted sum, but the penalty and reported uncertainty must use the same declared convention.

## Worked case: confident, correctly classified extremes

The fixture includes logits -1000 with label zero and +1000 with label one. A naive positive-logit exponential overflows, while the stable formula returns finite loss zero to floating-point precision. This is not a claim that the exact probability equals one. The omitted tail is smaller than the representation can distinguish. Check both finiteness and the serial oracle, because replacing every nonfinite answer by zero would also appear to pass an optimistic example.

The SQL reduction is compared with a separate standard-library calculation using `math.fsum`. This tests agreement between two implementations of the same objective. It does not establish that real observations satisfy the model. The expected evidence includes total loss, weight sum and absolute oracle error.

## Worked case: weights change the target

The row with logit -2 and label one receives weight two; its relatively large surprise contributes twice. Other rows have weights one, one-half and three. The total weight is 7.5, while the number of rows is five. The program also computes the unweighted objective and asserts that it differs. Dividing by five produces a different scale from dividing by 7.5. Neither changes an unpenalized minimizer when the denominator is constant, but either changes the effective strength of an unchanged regularizer.

Before adapting this fixture, reject labels outside zero and one, negative weights, missing features and nonfinite predictors. Do not silently let SQL ignore null losses: a lower objective could then mean fewer observations rather than a better fit.

## Failure diagnosis

An infinite loss for an intentionally misclassified extreme can be mathematically plausible for an infinite logit; the fixture uses finite logits so its expected loss remains finite. A NaN often means invalid input or an operation such as infinity minus infinity. A mismatch only after adding weights suggests a normalization error. Examine the full expression and declared row count before blaming partitions.

## Interview discussion

**Why prefer native column expressions to a Python UDF?** Spark can inspect their structure for planning and execute them inside its JVM engine. That improves transparency and often performance; it does not make arbitrary mathematics automatically differentiable.

**Does logistic regression require a sigmoid in the loss?** No. The stable logits form computes the identical Bernoulli objective without first rounding probabilities to zero or one. A sigmoid is still useful for prediction and the analytic gradient.

## Complete reproducible program

Run this complete source in its declared prepared Spark profile. The fixture is tiny, deterministic and offline. Scala sources are compiled before execution; Python sources use the prepared PySpark environment. These are worked tutorials with no hidden solutions or exams. Runtime: `spark-local-python`.

```python
from __future__ import annotations

import json
import math


def session(name):
    from pyspark.sql import SparkSession

    spark = (
        SparkSession.builder.master("local[2]")
        .appName(name)
        .config("spark.ui.enabled", "false")
        .config("spark.driver.host", "127.0.0.1")
        .config("spark.driver.bindAddress", "127.0.0.1")
        .config("spark.sql.shuffle.partitions", "2")
        .config("spark.sql.adaptive.enabled", "false")
        .config("spark.sql.ansi.enabled", "true")
        .config("spark.sql.session.timeZone", "UTC")
        .getOrCreate()
    )
    if spark.version != "4.0.1":
        spark.stop()
        raise RuntimeError("This worked reference is qualified for Spark 4.0.1")
    spark.sparkContext.setLogLevel("ERROR")
    return spark


def softplus(z):
    return max(z, 0.0) + math.log1p(math.exp(-abs(z)))


def sigmoid(z):
    return 1.0 / (1.0 + math.exp(-z)) if z >= 0 else math.exp(z) / (1.0 + math.exp(z))


def run(spark):
    from pyspark.sql import functions as F

    rows = [
        (-1000.0, 0.0, 1.0),
        (1000.0, 1.0, 1.0),
        (-2.0, 1.0, 2.0),
        (0.0, 0.0, 0.5),
        (2.0, 1.0, 3.0),
    ]
    frame = spark.createDataFrame(rows, "z double, y double, w double")
    loss = F.col("w") * (
        F.greatest(F.col("z"), F.lit(0.0)) + F.log1p(F.exp(-F.abs("z"))) - F.col("y") * F.col("z")
    )
    expected = math.fsum(w * (softplus(z) - y * z) for z, y, w in rows)
    actual = frame.agg(F.sum(loss).alias("loss"), F.sum("w").alias("weight")).first()
    assert math.isfinite(actual.loss) and math.isclose(actual.loss, expected, rel_tol=1e-13)
    assert actual.weight == 7.5
    wrong = math.fsum(softplus(z) - y * z for z, y, w in rows)
    assert not math.isclose(wrong, expected)
    assert softplus(1000.0) == 1000.0 and softplus(-1000.0) == 0.0
    print(
        json.dumps(
            {
                "weighted_loss": actual.loss,
                "weight_sum": actual.weight,
                "unweighted_loss": wrong,
                "serial_error": abs(actual.loss - expected),
            }
        )
    )


if __name__ == "__main__":
    spark = session("asm-005")
    try:
        run(spark)
    finally:
        spark.stop()
```
