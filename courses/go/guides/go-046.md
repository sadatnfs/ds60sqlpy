# go-046: Admission decisions, webhook contracts and failure policy

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-045

## Learning objectives

Write an admission decision function that validates exact boundaries, echoes the request UID and has no side effects in dry run. Along the way, explain admission, failure policy, dry run; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

Admission evaluates an API request after authentication and authorization and before persistence. Mutating admission can change an object; validating admission can accept or reject it. A webhook introduces a network dependency into control-plane writes, so latency, availability and failurePolicy have real consequences. Fail-open can preserve availability while allowing objects that were not checked; fail-closed can enforce policy while blocking writes during an outage. Choose deliberately and test recovery. AdmissionReview responses must correspond to the request UID and use the supported API version. A validation decision is not permission to perform unrelated side effects, especially for dry-run requests.

## Vocabulary and concepts

- **Admission:** Policy evaluation before an API object is persisted.
- **Failure policy:** Whether a failed policy service permits or blocks the API request.
- **Dry run:** A request evaluated without persisting its intended change.

## Syntax anatomy and reasoning

Separate the pure policy from the HTTP and AdmissionReview adapter. The fixture validates a replica range and preserves a synthetic request UID in its decision. A real adapter needs bounded body parsing, TLS, a configured timeout, correct response schema and no hidden external side effects. Rejection messages should identify the field and rule without exposing credentials or excessive source content.

## Worked example / walkthrough

### Worked example 1: Accept a valid range

Validate replica count 3 under maximum 5.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Decision struct {
	UID         string
	Allowed     bool
	Reason      string
	SideEffects int
}

func admit(uid string, replicas, maximum int, dryRun bool) Decision {
	d := Decision{UID: uid}
	if uid == "" {
		d.Reason = "request UID required"
		return d
	}
	if replicas < 0 || replicas > maximum {
		d.Reason = "replicas outside allowed range"
		return d
	}
	d.Allowed = true
	if !dryRun {
		d.SideEffects++
	}
	return d
}

func main() {
	// Accept a valid range
	{
		d := admit("r1", 3, 5, false)
		check(d.Allowed && d.UID == "r1", "allow")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The decision allows the request.

The pure rule is independently testable. The HTTP adapter still needs protocol and transport validation.

### Worked example 2: Reject a negative value

Validate replica count -1.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Decision struct {
	UID         string
	Allowed     bool
	Reason      string
	SideEffects int
}

func admit(uid string, replicas, maximum int, dryRun bool) Decision {
	d := Decision{UID: uid}
	if uid == "" {
		d.Reason = "request UID required"
		return d
	}
	if replicas < 0 || replicas > maximum {
		d.Reason = "replicas outside allowed range"
		return d
	}
	d.Allowed = true
	if !dryRun {
		d.SideEffects++
	}
	return d
}

func main() {
	// Accept a valid range
	{
		d := admit("r1", 3, 5, false)
		check(d.Allowed && d.UID == "r1", "allow")
	}

	// Reject a negative value
	{
		d := admit("r2", -1, 5, false)
		check(!d.Allowed && d.Reason != "", "negative")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The decision denies it with a reason.

Field-specific validation gives an actionable failure instead of an unexplained generic denial.

## Common pitfalls and diagnosis

A webhook that fails closed and then goes down blocks every write it covers, sometimes including the writes needed to repair it; one that fails open silently admits unchecked objects. Choose failurePolicy per webhook deliberately, scope it with selectors and keep its timeout short. A webhook with side effects must honor dryRun, and its response must echo the request UID.

General compiler, panic and error diagnosis is in the [study guide](../STUDY-GUIDE.md#diagnose-a-failure).

## Progressive hints

### Hint for investigation 1: Accept a valid range: change one input

1. Restate the expected observation: The decision allows the request.
2. 3 lies within 0 to 5. What are Allowed and UID?
3. The request UID is now r2, so the decision echoes r2 and `d.UID=="r1"` fails. Admission still allows the request; the identity changed.

### Hint for investigation 2: Reject a negative value: diagnose an edited check

1. Restate the expected observation: The decision denies it with a reason.
2. -1 is outside the range. Which reason is set?
3. A denied decision carries a reason, so `d.Reason==""` is false and the check fails. Restore `!=""` so the test requires an explanation.

### Hint for investigation 3: Check the exact upper boundary

1. Restate the expected observation: Five is allowed and six is denied.
2. The maximum itself is allowed. Is 6 within range?
3. The inclusive bound must be clear.

### Hint for investigation 4: Preserve request identity

1. Restate the expected observation: The exact request UID is copied.
2. The decision starts from the request UID. What does the response carry?
3. A response for another request must not be accepted as evidence for this one.

### Hint for investigation 5: Keep dry-run side effects absent

1. Restate the expected observation: Both decisions allow the request; only the real evaluation records a side effect.
2. dryRun skips the counter. What do the two SideEffects values show?
3. This validator records one audit side effect for an allowed real request and none for dry run.

### Hint for investigation 6: Transfer missing identity refusal

1. Restate the expected observation: The decision is denied.
2. An empty UID is refused before range checks. Is the request allowed?
3. A valid numeric object is insufficient if the adapter cannot bind the response to a request.
