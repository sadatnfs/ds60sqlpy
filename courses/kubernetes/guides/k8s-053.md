# k8s-053: Ingress, HTTP routing and controller ownership

## Level and prerequisites

## Learning objectives

## Purpose, vocabulary and mental model

Ingress describes HTTP and HTTPS routing intent to Services. It requires an Ingress controller that interprets the resource and implements a proxy path. Creating an Ingress object without a controller does not create a web server or make a hostname reachable.

A host rule matches the HTTP host name, while a path rule matches the URL path according to its pathType. Exact, Prefix and implementation-specific rules are not interchangeable. Prefix matching is based on path elements, not an arbitrary raw string startsWith rule. Rewriting paths is controller-specific behavior rather than a universal core Ingress feature.

The controller itself needs an exposure path, such as a load balancer or a deliberately mapped local port. DNS must point the chosen hostname at that entrypoint. An HTTP route can be configured correctly while public DNS or TLS is still wrong. Diagnose the request as a chain.

## Mechanism and field-by-field reasoning

Use networking.k8s.io/v1 and specify ingressClassName when the prepared environment requires it. Each backend references a Service and a port in the API, not a Pod directly. That reference does not require every controller to send packets through the Service ClusterIP. A controller can derive eligible Pod endpoints and proxy to them directly, or use the ClusterIP according to its implementation and configuration. Traefik’s documented nativeLB option is one concrete example of these alternatives. The fixture uses a reserved example hostname and is manual-only.

Ingress remains a supported API, while Gateway API offers a more expressive role-oriented model. Neither choice installs its own controller. A learner should understand both the API contract and the selected implementation before relying on annotations.

## Trace the request or control path

```text
browser Host header -> controller listener -> host/path rule -> Service backend reference
actual upstream: direct eligible Pod endpoint OR Service ClusterIP path, by controller configuration
-> Pod listener -> application route
```

Read this diagram as a sequence of responsibilities. A controller can successfully create desired state while a later traffic or application step still fails. Identify the component that makes each decision and the concrete observation that would prove it. The addresses in these lessons are synthetic examples, never instructions to contact a shared or public system.

## Worked example / walkthrough

### Worked example 1: Read a namespaced backend rule

This is a fragment for an explicitly prepared controller.

```yaml
rules:
  - host: study.example.test
    http:
      paths:
        - path: /
          pathType: Prefix
          backend:
            service:
              name: network-study
              port:
                number: 80
```

**Expected observation:** The API backend references Service port 80. The controller may resolve it to Pod listener 8080 directly or route through the ClusterIP, according to its documented upstream mode.

### Worked example 2: Separate proxy route and app route

No rewrite is implied in this example.

```text
client GET /reports -> Ingress forwards /reports -> app receives /reports
app has only / -> app may return404
```

**Expected observation:** A matched Ingress rule does not guarantee the application implements the forwarded path. The maintained original fixture serves /version with ds60-fixture-v1 plus a newline and /ready with ready plus a newline; / returns404. Use /version for the positive routing check rather than expecting the root path to succeed.

## Diagnosis, failure boundaries and common mistakes

The controlled failure in this chapter is: Diagnose an app 404 after a matched prefix route. Its distinguishing result is The forwarded path may not exist in the application. Keep that observation separate from guesses about adjacent layers. A DNS answer is not proof of a listening process. A Ready Pod is not proof of an externally reachable listener. A load-balancer address is not proof of TLS identity, path routing or a correct application response.

Use bounded observations from the actual caller's network namespace. Preserve timestamps, object UIDs, generation or resource versions where relevant, and the intended image identity. A stale healthy result from another namespace or an earlier revision cannot qualify the current path. Avoid broad packet captures, all-namespace dumps and secret output when a smaller field-level observation answers the question.

Do not repair a failed example by disabling NetworkPolicy, making a workload privileged, publishing every port or selecting another cluster. Those changes alter the contract rather than explain the failure. An unavailable capability is a valid boundary to report. Rehearse its mechanism with the synthetic fixture until the owned target is deliberately provisioned.
