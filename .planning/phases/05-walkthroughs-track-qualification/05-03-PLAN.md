How to choose and author each walkthrough (apply to every track):
1. List candidates per stage from the matrix: `.venv/bin/python -c "import json; rows=json.load(open('curriculum/coverage-matrix.json'))['lessons']; [print(r['id'], r['stage'], r['runtime'], r['learning_mode'], r['paths']['solutions'] or r['paths']['lesson']) for r in rows if r['track']=='TRACK']"`. Use only rows whose runtime is an ordinary profile (it appears in `check_module_references.py --list-only` as a case, not an exclusion).
2. Read `courses/<track>/AGENTS.md` (or README.md) for track rules, then the executable reference (practice: the single non-Markdown solution file; tutorial: the lesson source) and its guide.
3. Prefer a lesson whose reference prints a stable, deterministic line (a check marker, a computed label or count). Never use floating values that may vary, timestamps, paths or random draws as expected_output. If a reference prints nothing deterministic, pick another lesson in the same stage.
4. Write 3 to 8 steps that follow the program's logic in order, each with `lines` `[start, end]`, byte-exact `excerpt`, `title`, `explanation` (why the code does what it does, in plain American English for a newcomer), and `observe` (what the learner would see or what value now exists). Do not say "trace", "executed" or "live".
5. Compute `source_sha256` with `.venv/bin/python -c "import hashlib,sys; print(hashlib.sha256(open(sys.argv[1],'rb').read()).hexdigest())" PATH`.
6. Validate with `.venv/bin/python scripts/check_walkthroughs.py --track TRACK` and confirm three stages are listed.

Track notes from 05-RESEARCH.md "Track Classification":
- cpp: one `reading` row; use cpp20 rows. C++ guide outputs are also checked by `tests/test_cpp_worked_examples.py` against `authoring/depth/expected_outputs.json`; keep walkthrough outputs consistent with them.
- scala-spark: ordinary profiles scala-jvm, spark-local-scala, spark-local-python; avoid the 3 reading rows. Spark logs are noisy; choose explicit printed result lines.
- javascript-typescript: use javascript-node or typescript-node rows only; the 24 javascript-browser rows are browser-qualified, not corpus-run, and are not anchors.
- web-development: use php-cli rows only; html-browser rows are not anchors.
- r and tmb-modeling: r-statistics; tmb-modeling is a tutorial track (lesson source is the anchor, no reveal). Some R outputs are generator-owned (`scripts/format-policy.json`); if a rebuild changes a reference, use `--rebind` (only succeeds when excerpts still match) or re-author.
- swift: Linux compiler contract only (`docs/validation.md:571-572`); do not describe Apple UI behavior as checked.
- julia: guides have no worked-example heading; the walkthrough still anchors on the solution program.
