# go-033: Repository interfaces and transaction failure policy

## Level and prerequisites

Advanced. Allow about 120 minutes, then revisit the transfer case later. Prerequisites: go-032

## Learning objectives

Model a repository transaction that commits valid changes, rolls back failures and keeps retries idempotent. Along the way, explain transaction, repository boundary, unknown outcome; implement the six investigations below; and defend the expected result of a changed input before running it.

## Why this mechanism matters

A repository boundary separates business operations from database mechanics. The application should describe the transaction it needs, while an adapter manages SQL parameters, context cancellation, row scanning and commit or rollback. In database/sql, a DB is a connection pool rather than one connection. A Tx reserves a transaction context whose operations must all use that Tx. Calling the outer DB halfway through a transaction can escape its atomicity. This lesson uses a small copy-on-write transactional model to test policy offline. It is explicitly not evidence about PostgreSQL isolation, driver behavior or network failure. Those require a prepared database integration test.

## Vocabulary and concepts

- **Transaction:** A group of changes committed or rejected as one unit.
- **Repository boundary:** An application-facing data access contract.
- **Unknown outcome:** A state where failure to observe success does not prove work failed.

## Syntax anatomy and reasoning

A callback receiving a transaction-local value can stage changes before committing them to the outer state. An error aborts the staged changes. In a real database/sql adapter, begin with BeginTx(ctx, options), defer Rollback, execute parameterized statements through tx, and inspect Commit errors. SQL syntax and placeholder conventions depend on the selected driver. Never construct SQL by interpolating untrusted values. A transaction whose commit outcome is unknown cannot safely be replayed without an idempotency contract.

## Worked example / walkthrough

### Worked example 1: Commit a valid change

Transfer 3 between balances 5 and 5 in a staged transaction.

```go
package main

import (
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Balances struct{ A, B int }

func transact(s *Balances, f func(*Balances) error) error {
	copy := *s
	if err := f(&copy); err != nil {
		return err
	}
	*s = copy
	return nil
}

func main() {
	// Commit a valid change
	{
		s := Balances{A: 5, B: 5}
		err := transact(&s, func(t *Balances) error { t.A -= 3; t.B += 3; return nil })
		check(err == nil && s.A == 2 && s.B == 8, "commit")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The committed balances are 2 and 8.

The outer state changes only after the callback succeeds. This proves the local model policy, not database atomicity.

### Worked example 2: Rollback an explicit failure

Change staged state and return an error.

```go
package main

import (
	"errors"
	"fmt"
)

func check(ok bool, message string) {
	if !ok {
		panic(message)
	}
}

type Balances struct{ A, B int }

func transact(s *Balances, f func(*Balances) error) error {
	copy := *s
	if err := f(&copy); err != nil {
		return err
	}
	*s = copy
	return nil
}

func main() {
	// Commit a valid change
	{
		s := Balances{A: 5, B: 5}
		err := transact(&s, func(t *Balances) error { t.A -= 3; t.B += 3; return nil })
		check(err == nil && s.A == 2 && s.B == 8, "commit")
	}

	// Rollback an explicit failure
	{
		s := Balances{A: 5, B: 5}
		err := transact(&s, func(t *Balances) error { t.A = 0; return errors.New("reject") })
		check(err != nil && s.A == 5, "rollback")
	}
	fmt.Println("Worked example checks passed.")
}
```

**Observe:** The outer balances remain unchanged.

A staged mutation is not a committed mutation. The distinction is visible because the model uses a separate value copy.

## Exercises

### Exercise 1: Commit a valid change: change one input

### Exercise 2: Rollback an explicit failure: debug a regression

A regression changed one token in worked example 2, so one line now reads `s := Balances{A: 6, B: 5}`. Run worked example 2 with that line, use the failure to locate the defect and repair it without changing the check.

**Expected:** Before the repair the program panics with `rollback`; after it the line reads `s := Balances{A: 5, B: 5}` again and the outer balances remain unchanged.

**Verify:** Keep the failing and the repaired runs. Explain why the changed token alters the value tested by `err != nil && s.A == 5` for this input.

### Exercise 3: Reject invalid funds

Attempt a transfer larger than available balance.

**Expected:** The state remains 5 and 5.

**Verify:** Keep a check equivalent to `err != nil && s.A == 5 && s.B == 5`. As a control, change `s := Balances{A: 5, B: 5}` to `s := Balances{A: 6, B: 5}`: the run must panic with `funds`. Restore the line before continuing.

### Exercise 4: Preserve total value

Apply two successful transfers and inspect the combined balance.

**Expected:** The total remains 10.

**Verify:** Keep a check equivalent to `s.A+s.B == 10`. As a control, change `check(s.A+s.B == 10, "total")` to `check(s.A-s.B == 10, "total")` inside that check: it must panic with `total`, which shows the check can fail. Restore it.

### Exercise 5: Keep a failed retry distinct

Fail one transaction, then explicitly start a new valid transaction.

**Expected:** Only the second change commits.

**Verify:** Keep a check equivalent to `transact(&s, func(t *Balances) error { t.A--; t.B++; return nil }) == nil && s.A == 4`. As a control, change `s := Balances{A: 5, B: 5}` to `s := Balances{A: 6, B: 5}`: the run must panic with `retry`. Restore the line before continuing.

### Exercise 6: Transfer no-op semantics

Run a transaction that changes nothing.

**Expected:** The state is preserved and the operation succeeds.

**Verify:** Keep a check equivalent to `err == nil && s.A == 5 && s.B == 5`. As a control, change `s := Balances{A: 5, B: 5}` to `s := Balances{A: 6, B: 5}`: the run must panic with `no-op`. Restore the line before continuing.

## Common pitfalls and diagnosis

Read a compiler error from the first location in your source, then fix one cause at a time. Unused imports and variables are errors in Go; add an import when its use exists, rather than copying a large unused import list. A panic from `check` identifies a violated example contract. Compare the actual value with the expected value and inspect the state transition that produced it. A returned `error` is a value that the caller must handle; an ignored error can make later output look plausible while the original operation failed.

The lesson-specific explanations in the two examples identify the important counterexamples. Extend that reasoning to every investigation: explain why a plausible alternative would fail, and preserve a tiny input that distinguishes it. Treat empty data, missing values and cancellation as domain cases with explicit policies. In concurrent work, replace sleeps used as synchronization with channels, mutexes or an explicit ownership protocol.
