Learning objectives#

  • Build a query one clause at a time and inspect surviving identities.
  • Separate parser/name errors from a syntactically valid wrong answer.
  • Explain Boolean grouping, alias scope, and first-error recovery using a small fixture.

Vocabulary and concepts#

Debugging means locating the first place where observed behavior differs from the intended question. It is not guessing different punctuation until a query returns something. Start with the output sentence, choose the input, inspect its identities, add one restriction, and check again. This lesson has six tasks, so you can predict every intermediate result by hand. The small scale lets you reason before relying on a database error or an assistant.

  • Syntax error: A syntax error means PostgreSQL cannot parse the statement into valid SQL grammar.
  • Name error: A name error means the statement refers to a column or other object PostgreSQL cannot resolve.
  • Semantic error: A semantic error means the query runs but answers the wrong question.
  • Sqlstate: A SQLSTATE is a five-character code identifying an error category independently of localized message wording.
  • Alias scope: Alias scope describes where a name created with AS is available.
  • Checkpoint: A checkpoint is a deliberately small intermediate query whose returned identities can be compared with the question before more logic is added.

The debugging loop is question, prediction, execution, comparison, smallest repair. A zero-row answer is not necessarily an error. A successful command exit is not proof of a correct business answer. Record the actual SQL and complete first error when asking for help. If psql is waiting at a continuation prompt, inspect whether the semicolon or quote is unfinished before opening a second terminal. \r clears an unfinished interactive query buffer; it is not a database rollback and is not needed in the course file.

Syntax anatomy and query reasoning#

For SELECT task_id, effort * 2 AS doubled_effort FROM start_tasks WHERE effort * 2 >= 6 ORDER BY task_id;, FROM introduces the task columns and WHERE filters input rows before SELECT exposes the output alias. Therefore WHERE doubled_effort >= 6 cannot use that alias at the same query level. Repeat the expression for now. Later, a subquery or common table expression can make a calculated value an input to another query. ORDER BY can refer to a SELECT alias because it orders the final output.

Parentheses state Boolean grouping. AND binds more tightly than OR, so team = 'Red' AND status = 'open' OR status = 'blocked' admits every blocked task regardless of team. If the question requires Red tasks in either state, write the grouping around the status alternatives. Parentheses do not merely decorate a predicate: they change which rows qualify. Trace one Blue blocked task to expose the difference without a large dataset.

Each query follows FROM, WHERE, SELECT, ORDER BY, LIMIT for this lesson's logical reasoning. The physical execution plan is PostgreSQL's concern and may differ. Keep a unique task_id in diagnostic output and compare complete ID lists. Repairing an unknown-column spelling does not prove the threshold or grouping is right, so rerun the evidence checks after the syntax repair. The fixture includes an effort exactly 3, a missing effort, and a blocked Blue task to exercise three different boundaries rather than relying only on a comfortable normal case.

Worked example / walkthrough#

Run these in the complete learner file so the temporary fixture and transaction are present. The fixture values are fixed; the examples never depend on the current clock. Predict each result before running it.

Example 1: Watch a predicate narrow the identities#
SELECT task_id, team, status, effort
FROM start_tasks
WHERE status = 'open'
ORDER BY task_id;

Start with all six task identities. The status condition keeps 1,3,4,5, including the task with unknown effort because this predicate does not inspect effort. If your prediction omitted ID 3, you added an unstated assumption. Check this stage before introducing an effort threshold. The output is one open task per task_id, not one team.

Expected: Four rows, columns task_id, team, status, effort; IDs 1,3,4,5. ID 3 still has NULL effort.

Example 2: Compute a label without using it too early#
SELECT task_id, effort * 2 AS doubled_effort
FROM start_tasks
WHERE effort * 2 >= 6
ORDER BY doubled_effort DESC, task_id;

The filter repeats the arithmetic because doubled_effort is an output name unavailable to WHERE at this query level. ORDER BY can use the alias. The unknown effort yields an unknown comparison and does not qualify. The expression does not alter stored effort. Sorting ties by task_id makes the two doubled values of 6 appear in a declared order.

Expected: Three rows with columns task_id, doubled_effort: (2,10), (4,6), (5,6).

Self-check#

  • What evidence distinguishes a name error from a wrong business filter?
  • Why can ORDER BY use doubled_effort while same-level WHERE cannot?
  • Which fixture row catches the missing parentheses, and which rows catch the wrong threshold?

Keep your actual query and transcript. Explain one incorrect alternative and the exact fixture row that exposes it. A passing worked example does not prove an unattempted exercise. Revisit a failed prediction after taking a break, then answer the retrieval questions without looking at the code.

Common pitfalls#

  • An undefined-column error needs an identifier or scope investigation. Check the fixture columns and alias stage before changing installed software.
  • A query that runs can still include task 6 incorrectly. Inspect a counterexample row to test Boolean grouping.
  • After an unexpected error inside a transaction, later statements may report an aborted transaction. Fix the first error and rerun the complete file; do not treat later messages as independent root causes.

Exercise 5: Debug a threshold boundary#

The phrase at least translates to an inclusive comparison. The fixture deliberately places two open tasks exactly at 3, so a strict comparison fails visibly. The missing open effort produces unknown and is excluded by the measurement comparison, without any special zero replacement. The assertion tests the exact identities and values, which catches both a threshold error and forgetting the status filter. This kind of boundary fixture is usually more informative than adding dozens of ordinary rows that all satisfy both the correct and incorrect predicates.

FROM introduces tasks, WHERE keeps only open ones, SELECT chooses three output fields, ORDER BY defines a complete ranking, and LIMIT takes the first two. The largest effort anywhere in the table belongs to closed task 2, so ranking the whole table before applying eligibility would answer the wrong question. Unknown effort is explicitly placed last. Task_id resolves the tie between tasks 4 and 5. The assertion verifies the selected identities in their final ranking order.
