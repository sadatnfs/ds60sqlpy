# js-045: Keyed joins and object identity through updates

## Purpose, vocabulary and mental model

A key identifies the same entity across different arrays. It should be stable and unique within the joined group. An array index identifies a position, which can change after sorting or filtering. Confusing identity with position can attach the wrong interaction state or transition to a record.

A keyed join lets a DOM node continue representing the same entity even when the record order changes. The node can receive new values while preserving its identity. Exit removes entities no longer present; enter adds new identities. This is especially important for animated updates and keyboard focus.

Duplicate keys violate the intended one-entity-one-node relationship. D3 has defined matching behavior, but relying on it to silently fix bad input is a poor data contract. Validate uniqueness before drawing and decide explicitly whether repeated categories should be aggregated or represented by distinct IDs.

## Syntax anatomy and mechanism

Use `.data(records, d => d.id)` to match by identity. Save a node reference for entity A, reorder the records and redraw, then compare with `===`. This checks actual DOM reuse, not just a similar-looking chart.

Sort a copied array when you want display order without mutating a source collection owned elsewhere. Keep the key based on identity rather than the value being sorted. A value can change while the entity remains the same.

## Worked example / walkthrough

### Worked example 1: Match by stable ID

The key does not depend on array position.

```javascript
svg
  .selectAll("circle")
  .data(
    [
      { id: "A", v: 2 },
      { id: "B", v: 4 },
    ],
    (d) => d.id,
  )
  .join("circle");
```

**Expected observation:** One node per ID, with identity available across later updates.

### Worked example 2: Reject duplicate identity

A short check makes the assumption inspectable.

```javascript
const rows = [{ id: "A" }, { id: "A" }];
const unique = new Set(rows.map((d) => d.id)).size === rows.length;
console.log(unique);
```

**Expected observation:** false; decide how to repair the input rather than drawing ambiguous entities.

## Debugging and common mistakes

Keep three checkpoints separate: the records after parsing, the domain and geometry after transformation, and the visible marks after rendering. A chart can look plausible while silently dropping records or assigning the wrong scale. Inspect counts, IDs, finite coordinates and meaningful expected values before adjusting colors. A missing mark may come from invalid input, a missing selection, an undefined scale result or clipping outside the viewBox.

The controlled failure for this lesson is: Diagnose using a sorted index as the key. Its distinguishing evidence is Position changes can associate a node with a different entity. Preserve that failing case when repairing your program. Do not remove an assertion or broaden a scale merely to hide a wrong input. Explain whether a changed value should affect the data, an encoding, a layout or only presentation.

## Accessibility and interpretation

Give the visualization a descriptive title and a short textual summary of the main result. Keep a table or list when exact values matter. Do not encode a critical category only through color; use labels, shapes or position as appropriate. Interactive controls need keyboard operation and clear focus, and motion should respect the user's reduced-motion preference. Automated DOM checks support, but do not replace, a real keyboard and assistive-technology review.

A data scientist must also defend the statistical meaning. State the population, units, aggregation, missing-value policy and uncertainty where relevant. Synthetic points illustrate a mechanism and do not establish a real-world finding. A beautiful visualization should make a valid claim easier to inspect, not make a weak claim appear certain.
