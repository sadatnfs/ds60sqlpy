## Outcome and mechanism

Encode a bounded interactive view while preserving observation identity and a non-hover-dependent explanation.

Interaction can help a reader inspect a figure, but it should not be the only way to obtain essential information. Hover text can expose observation identity and units, while a printed table or concise static summary provides an alternative for readers who cannot use the same pointer interaction.

Stable IDs belong with the points. A point's array position can change after filtering, sorting or splitting into traces. customdata can retain an identity separate from displayed x and y values. A hover template should state the relevant quantities rather than producing an unlabeled list of numbers or relying on colour alone.

A visibility button changes the view of existing traces. It does not delete their underlying data, apply access control or necessarily recompute any statistical summary. If a displayed denominator or mean should change with a selection, that computation requires an explicit interaction contract. A static label calculated before filtering can otherwise become misleading.

The example defines two group traces and buttons for all groups or group A only. The figure specification can be inspected in R to verify that those controls target the intended trace identities. That source check does not prove a button actually worked in the delivered browser, nor does it establish keyboard navigation or screen-reader behavior.

Accessibility requires more than choosing a palette. Use meaningful labels, redundant encodings where appropriate, clear units and a noninteractive description or table. Actual interaction and assistive-technology checks belong to the final browser acceptance. This lesson encodes and validates the intended contract while keeping that unperformed observation explicit.

## Vocabulary

| Term | Meaning |
| --- | --- |
| Hover template | A declared presentation of point values and metadata when the renderer exposes a point. |
| Custom data | Point-associated metadata retained independently of displayed coordinate values. |
| Visibility control | A view operation that shows or hides existing traces. |
| Static alternative | A table or textual explanation that conveys essential information without requiring hover or pointer interaction. |

## Read the syntax

Attach stable IDs through customdata and define hovertemplate with labeled fields. Add layout updatemenus with explicit restyle visibility arguments tied to trace order. Inspect the built button arguments and trace metadata, then print the plot. Also print a small source table or summary so the main information is available outside hover.

## Worked examples

### Example 1: Retain identity and encode a view button

```r
d <- data.frame(id = c("A1", "A2", "B1", "B2"), group = c("A", "A", "B", "B"), x = c(1, 2, 1, 2), y = c(2, 3, 4, 6))
p <- plotly::plot_ly()
for (g in c("A", "B")) {
  part <- d[d$group == g, ]
  p <- plotly::add_trace(p, data = part, x = ~x, y = ~y, customdata = ~id, type = "scatter", mode = "markers", name = g, hovertemplate = "ID: %{customdata}<br>Input: %{x}<br>Value: %{y}<extra>%{fullData.name}</extra>")
}
p <- plotly::layout(p, xaxis = list(title = "Input"), yaxis = list(title = "Value"), updatemenus = list(list(type = "buttons", buttons = list(list(label = "All groups", method = "restyle", args = list("visible", list(TRUE, TRUE))), list(label = "Group A", method = "restyle", args = list("visible", list(TRUE, FALSE)))))))
built <- plotly::plotly_build(p)
stopifnot(length(built$x$data) == 2)
stopifnot(identical(as.character(built$x$data[[1]]$customdata), c("A1", "A2")))
stopifnot(identical(unlist(built$x$layout$updatemenus[[1]]$buttons[[2]]$args[[2]]), c(TRUE, FALSE)))
print(d)
print(p)
```

**Expected observation:** Two traces, retained IDs, an All/Group A control and a printed four-row table.

The table supplies a static alternative and the trace metadata retains point identity. The button arguments encode the intended view operation; actual clicking and keyboard behavior still require browser testing.

### Example 2: A prefiltered figure has a different data payload

```r
d <- data.frame(id = c("A1", "A2", "B1", "B2"), group = c("A", "A", "B", "B"), x = c(1, 2, 1, 2), y = c(2, 3, 4, 6))
selected <- d[d$group == "A", ]
p <- plotly::plot_ly(selected, x = ~x, y = ~y, customdata = ~id, type = "scatter", mode = "markers", name = "Group A")
built <- plotly::plotly_build(p)$x$data[[1]]
stopifnot(length(built$x) == 2, identical(as.character(built$customdata), c("A1", "A2")))
print(selected)
print(p)
```

**Expected observation:** Two retained observations in the actual figure data.

Filtering the data before construction produces a two-point payload. This differs from hiding a trace in a four-point payload; neither operation should be mislabeled as an authorization boundary.
