# c-030: Sanitizers, debugger evidence and safe regressions

## Level and prerequisites

Advanced, approximately 120 minutes plus a later retrieval session. Direct prerequisites: `c-029`

## Learning objectives

Turn a sanitizer finding into a bounds-checked regression test that runs safely without the original undefined behavior. Along the way, explain instrumentation, regression fixture and diagnostic evidence. Implement the six investigations, from the "guard a formerly unsafe index" case to the "transfer a newly discovered boundary" case, with explicit checks, identify a plausible defect and defend a fresh boundary case before execution. Completing a reference is not evidence of independent mastery.

## Purpose and mental model

Compiler warnings, static analysis, sanitizers and debugger traces reveal different classes of evidence. AddressSanitizer instruments many invalid memory accesses; UndefinedBehaviorSanitizer checks selected undefined operations. Neither establishes that every possible path is correct, and neither replaces ownership reasoning. A sanitizer failure should become a small regression case after the defect is repaired. Do not ship a reference that intentionally executes undefined behavior merely to print a diagnostic. This lesson runs safe regression cases and gives the separate instrumented build workflow. A debugger is most useful when you can name the first invariant that became false rather than merely stop at the final crash.

## Vocabulary and concepts

- **Instrumentation:** Additional checks inserted into a compiled program.
- **Regression fixture:** A small retained input exposing a prior defect.
- **Diagnostic evidence:** A trace or report tied to an actual source and execution.

## Syntax anatomy and execution trace

A prepared contributor build can add `-g -O1 -fsanitize=address,undefined -fno-omit-frame-pointer` to compilation and linking. Execute the same checked source under that build. The ordinary pad uses its fixed reviewed flags and does not claim sanitizer execution. Keep source, compiler command, exit status and diagnostic together. Disable neither an assertion nor a sanitizer report without explaining the actual correction.

## Worked example / walkthrough

### Worked example 1: Guard a formerly unsafe index

Use a checked accessor on the final valid index.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

bool at_index(const int *values, size_t n, size_t i, int *out) {
  if (values == NULL || out == NULL || i >= n)
    return false;
  *out = values[i];
  return true;
}

int main(void) {
  /* Guard a formerly unsafe index */
  {
    int values[] = {2, 4, 6}, out = 0;
    CHECK(at_index(values, 3, 2, &out) && out == 6);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The value 6 is returned.

The accessor proves the index is below length before reading.

### Worked example 2: Reject the one-past index

Request index 3 from length 3.

```c
#include <assert.h>
#include <limits.h>
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

static void lesson_check(bool condition, const char *file, int line) {
  if (!condition) {
    fprintf(stderr, "Check failed at %s:%d\n", file, line);
    abort();
  }
}
#define CHECK(condition) lesson_check((condition), __FILE__, __LINE__)

bool at_index(const int *values, size_t n, size_t i, int *out) {
  if (values == NULL || out == NULL || i >= n)
    return false;
  *out = values[i];
  return true;
}

int main(void) {
  /* Guard a formerly unsafe index */
  {
    int values[] = {2, 4, 6}, out = 0;
    CHECK(at_index(values, 3, 2, &out) && out == 6);
  }

  /* Reject the one-past index */
  {
    int values[] = {2, 4, 6}, out = 9;
    CHECK(!at_index(values, 3, 3, &out) && out == 9);
  }
  puts("Worked example checks passed.");
  return 0;
}
```

**Observe:** The operation fails and output remains 9.

The regression preserves the boundary that an unchecked implementation would access illegally.

Predict worked example 1: when you use a checked accessor on the final valid index, the CHECK on `at_index(values, 3, 2, &out) && out == 6` should see that the value 6 is returned. For the "reject the one-past index" case, predict that the operation fails and output remains 9. Write down the declared size of `values[]` before indexing it.

## Exercises

How the hints, control edits and regressions below work: [Work an exercise](../STUDY-GUIDE.md#work-an-exercise).

### Exercise 1: Guard a formerly unsafe index: change one input

In worked example 1, change `int values[] = {2, 4, 6}, out = 0;` to `int values[] = {2, 4, 7}, out = 0;`. Predict which value the CHECK on `at_index(values, 3, 2, &out) && out == 6` sees, then run and restore.

**Expected:** `Check failed` at `at_index(values, 3, 2, &out) && out == 6`; restoring `int values[] = {2, 4, 6}, out = 0;` passes again.

**Verify:** Name the value that made `at_index(values, 3, 2, &out) && out == 6` false, where worked example 1 showed that the value 6 is returned.

**Progressive hints:** First trace `values` and `out` from initialization. Then compute what the CHECK sees with `int values[] = {2, 4, 7}, out = 0;` in place.

### Exercise 2: Reject the one-past index: debug a regression

Worked example 2 now has a line reading `int values[] = {2, 4, 6}, out = 10;`. Repair it so that the operation fails and output remains 9 again.

**Expected:** `Check failed` at `!at_index(values, 3, 3, &out) && out == 9` until the line reads `int values[] = {2, 4, 6}, out = 9;` again.

**Verify:** Explain how `int values[] = {2, 4, 6}, out = 10;` changes the value `!at_index(values, 3, 3, &out) && out == 9` tests, using your failing and repaired runs.

**Progressive hints:** First trace `values` and `out` from initialization. Then compare `int values[] = {2, 4, 6}, out = 10;` with worked example 2's original line.

### Exercise 3: Reject an empty view

Request index zero from an empty logical view.

**Expected:** No access occurs.

**Verify:** Keep a CHECK equivalent to `!at_index(NULL, 0, 0, &out) && out == 9`. Control edit: changing `int out = 9;` to `int out = 10;` must fail it; then restore it.

**Progressive hints:** First trace `out` from initialization. Then recall: The function checks the pointer and bound instead of relying on a sanitizer to stop a bad access.

### Exercise 4: Verify a valid allocation lifetime

Allocate, initialize, inspect and free one integer.

**Expected:** The value is checked before release.

**Verify:** Keep a CHECK equivalent to `*p == 7`. Control edit: changing `*p = 7;` to `*p = 8;` must fail it; then restore it.

**Progressive hints:** First trace `p` from initialization. Then recall: There is no post-free dereference in a production reference.

### Exercise 5: Retain output capacity checks

Format a short message into sufficient storage.

**Expected:** The write fits completely.

**Verify:** Keep a CHECK equivalent to `n >= 0 && (size_t)n < sizeof out && strcmp(out, "ready") == 0`. Control edit: changing `int n = snprintf(out, sizeof out, "%s", "ready");` to `int n = snprintf(out, sizeof out, "%s!", "ready");` must fail it; then restore it.

**Progressive hints:** First trace `n` and `out` from initialization. Then recall: The explicit return-value check remains useful even when instrumentation is enabled.

### Exercise 6: Transfer a newly discovered boundary

Test a singleton at indices zero and one.

**Expected:** Only zero is valid.

**Verify:** Keep a CHECK equivalent to `at_index(values, 1, 0, &out) && out == 5`. Control edit: changing `int values[] = {5}, out = 0;` to `int values[] = {6}, out = 0;` must fail it; then restore it.

**Progressive hints:** First trace `values` and `out` from initialization. Then recall: A tiny case is easier to reason about and keep as a permanent regression than a large nondeterministic crash workload.

## Common pitfalls and diagnosis

Treating a clean sanitizer run as proof of safety: a sanitizer reports only the paths the run executed. Deleting the reproducer after a fix loses the regression; keep the smallest failing input as a permanent test.

General diagnosis order and the pointer checklist: [Diagnose failures](../STUDY-GUIDE.md#diagnose-failures).
