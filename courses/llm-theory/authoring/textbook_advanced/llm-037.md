## Evaluate the path from question to supported answer

A retrieval-and-answer system is a chain of decisions. It selects evidence, constructs context, produces an answer or abstention, and attaches claims to sources. A final correct/incorrect flag is useful, but it does not identify which stage caused a failure. The purpose of this chapter is to retain enough intermediate evidence to make the next engineering change defensible.

Begin with a stable question ID, a declared answerability label, permitted source versions and a scoring rubric. Then record the retrieved IDs, exact context supplied, generated answer, claim-level support and abstention decision. Without those artifacts, a failure category can become a guess made after seeing the final text. The local reference uses hand-authored records so the bookkeeping can be studied without claiming that an answer model produced them.

### Read the four-case table carefully

Question q1 has a retrieval miss and an incorrect final outcome. Question q2 has relevant context but an unsupported answer. Question q3 correctly abstains, and q4 answers correctly. These cases illustrate different mechanisms. Improving retrieval might help q1 but would not automatically fix q2, because its problem occurs after evidence is already available.

If the declared correctness rule treats appropriate abstention as a success on an unanswerable question, overall correctness is \(\frac{2}{4}\). Three cases are answered, so coverage is \(\frac{3}{4}\). Only one answered case is correct, giving answered-case accuracy \(\frac{1}{3}\). Reporting only \(\frac{2}{4}\) loses the coverage distinction; reporting only \(\frac{1}{3}\) loses the successful abstention. The denominators should travel with the numbers.

The categories need not be mutually exclusive in every real dataset. A system can miss the best evidence and also invent an unsupported claim. The worksheet assigns simple cases to isolate mechanisms, but a production taxonomy should state whether flags can overlap and how counts are aggregated. Forcing every failure into one bucket can conceal a chain of contributing errors.

### Define evidence sufficiency before judging the answerer

A document can be topically relevant without containing the information needed to answer the question. For an evidence-grounded task, distinguish retrieval relevance from context sufficiency. A source that mentions a product name may be relevant, while a source containing its applicable return policy may be sufficient for a particular question. Multi-part questions may require several complementary passages.

A context-sufficiency label should identify what evidence is required and whether it was present in the exact context delivered to the model. A relevant full document does not help if the chunker discarded the decisive paragraph. A context budget can truncate a condition or unit that makes a claim valid. Preserve the assembled context, not only the initial retrieval ranking.

This also clarifies a useful retrieval test. If the corpus itself lacks the answer, no retriever can return a sufficient passage from it. That case evaluates missing-evidence handling. If the corpus contains the answer but the retriever misses it, the failure concerns selection. Those cases should not be merged into one unexplained "RAG failed" label.

### Treat a citation as a relationship between a claim and a source span

The example source says "red square has four sides." The claim "The square has four sides" is supported by the relevant span. The claim "The square weighs 10kg" is not supported merely because it cites the same document ID. Source existence and claim support are different predicates.

A substring check can verify that a quoted span appears in a particular source version. It cannot by itself establish that an arbitrary paraphrase is entailed by the span. Negation, numerical units, time scope and quantifiers can change the meaning. For example, "may be red" does not support "is always red," and "up to ten" does not support "exactly ten." Keep these semantic relationships explicit when designing a rubric.

Compound claims deserve decomposition. An answer saying "The square is red, has four sides, and weighs ten kilograms" contains several propositions with potentially different support. A single citation at the end can hide that mixture. Claim-level evaluation records which propositions are supported, contradicted or not established by the permitted evidence. It should not turn an unknown claim into a false one automatically unless the task's scoring rule explicitly does so.

### Use an oracle-context control as an actual intervention

An oracle-context experiment supplies a known sufficient passage directly to the answerer, bypassing the retriever. If a question fails under ordinary retrieval and succeeds under oracle context while the other relevant conditions are controlled, that comparison supports the diagnosis that evidence selection or context construction mattered. If it fails even with sufficient context, the answerer, prompt, task specification or scorer needs investigation.

The word "oracle" does not make a row experimental evidence. In this reference, `oracle_context=True` and `answer_correct=True` are supplied fields in a small record; no answer model is rerun. They illustrate how a controlled result would be represented. A real study must preserve the actual normal and oracle contexts, generated answers, model identity, sampling policy and scoring rationale.

Control what can reasonably be controlled. Use the same question, answerer version and scoring rubric. If stochastic generation is involved, a single paired sample may reflect sampling variation; repeated paired runs or a suitable deterministic policy may be needed for the intended inference. Oracle context can also differ in length or formatting from ordinary context, so describe those differences rather than claiming a perfect single-factor intervention automatically.

A correct answer under oracle context does not prove that the retriever can find that source under deployment constraints. A correct answer under ordinary context does not prove it used the source rather than prior knowledge. Different controls answer different questions. Counterfactual evidence changes, source removal and claim-support checks can provide complementary evidence, each with its own assumptions.

### Separate correctness, grounding and usefulness

An answer can be factually correct but unsupported by the allowed context. In an evidence-grounded task, that can violate the contract even if the statement happens to be true. An answer can also quote a source accurately while the source is outdated or inapplicable to the user's case. Grounding, factual truth under a broader world model, source authority and task usefulness are related but distinct dimensions.

For data-science assistants, the distinction is concrete. A model might state the right mean by coincidence, cite a document defining a mean, and still have no executed calculation on the requested dataset. A grounded analysis should bind numeric claims to actual code/data outputs and explanatory claims to appropriate sources. A plausible narrative cannot substitute for the computation receipt.

The [applied retrieval-and-answer evaluation lesson](../../../llm-applied/guides/llm-applied-012.md) develops these controls in a more connected pipeline. The theory chapter's role is to make the measurement design understandable before a larger implementation introduces many moving parts.

### Keep the evaluation packet reproducible

Stable question IDs let results from different candidates and controls be joined without relying on row order. Duplicate IDs should be detected because they can overwrite or ambiguously pair observations. Source versions, model configuration, retrieval settings and exact answer artifacts should be retained with the ID. A metric table without those artifacts can be difficult to audit after a pipeline change.

Decide the aggregation unit before comparing systems. Several paraphrases from one source family can dominate a row-weighted average. A later reliability chapter will examine family-level comparisons and resampling. For now, preserve the family labels and per-question outcomes so that the intended aggregation remains possible.

A useful failure report ends with a targeted next experiment: test retrieval recall on the affected family, inspect context truncation, rerun with sufficient evidence, revise claim-scoring rules, or evaluate abstention behavior. It should not jump from one failed answer to retraining every component.
