js-019: TypeScript values and compile-time types#

Level and prerequisites#

Intermediate, approximately 90 minutes. Direct prerequisites: js-018

Learning objectives#

Explain static type, inference, erasure, unknown boundary with a concrete program. Trace how the values change, identify the assumptions, and make a boundary or invalid case observable. The first investigation is: Define a function accepting two numbers and returning their sum; inspect its runtime value. The final task tests narrow unknown before numeric use.

Purpose and mental model#

TypeScript adds a static checker to JavaScript. The checker reasons about possible values and operations before execution; the emitted program still follows JavaScript semantics. A type annotation does not create a runtime validator, convert a string to a number, or freeze an object. This distinction is essential when data comes from JSON, files, network responses or another program.

Inference lets the checker learn types from initial values and expressions. An explicit annotation is useful at a public boundary or when the intended set of values is broader than the initial expression. Repeating every obvious inferred type adds noise without necessarily improving the contract. Strict checking includes checks such as strictNullChecks and noImplicitAny, but it does not enable every possible compiler option. In particular, this profile does not silently claim exactOptionalPropertyTypes or noUncheckedIndexedAccess.

The prepared route compiles main.mts with TypeScript 5.9.3 using NodeNext resolution and noEmitOnError, then runs the resulting ES module on Node 24. An incorrect typed program is a compiler failure before runtime. Each deliberate negative type example is placed in an uncalled function with @ts-expect-error. The directive requires the next line to produce a compiler diagnostic; if that error disappears, the compiler reports an unused directive. These functions are teaching checks, not code paths to execute or broad permission to suppress errors.

Vocabulary and concepts#

Static type: A compile-time description of values and supported operations.

Inference: Deriving a type from code without an explicit annotation.

Erasure: Removal of type-only syntax from the emitted JavaScript.

Unknown boundary: An external value requiring runtime inspection before trusted use.

Syntax anatomy and execution trace#

A parameter annotation follows its name, and a return annotation follows the parameter list. const often preserves a literal primitive type, whereas let permits later assignment and commonly widens to the primitive category. A type alias names a compile-time description. unknown requires checking before use; any bypasses many checks and should not become the default for external input. The as syntax asserts what the author wants the checker to assume and performs no conversion.

Worked example / walkthrough#

Example A: Annotate a numeric function#

The annotation describes accepted calls to checked TypeScript code. It is erased during compilation; the emitted function still performs JavaScript addition and would need validation at an untyped boundary.

import { strict as assert } from 'node:assert';



export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    function add(left: number, right: number): number { return left + right; }
    const result = add(2, 3);
    assert.equal(result, 5);
    assert.equal(typeof result, 'number');
    function negativeTypeCheck(): void {
      // @ts-expect-error A string is not a numeric argument.
      add('2', 3);
    }
    void negativeTypeCheck;
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: sum 5 with runtime typeof number.

Example B: Show that an assertion does not convert data#

This intentionally unsafe assertion demonstrates the escape hatch. The correct repair for external data is a runtime check or parser, not a stronger-looking cast.

import { strict as assert } from 'node:assert';



export async function verify(): Promise<{ checks: number; status: string }> {
  // Worked example
  {
    const external: unknown = 'wrong';
    const claimed = external as number;
    assert.equal(typeof claimed, 'string');
    assert.equal(String(claimed), 'wrong');
  }

  return { checks: 1, status: "passed" };
}

console.log(JSON.stringify(await verify()));

Expected: the runtime value remains the string wrong.

Prediction before your attempt#

Trace the entry point and identify the values that exist before each operation. Distinguish a value from a reference to an object, a returned Promise from its eventual result, and a compile-time type from a runtime check. Write down the first observation that would disprove your explanation. A useful prediction includes an expected value or failure category, not merely a claim that the program should work.

For a loop, write the state before and after one iteration. For a callback, identify the caller and the arguments it supplies. For an asynchronous operation, identify who starts it, who awaits it, and who owns cleanup. These small traces make failures local: you can compare the first incorrect state instead of guessing from a much later symptom.

Exercises#

  1. Annotate a numeric function. Define a function accepting two numbers and returning their sum; inspect its runtime value. Expected: sum 5 with runtime typeof number. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Show that an assertion does not convert data. Assert that an unknown string is a number, then inspect the actual runtime type. Expected: the runtime value remains the string wrong. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Compare literal preservation and widening. Use const for a fixed tag and let for a changing text value. Expected: fixed tag remains ready; mutable text can change to done. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Handle null explicitly under strict checking. Write a length function accepting string or null. Expected: length 3 for abc and 0 for null. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Observe type erasure through object keys. Declare a record type and create a compatible object. Expected: runtime keys contain only id and count, with no type alias metadata. Verify: Record the observed value, exception or browser state and compare it with that expectation.
  1. Narrow unknown before numeric use. Accept only a finite number from an unknown value. Expected: 12 doubles to 24; string 12 and Infinity reject. Verify: Record the observed value, exception or browser state and compare it with that expectation.

Common pitfalls and diagnosis#

Keep the smallest fixture that distinguishes the intended behavior from a tempting alternative. Read the assertion message and inspect the input, return value and state at that point. Do not remove a failing check just to reach the success receipt. Preserve the original failure, repair the responsible assumption, then check the normal path and the negative case again.

If a host API is absent, confirm the actual host and version before changing the algorithm. A successful parse does not prove that an API exists. Compiler success does not prove that external data satisfies a type. A browser interaction requires browser evidence. For resource-owning examples, inspect cleanup after failure as carefully as the happy path. The separate explanations discuss the specific mistaken inference in each exercise.

Progressive hints#

Start by comparing the actual value with the literal expected result. Next, isolate the expression that transforms it or the boundary where its type or ownership changes. If the discrepancy involves scheduling, replace unrelated work with a small trace array and await the exact completion you intend to observe. Finally, ask for one hint about the first incorrect assumption before opening the reference. Keep one controlled failure that would catch the same mistake returning.
