**Level:** Advanced | **Prepared runtime:** `python-core`

**Direct prerequisites:** `dme-070`.

**Outcome:** Define latency denominators and distinguish compute, wall time, cohort composition and actual profiling evidence.

A serving system can truthfully report fast matrix operations while users wait several seconds for output. Queueing, tokenization, scheduling, persistence, network delivery and deliberate pacing all contribute to observed latency. Performance analysis starts by defining timestamps and denominators, then collecting evidence from the actual implementation and workload.

The pad uses synthetic timestamp fixtures with exact expected values. The real workshop exposes loading, warm-up, queue, model-step and generation-wall durations. Its optional pacing is separately labeled. These measurements teach the request lifecycle; the tiny CPU model is not a benchmark for large pretrained deployments or GPU capacity.

## Define the timestamps first

Let \(t_a\) be request arrival, \(t_s\) the start of model service, \(t_f\) the first selected output token, and \(t_c\) terminal completion. Queue delay is \(t_s-t_a\). Server time to first token is \(t_f-t_a\), while first-token time after service begins is \(t_f-t_s\). End-to-end server duration is \(t_c-t_a\).

A client may instead measure arrival at its own UI and first displayed text. That includes browser and network behavior and can differ from server token selection because of UTF-8 buffering or stop-prefix holdback. Name the observation point. Two metrics called TTFT can be incomparable if one starts after queue admission and another starts when the user clicks.

For \(N>1\) output tokens, a common average time-per-output-token measure after the first token is

\[
\operatorname{TPOT}=\frac{t_c-t_f}{N-1}.
\]

This convention needs a defined completion point and treatment of EOS or other non-visible tokens. For zero or one token, the denominator is not valid; report the case separately rather than dividing by zero or replacing it with a misleading zero latency. Individual inter-token gaps provide more detail than one average.

## Compute time and wall time

A model-step timer can include tensor construction, device transfers, kernel execution, sampling and synchronization depending on where it starts and stops. State that scope. On an asynchronous device, a host timer around an enqueue operation can measure submission rather than completed compute. Appropriate synchronization or device events are needed for the intended measurement.

Generation wall time includes waiting between steps, event persistence, transport backpressure and any pedagogical delay. The workshop records compute duration for each actual model operation and token selection, plus a separate pacing total and overall generation wall duration. The remaining difference is not automatically “network time”; it includes other uninstrumented work such as record persistence and scheduling overhead.

A decomposition is useful only when components cover a consistent boundary and do not double-count overlap. In a concurrent pipeline, adding separately measured durations may exceed wall time because work overlaps. The simple timestamp exercise uses a declared sequential decomposition so its arithmetic is exact. Do not generalize that additive assumption to every production trace.

## Percentiles and denominators

Mean latency, median latency and high percentiles answer different questions. A small slow cohort can barely affect the median while dominating p95 or p99. Averaging percentiles across workers generally does not yield the percentile of the pooled request distribution. Preserve the underlying distributions or an appropriate mergeable representation.

Request-weighted metrics and scenario-weighted metrics also differ. If one scenario supplies 90 requests and another ten, pooling requests gives the first scenario nine times the weight. Averaging the two scenario means equally answers a different question. Neither is universally right; the intended estimand determines the denominator.

Report rejected, cancelled, errored and incomplete requests. Measuring only successful short requests can make an overloaded service look excellent. Timeouts censor observed durations, and removing them silently biases a latency summary. A complete report states how each outcome enters the metric and how many observations are excluded.

## Worked case 1: one fully specified timeline

The first case uses arrival zero, model start 0.2, first token 0.5 and completion 1.7, with five output tokens. Queue delay is 0.2, TTFT is 0.5, first-token time after admission is 0.3, TPOT is 0.3 and end-to-end duration is 1.7. The program checks this vector independently.

It then presents a deliberately sequential illustrative decomposition: 0.4 compute, 0.8 transport/storage and 0.5 pacing seconds sum to 1.7. These labels are part of the synthetic fixture. In the live service, measured compute and pacing are explicit, while the rest of wall time is not relabeled as a separately measured network component.

This case is useful when a dashboard reports an unexpected improvement. Check whether a queue interval disappeared from the start timestamp, whether EOS handling changed the denominator, or whether a transport delay was excluded. A faster number can reflect a changed definition rather than a faster system.

## Worked case 2: a hidden slow cohort

The second case contains 90 requests at 0.1 seconds and ten at three seconds. The request-weighted mean is 0.39 seconds, median 0.1 and p95 three. If the two scenarios receive equal weight, the mean becomes 1.55 seconds. Both calculations are valid for their different denominators.

The changed condition shows why a single average can conceal workload composition. A release that receives fewer long prompts may appear faster without any implementation improvement. Compare cohorts or use a fixed representative workload before attributing a change to scheduling or kernels.

```python
"""Latency denominators and arrival-cohort effects from explicit synthetic timestamps."""

import numpy as np


def summarize(arrived, admitted, first, completed, output_tokens):
    if not arrived <= admitted <= first <= completed or output_tokens < 2:
        raise ValueError("Need ordered timestamps and at least two output tokens")
    return {
        "queue": admitted - arrived,
        "ttft": first - arrived,
        "after_admission_first_token": first - admitted,
        "tpot": (completed - first) / (output_tokens - 1),
        "e2e": completed - arrived,
    }


def example_one():
    values = summarize(0.0, 0.2, 0.5, 1.7, 5)
    np.testing.assert_allclose(list(values.values()), [0.2, 0.5, 0.3, 0.3, 1.7])
    print(values)
    compute, transport, pacing = 0.4, 0.8, 0.5
    assert abs(compute + transport + pacing - values["e2e"]) < 1e-12
    print(
        "Wall time",
        values["e2e"],
        "compute",
        compute,
        "transport/storage model",
        transport,
        "pacing",
        pacing,
    )


def example_two():
    fast = np.array([0.1] * 90)
    slow = np.array([3.0] * 10)
    pooled = np.concatenate([fast, slow])
    assert float(np.median(pooled)) == 0.1
    assert float(np.quantile(pooled, 0.95)) == 3.0
    weighted_scenario_mean = (fast.mean() + slow.mean()) / 2
    request_mean = pooled.mean()
    assert abs(request_mean - 0.39) < 1e-12
    assert abs(weighted_scenario_mean - 1.55) < 1e-12
    print(
        "Request mean",
        request_mean,
        "equal-scenario mean",
        weighted_scenario_mean,
        "p50",
        np.median(pooled),
        "p95",
        np.quantile(pooled, 0.95),
    )
    print("Different denominators answer different capacity and user-experience questions.")


def main():
    example_one()
    example_two()


if __name__ == "__main__":
    main()
```

## Profiling without changing the workload accidentally

Start with a correctness-qualified implementation and a bounded reproducible workload. Warm up deliberately, then retain warm-up policy in the report. Record model/tokenizer identity, source version, device, dtype, thread count, prompt/output lengths, arrival pattern, pacing and cancellation settings. These are not incidental details; they define what ran.

A profiler adds overhead and may alter scheduling. Capture enough detail to locate a bottleneck, then measure the intended workload without excessive instrumentation. On accelerators, inspect actual device activities and synchronization. On CPU, inspect thread behavior and contention rather than assuming every operation uses all assigned cores efficiently.

An open-loop load generator schedules arrivals independently of service completion. A closed-loop generator sends the next request after receiving a response. They exercise different queueing behavior. A closed-loop benchmark can reduce offered load when the service slows, hiding the queue growth a real external arrival process would cause. Use the arrival model that matches the question.

Avoid benchmarking against a shared learner service. Use an explicitly disposable project, fixed limits and bounded request counts. Retain evidence rather than repeatedly rerunning successful heavy checks without a changed source or unresolved concern.

## Interview discussion

**Why can TTFT improve while total completion time gets worse?** Scheduling may serve everyone's first step sooner while sharing later decode capacity. Output length, batching and fairness also change the relationship.

**Can you call wall time minus compute time network latency?** Not without instrumentation establishing that the remainder contains only network work. It can include persistence, scheduling, decoding, pacing and synchronization.

**What is wrong with reporting only successful-request p95?** It can exclude the slowest requests that timed out or were rejected. The report must state the population, outcome handling and denominators before the percentile is interpretable.
