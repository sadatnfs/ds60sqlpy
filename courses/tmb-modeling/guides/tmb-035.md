# The inner Newton solver and its controls

Start with: tmb-034, tmb-014.

Outcome: Relate inner-optimizer controls to curvature and numerical failure modes.

The classroom companion runs in the prepared R statistics runtime. It uses base R to expose the mathematics or data contract. Compiling and executing TMB uses the separate [owned project](../projects/tmb-local/README.md); a companion run is not a TMB compiler or rpy2 receipt.

TMB exports `newton`, the generalized Newton optimizer used for its inner problem, and `newtonOption` to inspect or change inner controls for an objective. Their many arguments serve different purposes: iteration and gradient tolerances, step-size controls, trace behavior and modified-curvature search. They are not interchangeable ways to demand “more accuracy.”

An ordinary Newton update solves \(H d=g\) and sets \(u_{new}=u-\alpha d\). For a positive-definite quadratic with an exact solve and \(\alpha=1\), one step reaches the minimum. For an indefinite Hessian, that direction need not decrease the objective. The documented smart-search approach modifies curvature using a quadratic penalty around the current expansion point.

### Worked case A: a stable quadratic step

The companion solves a two-dimensional positive-definite quadratic from a distant start. It prints the original gradient, step and exact optimum. A bounded local refinement after a successful outer fit, as used in our panel example, is justified by this kind of curvature calculation and strict acceptance checks, not by replacing the original optimizer status.

### Worked case B: indefinite curvature

The companion constructs a Hessian with one negative eigenvalue and shows how adding a diagonal shift can make it positive definite. This only stabilizes a local numerical step; it does not prove the unmodified objective has a useful global minimum. Inspect the original function and repeat the numerical analysis after any proposed move.

`newtonOption(obj, ...)` changes the particular model object's inner controls. Save the configuration with fit receipts. The raw `newton` API expects compatible gradient and Hessian functions, often sparse matrices; a teaching wrapper should not pass arbitrary dense or misshaped values and assume the optimizer repairs them.

The native API probe also exposed a representation detail: a diagonal Matrix object did not provide the sparse Cholesky methods expected by the raw helper. The corrected probe uses a symmetric compressed sparse matrix created by `Matrix::sparseMatrix(..., symmetric=TRUE)` and checks the known optimum. Matrix dimensions alone do not establish the required native sparse representation.

### Answered discussion

**Should I set `maxit=1` for speed?** Only for a proven quadratic inner objective with sufficiently accurate linear algebra, not for every latent model. **Can tracing be disabled without losing evidence?** Yes during a routine run if final diagnostics remain recorded; retain detailed traces when diagnosing a failure. **Does a small step imply convergence?** A solver can take small steps because of poor scaling, clipping or an indefinite basin. Check gradient, curvature and actual objective change.

Read [newton and newtonOption](https://cran.r-project.org/web/packages/TMB/TMB.pdf). The function's broad control surface is documented in the inventory; the current project uses a deliberately narrow subset with explicit evidence.

```r
H <- matrix(c(3, .5, .5, 2), 2, 2);b <- c(1, -2);u <- c(8, -7)
g <- drop(H %*% u) - b;step <- solve(H, g);updated <- u - step
print(list(gradient = g, step = step, updated = updated, exact = solve(H, b)));stopifnot(max(abs(updated - solve(H, b))) < 1e-12)
bad <- matrix(c(1, 2, 2, 1), 2, 2)
print(list(original = eigen(bad, symmetric = TRUE)$values, shifted = eigen(bad + 2 * diag(2), symmetric = TRUE)$values))
```
