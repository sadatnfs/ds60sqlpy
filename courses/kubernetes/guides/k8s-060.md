# k8s-060: IPv4, IPv6 and dual-stack Services

## Level and prerequisites

Advanced; about 120 minutes. Direct prerequisites: `k8s-059`. Shared workflow: [study guide](../STUDY-GUIDE.md#networking-extension-boundary).

## Learning objectives

- Build a family-specific acceptance table.
- Review dual-stack security coverage.

## Purpose, vocabulary and mental model

Dual-stack networking supports IPv4 and IPv6 together. It requires compatible cluster configuration, node networking, CNI behavior and service allocation. Adding an IPv6 address to a manifest cannot supply a missing network family underneath it.

A dual-stack Service can have addresses in both families. The order and primary family are meaningful in the API. A client may receive A and AAAA DNS records and choose or race connection attempts according to its library. A successful IPv4 request does not prove IPv6 reachability, and a timeout in one family can affect perceived latency.

IPv6 notation uses colons, so literal addresses in URLs need brackets before a port. Documentation addresses are suitable for examples but are never live targets. Use actual owned assigned addresses only in an explicitly prepared lab.

### Key terms

- **Dual stack:** Running IPv4 and IPv6 together, so Pods and Services can have an address in each family.
- **ipFamilyPolicy:** The Service field choosing SingleStack, PreferDualStack or RequireDualStack.
- **ipFamilies order:** The Service field listing address families. Its first entry is the primary family.
- **AAAA record:** A DNS record that maps a name to an IPv6 address, as an A record does for IPv4.
- **Bracketed IPv6 literal:** An IPv6 address written in square brackets, such as `[2001:db8::10]:8080`, so its colons are not read as a port separator.

## Mechanism and field-by-field reasoning

Service ipFamilyPolicy can express SingleStack, PreferDualStack or RequireDualStack under supported conditions. ipFamilies and clusterIPs describe the requested or assigned families and addresses. RequireDualStack should fail when the cluster cannot satisfy it rather than silently establish a second network.

The supplied course application in docker/kubernetes/fixture.py binds IPv4 only at 0.0.0.0. Therefore dual-stack-service.yaml is an API-design fixture, not a working IPv6 application lab. Before claiming IPv6 acceptance, prepare a separately reviewed listener that actually accepts IPv6 and an appropriate client, in addition to the cluster/CNI capability. Do not infer application-family support from a Service having two allocated addresses. The separate maintained fixture at courses/kubernetes/fixtures/networking/dual-stack/ supplies an AF_INET6 listener with IPV6_V6ONLY disabled, a non-root image, workload/Service example and an explicit-family client. Follow its README for the successful end-to-end path after the owned dual-stack cluster is prepared. It serves /version with ds60-dualstack-v1, while the original fixture serves ds60-fixture-v1.

Check family-specific endpoints, DNS and request paths independently. A NetworkPolicy or firewall rule that covers only IPv4 may leave different behavior for IPv6. Security and observability should cover both intended paths.

## Trace the request or control path

```text
client DNS -> A and/or AAAA -> client family selection
IPv4 Service -> IPv4 endpoint path
IPv6 Service -> IPv6 endpoint path
each path needs independent routing and policy acceptance
```

The first line is a client decision: DNS may return A and AAAA records and the client picks a family, often IPv6 first. The next two lines are independent paths, each with its own Service address, endpoints and routes. The last line is the point of the lesson: one family passing tells you nothing about the other, including policy coverage.

## Worked example / walkthrough

### Worked example 1: Read a dual-stack intent

This is a manual-only Service fragment.

```yaml
ipFamilyPolicy: RequireDualStack
ipFamilies: [IPv4, IPv6]
```

**Expected observation:** The cluster must support both families; the declaration does not install that support.

## Six progressive exercises

### Exercise 1: Predict a RequireDualStack request on a single-stack cluster.

**Expected evidence:** The intended requirement cannot be satisfied.

**Progressive hint:** What does RequireDualStack demand of the cluster, and what can the API server do if it cannot comply?

### Exercise 2: Distinguish A and AAAA records.

**Expected evidence:** IPv4 addresses versus IPv6 addresses.

**Progressive hint:** Each record type carries one family. Which one holds the longer address written with colons?

### Exercise 3: Build a family-specific acceptance table.

**Expected evidence:** DNS, Service, endpoints, policy and app response for both families.

**Progressive hint:** Make two columns, one per family, and fill DNS, Service, endpoints, policy and response separately.

### Exercise 4: Diagnose IPv4 success with IPv6 timeout.

**Expected evidence:** Inspect the IPv6 route, listener, endpoints and policy path.

**Progressive hint:** IPv4 works, so the app runs. Check the IPv6 leg: route, endpoint address, listener family and policy.

### Exercise 5: Explain bracketed IPv6 URL syntax.

**Expected evidence:** Brackets delimit the address before a colon-prefixed port.

**Progressive hint:** An IPv6 address already contains colons. How would a URL parser find the port without a delimiter?

### Exercise 6: Review dual-stack security coverage.

**Expected evidence:** Intended allow/deny rules and observations cover both families.

**Progressive hint:** Read every ipBlock in your policies. Does each one have a twin for the other family?

## Diagnosis, failure boundaries and common mistakes

The supplied network-study app binds IPv4 only, so creating network-study-dual and seeing an IPv6 ClusterIP is not success; IPv6 requests reach no listener. Use the separate dual-stack fixture when you need a real IPv6 response. Another mistake is testing one family and filling both rows, when a client that prefers IPv6 may be the only one failing. Policies are often written with IPv4 ipBlocks only, leaving IPv6 open or blocked by accident. Finally, typing an IPv6 address into a URL without brackets makes the last group look like a port.

Before concluding, record:

- The Service `ipFamilies` and `ipFamilyPolicy`, and whether a RequireDualStack request was accepted or rejected.
- Separate A and AAAA answers for the Service name; one row never stands in for both families.
- The app's listener bind address: 0.0.0.0 alone serves IPv4, while :: may also serve IPv6.
- IPv6 test URLs written with brackets, such as `http://[2001:db8::10]:8080/`, so the port parses correctly.

General evidence rules: [diagnosis rules](../STUDY-GUIDE.md#diagnosis-rules).
