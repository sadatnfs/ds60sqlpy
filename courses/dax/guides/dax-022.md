## The question and the mechanism

Locate a variable's binding context and avoid repeating one total for every member.

A variable outside an iterator can hold one scalar for the entire iterator. A variable declared in the iterator's expression can be bound separately for each row. The difference is easy to miss when both variables are named Revenue. Use names that expose whether the value is a global total, an incoming-context total or a current-member result.

With no filters, a variable bound to [NetRevenue] is 187. Summing that value once per Product row yields 748 because Product has four rows. Defining the variable inside SUMX(Product,...) instead invokes the measure for each row, giving 67,24,96 and BLANK, which sum to 187.

Outer filters still matter before either binding. In Paper there are two Product rows and the incoming total is 91. A shared scalar is repeated twice to give 182, while per-product binding sums 67 and 24 to 91. A variable can improve readability without preserving the intended meaning if moved across an evaluation boundary.

## Vocabulary and expression anatomy

The first named variable is outside SUMX; the second is declared after the iterator's table argument, inside its scalar expression. RETURN ends that inner variable block. This is a scope distinction, not a mutable assignment updated by each loop iteration.

Concepts to explain in your own words: **variable scope**, **iterator body**, **implicit transition**, **shared scalar**.

## Worked cases

The following query-local declarations are shared by these cases. They do not create persisted measures in this classroom.

```dax
DEFINE
    MEASURE Sales[NetRevenue] = SUM ( Sales[NetAmount] )
```

### Case A: One shared total versus one value per product

**Starting context:** No outer filters; four Product rows, including unsold Bag.

```dax
EVALUATE
VAR IncomingRevenue = [NetRevenue]
RETURN ROW ( "SharedScalarSum", SUMX ( Product, IncomingRevenue ), "PerProductSum", SUMX ( Product, VAR ProductRevenue = [NetRevenue] RETURN ProductRevenue ) )
```

**Context trace:**

1. IncomingRevenue is bound once to 187.
2. The shared scalar contributes 187 on four iterations, totaling 748.
3. The inner measure binding transitions each product and sums 67 + 24 + 96 = 187.

**Hand-derived worked-reference result:**

| SharedScalarSum | PerProductSum |
| --- | --- |
| 748 | 187 |

The shared value is not blank for Bag because it was never evaluated for Bag. Variable movement can therefore change both population and missing-value behavior.

Hand-derived for the named reference and fixture. Editing a draft does not recalculate this table.

### Case B: An incoming filtered total is still shared

**Starting context:** Paper is established before either variable binding; Product has two eligible rows.

```dax
EVALUATE CALCULATETABLE ( VAR IncomingRevenue = [NetRevenue] RETURN ROW ( "SharedScalarSum", SUMX ( Product, IncomingRevenue ), "PerProductSum", SUMX ( Product, VAR ProductRevenue = [NetRevenue] RETURN ProductRevenue ) ), Product[Category] = "Paper" )
```

**Context trace:**

1. The incoming measure total is 91.
2. An outer scalar is reused for Notebook and Pen, giving 182.
3. Binding inside the iterator evaluates 67 and 24 separately, totaling 91.

**Hand-derived worked-reference result:**

| SharedScalarSum | PerProductSum |
| --- | --- |
| 182 | 91 |

Context is not simply filtered versus unfiltered. The exact point at which a scalar is bound determines which filtered total gets repeated.

## Progressive hints

1. Home has one Product row.
2. The shared scalar contributes on every dimension row.
3. Only the denominator should be shared; the numerator should vary per member.
4. Readability does not override evaluation scope.
5. VAR is a binding within expression scope.
6. Distinguish an invariant target from per-member weights.
