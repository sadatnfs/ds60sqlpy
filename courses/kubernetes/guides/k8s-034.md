# k8s-034: Traffic changes and progressive delivery

## Level and prerequisites

Advanced; about 135 minutes plus review. Direct prerequisites: `k8s-013`, `k8s-021`, `k8s-027`.

## Learning objectives

Design a release gate from application evidence instead of replica count alone.

## Vocabulary and concepts

A rollout creates or replaces workload replicas; a traffic change determines which ready backends receive requests. Those operations are related but different. A Deployment can finish creating a candidate while the Service still selects only the stable release. Conversely, broadening a selector can send requests to a candidate before the team has collected the intended application evidence.

The host fixture has hello-stable and hello-candidate Deployments with distinct release labels. Both use the same preloaded 0.2 image, but /message returns hello or reviewer through a fixed environment value. This is a configuration-release rehearsal. It does not demonstrate a binary image upgrade, and /version remains the legacy fixture version string for both. A real two-image rehearsal requires separately qualified, preloaded image identities.

A release gate states what must be true before changing traffic and what triggers rollback. For this small fixture, require the expected candidate marker, zero unexpected payloads and zero errors in a declared finite request sample. That sample is evidence about the observed requests, not a proof of all future behavior or an exact traffic-share guarantee.

### Key terms

- **Canary release:** Sending a small, measured share of traffic to a new version before shifting the rest.
- **Weighted routing:** Splitting traffic between versions by explicit weights, which requires a separately qualified traffic implementation rather than replica counts.
- **Release label:** A Pod label, such as release=stable, that lets a Service selector choose one version.
- **Release gate:** A stated condition, measured from application evidence, that must hold before changing traffic.
- **Selector change:** Editing a Service selector to point at a different set of Pods, which switches traffic quickly and must be reversible.

## Compare rolling and two-version selection

A rolling Deployment update gradually changes replicas under one controller. Old and new Pods may coexist while readiness controls endpoint eligibility. The update strategy bounds replacement behavior, but it does not by itself evaluate whether the new application gives correct answers.

The two-Deployment fixture makes traffic selection explicit. Service hello starts with selector app=hello, release=stable. The candidate has matching app but a different release label, so it is excluded. Changing the release selector to candidate is a coarse cutover; a reviewed host operation must preserve Service identity and handle concurrent edits rather than replacing an unrelated object.

A canary exposes a subset of traffic to the candidate. Simply having one candidate Pod and one stable Pod does not prove a 50 percent request split. Connection reuse, endpoint selection, client behavior and topology can affect finite samples. Weighted routing requires a separately qualified traffic controller; the current browser adapter has none.

## Build an application release gate

Before cutover, probe the candidate through the host's fixed path and record message marker, error count, sample size and latency summary. A Ready Pod only says its probe passed. The marker confirms which configuration answered, while a schema or business assertion confirms whether the answer is acceptable.

After the selector change, collect another bounded sample through the ordinary Service. Record the Service UID, resourceVersion and selected endpoint identities. A candidate marker from a direct Pod check does not prove Service traffic moved. Mixed markers during a transition need an explanation based on actual connections and endpoints, not an assumed instantaneous global switch.

Rollback should restore the last verified selector or desired state through a conditional, identity-checked operation. Then verify the stable marker through the Service. Deleting the candidate without restoring a selector that points to it can leave the Service with no endpoints. Cleanup order therefore belongs in the runbook.

## Worked example / walkthrough

### Worked example 1: Trace Service selection

```yaml
apiVersion: v1
kind: Service
metadata:
  name: hello
spec:
  selector:
    app: hello
    release: stable
  ports:
    - name: http
      port: 8080
      targetPort: http
```
hello-stable has app=hello, release=stable. hello-candidate has app=hello, release=candidate.

**Expected:** Only the stable backend matches this selector, regardless of whether the candidate is Ready.

### Worked example 2: Evaluate a candidate and rollback

Synthetic candidate sample: reviewer, reviewer, ERROR, reviewer. The gate requires four valid reviewer responses and zero errors. It fails. Restore stable selection, then observe hello, hello, hello, hello through the Service.

**Expected:** The candidate is rejected; the four stable responses establish the finite rollback observation, not an unlimited future guarantee.

## Exercises

### Exercise 1: Distinguish binary and configuration versions

Compare /version with /message in both fixture Deployments.

**Expected result/shape:** Same binary version; different synthetic configuration markers.

**Verify:** Request `/version` and `/message` from each Deployment's Pods and compare the two responses separately.

**Progressive hints:** The image field is identical.

### Exercise 2: Predict selected backends

Apply the stable selector to the two Deployment label sets.

**Expected result/shape:** Stable matches and candidate does not.

**Verify:** Compare each Deployment's Pod template labels with every key-value pair of the selector.

**Progressive hints:** Selectors combine their key-value requirements.

### Exercise 3: Predeclare the release gate

Specify marker, sample size, error rule and bounded request deadline.

**Expected result/shape:** A concrete gate that can fail independently of Ready replicas.

**Verify:** Check that the gate has numeric thresholds and can fail while every replica is Ready.

**Progressive hints:** Use application observations, not only Kubernetes counts.

### Exercise 4: Reject the failing candidate

Evaluate a new candidate sample, reviewer, reviewer, reviewer, TIMEOUT, where the fourth request ran past the declared deadline, against the four-response gate.

**Expected result/shape:** Failure: only three valid responses arrived within the deadline; do not proceed to promotion.

**Verify:** Count all four attempts against the gate threshold, including the timed-out one.

**Progressive hints:** A late response counts as an error, not as a pass.

### Exercise 5: Restore and verify stable traffic

Use the conditional host selector repair, then sample the ordinary Service.

**Expected result/shape:** Correct Service identity and four observed hello responses.

**Verify:** Confirm that the Service UID matches the original and that four samples return the expected stable marker.

**Progressive hints:** Removing a candidate is not the same as restoring a route.

### Exercise 6: Explain ratio and evidence limits

Compare one-to-one replica counts with an uneven finite request sample.

**Expected result/shape:** Replica ratio does not establish an exact traffic ratio or production reliability.

**Verify:** Name one mechanism, such as connection reuse or a small sample, that makes request counts differ from the replica ratio.

**Progressive hints:** Connections and routing policy affect samples.

## Self-check

The candidate returned three of four valid responses within the deadline. Why does the gate reject it even though every candidate Pod was Ready, and what rollback evidence do you record?

## Common pitfalls

The two markers represent different configuration values in the same binary. Keep that distinction visible in the release packet. A successful finite sample cannot establish production capacity, error probability zero or exact canary ratios.

If the candidate fails, retain its observations and restore the verified path. Do not loosen the gate after seeing a failure merely to label the release successful. Predeclare acceptable conditions and record any later policy revision as a separate decision.

## Networking depth supplement

A load balancer distributes traffic among eligible destinations. It does not replicate application state, authenticate every business action or guarantee a valid certificate. Kubernetes Service type LoadBalancer requests an implementation-managed entrypoint; a local cluster without a prepared load-balancer controller may legitimately leave external status pending.

Some implementations route through node ports, while others can select Pod backends directly. Source-address preservation, health checks and failover differ with that design. Record the actual controller and traffic policy before interpreting an application's observed client address. `k8s-052` and `k8s-056` develop these distinctions.

Scaling increases process capacity only when routing and shared-state semantics support it. A process-local lock does not serialize writes across replicas. Network acceptance and data correctness remain separate checks, especially when a rollout changes several backends while clients retain long-lived connections.
