# k8s-023: Gateway, Ingress and the external route

## Level and prerequisites

Intermediate; about 120 minutes plus review. Direct prerequisites: `k8s-013`, `k8s-017`, `k8s-020`.

## Learning objectives

Distinguish an internal Service from a host-facing HTTP route and the controller that implements it.

## Vocabulary and concepts

A Service provides an internal backend abstraction; an ingress or gateway controller can expose selected routes through a managed listener. Gateway API separates infrastructure ownership, listener configuration and application route attachment. Creating an HTTPRoute object does not install a controller or create a working external address.

This host lab requires a preinstalled qualified Gateway controller, a host-owned Gateway named lesson-gateway, an owned Service backend and a loopback-only listener. A synthetic TLS case also needs a verified local trust chain and hostname. The normal browser adapter provides none of those cluster/controller operations and does not accept Gateway or Ingress resources.

The real HTTPRoute example matches host lesson.example.test and path prefix /version, then forwards to `hello:8080`. It leaves other paths unmatched. The Ingress comparison is a separate fixture with its own ingressClassName; do not assume the two APIs are interpreted by the same controller or apply both to an unreviewed listener.

### Key terms

- **Ingress:** An API object with host and path rules that an Ingress controller uses to route external HTTP traffic to Services.
- **Gateway API:** A family of role-oriented routing APIs, including GatewayClass, Gateway and HTTPRoute, that expresses more than Ingress can.
- **Gateway:** An object that requests listeners, such as a port and protocol, from the implementation named by its GatewayClass.
- **HTTPRoute:** A Gateway API object that attaches to a Gateway and matches HTTP requests by host, path or header to backend Services.
- **TLS verification:** Checking the presented certificate against a trusted CA and the requested hostname. A TCP connection or HTTP response alone does not establish the TLS contract.

## Follow Gateway ownership and route status

GatewayClass identifies a controller/infrastructure class and is cluster-scoped. A Gateway selects that class and defines listeners. HTTPRoute attaches through parentRefs and describes request matches and backends. The parent's allowedRoutes policy can restrict which namespaces may attach.

Inspect the route's parent-specific Accepted and ResolvedRefs conditions and their observed generation. A syntactically valid backend reference can still be unresolved or unauthorized. Cross-namespace references may require an explicit ReferenceGrant rather than being permitted by a matching name. The host must provide that capability deliberately; the learner should not widen it during diagnosis.

A positive status is necessary controller evidence, but a bounded client request must still prove routing and payload. A controller can accept a configuration before the data plane is ready, or a backend can be unready.

## Test path, host and TLS independently

For the positive case, connect through the loopback listener using the intended host and /version path. Verify the synthetic certificate against the provided CA and hostname when TLS is enabled. A successful TCP connection or HTTP response obtained by disabling certificate checks does not establish the TLS contract.

An unmatched path should produce the controller's expected no-route behavior, while a matching route should return the fixture's exact version body. A wrong hostname can select another listener/route or fail TLS verification. Record which layer failed rather than calling every negative result an application error.

The ordinary fixture client is HTTP-only and targets hello internally. It cannot prove the external TLS path. A separately qualified host client is required, with its CA file and loopback address from the owned receipt. No public load balancer or external IP is assumed.

## Worked example / walkthrough

### Worked example 1: Read the HTTPRoute

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: hello-route
spec:
  parentRefs:
    - name: lesson-gateway
  hostnames:
    - lesson.example.test
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /version
      backendRefs:
        - name: hello
          port: 8080
```

**Expected:** The route attaches to lesson-gateway for lesson.example.test and forwards `/version` to `hello:8080`.

### Worked example 2: Compare accepted and delivered

Synthetic status: Accepted=True, ResolvedRefs=True for the current generation. A matching client still receives 503 because the backend has no ready endpoints.

**Expected:** Route acceptance and reference resolution do not establish backend application readiness.

### Exercise 1: Draw the ownership layers

Connect GatewayClass, Gateway, HTTPRoute, Service and Pods.

**Expected result/shape:** Controller/listener ownership is separated from the application route and backend.

**Verify:** Mark each object cluster-scoped or namespaced and name who manages it: the controller, the platform owner or the application team.

**Progressive hints:** Identify cluster-scoped versus namespaced objects.

### Exercise 2: Read matches and references

Inspect host, path prefix, parent and backend port.

**Expected result/shape:** lesson.example.test, /version, lesson-gateway, hello 8080 are the declared contract.

**Verify:** Read each value from its HTTPRoute field (`hostnames`, `matches[].path`, `parentRefs` and `backendRefs`) rather than from the diagram.

**Progressive hints:** A reference name is interpreted within its API/namespace rules.

### Exercise 3: Inspect current conditions

Compare Accepted/ResolvedRefs with observed generation.

**Expected result/shape:** Current parent-specific conditions support configuration acceptance, not final delivery alone.

**Verify:** Confirm that each condition's `observedGeneration` equals the route's `metadata.generation` and identify the parent that reported it.

**Progressive hints:** Check which parent/controller produced the status.

### Exercise 4: Verify matching and unmatched requests

Use the qualified loopback client for /version and an unmatched path.

**Expected result/shape:** Expected version response on the match; documented no-route result on the negative path.

**Verify:** Send both requests with an explicit Host header and record status and body; the unmatched path must not reach the hello backend.

**Progressive hints:** Keep host header/hostname and path explicit.

### Exercise 5: Verify synthetic TLS correctly

Use the host-provided CA/hostname and test a mismatched identity.

**Expected result/shape:** Valid chain/hostname succeeds; wrong identity fails without an insecure bypass.

**Verify:** Verify with the supplied CA and the expected hostname; the wrong-identity case must fail certificate verification rather than be skipped with an insecure flag.

**Progressive hints:** Transport encryption and certificate identity are both part of the claim.

### Exercise 6: Compare Ingress and cleanup scope

Review the separate Ingress fixture and name what is independently required.

**Expected result/shape:** Qualified ingressClass/controller plus exact route cleanup; no assumption of API interchangeability.

**Verify:** List what the Ingress needs that the Gateway fixture does not provide, and confirm that cleanup names exact route UIDs.

**Progressive hints:** An API kind does not identify every implementation behavior.

## Self-check

hello-route shows Accepted and ResolvedRefs true, yet requests to lesson.example.test return 503. Which layer is failing, and why do route conditions not prove the backend can serve?

## Common pitfalls

A Kubernetes API object is not a running controller. An Ingress class or GatewayClass name must correspond to an installed, qualified implementation. A Service of type ClusterIP does not expose a host port by itself.

Keep listener ownership and cleanup separate from the namespaced route. The learner should remove only its recorded route UID unless the host capability explicitly owns the Gateway/controller lifecycle. Never disable TLS verification or install a remote controller automatically to make the example pass.

## Networking depth supplement

An HTTP routing resource needs an implementation. Ingress requires a selected controller; Gateway API requires supported APIs and a compatible GatewayClass/controller. A route object alone does not create an external listener, assign a usable public address or provision TLS. `k8s-051` through `k8s-055` trace those responsibilities separately.

A complete request path includes caller DNS, external routing, listener/TLS identity, host/path matching, Service port, eligible endpoint and application route. A matched prefix rule can still produce an application 404 if the upstream receives a path it does not implement. Path rewriting is an explicit implementation feature, not a universal effect of a matching rule.

Gateway status conditions distinguish attachment acceptance, reference resolution and data-plane programming. They help localize control-plane failures but still need an actual request to qualify behavior. Cross-namespace references and allowed route attachment are authorization boundaries; do not broaden them to make a sample appear accepted.
