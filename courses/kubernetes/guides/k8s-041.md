# k8s-041: Recovery objectives and reviewable runbooks

## Level and prerequisites

Advanced; about 150 minutes plus review. Direct prerequisites: `k8s-036`, `k8s-037`, `k8s-040`. The chapter separates desired configuration, API acceptance, controller observation and application evidence.

## Learning objectives

Measure a recovery objective with both service and data evidence.

## Vocabulary and concepts

A recovery objective is a target, and a recovery measurement is an observation. Recovery Time Objective, or RTO, sets an acceptable duration for restoring the defined service. Recovery Point Objective, or RPO, sets an acceptable data-loss window. A drill must define start, finish and data reference points before it can compare observations with those objectives.

For this synthetic drill, interruption begins at 12:00:00Z. The application and independently restored marker both pass at 12:01:30Z, giving90 seconds of observed recovery time. The source's last durable marker was timestamped11:59:50Z, while the latest restored durable marker is11:59:30Z, giving a 20-second loss boundary under this example's timestamp assumptions. With targets120 seconds and30 seconds, these observed measures meet the two targets.

These calculations do not establish database transaction consistency or prove that no record outside the markers was lost. The immutable marker fixture makes a narrow data contract measurable. A Ready Pod at 12:00:40Z is an intermediate milestone, not the finish when the marker and ordinary service path are still unverified.

## Define clocks, milestones and units

Use UTC timestamps with explicit offsets or a monotonic elapsed timer for duration measurements. Do not subtract mixed local time strings across a daylight-saving transition. Record whether the start is fault injection, detected impact or incident declaration; these choices produce different measures. The runbook must choose one definition and keep it consistent.

Finish means the declared application and data acceptance criteria have both passed. Pod scheduling, Ready state, successful restore command and open TCP port can be useful intermediate milestones, but none automatically satisfies the whole service contract. If data verification finishes after application reachability, the later required check determines the measured finish.

For the RPO example, compare the source last durable data point with the restored last durable point. The difference estimates the data-loss time boundary for the represented sequence. Backup completion time alone can be misleading: a backup finishing at noon may contain data only through an earlier point. Data lineage and durability semantics matter.

## Write a runbook another person can execute

A reviewable runbook names the exact owned target, required host capabilities, inputs, operation order, expected observations, stop conditions and rollback/cleanup. It distinguishes privileged host steps from learner observations. Each step should explain why it exists, so a missing prerequisite is diagnosed rather than bypassed.

The negative control deliberately omits the independent marker verification. The application responds and the Pod is Ready, but the finish gate remains false. This tests whether the runbook can reject an attractive incomplete result. A runbook that records success at the first green signal is measuring a narrower objective than it claims.

During a live drill, preserve actual timestamps and failed attempts. Do not replace observed durations with the planned schedule. If the host lease expires or a required backup is unavailable, stop and report the missing evidence. Renewing a lease or reprovisioning a destination is a new controlled operation, not an invisible continuation under stale credentials.

Start 12:00:00Z; finish 12:01:30Z gives90 seconds. Source durable point11:59:50Z; restored durable point11:59:30Z gives20 seconds. Targets are RTO120 seconds and RPO30 seconds.

**Expected:** Observed90<=120 and20<=30 meet the stated synthetic targets, assuming the milestone and durability definitions are valid.

### Worked example 2: Reject a missing verification step

At second 40 the Pod is Ready. At second 60 the service responds. The marker hash has not been read. The finish predicate requires service_ok and data_ok, so the drill remains incomplete.

**Expected:** No finish time is claimed until both required observations exist. Ready or service success alone cannot close the data recovery objective.

## Common pitfalls

Meeting an objective once is a useful rehearsal result, not a guarantee that every future incident will recover within the same duration. Report the tested fault, data size, environment and operator procedure. Repeatability and broader failure coverage require additional independent drills.

Do not export private backups or credentials to make the evidence packet self-contained. The packet can include synthetic marker hashes, timestamps, operation receipts and protected backup references while leaving sensitive payloads under the host's access and retention policy.
